The stable-diffusion.cpp image engine is retired — nobody was running it — and the OpenAI
Images client that used to be welded to it stays, generalized and renamed `openai-compat`, so
any OpenAI-compatible image server can be declared as a row.

### New

- **An `external` or `remote` row can now point at any OpenAI-compatible image server.**
  Declare it once, with `provider: "openai-compat"`:

  ```json
  {"key":"oai-image","api":"images","provider":"openai-compat",
   "url":"http://<host>:<port>","health":"/v1/models","lifecycle":"external"}
  ```

  The row's `model` is sent only when the row names one — leave it out and nothing is sent,
  exactly as before. Sizes come from the row too; nothing is guessed from a model name anymore.
  A bearer token, if the server wants one, reads from `AF_ENGINE_API_KEY_<KEY>`, where `<KEY>`
  is the row's `key` upper-cased **with every character that isn't a letter or digit turned
  into `_`** — the row above (`"key":"oai-image"`) reads its bearer from
  `AF_ENGINE_API_KEY_OAI_IMAGE`, not `AF_ENGINE_API_KEY_OAI-IMAGE` (a hyphen is not a legal
  shell variable character). **This path is declared and tested against this project's own
  test double, not against a real OpenAI-compatible server** — nobody has pointed it at one
  yet, so treat it as unverified until you have.

### Improved

- **A row whose `provider` this build cannot serve no longer disappears quietly.** Before, a row
  still declaring `sdcpp` just meant `generate_image` fell out of `tools/list`, with no error and
  no mark anywhere. Now the Control Plane logs one line per such row at load, and the **"Inference
  engines"** admin screen (not the neighboring "Inference engine models" screen) marks the row and
  names the provider it is stuck on.

### Fixed

- A managed session's turn could fail and still be reported as a completed answer waiting on
  you. That race is closed.

### Upgrade notes

- **`ImageEngine` now only accepts `comfy`.** The two parameters that only ever meant something
  to the retired engine, `ImageImageTag` (its ECR tag) and `ImageExtraArgs` (its `sd-server`
  flags), are gone — `deploy` refuses either key now. `ImageComfyImageTag` is unrelated and
  stays; don't confuse the two when editing a parameter file. The `EcrSdcpp` ECR repository and
  its 2.31 GB image are also gone.
- 🔴 **Update `60-engines` before `20-platform`, for this one release only** — the reverse of
  `update.sh`'s usual order. `60-engines` used to import an export (`EcrSdcppUri`) that
  `20-platform` no longer produces after this release; updating `20-platform` first would try to
  delete an export CloudFormation still sees in use, and roll back. `update.sh` checks for this
  itself: if your `60-engines` stack still imports `EcrSdcppUri`, it stops before touching
  anything and prints the exact `aws cloudformation deploy` command to update `60-engines` alone
  first. Run that command, then re-run `update.sh` as usual.
- **A stack still carrying `ImageEngine=sdcpp` is repaired for you.** `update.sh` overwrites a
  live stack's `ImageEngine` to `comfy` before deploying (`ImageEngine`'s allowed values
  narrowed, so the old value would otherwise fail validation); `standup.sh` drops the same value
  from a captured parameter file so the template's `comfy` default applies. Neither script
  requires anything from you beyond running them normally.
- A deployment already on `ImageEngine=comfy` has nothing to do.

Agent CLI pins are unchanged from 0.20.0.
