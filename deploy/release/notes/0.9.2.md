A follow-up to the EC2-backed persistent workspaces of 0.9.0, from running one as a real
deployment. A home created from the pre-baked *golden* snapshot could not start at all —
the task restarted forever and no log said why — and baking a golden by hand ran into a
step that never completes. Keeping the golden in step with the workspace image is no
longer a promise somebody has to remember: the Control Plane does it, and refuses to
publish a golden it could not boot.

### New

- **The Control Plane re-bakes the golden snapshot when the workspace image changes.**
  Re-baking used to be a manual step tied to each release, and the only sign that it had
  been forgotten was a warning repeating in the log. The Control Plane already made that
  judgement — it refuses a golden baked from a different image — so it now acts on it: it
  boots a reserved seed through the ordinary Start path, captures that home as a
  candidate, boots a second reserved member from the candidate, and publishes it only once
  that one has come up. A candidate that will not boot is kept and marked rejected with
  the reason, because a golden that cannot start looks like a success everywhere else and
  breaks for the next new user instead. The bake will not begin while the pool has fewer
  than two free slots, and it gives up on an image after two failed candidates; the pool
  panel says which of the two is happening. `AF_ECS_EC2_GOLDEN_AUTOBAKE=0` switches it off
  and makes the bake yours again.

### Fixed

- **A home created from a golden snapshot never started — the task restarted forever.**
  The entrypoint moves the sign-in state onto the always-available *keep* volume, and it
  skipped creating the destination directory whenever the link already pointed the right
  way. A golden home arrives with the seed's links already in place, while a brand-new
  user's keep volume is empty, so `~/.config` pointed at nothing that existed; the
  `mkdir -p ~/.config/opencode` that follows then failed with `File exists` and took the
  entrypoint down with it. The only symptom was the restart loop — no log named the cause.
  An empty home could never hit it, so it appeared exactly where a deployment starts
  serving new users from a golden.
- **A workspace whose Start failed before its home volume existed was retried once a
  minute, forever.** How long such a placeholder may live was measured from the volume's
  creation time, so a workspace row created without one — no free slot, out of capacity,
  an error from AWS — had no clock to expire against and nothing ever cleaned it up.
  Expiry now falls back to the workspace's own creation time.
- **Baking a golden by hand could not be finished as documented.** The procedure said to
  stop the workspace and wait for the sweeper to release the slot, but Stop deliberately
  leaves the home attached and the sweeper only stops the instance — so `bake-golden.sh`
  refused the slot no matter how long you waited, and asked you to do what you had just
  done. It now refuses a slot only while its instance is *running*; a stopped one is safe
  to capture, for the same reason the pool already relies on (an ordinary shutdown
  unmounts the filesystem). The instructions around it were corrected against measurement
  as well: the wait scales with the blocks actually used, so a home that has only paid
  boot-install is under three minutes even on a 50 GiB volume (the "30-40 minutes" figure
  belonged to hibernation snapshots); a seed has to be a member who can sign in; and no
  repository may be cloned into the seed, since `~/repos` sits on the home and would be
  handed to every new user.

### Upgrade notes

No migration, and nothing to do outside an `ecs-ec2` deployment. There the automatic bake
is on from this release, so after you move the image tag expect the Control Plane to spend
two pool slots over the following minutes baking a golden and proving it boots. Until it
finishes, a new user's home is built empty — a slow first start, the same as before the
golden existed — because a golden baked from the previous image is refused rather than
used.
