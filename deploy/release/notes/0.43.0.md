The Control Plane now refuses to start on a weak `AF_MASTER_KEY` or `AF_COOKIE_SECRET`, and signs
cookies with one key per purpose by default. Read the Upgrade notes before updating.

### Improved

- **The Control Plane will not start with a weak `AF_MASTER_KEY` or `AF_COOKIE_SECRET`** under
  `AUTH=oauth` or `AUTH=proxy`. The message names the variable (never its value) and points at the
  operator guide, "The deployment keys". `AUTH=dev` is unaffected.
  ([#3552](https://github.com/k-k1/agent-fleet/issues/3552))
- **Cookies are signed with one key per purpose by default**, so a cookie made for one purpose never
  verifies for another. Cookies issued by 0.42.0 stay valid for one session lifetime, so nobody is
  signed out. ([#3552](https://github.com/k-k1/agent-fleet/issues/3552))

### Upgrade notes

- **Before updating, check both keys.** A value is weak when it is under 32 bytes of key material
  (hex or base64 that decodes to fewer than 32 bytes, or a raw string under 43 characters) or is a
  repeated pattern. Replace a weak `AF_COOKIE_SECRET` with `head -c 32 /dev/urandom | base64`;
  everybody signs in once more. **A weak `AF_MASTER_KEY` cannot simply be swapped:** values sealed
  under it stop opening. Plan the move first (operator guide, "The deployment keys" and "Keys at
  rest"), because this release will not start on it. `deploy/aws/ecs/standup.sh` reports short
  stored values without printing them.
- **Update to 0.42.0 first.** A replica older than 0.42.0 cannot read the new cookie format, so
  updating straight from an older release signs people out whenever a request reaches an old
  replica.
- **To keep the old cookie format for one more release**, set `AF_COOKIE_PURPOSE_KEYS=0` (ECS:
  `CookiePurposeKeys=0`). The opt-out and the old format are removed in a later release.
  ([#3552](https://github.com/k-k1/agent-fleet/issues/3552))
