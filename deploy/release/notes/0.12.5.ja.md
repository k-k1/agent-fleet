`ecs-ec2` の配備で、載っているマシンが壊れた Workspace を起動し直せなくなる不具合を
直しました。健全なマシンへ自動で移すようになり、1 つの Workspace がマシンごと巻き込んで
落とすこともなくなります。

### Improved

- **Workspace が、載っているマシンを飢えさせられなくなりました**（`ecs-ec2`）。
  Workspace のメモリ上限をスロットより少し低くし、マシンを管理しているソフトウェアのぶんを
  残すようにしました。1 つの Workspace が使えるだけ使っても、マシンが自分ごと——そして
  本来なら復旧してくれるはずの仕組みごと——固まることはなくなります。Console には
  Workspace が実際に使える量を、マシンの容量と並べて出します（`6.4 GiB（箱 8 GiB）`）。
  上限に達したときも、黙って終わるのではなく理由が分かるようになります。
- **スロットプールが、限界まで酷使されているマシンを知らせられるようになりました。**
  プールのスタックに `PoolAlarmEmail` を設定すると、スロットのディスクが 15 分間
  飽和したときに CloudWatch からメールが届きます。設定しなければ何もしません。

### Fixed

- **Workspace が「起動しようとするたびにタイムアウトする」状態から抜け出せなくなることが
  ありました**（Console では `504` が出続けます）。Workspace が載っているマシンが、AWS から
  見ると健全なまま応答しなくなったときに起きます。起動処理が二度と戻らないマシンを待ち続ける
  ため、何度試しても直りませんでした。数分待っても駄目なマシンは見切って理由を記録した上で
  切り離し、別のマシンで Workspace を起動するようにしました。home のディスクはそのまま移り、
  利用者が起動ボタンを押し直す必要もありません。移す先も見つからない場合は、待たせ続けずに
  `stopped` に戻して再試行できるようにします。

### Upgrade notes

`ecs-ec2` の Workspace は、載るマシンより少しだけ小さいメモリ上限で動くようになります
（マシン側を管理可能に保つためです）。8 GiB のスロットなら Workspace は 6.4 GiB です。
以前の挙動に戻すには ingress スタックで `Ec2HostReserveMb=off` を設定してください。
各 Workspace の次の起動から反映されます。
