On `ecs-ec2` deployments, a workspace whose machine had failed could not be started
again. Agent Fleet now moves it to a healthy machine on its own, and keeps one workspace
from taking its machine down with it.

### Improved

- **A workspace can no longer starve the machine it runs on** on `ecs-ec2`. Its memory is
  now capped below the slot's, leaving room for the software that manages the box, so one
  workspace using everything it can no longer freezes the machine for itself and for the
  system that would otherwise recover it. The Console shows the number a workspace can
  actually use with the machine's beside it — `6.4 GiB (of 8 GiB)` — and reports when a
  workspace hits that ceiling instead of leaving it a mystery.
- **The slot pool can raise an alarm when a machine is being driven into the ground.**
  Set `PoolAlarmEmail` on the pool stack and CloudWatch mails you when a slot's disk has
  been saturated for fifteen minutes. Off unless you set it.

### Fixed

- **A workspace could get stuck with every start attempt timing out** (a `504` in the
  Console, indefinitely) on `ecs-ec2`. This happened when the machine hosting the
  workspace stopped responding while still appearing healthy to AWS — starting the
  workspace waited for a machine that was never coming back, and no amount of retrying
  helped. Agent Fleet now gives up on such a machine after a few minutes, takes it out
  of service with the reason recorded on it, and starts the workspace on another one.
  The home disk is moved across intact, and the person does not have to press start
  again. If no healthy machine can be found either, the workspace returns to `stopped`
  so it can be retried, rather than hanging.

### Upgrade notes

Workspaces on `ecs-ec2` get slightly less memory than the machine they land on, so that
the machine stays manageable. An 8 GiB slot gives its workspace 6.4 GiB. Set
`Ec2HostReserveMb=off` on the ingress stack to keep the old behaviour; the change takes
effect at each workspace's next start.
