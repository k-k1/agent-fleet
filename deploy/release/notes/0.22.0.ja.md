PostgreSQL と MySQL がワークスペースの中で動くようになりました——作業コピーごとに 1 つ、
Docker も手作業の導入もなしで、端末の `af-db` か設定の「データベース」タブから使えます。
モデル目録も目録らしくなりました。モデルには配布元が付けた名前と作例の絵が並び、
量子化リポジトリはダウンロードの前に GPU に収まるかを答え、モデルを選ぶ利用者には
id ではなく名前が届きます。

### New

- **ワークスペースの中の PostgreSQL と MySQL。** `af-db url` が、いまの作業コピーの
  データベースへの接続 URL を返します（初回はサーバの取得と起動もそこで行います）。
  `eval "$(af-db env)"` でシェルに入ります。データは Stop → Start をまたいで残り、
  ポートはフレームワークが既定で使う 5432 / 3306、エンジンを起動するとそのクライアント
  （`psql`・`mysql`）が `PATH` に出て、誰も接続していないサーバは自分で止まります。
- **ワークスペース設定の「データベース」タブ。** 各エンジンの状態・版・メモリ・接続 URL が
  出て、`af-db` でできることが端末なしでできます——エンジンの導入・開始・停止、名前を付けた
  データベースの作成・削除・リセット、そしてそのデータベースに接続済みのシェルを開くこと。
  **ワークスペース起動時に開始**を入れるとエンジンが起動時から上がります。既定はオフです——
  誰も問い合わせていないデータベースでもメモリは要るからです。
- **モデル目録に名前と作例が出ます。** 登録済みモデルの見出しが、ファイル名から作った鍵では
  なく配布元が付けた名前になり、配布元の作例画像が並びます。一覧はファミリーごとの区画に
  分かれ、上にファミリーのチップが出ます。この版より前に取り込んだモデルの名前と作例は、
  **名前と作例をまとめて取る**の 1 押しで埋まります。
- **量子化リポジトリが 1 枚のカードになり、ダウンロードの前に「収まるか」を答えます。**
  これまではどのファイルを選んでも、実際には動く GPU クラスで「入りません」と出ることが
  ありました。文脈窓がカードの項目になり（既定は収まる最大）、ファイルごとに
  **収まります**／**ぎりぎり**／**このクラスでは入りません**と、収まるクラス名が出ます。
  チャットのモデルはリポジトリごとにまとまり、**この配布元の他の量子化を見る**で、検索に
  戻らずに残りが並びます。
- **モデルを名前で選べます。** opencode のモデル一覧と画像生成ペインの選択欄に、id ではなく
  配布元の名前と見分けのつく部分が出ます。id はリクエストが名指す鍵としてそのままです。
- **ミラーの回答翻訳が自動で押せます。** 設定 › AI補助 › **自動翻訳**をオンにすると、
  そのセッションを見ている間に届いた回答について、ターンが完了した時点で「翻訳」ボタンを
  自動で押します。既定はオフで、開いた時点で画面にあった回答まで遡って訳すことはありません。

### Improved

- **登録済みモデルの一覧がカードのグリッドになりました。** 広いペインでは 1 行に複数枚が
  並び、カードの中身はウィンドウの大きさではなく、そのカードが実際にもらった幅で畳まれます。
- **opencode の鍵や枠を変えても、走っているターンが途中で切れなくなりました。** 設定 ›
  エージェントの opencode カードが「反映待ち」を伝え、再起動はターンの切れ目を選べる
  利用者に委ねます。モデル目録の変更は、そもそも再起動なしで動いているサーバへ届きます。

### Fixed

- **opencode のセッションが作業の途中で黙って止まっていました。** 共有の opencode サーバが
  数分ごとに入れ替えられ、そこで死んだターンが「完了した回答」として報告されていました。
  入れ替えは起きなくなり、頼んでいない中断は中断として報告されます。
- **`workspace-agent --version` が全 CLI の MCP 設定を書き換えていました。** Agent が
  知らない引数を渡すと 2 本目の Agent が起動し、自分の MCP サーバ名を採番し直して
  claude / codex / opencode / cursor の設定をそれに合わせて書き換えていました。知らない
  引数は使い方を出して止まるようになり、`--version` と `--help` は正式に使えます。
- **配備の全ワークスペースが極端に遅くなることがありました。** Agent が書き換わる状態を
  共有ファイルシステムに置き、応答のたびに全セッションの転写を読み通していたためです。
  どちらもそこから降りました——この修正のもう半分はスタックの更新です（下記）。
- **URL の直後の日本語の句読点がリンクを壊し、後ろの語を飲み込んでいました。**
  `…/pull/727（base は develop）` では次の空白までがリンクに入り、読点・句点・閉じ括弧・
  中黒でも同じことが起き、中黒で並べた 2 本の URL は 1 本のリンクに潰れていました。

### Upgrade notes

- **ファイルシステムのスループットモードがパラメータになり、既定が課金の形を変えます。**
  `10-data` は `bursting` を直書きしていて、それが配備を飢餓状態にした原因でした。
  `EfsThroughputMode` の既定は `elastic` なので、このスタックを次に更新した時点で稼働中の
  ファイルシステムがそちらへ移ります——上限なしの従量 I/O です。これまでのままにするなら
  `EfsThroughputMode=bursting` を渡してください。3 つめの選択肢は `provisioned`
  （`EfsProvisionedThroughputMibps`）ですが、AWS は引き下げと elastic への復帰を 24 時間
  ロックするので、多めに当てるのではなく後から上げてください。
- **遅さの修正は、新しいイメージとそのスタック更新の両方が要ります。** イメージだけ上げても、
  稼働中のファイルシステムは今のモードのままです。
