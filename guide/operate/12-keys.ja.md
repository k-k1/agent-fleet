# 12. 保存時の鍵: AWS KMS とホームごとの鍵

[English](12-keys.md) | 日本語

既定では、Control Plane が封じるすべての秘密は `AF_MASTER_KEY` から導いた鍵で守られます。`ecs` / `ecs-ec2` では、その
管理を AWS KMS に移せて、さらに各メンバーのホームに専用の鍵を持たせられます。この章は、各ステップが何を決めるか、
そして鍵を無効にすると何が破棄され、何が破棄されないかを扱います。これが答える脅威モデルは
[04 セキュリティ運用](04-secure.ja.md#残存リスク-運用でどう扱うか)、パラメータは
[ECS のランブック](../../deploy/aws/ecs/README.md#keys-at-rest-on-kms-optional-off-by-default) にあります。

## AWS KMS で保存時の鍵を守る

`ecs` / `ecs-ec2` では、Control Plane が封じるもの（MCP 接続のヘッダとテナントが MCP サーバー用に登録したクライアントシークレット、サインインと Git OAuth のクライアント
シークレット、エンジンのトークン、セッションの引き継ぎと共有、受信箱のメッセージとその添付、開発用ログインの
署名鍵とクライアントシークレット、各ワークスペースの資格情報ストアの鍵、ホームごとの鍵があるホームではその資格情報ストアの鍵）の
鍵を AWS KMS に持たせられます。値はそれぞれ KMS から得た新しいデータ鍵で封じられ、テナントに結び付くので、
別のテナントの名前では開けません。有効にする手順:

1. `10-data` を `CustodianKmsKey=create` でデプロイし（同じアカウントの自前の対称 KMS 鍵でもよい）、
   出力 `CustodianKmsKeyArn` を読む。
2. `30-ingress` を `CustodianKmsKeyArn=<その ARN>` でデプロイする。Control Plane に
   `AF_KEY_CUSTODIAN=kms` と `AF_KMS_KEY_ID` が渡り、タスクロールにはその鍵に限って、Control Plane の
   暗号化コンテキスト付きのときだけ `kms:GenerateDataKey` と `kms:Decrypt` が付きます。

切り替える前に知っておくこと:

- **`AF_MASTER_KEY` は引き続き必須。** 切り替え前に保存されたものはこの鍵で開き、ほかの鍵もこれから
  導かれます。これまでどおり保管してください。
- **自動では再暗号化しない。** 切り替え前に保存された値は読めるままで、守りは master 鍵だけのまま。
  `rewrap-keys`（[後述](#切り替え前に保存された値を封じ直す)）を実行するまで、KMS が守るのは切り替え後に
  保存されたものだけです。
- **メンバーが保存した資格情報は KMS では shred されない。** KMS に包まれるのは、切り替え後に鍵が初めて
  保存されるワークスペースだけです。すでに鍵を持つワークスペースは master 鍵で包まれたままで、再起動しても
  変わりません。いずれにしても鍵そのものは以前のストアを開けるよう今も `AF_MASTER_KEY` とメンバーから
  導かれ、master 鍵を持つ人は今も導けるので、master 鍵はこれまでどおり守ってください。ホームごとの
  専用の鍵はこの経路から master 鍵を外しますが、鍵のすべての写しを消すわけではありません
  （[後述](#ホームごとに専用の鍵を持たせる)）。
- **代替経路は無い。** KMS に届かない・拒否されたときは、封じるのも開くのも KMS を名指すエラーで失敗します。
  KMS が封じた値を Control Plane が気づかないうちに master 鍵で扱うことはありません。
- **開いた鍵はメモリに 5 分キャッシュする**（`AF_KMS_DATA_KEY_CACHE_TTL`、`0` で無効）。鍵の無効化が
  効くのはその時間内で、即時ではありません。
- **KMS 鍵を無効化または削除予定にすると、切り替え後に封じたものは全テナント一斉に Control Plane から読めなくなる。**
  これが crypto-shred の手段なので、鍵を管理できる人を絞ってください。1 テナントだけを止めるには、
  `kms:EncryptionContext:af:key_ref` がそのテナントの ID のとき `kms:Decrypt` を拒否する文を鍵ポリシーに
  足します。鍵の管理者が戻せる失効であって、shred ではありません。
- **KMS が封じた値があるうちは `local` に戻さない。** local の custodian はそれを、理由を示すエラーで拒否します。

## 切り替え前に保存された値を封じ直す

`af-cp rewrap-keys` は、切り替え前に Control Plane が master 鍵で封じた値をすべて KMS で封じ直します。
対象は各ワークスペースの資格情報ストアの鍵を包んだもの、MCP 接続のヘッダとテナントが MCP サーバー用に登録したクライアントシークレット、サインインと Git OAuth の
クライアントシークレット、セッションの引き継ぎと共有の提案、受信箱のメッセージとその添付、開発用ログインの
署名鍵とクライアントシークレット、ホームごとの資格情報ストアの鍵、エンジンの Hugging Face・Civitai・ComfyUI の鍵です。
実行後は、KMS 鍵を無効化するとこれらも読めなくなります。

- Control Plane 自身が `AF_KEY_CUSTODIAN=kms` で動くようになって**から**、Control Plane と同じ環境
  （同じ `AF_MASTER_KEY`・`AF_KMS_KEY_ID`・データベース設定・タスクロール）で実行します。`local` では
  実行を拒否します。`local` のままの Control Plane は、このコマンドが書いた値を開けません。
- まず `--dry-run` で。置き場所ごとに、KMS 済みの数・旧形式の数・封じずに保存された数（master 鍵の無い
  Control Plane が書いたもの。コマンドは触らない）を表示します。何も変えず、KMS も呼びません。
- `--dry-run` なしでは、値ごとに master 鍵で開き、KMS で封じ、KMS でもう一度開いて読み戻せることを確かめてから
  書きます。1 行ずつで、その間に行が変わっていなければ書きます。中断・KMS のエラー・`Decrypt` の拒否では、
  その時の行を書く前に止まります。どの行も旧形式か KMS 済みのどちらかで、どちらも開けます。書き直しの後、
  何も変えずにすべての置き場所をもう一度見て、終了コードはその最終確認で決まります。終了コードが `0` に
  なるまで繰り返し実行してください。やることが無い実行は何も変えません。
- **管理者が編集していないときに実行する。** Control Plane は動かしたままで構いませんが、サインインの
  プロバイダや Git OAuth アプリを秘密を入れ直さずに保存する、ComfyUI パネルを鍵を入れ直さずに保存する、
  といった操作は読み出した値をそのまま書き戻します。コマンドが書き直す前に古い値を読んだ保存は、古い値を
  戻してしまいます。実行中に起きたものは最終確認が見つけますが、その後に起きたものは見つけられません。
  終わったら `--dry-run` で確かめてください。
- 終了コード `0`（`--dry-run` の有無によらず）: コマンドが最後に見た時点で、旧形式は無く、どの行も読めた。
  `1`: 旧形式が残っている、読めない・書けない行がある、または途中で止まった。ログには置き場所と行の ID が
  出て、値は出ません。したがって `--dry-run` は rewrap 前は `1`、後は `0` です。`2`: 設定の問題（`kms` でない、
  master 鍵が無い、鍵 ID が無い、データベースが無い）。
- `ecs` / `ecs-ec2` では、Control Plane のタスク定義をコマンドだけ差し替えて一回限りのタスクとして動かします。貼り付けるコマンドは
  [ECS のランブック](../../deploy/aws/ecs/README.md#running-af-cp-commands-against-the-control-planes-database) にあります。

**実行後も `AF_MASTER_KEY` は外せず、変えてもいけません:**

- 各ワークスペースの資格情報ストアの鍵は、今もこの鍵とメンバーから導かれます（`HMAC(master, userKey)`）。
  コマンドが KMS に移すのはその鍵を*包んだ写し*なので、KMS 鍵を無効化すると Control Plane はその鍵で
  ワークスペースを起動できなくなりますが、master 鍵を持つ人は今も鍵を導いて `secrets.enc` を開けます。
  したがってメンバーが保存した資格情報は、まだ KMS では crypto-shred されません。ホームごとの専用の鍵が
  変えるのはその一部だけです（[次節](#ホームごとに専用の鍵を持たせる)）。
- 初めて起動するワークスペースも、同じ導き方で鍵を得ます。
- ワークスペースが Control Plane を呼び返すときのトークン（Git の資格情報、Git OAuth、メモ、スケジュール、
  エンジン、ブランチ規則、AWS と Google Cloud のプロファイル、ドキュメント、MCP）は、この鍵から導いた鍵で
  署名されます。
- `AF_KEY_CUSTODIAN=kms` で `AF_MASTER_KEY` が無いと、Control Plane は起動を拒否します。

コマンドで変わること: 封じ直した値は、master 鍵だけでは開けなくなります。導けてしまう資格情報ストアの鍵は除きます。

## ホームごとに専用の鍵を持たせる

`AF_WORKSPACE_DEK=random` にすると、Control Plane はメンバーのホームごとに資格情報ストア（`secrets.enc`）用の
ランダムな鍵を作り、KMS で封じます。受け付けるのは `AF_KEY_CUSTODIAN=kms` のときだけで、それ以外の組み合わせや
別の値では Control Plane は起動時に止まります。`ecs` / `ecs-ec2` では `30-ingress` のパラメータ
`WorkspaceDekRandom=on` で有効にします。`CustodianKmsKeyArn` が必須で、無いと更新は CloudFormation の実行時にロールバックされます（変更セット自体は作成できます）
（[有効にする前に](#ecs-で有効にする前に)）。

### ECS で有効にする前に

`30-ingress` を `WorkspaceDekRandom=on` と `CustodianKmsKeyArn` を付けてデプロイします。変わるのは Control Plane の
タスク定義（`AF_WORKSPACE_DEK=random` が加わる）だけで、サービスはローリング更新されます。先に確認してください。

- 残してあるホームは、このフラグでの最初の起動までは導出した鍵のままです。ワークスペースごとの SSM パラメータ
  `secret-key-next` はその起動から作られます。ホームの確定後の次の起動で削除を試み（失敗はログに残して起動は続行）、
  Destroy でも消えます。動いているタスクは再起動するまで環境変数を保持します。既存の `/af-ws/*` への権限で足ります。
- パラメータを戻しても止まるのは新しいホームへの鍵の作成だけで、すでに鍵を持つホームはその鍵を使い続け、
  再接続は要りません。ホームの鍵を知らない Control Plane へ戻す場合や `home_dek` 表を失った場合は別で、資格情報の
  再接続が必要になり得ます（下の「無効にしても元には戻らない」）。
- まだ起動していないホームや古いスナップショット・バックアップは、KMS 鍵を無効化しても **crypto-shred されません**。
  破棄したホームの鍵は、ランタイムがホームの消滅を証明できたときにだけ消えます（次の項目）。

### ホームの鍵のふるまい

- **鍵はワークスペースではなくホームのもの。** 残したホームの上でワークスペースを削除して作り直しても鍵は
  そのままです。鍵を消すのは 1 つの場合だけです: Destroy が終わり、どのワークスペースの行もそのホームを指しておらず、
  ランタイムがホームの全体が消えたことを**証明**したとき。ホームの一部が残ったまま鍵を消すとその部分が読めなくなる
  ので、それ以外の答えでは鍵を残します。ランタイムごとに示せること: `docker` と `native` は示せません
  （ディレクトリが無いのは、外れたボリュームや誤った `WS_DATA` でも同じ）。その鍵は下のオペレーターの経路で消します。
  `kubernetes` と `ecs`/`ecs-ec2` は、いま実行した Destroy からしか言えません（全 claim と volume の消滅を確認した後の
  StatefulSet の削除、全アクセスポイントが task の消すディレクトリを指していたうえで EFS の home task が 0 で
  終わったこと。別の場所を指すアクセスポイントは消さずに報告します）。後から確かめることも、「残りなし」から言うことも
  しません（home task の無い `ecs` はアクセスポイントだけを消し、再試行しても残りは報告されません）。
  `migrating` のままの鍵はこの経路では消えず、証明できないランタイムは鍵を残します。行が消えると、
  ストアと、その鍵で封じたストアの写し（スナップショットやバックアップ）は開けなくなります。ただし `home_dek` の行が
  残っているデータベースのバックアップを、KMS 鍵が有効なうちに戻すと開けます。ストアが移る前の写しは導いた鍵の
  ままです（[後述](#kms-鍵の無効化写しの復元無効に戻すとき)）。
- **取り残された鍵。** 残った鍵（golden bake の `migrating` なプローブ、証明できないランタイム、古い Control Plane
  による破棄）は `af-cp home-dek-status --orphans` が一覧します（読み取りのみ。どのワークスペースの行も指さない鍵）。
  一覧に出ただけでは候補であって証明ではありません。ホームはワークスペースの行より長く残り得るからです。ホームが
  消えたことを確かめた後（EFS のディレクトリ、EBS ボリュームとスナップショット、クラスタの claim、データディレクトリ）、
  `af-cp home-dek-status --remove-orphan <membership-id> --force` で消します。`--force` はホームが消えたという
  あなたの宣言です。このコマンドには確かめるランタイムが無いからです。ワークスペースの行が指す鍵と、その
  メンバーシップでワークスペースの操作が進行中の鍵は、これでも消しません。終了コードは消したとき `0`、何も
  消さなかったとき `1`、データベースのエラーで `2` です。ホームが残って
  いるのに鍵を消すと、その `secrets.enc` は二度と読めません。
- **ストアの移し替え。** 有効にした後の最初の起動でホームの鍵を作り、Control Plane は導いた鍵と並べて
  ワークスペースに渡します。ワークスペースは起動時に `secrets.enc` をどちらかの鍵で開き、ホームの鍵で封じ直します。
  どちらでも開けないストアには触りません。まだストアの無いホームには、その起動でホームの鍵で封じた空のストアを
  作ります。導いた鍵しか持たない書き手が、後から導いた鍵でストアを作れないようにするためです。結果はワークスペースの
  `/healthz` が `secrets_key`（`none`・`current`・`migrated`・ホームの鍵に移せなかった `derived`・`unreadable`）と
  `secrets_key_next`
  （ホームの鍵で封じたか）として返し、鍵は返しません。
- **確認。** そうした起動の後、Control Plane はその報告を待ちます。待つのはその起動が立ち上げたワークスペースの
  報告だけです。起動ごとに新しい識別子（`AF_HOME_KEY_START`、秘密ではない）を渡し、ワークスペースはそれを
  `secrets_key_start` として返すので、以前のタスクや別のワークスペースの応答は無視し、リダイレクトにも従いません。
  ワークスペースがホームの鍵で封じていて `migrated`・`current` を返したら、Control Plane はホームを確認済みにし、**次の**起動からワークスペースには
  ホームの鍵だけを（`AF_SECRET_KEY` として）渡し、導いた鍵は渡しません。`ecs` / `ecs-ec2` ではその起動で
  `secret-key-next` パラメータも消します。すでに動いているワークスペースは、再起動するまで両方の鍵を環境変数に
  持ったままです。`unreadable` や `derived` ではホームは移行中のままで、ログに残し、何も消しません。待つ間は
  3 秒ごとに尋ね、待つのは最長 15 分です。それを過ぎたとき、または待っている間に Control Plane が再起動したときは、
  ホームは移行中のままで、後の起動で確認されます。`af-cp home-dek-status` が移行中と確認済みのホームを数えます。
  `ecs` / `ecs-ec2` では、上の `rewrap-keys` と同じ単発タスクとして実行します。

### KMS 鍵の無効化、写しの復元、無効に戻すとき

- **KMS 鍵を無効化すると何が起き、何が起きないか。** ホームのストアが封じ直された後は、`AF_MASTER_KEY` から
  導いた鍵ではもう開けません。また Control Plane のデータ鍵キャッシュ（`AF_KMS_DATA_KEY_CACHE_TTL`、既定 5 分）が
  切れた後は、Control Plane はホームの鍵を新たに開けず、次の起動を拒否します。その TTL の間は起動が成功し得ます。
  **これだけでは crypto-shred ではありません。** すでに渡したホームの鍵の写しは今もストアを開け、それぞれ
  custodian の鍵とは別のもので守られています:
  - **動いているワークスペース**は鍵を環境変数に持ち、Agent・git の資格情報ヘルパー・MCP サーバは KMS に
    問い合わせずにストアを読み書きし続けます。
  - 起動に使う**ランタイム側の写し**で、停止しても残ります: docker ではコンテナの環境、Kubernetes では Secret、
    `ecs` / `ecs-ec2` ではワークスペースごとの SSM SecureString パラメータ（`secret-key`・`secret-key-next`）。
    これはアカウントの SSM 用の鍵で暗号化されています。

  ホームを残したままそのストアを shred するには、鍵を無効化し、**かつ**ワークスペースを止め、**かつ**それらの
  ランタイム側の写しを自分で取り除きます。ここには自動でそれをするものはありません。Destroy はその手順では
  ありません。ランタイム側の写しを消し、ホームも消そうとしますが、home task の無い `ecs` のスタックでは
  アクセスポイントだけを消し、ホームの EFS ディレクトリは残ります。
- **されないもの。** 有効にしてから一度も起動していないホームは導いた鍵のままで、KMS 鍵を無効化しても
  **shred されません**。`af-cp home-dek-status` がその数を数えます（読み取りのみ）。封じ直す前に作られた
  ホームの写し（ecs-ec2 のスナップショットやバックアップ）には古いファイルが残り、master 鍵で開けます。
  確認されるまでは、導いた鍵もホームの鍵と並べて渡します。封じ直したストアはもうそれでは開けません。
- **移す前の写しを戻した場合。** 確認済みのホームに、ストアが移る前のスナップショットやバックアップから
  `secrets.enc` を戻すと、それは導いた鍵で封じられていて、そのホームにはもう渡されない鍵です。ワークスペースは
  `unreadable` を返し、その上には書きません。Control Plane の環境で
  `af-cp home-dek-status --remigrate <membership-id>` を実行してからワークスペースを再起動すると、両方の鍵が
  再び渡され、戻したストアが封じ直されます。このコマンドは、そのメンバーシップに確認済みのホームの鍵が無いと `1`、
  データベースのエラーで `2` で終わります。
- **無効にしても元には戻らない。** `AF_WORKSPACE_DEK` を外しても、すでに鍵を持つホームにはその鍵を渡し続けます。
  ストアがその鍵で封じられているかもしれないからです。ストアが封じ直された後は、戻し方によって違います:
  - **ホームの鍵を知らない Control Plane に戻す、または `home_dek` 表を失う**（ワークスペースイメージは v0.31.0 以降）:
    ストアは開けなくなり、ワークスペースはそのストアへの書き込みを、資格情報の接続し直しを含めてすべて拒否します
    （そのイメージは開けないストアの上には書きません）。
  - **v0.31.0 より前のワークスペースイメージ: 移ったホームでは起動しないでください。** その Agent にはこの保護が無く、
    読めなかった後の保存が封じ直したストアの上に空のストアを書き、資格情報が失われ得ます。

  復旧するには、そのホームでワークスペースを起動する前に、まず開けるものを戻してください: Control Plane の版、
  その `home_dek` の行、KMS 鍵。保存していた資格情報をあきらめる場合に限り、ワークスペースを止め、読めない
  `secrets.enc` をメンバーのエージェント設定ディレクトリ（`~/.config/agent-fleet/`）から自分で退避してから、
  メンバーに接続し直してもらいます。Control Plane より古いワークスペースイメージは、ストアがまだ封じ直されて
  いなければ何も失いません。ホームの鍵を無視して導いた鍵を使い続けます。
- **代替経路は無い。** KMS がホームの鍵を封じられない・開けないときは、ワークスペースは起動しません。
  導いた鍵だけで起動することはありません。
