# 03. 日常運用

[English](03-run.md) | 日本語

構築後の定常運用（バックアップ、リストア、アップグレード、閉域網、Workspace の停止）を、
判断ポイントとともに説明します。**実際のコマンド（`backup.sh` / `restore.sh` / upgrade /
air-gapped の各手順）は [deploy/compose/README.md](../../deploy/compose/README.md) が正**です。
ここではコマンドを複製せず、「何が起きるか・何に注意するか」を補います。作業ディレクトリは
`deploy/compose/`。設計上の前提を深掘りしたいときは `docs/build/09-deploy.ja.md` §9.7。

## バックアップ

`deploy/compose/backup.sh` が `DATA_DIR` を丸ごと timestamped な `tar.gz` に固めます。コマンドと
オプション（`OUT_DIR` / `KEEP` / `--no-stop`）は runbook の "Backup & restore" 節を参照してください。

### 何が入り、何が入らないか

アーカイブに**入る**もの（= これだけあれば別ホストへ復元できる）：

- `control-plane.db`：テナント / メンバー / ポート / トークンのグラフ。
- 各ユーザーの home（作業ツリー・dotfiles・封筒暗号された `secrets.enc`）。
- 各ユーザーの `claude-config`（**平文の Claude ログイン状態**）。
- Caddy の証明書（復元時に Let's Encrypt のレート制限を避けるため）。

**入らない**もの：

- `shared/jvm`（再取得可能で巨大な Temurin JDK）は意図的に除外。
- **`AF_MASTER_KEY` は入りません。** これは `.env` にあり、設計上アーカイブに含めません。
  **データ領域の外に置いてください**。アーカイブにはテナント定義のサインイン方法の
  client secret（この鍵で封印済み）も入るようになったため、鍵をデータの隣に置くと
  封筒暗号の意味そのものが無くなります。

> この 2 点が運用の肝です。バックアップアーカイブは**平文の Claude 状態を含む機微データ**なので、
> 保管先の権限・暗号化を厳格にしてください。同時に、アーカイブだけを持っていても
> `AF_MASTER_KEY` が無ければ封筒暗号された資格情報は復号できません。逆に `AF_MASTER_KEY` を
> 失えば、すべての過去アーカイブが復号不能になります（crypto-shred・[04](04-secure.ja.md)）。**鍵と
> データは別々に、しかし両方をバックアップする**のが正解です。

### ユーザーへの影響

`backup.sh` は既定で **CP と Caddy を一瞬だけ停止**して SQLite の整合スナップショットを取り、
すぐ再開します。このとき**ユーザーの Workspace（`af-ws-*`）は compose 管理外なので止まりません**。
セッションは切れず、作業は継続します。停止中の数秒は Console のサインインや API 中継が一時的に
応答しなくなる程度です。呼び出し側で静止を保証済みなら `--no-stop` で無停止取得もできます。

### cron 化

本番では `backup.sh` を cron で定期実行します。`OUT_DIR` で社内のバックアップ領域（別ボリューム／
リモート）を指定し、`KEEP` で世代数を制御します。cron エントリの例は runbook の "Backup & restore"
節にあります。取得後は世代のプルーニングまで自動で行われます。

## リストア

クリーンなホスト、またはデータ喪失後の復旧手順です。コマンドは runbook の "Backup & restore" 節にあります。

流れは「`.env` を用意（**バックアップ元と同一の `AF_MASTER_KEY`** を金庫から復元）→ `restore.sh
<archive>` → `docker compose up -d` → Console から各 Workspace を**起動**」です。要点は 3 つです。

1. **`AF_MASTER_KEY` は元と同一値でなければならない。** 違う／欠落していると wrapped DEK を
   unwrap できず、資格情報は復号できません。金庫からの復元を最初に確認します。
2. **`DATA_DIR` の basename 制約。** 復元先の親パスは元と違ってよく（例 `/srv` → `/mnt`）、CP が
   起動時に各 Workspace の on-disk root を現在の `DATA_DIR` へ付け替えます。ただしアーカイブ先頭の
   ディレクトリ名（= 元 `DATA_DIR` の basename）と、復元先 `DATA_DIR` の basename は**一致**させて
   ください。`restore.sh` がこれを検証し、不一致なら拒否します。
3. **Workspace は Console からの「起動」で作り直される。** リストア直後には Workspace コンテナは
   存在しません（compose 管理外だから）。ユーザー（または管理者）が Console で「起動」を押すと、CP が
   復元済み DB のポート/トークンで `af-ws-*` を再作成し、home の `secrets.enc` と `claude-config`
   からユーザーの接続と Claude ログインが復活します。

## アップグレード

`.env` の `VERSION` を新しいタグに変え、image を pull（またはビルド）して `up -d` するだけです。
コマンドは runbook の "Upgrade" 節にあります。

- **image は GHCR から取得します**（`ghcr.io/k-k1/agent-fleet/*`。`REGISTRY` + `VERSION` で解決）。
  pull にレジストリログインは不要です。**Workspace image は compose のサービスではない**ので
  `docker compose pull` では取得されません。別途 `docker pull` するか、最初の「起動」で
  オンデマンドに取得させてください。
- **スキーマ migration は CP に埋め込まれ、起動時に自動適用**されます（**前方互換**）。手動の
  migration 実行は不要です。
- **ダウングレードは非対応**です。新バージョンで適用された migration を古い CP は理解できません。
  したがって**アップグレードの前に必ず `backup.sh` を取る**こと。何かあれば「古い image に戻す」の
  ではなく「バックアップからリストアする」のが正しい後退経路です。
- 破壊的変更の有無はリリースノートで確認してください。
- **AWS（`ecs` / `ecs-ec2`）の場合は compose ではなく `deploy/aws/ecs/update.sh`** です
  （`VERSION=<v> ./update.sh --profile <p> --region <r>`）。ECR へ push → ingress スタックを
  `ImageTag` だけ上書きして deploy → CP サービスの入れ替わりを待つ、までを 1 コマンドで行います。
  版によっては、あるスタックを別のスタックより先に更新する必要があります（スクリプトの通常の
  順序の逆）。`update.sh` はそれを最初に検査し、何にも触れる前に止まって、単独で実行する
  `aws cloudformation deploy` のコマンドをそのまま印字します。実行したら `update.sh` をもう一度。
  **走っているワークスペースは自動では新しくなりません**（次の「起動」から新しい image）。
  該当する利用者の Console には「要再起動」バッジが出るので、停止のタイミングは本人に委ねます。
  **データスタックと EFS バックアップ:** `update.sh` はデータスタックを更新しません。v0.26.0
  より前に構築した `Persistence=retain` の環境は、そのスタックを手で更新するまで EFS の日次
  バックアップがありません。`update.sh` はこれを（読み取りだけで）検出して警告し、change set
  のコマンドを印字します。`deploy/aws/ecs/README.md`「Upgrade (runbook)」の手順 1a を参照。
  同じ検出結果は、Console の管理画面の全セクションに super_admin 向けのバナー（「日次の EFS
  バックアップがない」）としても出るので、`update.sh` の出力を誰も読まなくても見落としません。
  `update.sh` が結果を ingress スタックに記録し（パラメータ `EfsBackup`）、データスタックにバック
  アップが入ったあとの`update.sh` が確認できた時点でバナーは消えます。`update.sh` がデータスタックを読めな
  かった場合は以前の判定を保持するので、既存のバナーは修復を確認できた実行まで残ります。
  一度も記録されていない環境ではバナーは出ません。

### ecs-ec2: 起動テンプレートを変えたあとのスロットの入れ替え

スロットはユーザーデータを起動時にしか読まず、停止したワークスペースは次の起動で同じスロットに
戻ります。そのため、スロットの起動テンプレートの変更（リリースのセキュリティ設定など）は今ある
スロットには届きません。インスタンスを手で終了するのではなく、Console から入れ替えます。

**`$Latest` より古いスロットは自動で入れ替わります。** ワークスペースの起動時にホームがそのような
スロットにあると、その起動で予約と同じ手順で新しいスロットへ移ります（WS バーへの表示はありません）。
`$Latest` より古い空きスロットはスイーパーが終了します。新しいスロットを起動できないとき（容量・
クォータ）も起動は古いスロットで成功し、後の起動でやり直します。自動の入れ替えは監査ログに残ります
（`pool.slot_replace_auto`）。スロット画面には **$Latest より古い・次回起動で自動入れ替え** と出ます。
止めたいときは Control Plane の `AF_ECS_EC2_AUTO_REPLACE_OUTDATED_SLOTS=false` を設定します。古いスロットへ戻すことを
禁じたいときは、次のように自分で予約します（その場合、新しいスロットを起動できなければ起動は失敗します）。

1. **設定 → 管理 → スロット**（super_admin）。**テンプレート**列に各スロットを起動した起動テンプレートの
   バージョンが出て、古いものには **$Latest より古い** と付きます。
2. **N 台すべてを入れ替え予約…** は `$Latest` より古いスロットと、それぞれに載っているワークスペースを
   一覧で示し、確認するとそのスロットだけを予約します。行の **入れ替えを予約** は 1 台だけ予約し（予約済みの行には
   **次回起動で入れ替え予定** と出ます）、**予約の取消** で戻せます。予約はすべて監査ログに残ります（`pool.slot_replace_reserve` /
   `pool.slot_replace_cancel`。移るワークスペース名つき）。
3. 実行中のワークスペースには何も起きません。利用者の WS バーに **新しいスロットへ移動** が出て、次に
   停止 → 起動したときに `$Latest` から新しいスロットを起動し、ホームを移して古いスロットを終了します。
   その起動はいつもより 25 秒ほど長くかかります。ファイル・リポジトリ・ログインはそのままで、
   ホームを削除することはありません。
4. 新しいスロットを起動できないとき（容量・クォータ）は、理由つきで起動が失敗し、予約は残ります。
   予約されたスロットに戻すことはしないので、時間をおいてやり直してください。ワークスペースが
   載っていない予約済みスロットはスイーパーが終了します。

詳細と結果の確かめ方は `deploy/aws/ecs/README.md` の「Moving retained slots onto new user data」に
あります。

**管理プレーンのメモリ保護。** スロットのユーザーデータは、SSM エージェント・docker・containerd に
systemd の `MemoryMin`（192 / 256 / 128 MiB）を与えます。ECS エージェントは `ecs.service` の子ではなく
docker コンテナとして動くため、小さな補助サービス（`af-protect-mgmt`）がそのスコープを探して
192 MiB の `memory.min` を設定します。補助サービスは 30 秒ごとに再適用するのでエージェントの
再起動にも追従し、ECS・SSM エージェントの OOM スコアも下げます（初回起動時にすでに動いている
SSM エージェントのプロセスにも効きます）。下限が効くよう `system.slice` に合計 832 MiB を設定します。
メモリが逼迫するとカーネルは先にワークスペースコンテナのページを回収するため、メモリを使い切る
ワークスペースのせいで、EC2 は正常のままエージェントだけが応答しなくなるスロットは生じにくくなります。
合計はホスト予約（`AF_ECS_EC2_HOST_RESERVE_MB`、既定では 1024 MiB 以上）に収まります。予約を
832 未満にすると、保護量が予約を上回ります。これは起動テンプレートの変更なので新しい `$Latest` が
作られ、今あるスロットには上の入れ替えを通してのみ届きます。cgroup v2（Amazon Linux 2023 の既定）が前提です。

### ecs-ec2: 動かなくなったスロットの停止

スロットは、隔離されていなくても **動かなくなる** ことがあります。EC2 インスタンスは起動中でステータスチェックも
`ok` なのに、ECS エージェントが未接続で、SSM も応答せず、メンバーの home がまだ載ったままの状態です。
そのメンバーの Start は待たされるか失敗し続けます。スロット画面ではこの行が起動中のまま **（まだタスクを受け付けない）** と出て、
**停止（強制）**（super_admin）が使えます。

1. **設定 → 管理 → スロット** の行で **停止（強制）** を押し、確認します。確認画面には載っているワークスペースが出ます。
   ECS エージェントが接続していて **かつ** SSM がオンラインのスロットは、サーバーが拒否します（`slot_healthy`）。この操作は
   応答しないスロット向けです。停止済みのスロットも拒否されます（`slot_not_running`）。どうしても正常なスロットを止めるときは
   API に `{"override_healthy": true}` を渡します。Console は送らず、そのスロットで動いているワークスペースも一緒に止まります。
2. そのスロット上のメンバーの Start や実行を打ち切り（ワークスペースは停止に見えます）、Control Plane が積んだコマンド
   （home のロックを握り続ける未実行の umount / mount）を取り消し、スロットを **隔離** して、インスタンスを停止します。
   停止はまず通常のシャットダウンなので、カーネルが home をアンマウントできます。3 分たっても止まらなければ Control Plane が
   Force 付きでやり直し、`stopping` 中にもう一度押すとすぐ Force で送ります。
3. スロットは **隔離されたまま** です。二度と配置されず、スイーパーも回収しません（ADR 0045 決定 20・23）。root ボリュームと
   タグは証拠として残るので、調べ終えたら同じ行の **終了** で消してください。メンバーの次の Start は、home が隔離スロットに
   あることを見つけて切り離し（停止中のインスタンスでは umount は不要）、別のスロットに置き直します。
4. 結果（取り消したコマンド数、Force を使ったか）は呼び出し直後に画面に出て、監査ログにも残ります
   （`pool.slot_force_stop`。ワークスペース・二つの健全性シグナル・件数つき）。

**STOPPING のまま残るタスク。** スロットのエージェントが停止を報告できないと、ECS はそのワークスペースの前のタスクを
`STOPPING` のまま保持し、メンバーの次の Start がそれを待ちます（サービスは同時に 1 タスクしか許しません）。エージェントが未接続の
スロットの行には **タスク STOPPING N 分** と出ます。解消するには **EC2 コンソールでそのインスタンスを一度起動** してエージェントを
再接続させ、タスクが停止と報告されたらもう一度停止します。他人のデータを持つかもしれないインスタンスについての判断なので、
Control Plane は自動では行いません。運用者なしで応答しないスロットを検出する仕組みは別の変更（#2450）です。実 AWS では未検証です。

## 閉域網（air-gap）へのインストール

外部ネットワークに出られないホストにも入れられます。ただし
ADR 0037 以降、image は GHCR で配布し
**リリースに image tar は添付しません**。レジストリに到達できないホストは、
`ghcr.io/k-k1/agent-fleet/*` を社内レジストリにミラーして `REGISTRY` をそこへ向けるか、
image を手で持ち込みます（ネット接続のあるマシンで `release.sh --save` してビルド＆
`docker save` → 対象ホストで `load-images.sh`）。コマンドは runbook の "Air-gapped install" 節にあります。

判断ポイントが 4 つあります。

- **image の取得元**: 社内レジストリのミラーなら `docker compose pull` がそのまま使え、
  保守も軽くなります。手持ち込みの tar は、アップグレードのたびにビルド／コピー／load を
  繰り返すことになり、image 名を `.env` の `REGISTRY` と一致させる必要があります。
- **TLS**: 閉域では Let's Encrypt が使えないので、[02 §4](02-install.ja.md) の `tls internal`（自己署名）
  へ切り替えるか、社内 CA を使います。
- **Claude のインストール**: Workspace image は既定でコンテナ起動時に最新の Claude を取得します。
  完全オフラインのホストでは `CLAUDE_INSTALL=0`（`WS_ENV` 経由）にし、Claude を焼き込んだ image を
  使ってください。

- **図のアイコン（`.drawio`）**: 同梱の drawio ビューアはオフラインでも図を描けますが、
  ベンダーアイコンの図案（`shape=mxgraph.aws4.*`・GCP・Azure・Kubernetes・ラック機器…）は
  **同梱していません**（全部で 40.8 MB あるため）。通常は初回に Control Plane が取得して
  キャッシュしますが、外に出られないとその取得が失敗し、図は**枠と色とラベルだけに気づかないうちに
  劣化します**。避けるには、持ち込んだディレクトリからキャッシュを埋めておきます:

  ```sh
  # 外に出られるマシンで 1 回
  git clone --depth 1 -b v31.1.8 https://github.com/jgraph/drawio
  # drawio/src/main/webapp/stencils を持ち込み、CP のホストで:
  control-plane drawio-preseed --from /path/to/stencils        # 既定束 49 件 / 17.0 MB
  control-plane drawio-preseed --from /path/to/stencils --all  # 全件 203 件 / 40.8 MB
  ```

  **1 件ずつ同梱台帳の SHA-256 で照合してから置く**ので、持ち込みの経路が信用できなくても
  中身は保証されます。キャッシュは内容アドレスで索引を持たないため、**埋めたディレクトリを
  そのまま tar で別ホストへ運んでも同じ**です。何が既定束に入り何が入らないかは、`--list` で
  先に確認できます。

「閉域で動く」の意味を取り違えないでください。image がローカルにあればフリートは**起動**
できますが、エージェント自身はモデルのエンドポイントに到達できなければ何もできません。この
オフライン導入経路は、制限された社内ネットワーク上のホスト向けであって、本当に切り離された
ネットワーク向けではありません。

## フリート方針（全エージェントへの指示）を配る

ワークスペースで動くすべてのエージェントに、**運用者からの方針**を読ませられます。実体は
リポジトリの `workspace/workspace-notes.md` で、Workspace イメージに焼き込まれて各
コンテナへ配られます（claude は `/etc/claude-code/CLAUDE.md` の managed policy として毎セッション
読み込み、codex / opencode / agy / copilot / kiro は起動ごとに同じ本文が各自の指示ファイルへ
合成されます）。

方針は短く保つために二層です。常時読み込まれる本体には、禁止事項と「エージェントが気づかないまま
踏む罠」だけを書き、末尾に**トピックファイル**（`workspace/notes/<topic>.md`、コンテナでは
`/usr/local/share/agent-fleet/notes/`）の索引を置きます。手順の長文はトピックファイル側にあり、
エージェントはその場面に来たときに該当ファイルを読みます。新しい規則を本体に足すのは
「必要になる前に知っていなければならないもの」だけで、それ以外はトピックファイルへ書き、
索引の一行で見つかるようにします。CLI にユーザー単位のスキル置き場がある種（claude / codex /
opencode）には、agent が起動のたびに各トピックファイルを `af-<topic>` という名前のスキルとしても
登録します。CLI 自身のスキル索引（起動時は説明文だけ、本文は必要時）が同じ本文へ至る第二の経路に
なり、それ以外の種は索引だけが経路です。

- **やってはいけないこと**（例: リポジトリを消す、認証情報を平文で書く）、**この環境の制約**
  （root が無い、Docker が無い、メモリが共有）、**ブランチの扱い**など、フリート共通の運用ルールを
  書く場所です。
- **反映にはイメージの再ビルドが必要**です。編集 → イメージを作り直し → 各利用者が
  ワークスペースを「作り直す」か、次にコンテナが作られたときに効きます。
- 利用者個人の書き足しは**この層ではありません**。各自の ⚙設定 →「エージェントへの指示」で行い、
  フリート方針と衝突したときはフリート方針が優先されます（[member/06](../member/06-agents.ja.md#エージェントへの指示自分の働き方を一度だけ書く)）。
- **本体の長さはそのまま全セッションのコンテキスト費用になります。** 全エージェントが毎回読むので、
  増やす前に「本当に全員・毎回必要か」を確認してください（トピックファイルは読まれるまで費用ゼロ
  です）。cursor にはこの層を配れません。

## opencode 2：ターミナルセッションと共有サーバー

opencode 2 では、ターミナル（CLI）セッションは Workspace Agent が動かす 1 つの opencode
サーバーにつながります（[member/06](../member/06-agents.ja.md#opencode-2-での違い)）。代わりに
ターミナルセッションごとの専用サーバーに固定したいとき（1 セッションあたりメモリがおよそ
150〜250 MB 多くなります。アイドル状態で計測）は、次を環境に入れて Workspace Agent を
起動します。

```
AF_OPENCODE_TUI_STANDALONE=1
```

- この設定で Agent が起動したあとに起動するターミナルセッションに効きます。実行中の
  セッションは起動したときのモードのままです。
- `AF_OPENCODE_SERVE_DISABLE=1`（マネージド opencode を無効にする）でも、つなぐ共有サーバーが
  無いため専用サーバーになります。
- opencode 1 に戻したイメージ（下記）では、どちらの変数もターミナルセッションには効きません。

### opencode 1 に戻す

イメージは opencode 2 にピン止めされています（`workspace/Dockerfile` の `OPENCODE_VERSION`）。お使いの環境で
うまく動かないときは、ピンを `1.19.0` にしたイメージで戻します。`--build-arg OPENCODE_VERSION=1.19.0` を
付けて再ビルドし（インストール・自己更新・ドリフト検査は、1.x のピンなら自動で `opencode-ai` を選びます）、
ワークスペースを Stop → Start してください。

- **引き継がれるもの。** 最初の opencode 2 起動で `~/.local/share/opencode/opencode.db` がその場で変換され、
  opencode 1 のセッションが ID のまま取り込まれています。opencode 1 は変換後のファイルでもそのまま動き、
  アップグレード前の会話はすべて見えます。
- **失われるもの。** opencode 2 で作った会話と、opencode 2 で古い会話に足したターンは、opencode 1 からは
  見えません（opencode 1 は opencode 2 が書く表を読みません）。戻したあとに opencode 1 で始めた会話も、
  次に opencode 2 へ上げたときは見えません。データが消えるわけではありません。
- **アップグレードを正確に取り消したいとき。** 最初の opencode 2 起動の前に、ワークスペースの
  `~/.local/share/opencode/opencode.db*` をコピーしておき、戻したあとにそのコピーを書き戻します。
- **以前のオプトインの残り。** `workspace-agent opencode-major 2` を使っていたワークスペース
  （`~/.local/share/agent-fleet/opencode2` の専用インストールと、`opencode2-data` の専用データベース）は、
  ピンが 2.x になるとどちらも使われなくなります。ピン止めされた opencode 2 がメインのデータベースを使い、
  専用データベースにしかないセッションはそちらに**統合されません**。2 つのディレクトリを削除するまでは
  ディスクに残ります。1.x のピンに戻した場合、オプトインは以前どおり動きます。

## インターネットに公開したとき

Control Plane を公開ホスト名で出すと、**数時間のうちに脆弱性スキャナが来ます**（実測: 公開から
9 時間で `/actuator/heapdump` や `/.env` を狙う探索が 172 回）。慌てる必要はありませんが、
知っておくべきことが 3 つあります。

- **セッション無しで届くのは限られています**: `/healthz`・`/readyz`・`/login`・`/oauth2/*`・
  `/brand/*` と旧 URL の転送だけで、それ以外は 401 です。`/internal/*`（egress 取り込み）と `/mcp`・`/git/*` は
  ゲートの外ですが、**それぞれ自前の認証**を持ちます（未有効なら 404）。
- **アクセスログに状態コードが出ます**。`GET /actuator/heapdump 401 0s` のように読めるので、
  「弾いたのか、返してしまったのか」をログだけで判断できます。探索を数えたいなら
  `401` で絞ってください。
- **IP 単位で見たい・遮断したいなら CP の外側で**。送信元別の分析は ALB のアクセスログ、
  遮断は AWS WAF です。CP 側で個別に弾く仕組みは、認証の外に新しい判断を増やすだけなので
  入れていません。AWS 版は `30-ingress` に**既定オフの WAF** があり、
  `WafRateLimitPer5Min`（レート制限）と `WafIpReputation`（AWS の IP 評価リスト）の 2 つだけを
  提供します。**署名系（Core rule set・SQLi・XSS）は意図的に用意していません**。この製品は
  チャット・ファイル書き込み・ターミナル入力という**普通の本文にコードとシェルコマンドが流れる**ので、
  `'; DROP TABLE` や `../../etc/passwd` が正当な通信として現れ、正常な操作がランダムに 403 になります。
  しかも原因が WAF だと気づくまでが長い。
- **社内だけで使うなら、そもそも受け口を絞るのが一番強い**。`00-network` の `AlbIngressCidr` を
  自社の範囲にすれば、探索は ALB に届きません（無料）。

## 2 つの配備を見分ける（色とラベル）

配備が 2 つになった時点（本番の隣にステージング、さらに手元のノート PC）で、タブに並ぶ
アイコンも、スマホのホーム画面も、同じ青緑の猫になります。サインイン画面もどちらのものか
わかりません。Control Plane の設定 2 つで区別できます。どちらも見た目だけの設定で、
アクセス権やデータには一切影響しません。

**どこで設定するか。** 手っ取り早いのは Console の **管理 → 配備全体 → 見た目**
（super_admin のみ）です。色を選んでラベルを入れて保存すれば、再起動なしで次のリクエストから
反映され、見ているタブはその場で変わります。下の環境変数は同じ設定の配備側の入口で、
新しい配備の初期値であり、モーダルの「環境変数に戻す」で戻る先です。**モーダルで保存した値の
ほうが優先される**ので、あとから環境変数を変えても、戻すまでは何も動きません。

| 設定 | 効果 |
|---|---|
| `AF_BRAND_COLOR` | favicon・PWA（ホーム画面）アイコン・Android のタスクスイッチャーの色を変えます。`teal`（同梱の既定）・`blue`・`violet`・`magenta`・`red`・`orange`・`green`・`slate` から選びます。 |
| `AF_BRAND_LABEL` | アプリ名に差し込む短いラベル（16 文字まで）。`[staging] Agent Fleet` の形で、ブラウザのタブ・インストールした PWA の名前・サインイン画面・Console の上部バー（同じ色のチップとして）に出ます。 |

```
AF_BRAND_COLOR=violet
AF_BRAND_LABEL=staging
```

compose は `.env` から読みます。AWS ECS ではスタックパラメータ `BrandColor` / `BrandLabel`、
native ランタイムと `run-dev.sh` は環境変数です。**再起動するだけ**で反映されます。
Control Plane が配信時に同梱の画像を塗り替えるので、環境ごとにイメージを作る必要はありません。

- ラベルが**前置き**なのは意図的です。混み合ったタブもスマホのランチャーも**末尾から**削るので、
  `[staging] Agent Fle…` なら現在地がわかります。
- **すでにインストール済み**の PWA は、インストール時の色・アイコン・名前を持ち続けます。
  Android ではこれらがインストール済みアプリに焼き込まれるので、同じ配備をブラウザの
  タブで見ると新しい色なのに、アプリの中のステータスバーだけ古い色のまま、ということが
  起きます。Chrome はいずれ裏でアプリを作り直しますが数日かかります。**すぐ反映したい
  ときは入れ直してください**。アイコンを長押ししてアンインストールし、ブラウザから
  もう一度インストールします。
- 知らない色名を書いても止まりません。ログに残して `teal` のまま動きます。

## アイドル停止と force-stop

- **終わらない起動は停止されます**: タスクが動かないまま **30 分**起動中の Workspace
  （ECS なら、たいていクラスターがタスクを配置できない場合）を停止し、容量を占有し続けないようにします。
  原因を直せばユーザーはもう一度 **「起動」** を押せます。30 分は最後の起動から数えます。Control Plane
  がそれより後に初めて起動中と見た場合（Control Plane の再起動後など）はその時点から数えます。判定は
  usage のサンプルごと（5 分）なので、停止は最大 1 サンプル分遅れます。メンバーには Console の通知センターに
  起動を止めた旨の通知が最後の起動フェーズ（`ecs-ec2` ならタスクを配置できない理由）付きで届き、テナントの
  管理者にも次の起動まで同じ理由がメンバーの名簿の行とメンバー詳細に出ます。Control Plane のログにも残ります（`start-deadline: stopped …`）。`AF_WORKSPACE_START_DEADLINE` で上限を変え、
  `0` で無効。`ecs-ec2` ではプール自身の起動予算（`AF_ECS_EC2_CLAIM_TTL_SEC`・`AF_ECS_EC2_WAIT_SEC`）
  より短くはなりません。usage サンプラーの上で動くため、`AF_USAGE_SAMPLE_INTERVAL=0` でも無効になります。

- **アイドル自動停止（scale-to-zero）**: 使われていない claude セッションを **1 時間**で停止し、
  何も動いていない Workspace を **2 時間**で停止します。**これが既定**で、
  `AF_SESSION_IDLE_TIMEOUT` / `AF_INTERACTION_IDLE_TIMEOUT`（質問や承認待ちで止まっているセッション）/ `AF_WS_IDLE_TIMEOUT` / `AF_PRESENCE_IDLE_TIMEOUT`（打鍵の無い端末を在席と数える猶予・既定 30 分）で変えられます（テナント単位の上書きは Admin UI。
  テナントが `0` を入れればそのテナントだけ無効、env に `0` を入れれば配備全体で無効）。
  停止した Workspace は、ユーザーが **「起動」を押せば**戻ります。加えて `AF_AUTOSTART`（既定 on）が、
  「今から使う」が明確な操作（セッションの作成・fork・再開、持ち越し質問への回答、SSM ノード探索）
  のときだけ自動で起こします。**ターミナルを開いても起動しませんし、閲覧や Console のリロードでも
  起動しません**（「停止しています。起動してください」を返します）。開きっぱなしのタブが Workspace を
  温め続けることはありません。バックグラウンド作業（アイドルのセッションが起動した開発サーバや
  `run_in_background` のタスク）が Workspace を抱える時間は最大 **2 時間**です
  （`AF_BACKGROUND_HOLD_MAX`、テナント単位は `background_hold_max`。`0` で無制限）。超えると
  Workspace を起こし続ける理由から外れます。本当に長いジョブを残すには「自動停止しない」ピンを使います。
  資源の節約に有効です。env の意味は `deploy/compose/.env.example`、仕組みは
  `docs/build/09-deploy.ja.md` §9.4。ターミナルの claude / agy / codex / cursor / copilot / kiro / opencode セッションが「作業中」と表示されて
  Workspace を起こし続けるのは、生きている兆候がある間だけです。出力・状態の変化・実行中の
  ツールプロセスのいずれも **1 時間**無ければ数えなくなります。これは総作業時間ではなく「変化が
  無い時間」の上限です。claude と agy は実行中のツールプロセスも生存とみなしますが、codex・cursor・
  copilot・kiro・opencode はペインの再描画だけが生存信号です（スピナーや経過時間の更新も含む）。
  そのため、ペインが 1 時間静止したままの無出力ツールは失効し得て、逆にスピナーが動き続ける固まった
  セッションは抱え続けます。これらの kind で長い無出力作業をするときは「自動停止しない」ピンを使ってください。managed の cursor・kiro・codex・opencode セッションも、ランタイム自身の生存信号（そのセッションに関する最後のメッセージ、
  または実行中のツール。未完了のツール呼び出し／item、cursor と kiro はランタイムの下のツールプロセスも）で同じように上限がかかります。
  実測は cursor-agent 2026.10.16・kiro-cli 2.31.0・codex 0.163.0・opencode 2.0.32 のローカル shell ツールです。
  Agent が何が動いているか判断できないとき（再起動・再接続・プロセス表の読み取り失敗）は抱え続けます。
  opencode 1.x と managed の muse・lcpp・copilot はこの上限の対象外です（ADR 0055 の 2026-10-17 追記を参照）。
  shell と ssm は「作業中」にならず、muse と lcpp にはターミナル方式が無いので、これらの kind に上限をかける対象はありません。
  バックグラウンド作業と「自動停止しない」ピンは常に対象外です。
- **force-stop（力業）**: `docker compose down` では**ユーザーの Workspace は止まりません**（compose
  管理外）。特定の Workspace を確実に止めたいときは、super_admin が Console の Admin パネルから
  force-stop します。ホスト全体をメンテナンスで完全に落とす必要があるときは、CP/Caddy を止めた
  うえで、残る `af-ws-*` コンテナを別途 `docker stop` する必要があります（この点は障害対応の
  [06](06-diagnose.ja.md) でも触れます）。
