# 04. セキュリティ運用

[English](04-secure.md) | 日本語

Agent Fleet を安全に運用するために、運用者が**理解しておくべき前提**と**日々行う統制**をまとめ
ます。ここは「隠れたバグの列挙」ではなく、**アーキテクチャに内在する性質を正直に開示し、運用で
どう扱うか**を示すものです。対外向けの脅威モデルは `SECURITY.md`（英語）、
設計の背景は `docs/build/07-security.ja.md` にあり、本書はそれを運用手順に展開します。

## 脅威モデル（要約）

Workspace の中では CLI エージェントが**任意コードを実行**します（`--dangerously-skip-permissions`
を含む運用が既定）。「ユーザーのセッションが untrusted なコードを動かす」前提で境界を引いており、
守る対象は「他ユーザーのデータ・CP/ホスト基盤・シークレット・情報持ち出し」です。主要な隔離境界は
**Workspace（信頼度低）** と **CP とそれが動く基盤（信頼度高）** の間にあります。これは複数利用者の
デプロイ先（`docker`・`ecs`・`ecs-ec2`）の場合です。`native` にこの境界はありません。単一利用者で、
その 1 人が運用者です（`SECURITY.md` の "`docker` and `native`"）。

ツール承認を全部スキップするのは**既定であって固定ではありません**。利用者はエージェント種別ごと
（設定 > エージェント）またはセッション単位（起動時）に承認ありへ戻せます。ただし変わるのは
**事故の起きやすさであって境界の位置ではありません**。選べるのは一部の種別だけで、TUI 内でモードを戻す
こともでき、CLI 自身の設定経路まで塞いでもいません。承認確認は事故を減らす手当と考え、実際に
閉じ込めているのは（複数利用者のデプロイ先では）依然として Workspace の境界だ、という前提は変えずに
運用してください。

- **CP はその配備のすべての Workspace に届く。** CP は Workspace を起動し、それぞれに DEK を渡し、
  `docker` ではマウントされた Docker ソケット越しにホストのデーモンを駆動します。そのため **CP か
  その下の基盤が侵害されると、その配備内の分離は一括で破れます**。
- **会社間は別配備で分離。** 上記の影響は**その配備 1 つの内側に限定**され、他社（= 別
  配備）には波及しません（AWS では、配備ごとに AWS アカウントを分けている場合に限ります）。
  これが 1 社 = 1 配備という提供モデルの核心的な強みです。

## 残存リスク: 運用でどう扱うか

残存リスクの一覧（それぞれ何で、なぜそうなのか）は `SECURITY.md` の "Known residual risks" に
あり、デプロイ先ごと（全デプロイ先共通・`docker` と `native`・`ecs` / `ecs-ec2`）にまとめられて
います。リスクそのものはそちらを読んでください。ここには運用の手順だけを残します。

- **CP が動く基盤への管理アクセスを絞る。** `docker` では**ホストに SSH / sudo / docker を実行できる
  人を最小限に絞り**、Docker ソケットをフィルタリングプロキシ（例 `tecnativa/docker-socket-proxy`）で
  前段することも検討します。AWS では**配備ごとに AWS アカウントを分け**、その管理者を絞ります。
- **`AF_MASTER_KEY`**: **DB や home とは別の金庫に保管し、独立してバックアップする**。データ領域や
  バックアップアーカイブには絶対に置かない（設計上も入りません）。生成タイミングと保管は
  [02 §2](02-install.ja.md)、リストア時の同一性要件は [03](03-run.ja.md)。
  **鍵が無いと、メンバーが保存した認証情報は各ホームに暗号化されずに置かれます。** これは
  `AUTH=dev` のためだけの動作です。それ以外の `AUTH` でも Control Plane は起動しますが、起動時に
  `WARNING` をログに出し、管理画面に警告の帯を出します。鍵なしで動かしてきた配備に後から鍵を
  設定するのは透過ではないので、メンバーと段取りして次の順で行ってください。鍵を設定して Control Plane を
  再起動する。**既存のワークスペースをすべて停止してから起動し直す**（動き続けているものは鍵を持たず、
  平文で書き続けます）。そのうえでメンバーが保存していた認証情報をつなぎ直す。最後に、暗号化されていない
  古いファイル（各ホームの `~/.config/agent-fleet/secrets.json`）を削除し、そこにあった認証情報を
  ローテーションする。このファイルはバックアップにも入っています。
- **バックアップ**: 保管先にアクセスできる人を厳しく限定し、保存時暗号化（at-rest）を徹底する。

補足の限界: 既定では各ワークスペースの資格情報を守る鍵は master 鍵から導かれるため、実効強度は単一
`AF_MASTER_KEY` と同等です。AWS ではこの鍵を KMS に持たせられます（[12 保存時の鍵](12-keys.ja.md)）。詳細は
`docs/build/07-security.ja.md` §7.6。

## 配備の鍵: 要件と変更の代償

2 つの秘密がほかのすべてを守っており、どちらも選んだ値の強さが上限です。

| | `AF_MASTER_KEY` | `AF_COOKIE_SECRET` |
|---|---|---|
| 守るもの | 封じられたすべての値（クライアントシークレット、MCP ヘッダー、ハンドオフ、受信箱）の根、メンバーごとの資格情報ストアの鍵、ワークスペースが Control Plane を呼び返すトークン | セッション・サインイン state・プレビューの各 cookie の署名 |
| 要件 | **ランダムな 32 バイト以上**（hex か base64。生の文字列なら 43 文字以上）。パスフレーズは不可 | 同じ |
| 生成 | `head -c 32 /dev/urandom \| base64` | `head -c 32 /dev/urandom \| base64` |
| 変えたときの代償 | **稼働中の配備では変えないでください。** 古い値で封じたものがすべて開かなくなり、鍵を付け替えるコマンドはありません。[12 保存時の鍵](12-keys.ja.md) を参照 | 全員が一度サインインし直す（後述の「緊急停止」を参照） |

起動時の検査が測るのは長さだけです（数種類のバイトの繰り返しも弾きます）。長いパスフレーズとランダムな
バイト列は区別できません。値は必ず生成してください。このリリースでは、検査に通らない値でも
**Control Plane は止まりません**。起動時に `WARNING` をログに出し、管理画面に警告の帯を出します
（`deployment_warnings` の `weak_master_key`、`weak_cookie_secret`）。後のリリースでは `AUTH=dev` 以外で
起動を拒否するので、指摘された値は次の計画的な作業枠で入れ替えてください。検査は値をログに出しません。
`deploy/aws/ecs/standup.sh` も保存済みのパラメータを同じ基準で調べ、OK か too short だけを表示します。

### cookie の鍵を用途ごとに分ける切り替え

Control Plane は、セッション・サインイン state・プレビューの各 cookie を用途ごとに別の鍵で署名できます。
ある用途のために作られた cookie が、別の用途では検証を通らなくなります。前のリリースのレプリカは新しい形式を
読めないため、切り替えは 2 段階で、**既定ではオフ**です。

1. このリリースをすべてのレプリカに配備します。両方の形式を読み、発行は従来の形式のままなので、
   ローリング更新でも誰もサインアウトされません。
2. 前のリリースのレプリカが無くなったら、`AF_COOKIE_PURPOSE_KEYS=1` を設定して再起動します
   （レプリカは 1 台ずつ再起動して構いません。設定の違う両者は互いの cookie を受け付けます）。
   切り替え前に発行された cookie は、セッション 1 回分の期間（`AF_SESSION_TTL`、既定 7 日）だけ使え、
   そのあと失効します。サインイン state とプレビューのトークンは数分で切れます。それまでは古い形式が
   用途で分かれていません。

オフに戻すのは、このリリースが両方の形式を読めるので問題ありません。手順 2 のあとで前のリリースへ
ロールバックしたときだけ、新しい形式を読めないため全員がサインアウトされます。

### 鍵を設定する前に保存された値

`AF_MASTER_KEY` が無い Control Plane は、一部の値を暗号化せずに保存しました（テナントのサインイン・Git OAuth の
クライアントシークレット、MCP のヘッダーとクライアントシークレット、エンジンのトークン、ハンドオフ、共有提案、
受信箱のメッセージ）。**後から鍵を設定しても、それらは封じられません**。そのまま読まれます。残っている間は、
起動時に `WARNING` をログに出し、管理画面に警告の帯を出します（`plaintext_sealed`）。

管理者が編集していないときに、Control Plane と同じ設定・データベースで封じます。

```
af-cp rewrap-keys --seal-plaintext --dry-run   # 数えるだけで何も変えない
af-cp rewrap-keys --seal-plaintext
```

ローカルの鍵管理でも `AF_KEY_CUSTODIAN=kms` でも動きます（設定されているほうで封じます）。1 行ずつ書き、
封じた値をもう一度開いて照合してから書き込み、最後の読み取り専用の確認で残りが無いときだけ終了コード 0 を
返します。警告の帯は数分以内（または次の再起動）で消えます。KMS も使う場合は、続けて [12](12-keys.ja.md) の
`af-cp rewrap-keys` を行ってください。これらの値は、これまでデータベースとバックアップから読める状態でした。
**発行元でもローテーションしてください**（IdP と Git OAuth のクライアントシークレット、MCP のトークン、
Hugging Face / Civitai / ComfyUI のトークン）。不要なバックアップは削除します。

## egress 統制の運用

Workspace からの外向き通信（egress）を統制する仕組みがあります。**forward proxy 方式**で FQDN
（CONNECT/SNI）を見て allow/deny を判定し、TLS は復号しません。super_admin だけが Console の Admin
パネルの **egress** タブで操作します。

**段階的に入れるのが設計の核**です。次の順で進めてください。

1. **log-only（観測のみ・既定）**：通信を遮断せず、宛先を記録するだけ。Admin の「観測された宛先」に
   ホストごとの許可/遮断候補件数が積み上がります。まずここで**実態を把握**します。
2. **allowlist を固める**：観測結果を見ながら、正当な宛先を許可リストに追加していきます。許可
   リストは版管理され（active / proposed / retired）、AI は**提案のみ・承認は人間**が行います
   （Admin の「提案中（要承認）」で承認/却下）。エントリは **host** か **`.suffix.example.com`** の形式で、理由を添えられ、
   不要になったら**取消**します。追加分が無い場合は製品既定の許可だけが有効です。製品既定には、ワークスペース自身のインストーラ（JDK・Node.js・Go・gcloud・MySQL・Postgres・Chromium）と、起動時に導入・更新するエージェント CLI（Claude・Cursor・Kiro・muse・Antigravity）のダウンロード元が含まれるので、enforce でも 設定 › ツールチェーン と起動時の導入はそのまま動きます。例外は `storage.googleapis.com` です。Antigravity の CLI は両アーキテクチャで初回導入と更新のたびにここから取得し、x64 での Chromium のオンデマンド導入もここから取得します。誰でもアップロードできる汎用のストレージなので既定には入れていません。Antigravity を使うか、x64 で Chromium を導入するワークスペースがあるときに追加してください。このデプロイ自身の Control Plane のホスト（公開 URL と、設定されていれば内部 URL）は常に許可され、**組み込み**として表示されます。ワークスペースは egress の経路を通って Control Plane に届くため、これは取り消せず、専用の名前で 80/443 で提供される Control Plane からは enforce でも切り離されません。エントリはホスト全体（どのポート・パスも）なので、Control Plane にはほかのサービスと共有しないホスト名を付けてください。gateway のほかの拒否（ほかのポート、内部アドレス）は解除しません。IPv6 リテラルの URL（`https://[2001:db8::5]`）は、小文字・圧縮形のアドレスとして、角括弧なしと角括弧つきの両方の表記で gateway に渡されます（ACL の照合は Squid 6.13 で確認済みです。実際の Control Plane への IPv6 到達と、お使いの Squid のバージョンでは未確認なので、ワークスペースから届くことを確かめてください）。ゾーン ID 付き、IPv4 射影・IPv4 互換、ループバック／リンクローカル／マルチキャストのアドレスは許可されず、起動時に Control Plane が警告をログに出します。自分で追加するエントリはホスト名と `.suffix` のままで、IPv6 リテラルは手では追加できません。メンバーが ⚙設定 →「MCP サーバー（セッションで使う）」で
   出した申請も提案として届き、あなたが決めるまでメンバー側には「管理者の承認待ちです」と出ます。

   **観測結果の読み方：** 件数は概数です。タイムアウト後に再送された報告は二重に数えられる
   ことがあり、Control Plane に届かない間 proxy が保持するのは最大 5000 宛先で（超過分は
   監査ログの `egress.dropped` に出ます）、proxy を再起動するとメモリ上の分は失われます。
   載っていないホストは「見ていない」だけで「使われていない」ではありません。enforce に
   する前に `egress.dropped` が無いか監査ログで確認してください。
   egress ゲートウェイが接続を記録する構成（AWS で `EgressRoute=gateway`）では、接続ごとにワークスペースへ
   紐づけた生イベントも残り、`GET /api/admin/egress/events`（super_admin）で読めます（Admin の画面に出るのは
   ホストごとの件数だけです）。生イベントは `AF_EGRESS_EVENT_RETENTION_DAYS`（既定 30 日、`0` で無期限）を過ぎると
   削除され、ホストごとの件数は残ります。
   それより長く残すには `AF_EGRESS_ARCHIVE_URL`（`s3://bucket/prefix`・`gs://bucket/prefix`・`file:///dir`。
   空が既定で無効）を設定します。Control Plane は削除する前に、過ぎた UTC の日ごとにここへ保存します。
   GKE では `deploy/gcp/gke` の `egress_archive = true` で非公開のバケットを作り（既存のバケットなら
   `egress_archive_existing_bucket`）、Control Plane の Google サービスアカウントに**そのバケットだけ**への
   `roles/storage.objectCreator` と `roles/storage.objectViewer` を付け、`cp.env` に足す行を
   `terraform output -raw egress_archive_env` で出します（追記ではなく既存の行を置き換え、アーカイブを止めるときは行を削除します）。viewer が無いと、先に書いた日を Control Plane が
   検証できず、purge がその日で止まります。`egress_archive_retention_days` を指定しない限り、バケットの中身は
   期限切れになりません。AWS ではデータスタックの `EgressArchive` パラメータです。
   **HTTP 以外の宛先（AWS の egress ゲートウェイのみ）。** SSH の git やデータベースは HTTP ではないので、
   ホストのエントリでは通りません。**`tcp:<host>:<port>`** のエントリ（`tcp:git.example.com:22`、
   `tcp:db.example.com:1433`、範囲なら `tcp:db.example.com:11000-11999`。範囲は最大 2048 ポート、完全なホストか
   IPv4 アドレスで、53・80・443・853・3128 は不可）を足さない限り、enforce では遮断されます（log-only では通って記録されます）。申請と承認は同じ流れで、
   承認するとそのホストへの HTTP 以外のアクセスが開きます。ゲートウェイはそのホストが解決されるアドレスへ、
   そのポートだけを通し、接続ごとにアドレスとポートを記録します。log-only では名前の無い宛先は通して
   遮断候補として表示し、enforce では落として記録します。切り替える前に、宛先側のファイアウォールが
   ゲートウェイの egress アドレスを通す必要があります。詳細は `deploy/aws/ecs/README.md` の
   「Egress gateway」。
3. **enforce へ切替**：許可リストが十分に固まってから、モードを enforce に切り替えます。以降は
   許可リスト外の通信を**遮断**します。いきなり enforce にするとエージェントの更新取得や MCP の接続先など必要な通信まで落ちるので、log-only のうちに
   「観測された宛先」の遮断候補を解消しておくと切替えが穏やかに済みます。Admin の UI も「先に log-only で実態を
   確認してから切替えてください」と警告します。

> 現状の実装範囲: **観測（log-only）と許可リスト管理が動作し、proxy 自体は遮断（enforce）できます**。
> Control Plane に `AF_EGRESS_PROXY_ADDR` を設定すると、どのターゲットでも
> すべての Workspace に `http_proxy` / `https_proxy` / `no_proxy`（と大文字の同名変数）が注入され
> （既定はオフ）、これらの変数に従うプログラムは proxy を通ります。CP の内部アドレス
> （`AF_CP_INTERNAL_URL`）は docker・Kubernetes・ecs・ecs-ec2 で proxy の対象から外され、ecs / ecs-ec2 では
> proxy がリンクローカル宛を拒否するため、タスク／インスタンスのメタデータアドレス
> （`169.254.170.2`・`169.254.169.254`）も対象から外されます。**まだ無い**のは、proxy を通ることの強制（proxy だけを出口に残す内部網や
> セキュリティグループの egress ルール、proxy を動かすテンプレート）です。変数を無視する
> プロセスはそのまま外へ出るので、**enforce へ切り替えても、まだ Workspace は縛られません**。
> 例外は AWS（`ecs` / `ecs-ec2`）で `00-network` の `EgressRoute=gateway` を選んだ場合です。
> Workspace のルートテーブルが egress ゲートウェイ（Squid）を通るので、Workspace に他の出口は無く、
> enforce が効きます。この選択肢は新しく、テスト用の配備でだけ確認済みで、**本番ではまだ使っていません**
> （[配備形態の選び方](01-choose.ja.md) の「AWS の出口経路の選び方」）。
> それ以外では「観測して許可リストを育てる」段階まで運用できる、と理解してください。設計の全体像は
> `docs/build/07-security.ja.md` §7.8。

## MCP サーバーと外部接続

利用者は ⚙設定 →「MCP サーバー（セッションで使う）」で**自分の MCP サーバーを登録**でき、テナント管理者は
**全メンバーへ配布**できます（[admin/04](../admin/04-mcp-outside.ja.md#mcp-サーバーをテナント全員に配るあなたの権限)）。運用者として押さえる点は
4 つです。

- **秘密の置き場所。** 環境変数とヘッダの値は封筒暗号で保存されます。加えて、そのサーバーを使う各エージェント CLI の
  設定ファイルにも、CLI が読む必要があるため、平文（ファイルモード 0600、メンバーの home 内）で書き出されます。
  このファイルは home のバックアップとスナップショットに入り、Workspace の鍵を破棄しても消えません。
- **配布できるのはリモート（HTTP）だけ。** stdio の配布は「管理者が全員のコンテナで任意コマンドを
  実行できる」ことと等価になるため、仕様として禁じています（個人登録では stdio も使えます）。
- **egress と直結します。** 接続先ホストが許可リストに無ければ、登録しても動きません。利用者からの
  許可申請は Admin の egress タブに「提案中（要承認）」として届きます（上記の運用手順を参照）。
- **外部から入ってくる口もあります。** 利用者は（外部からのアクセス →）「MCP トークン・接続アプリ」でトークンを発行して、手元の Claude Code /
  Claude Desktop からワークスペースを遠隔操作できます。エンドポイントは `/mcp`（Bearer 認証）で、
  配備側では機能フラグ（`AF_MCP_ENABLED`）と、ingress で `/mcp` を通すかどうかが効きます。
  スコープ（read / write / admin:dangerous）と有効期限は利用者が選び、失効も本人が行えます。
  この入口から、メンバーは自分のエージェントに自分の Agent Fleet メモリを使わせることもできます。メンバーごとの別設定で、
  既定はオフです（[メンバー編](../member/18-agent-memory.ja.md#外部のエージェントから-agent-fleet-のメモリを使う) 設定 > エージェントメモリ > 設定）。外からの保存と忘却は監査されます（`memory.entry.save` /
  `memory.entry.forget`、実行者は `mcp`、対象はプロジェクト ID）。テナント管理者はテナント全体でこれをブロックでき
  （[管理 04](../admin/04-mcp-outside.ja.md#agent-fleet-の外からのメモリ利用)）、`AF_MCP_ENABLED` はエンドポイント全体を止めます。

### リモート MCP クライアント向けのサインイン（OAuth）

既定では `/mcp` は Personal Access Token だけを受け付けます。`AF_MCP_OAUTH=1` を設定すると、Control Plane が `/mcp` 用の OAuth 2.1
認可サーバーにもなり（ADR 0118）、claude.ai・ChatGPT・Claude Code・Codex は
トークンを貼り付ける代わりに、メンバーが Console にサインインして接続できます。CI などの OAuth を使えないクライアント向けに PAT は引き続き使えます。

| 設定 | 意味 |
|---|---|
| `AF_MCP_OAUTH=1` | サーバーを有効にします。`AF_MCP_ENABLED=true` と `https` の `PUBLIC_BASE_URL` も必要です。どれか欠けていると、以下のパスはすべて 404、`/mcp` は従来どおりの素の 401 になり、クライアントはトークンを求める動作に戻ります |
| `AF_MCP_OAUTH_TRUSTED_HOSTS` | サインインのリダイレクト先になれる／クライアントメタデータを配信できる項目のカンマ区切り。ホスト名（全パス）か `https://host/path` の URL プレフィックス。既定は `https://claude.ai/api/mcp/auth_callback,claude.com,chatgpt.com`。`none` でループバックのクライアントだけになります。super admin は実行時に上書きできます（[信頼するクライアントのホスト](#信頼するクライアントのホスト配備全体-superadmin-のみ)）|

- **有効にする方法。** Compose / native / local: Control Plane の環境に `AF_MCP_ENABLED=true` と `AF_MCP_OAUTH=1`（この値そのもの。
  `AF_MCP_ENABLED` に `1` は通りません）、必要なら `AF_MCP_OAUTH_TRUSTED_HOSTS` を設定します。Kubernetes: Control Plane の
  環境ファイル（`cp.env`）に追記します。**ECS:** 30-ingress のパラメータ `McpEnabled=on`、`McpOAuth=on`、必要なら
  `McpOAuthTrustedHosts` を、`30-ingress.yaml` に対する個別の `aws cloudformation deploy`
  （`--parameter-overrides McpEnabled=on McpOAuth=on`）で設定します。`update.sh` が上書きするのは `ImageTag` と、ほかのスタックから読む事実（`EfsBackup`・`WorkspaceSubnets`・egress のパラメータ）だけなので、
  これらを有効にも無効にもしません（パラメータは前回の値を保ち、スタックにまだ無いパラメータはオフで始まります）。
  詳しくは [`deploy/aws/ecs/README.md`](https://github.com/k-k1/agent-fleet/blob/main/deploy/aws/ecs/README.md) を参照してください。
- **提供されるパス**（issuer は `{PUBLIC_BASE_URL}/mcp-oauth`）: `/.well-known/oauth-protected-resource/mcp`、
  `/.well-known/oauth-protected-resource/mcp/memory`、`/.well-known/oauth-authorization-server/mcp-oauth`、`/mcp-oauth/authorize`、`/mcp-oauth/consent`、
  `/mcp-oauth/token`、`/mcp-oauth/register`、`/mcp-oauth/revoke`。`/mcp` の 401 には
  `WWW-Authenticate: Bearer resource_metadata="…"` が付きます（提示されたトークンが無効な場合は `, error="invalid_token"` が付きます）。
  スコープはクライアントが要求し、同意ページは `read` を初期選択して、要求された場合だけ `write` を表示します。
- **ingress。** ホスト型クライアントは `/mcp` とトークンエンドポイントを**ベンダーのサーバーから**呼ぶので、Control Plane はこれらのパスでインターネットから
  到達できる必要があります。VPN の内側や ALB の ingress CIDR を絞った配備では、コマンドライン（ループバック）のクライアントだけが使えます。これは仕様であり不具合ではありません。
  `AUTH=oauth` と `AUTH=dev` では Console 自身のセッションゲートが、探索・`token`・`register`・`revoke` を素通しにし、`authorize` と `consent` はゲートの内側に置きます。
  **`AUTH=proxy`** ではゲートウェイ側で同じ設定が必要です。`/mcp-oauth/authorize` と `/mcp-oauth/consent` はゲートウェイを**通し**（メンバーの
  識別ヘッダーはそこで付きます）、残りの 6 パスと `/mcp`・`/mcp/memory` はゲートウェイを**迂回**させます。
- **2 つのリソース。** `/mcp` はすべてのツールを、`/mcp/memory` は外部メモリの 6 つのツールだけを提供します。後者は、claude.ai が
  メンバーのワークスペースのセッションにも渡してしまうコネクタ向けです。それぞれ専用のメタデータ文書と 401 チャレンジを持ち、相手のトークンを
  拒否します。OAuth のコード・グラント・トークンはクライアントが求めたリソースに結び付き（リフレッシュでも変わりません）、Personal Access Token は
  1 つのエンドポイント向けに発行されます（既定は `mcp`。分離前に発行したトークンもすべて `mcp`）。テナントのスイッチ、メンバーのメモリ設定、
  スコープの段階、監査記録は両方で同じです。
- **クライアントになれるもの。** 登録は誰でもできますが（動的クライアント登録は送信元ごとのレート制限と総数の上限があり、グラントが一度も生まれない登録は 30 日で削除されます）、
  登録で決められるのはコードの*送り先*だけなので、リダイレクトはループバックか、信頼リスト上のホストの `https` アドレスで、表記も正規形
  （大文字・末尾のドット・明示ポート・ユーザー情報・フラグメントなし）に限ります。メタデータ文書の URL でクライアントを示す場合は、その URL が同じリストにあるときだけ取得し、
  リダイレクトは追わず、短いタイムアウトとサイズ上限を課し、公開アドレス以外には接続しません。
- **トークン。** アクセストークンは不透明で 1 時間有効、`{PUBLIC_BASE_URL}/mcp` か `{PUBLIC_BASE_URL}/mcp/memory` に結び付きます。リフレッシュトークンは使うたびに更新され、使用済みのものが
  再提示されると接続全体が取り消されます。接続は 30 日間使われないか、90 日たつと終わります。保存されるのはハッシュだけで、PAT の行ではないため 20 個の PAT 上限には数えません。
- **監査。** `mcp.oauth.grant`（作成・取り消し・再利用による取り消し）と `mcp.oauth.token`（発行のたび）は、応答を返す前に書き込まれます。接続を使った呼び出しは、
  接続 ID を実行者として `mcp` で記録されます。監査ストアが止まっているときはトークンを発行しません。
  テナント設定の変更は `tenant.mcp_oauth`（`enabled=true/false`）で記録します。メンバーによる失効は
  `mcp.oauth.grant` の `revoked by member`、テナント無効化による失効は接続ごとの `revoked reason=tenant-disabled` です。
  無効化と競合してコード交換を拒否した場合は `refused reason=tenant-disabled` を追記し、発行前に記録した `created` が
  接続の成立ではなく試行だったと分かるようにします。
- **スコープ。** `read` と `write` だけです。`admin:dangerous` は、メンバーのロールにかかわらず OAuth では付与されません。
- **テナントのネットワーク制限**は確認（同意）の段階、つまりブラウザの前にいる人に適用されます。ベンダーのサーバーから来る `/mcp` とトークンエンドポイントには、PAT と同じく適用されません
  （ADR 0047）。

### 信頼するクライアントのホスト（配備全体 — super_admin のみ）

**管理 → 配備 → MCP ログイン許可ホスト** で、この配備の MCP OAuth サーバーが信頼するクライアントのホスト（サインイン後のリダイレクトを受け取れるホスト、およびクライアントメタデータを配信できるホスト）を編集します。テナントごとではなく配備全体の設定で、super administrator だけに表示されます。ループバックのクライアント（メンバー自身のマシン上の CLI など）は常に許可されます。

- **別の Agent Fleet 環境からこの環境の `/mcp` にサインインさせたいときは、そのホストをここに追加します**（ホスト名のみ。例: `af.example.com`）。
- **ベンダーを外すこともできます**: `chatgpt.com` を消して保存すれば、そのベンダーはサインインできなくなります。空の一覧を保存すると、ホスト経由のクライアントは一切信頼しません。
- 項目は、ホスト名の完全一致（`chatgpt.com`: そのホストの**すべてのパス**を許可）か、`https://host/path` の URL プレフィックス（`https://claude.ai/api/mcp/auth_callback`: そのパスとその下のパスセグメントだけを許可し、`…/auth_callbackx` のような長い名前は許可しません）のどちらかです。ポート・クエリ・ワイルドカード・IP アドレスは使えず、エンコード文字・`.` / `..`・空のセグメントを含むパスは一致しません。誤りがあるとメッセージとともに拒否され、何も保存されません。**URL プレフィックスを推奨します。** 動的クライアント登録はサインイン不要なので、ホスト名だけの項目は、大きな共有ホストで第三者が管理するパスも含め、全パスを信頼します。ホスト名だけの項目が有効な間は、画面に警告が出ます。既存の保存済みの一覧はそのまま動きます（ホスト名だけの項目は従来どおり「全パス」）。
- **登録数の上限**: 配備全体で動的登録は最大 2,000 件です。一度も接続されなかった登録は 24 時間で失効し、上限に達すると、そのような登録のうち最も古いものを削除して空きを作ります（接続のあるクライアントは削除されません）。上限に達すると、その後 24 時間は管理画面に警告が出ます（Control Plane のレプリカごと）。登録は送信元ごとに 1 時間 10 件までで、IPv6 の送信元は /64 全体で 1 つと数えます。
- 同意画面にはリダイレクト先の URI 全体と、クライアントがメタデータ文書（CIMD）と動的登録（DCR）のどちら由来かが表示されます。監査ログ `mcp.oauth.grant` には `via=cimd|dcr` と `redirect_path` が記録されます。
- **どの一覧が適用されるか**: ここで保存した一覧が最優先で、保存がなければ環境変数 `AF_MCP_OAUTH_TRUSTED_HOSTS`、それも未設定なら組み込みの既定値（`https://claude.ai/api/mcp/auth_callback`・`claude.com`・`chatgpt.com`。後の 2 つは、ChatGPT が固定のリダイレクトを使わないときはパスが接続ごとに変わり、`claude.com` のパスはここに記載がないため、ホスト名のままです）です。どれが適用中かは画面に表示されます。**既定に戻す**は保存した一覧を削除し、残りの 2 つが再び適用されます。
- 変更は次のリクエストから、再起動なしで、新しいサインイン・クライアント登録・トークン要求に反映されます。リダイレクト先のホスト（メタデータ URL のクライアントではそのクライアント自身のホスト）を外すと、その接続はトークン更新も未使用コードの交換もできなくなります。発行済みのアクセストークンは期限（最長 1 時間）まで使えます。ループバックの接続は影響を受けません。変更はすべて監査されます（`mcp_oauth.trusted_hosts.set` / `.reset`。変更前後の一覧を含みます）。
- **クライアントのホストが公開アドレスでない場合、メタデータ URL（CIMD）でのサインインは失敗します。** Control Plane は `client_id` のホストからクライアントのメタデータ文書を取得しますが、Control Plane から名前解決したアドレスが公開アドレスでないホスト（ループバック、プライベート範囲、リンクローカル、tailnet のアドレスが属するキャリアグレード NAT の `100.64.0.0/10` など）は拒否します。そのため、クライアント側の環境の名前がここから見てそのようなアドレスに解決される場合、この一覧に載せていても、サインインは `authorize` で汎用の拒否ページに止まります。そのクライアントでは動的クライアント登録（DCR）だけが使えます。クライアント側の「最後まで終わっていません」の案内に **動的登録でやり直す** ボタンがあります。この確認は意図的な SSRF 対策で、設定では変えられません。CIMD を使いたい場合は、Control Plane から見た名前解決を直してください。

### メンバーが登録した OAuth 必須の MCP サーバーへのサインイン

上の節とは逆向きです。メンバーが OAuth しか受け付けないリモート MCP サーバーを登録したとき、メンバー自身の Agent がそのサーバーにサインインします（ADR 0119）。
Control Plane はそのために 2 つの公開パスを持ち、どちらも到達できる `PUBLIC_BASE_URL` が必要です。

- `GET {PUBLIC_BASE_URL}/oauth2/mcp/callback` — サーバーの認可サーバーがブラウザを戻す先です。すでにセッションゲートの外にある `/oauth2/` の下にあり、
  呼び出した人の確認は自分で行います（`AUTH=oauth` では Console のセッション、`AUTH=proxy` ではゲートウェイの識別ヘッダー）。ブラウザはサインインを始めたメンバー本人のものでなければならず、サインインは 10 分間・1 回だけ有効です。
- `GET {PUBLIC_BASE_URL}/oauth/mcp-client.json` — クライアント ID メタデータ文書（CIMD）です。`PUBLIC_BASE_URL` が `https` のときだけ配信します。
  CIMD に対応する認可サーバーは**その側のサーバーから**取得するので、`AUTH=proxy` ではゲートウェイがこのパスだけを認証なしで通す必要があります。
  `/oauth/` の下のほかのパスは公開しません。コールバックは逆に、メンバーの識別ヘッダーが付くよう**ゲートウェイを通す**必要があります。識別がなければサインインは失敗します。`https` の基底 URL がない場合や認可サーバーが取得できない場合、Agent は動的クライアント登録に切り替えるか、メンバーにクライアント ID を尋ねます。

トークンは Agent がメンバーの暗号化ストアに保存します。Control Plane を通るのは 1 つの場合だけです。テナント管理者が、自分で登録した
**confidential クライアント**（クライアントシークレット付き）でそのサーバーを配布した場合です。シークレットは Control Plane に残るので、
メンバーの Agent に代わって Control Plane がトークン・更新・失効の要求を行い、応答を保存せずにそのまま返します。この場合だけは
**Control Plane** 自身が `https` で認可サーバーに到達できる必要があります（トークンエンドポイントは管理者が入力した issuer から自分で探し、
公開アドレスにだけ接続し、リダイレクトは追いません）。それ以外の要求はワークスペースから行います。Control Plane は `mcp.client_oauth` の監査行（`started` / `completed` / `failed` / `disconnected`）に、
サーバーと認可サーバーの名前だけを書き、コードやトークンは書きません。メンバーは設定 › MCP サーバー（セッションで使う）からサインインします（[メンバー向け 20](../member/20-settings.ja.md#mcp-サーバーセッションで使う)）。

### クライアントが `/mcp` に送ったものを読む

`/mcp` へのリクエストは、拒否されたもの、認証より前に 405 で答える `GET` / `DELETE`、バッチの各要素も含め、
1 件ごとに Control Plane のログへ 1 行出ます。接続はできるのにツールが出ないクライアントでも、実際に何をしたかから原因を追えます。

```
mcp-call endpoint="/mcp" http_method="POST" status=400 latency_ms=2 principal="grant:<id>" client_id="<id>" header_version="2026-07-28" mcp_method_header=false mcp_name_header=false accept="application/json, text/event-stream" content_type="application/json" user_agent="…" items=[{"method":"tools/list","era":"stateless","meta_version":"2026-07-28","client_name":"…","status":400,"error_code":-32020,"error_message":"header mismatch: Mcp-Method (absent) does not match body method \"tools/list\""}]
```

- `endpoint` はリクエスト先のパスで、`/mcp` か `/mcp/memory` です。
- `principal` は `pat:<id>`、`grant:<id>`（OAuth。続けて `client_id`）、`unauthenticated` のいずれかで、拒否したときは `reason=` に理由が入ります
  （Bearer なし、不明・期限切れのトークン、別リソース向けの OAuth トークン、別エンドポイント向けの PAT、`method not allowed`）。
- `era` は `legacy`（`initialize` ハンドシェイク）か `stateless`（2026-07-28。毎回 `_meta` を付ける）です。stateless で拒否されたときは
  JSON-RPC の `error_code`（-32020 ヘッダ不一致、-32022 非対応バージョン、-32602 `_meta` の欠落（`clientInfo` と `clientCapabilities` を含む））と、`Mcp-Method` / `Mcp-Name` ヘッダの有無が出ます。
  `tools/list` の要素には返したツール数 `tools` が付きます。実行して失敗した `tools/call`（200 で `isError`）には、本文なしで `tool_error:true` が付きます。
- トークン、`Authorization` の値、リクエストの引数、ツールの結果は記録しません。`tools/call` / `prompts/get` のツール名 / プロンプト名だけ記録します。
- 認証できた呼び出し者の記録は、本人が 設定 → 外部からのアクセス → MCP トークン・接続アプリ →「最近の呼び出し」で読めます（トークン / 接続ごとに直近 50 件、
  メモリ上のみで再起動すると消え、**Control Plane のレプリカごと**）。レプリカが複数あるときは全レプリカのログを探してください。405 と未認証のリクエストはログにしか残りません。

## ワークスペース内ブラウザの引き渡し

エージェントは、ワークスペース内で自分が起動した Chromium のページを Console のペインとして
利用者へ引き渡せます（ログイン操作などを人にやってもらうため）。remote debugging は
**loopback だけ**に開き、引き渡した直後は **view-only**（利用者の入力を一切通さない）から始まり、
操作を許すには明示的に user-control へ移す必要があります。CDP エンドポイントや cookie を
回答・ログ・コミットへ出さないことは、エージェント側の指示にも書かれています。

## `AUTH=dev` は既定値ではありません

`AUTH` に既定値はありません。`AUTH=dev` はサインインが一切ない状態で、すべてのリクエストが固定の
`super_admin` になります。そのため native 以外のランタイムでは、`AUTH` が未設定だと Control Plane は起動を拒否し、
`AUTH=dev` は `AF_ALLOW_INSECURE_DEV_AUTH=1` も設定したときだけ受け付けます（自分のマシンでの試用のみ）。
その場合も起動時に `WARNING` をログに出し、管理画面に警告の帯を出します。`PUBLIC_BASE_URL` が https のときは
`AUTH=dev` を一切受け付けません。native ランタイムは設計上単独利用なので、どちらの手順もなく `dev` を使えます。
共有する配備には `AUTH=oauth` か `AUTH=proxy` を設定してください。

## 開発用ログイン（開発用 OIDC IdP — super_admin のみ）

Admin モーダルの**開発用ログイン**で、Control Plane の開発用 OIDC IdP（ADR 0116）を配備全体でオン・オフします。
**既定はオン**で、super_admin だけの設定なので、テナント管理者には見えません。ワークスペースごとのスイッチはなく、
オン（かつプレビュー用サブドメインがある）の間はすべてのワークスペースのクライアントが対象です。

- 画面には issuer、クライアントを持つワークスペース数（IdP が提供されている間にワークスペースが起動すると作られ、
  その後も残ります）、そして肝心の一点が出ます。**本番のアプリはこの issuer を
  絶対に信頼しないでください**。パスワードなしで任意のメンバーとしてサインインできてしまうからです。
- オフにすると再起動なしで反映され（別の Control Plane レプリカも数秒で追随）、`/dev-idp/…` は全部 404 になります。
  **ワークスペースのクライアント登録は残る**ので、オンに戻せば同じ client id と secret が戻ります。
- **メンバーが使えるのはプレビュー用サブドメインがある環境だけ**です。プレビュー用ドメイン（`AF_PREVIEW_DOMAIN`）が
  無いと、この画面にその旨が出て、`/dev-idp/…` は 404、ワークスペースには何も渡されず、ワークスペースからは利用不可と
  見えます。スイッチ自体は操作できます。
- 運用者が `AF_DEV_IDP=0` を設定していると固定表示になり、`PUBLIC_BASE_URL` が無いとオンにできません。どちらに
  当たるかは画面に出ます。変更は毎回監査されます（`dev_idp.set`）。

## その他の運用上の統制

- **プレビュー用ドメインは別の登録可能ドメインに置く。** ログイン cookie は `SameSite=Lax` で、兄弟サブドメインは
  同一サイト扱いになるため、Console と同じドメイン配下のプレビューホストから配信されたページも、メンバーの
  cookie を付けて Console へリクエストできます。Control Plane は、cookie 認証の書き込みのうち
  `Sec-Fetch-Site` が `same-origin` でないもの、`Origin` が Console 自身のホストでないものを 403 で拒否し、
  `/api/` のボディに `application/json`（アップロードは `multipart/form-data`）を要求し、
  `X-Frame-Options: DENY` と `frame-ancestors 'self'` を返します。これらは安全網です。より強い構成は、
  `AF_PREVIEW_DOMAIN` を別の登録可能ドメインに置くこと（例: Console が `af.example.com`、プレビューが
  `*.af-preview.example.net`）で、cookie がそもそも送られなくなります。cookie 名は `af_session` で
  `__Host-` 接頭辞はまだ付かないため、`__Host-` 名は現時点では選べません。`AUTH=proxy` の背後では、ゲートウェイが
  `Host` をそのまま渡す（または `PUBLIC_BASE_URL` に公開ホストを設定する）必要があります。`Origin` の照合先が
  それだからで、WebSocket の接続と同じ条件です。
- **サインイン許可リストは fail-closed。** `AF_OAUTH_ALLOWED_*` の 3 系統がすべて空で、**かつ
  membership を持つ人も自動参加ドメインも無い**場合、全サインインを拒否します。`_EMAILS_FILE` は
  サインインごとに再読込されるので、**追加は CP 再起動なしで反映**されます（削除も同様）。判定は
  サインイン時だけでなく**毎リクエスト**走るため、リストから外した人は `AF_SESSION_TTL` の満了を
  待たずに**次のリクエストで**締め出されます（＝これがオフボーディング経路）。
  設定は [02 §6](02-install.ja.md)。
- **招待されたこと自体が、サインインできる資格になる。** 管理画面でテナントに追加された人は
  `AF_OAUTH_ALLOWED_*` に載っていなくてもサインインできます。招待運用の配備では名簿が
  1 箇所（membership）に寄り、ずれる 2 つ目のリストを持たずに済みます。入口を通ることは
  「どこかに入れる」を意味しません。使えるテナントの判定は別で、membership の無い人は
  従来どおり「管理者に依頼してください」の画面で止まります。
- **サインイン provider ごとに「その email をなぜ信じてよいか」を宣言させている。**
  `AF_OIDC_<ID>_TRUST`（`email_verified` または `issuer`）は必須で、宣言の無い provider は起動時に
  無効化されます。これは、許可リストがメールアドレスで書かれている以上、ここが認可の強度そのものだから
  です。特に Entra ID の issuer は自社テナント GUID に固定してください。`/common/` や
  `/organizations/` では Microsoft アカウントを持つ誰でもサインイン画面に進め、個人アカウントは
  自分の email を付け替えられるため、`AF_OIDC_<ID>_ALLOWED_TIDS` が無い限り CP は起動を拒否します
  （[05 §4](05-signin.ja.md) / `docs/build/07-security.ja.md` §7.3）。
- **監査ログ。** 変更・破壊操作のみが `audit_log` に記録されます（読み取りは記録しない。例外はメンバーの
  エージェントメモリーの書き出し。**ターミナルの生ストリームは秘密混入リスクのため保存しません**）。閲覧は super_admin / tenant_admin が Admin の
  audit タブから。運用上の見方は admin 分冊が扱います。
- **ベンダー製の同種機能を意図的に無効にしている箇所がある。** Claude Code 自身の
  cross-session messaging（`/list-agents` / `SendMessage`）は、**有効化すると Claude 側の
  利用統計送信（telemetry）も一緒に戻る**作りのため、セルフホストの既定として無効のままに
  しています。同じ用途は Agent Fleet 側の実装で提供し（設定 > エージェント > セッション間
  メッセージ・**既定オフ**）、そちらは配送も帰属もこちらの制御下にあります（届く相手は同一
  ワークスペース内に限られ、受信側には「利用者の指示ではない」と明示されます）。利用者から
  「`/list-agents` が使えない」と上がってきたら、故障ではなくこの判断です。
- **秘密をログに出さない設計。** CP は資格情報の平文を保持・解釈せず、ログにも出しません。統一
  cred helper が都度復号して渡すため、git とプロバイダの資格情報は平文ファイルになりません。例外は MCP サーバーの秘密で、
  エージェント CLI の設定ファイルへ home 内に平文（0600）で書かれます（`docs/build/07-security.ja.md` §7.6）。
- **ワークスペースにホストのクラウドの身元を渡さない。** ワークスペースのコンテナは、それが動くマシンの
  メタデータエンドポイント（`169.254.169.254`）に届き得ます。メンバーの資格情報を持たない AWS SDK はそこで
  見つけたロールに気づかないうちに切り替わります。インスタンスプロファイルを持つ EC2 ホストなら、すべてのセッションで、
  エラーも出さずにそのロールです。Control Plane はワークスペースを `AWS_EC2_METADATA_DISABLED=true` 付きで
  起動し（docker と Kubernetes）、またはタスクロールを外したうえでそれを立てる（ECS）ので、SDK は問い合わせなくなります。
  ネットワークでの遮断はホストの役目です。
  - **compose 用の EC2 ホスト**（`deploy/aws/ec2-single`）: IMDSv2 とホップ数 1（`HttpTokens: required`、
    `HttpPutResponseHopLimit: 1`）。ホストネットワークの Control Plane は 1 ホップなのでインスタンス
    プロファイルを使えますが、docker ブリッジ上のワークスペースは 2 ホップでトークンを得られません。既存の
    インスタンスには、スタックの更新ではなく動いているインスタンスに直接適用してください（コマンドは
    [ec2-single のランブック](../../deploy/aws/ec2-single/README.md#instance-metadata-imds)）。Ubuntu AMI のパラメータが進んでいると、スタック
    更新はインスタンスを作り直すことがあります。
  - **クラウド上のそれ以外の docker ホスト**: 同じメタデータ設定か、Docker の `DOCKER-USER` チェーンで
    ワークスペースのブリッジからの `169.254.169.254` を拒否するホストのファイアウォール規則（ホストの root が
    要ります。compose 自体に新しい権限は要りません）。
  - **Kubernetes**: この変数はクラスタのメタデータサーバ（ノードのサービスアカウント、GKE では
    Workload Identity）を塞ぎません。その経路を塞ぐのはクラスタの役目です（NetworkPolicy の egress 規則、
    または GKE のメタデータ隠蔽）。Control Plane はそれをしません。
  - **ecs-ec2**: スロットのユーザーデータが `ECS_AWSVPC_BLOCK_IMDS=true` を設定します。残っている
    スロットは入れ替えが要ります。管理 → スロットで入れ替え予約してください（[03-run](03-run.ja.md)
    「ecs-ec2: 起動テンプレートを変えたあとのスロットの入れ替え」）。

  Control Plane の `AF_WS_WORKLOAD_AWS=1` は ECS のタスクロールをワークスペースに戻し、SDK のメタデータ参照の
  抑止をやめます。上のネットワークの防護はどれも外さないので、docker のワークスペースがホストのインスタンス
  プロファイルに届くことはありません。それを渡すには、別に許した資格情報の経路が要ります。既定ではネットワークの
  防護を保ってください。

  **適用の手順。** 動作中の docker のワークスペースは、作られたときの環境を保ちます。`docker compose up -d` や
  Docker の再起動では変わりません。Control Plane とワークスペースのイメージを更新したら（`AF_WS_WORKLOAD_AWS` を
  変えたときも）、すべてのワークスペースを Console で**停止して起動**し（コンテナが作り直されます）、上のホストの
  メタデータ設定を適用してください。セッションのシェルから、環境を表示せずに確かめます（3 つの確認は
  [ec2-single のランブック](../../deploy/aws/ec2-single/README.md#instance-metadata-imds)）。オプトインがオフ（既定）なら、変数は `true` を示し、
  プロファイル無しの AWS 呼び出しは「Unable to locate credentials」で失敗し、IMDSv2 のトークン要求は
  成功しません。`AF_WS_WORKLOAD_AWS=1` のときは最初の 2 つは違って当然です（docker では変数が
  無く、ECS ではタスクロールが解決されます）。ホストがメタデータを遮断している所では、トークン要求はそのときも
  失敗しなければなりません。

  native ランタイムのワークスペースはメンバーのマシンで直接動くので、そのままにします。そこのインスタンスロールは
  そのマシン自身のものです。

  メンバーは `af-aws-exec` で自分として AWS コマンドを実行します（[メンバーガイド 16](../member/16-cloud-accounts.ja.md)）。

## オフボーディング — アクセスは実際どこで切れるか

入口が 2 つあるので、出口も 2 つあります。どちらを使うかは、その配備が人をどう受け入れて
いるかで決まります。

| 入り方 | 外し方 | 効くタイミング |
|---|---|---|
| 許可リスト（`AF_OAUTH_ALLOWED_*`） | リストから消す | 次のリクエスト（判定は毎リクエスト） |
| テナントの membership（招待） | **管理 → 該当テナント → 該当メンバー → 「メンバーを外す」** | 次のリクエスト |

**セッションを個別に失効させる手段はありません。** セッション cookie は stateless（署名付きの
`{email, exp}` だけ・サーバ側にセッションストアが無い）なので「全端末からログアウト」も存在せず、
cookie 自体は最大 `AF_SESSION_TTL`（既定 7 日）有効なままです。実際にアクセスを止めているのは上の
**毎リクエスト再判定**です。したがって:

> **IdP 側で無効化するだけでは足りません。** Microsoft / Google のアカウントを止めれば
> *新しい*セッションは取れなくなりますが、**すでにブラウザにある cookie は、許可リストまたは
> テナントから外すまで生き続けます。**

**API トークンも一緒に切れます。** 個人アクセストークン（PAT）と MCP OAuth の接続はセッションではないので、
上の「リクエストごとの確認」には掛かりません。別の経路で切ります。

- **membership を外すと**、その membership で発行された PAT と MCP OAuth の接続は同じ操作で**すべて失効**します。
  再招待しても戻りません。
- **許可リストから外すと**、次にそのトークンが使われたときに検知します。CP が、その人がサインインに使った
  方式に「まだ入れるか」を問い合わせ、どれも通さなければ、その人の PAT と接続を**すべて失効**させて 401 を返します。
  確定した拒否だけが失効させます。確認できない場合（再起動後や障害中の GitHub アダプタ、読めない許可リストのファイルなど）は失効させません。
- **PAT は必ず期限切れになります。** 「無期限」はありません。最長は `AF_PAT_MAX_DAYS`（既定 365 日、1〜3650。それ以外の値だと CP は起動しません）です。
  この上限の導入前に無期限で発行されたトークンは、作成から上限日数で切れるものとして扱うため、古いものは
  すぐ使えなくなります。

`/mcp` での PAT の**利用**は、ワークスペースがオフィス外から呼ぶため、従来どおりテナントの許可ネットワークの
対象外です（`docs/build/07-security.md` §7.3.2）。切るのは失効の役目です。

順序は次のとおり。**アクセスを切るのは 1 だけ**で、2 以降は後片付けです。

1. **membership を外す**（許可リスト運用ならリストから消す）。
2. **ワークスペースを停止**（管理 → メンバー詳細 → 「ワークスペースを強制停止」）。
3. **home を掃除**：本人に push させてからにします。`~/repos` は掃除後には戻せません。ログイン・接続は
   残り、home のバックアップを取る配備ではバックアップも残ります。それらを消すのは「バックアップを
   削除」と Workspace の破棄です。home の掃除が無い配備では、Workspace の破棄がこの手順になります
   （[ref/deploy-targets](../ref/deploy-targets.ja.md)）。

退職してから気づくと手遅れになる非対称が 2 つあります。**事前に**知っておいてください。

- **定時実行は個人所有。** スケジュールは membership に紐づくので、その人が仕込んだものは
  **止まります**。引き継ぐ人が作り直してください。
- **内部 git リポジトリはテナント所有。** 人が抜けても残ります。作った人が辞めても失われません。

### 緊急停止 — `AF_COOKIE_SECRET` のローテーション

いま直ちに全員のセッションを無効化したい場合（cookie の漏洩、端末の紛失、連絡の取れない
アカウント）、即時に効く唯一のスイッチが cookie 署名鍵の変更です。新しいランダム値を作り
（[compose のランブック](../../deploy/compose/README.md)に `AF_COOKIE_SECRET` のワンライナーがあります）、
`AF_COOKIE_SECRET`（`.env`・`oauth.env`・SSM パラメータ）に入れて CP を再起動します。

旧鍵で署名された cookie はすべて検証に通らなくなるので、**全員がログアウトされ、再サインインに
なります**。乱暴で、全員に 1 回ずつのサインインを強いますが、秒単位で効くのはこれだけです。
ただし**これはアクセスを剥奪しません**。許可リストや membership が残っていれば本人は再度
サインインできます。上の除外手順と**併用**してください（代わりにはなりません）。

## `super_admin` の移譲

`SUPER_ADMIN_EMAILS`（ホスト側の env）が「誰がこの配備の管理者か」の唯一の正で、
**起動時に 1 度だけ**読まれます。変更には CP の再起動が要ります。Console から super_admin を
昇格させる導線は意図的に作っていません。配備全体を動かせる権限は、そのホストのファイルに
触れる人だけが持つべきだからです。

1. `SUPER_ADMIN_EMAILS` を書き換え（後任を追加・前任を削除）、CP を再起動する。
2. 再起動時、CP は**リストに無い相手のロールを DB 側からも剥奪**します
   （`super_admin revoked (not in SUPER_ADMIN_EMAILS): …` とログに出ます）。これが無いと、
   前任のロールは DB に残り続けます。素直な対処（サインイン時に同期）では、
   **もうサインインしない退職者には永久に届かない**ためです。
3. 後任は初回サインインでロールが付きます。
4. そのうえで前任を上のとおりオフボーディングします（membership → 停止 → home）。

> 唯一の super_admin が引き継ぎ無しに抜けても復旧できます。ホストの env に触れる人が自分を
> 足して再起動すれば済みます。前提条件は **社内にホストへ触れる人が 1 人は居ること** だけ。
> 必要になる前に確認しておいてください。

## 脆弱性の報告窓口

脆弱性を見つけたら、**公開 issue を立てず**に非公開で報告してください。報告の窓口、報告に含める
情報、修正を受ける版は `SECURITY.md` の "Reporting a vulnerability" と "Supported versions" に
あります。
