# ホームごとに鍵を分ける

[English](home-keys.md) | 日本語

AWS の配備（`ecs` / `ecs-ec2`）だけの機能です。メンバーのホームディレクトリごとにランダムなキーを作り、認証情報ストア（`secrets.enc`）をそのキーで暗号化します。
`AF_MASTER_KEY` を持つ人でもストアを開けなくなり、KMS キーを無効にすればストアを読めなくできます。先に [保存時の鍵を AWS KMS にする](kms.ja.md) が必要です。パラメータは [パラメータで任意の機能をオンにする](../aws-ecs/options.ja.md#ホームごとに鍵を分ける) にあります。

## 全体像

| あなたがやること | 起きること |
|---|---|
| `30-ingress` を `WorkspaceDekRandom=on` でデプロイする | Control Plane に `AF_WORKSPACE_DEK=random` が加わり、サービスがローリング更新される |
| 何もしない（メンバーがワークスペースを起動する） | 最初の起動でホームディレクトリのキーができ、ワークスペースがストアをそのキーで暗号化し直す。Control Plane が結果を確かめる |
| `af-cp home-dek-status` を実行する | 移行中のホームディレクトリと確認済みのホームディレクトリ、まだ一度も起動していないホームディレクトリを数える |
| ホームディレクトリを消したあと、取り残されたキーを消す | そのホームディレクトリのストアと写しが、二度と開けなくなる |

## 有効にする

`30-ingress` を `WorkspaceDekRandom=on` と `CustodianKmsKeyArn` を付けてデプロイします。変わるのは Control Plane のタスク定義だけです。

- `CustodianKmsKeyArn` がないと、更新は CloudFormation の実行時にロールバックされます。変更セットは作れてしまうので、スタックのイベントで確かめてください
- `AF_WORKSPACE_DEK=random` は `AF_KEY_CUSTODIAN=kms` のときだけ受け付けます。ほかの組み合わせや別の値では、Control Plane が起動時に止まります
- 必要な権限は、既存の `/af-ws/*` への権限で足ります

### 有効にする前に確かめること

| 項目 | 内容 |
|---|---|
| 残してあるホームディレクトリ | このフラグでの最初の起動までは、導出したキーのままです |
| SSM パラメータ `secret-key-next` | その起動から、ワークスペースごとに作られます。ホームディレクトリが確認されたあとの次の起動で削除を試み、失敗はログに残して起動を続けます。Destroy でも消えます |
| 動いているタスク | 再起動するまで、今の環境変数を持ち続けます |
| パラメータを戻すと | 止まるのは新しいホームディレクトリへのキーの作成だけです。すでにキーを持つホームディレクトリはそのキーを使い続け、接続し直す必要はありません（[無効に戻すとき](#無効に戻すとき)） |
| 消えないもの | まだ起動していないホームディレクトリと、古いスナップショット・バックアップは、KMS キーを無効にしても読めるままです |

## ホームディレクトリのキーができて確認されるまで

1. 有効にしたあとの最初の起動で、Control Plane がホームディレクトリのキーを作り、導出したキーと並べてワークスペースに渡します
2. ワークスペースは起動時に `secrets.enc` をどちらかのキーで開き、ホームディレクトリのキーで暗号化し直します。どちらでも開けないストアには触りません。ストアがまだないホームディレクトリには、ホームディレクトリのキーで暗号化した空のストアを作ります
3. Control Plane は、その起動が立ち上げたワークスペースの報告を待ちます。3 秒ごとに問い合わせ、最長 15 分待ちます
4. ワークスペースがホームディレクトリのキーで暗号化し、`migrated` か `current` を返したら、ホームディレクトリを確認済みにします
5. **次の**起動からは、ホームディレクトリのキーだけを `AF_SECRET_KEY` として渡し、導出したキーは渡しません。ECS ではこの起動で `secret-key-next` も消します

空のストアを先に作るのは、導出したキーしか持たない書き手が、あとからそのキーでストアを作れないようにするためです。

### ワークスペースの報告

ワークスペースの `/healthz` は、キーそのものではなく結果だけを返します。

| `secrets_key` | 意味 | Control Plane がすること |
|---|---|---|
| `none` | ストアがない。ホームディレクトリのキーを渡したワークスペースは空のストアを作って `current` を返すので、ふつうは出ません | 移行中のまま |
| `current` | ストアはすでにホームディレクトリのキーで暗号化してある | 確認済みにする |
| `migrated` | この起動でホームディレクトリのキーに暗号化し直した | 確認済みにする |
| `derived` | ホームディレクトリのキーに移せず、導出したキーのまま | 移行中のまま。ログに残し、何も消さない |
| `unreadable` | どちらのキーでも開けない | 移行中のまま。ログに残し、何も消さない |

- `secrets_key_next` は、ホームディレクトリのキーで暗号化したかどうかを返します
- Control Plane は起動ごとに新しい識別子（`AF_HOME_KEY_START`。シークレットではありません）を渡し、ワークスペースはそれを `secrets_key_start` として返します。以前のタスクや別のワークスペースの応答は無視し、リダイレクトにも従いません
- 15 分を過ぎたとき、または待っている間に Control Plane が再起動したときは、ホームディレクトリは移行中のままで、あとの起動で確認されます
- すでに動いているワークスペースは、再起動するまで両方のキーを環境変数に持ちます

`af-cp home-dek-status` が、移行中と確認済みのホームディレクトリを数えます。ECS では `rewrap-keys` と同じく単発のタスクとして実行します（[Control Plane のデータベースに対して af-cp を実行する](../aws-ecs/options.ja.md#control-plane-のデータベースに対して-af-cp-を実行する)）。

## ホームディレクトリのキーが消えるとき

キーはワークスペースではなくホームディレクトリのものです。残したホームディレクトリの上でワークスペースを削除して作り直しても、キーはそのままです。

キーが自動で消えるのは、次の 3 つがすべてそろったときだけです。

- Destroy が終わった
- どのワークスペースの行も、そのホームディレクトリを指していない
- ランタイムが、ホームディレクトリの全体が消えたことを**証明**した

ホームディレクトリの一部が残ったままキーを消すと、その部分が読めなくなります。そのため、ランタイムの答えがそれ以外ならキーを残します。`migrating` のままのキーは、この経路では消えません。

| ランタイム | 証明できること |
|---|---|
| `ecs` / `ecs-ec2` | 今実行した Destroy で、EFS の home タスクが終了コード 0 で終わり、すべてのアクセスポイントがそのタスクが消すディレクトリを指していたときだけ。別の場所を指すアクセスポイントは消さずに報告します。home タスクのない `ecs` はアクセスポイントだけを消し、再試行しても残りは報告されません |
| `kubernetes` | 今実行した Destroy で、すべての claim と volume が消えたことを確かめたあとに StatefulSet を消したときだけ |
| `docker` / `native` | 証明できません。ディレクトリがないのは、外れたボリュームや誤った `WS_DATA` でも同じだからです |

あとから確かめたり、「残りがない」ことから判断したりはしません。

キーの行が消えると、ストアと、そのキーで暗号化したストアの写し（スナップショット・バックアップ）は開けなくなります。ただし `home_dek` の行が残っているデータベースのバックアップを、KMS キーが有効なうちに戻すと開けます。ストアが移る前の写しは、導出したキーのままです。

### 取り残されたキーを消す

自動で消えずに残ったキー（golden snapshot をビルドするときの `migrating` のままのプローブ、証明できないランタイム、古い Control Plane による破棄）は、自分で消します。

1. `af-cp home-dek-status --orphans` で一覧表示します。読み取りだけで、どのワークスペースの行も指していないキーが出ます
2. 一覧に出ただけでは候補です。ホームディレクトリはワークスペースの行より長く残り得るので、ホームディレクトリが消えたことを確かめます（EFS のディレクトリ、EBS ボリュームとスナップショット、クラスターの claim、データディレクトリ）
3. `af-cp home-dek-status --remove-orphan <membership-id> --force` で消します

`--force` は「ホームは消えた」というあなたの宣言です。このコマンド自身には、それを確かめるランタイムがないからです。ワークスペースの行が指しているキーと、そのメンバーシップでワークスペースの操作が進行中のキーは、`--force` でも消しません。

| 終了コード | 意味 |
|---|---|
| 終了コード 0 | キーを消した |
| 終了コード 1 | 何も消さなかった |
| 終了コード 2 | データベースのエラー |

ホームディレクトリが残っているのにキーを消すと、その `secrets.enc` は二度と読めません。

## KMS キーを無効にしたとき

ストアが暗号化し直されたホームディレクトリは、`AF_MASTER_KEY` から導出したキーではもう開けません。Control Plane のデータキーのキャッシュ（`AF_KMS_DATA_KEY_CACHE_TTL`、既定は 5 分）が切れたあとは、Control Plane はホームディレクトリのキーを開けなくなり、次の起動を拒否します。キャッシュが有効な間は、起動が成功することがあります。

**これだけではストアは消えません。** すでに渡したホームディレクトリのキーの写しが残っていて、どれも KMS キーとは別のもので守られています。

| 写し | 残る場所 |
|---|---|
| 動いているワークスペース | 環境変数。Agent・git の認証情報ヘルパー・MCP サーバーは、KMS に問い合わせずにストアを読み書きし続けます |
| ランタイム側の写し | 停止しても残ります。ECS ではワークスペースごとの SSM SecureString（`secret-key`・`secret-key-next`）で、アカウントの SSM 用のキーで暗号化されています。docker ではコンテナの環境、Kubernetes では Secret です |

ホームディレクトリを残したままストアを読めなくするには、次の 3 つを全部やります。自動でやるものはありません。

1. KMS キーを無効にする
2. ワークスペースを止める
3. ランタイム側の写しを自分で取り除く

Destroy はこの手順ではありません。ランタイム側の写しを消し、ホームディレクトリも消そうとします。home タスクのない `ecs` のスタックでは、アクセスポイントだけを消し、ホームディレクトリの EFS のディレクトリは残ります。

### 無効にしても読めるもの

- 有効にしてから一度も起動していないホームディレクトリ。導出したキーのままです。`af-cp home-dek-status` がその数を数えます
- 暗号化し直す前に作られたホームディレクトリの写し（`ecs-ec2` のスナップショットやバックアップ）。古いファイルが残っていて、`AF_MASTER_KEY` で開けます

## 移す前の写しを戻したとき

確認済みのホームディレクトリに、ストアが移る前のスナップショットやバックアップから `secrets.enc` を戻すと、それは導出したキーで暗号化されています。そのホームディレクトリにはもう渡されないキーなので、ワークスペースは `unreadable` を返し、そのストアを上書きしません。

1. Control Plane の環境で `af-cp home-dek-status --remigrate <membership-id>` を実行します
2. ワークスペースを再起動します。両方のキーがまた渡され、戻したストアがホームディレクトリのキーで暗号化し直されます

このコマンドは、そのメンバーシップに確認済みのホームディレクトリのキーがないと終了コード 1、データベースのエラーで終了コード 2 で終わります。

## 無効に戻すとき

`AF_WORKSPACE_DEK` を外しても、すでにキーを持つホームディレクトリにはそのキーを渡し続けます。ストアがそのキーで暗号化されているかもしれないからです。

ストアが暗号化し直されたあとに戻すと、戻しかたで結果が違います。

| 戻しかた | 結果 |
|---|---|
| ホームディレクトリのキーを知らない Control Plane に戻す、または `home_dek` 表を失う（ワークスペースイメージは v0.31.0 以降） | ストアは開けなくなります。ワークスペースは、認証情報の接続し直しを含め、そのストアへの書き込みをすべて拒否します |
| v0.31.0 より前のワークスペースイメージ | **移ったホームでは起動しないでください。** 読み込みに失敗したあとの保存で、暗号化し直したストアの上に空のストアが書かれ、認証情報が失われることがあります |

Control Plane より古いワークスペースイメージは、ストアがまだ暗号化し直されていなければ何も失いません。ホームディレクトリのキーを無視して、導出したキーを使い続けます。

### 復旧する

1. そのホームディレクトリでワークスペースを起動する前に、ストアを開けるものを戻します。Control Plane のバージョン、その `home_dek` の行、KMS キーです
2. 保存していた認証情報をあきらめるときに限り、ワークスペースを止め、読めない `secrets.enc` をメンバーのエージェント設定ディレクトリ（`~/.config/agent-fleet/`）から自分で退避します
3. メンバーに認証情報を接続し直してもらいます

## うまくいかないとき

| 症状 | 原因と対処 |
|---|---|
| ワークスペースが起動しない | KMS がホームディレクトリのキーを暗号化できない・開けないときは、ワークスペースは起動しません。導出したキーだけで起動する経路はありません。KMS キーが有効か、Control Plane のロールが使えるかを確かめます |
| ホームディレクトリが移行中のまま | ワークスペースが `derived` か `unreadable` を返したか、15 分の待ちが切れました。次の起動で確認されます。`unreadable` が続くなら [移す前の写しを戻したとき](#移す前の写しを戻したとき) を確かめます |
| 認証情報が開けないとメンバーが言う | キーを知らない Control Plane に戻したか、`home_dek` 表を失いました。[復旧する](#復旧する) に進みます |
