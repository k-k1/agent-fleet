# セルフホストの全体像

[English](overview.md) | 日本語

Agent Fleet を自分の基盤で動かすときに、何ができて、何を用意し、運用担当者が何に責任を持つのかをまとめています。
採用を判断する前と、初めて構築する前に読んでください。

## 全体像

| 運用担当者がやること | Agent Fleet がやること |
|---|---|
| ホストを用意し、設定とシークレットを決めて起動する | Control Plane がサインイン・テナントとメンバーの管理・ワークスペースの起動と停止を受け持つ |
| サインインの方法と、入れる人を決める | 許可リストと名簿に載っていない人を入れない |
| バックアップを取り、キーを守り、アップグレードする | 永続データをすべて `DATA_DIR` の下に置く |
| メンバーを迎え入れる | 各メンバーに隔離されたワークスペースを用意する。シートには各メンバーが自分でログインする |

## できること

- チームが CLI のコーディングエージェントをブラウザから使えます
- 各メンバーは隔離された環境（専用のコンテナ）を持ち、リポジトリをクローンして、エージェントやシェルのセッションを動かします
- ターミナルに触りたくない人向けに、チャット中心の使い方もあります
- 管理者はブラウザから、メンバーの追加・上限の設定・使用状況と監査ログの確認・外向きの通信先の観測ができます
- 部署を **テナント** で分けると、ワークスペースは完全に隔離されます。既定は 1 テナントです

## 用意するもの

| もの | 用途 |
|---|---|
| Docker の動く Linux ホスト（Docker Engine と `docker compose`） | 1 台で足ります |
| 公開ドメインと、そこを指す DNS | TLS の証明書を自動で取得します。公開 DNS を用意できない閉域の配備には、自己署名の代わりがあります（[テナントとプロビジョニングの方式を決める](install-decisions.ja.md#tls-internal-を使うか)） |
| サインイン用のプロバイダー | Google の OAuth クライアント、または Entra ID・Okta・Keycloak・Auth0・Cognito・GitLab の OIDC アプリ。いくつ有効にしても、登録するリダイレクト URI は 1 つです |
| シート | 各メンバーが持ち込みます。初回の起動のあと、各自が自分のシートでログインします。個人プランより、会社の Team / Enterprise のシートをおすすめします |

ほかの形態（AWS・Kubernetes・Docker のない機械）は [デプロイ先を選ぶ](choose.ja.md) で選びます。

## 1 社 1 配備で守る

- 各社が自社の基盤に、独立した配備を構築します
- 会社どうしの隔離は、**配備が別であること** で保証します。プロセスの中の境界には頼りません。侵害されても、影響はその配備の中に閉じます
- AWS では、配備ごとに AWS アカウントを分けている場合に限ります（[脅威モデルと残るリスクを知る](secure/threat-model.ja.md)）
- ワークスペースの中の境界は、エージェントが **任意のコードを実行する** 前提で作っています。守っているのは、ほかのユーザーのデータ・Control Plane とホスト・シークレットで、データの持ち出しにも備えています

### 採用の前に読むリスク

残るリスクが 4 つあり、[脅威モデルと残るリスクを知る](secure/threat-model.ja.md) と `SECURITY.md` に書いています。採用を判断する前に、必ず読んでください。

| リスク | 意味 |
|---|---|
| `docker.sock` | 触れる人はホストの root と同じことができます |
| `AF_MASTER_KEY` の紛失 | 保存した認証情報がすべて、二度と復号できなくなります |
| バックアップ | 中身は機微な情報です |
| ホストへのアクセス | すべての権限を持つのと同じです |

## 頭に入れておく最小のモデル

1 台のホストで `docker compose` が管理するのは、次の 2 つのサービスだけです。

| サービス | 役目 |
|---|---|
| Control Plane | サインインの認証、テナントとメンバーの管理、ワークスペースの起動と停止、すべての API の中継 |
| Caddy | 入口。TLS の証明書を自動で取得・更新し、背後の Control Plane へ流します |

**メンバーのワークスペースのコンテナは、compose の管理下にありません。** これらのコンテナは、Control Plane が実行時に起動します。そのため、次のことが起きます。

- `docker compose down` や Control Plane の再起動では、ワークスペースは止まりません。メンバーの接続も切れません
- バックアップのために Control Plane を一時停止しても、動いているワークスペースには影響しません
- compose を止めても全部は止まりません。全ワークスペースを強制停止するのは別の操作です（[アイドル停止と強制停止を使う](run/idle-stop.ja.md#ワークスペースを強制停止する)）

### データの置き場所

- 永続データはすべて `DATA_DIR` の下にあります。データベース、各メンバーのホームディレクトリ、暗号化した認証情報、Caddy の証明書です
- バックアップするのはこのディレクトリです
- 例外は `AF_MASTER_KEY` だけです。`DATA_DIR` にもバックアップにも入れません

### 破ると気づかないうちに壊れる 3 つの制約

コンテナからホストの Docker を動かすので、次の 3 つを守る必要があります。compose の定義が守っていますが、手で変えるときは注意してください。

- ホストネットワーク
- `DATA_DIR` の絶対パスが、ホストとコンテナで同じであること
- docker グループの GID

症状から読む説明は [症状から原因を探す](diagnose/checklist.ja.md#コンテナから-docker-を動かす-3-つの制約) にあります。

## 責任のチェックリスト

- [ ] `AF_MASTER_KEY` を **データとは別のシークレットストア** に置き、別途バックアップした。なくすと、保存した認証情報がすべて復号できなくなる
- [ ] `backup.sh` を定期的に実行し、保管先を権限と暗号化で守っている
- [ ] 復元の手順を **一度は実際に試した**（`DATA_DIR` の basename の制約も含めて）
- [ ] アップグレードの前に、毎回バックアップを取っている。**ダウングレードはできない**
- [ ] サインインの許可リストを設定した。空のままだと、誰もサインインできない
- [ ] Entra ID を使うなら、issuer を自社テナントの GUID に固定した。common のエンドポイントのままだと、すべての Microsoft アカウントがサインイン画面まで進める
- [ ] ホストで SSH・sudo・docker を使える人を最小限にした。これはホストの root と同じ権限になる
- [ ] 外向きの通信の制御を入れるなら、段階を理解した。まず log-only で観測し、それから enforce にする
- [ ] 脆弱性を見つけたときの報告の手順を知っている（`SECURITY.md`）

## エージェントが自律して動くことについて

- エージェントはメンバーに代わって、コマンドの実行・ファイルの編集・コミットとプッシュをします
- 人が見ていないとき（停止中のワークスペースを起動する定時実行）、権限の確認を省くモード、受け取った文字列をそのまま実行するシェルや SSM のセッションでも動きます
- その操作は破壊的なことや取り消せないことがあり、つないだ AI プロバイダーやクラウドのアカウントに費用がかかることもあります
- 運用担当者と各メンバーは、自分がつないだワークスペース・認証情報・リポジトリ・基盤と、エージェントのしたことを確かめる責任を持ちます。権限を絞った認証情報を使い、バックアップを取り、破壊的な操作には承認を挟んでください
- Agent Fleet は Apache License 2.0 で配布され、無保証です。使って生じた損害・データの消失・停止・費用について、作者は責任を負いません。`LICENSE` と、同梱の OSS の表示は `NOTICE` を見てください
- 公式のリリースは <https://github.com/k-k1/agent-fleet-dist> からだけ出ます。バンドルやパッケージを人に渡すときは、Apache-2.0 の §4(d) により、`NOTICE` の表示（この URL を含む）を一緒に渡します。受け取った人が元をたどれるようにするためです
