# 09. 自前の llama.cpp でチャットの推論を担う

[English](09-llm-lan.md) | 日本語

フリート自身の GPU エンジン——チャット補完の背後の `llm` 役——は AWS で買うものなので、
`ecs-ec2` 形態にしかありません。すでに AWS で Agent Fleet を運用しているなら
[08 別の配備のエンジンを借りる](08-borrowed-engine.ja.md)でその `llm` 役を使えます。

この章はどちらでもない配備のためのものです。**すでに自分の網の中で動いている
（あるいはこれから立てる）llama.cpp** を、`compose` / `native` / `docker` の配備から
指します。[07 自前の ComfyUI で画像を生成する](07-image-engine.ja.md)が画像でやっている
ことの、チャット版です——同じ立て付けで、誰かの机の下の GPU 機、WSL2 の Windows 側、
共有サーバーを指せます。

必要なのは環境変数と、手で維持するモデルの一覧だけです。**エンジンはあなたのもの
のまま**で、Control Plane はそれを起動も停止もしませんし、費用も付けません。

## 経路は 2 つ、コードで足したのは近道のほう

`llm` 役を外部管理の行にする経路はもともと 2 つあります。

| 経路 | 中身 | 要る変数 |
|---|---|---|
| **A. 近道** | `AF_LLM_URL` を設定するだけ。CP が起動時に `llm` 行を 1 本合成する | `AF_LLM_URL`、任意で `AF_ENGINE_API_KEY_LLM` |
| **B. 表に書く** | `AF_ENGINES_JSON`（または AWS ならエンジンスタックのテーブル）に `lifecycle:"external"` の行を自分で書く | 同じ `AF_ENGINE_API_KEY_LLM` |

**A は 07 の `AF_COMFY_URL` とまったく同じ形の近道で、B はコード無しで今日もう動きます。**
この章が説明するのは主に A です——1 行足すだけで済むほうなので。

どちらも Control Plane が**起動時に 1 回だけ**読みます。変更はどちらも CP の再起動です。

| 変数 | 意味 |
|---|---|
| `AF_LLM_URL` | ポートまで含めた完全な URL を、**CP から見た形**で。例: `http://192.168.1.20:8080`。これを設定することが経路 A を開くことです。 |
| `AF_ENGINE_API_KEY_LLM` | 任意。上流へ `Authorization: Bearer` として送ります。**専用の `AF_LLM_API_KEY` はありません**——次の節。 |

置き場所は形態によります。

| 形態 | 置き場所 |
|---|---|
| compose / docker | compose ファイルの隣の `.env`（CP のサービスがファイルごと読みます） |
| native | `af start` の環境、または systemd unit の `Environment=` — [deploy/native/README.md](../../deploy/native/README.md) |

### なぜ `AF_LLM_API_KEY` ではないか

07 の `AF_COMFY_API_KEY` のように、この役だけの鍵の名前を新設することもできました。
そうしなかったのは、**`AF_ENGINE_API_KEY_LLM` がすでにすべての外部管理の行の鍵**だからです
——手で書いた `llm` の行（経路 B）も、他の役の外部管理の行も、みなここから読みます。
専用の名前をもう1つ足すと、「どちらに書いた鍵が効くか」という調停が要り、
編集したはずの bearer が効かない 401 を作るだけです。**鍵は 1 つの変数に一本化しています。**

## LAN 機で llama-server を立てる

**実行するのは利用者の別ホストであって、Workspace の中ではありません。** 以下はその
LAN 機に貼り付けて実行するコマンドで、この配備が走らせるものではありません。

入手（簡単な順）:

| | Linux | Windows |
|---|---|---|
| コンテナ | `docker run ghcr.io/ggml-org/llama.cpp:server-cuda`(**この配備自身が使っているのと同じイメージ**) | — |
| パッケージ | `winget install llama.cpp` | 同左 |
| 配布物 | `llama-bNNNNN-bin-ubuntu-cuda-*.tar.gz`(**`.zip` ではありません**) | `llama-bNNNNN-bin-win-cuda-*.zip` **+ `cudart-*.zip`（CUDA ランタイムは別配布）** |

🔴 **CUDA 対応の Linux 配布物は新しいビルドにしかありません。** この配備が動かして
いる `b10830` の資産一覧には無く(当時は vulkan/rocm/sycl のみ)、`b11065` で
`ubuntu-cuda-12.8`/`ubuntu-cuda-13.3` として現れます。古いビルド番号を指定すると
探しても見つからないので、NVIDIA の GPU なら**コンテナが最も確実**です。

起動コマンドの形:

```
llama-server -hf <repo>:<quant> --alias <目録の id> -c <窓> -ngl 99 --jinja \
             --host 0.0.0.0 --port 8080 --api-key <鍵>
```

- 🔴 **`--alias` は必須級です。** この配備は毎リクエストで `model` にカタログの **id** を
  送るので、alias がその id と一致していないとリクエストは届きません（`--alias` を
  付けないと、単機モードの `/v1/models` の `id` は `-hf`/`-m` に渡したパスになります)。
- `-c`（窓）は、この行に登録するモデルの `context_tokens` 以上にしてください。目安は
  8192 以上です。
- `--host 0.0.0.0` が無いと loopback にしか応答しません。**`--port` も明示してください**
  ——上流は既定ポートを変える予告を出しています。
- 🔴 **`--api-key` を付けないと、その llama-server は LAN に認証なしで開きます。**
- `--jinja` は上流の既定で ON ですが、古いビルドに備えて明示しておくと安全です。
- gated な Hugging Face リポジトリを使うなら `HF_TOKEN=...`(または `-hft <token>`)。
- 任意で `--sleep-idle-seconds <N>`。アイドルで眠らせて VRAM を返せます——この配備の
  `llm` ロールがしている「常時起動」を、上流の機能で一部緩められます。

ファミリーは **Qwen3・GPT-OSS・Gemma** が実機で確認できています。**`llama-3.1` はこのエンジン版
では tool call が通りません**——このハーネスのツールループはコーディング作業の前提な
ので、`llama-3.1` を選ぶ場合はツールを使わない用途に限ってください。

## 先に切り替えてから、モデルを登録する

🔴 **この配備がまだ AWS のフリートを借りている（08）間は、`llm` のモデル一覧を編集
できません。**借りた行への書き込みは、向こうの配備を名指しして断られます。手順は
必ずこの順です。

1. `AF_LLM_URL`（と、必要なら `AF_ENGINE_API_KEY_LLM`）を設定して CP を再起動する。
2. そのあとで Console の**管理 → 推論エンジン**から `llm` の行にモデルを登録する
   ——`--alias` に渡した名前と同じ **id** で。

登録の中身は 07 の「モデルは手で登録する」と同じ形です。ここでは何も取り込まれません。
**カタログはあなたが書く宣言**で、id・`base_model`・窓（`context_tokens`）を、
LAN 機の起動コマンドと矛盾しないように書きます。

## 何を失うか(正直に書きます)

08 で借りていた行には、CP からエンジンへの**失効・追跡ができる認証**がありました
——向こうの配備がメンバーシップごとにトークンを発行し、消せば止まる仕組みです。
`AF_LLM_URL`(あるいは手書きの外部行)に切り替えると、それは**共有 bearer 1 本**に
変わります。`AF_ENGINE_API_KEY_LLM` を知っている全員が同じ鍵を使い、1 人だけを
締め出す方法はありません(鍵を回転させれば全員が締め出されます)。

**外部管理の行には起こす仕組みがありません。** 借りていたときの「遅いが繋がる」
(冷間起動を待つ)が、「速いか、即座に失敗するか」に変わります。LAN 機が答えていれば
速く、答えていなければ CP は待たずに `503 engine_unavailable` を返します——次節。

## 何が変わらないか

**使用量は引き続き CP の gateway を通ります。** チャット補完の答えに含まれる
`usage`(トークン数)は、外部管理の行でも gateway が注入するので、メンバーの
使用量台帳は今までどおり書かれます。ストリーミングでも同じです。

## 落ちているときの見え方

Control Plane は、自分が所有していないエンジンを待ちません。LAN 機が落ちている間の
要求は**即座に** `503 engine_unavailable` で断られ、本文には試した URL と health の
パス(`/health`)が入ります。数分にわたる再試行はありません——その予算はクラウドの
インスタンスを買っている間のためのものです。

## パネルに出るもの・出ないもの

07 の画像エンジンと同じです。

- **warm** はパネルを開いた瞬間の生存確認で、`/models` を見ます(`/health` は
  重みを積んでいなくても ok を返すので、warm 判定には使いません)。
- **稼働の履歴は出ません。** 外部管理の行に制御ループはありません。
- **費用は付きません。** 自分の網の中の機械に、配備が知りうる時間単価はありません。

どの形態が何に対応しているかは
[ref/deploy-targets.md](../ref/deploy-targets.ja.md)にあります。

## メンバー個人の接続先（docs/log/107）

ここまでは**配備管理者**の選択です——`AF_LLM_URL` は CP の起動時に 1 回だけ読まれ、
全メンバーに一律で効きます。もう 1 つ、lcpp を LAN の llama-server に向ける独立した
経路があり、これは**メンバー個人**の選択です。**設定 → エージェント → llama.cpp**
の欄に URL とオプションの API キーがあり、動いている Workspace の中から、管理者の
操作も CP の再起動も無しに保存できます。

- **置き場所。** 接続先は Workspace 自身の暗号化された秘密ストア（git トークンなど
  他のすべての資格情報と同じ場所）に保存され、平文の `ui-prefs.json` には置かれません。
  API キーは `GET /connections` では一切返らず、設定カードには接続の有無と URL だけが
  表示されます。
- **設定すれば常に優先されます。** メンバーが自分の接続先を設定すると、**その
  メンバーの** lcpp セッションでは、この配備が `llm` エンジンを持っているかどうか
  （上の経路 A/B）に関わらず、その接続先が使われます。欄を空にすると、その
  メンバーはこの配備自身の `llm` エンジンにそのまま戻ります。
- 🔴 **Control Plane を一切経由しないため、テナント管理者の `allow_engine_llm` の
  可否設定（ADR 0084）も迂回します。** チャット推論をオフにしたテナントであっても、メンバーが自分の
  網の中から届く LAN 機に自分のセッションを向けることは止められません——他の
  どんなツールでも、メンバーが自分の網の中のサーバーへ向けるのを止められないのと
  同じです。これは意図した設計上のトレードオフであり（docs/log/107）、見落としでは
  ありません。新しい門は作っていません。
- **「接続を確認」ボタン**は保存済みの接続先に実際にアクセスし、エンジンのビルド
  （`build_info`）・実際の窓（コンテキスト長）・現在配っているモデル id を返します
  ——上の「パネルに出るもの・出ないもの」が配備全体の経路について書いている内容と
  同じ事実を、CP の gateway を経由せずメンバー自身の機から直接読みます。
