# 08. 別の配備のエンジンを借りる

[English](08-borrowed-engine.md) | 日本語

フリート自身の GPU エンジン——チャット補完の背後の `llm` 役、`generate_image` の背後の
`image` 役——は AWS で買うものなので、`ecs-ec2` 形態にしかありません。
[07 自前の ComfyUI で画像を生成する](07-image-engine.ja.md) はその回避策のひとつ
（すでに自分で動かしている機械を指す）でした。**この章はもうひとつの方です。**

すでに AWS で Agent Fleet を運用しているなら、自分のホストで動くもう 1 つの配備
（`compose` / `native` / `docker`）から**そちらのエンジンを使えます**。手前の配備は
中継するだけで、向こうの配備はいつもどおりの仕事をします——GPU が要ると判断し、箱を買い、
モデルを載せ、また手放す。セッションからは区別がつきません。借りたモデルは、この配備
自身のエンジンのモデルが出る場所にそのまま出ます。

**できるようになること。** `llm` と `image` の両方、あるいは名指しした片方だけ。向こうの
配備に新しいコードを置く必要も、ポートを開ける必要も、VPN も、ワークスペースの変更も
ありません。

**できないこと。**

- **向こうのエンジンを操ること。**起動も停止もできず、モデルの一覧を編集することも、
  どの箱で動いているかを見ることもできません。それは向こうの管理者のもので、この章の
  大半は**その境目がどこにあるか**の話です。
- **音声。** VOICEVOX はトークン認証のゲートウェイを挟まない直接の URL で届くので、
  声を借りるのは別の設計であり、存在しません。
- **逆向き。** AWS の配備が自宅のエンジンを使うのは同じ行を逆に向けただけですが、
  住宅回線に届くことを前提にしている箇所はどこにも無く、対応していません。

🔴 **この章の内容は、実在する 2 つの配備の組で測ったものではありません。**コードは
向こう側の身代わりのゲートウェイに対して試験してあります。「最初の要求が待つもの」に
出てくる時間は、**向こうの配備が自分の要求で測った**冷間起動であって、借りた場合の
ものではありません。分かっていない数字には、分かっていないと書いてあります。

## 環境変数 2 つ、と任意の 1 つ

3 つとも、Control Plane が**起動時に 1 回だけ**読みます（先行する `AF_COMFY_URL` と
同じ形です）。変更はどれも CP の再起動です。

| 変数 | 意味 |
|---|---|
| `AF_REMOTE_ENGINE_URL` | 向こうのフリートのベース URL を、**パス無しで**: `https://af.example.com`。これを設定することが「借りる」を開くことです。 |
| `AF_REMOTE_ENGINE_TOKEN` | 向こうの配備のあるメンバーシップの `afei_…` 発行トークン（次の節）。 |
| `AF_REMOTE_ENGINE_KEYS` | 任意。役の名前をカンマ区切りで——`image` ならその役だけ。空なら、向こうのフリートが出している役を全部。 |

**両方か、どちらも無しか。** URL だけあってトークンが無い状態は断られるほかないので、
片方だけの宣言では何も借りず、起動時のログに**どちらが欠けているか**が出ます。
`AF_REMOTE_ENGINE_URL` を設定しないのが通常の状態で、そのときは何も変わりません。

置き場所は形態によります。

| 形態 | 置き場所 |
|---|---|
| compose / docker | compose ファイルの隣の `.env` — [deploy/compose/README.md](../../deploy/compose/README.md) |
| native | `af start` の環境、または systemd unit の `Environment=` — [deploy/native/README.md](../../deploy/native/README.md) |

**代わりに `AF_COMFY_URL` を向こうのフリートに向けないでください。**動きそうに見えますが、
なぜ「お金がかかったうえで失敗する」のかは最後の節にあります。

### 行は起動時ではなく、向こうが答えたときに現れる

どのエンジンが在るか、それぞれがどの API とどの provider を話すか、どのモデルを出すかは、
すべて**向こうの配備のカタログから読みます**。こちらで宣言することはありません。これは
意図的です——image 役は、ある配備では ComfyUI で別の配備では sd.cpp であり、セッションが
組み立てる要求はまったく別物なので、推測すれば ComfyUI のグラフを OpenAI 互換の
エンドポイントに投げることになります。

その結果、運用上こうなります。

- カタログは起動時に 1 回、その後は**10 分ごと**に取りに行きます。借りた役が使えるように
  なるのは、**最初に成功した取得**のときです。
- **CP の起動時に向こうのフリートへ届かないと、そのぶんモデルが起動メニューに出ません。**
  合図は CP のログの 1 行だけです。次の巡回で自然に復帰します。
- 取得に失敗したときは**前回の答えを保ちます**。一過性の失敗が「このエンジンにはモデルが
  無い」と読まれてはいけないからです（それは「このエンジンを使うな」と同義です）。
- **この配備がすでに出している役は借りません。**ローカルの `image` 行があれば向こうのものは
  無視され、どちらかを変えるまで巡回ごとにログへ 1 行出ます。

## 資格情報

向こうの配備は、メンバーシップごとに**発行トークン**（`afei_…`）をすでに作っています。
向こうで開くのはちょうど 2 つの経路——「セッション用のエンジントークンをくれ」と
「どのエンジンを出している?」——だけで、ほかには何も開きません。git も MCP も memo も
API も。この機能が欲しいのはその資格情報です。

🔴 **人の発行トークンを——自分のものも含めて——使い回さないでください。**それは向こうの
配備の署名マスタから決定的に導出されるので、**1 本だけ無効にする方法がありません**。
無効化はそのマスタの回転であり、同じマスタは git・memo・schedule のトークンの背後にも
あるので、**そのフリートのメンバー全員がログアウトします**。借り手 1 つを切るために、
フリート全体を払うことになります。

ですからトークンは、**ほかの用途に使わないメンバーシップ**のものでなければなりません。
向こうの配備でそれを 1 つ招き——ワークスペースは要らず、何も動かす必要はありません——
そのうえでその配備にトークンを訊きます。

**発行するのは向こうの配備の super-admin です。** 経路は
`POST /api/admin/engines/issue-token` に `{"tenant_slug": "...", "user_key": "..."}` で、
トークン・入れるべき変数・そのトークンが開けるもの・失効の方法が返ります。`GET` は
ありません: 資格情報が URL やブラウザ履歴・プロキシのログに残ってはいけないからです。
有効でないメンバーシップは、401 しか返さないトークンを渡す代わりに 409 で断られます。

⚠️ **古い向こうの配備にはこの経路が無いかもしれません。** 404 が返る場合、資格情報は
遠回りの道でまだ取れますし、その道がなぜこれほど厄介なのかを知っておく価値があります:
トークンはそのメンバーシップ自身のワークスペースのコンテナの中にしか現れず、**他人の
ワークスペースを起動する管理経路も、その中でセッションを開く経路もありません**——管理画面に
あるのは停止・ホームの掃除・破棄と、読み取り専用の一覧だけです。ですから古い配備が相手の
ときの手順は、**向こうのサインイン方式が実際に認証できる実在のアドレス**でメンバーを 1 つ
招き、そのメンバーとして 1 度サインインし、そのコンテナの環境から
`AF_ENGINE_ISSUE_TOKEN` を読み、そのワークスペースを停止する、になります。

**借り手の失効は、向こうの配備でそのメンバーシップを消すこと**です。メンバーシップは
**要求のたびに**引き直されるので、有効期限の切れ目ではなく次の要求で止まります。別に
消すべき資格情報も、待つべき期限も、維持すべき一覧もありません。

値はほかの秘密と同じに扱ってください。ほかの `AF_*` の秘密が置いてある場所が居場所で、
シェルの履歴やチケットの中ではありません。

## 向こうのカタログが決めること・こちらで変えられないこと

Console の**管理 → 推論エンジン**では、借りた役はほかの外部管理の行と同じように見え、
向こうのフリートの URL を持ちます。そこに出るモデルの情報——id、サイズ、行ごとの
ネガティブプロンプト、配備全体の「全画像から除外する語」——は、**向こうの配備のカタログの
鏡であり、読み取り専用**です。

借りた役では、そのパネルの書き込みはすべて `400 engine_not_ours` で断られ、本文が
向こうの配備を名指しします。

- モデルの有効/無効、選択や既定の指定、
- モデルの登録、モデルの削除、
- モデルの取り込み（ingest のフォーム）、
- 「全画像から除外する語」の編集。

どれも**向こうの配備の管理画面**で、そこを管理している人が行います。向こうでの変更は
1 巡回のうちにこちらへ届きます。

こちらで**できること**は、

- **on / off。**「off」はこの配備での経路を閉じるだけです——セッションにエンジンが提示
  されなくなります——向こうのフリートの箱には何もしません。
- それ以外はありません。**「オンデマンド」は断られます**。自前の ComfyUI のときと同じで、
  あれは「箱を手放す」という約束であり、ここには手放す箱がありません。

### 向こうが役を off にしたとき

向こうのカタログは、モードが `off` の役や、最後の有効なモデルが消えた役を、**単に載せ
なくなります**。こちら側にはそれが**その役のモデル 0** として届きます。

- 行はパネルに残り、「モデルが無い」として出ます、
- 要求は `503 engine_unavailable` と「このエンジンには有効なモデルがありません——
  管理者が選ぶ必要があります」で断られます、
- 起動メニューからはそのモデルが消えます。

ここで「選ぶ必要がある管理者」は**向こうの管理者**です。向こうが戻せば、1 巡回のうちに
また使えます。

## 最初の要求が待つもの

借りたエンジンは、たいてい眠っています。向こうの配備は要求があってから GPU の箱を買うので、
**その後の最初の 1 本が冷間起動をまるごと払います**——インスタンス、イメージ、VRAM への
ロード。

- **向こうの配備が自分の要求で測った値**（ADR 0071）: 冷間起動から `llm` 役が 527 秒、
  `image` 役が 165 秒。
- 🔴 **借りた場合の数字は測っていません。**2 つの配備の間には、2 つの保持、2 つの再試行
  ループ、そしてインターネットの往復が挟まります。「分の単位」を見込み、上の数字は**下限**
  として扱い、借りた場合の値として引用しないでください。

その間に何が起きるか（長い 1 本目を「失敗」と読まないために）。

- **チャット（ストリーミング）。**接続を保持したまま、10 秒ごとに heartbeat を流します。
  上限は `AF_ENGINE_WAKE_TIMEOUT`（既定 900 秒）。
- **それ以外（非ストリーミング）。**向こうの配備が約 45 秒保持し、そのうえで
  `503 engine_waking` を `Retry-After` つきで返します。その答えはそのまま中継されます。
  こちらの配備は**借りた行**を 75 秒保持します——向こうの言い分が届くほうが普通になるよう、
  意図的に長くしてあります——自分で管理する行は 45 秒のままです。
- **こちらの保持が先に切れても、答えは `engine_waking`** であって `engine_unavailable`
  ではありません。この区別が効きます。画像ツールは `engine_waking` なら最長 16 分まで
  訊き続け、`engine_unavailable` は**一度も再試行しません**。間違えると、いま起きつつある
  箱が恒久的な失敗になります。

🔴 **向こうの 45 秒は向こうの設定で、こちらからは読めません。**向こうの運用者が延ばして
いれば、こちらが何を設定しても再びこちらの保持が先に切れます——それで構わないのは、
1 つ上の項のおかげです。`AF_ENGINE_PLAIN_HOLD` を設定すれば保持を上書きできますが、
それは**すべての行に効く 1 つの値**なので、借りた行のために上げるとこの配備が自分で管理する
行も上がります。`ecs-ec2` ではそれがロードバランサでの 504 の戻し方そのものです。理由が
無い限り触らないでください。

## パネルに出るもの・出ないもの

- **外部管理**として、向こうのフリートの URL を持って出ます。ここで「管理」されていない
  のは、ここに管理すべきサービスが無いからです。
- **warm** は**向こうの配備が自分のエンジンについて最後に観測したもの**を、そのカタログが
  報告するまま読んだ値です——こちらから確かめた結果ではありません。こちら側は、パネルでも
  どこでも、借りたエンジンを**一度もプローブしません**。プローブは向こうのゲートウェイに
  着地して需要を記録し、箱を買ってしまいます。
- **推測せずに省くもの:** 状態・希望台数・どの箱・いつ止まるか・アイドル窓。どれも、他人の
  インスタンスについてこの配備が主張してよいものではありません。
- **稼働の履歴は出ません。**ヒートマップは制御ループが取る標本から描くもので、借りた行には
  制御ループがありません。
- **「次の冷間起動に +N 秒」**の見積もりは 0 と出ます。ファイルのサイズは通信路に乗らず、
  そもそもその見積もりは**この配備が払わない箱**についてのものです。

## 誰が払い、何が記録されるか

**箱を買って払うのは向こうの配備です。**この配備にはインスタンスが無いので、借りたエンジン
について**この配備のクラウド費用には何も出ません**。

**記録**は役によって違い、その違いは「借りられる側」に立つと重要です。

- **チャット（`llm`）は両側に使用量の行が出ます。**この配備はふだんどおり数えます。向こうの
  配備も、借りているメンバーシップに対して数え、その行は**借りたセッションの名前**を
  持ちます——向こうの運用者が借り手どうしの支出を見分けられる唯一の手がかりです。
  （名前はこちらの配備が申告し、向こうはそのまま受け取ります。ラベルであって権限では
  ありません。）借りているメンバーシップにはワークスペースが動いていないので、向こうの
  使用量の返送は届け先が無く、何もしません——**無関係なメンバーの台帳は汚れません**。
- **画像は、どちらの側にもエンジンの使用量の行が出ません。**画像の答えにはトークン数が
  含まれないので、エンジンの台帳には何も書かれません。こちら側でメンバーの画像生成が
  見えなくなるわけではなく、画像ツールがファイルを保存するときに自分の使用量の行を
  書きます（数えるのはトークンではなく枚数です）。しかし**向こうの運用者から見えるのは
  「買われた GPU」だけで、誰のためかの記録は残りません**。この穴は既知で、まだ塞がって
  いません。複数の配備にエンジンを貸すなら、画像は今日のところ帰属させられません。

## うまくいかないとき

まず見るのは**借りる側**の Control Plane のログです。現れなかった借用行は、ほかのどこにも
見えないからです。拾う価値のある行:

| 行の内容 | 意味 |
|---|---|
| `borrowing is declared but … is unset` | URL とトークンの片方しか設定されていない。何も借りていない |
| `is borrowed from …` | 役を取り込めた——これが成功の行 |
| `reading the borrowed catalogue from … failed` | 向こうのフリートに届かない、または断られた。状態コードは同じ行にある |
| `is already served by a … row` | ローカルの行がその役を持っている。向こうのものは無視された |
| `declares lifecycle "remote" but AF_REMOTE_ENGINE_URL / AF_REMOTE_ENGINE_TOKEN are unset` | 手書きの表の行に借りる先が無い。その役は出ない |

セッション側に見える答えは、

- **カタログのログ行の `401`** — 向こうの配備でそのメンバーシップが消されたか、トークンが
  違います。こちらからは同じに見えますが、それで正しい——消されたメンバーと壊れた資格情報は
  同じだけの権限です。
- **`400 engine_not_ours`** — この配備のエンジンのパネルで、借りた役に書き込もうとした。
  向こうの配備のパネルでどうぞ。
- **`503 engine_unavailable`（「有効なモデルが無い」）** — 向こうがその役を off にしたか、
  有効なモデルが 1 つも無い。
- **`503 engine_waking`** — 冷間起動の正常な姿。`Retry-After` を持っていて、画像ツールは
  訊き続けます。

🔴 **避けるべき近道が 1 つ。**`AF_COMFY_URL` を向こうのフリートの画像の経路
（`https://…/engine/image/v1`）に向けると、ここまでの手当て無しに動きそうに見えますが、
これが最悪の組み合わせです。その行はこちらからヘルスチェックされ、その検査は**向こうの
ゲートウェイに着地して需要を記録し、GPU の箱を買います**——そのうえで失敗します。検査が
許すのは 5 秒で、冷間起動は分の単位だからです。**失敗する検査が時間課金の GPU を買う**の
は、回り道してでも避ける価値のある唯一の結末です。

どの形態がどのエンジンの在り方に対応しているかは
[ref/deploy-targets.md](../ref/deploy-targets.ja.md) にあります。
