# 費用を抑える

[English](cost.md) | 日本語

ECS の配備で、だれも使っていなくてもかかる費用と、使うほど増える費用を知り、下げるつまみを選びます。
金額は、東京リージョン（ap-northeast-1）の定価を月 730 時間で計算した目安です。料金は変わるので、自分のリージョンの料金で計算し直してください。us-east-1 はおよそ 3 割安くなります。

## 全体像

| あなたがやること | 起きること |
|---|---|
| 何もしない | 止まっているワークスペースは 0 円。常時動く 4 つのリソースに月 $107 ほどと、EFS の使用量の分がかかる |
| 使わない期間は `pause.sh` で一時停止する | NAT・Control Plane・RDS の計算・スロット・GPU が止まり、ALB と保管の料金だけが残る |
| 起動の多い配備を `ecs-ec2` にする | スロットがイメージをキャッシュするので、起動ごとの NAT の通信が減る |
| 本番は `Persistence=retain` で構築する | スタックを消しても EFS と RDS が残り、毎日バックアップされる |

## 常にかかる費用

ワークスペースをすべて止め、だれもログインしていないときの費用です。

| 常時動くもの | 料金 | $/月 |
|---|---|---|
| NAT ゲートウェイ ×1 | $0.062/時 | **45.3** |
| **Control Plane / Console の Fargate タスク ×1**（0.5 vCPU + 1 GB、`DesiredCount: 1`） | $0.05056/vCPU 時 + $0.00553/GB 時 | **22.5** |
| RDS db.t4g.micro シングル AZ | $0.025/時 | **18.3** |
| ALB ×1 | $0.0243/時（+ $0.008/LCU 時。アイドルならほぼ 0） | **17.7** |
| RDS のストレージ 20 GiB | $0.138/GB 月 | 2.8 |
| Secrets Manager（RDS が管理するパスワード） | $0.40/シークレット | 0.4 |
| Cloud Map のプライベート名前空間（Route 53 のプライベートゾーン） | — | 0.5 |
| ECR（Control Plane とワークスペースで約 1.05 GB） | $0.10/GB 月 | 0.1 |
| EFS（全員のホームが残る） | $0.36/GB 月 | 使用量 |
| EFS のバックアップ（`Persistence=retain` のときだけ） | ウォームのバックアップストレージ $0.06/GB 月 | 使用量 |
| **合計** | | **約 $107/月 + EFS** |

- 止まっているワークスペースは**かかりません**。ACM、NAT の EIP、標準の SSM パラメータも無料です
- **動いている**ワークスペースは、Fargate で **$0.0616/時**（1 vCPU + 2 GB）です。1 日 8 時間・月 22 日なら月 $11 ほど、24 時間動かし続けると月 $45 です
- 費用の下限は、利用者の数に関係なく常時動く 4 つのリソースで決まります

## 費用を下げるつまみ

| つまみ | 下がる額 | 引き換え |
|---|---|---|
| NAT ゲートウェイを **NAT インスタンス**にする（t4g.nano $3.9 + 8 GB の gp3 $0.8 + パブリック IPv4 $3.7 ≈ **月 $8**） | 月 $37 ほど（マネージドは **$45**） | 自分で運用する。送信元/送信先チェックをオフ、iptables の MASQUERADE、置き換え用の ASG とルートの書き換え |
| Control Plane のタスクを 256/512 に下げる | 月 $11 ほど | 収まるかは確かめていない |
| 使わない期間に一時停止する | NAT・Control Plane・RDS の計算・スロット・GPU の分 | ALB・EFS・RDS のストレージは残る（[スクリプトで構築・一時停止・撤去する](lifecycle.ja.md)） |
| 試すだけなら、デプロイ → E2E → `delete-stack` でスタックを一時的なものにする | ほぼすべて | 毎回再構築する |

ALB と RDS は実質的に下限です。Aurora Serverless v2 は、最小の 0.5 ACU でもこれより高くなります。

### 1〜2 人なら EC2 1 台のほうが安い

| 構成 | 月額 |
|---|---|
| EC2 1 台（`deploy/aws/ec2-single`）の t3.medium + 30 GB の gp3 + EIP、**ワークスペース込み** | 約 $47 |
| 同じく t3.large（既定） | 約 $87 |
| 切り詰めた ECS の配備 | 約 $72 に、ワークスペースの時間を足す |

ECS のほうが安くなるのは、**同時に 8〜10 人**ほどが使うあたりからです。1 台の VM は全員のピークに合わせて 24 時間動かす必要がありますが、Fargate は各ワークスペースが動いた時間だけかかります。費用とは別に、ECS にはワークスペースを隔離できる利点もあります。

## NAT を通る通信

ワークスペースは git や Anthropic（公開インターネット）に接続するので、NAT が要ります。プライベートサブネットのタスクはパブリック IP を持たないので、ECR・CloudWatch Logs・SSM にも NAT を通って届きます。つまり NAT は、メンバーがインターネットを使うためだけのものではなく、**ワークスペースの起動経路**にもあります。

| 通信 | 経路 |
|---|---|
| git・Anthropic・npm・パッケージのレジストリ（本来の開発の通信） | NAT |
| ECR の認証とマニフェスト、Logs、SSM の小さな呼び出し | NAT |
| Fargate のワークスペースのイメージの層 | NAT（タスクの ENI で取得するため分けられない） |
| `ecs-ec2` のワークスペースのイメージの層 | S3 ゲートウェイエンドポイント（スロットの ENI で取得する） |
| `60-engines` のモデルの S3 Bucket の読み込み、通信の記録の S3 への書き出し | S3 ゲートウェイエンドポイント |
| `60-engines` の取り込みでの Hugging Face / Civitai からのダウンロード | NAT |

ECR・Logs・SSM などのインターフェースエンドポイントは、わざと置いていません。1 つあたり $0.01/AZ/時 × 2 AZ かかり、合計すると、通信を肩代わりさせたい NAT ゲートウェイの料金を上回ってしまいます。

### 起動ごとの費用

Fargate はイメージをキャッシュしないので、起動のたびにイメージ全体（圧縮で約 918 MiB）を NAT 経由で取得します。NAT のデータ処理料は GB ごとにかかります。

- $0.045〜0.062/GB なら、918 MiB ≈ 0.9 GB で**起動 1 回あたり $0.04〜0.06**です
- 1 日 100 回（月 3,000 回ほど）なら、NAT の時間料金に加えて**月 $120〜180**ほどです
- 料金はリージョンで違い、変わります。[Amazon VPC の料金](https://aws.amazon.com/vpc/pricing/)の「NAT Gateway」で確かめてください。ここの数字は例で、見積もりではありません

`ecs-ec2` では、スロットのルートボリュームがイメージのキャッシュです。

- 同じイメージを持つスロットで起動し直せば、層は取得しません。キャッシュが効いた起動では、NAT を通った通信はテスト用の配備で合計約 65 MiB でした
- 新しいスロットや作り直したスロット、キャッシュが外れたとき、イメージを更新したときは層を取り直しますが、その通信は S3 ゲートウェイエンドポイントを通ります。NAT を通るのは ECR の認証とマニフェストだけです（テスト用の配備で確かめたもので、本番ではまだです）
- 起動が多い配備では `ecs-ec2` を選びます
- ゴールデンスナップショットは別物です。起動時のインストールを済ませたホームのことで、起動の時間は短くなりますが、NAT を通るバイト数は減りません

NAT ゲートウェイと egress ゲートウェイの比べ方は [外向きの通信をゲートウェイで制御する](egress-gateway.ja.md#nat-ゲートウェイとの違い) にあります。

## S3 ゲートウェイエンドポイントを有効にする

ワークスペースは自分のサブネットを持ちます。

- `00-network` は AZ ごとにワークスペースのサブネットを作り、外向きの経路が NAT だけのワークスペース用ルートテーブルに関連付けます。Control Plane はワークスペースのタスクの ENI をそこに置きます（`AF_ECS_WORKSPACE_SUBNETS`、`30-ingress` の `WorkspaceSubnets` から）
- S3 ゲートウェイエンドポイントは、**プライベートのルートテーブルだけ**にあります（Control Plane、`ecs-ec2` のスロットのインスタンス、推論エンジン、ホーム用のタスク）。ポリシーが通すのは、ECR の層、AL2023 のリポジトリ、SSM エージェントの更新用と ECS エージェントのダウンロード用の S3 Bucket、モデルの S3 Bucket だけです
- 同じリージョンへのリクエストがこのポリシーで拒否されると、NAT には回らず AccessDenied になります。そのため、ワークスペースをこのルートテーブルに置いてはいけません。ワークスペース自身の S3 への通信は、記録できるように、いつも NAT（または egress ゲートウェイ）を通ります
- エンドポイントには `S3EndpointEnabled`（既定は `true`）のスイッチがあります。プライベートサブネットでまだワークスペースが動いているあいだは、`false` にしておきます。そのワークスペースがワークスペースのサブネットで起動し直すまで、ポリシーがその S3 への通信を拒否するためです

### 動いているスタックを移す

メンテナンスの時間を取ります。動いているワークスペースはすべて再起動します。

1. `cfn/00-network.yaml` を `S3EndpointEnabled=false` で、変更セットを通してデプロイします

   ```bash
   aws cloudformation deploy … --capabilities CAPABILITY_IAM --parameter-overrides \
     S3EndpointEnabled=false --no-execute-changeset
   ```

   そのあと `describe-change-set` で中身を見ます。
   - 増えるのは 6 つのリソースです。サブネット 2 つ、ワークスペースのルートテーブル、その既定ルート、関連付け 2 つ
   - S3 エンドポイントがすでにあるスタックでは、`S3Endpoint` の **Remove** も出ます。これは想定どおりで、作業のあいだ、プライベートサブネットからの S3 への通信は NAT を通ります
   - ほかに変更や置き換えがあれば止めます。なければ実行します
   - 既定値でデプロイして、この手順を飛ばさないでください。`S3EndpointEnabled=true` だと、ワークスペースがまだプライベートサブネットにいるうちに、`S3Endpoint` が制限つきのポリシーに **Modify** されます
2. `update.sh` を実行します。ネットワークスタックの `WorkspaceSubnets` を Control Plane に渡します（`AF_ECS_WORKSPACE_SUBNETS`）。以降の起動はワークスペースのサブネットに置かれます。`update.sh` は最後に、まだプライベートサブネットにいる動作中のワークスペースを一覧します
3. 動いていたワークスペースをすべて止めて起動し直します（`pause.sh --status`、または `aws ecs list-services` で `desiredCount > 0` のもの）。動いているタスクは今の ENI を持ち続け、起動し直したときにだけ移ります。各タスクの ENI がワークスペースのサブネットにあることを確かめます

   ```bash
   aws ecs describe-tasks --cluster <c> --tasks <t> --query \
     "tasks[].attachments[].details[?name=='subnetId'].value"
   ```

4. `cfn/00-network.yaml` を `S3EndpointEnabled=true` でデプロイします（`S3Endpoint` の **Add** が 1 つ）。プライベートサブネットからの S3 への通信が、NAT のルートからエンドポイントのルートに移ります。開いている TCP 接続は切れるので、大きなモデルの取得・取り込みやイメージの取得が動いていないときにやります

| 場面 | 起きること |
|---|---|
| 戻す | `S3EndpointEnabled=false` で、プライベートサブネットの S3 がすべて NAT に戻ります。手順 1 のあとなら、`S3Endpoint` を消すだけのスタックの更新です。ワークスペースのサブネットとルートテーブルは、使われている可能性があるうちは残します。消すのはパラメータではなくテンプレートの変更です |
| 新しく構築する | `standup.sh` は、ネットワークスタックがなければ、最初からエンドポイントを有効にして構築します（ワークスペースはまだありません） |
| 一時停止・再開 | `pause.sh` と `standup.sh` は、このスイッチを一度も持ったことのない稼働中のネットワークスタックに `S3EndpointEnabled=false` を渡すので、副作用で有効にすることはありません。`pause.sh --up` は、Control Plane が使っていないワークスペースのサブネットがあると警告します |
| 一時停止中（`NatEnabled=false`） | プライベートサブネットから S3 にはエンドポイントで届きます（ポリシーが通すものだけ）。ECR の API・ログ・ワークスペースのルートテーブルの外向きの経路には届きません |

## データを残すかを決める

`10-data.yaml` の `Persistence` パラメータで決めます。

| 値 | 意味 |
|---|---|
| `delete`（既定） | 試すための使い捨て。EFS と RDS はスタックと一緒に消え、バックアップもない |
| `retain` | 本番向け。EFS は `Retain` で、AWS Backup で毎日バックアップし `EfsBackupRetentionDays`（7）日残す。RDS は `Snapshot`、7 日のバックアップ、削除保護 |

**本番は `Persistence=retain` で構築します。** バックアップと復元は [EFS をバックアップ・復元する](backup.ja.md) にあります。
