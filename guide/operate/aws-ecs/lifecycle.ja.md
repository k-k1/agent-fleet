# スクリプトで構築・一時停止・撤去する

[English](lifecycle.md) | 日本語

ECS の配備を、4 つのスクリプトで記録し、一時停止し、撤去し、建て直します。
配備は `update.sh` と同じく **AWS のプロファイル**で指し、ほかの値はすべて動いている配備から読みます。同じテンプレートから建てた 2 つの配備でも、プールのスタック名が `af-ecs-pool` と `af-ecs-ec2-pool` のように違うことがあり、決め打ちの既定値では外れるためです。

## 全体像

| あなたがやること | 起きること |
|---|---|
| `capture-env.sh` で記録する | 各スタックに渡したパラメータが、リポジトリの外のファイルに残る |
| `pause.sh` で止める | 時間で課金されるものを、何も取り残さない順番で止める・消す。データは残る |
| `pause.sh --up` で戻す | NAT ゲートウェイ・データベース・Control Plane が戻る。ワークスペースはメンバーが起動する |
| `teardown.sh --yes` で撤去する | 配備のすべてを、止まらない順番で消す |
| `standup.sh --yes` で建て直す | 記録したパラメータで配備を建てる |

```bash
./capture-env.sh --profile <p> --region <r>            # record a live deployment
./pause.sh       --profile <p> --region <r> [--up]     # stop / resume (data stays)
./teardown.sh    --profile <p> --region <r> [--yes]    # delete everything
./standup.sh     --profile <p> --region <r> [--yes]    # build it back
```

## 共通の約束

- **`--yes` がなければ何もしません。** 計画（撤去なら、消えるものの一覧も）を表示して終わります。端末で `--yes` を付けると、さらに FQDN の入力を求めます
- **シークレットは記録も復元もしません。** SSM の SecureString は CloudFormation のパラメータではありません。`standup.sh` は、それがあることだけを確かめます。撤去は既定で `/af-cp/*` を残すので、同じアカウントに建て直せます

## 最初に `capture-env.sh` を実行する

各スタックに渡したパラメータを `~/.config/agent-fleet/deploy/<profile>.<region>/` に書きます。値はアカウントに固有なので、リポジトリの外に置きます。

- テンプレートはリポジトリにありますが、**それに渡した値は配備の中にしかありません**。`delete-stack` で消えます
- `teardown.sh` は、この記録がないと実行を拒みます。`standup.sh` は、これがないと何も建てられません
- **空で**記録したパラメータに同じ名前のスタックの出力があれば、その値を使います。空のパラメータは「スタックが自分で作った」ことが多く、作ったものの ID は出力にしかないためです（`NatEipAllocationId` など。[外向きの IP アドレスを固定する](egress-ip.ja.md)）

### 記録はイメージの存在を保証しない

記録が保証するのはパラメータで、そこに書かれたイメージがまだあるかは別です。次の 3 つが重なると、記録は残っているのに、指すワークスペースのイメージがどこにもない、という状態になります。

| 原因 | 中身 |
|---|---|
| `dev-deploy.sh` | イメージを焼き直さない実行では、ECR の中でワークスペースのイメージに付け直す。そのタグのワークスペースは GHCR に届かない |
| `capture-env.sh` | `--force` がないと記録し直さない。記録した `AF_IMAGE_TAG` は、記録した日のままになる |
| `20-platform` の ECR | `EmptyOnDelete: true` なので、撤去でイメージも消える |

そのため、次のように新しさを保ちます。

- `dev-deploy.sh` は、最後に新しいタグを記録に書きます
- `capture-env.sh` は `AF_IMAGE_RECOVERABLE=yes|no|unknown`（そのタグが GHCR から取れるか）を記録します。`unknown` は `crane` がなかったという意味で、「もうない」とはみなしません
- `teardown.sh` は、確認の**前**に、3 つのどれに当たるかを表示します。ECR から `crane copy` で救えるのは、そのときが最後です
- `standup.sh` の事前確認も名前を挙げて知らせますが、その時点では写す元がありません

開発用の配備がどれかは、このリポジトリには書いてありません。`dev-deploy.sh` は、手元の記録に `AF_DEV_DEPLOY=1` がある配備だけを触ります。

## `pause.sh` で一時停止する

時間で課金されるものを、何も取り残さない順番で止めるか消します。

| 順番 | 止まるもの | 戻るとき（`--up`） |
|---|---|---|
| 1 | ワークスペース | メンバーが自分で起動する |
| 2 | スロットと推論エンジンの GPU のインスタンス。止まるのを待つ。`--fast` なら直接止める | — |
| 3 | egress ゲートウェイ（`EgressRoute=gateway` のとき） | NAT ゲートウェイと一緒に起動し、Control Plane の前とあとで待つ |
| 4 | Control Plane | データベースのあと |
| 5 | まだ生きている推論エンジンのインスタンスを終了する | — |
| 6 | RDS のインスタンス（`--keep-db` で残す） | Control Plane より先に起動する |
| 7 | NAT ゲートウェイ（`--keep-nat` で残す） | いちばん先に戻す。Control Plane のイメージの取得とログが通るため |

- Control Plane が止まると、推論エンジンのインスタンスを終わらせるものはほかにありません。g6.xlarge を残すと 1 日 $28 ほどかかるので、最後にまとめて終了します
- `--status` で、いまの状態を表示します
- egress ゲートウェイの止め方と待ち方は [外向きの通信をゲートウェイで制御する](egress-gateway.ja.md#一時停止する) にあります。インターフェースと Elastic IP には触りません

### NAT ゲートウェイは消して作り直す

NAT ゲートウェイには「停止」がないので、消します。**`delete-nat-gateway` ではなく、`00-network` の `NatEnabled` パラメータで消します。** 手で消すと、スタックが存在しない物理 ID を持ったままになり、次の更新が失敗します。

- `pause.sh` は `cfn/00-network.yaml` を `NatEnabled=false` / `true` で `cloudformation deploy` します。ほかのパラメータは今の値のままです
- 往復はそれぞれ 1〜2 分です。`NatEip` は保持されるので、送信元の IP は変わりません
- ゲートウェイがないあいだ、プライベートサブネットからは ECR・ログ・インターネットに届きません
- 一時停止中に記録すると `NatEnabled=false` が残ります。`standup.sh` はそれを `true` に置き換えます
- `pause.sh` は**このチェックアウトの**テンプレートをデプロイします。古いネットワークスタックは、一時停止か再開でワークスペースのサブネットを得ます。S3 エンドポイントはオフ（`S3EndpointEnabled=false`、スイッチを持ったことのないスタックに渡す）のまま得ます
- `--up` は、ワークスペースが起動できるようになる前に、Control Plane がネットワークのワークスペースのサブネットを使っていなければ警告します。`update.sh` を実行し、[S3 ゲートウェイエンドポイントを有効にする](cost.ja.md#s3-ゲートウェイエンドポイントを有効にする) の手順に進みます

### RDS は 7 日で勝手に起動する

> [!CAUTION]
> **AWS は、止めた RDS のインスタンスを 7 日後に自動で起動します**（イベント `RDS-EVENT-0154`）。止めることはできません。

`10-data`（`RdsRestopOnForcedStart`、既定は `true`）が、もう一度止める仕組みを持っています。

- EventBridge のルール（`RDS-EVENT-0154` の強制起動と、`RDS-EVENT-0088` の起動）と、小さな Lambda です。`RDS-EVENT-0088` は、Lambda の約 46 分の待ちと再試行より長くかかった起動も拾います。止め直すと、7 日の時計もやり直しになります
- 動くのは、タグ `af-paused=true` の付いたインスタンスだけです。タグは「一時停止中」という意味です。わざとデータベースを動かしておくときは、タグを外すか `--up` を実行します
- `pause.sh` はデータベースを止める前にタグを付け、`--up` の最初に外します（`--keep-db` でも）。タグを書けなければ失敗します（データベースは止まったままです）
- 古い配備は、`10-data` を 1 回デプロイすると仕組みが入ります。`--status` は Lambda があればその名前を表示し、Control Plane が止まっているのにデータベースが動いていれば警告します
- データベースはふつうの RDS PostgreSQL のインスタンスです。Aurora のクラスターには `RDS-EVENT-0153` とクラスターの呼び出しが要り、ここにはありません

`--up` との競合は、なくせませんが小さくしてあります。RDS には「比べてから止める」操作がないためです。

- Lambda の最後のタグの読み込みと停止の呼び出しは、接続 3 秒・読み込み 5 秒のタイムアウトで、SDK の再試行はしません
- `--up` はタグを外してから 20 秒（`AF_TAG_GRACE_SEC`）待ってデータベースの状態を読みます。止まりかけていれば起動し直し、Control Plane が起動したあとにもう一度読んで、使えなければ失敗します
- タイムアウトは呼び出し側が待つ時間を決めるだけで、送った要求が効くかどうかは決めません。応答が失われた停止が `--up` のあとに効くことがあり、そのときは上の失敗になります。`--up` をもう一度実行すれば、データベースが起動します

## 撤去と建て直し

- 撤去の手順と、撤去しても残るものは [撤去する](teardown.ja.md) にあります。`teardown.sh` はその手順をそのまま実行します
- `standup.sh` は、記録したパラメータでスタックを建てます。読み上げ（`params/50-tts`）と推論エンジン（`params/60-engines`）は、そのファイルがあるときだけ建てます（[日本語の読み上げを足す](tts.ja.md)・[推論エンジンを足す](engines.ja.md)）
