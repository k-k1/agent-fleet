## 導入を検討している方へ

技術評価の入口として、まずここを読んでください。

**何ができるか。** チームが CLI のコーディングエージェントをブラウザから使えます。
各メンバーは隔離された環境（専用コンテナ）を持ち、リポジトリをクローンし、エージェントや
シェルのセッションを動かします。端末に触りたくない人向けのチャット中心の使い方もあります。
管理者はブラウザから、メンバーの追加・上限の設定・使用状況と監査ログの確認・外向き通信先の
観測ができます。部署を**テナント**で分ければワークスペースは完全に隔離されます（既定は 1 テナント）。

**必要なもの。**

- **Docker の動く Linux ホスト**（Engine + `docker compose`）。**1 台で足ります。**
- **公開ドメイン**と、そこを指す DNS（自動 TLS のため）。公開 DNS を用意できない
  閉域配備には自己署名の代替があります（[02 導入](02-install.ja.md)）。
- **ログイン用のプロバイダ**: Google の OAuth クライアント、または Entra ID / Okta /
  Keycloak / Auth0 / Cognito / GitLab の OIDC アプリ登録。**何個有効にしても、登録する
  リダイレクト URI は 1 つだけ**です（[05 サインイン](05-signin.ja.md)）。
- **エージェントの席は各メンバーが持ち込みます。**初回起動の後、各自が自分の席でサインイン
  します。個人プランより会社の Team/Enterprise 席を推奨します。

**提供モデルと防御の姿勢。** 1 社 1 配備、各社が自社の基盤に独立して建てます。
会社間の隔離は**配備が別であること**で保証され、プロセス内の境界ではありません。
だから侵害の影響範囲は**その 1 配備の中に閉じます**。ワークスペースの中の境界は、
エージェントが**任意のコードを実行する**前提で設計してあります。守っているのは、
他ユーザーのデータ・コントロールプレーンとホスト・秘密・持ち出しです。

**正直に開示すべき残留リスクが 4 つ**あります——`docker.sock` はホスト root 相当、
`AF_MASTER_KEY` の紛失は暗号的消去、バックアップは機微、ホストへのアクセスは全権。
[04 守る](04-secure.ja.md) と `SECURITY.md` にあります。
**採用を判断する前に必ず読んでください。**

## 頭に入れておく最小のモデル

1 台のホストで `docker compose` が管理するのは**2 つのサービス**です。**Control Plane** は
ログイン認証・テナントとメンバーの管理・ワークスペースの起動停止・全 API の中継を行い、
**Caddy** は玄関として TLS 証明書を自動取得・更新して背後の CP へ流します。

**利用者のワークスペースのコンテナは compose の管理下にありません。**CP が実行時に起動します。
ここから、人が驚く帰結が出ます。

- `docker compose down` や CP の再起動では**ワークスペースは止まりません**。利用者は切れません。
- バックアップのために CP を一時停止しても、動いているワークスペースには影響しません。
- 逆に「compose を止めれば全部止まる」は**嘘**です。全ワークスペースを強制停止するのは
  別の操作です（[03 動かし続ける](03-run.ja.md)）。

永続データは**すべて `DATA_DIR` の下**にあります——DB、各ユーザーのホーム、封筒暗号化された
資格情報、Caddy の証明書。バックアップの対象はこのディレクトリです。唯一の例外が
`AF_MASTER_KEY` で、これは `DATA_DIR` にもバックアップにも**入れません**。

コンテナからホストの Docker デーモンを駆動する方式には、**破ると黙って壊れる制約が 3 つ**
あります——ホストネットワーク、`DATA_DIR` の絶対パスの一致、docker グループの GID。
compose の定義がそれを封じ込めていますが、意味は
[06 切り分ける](06-diagnose.ja.md) が「この症状は何を意味するか」の側から説明します。

## 責任チェックリスト

- [ ] `AF_MASTER_KEY` を**データとは別の金庫**に置き、独立にバックアップした。
      紛失 = 全資格情報が永久に復号不能。
- [ ] `backup.sh` を定期実行し、保管先を権限と暗号化で守っている。
- [ ] 復旧手順を**一度は実際に試した**（`DATA_DIR` の basename 制約を含めて）。
- [ ] アップグレードの前に毎回バックアップを取っている。**ダウングレードはありません。**
- [ ] ログイン許可リストを設定した。**空は全拒否**（fail-closed）。
- [ ] Entra ID を使うなら、issuer を自社テナントの GUID に固定した。
      common エンドポイントのままだと**全 Microsoft アカウント**がログイン画面の前に立ちます。
- [ ] ホストで SSH・sudo・docker を実行できる人を最小限にした（= ホスト root 相当）。
- [ ] egress 統制を入れるなら、段階の方針を理解した——まず log-only で観測、それから enforce。
- [ ] 脆弱性を見つけたときの報告手順を知っている（`SECURITY.md`）。
