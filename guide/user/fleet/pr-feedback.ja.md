# PR のレビューをセッションに伝える

[English](pr-feedback.md) | 日本語

プルリクエストの CI が落ちたり、レビューで変更を求められたりしたら、その PR を出したセッションに Agent Fleet が知らせて、修正と push を促します。
あなたが気づくまで、セッションが止まったままになることがなくなります。

## 全体像

| あなたがやること | エージェントがやること |
|---|---|
| 設定で「PR へのフィードバックをセッションに伝える」をオンにする | PR の CI の失敗やレビューの指摘を受け取り、直して push する |
| マージのコンフリクトは、通知を見て自分で判断する | — |
| （設定は要らない） | 気になる PR を自分でウォッチし、変わったら知らせてもらう |

## オンにする

**⚙設定 →「エージェント」** の「セッション」で、「**PR へのフィードバックをセッションに伝える**」をオンにします。画面は [セッションから子セッションを起動する](child-sessions.ja.md#オンにする) にあります。

あなたが頼まなくてもターンを使い、停止中のセッションを起動するので、既定ではオフです。

## 伝える内容

| 出来事 | 伝え方 |
|---|---|
| 最新のコミットで CI が失敗した | そのコミットのチェックがすべて終わってから、失敗したチェックの名前をすべて並べて伝える。push したコミットごとに 1 回まで |
| レビューで変更を求められた、未解決のレビュースレッドが増えた | PR ごとに 3 回まで |
| マージのコンフリクト | セッションには伝えず、通知センターの「**プルリクエスト**」に届く。編集より先に、ベースをどうするかの判断が要ることが多いため |
| アーカイブ済みのセッション宛て | 通知センターに届く |

- セッションには、`[agent-fleet:notice kind=pr-feedback reply=none]` で始まる行として届きます。会話には、あなたの指示ではなく Agent Fleet からのお知らせとして印が付きます
- 伝えた内容は Agent を再起動しても覚えているので、同じことを 2 回伝えることはありません

## どのセッションに伝えるか

- 各セッションがいるブランチのプルリクエストを見ます
- セッションが「起動のもとになった」「作った」「作業中」として持つ PR リンクも、最大 5 件まで見ます。GitHub と Bitbucket の両方が対象です
- レビューや見守りのためだけに PR を持つセッションには伝えません
- 同じ PR を複数のセッションが持つときは、つながりの強いセッションに伝えます。起動のもと、作った、作業中の順で、同じ強さなら新しいほうです

## いつ伝えるか

- セッションが待機していて、入力を受け付けられるときだけ送ります
- 作業中のセッションや、あなたの返事（質問・プラン・許可）を待っているセッションには、手が空くまで送りません
- **停止中のセッションは、起動してから伝えます。** あなたが止めたセッションも同じです。起動は 1 つずつです

## セッションが自分で PR をウォッチする

エージェントは、プルリクエストを繰り返し確かめに行く代わりに、変わったら知らせてもらうよう頼めます。設定は要らず、いつ使うかはエージェントが決めます。

| af ツール | すること |
|---|---|
| `watch` | プルリクエスト（`owner/repo#45`、自分のリポジトリなら `#45`、または GitHub の URL）と、知りたい出来事を渡してウォッチする |
| `list_watches` | ウォッチを一覧する |
| `unwatch` | ウォッチを 1 つ終える |

ウォッチできる出来事は、チェックが終わった、マージのコンフリクトが起きた、マージできる状態になった、マージされた・クローズされた、レビューで変更を求められた、未解決のレビュースレッドが増えた、などです。プルリクエスト自体が削除された（リポジトリごと消えた、アクセスを失った）場合は、期限まで待ち続けず、その旨の知らせを送ってウォッチを終えます。一時的な GitHub のエラーやレート制限で終わることはありません。

- **チェックの失敗を早く知る・最後に知る。** `pr.checks.failing` は、チェックが 1 つでも失敗し、ほかがまだ動いている間に、コミットごとに 1 回だけ伝え、そこまでに失敗したチェックを挙げます。`pr.checks.failed` と `pr.checks.completed` は、これまでどおり全チェックが終わってから届きます。`pr.checks.*` は `pr.checks.failing` を含むので、このパターンで見ている既存のウォッチには、コミットごとに通知が 1 件増えることがあります。既定の `until: first` では `failing` を受けた時点でウォッチが終わり、最終結果は届きません。最終結果を待つときは `pr.checks.completed` と `pr.checks.failed` を名前で指定し、早い失敗と最終結果の両方を受けたいときは `until: deadline` を使ってください。PR へのフィードバックは変わらず、全チェックが終わってから失敗を伝えます
- **GitHub と Bitbucket に対応しています。** プルリクエストはあなた自身の接続で読むので、ウォッチできるのはあなたの接続で読めるものだけです
- **いつ伝えるか**は PR へのフィードバックと同じです。頼んだ時点ですでに起きていることは、すぐに伝えます
- **同じウォッチを頼み直しても増えません。** すでにあるウォッチ（同じプルリクエスト、同じ出来事、同じ終わり方）をもう一度頼むと、2 つ目は作らず既存のウォッチを返し、期限は 2 つのうち遅いほうに延びます。同じ出来事に当てはまるウォッチが 2 つあるとき（たとえば `pr.checks.completed` と `pr.checks.*`）も、伝えるのは 1 回で、どちらのウォッチもその出来事を伝え済みとして数えます
- **フィードバックと二重にはなりません。** PR へのフィードバックがオンでも、自分の PR のチェックの失敗・変更の要求・未解決スレッドの増加をウォッチしているセッションには、それをウォッチからだけ伝え、ウォッチが終わったあとも PR へのフィードバックから繰り返しません。ウォッチしていないものは、これまでどおり PR へのフィードバックから届きます
- セッションには `[agent-fleet:notice kind=watch` で始まる行として届きます。プルリクエストから来た文（チェックの名前、レビュアーの名前）は引用符で囲み、指示ではなくデータだと印を付けます

### CI の実行（GitHub Actions と Bitbucket Pipelines）

プルリクエストに紐づかないワークフローの実行（夜間やリリースのワークフロー、エージェントが手で起動したもの）もウォッチできます。エージェントはプルリクエストの代わりに実行かワークフローを渡し、種類には `ci.run.completed`（終わった実行すべて）か `ci.run.failed`（失敗だけ）を指定します。この 2 つの種類は GitHub でも Bitbucket でも同じなので、1 つの指定で両方に使えます。以前の名前の `github.workflow_run.completed` / `github.workflow_run.failed` も同じ意味で使えます。両方の名前を指定しても、1 つの実行は 1 回しか伝えません。実行やワークフローにプルリクエスト用の種類を指定すると断られます。

GitHub Actions:

| `ref` | 知らせるとき |
|---|---|
| 実行の URL（`https://github.com/o/r/actions/runs/123`、`/attempts/2` を付けてもよい）または `o/r:run/123` | その実行が終わったとき。すでに終わっている実行はすぐに伝えます。ウォッチがまだ続いているあいだ（エージェントが期限まで続けるよう頼んだ場合）は、実行の再実行を新しい試行として改めて伝えます。試行を指定したウォッチはその試行だけを伝え、既定のウォッチは最初の知らせで終わります |
| `o/r:cli-pin-bump.yml`、ブランチを付けるなら `o/r:cli-pin-bump.yml@main` | そのワークフローの次の実行が終わったとき。ウォッチを作ったあとに始まった実行に加えて、作る前のおよそ 10 分以内（分単位に切り下げるので最大 11 分弱前まで）に始まった実行も対象です（直前に待っていた実行から連鎖して起動した実行は、通知が届く数秒前に始まります）。この範囲内ですでに終わっている実行はすぐに知らせ、同じウォッチでは同じ完了を繰り返し知らせません（最初の確認で複数の実行が終わっていれば、新しい方を知らせます）。ただし範囲内に作り直した別のウォッチは、同じ実行をもう一度知らせます。範囲より前に始まった実行は対象になりません。ブランチを付けなければ、すべてのブランチ・イベントの実行が対象です。絞るには `@main` のように付けます。ブランチを指定できるのは `o/r:file.yml@branch` の形だけで、ワークフローの URL では指定できません。ウォッチより前からあった実行の再実行は知らせません。その実行を直接指定してください。ついさっき自分で起動した実行を追うときも、その実行を指定してください。実行が開くプルリクエストを待っているなら、ワークフローではなくそのプルリクエストをウォッチしてください |

- ワークフローはあなた自身の GitHub 接続で読みます。接続で読めないリポジトリや実行は、頼んだ時点で断ります。あとから実行が削除された場合（またはリポジトリへのアクセスを失った場合）は、待ち続けず、その旨の知らせを送ってウォッチを終えます
- 2 回の確認のあいだに多くの実行が始まっても、100 件までは全部読むので、新しい実行の陰で先に終わった実行も見逃しません。100 件を超えた分は、古いものから次の確認に回します
- 「あと」かどうかは、このワークスペースの時計ではなく、GitHub 自身の実行番号とタイムスタンプで決めます
- 知らせには、実行番号・試行・結果が入ります。ワークフローの名前と、失敗したジョブの名前・リンクは、チェック名と同じく引用符で囲んだデータとして渡します
- 読み取りは条件付きで、変わっていなければリクエストの枠を使いません。実行が待機中・実行中のあいだは短い間隔で読みます。ウォッチの数は、プルリクエストのウォッチと同じ上限に数えます

Bitbucket Pipelines も GitHub Actions と同じ形で指定し、`source` に `bitbucket` を加えます（`bitbucket.org` の実行 URL なら不要です）。

| `ref` | 知らせるとき |
|---|---|
| 実行の URL（`https://bitbucket.org/w/r/pipelines/results/123`）または `w/r:run/123` | その実行が終わったとき。すでに終わっている実行はすぐに伝えます |
| `w/r:pipelines`、カスタムパイプラインなら `w/r:pipelines/nightly`、ブランチなら `w/r:pipelines@main`、両方なら `w/r:pipelines/nightly@main` | （そのカスタムパイプライン・ブランチの）次の実行が終わったとき。ウォッチを作ったあとに始まった実行、または作る前のおよそ 10 分以内（分単位に切り下げるので最大 11 分弱前まで）に始まった実行が対象です（通知の繰り返しや複数完了の扱いも GitHub と同じ規則） |

- 停止（キャンセル）または期限切れの実行は、GitHub Actions のキャンセルと同じく失敗として扱います。知らせには実行番号と結果が入り、ブランチと失敗したステップの名前は引用符付きのデータです
- Bitbucket は 1 時間あたりのリクエスト数が少ないため、1 つのワークスペースで持てる Pipelines のウォッチは最大 5 件で、実行中はおよそ 1 分に 1 回、次の実行を待つあいだは 5 分に 1 回確認します。Bitbucket 接続に Pipelines を読む権限が必要で、足りないときはエージェントに再接続を促します
- 新しい実行かどうかは、Bitbucket 自身のビルド番号とタイムスタンプで決めます。ブランチを探すのはリポジトリの直近 250 件の実行までなので、実行がめったにないブランチは、ほかのブランチの実行が非常に多いと見逃すことがあります

### GitHub のリリースとタグ

上流のリリース（修正済みの依存、新しい CLI のバージョン）を待つセッションは、手で見に行く代わりにリポジトリをウォッチできます。種類は `github.release.published`（新しいリリース）と `github.tag.created`（新しいタグ。リリースを作らずにタグだけ打つプロジェクト向け）で、`github.release.*` や `github.tag.*` も使えます。プルリクエストや CI の種類は断られます。

| `ref` | 知らせるとき |
|---|---|
| `o/r:releases`、または URL `https://github.com/o/r/releases` | リリースが公開されたとき。下書きは数えません（あとで公開された下書きは数えます）。プレリリースも飛ばします |
| `o/r:releases+pre` | 同じで、プレリリースも数えます |
| `o/r:releases@v2.*` | 同じで、タグがパターンに合うリリースだけ（プレリリースも数えるなら `@` の前に `+pre`） |
| `o/r:tags`、`o/r:tags@v2.*` | タグが作られたとき（パターンがあれば合うものだけ）。タグにプレリリースはないので `+pre` は断られます |

- **ウォッチを作ったあと**に公開されたリリース、作られたタグだけが対象で、すでにあるものは知らせません。基準はウォッチを作ったときの GitHub 自身の応答から決め、このワークスペースの時計は使いません
- パターンはタグ名に対する簡単なグロブです。使えるのは英数字と `. _ - / + `、そして任意の長さを表す `*` と 1 文字を表す `?` で、64 文字までです。それ以外（空白、角括弧、ASCII 以外）はエージェントが頼んだ時点で断られます。この文字の範囲に収まらないタグ名は、ウォッチに一致しません
- GitHub はタグを時刻順に返さないため、ウォッチを作ったときになかった名前で、まだ伝えていないものを新しいタグとみなします。並びが変わっても知らせません。タグが削除されて同じ名前で作り直された場合は、2 回の確認で続けて見当たらなかったあとに現れたときに、作られたものとして数えます。作り直されたタグはもう一度伝えますが、それ以外で同じタグを 2 度伝えることはありません。伝えたリリースは、あとで新しいリリースが下書きに戻されても、繰り返しません
- タグのウォッチは一覧全体を読む必要があるため、タグが 300 を超えるリポジトリは、頼んだ時点で断られます（代わりにリリースをウォッチしてください）。あとからウォッチが追える範囲（2000 名）を超えたときも、推測せず、その旨の知らせで終わります。2 回の確認のあいだに複数のタグができたときは、名前が最大のものを 1 つ知らせ、ほかはデータとして並べます
- 知らせにはリポジトリとタグが入ります。リリースの名前と説明文は引用されたデータです。バージョンはリリースの id（リリース）かタグ名です
- GitHub の接続で読めないリポジトリ（アクセスのないプライベートなもの）は、頼んだ時点で断られます。あとでリポジトリが削除された、またはアクセスを失ったときは、その旨の知らせでウォッチが終わります
- 読み取りはあなた自身の GitHub 接続で、条件付き（変化がなければリクエスト枠を使わない）に約 5 分おきに行い、プルリクエストのウォッチと同じ上限に数えます。公開リポジトリに追加の権限は要りません

### 親に知らせを届ける

ほかのセッションが起動した子セッションは、知らせを親に届けるよう頼めます（`notify: parent`）。作業を配っている親のセッションが、子のプルリクエストの知らせを受け取れます。

- ウォッチは親のものになります。親が一覧して終わらせ、子ではなく親がアーカイブされたときに終わります
- 知らせには、どの子のためのものかが書かれます

### タイマー

エージェントはタイマーも設定できます（`watch` の `source: time`）。「20 分後に知らせて」「15:00 JST に知らせて」のような使い方です。時刻は UTC で保持します。エージェントは、オフセット付きの時刻（`2026-11-09T15:00:00+09:00`）か、待ち時間（`in 20m`、`3d`）のどちらかを渡します。指定できるのは最長 30 日先までです。

- **ワークスペースが動いている間**は、タイマーはワークスペース内で発火し、プルリクエストの場合と同じ方法でセッションに伝えます
- **`wake`** を付けると、その時刻にワークスペースが止まっていれば Control Plane に起動してもらい、そのうえで伝えます。起動するだけで、プロンプトは送りません。起動後は、ふだんどおり再び止まることもあります。Control Plane のスケジューラ（定時実行の機能）が動いている必要があります。動いていない環境では、受け付けたまま発火しない状態にはせず、エージェントの依頼を断ります
- **`wake` なし**で、ワークスペースが止まっている間に時刻になったタイマーは、次の起動のときに遅れた知らせだと印を付けて伝えます。それまでにウォッチの期限が切れていれば捨てます（タイマーは、指定した時刻の 1 日後まで残ります）
- `wake` のために作る予約は、「定時実行」の一覧には出ず、そこから編集もできません。タイマーが発火したとき、エージェントがウォッチを終えたとき、ウォッチを持つセッションが終わったときに消えます
- `list_watches` には、各タイマーの時刻と、`wake` の有無が出ます

### ほかのセッションを待つ

エージェントは、タイマーを保険に置く代わりに、ワークスペースのほかのセッションを待てます（`watch` の `source: fleet`）。`ref` はセッション名で、`list_child_sessions`（自分の子）か `list_peer_sessions`（それ以外のセッション。セッション間メッセージが有効なとき）に出る名前を使います。自分自身はウォッチできず、それらの一覧で見えない名前は断られます。

| 種類 | 知らせが出るとき |
|---|---|
| `fleet.session.idle` | セッションがターンを終えて、入力を待っているとき。ターンの終わり 1 回につき知らせ 1 件で、ワークスペースを再起動しても繰り返しません |
| `fleet.session.stopped` | セッションが停止したとき（すでに止まっていればすぐ。あとでもう一度止まれば、また伝えます） |
| `fleet.quota.reopened` | セッションが止められていた利用上限が明けたとき |

- **idle の意味はセッション一覧と同じです。** 質問・プラン・許可の返事を待っているセッションは idle ではありません
- **ウォッチを作る前に終わったターンは数えません。** ウォッチを作った時点で idle のセッションは、次のターンの終わりに伝えます。そのため親は、子へのメッセージとウォッチをどちらの順で行っても、メッセージより前のターンを知らされません。もうターンを実行しない子には知らせは出ないので、その状態は `list_child_sessions` で読みます
- **agy・copilot・cursor・kiro では確実とは限りません。** これらにはターン終了のフックがなく、終了はエージェント自身の状態をポーリングして読みます。新しいメッセージの直後は、状態がまだ前のターンの idle を示すことがあります。ワークスペースはターン開始から 10 秒以内の idle は無視しますが、それより長く続くものは新しいターンの終わりと取り違えられ、早すぎる知らせになったり、本当の終わりを取り逃がしたりします。知らせが、終わってからポーリング 1 回分遅れて届くこともあります。エージェントは、知らせを受けたら動く前にセッションの状態を確かめてください。
- **報告と知らせは別です。** `fleet.session.idle` は、子が報告を返したかどうかにかかわらず出ます。この種類は、報告を返さずにターンを終えた子に気づくためのものです。報告がすでに届いた親は、`unwatch` でウォッチを終えます
- 削除されたセッションは、知らせとともにウォッチを終えます。知らせに書くのはセッション名と状態だけで、セッションが書いたものは入りません

### ウォッチを見る・終える

ウォッチの知らせを待っているセッションは、何もしていないように見えます。そこでセッションのチャット画面では、メッセージ欄のすぐ上、バックグラウンドコマンドのパネルの隣に、動いているウォッチを一覧します。

- 各行には、何をウォッチしているか（プルリクエスト、タイマー、CI の実行、拡張機能の独自の取得元）と、待っている出来事（「CI 完了」「マージ済み」など）が出ます。タイマーには残り時間も出ます
- エラー付きの警告マークは、取得元がいま応答していないことを表します。ウォッチは残り、また読みに行きます
- 行がリンクになるのは、アドレスが github.com か bitbucket.org のときだけです。それ以外は文字で表示します


- 「**ウォッチを終了**」は、確認してから、そのウォッチを終えます。エージェントの `unwatch` と同じです。すでに終わっていた場合は、行が消えるだけです。閲覧だけできる人には、行は見えてもボタンは出ません
- 子が親に届けるよう頼んだウォッチ（`notify: parent`）は、親のチャット画面に、子の名前付きで出ます
- ウォッチがないセッションでは、パネルは出ません

### ウォッチの上限

| 決まり | 値 |
|---|---|
| ウォッチが終わるとき | 最初の知らせで終わる（エージェントが続けるよう頼んだときを除く）。どの場合も 7 日（最長 30 日）か、オーナーのセッションがアーカイブされたとき |
| 1 つのセッションが持てる数 | 20。親に届けるウォッチは、親の 20 と、子が自分で持つウォッチと合わせた子の 20 の両方に数える（どの子が作ったかは `list_watches` に出る） |
| ワークスペース全体 | 200 |
| `wake` 付きのタイマー | 未実行の起動予約は、メンバーごとに 250 まで（そのメンバーの全ワークスペースで共有） |
| Bitbucket のウォッチ | ワークスペースで 10 まで。約 5 分ごとに読む（Bitbucket の 1 時間あたりのリクエスト上限に収めるため） |
| Bitbucket Pipelines のウォッチ | ワークスペースで 5 まで。上の PR のウォッチとは別に数える |

- Bitbucket では、未解決のレビュースレッドの増加はウォッチできません。どのスレッドが解決済みかを Bitbucket が返さないためです
- Bitbucket でマージできる状態とみなすのは、誰かが承認していて、変更を求める人がいないときです
- ウォッチは Agent を再起動しても残ります

### Webhook で早く知る

ウォッチは常に、あなた自身の接続によるポーリングで読みます。管理者が Webhook を追加すると、Control Plane が次の周期を待たずに「このプルリクエストを今読んで」とワークスペースに伝えます。
Webhook がワークスペースに運ぶのは「このプルリクエストが変わった」という合図だけです。データは渡さず、停止中のワークスペースを起動することもありません（停止中のワークスペースは、起動したときに追いつきます）。

- **公開リポジトリ**: 配備の GitHub App に Webhook が設定されていれば（配備を運用する側の設定です。[設定リファレンス](../../ref/settings.ja.md)）、公開リポジトリの配信でウォッチが早くなります。
- **プライベートリポジトリ**: 配備共通の App は全テナントで共有しているので、プライベートリポジトリの配信は無視します。プライベートリポジトリには、あなたのテナントの Webhook（リポジトリのフック、またはテナント自身の GitHub App。Bitbucket は常にこれ）が必要です。なければウォッチはポーリングのままです（数分以内の遅れ）。ワークスペースからは [`af-watch-hook`](../../ref/cli/af-watch-hook.ja.md) で作れます。

#### プライベートリポジトリにフックを追加する

```sh
af-watch-hook add github owner/name      # Bitbucket は: af-watch-hook add bitbucket workspace/name
af-watch-hook list
af-watch-hook rm <id>
```

`add` は Control Plane にフックを作り、あなた自身の接続（設定 > 接続）でリポジトリに登録します。以後は、プルリクエスト・レビュー・コメント・チェックの出来事があるたびに、ワークスペースのウォッチに合図が届きます。フックの秘密は GitHub / Bitbucket にそのまま渡し、表示も保存もしません。`rm` はリポジトリ側と Agent Fleet 側の両方から消します。

- **リポジトリの管理者権限が要ります。** GitHub では `repo`（または `admin:repo_hook`）スコープの classic トークンか、Webhooks: Read and write の fine-grained トークンが必要です。Bitbucket では Webhooks スコープとリポジトリ管理者の権限が必要です。足りなければ `add` がそう伝え、何も残しません。リポジトリの管理者に頼むか、ポーリングのままにしてください
- **配備に公開 URL が要ります。** なければ外部のサービスがフックに届きません
- **すでにフックのあるリポジトリに `add` しても何も変わりません。** やり直すには `rm` してから `add` します
- **自分の GitHub App**: App の設定に貼る Webhook のシークレットは、一度あなたに表示する必要があります。`af-watch-hook` はシークレットを表示しないので、まだこの形には対応していません。それまでは、App が要らない `af-watch-hook add` を使ってください
- GitHub Enterprise Server と Bitbucket Data Center は対象外です
