# 01. メンバー管理

[English](01-members.md) | 日本語

メンバーの管理は、テナント設定の左レール **「運用 → メンバー」** で行います。ここは
「名簿 → メンバー詳細」の 2 段の掘り下げ（ドリルダウン）です。上の段へ戻るには「戻る」ボタン、
または画面上部のパンくず（メンバー › 対象の人）をたどります。

## 画面をたどる

**テナントの数字** — レールの **「テナント → 上限・自動停止」** に、このテナントの表示名、
メンバー数（「◯ 人」）、いま起動中のワークスペース数（「◯ 起動中」）、テナント全体の上限
（「上限 — ワークスペース: X / セッション: Y」）が出ます。**読むだけの面**です（上限を決めるのは
super_admin・[02-limits.md](02-limits.ja.md) を参照）。

**名簿** — 各メンバーの行には、稼働状態を示す点、内部識別子（`user_key`）、メールアドレス、
ロール（`member` / `tenant_admin`）が並びます。行をクリックするとメンバー詳細へ進みます。

**メンバー詳細** — そのメンバーのワークスペース資源、稼働セッション、各種操作が集まる画面です。
資源とセッション、強制停止・上限設定は [02-limits.md](02-limits.ja.md) で扱います。

## メンバーを追加する

名簿のいちばん下に **「メンバー追加」** のフォームがあります。

1. 「email」欄にそのメンバーがサインインに使うメールアドレスを入れます。または「内部識別子（user_key）」欄に
   キーを直接入れても構いません（メールを入れれば、そこから自動でキーが作られます）。
2. tenant_admin のあなたが追加できるのは **`member`（一般メンバー）だけ** です。ロールを選ぶ欄は
   super_admin にしか表示されません。誰かを管理者にしたい場合は後述のとおり super_admin に依頼します。
3. 「追加」を押すと、そのメンバーがこのテナントに加わります。まだ一度もログインしていない相手でも
   先に追加できます（招待の先出し）。相手が初回ログインしたときに、この所属をもとにワークスペースが
   払い出されます。

追加された本人には、このガイドの [member/](../member/README.ja.md) を案内してあげてください。

### メールアドレスと内部識別子の関係

メンバーは内部的に **user_key**（メールから作られる短い識別子）で識別されます。メンバー行やセッション一覧に
出るモノスペースの文字列がそれです。ふだんはメールアドレスを入れれば自動でキーが決まるので意識する必要は
ありませんが、監査ログやセッション俯瞰では内部識別子が主役になるので、「この識別子＝この人」の対応を
つかんでおくと読みやすくなります。同じ人でもテナントが違えば所属（とワークスペース）は完全に別扱いです。

## 自動加入と招待制

新しい人がこのテナントに入る道は、デプロイの設定で 2 通りあります。

- **招待制（`AF_PROVISION=invite`・新規インストールの既定）** — 管理者が「メンバー追加」で登録した人だけが
  入れます。登録の無い人はサインインまでは通り、**「まだ招待されていません」の画面**に着地します。
  その画面には本人のサインイン済みアドレスが出るので、追加を頼まれたらそのアドレスをそのまま
  使ってください（表示名やいつものアドレスとは限りません）。
- **自動加入（`AF_PROVISION=auto`）** — ログインが許可されているメールアドレスなら、初回ログインで
  自動的に既定テナントのメンバーになります。あなたが一人ずつ追加する必要はありません。

**どちらのモードかを切り替えるのは、あなたの権限の外です。** これはデプロイ全体の環境設定なので、
変更したいときは情シス／デプロイ管理者に依頼してください（[operator/README.md](../operate/README.ja.md)）。
招待制であっても、追加操作そのものはこのページの「メンバーを追加する」で行えます。

なお、そもそもログインできる範囲（許可されたメールドメイン／アドレス）を決めるのも情シスの領分です。
許可されていない相手はテナントに追加しても本人がログインできません。

## メンバーを外すには

退職・異動の一式は **あなたの権限で完結します**。誰が抜けたかを知っているのは部署なので、
手続きの半分だけを情シスへのチケットにしない、という考え方です。メンバー詳細の「操作」欄から、
この順に打ってください。

1. **メンバーを外す** — 名簿から外し、アクセスを止めます。**これを最初にやります**（署名済みの
   セッション Cookie は個別に失効させられないため、次のリクエストから効くこの操作が実際の遮断です）。
   ワークスペース・home・保存済みの認証情報は残るので、間違えたら同じメールアドレスでもう一度
   追加すれば戻せます。
2. **ワークスペースを強制停止** — 動いているものを止めます（[02-limits.md](02-limits.ja.md)）。
3. **home を掃除** — home の中身を消します。**戻せません。**

外した人も名簿には「外れています（名簿から削除済み）」として残ります。2 と 3 をあとから打てる
ようにするためで、消えたわけではありません。

**行そのものを消す。** 外した人の Workspace を破棄し終えると、同じ「操作」欄に
**「メンバーを完全に削除」**が出ます。出るのは Workspace が無くなってからだけです——残っている
うちに行を消すと、home とクラウド資源を指すものが無くなるためで、サーバも同じ理由で拒否します。

- **消えるもの**: 上限設定・アクセストークン・SSM の設定・定時実行・メモ・通知・セッション共有。
- **残るもの**: 監査ログ・クラウド費用・稼働時間。退職処理がその記録自体を消せてはいけませんし、
  過去月の費用合計が後から変わってもいけません。

取り消せません。同じ人をもう一度招待すると、まっさらな新しいメンバーとして始まります。

## ロールの意味

Agent Fleet には 3 つのロールがあります。あなた（tenant_admin）に関係するのは主に下の 2 つです。

- **member（一般メンバー）** — 自分のワークスペースでコードを書き、セッションを動かす人。テナント設定には入れません。
- **tenant_admin（テナント管理者）** — このテナント内のメンバー管理・資源閲覧・ワークスペース強制停止・
  セッション上限設定、メンバーを外すこと、home の掃除ができます。**他テナントには一切関与できません。**
  テナントの新規作成、テナント全体の上限変更、管理者権限の付与、ログイン規則の変更はできません。＝あなたです。
- **super_admin** — デプロイ全体の管理者。すべてのテナントを見て、テナントの作成、上限設定、そして
  「誰かを tenant_admin にする」といった権限付与を行えます。super_admin は環境設定
  （`SUPER_ADMIN_EMAILS`）で決まり、名簿では星印で示されます。

**誰かを tenant_admin に昇格させたい**ときは、あなたにはできません。super_admin だけが、メンバー詳細の
「権限」欄からロールを付与できます。付与された管理者もそのテナント内だけの権限で、他テナントには影響しません。
権限モデルの厳密な定義とテーブル構造は、開発者向けの資料にあります。
