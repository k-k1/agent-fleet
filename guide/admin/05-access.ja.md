# 05. 誰が、どこからサインインできるか

[English](05-access.md) | 日本語

誰がどうやってテナントに到達するかは、4 つの画面で決まります。2 つはあなたが変えられ、
1 つは読み取り専用、1 つは**あなたが登録して、承認は別の人**です。

| 画面 | あなたのもの？ |
|---|---|
| **サインイン方式** | 登録・編集はあなた。**承認は配備管理者** |
| **サインイン規則** | 読み取り専用 |
| **接続元の制限** | あなたのもの |
| **連携アプリの OAuth** | あなたのもの |

最後の節の開発用ログインは、この 4 つには入りません。配備全体のスイッチで、super_admin にしか見えません。

## 接続元の制限

既定では、配備そのものに届く場所からならどこからでもテナントに到達できます。
**接続元ネットワーク**は、それをあなたが書いた一覧に絞ります。CIDR か単独アドレスを
カンマ区切りで書き、IPv4 でも IPv6 でも使えます。**空なら制限なし**です。

画面には**この配備から見えているあなたのアドレス**が出ます。規則が照合されるのは
この値で、**ブラウザ自身が認識しているアドレスではありません**。保存する前に必ず
見比べてください。要求の送信元を配備側が特定できない場合は画面がそう言い、規則は
適用できません。これは配備側の設定（信頼するプロキシの段数）なので、範囲を当てずっぽうで
書かず、**配備管理者に確認してください**。

> **締め出したら、ここからは直せません。** いま自分が接続している範囲を、**保存する前に**
> 追加し、画面のアドレスと突き合わせてください。書き損じからの復旧には配備管理者が要ります。

ほかに 2 点あります。

- 制限がかかるのは**認証の後**で、認証の代わりではありません。有効なセッションを持つ人を
  絞るだけで、サインインの代替にはなりません。
- 効くのはあなたのテナントです。他テナントにも属している人は、そちらへはそちらの規則で
  到達します。

## MCP OAuth

**テナント設定 → 接続元の制限** の **MCP OAuth** 欄で、外部アプリが OAuth でこのテナントに接続できるかを設定します。配備が MCP OAuth を提供している場合だけ表示されます。テナントの設定は既定で有効で、テナント管理者または配備管理者が変更できます。

**MCP OAuth によるアプリの接続を許可する**を外し、**保存**して確認します。そのテナントの既存の OAuth 接続はすぐに取り消され、監査に記録されます。同意画面のテナント選択肢から除かれ、コード交換・トークン更新は拒否され、OAuth アクセストークンも `/mcp` で使えなくなります。他のテナントと Personal Access Token には影響しません。

再度有効にしても、取り消した接続は復元されません。メンバーがアプリから接続し直します。個別の接続は **設定 → 接続 → MCP トークン → 接続済みアプリ** の **失効** ボタンからも取り消せます。

### 信頼するクライアントのホスト（配備全体 — super_admin のみ）

**管理 → 配備 → MCP ログイン許可ホスト** で、この配備の MCP OAuth サーバーが信頼するクライアントのホスト（サインイン後のリダイレクトを受け取れるホスト、およびクライアントメタデータを配信できるホスト）を編集します。テナントごとではなく配備全体の設定で、super administrator だけに表示されます。ループバックのクライアント（メンバー自身のマシン上の CLI など）は常に許可されます。

- **別の Agent Fleet 環境からこの環境の `/mcp` にサインインさせたいときは、そのホストをここに追加します**（ホスト名のみ。例: `af.example.com`）。
- **ベンダーを外すこともできます**: `chatgpt.com` を消して保存すれば、そのベンダーはサインインできなくなります。空の一覧を保存すると、ホスト経由のクライアントは一切信頼しません。
- 入力はホスト名の完全一致です。`https://`・ポート・パス・ワイルドカード・IP アドレスは使えません。誤りがあるとメッセージとともに拒否され、何も保存されません。
- **どの一覧が適用されるか**: ここで保存した一覧が最優先で、保存がなければ環境変数 `AF_MCP_OAUTH_TRUSTED_HOSTS`、それも未設定なら組み込みの既定値（`claude.ai`・`claude.com`・`chatgpt.com`）です。どれが適用中かは画面に表示されます。**既定に戻す**は保存した一覧を削除し、残りの 2 つが再び適用されます。
- 変更は次のリクエストから、再起動なしで、新しいサインイン・クライアント登録・トークン要求に反映されます。リダイレクト先のホスト（メタデータ URL のクライアントではそのクライアント自身のホスト）を外すと、その接続はトークン更新も未使用コードの交換もできなくなります。発行済みのアクセストークンは期限（最長 1 時間）まで使えます。ループバックの接続は影響を受けません。変更はすべて監査されます（`mcp_oauth.trusted_hosts.set` / `.reset`。変更前後の一覧を含みます）。

## 連携アプリの OAuth

メンバーは**未登録でも**トークンを貼り付けて GitHub / Bitbucket に接続できます。
テナント**自身の** OAuth アプリを登録すると、便利な経路が増えます。
そのプロバイダに「**OAuth で接続**」が出るようになり、誰も手でトークンを作らずに済みます。

### GitHub: 使うアプリを選ぶ

GitHub の欄は空から始まりません。ボタンがどのアプリを使うかを選びます。

| 選択肢 | メンバーがすること | 向いている場合 |
|---|---|---|
| **組み込みの OAuth App** | 認可 1 回。トークンはメンバーがアクセスできる全リポジトリに届きます（scope は `repo` と `workflow`）。 | 個人・小規模。配備の最初のテナントでは**既定**なので、個人の環境では最初からボタンが出ます。 |
| **組み込みの GitHub App** | 自分のアカウントや organization にアプリをインストールし、リポジトリを選んでから認可。 | リポジトリ単位で狭く付与したいチーム。organization では owner しかインストールできません。 |
| **自前のアプリ** | 自社で登録した OAuth App / GitHub App のとおり。 | 自社のアプリを持ちたい組織。 |
| **使わない** | ボタンなし。トークンを貼り付けて接続。 | |

組み込みアプリは登録不要で、メンバーのトークンを見ることもできません。GitHub が使う
device flow には secret が無く、トークンはメンバー自身のワークスペースにだけ入ります。運用者は
配備全体から組み込みアプリを外せます（`AF_GITHUB_BUILTIN_APPS=off`）。そのときは欄にそう
表示されます。

**自前のアプリ**では client_id を貼ります。OAuth App か GitHub App かは**保存時に GitHub に
問い合わせて判別**し、欄に表示します。GitHub に届かないときは推定を表示し、最初のメンバーの
接続で確定します。GitHub 側で設定するものは 2 つです。

- **Enable Device Flow** にチェックが必要です。無いと保存時に断られます。
- GitHub App では **Expire user authorization tokens** をオンのままにできます。af がこの
  トークンを自分で更新し、クライアントシークレットは保存しません。認可が取り消された、または refresh token が
  約 6 か月使われないまま期限切れになったメンバーには、接続画面に「再接続が必要」と出るので、接続し直してもらいます。
  アプリのページ（`https://github.com/apps/<名前>`）をインストールページに入力します。GitHub App はインストールされたリポジトリにしか届きません。
  メンバーはそこへ案内され、どこにもインストールされていなければ接続後に警告が出ます。

**既定に戻す**で選択を消せます。

### Bitbucket と Jira

登録の手順:

1. プロバイダ側で、自分の組織に OAuth アプリを作ります（登録先は画面に出ます）。
2. 画面に出ている**コールバック URL** をそのアプリに設定します。**完全一致が必要**で、
   ずれていると承認時に、プロバイダの分かりにくい文言のエラーで返ってきます。
3. **client_id** と **client_secret** をここに貼ります。Bitbucket は同じものを
   Key / Secret と呼びます。

> **Jira は Sharing の有効化も要ります。** Atlassian の 3LO アプリは、**Distribution** で
> Sharing を有効にするまで「開発中」で、**作った本人しか認可できません**。自分で試すと
> 通ってしまい、他のメンバー全員が Atlassian の *"You don't have access to this app"* で
> 止まります。この画面は認可画面より手前なので **af には何も返ってこず**、エラーはどこにも
> 出ないまま接続されないだけになります。有効化には **Vendor name**・**Contact link**・
> **Privacy policy URL** の入力が要り、これらは認可するメンバーに見えます。個人名や私用の
> アドレスではなく、会社名と問い合わせ窓口を入れてください。Atlassian Marketplace には
> 載りません。なお、メンバーには「このアプリは Atlassian の審査を受けていない」旨の注意も
> 出ますが、自分で登録したアプリならそれが正常です。

> **Jira のボード・スプリント・エピックにはスコープの追加が要ります。** メンバーのセッションの
> Jira CLI は、ボード・スプリント・エピックを Jira Software 経由で扱います。Jira Software は
> 上のスコープを一切受け付けません。Developer Console でアプリの **Permissions → Jira API →
> Configure → Granular scopes → Edit Scopes** を開き、次の 8 つを選んでください。同じアプリの
> クラシックスコープと並べて持てるので、そちらはそのまま残します。
>
> | 画面での名前 | コード |
> |---|---|
> | View boards, backlogs, and related items | `read:board-scope:jira-software` |
> | View sprints | `read:sprint:jira-software` |
> | Update and delete sprints | `write:sprint:jira-software` |
> | View epics and related issues | `read:epic:jira-software` |
> | Update epics | `write:epic:jira-software` |
> | View projects | `read:project:jira` |
> | View issue details | `read:issue-details:jira` |
> | View JQL | `read:jql:jira` |
>
> コードの列で確かめてください。*View board configuration*（`read:board-scope.admin:jira-software`）は
> 1 行目と似ていますが別のスコープで、af は求めません。**そのあとで** Jira のカードの
> 「このアプリに Jira Software のスコープ（ボード・スプリント・エピック）も許可済み」に
> チェックを入れて保存します。順番が大事です。アプリにないスコープを求める認可は Atlassian に
> 拒否されるので、先にチェックを入れると全メンバーが接続できなくなります（実測: この拒否は
> Atlassian 側の行き止まりのページで af に戻るリダイレクトがないため、af が基本のスコープに
> 切り替えることはできません）。Jira カードに「ボード・スプリント・エピック: 利用できません」と
> 出ているメンバーは、これらのスコープなしで接続しています。接続済みのメンバーは、
> Jira を接続し直すと新しいスコープを受け取れます。

secret は**保存時に暗号化され、二度と表示されません**。後で登録を編集するとき、
secret を空のままにすれば保存済みのものが保たれます——**変更するときだけ**入力してください。
**登録を削除**すると OAuth ボタンが消えます。トークンで接続済みのメンバーには影響しません。

これはプロバイダごと・テナントごとの設定です。メンバーがそのプロバイダで**何をできるかは
広がりません**。できることは、アプリのスコープと、各メンバーのそちらでの権限が決めます。

## サインイン方式とサインイン規則

**サインイン方式**は、自社の IdP や GitHub 組織をこのテナントへの入口として登録する
画面です。登録だけでは足りず、**配備管理者が承認**します。後からの変更（組織の追加、
同一アカウントの認識方法の変更）は、その行を**再び承認待ちへ戻します**。

**サインイン規則**は、効いている参加方式とドメインの表示です。あなたには読み取り専用です。
**「なぜ招待が弾かれたのか」を誰にも訊かずに読める**ようにするための画面です。

どちらの画面にも、気づくより先に踏んでしまう角があります。詳細は配備管理者側の
サインインの章（[operate/](../operate/README.ja.md)）にありますが、重要な点は次のとおりです。

- **受け入れる方式を絞ると、他テナントにも属している人を締め出せます。**
  同じアドレスでも IdP が違えば**別のサインイン**です。その方式は「受け入れる」のまま残し、
  **ボタンの表示だけ**を止めてください。
- **ボタンを消しても方式は受け入れられたまま**です。既にそれで入っている人はそのまま入れ、
  サインイン画面に出なくなるだけです。**全部の方式で消すことはできません**。ボタンの無い
  サインイン画面は行き止まりなので、その設定は無視されます。
- 両方のアカウントを持っている人は、自分の個人設定から 2 つ目の方式を自分のアカウントへ
  紐づけられます。**あなたのやることはありません。**

## 開発用ログイン（開発用 OIDC IdP — super_admin のみ）

Admin モーダルの**開発用ログイン**で、Control Plane の開発用 OIDC IdP（ADR 0116）を配備全体でオン・オフします。
**既定はオン**で、super_admin だけの設定なので、テナント設定には出ません。ワークスペースごとのスイッチはなく、
オン（かつプレビュー用サブドメインがある）の間はすべてのワークスペースのクライアントが対象です。

- 画面には issuer、クライアントを持つワークスペース数（IdP が提供されている間にワークスペースが起動すると作られ、
  その後も残ります）、そして肝心の一点が出ます。**本番のアプリはこの issuer を
  絶対に信頼しないでください**。パスワードなしで任意のメンバーとしてサインインできてしまうからです。
- オフにすると再起動なしで反映され（別の Control Plane レプリカも数秒で追随）、`/dev-idp/…` は全部 404 になります。
  **ワークスペースのクライアント登録は残る**ので、オンに戻せば同じ client id と secret が戻ります。
- **メンバーが使えるのはプレビュー用サブドメインがある環境だけ**です。プレビュー用ドメイン（`AF_PREVIEW_DOMAIN`）が
  無いと、この画面にその旨が出て、`/dev-idp/…` は 404、ワークスペースには何も渡されず、ワークスペースからは利用不可と
  見えます。スイッチ自体は操作できます。
- 運用者が `AF_DEV_IDP=0` を設定していると固定表示になり、`PUBLIC_BASE_URL` が無いとオンにできません。どちらに
  当たるかは画面に出ます。変更は毎回監査されます（`dev_idp.set`）。
