# 04. MCP の配布と外部通信の統制

[English](04-mcp-egress.md) | 日本語

チーム共通のツールを配るのはあなたの権限で完結し、外部通信の統制は
情シス／デプロイ管理者の担当です。

## MCP サーバーをテナント全員に配る（あなたの権限）

テナント設定の **「運用 → MCP 配布」** で、テナントの全メンバーへ MCP サーバーを配布できます。
配布したサーバーは、各メンバーの ⚙設定 →「MCP サーバー」に **「テナント」** の出自ラベル付きで
並び、そのままアシスタントやセッションから使えます（メンバー側の見え方は
[member/12 設定](../member/12-settings.ja.md#mcp-サーバー)）。

### 配れるのはリモート（HTTP）だけ

**stdio（ワークスペース内でコマンドを起動する方式）は配布できません。** 配布は
「管理者が全メンバーのコンテナで任意のコマンドを実行できる」ことと等価になるためです。
配布できるのは **Streamable HTTP のエンドポイント**だけで、指定するのは URL とヘッダです。
stdio が必要なメンバーは、自分の設定に個人登録してもらってください。

### 資格情報の扱いを決める（重要）

追加フォームの **「資格情報の扱い」** で 2 通りから選びます。ここが配布の設計上いちばん重要な
判断です。

| 選択 | 何が配られるか | 向いている場面 |
|---|---|---|
| 値も配布する | ヘッダの値ごと配布（暗号化して保存され、サーバー起動時にだけ渡されます） | 共有の read-only トークンなど、全員が同じ資格で読むもの |
| **「認証の値は各メンバーが入力する」** | **接続先とヘッダ名だけ**。値は各メンバーが自分のワークスペースで入力 | 個人ごとのトークン、監査で個人を識別したいもの |

**値を配ると、そのトークンは全メンバーのコンテナ内で読める状態になります。** 個人を識別したい
場合や、権限の強いトークンは「各メンバーが入力する」を選んでください。この形で配ると、
メンバー側のカードには **「値を入力」** の導線が出ます（入力が済むまでそのサーバーは使われません）。

### 反映されるまで

- 各メンバーのワークスペースは、配布内容を **5 分ごとに取得**します。
- 実際に効くのは、**その後に起動したセッションから**です。すでに動いているセッションは変わりません。
- **無効**にすると、定義は残したまま誰にも配られなくなります。**削除**すると、各ワークスペースからは
  次回の取得時に消えます。
- 配布と**同じ名前の個人登録**があるメンバーには、配布のほうが使われます（メンバー側にその旨が
  表示されます）。名前は衝突しにくいものにしてください。

### 運用の勘所

- まず**自分のワークスペースで個人登録して接続テスト**し、動く構成を確認してから配布に移すと確実です。
- 配布したトークンを失効させるときは、**先に配布側の値を差し替えて**から旧トークンを無効化します
  （順序を逆にすると、次の取得までメンバー全員のツールが失敗します）。
- 外向き通信が制限されたデプロイでは、配布しても**接続先ホストが許可されていないと動きません**。
  次節の許可リストに入っているかを先に確認してください。

## 読み上げ（テナント共通の設定）

読み上げの設定は super_admin 専用（管理モーダルの「読み上げ」）で、VOICEVOX（ずんだもん）エンジンの
起動・停止と、**テナント共通の読み仮名辞書**を扱います。共通辞書は全メンバーの読み上げに
適用され、各メンバーの個人辞書が同じ表記を上書きします。製品名や社内用語の読み間違いが
気になるときは、共通辞書への追加を super_admin に依頼してください。

## 推論エンジン（自前の GPU・super_admin 専用）

配備が**自前の推論エンジン**（会話用の `llamacpp`、画像用の `sdcpp`）を動かしている場合だけ、
管理モーダルに「推論エンジン」が出ます。動かしていない配備には項目そのものが現れません。

役ごとに 3 つのうち 1 つを選びます。

| | 何が起きるか |
|---|---|
| **無効** | そのエンジンは起動メニューからも `generate_image` からも消え、要求は 503 で断られます。インスタンスはすぐ止まります。 |
| **オンデマンド** | 要求が来たときだけ GPU のインスタンスを買い、しばらく誰も使わなければ自分で止まります。**既定はこれです。** |
| **常時稼働** | インスタンスを止めません。応答は速くなりますが、**使っていない間も課金され続けます**。 |

「状態」は選んだモードではなく、**いま実際に何が動いているか**です。「無効」を押した直後は
モードが無効・状態が「停止処理中」になります——押した瞬間にインスタンスが消えるわけではないからで、
これは食い違いではありません。

⚠️ **初回の要求は待たされます。** 止まっているエンジンへの最初の要求は、インスタンスを買って
モデルを読み込む 3 分前後を待ってから答えが返ります（呼び出し自体は 1 回で完結し、
やり直しは要りません）。急いでいる作業の前に、あらかじめ「常時稼働」で暖めておく手もあります
——**戻すのを忘れないでください。**

### GPU のインスタンスクラス

配備が**インスタンスクラス**を宣言している場合だけ、モードの下に選択欄が出ます。宣言して
いない配備には**欄そのものが出ません**（インスタンスは配備時に決めたもので固定です）。

VRAM を多く使うモデルを試したいときに、**より大きい GPU のインスタンスへ一時的に上げる**ためのものです。

- **選んでも、いま動いているインスタンスは変わりません。** 効くのは**次に買うインスタンス**からです。動いている
  ときは「いま動いているのは g6.xlarge のインスタンスです」と出て、隣に**「いま入れ替える」**が並びます。
- **入れ替えはコールドスタート 1 回ぶんかかります**（llm で約 9 分、image で約 3 分）。
  新しいインスタンスはモデルを取り直します。さらに、**古いインスタンスがクラスタから消えるまで新しいインスタンスは
  起動しません**——先に起こすと GPU の台数上限に当たり、*静かに配置されないまま*
  「起動が遅い」ようにしか見えないからです。
- **止まっているエンジンなら、選ぶだけで費用はかかりません。** 次に誰かが使ったときの
  起動に反映されます。
- 🔴 **既定と違うクラスのままにすると、時間単価が上がったまま戻りません。** そのときは
  「既定と違います」というバッジと**「既定に戻す」**が常に出ます。**用が済んだら戻して
  ください。**
- **買えないクラスもあります。** アカウントの GPU 台数上限を超えるクラスを選ぶと、インスタンスは
  いつまでも用意されません。そのときは「状態」の下に ECS の理由（`VcpuLimitExceeded`）が
  そのまま出ます。上限の引き上げは配備管理者に依頼してください。

### モデルが載るかどうかの警告

モデルを**有効にするとき**、そのモデルが必要とする VRAM が選択中のクラスを超えていると、
確認を求められます。**禁止ではありません**——量子化やオフロードで載ることもあるので、
承知のうえなら続けられます。VRAM が足りないと、CUDA は遅くなるのではなく**落ちます**。

必要量の出どころは 3 通りで、画面にどれなのかが書かれます。

| 表示 | 意味 |
|---|---|
| 実測 | 運用者がそのモデルで測った値です。 |
| 重みだけの下限 | ファイルの大きさから出した**下限**で、コンテキストの分は含みません。「少なくともこれだけ」という意味です。 |
| 不明 | 誰も測っていません。🔴 **「収まる」という意味ではありません。** |

### モデルの取り込みと、テナントとの関係

Hugging Face・Civitai・URL からモデルを取り込む（バケットへ落としてカタログに行を作る）操作は、
既定では **super_admin だけ**が起こせます。運用者がテナントごとに許可を出すと、そのテナントの
**tenant_admin も取り込めるようになります**（管理モーダル → テナント → 「上限・自動停止」の
**「推論エンジンのモデル取り込み」**）。

許可されるのは**取り込みを起こすことだけ**です。次の 4 つは許可の有無にかかわらず super_admin のままです。

- モデルを**有効にする**（メンバーが選べるようにする）
- image の**選択中チェックポイント**を変える
- 行を**削除する**
- デプロイの **Hugging Face トークン**を登録する

🔴 **カタログはデプロイに 1 つで、テナントごとには分かれません。取り込まれたモデルの id は
どのテナントからも見えます。** これは意図した設計です——GPU のインスタンスはテナント間で共有していて、
有効なモデルは起動のたびに全部そのインスタンスへ同期されるので、テナントごとにカタログを持たせると
**1 テナント 1 モデルでも約 5 テナントでコールドスタートが 10 分を超えます**（実測。同期は直列で
約 159 MB/s）。分けたい境界は GPU のインスタンスであって、カタログではありません。
**この許可を「テナント間の分離」として読まないでください。**

誰がどのライセンスに同意したかは行に残ります——**どのテナントの・誰が・いつ・どのライセンスに**の
4 点で、監査ログにも同じ組で残ります。super_admin が取り込んだときのテナントは空欄で、これは
「デプロイ全体に対して運用者が同意した」という意味です。

#### テナント管理者に見える範囲

許可されたテナントの tenant_admin には、**テナント設定 →「推論エンジンのモデル」**に縮小版の
画面が出ます（管理モーダルではありません——あちらは super_admin 専用です）。出るのは
**モデルの検索・取り込みのフォーム・自分のテナントが起こした取り込みの履歴・カタログの行の一覧**
（id・名前・ファミリー・ライセンス・有効/無効を**読むだけ**）の 4 つです。**モード（無効／
オンデマンド／常時稼働）・GPU のクラス・インスタンスの状態・有効化と選択・行の削除・
Hugging Face トークン**は出ません——どれも「他の全テナントが何を走らせるか」と「誰が GPU の
代金を払うか」を決めるからです。取り込みの履歴は**そのテナントが起こしたものだけ**で、
super_admin が起こしたものは出ません（逆に super_admin の画面には全部出ます）。

### いまの状況を見る

モードの下に、そのエンジンの現況が出ます。**書いていない行は「分からない」という意味**で、
0 や「予定なし」で埋めてはいないので、そのつもりで読んでください。

- **インスタンスの起動** — GPU インスタンスがクラスタに入った時刻と、そこからの経過時間、
  インスタンス ID。「サービスの更新」と出ているときはインスタンスが見つからなかったときで、
  そちらは配備の更新でも動く時刻なので、インスタンスの寿命そのものではありません。
- **自動停止** — オンデマンドで動いているときだけ出ます。**「常時稼働」では出ません**
  ——止まらないからです。「無効」や停止中も同じで、出ないことが答えです。
- **直近 N 分の要求** — その窓に届いた要求の数です。⚠️ この数は **Control Plane が
  自分のメモリで数えているだけ**なので、Control Plane が入れ替わると 0 に戻ります。
  数え始めてから窓ぶん経っていないときは「この CP が数えているのは直近 … だけです」と
  但し書きが付きます。隣の**「最後の要求」は保存されている**ので、そちらは入れ替えを跨いでも
  正しい値です。**0 件だからといって誰も使っていないとは限りません。**
- **モデル** — スタックが宣言しているモデル名です。`(読み込み済)` は、そのエンジンが実際に
  応答を返せる状態まで暖まっていることを表します（起動直後は `(宣言。まだ読み込まれて
  いません)` で、ここが 3 分前後かかる部分です）。
- **起動に失敗しているとき**は、ECS の理由がそのまま出ます（「配置できるインスタンスが無い」
  など）。AWS のコンソールを開かなくても、ここで読めます。

### 稼働実績（14 日）

「稼働実績」を開くと、**縦 24 時間 × 横 日付**のヒートマップが出ます。1 マスが 1 時間で、
色が濃いほどその時間の稼働が長かったことを表します。

- 濃さの意味は 2 つから選べます。**「応答できた時間」**は要求に答えられた時間、
  **「インスタンスがあった時間」**はそれに加えて、起動中（まだ答えられない）と後始末（タスクが消えた
  あとインスタンスが残っている）を含みます。**後ろ 2 つも課金されます**ので、請求書と
  突き合わせるときは「インスタンスがあった時間」で見てください。
- 🔴 **空白のマスは「止まっていた」ではなく「記録が無い」です。** Control Plane が
  動いていなかった時間、またはそのエンジンがまだ無かった時間で、後から埋めることはできません。
  止まっていた時間は灰色で、空白とは別の色です。
- **金額は出ません。** クラウドの実費は日単位でしか取れないため、時間別に金額を出すと
  「単価×秒数」の見積りにしかならないからです。この画面が答えるのは「いつ動いていたか」で、
  「いくらだったか」はクラウド費用の画面が答えます。

## 外部通信の統制（egress・super_admin 専用）

管理モーダルの **「通信」** です。**super_admin 専用なので、あなたのテナント設定には出ません。**
ここは情シス／デプロイ管理者の担当なので、必要になったら依頼してください
（依頼の書き方は最後の節）。以下は、依頼先で何が行われるかを知っておくための説明です。

### log-only と enforce

- **log-only** — 観測のみで遮断しません。まずこれで**実態を把握**します。
- **enforce** — 許可リストにない通信を**遮断**します。

順序が大事です。いきなり enforce にすると、エージェントの更新取得や MCP の接続先など、
必要な通信まで落ちます。**log-only で観測 → 許可リストを固める → enforce** が正しい進め方です。

### 許可リストと、メンバーからの申請

- 許可エントリは **host** か **`.suffix.example.com`** の形式で追加し、理由を添えられます。
  不要になったものは**取消**します。追加分が無い場合は製品既定の許可だけが有効です。
- メンバーが ⚙設定 →「MCP サーバー」で許可の申請をすると、ここに **「提案中（要承認）」** として
  並びます。内容を確認して **承認**（許可リストに入る）か **却下**を選びます。
  メンバー側は申請後「管理者の承認待ちです」と表示された状態で待っています。
- **観測された宛先**では、期間を区切って実際の通信先と、**許可 / 遮断 / 遮断候補**の別を確認できます。
  log-only のうちに「遮断候補」を潰しておくと、enforce へ切り替えたときに事故が起きません。

## 上流へ依頼するときのテンプレート

tenant_admin の権限で完結しないものは、super_admin ／ 情シスに依頼します。
次の 3 点を添えると、そのまま作業できます。

- **何を**: 許可したいホスト名（`api.example.com` か `.example.com`）
- **なぜ**: どの MCP サーバー・どの業務で使うか
- **いつまで**: 恒久か、期限付きか
