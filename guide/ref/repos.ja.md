# リポジトリ種別 — 何に対応しているか

[English](repos.md) | 日本語

作業コピーをどこから持ってこられるか、持ってきた後に Console で何ができるかをまとめます。この違いは見た目だけの話では
ありません。**横断検索のないプロバイダーでは作業項目の受信箱の動かし方が変わり、
プルリクエストのないプロバイダーではレビューの流れで提供できるものが根本から変わります**。

✓ = 対応、— = 非対応 / 該当なし。

| 機能 | GitHub | Bitbucket | 内部 git | SVN | ローカル |
|---|:--:|:--:|:--:|:--:|:--:|
| Console からアカウント接続 | ✓ | ✓ | ✓¹ | ✓² | — |
| OAuth でログイン | ✓³ | ✓ | — | — | — |
| トークン / アプリパスワードでログイン | ✓ | ✓ | ✓¹ | ✓² | — |
| テナントが登録した OAuth アプリ | ✓ | ✓ | — | — | — |
| リポジトリの一覧と選択 | ✓ | ✓ | ✓ | — | — |
| private リポジトリ | ✓ | ✓ | ✓ | ✓ | ✓ |
| クローン / チェックアウト | ✓ | ✓ | ✓ | ✓ | ✓⁴ |
| 認証を透過した push | ✓ | ✓ | ✓ | ✓ | — |
| ブランチと worktree | ✓ | ✓ | ✓ | —⁵ | ✓ |
| コミットグラフと差分 | ✓ | ✓ | ✓ | —⁵ | ✓ |
| 大きなファイル（LFS）| ✓ | ✓ | ✓ | — | ✓ |
| 受信箱に Issue を出す | ✓ | — | — | — | — |
| 受信箱にプルリクエストを出す | ✓ | ✓⁶ | — | — | — |
| プルリクエストからレビューを始める（head ブランチを checkout）| ✓ | ✓⁶ | — | — | — |
| リポジトリ横断の検索 | ✓ | —⁷ | — | — | — |
| 項目への書き戻し（コメント）| ✓ | ✓⁸ | — | — | — |
| セッション行のプルリクエストチップ（状態・ドラフト・チェック）| ✓ | ✓ | — | — | — |
| ブランチのプルリクエストがマージ / クローズされた通知 | ✓ | ✓ | — | — | — |
| ブランチのプルリクエストがマージ可能になった通知 | ✓ | — | — | — | — |

¹ 内部プロバイダーは配備自身がホストし、認証情報はメンバーシップごとに**その都度導出**されます
（保存しません）。接続する手順そのものがありません。

² URL ＋ 基本認証。自己署名証明書は、チェックアウトごとに明示的に信頼する設定ができます。

³ GitHub は Copilot エージェントの接続も兼ねます。GitHub を接続すると Copilot も
接続され、切ると一緒に切れます。

⁴ 「ローカル」はリモートのない作業コピー、つまりここで始めた新規フォルダや、自分で
クローンしたものです。動きますが、どこへも push されません。

⁵ SVN のチェックアウトはフラットな作業コピーです。ブランチ・worktree・コミット
グラフの画面は git の形をしているので該当しません。代わりに svn 行には、読み取り専用の
**ログを表示**（直線のリビジョン一覧とリビジョンごとの差分）と **ローカルの変更**
（`svn status`）があります。

⁶ Bitbucket が出すのは**プルリクエストだけ**で、課題トラッカーは読みません。

⁷ **Bitbucket にはリポジトリ横断の検索 API がありません。**クエリはワークスペース
（普通はリポジトリも）を指定する必要があります。Console はそのクエリを**書かせずに
組み立てます**。ワークスペースを指定しないクエリは空の結果を返し、それは
「自分に割り当てがない」と**見分けがつきません**。

⁸ Bitbucket のプルリクエストへのコメント投稿にはプルリクエストの書き込み権限（OAuth アプリの
`pullrequest:write`）が要り、それは**テナント管理者がスコープを広げ、全員が再認可する**変更になります。
読み取りをこの権限なしで先に使えるようにしているのは意図的です。Console が Bitbucket の行にボタンを出すのは、接続がその
スコープを持つと分かっているときだけで、そうでなければ Agent Fleet は読むだけです
（[Bitbucket のスコープ](../user/integrations/bitbucket-cli.ja.md#スコープ)）。Bitbucket の Issue は一覧に出ないので、コメントできるのは
プルリクエストだけです。

## 課題管理は別の軸

トラッカーはコードのホストと同じ製品とは限りません。Jira は Bitbucket や GitHub と
並べて使うもので、別に接続します。

| トラッカー | 出すもの | 書き戻し |
|---|---|---|
| GitHub | Issue とプルリクエストを 1 つのクエリで | ✓ コメント |
| Jira | Issue | ✓ コメント |
| Bitbucket | プルリクエスト | ✓ コメント（書き込みスコープが要る⁸）|

**プロバイダーからの 404 は「存在しない」根拠には決してなりません。**「あなたには見えない」
という意味でもあり得るので、それを不在として扱うと**受信箱が気づかないうちに取りこぼします**。

## この表にないもの

そもそも**その配備からプロバイダーへ到達できるか**は egress の話であって、プロバイダーの
能力ではありません（[deploy-targets.md](deploy-targets.ja.md) とテナント設定を参照）。
