# 配備形態 — どこに何があるか

[English](deploy-targets.md) | 日本語

コアはどの形態でも同じで、変わるのは外側のアダプタだけです。そのため差は小さく具体的で、
**だからこそ正確に書く価値があります**。「自分の配備では動いた」を前提に書くのが、ここでは
いちばん高くつくドキュメントの誤りです。

| 形態 | ワークスペースの実体 | ホームの置き場 | 選ぶとき |
|---|---|---|---|
| docker | ホストの Docker デーモン上のコンテナ | ホスト上の bind mount したディレクトリ | オンプレの既定。1 台をチームで共有する |
| native | Docker を使わない、サンドボックスされたホストプロセス | ホスト上のディレクトリ | Docker を入れられない（素の WSL2 など）。**単独利用のみ**。コンテナ境界がないので、共有モードでは起動を拒否する |
| ecs | AWS ECS / Fargate のタスク | EFS | AWS で、インスタンスを管理したくない |
| ecs-ec2 | プールから取った EC2 スロット上のタスク | ユーザーごとの EBS ボリューム | AWS で、起動レイテンシとディスク性能がインスタンス管理に見合う、または起動が多く Fargate の NAT 経由イメージ取得費用が無視できない（[デプロイ先を選ぶ](../operate/choose.ja.md#fargate-の起動は-nat-で課金される)） |
| kubernetes | Kubernetes クラスタ上の、ワークスペース専用の StatefulSet の Pod | ユーザーごとの永続ボリューム（ブロックストレージ）。ログインと Claude の状態はもう 1 本の専用ボリューム | **プレビュー。** すでに Kubernetes を運用している、または Google Cloud で、使わないときは 0 台に縮むワークスペースが欲しい。最初に検証するクラスタは GKE Standard |

> **プレビュー。** `kubernetes` ランタイムはプレビューです。GKE Standard クラスタで受け入れを確かめて
> いますが、本番での利用はまだサポートしていません。既知の制約：このランタイムにはブラウザ機能が
> ありません（ブラウザペインもヘッドレス Chromium もなし）。ホームは 1 つのゾーンに置かれ、
> バックアップされません。GKE では、始める前にリージョンの SSD ディスク割り当てが配備に足りている
> 必要があります（[ディスクの割り当て（GKE）](../operate/kubernetes/overview.ja.md#ディスクの割り当てgke)）。ロードバランサは、
> タイムアウトの設定にかかわらず、使用中の WebSocket を 24 時間で切ります
> （[7. ロードバランサを知る](../operate/kubernetes/gke.ja.md#7-ロードバランサを知る)）。切れたあとの
> ターミナルペインには `[disconnected]` と出て、クリックするかタブに戻るとつなぎ直します。シェルと
> その tmux セッションは動き続けます。これは接続を強制的に切って確かめたもので、1 日待って確かめた
> ものではありません。GKE で実測した費用は [一時停止する・費用を見る](../operate/kubernetes/pause.ja.md#既定の構成の費用) に
> あります。試用や 1 チームで使うなら、`deploy/gcp/gke` の小さなゾーン構成（1 ゾーン、データベースの
> 待機系なし）で、請求先アカウントの GKE の無料枠が残っていれば既定の構成の最低費用のおよそ半分になります（ほかの
> クラスタが無料枠を使っていれば、およそ 3 分の 2）。請求額ではなく、実測した単価からの見積もりです。数字と
> その前提は [小さな構成の費用](../operate/kubernetes/pause.ja.md#小さな構成の費用) にあります。

**Mac（Apple Silicon）では。** `docker` は Docker Desktop・OrbStack・colima の上で
`deploy/compose/docker-compose.macos.yml` を重ねて動き、`native` は Linux VM（Lima または OrbStack の
マシン）の中で `linux-arm64` パッケージとして動きます。どちらも macOS そのものの上では動きません。
単独利用のみで、`127.0.0.1` で使います。手順は
[macOS（Apple Silicon）で動かす](../operate/compose/macos.ja.md) にあります。

`docker` は `local`、`ecs` は `aws`、`native` は `wsl`、`kubernetes` は `k8s` という綴りでも通ります。
それ以外は**起動時に失敗**します（知らないうちに docker に切り替わったりしません）。
`ecs` と `ecs-ec2` をフラグでなく**別プロファイル**にしてあるのは意図的です。EC2 プールは
「実績のある 2 リソースのワークスペース」を「6 リソースのもの」に取り替えるので、
配備は明示的に選び、**コードを戻さずこの 1 つの値だけで元に戻せる**ようにしてあります。

## 能力の差

| 機能 | docker | native | ecs | ecs-ec2 | kubernetes（プレビュー） |
|---|:--:|:--:|:--:|:--:|:--:|
| 複数ユーザーの相互不可視な利用 | ✓ | — | ✓ | ✓ | ✓ |
| ユーザーごとの CPU / メモリ上限 | ✓ | — | ✓ | ✓ | ✓ |
| ユーザーごとのディスクサイズ指定 | — | — | ✓ | ✓ | ✓¹¹ |
| アイドル自動停止 | ✓ | ✓ | ✓ | ✓ | ✓ |
| ホームを保ったまま停止 / 再開 | ✓ | ✓ | ✓ | ✓ | ✓ |
| コンテナ内のユーザーガイド | ✓¹ | ✓¹ | ✓² | ✓² | ✓² |
| ブラウザペイン | ✓ | ✓³ | —¹² | ✓ | —¹² |
| メンバーごとの費用の按分 | — | — | ✓ | ✓ | — |
| 配備が提供する画像エンジン | ✓⁴ | ✓⁴ | — | ✓⁵ | ✓⁴ |
| 配備が提供するチャットエンジン | ✓⁶ | ✓⁶ | — | ✓⁶ | ✓⁶ |
| メンバー自身による作り直し・ホームの掃除（危険な操作） | ✓ | ✓ | ✓⁷ | ✓¹⁰ | ✓¹³ |
| 管理者によるホームの掃除（退職処理） | ✓ | ✓ | ✓⁷ | ✓⁸ | ✓¹³ |
| メンバーのホームのバックアップの削除 | — | — | — | ✓⁹ | — |
| Control Plane が封じる秘密をクラウドの鍵サービス（AWS KMS）で守る | — | — | ✓¹⁴ | ✓¹⁴ | — |

¹ ホスト側でステージして、起動時に bind mount します。

² タスクへ mount できるホスト経路がないので、コンテナが Control Plane の内部
エンドポイントから**同じツリー**を取りに行きます。ツリーは 1 つで、配り方が 2 つあります。

³ `native` が使う軽量イメージには Chromium を焼き込んでいないので、初回にオンデマンドで
取得します。

⁴ **自分のネットワークの中ですでに動いている** ComfyUI を環境変数 1 つで指すか、
LAN の ComfyUI・借りたエンジン・OpenAI 互換のサーバーを、エンジンの行として並べます
（[自前の ComfyUI で画像を生成する](../operate/engines/comfyui.ja.md)）。

⁵ 配備自身の GPU を、要求が来たときに買います。Fargate に相当するものはありません。
なお**どの形態でも**、セッションは**メンバー自身の CLI のプラン**（Codex /
Antigravity）で画像を生成できます。この行が指すのは**配備が提供するエンジン**の
ことです。

⁶ `ecs-ec2` では配備自身の GPU を使います。`docker`・`native`・`kubernetes` では、**自分のネットワークの中ですでに
動いている** llama.cpp を環境変数 1 つで指します（[LAN の llama.cpp でチャットする](../operate/engines/llama-cpp.ja.md)）。

⁷ Control Plane 自身はメンバーの EFS のホームをマウントできないので、スタックが宣言した短い
タスク（`30-ingress` の `HomeOpsTaskDef`）を起動し、それがファイルシステムをマウントして
ファイルを消します。Fargate のタスクは起動に数分かかるので、処理はボタンへの応答のあとで終わります。
メンバーの作り直しとホームの掃除では、ワークスペースが再び動き出すまで起動中のダイアログ
（「作り直し・ホームの掃除で消す分を home から削除しています」）を出します。削除に失敗したら
ワークスペースは停止したままで、理由を次の起動までメンバー本人と管理者のメンバー一覧の行に
表示します（失敗のあとで Control Plane が再起動しても消えません）。管理者によるホームの掃除と
「**ワークスペースを破棄**」はすぐに応答し、結果はタスクが終わった時点で監査ログに記録します。
破棄ではメンバーの EFS のディレクトリも消すので、消せなかったものとして並べることは
ありません。このタスクより前のスタック（`AF_ECS_HOME_TASK` がない）では、これまでどおり
これらのボタンを出しません。`ecs-ec2` ではホーム自体は EBS にありますが、Claude の状態と、残す
ログイン・接続は EFS にあります。「**ワークスペースを破棄**」はそれらを同じタスクで消すので、こちらでも
すぐに応答し、結果を監査ログに記録します。
タスクの実行中は、Control Plane が再起動しても、そのホームの起動と 2 つ目の操作を断ります。
操作はタスクの起動前に Control Plane のデータベースへ記録するので、途中で再起動しても何も
失われません。戻ってから 1〜2 分のうちに Control Plane がその操作を拾い、タスクの終了を待ちます
（起動の応答が失われていたら、同じリクエストトークンで ECS に起動を頼み直します。ECS は 2 つ目を
起動せず、すでに起動したタスクを返します）。そのうえで残りを片付けます。メンバーのワークスペースを
起動し（その間にメンバーが削除されていれば起動しません）、失敗ならその理由を表示し、監査ログに
結果を記録し、破棄ならワークスペースの行を消します。それまでの起動は上のとおり断ります。タスクがどう
終わったかは、タスク自身のログ（ワークスペースのロググループ、ストリームの接頭辞 `home-ops`）にあります。
ホームが解放されるのは、Control Plane がそのタスクの停止を見たときだけです。ECS がタスクを
報告しなくなったときや起動の応答が失われたときは、同じトークンで ECS に頼み直します。最初の要求から
23 時間のうちなら、すでに起動したタスクが返ります（それが終わっていれば削除をもう一度実行します。消すのは
その操作が消すものだけで、その間にホームを起動できた人はいないので安全です）。運用者が必要になるのは
2 つの場合だけで、どちらも Control Plane のログが示します。このバージョンより前の Control Plane が
残した拒否（記録を持たない）と、要求から 23 時間を過ぎてもタスクの停止を見ていない場合（頼み直しが
2 つ目を起動せず同じタスクを返すことを ECS がもう保証しない）です。`af-home/<membership>` が
起動したタスクが動いていないことを ECS で確かめた運用者が、SSM パラメータ
`/af-ws/<workspace>/home-task` を削除します。後者ではそのあと Control Plane が自分で操作を終えます。

⁸ メンバーのホームのボリュームと、その休眠コピーを削除します。次の起動では、新しいメンバーと
同じように新しいホームが作られます。この形態ではログイン・接続・Claude の状態はボリュームの外の
EFS にあるので、ほかの形態と同じく残ります。ただし、その中のファイルを前回の起動のあとで
ツールが置き換えていた場合、そのファイルは次の起動までボリューム側にあり、ボリュームと一緒に消えます。

⁹ ホームのバックアップを取るのは `ecs-ec2` だけで、それも運用者がバックアップを有効にしたとき
だけです。ホームの掃除はバックアップを消しません。消すのはメンバーの詳細画面にある別の操作で、
ワークスペースの破棄でも消えます。

¹⁰ 要求はホームに印を付けて戻り、それに続く起動が、ホームをマウントした後・ワークスペースが
動き出す前にファイルを消します。そのため起動中のダイアログには削除が起動の一段として出て、
ホームが大きいほどその起動は長くなります。メンバーのマシンが眠っていても、ホームが外れていても、
休眠コピーとして片付けられていても効きます。削除に失敗したらワークスペースは停止したままで、
次の起動がやり直します。消すはずのものを残したまま起動することはありません。起動がまだ進んでいる間は、
何も止めずにどちらも断るので、起動し終わってから押し直してください。ホームの掃除はログインと
接続を名前で残し、前回の起動のあとでツールが置き換えたものも残ります。ホームの掃除のあとの最初の
起動では、`docker` と同じくエージェント CLI を入れ直します。

¹¹ ホームのボリュームの大きさです。増やせますが、減らせません。

¹² ブラウザ機能は一切ありません（ブラウザペインも、Chromium の接続も、ヘッドレス Chromium もありません）。
`kubernetes` では、ワークスペースの pod の Pod Security `restricted` レベルにより、Chromium の
サンドボックスが setuid のヘルパーもユーザー名前空間も使えません。`ecs`（Fargate）ではタスクに
`SYS_ADMIN` を足せないため、既定の seccomp が名前空間を断り、setuid ヘルパーが使える capability も
ありません。サンドボックスなしで Chromium を動かすことはしないと決めています。
`ecs-ec2` はブラウザを使えます。`docker` と同じく、タスクに `SYS_ADMIN` を足しているからです。Console は入り口を押せない状態にして理由を示します。軽量プレビューは使えます
（[browser-pane.ja.md](browser-pane.ja.md#ブラウザペインが無い配備)）。

¹³ メンバーの作り直しとホームの掃除はホームに印を付けて戻り、次の起動がワークスペースが動き出す
前にファイルを消します（`ecs-ec2` と同じ）。管理者によるホームの掃除は、ワークスペースを止めた状態で
その場で消します。どちらもログイン・接続・Claude の状態を残します。これらは専用の 2 本目のボリュームに
あるからです。ホームのボリューム自体は残ります。

¹⁴ 既定はオフで、運用者がスタックで有効にします（[保存時の鍵を AWS KMS にする](../operate/keys/kms.ja.md)）。
有効にすると、切り替え後に Control Plane 自身が封じる秘密（MCP 接続のヘッダ、サインインのクライアント
シークレット、エンジンのトークン、セッションの引き継ぎと共有）は AWS KMS の鍵で封じられ、KMS 鍵を無効に
すると読めなくなります。メンバーが保存した資格情報の鍵が KMS で包まれるのは、切り替え後に鍵が初めて保存される
ワークスペースだけです。しかも既存のストアを開けるよう今も `AF_MASTER_KEY` から導かれるので、こちらは
マスター鍵だけで足りてしまいます。`AF_MASTER_KEY` はどの配備先でも
引き続き必須です。

## どの形態でも同じもの

ワークスペースのイメージと、その中のエージェントは、**どの形態でも同一の成果物**です
（分離の目的がまさにこれ）。本当に差が出るのは隔離の強度・ストレージ性能・egress の
統制手段で、これらは Agent Fleet の性質ではなく**基盤の性質**です。
