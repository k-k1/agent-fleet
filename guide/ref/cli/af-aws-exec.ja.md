# af-aws-exec

[English](af-aws-exec.md) | 日本語

AWS プロファイル 1 つの短命の資格情報で、コマンドを 1 つ実行します。資格情報はそのコマンドにだけ渡されます。
使いかたの流れは [AWS SSO を使う](../../user/integrations/aws-sso.ja.md) にあります。

## 書式

```sh
af-aws-exec --profile <名前> [--account <ID>] [--region <リージョン>] [--login | --no-login]
            [--keep-aws-config] [-q] -- <コマンド> [引数...]
af-aws-exec --list
af-aws-exec --help
af-aws-exec --version
```

`--` より後ろが、実行するコマンドです。

## オプション

| オプション | 意味 |
|---|---|
| `--profile <名前>` | 使うプロファイル。必須です。名前は `--list` で確かめられます |
| `--account <ID>` | プロファイルのアカウントがこの ID でなければ、何も実行せずに止めます。設定画面のプロファイル**以外**（自分で `~/.aws` に定義したもの）では必須です |
| `--region <リージョン>` | コマンドに渡すリージョン。決まり方は [af-aws-exec が確かめること・渡すもの](#af-aws-exec-が確かめること渡すもの) の「リージョン」 |
| `--login` | ログインが使えないとき、この端末で device-code のログインを始めます |
| `--no-login` | ログインを求めず、ログイン用のコマンドを表示して終了コード 3 で終わります |
| `--keep-aws-config` | 自分の `~/.aws` のファイルと `AWS_ENDPOINT_URL*` の設定を、コマンドにもそのまま渡します |
| `-q` | 実行する身元の行を表示しません |
| `--list` | 設定からプロファイルを読み直して、使える名前を一覧にします |
| `-h`, `--help` | ヘルプを表示します |
| `--version` | バージョンを表示します |

## 終了コード

| コード | 意味 |
|---|---|
| コマンドのもの | 実行できたときは、コマンド自身の終了コードをそのまま返します |
| 1 | そのほかの拒否・失敗（アカウントが `--account` と違う、など） |
| 2 | 使い方の誤り |
| 3 | ログインが必要なのに始めなかった（`--no-login`、Console で時間内に承認されなかった、待っている間に Ctrl-C） |
| 4 | 「使用前に確認」のプロファイルで、Console で拒否された・時間内に答えがなかった・Agent Fleet のセッションの外から実行された |

終了コード 4 のとき、依頼は Console に残っています。許可してから、もう一度実行してください。

## 出力

コマンドを実行する前に、標準エラーに次の 1 行を出します（`-q` で消せます）。

```
af-aws-exec: running as arn:aws:sts::222222222222:assumed-role/AWSReservedSSO_Developer_…/you@example.com in region ap-northeast-1 (expires …)
```

実際にどのアカウント・ロールで動くかは、この行で確かめられます。

## `--list` の見方

1 行に 1 つ、`名前　アカウント　ロール　（ラベル）` の順に並びます。
`~/.aws/config` に書き出されなかったプロファイルは、`(not exported: …)` の形でその理由が出ます
（同じ名前になるラベルが 2 つある、自分の `~/.aws` に同じ名前の定義がある、など）。

## プロファイルの名前と ~/.aws/config

登録したプロファイルは **`~/.aws/config`** にも書き出されます。`aws --profile <名前>`・AWS SDK・ビルドツール
（Gradle、Maven、CDK、Terraform など）から、設定を写し直さずに名前で選べます。`AWS_PROFILE=<名前>` よりも
`--profile`（またはツール自身のプロファイル設定）を使ってください。シェルに設定済みのキー（`AWS_ACCESS_KEY_ID` など）は
`AWS_PROFILE` より優先されるので、コマンドが誰として動くかを固定できません。

- **名前**はプロファイルのラベルの、英数字と `._@-` 以外の文字を `-` に置き換えたものです（ラベル `prod app`
  → プロファイル `prod-app`）。`af-aws-exec --list` で、名前ごとにアカウント・ロール・ラベルを一覧できます。
  名前だけでなく、それらを見て選んでください。
- 2 つのラベルが同じ名前になるとき（`prod app` と `prod-app`）は、**どちらも書き出しません**（`--list` に出ます）。
  どちらを選んでも別のアカウントかもしれないためです。設定画面でどちらかの名前を変えてください。
- ファイル末尾の **管理ブロック**（`# agent-fleet` で始まる 2 行の目印の間）に入ります。編集は設定画面で行って
  ください。ブロックの中は（`aws configure set` で書き込んだ分も）書き直されます。ブロックの外はあなたのもので、
  そのまま残ります。書き出すのは**アカウントとロール**の両方があるプロファイルだけです。両方無いと
  `aws --profile <名前>` は SSO を使わず、ワークスペース自身のロールで気づかないうちに動き、片方だけだと失敗するためです。
  どちらが無いかは `--list` に出ます。`~/.aws/config` の `[DEFAULT]` の行がプロファイルを壊す場合（違うリージョン、すべてのプロファイルに
  そのロールを引き受けさせる `role_arn` など）、そのプロファイルは書き出さず、`af-aws-exec --list` がその行を示します。
  同じ名前のプロファイルを自分で定義済みなら（`~/.aws/config` でも `~/.aws/credentials` でも）、
  **あなたの定義が使われ**、こちらからは書き出しません。ラベルが `default` のプロファイルは書き出しません。
  プロファイルを指定しないすべてのコマンドの身元が変わってしまうためです。
- 変更は **5 分ほどで**、または次のワークスペース起動時に反映されます。`af-aws-exec` を実行するとその場で反映されます。

## 端末からのログイン

Console ではプロファイルの行の**ログイン**（前述）で同じことができます。端末では、素の `aws sso login` はワークスペース内の `127.0.0.1` へ戻す方式で、あなたのブラウザからは
届きません。device-code 方式を使ってください。

```sh
aws sso login --profile <名前> --use-device-code --no-browser
```

表示された URL を開いてコードを承認します（承認するのは、いま自分で始めたコードだけ）。ログインは同じプロファイルの
SSM セッションと共有されるので、1 回で両方に効きます。

## コマンドを 1 つ、あなたとして実行する: `af-aws-exec`

ワークスペースは自分自身の AWS の身元（**ワークロード
ロール**）を持つことがあり、その下のマシンも身元を持つことがあります。コンテナのワークスペース（docker または
AWS ECS、Agent Fleet 0.26.0 以降）では、セッションとターミナルにはどちらも渡りません。Agent が起動するもの
すべてからワークスペースの資格情報の環境変数を外し、SDK のインスタンスメタデータ参照を止めます
（`AWS_EC2_METADATA_DISABLED=true`）。この変数を無視するツールを止めるのはホスト側のネットワーク遮断で、
管理者が 0.26.0 への移行を終えて初めて効きます（[運用ガイド 04](../../operate/04-secure.ja.md)の「その他の運用上の統制」）。
あなた自身のマシンで直接動くワークスペースはそのままです。そこのインスタンスロールはあなたのマシンのもので、SDK は
引き続きそれを見つけます。そのため、プロファイルをまったく指定しないコマンド（素の `aws …`、SDK の既定の資格情報チェーン、
プロファイル設定の無いビルドツール）は、ワークスペースの身元で動く代わりに「Unable to locate credentials」（または
その SDK の言い回し）で止まります（プロファイルを指定していれば、名前の打ち間違いやログイン切れはそれぞれのエラーに
なります）。管理者がワークスペース自身のタスクロール（AWS ECS）を再び使えるようにすることもでき、その場合
そうしたコマンドはそのロールで、別のアカウントで気づかないうちに動きます。どちらの場合も、「Unable to locate credentials」は
「プロファイルを指定する」という意味で、「資格情報を設定する」という意味ではありません。`aws configure`、`aws login`（CLI 自身の案内）や
`~/.aws` の `[default]` セクションのキーで対処せず、資格情報を別の所から探さないでください。デプロイ、書き込み、
その他アカウントが重要な操作は、資格情報を明示して渡してください。

```sh
af-aws-exec --profile <名前> -- ./gradlew deploy
af-aws-exec --profile <名前> -- npx cdk deploy
```

## 例: S3 アップロードのプラグインを使うビルドツール

AWS プラグイン（S3 へのアップロードタスクなど）で組んだ
Gradle のデプロイタスクは、ビルドスクリプトにプロファイルが無ければ SDK の既定のチェーンに尋ねます。環境変数、
JVM のシステムプロパティ、`~/.aws` の `default` プロファイル、そしてコンテナの資格情報とインスタンスメタデータの
順です。そのためセッションで `./gradlew uploadArtifact` を実行すると、成果物をワークスペースのロールでアップロード
する代わりに「Unable to load AWS credentials from any provider in the chain」で止まります。アカウントを指定して、
あなたとして実行してください。

```sh
af-aws-exec --profile <名前> --account <ID> --region <リージョン> -- ./gradlew uploadArtifact
```

プラグインはチェーンの最初に見る環境変数でプロファイルの短命な資格情報を見つけ、「running as」の行で誰が
アップロードするかが分かります。ビルドスクリプト自身がプロファイルを指定している（`profileName = "prod"` など）
ときは、下の「could not be found」を見てください。

## 実行はすべてセッションの会話に出ます

`af-aws-exec` の実行はそれぞれ、実行したセッションの会話に 1 行を
残します。中身は、プロファイル、実行に使ったアカウントとロール、リージョン、コマンド
（`aws s3 ls`、またはプログラム名だけ）、または af-aws-exec が実行を拒否した理由です。行はそれを実行したシェルの
呼び出しの下、ターンの作業の中に付くので、実行の多いターンでも返答が埋もれません。1 つの呼び出しの複数の実行は
件数付きの 1 行にまとまり、開くと 1 件ずつ見られます。拒否された実行は赤字の件数で出ます。どの呼び出しにも
結びつけられない実行（会話に時刻を記録しない種類、バックグラウンドのプロセス）は、開始した時刻の位置に同じように
まとめて出ます。表示が途中で切れたシェルの呼び出しは、開くと実行したコマンド全文が見られます。コマンドがどう終わったかは
出ません。af-aws-exec はそのコマンド自身になるので、終了ステータスはシェルが受け取るものがそのまま正です。設定 > AWS プロファイル/SSM の「最近の実行」には、
全セッションの最近の実行が並びます。行にコマンドの引数は決して入りません（秘密が入りうるため）。何が動いたかを
見るためのもので、監査ではありません。セッションは実行が申告したもので、コマンド側から変えられます。素の `aws`
で実行したコマンドは行を残しません。

## 使用前に確認

設定 > AWS プロファイル/SSM のプロファイルのフォームで「使用前に確認」をオンにできます。すると
`af-aws-exec` は、各セッションでそのプロファイルを初めて使う前、資格情報を取り出す前に確認を求めます。セッションの
会話にカード（その会話が画面にないときはトースト）が出て、セッション、プロファイル、そのアカウントとロールを示し、
**このセッションで許可** と **拒否** を選べます。許可は 8 時間かセッションの終了まで続き、今の設定のプロファイルに
対してだけ有効です。アカウント、ロール、ポータルを編集すると、もう一度確認を求めます。拒否したとき、または時間内に
答えなかったときは、コマンドは実行されず、af-aws-exec は 4 で終わります。答えていない依頼は 15 分残るので、後から
許可すれば、エージェントの次の実行は通ります。このように設定したプロファイルから連鎖するロールも、そのプロファイルの
確認を求めます。このプロファイルは `~/.aws/config` に書かれないので、素の `aws --profile` では使えません。
`af-aws-exec` で実行してください。

できないこと: 間違いや気付かない使用を防ぐもので、わざと回り込もうとするエージェントは止めません。エージェントは
ワークスペース自身の仕組みで依頼に答えられ（そのときの会話の行には「Console を通さずに承認」と出ます）、同じ
サインインのほかのプロファイルが保っているログインを使い回せます。専用のサインインに置き、使い終わったらログアウト
するプロファイルは、毎回デバイスコードの承認が要ります。

## モデルのルート

プロファイルのフォームで「モデルのルート」の印を付けられます。この印は、そのプロファイルのロールが
`bedrock:InvokeModel*`（モデルを実行する呼び出し）だけを許可し、それより広い権限を持たないことをあなたが示すもので、
AF のルートゲートウェイがそのプロファイルを Amazon Bedrock のモデル呼び出しに使うための条件です（ADR 0128）。ゲートウェイは
ワークスペースの中で動き、各モデル呼び出しをプロファイルの短命な資格情報で署名して転送するので、呼び出しをするセッションには
AWS の資格情報が渡りません。転送するのは `invoke`、`invoke-with-response-stream`、`converse`、`converse-stream` だけで、
モデルの一覧取得などほかの AWS 操作はできません。印のないプロファイルはルートとして拒否され、その理由は呼び出しへの応答に
出ます。ルートのトークンは 1 つのセッション、今の設定のプロファイル、セッションが選んだルートに結び付いており、そのセッション自身の
プロセスにしか使えません（ゲートウェイはワークスペース内のソケットで待ち受け、呼び出してきたプロセスを確かめるので、
トークンを写した別のセッションは拒否されます）。セッションの停止・削除・アーカイブ・作り直し、選択の変更、プロファイルの
編集・印の解除・削除で失効し、何にも失効させられなかったトークンも、セッションが動かなくなってから 10 分で切れます。「使用前に確認」を付けたプロファイルは、
上と同じようにセッションの開始時に確認を求め、以後もモデル呼び出しのたびに確認し直します。許可するまで、呼び出しは理由とともに
すぐ失敗します。印はあなたの申告にすぎません。AF はロールの権限を読めないので、権限を確かめたプロファイルにだけ付けてください。
claude のセッションは、起動ダイアログの **モデルのルート** で **Amazon Bedrock** を選ぶとこのルートを使います
（[claude の経路](../agents.ja.md#claude-api-キー経路) を参照）。印の付いたプロファイルが 1 つ以上あり、
かつこの経路が実機での受け入れ確認を終えたときだけ選べます（それまでは、運用者がその確認のために有効にしたワークスペースでだけ）。

## 読み取りだけの調べものは `aws --profile` で

デプロイ、書き込み、ビルドツール、SDK のプログラム、スクリプトは
引き続き `af-aws-exec` で実行します。アカウントを確かめ（`--account`）、SSO プロファイルを読めない SDK のツール
（Gradle/Maven のプラグインに多い AWS SDK for Java v1 などの古い SDK）にも短命な資格情報を渡し、ログインが無ければ
Console であなたに尋ね、ツールによって別の身元を指す名前を断り、`--region` でリージョンを固定し、エンドポイントの
上書きを外すからです。AWS CLI そのものでのちょっとした調べもの（`describe-*`、`list-*`、`s3 ls`）は、設定画面の
プロファイルを直接指定してかまいません。ただし、次の確認が `isolated` と出るシェルの中だけです。確認は 1 語だけを
出力し、環境の中身もエラーの内容も出しません。

```sh
if err=$(env -u AWS_PROFILE -u AWS_DEFAULT_PROFILE AWS_IGNORE_CONFIGURED_ENDPOINT_URLS=true \
           aws sts get-caller-identity 2>&1 >/dev/null); then st=0; else st=$?; fi
err=${err#"${err%%[![:space:]]*}"}
if [ "$st" = 253 ] && [ "$(printenv AWS_EC2_METADATA_DISABLED)" = true ] && [ "${AF_WS_WORKLOAD_AWS:-}" != 1 ] \
   && [ -z "$(env | cut -d= -f1 | grep -E '^AWS_(CONTAINER_|CONFIG_FILE$|SHARED_CREDENTIALS_FILE$|ENDPOINT_URL)')" ] \
   && case $err in "Unable to locate credentials"* | \
        "aws: [ERROR]: An error occurred (NoCredentials): Unable to locate credentials"*) true ;; *) false ;; esac
then echo isolated; else echo not-isolated; fi; unset err st
```

`isolated` は、`AWS_EC2_METADATA_DISABLED=true` が export されていて CLI がインスタンスメタデータに尋ねず、環境にワークロードの資格情報も AWS の設定ファイルや
エンドポイントの上書きも無く、CLI の既定のチェーン（`AWS_PROFILE` を外し、設定済みのエンドポイントを無視して）が CLI 自身の「資格情報が無い」
エラー（終了コード 253）で終わった、という意味です。そのため打ち間違えたプロファイルやログイン切れのプロファイルは、別のアカウントについて答える
代わりに失敗します。それ以外（あなた自身の既定の資格情報、期限切れのセッション、失敗した `credential_process`、ネットワークのエラー）はすべて
`not-isolated` で、あなた自身のマシンで動くワークスペース、タスクロールを戻している配備、アップグレード後にまだ
起動し直していないワークスペースも、ふつうはそう出ます。この確認が見るのはこのシェルが CLI に渡すものだけで、
実行方式やバージョン、ホストのネットワーク遮断までは保証しません。`not-isolated` なら調べものも `af-aws-exec` で
実行してください。`isolated` でも、直接の調べものには次のすべてが要り、欠ければ `af-aws-exec` で実行します。

- プロファイルは `af-aws-exec --list` が書き出し済みと示すもので、名前だけでなくアカウントとロールで選びます。
  どのアカウントか分からなければ、先に確かめてください。`--list` が「from an earlier sync; not checked against
  Settings now」と警告するときは何も確かめられていないので、`af-aws-exec` で。`--list` に出ないもの、書き出していないと示されるもの、
  自分で定義したもの（`role_arn`、`credential_process`）は `af-aws-exec` で。
- リージョンを指定し、設定済みのエンドポイントを無視させます:
  `AWS_IGNORE_CONFIGURED_ENDPOINT_URLS=true aws --profile <名前> --region <リージョン> ec2 describe-instances`
  （`--endpoint-url` は付けません）。シェルに古い `AWS_REGION` が残っているとプロファイルのリージョンより優先され、
  `~/.aws/config` の `endpoint_url`（エミュレーターの設定の残りなど）があると AWS 以外へ要求が送られます。
- 確認したのと同じシェルで実行します。
- SSO トークンのエラーはログインが無いという意味です。素の `aws --profile` は Console に尋ねないので、尋ねる
  `af-aws-exec` で実行し直してください。
- `af-aws-exec` が断ったプロファイルは、ここでも使えません。素の `--profile` は抜け道になりません。

ワークスペースのエージェントも同じ決まりに従います。

## af-aws-exec が確かめること・渡すもの

- プロファイルの**短命な**資格情報を、そのコマンド 1 つの環境変数にだけ渡します。`af-aws-exec` 自身は資格情報を
  どこにも書かず、表示するのは実行する身元（ARN）だけです（AWS CLI は従来どおり `~/.aws` に自分のログインと
  ロールのキャッシュを持ちます）。
- プロファイルには設定画面で**アカウントとロール**を入れておく必要があります。`role_arn`（空でも）か
  パスの入った `web_identity_token_file` も持つプロファイルは断ります。AWS CLI がその SSO ログインを使わなくなるためです。
  `source_profile`・`credential_source`・`credential_process`・静的キー（`~/.aws/config` でも `~/.aws/credentials`
  でも）、空の `web_identity_token_file`（`role_arn` と一緒でも）を持つプロファイルも断ります。AWS CLI は SSO を使いますが、他の SDK やツールはそちらを先に使うため、1 つの
  名前がツールごとに別の身元を指してしまうからです。資格情報を同じ名前で `~/.aws/credentials` に同期するツール
  （yawsso など）が原因になるので、別の名前に同期してください。`[DEFAULT]` セクションのキーも（CLI がすべての
  プロファイルに適用するため）、値が空のキーも数えます。資格情報は、
  そのプロファイルの SSO 設定だけを書いた最小の設定ファイルから、エンドポイントの上書きを無視して SSO ログイン経由でのみ
  取得し、さらにそれがそのアカウントの、そのプロファイルの許可セットのロールのセッションであることを AWS に確かめます。`--profile default` は
  断ります。SSO プロファイルを名前で指定してください。
- **SSO ではないプロファイル。** アカウントによっては、`~/.aws` に自分で書いたプロファイルでしか入れません。
  `source_profile` からロールを引き受けるもの（`role_arn` と `source_profile`）や、`credential_process` を持つものです。
  このようなプロファイルは、`--account` でアカウントを指定すれば `af-aws-exec` で実行できます（ここでは必須です）。

  ```sh
  af-aws-exec --profile deploy-target --account <ID> --region <リージョン> -- ./deploy.sh
  ```

  AWS CLI があなた自身のファイルからプロファイルを解決します。このとき AWS CLI 自身がワークロードロールに届く経路
  （コンテナの資格情報の環境変数・IMDS）とエンドポイントの上書きは止めてあります。AWS が報告する資格情報のアカウントが
  そのアカウントのとき（ロールならそのロールのセッションのとき）だけ、コマンドを実行します。`credential_process` は
  あなた自身のプログラムで、書かれたとおりに動きます。`af-aws-exec` が確かめるのは返された資格情報のアカウントで、
  その出どころではありません。プロファイル自身か `source_profile` でたどる先のどれか（`[DEFAULT]` セクションも
  含む）が `credential_source`（ワークスペース自身の資格情報を取るもの）、`web_identity_token_file`、`login_session`、
  `mfa_serial`（エージェントが実行すると MFA の入力に誰も答えられない）を持つとき、たどる先のプロファイルが資格情報の
  取り方を 2 つ以上持つとき（たとえば `credential_process` やロールのプロファイルにキーもある。セッショントークンだけ
  でも、`~/.aws/config` に書いたキーでも数えます。AWS CLI と他の SDK で使う方が食い違うため）、たどった先の SSO
  プロファイルの設定が欠けているとき、またはたどる先が壊れているときは、何も取得せずに断ります。取り方は
  プロファイルごとに 1 つにして、キーは専用のプロファイルに置き、それを `source_profile` に指定してください。
  例外は、名指ししたロールのプロファイルが自分自身を `source_profile` にし、キーをそこに持つ場合だけです。
  `credential_process` が失敗したときは、その出力を表示しません。原因は自分で実行して確かめてください。渡すのは一時的な資格情報だけです。長期のキーそのものになるプロファイルは断るので、そのキーでロールを
  引き受ける形にしてください。たどった先が SSO プロファイルでログインが無いときは、終了コード 3 で、その SSO
  プロファイルの `aws sso login` コマンドを示します（端末ではその場でログインを始めます）。Console には尋ねません。
  このプロファイルは `af-aws-exec --list` には出ず、設定画面のプロファイルと同じ名前にはできません。元のキーは
  これまでどおり `~/.aws` のファイルにあり、`af-aws-exec` がコマンドに渡すことはありません。
- そのコマンドからワークロードロールへの経路は**塞がれます**。ログインが無い・切れているときは、別の身元に
  落ちずに失敗します。ワークスペース内では端末でも次の項目のとおり Console に尋ね、`--login` を付けるとその端末で
  device-code ログインを走らせます。
- **コマンドがログインを必要としたとき**（エージェントのコマンド、または shell セッションの端末で自分が実行したコマンド）は、Console で尋ねます。画面下部のトーストに、
  プロファイル、Settings のアカウントとロール、依頼元のセッションと、依頼が取り下げられるまでのカウントダウン（コマンドが最後に
  尋ねてから 15 分。そのログインを進めている間は出ません）が出ます。**ログイン**を押すとログインの画面が
  開くので、何のためのログインかを確かめ、そこで**ログイン**を押します。ログインのコードはそのとき初めて作られ、
  その画面にだけ表示されます。コードを確かめて**ログインして承認**を押し、開いたページで承認してください。
  エージェントのコマンドは 1 分半ほど（エージェントのセッション以外、たとえば shell のセッションのスクリプトからなら数秒）待ち、
  承認されれば続きます。
  それまでに諦めていれば、エージェントがもう一度実行します。
  **閉じる**では依頼は残り、ほかのブラウザの Console にも出続けます。ブラウザでログインできない端末では、閉じてから
  別のブラウザの Console で**ログイン**を押してください。**依頼を取り消す**は、そのログインをしないときに使います。
  依頼を取り下げ、そのプロファイルについては 1 分ほど再び尋ねません。トーストを閉じても、そのタブで隠れるだけです。設定のプロファイルの行の**ログイン**は、その 1 分の間も含めていつでも使えます。対象は Settings のプロファイルです。自分で定義したプロファイルや `--no-login` では、
  終了コード 3 と、端末で実行するログイン用のコマンドを出して終わります。
  **自分の端末**（shell・SSM セッション）では、Console に尋ねたことを表示し、device コードの有効期間と同じ最大 10 分、あなたが
  そこで承認するのを待ち、承認されれば再実行なしで続きます。**Ctrl-C** で待つのをやめると、終了コード 3 で終わり、依頼は
  Console に残ります。`--login` を付けると、代わりにその端末で device-code ログインを走らせます（URL とコードがそこに出ます）。
  Console に尋ねられないときや、上の Console の対象外のプロファイルでも同じです。ワークスペースの外は従来どおりで、
  端末ならその場でログインを始め、端末が無ければ終了コード 3 で終わります。
- コマンドには、**選んだプロファイルだけ**を定義した AWS 設定（同じ短命の資格情報を返します）を渡し、資格情報
  ファイルと `AWS_ENDPOINT_URL*` の上書きは渡しません。同じプロファイルを指定するツールはそのまま動きます。
  Terraform の `profile = "staging"`、`cdk deploy --profile staging`、スクリプト内の `AWS_PROFILE=staging` のように
  別のプロファイルを指定していると、気づかないうちにそちらで動くのではなく「The config profile (staging) could not be found」
  で失敗します。その設定を非公開に保てない場合（他のユーザーが書き込めるホームディレクトリなど）は、代わりに空の
  AWS 設定を渡して警告を出します。分離は保たれ、同じプロファイルを指定するツールだけがそれを見つけられなくなります。
  コマンド内のスクリプトが `AWS_ACCESS_KEY_ID` を差し替えると
  （`assume-role` の後など）、選んだプロファイルはそこでは解決できなくなります。気づかないうちに新しいアカウントを指すことは
  ありません。新しい資格情報は `--profile` を付けずに使ってください。
- **「could not be found」が出たら**、ツールが別のプロファイルを求めています。ツール側のプロファイル指定を外すか、
  そのプロファイルで実行してください（`af-aws-exec --profile staging …`）。これを通すために `--keep-aws-config` を
  付けないでください。あなたの `~/.aws` とエンドポイント設定がツールに戻り、ツールが指定したプロファイルで動いて
  しまいます。`--keep-aws-config` は、それらのファイルの他の設定が必要なツールのためのものです。
- **リージョン**: `--region` を付ければそれ、付けなければシェルで既に設定済みのもの（`AWS_REGION`、次に
  `AWS_DEFAULT_REGION`）、どちらも無ければプロファイルのものです。コマンドには `AWS_REGION` と
  `AWS_DEFAULT_REGION` の両方で渡し、「running as」の行にも出ます。
  シェルに古い `AWS_REGION` が残っているとプロファイルのリージョンより優先されるので、デプロイでは `--region` を
  付けてください。
- `--account <ID>` を付けると、そのプロファイルがその AWS アカウントでない限り実行しません。デプロイするスクリプト・
  手順書・エージェントへの指示には付けておくと、プロファイル名を間違えても何も起きる前に止まります。設定画面の
  プロファイル**ではない**（自分で定義した）プロファイルでは `--account` が必須です。
- 1 つの名前が 2 つを指す場合は断ります。2 つの設定ラベルが同じ名前になる場合と、設定のプロファイルと同じ名前を
  `~/.aws` で自分で定義していて、アカウント・ロール・ログインのポータルのどれかが違う場合です。
- 資格情報の寿命は SSO のロールセッション、または引き受けたロールのセッション（多くは 1 時間）です。それより長いコマンドは、期限で身元が切り替わるのでは
  なく失敗します。
