## ログインの仕方

| 種別 | ログイン |
|---|---|
| claude | OAuth。ブラウザで承認し、表示されたコードを貼り戻す。接続後はアカウントのメールとプランが出る。|
| codex | ChatGPT サブスク（device code。事前に ChatGPT の「セキュリティ」で device-code 認証を有効にする）か、OpenAI の API キー。|
| opencode | 2 段構え。**「opencode を使う」**（オフのあいだは鍵もログインも無視・既定オフ）と、**「opencode.ai への課金」**（使わない（自分の鍵だけ）/ 無料モデルのみ / Go（定額）/ Zen（従量））。後者は opencode.ai の使い方だけを決め、自分でつないだプロバイダのモデルはどれを選んでも残る。キーは使いたい LLM プロバイダの API キーを env として保存（プリセットで env 名が入る・複数登録可）。|
| copilot | 専用のログインは無い。**GitHub を git プロバイダとして接続すると接続済みになり**、GitHub を切ると一緒に切れる。そのアカウントに Copilot サブスク（Free 含む）が要る。|
| cursor | 承認リンクをブラウザで開いて承認するだけ（**貼り戻すコードは無い**）。Cursor アカウントが必要で、API キーでは接続できない。|
| kiro | device flow。確認コード付きのリンクを開いて承認（Builder ID / Google / GitHub 等）。API キーでは接続できない。CLI が大きいので、焼き込んでいない配備では初回にオンデマンド導入される。|
| agy | エージェント設定のカードからログインする。|
| lcpp | 不要。配備のエンジンにログインは要らない。カードには **「llama.cpp を使う」**（電源。オフにすると起動導線から消え、どの経路の起動も拒まれる）と **「自分の接続先」**（URL・任意の API キー・**「接続を確認」**）があり、後者は配備のエンジンの代わりに自分のネットワークの llama-server へセッションを向ける。|
| muse | 一度だけ **「Muse Code を導入」**（約 299 MB をホームへ）、その後 **「Meta アカウントでログイン」**（ブラウザで承認。貼り戻すコードは無い。サブスク契約の経路）か **「API キーを使う」**（従量課金。キーを保存すると保存済みのアカウントのログインは消える）。|
| shell | 該当なし。|
| ssm | ワークスペースの AWS SSM 接続を使う。|

## ミラーに出る状態

| 種別 | 状態 |
|---|---|
| claude | 進行中… / 質問あり / プランあり / 許可待ち / 入力待ち |
| codex | 進行中… / 質問あり / プランあり / 入力待ち |
| opencode | 進行中… / 質問あり / 入力待ち |
| copilot | 進行中… / 許可待ち / 入力待ち |
| cursor | 進行中… / 許可待ち / プランあり / 入力待ち |
| kiro | 進行中… / 質問あり / 入力待ち |
| agy | 進行中… / 質問あり / 許可待ち / 入力待ち |
| lcpp | 進行中… / 入力待ち |
| muse | 進行中… / 質問あり / 入力待ち |

ターミナル（CLI）のセッションの cursor がコマンドの承認で止まるのは、**権限確認**で許可を
求める設定にしたときか plan モードで起動したときだけで、ビルドの判断で止まるのは plan 起動の
ときだけです。ミラーは状態を出しますがカードは描かないので、ターミナルで答えてください。
待っている間はどこから送ったテキストも断られます。これは、メニューが Enter を「実行」「ビルド」として
受け取ってしまうためです。

kiro は、待っているツールの承認を許可待ちではなく **質問あり** として出します。
lcpp のツールの承認と質問はミラーにカードとして出ますが、その間も状態は進行中…のままです。
muse はツールの承認を求めないので（脚注 13）、許可待ちにはなりません。

利用上限でターンが止まると、claude・マネージドの codex・muse は時刻付きの **制限解除待ち** に
なり、上限が解けると自分で再開します。ターンが終わったあとも、そのターンが始めた作業がまだ
動いていると、claude・マネージドの codex・agy・muse は **入力待ち · BG 実行中** と出ます。

`shell` と `ssm` は会話が無いので状態モデルも通知もありません。

会話を持つ種別の停止中セッションは、どれも再開できます。ただし claude・codex・opencode・copilot・cursor・kiro・
agy・lcpp・muse は、起動時の作業フォルダが消えていると再開できません（shell はホームに戻って再開します）。
[05 止める・片付ける](../member/05-stopping-and-tidying.ja.md#再開できるできない)を参照してください。

## ターンの停止と、実行中に送ったメッセージ

キューが残っているときに「停止」がどう働くかは
[04 セッションと会話する](../member/04-conversation.ja.md#キューがあるときにターンを止める)にあります。
ここには、種別ごとの違いを書きます。

**マネージド**

- **ターンの実行中に送ったメッセージ。** codex と muse ではキューに入れず、エージェントが実行中のターンにすぐ
  取り込むので、ふつうは止める必要がありません。それでも止めた場合、メッセージはそのターンと一緒に終わり、
  次のターンは会話の中でそれを見ます。送信待ちの**今すぐ送る**も同じです。それ以外の種別は、メッセージを受け付けて
  実行中のターンの後に処理します。
- **受け渡しの途中で停止が届いたとき。** codex と muse では、エージェントがそのメッセージを始めた時点で確実に止めます
  （lcpp は Agent の中で動くので、同じように止まります）。copilot・cursor・kiro・opencode では best effort で、
  止まる前に最初の一歩が進むことがあります。
- **質問の取り消し**でターンが止まるのは codex だけです。ほかの種別は、質問に「断った」と答えるだけで、キューには触れません。

**ターミナル（CLI）**

「停止」は、その CLI がターンを止めるキー（Esc、opencode は Esc 2 回、cursor と copilot は Ctrl+C）を送ります。
cursor と copilot の Ctrl+C はターンが実行中のときだけ送り、そうでなければ「実行中ではない」と返します。
ターンの実行中に打ったプロンプトを各 CLI がどう扱ったかを、CLI ごとに 1 回ずつ測った結果が次の表です。
観察した結果であって約束ではなく、CLI の更新で変わることがあります。

| CLI | キューにある間に停止 | キューにある間にペインが閉じた |
|---|---|---|
| claude | ターンが止まり、キューのプロンプトが次に実行される | キューのプロンプトは失われる |
| codex | ターンが止まり、キューのプロンプトが次に実行される | それでも実行される（codex の裏のプロセスがペインより長く残る） |
| opencode | 「停止」は Esc を 0.5 秒ほど空けて 2 回送る（Esc 1 回では中断の準備だけ）。ターンが止まり、キューのプロンプトが次に実行される | それでも実行される（opencode の裏のサーバーがペインより長く残る） |
| cursor | 「停止」は Ctrl+C を送る。ターンが止まり、プロンプトは CLI の欄に送られないまま残る（Esc だけだとキューのプロンプトが取り消され、ターンは走り続ける） | CLI を再開しても戻らず、実行もされない |
| kiro | ターンが止まり、キューのプロンプトが次に実行される | CLI を再開しても戻らず、実行もされない |
| copilot | 「停止」は Ctrl+C を送る。ターンが止まり、キューのプロンプトは消える（Esc ではターンは止まらない） | CLI を再開しても戻らず、実行もされない |
| agy | 測っていない（「停止」は従来どおり Esc 1 回を送り、応答でキーが未測定だと伝える） | 測っていない |

**別のセッションからターミナル（CLI）のセッションへのメッセージ**も同じ規則に従い、送り手には次のように返ります。

- claude のセッションがターンの途中でメッセージを受けると、送り手には「届いた」ではなく「キューに積まれた」と返ります。
  claude はそれをメモリにしか持たないので、ターンが終わる前にペインが終了する（セッションの停止・アーカイブ・再作成）と失われます。
- CLI を起動して 3 分未満の claude のセッション（たとえば送信で再開したばかりのもの）へのメッセージは、`starting` 待ちの
  「キューに積まれた」として返ります。起動中の claude に打ち込んだ文は失われることがあるので、メッセージは預かり、
  ペインが入力待ちのまま約 45 秒落ち着いてから届けます。
- cursor のセッションの CLI が送信時にメッセージを拒んだ場合（たとえばプランで使えないモデル）も同じ形で返り、
  CLI のエラー文が添えられます。メッセージは入力欄に残るだけで実行されないので、送り手には再送しないよう伝わります。
- cursor のセッションの入力欄に、送られていない文（CLI が前に拒んだプロンプトや書きかけ）が残っていると、
  メッセージは断られます。そのまま送ると cursor が 2 つを 1 つのプロンプトとして実行するためです。送り手には、
  先にペインでその文を送るか消してもらうよう伝わります。

## 別のエージェントへ移す

移動（[05 止める・片付ける](../member/05-stopping-and-tidying.ja.md#別のエージェントへ移すmove)）には移動元と
移動先の 2 つの立場があり、種別によっては片方にしかなれません。

| 種別 | 移動元として | 移動先として |
|---|:--:|:--:|
| claude | ✓ | ✓ |
| codex | ✓ | ✓ |
| opencode | ✓ | ✓ |
| copilot | ✓ | ✓ |
| cursor | ✓（停止中のマネージドを除く） | —（未検証） |
| kiro | ✓ | ✓ |
| agy | ✓ | ✓ |
| lcpp | ✓ | —（引き継ぎファイルを読めない） |
| muse | ✓ | ✓ |
| shell / ssm | — | — |

- **停止中のマネージドの cursor セッションは移せません。** 会話は動いていたエージェントの中に
  しか無かったので、引き継ぎファイルを書く材料が残っていません。
- **cursor は移動先に出ません。** マネージドのドライバー経由で引き継ぎファイルを読めることを
  確認するまでは選べません。
- **lcpp は移動先に出ません。** lcpp のファイル操作のツールは作業フォルダの外のパスを拒み、
  引き継ぎファイルはその外にあるためです。
- 移動先は必ず別の種別です。同じ種別で続けたいときは、分岐できる種別ならセッションを分岐して
  ください。shell と ssm には引き継ぐ会話がありません。

| 種別 | スイッチがオンの間 | Agent Fleet のメモリへの取り込み | オフにしたときの書き戻し |

| muse | 新しいホストは Muse Code のネイティブメモリをオフにして起動する | **muse から取り込む** で 1 回 | — |

## どれを選ぶか

**すでに払っている契約で選ぶ**のが確実です。Anthropic のアカウントなら **claude**、
ChatGPT や OpenAI API なら **codex**、複数プロバイダの API キーを切り替えたいなら
**opencode**、GitHub Copilot のサブスクがあるなら **copilot**、Cursor のプランがあるなら
**cursor**、AWS Builder ID（や Kiro プラン）なら **kiro**、Meta アカウント（や Meta の
Model API キー）があるなら **muse**。ベンダーのアカウントがいらないモデルを使いたいなら **lcpp** です。
組織の engine（またはネットワーク上の llama-server）で動くので、サインインも契約の上限もありません。

どれも会話表示・ミラーからの回答・他エージェントへの引き継ぎに対応します。実際に
決め手になりやすい差は、コンテキストゲージ（claude / codex / opencode / kiro / lcpp / muse）、
画像貼り付け、そしてマネージド実行が要るかどうかです。**Codex と opencode は
セッションごとのプロセスを持たない**ので、数を並べても重くなりません。

## lcpp: 実機計測で分かったこと

`lcpp`（ADR 0093）はベンダーのホスト型 API ではなく、自前の llama.cpp エンジンの
インスタンスを動かします。16 回の実機走行で、最初のセッションの前に知っておくべき
実際の費用が分かりました。

- **最初のターンは分単位で待ちます。** エンジンのインスタンスが止まっていると、
  真のコールドスタートに**おおよそ 3.5〜7 分**かかります（多くは 4〜5 分帯に収まり、
  1 件は 302 秒でタイムアウトしました）。セッションが固まっているのではなく、
  インスタンスを購入して起動している時間です。2 回目以降のターンは、インスタンスが
  温かいままなら速く返ります。
- **文脈窓は 8000 トークン以上を選んでください。** 窓 3500 では、一部のモデル
  ファミリーが圧縮を連続で発火させ、ハーネスが無限に回り続ける代わりに意図的に
  停止します。Gemma と Qwen3-Coder の両方で再現しました。窓 8000 ではどちらも
  問題なく完走し、窓 24000 では圧縮自体が起きません。この停止は設計どおりの
  動作であり、不具合ではありません。
- **同じ課題でもファミリーによってターン数が大きく違います。** 同じ窓でも
  費用差は数倍に及びます。ある実測の課題（小さなプロジェクトの 5 か所の
  不具合修正＋想起の質問 1 問）では、Qwen3.8 が 29〜30 ターン、Gemma-4 が 63
  ターン、GPT-OSS が 95 ターン、Qwen3-Coder が 164 ターン（Gemma-4・Qwen3-Coder
  はどちらも窓 8000）でした。4 つとも正しく完走しており、差は正しさではなく
  費用です。
- **動作を確認したモデルファミリーは Qwen3・GPT-OSS・Gemma の 3 つ**（4
  チェックポイントで確認）。`llama-3.1-8b-instruct-q4_k_m` は**動きません**:
  このエンジンのビルドには Llama 専用の tool call パーサが無く、tool call の
  構文解析が失敗します。目録にあるモデルがどれも同じように動くわけではないので、
  確認済みのファミリーを選んでください。
- **モデルの入れ替えにインスタンスの入れ替えは要りません。** 最初の 1 回を除き、
  同じエンジン上で別のモデルへ切り替えてもコールドスタートは発生しませんでした。
  高くつくのは最初の購入だけです。

`lcpp` には Terminal（CLI）経路が一切ありません。上の脚注 9 のとおり、動くのは
Managed だけです。

## muse: Agent Fleet からは見えないもの

Muse Code は、Agent Fleet にもある機能を自前でいくつか持っています。muse のセッションの
中ではそれらがそのまま動きますが、Agent Fleet の側からはほとんど見えません。使うのは構いませんが、
Console に出る情報は Muse Code 自身よりずっと少ないと分かったうえで使ってください。

- **muse のセッションが自分で入れる予約実行。** muse のセッションは、プロンプトを自分の
  タイマーに載せて、あなたがいないところで後から走らせることができます。これは Muse Code
  の予約であって Agent Fleet の予約ではありません。Console の予約実行の一覧には出ず、
  Agent Fleet からは取り消せず、一覧も削除もそのセッション自身にしかできません（本人に
  頼んでください）。予約が発火するとミラーに `scheduledFire` という 1 行が出るので、走ったことは
  分かります。発火するのはそのセッションが動いている間で、繰り返しの予約は 7 日で
  自動的に期限切れになります。Agent Fleet からこの機能を止めることもできません。これは、Muse Code
  にその設定が無く、そのツールを外せる唯一の制御は連携（MCP）のツールを（Agent Fleet が
  セッションに渡しているものも含めて）まとめて外してしまうからです。上の表の「定時実行
  （無人実行）」の行は Agent Fleet 自身の予約の話で、これとは別ものです。
- **muse のセッション同士のメッセージと、そこで使われる名前。** Muse Code はセッション間
  メッセージと、セッション名の登録簿を自前で持っていて、どちらも利用者ごとにホーム
  ディレクトリへ置かれます。Agent Fleet はそのどちらにも繋がっていません。その経路で送られた
  メッセージはミラーにも会話にも通知にも出ませんし、その登録簿の名前は Console が表示する
  セッション名とは別ものです。あるセッションから別のセッションへ話しかけたいときは、ミラーに
  出る Agent Fleet 自身のセッション間メッセージを使ってください。
- **muse が持つ、あなたの muse 会話の一覧。** 1 つのワークスペースの muse セッションは
  Muse Code のストアを 1 つだけ共有するので、Muse Code 自身のセッション一覧はセッション単位
  ではなく利用者単位です。実測でも、ある muse セッションが、自分とは無関係の muse セッションの
  会話を一覧に出しました。Agent Fleet は自分が始めていない muse の会話を出すことは決して
  ありませんが、セッション自身は Muse Code 自前のコマンドや `read-session` スキルから他の
  会話に届きます。

> エージェントはあなたの代わりにコマンドを実行し、ファイルを編集し、push します。
> 定時実行では無人で、権限確認をスキップするモードでは都度尋ねずに、これらを行います。`shell` と `ssm`
> は送った文字列を**そのまま**実行します。バックアップを取り、最小権限の資格情報を使い、
> 承認ゲートに頼ってください。

¹¹ muse を起動メニューやアシスタントの相手として出すには、2 つが揃っている必要が
あります：Muse Code はプロプライエタリでイメージに含まれないのでオンデマンドでの導入が要り（Muse
Code の接続カードから・約 299MB がホームに入ります）、かつログイン済みであることです。未認証の
セッションは仕事を受け取ったうえで毎ターン失敗します。アシスタントとしての muse は 1 ターンを
1 回のヘッドレス実行で答え、会話を覚えています。続けて尋ねれば前のターンを踏まえて返します。
そして「答える」だけで「する」ことはありません。Agent Fleet はこのターンをシェル・ファイル書き込み・
Web ツールを切って走らせており、実測 2 回、ファイルを書くよう頼んだチャットターンはツールを
1 度も呼ばず何も書きませんでした。

¹² Agent Fleet は muse の会話を進行中に自分の側へ書き写すので、停止中のセッションでも
履歴が見えます。Muse Code 自身のセッションファイルは読める転写ではなく内部形式の実行時
ログなので、ここでは出典になりません。

¹³ muse のセッションはツールの承認を一度も求めません。スキップする対象が無いので選べませんが、
この行の「—」は、機能が無いという意味ではなく**安全側が薄い**という意味です。Muse Code
自身のサンドボックスは Workspace のコンテナの中では構築できず（コンテナのセキュリティプロファイル
が拒否します）、そのサンドボックスを切るフラグはセッションのファイルシステムとローカル網の制限も
一緒に外します。結果、どのツール呼び出しも承認を考える前にポリシーで許可されます。実測では、muse
のターンが作業コピーの外にあるファイルを確認なしで書きました。よって muse のセッションはこの
コンテナに対して `shell` と同じ届き方をするものとして扱い、上の警告はそのまま当てはまると読んで
ください。

¹⁴ Muse Code には **contributor モード**があり、オンの間は会話（セッション間のメッセージを含む）が
Meta の製品改善に使われることがあります。Agent Fleet は会話を扱う muse を起動するたびに、このモードを明示して
渡します。設定 › エージェント › Muse Code › 動作 の **contributor モード** でオンにしない限り
**オフ**です。各セッションは作成時のモードを、停止・再開や Agent の再起動をまたいでも保ち、
フォーク・作り直しでも引き継ぎます。設定の変更は、以後に作成するセッションと、次回以降の
アシスタントチャット・AI 補助に反映されます。セッションが自分でこの設定をオンにすることはできず、
オンにできるのは Console からの変更だけです。

Muse Code 1.3 では、同じ選択がどのモデルにも並ぶ「-contributor」版として提供され、しかもその版が
Muse Code 自身の既定でした。いまもその版を一覧に出すホストでは、Agent Fleet が代わりに選ぶことは
ありません。**既定**のまま起動したセッションは、その条件が付かない最新のモデルで動き、選びたい人の
ために contributor 版もピッカーに残してあります。既定のモデルと reasoning effort（`none`〜`ultra`）も
同じ 動作 設定で選びます。

アシスタントチャットも同じ扱いで、選ぶ場所は 設定 › AI です。推奨のままならその条件が付かない最新の
モデルで動き、一覧そのものが読めないときは Muse Code の既定で黙って走らせず、そのターンを断ります。

¹⁵ muse のチップは、稼働中の muse セッションが**最後に観測した値**です。Agent Fleet の側から
取りに行ける数字ではありません。Muse Code は自分の使用量をセッションプロトコルで報告し、それが
届くのはターンが終わったあとです。このワークスペースで muse をまだ動かしていない間、チップは
「—」＝「まだ観測が無い」を出します（使用量ゼロではありません）。1 つ目の利用枠の長さは提供元が決める
ため（実測では 5 時間）、行の名前は「現在の利用枠」にしてあります。

¹⁶ Muse Code は個人のルールを `~/.config/muse/AGENTS.md` の 1 ファイルに置く作りで、
ワークスペースの方針とあなた自身の指示の両方がそこへ行きます。Agent Fleet は印付きの 2 ブロックと
して書き、それ以外はそのまま残すので、あなたが自分で書いたルールは消えません。ワークスペースの
トピックファイルは別経路で、`~/.config/muse/skills/` 配下のスキルとして届きます。セッションは
作業コピーを信頼した状態で動くので、リポジトリ自身の `AGENTS.md` も読まれます。なお Muse Code は
`AGENTS.md` と `CLAUDE.md` を足し合わせではなく**優先順位**として扱い、両方あると `AGENTS.md` を
使って他方は飛ばしたと言います。

¹⁷ muse は、連携サーバーを設定ファイルに書いてもらう代わりに、**セッションの開始時に Muse Code へ
手渡す** kind です（もう 1 つは lcpp です。脚注 18）。つまりサーバーの組み合わせをワークスペース全体で 1 つに揃える必要が
なく、セッションごとに変えられます。ここから 2 つ。追加したサーバーが効くのは、その**あとに**
起動したセッションからです（稼働中のセッションは渡された組み合わせのまま）。そして各サーバーが
起動するのはセッションを開いた時ではなく**最初のターンが走る時**なので、立ち上げ直後のセッションは
まだ何も繋がっていないように見えます。どのサーバーも「任意」として渡すので、起動に失敗しても
失うのはその連携だけで、セッションそのものは動きます。

¹⁸ lcpp にも設定ファイルはありません。ベンダー CLI を駆動しないので、有効にしたサーバーは
**毎ターンの開始時**に読み直され、Agent Fleet 自身が接続します。したがってサーバーを足したり
外したりすると、**すでに開いているセッションでも次のターンから**効きます（再起動は要りません。
ここが muse との違いです。脚注 17）。接続できないサーバーがあっても失うのはそのターンの
そのツールだけで、ターン自体は動きます。失敗は毎ターンではなく会話に 1 度だけ記録されます。
ツールを動かしているのが Agent Fleet 自身であることの帰結がもう 1 つあります。
**連携サーバーのツールは、どれも実行前に許可を求めます**。これは、MCP の仕様には「このツールは読むだけ」
と機械的に判定する手段が無いためです。

¹⁹ lcpp のモデル一覧は**あなた自身の llama.cpp サーバーのもの**なので、ベンダー CLI のような
「ツールに任せる」項目がありません。選ぶまで起動は待ちます。この種別では**どれを選ぶかが費用の
判断**です: ある実測ベンチマークでは同じ作業がファミリーによって 29 ターンと 164 ターンに分かれ、
どちらも正しく完了しました。後からモデルを替えてもインスタンスを買い直しません（上の
「lcpp: 実機計測で分かったこと」）。

²⁰ codex と opencode が分岐できるのはマネージド実行のときだけです（CLI の起動コマンドには分岐点を渡す方法がないため。
lcpp と muse は常にマネージドです）。例外として、共有サーバーに接続した opencode 2 のターミナル（CLI）セッションも分岐できます
（共有サーバーが分岐点を受け取れるため）。専用サーバーのターミナルセッションや opencode 1.x では使えません。

²¹ copilot の Plan モードは起動時に設定し、マネージドの設定から切り替えることもできます。

²² cursor のモデル一覧は、ログインしているアカウントで使えるモデルそのものです（ライブ取得）。kiro は Free プランでも named モデル（Auto、Claude Sonnet / Haiku ほか）を選べます。

²³ RTK は、エージェントが実行するコマンドを書き換えて、出力で消費するトークンを減らす仕組みです。
⚙設定 →「エージェント」でエージェントごとにオン／オフでき、ワークスペースのイメージに
`rtk` が無いときは何も起きません。効き方は違います。claude・opencode・copilot は、シェルコマンドを実行前に
書き換えるフックかプラグインを持つので、毎回効きます（copilot は変更後に始めたセッションから）。
codex と agy にはコマンドを書き換える手段が無く、Agent Fleet は「`rtk` を使ってね」という指示ブロックを
足すだけです。使うかどうかはエージェント次第（ベストエフォート）です。cursor・kiro・lcpp・muse に RTK の設定は
ありません。この行はコードと突き合わせて検査されています。ドライバが RTK の仕掛けを持つ種別に印が付きます。

²⁴ どちらも既定でオフのオプトイン設定です（設定 › エージェント › セッション）。セッションが子を起こす・メッセージを
送るのは Agent Fleet 自身の MCP サーバーのツールで、それは「連携（MCP）サーバーを受け取る」行に印のある
種別すべてに渡ります。そのためこの行はその行に連動し、検査も同じコード上の項目に結び付けてあります。
受ける側はこの行の種別すべてです。子はこの 9 種別のどれでもよく、メッセージの宛先にもなれます
（停止中なら先に再開します）。`shell` と `ssm` はどちらも不可です。送られた文字列がコマンドとして
実行されてしまうためです。

²⁵ スタジオのエージェントのセッションは、どちらの実行方式でも付けられます。ただし、スタジオのツールに
「自分はどのセッションか」を伝えられないエージェントは別です。opencode はマネージド（1 つのサーバーを
フォルダ内の全セッションが共有するため、書き込みがどのセッションのものか区別できません）、
copilot・cursor・kiro もマネージド（セッション名をまだ伝えられません）で、この 4 つはターミナル（CLI）でだけ
付けられます。claude と agy はマネージドが無いのでもともとターミナル（CLI）だけです。codex はどちらの方式でも付けられ、
lcpp（マネージドのみで、ターミナル（CLI）はありません）はマネージドで付けられます。muse は戻れるターミナル（CLI）が無く、
マネージドも同じ理由で断られるため、いまは付けられません。付けられるかどうかはコードと突き合わせて検査されています。
スタジオのセッションは既定で worktree 付きで、Console でオフにできるのはターミナル（CLI）のセッションと lcpp だけです。
