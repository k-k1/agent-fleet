# 上限と既定値

[English](limits.md) | 日本語

1 箇所に集めているのは、**上限は必ず最悪の瞬間にしか出会わない**からです。そのとき読者は
3 つを同時に知る必要があります：天井はいくつか、誰が上げられるか、達したら何が起きるか。

## 製品として固定のもの

配備によって変わりません。

| 上限 | 値 | 達したときに起きること |
|---|---|---|
| セッション名 | 80 文字 | 制御文字を落として切り詰める。**全ての層で同じ値で検査する**（理由は下）|
| ブラウザペイン: Chromium プロセス | ワークスペース当たり 1 | — |
| ブラウザペイン: 同時 Page | ワークスペース当たり 2 | どれかを手放すまで 3 つ目は開けない |
| ブラウザペイン: viewport | 1600×1200（DPR 1）| それ以上は切り詰める |
| ブラウザペイン: フレームレート | 表示中 12 fps | 動画の確認には使えない |
| ブラウザペイン: 非表示時の保持 | 60 秒 | 過ぎると Page を解放し、戻ったときは保存済みの port/path から作り直す |
| フォルダの zip ダウンロード: ファイル数 / フォルダ数 / 深さ | 20,000 / 4,000 / 32 階層 | 413 と上限の名前を挙げたメッセージで断る。切り詰めはしない（ADR 0111）|
| フォルダの zip ダウンロード: 読むバイト数 | 512 MB | 一覧ではなく実際に読んだバイト数で数えるので、作成中に大きくなったファイルも止まる。413 で断る |
| フォルダの zip ダウンロード: 見たエントリ数 / 名前の長さの合計 | 100,000 / 4 MiB | 413 で断る |
| フォルダの zip ダウンロード: 読む時間 | 45 秒 | 413 で断る（アーカイブができるまで何も送らないので、ロードバランサーのアイドル 60 秒より短くしてある）。協調的な上限: 読み込みの間と最後の読み込みの後に確かめるので、固まったボリューム上で止まっている呼び出しは、返るまで作成枠を握る |
| フォルダの zip ダウンロード: 転送の時間 | 15 分 | 接続を閉じる。止まったクライアントが唯一の作成枠を長く握れないようにする |
| フォルダの zip ダウンロード: 同時の作成 | ワークスペース当たり 1 | 2 つ目の押下は最大 2 秒待って 503「混雑」。作成ごとにホームのボリュームに最大でバイト上限ぶんの一時ファイルができる |
| ブラウザペイン: console メッセージ保持 | 200 件 | 古いものから捨てる。**永続ログではない** |

> **なぜセッション名の上限をわざわざ書くのか。** かつては層ごとに値が違いました。
> 引き継ぎ提案は 512 バイトまで受け取り、カードにも起動ダイアログにも出て編集もできたのに、
> **セッション作成だけが 80 で弾き**、利用者には「worktree 起動に失敗: title is too long」
> としか見えませんでした。層ごとに違う値で検査する上限は、**特定の瞬間にしか出ない故障**を
> 生みます。値は 1 つ、置き場も 1 つ。

## 配備が決めるもの

既定値は `deploy/compose/.env.example` が正です。

| 上限 | 既定 | 決める変数 |
|---|---|---|
| ワークスペースのメモリ | 5g | `WS_MEMORY` |
| ワークスペースの作業ディスク（Fargate）| 50 GiB | `AF_ECS_WS_DISK_GB` |
| ユーザー毎のホームボリューム（EC2 形態）| 50 GiB | `AF_ECS_EC2_HOME_GB` |
| 停止の猶予 | 30 秒 | `AF_STOP_GRACE_SEC` |
| 起動タイムアウト（AWS 形態）| 300 秒 | `AF_ECS_START_TIMEOUT_SEC` |
| 停止中セッションが一覧に残る期間 | 7 日 | 利用者ごとの **設定 → エージェント → セッション**（1 / 3 / 7 / 14 / 30 日、またはしない）。「既定」のままの利用者には配備の `AF_SESSION_STOPPED_TTL` が効き、過ぎるとアーカイブへ移る。削除はされず、作業コピーも残る。削除ロック中のセッションは一覧に残る |
| クラウド費用の集計窓 | 7 日 | `AF_CLOUD_COST_WINDOW_DAYS` |
| アイドルの掃除 | 有効 | `AF_IDLE_SWEEP_INTERVAL`：**`0` は掃除を完全に止める**ので、アイドルで停止されることが一切なくなる |

セルフホストのエンジン自身の自動停止はこの表にはありません。「**自動停止まで**」を管理モーダル →
推論エンジンで役ごとに決め、保存した値はコントローラの次の巡回からエンジンのスタックの既定より
優先されます（[admin/04](../admin/04-mcp-egress.ja.md)）。

## テナントが決めるもの

引用できる固定の数字はありません。テナント管理者は**テナント設定 → 上限・自動停止**で
効いている値を見られ、決めるのは配備管理者です。**このページではなく画面を見てください。**

- テナント当たりのワークスペース数、メンバー当たりのセッション数
- ワークスペースのサイズ（CPU / メモリ / ディスク。形態が対応していれば）：[deploy-targets.md](deploy-targets.ja.md)
- アイドル自動停止のしきい値
- テナントの管理者がエンジンのモデルを取り込めるか（許可しない限り不可）と、テナントが
  セルフホストのエンジンをそもそも使えるか（役ごと、llm / image。オフにしない限り可）

## 状態

このページを増やす人へ、規則を 2 つ。**複数の層で検査している上限は全ての層を書く**こと
（理由は上）。そして**どこでも計測していない上限は、それらしい数字を置かずに
「計測していない」と書く**こと。でっち上げた既定値は、穴を認めるより悪い。
人が確かめるのをやめさせてしまうからです。
