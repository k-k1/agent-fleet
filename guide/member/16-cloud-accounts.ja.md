# 16. クラウドのアカウント — AWS プロファイル・SSM ホスト・Google Cloud

[English](16-cloud-accounts.md) | 日本語

## 社内の別ホストに入る（SSM）

自社 AWS の EC2 に、AWS SSM Session Manager でログインできます。設定は **⚙設定 →
「AWS プロファイル/SSM」タブ**で、**2 層**に分かれています。

- **プロファイル（共通設定）**：アクセスポータル（IAM Identity Center）とアカウント／ロール。複数のホストで使い回す SSO の設定のまとまりです。まずこれを 1 つ作ります。
- **SSM ホスト（個別）**：ログイン先の別名 → インスタンス ID。認証はプロファイルを選ぶだけです。

プロファイルの登録・ログイン・ログアウト・取り込み・書き出し・共有サインイン・ロールの引き受けは [AWS SSO を使う](../user/integrations/aws-sso.ja.md) に、細かい規則は [AWS プロファイルの仕様](../ref/aws-profiles.ja.md) にあります。

プロファイルとホストの各行には**編集**があり、同じフォームを入力済みで開いてその場で保存します。削除して登録し直すのではなく
編集を使ってください。ホストはプロファイルを内部 ID で参照するので、登録し直したプロファイルは別物になります。
ホストが使っているプロファイルは削除できず、画面がそのホストを挙げます。先にホストを編集して別のプロファイルを選ぶか、
ホストを削除してください。この制限より前にプロファイルを失ったホスト（行にその旨が出ます）も同じく、編集して選び直します。プロファイルのワークスペースでの名前は
表示名から作られ、ログインはその名前に付きます。表示名や start URL・SSO リージョンを変えたらログインし直しが要り、フォームが
そう警告し、その行から改めてログインするまで行に**要再ログイン**と出ます。ワークスペースの `~/.aws/config` には 5 分以内か、**ログイン**を押した時点で反映されます。開いているセッションは
古い設定のままです。

**AWS の秘密情報は Agent Fleet に保存されません。** ログインはセッション開始時に、
端末に出る **`aws sso login`** の URL をブラウザで承認する device-code 方式で、
短命の資格情報はワークスペース内にだけ保持されます。

登録後は、ワークスペース操作バーの **「はじめる」→「SSM — 別ホストへログイン」** で
**ログイン先ホスト**を選んで接続します。
認証が必要なら `aws sso login` の URL が確認画面に出るので、別タブで承認してください
（身に覚えのないコード／URL は入力しないこと）。

### ~/.ssh/config から SSM ホストを取り込む

**「~/.ssh/config から取り込む」**（プロファイルの取り込みの隣）は、ssh の設定を読んで SSM ホストを作ります。
先に読んでください：**接続方式が変わります。** ssh の設定では、これらのエントリは
`ProxyCommand aws ssm start-session … --document-name AWS-StartSSHSession` で SSM のトンネル越しに SSH セッション
（ユーザー・鍵・ポート）を開きます。Agent Fleet のホストは、インスタンス上で `aws ssm start-session` のシェルを
開き、SSH のユーザー・鍵・ポートはありません。`User`・`IdentityFile`・`Port`・転送などの設定は引き継がれず、
プレビューにその名前が出ます。

ファイルはブラウザの中だけで読み、**`ProxyCommand` は実行も表示も送信も保持もしません。** 保存されるのは、チェックした
行の別名・インスタンス ID・AWS プロファイル・リージョンだけで、ホスト追加フォームと同じ保存を使います。

読むのは決まった 1 つの形だけです。**1 つの具体的な名前の `Host`** で、`ProxyCommand` が `aws ssm start-session`
（`sh -c "…"` で包んだ形も可）であり、次のオプションだけを各 1 回まで使うもの：`--target`（インスタンス ID
`i-…` / `mi-…`、または `%h`。`%h` はそのエントリの `HostName`、`HostName` がなければ `Host` の名前そのもので、
インスタンス ID であること）、`--document-name AWS-StartSSHSession`、`--parameters portNumber=%p`（または
`portNumber=22`）、`--profile`、`--region`。それ以外は理由つきで**取り込めません**：他のドキュメント（ポートフォワード・
独自）、他のオプション、他の `%` トークン、シェルの構文（`;`・`|`・`$(…)`・単語全体を囲む以外の引用符）、`ProxyJump`、
ワイルドカード（`*`・`?`）、否定（`!`）、`Match`、`Include`。

OpenSSH は、名前に当てはまる全ブロックを通して、各キーワードの**最初の**値を使うので、ブロックは互いに独立していません。
`ProxyCommand`（`%h` が要るときは `HostName` も）が最初の値で、かつ**そのホスト名を直接書いたブロック**から来ている
ときだけ取り込めます。`Host *` や前にあるパターンから受け継ぐ値、これらのキーワードを設定する `Match` や
`Include`（その中身は貼り付けた文面にありません）より後ろの値は拒否します。取り込みたいときは、Include 先の内容を
上に貼り、そのホストのエントリを全部書いてください。

**AWS プロファイル**は、AWS 名がコマンドの `--profile` と同じ Settings のプロファイルです。`--profile` がない、または
一致するものがないときは、行の中でプロファイルを選びます。すでにある行（別名とインスタンスが同じ）は**登録済み**と
表示し、別のインスタンスで使われている別名は拒否します。「取り込む」を押すまで何も作らず、今のホスト一覧を読めなければ何も送りません。

端末・SDK・ビルドツールから使うときと、`af-aws-exec` の詳しい使いかたは [af-aws-exec](../ref/cli/af-aws-exec.ja.md) にあります。

## Google Cloud で自分としてコマンドを実行する（af-gcloud-exec）

Google Cloud のプロファイルは **⚙設定 →「Google Cloud」タブ**に置きます。プロファイルは、コマンドがどのプロジェクトに
向き、誰として動くかを決めます。

- **ラベル**：表示名です。コマンドで使うプロファイルの**名前**はここから作られ、ラベルの横に表示されます。英小文字・数字・
  `-` だけになり（それ以外の文字の並びは `-` に、数字で始まる名前は先頭に `p` が付き、日本語のラベルのように使える文字が
  無いものは `p-` と短い符号になります）。2 つのラベルが同じ名前になると（`Prod` と `prod`）、**どちらも**ワークスペースで
  **使えず**、行にそう表示されます。片方の名前を変えてください。
- **ログイン方法**：Google アカウント（Google Workspace・Cloud Identity のアカウントを含む）。
- **プロジェクト**：コマンドが既定で向くプロジェクト ID（番号ではありません）。
- **割り当てプロジェクト**（任意）：API の割り当てを課金するプロジェクトで、空欄ならプロジェクトと同じです。個人の
  ログインでは割り当てプロジェクトが要る API があり、あなたのアカウントにはそのプロジェクトでサービスを使う権限が要ります。
- **アカウント**（任意）：ログインする Google アカウントで、ほかのアカウントでのログインは断られます。空欄なら
  最初のログインで選びます。
- **権限を借用するサービスアカウント**（任意）：コマンドは、あなたのログインを通じてこのサービスアカウントとして動きます。
  あなたのアカウントには、そのサービスアカウントに対するサービス アカウント トークン作成者のロールが要ります。サービス
  アカウントとして動く方法はこれです。サービスアカウントキーはどこでも受け付けません。
- **リージョン / ゾーン**（任意）。

**Google の認証情報は Agent Fleet に保存しません。** ログインはワークスペースの中の、ワークスペース専用の gcloud の保存場所に
あります。端末で使う自分の `gcloud` とは別物で、片方でログインしてももう片方はログインしません。プロファイルが自分の gcloud の
設定・ログイン・アプリケーションの既定認証情報を読んだり変えたりすることはありません。設定の変更は 5 分ほどで
ワークスペースに届き、`af-gcloud-exec` を走らせればすぐに届きます。プロファイルのアカウントを変えたとき、ラベルを変えて名前が
変わったとき、削除して追加し直したときは、どのアカウントを使うかがリセットされます。指定したアカウントがすでにワークスペースでログイン済みで
なければ、次の実行でログインを求められます。プロファイルは書き出し・取り込みで持ち運べます（[20 設定](20-settings.ja.md#書き出し-取り込み)）。

### gcloud の構成から取り込む

Google Cloud タブの **gcloud の構成から取り込む** は、手元の PC の構成ファイル
（`~/.config/gcloud/configurations/config_<名前>`。複数を同時に選べます。1 つ貼り付けるときは名前も入れます）を読みます。
ファイルはこの画面の中で読むだけで送信されず、チェックを入れたプロファイルの項目だけが保存されます。プレビューは
すべてのファイルを**作成**・**登録済み**・**取り込めません**（理由つき）に分けて並べ、ラベル（既定は構成名）は取り込む前に変えられます。

- **引き継ぐもの**：`core/project`・`core/account`・`billing/quota_project`・`compute/region`・`compute/zone`、
  そして 1 つだけの `auth/impersonate_service_account`。追加フォームと同じ検証をかけます。
- **理由をつけて断るもの**：project の無い構成、`core/account` がサービスアカウントのもの（鍵なしではログインできません。
  Google アカウントでログインしてサービスアカウントを権限借用してください）、サービスアカウントを並べたもの（委任チェーン）、
  認証情報ファイル・アクセストークンファイル・独自の OAuth クライアントなど `auth/` の他の設定、プロキシや API エンドポイントの設定、
  universe domain や独自 CA ファイル。これらを省いて作ると、手元の構成とは別の相手に向くプロファイルになるためです。
- **読まない・表示しないもの**：gcloud の認証情報、アプリケーションのデフォルト認証情報、鍵ファイル、構成に書かれたパスや
  トークンファイル。理由には設定名と行番号だけを出し、値は出しません。
- 同じラベルがすでに同じ内容で登録されていれば**登録済み**、内容が違えば別のラベルを求めます。現在のプロファイルを読めないときは
  何も作りません。
- 取り込んでもログインはされません。新しいプロファイルごとに**ログイン**を使ってください。

### プロファイルとしてコマンドを実行する

```sh
af-gcloud-exec --list
af-gcloud-exec --profile <name> --project <project-id> -- gcloud compute instances list
af-gcloud-exec --profile <name> --project <project-id> -- terraform plan
af-gcloud-exec --profile <name> --project <project-id> -- kubectl get pods
```

- `--list` は各プロファイルの名前・プロジェクト・アカウント（最初のログインまでは「chosen at the first login」）・権限を
  借用するサービスアカウント・ラベルを表示し、使えないプロファイルとその理由も挙げます。名前だけでなく、プロジェクトと
  アカウントで選んでください。
- `--project` はプロファイルのプロジェクトと同じでなければならず、違えば断られます。Google のログインはプロジェクトに
  結び付かないので、これは「コマンドが既定でどこを向くか」についてあなたとプロファイルの考えが一致しているかの確認に
  とどまります。コマンド自身の `--project` や、Terraform の設定に書いたプロジェクトはそちらが優先されます。
- コマンドが受け取るのは、プロファイルの短命な**アクセストークン**だけです。gcloud のログインも、アプリケーションの
  既定認証情報も、マシン自身の Google の身元も渡りません。`af-gcloud-exec` は「profile … runs as <account> in
  project …; the token is valid for N more minutes」と表示します（`-q` で省けます）。トークンそのものは表示しません。
- トークンの寿命は、渡した時点の残りです。最短 10 分、最長でおよそ 1 時間です。コマンドの実行中は `af-gcloud-exec` が
  横で動き続け、トークンが切れる約 8 分前に**トークンファイルを更新**します。その後にコマンドが起動する `gcloud`、
  `bq`、GKE 認証プラグインのプロセスは新しいトークンを読むので、それらを呼び直すスクリプトは動き続けます。起動時に
  読んだトークンを持ち続けるプロセスは、そのトークンのままです。1 つの長く動く `gcloud`（SDK 587.0.0 はファイルを
  1 度だけ読みます）と、`GOOGLE_OAUTH_ACCESS_TOKEN` を 1 度だけ読むプログラム（**長い `terraform apply`**）は、
  そのトークンが切れると失敗します。`kubectl` の watch や接続中の通信は、プラグインの再実行と再接続に依存します
  （未計測）。そうした作業は短い実行に分けてください。
- トークンを更新できないとき（ログインが取り消された、ログインし直しが必要、権限、ネットワーク）は、`af-gcloud-exec` が
  その旨を表示し、トークンが切れるまで再試行を続け、切れたらコマンドを止めます（SIGTERM。終わらなければ 30 秒後に
  SIGKILL）。終了ステータスは、ログインし直しが必要なら 3、それ以外は 1 です。実行の開始時に Console へ尋ねられる
  実行だったなら、起動時と同じくログインの依頼が Console に出ます。`--login`、`--no-login`、ワークスペースの外では、
  端末で実行するコマンドがメッセージに出ます。Console で取り消された依頼は、取り消されたと表示します。
- `af-gcloud-exec` を止めると、起動したコマンドに SIGTERM が送られます（コマンドは無視できます）。`af-gcloud-exec` が
  強制終了されたときも同じです。コマンド自身が起動したプログラムには届きません。`af-gcloud-exec` が強制終了された場合、
  トークンファイルはトークンの期限が切れるまで残り、後の実行が消します。
- 実行はそれぞれ、`af-aws-exec` と同じようにセッションの会話に 1 行を残します。プロファイル、プロジェクト、
  アカウント（とその権限を借用するサービスアカウント）、プログラム名とコマンドの終了ステータス、または拒否された
  理由です。引数は決して入りません。設定 > Google Cloud の「最近の実行」には、全セッションの最近の実行が並びます。
- 最初の実行で、Google Cloud SDK（ピン留めした 1 つの版と GKE 認証プラグイン）をホームに入れます。ダウンロードは約 85 MB、
  ディスクは約 510 MB で、停止しても作り直しても残ります。その後は gcloud の各コマンドの初回だけ数秒遅くなります。入れた後は
  **ツールチェーン**タブのツールの版の表に gcloud が出ます。端末で素の `gcloud` を走らせると同じプログラムが動きますが、
  使うのは（あれば）自分のログインで、プロファイルのものではありません。
- `kubectl` を使うときは、クラスタの接続情報を一度プロファイル経由で取り
  （`af-gcloud-exec --profile <name> --project <project-id> -- gcloud container clusters get-credentials <cluster> --location <location>`）、
  `kubectl` も `af-gcloud-exec` 経由で走らせます。GKE 認証プラグインはトークンを gcloud に求め、gcloud がトークンを持つのは
  `af-gcloud-exec` の中だけだからです。

**トークンを使う道具。**

| 道具 | `af-gcloud-exec` 経由で |
|---|---|
| `gcloud`（`gcloud storage` を含む） | 使う |
| GKE クラスタへの `kubectl` | 使う（GKE 認証プラグイン経由） |
| Terraform の Google プロバイダ | 使う（割り当てプロジェクト付き。実行中のトークン更新は届かない） |
| `bq` | 使う。SDK に入っていますがパスは通っていません。`~/.local/share/agent-fleet/google-cloud-sdk/bin/bq` で走らせます |
| `gsutil` | **使わない**。トークンを無視します。自分の gsutil（boto）の設定が無ければログイン無しで要求を送るので、公開バケットは応答します。設定があれば、その設定にある身元で動くことがあります。`gcloud storage` を使ってください |
| Google のクライアントライブラリ（Go・Python・Node など） | プログラムがトークンを渡したときだけ |

クライアントライブラリで作ったプログラムは、既定の認証情報について「File … was not found」や「no such file or directory」
のようなエラーで止まります。これは意図したものです。そうしないと別の身元（自分の gcloud のログインや、マシンのもの）を
見つけてしまいます。プログラムはトークンを自分で受け取る必要があります。Python なら
`google.oauth2.credentials.Credentials(os.environ["GOOGLE_OAUTH_ACCESS_TOKEN"])`、Go なら
`option.WithTokenSource(oauth2.StaticTokenSource(&oauth2.Token{AccessToken: os.Getenv("GOOGLE_OAUTH_ACCESS_TOKEN")}))`
です（Go のライブラリは、`af-gcloud-exec` が `GOOGLE_CLOUD_QUOTA_PROJECT` に入れるプロファイルの割り当てプロジェクトを使います。
Python では `Credentials` に `quota_project_id=os.environ["GOOGLE_BILLING_PROJECT"]` を渡してください）。Node では、クライアントライブラリが使っているのと同じ版の `google-auth-library` から `OAuth2Client` を作ってください。
メジャー版の違うものはエラーにならずに受け取られ、ログインを何も送りません。エージェントは、コードをこのように変える前に
あなたに確認します。

### ログイン

**Console で。** **⚙設定 → Google Cloud** のプロファイルの各行に**ログイン**があります。ワークスペースがそのプロファイルの
ログインを持つと、行に **「<アカウント> でログイン済み」** と出て、ボタンは**再ログイン**に変わります。WS バーの
Google Cloud バッジにも同じボタンがあります（[下記](#ws-バーの-google-cloud-バッジ)）。ボタンを押すと、プロファイル・
プロジェクト・アカウントを示すログインの画面が開きますが、まだ何も始まりません。ログインはその画面で**ログイン**
（または**再ログイン**）を押したときに初めて始まり、そのログインはその画面にだけ表示されます。

1. **Google ログインを開く**を押します。Google のログインページが新しいタブで開きます（画面にはそのアドレスも出ます。
   必ず `accounts.google.com` のもので、ワークスペースはそれ以外を表示しません）。ログインします。プロファイルが
   アカウントを指定していればそのアカウントで、ほかのアカウントでのログインは断られます。
2. Google が**確認コード**を表示します。同じログインの画面の**確認コード**に貼り付け、**コードを送信**を押します。
   ログインでトークンが得られることをワークスペースが確かめると、画面に「ログインしました」と出ます。

**コードは、いまここで自分で始めたログインにだけ貼り付けてください。** コードが使えるのは、そのコードを出したページの
ログインだけで、Console がコードの欄を出すのも**ログイン**を押した画面だけです。ただし、誰がログインを始めたかを
証明するものはありません。ワークスペースの中のプログラムなら、エージェントも含めて誰でも始められます。ほかの誰かが
目の前に出した欄・端末・チャットのメッセージに、コードを貼り付けないでください。

ワークスペースがそのアカウントの使えるログインをすでに持っていれば、**ログイン**はログインのページ無しですぐ終わります。
**再ログイン**は保存済みのものを使い回さず、必ずログインし直させます。ログインが取り消されたと分かっているときに
使ってください（ワークスペースは、コマンドが断られるまでそれに気づけません）。別の画面や端末でもう一度**ログイン**を
押すと、先のログインは止まり、そのコードはもう使えません。15 分以内に終わらなかったログインは終わります。
**やり直す**で新しく始めます。

ログイン済みの行（設定でもバッジでも）の**ログアウト**は、そのプロファイルの Google アカウントについてワークスペースが
保存したログインを削除します。ログインはアカウントごとに 1 つなので、同じアカウントを使うプロファイルはすべて一緒に
ログアウトします。確認の画面で、削除の前にそれらの名前を示します。Google 側のサインインと、ほかのマシンの gcloud には
影響せず、コマンドがすでに受け取ったトークンは期限（最長 1 時間）まで有効です。それらのプロファイルのログインの画面で
コードを待っているログインは止まります。再び使うにはログインし直してください。確認からログアウトまでの間にプロファイルのアカウントが変わった（別のログインが
終わった）ときは、何もログアウトせず、Console がそう知らせます。

**エージェントのコマンドがログインを必要としたとき**は、Console で尋ねます。`af-gcloud-exec` は「Google Cloud login for
profile … requested in the Agent Fleet Console」と表示し、画面下部に **「エージェントが Google Cloud へのログインを待っています」**
のトーストが、プロファイル・プロジェクト・アカウント・依頼元のセッションとコマンド、依頼が取り下げられるまでのカウントダウンとともに出ます。トーストの**ログイン**でログインの
画面を開き、上のとおり続けます。Google が保存済みのログインを断った場合は画面にそう出て、ログインは最初からやり直しに
なります。エージェントのコマンドは 1 分半ほど（エージェントのセッション以外、たとえば shell のセッションのスクリプトからなら
数秒）待ち、ログインが済めば続きます。それまでに諦めていれば、ログインが Console で待っている旨を出して終了コード 3 で
終わり、済んだと伝えればエージェントがもう一度実行します。**閉じる**では依頼は残り、ほかのブラウザの Console にも出続けます。
**依頼を取り消す**は、そのログインをしないときに使います。依頼を取り下げ、コマンドは終了コード 3 で終わり、そのプロファイル
については 1 分ほど再び尋ねません。トーストを閉じても、そのタブで隠れるだけです。設定のプロファイルの行やバッジの
**ログイン**はいつでも使え、そこでログインすれば依頼も片付きます。

**ワークスペース内の端末では**、`af-gcloud-exec` はエージェントのコマンドと同じように Console に尋ね、最大 10 分、あなたが
そこでログインを終えるのを待ちます。Ctrl-C で待つのをやめると終了コード 3 で終わり、依頼は Console に残ります。`--login` を付ける
と（ワークスペースの外や、Console に尋ねられないときも）、その端末で自分で Google のログインを始めます。表示される URL を
ブラウザで開いてログインし、ページに出る確認コードを**その**端末に貼り付けます。ここでも決まりは同じで、貼り付けてよいのは
いま自分で始めたログインのコードだけです。Console に尋ねられないコマンド（`--no-login` を付けたとき、ワークスペースの外）は、
終了コード 3 と、自分の端末（シェルのセッション、または Claude Code ならプロンプトで `!` に続けて入力）で走らせるコマンドを
表示して終わります。

```sh
af-gcloud-exec --profile <name> --project <project-id> --login -- true
```

**Compute Engine の VM では。** Google Cloud の VM の上で直接動くワークスペース（`native` ランタイム）では、gcloud がまず
その VM で個人アカウントを使うかを尋ねます。Console のログインはこの問いにあなたの代わりに答えません。ログインの画面は
そう表示して終わるので、上の端末のコマンドでログインしてください。

**ログインが終わるとき。** Google は保存したログインを断ることがあります。取り消されたときや、組織が一定時間ごとの
ログインし直しを求めているとき（セッションの長さ）です。すると新しいトークンが要る次の実行が上と同じようにログインを
求め、そのログインは保存済みのものを使い回さずに本当にログインし直させます。ワークスペースはその終わりを**前もって
知らせられません**。その時刻はワークスペースが読めるどこにも記録されないからです。すでに渡したトークンの残りが 10 分を
切るまでは実行が動き続けるので、ログインを求められるのは終わりから最長でおよそ 50 分後になります。

### WS バーの Google Cloud バッジ

ワークスペースが動いていて Google Cloud のプロファイルが 1 つ以上あると、WS バーの AWS バッジの隣に Google のマークの
バッジが出ます。ログイン済みのプロファイルがちょうど 1 つならその名前を、それ以外は数を（「1/3」なら 3 つのうち 1 つが
ログイン済み）示します。何かがログイン済みなら緑、何も無ければ枠だけ、エージェントのコマンドがプロファイルのログインを
待っている間は琥珀色です。押すと一覧が開きます。各プロファイルの**ログイン済み**／**未ログイン**、名前・プロジェクト・
アカウント、エージェントが待っている行には **「このログインを待っているエージェントがあります」**、そして上のログインの
画面を開く**ログイン**／**再ログイン**、ログイン済みの行には**ログアウト**（上を参照）が並びます。既定のプロファイルはありません。ログイン済みのプロファイルはどれも同時に
使え、コマンドごとに `af-gcloud-exec --profile <名前>` で選びます。下の **Google Cloud の設定**で設定のタブが開きます。

**ログイン済み**は、そのプロファイルのアカウントの Google ログインがワークスペースに保存されている、という意味でしかありません。
ワークスペースはそれを Google に確かめず、Google に断られても消さないので、取り消されたログインは、コマンドがそれに
気づいた後も**ログイン済み**のままです。そのコマンドのログインの依頼が待っている間はバッジが琥珀色になりますが、依頼を
取り消すか依頼が期限（15 分）で消えると、ログインが使えないままでもバッジは緑に戻ります。**再ログイン**でログインし直すと
直ります。バッジは定期的には問い合わせません。ワークスペースが起動したとき、一覧を開いたとき、ログインの依頼が出たり
片付いたりしたとき、ログインの後、タブに戻ったとき、設定でプロファイルを変えた後に尋ねます。追加や削除したプロファイルは、
ワークスペースが変更を取り込んでから（5 分ほどで）バッジに反映されます。

### 止まったとき

| 表示 | 意味 |
|---|---|
| 終了コード 3、「the login was requested in the Agent Fleet Console and is waiting …」 | プロファイルにまだログインが無いか Google が保存済みのログインを断り、コマンドが待つのをやめました。トーストか設定からログインし、コマンドをもう一度走らせてもらいます。終了コード 3 は必ずログインのことです |
| 終了コード 3、「the login request was cancelled in the Agent Fleet Console」 | 依頼を取り消しました。ログインしたいなら設定からログインします |
| 終了コード 3、「Google Cloud login required … log in from a terminal with:」 | Console に尋ねられませんでした（`--no-login`、またはワークスペースの外）。表示されたコマンドを端末で走らせます |
| 「is for project X, not Y; --project must be the profile's project」 | このプロジェクトには違うプロファイルです。`--list` を確かめてください |
| 「no Google Cloud profile …」または「not exported: …」 | その名前は使えるプロファイルにありません。設定で追加するか直します |
| 「gcloud could not mint a token: …」 | ログインの問題ではありません。権限が無い（借用するサービスアカウントへの権限も含む）、API が有効でない、ネットワークのどれかで、メッセージに書いてあります |
| 「the token gcloud minted is valid for only …」 | gcloud が残り 10 分のトークンを出せませんでした。1 分ほどして、もう一度試してください |
| 「this deployment does not export Google Cloud profiles」 | この配備は Google Cloud のプロファイルを提供していません |
| 「could not renew the token of profile … trying again until it ends in N minutes」 | 使っているトークンをまだ更新できていません。実行は更新を試し続け、先にトークンが切れたらコマンドを止めます |
| 「the profile's login is now X, not Y, which the command started as; run it again」 | 実行中に、そのプロファイルが別のアカウントでログインし直されました。コマンドをもう一度走らせます |
| 「the profile changed in Settings while this run started; run it again」 | もう一度走らせます。アカウントやプロジェクトが変わっていれば `--list` で確かめてください |
| 「waiting for another af-gcloud-exec or a profile sync …」 | 端末でのログインか別の実行が、ワークスペースの gcloud の保存場所を使っています。終われば続きます |

**保証しないこと。** コマンドはあなたとして動くので、自分の gcloud のディレクトリを含めてホームを読めます。`af-gcloud-exec`
は、Google の認証情報を探す標準の方法（gcloud とクライアントライブラリのもの）が、渡したトークン以外を見つけないように
するだけで、ファイルを読めなくするわけではありません。自分の設定を持つ `gsutil` のように、別の場所を探す道具は対象外です。
Google Cloud の VM の上で直接動くワークスペースでは、その標準の方法を無視するプログラムが、VM 自身の身元に届く可能性が
あります。Kubernetes の Pod でも同じです。ワークスペースは
`AWS_EC2_METADATA_DISABLED=true` で起動しますが、この変数はクラスタのメタデータサーバ（ノードのサービスアカウント、GKE では
Workload Identity）を塞ぎません。標準の方法を無視するプログラムは、管理者がクラスタのネットワークで経路を塞がない限り、
その身元に届く可能性があります。
