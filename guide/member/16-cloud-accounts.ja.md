# 16. クラウドのアカウント — AWS プロファイル・SSM ホスト・Google Cloud

[English](16-cloud-accounts.md) | 日本語

## 社内の別ホストに入る（SSM）

自社 AWS の EC2 に、AWS SSM Session Manager でログインできます。設定は **⚙設定 →
「AWS プロファイル/SSM」タブ**で、**2 層**に分かれています。

- **プロファイル（共通設定）**：アクセスポータル（IAM Identity Center）とアカウント／ロール。複数のホストで使い回す SSO の設定のまとまりです。まずこれを 1 つ作ります。
- **SSM ホスト（個別）**：ログイン先の別名 → インスタンス ID。認証はプロファイルを選ぶだけです。

プロファイルの各行には**ログイン**があり、Console から離れずにそのプロファイルで IAM Identity Center にログインできます。
押すとログインの画面が開き、ログインのコードはそこで**ログイン**を押したときに初めて作られ、その画面にだけ表示されます。
このログインは、そのプロファイルの SSM セッションと `af-aws-exec` に効きます。アカウントとロールの両方が無いプロファイルと、
別の表示名と同じ名前になるプロファイル（後述）では押せません。
表示名の横のバッジはログインの状態を示します：**ログイン済み**、**使うときに更新**（アクセストークンは期限切れで、
ポータルのセッションが続いていれば次に使うときに更新される）、**未ログイン**。残り時間は出しません。ワークスペースに
分かるのはアクセストークンの期限（1 時間ほど）だけで、ポータルのセッションがいつ終わるかは分からないためです。

**ログインが切れる前の警告は、更新できないログインだけです。** 設定からの通常のログインは、ポータルのセッションが終わるまで
使うたびに更新され、その終わりはワークスペースが読める場所に記録されません。そのため**前もっては知らせません**。ポータルが
終わらせると、次のコマンドが後述のとおりログインを依頼します。キャッシュに更新の手段が無い（リフレッシュトークンが無い、または
ログイン用クライアントの登録が期限切れ）ときだけ終わりが分かり、Console がプロファイルごとに 1 回、終わりの 10〜15 分ほど前に
「AWS のログインが … に切れます」のトースト（と通知）を、残り時間のカウントダウン付きで出します。**ログイン**で同じログイン画面が開きます。ログインし直すと消え、
閉じるとそのタブではその期限について出なくなります。管理ブロックに入っていないプロファイル（`af-aws-exec --list` を参照）は
知らせません。

**1 つのプロファイルからログアウトする。** ログイン中（または**使うときに更新**）の行には**ログアウト**があります。ここと、
WS バーの AWS バッジのポップオーバーの両方にあります。確認すると、ワークスペースはそのプロファイルのログインを AWS 側でも
終わらせ、キャッシュされたログインとロールの認証情報を削除します。これに従わないプロファイルはログインしたままです。ロールを引き受けるプロファイル（後述）がこのプロファイルに従っているときは、
確認の画面が先にその名前を示し、一緒にサインアウトされます。実行中のコマンドが
すでに受け取った認証情報は期限まで有効です（AWS には取り消す手段がありません）。問題になるならそのコマンドを止めてください。
アクセストークンが期限切れの行（**使うときに更新**）は、ログアウトが AWS に届くよう先に更新します。AWS がログインはもう
終わっていると答えたときは、通常のログアウトになります。AWS に届かない・それ以外の理由で更新に失敗した・ログアウトそのものを
断られた・ログインに更新の手段が無い、のいずれかのときも、ワークスペースからはログアウトし、Console がその旨を伝えます。このとき AWS 側のログインは期限まで
有効なままの可能性があります。この目的で `aws sso logout` は使わないでください。`--profile` に関係なく全プロファイルを
一度にログアウトさせます。

プロファイルとホストの各行には**編集**があり、同じフォームを入力済みで開いてその場で保存します。削除して登録し直すのではなく
編集を使ってください。ホストはプロファイルを内部 ID で参照するので、登録し直したプロファイルは別物になります。
ホストが使っているプロファイルは削除できず、画面がそのホストを挙げます。先にホストを編集して別のプロファイルを選ぶか、
ホストを削除してください。この制限より前にプロファイルを失ったホスト（行にその旨が出ます）も同じく、編集して選び直します。プロファイルのワークスペースでの名前は
表示名から作られ、ログインはその名前に付きます。表示名や start URL・SSO リージョンを変えたらログインし直しが要り、フォームが
そう警告し、その行から改めてログインするまで行に**要再ログイン**と出ます。ワークスペースの `~/.aws/config` には 5 分以内か、**ログイン**を押した時点で反映されます。開いているセッションは
古い設定のままです。

**AWS の秘密情報は Agent Fleet に保存されません。** ログインはセッション開始時に、
端末に出る **`aws sso login`** の URL をブラウザで承認する device-code 方式で、
短命の資格情報はワークスペース内にだけ保持されます。

登録後は、ワークスペース操作バーの **「はじめる」→「SSM — 別ホストへログイン」** で
**ログイン先ホスト**を選んで接続します。
認証が必要なら `aws sso login` の URL が確認画面に出るので、別タブで承認してください
（身に覚えのないコード／URL は入力しないこと）。

### ~/.aws/config からプロファイルを取り込む

手元の PC から移るときは、プロファイル一覧の下の **「~/.aws/config から取り込む」** で、そのファイルを読んで
プロファイルを作れます（手で打ち直す必要はありません）。ファイルを選ぶか中身を貼り付けます。読むのは
**このブラウザの中だけ**で、送るのはチェックしたプロファイルの設定項目だけです（フォームの保存と同じ経路）。
ワークスペースが止まっていても使えます。

プレビューには、ファイルにあるすべてのプロファイルと、その扱いが並びます。

- **作成（SSO）**：ポータル・SSO リージョン・アカウント・ロールがそろったプロファイル（`sso_session` 形式でも、
  古い `sso_*` を直接書く形式でも）。
- **作成（ロールの引き受け）**：`role_arn` + `source_profile` で、引き受け元が上の SSO プロファイルのもの。
  引き受け元はファイル内でも、Settings に登録済みのものでもかまいません（ポータル・SSO リージョン・アカウント・
  ロールが同じときだけ）。引き受け元がファイルにないときは、使う Settings のプロファイルを選びます。その行には
  「あなたが選んだ接続先で、手元と同じとは確かめていない」と出ます。
- **同じものが登録済み**：Settings に同じプロファイルがあります。何も変えません。
- **取り込めません**（理由つき）：アクセスキー、`credential_process`、`mfa_serial`、`credential_source`、
  `web_identity_token_file`、`login_session`、認証の方法が 2 つ以上（`[DEFAULT]` から継いだキーを含む）、
  ロールからさらにロールを引き受けるもの、アカウントとロールがそろわない SSO、`sso-session` と値が食い違うキーがあるもの
  （AWS CLI も断ります）、Settings が持てない値、
  名前が使用済み・ほかと同じ AWS プロファイル名になるもの。

行ごとにチェックを外す、表示名を変える（`[default]` はこれが必要です。`default` は Settings の名前にできません）、
ロールのセッション時間（900〜3600 秒）を直す、ができます。引き受け元の名前を変えても、それを使うロールは
付いてきます。

- **秘密は取り込みません。** テキストにアクセスキーがあるとそう表示します。そのテキストはほかに貼らないで
  ください。読むのは `~/.aws/config` だけで、`~/.aws/credentials` は求めません。
- AWS CLI が読めないファイル（同じセクション・キーが 2 回、セクションより前のキー）は、行番号つきで断ります。
- **Settings のプロファイルはそれぞれ別にログインします。** 手元で 1 つの `sso-session` を共有していた 20 個は、
  ここでは 20 回のログインになります。プレビューに回数が出ます（ログインの共有は #3014）。
- リージョンを書いていないプロファイルは SSO リージョン（ロールは引き受け元のもの）を使います。手元では環境変数で
  決まっていたかもしれません。プレビューに各行のリージョンが出ます。
- 同じ選び方でもう一度取り込んでも、何も増えません。途中で止まったときは、もう一度ファイルを読めば、作成済みの
  ものは「登録済み」と出て、残りを取り込めます。

### ~/.ssh/config から SSM ホストを取り込む

**「~/.ssh/config から取り込む」**（プロファイルの取り込みの隣）は、ssh の設定を読んで SSM ホストを作ります。
先に読んでください：**接続方式が変わります。** ssh の設定では、これらのエントリは
`ProxyCommand aws ssm start-session … --document-name AWS-StartSSHSession` で SSM のトンネル越しに SSH セッション
（ユーザー・鍵・ポート）を開きます。Agent Fleet のホストは、インスタンス上で `aws ssm start-session` のシェルを
開き、SSH のユーザー・鍵・ポートはありません。`User`・`IdentityFile`・`Port`・転送などの設定は引き継がれず、
プレビューにその名前が出ます。

ファイルはブラウザの中だけで読み、**`ProxyCommand` は実行も表示も送信も保持もしません。** 保存されるのは、チェックした
行の別名・インスタンス ID・AWS プロファイル・リージョンだけで、ホスト追加フォームと同じ保存を使います。

読むのは決まった 1 つの形だけです。**1 つの具体的な名前の `Host`** で、`ProxyCommand` が `aws ssm start-session`
（`sh -c "…"` で包んだ形も可）であり、次のオプションだけを各 1 回まで使うもの：`--target`（インスタンス ID
`i-…` / `mi-…`、または `%h`。`%h` はそのエントリの `HostName`、`HostName` がなければ `Host` の名前そのもので、
インスタンス ID であること）、`--document-name AWS-StartSSHSession`、`--parameters portNumber=%p`（または
`portNumber=22`）、`--profile`、`--region`。それ以外は理由つきで**取り込めません**：他のドキュメント（ポートフォワード・
独自）、他のオプション、他の `%` トークン、シェルの構文（`;`・`|`・`$(…)`・単語全体を囲む以外の引用符）、`ProxyJump`、
ワイルドカード（`*`・`?`）、否定（`!`）、`Match`、`Include`。

OpenSSH は、名前に当てはまる全ブロックを通して、各キーワードの**最初の**値を使うので、ブロックは互いに独立していません。
`ProxyCommand`（`%h` が要るときは `HostName` も）が最初の値で、かつ**そのホスト名を直接書いたブロック**から来ている
ときだけ取り込めます。`Host *` や前にあるパターンから受け継ぐ値、これらのキーワードを設定する `Match` や
`Include`（その中身は貼り付けた文面にありません）より後ろの値は拒否します。取り込みたいときは、Include 先の内容を
上に貼り、そのホストのエントリを全部書いてください。

**AWS プロファイル**は、AWS 名がコマンドの `--profile` と同じ Settings のプロファイルです。`--profile` がない、または
一致するものがないときは、行の中でプロファイルを選びます。すでにある行（別名とインスタンスが同じ）は**登録済み**と
表示し、別のインスタンスで使われている別名は拒否します。「取り込む」を押すまで何も作らず、今のホスト一覧を読めなければ何も送りません。

### ~/.aws/config として書き出す

**「~/.aws/config として書き出す」**（取り込みの隣）は、Settings のプロファイルから AWS 設定ファイルのテキストを作り、
`agent-fleet-aws-profiles.aws-config-fragment.txt` としてダウンロードします。作成はブラウザの中で、何も送信しません。
**これは手元の `~/.aws/config` に手で取り込むための断片で、置き換え用ではありません。** 入るのは Agent Fleet が
表現できるもの（SSO プロファイルと、それぞれ独自の `sso-session`、そこから引き受けるロール）だけなので、これで
自分のファイルを置き換えると、アクセスキー・MFA・`credential_process` のプロファイルや既存の `[default]` が消えます。
ファイル名を `config` にしないのもそのためです。

ダイアログには、**除外したプロファイル**が理由つきで並びます：

- `default` という名前（予約名）；
- 表示名が同じ AWS プロファイル名になる 2 つ（`prod app` / `prod-app`）：どちらかの名前を変えるまで両方を除外します
  （ワークスペースの `~/.aws/config` と同じ扱い）；
- アカウントとロールの両方がない SSO プロファイル；
- AWS 設定に書けない値（書き出す前に、ワークスペースと同じ規則ですべての値を確かめるので、保存された値が別の設定や
  セクションを紛れ込ませることはありません）；
- `sso-session` が別のサインイン・別のプロファイル・別のポータルとも共有になるプロファイル（同じ名前のサインインと
  プロファイル、ポータルが食い違うメンバーなど）：名前かポータルがそろうまで、該当するものをすべて除外します；
- 引き受け元が除外された・存在しない・SSO プロファイルでないロール。

SSO プロファイルはそれぞれ独自の `sso-session`（`af-<名前>`）で書かれるため、手元でもプロファイルごとにログインが必要です。
共有サインイン（後述）のメンバーは 1 つの `[sso-session af-<サインイン名>]` を共有するので、手元でも 1 回のログインで全員分になります。

### 共有サインイン：複数のプロファイルで 1 回のログイン

アカウントやロールが違う複数のプロファイルでも、IAM Identity Center のポータルは **1 つ** ということがよくあります（手元のマシンで 1 つの `[sso-session]` を共有しているのと同じ状態です）。それらを 1 つの **共有サインイン** に入れると、ワークスペースはプロファイルごとではなく、全員分で **1 回** だけそのポータルにログインします。

**作成と参加。** プロファイルのフォームの **サインイン** で選びます。

| 選択 | 動作 |
|---|---|
| 専用のサインイン（既定） | これまでどおりです。プロファイルは専用のログインと、専用の start URL・SSO リージョンを持ちます。 |
| 自分のサインインのどれか | そのサインインに参加します。start URL と SSO リージョンはサインインのものを使い、入力し直しません。 |
| 新しい共有サインイン… | 入力した名前と start URL・SSO リージョンでサインインを作り、プロファイルをそこに入れます。 |

サインイン名は英数字と `.` `@` `-` で 1〜61 文字です。ワークスペースではそのログインを `af-<名前>` と呼びます。保存は次の理由で断られることがあり、そのときは理由が表示されます。

- **別の start URL か SSO リージョン**：選んだサインインは別のポータルを使っています。サインインに入ったプロファイルは常にサインインのポータルを使います。本当にポータルが変わったなら、サインインの見出しで変更してください。
- **名前が使われている**：専用ログインを持つ別のプロファイルがその名前です。別のサインイン名にするか、そのプロファイルの名前を変えてください。
- **同じ名前のサインインがすでにある**：一覧から選ぶと参加できます。

**一覧。** サインインのプロファイルは 1 つの見出しの下にまとめて表示されます。見出しにはサインイン名とポータルがあり、ログイン状態・**ログイン**・**ログアウト** も見出しに 1 つずつだけ並びます。メンバーの行にはアカウント・ロール・リージョンが残り、ログインボタンはありません。専用のサインインのプロファイルは、これまでどおり自分の行を持ちます。

**ログアウト** すると（見出しから、または WS バーの AWS バッジのメンバーから）、**すべての** メンバーがサインアウトします。メンバーのどれかに従うロール引き受けプロファイルも同じです。確認ダイアログが先にそれらを一覧で示します。

**サインインの改名・ポータルの変更。** 見出しの **編集** でどちらも変更できます。どちらを変えてもすべてのメンバーがサインアウトします。改名するとログインの名前が変わりますし、古いポータルのトークンが新しいポータルに使われることはないからです。確認ダイアログがそのことを説明してメンバーを示し、変更後のメンバーには **要再ログイン** が表示されます。

**まとめるときにログインを残す。** 今ログインしているプロファイルの名前をサインインの名前にすると、そのプロファイルのログインがサインインのものになり、誰もログインし直さずに済みます。ほかの名前にした場合、サインインはサインアウトした状態で始まるので、1 回ログインが必要です。サインインを抜ける（**専用のサインイン** を選ぶ）と、プロファイルは再び専用のログインになるので、やはりログインが必要です。

制限：

- 自動でまとめられることはありません。同じポータルでもサインインに入っていない 2 つのプロファイルや、別々のサインインに入ったプロファイルは、それぞれ別にログインします。
- メンバーの SSM ホストで **ログインし直す** を使うと共有のログインが消え、すべてのメンバーがサインアウトします。
- 自分の `~/.aws/config` に `[sso-session af-<サインイン名>]` があると、自分で定義したプロファイル名の場合と同じく、そのサインインのメンバーは全員書き出されません（理由は `af-aws-exec --list` で確認できます）。
- キャッシュされたログインは、作られたときのサインイン（またはプロファイル）とポータルに結び付きます。別の持ち主や別のポータル向けに作られたログインは使われません。ワークスペースはそれを脇に移し、それを使って取得したロールの認証情報を削除して、新しいログインを求めます。
- サインインからログアウトすると、メンバーが参加する前に持っていた専用のログインも削除されます。ただし、それが確かにそのメンバーのもので、ほかに同じ名前を使うものがない場合に限ります。
- `~/.aws/config` からの取り込みは、まだプロファイルをサインインに入れません。取り込んだあと、各プロファイルのフォームで参加させてください。

### プロファイルの種類：別のプロファイルからロールを引き受ける

アカウントへのアクセスが、IAM Identity Center のサインインを信頼するロール経由なら、`~/.aws/credentials` に長期キーを
置く必要はありません。設定 > AWS プロファイル/SSM で、種類 **「別のプロファイルからロールを引き受ける」** のプロファイルを
追加します。

| 項目 | 意味 |
|---|---|
| 元のプロファイル（`sourceProfileId`） | ロールを引き受けるサインインを持つ SSO プロファイル。必須。SSO プロファイルに限り、別の「ロールを引き受ける」プロファイルは選べません。 |
| ロール ARN（`roleArn`） | `arn:aws:iam::<アカウント>:role/<名前>`。必須。プロファイルのアカウントはここから決まります。 |
| 外部 ID（`externalId`）・セッション名（`sessionName`）・有効期間（`durationSeconds`、900〜3600。ロールチェーンは AWS の制限で 1 時間まで） | 任意の AssumeRole パラメータ。 |
| 既定のリージョン（`region`） | 任意。空なら元のプロファイルのリージョン。 |

秘密情報は保存も書き出しもされません。プロファイルは `~/.aws/config` の管理ブロックに
`role_arn` + `source_profile = <元のプロファイル名>` として書き出されるので、`aws --profile <名前>`・SDK・`af-aws-exec` が
ほかの設定済みプロファイルと同じように使え、SSM のホストからも選べます。

- 対象ロールの信頼ポリシーが、元のアカウントにあるあなたの Identity Center ロール（`AWSReservedSSO_<権限セット>_*`）を
  許可している必要があります。
- 自分のサインインはありません。行の **ログイン** は元のプロファイルへのサインインで、状態も元のプロファイルに従います。
  行の **ログアウト** は元のプロファイルのログインを終わらせます（連鎖するプロファイルに自分のログインはありません）。
  元のプロファイルとそれに従うすべてのプロファイルがサインアウトされ、確認の画面が先にそれらの名前を示します。確認しなければ何もログアウトしません。WS バーの AWS バッジのポップオーバーでは
  **「<元のプロファイル> のログインに従います」** と出て、元のプロファイルが無いか書き出されていないときは **元プロファイルなし** と
  出ます。バッジはログインを数えるので、ログイン中の数（「1/3」など）に連鎖するプロファイルは入りません。
  `af-aws-exec --profile <名前> -- <コマンド>` は `--account` が要りません（ロールのアカウントと、AWS が返すアカウントを
  照合します）。元のログインが無いときは、元のプロファイルの名前で Console に依頼します。
- 元のプロファイルが書き出されている間だけ書き出されます。元の名前を自分の `~/.aws` で定義している、または `[DEFAULT]` の
  行が壊す場合は、連鎖するプロファイルも書き出されず（理由は `af-aws-exec --list`）、自分のキーから連鎖が始まることはありません。
- ほかのプロファイルが元にしている間は、そのプロファイルを削除することも、「ロールを引き受ける」種類に変えることもできません。
- 設定の書き出しでは、元のプロファイルをラベルで記録します。取り込みでは、ラベルが完全に同じで、サインイン（開始 URL・
  SSO リージョン・アカウント・ロール）も同じプロファイルが既にあるか同じファイルにあるときだけ追加し、それ以外は飛ばします。

### プロファイルを端末・SDK・ビルドツールから使う

登録したプロファイルは **`~/.aws/config`** にも書き出されます。`aws --profile <名前>`・AWS SDK・ビルドツール
（Gradle、Maven、CDK、Terraform など）から、設定を写し直さずに名前で選べます。`AWS_PROFILE=<名前>` よりも
`--profile`（またはツール自身のプロファイル設定）を使ってください。シェルに設定済みのキー（`AWS_ACCESS_KEY_ID` など）は
`AWS_PROFILE` より優先されるので、コマンドが誰として動くかを固定できません。

- **名前**はプロファイルのラベルの、英数字と `._@-` 以外の文字を `-` に置き換えたものです（ラベル `prod app`
  → プロファイル `prod-app`）。`af-aws-exec --list` で、名前ごとにアカウント・ロール・ラベルを一覧できます。
  名前だけでなく、それらを見て選んでください。
- 2 つのラベルが同じ名前になるとき（`prod app` と `prod-app`）は、**どちらも書き出しません**（`--list` に出ます）。
  どちらを選んでも別のアカウントかもしれないためです。設定画面でどちらかの名前を変えてください。
- ファイル末尾の **管理ブロック**（`# agent-fleet` で始まる 2 行の目印の間）に入ります。編集は設定画面で行って
  ください。ブロックの中は（`aws configure set` で書き込んだ分も）書き直されます。ブロックの外はあなたのもので、
  そのまま残ります。書き出すのは**アカウントとロール**の両方があるプロファイルだけです。両方無いと
  `aws --profile <名前>` は SSO を使わず、ワークスペース自身のロールで気づかないうちに動き、片方だけだと失敗するためです。
  どちらが無いかは `--list` に出ます。`~/.aws/config` の `[DEFAULT]` の行がプロファイルを壊す場合（違うリージョン、すべてのプロファイルに
  そのロールを引き受けさせる `role_arn` など）、そのプロファイルは書き出さず、`af-aws-exec --list` がその行を示します。
  同じ名前のプロファイルを自分で定義済みなら（`~/.aws/config` でも `~/.aws/credentials` でも）、
  **あなたの定義が使われ**、こちらからは書き出しません。ラベルが `default` のプロファイルは書き出しません。
  プロファイルを指定しないすべてのコマンドの身元が変わってしまうためです。
- 変更は **5 分ほどで**、または次のワークスペース起動時に反映されます。`af-aws-exec` を実行するとその場で反映されます。

**端末からのログイン。** Console ではプロファイルの行の**ログイン**（前述）で同じことができます。端末では、素の `aws sso login` はワークスペース内の `127.0.0.1` へ戻す方式で、あなたのブラウザからは
届きません。device-code 方式を使ってください。

```sh
aws sso login --profile <名前> --use-device-code --no-browser
```

表示された URL を開いてコードを承認します（承認するのは、いま自分で始めたコードだけ）。ログインは同じプロファイルの
SSM セッションと共有されるので、1 回で両方に効きます。

**コマンドを 1 つ、あなたとして実行する: `af-aws-exec`。** ワークスペースは自分自身の AWS の身元（**ワークロード
ロール**）を持つことがあり、その下のマシンも身元を持つことがあります。コンテナのワークスペース（docker または
AWS ECS、Agent Fleet 0.26.0 以降）では、セッションとターミナルにはどちらも渡りません。Agent が起動するもの
すべてからワークスペースの資格情報の環境変数を外し、SDK のインスタンスメタデータ参照を止めます
（`AWS_EC2_METADATA_DISABLED=true`）。この変数を無視するツールを止めるのはホスト側のネットワーク遮断で、
管理者が 0.26.0 への移行を終えて初めて効きます（[運用ガイド 04](../operate/04-secure.ja.md)の「その他の運用上の統制」）。
あなた自身のマシンで直接動くワークスペースはそのままです。そこのインスタンスロールはあなたのマシンのもので、SDK は
引き続きそれを見つけます。そのため、プロファイルをまったく指定しないコマンド（素の `aws …`、SDK の既定の資格情報チェーン、
プロファイル設定の無いビルドツール）は、ワークスペースの身元で動く代わりに「Unable to locate credentials」（または
その SDK の言い回し）で止まります（プロファイルを指定していれば、名前の打ち間違いやログイン切れはそれぞれのエラーに
なります）。管理者がワークスペース自身のタスクロール（AWS ECS）を再び使えるようにすることもでき、その場合
そうしたコマンドはそのロールで、別のアカウントで気づかないうちに動きます。どちらの場合も、「Unable to locate credentials」は
「プロファイルを指定する」という意味で、「資格情報を設定する」という意味ではありません。`aws configure`、`aws login`（CLI 自身の案内）や
`~/.aws` の `[default]` セクションのキーで対処せず、資格情報を別の所から探さないでください。デプロイ、書き込み、
その他アカウントが重要な操作は、資格情報を明示して渡してください。

```sh
af-aws-exec --profile <名前> -- ./gradlew deploy
af-aws-exec --profile <名前> -- npx cdk deploy
```

**例: S3 アップロードのプラグインを使うビルドツール。** AWS プラグイン（S3 へのアップロードタスクなど）で組んだ
Gradle のデプロイタスクは、ビルドスクリプトにプロファイルが無ければ SDK の既定のチェーンに尋ねます。環境変数、
JVM のシステムプロパティ、`~/.aws` の `default` プロファイル、そしてコンテナの資格情報とインスタンスメタデータの
順です。そのためセッションで `./gradlew uploadArtifact` を実行すると、成果物をワークスペースのロールでアップロード
する代わりに「Unable to load AWS credentials from any provider in the chain」で止まります。アカウントを指定して、
あなたとして実行してください。

```sh
af-aws-exec --profile <名前> --account <ID> --region <リージョン> -- ./gradlew uploadArtifact
```

プラグインはチェーンの最初に見る環境変数でプロファイルの短命な資格情報を見つけ、「running as」の行で誰が
アップロードするかが分かります。ビルドスクリプト自身がプロファイルを指定している（`profileName = "prod"` など）
ときは、下の「could not be found」を見てください。

**実行はすべてセッションの会話に出ます。** `af-aws-exec` の実行はそれぞれ、実行したセッションの会話の、開始した
時刻の位置に 1 行を残します。中身は、プロファイル、実行に使ったアカウントとロール、リージョン、コマンド
（`aws s3 ls`、またはプログラム名だけ）、または af-aws-exec が実行を拒否した理由です。コマンドがどう終わったかは
出ません。af-aws-exec はそのコマンド自身になるので、終了ステータスはシェルが受け取るものがそのまま正です。設定 > AWS プロファイル/SSM の「最近の実行」には、
全セッションの最近の実行が並びます。行にコマンドの引数は決して入りません（秘密が入りうるため）。何が動いたかを
見るためのもので、監査ではありません。セッションは実行が申告したもので、コマンド側から変えられます。素の `aws`
で実行したコマンドは行を残しません。

**使用前に確認。** 設定 > AWS プロファイル/SSM のプロファイルのフォームで「使用前に確認」をオンにできます。すると
`af-aws-exec` は、各セッションでそのプロファイルを初めて使う前、資格情報を取り出す前に確認を求めます。セッションの
会話にカード（その会話が画面にないときはトースト）が出て、セッション、プロファイル、そのアカウントとロールを示し、
**このセッションで許可** と **拒否** を選べます。許可は 8 時間かセッションの終了まで続き、今の設定のプロファイルに
対してだけ有効です。アカウント、ロール、ポータルを編集すると、もう一度確認を求めます。拒否したとき、または時間内に
答えなかったときは、コマンドは実行されず、af-aws-exec は 4 で終わります。答えていない依頼は 15 分残るので、後から
許可すれば、エージェントの次の実行は通ります。このように設定したプロファイルから連鎖するロールも、そのプロファイルの
確認を求めます。このプロファイルは `~/.aws/config` に書かれないので、素の `aws --profile` では使えません。
`af-aws-exec` で実行してください。

できないこと: 間違いや気付かない使用を防ぐもので、わざと回り込もうとするエージェントは止めません。エージェントは
ワークスペース自身の仕組みで依頼に答えられ（そのときの会話の行には「Console を通さずに承認」と出ます）、同じ
サインインのほかのプロファイルが保っているログインを使い回せます。専用のサインインに置き、使い終わったらログアウト
するプロファイルは、毎回デバイスコードの承認が要ります。

**読み取りだけの調べものは `aws --profile` で。** デプロイ、書き込み、ビルドツール、SDK のプログラム、スクリプトは
引き続き `af-aws-exec` で実行します。アカウントを確かめ（`--account`）、SSO プロファイルを読めない SDK のツール
（Gradle/Maven のプラグインに多い AWS SDK for Java v1 などの古い SDK）にも短命な資格情報を渡し、ログインが無ければ
Console であなたに尋ね、ツールによって別の身元を指す名前を断り、`--region` でリージョンを固定し、エンドポイントの
上書きを外すからです。AWS CLI そのものでのちょっとした調べもの（`describe-*`、`list-*`、`s3 ls`）は、設定画面の
プロファイルを直接指定してかまいません。ただし、次の確認が `isolated` と出るシェルの中だけです。確認は 1 語だけを
出力し、環境の中身もエラーの内容も出しません。

```sh
if err=$(env -u AWS_PROFILE -u AWS_DEFAULT_PROFILE AWS_IGNORE_CONFIGURED_ENDPOINT_URLS=true \
           aws sts get-caller-identity 2>&1 >/dev/null); then st=0; else st=$?; fi
err=${err#"${err%%[![:space:]]*}"}
if [ "$st" = 253 ] && [ "$(printenv AWS_EC2_METADATA_DISABLED)" = true ] && [ "${AF_WS_WORKLOAD_AWS:-}" != 1 ] \
   && [ -z "$(env | cut -d= -f1 | grep -E '^AWS_(CONTAINER_|CONFIG_FILE$|SHARED_CREDENTIALS_FILE$|ENDPOINT_URL)')" ] \
   && case $err in "Unable to locate credentials"* | \
        "aws: [ERROR]: An error occurred (NoCredentials): Unable to locate credentials"*) true ;; *) false ;; esac
then echo isolated; else echo not-isolated; fi; unset err st
```

`isolated` は、`AWS_EC2_METADATA_DISABLED=true` が export されていて CLI がインスタンスメタデータに尋ねず、環境にワークロードの資格情報も AWS の設定ファイルや
エンドポイントの上書きも無く、CLI の既定のチェーン（`AWS_PROFILE` を外し、設定済みのエンドポイントを無視して）が CLI 自身の「資格情報が無い」
エラー（終了コード 253）で終わった、という意味です。そのため打ち間違えたプロファイルやログイン切れのプロファイルは、別のアカウントについて答える
代わりに失敗します。それ以外（あなた自身の既定の資格情報、期限切れのセッション、失敗した `credential_process`、ネットワークのエラー）はすべて
`not-isolated` で、あなた自身のマシンで動くワークスペース、タスクロールを戻している配備、アップグレード後にまだ
起動し直していないワークスペースも、ふつうはそう出ます。この確認が見るのはこのシェルが CLI に渡すものだけで、
実行方式やバージョン、ホストのネットワーク遮断までは保証しません。`not-isolated` なら調べものも `af-aws-exec` で
実行してください。`isolated` でも、直接の調べものには次のすべてが要り、欠ければ `af-aws-exec` で実行します。

- プロファイルは `af-aws-exec --list` が書き出し済みと示すもので、名前だけでなくアカウントとロールで選びます。
  どのアカウントか分からなければ、先に確かめてください。`--list` が「from an earlier sync; not checked against
  Settings now」と警告するときは何も確かめられていないので、`af-aws-exec` で。`--list` に出ないもの、書き出していないと示されるもの、
  自分で定義したもの（`role_arn`、`credential_process`）は `af-aws-exec` で。
- リージョンを指定し、設定済みのエンドポイントを無視させます:
  `AWS_IGNORE_CONFIGURED_ENDPOINT_URLS=true aws --profile <名前> --region <リージョン> ec2 describe-instances`
  （`--endpoint-url` は付けません）。シェルに古い `AWS_REGION` が残っているとプロファイルのリージョンより優先され、
  `~/.aws/config` の `endpoint_url`（エミュレーターの設定の残りなど）があると AWS 以外へ要求が送られます。
- 確認したのと同じシェルで実行します。
- SSO トークンのエラーはログインが無いという意味です。素の `aws --profile` は Console に尋ねないので、尋ねる
  `af-aws-exec` で実行し直してください。
- `af-aws-exec` が断ったプロファイルは、ここでも使えません。素の `--profile` は抜け道になりません。

ワークスペースのエージェントも同じ決まりに従います。

- プロファイルの**短命な**資格情報を、そのコマンド 1 つの環境変数にだけ渡します。`af-aws-exec` 自身は資格情報を
  どこにも書かず、表示するのは実行する身元（ARN）だけです（AWS CLI は従来どおり `~/.aws` に自分のログインと
  ロールのキャッシュを持ちます）。
- プロファイルには設定画面で**アカウントとロール**を入れておく必要があります。`role_arn`（空でも）か
  パスの入った `web_identity_token_file` も持つプロファイルは断ります。AWS CLI がその SSO ログインを使わなくなるためです。
  `source_profile`・`credential_source`・`credential_process`・静的キー（`~/.aws/config` でも `~/.aws/credentials`
  でも）、空の `web_identity_token_file`（`role_arn` と一緒でも）を持つプロファイルも断ります。AWS CLI は SSO を使いますが、他の SDK やツールはそちらを先に使うため、1 つの
  名前がツールごとに別の身元を指してしまうからです。資格情報を同じ名前で `~/.aws/credentials` に同期するツール
  （yawsso など）が原因になるので、別の名前に同期してください。`[DEFAULT]` セクションのキーも（CLI がすべての
  プロファイルに適用するため）、値が空のキーも数えます。資格情報は、
  そのプロファイルの SSO 設定だけを書いた最小の設定ファイルから、エンドポイントの上書きを無視して SSO ログイン経由でのみ
  取得し、さらにそれがそのアカウントの、そのプロファイルの許可セットのロールのセッションであることを AWS に確かめます。`--profile default` は
  断ります。SSO プロファイルを名前で指定してください。
- **SSO ではないプロファイル。** アカウントによっては、`~/.aws` に自分で書いたプロファイルでしか入れません。
  `source_profile` からロールを引き受けるもの（`role_arn` と `source_profile`）や、`credential_process` を持つものです。
  このようなプロファイルは、`--account` でアカウントを指定すれば `af-aws-exec` で実行できます（ここでは必須です）。

  ```sh
  af-aws-exec --profile deploy-target --account <ID> --region <リージョン> -- ./deploy.sh
  ```

  AWS CLI があなた自身のファイルからプロファイルを解決します。このとき AWS CLI 自身がワークロードロールに届く経路
  （コンテナの資格情報の環境変数・IMDS）とエンドポイントの上書きは止めてあります。AWS が報告する資格情報のアカウントが
  そのアカウントのとき（ロールならそのロールのセッションのとき）だけ、コマンドを実行します。`credential_process` は
  あなた自身のプログラムで、書かれたとおりに動きます。`af-aws-exec` が確かめるのは返された資格情報のアカウントで、
  その出どころではありません。プロファイル自身か `source_profile` でたどる先のどれか（`[DEFAULT]` セクションも
  含む）が `credential_source`（ワークスペース自身の資格情報を取るもの）、`web_identity_token_file`、`login_session`、
  `mfa_serial`（エージェントが実行すると MFA の入力に誰も答えられない）を持つとき、たどる先のプロファイルが資格情報の
  取り方を 2 つ以上持つとき（たとえば `credential_process` やロールのプロファイルにキーもある。セッショントークンだけ
  でも、`~/.aws/config` に書いたキーでも数えます。AWS CLI と他の SDK で使う方が食い違うため）、たどった先の SSO
  プロファイルの設定が欠けているとき、またはたどる先が壊れているときは、何も取得せずに断ります。取り方は
  プロファイルごとに 1 つにして、キーは専用のプロファイルに置き、それを `source_profile` に指定してください。
  例外は、名指ししたロールのプロファイルが自分自身を `source_profile` にし、キーをそこに持つ場合だけです。
  `credential_process` が失敗したときは、その出力を表示しません。原因は自分で実行して確かめてください。渡すのは一時的な資格情報だけです。長期のキーそのものになるプロファイルは断るので、そのキーでロールを
  引き受ける形にしてください。たどった先が SSO プロファイルでログインが無いときは、終了コード 3 で、その SSO
  プロファイルの `aws sso login` コマンドを示します（端末ではその場でログインを始めます）。Console には尋ねません。
  このプロファイルは `af-aws-exec --list` には出ず、設定画面のプロファイルと同じ名前にはできません。元のキーは
  これまでどおり `~/.aws` のファイルにあり、`af-aws-exec` がコマンドに渡すことはありません。
- そのコマンドからワークロードロールへの経路は**塞がれます**。ログインが無い・切れているときは、別の身元に
  落ちずに失敗します。ワークスペース内では端末でも次の項目のとおり Console に尋ね、`--login` を付けるとその端末で
  device-code ログインを走らせます。
- **コマンドがログインを必要としたとき**（エージェントのコマンド、または shell セッションの端末で自分が実行したコマンド）は、Console で尋ねます。画面下部のトーストに、
  プロファイル、Settings のアカウントとロール、依頼元のセッションと、依頼が取り下げられるまでのカウントダウン（コマンドが最後に
  尋ねてから 15 分。そのログインを進めている間は出ません）が出ます。**ログイン**を押すとログインの画面が
  開くので、何のためのログインかを確かめ、そこで**ログイン**を押します。ログインのコードはそのとき初めて作られ、
  その画面にだけ表示されます。コードを確かめて**ログインして承認**を押し、開いたページで承認してください。
  エージェントのコマンドは 1 分半ほど（エージェントのセッション以外、たとえば shell のセッションのスクリプトからなら数秒）待ち、
  承認されれば続きます。
  それまでに諦めていれば、エージェントがもう一度実行します。
  **閉じる**では依頼は残り、ほかのブラウザの Console にも出続けます。ブラウザでログインできない端末では、閉じてから
  別のブラウザの Console で**ログイン**を押してください。**依頼を取り消す**は、そのログインをしないときに使います。
  依頼を取り下げ、そのプロファイルについては 1 分ほど再び尋ねません。トーストを閉じても、そのタブで隠れるだけです。設定のプロファイルの行の**ログイン**は、その 1 分の間も含めていつでも使えます。対象は Settings のプロファイルです。自分で定義したプロファイルや `--no-login` では、
  終了コード 3 と、端末で実行するログイン用のコマンドを出して終わります。
  **自分の端末**（shell・SSM セッション）では、Console に尋ねたことを表示し、device コードの有効期間と同じ最大 10 分、あなたが
  そこで承認するのを待ち、承認されれば再実行なしで続きます。**Ctrl-C** で待つのをやめると、終了コード 3 で終わり、依頼は
  Console に残ります。`--login` を付けると、代わりにその端末で device-code ログインを走らせます（URL とコードがそこに出ます）。
  Console に尋ねられないときや、上の Console の対象外のプロファイルでも同じです。ワークスペースの外は従来どおりで、
  端末ならその場でログインを始め、端末が無ければ終了コード 3 で終わります。
- コマンドには、**選んだプロファイルだけ**を定義した AWS 設定（同じ短命の資格情報を返します）を渡し、資格情報
  ファイルと `AWS_ENDPOINT_URL*` の上書きは渡しません。同じプロファイルを指定するツールはそのまま動きます。
  Terraform の `profile = "staging"`、`cdk deploy --profile staging`、スクリプト内の `AWS_PROFILE=staging` のように
  別のプロファイルを指定していると、気づかないうちにそちらで動くのではなく「The config profile (staging) could not be found」
  で失敗します。その設定を非公開に保てない場合（他のユーザーが書き込めるホームディレクトリなど）は、代わりに空の
  AWS 設定を渡して警告を出します。分離は保たれ、同じプロファイルを指定するツールだけがそれを見つけられなくなります。
  コマンド内のスクリプトが `AWS_ACCESS_KEY_ID` を差し替えると
  （`assume-role` の後など）、選んだプロファイルはそこでは解決できなくなります。気づかないうちに新しいアカウントを指すことは
  ありません。新しい資格情報は `--profile` を付けずに使ってください。
- **「could not be found」が出たら**、ツールが別のプロファイルを求めています。ツール側のプロファイル指定を外すか、
  そのプロファイルで実行してください（`af-aws-exec --profile staging …`）。これを通すために `--keep-aws-config` を
  付けないでください。あなたの `~/.aws` とエンドポイント設定がツールに戻り、ツールが指定したプロファイルで動いて
  しまいます。`--keep-aws-config` は、それらのファイルの他の設定が必要なツールのためのものです。
- **リージョン**: `--region` を付ければそれ、付けなければシェルで既に設定済みのもの（`AWS_REGION`、次に
  `AWS_DEFAULT_REGION`）、どちらも無ければプロファイルのものです。コマンドには `AWS_REGION` と
  `AWS_DEFAULT_REGION` の両方で渡し、「running as」の行にも出ます。
  シェルに古い `AWS_REGION` が残っているとプロファイルのリージョンより優先されるので、デプロイでは `--region` を
  付けてください。
- `--account <ID>` を付けると、そのプロファイルがその AWS アカウントでない限り実行しません。デプロイするスクリプト・
  手順書・エージェントへの指示には付けておくと、プロファイル名を間違えても何も起きる前に止まります。設定画面の
  プロファイル**ではない**（自分で定義した）プロファイルでは `--account` が必須です。
- 1 つの名前が 2 つを指す場合は断ります。2 つの設定ラベルが同じ名前になる場合と、設定のプロファイルと同じ名前を
  `~/.aws` で自分で定義していて、アカウント・ロール・ログインのポータルのどれかが違う場合です。
- 資格情報の寿命は SSO のロールセッション、または引き受けたロールのセッション（多くは 1 時間）です。それより長いコマンドは、期限で身元が切り替わるのでは
  なく失敗します。

### WS バーの AWS バッジ

ワークスペースが動いていて、設定に AWS プロファイルが 1 つ以上あると、WS バーに AWS のマークのバッジが出ます。
ログイン済みのプロファイルがちょうど 1 つならその名前を、それ以外は数を（「1/3」なら 3 つのうち 1 つがログイン済み。
**使うときに更新**のログインもログイン済みに数えます）示します。別のプロファイルからロールを引き受けるプロファイルは
自分のログインを持たないので、数には入りません。何かがログイン済みなら**緑**、何も無ければ**枠だけ**、
どれかのログインがまもなく切れるときは**琥珀色**です（上の「ログインが切れる前の警告」と同じ条件）。琥珀色のときの
ツールチップは「AWS プロファイル: まもなく切れるログインがあります」です。押すと一覧が開きます。各プロファイルの状態
（**ログイン済み**／**使うときに更新**／**未ログイン**）、名前・アカウント・ロール、終了時刻が分かっている行には
**{時刻} に終了**（まもなく切れるなら琥珀色）、未ログインまたはまもなく切れる行には**ログイン**、
ログイン済みの行には**ログアウト**（上を参照）が並びます。ロールを引き受けるプロファイルの行は
**「{元} のログインに従います」**（元が無い、または書き出されていないときは **元プロファイルなし**）と読め、
**ログイン**は元プロファイルへのログインに、**ログアウト**は元プロファイルのログインを終わらせる操作になります（確認の画面で元プロファイルを示します）。既定のプロファイルはありません。ログイン済みの
プロファイルはどれも同時に使え、コマンドごとに `af-aws-exec --profile <名前>` で選びます。下の **AWS プロファイルの設定**で
設定のタブが開きます。一覧は、ワークスペースの起動時、開いたとき、ログイン・ログアウトの後、分かっているログインの終了時刻を
過ぎたときに更新されます。

## Google Cloud で自分としてコマンドを実行する（af-gcloud-exec）

Google Cloud のプロファイルは **⚙設定 →「Google Cloud」タブ**に置きます。プロファイルは、コマンドがどのプロジェクトに
向き、誰として動くかを決めます。

- **ラベル**：表示名です。コマンドで使うプロファイルの**名前**はここから作られ、ラベルの横に表示されます。英小文字・数字・
  `-` だけになり（それ以外の文字の並びは `-` に、数字で始まる名前は先頭に `p` が付き、日本語のラベルのように使える文字が
  無いものは `p-` と短い符号になります）。2 つのラベルが同じ名前になると（`Prod` と `prod`）、**どちらも**ワークスペースで
  **使えず**、行にそう表示されます。片方の名前を変えてください。
- **ログイン方法**：Google アカウント（Google Workspace・Cloud Identity のアカウントを含む）。
- **プロジェクト**：コマンドが既定で向くプロジェクト ID（番号ではありません）。
- **割り当てプロジェクト**（任意）：API の割り当てを課金するプロジェクトで、空欄ならプロジェクトと同じです。個人の
  ログインでは割り当てプロジェクトが要る API があり、あなたのアカウントにはそのプロジェクトでサービスを使う権限が要ります。
- **アカウント**（任意）：ログインする Google アカウントで、ほかのアカウントでのログインは断られます。空欄なら
  最初のログインで選びます。
- **権限を借用するサービスアカウント**（任意）：コマンドは、あなたのログインを通じてこのサービスアカウントとして動きます。
  あなたのアカウントには、そのサービスアカウントに対するサービス アカウント トークン作成者のロールが要ります。サービス
  アカウントとして動く方法はこれです。サービスアカウントキーはどこでも受け付けません。
- **リージョン / ゾーン**（任意）。

**Google の認証情報は Agent Fleet に保存しません。** ログインはワークスペースの中の、ワークスペース専用の gcloud の保存場所に
あります。端末で使う自分の `gcloud` とは別物で、片方でログインしてももう片方はログインしません。プロファイルが自分の gcloud の
設定・ログイン・アプリケーションの既定認証情報を読んだり変えたりすることはありません。設定の変更は 5 分ほどで
ワークスペースに届き、`af-gcloud-exec` を走らせればすぐに届きます。プロファイルのアカウントを変えたとき、ラベルを変えて名前が
変わったとき、削除して追加し直したときは、どのアカウントを使うかがリセットされます。指定したアカウントがすでにワークスペースでログイン済みで
なければ、次の実行でログインを求められます。プロファイルは書き出し・取り込みで持ち運べます（[20 設定](20-settings.ja.md#書き出し-取り込み)）。

### gcloud の構成から取り込む

Google Cloud タブの **gcloud の構成から取り込む** は、手元の PC の構成ファイル
（`~/.config/gcloud/configurations/config_<名前>`。複数を同時に選べます。1 つ貼り付けるときは名前も入れます）を読みます。
ファイルはこの画面の中で読むだけで送信されず、チェックを入れたプロファイルの項目だけが保存されます。プレビューは
すべてのファイルを**作成**・**登録済み**・**取り込めません**（理由つき）に分けて並べ、ラベル（既定は構成名）は取り込む前に変えられます。

- **引き継ぐもの**：`core/project`・`core/account`・`billing/quota_project`・`compute/region`・`compute/zone`、
  そして 1 つだけの `auth/impersonate_service_account`。追加フォームと同じ検証をかけます。
- **理由をつけて断るもの**：project の無い構成、`core/account` がサービスアカウントのもの（鍵なしではログインできません。
  Google アカウントでログインしてサービスアカウントを権限借用してください）、サービスアカウントを並べたもの（委任チェーン）、
  認証情報ファイル・アクセストークンファイル・独自の OAuth クライアントなど `auth/` の他の設定、プロキシや API エンドポイントの設定、
  universe domain や独自 CA ファイル。これらを省いて作ると、手元の構成とは別の相手に向くプロファイルになるためです。
- **読まない・表示しないもの**：gcloud の認証情報、アプリケーションのデフォルト認証情報、鍵ファイル、構成に書かれたパスや
  トークンファイル。理由には設定名と行番号だけを出し、値は出しません。
- 同じラベルがすでに同じ内容で登録されていれば**登録済み**、内容が違えば別のラベルを求めます。現在のプロファイルを読めないときは
  何も作りません。
- 取り込んでもログインはされません。新しいプロファイルごとに**ログイン**を使ってください。

### プロファイルとしてコマンドを実行する

```sh
af-gcloud-exec --list
af-gcloud-exec --profile <name> --project <project-id> -- gcloud compute instances list
af-gcloud-exec --profile <name> --project <project-id> -- terraform plan
af-gcloud-exec --profile <name> --project <project-id> -- kubectl get pods
```

- `--list` は各プロファイルの名前・プロジェクト・アカウント（最初のログインまでは「chosen at the first login」）・権限を
  借用するサービスアカウント・ラベルを表示し、使えないプロファイルとその理由も挙げます。名前だけでなく、プロジェクトと
  アカウントで選んでください。
- `--project` はプロファイルのプロジェクトと同じでなければならず、違えば断られます。Google のログインはプロジェクトに
  結び付かないので、これは「コマンドが既定でどこを向くか」についてあなたとプロファイルの考えが一致しているかの確認に
  とどまります。コマンド自身の `--project` や、Terraform の設定に書いたプロジェクトはそちらが優先されます。
- コマンドが受け取るのは、プロファイルの短命な**アクセストークン**だけです。gcloud のログインも、アプリケーションの
  既定認証情報も、マシン自身の Google の身元も渡りません。`af-gcloud-exec` は「profile … runs as <account> in
  project …; the token is valid for N more minutes」と表示します（`-q` で省けます）。トークンそのものは表示しません。
- トークンの寿命は、渡した時点の残りです。最短 10 分、最長でおよそ 1 時間です。コマンドの実行中は `af-gcloud-exec` が
  横で動き続け、トークンが切れる約 8 分前に**トークンファイルを更新**します。その後にコマンドが起動する `gcloud`、
  `bq`、GKE 認証プラグインのプロセスは新しいトークンを読むので、それらを呼び直すスクリプトは動き続けます。起動時に
  読んだトークンを持ち続けるプロセスは、そのトークンのままです。1 つの長く動く `gcloud`（SDK 587.0.0 はファイルを
  1 度だけ読みます）と、`GOOGLE_OAUTH_ACCESS_TOKEN` を 1 度だけ読むプログラム（**長い `terraform apply`**）は、
  そのトークンが切れると失敗します。`kubectl` の watch や接続中の通信は、プラグインの再実行と再接続に依存します
  （未計測）。そうした作業は短い実行に分けてください。
- トークンを更新できないとき（ログインが取り消された、ログインし直しが必要、権限、ネットワーク）は、`af-gcloud-exec` が
  その旨を表示し、トークンが切れるまで再試行を続け、切れたらコマンドを止めます（SIGTERM。終わらなければ 30 秒後に
  SIGKILL）。終了ステータスは、ログインし直しが必要なら 3、それ以外は 1 です。実行の開始時に Console へ尋ねられる
  実行だったなら、起動時と同じくログインの依頼が Console に出ます。`--login`、`--no-login`、ワークスペースの外では、
  端末で実行するコマンドがメッセージに出ます。Console で取り消された依頼は、取り消されたと表示します。
- `af-gcloud-exec` を止めると、起動したコマンドに SIGTERM が送られます（コマンドは無視できます）。`af-gcloud-exec` が
  強制終了されたときも同じです。コマンド自身が起動したプログラムには届きません。`af-gcloud-exec` が強制終了された場合、
  トークンファイルはトークンの期限が切れるまで残り、後の実行が消します。
- 最初の実行で、Google Cloud SDK（ピン留めした 1 つの版と GKE 認証プラグイン）をホームに入れます。ダウンロードは約 85 MB、
  ディスクは約 510 MB で、停止しても作り直しても残ります。その後は gcloud の各コマンドの初回だけ数秒遅くなります。入れた後は
  **ツールチェーン**タブのツールの版の表に gcloud が出ます。端末で素の `gcloud` を走らせると同じプログラムが動きますが、
  使うのは（あれば）自分のログインで、プロファイルのものではありません。
- `kubectl` を使うときは、クラスタの接続情報を一度プロファイル経由で取り
  （`af-gcloud-exec --profile <name> --project <project-id> -- gcloud container clusters get-credentials <cluster> --location <location>`）、
  `kubectl` も `af-gcloud-exec` 経由で走らせます。GKE 認証プラグインはトークンを gcloud に求め、gcloud がトークンを持つのは
  `af-gcloud-exec` の中だけだからです。

**トークンを使う道具。**

| 道具 | `af-gcloud-exec` 経由で |
|---|---|
| `gcloud`（`gcloud storage` を含む） | 使う |
| GKE クラスタへの `kubectl` | 使う（GKE 認証プラグイン経由） |
| Terraform の Google プロバイダ | 使う（割り当てプロジェクト付き。実行中のトークン更新は届かない） |
| `bq` | 使う。SDK に入っていますがパスは通っていません。`~/.local/share/agent-fleet/google-cloud-sdk/bin/bq` で走らせます |
| `gsutil` | **使わない**。トークンを無視します。自分の gsutil（boto）の設定が無ければログイン無しで要求を送るので、公開バケットは応答します。設定があれば、その設定にある身元で動くことがあります。`gcloud storage` を使ってください |
| Google のクライアントライブラリ（Go・Python・Node など） | プログラムがトークンを渡したときだけ |

クライアントライブラリで作ったプログラムは、既定の認証情報について「File … was not found」や「no such file or directory」
のようなエラーで止まります。これは意図したものです。そうしないと別の身元（自分の gcloud のログインや、マシンのもの）を
見つけてしまいます。プログラムはトークンを自分で受け取る必要があります。Python なら
`google.oauth2.credentials.Credentials(os.environ["GOOGLE_OAUTH_ACCESS_TOKEN"])`、Go なら
`option.WithTokenSource(oauth2.StaticTokenSource(&oauth2.Token{AccessToken: os.Getenv("GOOGLE_OAUTH_ACCESS_TOKEN")}))`
です（Go のライブラリは、`af-gcloud-exec` が `GOOGLE_CLOUD_QUOTA_PROJECT` に入れるプロファイルの割り当てプロジェクトを使います。
Python では `Credentials` に `quota_project_id=os.environ["GOOGLE_BILLING_PROJECT"]` を渡してください）。Node では、クライアントライブラリが使っているのと同じ版の `google-auth-library` から `OAuth2Client` を作ってください。
メジャー版の違うものはエラーにならずに受け取られ、ログインを何も送りません。エージェントは、コードをこのように変える前に
あなたに確認します。

### ログイン

**Console で。** **⚙設定 → Google Cloud** のプロファイルの各行に**ログイン**があります。ワークスペースがそのプロファイルの
ログインを持つと、行に **「<アカウント> でログイン済み」** と出て、ボタンは**再ログイン**に変わります。WS バーの
Google Cloud バッジにも同じボタンがあります（[下記](#ws-バーの-google-cloud-バッジ)）。ボタンを押すと、プロファイル・
プロジェクト・アカウントを示すログインの画面が開きますが、まだ何も始まりません。ログインはその画面で**ログイン**
（または**再ログイン**）を押したときに初めて始まり、そのログインはその画面にだけ表示されます。

1. **Google ログインを開く**を押します。Google のログインページが新しいタブで開きます（画面にはそのアドレスも出ます。
   必ず `accounts.google.com` のもので、ワークスペースはそれ以外を表示しません）。ログインします。プロファイルが
   アカウントを指定していればそのアカウントで、ほかのアカウントでのログインは断られます。
2. Google が**確認コード**を表示します。同じログインの画面の**確認コード**に貼り付け、**コードを送信**を押します。
   ログインでトークンが得られることをワークスペースが確かめると、画面に「ログインしました」と出ます。

**コードは、いまここで自分で始めたログインにだけ貼り付けてください。** コードが使えるのは、そのコードを出したページの
ログインだけで、Console がコードの欄を出すのも**ログイン**を押した画面だけです。ただし、誰がログインを始めたかを
証明するものはありません。ワークスペースの中のプログラムなら、エージェントも含めて誰でも始められます。ほかの誰かが
目の前に出した欄・端末・チャットのメッセージに、コードを貼り付けないでください。

ワークスペースがそのアカウントの使えるログインをすでに持っていれば、**ログイン**はログインのページ無しですぐ終わります。
**再ログイン**は保存済みのものを使い回さず、必ずログインし直させます。ログインが取り消されたと分かっているときに
使ってください（ワークスペースは、コマンドが断られるまでそれに気づけません）。別の画面や端末でもう一度**ログイン**を
押すと、先のログインは止まり、そのコードはもう使えません。15 分以内に終わらなかったログインは終わります。
**やり直す**で新しく始めます。

ログイン済みの行（設定でもバッジでも）の**ログアウト**は、そのプロファイルの Google アカウントについてワークスペースが
保存したログインを削除します。ログインはアカウントごとに 1 つなので、同じアカウントを使うプロファイルはすべて一緒に
ログアウトします。確認の画面で、削除の前にそれらの名前を示します。Google 側のサインインと、ほかのマシンの gcloud には
影響せず、コマンドがすでに受け取ったトークンは期限（最長 1 時間）まで有効です。それらのプロファイルのログインの画面で
コードを待っているログインは止まります。再び使うにはログインし直してください。確認からログアウトまでの間にプロファイルのアカウントが変わった（別のログインが
終わった）ときは、何もログアウトせず、Console がそう知らせます。

**エージェントのコマンドがログインを必要としたとき**は、Console で尋ねます。`af-gcloud-exec` は「Google Cloud login for
profile … requested in the Agent Fleet Console」と表示し、画面下部に **「エージェントが Google Cloud へのログインを待っています」**
のトーストが、プロファイル・プロジェクト・アカウント・依頼元のセッションとコマンド、依頼が取り下げられるまでのカウントダウンとともに出ます。トーストの**ログイン**でログインの
画面を開き、上のとおり続けます。Google が保存済みのログインを断った場合は画面にそう出て、ログインは最初からやり直しに
なります。エージェントのコマンドは 1 分半ほど（エージェントのセッション以外、たとえば shell のセッションのスクリプトからなら
数秒）待ち、ログインが済めば続きます。それまでに諦めていれば、ログインが Console で待っている旨を出して終了コード 3 で
終わり、済んだと伝えればエージェントがもう一度実行します。**閉じる**では依頼は残り、ほかのブラウザの Console にも出続けます。
**依頼を取り消す**は、そのログインをしないときに使います。依頼を取り下げ、コマンドは終了コード 3 で終わり、そのプロファイル
については 1 分ほど再び尋ねません。トーストを閉じても、そのタブで隠れるだけです。設定のプロファイルの行やバッジの
**ログイン**はいつでも使え、そこでログインすれば依頼も片付きます。

**ワークスペース内の端末では**、`af-gcloud-exec` はエージェントのコマンドと同じように Console に尋ね、最大 10 分、あなたが
そこでログインを終えるのを待ちます。Ctrl-C で待つのをやめると終了コード 3 で終わり、依頼は Console に残ります。`--login` を付ける
と（ワークスペースの外や、Console に尋ねられないときも）、その端末で自分で Google のログインを始めます。表示される URL を
ブラウザで開いてログインし、ページに出る確認コードを**その**端末に貼り付けます。ここでも決まりは同じで、貼り付けてよいのは
いま自分で始めたログインのコードだけです。Console に尋ねられないコマンド（`--no-login` を付けたとき、ワークスペースの外）は、
終了コード 3 と、自分の端末（シェルのセッション、または Claude Code ならプロンプトで `!` に続けて入力）で走らせるコマンドを
表示して終わります。

```sh
af-gcloud-exec --profile <name> --project <project-id> --login -- true
```

**Compute Engine の VM では。** Google Cloud の VM の上で直接動くワークスペース（`native` ランタイム）では、gcloud がまず
その VM で個人アカウントを使うかを尋ねます。Console のログインはこの問いにあなたの代わりに答えません。ログインの画面は
そう表示して終わるので、上の端末のコマンドでログインしてください。

**ログインが終わるとき。** Google は保存したログインを断ることがあります。取り消されたときや、組織が一定時間ごとの
ログインし直しを求めているとき（セッションの長さ）です。すると新しいトークンが要る次の実行が上と同じようにログインを
求め、そのログインは保存済みのものを使い回さずに本当にログインし直させます。ワークスペースはその終わりを**前もって
知らせられません**。その時刻はワークスペースが読めるどこにも記録されないからです。すでに渡したトークンの残りが 10 分を
切るまでは実行が動き続けるので、ログインを求められるのは終わりから最長でおよそ 50 分後になります。

### WS バーの Google Cloud バッジ

ワークスペースが動いていて Google Cloud のプロファイルが 1 つ以上あると、WS バーの AWS バッジの隣に Google のマークの
バッジが出ます。ログイン済みのプロファイルがちょうど 1 つならその名前を、それ以外は数を（「1/3」なら 3 つのうち 1 つが
ログイン済み）示します。何かがログイン済みなら緑、何も無ければ枠だけ、エージェントのコマンドがプロファイルのログインを
待っている間は琥珀色です。押すと一覧が開きます。各プロファイルの**ログイン済み**／**未ログイン**、名前・プロジェクト・
アカウント、エージェントが待っている行には **「このログインを待っているエージェントがあります」**、そして上のログインの
画面を開く**ログイン**／**再ログイン**、ログイン済みの行には**ログアウト**（上を参照）が並びます。既定のプロファイルはありません。ログイン済みのプロファイルはどれも同時に
使え、コマンドごとに `af-gcloud-exec --profile <名前>` で選びます。下の **Google Cloud の設定**で設定のタブが開きます。

**ログイン済み**は、そのプロファイルのアカウントの Google ログインがワークスペースに保存されている、という意味でしかありません。
ワークスペースはそれを Google に確かめず、Google に断られても消さないので、取り消されたログインは、コマンドがそれに
気づいた後も**ログイン済み**のままです。そのコマンドのログインの依頼が待っている間はバッジが琥珀色になりますが、依頼を
取り消すか依頼が期限（15 分）で消えると、ログインが使えないままでもバッジは緑に戻ります。**再ログイン**でログインし直すと
直ります。バッジは定期的には問い合わせません。ワークスペースが起動したとき、一覧を開いたとき、ログインの依頼が出たり
片付いたりしたとき、ログインの後、タブに戻ったとき、設定でプロファイルを変えた後に尋ねます。追加や削除したプロファイルは、
ワークスペースが変更を取り込んでから（5 分ほどで）バッジに反映されます。

### 止まったとき

| 表示 | 意味 |
|---|---|
| 終了コード 3、「the login was requested in the Agent Fleet Console and is waiting …」 | プロファイルにまだログインが無いか Google が保存済みのログインを断り、コマンドが待つのをやめました。トーストか設定からログインし、コマンドをもう一度走らせてもらいます。終了コード 3 は必ずログインのことです |
| 終了コード 3、「the login request was cancelled in the Agent Fleet Console」 | 依頼を取り消しました。ログインしたいなら設定からログインします |
| 終了コード 3、「Google Cloud login required … log in from a terminal with:」 | Console に尋ねられませんでした（`--no-login`、またはワークスペースの外）。表示されたコマンドを端末で走らせます |
| 「is for project X, not Y; --project must be the profile's project」 | このプロジェクトには違うプロファイルです。`--list` を確かめてください |
| 「no Google Cloud profile …」または「not exported: …」 | その名前は使えるプロファイルにありません。設定で追加するか直します |
| 「gcloud could not mint a token: …」 | ログインの問題ではありません。権限が無い（借用するサービスアカウントへの権限も含む）、API が有効でない、ネットワークのどれかで、メッセージに書いてあります |
| 「the token gcloud minted is valid for only …」 | gcloud が残り 10 分のトークンを出せませんでした。1 分ほどして、もう一度試してください |
| 「this deployment does not export Google Cloud profiles」 | この配備は Google Cloud のプロファイルを提供していません |
| 「could not renew the token of profile … trying again until it ends in N minutes」 | 使っているトークンをまだ更新できていません。実行は更新を試し続け、先にトークンが切れたらコマンドを止めます |
| 「the profile's login is now X, not Y, which the command started as; run it again」 | 実行中に、そのプロファイルが別のアカウントでログインし直されました。コマンドをもう一度走らせます |
| 「the profile changed in Settings while this run started; run it again」 | もう一度走らせます。アカウントやプロジェクトが変わっていれば `--list` で確かめてください |
| 「waiting for another af-gcloud-exec or a profile sync …」 | 端末でのログインか別の実行が、ワークスペースの gcloud の保存場所を使っています。終われば続きます |

**保証しないこと。** コマンドはあなたとして動くので、自分の gcloud のディレクトリを含めてホームを読めます。`af-gcloud-exec`
は、Google の認証情報を探す標準の方法（gcloud とクライアントライブラリのもの）が、渡したトークン以外を見つけないように
するだけで、ファイルを読めなくするわけではありません。自分の設定を持つ `gsutil` のように、別の場所を探す道具は対象外です。
Google Cloud の VM の上で直接動くワークスペースでは、その標準の方法を無視するプログラムが、VM 自身の身元に届く可能性が
あります。Kubernetes の Pod でも同じです。ワークスペースは
`AWS_EC2_METADATA_DISABLED=true` で起動しますが、この変数はクラスタのメタデータサーバ（ノードのサービスアカウント、GKE では
Workload Identity）を塞ぎません。標準の方法を無視するプログラムは、管理者がクラスタのネットワークで経路を塞がない限り、
その身元に届く可能性があります。
