# 17. ワークスペースの環境 — 環境設定・作り直し・テスト用データベース・ローカル AWS エミュレータ

[English](17-workspace-environment.md) | 日本語

この章は、ワークスペースが動く環境を扱います。環境設定、ワークスペースの再作成とホームのクリーン、テスト用のデータベース、ローカルの AWS エミュレータで AWS のコードを試す方法です。

## 環境設定とワークスペースの作り直し

**⚙設定 → 「ツールチェーン」タブ**で、ワークスペースの環境を調整できます。変更は**この後に
起動するセッション／シェルに反映**されます（起動中のものと既存プロセスには、ワークスペースを停止してから再び起動すると反映されます）。

- **タイムゾーン (TZ)**：既定は日本時間。変更の反映にはワークスペースの停止・起動が必要です。
- **Node.js / Java (JAVA_HOME) / Go**：使うバージョンを選べます。Node.js と Java は**このワークスペースに
  まだ無い**版も一覧に出ます。未インストールの版を選ぶと「インストール」ボタンが出て、その場で取得できます
  （Java は約 200MB。どちらも home ボリュームへ入るので再起動しても残ります）。使っている Java の版に新しい
  パッチが出ると、**「… に更新」** で同じように取得できます。完了後に起動したセッションから使われるので
  （Java は `JAVA_HOME`）、停止・起動は要りません。
- **エージェント CLI の更新**：「起動時にエージェント CLI と rtk を最新へ更新する」（対象は claude / opencode / codex / cursor / GitHub Copilot / [Antigravity（agy）](09-agents.ja.md#antigravityagy) / rtk）。既定はオフ（イメージに焼いた版で固定）。Kiro はこのトグルの対象外です — 版はイメージ再ビルド / オンデマンド導入で固定し、Kiro 自身の自動更新も無効にしています。Muse Code も対象外です。カードからイメージがピンした版を導入し、自分で更新することはありません。新しいピンの版がイメージと一緒に届くと、カードに **「Muse Code を更新」** が出ます（[09](09-agents.ja.md#muse-code)）。lcpp にはワークスペースで更新する CLI がありません。エンジンは配備側のものです。

### ワークスペースを作り直す（危険な操作）

**⚙設定 → 「危険な操作」タブ**に **「ワークスペースを作り直す」** があります。コンテナを
破棄して最新イメージで作り直す操作で、**「作り直す」** を押すと確認が出ます。何が残り、
何が消えるかは以下のとおりです。

このタブはすべての配備にあるわけではありません。作り直しとホームの掃除はホームそのものから
ファイルを消す操作で、配備によってはホームが Control Plane から届かない場所にあります
（[ref/deploy-targets](../ref/deploy-targets.ja.md)）。その配備ではタブ自体が表示されません。
ワークスペースバーからの停止・起動はどの配備でも使えます。

- **消えるもの**：実行中のセッション、および **クローン済みリポジトリ（`~/repos`・未コミット変更を含む）**。
  削除されるのは `~/repos` **だけ**です。
- **残るもの**：それ以外のホーム（`~`）はすべて残ります。ログイン・接続（GitHub / Bitbucket /
  Claude など）、`~/.local`（claude / node など）、各種設定・キャッシュは、ホームボリュームが
  作り直したコンテナへ再び接続されるので保持されます。

イメージ更新を取り込みたい、環境が壊れた、というときに使います。**未コミットの変更が消える**ので、
実行前に push / コミットを済ませてください（[06](06-code.ja.md)）。

### ホームを掃除する（さらに深いリセット）

作り直しは `~/repos` しか消さないため、ホーム側（`~/.local` の壊れた claude 導入、
壊れたキャッシュや設定ファイルなど）が原因のときは直りません。その場合は同じ「危険な操作」タブに
ある **「ホームを掃除する」** を使います。ホームのほぼ全体を削除して最新イメージで
作り直す、より深いリセットです。

- **残るもの**：ログイン・接続（GitHub / Bitbucket / Claude）**のみ**。
- **消えるもの**：実行中のセッション、クローン済みリポジトリ、および `~/.local`・キャッシュ・
  設定など**ホームのその他すべて**。

まず「作り直す」で直るか試し、それでも直らないときだけ「掃除」を使ってください。
こちらも先に push / コミットを済ませてください。

## DB を使うテストを回す

ワークスペースの中では、Docker や外部サービス不要で Postgres を使えます。`af-db url` は現在の
作業コピー用データベースへの接続 URL を返します。初回は必要に応じてダウンロード・初期化・
起動を行うため数分かかることがあります。サーバは 30 分接続が無いと自動停止します。

```bash
# DATABASE_URL を現在のシェルにエクスポートする
eval "$(af-db env)"
go test -count=1 ./...

# またはプロジェクト固有の変数名で URL を渡す
MY_DB_URL="$(af-db url)" go test -count=1 ./...
```

`af-db status` で稼働状況を確認できます。終わったらサーバを停止します:

```bash
af-db down
```

メモリを多く使うビルドの前には停止してください。サーバはワークスペースのメモリ枠から
≈ 47 MB を使っており、大きな JVM ビルドと並行すると枠を使い切ることがあります。

知っておくと便利なこと:

- **作業コピーごとに 1 DB。** 同じ作業コピーを使う 2 セッションは同じデータベースを共有
  します。名前で明示的に指定するには `af-db url --db=<name>`。
- **`af-db url --tcp`**：テストドライバが TCP を必要とする場合（例:
  `jdbc:postgresql://127.0.0.1:…`）に使います。既定 URL は unix socket を使います
  （Go / Python の多くのクライアントは対応していますが、JDBC は対応していません）。
- **データはストップ→スタートをまたいで残ります。** DB ファイルはホーム
  （`~/.local/state/af-db`）にあり、ホームの他のものと同じワークスペースの状態です。消えるのは
  2 つの操作だけです（`af-db down --purge` と、データベースタブからの削除）。
- **`af-db up --durable`**：コミットごとにディスクへ書き切ります（`fsync`）。既定はこれを
  速さと引き換えにしています。テストデータには妥当なトレードオフで、ワークスペースがクラッシュすると
  直前の数トランザクションを失うことはありますが、通常の停止で失うことはありません。
  （`--persist` はこのフラグの古い名前で、今も動きます。）
- **`af-db up --ephemeral`**：その逆で、ファイルをタスクローカルディスクに置きます。速い代わりに
  **ワークスペースの停止で消えます**。中身が使い捨ての治具だと分かっているときに使ってください。
  タスクローカルディスクが無い配備では、その旨を表示してホームを使います。
- **`psql` と `mysql` は PATH にあり、引数なしで繋がります。** エンジンを起動すると、その
  クライアントも導入されて PATH に置かれます（`psql` は別ダウンロード、`mysql` はサーバに同梱）。
  そのあとに起動したセッションには `PGHOST` / `PGPORT` / `PGUSER` / `PGPASSWORD` / `PGDATABASE` と
  `MYSQL_UNIX_PORT` / `MYSQL_PWD` が入るので、`psql` はその作業コピーのデータベースを開き、
  MySQL は `mysql <名前>` で開けます。
- **ポートは固定です**。Postgres は 5432、MySQL は 3306 で、フレームワークが既定にしている番号
  そのものです。起動時にコンテナ内の別の何かが使っていた場合だけずれ、その場合も一度取った番号を
  以降の再起動でも使い続けます。開発中のアプリの接続文字列を書き換える必要はありません。
  現在の番号は `af-db status` でいつでも確認できます。
- **`af-db connect [engine] [--db=NAME]`** は、シェルの状態に関係なくクライアントを開きます。
  ソケット・パスワード・ユーザを自分で解決し、サーバが止まっていれば先に起動します。
  サーバを起動する前に開いたシェルではこれを使ってください。

### MySQL

MySQL 8.4 も使えます。同じ手順で起動します:

```bash
af-db up mysql
eval "$(af-db env)"
```

`eval "$(af-db env mysql)"` を実行したシェルにだけ `AF_DB_URL_MYSQL`（と `DATABASE_URL`）が
入ります。自動では設定されません。
`go-sql-driver/mysql` 形式の接続文字列が必要な場合は
`af-db url mysql --format=go-dsn` を使います。

MySQL 固有の注意点:

- **常駐メモリ約 226 MB**（MySQL は InnoDB バッファプールをアイドル時も保持します）。
  JVM ビルドなどメモリを多く使う作業の前には停止してください。ワークスペースの cgroup
  は全セッションで共有されます: `af-db down mysql`。
- **arm64 では導入時に 909 MB のダウンロードが発生します**。arm64 向けの `minimal`
  ビルドが存在しないため、フルアーカイブが必要です。インストーラーは必要な部分だけを
  取り出してデバッグセクションを除去するので、**導入後は約 147 MB**（x86_64 の
  `minimal` 展開後より小さい）。実測では取得から導入完了まで約 30 秒でした。
- **x86_64 では約 63 MB のダウンロード**（`minimal` アーカイブ・展開後は約 446 MB）。
- ワークスペースの cgroup 上限が 1 GiB 未満の場合、`af-db up mysql` はメモリ不足を
  報告して拒否します。Postgres が稼働中なら先に `af-db down postgres` してください。

### Console のデータベースタブ

ワークスペース設定の **データベース** タブで、各エンジンの状態（バージョン・常駐サイズ (MB)・
ポート・接続 URL）を確認し、端末を開かずにエンジンの起動／停止と、データベースの作成・削除・
リセットができます。

- **Start**：未インストールのエンジンを選ぶと、まず導入してから起動します。
  `installing` / `starting` 状態の間はカードが自動でポーリングします。
- **Stop**：「停止してデータも削除」(`--purge`) を選ぶとデータディレクトリも削除します。
  消えるのは**そのエンジン上の全データベース**です（他の作業コピーのものや `--db=` で作った
  共有データベースも含みます）。1 つだけ作り直したいときは、その行の **リセット** を使ってください。
- **ワークスペース起動時に開始**：チェックすると、ワークスペースが起動するたびに Agent が
  そのエンジンを起動します。端末もボタンも要りません。一度起動したことのあるエンジンにだけ
  表示されるので、起動時にサーバをダウンロードすることはありません。既定はオフです。
  これは、データベースは問い合わせが無くてもメモリを使うためです。
- **接続**：ホームで Shell セッションを開き、その行のデータベースに `psql` / `mysql` で
  接続します（`af-db connect`）。クライアントを抜けるとシェルが残ります。
- **作成**：入力した名前でデータベースを作ります（`af-db create --db=<name>` と同じ）。
  作業コピー用の 1 つでは足りないとき（使い捨てのスキーマ、1 プロジェクトで 2 つめ、
  セッション間で共有するもの）に使ってください。名前に使えるのは英小文字・数字・`_` で、
  先頭に数字は置けません。使えない名前のあいだはボタンが無効のまま、理由が下に出ます。
- **削除**：データベース 1 つを、中身ごと削除します（`af-db drop --db=<name>` と同じ）。
  名前を言う確認のあとに実行され、接続が残っていても切断されます。
- **リセット**：データベース 1 つを空にします（破棄して再作成。`af-db reset` と同じ）。
  実行前に確認が表示されます。
- **データベースの行**：そのエンジンにあるデータベースが、作業コピーのパスと一緒に 1 行ずつ
  並びます。コピーできるのは**その行のデータベースの URL** です。まだ 1 つも無いときは、
  ここで作成するか、作業コピーで `af-db url` を実行してください。
- **Socket / TCP 切替**：ドライバに合わせた形式の URL をコピーできます。
- 直前の操作のエラーがあればエンジン行の下にインラインで表示されます。

タブはワークスペースが起動中のときのみ有効です。停止中はプレースホルダーが表示され、
API コールは発生しません。

## ローカルのエミュレーター（MiniStack）で AWS のコードを試す

本物のアカウントに触らずにコード・テンプレート・スクリプトを試したいときは、オープンソースの AWS API
エミュレーター [MiniStack](https://github.com/ministackorg/ministack) をワークスペースの中で動かせます。PyPI から
入れれば Docker は要らず、数秒で起動し、小さいままです。イメージには入っていないので自分で入れてください。

```sh
python3 -m venv ~/.local/ministack && ~/.local/ministack/bin/pip install ministack
GATEWAY_PORT=14566 ~/.local/ministack/bin/ministack
```

ポートは他のセッションと共有です。空いているものを選び（既定の 4566 は使われていることがあります）、使い終わったら
サーバーを止めてください。

**専用のプロファイルを向け、毎回その名前を指定します。** まだどこにも使われていないプロファイル名を選んでください。
`aws configure list-profiles` にも、`af-aws-exec --list` にも、`~/.aws/credentials` にも無い名前です。
`~/.aws/credentials` に `[ministack]` があると下の鍵よりそちらが優先され、本物の資格情報がエミュレーターに送られます。
設定画面に同じ名前のプロファイルがあれば、そちらは書き出されなくなります。そのうえで `~/.aws/config` の管理ブロックの
外に新しい節を足します。

```ini
[profile ministack]
region = us-east-1
endpoint_url = http://127.0.0.1:14566
aws_access_key_id = 000000000001
aws_secret_access_key = test
```

あとは `aws --profile ministack …` で実行します。プロファイルがエンドポイントを運ぶのは、プロファイルの
`endpoint_url` を読むクライアントだけです。AWS CLI v2 と現行の SDK は読みますが、AWS SDK for Java 1.x・
JavaScript v2・Go v1 は読まず、自分でエンドポイントを決めるツールも読みません。それらはクライアント自身に
エンドポイントを渡さない限り（Terraform の `endpoints` ブロック、SDK のエンドポイント指定）、ダミーの鍵のまま
本物の AWS に向かいます。シェルに `AWS_ENDPOINT_URL*` や `AWS_IGNORE_CONFIGURED_ENDPOINT_URLS=true` が
`export` されているとプロファイルのエンドポイントより優先されるので、それも確かめてください。

代わりにダミーの鍵をシェルに `export`（`AWS_ACCESS_KEY_ID=test`）**しないでください**。すべてのコマンドが
その鍵を持つことになり、`--endpoint-url` を付け忘れたコマンドは、何もワークスペースの外に出る前に「Unable to
locate credentials」で止まる代わりに、本物の AWS へリクエストを送ります（ダミーの鍵なので拒否されます）。
プロファイルを付け忘れたときにどこまで守られるかはワークスペースによります。プロファイル無しのコマンドがその
エラーで止まるワークスペース（[16](16-cloud-accounts.ja.md) の `af-aws-exec` を参照）では止まります。ワークスペース自身のロールが戻される
（`AF_WS_WORKLOAD_AWS=1`）場合や、マシン自身の資格情報を持つネイティブランタイムでは、プロファイル無しの
コマンドはその身元で本物の AWS に対して動きます。そこでは決してプロファイルを省かないでください。MiniStack は
`af-aws-exec` を通しては使いません。`af-aws-exec` はエンドポイントの設定を意図して外します。

- **1 つのサーバーを共有する。** 12 桁のアクセスキーがそのままアカウント ID になり、リソースはアカウントごとに
  分かれるので、互いのリソースを見てはいけないセッションは別々のキーを使います。リージョンで分かれるかは
  サービスによります（たとえば S3 のバケットはどのリージョンからも見えます）。2 つのセッションを分けるのに
  リージョンを頼らないでください。
- **ここでは動かないもの。** RDS・ElastiCache・ECS は本物の Docker コンテナを起動しますが、ワークスペースには
  Docker がありません。それでも RDS は `available` と答え、`localhost:5432` のような、自分のデータベースが
  どこにも無いエンドポイントを返します。そこではワークスペースの別の Postgres が待ち受けていることがあります。
  データベースが要るなら `af-db` を使ってください（[DB を使うテストを回す](17-workspace-environment.ja.md#db-を使うテストを回す)）。
- **状態**はメモリ上にあり、サーバーを止めると消えます。`PERSIST_STATE=1` はサービスの状態を残しますが S3 の
  オブジェクトの中身は残さず、それには `S3_PERSIST=1` も要ります。どちらも既定の置き場は `/tmp` の下なので、
  `STATE_DIR` と `S3_DATA_DIR` を home の下のディレクトリにしてください。
- **エミュレーターです。** これで動いたテンプレートや IAM ポリシーが AWS では失敗することもあります。試行錯誤に使い、
  頼る前に本物を `af-aws-exec` で確かめてください。
