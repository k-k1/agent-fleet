  ADR 0081 決定 9 の残り半分（「塗るキャンバス」＝フェーズ P2）に対する設計案で、
  **ADR は書き換えていない**。§8 に利用者へ上げる判断が 6 件あり、そのうち 6 番目
  （訓練比率表の出所）は着工前の追加調査事項である。
- 前提として動いているもの: マスクを**パスで渡す**半分は入っている（PR #854）。
  `draft.mask`＋`op === "inpaint"` のときだけ出るパス欄＋マスク未指定では押せない投入ボタン。
  Agent 側の `inpaint` 宣言と配線は PR #853（`comfyQwenEditNoiseMask`）。
  **この設計案が作るのは「`draft.mask` に入るパスを生成する別経路」だけ**で、
  ワイヤも Agent も変更しない。
- 関連: `docs/decisions/0081-image-generation-pane.ja.md` の決定 9 とフェーズ P2（正本）/
  `docs/decisions/0094-instruction-edit-image-models.ja.md` の決定 3・未解決 2

## 1. 成果物の定義 (変えないもの)

- キャンバスが作る成果物は `draft.mask` に入る browse-root パス 1 本だけ。
- ワイヤ (`mask?: string`) も Agent (`comfyQwenEditNoiseMask`) も変更なし。
- 既存のパス欄 (PR #854, `InputPicker` max=1) は残す。キャンバスは「パスを生成する別経路」。
  パス欄との関係: キャンバス保存 → `patch({ mask })` でパス欄に反映。パス欄を手で変えたら
  キャンバス再開時はそのマスクを下絵として読み込む (読み込めなければ白紙 + 注意表示)。

## 2. 実測制約 → 設計要件 (5 件)

1. **同画素数**: 書き出す PNG は参照画像と同 W×H。qwen 族は不一致で Agent が 400。
   → 対策: 表示は縮小でも、書き出しは原寸 offscreen canvas にストロークを再描画。
   構造上不一致が出ない作りにする (リサイズ選択肢を出さない)。
2. **クロップ帯 (新規・最重要)**: `FluxKontextImageScale` が中央クロップしてから縮小する
   (実測: 1820×1024 → 1820×984 → 1392×752)。マスク座標自体は正しい (Agent 側で同ノードを
   通すため) が、利用者は「切られる帯に塗っても出力に存在しない」ことを知らない。
   → 対策は二択:
   - (A 推奨) **エンジン視点プレビュー**: クロップ後の領域だけをキャンバス背景にする。
     帯の分は表示しない。「塗った所 = 出力に存在する所」が自明。
   - (B) 全体表示 + 帯を暗幕。構図の全体は見えるが、「暗い所に塗れた」誤解が残る。
   推奨は (A)。ただし参照画像の全体確認が必要な場合は元画像へのトグルを付ける。
   計算は Agent と同一規則 (中央クロップ、最近傍の訓練比率) で行う必要があり、
   比率表は Agent の言葉 (`status` の `sizes` 等) から取る。自前表は持たない (決定 4 の原則)。
   **穴**: qwen 族の訓練比率一覧を Console が今日持っているか未確認。要確認。
3. **赤チャンネル + 不透明**: 白=塗り直し、`ImageToMask(channel:"red")`。
   `LoadImage` の MASK 出力は `1-alpha` のためアルファのみ PNG は全ゼロマスクになる。
   → 対策: 書き出し時は黒 (`#000`) で全面フィルしてから白ストロークを描く。
   `toBlob("image/png")` 前に `globalCompositeOperation` を確認し、透過を残さない。
   プレビュー表示と書き出しを同一コードパスにしない (表示は半透明オーバーレイ可)。
4. **latent 8px 刻み**: 1024² なら 128×128 が実効解像度。細い線の精度は嘘になる。
   → 対策: 筆の既定幅を太め (例: 原寸基準 24px 以上を既定)、細筆は選べても警告表示。
   にじみ (feather) は未測定 → ぼかしスライダは付けない (測ってから)。
5. **生成が遅い (150 秒/枚)**: 試行回数が UI の価値。
   → 対策: 「塗る→試走→塗り直す」の輪を切らない。キャンバスのストロークは試走後も保持
   (draft は localStorage に既存)、試走結果サムネイルをキャンバス脇に表示、
   マスク版管理はしない (上書き + やり直しで足りる。版管理は P2 後半の検討)。

## 3. 配置 (推奨: 生成ペイン内モーダルを先に)

- **P2a (先)**: 生成ペイン内、参照画像ブロック上の「マスクを塗る」ボタン → モーダル。
  理由: `draft`・`patch`・`needsMask` の文脈がそのまま使え、投入/試走ボタンとの距離が
  最短。既存の `InputPicker` の隣に置ける。
- **P2b (後)**: ギャラリー/ビュアー (ADR 0080) カードの「この部分を直す」。
  出来た絵を `inputs[0]` に写し、`op=inpaint` + キャンバス起動までを一気にやる導線。
  ギャラリー側の変更 (カードのボタン、`open.ts` の導線) が要るため分離する。
- モーダルにしない理由はない (決定 6 の「モーダルでなくペイン」はスタジオ全体の話で、
  塗りは一作業の集中画面。`ImageLightbox` の前例もある)。

## 4. タッチ/ポインタ (本体扱い)

- `PointerEvent` 一本化 (mouse/pen/touch)。`ImageView.tsx` の前例を再利用:
  ホイール/ピンチでズーム、ドラッグでパン、ダブルタップで 1×↔2.5×。
- モード分離が必須: **「描く」と「動かす (パン/ピンチ)」のモード切替**。
  推奨: 既定=描く、1 本指=描く、2 本指=常時パン/ピンチ (モード不問)、
  スマホ用の「移動モード」トグルを別途用意。`touch-action: none` はキャンバス要素のみ。
- 筆圧・パームリジェクションはやらない (P2 範囲外)。

## 5. 道具立て (推奨: 標準セット)

最小ではなく標準を推奨。理由は制約 5 (1 回 150 秒。戻す手段の欠如は試走を増やす)。

- 筆 (白で描く)、消しゴム (黒で描く = 実質「塗り戻し」)、取消 (undo, 20 手程度)、
  ズーム/パン (ImageView 流用)、筆太さ (3 段階で十分: 細/中/太 + 原寸換算表示)。
- やり直し (redo) は任意。取消スタックと対で持つだけなので、入れるなら同時。
  筆形 (円のみ。四角・ぼかしは入れない)。
- 「クリア」「元に戻す (初期マスクに戻す)」は別物として両方置く。

## 6. 保存フロー

1. 背景 = 参照画像 (`downloadURL(path)` の原寸。表示は縮小、座標は原寸換算)。
2. ストロークはベクタ保持 (`{x, y, w}` の配列、原寸座標)。表示 canvas と書出 canvas に再描画。
3. 保存時: 原寸 offscreen に黒フィル → 白ストローク再描画 → `toBlob` →
   `POST /fs/upload` → パスを `draft.mask` に。
4. **穴**: アップロード先。現行 `INPUT_DIR (generated/console/inputs/)` の再利用が最短だが、
   マスク専用 `generated/console/masks/` を切るかは要判断 (一覧の汚れ vs 変更の少なさ)。
   推奨は当面 `inputs/` 再利用 (変更最小。ギャラリーに混ざる問題はパス欄既存と同条件)。
5. `needsMask` の解除は保存成功時のみ。白紙保存は拒む (全黒 = 全ゼロマスクで「何も起きない」ため)。
   全消し保存も同様に警告する。

## 7. 試験方針 (実装時)

- 純関数: 中央クロップ矩形計算、原寸↔表示座標換算、ベクタ→ラスタ再描画の往復。
- DOM (`*.dom.test.tsx`): 白紙で保存不可、保存で `patch({mask})` が呼ばれる、
  モード切替、取消/やり直し。陽性対照あり (変異→赤→Edit で戻す)。
- 実機: 非正方形入力で「帯の外に塗っても効かない」ではなく「帯自体が塗れない」ことを目視。
- 型 `npx tsc --noEmit`、`console/` 固定で `npm test`。

## 8. 利用者への確認 (ADR を変えずに上げるもの)

1. 配置: P2a (ペインモーダル) 先行・P2b (ギャラリー「この部分を直す」) 後追いでよいか。
2. スマホ優先でよいか (タッチ対応を本体工数として見積もる)。
3. 道具は標準セット (筆/消し/取消/ズーム/パン/太さ3段) でよいか。やり直しは同時に入れるか。
4. アップロード先: `inputs/` 再利用でよいか、強いては `masks/` を切るか。
5. クロップ表示: (A) エンジン視点 (帯なし) 推奨でよいか、強いては (B) 暗幕か。
6. 訓練比率表を Console がどこから得るか (Agent `status` に無ければ Agent 側追加が要る)。
   → 6 は実装前の追加調査事項。

## 9. レビューで出た穴（別セッション `swizisl`・2026-09-22）

設計だけの段階で、別セッションに読み取り専用のレビューをかけた。**置き場所・番号・書式は先例
（103・106）と一致で合格**、中身は 🔴 2 件・🟡 3 件。以下は**この設計案の本文には手を入れず**、
着工前に決め直すべき点として残す。

🔴 **§2 の制約 2（クロップ帯）は、今日どちらの案も実装できない。** 案 A（エンジン視点プレビュー）も
案 B（暗幕）も「切られる帯がどこか」を知る必要があるが、その出所が無い。

- 設計案は「比率表は Agent の言葉（`status` の `sizes` 等）から取る」と書いたが、**この族の
  `sizes` は決定 4 で空に固定されている**（`comfy.go:605-609` の `comfySizesFor` が
  `comfyFamilyHasNoSizes` を見て `nil` を返す）。
- さらに **`PREFERRED_KONTEXT_RESOLUTIONS` はこのリポジトリに 1 か所も無い**（Go にも TS にも。
  親セッションが全文検索で確認）。ADR 0094 決定 4 はこの表を「v0.35.2 のノード定義を**読んだ**」
  と書いているだけで、機械が読める複製はどこにも無い。Agent 自身も知らない——枠の寸法を知るのは
  絵が返ってきた後である。
- したがって選択肢は「Console が自前表を持つ」「Agent が新しい欄で配る」「そもそも帯を見せない
  作りにする（入力の比率を先に整えさせる等）」のいずれかで、**設計の書き直しが要る**。
- 🔴 自前表を持つ案は ADR 0094 **決定 9 の 2 つ目の危険（「ピン留めが無意味になる」）**を
  そのまま踏む。この表は ComfyUI の版に属し、**ピンは実際に動いた**（ADR 0098 で 0.35.2 から
  引き上げ）。持つなら「版が動いたら検算する」までを設計に含める。

🔴 **§8 の 6 番は「利用者への確認」ではない。** 「訓練比率表をどこから得るか」は技術判断であって
利用者に問うものではない。上の穴と同じものなので、§8 から外して設計の課題として扱う。

🟡 残り 3 件（実装時に気をつける）:

- **ストロークの保存先が未設計**。`draft.ts` の `mask` はパス 1 本（512 文字上限）だけで、
  `{x, y, w}[]` を置く欄は無い。draft を広げるなら型・`parseDraft`・上限の再考が要る。
- **白紙・全消しの判定基準**が未明記（ストローク 0 件で見るか、画素が全黒かで見るか）。
  黒フィル後にストローク 0 なら実質同じだが、試験の書きやすさが変わる。
- **下絵の読み込み失敗の条件**が未定義。パスが無効（404）と寸法不一致（読めるが W×H が違う）は
  別物で、後者を「白紙で開く」か「拡縮して使う」かは判断が要る。
