## 1. 成果物の定義 (変えないもの)

- キャンバスが作る成果物は `draft.mask` に入る browse-root パス 1 本だけ。
- ワイヤ (`mask?: string`) も Agent (`comfyQwenEditNoiseMask`) も変更なし。
- 既存のパス欄 (PR #854, `InputPicker` max=1) は残す。キャンバスは「パスを生成する別経路」。
  パス欄との関係: キャンバス保存 → `patch({ mask })` でパス欄に反映。パス欄を手で変えたら
  キャンバス再開時はそのマスクを下絵として読み込む (読み込めなければ白紙 + 注意表示)。

## 2. 実測制約 → 設計要件 (5 件)

1. **同画素数**: 書き出す PNG は参照画像と同 W×H。qwen 族は不一致で Agent が 400。
   → 対策: 表示は縮小でも、書き出しは原寸 offscreen canvas にストロークを再描画。
   構造上不一致が出ない作りにする (リサイズ選択肢を出さない)。
   🔄 改訂（2026-09-23）: 寸法が違っても断られなくなった。要るのは「同じ縦横比」だけ（§10.2・§10.3）。
2. **クロップ帯 (新規・最重要)**: `FluxKontextImageScale` が中央クロップしてから縮小する
   (実測: 1820×1024 → 1820×984 → 1392×752)。マスク座標自体は正しい (Agent 側で同ノードを
   通すため) が、利用者は「切られる帯に塗っても出力に存在しない」ことを知らない。
   → 対策は二択:
   - (A 推奨) **エンジン視点プレビュー**: クロップ後の領域だけをキャンバス背景にする。
     帯の分は表示しない。「塗った所 = 出力に存在する所」が自明。
   - (B) 全体表示 + 帯を暗幕。構図の全体は見えるが、「暗い所に塗れた」誤解が残る。
   推奨は (A)。ただし参照画像の全体確認が必要な場合は元画像へのトグルを付ける。
   計算は Agent と同一規則 (中央クロップ、最近傍の訓練比率) で行う必要があり、
   比率表は Agent の言葉 (`status` の `sizes` 等) から取る。自前表は持たない (決定 4 の原則)。
   **穴**: qwen 族の訓練比率一覧を Console が今日持っているか未確認。要確認。
   🔄 改訂（2026-09-23）: **対象が消えた。** 入力は切られず全体が縮む。A も B も比率表も要らない（§10.2）。
3. **赤チャンネル + 不透明**: 白=塗り直し、`ImageToMask(channel:"red")`。
   `LoadImage` の MASK 出力は `1-alpha` のためアルファのみ PNG は全ゼロマスクになる。
   → 対策: 書き出し時は黒 (`#000`) で全面フィルしてから白ストロークを描く。
   `toBlob("image/png")` 前に `globalCompositeOperation` を確認し、透過を残さない。
   プレビュー表示と書き出しを同一コードパスにしない (表示は半透明オーバーレイ可)。
4. **latent 8px 刻み**: 1024² なら 128×128 が実効解像度。細い線の精度は嘘になる。
   → 対策: 筆の既定幅を太め (例: 原寸基準 24px 以上を既定)、細筆は選べても警告表示。
   にじみ (feather) は未測定 → ぼかしスライダは付けない (測ってから)。
5. **生成が遅い (150 秒/枚)**: 試行回数が UI の価値。
   → 対策: 「塗る→試走→塗り直す」の輪を切らない。キャンバスのストロークは試走後も保持
   (draft は localStorage に既存)、試走結果サムネイルをキャンバス脇に表示、
   マスク版管理はしない (上書き + やり直しで足りる。版管理は P2 後半の検討)。

## 3. 配置 (推奨: 生成ペイン内モーダルを先に)

- **P2a (先)**: 生成ペイン内、参照画像ブロック上の「マスクを塗る」ボタン → モーダル。
  理由: `draft`・`patch`・`needsMask` の文脈がそのまま使え、投入/試走ボタンとの距離が
  最短。既存の `InputPicker` の隣に置ける。
- **P2b (後)**: ギャラリー/ビュアー (ADR 0080) カードの「この部分を直す」。
  出来た絵を `inputs[0]` に写し、`op=inpaint` + キャンバス起動までを一気にやる導線。
  ギャラリー側の変更 (カードのボタン、`open.ts` の導線) が要るため分離する。
- モーダルにしない理由はない (決定 6 の「モーダルでなくペイン」はスタジオ全体の話で、
  塗りは一作業の集中画面。`ImageLightbox` の前例もある)。

## 4. タッチ/ポインタ (本体扱い)

- `PointerEvent` 一本化 (mouse/pen/touch)。`ImageView.tsx` の前例を再利用:
  ホイール/ピンチでズーム、ドラッグでパン、ダブルタップで 1×↔2.5×。
- モード分離が必須: **「描く」と「動かす (パン/ピンチ)」のモード切替**。
  推奨: 既定=描く、1 本指=描く、2 本指=常時パン/ピンチ (モード不問)、
  スマホ用の「移動モード」トグルを別途用意。`touch-action: none` はキャンバス要素のみ。
- 筆圧・パームリジェクションはやらない (P2 範囲外)。

## 5. 道具立て (推奨: 標準セット)

最小ではなく標準を推奨。理由は制約 5 (1 回 150 秒。戻す手段の欠如は試走を増やす)。

- 筆 (白で描く)、消しゴム (黒で描く = 実質「塗り戻し」)、取消 (undo, 20 手程度)、
  ズーム/パン (ImageView 流用)、筆太さ (3 段階で十分: 細/中/太 + 原寸換算表示)。
- やり直し (redo) は任意。取消スタックと対で持つだけなので、入れるなら同時。
  筆形 (円のみ。四角・ぼかしは入れない)。
- 「クリア」「元に戻す (初期マスクに戻す)」は別物として両方置く。

## 6. 保存フロー

1. 背景 = 参照画像 (`downloadURL(path)` の原寸。表示は縮小、座標は原寸換算)。
2. ストロークはベクタ保持 (`{x, y, w}` の配列、原寸座標)。表示 canvas と書出 canvas に再描画。
3. 保存時: 原寸 offscreen に黒フィル → 白ストローク再描画 → `toBlob` →
   `POST /fs/upload` → パスを `draft.mask` に。
4. **穴**: アップロード先。現行 `INPUT_DIR (generated/console/inputs/)` の再利用が最短だが、
   マスク専用 `generated/console/masks/` を切るかは要判断 (一覧の汚れ vs 変更の少なさ)。
   推奨は当面 `inputs/` 再利用 (変更最小。ギャラリーに混ざる問題はパス欄既存と同条件)。
5. `needsMask` の解除は保存成功時のみ。白紙保存は拒む (全黒 = 全ゼロマスクで「何も起きない」ため)。
   全消し保存も同様に警告する。

### 10.1 今の Agent が保証していること（キャンバスの土台）

コードで確かめた（develop `542eb6049`）:

- **マスクは「絵の同じ相対領域」**——全ファミリー共通（`comfy.go` の `Generate`、マスクのアップロード直後の注釈）。
  寸法が絵と違うマスクも断られない。
- **指示編集（2509/2511）**: 絵は `comfyQwenEditSize`（`comfy_qwenedit_size.go`）が返す寸法へ
  `ImageScale(lanczos, crop="disabled")` で**全体が縮む**。比率の歪みは 1:4〜4:1 で最大 1.52%。
  マスクは `LoadImage → ImageToMask(red) → SetLatentNoiseMask`（`comfyQwenEditNoiseMask`）で latent へ
  一様に引き伸ばされる。絵も一様な縮小なので、2 つの写像は一致する。実測: 1820×1024 で境界のずれ 3 px
  （log 112 §14 (c)。塗り替えの遷移帯の幅の内）。
- **他の ComfyUI ファミリー**（sdxl 等、`comfyRequestLatent`）: 絵は縮めずにそのまま `VAEEncode`、マスクは
  `LoadImageMask(red) → SetLatentNoiseMask` で同じく引き伸ばされる。
- **向き**: ComfyUI の `LoadImage` は `ImageOps.exif_transpose` をかける——絵にもマスクにも。Agent は寸法を
  向きの適用後の値で読む（`comfy_picture_size.go` の `comfyPictureSize`。Orientation 5〜8 で幅と高さを入れ替える）。
  実測: Orientation 6 の JPEG は縦の 752×1400 で返る（log 112 §14 (f)）。
- **保証していない経路**: `openai_compat`（sd-server）も `inpaint` を名乗る（`openai_compat.go` の `Caps`）が、
  マスクは届いたまま転送するだけである。寸法の違うマスクと、EXIF で回転した入力をあちらのサーバがどう扱うかは
  誰も測っていない（§10.8）。

| 4. latent の 8 px 刻み | **生きているが、物差しが変わった** | 下の注を参照 |
| 5. 1 枚 150 秒 | **そのまま** | 試行の輪を切らない |

**制約 4 の物差し。** §2 は「原寸基準 24 px 以上」と書いたが、原寸の 1 px は latent の同じ量ではない:

- 指示編集では latent は**縮めた後の寸法**（約 1 MP）の 1/8 である。4032×3024（4:3 のスマホ写真）は
  1184×888 へ縮むので、latent の 1 マスは**入力の約 27 px**。1820×1024 なら約 10.6 px。
- 他の ComfyUI ファミリーは絵を縮めないので、latent の 1 マスは入力の 8 px のままである。

同じ「24 px」が、族と入力によって 1 マスの 1/3 にも 3 マスにもなる。**筆の太さは絵の長辺に対する比で持つ**
（例: 細 1.5%・中 3%・太 6%。1184 幅なら 18・36・71 px＝約 2・4・9 マス）。細筆の警告も「長辺比がいくつ未満」で
出す。数値は実装時に 1 か所の定数で決める（技術判断）。

**消えたもの**: §2 の案 A・B とその比率表、§3 の「元画像へのトグル」の理由（案 A で帯を隠すための逃げ道だった）、
§7 の「中央クロップ矩形計算」と実機の「帯自体が塗れない」、§8 の 5・6、§9 の 🔴 2 件。

### 10.3 書き出しの寸法

候補は 3 つある:

- (a) **原寸**＝向きを適用した後の `naturalWidth × naturalHeight`。
- (b) **比率だけ揃える**（長辺を固定値、例えば 2048 へ）。
- (c) **原寸。ただしキャンバスの面積の上限を超えるときだけ、比率を保って上限まで縮める。**

ComfyUI のファミリーはどれでも通る（§10.1）。ただし (b) は「マスクは引き伸ばされる」に頼りきりで、sd-server の
経路（§10.8、未測定）ではそれが保証されていない。(a) は Agent の写像を何も仮定しないが、ブラウザにはキャンバスの
面積の上限がある。iOS Safari の値として広く知られているのは 16,777,216 px（4096²）で、2400 万画素級の写真
（5712×4284 など）はこれを超える（**この環境では確かめられない**）。

→ **(c) を採る（技術判断）。** 上限以下の入力（ほとんどの入力）は原寸なので、どの経路でも寸法が揃う。上限を
超えるときだけ縮め、そのとき縦横比の誤差は丸めの 0.5 px 以下——latent の 1 マス（入力で 8〜27 px 以上）より
ずっと小さい。上限は定数 1 つで持ち、超えたかどうかは寸法から判断する（キャンバスの失敗を当てにしない）。
書き出しは §6 と同じく「黒で全面 → 正規化座標のストロークを書き出し寸法で描き直す」。

### 10.4 向き（EXIF）——headless Chromium での実測

ブラウザは `<img>` と `drawImage` に EXIF の向きを既定でかける（`image-orientation: from-image`）。ComfyUI の
`exif_transpose` と本当に同じ向きになるかを、この Workspace で測った（Chromium 153・2026-09-23）。

入力: PIL で作った JPEG。保存上は 400×200（左半分が赤・右半分が青）で、Orientation=6。
PIL の `ImageOps.exif_transpose`（`LoadImage` が使うもの）の答えは **200×400・上半分が赤**。

| 読み方 | 報告された寸法 | `drawImage` した結果 |
|---|---|---|
| 文書内の `<img>` | natural 200×400・表示 200×400 | 上が赤・下が青 |
| 切り離した `new Image()` | 200×400 | 上が赤・下が青 |
| `createImageBitmap(blob)`（既定） | 200×400 | 上が赤・下が青 |
| `createImageBitmap(blob, {imageOrientation: "none"})` | 200×400（この版では既定と同じ寸法を報告した） | — |
| 🔴 CSS `image-orientation: none` の `<img>` | natural 200×400・**表示は 400×200** | **上が赤・下が青** |

- **Chromium では、利用者が見る向き＝`drawImage` の向き＝`exif_transpose` の向き**になる。キャンバスは
  「見えている向きで塗らせ、`naturalWidth/Height` で書き出す」でよい。
- 🔴 **罠が 1 つある**: 背景の `<img>` に `image-orientation: none` が付くと、**見える絵だけ**が横倒しになり、
  `naturalWidth` と `drawImage` は縦のままになる——利用者は横倒しの絵に塗り、マスクは縦で書き出される。
  Console に今この指定は 1 つも無い（`console/src` を grep して 0 件）。背景に向きの指定を付けないこと、を
  実装の注釈と試験（§10.7）に入れる。
- 最後の行は陽性対照を兼ねる: 同じファイルで表示の寸法が変わったので、この測り方は向きの違いを見分けられる。
- **測っていないこと**: 実機の iOS Safari・Android Chrome。どちらも `from-image` を既定にしていると言われるが、
  この環境では確かめられない。確かめ方は §10.7。

### 10.5 §9 の 🟡 3 件と 🔵 1 件への答え（技術判断として決める）

1. **ストロークの持ち方と置き場。** 座標は**絵に対する比（0〜1）**、太さは**長辺に対する比**で持つ。表示・書き出し・
   縮小のどれとも独立になり、「相対領域」という Agent の意味とも一致する。
   置き場は **`draft` に足さない**。持続する状態は**保存した PNG そのもの**とし、キャンバスを開き直したら PNG を
   下絵（ラスタの層）として読み、新しいストロークはその上に描く。取消は開いている間だけで、下絵が取消の底になる。
   `draft` の型・`parseDraft`・512 文字上限（§9 の 🟡）には触らずに済み、「試走後も保持」（§2-5）は PNG が満たす。
   失うのは、閉じた後の取消の履歴だけである（利用者への確認 §10.9-5）。
   並走する画像生成スタジオの設計（log 113 D13。`temp/s24yagr`・未マージ）はストロークをスタジオの
   `mask_strokes` に置く案を出している。スタジオが入れば、正規化座標のベクタをそこへ持っていける。この設計は
   それを前提にしない。
2. **白紙・全消しの判定は画素で見る。** 下絵がラスタで消しゴムもあるので、ストロークの数では判定できない。
   書き出したキャンバスの赤チャンネルに 0 でない画素が 1 つも無ければ白紙として保存を拒む（全ゼロのマスクは
   「何も起きない」）。ほぼ全面が白なら警告だけ出す（マスク無しの edit とほぼ同じになる。しきい値は定数 1 つ）。
   試験は純関数（画素列 → 白紙／全面／普通）で書ける。
3. **下絵の読み込み失敗。** 失敗は「読めない」だけになった:
   - 404・デコードできない → 白紙で開き、注意を出す（§1 のまま）。
   - **寸法が違う → 失敗ではない。** 絵の枠へ引き伸ばして重ねる。Agent が生成でやる写像と同じなので、見える通りに
     効く。縦横比が絵と 1% 以上違うときだけ「このマスクは絵と縦横比が違う。生成でも同じく引き伸ばされる」と出す
     （パス欄で別の絵のマスクを選んだ、参照画像を差し替えた、の 2 つが典型）。保存すれば §10.3 の寸法で書き直される。
   - 下絵は**赤チャンネルを読んで**重ねる。見た目の色ではなく、Agent が読む値を見せるため
     （白黒以外の PNG をパス欄に置かれたとき、見た目と効き方がずれない）。
4. 🔵 `ImageView.tsx` の流用（モーダル内のポインタとスクロールの干渉）は変わらず実装時に確かめる。

### 10.6 変わらないもの

§3（配置）・§4（ポインタ）・§5（道具）・§6 の流れ（背景 → ストローク → 黒フィル＋白で書き出し →
`POST /fs/upload` → `patch({ mask })`、`needsMask` の解除は保存が成功したときだけ）。§6 の「座標は原寸換算」は
§10.5-1 の正規化座標に置き換わる。

### 10.7 試験方針（§7 を差し替える）

- **純関数**: 正規化座標 ↔ 表示座標 ↔ 書き出し座標、書き出し寸法（上限以下は原寸、超えたら比率を保って縮め、
  比の誤差は 0.5 px 以下）、白紙判定、長辺比の筆の太さ。
- **DOM**（`*.dom.test.tsx`）: 白紙で保存できない、保存で `patch({ mask })` が呼ばれる、寸法の違う下絵が断られずに
  引き伸ばされ注意が出る、404 の下絵で白紙＋注意、モード切替、取消。陽性対照あり（変異 → 赤 → Edit で戻す）。
- **向き（headless Chromium）**: §10.4 と同じ Orientation 6 の JPEG を背景に、上 1/4 を塗って書き出し、PNG の
  上 1/4 が白であること。**陽性対照**: 背景に `image-orientation: none` を付ける変異で、見た目の上 1/4 と書き出しが
  ずれて赤くなること。jsdom はレイアウトも EXIF も持たないので、ここは DOM 試験では代われない。
- **実機（スマホ対応を名乗る前）**: iPhone の Safari と Android の Chrome で縦に撮った JPEG を参照画像にし、
  上 1/4 を塗って指示編集の inpaint を 1 回。出力の上 1/4 だけが塗り替わること。境界のずれは log 112 §14 (c) と
  同じ測り方で、遷移帯の内に収まること。
- **実機（非正方形）**: 16:9 と 3:1 の入力で同じことを 1 回ずつ（帯が無くなったので、端に塗っても効くこと）。
- 型 `npx tsc --noEmit`、`console/` を作業ディレクトリにして `npm test`。

### 10.8 残る穴

- 🟡 **sd-server（`openai_compat`）の経路は未測定。** この経路も `inpaint` を名乗り、マスクをそのまま送る。
  (1) 寸法の違うマスクを受け付けるか、(2) EXIF で回転した JPEG を回して読むか、の 2 点を誰も確かめていない。
  (2) を回さずに読むなら、利用者が縦に見て塗ったマスクと、あちらの横倒しの絵が食い違う。(c) の寸法規則なら、
  上限以下の入力で (1) は起きない。(2) は、キャンバスを出す前に 1 組測るか、測るまで**キャンバスを ComfyUI の
  経路に限る**（技術判断。どちらを取るかは実装の着手時に決める）。
- 🟡 **キャンバスの面積の上限は確かめていない**（§10.3）。値を決めるときに実機で 1 回測る。
- 🟡 **別件（この設計の外・Agent 側）: 指示編集の inpaint は再現情報からマスクが落ちる。** `props.go:479` は
  `LoadImageMask` のノードだけを探すが、この族のマスクは `maskimg`（`LoadImage`）→ `mask`（`ImageToMask`）で、

  ギャラリーから設定を再利用すると、マスク無しの edit として走り直す。PR #853 からの問題でクロップとは関係ない
  （コードを読んで確かめた。実行はしていない）。「この部分を直す」（§3 の P2b・log 113 D13）の導線が再現情報を
  使うなら、その前に直す。直し方は `ImageToMask` を辿って `maskimg` の `image` を読むこと。
- 🔵 log 113（未マージ）が 111 を参照している箇所（D13・§8-5）は、この改訂で「帯の問題に戻る」心配が無くなった。
  あちらの本文を直すのはあちらのセッションの仕事で、ここでは触らない。

### 10.9 利用者に確認すること／技術的に決めること

**利用者に確認すること**（使い方と好みの問題で、コードからは決まらない）:

1. **配置**（§8-1 のまま）: P2a（生成ペインのモーダル）を先、P2b を後でよいか。P2b の入口を
   ギャラリーではなくスタジオの結果カードに置く案（log 113 D13）もある。
2. **スマホを優先するか**（§8-2 のまま）。優先するなら §10.7 の実機 2 台の確認が出荷の条件になる。
3. **道具**（§8-3 のまま）: 標準セット（筆・消し・取消・ズーム・パン・太さ 3 段）でよいか。やり直しも同時に入れるか。
4. **アップロード先**（§8-4 のまま）: `inputs/` の再利用でよいか、`masks/` を分けるか。
5. **（新規）閉じた後の取消**: 開き直したマスクは 1 枚の下絵になり、前回のストロークを 1 本ずつは戻せない（§10.5-1）。
   これでよいか。推奨: よい（戻したければ消しゴムで消す。1 本ずつ戻したい需要が出たらスタジオの `mask_strokes` へ）。
6. **（新規）元画像トグル**: 元の理由（帯を隠す案 A で全体を見る逃げ道）は消えた。残るのは「マスクを隠して下の絵を
   見る」だけ。推奨: トグルではなく**押している間だけマスクを隠す**ボタン 1 つ。付けないでもよい。

**技術的に決めること**（ここで決めた。利用者には問わない）:

- 書き出しの寸法: (c) 原寸、キャンバスの面積の上限を超えたら比率を保って縮める（§10.3）。利用者から見える違いは
  アップロードの大きさだけで、正しさは経路の性質で決まる。
- 座標は正規化（0〜1）、筆の太さは長辺比（§10.2・§10.5-1）。
- 向き: 背景は `<img>`／`drawImage` の既定のまま、寸法は `naturalWidth/Height`。`image-orientation` を指定しない（§10.4）。
- 白紙の判定は画素（§10.5-2）。寸法の違う下絵は引き伸ばして使い、比が 1% 以上違えば注意（§10.5-3）。
- 比率表は持たない（要らなくなった）。
- sd-server の経路を測るか、キャンバスを ComfyUI に限るか（§10.8）——着手時に決める。
- 再現情報でマスクが落ちる別件（§10.8）は Agent 側の修正として別に起票する。
