## 115.1 依頼時の表の読み直し

依頼では、セッションを消す経路を 3 つとしていた。コードで読み直すと、**入口は 7 つ、メタを忘れる
関数は 3 つ**で、表の 1 行目は前提が違っていた。

### 115.1.1 メタを忘れる 3 つの関数

| 関数 | 呼ぶ経路 | メタ | 会話ログ（claude の jsonl） | side files ※1 | 端末履歴 | worktree | ごみ箱 |
|---|---|---|---|---|---|---|---|
| `HandleStopSession`（`session_handlers.go:1296`） | `POST /sessions/{name}/stop` | 消す | **残る** | **残る** | 消す | **`MaybePruneWorktree`（:1348）で消すことがある** | 通らない |
| `handleDeleteSession` の reclaim なし（`cleanup_ops.go:80`） | `DELETE /sessions/{name}` | 消す | 残る | 消す | 残る | 触らない | 通らない |
| `handleDeleteSession` の `?reclaim=1`（`cleanup_ops.go:84`） | `DELETE /sessions/{name}?reclaim=1` | 消す | 退避してから消す | 消す | **残る** | 触らない | **通る** |
| `forgetNonLiveMetasUnder`（`gitx/git.go:1681`） | `DELETE /repos/{name}?prune_sessions=1` | 消す（停止中・未アーカイブ・未ロックだけ） | 残る | 残る | 残る | （WT 自体を消した後） | 通らない |

### 115.1.3 依頼の前提と違っていたこと

1. **セッション行の「削除」は AI セッションに出ない。** 出るのは shell / ssm だけで、AI セッションの
   行にはアーカイブが出る。この UI は 2026-07-07 の Console 再構築（489965120）からそうなっている。
   だから**行の削除が「jsonl を残してメタだけ消す」のは、今は起きない**。shell / ssm には jsonl が
   無い。行の削除で失われるのはメタと**端末履歴**（`removeTerminalHistory`、1 セッション 4 MiB まで、
   `terminal_history.go:19`）で、ごみ箱には入らない。
2. **AI セッションを `/stop` で消す入口は、スタジオの切り替え（5）だった。** メタは消え、会話ログは
   残り、ごみ箱には入らない。さらに `MaybePruneWorktree` が、前のセッションの worktree を消すことが
   ある（そのメタが最後の参照で、クリーンで先行コミットも無いとき）。スタジオを worktree で起動していれば
   条件が揃う。**実機では確かめていない**。
3. **worktree の削除で AI セッションを忘れる入口は、掃除モーダル②と MCP の 2 つ（6・7）。** 左ペインの
   「作業コピーを削除」（4）は、先に AI セッションを棚へ移し、`prune_sessions` を付けずに消す。
   **worktree を消すときはセッションを棚へ移す、という形は、この入口で既に実装されている。**
4. **`prune_sessions` を付けない worktree 削除は、メタを残す。** Dir の無いメタが一覧に残り、行は
   「フォルダがありません（再開できません）」になる。4 は先に棚へ移すのでこうならないが、Agent の
   `DELETE /repos` を直接呼ぶとこうなる。
5. **reclaim の経路は、`/stop` がする後始末を全部はしない。** 端末履歴と、managed 系 kind の
   ClientMessageID 台帳（`removeManagedLedger`）を消さない。逆に `/stop` は side files を消さない。
   今は、消す経路によって残るものが違う。
6. **ADR 0097 の背景は当時から不正確だった。** 「自動 prune だけが、ごみ箱を通らない唯一の削除だった」と
   書いているが、同じ時点で `/stop` と `prune_sessions` もごみ箱を通っていなかった。決定 2 の
   「『削除は常に gz 退避経由』がこれで例外なく真になる」も成り立っていない。
7. **CP の監査ログは `/stop` を `session.stop` として記録する**（`control-plane/proxy.go:85`）。
   `DELETE /api/sessions/{name}` は記録しない（DELETE で監査するのは `/api/repos/{name}` など）。
   行の削除を DELETE に替えると、**監査の記録が消える**。

### 115.1.4 そのほか確かめた事実

- **`MaybePruneWorktree` を呼ぶのは `/stop` だけ**（`session_handlers.go:1348`）。ADR 0097 決定 5 で
  TTL の掃引（`:222` のコメント）からは外れたが、人の削除にはまだ付いている。アーカイブ（`HandleArchiveSession`）は呼ばない。
- **ごみ箱からの復元は、メタを削除した時点のまま書き戻す**（`restoreCleanupArchive`、
  `CreateMetaIfAbsent`）。`Archived` も含めて戻るので、棚から消したものは棚に、一覧から消したものは
  一覧に戻る。Dir が無ければ「フォルダがありません」になり、再開はできない（`agents.DirGoneErr`。
  7 つの kind のドライバがこのエラーで起動を断る）。会話は読める（`DirGoneNotice`、
  `ComposerNotices.tsx:9`）。claude の会話ログは sid の glob で探す（`TranscriptRead` →
  `jsonlByMtime`）ので、Dir が無くても見つかる。
- **claude 以外の kind は、ごみ箱に入るのはメタだけ**（`archiveSessionForDelete`）。codex の rollout や
  opencode の sqlite は各 CLI の保存先に残り、容量は回収されない。
- **キャッシュの孤児判定**（ADR 0097 追記、`cache_orphans.go`）は、「どのメタにも、ごみ箱のどの
  アーカイブにも、フォーク系譜にも無い UUID」を孤児とみなす。今の `/stop` と `prune_sessions` の後は、
  **そのセッションの貼り付け画像がすぐ掃除の対象になる**。ごみ箱を通せば、アーカイブを完全削除する
  まで守られる。
- **side files のコメント（`cleanup_ops.go:103`）は「セッション名は再利用される」を前提にしている。**
  これは誤りで（名前は再利用されない乱数スラグ）、ADR 0097 の「剥がれるコメント」にも挙がっていない。

## 115.2 問題の整理

1. **削除がごみ箱を通るかどうかが、入口で決まっている。** 利用者から見て同じ「消す」なのに、行の削除
   （shell/ssm）・スタジオの切り替え・掃除② / MCP の worktree 削除は戻せず、棚と掃除①の削除は戻せる。
   ガイドは「消しすぎても戻せます」と書き（`02-sessions.md:301` / `.ja.md:281`）、行の確認ダイアログは
   「取り消せません」と書く。どちらも一部だけ正しい。
2. **戻せない削除が、容量も回収しない。** `/stop` と `prune_sessions` はメタだけを消し、会話ログと
   side files を残す。行が無いので、利用者には存在が見えず、消す手段も無い。
3. **停止・削除と worktree の片付けが絡み合っている。**
   - セッションを消すと worktree が消えることがある（`/stop` → `MaybePruneWorktree`）。
   - worktree を消すとセッションが消えることがある（`prune_sessions=1`）。
   - エンドポイント名の `/stop` は、実際には「削除」をする。「停止」は `/halt` である。
4. **消す経路によって、後始末の中身が違う**（115.1.3 の 5）。

## 115.3 提案

### D1 — セッションを消す操作は 1 つにする：「ごみ箱へ移す」

Agent に `trashSession(m)` を 1 つ作り、**メタを忘れる経路は例外なくこれを通す**。
中身は今の reclaim 経路に、`/stop` にだけあった後始末を足したものになる。

1. 稼働中なら止める（halt と同じ順序で、キャリーオーバーの昇格 → 接続の切断 → kill または DropHandle）。
   **止めてよいかは呼ぶ側が決める**：行の削除は確認ダイアログを出すので止めてよい。掃除①と
   `delete_session` は今どおり、稼働中なら 409 で断る。
2. `finalizeSessionUsage`。
3. `archiveSessionForDelete` で、メタ・会話ログ（claude）・**端末履歴（新規）**を 1 つの gz に入れる。
4. 退避が済んでから、会話ログ・メタ・系譜・side files・端末履歴・managed 台帳・status の各記録を消す。
5. **worktree には触らない**（D3）。

`/stop` と `DELETE /sessions/{name}`（reclaim の有無を問わない）は、どちらも `trashSession` を呼ぶ。
**古い Console が `/stop` を呼んでも、ごみ箱に入る。** Console のバンドルは CP が配るので、Agent と
版がずれることがあり、その場合も安全側に倒れる。`/stop` という名前は互換のためだけに残し、新しい
Console は `DELETE /sessions/{name}?stop=1`（稼働中なら止めてから）を使う。CP の監査は
`DELETE /api/sessions/{name}` を `session.delete` として記録するよう足す（115.1.3 の 7）。

**端末履歴をごみ箱に入れる理由。** shell / ssm にとって、端末履歴は会話ログにあたる唯一の中身である。
上限は 1 本 4 MiB で、テキストなので gz がよく効く（**推測**：実測はしていない）。入れないなら
shell のごみ箱は「メタが戻るだけ」になり、復元する意味がほとんど無い。

### D2 — Console の行メニュー：出す項目は今のまま、「削除」の意味をごみ箱へ変える（問い 1）

| 行の種類 | 今 | 提案 |
|---|---|---|
| AI セッション | 停止／アーカイブ／作り直し（削除なし） | **変えない** |
| shell / ssm | 停止／削除（`/stop`、取り消せない） | 停止／**削除（ごみ箱へ）** |

- 確認ダイアログ（`sess.delete_body`）: 「『{name}』をごみ箱へ移します。掃除のごみ箱から復元できます。」
- 入口 2〜4（まとめて整理・孤児整理・作業コピー削除）の shell/ssm も `/stop` をやめ、同じ削除を呼ぶ。
  文言の「破棄」「取り消せません」（`rp.del.summary_forget`、`sess.tidy_orphans_irreversible` など）も直す。
- 入口 5（スタジオの切り替え）は、前のセッションを**棚へ移す**（`/archive`）。スタジオの結び付けは
  既に外れているので、会話は棚から読める。消すかどうかは、ほかのセッションと同じく人が棚で決める。

**AI セッションの行に「削除」を足さない理由。** 行から一度で消せると、ADR 0097 の「残したいなら棚、
消したいなら棚から削除」という 2 段が崩れる。今の利用者は、行の削除が無いことで困っていない
（棚からの削除は既にある）。ごみ箱を通すなら戻せるので、足しても危険ではない。ただし今回の目的
（すべての削除をごみ箱に通す）には要らないので、判断 2（§7）として分けた。

### D3 — セッションを消しても worktree は消さない

`/stop` から `MaybePruneWorktree` を外す（呼び手はこれで 0 になるので、関数ごと消す）。
worktree を消すのは、掃除②・作業コピーの削除・MCP `delete_worktree` だけにする。

- **代償**: 最後の shell セッションを消した worktree は、自動では消えなくなる。ADR 0097 決定 5 が TTL の
  掃引で受け入れたのと同じ代償で、片付けは掃除②に任せる。AI セッションの行には削除が無いので、
  今この自動片付けが働くのは shell/ssm の削除とスタジオの切り替えだけ（115.1.4）で、影響は小さい。
- **利点**: ごみ箱からセッションを戻したとき、作業場所がまだある。今は、戻したセッションの worktree が
  消えている、ということが起こりうる。

### D4 — worktree の削除は、中のセッションを棚へ移す。ごみ箱には入れない（問い 2）

`forgetNonLiveMetasUnder` を `shelveSessionsUnder` に置き換える。中身は入口 4（作業コピーの削除）が
Console 側で既にしていることを、Agent 側で全入口に揃えるもの。

| worktree の中のセッション | 今（`prune_sessions=1`） | 提案 |
|---|---|---|
| 稼働中 | 削除そのものを 409 で断る | 変えない |
| ロック済み | 削除そのものを 403 で断る | 変えない |
| 棚にある | 触らない | 変えない |
| 停止中の AI セッション | メタを忘れる（ごみ箱なし） | **棚へ移す**（`Archived = true`） |
| 停止中の shell / ssm | メタを忘れる（ごみ箱なし） | **ごみ箱へ**（D1。作業場所が無いと再開しても意味が無い） |

- **`prune_sessions` の有無で動きを変えない。** Agent は常にこれをする。付けない呼び出し（入口 4）でも、
  Dir の無いメタが一覧に残らなくなる（115.1.3 の 4）。入口 4 の Console 側の archive は冗長になるが、
  害は無いので残してよい（進捗を行ごとに出すため）。
- **棚へ移す理由（ごみ箱ではなく）**: 利用者の方針 2（worktree とセッションは別の操作）。worktree を
  消す人が決めたのは作業コピーのことで、会話を捨てるかどうかではない。会話を捨てるのは、棚からの
  削除という別の操作にする。ADR 0097 決定 1 の「自動や巻き添えでは移動だけ、削除は人がそのものに対して」
  とも同じ考え方になる。
- **選ばせない理由**: 選択肢を足すと、確認ダイアログとツールの引数が増える。棚からごみ箱へは 1 押しで
  移せるので、選ばせて得られるのは「1 押し減る」ことだけ。§7 判断 3 で確認する。

**worktree が消えた後のセッションの見え方**（今のコードのまま変わらないもの）:

- 棚の行: 会話は読める。「フォルダがありません（再開できません）」になり、再開ボタンは出ない。
- 棚から一覧へ戻した行: 取り消し線で「フォルダがありません」。クリックできない。
- ごみ箱から復元した行: 削除時の `Archived` のまま戻り、見え方は上の 2 つと同じ。
- 再開: できない（`DirGoneErr`）。**ブランチはまだあるので（`delete_branch` するまで）、同じパスに
  worktree を作り直せば再開できるはず**だが、これは**推測**である。sid は `UUID(dir, name)` なので、
  同じパスでなければ claude は同じ会話を引けない。「worktree を作り直して再開する」導線は、この提案の
  範囲外とする（§8）。

### D5 — MCP とオペレーター（問い 3）

| ツール | 今 | 提案 |
|---|---|---|
| `delete_session` | `?reclaim=1`（ごみ箱あり） | 変えない（中身は D1 の `trashSession` になる） |
| `delete_worktree` | `?prune_sessions=1`（停止中を忘れる） | 中のセッションを棚へ移す（D4）。**説明文を直す**：「削除でその worktree に紐づく停止中セッションも一覧から整理される」→「停止中の AI セッションは棚へ移り、shell/ssm はごみ箱へ入る。どちらも復元できる」 |
| `stop_session` | `/halt`（再開できる） | 変えない |
| `archive_session`・`restore_cleanup_archive`・`purge_cleanup_archive` | — | 変えない |

- **権限は変えない。** どれも `writeEnabled()` のオペレーターだけに見え、セッション（子を含む）には
  見えない（ADR 0073）。
- **承認も変えない。** `bridgeApprovalGate` は Discord から動くオペレーターのターンだけで承認ボタンを出し、
  Console のチャットでは何もしない（`bridge_approval.go:132`）。`delete_worktree` から戻せない副作用が
  1 つ減るが、作業コピーそのものは戻せないので、承認は外さない。
- 新しいツールは足さない。

### D6 — ごみ箱が増えることへの対処（問い 4）

**この提案で増える量は小さい（推測）。**

- D4 は棚へ移すだけなので、ごみ箱は増えない。
- 増えるのは shell/ssm の削除（メタ＋端末履歴 ≤4 MiB）。今は年に何件あるか分からない。CP の監査ログの
  `session.stop` を数えれば分かる（**未測定**）。
- AI セッションの削除は今も棚経由で、それが 1,046 件・約 500 MB の大半を占める。この提案で増えも
  減りもしない。

**期限で自動に消すことはしない**（ADR 0097 決定 2・3 をそのまま守る）。代わりに次の 2 つを足す。

1. **設定 → マシン**のごみ箱の表示（PR #919）に、件数と最も古い日付を足す。
2. 掃除モーダルの「ごみ箱（復元）」タブに、**人が押す「N 日より古いものを完全に削除」**を足す。
   アーカイブ一覧の「古いものを削除（30 日）」と同じ形にし、既定は 30 日。確認ダイアログに件数と
   容量を出す。

2 は決定 2 の「削除は人の操作だけ」の中に収まる。増えるたびに 1 件ずつ選ぶ手間を減らすのが目的である。

### D7 — 既存データの移行（問い 5）

**移行はしない。まず測る。**

- **`/stop` や `prune_sessions` で消えたセッションは、ごみ箱に戻す手段が無い。** メタが残っていないので、
  名前が分からない。sid は `UUID(dir, name)` で、sid から名前は逆算できない。ごみ箱の復元は
  `meta.Name` の無いセッションを飛ばす（`restoreCleanupArchive`）。
- 見分けられないものがある。`~/.claude/projects` には、フリートのセッション以外の会話ログもある
  （shell セッションの中で人が直接起動した claude など）。メタから届かない sid を全部「消したセッション」と
  みなすと、それを巻き込む。
- **ADR 0097 以前の TTL prune（〜2026-09-20）も、メタだけを消して会話ログを残していた。**
  メタの無い会話ログの大半はこちら由来だろうと思うが、**推測**である。

そこで次の順にする。

1. **P3 で数える（読むだけ）。** キャッシュの孤児判定（メタ・ごみ箱・フォーク系譜から届くか）と同じ規則で、
   claude の会話ログのうち届かないものの件数と容量を出す。フリートのセッションだったと確かめられるもの
   （利用量台帳などに sid と名前の対応が残っているもの。**残っているかは未確認**）と、確かめられない
   ものに分ける。
2. 数を見てから、利用者が次のどれかを選ぶ（§7 判断 5）。
   - (a) そのまま残す（今と同じ。見えず、容量も戻らない）。
   - (b) 掃除モーダルに「消えたセッションの会話ログ」の行を足し、人が押して**完全に削除**する。
     ごみ箱を通らない例外になるが、ADR 0097 追記のキャッシュと同じ論理で説明できる（もう復元の
     道筋が無いものだけを対象にする）。
   - (c) 名前の分かるものだけ、メタを作り直してごみ箱に入れる（戻せるようになる）。

`prune_sessions` なしの worktree 削除で残った「Dir の無いメタ」は、既に行として見えていて棚にも移せる
ので、移行は要らない。

## 115.4 却下した案

- **Console を `DELETE ?reclaim=1` に替えるだけで、`/stop` は今のまま残す。** 古い Console と、ほかの
  呼び手（スタジオなど）が戻せない削除を続ける。Agent 側で 1 つにしないと、次に増えた入口がまた外れる。
- **worktree の削除で中のセッションもごみ箱へ入れる。** 利用者の方針 2 に反する。worktree を消す人は会話を
  捨てると言っていない。掃除②の「安全」判定（マージ済み・クリーン）は作業コピーについての判定で、会話に
  ついてのものではない。
- **ごみ箱に期限を付ける。** ADR 0097 決定 2・3 と衝突する。量の問題は D6 の「人が押す一括削除」で扱う。
- **`MaybePruneWorktree` を残し、ごみ箱に入れたときだけ止める。** 条件が増え、どちらの向きの絡み合いも
  残る。

## 115.5 影響

- shell/ssm の削除が戻せるようになる。ごみ箱が少し増える（D6）。
- セッションを消しても worktree が残る。掃除②の候補が少し増える。
- worktree を消しても会話が棚に残る。棚が少し増える（棚にも期限は無い）。
- 監査ログの操作名が `session.stop` から `session.delete` に変わる（CP）。
- キャッシュの孤児判定は変えなくてよい。消したセッションがごみ箱に入るので、貼り付け画像はアーカイブを
  完全削除するまで守られる。

## 115.6 実装の段取り（合意後）

- **P0（Agent）**: `trashSession` を作り、`/stop`・`DELETE /sessions/{name}`・`forgetNonLiveMetasUnder`
  の置き換えをこれに寄せる。`MaybePruneWorktree` を外す。端末履歴をアーカイブに入れ、復元で戻す。
  テスト：メタを忘れる経路がすべてごみ箱を通ることを、`meta_remove_sites_test.go` と同じ形で呼び出し元を
  数えて守る。
- **P1（Console・CP）**: 入口 1〜5 の書き換え、文言、監査名。
- **P2（文書）**: ガイド、ADR、MCP の説明文。
- **P3（測る）**: D7 の件数。§7 判断 5 はその結果を見てから決める。
- **P4（任意）**: D6 の一括完全削除とマシン設定の表示。

## 115.7 利用者に決めてほしいこと

1. **D1 の方針**（メタを忘れる経路はすべて `trashSession` を通す、`/stop` も含める）でよいか。
   推奨：はい。
2. **AI セッションの行に「削除（ごみ箱へ）」を足すか。** 推奨：足さない（今は棚経由で消せる。2 段の
   意味を保つ）。
3. **worktree を消すとき、中の停止中 AI セッションをどうするか。** 推奨：棚へ移す（選ばせない）。
   代案：確認ダイアログで「棚へ／ごみ箱へ」を選ばせる。
4. **セッションを消したときに worktree を自動で片付けるのをやめるか**（D3）。推奨：やめる。
5. **既存の、メタの無い会話ログをどうするか**（D7）。推奨：P3 で数えてから決める。
6. **ごみ箱の一括完全削除（N 日より古いもの）を足すか**（D6）。推奨：足す（既定 30 日、人が押す）。
