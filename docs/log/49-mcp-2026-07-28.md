## 0. 何が起きたか

MCP 仕様の **2026-07-28** 版が確定した（RC 公開 2026-05-21、10 週の検証期間を経て 7/28 lock）。
「launch 以来最大の改訂」と位置づけられており、**破壊的変更**を含む。

af にとっての位置づけは 2 つある。

| 立場 | どこ | 影響 |
|------|------|------|
| MCP を**提供**する側 | CP `/mcp`（`control-plane/mcp.go`）、Agent `mcp-stdio`（`workspace/agent/mcp_stdio.go`） | 手元の claude / codex が新版クライアントになると、旧作法しか喋らないサーバーは繋がらなくなる |
| MCP を**利用**する側 | レジストリの接続テスト（`internal/mcpreg/probe.go`、docs/48 P0） | 利用者が登録するサーバーが新旧どちらかは分からない |

**materialize 経路（docs/48 P3/P5）は無風**。af は各 CLI のネイティブ設定を書くだけで、
プロトコルは CLI 自身が喋る（ADR0031 決定 3）。仕様が変わっても書く内容は変わらない。

## 1. 仕様の変更点（1 次資料ベース）

出典: [RC 発表](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/) /
[SEP-2575 Make MCP Stateless](https://modelcontextprotocol.io/seps/2575-stateless-mcp) /
[server/discover](https://modelcontextprotocol.io/specification/draft/server/discover) /
[Streamable HTTP](https://modelcontextprotocol.io/specification/draft/basic/transports/streamable-http)

### 1.1 ステートレス化（中核）

- **`initialize` / `notifications/initialized` を削除**。版・クライアント情報・クライアント能力は
  **毎リクエストの `_meta`** で運ぶ。
- **`Mcp-Session-Id` とプロトコルレベルのセッションを削除**（SEP-2567）。sticky routing も
  共有セッションストアも不要になる。
- 能力の問い合わせは **`server/discover`** に移った。**サーバーは MUST 実装**。

### 1.2 per-request `_meta`（必須）

```json
"_meta": {
  "io.modelcontextprotocol/protocolVersion": "2026-07-28",
  "io.modelcontextprotocol/clientInfo": { "name": "...", "version": "..." },
  "io.modelcontextprotocol/clientCapabilities": {}
}
```

3 つとも **必須**。欠けたら malformed（`-32602` / HTTP 400）。`io.modelcontextprotocol/logLevel`
は任意で、`logging/setLevel` を置き換える。**サーバーは過去のリクエストから能力を推測してはならない。**

### 1.3 Streamable HTTP のヘッダ

| ヘッダ | 中身 | 必須範囲 |
|--------|------|----------|
| `MCP-Protocol-Version` | `_meta` の版と**一致必須** | 全リクエスト |
| `Mcp-Method` | `method` | 全リクエスト |
| `Mcp-Name` | `params.name` または `params.uri` | `tools/call` / `resources/read` / `prompts/get` |

**ヘッダと本文が食い違ったらサーバーは拒否**（`400` + `-32020` HeaderMismatch）。ロードバランサが
ヘッダで、サーバーが本文で判断する構成での取り違えを塞ぐための規定。ASCII 表現できない値は
`=?base64?<b64>?=` の sentinel 形で運び、**サーバーは比較前に復号する**。

その他: **GET ストリーム endpoint 削除**（全部 POST）、`Last-Event-ID` の再開不可、
SSE ストリーム上でのサーバー発 request 禁止（`InputRequiredResult` に埋め込む＝MRTR）。

### 1.4 エラーコード

| コード | 名前 | HTTP |
|--------|------|------|
| `-32020` | HeaderMismatch | 400 |
| `-32021` | MissingRequiredClientCapability | 400 |
| `-32022` | UnsupportedProtocolVersion（`data.supported` / `data.requested`） | 400 |
| `-32601` | Method not found | **404** |
| `-32602` | InvalidParams（`_meta` 欠落を含む） | 400 |

### 1.5 削除・廃止

- 削除された RPC: `initialize` / `notifications/initialized` / `logging/setLevel` /
  `roots/list` / `notifications/roots/list_changed` / `resources/subscribe` / `resources/unsubscribe` /
  **`ping`（両方向）**。
- 廃止予告（12 ヶ月以上の猶予、最短撤去 2027-07-28）: **Roots / Sampling / Logging**。
- `Result` に **`resultType`** が入った（`"complete"` / `"input_required"`）。
  サーバーは MUST 付与。**無い場合クライアントは `"complete"` として扱う**（後方互換）。

### 1.6 版の互換モデル

- 直前のリリース版は **`2025-11-25`**。既存サーバーが 7/28 に止まるわけではない。
- **両対応サーバーは許されている**: 「旧 `initialize` を実装し続けつつ、新しいステートレス RPC を
  併せて公開してよい」（SEP-2575 Backward Compatibility）。
- クライアントの fallback:
  - **HTTP**: 新版で投げる → `400` なら**本文を見る**。既知の新版エラーなら「新版サーバー。要求を直せ」。
    そうでなければ旧版 `initialize` へ落ちる。
  - **stdio**: ステータスコードが無いので **`server/discover` を先に投げる**。
    `Method not found` / `Unsupported protocol version` なら旧版へ落ちる。

## 2. af への影響（コードと突き合わせた結果）

### 2.1 効かなかったもの（＝移行が軽い理由）

- **セッション state の撤去が不要**。`control-plane/mcp.go` も `mcp_stdio.go` も
  純粋な switch で、`initialize` は版を echo するだけ、`notifications/initialized` は no-op、
  `Mcp-Session-Id` は発行も参照もしていなかった。**`initialize` 抜きでいきなり `tools/list` を
  投げても元から答える**実装だった。今回の改訂で最も重い部分に、やることが無かった。
- **廃止機能を 1 つも使っていない**: Roots / Sampling / Logging 未実装、Tasks 未実装
  （`tasks/list` 削除の影響なし）、resources 未実装（missing-resource のコード変更の影響なし）、
  `resources/subscribe` 未実装。
- **認証は元から per-request**。CP は毎リクエスト Bearer PAT を解決している。
  「セッション廃止で認証が迂回されないこと」という SEP の要求は既に満たしている。

### 2.2 効いたもの（実装した差分）

| 箇所 | 内容 |
|------|------|
| `control-plane/mcp_era.go`（新規） | era 判定・`_meta` 検証・ヘッダ照合・`server/discover` の結果組み立て |
| `control-plane/mcp.go` | `dispatchMCPHTTP` で検証→HTTP ステータス決定、`server/discover`、全結果に `resultType`、`rpcError.Data` |
| `workspace/agent/mcp_stdio.go` | `server/discover`、`_meta` 検証、版宣言、`resultType` |
| `workspace/agent/internal/mcpreg/probe.go` | 両 era クライアント（下記 §3） |

### 2.3 版のズレ（発見）

af は 3 箇所とも `2025-06-18` を宣言していた。**現行リリース版は `2025-11-25`** なので、
気づかないうちに 1 版遅れていた。今回、宣言を**複数版**に改めた:

```
supportedVersions = ["2026-07-28", "2025-11-25", "2025-06-18"]
```

## 3. 実装した契約

### 3.1 サーバー側（CP `/mcp` と Agent `mcp-stdio` に同型で）

- **era の判別は 1 点だけ**: `_meta` に `io.modelcontextprotocol/protocolVersion` があるか。
  旧クライアントは絶対に送らず、新クライアントは必ず送る。分岐を 1 つに保つのが要点。
- **旧 era の挙動は一切変えない**。検証もヘッダ規則も適用せず、`initialize` も `ping` も
  従来どおり答え、未知メソッドは従来どおり `200` + `-32601`。
- **新 era のみ**に検証を適用する。順序は「版 → `_meta` 必須項目 → ヘッダ照合」。
  版を先に見るのは、旧新の取り違えに対して**行動可能な** `UnsupportedProtocolVersionError`
  （`supported` 一覧つき）を返すため。
- `resultType: "complete"` は**両 era に常時付与**する。旧クライアントは未知フィールドを
  無視するだけなので、era で分岐する理由がない。
- `serverInfo` は **top-level と `_meta` の両方**に出す（§5 の不一致対策）。

### 3.2 クライアント側（probe）

`server/discover` を先に投げ、その応答で era を決める。HTTP でも同じ手順を使う
（1 本の経路で済み、ついでに `serverInfo` と `supportedVersions` が UI に出せる）。

```
server/discover（新版の _meta + ヘッダ）
├ result            → 新版。tools/list（新版）へ
├ -32601            → 旧版。initialize → initialized → tools/list へ
├ -32022            → data.supported に新版が無ければ旧版へ、あれば新版エラーとして報告
├ 既知の新版エラー  → 新版サーバー。fallback せず報告（spec の指示）
└ 無反応（2 秒）    → 行儀の悪い旧版とみなして旧版へ  ★下記
```

**★ 無反応の扱い**は仕様に無い af の判断。JSON-RPC 上は未知メソッドに `-32601` を返す義務が
あるが、黙殺する実装は現実に存在する。それを待つと probe 全体のタイムアウト（既定 10 秒）を
食い潰して「タイムアウトしました」としか言えなくなるので、**era 判定にだけ 2 秒の専用
デッドライン**を置き、沈黙は旧版と解釈する。

接続テストの結果には **どちらの版で応答したか（`revision`）** を載せる。移行期に
「繋がるが旧版経由」を利用者が区別できることに意味があるため。

## 4. 実測記録

### 4.1 実バイナリでの往復（2026-07-27）

`workspace-agent mcp-stdio` を実際にビルドして stdin から流し込んだ結果:

| 投げたもの | 応答 |
|------------|------|
| `server/discover`（新版 `_meta`） | `supportedVersions=[2026-07-28, 2025-11-25, 2025-06-18]`、`serverInfo=agent-fleet-local/q1`、`resultType`・`_meta`・`instructions` あり |
| `tools/list`（新版 `_meta`） | `tools=11`、`resultType=complete` |
| `initialize`（旧作法・`_meta` なし） | `protocolVersion=2025-06-18` を echo（従来どおり） |
| `tools/list`（`_meta` の版 = `1999-01-01`） | `-32022` + `data={requested, supported[3]}` |

### 4.2 自作 probe × 自作サーバー

`mcpreg.Probe` を実 `mcp-stdio` に向けて実行:
`OK=true revision=2026-07-28 server=agent-fleet-local/q1 tools=11 supported=[2026-07-28 2025-11-25 2025-06-18]`。

### 4.3 実装中に踏んだ不具合（記録）

probe の stdio 読み取りを**やり取りごとに goroutine で起こしていた**ため、era 判定の短い
デッドラインで待つのをやめた後も**孤児の goroutine が stdout を読み続け、次のやり取りの応答を
食い潰して**いた。結果、旧版 fallback が必ずタイムアウトする。読み手を probe 全体で 1 本に
集約し、待ち手はチャネルから id で拾う形に変えて解消（`probe.go`）。
**「待つのをやめる」設計には、読み手を共有する形が要る。**

## 5. 仕様側の不一致（把握しておくこと）

`DiscoverResult` の `serverInfo` の置き場が、SEP-2575 と draft ドキュメントで食い違う。

| 出典 | 形 |
|------|----|
| SEP-2575 の `DiscoverResult` | **top-level** の `serverInfo` |
| draft ドキュメントの例 | `_meta["io.modelcontextprotocol/serverInfo"]` |

af は**サーバーとして両方に出し、クライアントとして両方を読む**。余分なフィールドは無害で、
どちらが正になっても壊れない。仕様が収束したら片方に寄せる。

## 6. 積み残し

1. **認可の OAuth 2.1 / OIDC 整合**（6 SEP）。CP `/mcp` は PAT Bearer 主で、これは
   [decisions/0006](../decisions/0006-mcp-unified.ja.md) の前提そのもの。別 ADR で判断する。
2. **`subscriptions/listen`**（GET ストリーム廃止の代替）。af は list_changed 通知を
   出していないので現状不要。
3. **MRTR / `InputRequiredResult`**。af のツールはサーバー発の入力要求を使わない。
4. **キャッシュ指示（`ttlMs` / `cacheScope`）**。`tools/list` に付ければ効果はあるが未実装。
5. **MCP Server Card（`.well-known/mcp.json`）**。CP に置く価値はあるが今回は対象外。
6. **`Mcp-Param-{Name}`（`x-mcp-header`）**。af のツール定義は使っていない。クライアント側は
   MUST 対応だが、probe はツールを呼ばないので不要。
7. **Tier 1 SDK（Go beta）への乗り換え**。今は自前実装。SDK が安定したら比較検討する。
8. **利用者の CLI がいつ新版クライアントになるか**は af の管理外。両対応にしたので
   どちらでも繋がるが、CLI 側が旧版を切ったときに初めて新版経路が本番で効く。
