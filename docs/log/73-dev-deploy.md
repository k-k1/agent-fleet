# 73. 開発デプロイと配備の出し入れ（立てる・眠らせる・畳む）

**配備のひとつを開発用と決め**、`develop` をバージョンタグ無しでそこへ載せる操作を
1 コマンドにする。⚠️ **どの配備が開発用か（名前も FQDN も）はこのリポジトリに書かない**
——公開リポジトリだからで、印は手元の環境ファイルの `AF_DEV_DEPLOY=1` が持つ（§73.6）。[72](72-cp-arch-and-availability.md) §72.6 がその手順を初めて実機で通した
ところまでで、本書はそれを**繰り返せる形**にした記録である。

そして「気軽に載せられる」は「気軽に**作り直せる**」と対で初めて意味を持つので、
**配備そのものを立てる／眠らせる／畳む**も同じ形（1 コマンド＋既定は何もしない）にした
（§73.6）。こちらは**どの配備でも**使う（開発用のものも、実利用者が居るものも）。

関連: [72](72-cp-arch-and-availability.md) §72.6（dev イメージと `CpArch`）・
[70](70-slot-instance-classes.md) §70.14（EC2 で手焼きしていた頃）・
[64](64-ec2-persistent-workspace.md) §64.28（golden の自動焼き）・
[35](35-packaging.md)（本物のリリース経路）。決定は [ADR 0054](../decisions/0054-dev-deploy.ja.md)。

## 73.1 何が足りなかったか

部品は揃っていた。繋がっていなかった。

| 部品 | 何をする |
|---|---|
| `.github/workflows/dev-image.yml` | GHCR の `-dev` 付きタグへ 2 アーキで焼く。**リリースタグは仕掛けで拒否**（§72.6.1） |
| `crane copy` | GHCR → ECR を**インデックスごと**運ぶ（`docker pull`+`push` は 1 アーキに潰れる） |
| `deploy/aws/ecs/update.sh` | `ImageTag` を動かす。タグ不在・空チェンジセット・`CpArch` 不整合・走行中 WS の一覧まで見る |

手作業として残っていたのは繋ぎだけ——**タグを手で決める → dispatch して待つ → CP を copy →
workspace を同じタグに置く → `update.sh`**。順番と前提を知っている人だけが通せる 4 段で、
間違えたときは**静かに間違ったものがデプロイされる**（焼いていない commit のタグ、1 アーキに
潰れたインデックス、workspace 側だけ古いタグ）。

## 73.2 決定

1. **開発配備にしか当たらない。** `ImageTag` を動かす操作は、そこで走っている人に
   「要再起動」バッジを出す。`dev-deploy.sh` は **手元の控えに `AF_DEV_DEPLOY=1` の印が
   ある配備にしか当たらない**。⚠️ 印を**スクリプト側の既定 FQDN**にしないのは、それが
   配備の身元をリポジトリに置くことになるからである（このリポジトリは公開）。
2. **入口は 1 本、出口は必ず `update.sh`。** 前検査（`CpArch` とマニフェストの噛み合わせ、
   可変タグの空チェンジセット、golden の陳腐化、走行中 WS）は `update.sh` にしかない。
   dev 用に 2 本目を書けば、そこから先にドリフトするのは**検査の方**である
   （§72.6.1 が「焼くのは `release.sh` 経由」と決めたのと同じ理由）。
3. **golden の同一性は内容で持つ**（`af-image-fp`）。§72.6.4 で digest が完全に同じイメージを
   再タグしただけで 2 アーキ分が焼き直された（約 10 分・EC2 スロット 2 本）。`af-image` が
   持っているのは**参照文字列であって内容ではない**からで、開発デプロイは**毎回それをやる**
   （CP だけ焼いて workspace は再タグする）ので、放っておくとデプロイのたびに 10 分を払う。
   - 指紋は再起動バッジと**同じ関数**（`imageFingerprint` ＝ プラットフォーム毎の manifest
     digest の集合）を使い、EC2 のタグ値に収まるよう `sha256:` へ畳む。
     ⚠️ **2 辺を別の関数で作らない**は [`runtime_ecs_stale.go`](../../control-plane/internal/runtime/runtime_ecs_stale.go)
     の注記そのままで、そこでは実測で踏んでいる。
   - ⚠️ **逆向きの穴も同時に塞がる**: 可変タグ（`:dev`）へ新しい内容を push すると文字列は
     一致したままなので、**新規メンバーだけが古いイメージで焼かれた home を配られる**。
     費用の話（同じものを焼き直す）と正しさの話（違うものを配る）は同じ 1 行の裏表である。
   - ⚠️ **指紋が読めないときは文字列で比べる**（ECR ではない・権限が無い・指紋タグが無い旧
     golden）。unknown を「不一致」と読むと、**アップグレードした瞬間に全配備の golden が
     捨てられる**。
4. **workspace を焼くかは差分で決める**（既定 `--image auto`）。ws イメージのビルドコンテキストは
   `workspace/` だけなので、そこに差分が無い回は **ECR 内の再タグ**で済ませる。
   焼き直すと QEMU で **+593 秒**（§72.5.1）。
   ⚠️ ビルド引数側（`release.sh` の `BAKE_AGENT_CLIS` など）を触った回は差分に出ない。
   そのときは `--image both` を明示する。
5. **タグは可変 `:dev` ではなくコミット毎の `<次のパッチ>-dev-<sha8>`。** 可変タグの利点は
   「golden が焼き直されない」の 1 点で、それは決定 3 で得られる。失うものの方が大きい:
   **CP の版文字列（ログ・Console）がどの commit か言えなくなる**。要再起動バッジは
   内容指紋で判定しているのでタグ方式に依存しない。
6. **CI から直接デプロイ（GitHub OIDC）は今はやらない。** ボタン 1 つになるのは魅力だが、
   sandbox アカウントに OIDC プロバイダと deploy 権限のロールを常設することになる。
   いまの手数は「1 コマンド」なので、**払う対価に見合っていない**。やるとしたら
   push 毎の自動ではなく手動 dispatch（`ImageTag` を動かす操作は人が選ぶ時刻に起きるべき）。

## 73.3 使い方

```bash
deploy/aws/ecs/dev-deploy.sh --profile <p> --region <r>
```

これだけで `origin/develop` が開発配備に載る。中でやっていること:

1. リモートの `develop` の sha を取り、`<直近タグ+1>-dev-<sha8>` をタグにする
2. `workspace/` の差分を見て、焼くのを CP だけにするか両方にするか決める
3. `gh workflow run dev-image.yml` → run を名前で見つけて `gh run watch`
4. `crane copy` で ECR へ（workspace を焼いていない回は ECR 内で再タグ）
5. digest が一致するときだけ golden の `af-image` を貼り替える（決定 3 が入る前の
   golden 用の橋渡し。指紋タグを持つ golden はそもそも貼り替え無しで一致する）
6. `update.sh`

よく使う指定:

| | |
|---|---|
| `--ref temp/xxx` | develop 以外を焼く |
| `--image both` | workspace も必ず焼く（+~10 分） |
| `--skip-bake` | もう GHCR にあるタグをデプロイするだけ |
| `--dry-run` | 何が起きるかだけ出す |

## 73.4 引き受けた落とし穴

1. **CI が焼くのは origin の ref であって手元の作業ツリーではない。** ローカルに
   コミット（あるいは push）していない変更は黙って入らず、デプロイは「成功」する。
   タグの sha は**リモートの ref から**取り、手元がそれと違えば警告する。さらに **run の
   `headSha` を焼いたあとに突き合わせる**——dispatch と checkout の間に develop が動けば、
   タグが指す sha は嘘になる。
2. **`ImageTag` は CP と workspace で共有**（[ADR 0045](../decisions/0045-ec2-persistent-workspace.ja.md)
   決定 8）。CP だけ焼き直しても workspace 側を同じタグに置かないと、タグ不在で CP タスクが
   上がらない。
3. **`docker pull` + `push` はインデックスを 1 アーキに潰す。** GHCR → ECR は `crane copy`。
   Workspace コンテナに docker は無いので、これは制約ではなく前提である。
4. **同じ digest の再タグで golden が焼き直される**（決定 3）。
5. **実ユーザーが居る配備に当てない**（決定 1）。

## 73.5 状態

| | 内容 | 出口 |
|---|---|---|
| **P0** ✅ | `dev-deploy.sh`（決定 1・2・4・5）＋ `dev-image.yml` の `run-name` | 1 コマンドで develop が載る |
| **P1** ✅ | golden の同一性を内容で持つ（決定 3・`af-image-fp`） | 再タグで焼き直さない／可変タグで古い home を配らない。両方向をテストで固定 |
| **P2** ✅ | 配備の出し入れ（§73.6）: `capture-env.sh` / `standup.sh` / `teardown.sh` / `pause.sh` ＋ 順序ゲート | どの配備も同じ道具で扱える |
| **P3** — | CI から直接デプロイ（決定 6 で見送り） | やるなら OIDC ロール ＋ 手動 dispatch |

⏳ **実機での初回実行はまだ**（本書を書いた時点で開発配備は `0.10.1-dev-2b0984c9` で走っている）。
最初の 1 回は `--dry-run` で段取りを見てから通すこと。§73.6 の 4 本も、読み取り側
（`capture-env.sh` の実行・`standup.sh` の preflight・`teardown.sh` の計画表示）は
**2 つの実配備で通してある**が、**書き込み側は実機で走らせていない**。

## 73.6 立てる・眠らせる・畳む（両配備で使う）

デプロイだけ 1 コマンドになっても、**配備そのものの出し入れ**が手打ちの runbook のままでは
片手落ちだった。開発配備の価値は「気軽に作り直せる」ことにあり、それは畳めることと同義である。

どれも配備を **`--profile <p> --region <r>`** で指す（`update.sh` と同じ形）。

| | | 何をするか |
|---|---|---|
| 記録 | `capture-env.sh` | 生きている配備から**引数一式**を手元へ書き出す（立て直しの材料） |
| 眠らせる | `pause.sh` / `--up` / `--status` | Workspace と CP を止める／戻す（数分で往復・データはそのまま） |
| 畳む | `teardown.sh`（`--yes` で実行） | 12 段の撤収 ＋ ゼロ確認のスイープ |
| 立てる | `standup.sh`（`--yes` で実行） | `00 → 10 → 20 → イメージ → 40 → 30` |

### 73.6.1 決めたこと

**① 配備は AWS プロファイルで指し、実体は生きている配備から引く。** 人が別名を発明する層は
要らない——プロファイルは既に「どのアカウントの、どの権限で」を持ち、`~/.aws/config` ＝
**リポジトリの外**にある（`update.sh` が最初からその形である）。
同じテンプレートから立てても実体の名前は揃わない——**実測で、ある配備のプール層は
`af-ecs-pool`、別の配備では `af-ecs-ec2-pool`** だった。だからスクリプトに既定値を書かず、
**エクスポート `<stack>-SlotLaunchTemplateId` の値が 30 の `Ec2SlotLaunchTemplate` と一致する
スタック**として実体から引く。
⚠️ **控えを持つのは「立て直す」ときだけ**——そのときは何も生きていないから。控えは
`~/.config/agent-fleet/deploy/<profile>.<region>/`（**リポジトリの外**。中身はホストゾーン
ID・許可メール・OAuth クライアント ID といったアカウント固有の値）。
⚠️ **生きている配備に対して控えを読んではいけない**（古い控えで実物を塗り替えると、
「実物ではない配備」に向けて実行することになる）。

**② 撤収の第 0 歩は記録である。** 2026-08-22 の削除では引数一式を手で JSON に退避した。
テンプレートは repo にあるが、**そこに何を渡したかは配備の中にしか無く、`delete-stack` を
出した瞬間に読めなくなる**。だから `teardown.sh` は控えが無ければ実行を拒み、
`standup.sh` も控えが無ければ何を渡せばよいか言えずに止まる。

**③ 秘密は運ばない。** SSM SecureString の 3 つ（cookie-secret / master-key / IdP の
client secret）は CFN の引数ではないので控えにも入らず、`standup.sh` は
**有無だけ**を見る（`--with-decryption` を付けない）。撤収は既定でそれらを残す＝
同じアカウントに立て直せる。⚠️ **CFN の引数にも「秘密に見える値」は混じる**
（`BitbucketOauthKey`）ので、計画表示と dry-run では `*Secret*` `*Token*` `*OauthKey*` …
を伏せる。端末とログに残る出力に値を流す理由が無い。

**④ 既定は「何もしない」。** `teardown.sh` も `standup.sh` も `pause.sh --down` も、
`--yes` が無ければ計画を出して終わる。`--yes` があり**端末があるときは FQDN を打たせる**——
配備が複数あって片方に実利用者が居る以上、「どちらに向かって実行しているか」を目で
確かめさせるのが唯一効く防具である（プロファイル名は似ていて、履歴から引いた 1 行は
取り違えても気づけない）。

**⑤ 守るべきは「消えること」ではなく順序である。** 実測で踏んだ壊れ方はすべて順序だった:
CP を止める前に片付けると**動いている CP が作り直す**／スロットを terminate しても
**home の EBS は残る**／スタックをまとめて delete すると importer が居る間
**exporting stack の削除が無言でキャンセル**される／立てる側は 20 の後にイメージを入れ、
40 の**新しい** launch template を 30 に渡さないと**スロットだけが二度と起きない**。
これを `deploy/local/ecs-lifecycle-stub-test.sh`（偽 `aws`/`crane` で順序を突き合わせる）で
固定し、release-gate から回す。「`--yes` の無い撤収が 1 つも書き込みを出さない」ことも
そこで検査する。

### 73.6.2 撤収は 3 段階のいちばん深いところ

| | 何が残るか | 戻すコスト |
|---|---|---|
| `pause.sh` | NAT / ALB / RDS / EFS ＋ home の EBS（**固定費は半分残る**——実測の日額 $5.5 → $2.6） | 数分 |
| `teardown.sh`（既定） | ホストゾーンと `/af-cp/*` だけ | `standup.sh` で再構築（ECR は空から） |
| `teardown.sh --purge-secrets --purge-retained` | ほぼ何も | 秘密の作り直しから |

⚠️ **ECR は温存できない。** `af-control-plane` / `af-workspace` は 20-platform のリソースで
`EmptyOnDelete: true` ＝スタック削除でイメージごと消える。だから `standup.sh` は
GHCR から `crane copy` し直す前提で書いてある。
⚠️ **`Persistence=retain` の配備では既定で残す**。削除保護は外す（外さないと削除自体が落ちる）が、
最終スナップショットと EFS は `--purge-retained` を明示したときだけ消す——それが retain の意味である。

## 73.7 未決

1. **`bake-golden.sh`（手焼き）は指紋を刻まない。** 刻まなくても文字列で拾われるので壊れない
   が、そのあと再タグすると焼き直しが起きる。手焼き自体が「CP が焼けないとき」の逃げ道
   なので、**手で刻める形にするか、刻まないままにするか**は使う頻度を見てからでよい。
2. **撤収→再構築を実機で 1 往復していない。** 手順そのものは 2026-08-22 に手で通っており、
   スクリプトは順序をスタブで固定しているが、**通しで走らせた実績はまだ無い**。最初の
   1 往復は実利用者が居ない側の配備でやること。
3. **開発配備をどこまで本番相当に保つか。** いまは同じテンプレートで同じ形をしているが、
   golden の焼き直しやスロットの起動が実費なので、**`Ec2MaxSlots` を下げる**などの
   「開発用の削り方」は決めていない。
