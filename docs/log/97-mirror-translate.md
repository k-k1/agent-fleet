# 97. 回答をミラーで訳す（ターンを使わない翻訳）— 設計・実装

> 状態: **P0 完了**（2026-09-13）。利用者の要求は「エージェントの回答が英語だったとき、
> **エージェントのターンを使わずに**、ミラービュー上で指定言語に訳す」。

> セッションの削除まで保持**／**共有相手は押せない（所有者のみ）**。

> アンカー）/ [46-usage-accounting.md](46-usage-accounting.md)（台帳の feature 軸）/

## 97.1 何を作ったか

ミラーの各回答のフッタに **「翻訳」/「原文」** を出す（当初は「訳す」。2026-09-13 に利用者の指定で改称）。押すとその回答の**文章パートだけ**が
表示言語（回答言語を固定していればその言語）に置き換わる。

- 生成は `chatx.OneShotHeadless`（`OneShotProse`）＝タイトル提案・返信候補・編集提案と同じ
  **バックエンド非依存のワンショット**。別プロセスで 1 回 CLI を回すだけなので、**セッション本体の
  エージェントには触れない**（ターンを消費しない・文脈が増えない・実行中の作業の後ろに並ばない）。
- 消費は台帳に `translate.mirror` として載る（`usagex.FeatureTranslate`）。
- 設定 > AI補助 の `mirrorTranslateEnabled` でオフにできる（既定オン。押すまで無料なので）。

## 97.2 決めたこと（と、その理由）

| 決定 | 理由 |
|---|---|
| **自動ではなくボタン** | 自動にすると「どの回答を」「いつ」訳すかを機械が決めることになり、**追記中のターンを訳して古い訳が残る**。押した時点＝そのターンが完結している、で解ける。ミラーは毎秒ポーリングするので、自動翻訳は「押していない人の分まで 1 回答 1 モデル実行」になる |
| **キャッシュ鍵＝原文のハッシュ** | `Idx`（行序数）は compaction でずれ、`anchorId` はフォークで別 ID が付く（本文は同一）。走行中のターンは育つので「ターン」は鍵にならない。**押した本文**だけが安定している |
| **鍵はサーバが自分で計算する** | クライアントが鍵を名乗れると、古いペインが無関係な訳を引き出せる。鍵はその回答の訳を決める唯一の根拠 |
| **言語も鍵の一部** | 回答言語を切り替えたときに前の言語の訳が出る |
| **パート単位** | コードフェンス・ツール出力を自然に飛ばせ、段落が 1 つ増えた回答は**増えた分だけ**再実行になる |
| **保存はセッション削除まで** | `removeSessionSideFiles`（`cleanup_ops.go`）に 1 行足す。**セッション名はスロット名で使い回される**ので、消し忘れると次にその枠に入った会話へ他人の訳が出る。ハッシュ鍵なので誤ヒットはまず起きないが、ディスクと回答のプライバシーは別問題。派生物なので**削除アーカイブには入れない**（マークと同じ） |
| **ポーリングに載せない** | `/messages` に訳を混ぜると (a) 毎 poll のバイトが増え（スマホの電池）、(b) CP の sessionWire に欄を足す 4 か所仕事が出る。別エンドポイント＋開いたとき 1 回の GET |
| **共有相手は押せない** | 押すと**所有者のワークスペースでモデルが走り、所有者のトークンを使う**。CP の `registerSessionShareRoutes` には対の経路を置かない＝共有ビューには capability が無く、ボタン自体が描かれない（`capabilities.ts` の原則） |

## 97.4 踏みどころ（次に触る人へ）

- **ハッシュは日英 2 実装で、UTF-8 バイト列を数える。** ブラウザ側の唯一の組み込みダイジェスト
  （SubtleCrypto）は非同期で、しかも jsdom に無い＝描画テストが書けなくなる。なので FNV-1a を
  Go と TS の両方に置いた。**JS が UTF-16 コード単位を数えると ASCII のテストは全部通り、
  実際の回答だけ鍵が食い違う**ので、ベクタに日本語と絵文字を入れて両側で固定している
  （`session_translate_test.go` / `translate.test.ts`）。
- **マークは訳文の上に置けない。** マークは引用文字列でアンカーする（§69.3）ので、訳文に
  当てると「たまたま一致した別の文」に線が引かれる。訳を表示しているパートは `markRoot` を
  外す＝マークは原文に残る。
- **訳文は同じ MarkdownView に流す。** 別の描画経路を作ると Markdown の不具合が 2 セットになる
  （全角パイプ表・`<…>` の消失などは既に踏んでいる）。
- **コピーは「いま見えている方」を返す。** 訳を見ている人に読めない原文を渡すのは驚きになる。
- **返信サジェストに訳文を食わせない。** サジェストの言語軸は「会話の言語」で、訳文を渡すと
  相手セッションの出力言語まで反転する（§6.6 の地雷そのもの）。今回は経路を分けてあるだけで、
  将来まとめようとしたときに壊れる箇所。
- **persona はロケール分岐しない。** 出力言語がパラメタそのものなので、指示文を 2 本持っても
  読者が見るものは変わらず、維持コストだけが増える（`fs_suggest_edit.go` と同じ判断・§6.6 の
  判定表の「生成物の言語が UI ロケールで決まらないもの」）。

## 97.8 🔴 訂正（2026-09-14）: 引用ラベル 1 個でボタンが消える

`looksForeign`（§97.4 が「両方向にわざと鈍い」と書いた判定）に、想定していなかった外れ値が
見つかった。英語主体の PR レビュー報告のように、**地の文はすべて英語だが、UI ラベルを
`"レビューする"/"Review this pull request"` のように原文つきで引用する 1 箇所だけがある**
ターンで、日本語読者に翻訳ボタンが一度も出ない事象。

原因は `cjk === 0` という全か無かの閾値——`proseOnly` はコードフェンス／インラインコードを
「地の文ではない」として既に除いていたが、**引用ラベルは除いていなかった**ので、かな 1 文字でも
混じれば「もう読める」と誤判定してターン全体のボタンを消していた。

`proseOnly` に、コードと同じ扱いで**引用スパン**（ASCII `"…"` ／全角 `“…”` ／`「…」` ／
`『…』`、いずれも改行をまたがない 1 行分）を足して除去するよう修正
（`console/src/features/mirror/translate.ts`）。引用ラベルは「そのラベルを指している」だけで
どちらの言語のプロースでもない、という位置づけはコードブロックと同じなので、判定の閾値
（`cjk === 0` / `cjk >= MIN_CJK`）自体は変えていない。回帰試験は `translate.test.ts`
「does not let a quoted label alone flip the verdict」（英語本文が日本語ラベルを引用／日本語
本文が英語ラベルを `「」` で引用／引用だけが全文、の 3 パターン）。Console 全体
2780 件・typecheck・oxlint・i18n:lint いずれも緑。

## 97.9 🔴 訂正（2026-09-14）: 折りたたんだ作業過程の中間応答が翻訳リクエストに乗る

§97.8 を配備して実機（このホスト＝配備済みの workspace-agent、セッション s6hegkv）で押したところ、
今度は `translate_too_long`（Console 表示「この回答は長すぎて翻訳できません」）で失敗した。対象の
ターンは「作業過程 ツール110件・途中応答31件」を畳んだ長い実行で、最終回答自体は短い。

原因は `translatableTexts(turn)`（`TranscriptTurn.tsx:122`、当時）が **work-split（作業過程の
折りたたみ境界、`mirrorParts.ts` の `workSplit`）を見ずに `turn.parts` 全体**を渡していたこと。
コピー本文(`copyParts`)とツール痕跡の折りたたみ描画は既にこの境界を使っていた
（[69](69-transcript-marks.md) §69.8 の教訓そのもの）のに、翻訳対象抽出だけそれを見落としていた。
畳みの中の 31 件の中間応答が一緒に送られ、`session_translate.go` の `translateMaxParts`（8）／
`translateMaxPartBytes`（32 KiB）を、**最終回答単体なら十分収まるところ**で超えていた。

`TranscriptTurn.tsx` で `copyParts` と同じ `split.at` 基準のスライス（`visibleParts`）を計算し、
`translatableTexts` にはそれだけを渡すよう修正——読者が実際に見ている範囲（畳みの外）だけが
コピーにも翻訳にも乗る、という 1 本の規則に揃えた。回帰試験は `TranslateTurn.dom.test.tsx`
「does not send the folded work process's intermediate replies to translate」（ツール→短い中間応答
→ツール→短い中間応答→ツール→長い最終回答、という形のターンで、送られるのは最終回答だけである
ことを確認）。Console 全体 2781 件・typecheck・oxlint・i18n:lint・`docs-check.py` いずれも緑。

## 97.10 利用者要望（2026-09-14）: タブ切り替えで Original に戻る／長すぎる答えの分割翻訳

配備後、利用者から実運用で 2 件。

1. **翻訳を表示したままタブを切り替えると Original に戻る。** `useTranslate.ts` の `shown`
   （どのターンを表示中か）は `useState` のコンポーネントローカル state だった。`Pane.tsx` は
   同じセルの別セッションタブへ切り替える際 `MirrorView` インスタンスを使い回して `session` prop
   だけを差し替える（`MirrorView.tsx` 自身がその前提でコメントされている）ため、① `session` が
   変わるたび `useTranslate` の effect が無条件に `setState(emptyState())` していたこと、②
   チャット以外のタブに切り替えると `MirrorView` 自体が条件レンダーでアンマウントされること、の
   両方で `shown` が空に戻っていた。`shown` はサーバーに存在しない（`session_translate.go` の
   保存はハッシュ→訳文のみで「どのターンが表示中か」は持たない）ので、消えたら復元しようがない。
   同種の問題（`MirrorView` のアンマウントで消える）は送信エコー（`parts/sendEcho.ts` の
   `echoStore`）で既に module-level Map による退避という形で解決済みだったので、同じ形を転用:
   `useTranslate.ts` に `session+lang` をキーにした module-level `stateStore` を足し、`shown` を
   含む state 全体を write-through で退避・復元する。GET `/translations` の結果は退避済み
   `entries` を**上書きせずマージする**（`splitForTranslate` で作った復元済みエントリ、後述、は
   サーバー側に存在しないので上書きすると消える）。
2. **答えが長すぎると `translate_too_long` で丸ごと失敗する。** §97.9 で畳みの外だけに絞っても、
   最終回答そのものが 1 パートで `translateMaxPartBytes`（32 KiB）を超えることがある。利用者の
   要望どおり「きりの良い改行で分割して翻訳し、結合して表示」を実装。`translate.ts` に
   `splitForTranslate(text, maxBytes)` を追加——空行、次に単一改行、次に文の区切り
   （`. `/`; `/`! `/`? ` や `。`/`、`/`！`/`？`）、最後に UTF-8 セーフな生のバイト境界、の
   優先順で分割し、返ったチャンクを**区切り文字なしで結合すると原文と完全一致**する（分割点は
   区切り文字の直後に置くので区切り自体は各チャンクが持ち歩く）。文の区切りの段は、改行が
   一つも無い長い1行（利用者の指摘どおり、ラップされていない長い文・ログ行・表の1行などで
   起こりうる）をバイト境界の生カットから救うためのもの。フェンスコード ` ``` `〜` ``` ` は
   単体で収まる限り 1 チャンクに保つ（またいで分割すると開始/終了が別リクエストに分かれ、
   persona の「コードフェンスは原文のまま」が守れなくなる）。
   `useTranslate.ts` の `toggle()` でこの分割を行い、各チャンクを独立した translate request part
   として送って個別にキャッシュさせつつ、返ってきた訳文をまとめて**元のテキスト全体のハッシュ**の
   下にも保存する——`translatedOf`/`copyText`（`TranscriptTurn.tsx`）や次回以降の cache-hit 判定
   は元テキスト全体のハッシュだけを見るので、分割されたことを外側は一切知らなくてよい。
   `translateMaxParts`（8）は分割後の合計パート数がこれを超えるとサーバー側がそのまま
   `translate_too_long` を返す（同じエラーコード・同じ利用者向け文言）——本当に巨大な答え
   （目安 256 KiB 超）はこの機構でも救えないが、実際に踏んだケース（畳みを除いた最終回答が
   32〜90 KiB 程度）はこれで通る。

   🔥 **レビュー中に見つけた別の不具合**: 生のバイト境界カット（`hardCut`）が、UTF-16 の
   サロゲートペア（🔴 のような絵文字、BMP 外の文字）のちょうど真ん中で切ることがあった。
   `text.slice()` の時点では「コード単位の連結が原文と一致」して見えるが、実際に fetch の
   body が UTF-8 へエンコードされる際、対になっていないサロゲートは**それぞれ独立に**
   U+FFFD（置換文字）へ化ける——１文字の絵文字が、別々の 2 リクエストパートにまたがる
   2 個の `�` に壊れて消える。JS 文字列レベルの一致だけを見るテストではこれを検出できず、
   「チャンクを実際に UTF-8 へ encode→decode の往復をさせて元と一致するか」を確認する回帰試験
   で初めて捕まえた。`hardCut` に、カット位置がサロゲートペアの間に来たら 1 つ前（可能なら）
   へ寄せる補正を追加。

   回帰試験: `translate.test.ts`「splitForTranslate」7 件（下限以下は無加工／段落境界で分割し
