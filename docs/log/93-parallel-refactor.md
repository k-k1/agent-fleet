### 2.2 守られなかった／あとから変えた決定

🔴 **決定 7「`develop` へのマージは維持者の手に残す」→ 運用変更で司令塔がマージ**（2026-09-02・利用者指示）。
**得たもの**: 判定 → マージ → 次の依頼が 1 ターンで回り、2 代目が出した「23 分の空転」が二度と起きなかった。
**失ったもの**: **板を書けるのはレビュワーだけ**なので、**司令塔がマージした瞬間に板は必ず 1 手遅れる**——
この構造的な遅れが **#293 / #308 / #323 の 3 回**「合格・マージ待ちのまま取り残された行」を生んだ。
処方（**`gh pr merge` の直後の 1 手を必ずレビュワーへの notice にする**）が固まったのは最終ウェーブで、
それまでに通知落ちが 3 回（#342 / #344・#345 / #350）。
📌 5 代目の総括が正確である——**「『気をつける』で直る失敗と、手順を変えないと直らない失敗がある。3 回目でようやく区別した。」**

🔴 **`ownercheck.sh` の機械判定に穴があった**（ウェーブ D で AG-SESSION が実測 → 司令塔が修正）。
`git diff --name-only` は**既定の改名検出で「移動先 1 本」に畳む**ので、**所有外のファイルを自領域へ持ち出しても
元パスが差分に出ず、検査が緑**になる（→ `--no-renames` を追加）。
**同じ 1 行の裏面にもう 1 つ**——`git status --porcelain` の `R old -> new` を 1 パスに潰して**偽の所有外**を報告していた。
📌 **片方は「見逃す」欠陥・もう片方は「誤報する」欠陥で、同じ 1 行の両面だった。**
✅ **直したあと「過去も白」を遡って測った**（Phase 0 以降の全 rename を具体的な所有で照合 → 持ち込み 0 件）。
📌 **道具の欠陥を見つけたら、直すのと同じ手間で「過去に効いていたか」まで測れる。**
測らなければ「あの穴を通った PR があるかもしれない」が以後ずっと残る。

🔴 **`owners.tsv` の glob `*` が機械判定を無効化していた。**`CONTRACT *`（単独走行前提の登録）のままだと
**ownercheck は所有外を常に 0 と出す＝「green」に情報が無い**。2 トラック並走が決まった時点で割り直した。
📌 **`ownercheck.sh` は階層の深さも見ない**（bash の `case` では `*` が `/` を跨ぐので `features/mirror/*` は
`mirror/a/b/c/x.tsx` まで通す）。**「ディレクトリは 1 階層まで」は慣行であって機械の保証ではない**——
ウェーブ A の台帳の記述は誤りだった。

🔴 **司令塔が「触ってよい」と書いたファイルが `owners.tsv` に無い、を 3 回**（#344 / #349 / B' の 3 行）。
**3 回ともワーカーが ownercheck の赤で止めて聞いてきた**（止めなければレビュワーが差し戻していた）。
→ 着手指示を書く側で「触ってよいと書いたファイルが登録済みか」を機械で当てることにし、
**ワーカー側の「新しい種類のファイルに触る前に ownercheck を空打ちする」と両側から挟む形**に落ち着いた。

⚠️ **決定 10 の上限 6 本を 1 度だけ超えた**（ウェーブ D ＋ 実機一巡で 7 本）。
**実機一巡は重いゲートを回さない**という理由で数えなかった——**上限の意味（メモリ）に照らせば正しい例外**だが、
**ADR の数字そのものは守っていない。**

### 2.3 ADR に書かれていなかったが、効いた運用

1. **マージ前に必ず先端で CI を取り直す**——#335 は PASS 後・マージ直前に止まった。
   **判定が PASS でも、判定者が回していないゲートは緑ではない。**
2. **中継に自分の見立てを添える**——添えると「違う」も返ってくる（#333 で「継ぎ目が多い」を否定され、
   効くのは別の穴だと分かった）。🔴 **ただし**: **見立てを「指示」の形で配ると、ワーカーはそれを実行してしまう。**
   実際に司令塔の指示が誤っていて**ワーカーが実測で倒したのが 2 件**（`go list -deps ./...` は自分自身を必ず含むので
   判定にならない／`;` 分割の警告は当該実装に当たらなかった）。
   → **「これは私の見立てなので実測で倒してよい」と明示する。**
3. **枠は「数」ではなく「種類」でも断る**（`npm run build` は単独で約 3 GiB。`go test` と並べない）。
4. **待たせたら自分側に検知手段を置く**（pid ウォッチャ。**「開始を観測してから 30 秒連続で不在」**にする——
   単純な消滅待ちはゲートの切れ目で誤発火する）。
5. **判定は「送った」ではなく「板に書いた」で完了する**——#339 の判定メッセージは**環境の MCP 障害で消えた**が、
   板に書いてあったので中継が続いた。
   📌 **peer メッセージは届いたことを送り手が確認できない。板を薄くして本文をメッセージに載せると、
   その 1 通が消えた時点で判定が消える。**

### 2.4 3 者の誤りの分布

**司令塔・ワーカー・レビュワーの全員が、同じ日に自分の誤りを訂正している**——
司令塔＝3 マージ遅れの木で実在を判定／ワーカー＝頻度を測らず「既存の失敗」と断定／
レビュワー＝負の対照の当て先を間違えた（`cpSync` が 2 本あった）。
📌 **訂正を出せる関係を保つことが、検査の精度そのものだった。**
`intent=question` で来た反論だから届いた——**`notice` で配っていたら届かなかった。**

## 3. この仕組みが実際に見つけた欠陥

### 3.1 契約の型化が掘り当てた実バグ

| | 症状 | 状態 |
|---|---|---|
| `secretScanFailed` | Go と Console の食い違い | **#349 で修正** |
| **`SsmHost.accountId`** | `console/src/features/repos/StartModal.tsx:185,686` が `h.accountId` を読んでカード副題を出すが、**`control-plane/ssm.go:50` の `ssmHostDTO` に `accountId` が無い**（持っているのは兄弟の `ssmProfileDTO`・`ssm.go:44`）＝**この表示は一度も出ていない** | **未修正**（2026-09-04 時点） |

**加えて、免除表に【穴】と明記された食い違いが 20 件**（§1.3）。多くは監査メタ（`created_by` / `created_at` /

→ **終了コードはパイプ無しで直接取る**（`go test ./... > out; echo $?`）。
📌 **どちらの向きも「パイプが終了コードを壊す」の同じ根。**報告に「真の終了コード」と書くなら、
**パイプを通していないことまで含めて言うこと。**

**下の「0 件」の裏返し。****検査が緑なのは「対象を拾って合格した」からとは限らず、

📌 **「検査が仕事をしなくなったこと自体を検査する」形は 2 種類ある**（RECLAIM-D の言語化）:
**#320 型＝走査の母数を見張る**（`if n != 12 { …無言化している }`）／

**前者は「対象が消えた」を、後者は「例外が要らなくなった」を捕まえる。両方要る。**

**diff を読むだけで目に入る**ので、下の列挙より安い。#334 の実例: 説明コメント 2 行は分割時点から
`parts/ttsAudio.ts` に在り、**前の head は「設定変更を再生中の音へ反映する」と書いた直後が空だった。**
→ **移送・分割の diff を読むとき、コメントの直後が空になっていないかを見る。**

→ **報告の `notes` に 1 行必須**: **列 0 の呼び出し文を両側で列挙して本数が一致すること。**
```
git show <ref>:<file> | grep -nE '^[a-zA-Z_$][A-Za-z0-9_$.]*\('
```
（実測: develop の `tts.ts` = **2 本** 対 ブランチの `features/chat` 全体 = **1 本**）
📌 **序列①②③の死角はここ**——**DOM を撮る方式は「描かれるもの」しか見ない**ので、
**購読の登録・イベントの結線・グローバルの初期化は全部この穴に落ちる。**
📌 **同じ理由で「テスト関数の集合が一致」「golden 差分 0」も素通しする。**

### 🔥 必須項目: **配線層の「取り違え」に変異を当てたか**（2026-09-03・**3 例そろったので様式に格上げ**）

**移送で新しく生まれた配線層（`Deps` / `Configure` / `*_wiring.go` / アダプタ表）は、
「埋め忘れ」は捕まえるが「取り違え」は無言で通す。**型の守りも reflect の網羅検査も
**「在ること」しか見ない**——**同じ型の 2 つを入れ替えても、型は合うので何も鳴らない。**

**実測 3 例**（すべて**全テスト緑**になった）:
| PR | 変異 | 結果 |
|---|---|---|
| #312→#319 | `ApprovalGate` を「常に承認」／`write=false` 固定／`ConvID` 定数化 | 当時は全緑（#319 で塞いだ） |
| #333 CP-TENANT | `Evict` 入れ替え／`InvalidateTenantLogin` を no-op／`Stop`↔`CleanHome` 入れ替え | **CP 全テスト緑**（33 アダプタ中 32 本が無防備） |
| #332 AG-MEMORY | `memoryDeps()` の `ErrCodeBadRev`↔`ErrCodeBadPath` 入れ替え | **agent 32 パッケージ全緑** |

→ **報告の `notes` に必ず 1 行入れる**:
**「同じ型のフィールドを 2 つ入れ替える変異を当て、赤くなったか」**（当てた場所を `file:line` で）。
- **赤くならないなら、それは配線を検査していない**。処方は姉妹家系の写しでよい
  （`git_wiring_test.go` / `mcp_wiring_test.go` が先例。**本物の定数と一致 ＋ `Deps` のフィールド集合と
  検査の集合の突き合わせ**の 2 本立て）。
- 🔴 **`Configure` / `Wired()` を「公開しているのに呼ぶ検査が無い」は同じ穴の別の顔**
  （#332 では **main が参照しない非テスト公開シンボルが `Wired` だけ**という形で出た）。
- 📌 **「インタフェースにしたから検査が要らない」は埋め忘れにだけ正しい。**取り違えには効かない。

🔥 **標準ライブラリの近似で「作り直す」と、変異試験でも捕まらないまま被覆だけが縮む。**
（2026-09-03・AG-CHAT2 が自分で発見して差し戻した）
`japaneseRanges` の範囲表を `unicode.Hiragana/Katakana/Han` で書き直したところ、
**CJK 記号と全角英数の 2 レンジが落ちていた**。→ **範囲表・定数表はテーブルごと写す。**
📌 これは **§4 の両側変異試験でも捕まらない型**である点が重要: アサーションも通る枝も同じで、
**変わったのは入力の被覆だけ**。同じ理由で「テスト関数の集合が一致」「golden 差分 0」も素通しする。
**移送で「同じ意味の標準的な書き方」に置き換えたくなったら、それは移送ではなく変更**——
別コミットにして報告に書く。

🔥 **相対パスの深さは移送で必ず変わり、直し忘れは `t.Skipf` で黙って飛ぶ。**（同上）
`../../` → `../../../../`。テストが Skip に落ちても**緑**なので誰も気付かない。
→ **Skip に落ちていないことを見るテストを 1 本足す。**
⚠️ 完了条件の「テスト関数の集合が develop と一致」に対しては**意図した増加**になるので、
**報告に明記する**（書かないと機械判定で差し戻しになる）。

⚠️ **「検査を強化した」PR では、片側だけ赤いのが正しい**（before は無言で緑＝それが直したかった穴、
mine が赤）。1 の「両方赤」を機械的に当てはめない。**どちらの形を狙ったのかを報告に書く。**

🔥 **表テストのケース名は「どの枝で落ちるか」を主張してしまう。**（#322 参考 A・レビュワーが実証）
`{"36 桁ちょうどの traversal", "../../../etc/passwd/aaaaaaaaaaaaaaaaa"}` は**実際は 37 文字**で、
**長さの枝で落ちていて文字種の枝に届いていなかった**。ケース名が嘘をついても誰も気付かない。
→ **枝ごとに変異を分けて当てる**（実測: 常に true → 8 例中 7 例 FAIL / 長さの枝だけ殺す → 2 例 /
文字種の枝だけ殺す → 3 例。**「このケースだけ落ちない」ことで名前の嘘が出た**）。

⚠️ **テストが「落ちる」のと「固まる」のは別**（#321）。無期限の受信（`<-ch`）で待つテストは、
配線事故のとき **CI が「赤」ではなく「ジョブのタイムアウト」になり原因が読めない**。
**待ちには上限を付け、超えたら理由を書いて FAIL する**（実測: 45 秒ハング → 5 秒で
「道具が出ていない: --write の配線 / 広告漏れ / 名前の変更を疑う」の赤に変わった）。

🔥 **ハングは「壊れている件数」まで隠す**（レビュワーの訂正・実測）。
**ハングはテストバイナリごと落とすので後続が走らずじまいになる**——同じ変異で
**旧版は 1 失敗（＋ハング）／新版は 8 失敗**だった。壊れているものの集合は同じでも、
**報告される集合が 1 → 8 に増える**。
→ **「報せ方が変わっただけ」と書くと効果を過小評価する。「残りが見えるようになった」まで書く。**

🔥 **「テストを元パッケージに残してよいか」は好みではなく、外向き集合の差集合で決まる。**
（2026-09-03・ウェーブ C で **2 例が別々の答えを出し、同じ測り方で両方説明できた**ので規則にする）
移送のとき、元パッケージの未公開状態を駆動しているテストが必ず何本か出る。残すか一緒に移すかは、
**「そのテストを残した場合」と「全部移した場合」で、元パッケージが新パッケージに要求する
未公開シンボルの集合を AST で取り、差集合を見る**:
- **差集合が空 かつ 中身が境界（非テストの元パッケージが既に外から呼んでいるもの）→ 残してよい**
  実例 **AG-GIT**: 18 枚中 2 枚を残しても公開要求は **80 のまま（増分 0）**、2 枚が使う 8 シンボルは
  `Repo` / `handleInitRepo` / `isGitRepo` など**全部が境界**で内臓は 0
- **差集合が大きい／中身が家系の内臓 → 残さず全部移し、駆動を新パッケージ側で作り直す**
  実例 **AG-CHAT2**: 13 本を残すと **110 → 205（+98）**に膨らみ、増える 98 は
  `instrRow` / `reportReconciler` / `foldFact` のような**内臓**＝公開したら internal の意味が消える
📌 **数の大小だけで決めない。「増分が境界か内臓か」まで見る**（境界なら既に公開されている）。
📌 測り方（AG-GIT の実測手順が良い）: **develop 原本のファイル一覧を並べ、家系 N 枚を除いた場合と
N-k 枚を除いた場合で外向き集合をそれぞれ AST で取り、差集合を取る。**

🔥 **テスト関数の本数は「既定ビルドの `go test -list`」で数える。**（2026-09-03・ウェーブ C で
2 トラックの数え方が割れた）AG-CHAT2 は `go test -list`（**1,577**）、AG-GIT は
`grep '^func Test…'`（**build tag 付きファイルを含む**ので **1,633**）で報告し、
**どちらも「+4・消えた 0」で結論は同じなのに絶対値が 56 本ずれた**。
→ **正は `go test -list`。** grep 方式を使うなら**その旨を併記**する。
📌 **結論が同じでも、数え方が違う数字は台帳に並べた瞬間に横並びが壊れる**
（後から読む人には「どちらかが 56 本落とした」ようにしか見えない）。

🔥 **移送のあとは「テスト関数の集合」を develop と多重集合で突き合わせる。**
移送でテストが 1 本消えても**緑のまま**通る。ユニーク集合ではなく**多重集合**で比べること——
サブパッケージに同名のテストが実在する（AG-GIT 実測: 多重集合 1,633 / ユニーク 1,600・
重複 33 は agent の別サブパッケージの同名で **develop でも同じ**）。
**「ユニークで一致」は「1 本も落ちていない」の証明にならない。**

🔥 **エイリアス残数は「AST で数えた値」を書く。ウェーブ B で 2 度ずれた**（#310 は申告 48 / 実測 47、
#315 は申告 12 / 実測 14）。数えるのは **「パッケージスコープの宣言のうち RHS が素のセレクタ」だけ**:
- 継ぎ目のために書いた**関数**（`loginTextFor(lang)`）はエイリアスではないので**足さない**
- **フックの `init` 代入は `= pkg.X` の形をしていないので、そもそも数に入っていない**
  （「init が 1 本消えたから 1 減った」という引き算は成り立たない）
- 🔥 **引数を取るようにしたシンボルは薄いラッパ関数になり、`grep '= pkg\.[A-Z]'` では拾えない**。
  ラッパは**別勘定**にして、`grep -rn 'pkg\.'` で数える。**#315 でずれた原因はまさにここ**
  （拾えないものを別勘定にする段で取り違えた）
- 🔥 **AST 規則（RHS が素のセレクタ）も `&` 付きの RHS を数えない**（`var usageMu = &usagex.Mu`）。
  #318 では**この形の結線が 8 件**あり、AST の 82 と実際の 90 がずれた
- 回収の目標値は **「素の別名 N ＋ ラッパ M ＋ 継ぎ目関数 K」**の 3 つ組で書く（合計 1 つでは足りない）

🔥 **`var` の遠側が `sync.Mutex` のときは、必ずポインタで受ける**（#318）。
`var usageMu = usagex.Mu` は **mutex ごと写して別物にする**ので、追記側と読み側が違う錠を掛ける。
`&usagex.Mu` なら同一実体で、呼び出し側の綴り（`usageMu.Lock()`）も変わらない。
**所有外のファイルが同じ錠を取っているかを必ず確かめること**（#318 では無変更の
`usage_rollup.go:413` が参照していた）。

⚠️ **ただし危険度の書き方に注意**（レビュワーの訂正・司令塔が再現して確認）。
**直接の値コピーは `go vet`(copylocks) が捕まえる**——実測:
```
var usageMu = usagex.Mu
  go build → exit 0（通る）
  go vet   → exit 1  variable declaration copies lock value to usageMu: sync.Mutex
```
vet は全トラックのゲートにも CI にも入っているので、**この形が develop へ無言で入ることはない**。
（司令塔は当初「直列化が無言で消える」と書いたが**言い過ぎだった**。）
捕まらないのは**錠を含む構造体を関数の戻り値で受け渡す形**など。
→ **「vet が通ったから安全」ではなく、遠側が錠なら常にポインタで受け、
所有外が同じ錠を取っていないかを確かめる。**

判断が要ることが出たら、**推測で決めずに止まって聞く**（司令塔へ `intent=question` で 1 通。
司令塔が利用者へ上げる）。

peer メッセージの規律: 1 行目が用件、挨拶・了解・進捗報告は書かない（1 通＝相手の 1 ターン）。
`intent` は欲しい戻りで選ぶ（`notice`/`answer` は何も返らない、`request` はできない時だけ返る、
`question` は短い答えが 1 通返る）。

## 6. 付録 —— 機械置換と検算（運用台帳 §0.5 の全文・凍結・逐語）

**移送と回収は検算の向きが逆**という、このウェーブで最初に確立した規約。
§5 と同じく `~/af-refactor/README.md` からの逐語の写しで、節見出しだけ 1 段下げてある。

### 【原文】台帳 README §0.5 機械置換と検算（ウェーブ B の回収で実測。**移送と回収で向きが逆**）

🔥 **検算の向きは、改名がどちらへ進んだかで決まる。取り違えると偽の差分に埋もれる。**

| | 何が起きるか | 検算 |
|---|---|---|
| **移送 PR**（`main`→`internal`・エイリアスが**増える**） | 改名の雑音で diff が読めない | **逆写像**。ブランチ側に「新名→旧名」を当てて原本と行単位で比べる＝**落ちた行だけが残る** |
| **回収 PR**（エイリアスが**消える**） | 回収後の `pkg.X` は**元から直参照だったものと区別できない**ので逆写像は偽差分だらけ | **前向き**。**develop の package main へ同じ表を当て、ブランチと突き合わせる**＝残差が機械置換で説明できない部分 |

（レビュワーが移送 PR で 3 方式を比較した結論: **正規化トークン列も関数本体の多重集合も、
どちらも改名の雑音に埋もれて結論が出ない**。使えるのは上の 2 つだけ。）

🔥 **移送 PR でも、新名が原本に既に在るなら逆写像は使えない。前向きに切り替える。**
（2026-09-03・AG-GIT が申告 → **司令塔が実物で確認**。上の表への例外ではなく**前提条件**）
逆写像は「新名 → 旧名」を**文字列として**当てるので、**改名先の綴りが原本に別の意味で
存在していると、その別物まで巻き込んで書き換える**。
実例（#327）: 非公開関数 `workingCopyID` を `WorkingCopyID` へ公開したが、**原本の `Repo` には
既に公開フィールド `WorkingCopyID string \`json:"workingCopyId"\`` が在る**（`git.go:58`）。
逆写像を当てると**このフィールド宣言まで未公開に潰し、JSON から消える**＝偽差分の山になる。
- ✅ **当てる前に 1 手で分かる**（判断ではなく検査）:
  ```
  for n in <改名表の新名>; do git grep -w "$n" origin/develop -- <家系のパス>; done
  ```
  **1 つでもヒットしたら逆写像は捨てて前向き**（develop の原本に改名表を当て、ブランチと突き合わせる）。
- 📌 同じ根の既知の罠がもう 2 つある——**小文字始まりの別名は変数名と衝突する**（下記）／
  **`gofmt -r` は行末コメントを落とす**。**共通するのは「機械置換は意味を見ない」**。
- 📌 **ワーカーが「規約の例外だ」と言ってきたら、まず実物で確かめる。**
  今回は**規約の側が不完全**だった（例外ではなく前提条件が抜けていた）。

🔥 **機械置換の走査範囲は `package main`（maxdepth 1）に限定する。**
別名は package main にしか無いのに `internal/` まで走らせると、**内側の DI 継ぎ目を直参照に潰して
スタブが効かなくなる**（実測: `internal/mcpx` の `readUIPrefs()` を潰した）。
**同名衝突は実在する**——`internal/agents/{agy,copilot}/usage.go` に**同名の `usageMu`** が居る。
📌 **走査範囲を間違えたことは `git diff --numstat` に `internal/` が出ることで分かる。**

🔥 **大文字始まりの別名は struct のフィールドキーと衝突する。**（2026-09-03・RECLAIM-C で実測）
`gofmt -r 'Repo -> gitx.Repo'` は **`SomeStruct{Repo: x}` の複合リテラルのキーまで書き換える**。
develop の package main に **18 箇所**あり、`invalid field name gitx.Repo in struct literal` で
ビルドが落ちた（**落ちるので無言では入らない**が、後始末を当てるまで進めない）。
→ **当てる前に `git grep -nE '\b<新名>:' ` でフィールドキーとしての出現を数える。**

🔥 **そもそも呼ばれていない別名は、置換せず消すだけでよい。**（同上）
`firstLine` は**ローカル変数と同名**で置換が荒れたが、調べると **package main から 1 度も
呼ばれていなかった**。→ **置換表に入れる前に「package main からの呼び出し数」を数える。0 なら
表から外して別名ごと削る**——衝突の解決コストがまるごと消える。

🔥 **小文字始まりの別名は変数名と衝突する。** `gofmt -r 'assistant -> assistants.Assistant'` は
**ローカル変数 `assistant := …` まで書き換える**（Go では型と変数が同じ綴りを取れるので避けられない）。
→ **当てる前に走査し、衝突が少数なら機械置換から外して手で直す。**

🔥 **`gofmt -r` は書き換えた式に付いていた行末コメントを落とす。**（#322 で実測。残差の主因だった）
→ **機械置換のあとは `//` 行を develop と突き合わせる。**コメントは**ビルドもテストも通る**ので、
これを見る検査は他に無い。

🔥 **複製を 1 本化するときは「どちらが原本か」をコメントまで含めて見る。**（#322・ワーカーが自分で発見）
実例: env ヘルパ 5 本を `internal/envx` へ畳むとき**写し元に `internal/auth/env.go` を使ったが、
doc コメントは原本の `main.go` 側にしか無かった**ので、`EmailSet`/`DomainSet`/`SplitCSV` の
説明 4 行が無言で消えた。**コードが byte 一致でも、原本と写しはコメントが違う。**

🔥 **回収 PR のゲートには「全 build tag の vet」を含める。**（#322 の B-1）
タグ付きファイルは既定ビルドに入らず **gofmt / vet / build / test / CI 6 ジョブのどれも触らない**ので、
移送・回収で参照が腐っても**緑のまま通る**。
`for t in clicontract drift driftlive tui_contract; do go vet -tags "$t" ./...; done` を
**両モジュールで**（実測 8 通り）。※ CI 側にも入れた（PR #323）。
