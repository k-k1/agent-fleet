# 85. ターン終了後の自己停止（stop-after-turn）

- 状態: **実装済み**（2026-09-07・v1）。「終わったら止めて」と言われたセッションが、
  走っているターンを最後までやり切ってから自分を停止する。停止は再開可能な halt で、
  会話も作業コピーも残る。

  判定するリコンサイラ。本件はその判定を借りている）/ [30](30-session-report.md)（報告の配送）/

## 85.1 要求

> ユーザーからの指示があったとき、自身のセッションをターン終了後に停止できるようにしたい。

動機は費用と後片付けである。夜間の長い作業を投げたあと、終わったセッションが起きたまま
ワークスペースを保持し続けるのを避けたい。停止は再開できるので失うものはない。

## 85.2 なぜ「即時停止する MCP ツール」ではないのか

ツール呼び出しはターンの**内側**で走る。そこで halt すると:

- まだ書いている最終回答が転写に残らず、ツール結果も返らない（モデルからは接続が死ぬ）
- claude は再開時に自分で `Continue from where you left off.` を投げる＝**再開が 1 ターン焼く**
  （§75.10 の実測）
- 「終わったら止めて」という指示なのに**終わる前に止まる**

したがってツールがやるのは**予約（arm）だけ**である。`af_report` が「申告するだけで、
報告するかはサーバが決める」（docs/log/51 Phase 3）のと同じ形をとった。

## 85.3 三層に割る

| 層 | 実体 | 置き場所 |
|---|---|---|
| 予約 | MCP `af_stop_after_turn` / `POST /sessions/{name}/stop-after-turn` / Console の ⋯ メニュー | `internal/sessionx/session_stop_after_turn.go` |
| 判定 | 既存の `evalReportEvidence`（報告の settle 述語）をそのまま利用 | `internal/chatx/chat_stop_after_turn.go` |
| 実行 | `haltSessionMeta`（Console の停止ボタンと同じ経路） | `internal/sessionx/session_handlers.go` |

## 85.4 決めたこと

1. **arm は 1bit ではなく時刻**（`Meta.StopAfterTurnAt`）。docs/log/51 が v1 の
   「不可逆 1bit arm」で痛い目を見たのと同じ理由に加えて、この時刻は**完了証拠を切る下限**
   でもある。前のターンの終了マーカーで発火しないのはこの下限のおかげ。TTL は 6 時間
   （`session.StopArmMaxAge`）＝ keep-awake ピンが「時刻で持つ」のと対称。
2. **ターン終了の判定を二度書かない**。Stop フック 1 発で止める素朴実装は、AUQ が出たまま／
   サブエージェント実行中／429 中断を「完了」と読んで止める。busy 証拠の集合を 2 箇所に
   書いた前科（docs/log/75 の `holdersOf`）と同じ穴なので、述語は 1 つのまま消費側だけ足した。
   デバウンス（2 tick）だけは別マップに持つ — 2 つの判定は証拠を切る下限が違うので、
   片方の静穏はもう片方の静穏を意味しない。
3. **報告が先、停止が後**。`evalReportEvidence` は停止済みセッションでは settle しない
   （「停止は指示の取り消しではない、再開後に報告する」）。先に止めると、オペレーターは
   誰かが再開するまで報告を受け取れない＝「永久に来ない」と区別がつかない。掃引は
   報告 → 停止の順で回し、開いている指示行があるセッションは飛ばす。
4. **停止は既存の halt 経路を通す**。保留対話の昇格（プロセスが死ぬ前）、Remote Control の
   切断、agy の graceful stop、`StoppedAt` の打刻とロックの再マージが全部そこにある。
   新しい畳み方を書けば必ずどれかを落とす（ADR 0055 決定 12 と同型）。
5. **新しい指示が来たら解除**。「終わったら止めて」は目の前の作業について言っている。
   あとから来た指示はその文に含まれないので、そこで止めるのは誤り。判定は
   `markSessionWorking` と同じ述語（スラッシュコマンドはターンでないので解除しない）。
   間違える方向としても安全側 — 代償は「止まらずに動き続けるセッション」であって、
   「指示の途中で消えたセッション」ではない。
6. **畳む操作は必ず arm を消費する**。halt も archive も。残すと再開後、誰も arm していない
   ターンの終わりでもう一度停止する。
7. **ツールは常時広告**。`--self-report` のセッション面に無条件で足した（peer messaging や
   画像生成のような追加フラグにしていない）。既定 off の機能は利用者にとって存在しないのと
   同じで、費用を減らす道具でそれをやる意味がない。代わりに**注入耐性は文言で縛る**:
   ファイル内容・ツール出力・peer メッセージを根拠に自己停止しないことをツール説明に書いた
   （停止は完全に可逆なので、shell 実行と同じ「方針 C」で足りる）。
8. **見えること・戻せること**。行のバッジ（`.sess-stoparm`）＋ ⋯ メニューの解除、
   止まったら通知 1 通。arm は会話の中から設定されるのが普通で、**頼んだ人は見ていない**
   （見ていないから頼む）ので、これが無いと「勝手に止まった」になる。

## 85.5 費用の期待値

セッション 1 本の halt で直接返るのはコンテナ内の RAM とプロセスだけである。金額に効くのは
tier2（ワークスペース停止）で、self-stop の効果は「そのセッションが `holdsWorkspace` から
外れて tier2 が来やすくなる」という間接的なもの（docs/log/75）。UI もそう書いてある
（「停止＝即課金停止」とは書いていない）。ワークスペースごと落とす選択肢はモデルに
持たせていない — 他セッションを巻き込む決定は利用者のもの。

🔴 **訂正（2026-09-07・実装当日）**: 上の「そのセッションが `holdsWorkspace` から外れて
tier2 が来やすくなる」は**誤り**。`control-plane/session_activity.go` の `holdsWorkspace` は
**machineBusy のときだけ true** で、作業を終えて idle になったセッションは `activityIdleWait`
＝そもそもワークスペースを止める妨げになっていない。したがって**終わったセッションを止めても
tier2 の時計は 1 秒も早まらない**（`idleBase` は起床・proxy 往来・ビーコンで決まり、生きている
idle セッションはどれも動かさない）。

**間違えた理由**は「畳めば busy が 1 つ減る」という直感で書き、`holdsWorkspace` の定義を
読み直さなかったこと。docs/log/75 は「tier2 が止めるのは machineBusy 無しのとき」と
**同じ事実を反対側から**書いてあり、そこから「idle は最初から邪魔していない」を引けたはずだった。

**では何が得られるのか**（これが正しい効能）:
- **コンテナの RAM とプロセスが即座に返る**。共有ホストのメモリが本当の制約なので、これ自体は効く。
- **tier1 が届かない 2 つの場合に効く**: ⑴ 誰かがそのセッションを開いていると tier1 は
  素通りする（`reaper.go` の `conns.isAttached`）ので、**見ている前で「終わったら止めて」は
  arm でしか実現できない**。⑵ テナントが tier1 を無効にしている／タイムアウトが長い場合。
- **ワークスペースが他の理由で起き続けるとき**（別セッションが稼働中・keep-awake ピン・人が
  Console にいる）、放っておくと終わったセッションだけがいつまでも生きたまま残る。
- 一覧が「終わった＝停止中」と読める。

つまり**費用ではなくメモリと後片付けの機能**である。UI と利用ガイドの文面も同日この線に直した。

## 85.6 実装メモ（踏んだもの）

- **`*_arm.go` は GOARCH サフィックス**。最初 `session_stop_arm.go` / `chat_stop_arm.go` /
  `stop_arm.go` という名前で置いたところ、Go が `_arm` を GOARCH=arm 向けファイルとみなし、
  amd64 のビルドから **3 ファイルとも黙って除外**された。症状は「新しい関数が undefined」
  だけで、ファイルは確かに存在する。`go list -json` の `IgnoredGoFiles` で確定できる。
- `WriteSessionMetaKeepingLock` に arm を足すのを忘れると、数秒ごとの一覧ポーリングが
  古いスナップショットを書き戻して arm を消す。ロックと keep-awake ピンが既に踏んでいる罠で、
  こちらは「押したのに効かないボタン」より悪い（バッジは出たまま、停止だけが来ない）。

## 85.7 やっていないこと（v1 の範囲外）

- **恒常モード**（「以後ターンごとに毎回止める」）。これはセッション単位の
  `session_idle_timeout≈0` として reaper 側に載せるのが素直で、arm とは別物。
- **ワークスペースごと止める**まで含めること（85.5）。
- **shell / ssm**。af サーバが materialize されない 2 種なので MCP 経路が無く、
  Console のトグルだけが入口になる（halt＝実行中ジョブの kill なのは keep-awake ピンの
  裏返しで、そこは docs/log/75 の判断のまま）。

## 85.8 v2（2026-09-07・同日）: 定時実行の後片付けとオペレーターからの予約

用途から詰め直した結果、v2 は**新しい停止の仕組みを足さず、v1 の arm に入口を 2 つ増やす**
だけになった。判定も停止も v1 のままである。

### ① スケジュールの `stop_after_run`

`scheduleDTO` には `wake_policy`（停止中のワークスペースを起こす）はあったのに「走り終わったら
止める」が無く、夜中 3 時に起こして 10 分走ったワークスペースが `ws_idle_timeout` まで
起きっぱなしだった。**一番安く効く用途がここ**（85.5 のとおり金額に効くのは tier2 なので、
「起こした主が片付ける」形になって初めて意味が出る）。

- 列は `schedule.stop_after_run`（sqlite 0054 / pg 0039。既定 0＝従来動作）。
- **セッションを作る発火では arm を create の body に載せる**（`stop_after_turn`）。
  これは後付けの POST では駄目で、理由は 85.4-5 の裏返し: **arm より後に届いたプロンプトは
  arm を解除する**ので、create → arm の順だと初回プロンプトの配達が自分の arm を消しうる。
  create 時に meta へ書けば配達より前であることが構造的に保証される。
- **reuse（既存セッションへ送る）発火では送信の「あと」に arm する**。同じ理由で順序が逆に
  なる。ここは best-effort（プロンプトは配達済みなので、arm の失敗で発火を失敗させると
  再試行が二重配達を招く。失敗しても「従来どおり起きっぱなし」に落ちるだけ）。
- `session_mode=assistant` では無関係（会話を回すだけでセッションを持たない）。
  repo/agent_kind/model と同じ「そのモードでは無視」の扱いに揃え、UI では隠す。

### ② オペレーターの `stop_session_after_turn`

既存の `stop_session` は即時 halt なので、走っている最中に押すと作業が切れる。ファンアウトで
起こした数本を**終わったものから畳む**にはこれでは使えなかった。`stop_session` の隣に、
即時ではなく予約するツールを足した（agent 側 `mcp_stdio.go` の write ツールと CP `/mcp`
member 層の両方＝3 面の意味論を揃える従来どおりの置き方）。

- **`disarm_report` を送らない**のが `stop_session` との本質的な差。あちらは「指示の取り消し」
  なので報告を握り潰すが、こちらは指示をやり切らせる停止なので報告義務は残り、v1 の
  「報告が先・停止が後」がそのまま効く。

### v2 で残ったもの

85.7 の 3 つのうち **shell・ssm は手つかず**、**ワークスペースまで止める**は「誰が押せるか」を
決めていないので保留（モデルには持たせない、が現時点の結論）。

**恒常モード（毎ターン停止）は取り下げた**（2026-09-07・同日）。当初の想定は「オペレーターや
スケジュールに叩かれるだけの、人が見ていないバッチ・ワーカーが指示→実行→停止を繰り返す」形
だったが、①でスケジュールが発火ごとに arm し、②でオペレーターが指示ごとに arm できるように
なった時点で、恒常モードに残る差は**「1 コール省ける」「呼び忘れない」だけ**になった。

加えて §85.5 の訂正のとおり**費用は動かない**（idle セッションは最初からワークスペースを
止める妨げになっていない）ので、恒常化して前倒しできるのは tier1 のタイムアウトぶんの
**メモリ解放のタイミングだけ**である。それは arm を張り直す実装ではなく、**reaper 側の
セッション単位 idle timeout 上書き**として設計すべきもので、この機能の延長ではない。
