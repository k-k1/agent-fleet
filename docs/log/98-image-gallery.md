## 98.1 要求と、決め方

利用者の言葉: 「フォルダの画像をカードで並べて見比べたい」。いちばん効くのは画像生成
（[ADR 0069](../decisions/0069-image-generation-providers.ja.md)）で、出力は
`~/.cache/agent-fleet/generated/<sid>/` に溜まるがフォルダ名がセッションの UUID なので、
ファイルツリーからは事実上たどれない。1 回で複数枚・何度も回すのが普通なのに、見比べる場所が
どこにも無かった。

決め方は ADR 先出し。利用者に確認した 4 点と答え: ①カード本体＝拡大／角＝ペイン（既存の
転写カードと同じ分け方）、②導線は 5 か所**全部**、③ P0 は「ギャラリー＋導線」に絞る、
④ ADR を先に書いてからコード。

## 98.2 起草で分かった「作らなくていいもの」

- **サムネイルの口は既にあった** — `GET api/fs/download?path=…&thumb=<最長edge>`（`fs_thumb.go`）。
  引数は助言的（デコーダ無し・小さすぎる・巨大は原本が返る）で、呼ぶ側に能力判定が要らない。
  **キャッシュ鍵に最長辺が入る**ので、ミラーと違う値を頼むと同じ画像を 2 回デコードする
  → ギャラリーも 512 に揃える、という決定はここから出た。
- **拡大の部品もあった** — `viewer/ImageView.tsx`（zoom ハンドルが外に出ている）と
  `mirror/parts/ImageLightbox.tsx`。
- **ペイン種別追加の定型 8 か所**（union・`migrate.ts` の検証・`sameTarget`・描画 switch・
  `paneTitle`・`LayoutMap` 略号・ポップアウト可否・i18n）は 96 章で踏んだばかりだった。

足りないのはフォルダ単位の面と導線だけ、という結論が出たので、新しいエンドポイントは
`fs/tree` への `mtime` 1 フィールドだけに抑えられた。

## 98.3 レビューで剥がれた 4 つの思い込み

起草の翌ステップで ADR をコードに突き合わせて読み直したところ、**4 か所が事実と食い違っていた**。
どれも grep 1 回で分かるもので、起草時に引かなかっただけである。

1. **「ペインにすれば `Ctrl+F` も只で付く」** — 付かない。Console に find-in-pane の仕組みは無く
   （`features/keys/commands.ts` にも `bindings.ts` にも `mod+f` は無い）、`Ctrl+F` はブラウザ素の
   検索でカードのファイル名しか当たらない。**「只で付くもの」を数えるときは実在を確かめる。**
2. **「フォルダ名は Console からは導出できない」** — できる。`uuidV5(dir + "|" + name)` の入力は
   両方 wire にあり、SHA-1 は `crypto.subtle` にある。やらない理由は「不可能」ではなく
   **Agent の内部事情を写す重複**である。🔴 決定の根拠を偽の不可能性に置くと、次の読者が
   「できるじゃないか」で決定ごと壊す。
3. **「ミラーの共有ファイル欄」** — そんな面は無い。あるのは転写の中の `FileCard`
   （`transcript/blocks.tsx`）で、**画像カードは本体＝拡大・角＝ペインで既に 2 つとも埋まっている**。
   3 つ目のボタンを角に足すと決定 5 の分け方が読めなくなるので、導線は既にあるボタン列
   （共有するライトボックスのバー）へ移した。
4. **導線の置き場が `viewer/parts/FileViewerShell.tsx`** — Shell は読む面そのもので**ヘッダを持たない**。
   ヘッダは `FileHeadControls.tsx`（`FileView` が組み立てる情報バー）だった。

補った欠落も 5 件: `gallerySession` が型に居るだけで無説明だったこと、ADR 0017 を関連に挙げながら
コマンド表の扱いが無かったこと（P0 では登録しない——フォルダが要るのでグローバルなキーに渡す当てが
無い）、古い Agent への落ち方（`mtime` 無し＝名前順・wire 無し＝項目を出さない）、
`useBackClose` が部品でなく `MirrorView` 側にあること、中継の 4 か所の名指し。

## 98.4 3 レーンに割って並列で実装する

依存が一直線にならないように切った。

| レーン | 範囲 | 依存 |
|---|---|---|
| A `feat/0080-wire` | `fsEntry.mtime`・`wireSession` の 2 フィールド・CP の 4 か所・`types/session.ts` | 無し |
| B `feat/0080-gallery` | ペイン種別の 8 か所・`features/gallery/`・ライトボックスの引き上げ | 無し |
| C `feat/0080-entrypoints` | 導線 5 つと i18n | A と B |

C を止めないために、**契約を先に文字で固定**した: `openGallery(path, {focus, session, newPane})`、
`Session` の 2 フィールド、共有ライトボックスの置き場 `features/viewer/ImageLightbox.tsx`、
`onOpenFolder` は渡されたときだけ描く。C はこの契約に対して書き始め、仕上げの前に A と B の
ブランチを自分の worktree に merge して緑を出した。所要は 3 本とも 20〜40 分で、CI は全緑。

**効いた指示**（93 章の 30 則から）: `-count=1` を必ず付ける、緑と言う前に陽性対照を取る、
戻すのは `git checkout` ではなく Edit、終了コードはパイプを通さずに取る。3 本とも陽性対照の
一覧（A が 6 種、B が 8 か所、C が DOM 4 件）を報告に載せてきた。

## 98.5 実装で分かったこと

- 🔥 **`gallerySession` に表示名を入れてはいけない。** ADR の「表示専用」という文言（起草者＝
  レビュー担当の誤り）を読んだ C が `displayName(s)` を渡し、**日本語の題が再読み込みで消える**
  状態になった。レイアウトの保存値は `migrate.ts` がセッション名の字種
  `^[A-Za-z0-9_-]{1,40}$` で検証するためで、正しくはスラグを入れて描画側で引き直す。
  ADR は #621 で訂正した。**レーンをまたぐ契約は、コメント 1 行の言い回しで事故る。**
- **「新しい順」は全件に `mtime` があるときだけ**（B の判断・`gallery.ts` の `hasTimes`）。
  ADR は「無ければ名前順」としか書いていなかったが、混在したリストでは時刻の無い分が
  いちばん古い写真の位置に沈み、**間違った答えを自信満々に出す**。
- **画像判定の表を 2 枚にしない**ために、A が `imageContentType` を `internal/filemeta` へ切り出した
  （`sessionx` は `package main` を import できない）。設計から外れた唯一の判断で、妥当だった。
- B が試験中に**生の NUL バイトをソースに混入**させ、「弾かれるべきパスの試験」が偽陽性で緑に
  なっていたのを自力で検出した（同種の事故は過去にもある）。エスケープ表記に直し、
  空白入りの正当なパスが通る試験を足して塞いだ。

## 98.6 🔴 マージ順を間違えて C の PR が B を連れて行った

C の PR（#620）は B のブランチを取り込んだ木で緑にしてあった。その状態で **#620 を先にマージ
した**ため、B の途中版（`2cc034ef`）が develop に入り、B の残り（GalleryView 本体を含む
`b225a8d7`）が develop と三方向で衝突した。#622 は GitHub 上で `mergeable=false` になり、
B が develop を取り込み直して解消した。

- 手元の `git merge-tree`（ort）は**きれいに解けると答えた**が、GitHub の判定では衝突マーカーが
  2 か所出た。**「ローカルで解けた」は「GitHub でマージできる」ではない。**
- 一般化: **依存のあるレーンは、依存される側から順にマージする。**「取り込んだ木で緑」は
  取り込んだ相手の**その時点の版**を連れて行くという意味で、レビューの単位が静かに壊れる。
  親（レビュー役）が PR に順序を書いておくだけでは足りず、順序そのものを守る必要がある。

## 98.7 実測: 生成画像の PNG には既に seed が埋まっている

利用者から「生成画像の seed などのプロパティを見たい・コピーしたい」という要望が出たので、
配備の `~/.cache/agent-fleet/generated/` の 251 枚を PNG チャンク単位で走査した。

- **comfy（自前エンジン）経路の PNG は `tEXt` チャンク（キー `prompt`）を持つ。** 1 枚 1550 バイトで
  中身は ComfyUI の API グラフ。`KSampler` に `seed: 1755201164188694318`・`sampler_name: dpmpp_2m`・
  `scheduler: karras`・`steps: 20`・`cfg: 7.0`、`CheckpointLoaderSimple` に ckpt 名、
  `EmptyLatentImage` に size、`CLIPTextEncode` に正負プロンプト。
- **ベンダー API 経路（codex / agy）の PNG には `tEXt` が 1 件も無い。** 過去分は原理的に復元できない。
- **サムネイル（`thumb=512`）は JPEG 再エンコードなのでメタは消える。** 読むなら原本か、
  Agent 側に「ヘッダだけ読む」軽い口が要る。
- af 自身は seed をどこにも記録していない（`Result`・`StoredFile`・MCP の答えのいずれにも欄が無い）。

この 3 件は起草中の ADR 0081（Console から画像を作るペイン・未マージ）の決定 3 が扱う範囲だった
ので、**表示もコピーも 0081 に一本化する**と利用者が決め、実測をそちらへ渡した。0080 側では
実装していない。

  同一ホスト 6 本で待つ）も込みにする。
