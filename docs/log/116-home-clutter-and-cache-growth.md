# 116 HOME の散らかりとキャッシュの肥大（2026-09-24）

利用者の訴え:「エージェントの作業で HOME や `.cache` にゴミが大量にばらまかれている」。
開発者の Workspace 1 台を実測し、当座の掃除・ポリシー追記・製品側の案を記す。

## 実測（掃除前）

HOME 113G、ボリューム使用率 84%。中身は性質の違う 2 種類に分かれる。

| 種類 | 場所 | 量 |
|---|---|---|
| 再生成できるキャッシュ | `~/.npm/_cacache` | 41G（npm は古いものを消さない） |
| | `~/.cache/go-build` | 34G（Go の 5 日トリムが worktree の数に追いつかない） |
| | `~/.cache/{copilot,agent-fleet,uv,chromium-headless,ms-playwright}` | 約 6.5G |
| テストの取り残し | `~/.cache/af-codex-drift-*` ×8・`af-probe-*` | 約 0.85G（7 月作成。`drift_test.go` は `t.Cleanup` で消すので、残るのは強制終了されたときだけ） |
| 持ち主不明の作業物 | HOME 直下の非ドット項目 | **193 個**（`probe-*`・`review-9xx`・`muse-probe`・`af-ec2b`・`sb-bundle.js` 等、179 個が 9 月作成）。合計は 2G 程度 |

容量を食っているのはキャッシュで、散らかりの原因は作業物という分担になっている。

## 当座の対処（実施済み）

他セッションのビルドが走っていないことを `ps` で確かめてから
`go clean -cache`・`npm cache clean --force`・`uv cache prune` とテスト残骸の削除を実行した。
**使用率は 84%（空き 75G）から 67%（空き 150G）へ下がった**。HOME 直下の 193 個は、必要なものかどうかを
エージェントが判断できないので手を付けていない。

## 原因

作業物については、ポリシー（`workspace/workspace-notes.md`）に「使い捨てのファイルをどこに置くか」が書かれていなかった。
`/tmp` は全セッションで共有され、再起動で消える（memory: tmp-file-collision）。
そのためエージェントは `~` の直下に逃げ、あとから誰にも持ち主が分からなくなる。

## ポリシー追記（この PR）

- `workspace-notes.md` の「What survives」に「使い捨ては `~/.af-work/<session>/`。`~` と `~/.cache` の直下に置かない。
  終わったら消す」を 1 項目足した。
- `notes/environment.md` の Disk 節に、作り方と、キャッシュを空ける 3 コマンド（他セッションのビルド中は実行しない）を足した。
- **`<session>` の出どころ**: `$AF_SESSION_NAME` はターミナル（CLI）起動の tmux 環境にしか入らない
  （`session_tmux.go:42`）。Managed では空なので、作業コピーのディレクトリ名で代える。
  代わりに使う名前がないと全員が `~/.af-work/` 直下に置くことになり、散らかる場所が 1 段下がるだけになる。

## 製品側の案（未着手）

1. **セッション作業ディレクトリを Agent が用意する。** ターミナル起動で `~/.af-work/<slug>` を作り、
   その場所を環境変数（例: `AF_WORK_DIR`）で渡す。セッション削除（ADR 0101）のときに一緒に消す。
   ごみ箱には入れない。定義からして使い捨てだからである。
   - 未決: Managed は kind ごとの共有デーモンなので、セッション単位の環境変数を渡せない
     （`codex/driver.go:88`）。作業コピー名で鍵にした場合は、作業コピーの削除に合わせて消すことになるが、
     作業コピー名とセッションのスラグは一致しないことがある（例: 作業コピー `wip-sedfu6c` とセッション `sml4fdo`）。
   - `TMPDIR` をそこへ向ける案は採らない。CLI 自身の一時ファイルまで巻き込み、影響範囲が読めないからである。
2. **キャッシュの上限を Agent が見る。** 1 日に 1 回 `go-build` と `_cacache` の量を測り、
   しきい値（例: ディスクの 15%）を超えたら掃除する。条件は、同じコンテナ内に `go build`/`go test`/`npm ci` の
   プロセスがないことである。Go のキャッシュも npm のキャッシュも年齢で選んで消す手段がなく、全消しになる。
   そのため、掃除した直後の 1 回のビルドが遅くなることを受け入れる設計になる。
3. **Console の設定 > 環境に「キャッシュだけ掃除」を置く。** 内訳（キャッシュ別の量と HOME 直下の作業物の数）を見せる。
   今ある admin の「clean home」（`runtime_docker.go:557`）は `homeKeep` 以外をすべて消すので、
   日常の掃除には重すぎる。案 3 はその隙間を埋める。

## 未決

- 案 1 で、Managed セッションの作業ディレクトリをどう鍵にするか（上記）。
- 今ある 193 個の一括整理は、利用者が一覧を見て選ぶ。自動では消さない。

## 実装（2026-09-25）

上の「製品側の案」に利用者の判断が入ったので、次の形で実装した。案の本文は起票時のまま残す。

- **案 2（Agent による自動掃除）は作らない。** 利用者の判断。Go も npm も年齢で選んで消せず全消しになるため、
  いつ次のビルドを遅くするかは人が決める。
- **案 1 はターミナル（CLI）セッションだけ。** `startSessionTmux` が `~/.af-work/<slug>` を作り、`AF_WORK_DIR` で渡す。
  `removeSessionSideFiles` がセッションの削除（ADR 0101 のごみ箱行き）でこれを消す。アーカイブには入れず、復元でも戻らない。
  Managed への配達は #978 に切り出した（`AF_SESSION_NAME` と同じ経路の問題）。
  - 案 1 の未決（作業コピー名で鍵にしたときの削除契機）は、Managed が #978 でセッション名を受け取れるようになれば消える。
    それまでは、ポリシーが「Managed では自分で消す」と書いておく。
- **案 3** は設定 > マシンの「ツールのキャッシュ」節として実装した。`GET/DELETE /cleanup/tool-caches[/{name}]`、`tool_caches.go`。
  - 測るのはボタンを押したときだけにした。go-build は数十万ファイルあり、既存の「Agent Fleet が使っているディスク」
    （タブを開くと測る）に混ぜると、タブを開くたびに重くなる。
  - 同じコンテナの `/proc` に、そのキャッシュを使うプロセス（`go`、`node …/npm-cli.js`、`uv`、`python -m pip` など）が
    いる間は、409 `cache_in_use` で断る。数えるのは押した時点と削除の直前の 2 回。
  - ディレクトリ自体は残し、中身だけ消す。`$AF_WS_SCRATCH` ではディレクトリが作業ディスクへのシンボリックリンクで、
    リンクごと消すとキャッシュが home に戻ってしまう。
  - 場所は各ツールの変数（`GOCACHE`・`npm_config_cache`・`UV_CACHE_DIR`・`PIP_CACHE_DIR`）が Agent の環境にあればそれに従う。
    🔥 テストはこの 4 つを必ず一時ディレクトリへ向ける。向けないと、CI や手元でこれらが設定されていた場合に、
    テストが本物のキャッシュを空にする。

## 追記: 古い CLI の版（#981、2026-09-25）

同じ Workspace で、キャッシュとは別にもう 1 種類の肥大が見つかった。**使い終わった CLI の版**である。

| CLI | 場所 | 残っていた版 | 量 |
|---|---|---|---|
| copilot | `~/.cache/copilot/pkg/linux-x64/<版>/` | 15（1.0.73〜1.0.88） | 2.7G |
| cursor | `~/.local/share/cursor-agent/versions/<版>/` | 12（2026.07.20〜2026.09.23） | 4.6G |

- copilot は、プラットフォーム用のバイナリが初回起動時に自分を `pkg/<版>` へ展開する（実測: 起動中のプロセスが
  `pkg/1.0.88/app.js` を開いている）。cursor は、entrypoint のピン導入も上流の `install.sh` も `versions/<版>` に
  展開して symlink を張り替えるだけである。どちらも古い版を消さない。home はイメージより長生きするため、
  ピンを上げるたび、あるいは自己更新 opt-in で最新を取るたびに 1 版ずつ溜まる。
- 起票時の「cursor がピンを越えて自己更新している」という観察は、この Workspace で自己更新 opt-in が ON だった
  （`AF_AGENT_SELF_UPDATE=1`）ためで、設計どおりの動きだった。agy の自己更新問題とは別物である。

**上の「案 2 は作らない」と矛盾しない理由**: 案 2 で自動掃除を見送ったのは、キャッシュは次のビルドがまた読むので、
消すと遅くなるからだった。古い版は二度と読まれないので、消しても何も遅くならない。

**実装**（`cli_version_prune.go`）: Agent の起動時に 1 回だけ、バックグラウンドで消す。版が変わるのは Agent より先に
走る entrypoint の中だけなので、起動時の 1 回で足りる。CLI ごとに残す版は次のとおり。

- launcher が今指している版（cursor は `~/.local/bin/{cursor-agent,agent}` の symlink、copilot は `@github/copilot` の `package.json`）
- `versions.json` のピン（opt-in を OFF に戻したとき、entrypoint はピン版のディレクトリへ symlink を張り直すだけで、再ダウンロードしない）
- `/proc/*/{exe,maps,fd}` のどれかがその版の下を指している版（実行中のセッション）

判断できないときは、その CLI の版を 1 つも消さない。該当するのは、launcher が home の外を指しているとき、
copilot の `package.json` が見つからないとき、動いている copilot のバイナリが差し替え済み（`(deleted)`）で版を
特定できないとき。版の形をしていない名前と symlink には触らない。`versions.json` の無い環境（native ランタイムで
他人のマシンの home を使う場合）でも何もしない。

レビュー（codex の子セッション）の指摘で 2 点を直した。

- `/proc` は symlink を解決した実パスを返す。`~/.cache` や `~/.local/share` が別ストレージへの symlink だと、
  書いたままの root と突き合わせても一致せず、実行中の古い版を見落として消す。root は書いたままのパスと
  解決後のパスの両方で照合する。
- `/proc` の列挙や、自分のプロセスの exe・maps・fd が読めないときに、黙って読み飛ばしていた（読めないと「使用中なし」とみなす安全でない向き）。
  今は消さない側に倒す。例外は、自分を non-dumpable にしたプロセス（ssh-agent など）で、同じ uid からでも
  EACCES になる。そこで毎回止まると永久に掃除されないので、読める cmdline に CLI の名前が無ければ読み飛ばす。
- 2 巡目の指摘で、さらに 2 点を直した。1 つ目は、他の uid のプロセスを丸ごと読み飛ばしていたこと。home は他人から読めることが多く、
  他の uid のプロセスでも古い版を実行できる。そこで他の uid のプロセスも読み、EACCES のときは上と同じく cmdline で判断する。
  2 つ目は、copilot の「今の版」にプラットフォーム用パッケージの版も含めたこと。Agent が掃除と並行して起動する
  Managed の copilot は、この版を展開する。ふだんは本体の版と同じだが、ずれても新しいセッションが使う版を消さないようにする。

実機（この Workspace）: 古い cursor（2026.08.04）の node を動かしたまま実行したところ、23 版・5,805 MiB が消えた。
残ったのは、copilot 1.0.88、cursor の 2026.08.04（使用中）・2026.09.15（ピン）・2026.09.23（現行）で、
両方の CLI とも `--version` はそのまま動いた。
