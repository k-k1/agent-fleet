# 116 HOME の散らかりとキャッシュの肥大（2026-09-24）

利用者の訴え:「エージェントの作業で HOME や `.cache` にゴミが大量にばらまかれている」。
開発者の Workspace 1 台を実測し、当座の掃除・ポリシー追記・製品側の案を記す。

## 実測（掃除前）

HOME 113G、ボリューム使用率 84%。中身は性質の違う 2 種類に分かれる。

| 種類 | 場所 | 量 |
|---|---|---|
| 再生成できるキャッシュ | `~/.npm/_cacache` | 41G（npm は古いものを消さない） |
| | `~/.cache/go-build` | 34G（Go の 5 日トリムが worktree の数に追いつかない） |
| | `~/.cache/{copilot,agent-fleet,uv,chromium-headless,ms-playwright}` | 約 6.5G |
| テストの取り残し | `~/.cache/af-codex-drift-*` ×8・`af-probe-*` | 約 0.85G（7 月作成。`drift_test.go` は `t.Cleanup` で消すので、残るのは強制終了されたときだけ） |
| 持ち主不明の作業物 | HOME 直下の非ドット項目 | **193 個**（`probe-*`・`review-9xx`・`muse-probe`・`af-ec2b`・`sb-bundle.js` 等、179 個が 9 月作成）。合計は 2G 程度 |

容量を食っているのはキャッシュで、散らかりの原因は作業物という分担になっている。

## 当座の対処（実施済み）

他セッションのビルドが走っていないことを `ps` で確かめてから
`go clean -cache`・`npm cache clean --force`・`uv cache prune` とテスト残骸の削除を実行した。
**使用率は 84%（空き 75G）から 67%（空き 150G）へ下がった**。HOME 直下の 193 個は、必要なものかどうかを
エージェントが判断できないので手を付けていない。

## 原因

作業物については、ポリシー（`workspace/workspace-notes.md`）に「使い捨てのファイルをどこに置くか」が書かれていなかった。
`/tmp` は全セッションで共有され、再起動で消える（memory: tmp-file-collision）。
そのためエージェントは `~` の直下に逃げ、あとから誰にも持ち主が分からなくなる。

## ポリシー追記（この PR）

- `workspace-notes.md` の「What survives」に「使い捨ては `~/.af-work/<session>/`。`~` と `~/.cache` の直下に置かない。
  終わったら消す」を 1 項目足した。
- `notes/environment.md` の Disk 節に、作り方と、キャッシュを空ける 3 コマンド（他セッションのビルド中は実行しない）を足した。
- **`<session>` の出どころ**: `$AF_SESSION_NAME` はターミナル（CLI）起動の tmux 環境にしか入らない
  （`session_tmux.go:42`）。Managed では空なので、作業コピーのディレクトリ名で代える。
  代わりに使う名前がないと全員が `~/.af-work/` 直下に置くことになり、散らかる場所が 1 段下がるだけになる。

## 製品側の案（未着手）

1. **セッション作業ディレクトリを Agent が用意する。** ターミナル起動で `~/.af-work/<slug>` を作り、
   その場所を環境変数（例: `AF_WORK_DIR`）で渡す。セッション削除（ADR 0101）のときに一緒に消す。
   ごみ箱には入れない。定義からして使い捨てだからである。
   - 未決: Managed は kind ごとの共有デーモンなので、セッション単位の環境変数を渡せない
     （`codex/driver.go:88`）。作業コピー名で鍵にした場合は、作業コピーの削除に合わせて消すことになるが、
     作業コピー名とセッションのスラグは一致しないことがある（例: 作業コピー `wip-sedfu6c` とセッション `sml4fdo`）。
   - `TMPDIR` をそこへ向ける案は採らない。CLI 自身の一時ファイルまで巻き込み、影響範囲が読めないからである。
2. **キャッシュの上限を Agent が見る。** 1 日に 1 回 `go-build` と `_cacache` の量を測り、
   しきい値（例: ディスクの 15%）を超えたら掃除する。条件は、同じコンテナ内に `go build`/`go test`/`npm ci` の
   プロセスがないことである。Go のキャッシュも npm のキャッシュも年齢で選んで消す手段がなく、全消しになる。
   そのため、掃除した直後の 1 回のビルドが遅くなることを受け入れる設計になる。
3. **Console の設定 > 環境に「キャッシュだけ掃除」を置く。** 内訳（キャッシュ別の量と HOME 直下の作業物の数）を見せる。
   今ある admin の「clean home」（`runtime_docker.go:557`）は `homeKeep` 以外をすべて消すので、
   日常の掃除には重すぎる。案 3 はその隙間を埋める。

## 未決
