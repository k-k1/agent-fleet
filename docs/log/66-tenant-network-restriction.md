# 66. テナント管理者が自分のテナントの「接続元ネットワーク」を絞れるようにする

## 66.1 問題

今ある接続元の制限は `00-network.yaml` の **`AlbIngressCidr`（既定 `0.0.0.0/0`）だけ**である。

- **デプロイ全体に効く。** テナント A だけ絞る、はできない。
- **CloudFormation の再適用が要る。** テナント管理者は AWS を触れない（触らせない）。
- **AWS 限定。** docker / native のデプロイには存在しない。

「テナント管理者が Console から自分のテナントの接続元 IP を絞れる」方が手軽ではないか——
が本書の問いである。**結論は採用**。ただし**何ではないか**を先に固定しないと、
名前だけ立派で守っていないものになる。

## 66.2 層の住み分け（先に）

3 つは**代替ではなく直列**である。どれか 1 つで足りる、という話ではない。

| 層 | どこで止まるか | 誰が設定するか | 粒度 | 何を守れないか |
|---|---|---|---|---|
| `AlbIngressCidr`（SG） | **ALB に届く前** | 運用者（CFN 再適用） | デプロイ全体 | テナント毎に変えられない |
| WAF（レート制限・IP 評価） | ALB の手前 | 運用者（CFN パラメータ） | デプロイ全体 | 同上。既定オフ（[64](64-ec2-persistent-workspace.md) §64.25 の議論） |
| **本書（テナント接続元制限）** | **CP の中・認証の後** | **テナント管理者（Console）** | **テナント単位** | **CP に届くこと自体は止められない** |

⚠️ **本書はネットワーク防御ではない。** 要求は ALB を通り、CP に届き、TLS が解け、
HTTP として解釈され、**セッション cookie が検証されたあとで**初めて拒否される。したがって:

- 認証前の脆弱性・DoS・帯域・探索の削減には**一切効かない**。それは上 2 層の仕事である。
- 効くのは「**資格情報を持っている人が、許されていない場所からデータに触る**」だけ。
  ——ただしそれは、実際に事故として起きるものの大半でもある（端末の持ち出し、
  委託先からの接続、退職者の私物端末）。
- **私有デプロイで一番安くて強いのは今も `AlbIngressCidr`** である。本書はそれを置き換えない。
  Console の文言でもそう言う。

## 66.3 本丸——送信元 IP をどう同定するか

CP は現在 **`r.RemoteAddr` を一度も読んでいない**（grep で確認）。つまり同定の仕組みは
まだ 1 行も無い。ALB の後ろでは `RemoteAddr` は ALB になり、実クライアントは
`X-Forwarded-For`（XFF）にいる。そして **XFF は偽装できる**。

### 66.3.1 右から数える（左から読んではいけない）

各プロキシは「自分が受け取った相手の IP」を XFF に**追記**する。client → P2 → P1 → CP なら:

```
P2 が追記 → "client"
P1 が追記 → "client, P2"
CP から見て RemoteAddr = P1
```

信頼できるのは**右端から数えた分だけ**である。CP の手前に信頼するプロキシが N 台なら、
**クライアント = `XFF[len-N]`**。ALB 1 台なら **右端**が実クライアントになる。

利用者が `X-Forwarded-For: 1.2.3.4` を勝手に付けても、ALB はその**右に**本物を足すので、
右から数える限り影響しない。**左端を読む実装だけが偽装可能**である——それが唯一の間違え方で、
世に出回っている「XFF の先頭を取る」コードがまさにそれ。

### 66.3.2 何台を信頼するかは、製品ではなくデプロイが知っている

`AF_TRUSTED_PROXY_HOPS`（既定 `0`）を足す。

- `0` = プロキシ無し。**`RemoteAddr` が本物**で、XFF は読まない（docker / native の素の形）。
- `1` = ALB だけ（`30-ingress.yaml` が CP のタスク環境に渡す）。compose + Caddy も 1。
- `N` = CDN + ALB のように増えたとき。

⚠️ **既定 0 のまま ALB の後ろで動かすと、全員の IP が ALB の私有アドレスに見える。**
これは「効かない」より悪い——**テナント管理者が `10.20.10.5/32` を許可して
「絞れた」と思う**状態になりうる。そこで**保存時に検出して拒否する**（§66.5.2）。

CP は起動バナーに `trusted-proxy-hops=N` を出す。運用者が「どちらのつもりか」を
1 行で読めるようにするため。

## 66.4 効く範囲——ログイン前には効かない（そして、それでよい）

`authGate` の外は `routes.go` の除外レジストリで宣言されている:
`/healthz`・`/login`・`/login/*`・`/oauth2/*`・`/brand/*`・`/internal/*`・`/mcp`・`/git/*`。

**ログイン画面と OAuth の往復は、テナントが決まる前**である（誰なのかが分かるのは
callback の後で、どのテナントを使うかは `X-AF-Tenant` を見る `selectMembership` の後）。
したがって IP でテナントを判定できる最初の地点は**認証の後**にしか無い。

これを「意味が無い」と読むかどうか:

- **意味はある。** 守るべきものは**データ**であり、データに触る経路（Console の API・
  ターミナル・プレビュー・ファイル・履歴）は全部テナントを解決してから通る。
  許されない場所からは**サインインはできるが何も見えない**、が成立する。
- **意味の無いことは正直に書く。** 「ログイン画面が見える」「サインインは通る」ことは
  隠さない。隠すと、後で誰かが「IP 制限したのにログインできた＝壊れている」と読む。

### 66.4.1 ⚠️ `/mcp` と `/git/*` は**対象にしない**（危うく間違えるところだった）

この 2 つは authGate の外だがテナントを解決する（PAT → `resolveByMembership`）。
「じゃあそこにも入れよう」は**誤り**である——**この経路の送信元は本人の Workspace コンテナ**
であり、人がどこにいるかを一切表さない。`AF_MCP_TOKEN` は起動時にコンテナへ注入され、
git も `git clone http://<cp>/git/...` をコンテナの中から叩く。オフィスの CIDR を許可した
テナントは、**自分のワークスペースの中からの MCP と git を全部塞ぐ**。

したがって除外し、**なぜ除外なのかを実装のコメントと本書に残す**。この経路を止めたい人の
道具は既にある——メンバーシップの無効化（PAT はそれで失効する）。

## 66.5 締め出し事故

テナント管理者が自分の CIDR を間違えると、**自テナントごと入れなくなる**。しかも
気づくのは保存した直後で、直す画面にはもう入れない。逃げ道を 3 つ用意する。

### 66.5.1 super_admin は対象外

運用者はいつでも解除できる。これが最終手段である（`ident.Role == "super_admin"` で素通し）。

### 66.5.2 保存時に「今のあなた」を必ず通す

空でないリストを保存するとき、**編集者自身の現在 IP が含まれていなければ 400 で拒否**する。
メッセージには**CP から見えている IP をそのまま出す**（`203.0.113.9 はこの一覧に含まれません`）。

そして §66.3.2 の誤設定も同じ入口で捕まえる:

- `hops == 0` なのに要求に XFF が付いている → **`proxy_not_configured`**。
  「CP の手前にプロキシがいるのに `AF_TRUSTED_PROXY_HOPS` が設定されていません。
  運用者に連絡してください」。**この状態では一切保存させない。**
- XFF が短すぎて `XFF[len-N]` が取れない → **`client_ip_unknown`**。同じく保存させない。

⚠️ **画面に「あなたの現在 IP」を出すだけでは足りない**。出すと、誤設定時に見えている
`10.20.10.5` を「これが私の IP か」と思って**そのまま登録**できてしまう。
だから**表示ではなく拒否**にする。

### 66.5.3 既定オフの機能は作らない

`AF_TENANT_IP_RULES=on/off` のような運用者スイッチは**足さない**。
[ADR 0044 決定 3 が一度も発火していなかった](../decisions/0044-workspace-sizing.ja.md)（既定オフで
出した機能は存在しないのと同じ）を繰り返さないため。**「オフ」はリストが空であること**——
それ以外の消し方を用意しない。

## 66.6 仕様（採る形）

1. **保存先は `tenant.allowed_cidrs`（CSV・1 列）**。`tenant.allowed_providers` と同じ行で、
   **同じ 30 秒キャッシュ（`tenantLoginCache`）から読む**。要求毎に DB を叩かない。
   `tenantLimits`（JSON・super_admin 編集）ではなく**こちら**にするのは、
   (a) 要求毎に読む場所には既にキャッシュがある、(b) これは**テナント管理者が持つもの**で、
   super_admin 専用の上限とは持ち主が違うから。
2. **編集は `PUT /api/admin/tenants/{slug}/network`（`tenantAdminFor`）**。
   `setTenantLogin`（super_admin 専用）には**足さない**——あちらの 3 項目はテナントの外へ
   届く（ADR 0043 決定 24/25）。接続元制限は**このテナントの中で閉じる**ので、
   同じ線引きに従うとテナント管理者のものになる。
3. **判定は `checkTenantProvider` の隣**（`resolveFull` / `resolveMembership`）。
   1 つの関数 `checkTenantIP(ctx, mv)` を両方から呼ぶ。
   403 `ip_not_allowed`。**`resolveByMembership`（PAT）には入れない**（§66.4.1）。
4. **同定は `clientIPFrom(ctx)`**。最外周のミドルウェア（`logRequests` の隣）が 1 回だけ
   計算して context に入れる。ヘッダは**そこでしか読まない**——`authGate` が識別ヘッダを
   `r.Header.Del` してから自分のものを入れているのと同じ理由で、下流に生の XFF を
   信用させない。
5. **表記**は `192.0.2.0/24`（prefix）と `192.0.2.7`（単独 IP = `/32`・`/128`）の両方を受ける。
   IPv4 / IPv6 の両方。保存前に `netip` で正規化する（`192.0.2.7/24` のような
   「ホスト部が残った prefix」は**そのまま通さず** `192.0.2.0/24` に丸めて保存し、
   丸めたことを応答に出す——黙って意味を変えない）。
6. **監査に残すのは「規則を変えたこと」だけ**（`tenant.network_rules`）。
   ⚠️ **拒否そのものは記録しない。** 弾かれたクライアントは普通ポーリングを続けるので、
   1 拒否 1 行にすると監査台帳が 1 つの端末で埋まる。⚠️ **全要求のアクセスログに
   送信元 IP を出す変更もしない**——個人データの扱いが変わる。必要になったら
   保存期間と併せて別途決める。

## 66.7 実装した形（2026-08-17）

- `control-plane/clientip.go` —— `AF_TRUSTED_PROXY_HOPS`／`XFF[len-N]`／CIDR の正規化と照合。
  ヘッダを読むのは最外周ミドルウェア 1 箇所だけ（`main.go` の `withClientIP`）。
  起動バナーに `edge: trusted-proxy-hops=N (...)` を出す。
- `tenant.allowed_cidrs`（`migrations/0045` ＋ `migrations-pg/0028`）と、既存の
  `tenantLoginCache` 経由の読み出し（`networkAllowed`）。
- `resolver.go` の `checkTenantIP` を `resolveFull` / `resolveMembership` から呼ぶ。
  **`resolveByMembership`（PAT）には入れない**（§66.4.1）。回帰テストで固定した。
- `GET/PUT /api/admin/tenants/{slug}/network`（`tenantAdminFor`）。
  GET は `your_ip` / `proxy_hops` / `editable` / `reason` も返す。
- Console: テナント設定の「接続元の制限」。`editable=false` のときは入力も保存も出さず、
  理由（`AF_TRUSTED_PROXY_HOPS` 未設定）を警告色で書く。
  ⚠️ **入口を 1 つにして失敗した（実デプロイで即発覚）。** テナント設定モーダルの入口は
  アカウントメニューにあり、**`tenant_admin` の在籍だけ**で出る。したがって在籍の無い
  super_admin からは**面ごと一生見えない**——「設定にも管理にも無い」になった。
  ログイン規則とサインイン方法は最初から**管理モーダルのテナント詳細にも**置いてあり、
  接続元の制限だけ片方だったのが誤り。両方に置いた（権限はサーバが持つので、
  画面側に出し分けは足さない）。**新しい面を足すときは「入口が何で決まるか」まで見る。**
  さらに**入口そのものも直した**: テナント設定の入口を **super_admin にも出す**。
  サーバは前から super_admin をどのテナントの管理者としても通す（`tenantAdminFor`）ので、
  隠していたのは表示だけであり、その表示が「デプロイ管理者は管理モーダルから入る」という
  **暗黙のルールを人に要求していた**。あわせて、super_admin がこのモーダルから入ったときの
  ログイン規則は読み取り専用にしない——「変更できるのはデプロイ管理者だけです」と
  書かれた画面を当のデプロイ管理者が眺めることになるため。
- `30-ingress.yaml` の CP タスクに `AF_TRUSTED_PROXY_HOPS=1`、
  `deploy/compose/.env.example` に Caddy 構成での 1 を案内。

## 66.8 実機で確かめること

**入れたところまで（2026-08-17・開発配備）**: `30-ingress` の CP タスクに
`AF_TRUSTED_PROXY_HOPS=1` が入り、起動ログに
`edge: trusted-proxy-hops=1 (client IP = X-Forwarded-For counted from the right)` が出た。
`GET/PUT /api/admin/tenants/{slug}/network` は 404 ではなく **401**（ルートは生きている）。

⚠️ **肝心の 1 行はまだ見ていない。** 「CP が実際にどのアドレスを見ているか」は
`your_ip` を返す画面にしか出ず、**その画面はログインの先**にある（Google は headless を
弾く）。CP の設計としてアクセスログに送信元 IP を出さないと決めた（§66.6-6）ので、
ログから読む逃げ道も**意図的に無い**。人がブラウザで開いて確かめる。

- ALB の後ろで `AF_TRUSTED_PROXY_HOPS=1` にしたとき、CP が**自宅回線のグローバル IP**を
  見ていること（`10.20.x.x` ではないこと）。**これが全ての前提**で、机上では確かめられない。
- 偽の `X-Forwarded-For` を付けた要求で判定が変わらないこと。
- 許可外の IP から: ログイン画面は出る／サインインは通る／Console の API が 403 になる。
- 誤設定の検出: `AF_TRUSTED_PROXY_HOPS` を外した状態で保存を試み、`proxy_not_configured`
  で拒否されること。

## 66.9 検討して採らなかったもの

- **ログイン画面自体を IP で絞る。** テナントが決まる前なので、絞れるのは `/login/<slug>` の
  slug からだけ。**slug の存在を漏らす**（`handleLogin` が未知 slug で 404 を返さないのは
  そのため）し、汎用 `/login` から入られると意味が無い。
- **メンバー単位の IP 制限。** 粒度は魅力的だが、運用が破綻する（人は移動する）。
  テナント単位で足りる。
- **`AlbIngressCidr` をテナント管理者に開放する。** SG の書き換えを製品から行うことになり、
  デプロイ全体の入口を 1 テナントの管理者が操作できてしまう。層を跨いだ権限であり不可。
- **全要求のアクセスログに送信元 IP を出す。** 探索の追跡には有効だが、本件の目的ではない。
  必要になったら別途、保存期間と併せて決める。
