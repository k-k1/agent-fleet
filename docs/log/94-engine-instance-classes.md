## 94.1 何を測りに行ったか

P0（実装・単体テスト・描画確認）は前日に終わっていて、**単体テストでは絶対に分からない
ことだけ**が残っていた。ADR の「P1 の実験計画」が挙げた 9 項目である。梯子は image 役に
3 段を宣言した（llm 役は空のまま＝決定 3 の対照）:

```
l4|L4 24GB (g6.xlarge)|8000|g6.xlarge|4-8|15000-65536|1.26
l40s|L40S 48GB (g6e.xlarge)|44000|g6e.xlarge|4-8|30000-65536
l40s2x|L40S 48GB 8vCPU (g6e.2xlarge)|44000|g6e.2xlarge|8|30000-65536
```

1 段目は**この配備の CFN パラメータをそのまま書き写した**（`ImageAcceleratorMemMinMiB=8000`・
`g6.xlarge` 単独）。「既定に戻す」で実験前と 1 バイトも違わない状態に戻せるようにするためで、
実際そうなった。3 段目はクォータ 8 を超えさせるためだけの段である（陽性対照用）。

事前確認で 2 つ分かった。**`g6e.xlarge` も `g6e.2xlarge` も ap-northeast-1a / 1c にある**
（代替の `g5.xlarge` は要らなかった）。そして **ADR が書いていたクォータコード `L-DB2E81BB`
は誤り**で、それは Spot 用（値 0）。On-Demand の G/VT は **`L-DB2E81BA`＝8** だった。

## 94.2 事故: 同じ配備を 2 つのセッションが同時に deploy した

**最初にやったのは計測ではなく、他人の配備を壊すことだった。**

`dev-deploy.sh` を走らせた時刻に、別セッション（ADR 0072 P2・ComfyUI）が**同じ af-sandbox へ
develop を deploy している最中**だった。私のブランチは develop より 26 コミット古く、
その古いテンプレートで 60-engines を上書きしたため、相手が 20:46 に入れた
`ImageEngine`（ComfyUI）が 20:51 に消えた。`ImageTag` も一時的に私の像へ動いた。

**気づいた理由は偶然である。** 両方が `| tee /tmp/dev-deploy.log` と書いていたので、
同じファイルに 2 つの実行が混ざり、「私の実行のはずのログに、私が指定していないタグが
出てくる」という形で見えた。混ざっていなければ、CFN の履歴を見るまで分からなかった。

対応と結果:

- 自分の deploy を止め（`kill` は自分が起こした PID だけ）、相手へ**何を壊したか・どう直すか**を
  そのまま送った。相手は「P1 を先にどうぞ、二重に直さない、それまで deploy を止める」と返答。
- `origin/develop` を取り込み、**ComfyUI と GPU クラスの両方が入った像**を 1 回 deploy して
  戻した。60-engines.yaml の衝突 14 か所は、**双方が 51,200 バイトの壁のために散文を削った
  結果**で、develop 側を採って ADR 0074 の意味のある差分 4 か所だけを載せ直した。

⚠️ **教訓 3 つ。**

1. **共有の開発配備に deploy する前に、他のセッションが同じことをしていないか確かめる。**
   `pgrep -af dev-deploy.sh` で 30 秒で分かる。
2. **`/tmp` の固定パスをログに使わない。** 混ざる（今回は助かったが、逆に読み違えもした）。
   ついでに **`/tmp` は掃除される**——実験の途中でスナップショット一式が消えた。以後
   `~/.cache/` に置いた。
3. **worktree のブランチが古いまま配備に触らない。** ADR 0074 の実装だけを載せたつもりが、
   develop の 26 コミットぶんを巻き戻していた。

## 94.4 実機だけが教えてくれたバグ 2 件

**どちらも P0 の単体テストは全部緑のままだった。** これが P1 の存在理由である。

### 1. `DescribeCapacityProviders` に cluster と名前を両方渡していた

段を選んだ瞬間、必ずこれが出た:

```
InvalidParameterException: Cannot specify both capacity providers and cluster in the
same request. Provide either capacity provider names or cluster, but not both.
```

**API リファレンスにも SDK の doc コメントにも書かれていない。** SDK は `Cluster` を
「指定するとそのクラスタの provider だけが返る」としか説明しない。単体テストが通っていたのは
**fake が何でも受け取っていたから**で、これは書き手の落ち度というより**テストダブルの
既定の甘さ**である。

直し方は 2 段構え:

- 名前だけで引き、**cluster は答えの側で検査する**（`cur.Cluster` が別のクラスタなら書かない。
  update は subnets と security group ごと再宣言するので、宛先違いは読み取り専用の事故では
  済まない）。ARN でも名前でも同じと見なす。
- **fake を実 API と同じだけ厳しくした。** 両方渡したら `InvalidParameterException` を返す。
  これで**既存のテスト全部が番人**になる。陽性対照つき——`Cluster` を戻すと 2 件が実際に落ちる。

### 2. `ecs:PutClusterCapacityProviders` が要る

describe を直したら、今度は書き込みで落ちた:

```
AccessDeniedException: User: .../af-af-ecs-platform-cp-task/... is not authorized to perform:
ecs:PutClusterCapacityProviders on resource: .../cluster/af-af-ecs-platform
```

**ECS は MI の provider に対する `UpdateCapacityProvider` を、クラスタ側の
`PutClusterCapacityProviders` としても認可する。** CP はその API を一度も呼んでいないので、
**コードを grep しても権限表を読んでも出てこない**。ADR 0074 決定 9 の「2 動作＋PassRole で
足りる」は誤りだった。

⚠️ **これは決定 9 の見出し（「2 つの capacity provider に限定する」）を部分的に裏切る。**
他の 3 つが provider スコープなのに、この 1 つは**クラスタスコープ**で、同じ動作で
クラスタの provider 関連付け一覧ごと差し替えられる。60-engines が元々その一覧を所有して
いることが、許容する唯一の根拠である。**限定できないなら書かない**という道は無かった——
書かなければ機能そのものが動かない。

⚠️ 直したあと **CP の再作成は不要だった**。変えたのはタスクロールのポリシーで、CP は
ロールを引き受けているだけなので、次の API 呼び出しから効く。

## 94.5 ADR の予想が外れていた点 2 件

### 1. 門を迂回すると、まず起きるのはクォータ超過ではなく「古いカードへの再着地」

実験計画は「待たずに起こせば `VcpuLimitExceeded` が出る」と書いていた。**出なかった。**

退場を待たずに `update-service --desired-count 1` を叩いたら、タスクは**居残っている
前の段の箱にそのまま置かれ**、64 秒で `steady state` になった。理屈は単純で、
**provider の要求は「何を買うか」の条件であって「どこに置くか」の条件ではない**。空いている
箱が居るあいだ、ECS はそもそも 2 台目を買おうとしない。

**エラーはどこにも出ない。** サービスイベントも CP のログも無言で、パネルは「稼働中」と言う。
つまり**決定 4 が防いでいる一番手前の失敗は、静かな再着地**である——段を上げたつもりの
管理者が、古いカードの上で走り続ける。今回は両方 L40S だったので実害は無かったが、
24GB → 48GB の切替でこれが起きれば、次に大きいモデルを載せた時点で CUDA が落ちる。

門そのものは正しく効いていた:

```
09:09:18  engine image: holding the start back (class_swap_wait after admin_on)
09:09:24  engine image: holding the start back (class_swap_wait after admin_on)
```

陽性対照は取り直した。**古い箱でタスクが走っている状態で 2 台目を要求する**と、期待どおり:

```
VcpuLimitExceeded: You have requested more vCPU capacity than your current vCPU limit of 8
allows for the instance bucket that the specified instance type belongs to.
```

### 2. 「箱が消えるまで待つ」は必要条件だが十分条件ではない

4 vCPU の箱が ECS から消えた直後に 8 vCPU の段を買おうとしたら、**5 分以上
`VcpuLimitExceeded` が続いた**:

| 時刻 | 出来事 |
|---|---|
| 09:19:43 | 古い箱が ECS から消える（＝CP の門が解ける） |
| 09:19:50 / 09:20:30 / 09:21:11 | `VcpuLimitExceeded` ×3 |
| 09:26:12 | ようやく `g6e.2xlarge` が登録される（+389 秒） |
| 09:28:00 | `listening`（起動決定から 497 秒） |

**EC2 のクォータ解放は ECS の登録解除より遅い。** CP が見られる唯一の手がかり
（container instance が居るか）は、EC2 の会計とは別物である。ECS が再試行するので壊れは
しないが、**段を上げる起動は「退場 150 秒＋クォータ待ち最大 6 分＋コールドスタート」**で
見積もる必要があり、`StartDeadlineSec`（既定 900 秒）はその合計を超えていなければならない
（実測 497 秒）。4→4 の入れ替えでは起きない。

## 94.6 数字（未解決 3 の材料）

Pricing API（東京・Linux・共有テナンシー・オンデマンド、2026-09-10）:

| 型 | $/h | メモリ | VRAM（公称） |
|---|---|---|---|
| `g6.xlarge` | 1.1672 | 16 GiB | 24 GB |
| `g5.xlarge` | 1.4590 | 16 GiB | 24 GB |
| `g6e.xlarge` | 2.6990 | 32 GiB | 48 GB |
| `g6e.2xlarge` | 3.2517 | 64 GiB | 48 GB |

🔴 **梯子に書くべきなのはこの数字ではない。** ADR 0071 が実測した g6.xlarge の **$1.26** は
list price より **8% 高い**。差は ECS Managed Instances の管理料（EC2 の料金に上乗せ）と
整合する。**list price をそのまま書くと、パネルが請求より安く見える。** 1 点から係数は
作れないので、**「実測があるものは実測、無いものは書かない」**（`usdPerHour` は任意）を勧める。

VRAM は `ggml_cuda_init` の報告で **L40S = 45,457 MiB**。梯子の 44,000 は「公称より下」の
作法どおりで妥当だった。

**決定 6 の下限の精度**（juggernaut-xl-v9・fp16・SDXL 系）:

| 出所 | 値 |
|---|---|
| 宣言された下限（ファイルの bytes から） | 6,776 MiB |
| 実際の重み（`total params memory size`） | 6,624 MiB |
| auto-fit の計算用予備（DiT 2,048 + Conditioner 2,048 + VAE 1,024） | 5,120 MiB |
| 実使用 | 約 11.7 GiB |

**下限は重みとしては 2% の精度、実使用の 58%。** 「下限としか言わない」という決定 6 は
正しかった。予備は解像度とバッチに依存するはずなので、1 点から係数は作らない。

## 94.7 費用

**合計 $4.6**（見積り $3〜5 の上限寄り）。

| 型 | 稼働 | 費用 |
|---|---|---|
| `g6e.xlarge` | 07:49:16 → 09:19:43（90.5 分） | $4.07 |
| `g6e.2xlarge` | 09:26:12 → 09:36:25（10.2 分） | $0.55 |

⚠️ **計測そのものは 13 分で、残りの 77 分は箱が遊んでいた時間である。** 人にボタンを
押してもらう構成（管理 API は super_admin のブラウザセッションでしか叩けない）だったため、
チェックポイントの待ちがそのまま GPU の課金になった。**次に同じことをするなら、
先に段の切替を全部済ませてから 1 回だけ起こす**か、押す人が待機している時間帯に寄せる。

後片付けは Console のトグル（`mode=off`）→「既定に戻す」→ **箱が消えるまで見届ける**
（149 秒）。provider は実験前と 1 バイトも違わない状態に戻った。⚠️ `mode=on` のエンジンは
AWS 資格情報では止められない（`desired-count 0` は 30 秒で取り消される）。

## 94.8 直していない、分かっていること

- **適用に失敗した段は、同じ段を選び直しても再試行できない。** `putClass` は設定を保存して
  から ECS に適用するので、失敗しても選択は保存済みになり、Console は「変化なし」と見て
  要求を送らない（アクセスログに `PUT …/class` が 1 本も来ない）。回復するには別の段へ
  移してから戻す。順序自体は意図どおり（適用できなかったことを画面で言うため）なので、
  直すなら **Console 側に再試行の口**を足すことになる。
- **`fipsEnabled` はこの配備が一度も設定していないので、直接は測れていない。** 兄弟の欄
  （`capacityOptionType`）が保持されたことからの推定である。FIPS を使う配備で段を切り替える
  前に、ここだけもう一度確かめること。
- **llm 役は 1 度も起こしていない。** コールドスタートが 3 倍（527〜586 秒）で、同じことを
  3 倍の時間と費用で測ることになるため、実験計画のとおり image 役だけで行った。llm 役の
  梯子は空のままで、決定 3 の対照として使った。
