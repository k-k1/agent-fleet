# 99. プランを別セッションにレビューさせる — 起動導線（P1）

> 状態: **P1 実装**（2026-09-19）。プラン承認待ちのカードに「別セッションでレビュー」を置き、
> 利用者がエージェント／モデルを選んでレビューセッションを起こせるようにした。戻りは **peer 通信**。
> 価値があるのは機能そのものより、**設計を 3 回ひっくり返した測定**（§99.2）である。
> 関連: [30-session-report.md](30-session-report.md) §プラン承認 /
> [58-cross-session-messaging.md](58-cross-session-messaging.md)（peer 封筒）/
> [75-idle-stop-and-pending-interactions.md](75-idle-stop-and-pending-interactions.md)（carried）

## 99.1 要求

利用者の言葉で 5 段:

1. 立案セッションの提案パネルでボタンを押す
2. エージェント／モデルを選んでレビューセッションを起動
3. レビューセッションがプランファイルをレビューし、結果を立案セッションに通知して自動停止
4. 立案セッションが指摘を検証し、プランファイルを更新
5. 立案セッションが再提示

## 99.2 測って 3 回ひっくり返った

**① 「Console 側でレビューの完了を待てばよい」→ 不可。** 数分〜十数分かかるので、タブを閉じる・
別セッションに切り替える・スマホがスリープするのどれでも落ちる。同型の失敗は
`useStartWork.ts` の初回プロンプト配送で既に一度直している（ミラーがマウントされている間しか
動かなかった）。ポップアウト窓と本体タブの 2 箇所で走れば子が 2 本立つ、も同じ穴。

**② 「常駐ジョブで回収して `/plan-respond` に載せる」→ 過剰だった。** 戻りを **peer 通信**に
すると、要るのは「却下を先にやる」ことだけになる。保留中のセッションは自由文を 409
`plan_pending` で弾く（モーダルが文字を食い、末尾の Enter が**承認**になる事故の対策）ので、
プランを保留したまま横から指摘を入れる経路は原理的に無い。却下してしまえば親は plan モードの
idle で、peer は普通に届く。**利用者が最初に言った順（却下 → 起動 → 返信）が正しかった。**

**③ 「プランファイルのパスは記録されていない」→ 版による。** 手元の `plans/*.md` 7 本を転写
317 本に突き合わせると 5 本は `tool_input` としてどこにも現れず、CLI が内部で書いていると
読んだ。これは**古い 5 本（08-22〜09-08）だけ**の話で、9-13 以降の 3 本はすべて
`Write` の tool_use を持つ——**今の claude はプランファイルをモデル自身の Write で書く**
（この機能の計画ファイル自体がその証拠になった）。`PreToolUse(Write|Edit|MultiEdit|NotebookEdit|Bash)`
＝`permtool` は全 claude セッションに既に入っていて権限モードに関係なく焼かれるので、
`tool_input.file_path` が `plans/` 配下を指したときに記録するだけでパスが手に入る。

mtime で当てにいく案は採らない（`plans/` はコンテナ共通なので、2 セッションが同時にプランを
出した瞬間に**別セッションのプランをレビューする**）。本文をプロンプトに埋める案も採らない
（実測 12〜36 KB、TUI 起動の初回プロンプトは打鍵で配送される）。

**レビュアーが自分で取りに行くこともできない**: `get_session_output` は「自分が起こした子」限定で、
peer から読む口は意図的に置かれていない（`mcp_stdio.go`）。プランは渡すしかない。

## 99.3 実装

- **記録**: `status.WritePlanFile` / `ReadPlanFile`（`plan-file/<sid>.txt`）。`permtool` 分岐で
  `planFileOf()` が `plans/*.md` と認めたときだけ書く。保留の解決では消さない——改訂は同じパスに
  書き直されるので、記録は 1 セッション 1 本で多周回に耐える。消えるのは `status.Remove` のとき。
- **読み**: `GET /sessions/{name}/plan-file` → `{path, source}`。記録があり実在すれば
  `source:"claude"`、無ければ保留中の本文をスナップショットに書いて `source:"snapshot"`。
  `source` を応答に載せているのは、**snapshot ばかり返り始めたら版が変わった合図**だから。
- **導線**: カードのボタン → パス取得 → 却下（既存の Escape 経路）→ `handoffLaunchTarget` で
  作業コピーを解決 → `useLaunchSeed.set(prompt, title)` → `useLaunchTarget.open(repo, "", true)`。
  引き継ぎ提案カードと同じ 2 行で、エージェント／モデル選択も初回プロンプト配送も既存のまま乗る。
  lineage 欄は入れない（あれは handoff **提案**のもので、StartHost が存在しない提案を badge しに行く）。
- **プロンプト**（`planReview.ts`）: パス・作業コピー・観点・判定と指摘の形式・
  「`send_to_peer_session` で親に返し `af_stop_after_turn` で畳む」。本文は入れない。
