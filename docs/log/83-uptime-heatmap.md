## 83.1 いま何が起きているか

占有についてこのシステムが持っている数字は、**1 日 1 つ**しか無い。

| 台帳 | 粒度 | 中身 |
|---|---|---|
| `usage_daily`（稼働時間） | 日 | membership × day の `running_secs` だけ |
| `cloud_cost_daily`（クラウド費用） | 日 | Cost Explorer の実費・約 24h 遅れ |
| `session`（CP のミラー） | 履歴なし | 一覧を叩いた時のスナップショット。`ReplaceSessions` が毎回全消しする |

だから「金曜だけ高い」までは分かるのに、**止め忘れなのか働いていたのかが分からない**。そして
セッションの本数は**どこにも時系列で記録されていない**（CP のミラーは現在値であって履歴ではない）。

管理者にできることは「強制停止」と「ディスク上限」だが、そのどちらを押すべきかの根拠が
1 日 1 つの数字からは出てこない。

## 83.2 決定：これは「稼働時間」の面であって「クラウド費用」の面ではない

最初の相談は「クラウド費用をヒートマップにできないか」だった。**できない。**

実費は Cost Explorer が**日単位でしか返さない**（時間別は有料オプトイン＋直近 14 日）。時間別の
金額を出すなら「秒 × 誰かが一度打ち込んだ単価」に戻るしかなく、それは ADR 0048 決定 2 が
明示的に否定した見積である（単価を更新しない限り静かに嘘をつき続ける）。

なので**マスが表すのは占有と本数だけ**で、色は値段を意味しない。置き場所も「稼働時間」に寄せた。
ヒートマップは請求書の 1 日を**説明する**のであって、値段を付けない。

代わりに、メンバー詳細では**クラウド費用のカードのすぐ下**に置いた。「この日だけ高い」の理由が
同じ画面で下に降りて読める——夜通しの帯なら止め忘れ、昼だけ濃いなら働いていた。金額の面に
時間別の色を塗るのではなく、**別のカードとして隣に置く**のがこの機能の形である。

## 83.3 P0：時バケットを刻む（先に入れる理由）

⚠️ **過去は取れない。** 新しい粒度の台帳は、入れた瞬間から先しか埋まらない。これは
[67-member-cloud-cost.md](67-member-cloud-cost.md) のコスト配分タグで踏んだのと同じ型
（「打った時ではなく有効化した時から時計が動く」）で、**実装が遅れた日数がそのまま永久に
取れない日数になる**。だから UI より先にサンプラを書いた。

`migrations/0053_usage_hourly.sql`（Postgres は `migrations-pg/0038`）:

```sql
CREATE TABLE usage_hourly (
  membership_id TEXT NOT NULL,   -- '' = サンプラのハートビート
  tenant_id     TEXT NOT NULL,
  hour          TEXT NOT NULL,   -- YYYY-MM-DDTHH (UTC)
  samples       INTEGER NOT NULL DEFAULT 0,
  running_secs  INTEGER NOT NULL DEFAULT 0,
  measured_secs INTEGER NOT NULL DEFAULT 0,
  session_secs  INTEGER NOT NULL DEFAULT 0,
  busy_secs     INTEGER NOT NULL DEFAULT 0,
  max_sessions  INTEGER NOT NULL DEFAULT 0,
  max_busy      INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (membership_id, hour)
);
```

### 83.3.1 ⚠️ マスは 3 値である（停止 / 稼働 / 未観測）

一番踏みやすい穴がこれ。「行が無い＝止まっていた」にすると、**CP が落ちていた日が
「誰も働かなかった日」として自信たっぷりに表示される**。

`membership_id=''` の行を**その時間のハートビート**にした（`cloud_cost_daily` の共有バケットと
同じ規約）。読み方は:

- ハートビートがあり、メンバーの行が無い → **観測できて、止まっていた**（灰色）
- ハートビートが無い → **観測していない**（空白）

停止中のワークスペースぶんの行を毎回書けば同じことはできるが、それは 5 分ごとに N 本の
書き込みになる。ハートビートなら 1 本で済む。

⚠️ **ハートビートはスイープが完走したときだけ打つ**。テナントの一覧に失敗した回でも打つと、
そのスイープが辿り着かなかったワークスペースに灰色が塗られる＝**失敗が作った自信のある答え**。

### 83.3.2 ⚠️ `measured_secs` — 同じ区別のもう一段下

ワークスペースが動いていても Agent に届かないことがある（起動途中・刺さっている）。そこで
「セッション 0 本」と記録すると、**忙しかった時間に冷たいマスが描かれる**。

セッションの計数は `measured_secs` の上でだけ積む。`running_secs > 0` かつ `measured_secs == 0`
は「稼働中・本数不明」として、0 本とは別の見た目（地模様）で描く。

### 83.3.3 「動いている」の定義は写さない

濃さの指標に「動いていた本数」を入れたが、述語は `session_activity.go` の `sessionActivity` を
**そのまま呼ぶ**。ここに `busyState(s.State) || s.BackgroundBusy` と書き写すと、状態が増えた日に
片方だけ古くなる（docs/log/75 が同じ事故を 2 回記録している）。

`keepAwake` のピンが machineBusy に入るのも意図どおり。**週末ずっと濃いまま残るピンこそ、
この画面が見せたい浪費**である。

### 83.3.4 相乗りする（常駐タイマーを増やさない）

`usageSampler.sample` は既に全テナントのワークスペースを列挙し、各ランタイムに状態を聞いて
いる。同じ walk をするタイマーをもう 1 本立てるのは、この host でメモリを使い切る典型
（docs/log/26）。セッション一覧の取得だけが増える分で、**1 回あたり 10 秒で打ち切る**
（共有クライアントの既定は 2 分で、それだと刺さった Agent が数台あるだけで自分の tick を
追い越す＝取り返しのつかない占有の取りこぼしになる）。

保持は 92 日。`usage_daily` の 24 倍の行数で、去年の春の何時に何をしていたかは誰も聞かない。

## 83.4 P1：API

| 経路 | 誰 |
|---|---|
| `GET /api/usage/me/hourly` | 本人（`withMembership`） |
| `GET /api/admin/usage/hourly?tenant=` | super_admin（全体）/ tenant_admin（自テナント） |
| `GET /api/admin/tenants/{slug}/members/{key}/usage-hourly` | メンバー詳細 |

応答は 3 つとも同じ形（クラウド費用が `/api/cost/me` と管理側で形を揃えたのと同じ理由——
形が 2 つあると、片方だけ直った日から静かに食い違う）。

⚠️ **合算を返さず、メンバー別の系列を返してクライアントで積む。** 合計とホバーの内訳が
同じデータから出るので、「合計と内訳が食い違う」が原理的に起きない。

⚠️ **メンバー 1 人を引くときはテナントで絞らない。** 所属は `tenantAdminFor` + `resolveMember`
が証明済みで、テナントでも絞ると破棄済みワークスペースぶんが落ちる（docs/log/67 §67.15 の
「自信たっぷりの $0.00」と同型）。テナント合算の方は絞ってよい——サンプラは書き込み時に
生きている `ws.TenantID` を焼くので、過去の行はテナントを持ったままである。

⚠️ **テナントで絞ってもハートビート行は返す**（`tenant_id` が空なので、素直に AND すると
消える）。消すと、テナント管理者のヒートマップが**全マス空白**になる。

## 83.5 P2：Console

3 面すべて `console/src/features/usage/UptimeHeatmap.tsx`（純関数は `uptime.ts`）:

- 本人の設定 → **稼働時間**タブ（使用量＝トークン / クラウド費用＝金額 / ここ＝占有）
- 管理モーダル → 稼働時間の合計の**下**に合算 1 枚（ホバーで寄与メンバー）
- メンバー詳細 → クラウド費用カードの**下**に本人 1 枚

### 83.5.1 ⚠️ タイムゾーン

サーバは UTC でしか刻まない。ずらすのは**描画側**で、UTC の時バケットを `Date` でローカルの
(日, 時) に落とす。ここでずらさないと、日本の利用者のヒートマップは 9 時間ずれて
**「毎晩深夜に働いている」**という表になる。

ローカルの端の列を埋めるには、要求する窓を**前後 1 日ぶん広げる**必要がある（+09:00 なら
UTC の 15:00 がローカルの翌日 0 時のマス）。+05:30 のような 30 分オフセットではマスが
時間境界をまたぐので、開始時刻の属する時間に丸め、その旨を画面に出す。

### 83.5.2 色（dataviz の検証器を通した）

**逐次（ordinal）ランプ**であって、カテゴリの `--viz-1..8` ではない。1 色 5 段、暖色。
検証器を `--ordinal` で明色（`--panel #f4f5f7`）と暗色（`#181818`）それぞれに通し、
単調な明度・隣接 ΔL ≥ 0.06・面に近い端の 2:1 コントラストを確認した:

```
node scripts/validate_palette.js "#ec9861,#d97030,#bb5518,#93400f,#682a08" --ordinal --mode light --surface "#f4f5f7"
node scripts/validate_palette.js "#f0b07c,#e08a4a,#c96827,#a44f1e,#7a3a18" --ordinal --mode dark  --surface "#181818"
```

⚠️ **1 段だけ手で直さない**——変えるならランプごと検証器に通す。

段は 5 つしか無いので、指標によって 0 の扱いを変える。本数の指標では「起きていたが 0 本」が
最下段（薄い暖色）で、**灰色（止まっていた）とは別物**。稼働率の指標では 0 のマスは描かれない
ので 5 段を全部使える。

色だけで意味を運ばないための逃げ道は 3 つ用意した: 凡例（常時）・ホバー / フォーカスの読み出し・
表ビュー。マスには `aria-label` で「9/1 10:00 停止」まで入る。

### 83.5.3 目視でしか出なかった 1 件

**列を `1fr` にすると 1 マスが 59×9px の「横棒」になり、ヒートマップではなく積み上げ棒に
見える。** DOM テストは全部緑だった（マスの数も class も正しい）。列に上限（22px）を置き、
行を 14px に固定し、左寄せにした。

日付ラベルの間引きの下限が 2 なのも列幅の問題であって本数の問題ではない。「08-19」は約 45px
あるのに列は 22px しかないので、3 日ぶんを選ぶと stride 1 になって隣とくっつく
（クラウド費用の棒グラフが「08-1708-18」になったのと同じ壊れ方）。
