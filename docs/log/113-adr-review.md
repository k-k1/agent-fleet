## 0. 総評と ADR の体裁

状態・関連・背景・決定・却下した案・影響・フェーズ・未解決の順序と 12 件の番号は日本語・英語で一致する
（ADR 0100 日本語:5-16,18,54,203,218,233,245／英語:5-18,20,59,228,246,264,276）。
0081 と 0094 は同じ主要節を持つ（0081:19,102,451,487,516,538／0094:29,63,438,458,499,607）。
0098 は「影響」が「未解決」より後にあるので、先例自体が厳密な順序規則ではない
（0098:487,506）。各決定はおおむね断定形で、提案段階の D 記号を残していない。
ただし「将来は roots に加える」は実装だけで成立するかのような未確定の約束である（🟡11）。

番号 0100 は妥当。`origin/develop` の ADR は 0098 までで、`temp/sidv2bw` と
`temp/sjys6nk` の HEAD はどちらも `docs(0099)` である（ADR 0100 日本語:8-9、
`git ls-tree origin/develop docs/decisions` と両ブランチの HEAD を照合）。
両方とも同じ番号なので将来の統合側では 0099 同士を調整する必要があるが、0100 の予約理由は成立する。

**日本語と英語の対応**: 決定 12 件、ツール表 4 行、書ける欄の表 1 行、未解決 4 件、
P0/P1/P2 の分配、3 枚・5 件・8 KB・1 KB・600 秒などの数値、記載された file:line は対応する。
決定の訳落ち・訳し過ぎは見つからなかった（日本語:80-201,233-253／英語:86-226,264-284）。
以下の事実誤りと設計の穴は両言語に共通し、修正時も対で直す。

## 1. 指摘（重大度順）

### 🔴1 空の下書きに部分更新できない

決定 3 は `set_image_draft` を「部分更新」「検証は投入と同じ `spec()`」とする（ADR:85）。
決定 2 の移行前を含め、空の下書きは実在する（ADR:77、`con/features/imagegen/draft.ts:80-102`）。
ところが `jobRequest.spec()` は `prompt` が空なら直ちに `bad_prompt` を返す
（`agent/internal/imagegen/jobs_http.go:103-106`）。「まず `op`、次に参照と prompt」のような
合法な部分更新は投入用検証をそのまま通すと失敗する。さらに `spec()` は `model`・`provider` の
実効値を確定する関数ではない（同:152-162）。**保存時は変更欄の型・錠・安全性を検証し、投入時に
完成した要求を別途検証する**と ADR に分けて書く必要がある。`null` で消した後の空 prompt も保存は許し、
投入を断るのが自然である。英訳:91。

### 🔴2 引数なし試走の「画面どおり」が保証されない

決定 3 は「いまペインに見えている下書きそのもの」で試走すると断定する（ADR:86,93-96）。
現行ペインは `providerId` の選択を ready な行へ解決し、その行の `model` を選んでから
`buildRequest` に渡す（`con/features/imagegen/ImagegenView.tsx:161-170,209-218`）。
`providerId` と `model` が空・古いとき、Agent 側の既定 provider と warm モデルの選択は
別の規則になる（`agent/internal/imagegen/jobs.go:854-884,896-920`）。特に複数 fleet 行で
モデル id が重複し得る（`con/features/imagegen/wire.ts:421-428`）。画面が選んだ行・モデル・
ファミリーの試走 steps を Agent が同じスナップショットで確定する規則が要る。
`needs_mask` が立つ inpaint はマスクが付くまで明示的に拒否する規則、冷えたモデルの待機・
MCP の 600 秒超過後もジョブと版をどう見せるかも同じ決定に必要
（ADR:107-111,249-250、`agent/internal/imagegen/comfy.go:1152-1157`）。英訳:92。

### 🔴3 `generate_image` を隠す配線と保証の範囲が決まっていない

既存の `generate_image` は設定が ON なら `--image-gen` でサーバに入り、
`mcpStdioToolList` が `mcpImageGenAdvertise()` を通して広告する
（`agent/ui_prefs.go:275-295`、`mcpx/mcp_stdio.go:92-98,166-170,397-414,1470-1474`）。
決定 3 の「スタジオなら広告しない」を実現するには、この経路で所有セッションの `Studio` を
判定して**既存ツールを除外**し、呼び出し時の広告照合も同じ集合にする必要がある
（ADR:89-97、`mcpx/mcp_stdio.go:2287-2295`）。影響・P0 にこの変更を明記する。
また ADR 0069 のとおり CLI 自身の画像ツールは af の広告集合の外にある
（`mcpx/mcp_stdio.go:1456-1465`）。「生成は人がボタンで」を全画像生成に対して構造的に保証する
とは言えない。保証対象を**スタジオのジョブキューへの N 枚投入**と明示するか、CLI 側も
制限する判断が必要。英訳:95-104。

### 🔴4 「版＝編集履歴の押した印」は追記 JSONL と食い違う

決定 9 では編集履歴は「下書きが変わるたび 1 件」で追記専用、版は「押した瞬間の写し」かつ
「編集履歴のうち押した印の付いた 1 件」（ADR:164-170）。下書きを編集せずに 2 回押すと
新しい編集行は無い。既存行へ印を付ければ追記専用に反し、同じ行で押下 2 回・別 seed・
別ジョブ ID を表せない。113 §3 D7 は `versions[]` を別に持ち、§5.1 は専用
`POST /versions` を置いていた（113:289-305,539）。**押下を独立した追記イベントにする**か、
版を編集履歴から分離する、と ADR で選ぶこと。試走の失敗・投入失敗で版を残すか、
`POST /versions` と `/jobs` の間の失敗をどう表すかも定義する。英訳:183-193。

### 🔴5 P0 の「履歴を残す」が完成画像には成り立たない

背景の要求には「結果を見ながら微調整し、履歴を残す」がある（ADR:20-23）。
P0 は編集履歴と版だけで、絵の `history.jsonl`・検索・「この設定に戻す」を P1 に置く
（ADR:169-173,235-241）。現行のジョブ一覧は完了 500 件までのメモリ上で再起動時に消える
（ADR:35-36、`agent/internal/imagegen/jobs.go:17-18,41-57`）。P0 の画像は版から辿れず、
元の絵を見て直す主な輪が再起動を跨げない。**絵と版の最小限の永続的な対応付けを P0 に入れる**か、
P0 では「履歴」は設定だけと明記して受け入れ条件を変える必要がある。比較 UI は P1 でよい。
英訳:188-193,266-272。

### 🔴6 `AF_SESSION_NAME` が届く kind でも worktree OFF は常に安全ではない

決定 8 は codex Managed 新規なら OFF 可とする（ADR:155-160）。しかし codex は
Agent のデーモンが差し替わった後に resume したスレッドへセッション名が届かず、
cwd 推測へ落ちる（`mcpx/mcp_stdio.go:3311-3340`、113-review §2 🔴3）。
同じリポジトリに別セッションがあれば、後の `get_image_studio`／`set_image_draft` の所有者を
確定できない。OFF 可否を **kind × 実行方式 × resume 状態**で扱うか、
名前を渡せない再開経路がある Managed kind の OFF を拒否する、と決める必要がある。
「未コミットの資料を見せたい」要求は worktree ON では満たされないことも起動 UI に明示する。
英訳:173-179。

### 🔴7 人格を初回指示に入れる契約が ADR から落ちている

決定 5 は「発言を受けたらまず `get_image_studio`」という人格に依存する
（ADR:114-118）。決定 8 は起動ダイアログに prompt 欄を置かない（ADR:148-150）。
113 §3 D10 は人格を `initial_prompt` とツール説明文に置くと決めている（113:356-370）が、
ADR の決定・影響・P0 に**誰が初回指示を組み、作成 API に渡すか**が無い
（ADR:218-238）。合図は無い Terminal 発言にも pull を求めるので、初回指示が欠ければ
最初の発言から `get_image_studio` を引く根拠が無くなる。結び替え・再作成時にも
人格を再投入する規則を ADR に書く必要がある。英訳:125-130,164-168,246-269。

### 🔴8 パスの番人は文字列の範囲検査だけでは足りない

決定 4 と P0 前提作業は browse root 内＋Files の拒否リストを `spec()` に足す
（ADR:109-110,235-236）。既存の Files の読み口は symlink を拒否する FD ベースの
`openat2NoSymlinks` を使う（`agent/fs_fd_linux.go:215-250`）。`spec()` の段で単に
`filepath.Rel` と `isDenied` を確認しても、検査後に symlink を差し替えられ、
`comfy.go` の `os.ReadFile(path)` はその先を読む（`agent/internal/imagegen/comfy.go:1192-1194`）。
**実際に読むファイルを root に固定した安全な open で取得する**、または同等の
TOCTOU 対策を番人の要件に入れる必要がある。これは 113-review 🔴5 を
「番人を足す」と書くだけでは塞がらない。英訳:119-121,266-267。

### 🔴9 P0 で `op=inpaint` を書けるがマスクを作る画面は P1

決定 4 はエージェントが `op` と `needs_mask: true` を書けるとする（ADR:105,109-111）。
決定 11 のキャンバスは P1 で、P0 が明記するのは「参照あり・マスク無し」の指示編集だけ
（ADR:182-186,237-241）。P0 で `op=inpaint` を許すと、マスク無しの下書きは
`run_image_trial` と人の投入で必ず拒否され、`needs_mask` の導線も行き先がない
（`agent/internal/imagegen/comfy.go:1152-1157`、113 §6 P1）。
P0 のエージェントに許す `op` は `generate`／マスク無し `edit` に限るか、
既存のマスクファイルを人が指定する導線まで P0 に含める、と決める必要がある。
英訳:114,119-123,205-209,268-272。

### 🟡1 合図は通常の送信経路だけに付く

113 §5.1 は Console が Managed `/turn` と TUI `/input` の本文末尾に付けるという
（113:564-568）。現行 `MirrorView.send` は Managed の本文と TUI の
`buildImagePrompt` を分け、後者は添付パスを本文末尾に足す
（`con/features/mirror/MirrorView.tsx:1165-1199`）。合図を `buildImagePrompt` より前に
足すと「末尾」ではなくなる。`sendPrompt` を経る提案チップ・フィードバックもある
（同:834-866,1322-1350）。一方、メモの直接送信・peer・予約実行は Console の composer を
通らない（113-review §2 🔴2）。合図が無くても pull するという決定 5 は妥当だが、
合図を付ける範囲と「末尾」の組み立て順を受け入れ試験で固定する。ADR:116-124。

### 🟡2 錠を残す rewind は履歴上の効力も定義する

rewind が錠を巻き戻さず、編集履歴を消さないのは妥当（ADR:164-168、ADR 0022 決定 4 の
restore commit と同じ方向）。ただし戻した全文が現在の錠と矛盾しても人の rewind は通るのか、
履歴カードの「戻す」が自分自身の版へ戻るのか、巻き戻し行の before/after をどう付けるのかを
実装契約に固定する。`set_image_draft` だけが錠を拒否するなら人の rewind は可能で、
その例外を UI に見せる。ADR:112,164-170。

### 🟡3 スタジオとセッションの双方向参照は原子的に更新できない

スタジオ JSON と `session.Meta.Studio` を別々に持ち、結び替え・削除・recreate・fork を扱う
（ADR:65-76,175-180）。Agent のメタと JSON は別の保存先なので同時更新できない。
片側の書込み失敗・クラッシュ後にどちらを正として修復するか、古いセッションに広告済みの
書き込みツールをいつ拒否するかを決める。広告条件だけでなく**呼出し時にも
「現在の結び相手か」を照合**する必要がある（ADR:89-97、113 §5.1）。

### 🟡4 「曖昧なら広告し、呼出し時に断る」は所有者の特定が要る

決定 3 の「広告から消すのでなく理由付きで断る」は利用者に分かりやすい（ADR:97）。
しかし `mcpOwningSession()` が失敗した時点では `Studio` も読めない
（`mcpx/mcp_stdio.go:3335-3358`）。ツールを条件付きで広告する規則（ADR:89）と
両立させるには、曖昧時に「スタジオの可能性がある」ツールを広告して呼出し時に拒否するか、
所有者を確定する別手段が要る。広告集合と call 側拒否の表を作る。

### 🟡5 背景の語彙列挙は完全ではない

`jobs_http.go:28-59` には ADR の列挙に無い `provider`、`op`、`aspectRatio`、
`background` もある（ADR:31-34、`agent/internal/imagegen/jobs_http.go:28-59`）。
特に `provider` は 🔴2 の選択一致に必須で、`op` は決定 4 に現れる。
「代表例」とするか全欄を列挙する。英訳:35-38。

### 🟡6 背景の根拠行が 2 か所ずれる

`comfy.go:1186-1187` はアップロード名についてのコメントで、`os.ReadFile(path)` は
`comfy.go:1193`（ADR:33-34、英訳:37-38）。またチャットの `generate_image` 不可は
「所有セッションが要る」だけでなく、チャット側に `--self-report` が無いため
`mcpImageGenEnabled=false` になるのが直接の理由
（ADR:46、`mcpx/mcp_stdio.go:166-170`、113-review §1「generate_image」）。
後者は結論に影響しないが、根拠の言い方を正す。

### 🟡7 `AF_BROWSE_ROOT` を変えた環境では知識が Files に出ない

通常の `browseRoot()` は home なので `~/imagegen-knowledge/` は拒否リスト外で見える
（ADR:193-197、`agent/fs.go:23-33,122-156`）。ただし `AF_BROWSE_ROOT` が設定されると
root はその値であり、Files の一覧はそこに固定される（`agent/fs.go:28-33,462`）。
「Files ペインで開ける」を環境共通の決定とするなら、起動時に root が home を含むか
検証するか、配置場所を browse root の下から導く必要がある。英訳:217-222。

### 🟡8 P0 前提作業の②は全員の前提ではない

P0 前提の `AF_SESSION_NAME` 配達は copilot/cursor/kiro/muse Managed を使う条件であり、
claude TUI・codex Managed 新規・Terminal だけの最小 P0 の輪はこれ無しでもつながる
（ADR:152-160,235-238、113-review §2 🔴3）。②を P0 全体の阻害要因から
対応 kind の解放条件へ移すと、重い MCP 子の実機照合を別に進められる。
①の番人は `op`/`inputs` を解放する前提、③の剥がし手は合図を転写へ出す前提であり、
どちらも P0 の該当機能より前に要る。

### 🟡9 P1 の「見せる」と P0 の微調整要件の境界を明記する

P0 の最小輪は人が結果を見て文章で微調整を頼めるが、エージェントは絵そのものを
見られない（ADR:129-135,239-241）。結果を視覚で批評して直すことまで P0 の受け入れに
含めるなら決定 6 を P0 に繰り上げる必要がある。含めないなら P0 の説明を
「人の観察を言葉で渡す」までに限定する。🔴5 の絵と版の対応付けとは別問題である。

### 🟡10 マスクのキャンバスには追加の未解決がある

ADR は log 111 §10 の「EXIF 実測済み」を採る（ADR:182-186）。実測は Chromium で、
iOS Safari／Android は未測定。`openai_compat` の異寸法マスク・EXIF 経路も未測定
（log 111 §10.1, §10.4, §10.8）。「マスク無し拒否」だけでなく、
キャンバスの対象 provider と実機受け入れ条件を P1 に書く。

### 🟡11 ADR 0022 の roots 追加は「そのまま手に入る」ではない

ADR 0100:200-201 は知識ディレクトリを roots に加えれば差分・復元・輸出入が
そのまま手に入るとする。0022 決定 3・5・6 は glob の allowlist、symlink 非追跡、
import の範囲検査、全履歴の secret 走査を要件にする
（ADR 0022:33-40,51-64,65-91、`agent/internal/memoryx/memory_roots.go:26-57,63-104`、
`memory_export.go:1-10,60-75`）。可視ファイルには人とエージェントが任意の文を書けるため、
専用 root の `families/*.md`・`models/*.md` だけを取り、symlink と秘密を既存規則で扱う
新しい宣言・復元範囲・UI 名・import 互換性の設計が必要。P2 の独立した改訂条件にする。

### 🟡12 旧 ADR と PR の状態は現在の記述でおおむね正しい

0081 の決定 6・7 を置き換える位置付けは 0081:277-334 と一致する。
0094 の改訂は全体縮小を決め（0094:923-990）、#907・#913・#914・#915 は
いずれも MERGED（`gh pr view` の state/mergedAt を確認）。#914 は実機受け入れの
記録であり、実測は log 112 §14 にある。ADR 0094 自身の改訂末尾にはなお
「実機の受け入れはまだ」と残る（0094:1064-1086）ため、0100 で「受け入れ #914」を
根拠に使う際は log 112 §14 を直接示す方が誤読がない。ADR:51-52、英訳:56-57。

### 🔵1 知識と履歴の P0 をさらに小さくできる

知識の「要約」を `get_image_studio` へ載せる契約だけ P0 に置き、
`add_image_knowledge` と 4 節編集 UI を P1 に分ける案は検討に値する。
空の要約を返す契約ならツール結果の形は変わらない
（ADR:84,87,188-197,235-241）。ただし利用者の「知識を貯めたい」を
初日から満たすことを優先するなら現行の P0 を維持する。その場合も
P0 前提 3 件とは別の作業量として見積もる。
