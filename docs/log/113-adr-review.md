## 0. 総評と ADR の体裁

状態・関連・背景・決定・却下した案・影響・フェーズ・未解決の順序と 12 件の番号は日本語・英語で一致する
（ADR 0100 日本語:5-16,18,54,203,218,233,245／英語:5-18,20,59,228,246,264,276）。
0081 と 0094 は同じ主要節を持つ（0081:19,102,451,487,516,538／0094:29,63,438,458,499,607）。
0098 は「影響」が「未解決」より後にあるので、先例自体が厳密な順序規則ではない
（0098:487,506）。各決定はおおむね断定形で、提案段階の D 記号を残していない。
ただし「将来は roots に加える」は実装だけで成立するかのような未確定の約束である（🟡11）。

番号 0100 は妥当。`origin/develop` の ADR は 0098 までで、`temp/sidv2bw` と
`temp/sjys6nk` の HEAD はどちらも `docs(0099)` である（ADR 0100 日本語:8-9、
`git ls-tree origin/develop docs/decisions` と両ブランチの HEAD を照合）。
両方とも同じ番号なので将来の統合側では 0099 同士を調整する必要があるが、0100 の予約理由は成立する。

**日本語と英語の対応**: 決定 12 件、ツール表 4 行、書ける欄の表 1 行、未解決 4 件、
P0/P1/P2 の分配、3 枚・5 件・8 KB・1 KB・600 秒などの数値、記載された file:line は対応する。
決定の訳落ち・訳し過ぎは見つからなかった（日本語:80-201,233-253／英語:86-226,264-284）。
以下の事実誤りと設計の穴は両言語に共通し、修正時も対で直す。

## 1. 指摘（重大度順）

### 🔴1 空の下書きに部分更新できない

決定 3 は `set_image_draft` を「部分更新」「検証は投入と同じ `spec()`」とする（ADR:85）。
決定 2 の移行前を含め、空の下書きは実在する（ADR:77、`con/features/imagegen/draft.ts:80-102`）。
ところが `jobRequest.spec()` は `prompt` が空なら直ちに `bad_prompt` を返す
（`agent/internal/imagegen/jobs_http.go:103-106`）。「まず `op`、次に参照と prompt」のような
合法な部分更新は投入用検証をそのまま通すと失敗する。さらに `spec()` は `model`・`provider` の
実効値を確定する関数ではない（同:152-162）。**保存時は変更欄の型・錠・安全性を検証し、投入時に
完成した要求を別途検証する**と ADR に分けて書く必要がある。`null` で消した後の空 prompt も保存は許し、
投入を断るのが自然である。英訳:91。

### 🔴2 引数なし試走の「画面どおり」が保証されない

決定 3 は「いまペインに見えている下書きそのもの」で試走すると断定する（ADR:86,93-96）。
現行ペインは `providerId` の選択を ready な行へ解決し、その行の `model` を選んでから
`buildRequest` に渡す（`con/features/imagegen/ImagegenView.tsx:161-170,209-218`）。
`providerId` と `model` が空・古いとき、Agent 側の既定 provider と warm モデルの選択は
別の規則になる（`agent/internal/imagegen/jobs.go:854-884,896-920`）。特に複数 fleet 行で
モデル id が重複し得る（`con/features/imagegen/wire.ts:421-428`）。画面が選んだ行・モデル・
ファミリーの試走 steps を Agent が同じスナップショットで確定する規則が要る。
`needs_mask` が立つ inpaint はマスクが付くまで明示的に拒否する規則、冷えたモデルの待機・
MCP の 600 秒超過後もジョブと版をどう見せるかも同じ決定に必要
（ADR:107-111,249-250、`agent/internal/imagegen/comfy.go:1152-1157`）。英訳:92。

### 🔴3 `generate_image` を隠す配線と保証の範囲が決まっていない

既存の `generate_image` は設定が ON なら `--image-gen` でサーバに入り、
`mcpStdioToolList` が `mcpImageGenAdvertise()` を通して広告する
（`agent/ui_prefs.go:275-295`、`mcpx/mcp_stdio.go:92-98,166-170,397-414,1470-1474`）。
決定 3 の「スタジオなら広告しない」を実現するには、この経路で所有セッションの `Studio` を
判定して**既存ツールを除外**し、呼び出し時の広告照合も同じ集合にする必要がある
（ADR:89-97、`mcpx/mcp_stdio.go:2287-2295`）。影響・P0 にこの変更を明記する。
また ADR 0069 のとおり CLI 自身の画像ツールは af の広告集合の外にある
（`mcpx/mcp_stdio.go:1456-1465`）。「生成は人がボタンで」を全画像生成に対して構造的に保証する
とは言えない。保証対象を**スタジオのジョブキューへの N 枚投入**と明示するか、CLI 側も
制限する判断が必要。英訳:95-104。

### 🔴4 「版＝編集履歴の押した印」は追記 JSONL と食い違う

決定 9 では編集履歴は「下書きが変わるたび 1 件」で追記専用、版は「押した瞬間の写し」かつ
「編集履歴のうち押した印の付いた 1 件」（ADR:164-170）。下書きを編集せずに 2 回押すと
新しい編集行は無い。既存行へ印を付ければ追記専用に反し、同じ行で押下 2 回・別 seed・
別ジョブ ID を表せない。113 §3 D7 は `versions[]` を別に持ち、§5.1 は専用
`POST /versions` を置いていた（113:289-305,539）。**押下を独立した追記イベントにする**か、
版を編集履歴から分離する、と ADR で選ぶこと。試走の失敗・投入失敗で版を残すか、
`POST /versions` と `/jobs` の間の失敗をどう表すかも定義する。英訳:183-193。

### 🔴5 P0 の「履歴を残す」が完成画像には成り立たない

背景の要求には「結果を見ながら微調整し、履歴を残す」がある（ADR:20-23）。
P0 は編集履歴と版だけで、絵の `history.jsonl`・検索・「この設定に戻す」を P1 に置く
（ADR:169-173,235-241）。現行のジョブ一覧は完了 500 件までのメモリ上で再起動時に消える
（ADR:35-36、`agent/internal/imagegen/jobs.go:17-18,41-57`）。P0 の画像は版から辿れず、
元の絵を見て直す主な輪が再起動を跨げない。**絵と版の最小限の永続的な対応付けを P0 に入れる**か、
P0 では「履歴」は設定だけと明記して受け入れ条件を変える必要がある。比較 UI は P1 でよい。
英訳:188-193,266-272。

### 🔴6 `AF_SESSION_NAME` が届く kind でも worktree OFF は常に安全ではない

決定 8 は codex Managed 新規なら OFF 可とする（ADR:155-160）。しかし codex は
Agent のデーモンが差し替わった後に resume したスレッドへセッション名が届かず、
cwd 推測へ落ちる（`mcpx/mcp_stdio.go:3311-3340`、113-review §2 🔴3）。
同じリポジトリに別セッションがあれば、後の `get_image_studio`／`set_image_draft` の所有者を
確定できない。OFF 可否を **kind × 実行方式 × resume 状態**で扱うか、
名前を渡せない再開経路がある Managed kind の OFF を拒否する、と決める必要がある。
「未コミットの資料を見せたい」要求は worktree ON では満たされないことも起動 UI に明示する。
英訳:173-179。

### 🔴7 人格を初回指示に入れる契約が ADR から落ちている

決定 5 は「発言を受けたらまず `get_image_studio`」という人格に依存する
（ADR:114-118）。決定 8 は起動ダイアログに prompt 欄を置かない（ADR:148-150）。
113 §3 D10 は人格を `initial_prompt` とツール説明文に置くと決めている（113:356-370）が、
ADR の決定・影響・P0 に**誰が初回指示を組み、作成 API に渡すか**が無い
（ADR:218-238）。合図は無い Terminal 発言にも pull を求めるので、初回指示が欠ければ
最初の発言から `get_image_studio` を引く根拠が無くなる。結び替え・再作成時にも
人格を再投入する規則を ADR に書く必要がある。英訳:125-130,164-168,246-269。

### 🔴8 パスの番人は文字列の範囲検査だけでは足りない

決定 4 と P0 前提作業は browse root 内＋Files の拒否リストを `spec()` に足す
（ADR:109-110,235-236）。既存の Files の読み口は symlink を拒否する FD ベースの
`openat2NoSymlinks` を使う（`agent/fs_fd_linux.go:215-250`）。`spec()` の段で単に
`filepath.Rel` と `isDenied` を確認しても、検査後に symlink を差し替えられ、
`comfy.go` の `os.ReadFile(path)` はその先を読む（`agent/internal/imagegen/comfy.go:1192-1194`）。
**実際に読むファイルを root に固定した安全な open で取得する**、または同等の
TOCTOU 対策を番人の要件に入れる必要がある。これは 113-review 🔴5 を
「番人を足す」と書くだけでは塞がらない。英訳:119-121,266-267。

### 🔴9 P0 で `op=inpaint` を書けるがマスクを作る画面は P1

決定 4 はエージェントが `op` と `needs_mask: true` を書けるとする（ADR:105,109-111）。
決定 11 のキャンバスは P1 で、P0 が明記するのは「参照あり・マスク無し」の指示編集だけ
（ADR:182-186,237-241）。P0 で `op=inpaint` を許すと、マスク無しの下書きは
`run_image_trial` と人の投入で必ず拒否され、`needs_mask` の導線も行き先がない
（`agent/internal/imagegen/comfy.go:1152-1157`、113 §6 P1）。
P0 のエージェントに許す `op` は `generate`／マスク無し `edit` に限るか、
既存のマスクファイルを人が指定する導線まで P0 に含める、と決める必要がある。
英訳:114,119-123,205-209,268-272。

### 🟡1 合図は通常の送信経路だけに付く

113 §5.1 は Console が Managed `/turn` と TUI `/input` の本文末尾に付けるという
（113:564-568）。現行 `MirrorView.send` は Managed の本文と TUI の
`buildImagePrompt` を分け、後者は添付パスを本文末尾に足す
（`con/features/mirror/MirrorView.tsx:1165-1199`）。合図を `buildImagePrompt` より前に
足すと「末尾」ではなくなる。`sendPrompt` を経る提案チップ・フィードバックもある
（同:834-866,1322-1350）。一方、メモの直接送信・peer・予約実行は Console の composer を
通らない（113-review §2 🔴2）。合図が無くても pull するという決定 5 は妥当だが、
合図を付ける範囲と「末尾」の組み立て順を受け入れ試験で固定する。ADR:116-124。

### 🟡2 錠を残す rewind は履歴上の効力も定義する

rewind が錠を巻き戻さず、編集履歴を消さないのは妥当（ADR:164-168、ADR 0022 決定 4 の
restore commit と同じ方向）。ただし戻した全文が現在の錠と矛盾しても人の rewind は通るのか、
履歴カードの「戻す」が自分自身の版へ戻るのか、巻き戻し行の before/after をどう付けるのかを
実装契約に固定する。`set_image_draft` だけが錠を拒否するなら人の rewind は可能で、
その例外を UI に見せる。ADR:112,164-170。

### 🟡3 スタジオとセッションの双方向参照は原子的に更新できない

スタジオ JSON と `session.Meta.Studio` を別々に持ち、結び替え・削除・recreate・fork を扱う
（ADR:65-76,175-180）。Agent のメタと JSON は別の保存先なので同時更新できない。
片側の書込み失敗・クラッシュ後にどちらを正として修復するか、古いセッションに広告済みの
書き込みツールをいつ拒否するかを決める。広告条件だけでなく**呼出し時にも
「現在の結び相手か」を照合**する必要がある（ADR:89-97、113 §5.1）。

### 🟡4 「曖昧なら広告し、呼出し時に断る」は所有者の特定が要る

決定 3 の「広告から消すのでなく理由付きで断る」は利用者に分かりやすい（ADR:97）。
しかし `mcpOwningSession()` が失敗した時点では `Studio` も読めない
（`mcpx/mcp_stdio.go:3335-3358`）。ツールを条件付きで広告する規則（ADR:89）と
両立させるには、曖昧時に「スタジオの可能性がある」ツールを広告して呼出し時に拒否するか、
所有者を確定する別手段が要る。広告集合と call 側拒否の表を作る。

### 🟡5 背景の語彙列挙は完全ではない

`jobs_http.go:28-59` には ADR の列挙に無い `provider`、`op`、`aspectRatio`、
`background` もある（ADR:31-34、`agent/internal/imagegen/jobs_http.go:28-59`）。
特に `provider` は 🔴2 の選択一致に必須で、`op` は決定 4 に現れる。
「代表例」とするか全欄を列挙する。英訳:35-38。

### 🟡6 背景の根拠行が 2 か所ずれる

`comfy.go:1186-1187` はアップロード名についてのコメントで、`os.ReadFile(path)` は
`comfy.go:1193`（ADR:33-34、英訳:37-38）。またチャットの `generate_image` 不可は
「所有セッションが要る」だけでなく、チャット側に `--self-report` が無いため
`mcpImageGenEnabled=false` になるのが直接の理由
（ADR:46、`mcpx/mcp_stdio.go:166-170`、113-review §1「generate_image」）。
後者は結論に影響しないが、根拠の言い方を正す。

### 🟡7 `AF_BROWSE_ROOT` を変えた環境では知識が Files に出ない

通常の `browseRoot()` は home なので `~/imagegen-knowledge/` は拒否リスト外で見える
（ADR:193-197、`agent/fs.go:23-33,122-156`）。ただし `AF_BROWSE_ROOT` が設定されると
root はその値であり、Files の一覧はそこに固定される（`agent/fs.go:28-33,462`）。
「Files ペインで開ける」を環境共通の決定とするなら、起動時に root が home を含むか
検証するか、配置場所を browse root の下から導く必要がある。英訳:217-222。

### 🟡8 P0 前提作業の②は全員の前提ではない

P0 前提の `AF_SESSION_NAME` 配達は copilot/cursor/kiro/muse Managed を使う条件であり、
claude TUI・codex Managed 新規・Terminal だけの最小 P0 の輪はこれ無しでもつながる
（ADR:152-160,235-238、113-review §2 🔴3）。②を P0 全体の阻害要因から
対応 kind の解放条件へ移すと、重い MCP 子の実機照合を別に進められる。
①の番人は `op`/`inputs` を解放する前提、③の剥がし手は合図を転写へ出す前提であり、
どちらも P0 の該当機能より前に要る。

### 🟡9 P1 の「見せる」と P0 の微調整要件の境界を明記する

P0 の最小輪は人が結果を見て文章で微調整を頼めるが、エージェントは絵そのものを
見られない（ADR:129-135,239-241）。結果を視覚で批評して直すことまで P0 の受け入れに
含めるなら決定 6 を P0 に繰り上げる必要がある。含めないなら P0 の説明を
「人の観察を言葉で渡す」までに限定する。🔴5 の絵と版の対応付けとは別問題である。

### 🟡10 マスクのキャンバスには追加の未解決がある

ADR は log 111 §10 の「EXIF 実測済み」を採る（ADR:182-186）。実測は Chromium で、
iOS Safari／Android は未測定。`openai_compat` の異寸法マスク・EXIF 経路も未測定
（log 111 §10.1, §10.4, §10.8）。「マスク無し拒否」だけでなく、
キャンバスの対象 provider と実機受け入れ条件を P1 に書く。

### 🟡11 ADR 0022 の roots 追加は「そのまま手に入る」ではない

ADR 0100:200-201 は知識ディレクトリを roots に加えれば差分・復元・輸出入が
そのまま手に入るとする。0022 決定 3・5・6 は glob の allowlist、symlink 非追跡、
import の範囲検査、全履歴の secret 走査を要件にする
（ADR 0022:33-40,51-64,65-91、`agent/internal/memoryx/memory_roots.go:26-57,63-104`、
`memory_export.go:1-10,60-75`）。可視ファイルには人とエージェントが任意の文を書けるため、
専用 root の `families/*.md`・`models/*.md` だけを取り、symlink と秘密を既存規則で扱う
新しい宣言・復元範囲・UI 名・import 互換性の設計が必要。P2 の独立した改訂条件にする。

### 🟡12 旧 ADR と PR の状態は現在の記述でおおむね正しい

0081 の決定 6・7 を置き換える位置付けは 0081:277-334 と一致する。
0094 の改訂は全体縮小を決め（0094:923-990）、#907・#913・#914・#915 は
いずれも MERGED（`gh pr view` の state/mergedAt を確認）。#914 は実機受け入れの
記録であり、実測は log 112 §14 にある。ADR 0094 自身の改訂末尾にはなお
「実機の受け入れはまだ」と残る（0094:1064-1086）ため、0100 で「受け入れ #914」を
根拠に使う際は log 112 §14 を直接示す方が誤読がない。ADR:51-52、英訳:56-57。

### 🔵1 知識と履歴の P0 をさらに小さくできる

知識の「要約」を `get_image_studio` へ載せる契約だけ P0 に置き、
`add_image_knowledge` と 4 節編集 UI を P1 に分ける案は検討に値する。
空の要約を返す契約ならツール結果の形は変わらない
（ADR:84,87,188-197,235-241）。ただし利用者の「知識を貯めたい」を
初日から満たすことを優先するなら現行の P0 を維持する。その場合も
P0 前提 3 件とは別の作業量として見積もる。

### 5.1 改訂後の本文から新たに見つけた点

#### 🔴A 結び替え直後は、古い広告集合から `generate_image` を呼べる

決定 3 は `mcpImageGenAdvertise()` でスタジオのセッションを除外し、「呼び出し側の照合も
同じ集合」とする（ADR 日本語:102-115／英語:109-126）。しかし現行の呼び出し側は
**最後に記憶した tools/list**だけを見る（`mcpx/mcp_stdio.go:547-565,2287-2295`）。
結び直してメタに `Studio` が付いても、次の tools/list または 1 分ごとの watcher まで
古い集合に `generate_image` が残る（同:489-533）。その間に既存ツールを呼ぶと
`mcpGenerateImage` へ進み、スタジオの結びを検査しない
（同:2412-2419、`mcpx/mcp_imagegen.go:206-228`）。「生成は人のボタン」の af 側の
境界を成り立たせるには、**ツール呼出し時に現在の `Studio` を再検査して拒否する**か、
結び替えと同時に全 MCP 子の広告状態を無効化する必要がある。🔴3 の修正はここまで届いていない。

#### 🔴B 安全な open が comfy のアップロードだけでは、別の読み口から漏れる

決定 4 と P0 前提 ① は comfy のアップロードだけを root 固定 open に替える
（ADR 日本語:127-130,259-261,275-276／英語:140-144,295-297,314-315）。
同じ `/imagegen/jobs` は `openai_compat` の edit/inpaint も通し、その添付関数は
`os.ReadFile(path)` で `inputs` と `mask` を読む
（`agent/internal/imagegen/openai_compat.go:379-405`）。comfy 自身もアップロードより前の
寸法読取りで `os.ReadFile(req.Inputs[0])` を呼ぶ
（`agent/internal/imagegen/comfy.go:1040-1052`）。`spec()` の文字列検査後に symlink を
差し替えればこれらは root 外を読む。**すべての provider の全読取りを同じ安全な open へ
通す**と前提を広げる必要がある。P0 は openai_compat のマスクパスを対象外にしていない
（ADR 日本語:280-287）。🔴8 の修正は不十分。

#### 🔴C MCP の 600 秒上限に「掛かったら返す」はクライアントからは受け取れない

`run_image_trial` は codex の上限に掛かったとき「まだ走っています（ジョブ id）」を返す
（ADR 日本語:99／英語:106）。現行の `tool_timeout_sec` は MCP **クライアント側**の
600 秒上限で、そこで呼び出しが切られる（`mcpx/mcp_imagegen.go:196-204`）。
サーバが 600 秒後に返答しても、切れた呼び出しには届かない。
**600 秒より前に自分で期限を切ってジョブ id を返す**、または試走ツールを投入後すぐ
ジョブ id を返す形にする、と決める必要がある。冷えたエンジンが 16 分待つ条件は
ADR 未解決 2（日本語:295-296）自身が認めている。🔴2 の待機の修正は不十分。

#### 🔴D `needs_mask` を真にした後、マスクを置いても試走が戻らない

エージェントは `needs_mask: true` を書き、P0 の人は既存のパス欄へマスクを置く
（ADR 日本語:131-133／英語:145-148）。一方、`run_image_trial` は
**`needs_mask` が立っていること自体**を拒否条件にする（日本語:99／英語:106）。
マスクを置く操作でこの旗を消す規則が無いので、そのままでは条件が永続し、
マスクがある有効な inpaint もエージェントだけ試走できない。拒否条件を
「`op=inpaint` かつ `mask` が空」にするか、人がマスクを置くと旗を原子的に
消すと決める。現行のフォームも `mask` の空だけで押下を止める
（`con/features/imagegen/parts/GenerateForm.tsx:94-100,468-476,496-518`）。🔴2・9 に残る。

#### 🔴E press 1 行へジョブ id と失敗を同時に書く順序が未成立

決定 9 は押した瞬間に追記する `kind: "press"` の 1 行へ
`ジョブ／グループ id` と投入失敗時の `error` も入れる（ADR 日本語:200-203／英語:224-228）。
しかし id と失敗は投入の応答後に初めて分かる。根拠文書の配線は
`POST …/versions` → `POST /imagegen/jobs` の 2 要求である（113 §5.1、§5.2）。
最初の要求で追記した行は後から編集できず、2 番目の応答を反映できない。
**押下時の写しと投入結果を別の追記イベントにする**か、1 つの Agent API で
投入結果が出てから押下時の写しを追記するかを決める必要がある。後者なら
決定 1 の「生成経路は変えない」の例外を明記する（ADR 日本語:66-71）。🔴4 は不十分。

#### 🔴F スタジオ作成と `initial_prompt` 発火の順序が逆になり得る

決定 2 は「最初の発言で」スタジオを作る（ADR 日本語:90-91／英語:97-98）。
決定 5 はスタジオ id を使う `GET /imagegen/studios/{id}/persona` を
「エージェントを付ける」の**作成要求より前**に呼び、その結果を `initial_prompt` で
送る（日本語:138-143／英語:153-159）。Agent のセッション作成は Managed なら
`initial_prompt` を作成処理中に `h.Send` する
（`agent/internal/sessionx/session_handlers.go:1014-1035`）。
その時点でスタジオをまだ作っていない、またはセッションのメタと結んでいないと、
最初の人格ターンの `get_image_studio` は広告されない（ADR 日本語:102-105）。
**「エージェントを付ける」押下時にスタジオを先に作る→セッション作成時に `Studio` を
メタへ入れる→初回ターンの前にスタジオの `session` を結ぶ**順序を決め、
失敗時の孤児をどう扱うか書く必要がある。🔴7 の注入先は決まったが初回の成立条件は残る。

#### 🔴G TUI 専用の claude が起動候補から落ちる記述が残る

決定 8 は claude を P0 に入れるため TUI が必要と言いながら、
「kind 一覧は `managedDrivers` から引く」と一続きで書く
（ADR 日本語:179-181／英語:202-204）。その表は 7 kind で claude・agy を持たない
（`agent/internal/sessionx/session_turn.go:30-41`）。文字どおり 1 つの一覧を作れば

#### 🟡A 新しい根拠行は意味を指すが、マスク欄の行はコメント

`fs_fd_linux.go:192` は `openat2NoSymlinks` の定義、`comfy.go:1193` は
`os.ReadFile` で正しい（ADR 日本語:38-40）。PR #854 は MERGED。
一方 `GenerateForm.tsx:96-100` は「マスク欄がある理由」と `needsMask` の判定で、
実際の欄は `con/features/imagegen/parts/GenerateForm.tsx:468-476`。背景の

（ADR 日本語:60-62／英語:65-68）。

#### 🟡B 可視性を直した知識 root の存続は browse root の場所次第

改訂は `<browse root>/imagegen-knowledge/` に置き、`AF_BROWSE_ROOT` が変わっても
Files に出す（ADR 日本語:228-233／英語:259-266、`agent/fs.go:23-33`）。

スタジオは `provider` と `model` を持ち、モデル無しのエージェント試走は断る

人の既存の生成ボタンは今までどおり動く条件を定義する。

### 6.1 改訂後の本文から新たに見つけた点

#### 🔴H CLI 子プロセスに渡した参照パスは `openRequestFile` を通らない

決定 4 は要求のパスを読む**すべて**の場所を `openRequestFile` に通し、provider の
`os.ReadFile` を AST で見張る（ADR 日本語:138-144／英語:153-160）。ComfyUI の事前読取り・
upload と `openai_compat` の添付には効く。しかし codex provider は参照パスを `-i` として
**別プロセス**に渡す（`agent/internal/imagegen/codex.go:173-180`）。agy も `ImagePaths` を
プロンプトへ文字列で渡す（`agent/internal/imagegen/agy.go:449-458`）。その子が後でパスを
開くので、Agent 側の検査後に symlink を差し替える窓が残る。AST に `os.ReadFile(req.Inputs)`
が無いことも安全性の証明にならない。**安全な FD から bytes を固定した一時ファイルを作り、
子プロセスにはその固定コピーだけを渡す**など、CLI provider も含めた契約が要る。
影響と P0 前提はなお「comfy 側」とだけ書く（ADR 日本語:284-288,300-304／英語:323-328,
342-347）ので、決定 4 の全 provider 対象とも矛盾する。

#### 🔴I 120 秒は opencode の MCP 待機上限より長い

`run_image_trial` は 120 秒を「どのクライアントの上限より短い」とする
（ADR 日本語:107／英語:115）。既存の `generate_image` は **opencode が通知なしだと 60 秒で
切る**ため 10 秒間隔の progress heartbeat を送る
（`mcpx/mcp_imagegen.go:222-228`）。opencode Terminal は P0 の対象（ADR 日本語:202-208）。
新ツールが 120 秒待つだけなら 60 秒以降のジョブ id は届かない。**試走にも heartbeat を
付けるか、opencode では 60 秒より前に返す**と決定 3 に書く必要がある。

#### 🔴J press を投入後に追記するだけでは、絵へ版 id が渡らない

決定 9 はキューへ投入した**後**に press 1 行を書き、その press id をサイドカーと
`history.jsonl` に載せる（ADR 日本語:219-229／英語:245-258）。現行キューは `Enqueue` の
中で worker を起こし、応答前から走れる（`agent/internal/imagegen/jobs.go:297-342,364-393`）。
絵のサイドカーは完了時に `jobRec` から作る（同:426-461,477-511）が、現行の
`JobSpec`・`jobRec` に `studio`・`version` の口は無い（同:114-145,214-229）。
press 行を応答後に初めて作るだけでは、worker が先に保存した絵へ版 id を載せられず、
「絵と版の対応は永続」という決定 9 が成立しない。**press id を投入前に予約し、
`studio`・`version` をジョブへ渡してから worker を起こす**順序と、投入失敗時に
その id で `error` 行を残す手順が要る。投入と追記の間に Agent が落ちる場合も定める。

#### 🔴K browse root を repo にした配備では、既定の生成結果を参照に戻せない

決定 4 の番人は `inputs`/`mask` を **browse root の内側**に限る
（ADR 日本語:138-143／英語:153-160）。一方、既定の keeper と試走は browse root でなく
`~/.cache/agent-fleet/generated/console[/trial]` に置く
（`agent/internal/imagegen/store.go:28-34,50-53`、`jobs.go:923-939`）。`AF_BROWSE_ROOT` は
home 以外にでき、決定 12 自身が `~/repos` 配下の場合を扱っている
（`agent/fs.go:28-33`、ADR 日本語:251-255）。その場合、結果カードの
「参照にする」と P0 の参照あり指示編集（ADR 日本語:227-231,305-308）が、
自分で生成した既定のパスを番人に拒否される。**生成物 root を別の許可 root として
安全な open に加えるか、参照選択時に browse root 内へ固定コピーする**と決める必要がある。

#### 🟡E 「指紋を進める」には Agent から MCP 子への通知経路が要る

結び替え時に Agent が指紋を進め `list_changed` を早めるという文
（ADR 日本語:114-119／英語:123-129）は、現行の指紋が **MCP 子プロセス内で
tools/list から計算した hash**であることと噛み合わない
（`mcpx/mcp_stdio.go:445-476,518-533`）。Agent がこの値を直接進める口は無い。
再検査により呼出し境界は守られるので 🔴A は直っているが、早期通知を要件にするなら
子への invalidation 経路を定める。無ければ 1 分 watcher の約束に揃える。

#### 🟡F home 固定の知識は、Files ペインでの編集説明を揃える

改訂は永続性を優先し、browse root が home 以外なら Files ペインに出ないことを認める

明記する。日本語の「Read で読み書き」も読み取りツールの役割と合わない（日本語:254-255）。

#### 🟡G 起動候補の「TUI kind 表」は現行 Console に無い

決定 8 は TUI 候補を起動ダイアログの「TUI の kind 表」から引くと言う

`managedDriver` と `terminalDriver` で実行方式を選ぶ

786-817`）。その配列には TUI の無い lcpp・muse と shell も入る。TUI 候補は
`repoLaunchKinds` のうち Terminal 可能な kind から導く、と出所を具体化する。

#### 🟡H 作成後の初回送信失敗は、現行 API では成功応答になる

決定 2 はセッション作成が失敗すればスタジオを結び無しで残し、決定 5 は初回人格を
`initial_prompt` で送る（ADR 日本語:94-99,155-159）。現行 Managed 作成は
`h.Send` が失敗してもログだけ書いて `writeCreated` を返す

Console は結び済みを成功と見ても最初の人格ターンが無い。送信失敗時の再送・結び解除・
利用者への表示のいずれかを実装契約に含める。

#### 🔴L 「ジョブ別コピー」と `JobSpec.Inputs` は現行キューの順序では同時に作れない

決定 4 は投入時に `generated/console/inputs/<job>/` へ**ジョブ私有**のコピーを置き、
`JobSpec.Inputs` を「コピーの型」にして provider には原本パスを渡さず、サイドカーには
原本パスを記録するとする（ADR 日本語:147-160／英語:163-178）。現行の `JobSpec` に
`Inputs` 欄は無く、`Request.Inputs []string` と `Request.Mask` を内包する
（`agent/internal/imagegen/jobs.go:214-229`、`imagegen.go:76-85`）。ジョブ id は
`Enqueue` の**内部**で初めて採番される（`jobs.go:297-327`）。したがって呼出し前に
`JobSpec` へ `<job>` のコピーを入れることはできない。さらに worker が provider に渡す
`jobRec.req` と、サイドカーに写す `jobRec.req.Inputs/Mask` は現在**同じ値**
（同:426-461,477-511）。コピーへ置換するだけでは、サイドカーが終了後に消すコピーを
原本として記録する。逆に原本を保持すると provider に渡る。**ジョブ id を作った後、
worker を起こす前に各ジョブのコピーを作り、provider 用の型とサイドカー用の原本パスを
別に保持する**順序・型を決める必要がある。`mask` にも同じ分離が要る。
決定 1 の「ジョブはそのまま」（日本語:74-80）と、決定 9 の「キューも変わらない」
（日本語:236-247）は、このジョブ構築順序と記録形を変える範囲を例外として認めるべきである。

#### 🔴M `recovered: true` の press 行をサイドカーから復元できない

決定 9 は press を**下書き全文・seed 方針・書き手・ジョブ／グループ id**の 1 行とし、
投入と追記の間に落ちたら `history.jsonl` の `version` から同じ id の
`recovered: true` 行を合成する（ADR 日本語:236-250／英語:264-280）。しかし
サイドカーの `ImageProps` は生成結果の記録であり、下書き全文・`seed_policy`・`jobs`・
`out_dir`・書き手を持たない（`agent/internal/imagegen/props.go:42-90`）。特に
`Negative` は**合成後**の値で、元の下書きとは異なる（`jobs.go:477-511`）。
その情報だけでは「この設定に戻す」に使える press を合成できない。
また絵と sidecar の書込みは先で、`history.jsonl` は別の追記ファイルなので、落ちる時点に
よっては sidecar があるのに index 行だけ無い。index が存在するが末尾を欠く場合は
「無ければ走査して再生成」（ADR 日本語:248-250）にも該当しない。
**投入前に復旧用の下書き全文を永続化する**か、sidecar 自体へその全文を持たせ、
起動時は index の有無によらず sidecar と log を突き合わせる契約が要る。

#### 🔴N TUI の初回ターン失敗を作成応答の `warning` に載せられない

決定 2 は初回ターン送信が失敗したとき、作成応答に `warning` を載せてペインに再送を
出す（ADR 日本語:99-107／英語:107-116）。Managed は作成処理内で `h.Send` するが、
**TUI は応答と独立した goroutine で配達し、応答は完了を待たない**

確認不能時の再送をどう扱うか決める必要がある。

#### 🔴O `terminalDriver` の真偽で絞ると claude・agy が落ちる

決定 8 は TUI 候補を `repoLaunchKinds` のうち `terminalDriver` を**持つ** kind とする

`Request` を丸ごと保持し、`jobRec.req` へ写し、worker が同じ `Request` を
`prov.Generate` に渡す（`workspace/agent/internal/imagegen/jobs.go:214-229,318-326,426-437`。
`Request` 自体は provider の引数型、`imagegen.go:53-85`）。欄名だけを「記録用」にしても
provider は原本パスを受け取る。**原本は `Request` の外で、`JobSpec`／`jobRec` の記録専用欄に
分けるか、provider 呼出し前に原本欄を落とした別の `Request` を作る**契約が必要。
「原本を provider に渡さない」は子プロセスまで含む決定 4 の安全境界なので、型の置き場を
直さないまま実装へ渡せない。決定 1 の「`Request` に原本の記録欄」（日本語:83-85／
英語:91-94）も同時に直す必要がある。

#### 🔴Q `press` 行の欄一覧に、投入後にしか分からない値が残る

決定 9 の冒頭は `kind: "press"` の独立イベントに「ジョブ／グループ id・失敗なら
`error`」を含める（ADR 日本語:248-250／英語:280-283）。直後の確定した順序では
**① `press` 行を投入前に書き**、③で初めて `Enqueue` が job/group id を採番し、
④の `press_result` 行にその id または `error` を書く（日本語:251-258／英語:284-293）。
現行キューの採番も `Enqueue` 内にある（`workspace/agent/internal/imagegen/jobs.go:297-327`）。
冒頭のスキーマと実行順を同時には満たせない。`press` の欄を版 id・全文・seed 方針・
書き手・押下時刻に、結果欄を `press_result` に分けて書き直す必要がある。

#### 🔴R 60 秒の `unknown` は TUI の送信処理中にも起き、再送が二重ターンになり得る

決定 2 は `InitialPromptState` を `delivered/failed/unknown` とし、TUI でも
60 秒経って `unknown` なら「再送」を出す（ADR 日本語:104-114／英語:114-126）。
現行の TUI 配達は pane を最大 30 秒、composer をさらに最大 30 秒待ち、
2.5 秒の fallback 後に入力し、0.9 秒後の Enter と配達確認を行う
（`workspace/agent/internal/sessionx/session_io.go:853-920`）。確認は最初の 12 秒と
再試行後の 12 秒まで待てる（`session_delivery.go:41-47,108-141`）。したがって
**60 秒時点で一度も送っていない、あるいは送信済みだが確認中**が通常の経路としてある。
このとき再送すると、後から元の goroutine も送って二重に人格ターンが走り得る。
`pending` と確認不能を区別し、送信処理が終わるまでは再送を許さない契約が要る。

#### 🟡M 影響欄の `JobSpec.Inputs` は改訂 4 の型と一致しない

決定 4 は入力セット id と `Request.Inputs/Mask` のコピー欄を採用したが、影響欄はなお
「`JobSpec.Inputs` の型」と書く（ADR 日本語:159-165,320-324／英語:179-186,364-370）。
現行 `JobSpec` に独立した `Inputs` 欄は無い（`jobs.go:214-229`）。🔴P の型の修正に
合わせて影響欄も揃えると、実装範囲の取り違えを防げる。

#### 🟡N 入力セットの「最後のジョブ」には取消で終わるジョブも含める

決定 4 はグループの最後のジョブ終了時に固定コピーを消す（ADR 日本語:169-171／
英語:190-193）。現行の queued job の個別取消とグループ取消は `q.finish` を通らず、
その場で `JobCancelled` にする（`jobs.go:701-726,781-800`）。全件が待機中のまま
取り消されたグループにも後始末が必要。終了判定と掃除を `finish` のみに付けず、
両取消経路を含める実装上の注意点である。

#### 🟡O `press_result` の追記失敗をその場でどう扱うか

決定 9 はキュー投入後に `press_result` を書き、欠落行は**起動時**に sidecar から
補う（ADR 日本語:251-260／英語:284-295）。`Enqueue` は worker を起こしてから
返る（`jobs.go:297-342`）。④の追記だけ失敗すると画像生成は続く一方、稼働中の版は
結果行が無いままで、ペインへの応答も未定義になる。投入成功と記録失敗の区別を
レスポンスで示し、稼働中にも欠落行を補うか、少なくとも履歴を「保留」として読める
ようにする実装上の注意点である。
