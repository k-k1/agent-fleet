# 執筆規範

[English](CONVENTIONS.md) | 日本語

全棚の全ファイルに適用します。機械的に検査できる部分は
`scripts/docs-check.py` が見ます。push の前に走らせてください。

```
python3 scripts/docs-check.py           # CI が走らせるもの
python3 scripts/docs-check.py --strict  # warn を error に格上げ
```

## 1. 1 ファイルに寿命は 1 つ

旧レイアウトが失い、そして崩壊した原因の規則です。文章は 3 通りの速さで古びます。
**この 3 つを同じファイルに入れてはいけません。**

| 寿命 | 置き場 |
|---|---|
| コードが変われば変わる（仕様・手順・能力表）| `guide/` の各棚と `docs/build/` |
| 二度と変わらない（決定・実測・事故・捨てた案）| `docs/decisions/`、または凍結した `docs/log/` |
| 毎日変わる（いま何が動いているか）| `docs/HANDOFF.md` |

混ざったファイルは陳腐化のレビューができません。**どの文が「まだ真であるはず」なのかを
判別する手段が無い**からです。現役の文書に「第 7 ラウンド」を追記しそうになったら、
それはジャーナルを書いています。恒久的な結論だけを現役の文書に残し、経緯は決定記録へ。

## 2. 棚は「読者」で切る。ジャンルでは切らない

文書の置き場は**誰が読むか**で決まり、どういう種類の文書かでは決まりません。
ジャンルで切った棚は、誰にも配れません。読者は 3 人います（ADR 0064）。

| 読者 | 置き場 | 答えるのは | 配布 |
|---|---|---|---|
| 使ってみたい人 | ルートの `README.md` / `README.ja.md` | これは何で、自分に要るか？ | GitHub のみ |
| 使っている人（メンバー・テナント管理者・配備管理者）| `guide/` | どうやるの？ | **コンテナへ配る** |
| コードを変える人 | `docs/` | どう動いている？ なぜこうなった？ | **誰にも配らない** |

**ディレクトリの境界がそのまま配布の境界です。** `guide/` がコンテナへ入る唯一の
ツリーで、ロールでは切りません——誰もが同じものを受け取ります。

だから規則は一方通行です。

> **`guide/` から `docs/` へリンクしてはいけません。逆は自由です。**

`docs/` は読者のコンテナに存在しないので、そこを指すリンクは**リポジトリ上では
実在するのに読者の手元では必ず切れる**——検査を素通りする、いちばん厄介な壊れ方です。
散文で「詳細は開発者向けの資料にあります」と告げるのは正しく、それをクリックできる
ようにするのが誤りです。`check_closure` が機械で見ます。

## 3. 必須の front matter

`guide/` の各棚と `docs/build/` の全ファイルは、こう始めます。

```markdown
---
audience: "誰のためか（一句で）"
source_of_truth: "この文書と食い違ったとき、どちらが正か"
updated: "2026-09"
---

# タイトル

[English](title.md) | 日本語
```

**値は必ず二重引用符で囲みます**——`source_of_truth` の値にはコロンや読点が入ります。

これは書き手と CI のための情報で、読者の読むものではありません。だから地の文には
置かず front matter にします。Console は front matter を本文と切り分けてメタデータ枠に
描くので（`splitYamlFrontMatter`）、**本文から降格したまま、失われはしません**。

`source_of_truth` があると陳腐化に耐えられます。`docs/build/` なら普通はコード、
`guide/operate/` なら `deploy/` のスクリプト、`guide/member/` なら Console そのもの。
**明記しておけば、矛盾を見つけた読者がどちらを信じるべきか分かります。**

- **`source_of_truth` だけは棚の README から継承してよい。** `guide/member/` の 16 枚と
  `guide/admin/` の 6 枚は値が一字句同じで、同じ一文が 22 回並んでいました——読者に
  とっては情報量ゼロの定型です。棚の README に 1 回書いて、各ファイルからは省きます。
- **値が棚ごとに違う棚では省けません。** `guide/ref/` は 10 枚すべて違い
  （「この表が正」「画面欄は Console・実装欄はコード」…）、これは本物の情報です。
- **`> 対象: …` のような引用ブロックを添えないこと。** `audience` の言い換えになります。
  1 文に価値がある章だけ、引用ではなく本文の導入として書いてください。

## 4. 棚ごとの語彙

- **`guide/member/` と `guide/admin/` は画面の名前だけで話す。** 読者が Console で見る
  言葉が正しい言葉です。env 変数名・内部の種別識別子・API パス・ソースのパスは地の文に
  書けません（どうしても示すならコードブロックで引用）。CI が検査します。
- **`guide/operate/` はコマンド・パス・変数を使ってよい**——読者は端末の前にいます。
- **`guide/ref/` は画面欄と実装欄の対応表そのもの**なので、両方の語が出ます。
- **`docs/build/` はワイヤ契約と責務で書く**。どのプロセスが何を持ち、外から見た契約は
  何か。**行番号は絶対に書かない**（1 週間で腐ります）。grep できるアンカー
  （エンドポイントパス・env 名・エラーコード文字列）かコードマップを指してください。

### 読者向けの棚で避ける語

`driver` / `runtime` / TUI / PTY / tmux / 実装語としての pane / `kind` ——
これらは**どう作られているか**であって、読者が見るものではありません。
`docs/build/` では使い、利用者向けの文書では
**読者が仕組みを訊いたときにだけ**補足します。

同じ規則が、人に話すエージェントにも当てはまります。「driver」ではなく
「実行方式」「マネージド」、「tmux セッション」ではなく「セッション」。

### 書き方の約束

- 画面上の名前は**リポジトリ**・**ファイル**・**セッション**のように書く。
- セッションの種別は `claude` / `codex` / `opencode` / `shell` / `ssm` と書く。
- 製品や話し手を指すときは Claude / Codex と書いてよい。
- ボタンは「Clone」、コマンドは `git clone` と書く。
- **アイコン**は絵だけの表示、**状態表示**は色つきの状態、**バッジ**は件数やペイン番号の
  ような小さな補助表示。

## 5. 二言語

英語が正（`X.md`）、日本語は隣（`X.ja.md`）。**同じ変更で両方を更新します**——
訳が古い棚は、訳が無い棚より悪い。

- H1 の直後の行が言語スイッチャで、**言語をまたいでよい唯一のリンク**です。
- 他の内部リンクは言語内で閉じます（`.ja.md` からは `.ja.md` へ）。日本語のみの区画
  （`log/`）へは、両言語とも同じターゲットを指します。
- `decisions/` も同じ条件で二言語です。ADR は追記型・不変なので、訳すのは翻訳であって
  書き直しではありません——決定・実測値・捨てた案の文言を、読みやすさのために
  変えないこと。
- UI ラベルは Console の文字列を引用します（英語は
  `console/src/lib/i18n/locales/en.ts`、日本語は `ja.ts`）。ボタンの訳を勝手に作ると、
  **画面上に存在しない言葉**を読者に探させることになります。

## 6. 同じことは `guide/ref/` に一度だけ書く

能力の事実——どのエージェントが何に対応しているか、どのプロバイダが、どのデプロイ形態が、
どのロールが何をできるか——は `guide/ref/` にだけ置きます。他の棚は表へリンクします。
**表が 2 つあるということは、片方はもう間違っている**ということです。

同じ問いが、利害の違う読者から届くからでもあります。「cursor は Plan モードに対応して
いる？」は、エージェントを選ぶメンバーからも、何を提供するか決める管理者からも、
8 つ目の種別を足す開発者からも来ます。棚ごとに答えの写しを持つと**必ずずれ、しかも
読者にはどちらが古いか分かりません**。

軸がコードに在る表は、コードと突き合わせます。エージェントの列は
`workspace/agent/internal/session/session.go` の `Kind*` 定数を、デプロイの行は
`control-plane/runtime.go` の `newRuntimeFactory` が受け付けるプロファイルを
覆っている必要があります。CI は**突合するだけで生成はしません**（表現は人が決める）。

## 7. `docs/log/` へリンクしない

`docs/log/` は凍結アーカイブです。現役の文書がそこへリンクするのは「本当の答えは
ジャーナルの中にある」と言うのと同じで、旧レイアウトが 3,400 行の作業ログに仕様を
埋没させたのはまさにこれです。**必要な事実は現役の文書へ転記し、実測はその場に書く。**
CI がこのリンクを弾きます。

## 8. 機能の完了条件

利用者から見える変更は、次が済むまで終わっていません。

1. `guide/ref/features.md` に行が在る。
2. 影響する読者の棚に節が在る。
3. 蒸し返され得る論点を決着させたなら、`docs/decisions/` に記録が在る
   （**何を退けたか、その理由も**）。

## 9. 棚ごとの担当

読者に見せる文書に「この棚には何を書くか」を書かないでください——それは書き手への
指示であって、読者への案内ではありません。**その取り決めはここに置きます。**

### `guide/member/` — Console からエージェントを動かす人

- **書く**: 手順（読者が実際にやる順番で）／画面・バッジ・メニューの意味／
  おかしく見えるときに何を試すか、「まだ動いている」と「止まっている」の見分け方。
- **書かない**: 能力の事実（`guide/ref/` にだけ置く）／画面に出てこないもの
  （env 変数名・内部の識別子・API パス・ソースのパス）／他人に影響する管理の話
  （`guide/admin/`）／配備を建てて維持する話（`guide/operate/`）。
- **更新トリガ**: 読者が気づく画面・導線・既定値の変更。**機能を出したのにこの棚が
  何も言っていなければ、その機能は完了していません**（§8）。

### `guide/admin/` — テナント管理者

- **書く**: メンバー・上限・監査・チーム共通の連携の運用手順。
- **書かない**: テナントをまたぐ設定（配備管理者のもの）。
- **更新トリガ**: テナント設定の画面と権限の変更。

### `guide/operate/` — 配備を建てて維持する人

- **書く**: 各手順が**何を決めているか**と、その判断の理由。
- **書かない**: コマンドそのもの——`deploy/` 配下の runbook が正で、この棚は写しません。
- **更新トリガ**: 手順の意味が変わる `deploy/` の変更。

### `guide/ref/` — 全員が引く能力表

- **書く**: 機能・エージェント・リポジトリ種別・デプロイ形態・ロール・設定・上限の表。
- **書かない**: やり方（リンク先の担当）／表が真であり続ける仕組みの説明（§6）。
- **更新トリガ**: 能力が増減したとき。軸がコードに在る表は CI が突き合わせます。

### `docs/build/` — コードを変える人

- **書く**: ワイヤ契約・責務・データの流れ・拡張の型。
- **書かない**: 利用者向けの手順（`guide/`）／日付つきの作業記録（`docs/log/`）。
- **更新トリガ**: 契約が変わったとき。
