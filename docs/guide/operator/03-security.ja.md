# 03. セキュリティ運用

[English](03-security.md) | 日本語

Agent Fleet を安全に運用するために、運用者が**理解しておくべき前提**と**日々行う統制**をまとめ
ます。ここは「隠れたバグの列挙」ではなく、**アーキテクチャに内在する性質を正直に開示し、運用で
どう扱うか**を示すものです。対外向けの脅威モデルは [SECURITY.md](../../../SECURITY.md)（英語）、
設計の背景は [dev/07 セキュリティ](../../dev/07-security.md) にあり、本書はそれを運用手順に展開します。

## 脅威モデル（要約）

Workspace の中では CLI エージェントが**任意コードを実行**します（`--dangerously-skip-permissions`
を含む運用が既定）。「ユーザーのセッションが untrusted なコードを動かす」前提で境界を引いており、
守る対象は「他ユーザーのデータ・CP/ホスト基盤・シークレット・情報持ち出し」です。主要な隔離境界は
**Workspace コンテナ（信頼度低）** と **CP/ホスト基盤（信頼度高）** の間にあります。

- **`docker.sock` = ホスト root 相当。** CP はマウントされた Docker ソケット越しにホストのデーモンを
  駆動し、Workspace 起動時に平文 DEK を注入します。そのため **CP かホストが侵害されると、その
  デプロイ内の分離は一括で破れます**。
- **会社間は別デプロイで分離。** 上記の影響は**そのデプロイ 1 つの内側に限定**され、他社（= 別
  デプロイ）には波及しません。これが 1 社 = 1 デプロイという提供モデルの核心的な強みです。

## 残存リスク 4 点（運用者は必ず理解する）

[SECURITY.md](../../../SECURITY.md) が挙げる 4 点を、運用の観点で展開します。これらは未開示のバグ
ではなく、現アーキテクチャに内在する既知の性質です。

1. **CP はホスト root 相当の権限を持つ。** 上記のとおり docker.sock 経由でホストを操作できます。
   運用: **ホストに SSH / sudo / docker を実行できる人を最小限に絞る**。Docker API の面を狭めたい
   場合は、ソケットをフィルタリングプロキシ（例 `tecnativa/docker-socket-proxy`）で前段する
   ハードニングが選べます。

2. **`AF_MASTER_KEY` が資格情報暗号の根。** すべての per-workspace DEK がこの鍵由来の per-tenant
   KEK で wrap されています。**失えば crypto-shred = 保存済み資格情報も全バックアップも永久に
   復号不能**。運用: **DB や home とは別の金庫に保管し、独立してバックアップする**。データ領域や
   バックアップアーカイブには絶対に置かない（設計上も入りません）。生成タイミングと保管は
   [01 §2](01-install.ja.md)、リストア時の同一性要件は [02](02-operations.ja.md)。

3. **バックアップは機微。** アーカイブには各ユーザーの home と**平文の Claude ログイン状態**が
   含まれます。運用: 保管先の権限（アクセスできる人を限定）と保存時暗号化（at-rest）を徹底する。

4. **docker.sock へのアクセス = ホストへのアクセス。** CP コンテナを実行できる人、あるいは Docker
   ソケットに到達できる人は誰でもホストを制御できます。運用: **誰がデプロイ／運用できるかを絞る**。

補足の限界: 現行の localCustodian は KEK が master 鍵由来のため、実効強度は単一 `AF_MASTER_KEY` と
同等です。テナント鍵の無効化による**真の per-tenant crypto-shred は将来の Vault/KMS custodian 採用時**
に達成されます（現状は設計のみ）。詳細は [dev/07 §7.6](../../dev/07-security.md)。

## egress 統制の運用

Workspace からの外向き通信（egress）を統制する仕組みがあります。**forward proxy 方式**で FQDN
（CONNECT/SNI）を見て allow/deny を判定し、TLS は復号しません。super_admin だけが Console の Admin
パネルの **egress** タブで操作します。

**段階的に入れるのが設計の核**です。次の順で進めてください。

1. **log-only（観測のみ・既定）** — 通信を遮断せず、宛先を記録するだけ。Admin の「観測された宛先」に
   ホストごとの許可/遮断候補件数が積み上がります。まずここで**実態を把握**します。
2. **allowlist を固める** — 観測結果を見ながら、正当な宛先を許可リストに追加していきます。許可
   リストは版管理され（active / proposed / retired）、AI は**提案のみ・承認は人間**が行います
   （Admin の「提案中（要承認）」で承認/却下）。
3. **enforce へ切替** — 許可リストが十分に固まってから、モードを enforce に切り替えます。以降は
   許可リスト外の通信を**遮断**します。Admin の UI も「先に log-only で実態を確認してから切替えて
   ください」と警告します。

> 現状の実装範囲: **観測（log-only）と許可リスト管理までが動作**します。実際の遮断（enforce）と、
> それに伴うコンテナ側の常時配線（内部網 + proxy env 注入）の有効化は**後続の作業で未完了**です。
> 今は「観測して許可リストを育てる」段階まで運用できる、と理解してください。設計の全体像は
> [dev/07 §7.8](../../dev/07-security.md)。

## MCP サーバーと外部接続

利用者は ⚙設定 →「MCP サーバー」で**自分の MCP サーバーを登録**でき、テナント管理者は
**全メンバーへ配布**できます（[admin/04](../admin/04-mcp-egress.ja.md)）。運用者として押さえる点は
4 つです。

- **秘密の置き場所。** 環境変数とヘッダの値は封筒暗号で保存され、サーバー起動時にだけ渡されます。
  設定ファイルに平文では残りません。
- **配布できるのはリモート（HTTP）だけ。** stdio の配布は「管理者が全員のコンテナで任意コマンドを
  実行できる」ことと等価になるため、仕様として禁じています（個人登録では stdio も使えます）。
- **egress と直結します。** 接続先ホストが許可リストに無ければ、登録しても動きません。利用者からの
  許可申請は Admin の egress タブに「提案中（要承認）」として届きます（上記の運用手順を参照）。
- **外部から入ってくる口もあります。** 利用者は「MCPトークン」を発行して、手元の Claude Code /
  Claude Desktop からワークスペースを遠隔操作できます。エンドポイントは `/mcp`（Bearer 認証）で、
  デプロイ側では機能フラグ（`AF_MCP_ENABLED`）と、ingress で `/mcp` を通すかどうかが効きます。
  スコープ（read / write / admin:dangerous）と有効期限は利用者が選び、失効も本人が行えます。

## ワークスペース内ブラウザの引き渡し

エージェントは、ワークスペース内で自分が起動した Chromium のページを Console のペインとして
利用者へ引き渡せます（ログイン操作などを人にやってもらうため）。remote debugging は
**loopback だけ**に開き、引き渡した直後は **view-only**（利用者の入力を一切通さない）から始まり、
操作を許すには明示的に user-control へ移す必要があります。CDP エンドポイントや cookie を
回答・ログ・コミットへ出さないことは、エージェント側の指示にも書かれています。

## その他の運用上の統制

- **ログイン許可リストは fail-closed。** `AF_OAUTH_ALLOWED_*` の 3 系統がすべて空で、**かつ
  membership を持つ人も自動参加ドメインも無い**場合、全ログインを拒否します。`_EMAILS_FILE` は
  ログインごとに再読込されるので、**追加は CP 再起動なしで反映**されます（削除も同様）。判定は
  ログイン時だけでなく**毎リクエスト**走るため、リストから外した人は `AF_SESSION_TTL` の満了を
  待たずに**次のリクエストで**締め出されます（＝これがオフボーディング経路）。
  設定は [01 §6](01-install.ja.md)。
- **招待されたこと自体が、ログイン画面に立てる資格になる。** 管理画面でテナントに追加された人は
  `AF_OAUTH_ALLOWED_*` に載っていなくてもサインインできます。招待運用のデプロイでは名簿が
  1 箇所（membership）に寄り、ずれる 2 つ目のリストを持たずに済みます。入口を通ることは
  「どこかに入れる」を意味しません — 使えるテナントの判定は別で、membership の無い人は
  従来どおり「管理者に依頼してください」の画面で止まります。
- **ログイン provider ごとに「その email をなぜ信じてよいか」を宣言させている。**
  `AF_OIDC_<ID>_TRUST`（`email_verified` または `issuer`）は必須で、宣言の無い provider は起動時に
  無効化されます — 許可リストがメールアドレスで書かれている以上、ここが認可の強度そのものだから
  です。特に Entra ID の issuer は自社テナント GUID に固定してください。`/common/` や
  `/organizations/` では Microsoft アカウントを持つ全人類がログイン画面に立て、個人アカウントは
  自分の email を付け替えられるため、`AF_OIDC_<ID>_ALLOWED_TIDS` が無い限り CP は起動を拒否します
  （[01 §3](01-install.ja.md) / [dev/07 §7.3](../../dev/07-security.md)）。
- **監査ログ。** 変更・破壊操作のみが `audit_log` に記録されます（読み取りは既定オフ、**ターミナルの
  生ストリームは秘密混入リスクのため保存しません**）。閲覧は super_admin / tenant_admin が Admin の
  audit タブから。運用上の見方は admin 分冊が扱います。
- **ベンダー製の同種機能を意図的に無効にしている箇所がある。** Claude Code 自身の
  cross-session messaging（`/list-agents` / `SendMessage`）は、**有効化すると Claude 側の
  利用統計送信（telemetry）も一緒に戻る**作りのため、セルフホストの既定として無効のままに
  しています。同じ用途は Agent Fleet 側の実装で提供し（設定 > エージェント > セッション間
  メッセージ・**既定オフ**）、そちらは配送も帰属もこちらの制御下にあります（届く相手は同一
  ワークスペース内に限られ、受信側には「利用者の指示ではない」と明示されます）。利用者から
  「`/list-agents` が使えない」と上がってきたら、故障ではなくこの判断です。
- **秘密をログに出さない設計。** CP は資格情報の平文を保持・解釈せず、ログにも出しません。統一
  cred helper が都度復号して渡すため、平文ファイルは作られません（[dev/07 §7.6](../../dev/07-security.md)）。

## オフボーディング — アクセスは実際どこで切れるか

入口が 2 つあるので、出口も 2 つあります。どちらを使うかは、そのデプロイが人をどう受け入れて
いるかで決まります。

| 入り方 | 外し方 | 効くタイミング |
|---|---|---|
| 許可リスト（`AF_OAUTH_ALLOWED_*`） | リストから消す | 次のリクエスト（判定は毎リクエスト） |
| テナントの membership（招待） | **管理 → 該当テナント → 該当メンバー → 「メンバーを外す」** | 次のリクエスト |

**セッションを個別に失効させる手段はありません。** セッション cookie は stateless（署名付きの
`{email, exp}` だけ・サーバ側にセッションストアが無い）なので「全端末からログアウト」も存在せず、
cookie 自体は最大 `AF_SESSION_TTL`（既定 7 日）有効なままです。実際に扉を閉めているのは上の
**毎リクエスト再判定**です。したがって:

> **IdP 側で無効化するだけでは足りません。** Microsoft / Google のアカウントを止めれば
> *新しい*セッションは取れなくなりますが、**すでにブラウザにある cookie は、許可リストまたは
> テナントから外すまで生き続けます。**

順序は次のとおり。**アクセスを切るのは 1 だけ**で、2 以降は後片付けです。

1. **membership を外す**（許可リスト運用ならリストから消す）。
2. **ワークスペースを停止**（管理 → メンバー詳細 → 「ワークスペース強制停止」）。
3. **home を掃除** — 本人に push させてから。`~/repos` は掃除後には戻せません。

退職してから気づくと手遅れになる非対称が 2 つあります。**事前に**知っておいてください。

- **定時実行は個人所有。** スケジュールは membership に紐づくので、その人が仕込んだものは
  **止まります**。引き継ぐ人が作り直してください。
- **内部 git リポジトリはテナント所有。** 人が抜けても残ります。作った人が辞めても失われません。

### 緊急停止 — `AF_COOKIE_SECRET` のローテーション

いま直ちに全員のセッションを無効化したい場合（cookie の漏洩、端末の紛失、連絡の取れない
アカウント）、即時に効く唯一のスイッチが cookie 署名鍵の変更です。

```sh
openssl rand -base64 32          # 新しい値を生成
# .env / oauth.env / SSM パラメータの AF_COOKIE_SECRET を差し替えて CP を再起動
docker compose up -d control-plane
```

旧鍵で署名された cookie はすべて検証に通らなくなるので、**全員がログアウトされ、再ログインに
なります**。乱暴で、全員に 1 回ずつのサインインを強いますが、秒単位で効くのはこれだけです。
ただし**これはアクセスを剥奪しません** — 許可リストや membership が残っていれば本人は再度
ログインできます。上の除外手順と**併用**してください（代わりにはなりません）。

## `super_admin` の移譲

`SUPER_ADMIN_EMAILS`（ホスト側の env）が「誰がこのデプロイの管理者か」の唯一の正で、
**起動時に 1 度だけ**読まれます — 変更には CP の再起動が要ります。Console から super_admin を
昇格させる導線は意図的に作っていません。デプロイ全体を動かせる権限は、そのホストのファイルに
触れる人だけが持つべきだからです。

1. `SUPER_ADMIN_EMAILS` を書き換え（後任を追加・前任を削除）、CP を再起動する。
2. 再起動時、CP は**リストに無い相手のロールを DB 側からも剥奪**します
   （`super_admin revoked (not in SUPER_ADMIN_EMAILS): …` とログに出ます）。これが無いと、
   前任のロールは DB に残り続けます — 素直な対処（ログイン時に同期）では、
   **もうログインしない退職者には永久に届かない**ためです。
3. 後任は初回サインインでロールが付きます。
4. そのうえで前任を上のとおりオフボーディングします（membership → 停止 → home）。

> 唯一の super_admin が引き継ぎ無しに抜けても復旧できます。ホストの env に触れる人が自分を
> 足して再起動すれば済みます。前提条件は **社内にホストへ触れる人が 1 人は居ること** だけ。
> 必要になる前に確認しておいてください。

## 脆弱性の報告窓口

脆弱性を見つけたら、**公開 issue を立てず**に非公開で報告してください。優先は GitHub の Security →
"Report a vulnerability"（非公開アドバイザリ）。報告に含める情報（対象バージョン/コミット・デプロイ
形態・再現手順・観測した影響）と対応方針は [SECURITY.md](../../../SECURITY.md) にあります。pre-1.0
のため、修正は最新タグに対して行われます。報告前に最新版へ更新してください。
