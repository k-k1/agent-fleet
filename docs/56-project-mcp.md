## 0. 目的 / 非目的

**目的**: 1 つの作業コピー（`~/repos/<name>`）の中に散らばった**プロジェクトスコープの MCP 設定**を
横断で 1 枚に見せ、指定したファイルの定義を同じリポジトリの別エージェントのファイルへ**利用者の
明示操作で**反映できるようにする。併せてプロジェクトスコープのエントリを追加・編集・削除できる。

**非目的**:

- **継続同期をしない**。正本を記録して追随させる仕組みは持たない（§5）。
- **AF レジストリ（docs/48）との相互取り込みをしない**。レジストリは全リポジトリに効く user スコープで、
  軸が違う（§11）。
- **ゲートを代行しない**。承認・`mcp enable`・trust は利用者が行う（§8）。
- プロジェクトスコープを持たない kind（agy）を無理に扱わない（§4.3）。
- MCP サーバーそのもののホスティング・接続テストの再発明（接続テストは docs/48 §10 を再利用しうるが v1 では出さない）。

## 1. 動機

`~/repos/novel-lab` は同じ 1 本の MCP サーバーを 2 つのファイルに**二重に**登録している。
どちらも **git 管理下**（`git ls-files` で確認）:

```jsonc
// .mcp.json（claude — copilot も同じファイルを読む）
{"mcpServers":{"syosetu":{"type":"stdio","command":"uv",
  "args":["run","--quiet","${HOME}/repos/narou-mcp-stdio/narou_mcp.py"],
  "env":{"SYOSETU_MIN_INTERVAL":"0.7"}}}}

// opencode.json
{"mcp":{"syosetu":{"type":"local",
  "command":["uv","run","--quiet","{env:HOME}/repos/narou-mcp-stdio/narou_mcp.py"],
  "environment":{"SYOSETU_MIN_INTERVAL":"0.7"},"enabled":true}}}
```

片方を直すともう片方が腐る。しかも**同じ意味の値の綴りが違う**（`${HOME}` と `{env:HOME}`）。
これは書き写しの誤差ではなく**CLI ごとに展開する構文が違う**からで（§2.1 で実測）、
「キーの詰め替え」だけの反映ツールを作ると**静かに壊れた設定を量産する**。

**このコンテナでの実地確認（2026-08-09）**: `~/repos/novel-lab` で各 CLI に聞いた結果、
syosetu が**実際に使えるのは opencode だけ**だった。claude は `.mcp.json` を読むが
**⏸ 承認待ち**、copilot も同じ `.mcp.json` から Workspace サーバとして拾う、
codex / cursor / kiro は**そもそもファイルが無い**（agy はプロジェクトスコープ自体が無い）。
7 種のうち 1 種でしか動いていない — この機能が埋めようとしている穴の実物。

この機能が直すのは次の 3 つ:

1. 同じサーバーが N ファイルに散り、**どれが最新か分からない**。
2. 反映しようとした人が**方言差を知らない**（`${HOME}` を opencode に貼っても展開されない）。
3. 書いた直後に**効いていないのに効いたと思う**（claude / cursor は承認待ち・§2.2）。

## 2. 実測

### 2.1 プレースホルダの方言（実測 2026-08-09・新規）

**測り方**: 隔離 HOME に stdio サーバーを 1 本書き、`command` は argv と env を追記するだけの
プローブスクリプトにする。CLI 自身の `mcp list`（claude / opencode / cursor）が接続を試みる時点で
プローブが起動するので、**プローブが受け取った argv と env の実値**を読む。codex は `mcp list` が
接続しないので、`mcp_config_drift_test.go` と同じ **app-server ＋ `thread/start`** に載せた
（認証不要 — MCP 子の spawn はモデル呼び出しの前に完結する）。

| kind | 版 | `${VAR}` | `{env:VAR}` | `${env:VAR}` | 測った層 |
|------|----|----------|-------------|--------------|---------|
| claude | 2.1.226 | **✔ 展開**（args / env 値とも） | ✘ 素通し | ✘ 素通し | user（`.claude.json`） |
| codex | 0.147.0 | **✘ 一切展開しない** | ✘ | ✘（`$HOME` も展開しない） | user（`config.toml`・app-server 経由） |
| opencode | 1.18.15 | ✘ 素通し | **✔ 展開**（args / `environment` 値とも） | ⚠️ **壊れる** | user + **project 両方** |
| cursor | 2026.08.04 | **✔ 展開** | ✘ 素通し | **✔ 展開** | user（`~/.cursor/mcp.json`） |
| copilot | 1.0.78 | **✔ 展開**（args / env 値とも） | ✘ 素通し | 未測 | 実ターン（`--additional-mcp-config`・0.36 credits） |
| kiro / agy | — | 未測 | 未測 | 未測 | — |

読み取れること:

- ⚠️ **どの 2 つを取っても構文が一致しない。** claude と cursor だけが `${VAR}` で重なるが、
  cursor はさらに VS Code 系の `${env:VAR}` も解釈する。**「そのままコピーしてよい組み合わせ」は
  claude → cursor の一方向しか無い**（逆向きは `${env:VAR}` が claude で素通しになる）。
- ⚠️ **`${env:HOME}` を opencode に入れると静かに壊れる。** 実測値は `$/tmp/…`（`{env:HOME}` の
  部分だけ展開され、頭の `$` が残る）。存在しないパスとして起動に失敗するのではなく、
  **`$` 始まりの別のパス**になる。エラーメッセージが原因を指さない類の壊れ方。
- ⚠️ **codex は何も展開しない。** `${HOME}` も `{env:HOME}` も `$HOME` も literal のまま子へ渡る。
  つまり**動機の実例（novel-lab の syosetu）は、値を実パスへ展開しない限り codex へは持って
  行けない**。これは本ツールの限界であり、UI が最初に言うべきこと（§9）。
- ✔ **`.mcp.json` を共有する claude と copilot は同じ方言**（どちらも `${VAR}` を展開し
  `{env:VAR}` は素通し）。**1 ファイルが 2 kind で同じ意味になる**ことを実測で確認した
  （2026-08-09 追測）。`copilot mcp list` / `mcp get` は接続を試みず、`mcp get` は展開前の
  文字列を表示するだけなので、**認証済みの実ターン**（`--additional-mcp-config` にプローブを渡し
  「ok とだけ返す」1 ターン・0.36 credits）で測った。プローブが受け取ったのは
  `args=/home/dev/A|{env:HOME}/B` / `env_V=/home/dev/E`。

### 2.2 プロジェクトスコープのゲート（実測 2026-08-09・新規）

同じプローブをプロジェクトスコープに置いて `mcp list` を走らせた:

| kind | 新規に書いた直後の状態 | 有効化に要るもの |
|------|----------------------|-----------------|
| claude | `⏸ Pending approval (run 'claude' to approve)` — **プローブは起動しない** | `claude` を起動して承認 |
| cursor | `probe: not loaded (needs approval)` — **起動しない** | `cursor-agent mcp enable <name>` |
| opencode | 即 spawn（プローブが起動した） | 無し |
| codex | （docs/48 §8.4 既測）`[projects."<dir>"] trust_level="trusted"` が無いと読まれない | trust |
| copilot | （docs/48 §8.4 既測）ゲート無し | 無し |

⚠️ **claude と cursor では「書いたのに何も起きない」が正常状態**であり、しかも **AF 自身も
`mcp list` で書き込みの成否を検証できない**（起動しないので接続結果が出ない）。反映結果の表示は
「成功／失敗」の 2 値ではなく、**「書いた」と「効いている」を別の行として出す**必要がある（§8）。

### 2.3 スコープの住み分け（docs/48 §8.4 の再掲）

| kind | プロジェクトスコープ | マージ | 同名衝突の勝者 |
|------|--------------------|--------|--------------|
| claude | `.mcp.json` | ✔ | user |
| codex | `.codex/config.toml` | ✔ | project |
| opencode | `opencode.json`（リポジトリ直下） | ✔ | project |
| cursor | `.cursor/mcp.json` | ✔ | project |
| copilot | `.mcp.json` / `.github/mcp.json` | ✔ | project |
| kiro | `.kiro/settings/mcp.json` | 未検証 | 未検証 |
| agy | **無し**（global 専用） | — | — |

本設計に効く点:

- **`.mcp.json` は 1 ファイルで 2 kind に効く**。したがって画面の列は **kind ではなくファイル**
  であるべきで、「反映先」を kind で数えると二重に書く事故になる（§9）。
- **claude 以外はプロジェクトが勝つ**。よって**プロジェクト側に `af` / `af_xxxxxxxx` という名前が
  あれば AF 自身の乗っ取り**であり（docs/48 §8.4）、この画面は**それを見つけられる唯一の場所**になる。
  副産物だが価値が高いので、v1 の警告に入れる（§7.3）。

### 2.4 git の無視設定と「切り離せるか」（実測 2026-08-09・新規）

§7.5 の「無視設定へ追加する」機能のために測った 4 つ:

| 測ったこと | 結果 |
|-----------|------|
| `.gitignore` は**追跡済み**ファイルに効くか | ✘ **効かない**。`.gitignore` に足しても tracked のままで、変更は差分に出続ける |
| `.git/info/exclude` は worktree 単位か | ✘ **common dir にある**（`git rev-parse --git-common-dir` = 親の `.git`）。**親クローンと全 worktree に効く** |
| opencode のプロジェクト設定は分割できるか | ✔ **`opencode.json` と `opencode.jsonc` を両方読んでマージする**（実測 2 サーバー）。**チーム分をコミットし、個人分を別ファイルにして無視する**分割が成立する |
| claude は分割できるか | ✘ `.claude/settings.local.json` に `mcpServers` を書いても**認識されない**（実測: `.mcp.json` の分だけが出る）。定義の置き場は `.mcp.json` 一択 |

⚠️ **動機の実例はこの 1 行目に当たる。** novel-lab の `.mcp.json` と `opencode.json` は
**既に tracked** なので、無視設定を足すだけでは何も起きない。実際に外すには
`git rm --cached` で追跡から外し、**コミットして push した時点で同僚の作業コピーからそのファイルが
消える**。無視の追加と追跡の解除は**別の操作・別の確認**にしなければならない（§7.5）。

⚠️ **`opencode.json` と `.codex/config.toml` は MCP 専用ファイルではない。**
opencode のプロジェクト設定にはモデル・エージェント・権限が、codex の
`.codex/config.toml` にも MCP 以外の設定が入る。**ファイルごと無視すると MCP 以外も一緒に消える。**
opencode は上表のとおり分割で逃げられるが、**codex には逃げ道が無い**（分割の口が無い）。
`.mcp.json` / `.cursor/mcp.json` / `.kiro/settings/mcp.json` / `.github/mcp.json` は MCP 専用なので
この問題が無い。

## 3. docs/48 §8.2 との関係 — 2 つの軸を分ける

docs/48 §8.2 の規約は「**af が書くのは user/global スコープだけ、プロジェクトスコープは利用者のもの**」。
本ツールはプロジェクトファイルを書くので、この一線に触れる。**規約は改訂せず、適用範囲を明確化する**:

| 軸 | 何 | 書き手 | 契機 | 所有 |
|----|----|--------|------|------|
| **配布軸**（既存・docs/48） | レジストリ → 各 CLI の user/global 設定 | af が**自動で**書く | agent 起動 / セッション起動 / CRUD / テナントポーリング | af（`mcp-managed.json` の台帳） |
| **管理軸**（本設計） | 作業コピーのプロジェクト設定 | af は**利用者の代理として**書く | **利用者の明示操作のみ**（自動契機はゼロ） | **利用者**（af は所有しない） |

§8.2 の文言は「af が**自動で**書くのは user/global だけ」と読み替える形で 1 節を足す。
`Materialize` / `MaterializeAll` はプロジェクトスコープへ一切触れない — この不変条件はテストで固定する
（新パッケージが `mcpreg.Materialize*` から呼ばれないこと、逆にプロジェクト側の書き込みが
セッション起動経路から呼ばれないこと）。

**所有マーカーを置かない。** 「af が書いた」印をファイルに残す案は採らない:

1. マーカーは「af が後で**自動的に**触るため」の仕組みで、自動で触らないなら用が無い。
2. プロジェクトファイルは**同僚も読む共有物**で、しかもコミットされる。AF 固有のキーやコメントを
   混ぜると、AF を使っていない人のリポジトリに痕跡と疑問を残す（`.mcp.json` は JSON なので
   コメントも置けない）。
3. スキーマ検証を持つ CLI で未知キーが警告になりうる。

**代わりに git が台帳になる。** 書いた後に何が起きたかは `git diff` が完全に記録する。
これは user スコープ（home 配下・バージョン管理外）では得られなかった保証で、
台帳とマーカーを不要にする根拠そのもの。UI は書き込み後に **SCM ペインへの導線**を出す（§9）。

⚠️ SVN 作業コピー（docs/41）では tracked 判定ができない。**「判定不可」を黄色の警告として扱い、
git と同じ強さの断定をしない**（§7.2）。

## 4. データモデル

### 4.1 スナップショット

新パッケージ `workspace/agent/internal/mcpproj/`。`mcpreg` に入れない理由は §4.4。

```go
// 1 つの作業コピーのプロジェクトスコープ MCP、まるごと。
type Snapshot struct {
    Repo  string        // ~/repos/<name>（作業コピー 1 つ。他の worktree は見ない）
    VCS   string        // "git" | "svn" | "none"
    Files []File
}

type File struct {
    Path     string   // repo 相対（".mcp.json" / "opencode.json" / ".codex/config.toml" …）
    Kinds    []string // このファイルを読む kind。".mcp.json" は ["claude","copilot"]
    Exists   bool
    Parsable bool     // 素の JSON / TOML として読めるか。読めないファイルは触らない
    Tracked  bool     // git 管理下か（秘密警告の判定に使う・VCS!="git" なら不定）
    Ignored  bool     // .gitignore にマッチするか
    Servers  []Server
    Note     string   // 読めなかった理由など
}

type Server struct {
    Name     string
    Transport string            // "stdio" | "http"
    Command  string
    Args     []string
    Env      map[string]string  // 値は Console へ出す時点でマスクする
    URL      string
    Headers  map[string]string  // 同上
    Extra    map[string]any     // 正規化で拾えなかった kind 固有キー（往復で失わないため）
    Span     [2]int             // ファイル内のバイト範囲（整形を壊さない編集に使う・§6）
}
```

### 4.2 `mcpreg.ServerDef` を再利用しない理由

形はほぼ同じだが、意味論が違う:

- `ServerDef` は「**AF が配るもの**」で、`ID` / `Origin` / `Targets` / `Enabled` を持つ。
  プロジェクト由来のエントリにこれらは無い。
- `mcpreg.Validate()` は `reservedNames`（`af` / `agent-fleet` / `af_xxxxxxxx`）を**弾く**。
  プロジェクト側では逆で、その名前は**弾かずに見つけて赤く出す**のが仕事（§2.3）。
- 同じ型にすると、実効レジストリの合成（docs/48 §4）や `ForSession` にプロジェクト由来が
  紛れ込む余地が残る。**紛れ込んだら user スコープへ配ってしまう**ので、型で隔てる。

一方 **綴り方（シリアライザ）は共有する**。`mcpreg` の `ClaudeServers` / `OpencodeServers` /
`cursorServers` / `copilotServers` / `kiroServers` と codex の TOML 生成は、kind ごとの
「エントリ 1 件の書き方」を既に持っている唯一の場所で、二重定義したら必ずドリフトする。
`mcpreg` 側に **kind → {シリアライザ, パーサ, ファイル名}** の 1 本のテーブルを export する
小リファクタを行う（docs/23 の「契約の型化」と同方向）。

### 4.3 パーサは新規

AF はこれまで各 CLI の形を**書く**コードしか持っていない。**ファイル → 中間形**の逆変換は新規で、
kind ごとに 1 関数。往復テスト（`parse(serialize(x)) == x`）で固定する。

v1 の対象:

| kind | ファイル | 読む | 書く |
|------|---------|------|------|
| claude + copilot | `.mcp.json` | ✔ | ✔ |
| opencode | `opencode.json` | ✔ | ✔ |
| codex | `.codex/config.toml` | ✔ | ✔ |
| cursor | `.cursor/mcp.json` | ✔ | ✔ |
| copilot（第 2 の場所） | `.github/mcp.json` | ✔ | ✔（存在する場合のみ・新規作成はしない） |
| kiro | `.kiro/settings/mcp.json` | ✔（同形と仮定） | **✘ v1 対象外** |
| agy | — | — | **プロジェクトスコープ無し** |

- **kiro を書かないのは、プロジェクトスコープの契約が未検証だから**（`mcp` 系が全てログイン必須で、
  マージするか・衝突の勝者・そもそも読むかが測れていない）。読み取りは「同形と仮定」で出し、
  行に**未検証バッジ**を付ける。書き込み先として選べない。
- **agy は行そのものを出す**（「このエージェントはプロジェクト設定を持ちません。global のみ」）。
  黙って一覧から消すと「対応漏れ」に見え、同じ質問が繰り返される。

### 4.4 対象は「選んだ作業コピー 1 つ」だけ

同じリポジトリの他の worktree は**列挙も編集もしない**。他の worktree は別セッションの机で、
そこに未コミットの変更を作るのは Workspace の運用規約に反する。

代わりに、対象が worktree のときは注記を出す:
**「これは worktree です。コミットするまで他の作業コピーには反映されません」**
— プロジェクトスコープの共有経路は AF ではなく git である、という事実の説明。

## 5. 操作モデル — 純粋なワンショット

- **正本を永続化しない。** 「どのファイルが正本か」は操作のたびに利用者が選ぶ。記録もしない。
- **ドリフト検出も追跡もしない。** モーダルを開いたその瞬間のスナップショットだけを見せる。
  差分の可視化はスナップショット内の比較（同名サーバーがファイル間で違う）に限る。
- **自動反映の契機はゼロ。** セッション起動・agent 起動・レジストリ CRUD のいずれからも呼ばれない。
- **マージ（衝突解決）は利用者が 1 件ずつ決める。** 反映先に同名がある場合、AF は自動で
  上書き・スキップのどちらにも倒さない。行ごとに「上書き / スキップ / 別名で追加」を選ばせる。

**plan → apply の 2 段**にする:

1. `plan`: 操作の列を受け取り、**書かずに**結果を計算する。返すのは (a) 各ファイルの差分
   （値はマスク）、(b) 警告（方言・秘密・ゲート・名前）、(c) `planHash`。
2. `apply`: 同じ操作列＋`planHash` を送る。**ファイルが plan 以降に変わっていたら 409**。
   作業コピーは他セッションや利用者本人のエディタと共有されているので、
   read-modify-write の間に人が編集しうる。ここを楽観ロックにしないと他人の編集を踏む。

## 6. 書き込み規約（プロジェクト版）

user スコープ（docs/48 §8.2）から**引き継ぐもの**:

- **読めないファイルは触らない。** 素の JSON / TOML として読めなければエラーで返し、上書きしない。
- **read → merge → 一時ファイル → `os.Rename`**（原子的）。
- **これから書く名前の既存エントリだけを置き換える。** それ以外のキーには触れない。
- codex の TOML は**行ベース編集**（パースして再出力するとコメントと `[projects."…"]` が壊れる）。

user スコープと**違うもの**:

- ⚠️ **整形を保存する。** このファイルは**コミットされる**ので、`json.MarshalIndent` で全体を
  書き直すと**差分が全行になる**。レビューできない diff を作る道具は使われない。
  → JSON も codex の TOML と同じ思想の**テキスト編集**にする。`encoding/json` の
  `Decoder.Token()` + `InputOffset()` で対象エントリのバイト範囲（`Server.Span`）を取り、
  **その範囲だけを差し替える**。追加は map の末尾に、既存の字下げ幅を検出して挿入する。
  これが本機能の実装コストの主要因（§12）。
- ⚠️ **モードは 0600 にしない。** 他人がチェックアウトするファイルで、しかも git はモードを
  `100644` / `100755` しか記録しないため、**0600 は原理的に守れない**。既存ファイルはモードを保ち、
  新規作成は 0644。**「user スコープの安全弁がここでは効かない」ことが、§7 の警告の根拠**。
- **所有台帳を持たない**（§3）。削除は利用者が選んだときだけ起きる。
- 新規作成するファイルの形は、その CLI 自身が作るものに合わせる（opencode の `$schema` など、
  既存 `jsonConfig.seed` と同じ考え方）。**書くものが無いのにファイルを作らない**。

## 7. 秘密

### 7.1 コピー元はプロジェクトファイルだけ

v1 の反映は **プロジェクトファイル → プロジェクトファイル**に限る。
AF レジストリ（user / tenant / builtin）を**コピー元にしない**:

- **tenant 配布の値をリポジトリへ吐き出せると、テナントの資格情報が git に載る**。
  docs/48 §5.2 は「メンバー本人が読める」ところまでしか許容していない。
- builtin の値は `mcp-run` ラッパーが暗号化ストアから解決するコンテナ固有のもので、
  リポジトリへ書いても他人の環境では意味を持たない。
- user origin の行をプロジェクトへ複製すると、**全リポジトリで効いているものが二重になる**
  — まさにこの機能が直そうとしている病気を増やす。

この 1 本の制約で、**秘密の新規流出は原則として起きない**（コピーされる値は元々そのリポジトリに
ある値）。残る唯一の新規流出経路は次項。

### 7.2 唯一の新規流出経路 — tracked 状態の差

コピー元が `.gitignore` 対象（または未追跡）で、コピー先が tracked なら、
**今まで git に載っていなかった値が載る**。警告はこの差で決める:

| コピー元 → コピー先 | 表示 |
|---------------------|------|
| tracked → tracked | 黄「値は既にコミット済みの内容です。複製先も履歴に残ります」 |
| ignored / 未追跡 → **tracked** | **赤「この操作で値が新たに git 管理下へ入ります」** |
| → ignored / 未追跡 | 情報「現在は git 管理外です」 |
| VCS が git でない（SVN 等） | 黄「バージョン管理の状態を判定できません」 |

加えて、**キー名と値の見た目**で秘密らしさを検出して赤を出す（`token` / `key` / `secret` /
`password` / `authorization` を含むキー名、高エントロピーな値）。既に git にあっても、
増やす前に気付かせる価値がある。

### 7.3 既定は「値を書かない」

利用者判断は「**警告の上でコピーを許可**」。これは次の形で実装する:

- **既定はキー名だけをコピーし、値は空にする**（`"V": ""`）。
- 値を持って行くには、**サーバーごとに明示チェック**が要る。チェックすると §7.2 の警告が出る。
- ⚠️ **Console は値を一度も受け取らない。** docs/48 §5.1 の「Console へは返さない」を維持する。
  スナップショット API は値を `***` にして返し、`apply` は `withSecrets: true` という**フラグだけ**を
  受ける。実値は Agent が自分でファイルから読んで書く。**これが §5.1 を壊さずに利用者判断を
  実装できる唯一の形**（Console 経由で値を運ぶと、Console が `***` を書き込んで壊すか、
  Console に平文を渡すかの二択になる）。
- ログ・監査・差分プレビューに値を書かない。差分では値を `***` にし、
  「値あり（非表示）」であることだけを示す。

### 7.4 名前の警告

- プロジェクト側に **`af` / `af_xxxxxxxx`** があれば**赤**。docs/48 §8.4 の乗っ取りが現に
  起きており、そのリポジトリのセッションでは自己申告・引き継ぎ提案・Chromium attach が
  死んでいる（claude 以外）。判定は `mcpreg` の `reservedNames` / `afNameRE` を再利用する。
- 新規に追加する名前が `mcpreg` の `nameRe`（`[a-zA-Z0-9][a-zA-Z0-9_-]{0,47}`）から外れる場合は
  **黄**。プロジェクトファイルは利用者のものなので**拒否はしない**が、codex の TOML bare key で
  破綻しうることは伝える。

### 7.5 git の無視設定へ追加する

§7.2 の警告は「この値は git に載る」と言うだけで、**その場で直す手段が無い**。
プロジェクト MCP のファイルはホスト固有の絶対パス（`${HOME}/repos/…`）や個人のトークンを
抱えがちで、「そもそもコミットしたくない」が正解であることが多い。
そこで **無視設定への追加を機能として持つ**。ただし §2.4 の実測から、**これは 2 つの別の操作**になる。

#### 操作 A: 無視に追加する（安全・取り返しがつく）

| 追加先 | コミットされるか | 効く範囲 | 既定 |
|--------|----------------|---------|------|
| `.git/info/exclude` | **されない** | ⚠️ **親クローンと全 worktree**（common dir にある・§2.4 実測）。「この作業コピーだけ」ではない | **✔ 既定** |
| `.gitignore` | **される** | リポジトリ全体＋**同僚全員**（PR に載る） | 選択 |
| global excludes（`core.excludesFile`） | されない | 全リポジトリ | **v1 では出さない**（§14） |

- 既定を `.git/info/exclude` にするのは、**コミットを増やさない＝取り返しがつく**方だから。
  `.gitignore` は「同じ判断をチームにも課す」操作なので、その旨を書いてから選ばせる。
- ⚠️ `.git/info/exclude` が worktree 単位ではないことは**必ず表示する**。ここを「この作業コピーだけ」と
  誤解させると、他の worktree で同僚…ではなく**自分の別セッション**が黙って影響を受ける。
- 書き方は行の追記のみ（憲章 4）。既に同じパターンがあれば足さない。末尾改行を保つ。
  **マーカーコメントは付けない**（憲章 2）。
- 対象は**その画面が扱っている実在のファイルだけ**。存在しないファイルを先回りで無視しない。

#### 操作 B: 追跡から外す（危険・別の確認が要る）

`.gitignore` は**追跡済みファイルに効かない**（§2.4 実測）。動機の実例（novel-lab）は
まさにこれで、A だけでは何も起きない。実際に外すには `git rm --cached <path>` が要る。

- ⚠️ **コミットして push した時点で、同僚の作業コピーからそのファイルが消える。**
  「無視した」の帰結としては重すぎるので、**A とは別のボタン・別の確認文**にする。
- **AF はコミットしない。** `git rm --cached` で index を変えるところまでを行い、
  コミットは利用者が SCM ペインで行う（憲章 2 の「監査は git」と同じ線。
  ステージされた削除は SCM ペインにそのまま出る）。
- `--assume-unchanged` / `--skip-worktree` は**使わない**。ローカルで「無視しているように見える」だけで、
  pull やブランチ切り替えで壊れ方が分かりにくい。**問題を隠すだけの逃げ道は提示しない**。

#### ファイルごと無視してよいか（kind で違う）

| ファイル | MCP 専用か | 無視の可否 |
|---------|-----------|-----------|
| `.mcp.json` / `.cursor/mcp.json` / `.kiro/settings/mcp.json` / `.github/mcp.json` | ✔ 専用 | そのまま無視してよい |
| `opencode.json` | ✘ モデル・エージェント・権限も入る | ⚠️ **分割で逃げる**: チーム分を `opencode.json` に残し、個人の MCP を `opencode.jsonc` へ移して**そちらを無視**する（§2.4 で両方読まれることを実測） |
| `.codex/config.toml` | ✘ MCP 以外も入る | ⚠️ **逃げ道が無い**。ファイルごと無視すると MCP 以外の設定も一緒に消える。その旨を書いて選ばせる |

claude は分割できない（`.claude/settings.local.json` に定義を書いても効かない・§2.4 実測）が、
`.mcp.json` が MCP 専用なので分割の必要が無い。

#### 誰が困るかを書く

無視は「自分が commit しなくなる」だけでなく、**チームがその設定を共有できなくなる**操作でもある。
リポジトリの `.mcp.json` を頼りにしている同僚がいるなら、無視ではなく**値の外出し**
（env 参照へ書き換える）が正解のこともある。UI はこの二択を並べて出し、AF はどちらにも倒さない。

## 8. ゲートの表示（代行しない）

反映結果は「書いた」と「効いている」を**別の行**にする（§2.2 の実測が根拠）。

| kind | apply 直後の表示 |
|------|-----------------|
| claude | ⏸ **承認待ち** — `claude` を起動して承認してください（`.mcp.json` の新規サーバーは承認まで起動しません） |
| cursor | ⏸ **未承認** — `cursor-agent mcp enable <name>` |
| codex | ⚠️ **trust 未設定なら読まれません** — `[projects."<dir>"] trust_level="trusted"`（`$CODEX_HOME/config.toml`） |
| opencode / copilot | ✔ 次に起動するセッションから有効 |
| 全 kind 共通 | **既に走っているセッションには効きません**（どの CLI も起動時に設定を読む） |

AF は承認・`mcp enable`・trust の**いずれも代行しない**。trust はエージェントが
「このディレクトリのコードとコマンドを信用してよいか」を利用者に問うている信頼境界で、
その回答を AF が代筆すると、AF を使うだけで信頼判断が省略されたことになる。承認系も同じ。
コマンドは提示するが、実行は利用者が行う。

⚠️ AF は書き込みの成否を `mcp list` で**検証できない**（claude / cursor は承認前に起動しない）。
「反映しました」と言い切らず、「書きました。有効化には次が要ります」と書く。

## 9. UI

### 9.1 入口はレポの右クリックメニュー

**レポ行（`RepoRow.tsx`）の右クリックメニュー → モーダル**を採る。
このモーダルは**プロジェクト単位ツールの共通の入口**（docs/57 §3）で、
本機能はその中の「MCP」セクション。2 号機以降は左レールに項目が増える形で生える。

- 対象が「1 つの作業コピー」であり、設定モーダルは workspace 全体（user スコープ）の場所。
  混ぜると**どちらのスコープを触っているかが画面から消える** — §3 の 2 軸分離を UI でも守る。
- レポの右クリックメニューには既に「変更を見る」「ブランチ」「掃除」など**リポジトリ単位の
  重い操作**が並んでいて、そこが自然な居場所。
- SCM ペインは「差分と履歴」の場所で、設定編集は異物。ただし **apply 後に SCM ペインへ誘導**する
  （§3 の「git が台帳」の帰結）。
- 設定モーダルの「MCP サーバー」タブ（`McpTab.tsx`）には**注記を 1 行だけ**置く:
  「プロジェクトスコープ（リポジトリの `.mcp.json` 等）はここでは扱いません → リポジトリのメニューから」。
  §8.4 の乗っ取りを疑った人が最初に探しに来るのはこのタブなので、行き止まりにしない。

### 9.2 モーダルの構造

`LaunchModal.tsx` の 3 層 IA に倣う。

```
┌ プロジェクト MCP — novel-lab (main)  [worktree 注記があればここ]
├ ① ファイル       .mcp.json [claude][copilot] ✔tracked [無視に追加…]   opencode.json ✔tracked
│                  .codex/config.toml (無し)  .cursor/mcp.json (無し)  agy: 対象外
├ ② サーバー × ファイル のマトリクス
│      サーバー      .mcp.json      opencode.json   .codex/…   .cursor/…
│      syosetu       ● stdio        ● stdio ⚠差分    ○           ○
│      af_1a2b3c4d   ● ⛔乗っ取り    ○               ○           ○
├ ③ 選択したセルの操作
│      [→ 他のファイルへコピー] [編集] [削除]      + [新規追加]
│      プレビュー（差分・値はマスク）
│      警告: ⚠️ ${HOME} は opencode では展開されません → [方言を変換して書く（推奨）]
│                                                        [そのまま書く] [実値へ展開して書く（非推奨）]
│      ⏸ claude は承認待ちになります
└ [キャンセル]  [適用]
```

- **列は kind ではなくファイル**（`.mcp.json` は 2 kind バッジを持つ 1 列）。§2.3 の帰結。
- ② のマトリクスが中心部品。動機（「二重に登録してあり片方が腐る」）に直接答える。
  `⚠差分` は同名サーバーの中身がファイル間で違うことを指す。
- ③ の方言選択は **AF が自動変換しない**（§5「マージは利用者」）が、
  **変換候補は AF が計算して見せる**。既定の推奨は「方言を変換して書く」。
  **変換できない組み合わせ（codex）は選択肢を出さず、理由を書く**（§2.1）。
- 「実値へ展開して書く」は**非推奨バッジ**。`/home/dev/...` をコミットすると他人の環境で壊れる。
- **無視の導線は 2 段**（§7.5）。① のファイル行の「無視に追加…」と、§7.2 の赤い警告の**隣**
  （そこが「この値は git に載る」と言っている当の場所）に出す。押すと追加先（`.git/info/exclude`
  既定 / `.gitignore`）と影響範囲を書いた確認を挟む。**追跡済みのファイルでは「無視だけでは
  効きません」を先に出し**、「追跡から外す（`git rm --cached`）」は別のボタンにする。
- **ワークスペース稼働ゲート必須**（docs/48 §11.1 と同じ理由 — 停止中は「設定ゼロ」に見える）。
- i18n（ja / en 両方・裸和文 AST lint が CI で落ちる）、キーボード操作体系（docs/29）、
  既存のモーダル作法（`useDismiss` / `useMenuRoving` / focus trap）に従う。

## 10. REST

プロジェクトファイルはコンテナ内のファイルなので **Agent 側だけ**で閉じる（CP は DB を持たない）。

| メソッド | パス | 役割 |
|---------|------|------|
| GET | `/repos/{name}/mcp` | スナップショット（§4.1・値はマスク） |
| POST | `/repos/{name}/mcp/plan` | 操作列 → 差分＋警告＋`planHash`（**書かない**） |
| POST | `/repos/{name}/mcp/apply` | 操作列＋`planHash` → 実行（不一致なら 409） |

操作列の形:

```jsonc
{"ops":[
  {"op":"copy",   "from":{"file":".mcp.json","name":"syosetu"}, "to":{"file":"opencode.json"},
   "as":"syosetu", "onConflict":"overwrite|skip|rename", "withSecrets":false,
   "dialect":"as-is|translate|expand"},
  {"op":"upsert", "file":"opencode.json", "server":{…}},
  {"op":"delete", "file":".mcp.json", "name":"old"},
  {"op":"ignore",  "file":".mcp.json", "where":"exclude|gitignore"},
  {"op":"untrack", "file":".mcp.json"}   // git rm --cached。コミットはしない
]}
```

`ignore` / `untrack` も同じ plan → apply に乗せる（差分と影響を先に見せてから実行する）。
`untrack` は index を変えるので、plan の差分には**ステージされた削除**として現れ、
`.gitignore` を選んだ場合はその 1 行も差分に出る。

⚠️ **新 REST は `workspace/agent/routes.go` と `control-plane/routes.go` の両方に登録する**
（CP は明示許可リスト方式。片方漏れると Console から 404 — docs/48 §6 の再発注意）。

拒否理由は **1 理由 = 1 コード**（`mcpproj.ValidationError.Code`）にし、Console は `err.<code>`
カタログで解決する。ja / en 両方に文言を足す。

## 11. AF レジストリとの関係（逆方向は v1 で作らない）

「プロジェクトの設定を AF レジストリへ取り込む」は**入れない**。理由:

- レジストリは **user スコープ = 全リポジトリのセッションに効く**。プロジェクト設定を取り込むと、
  そのリポジトリのためのサーバーが**他の全リポジトリでも起動する**。
- レジストリには「このリポジトリだけ」を表す概念が無い（`Kinds` で kind は絞れるが repo は絞れない）。
  取り込みを作るなら、まず `ServerDef` に repo スコープを足す設計が要る — それは別の決定。

代わりに、レジストリは**参照としてだけ読む**:

- 名前衝突（§7.4）の判定に使う。
- 「同じ名前が AF レジストリにもあります（全リポジトリで有効）」という情報行を出す。
  二重登録に気付ける。

## 13. 検証計画

- **往復（unit）**: kind ごとに `parse(serialize(x)) == x`。`Extra` に落ちた kind 固有キーが
  書き戻しで失われないこと。
- **整形の保存（unit・黄金ファイル）**: 1 エントリだけ変更したとき、**diff がそのエントリの
  行だけ**になること（キー順・インデント・末尾改行・既存のコメント（TOML）が保たれる）。
  ここが崩れると「レビューできない diff」になり、機能そのものが使われなくなる。
- **非破壊性**: 読めないファイルを上書きしないこと。手書きの他エントリを触らないこと。
  書くものが無いのにファイルを作らないこと。
- **楽観ロック**: plan 後にファイルを書き換えてから apply すると 409。
- **秘密**: 既定で値を書かないこと。**API 応答に平文の値が一度も出ないこと**（§7.3 — 独立した
  assertion にする。docs/48 §13 の「秘密が argv に出ないこと」と同じ強さで固定する）。
  tracked 差の警告判定（git / SVN / VCS 無し）。
- **無視設定（§7.5）**: 同じパターンを二重に足さないこと・末尾改行を保つこと・
  マーカーコメントを書かないこと。**追跡済みファイルでは「無視だけでは効かない」と返すこと**
  （黙って成功と言わない）。`untrack` が index だけを変え**コミットしない**こと。
  `.git/info/exclude` の書き先が **common dir**（worktree からでも親の `.git/info/exclude`）に
  解決されること — §2.4 の実測をテストで固定する。
- **軸の分離**: `mcpreg.Materialize*` がプロジェクトスコープへ書かないこと、
  `mcpproj` の書き込みがセッション起動経路から呼ばれないこと。
- **drift（実 CLI・build tag `drift`）**: §2.1 の方言表と §2.2 のゲート表を、
  今回の測定手法（プローブ + 各 CLI の `mcp list` / codex は app-server）でそのまま固定する。
  **CLI 版が上がったら赤くする**のが目的。`materialize_scope_drift_test.go` の隣に置く。
- **実描画**: headless Chromium ＋素の CDP（`console/scripts/shots/server.mjs` にスナップショットの
  スタブを足す）。マトリクス・警告・差分プレビューの 3 状態を目視確認。
