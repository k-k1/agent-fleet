## 背景

メンバーは Settings で AWS のプロファイルを定義し、`af-aws-exec --profile <name> --account <id> -- <command>` で任意のコマンドを
その 1 つとして動かせる。プロファイルはメンバーごとのブリッジで Workspace に届き、ラッパーは Workspace 自身のクラウドの ID を
コマンドから遠ざけ、ログインが無ければ Console がそれを仕上げる（[0102](0102-aws-login-through-the-console.ja.md)）。Google Cloud
にはこの種のものが何も無い。イメージに gcloud は無く、プロファイルもラッパーも無く、ポリシーの文章も Google の認証情報について
エージェントに何も教えない。Google Cloud 対応を求めた利用者（ADR 0106）は GKE を運用しており、今セッションから自分のプロジェクトを
運用するには、gcloud を手で入れ、ターミナルにログインを貼り付けるしかない。

### AWS から持ち込めるもの

- **ブリッジ。** メンバーシップごとの HMAC トークンを Workspace に注入し、取得のたびに生きたメンバーシップの照会とともに検証し、
  Workspace 専用 listener の許可リストに載せる（`aws_profiles_bridge.go`、`workspace_listener.go`）。整えた後に衝突する名前は、
  どちらの行も出さない。
- **Agent の取得ループ。** 起動時と 5 分ごとに、ロックの下で、CP に届かないときのためにトークンに結び付けたキャッシュを持つ
  （`internal/awsx/profiles.go`）。
- **0102 の Console ログインの骨組み。** ラッパーが出す要求、ペイロードが id だけの送り箱の通知、残り続ける toast、押下で始まり
  その id を押したタブだけが持つ試行、監査記録付きの CP の中継、待ってから終了コード 3 で終わる約束。そして 0102 の脅威モデルも
  一緒に持ち込む（下の決定 3）。
- **ラッパーの形。** コマンドへの `syscall.Exec`、非公開の状態ディレクトリ、`--list`、終了コード 2（使い方）、3（ログインが要り
  始まっていない）、1（拒否）。

持ち込め**ない**のは、AWS の認証情報の置き場を読むものすべてである。セッションごとの SSO キャッシュのファイル、その期限と
トークンのハッシュ、0102 の「解決した」の判定、期限の警告。gcloud は認証情報をプロファイルではなくアカウントをキーにした SQLite に
置く。Google Cloud のバックエンドは、それらの問いに自分のやり方で答えなければならない（決定 3）。

### gcloud が違うところ（実測）

- **ログインは逆向きに進む。** `gcloud auth login --no-launch-browser` は、リダイレクト先が
  `https://sdk.cloud.google.com/authcode.html` の `https://accounts.google.com/o/oauth2/auth?…` の URL を出し、「ブラウザに
  表示された検証コード」を stdin で待つ。メンバーは自分のブラウザでサインインし、**コードを貼り戻す**。URL は PKCE
  （`code_challenge_method=S256`）を持つので、コードはその URL を出した gcloud のプロセスでしか引き換えられない。URL に
  `login_hint` は無い。
- **`gcloud auth login <account>` はアカウントを強制する。** SDK はサインインしたメールを引数と比べ、何かを保存する**前に**断る
  （`WrongAccountError`）。そのアカウントの有効な保存済み認証情報があれば、URL を出さずにすぐ成功する（「Re-using locally stored
  credentials」）。
- **置き場はアカウントごと。** 認証情報は設定ルート（`CLOUDSDK_CONFIG`）の下の `credentials.db` と `access_tokens.db` に、
  アカウントをキーにして置かれる。名前付き構成（`configurations/config_<name>`）はプロパティだけを持ち、ログインは使った構成に
  `core/account` を書く。
- **構成名**は小文字で始まり、`a-z`、`0-9`、`-` だけでなければならない。`af-Prod`、`af-prod_app`、`af-prod.app` は断られる。
- **アクセストークンの上書きはすべてに勝つ。** `CLOUDSDK_AUTH_ACCESS_TOKEN_FILE` があれば、gcloud は構成のアカウントが何であれ
  そのトークンを使う。ラッパーの子に対してと同じく、ラッパーの呼び出し側に対しても。
- **`print-access-token` はキャッシュ済みのトークンを返す。** その残りの寿命は残っている分であり、今から 1 時間ではない。
- **Application Default Credentials は gcloud の設定ルートの外で見つかる。** Google の Go ライブラリ（`golang.org/x/oauth2/google`、
  `cloud.google.com/go/auth`）は `CLOUDSDK_CONFIG` にかかわらず `$HOME/.config/gcloud/application_default_credentials.json` を探し、
  それも無いときだけメタデータサーバに落ちる。Python の `google.auth` は `CLOUDSDK_CONFIG` に従う。
- **大きさ。** SDK は展開すると 486 MB（圧縮で 88 MB）。

## 決定

### 1. Google Cloud プロファイルはメンバーの Settings の行であり、Agent は自分専用の gcloud の置き場を持つ

Settings の AWS の隣に **Google Cloud** の欄を足し、AWS と同じくメンバー単位とする。プロファイルは次を持つ。

| 項目 | 必須 | 意味 |
|---|---|---|
| ラベル | はい | 表示名 |
| ログイン方式 | はい | `google`（Google アカウント）。最初の版の値はこれだけで、`workforce` は #1487 |
| プロジェクト | はい | コマンドが既定で向く資源のプロジェクト |
| クォータのプロジェクト | いいえ | 利用者のトークンで API のクォータを課金するプロジェクト。既定はプロジェクト |
| アカウント | いいえ | ログインする Google アカウント。設定すると gcloud がほかを断る |
| リージョン、ゾーン | いいえ | `compute/region`、`compute/zone` |
| なりすますサービスアカウント | いいえ | ログインしたアカウントを通してコマンドが振る舞うサービスアカウント。実用上の AWS のロールに当たる |

**名前。** プロファイルの名前はラベルから作る。小文字にし、`a-z0-9` 以外の文字の連なりを `-` に置き換え（先頭と末尾の `-` は
落とし、数字で始まるなら先頭に `p` を付ける）、ラベルの隣に表示する。名前が衝突するラベル（`Prod` と `prod`、`prod_app` と
`prod.app`）は、AWS と同じくどちらも出さず、Settings と `--list` がその理由を言う。`本番`、`開発`、`---` のように何も残らない
ラベルには、代わりに `p-` と行の id の短い安定したハッシュを使い、日本語のラベルでも使える名前になるようにする。Settings・ブリッジ・
`--list` は、正規化・空の名前の規則・衝突の規則を 1 つの実装で共有する。

CP には秘密を置かない。サービスアカウントの JSON 鍵はどこでも受け付けない。長寿命の秘密であり、禁じている組織が多く、なりすましが
同じ必要を満たす。

プロファイルは `GET /internal/gcp-profiles` を通して、専用のトークン（`AF_GCP_PROFILES_TOKEN`）で、Workspace 専用 listener の
許可リストに載って Workspace に届く。Settings のエクスポートとインポートは、AWS プロファイルと同じく追加のみで行を運ぶ。

**Agent は自分専用の gcloud の設定ルートを持つ。** 置き場は Agent の状態ディレクトリの下で、メンバーの `~/.config/gcloud` では
ない。メンバー自身の gcloud（そのログイン、使っている構成、その ADC）を、プロファイルが読むことも変えることも無い。両者が奪い合う
ファイルは無く、所有を推し量る必要も無く、取得がメンバーのターミナルを別のプロジェクトに切り替えることも無い。そのルートで各
プロファイルは名前付き構成 `af-<name>` になり、`--no-activate` で作る。ルートはまるごと Agent のものであり、プロファイルが消えた
構成は取り除く。

構成の中では、プロジェクト・クォータのプロジェクト・リージョン・ゾーン・なりすましは **Settings が持ち**、プロファイルがアカウントを
指定しないときの `core/account` は**ログインが持つ**。同期は前者を書き直し、後者を残す。プロファイルのアカウント、ログイン方式、
名前が変わったとき、あるいはプロファイルが作り直されたときは、その選択を初期化し、保留中の要求を捨てる。ログインが持つアカウントは
消え、次の実行でどのアカウントを使うかを尋ねる。これは認証のやり直しではない。置き場はアカウントごとなので、別のプロファイルですでに
ログインしているアカウントを指定した構成は、その認証情報をすぐに使える。

**Agent 自身が動かす gcloud の設定。** 上のプロファイルのプロパティとは分け、呼び出し側の変数を取り除いた後に適用する（決定 2）。
呼び出し側が何を設定してもこれは覆せない。

- `CLOUDSDK_CORE_DISABLE_FILE_LOGGING=true`。そうしないと gcloud は実行ごとに設定ルートの下へ DEBUG レベルのログファイルを書き、
  そこには `print-access-token` が出力したもの、ログインの URL、そしてコードの交換の中では要求と応答の本文まで入る（実測: ログに
  トークンが現れた。この設定ではログファイルは書かれない）。
- `CLOUDSDK_CORE_CHECK_GCE_METADATA=false`、そして呼び出し側の `GCE_METADATA_*` の変数は引き継がない。そうしないと、アカウントが
  選ばれていない構成は GCE では VM のサービスアカウントに落ちる（メタデータのモックで実測: 一度もログインしていない構成に対して
  `print-access-token` が VM のトークンを返した）。これは gcloud のプロパティであり、Google のライブラリのスイッチではない。

### 2. `af-gcloud-exec --profile <name> --project <id> -- <command>` は 1 つのプロファイルのトークンでコマンドを動かす

- **`--project` はプロファイルのプロジェクトと等しくなければならない。** AWS の `--account` は認証情報がどのアカウントに属するかを
  確かめる。Google の利用者のトークンはプロジェクトに縛られないので、これはそれより弱く、使い方の文章でそう述べる。確かめるのは、
  呼び出し側とプロファイルがコマンドの既定の向き先で一致していることである。コマンド自身の `--project` や、Terraform の構成に
  書かれたプロジェクトは、なお優先する。
- **トークンは選ばれたアカウントについてだけ発行する。** 構成はアカウントを持たなければならない。Settings からのものか、完了した
  ログインからのもので、その認証情報が Agent の置き場の利用者の認証情報であること。そうでなければラッパーは発行せず、ログイン要求を
  出す。VM やノードの ID を代わりに使うことは決して無い。
- **トークンはきれいな環境で発行する。** ラッパーは Agent の設定ルートに対して `gcloud auth print-access-token --configuration af-<name>`
  を（プロファイルが指定していれば `--impersonate-service-account` 付きで）動かす。その際、呼び出し側の `CLOUDSDK_*`、`GOOGLE_*`、
  `GCLOUD_*` の変数をすべて取り除く。そうしないと、引き継いだ `CLOUDSDK_AUTH_ACCESS_TOKEN_FILE` が、プロファイルが参照される前に
  その ID を置き換えてしまう。読む構成は決定 1 のプロパティだけを持ち、そこに見つかったほかのプロパティは次の同期が取り除く。
  stderr には、アカウント、なりすました主体（あれば）、トークンの残りの分数を出す。トークンは決して出さない。
- **コマンドが受け取るのはトークンだけで、メンバーのほかのものは受け取らない。** その環境は、呼び出し側のものから `CLOUDSDK_*`、
  `GOOGLE_*`、`GCLOUD_*` の変数をすべて取り除き、そのうえで次を設定したものである。
  - `CLOUDSDK_CONFIG` → 空の非公開ディレクトリ。`CLOUDSDK_AUTH_ACCESS_TOKEN_FILE` → トークンのファイル。
    `CLOUDSDK_CORE_DISABLE_FILE_LOGGING=true`。子の gcloud や GKE のプラグインの `config-helper` が、既定でトークンをログに写さない
    ようにする。
  - `GOOGLE_OAUTH_ACCESS_TOKEN` → トークン（Terraform の Google プロバイダ）。
  - `CLOUDSDK_CORE_PROJECT`、`GOOGLE_CLOUD_PROJECT`、`GOOGLE_PROJECT` → プロジェクト。
  - `CLOUDSDK_BILLING_QUOTA_PROJECT`、`GOOGLE_BILLING_PROJECT`、`USER_PROJECT_OVERRIDE=true` → クォータのプロジェクト。gcloud の
    OAuth クライアントから得た利用者のトークンは、API によってはそれを必要とするため（主体はそのプロジェクトに対する
    `serviceusage.services.use` が要る）。
  - リージョンとゾーンを `CLOUDSDK_COMPUTE_*` と `GOOGLE_*` の両方の形で。
  - `GOOGLE_APPLICATION_CREDENTIALS` → 非公開ディレクトリの中の、認証情報を持たないパス。トークンの変数を無視するクライアント
    ライブラリは、メンバーのよく知られた ADC のファイルを見つけたりメタデータサーバに手を伸ばしたりせず、**そのパスで止まる**。
    Go・Python・Node のライブラリでこれが失敗に倒れることは段階 1 で測る（未決事項 1）。
- **トークンの寿命は、発行されたときに残っていた分である。** 残りが 10 分を切っていれば、ラッパーはコマンドを始める前に gcloud に
  新しいトークンを発行させる。Agent が置き場を持っているので、そのアカウントのキャッシュ済みアクセストークンを落とせる。具体的な
  方法は段階 1 で測る。それでも得られなければ始めない。コマンドの途中で更新はしない。トークンより長生きするコマンド（長い
  `terraform apply`、`kubectl` の watch）は失敗する。更新は #1488。
- **GKE は最初から対象に入れる。** `install-gcloud` はコアと一緒に `gke-gcloud-auth-plugin` を入れ、ラッパーを通した GKE クラスタへの
  `kubectl` を段階 1 の完了条件に含める。プラグインは `gcloud config config-helper` を呼び、それはファイルからトークンを取る（実測。
  報告される期限は null なので、トークンが切れたときの kubectl の振る舞いも測る）。
- **終了コードと `--list` は `af-aws-exec` に従う。**

ラッパーが保証しないこと: コマンドはメンバーの uid で動き、メンバーの home（メンバー自身の gcloud のディレクトリを含む）を読める。
ラッパーは、標準の認証情報の探索が渡したトークン以外のものを見つけないようにするが、home を読めなくはしない。メタデータサーバに
届き、それを止めるものの無いホスト（GCE VM 上の `native`。ADR 0106 は扱っていない）では、`GOOGLE_APPLICATION_CREDENTIALS` を
迂回するライブラリはなお届きうる。notes はそう書く。そのようなホストでは gcloud のログインも、まず GCE VM 上で個人のアカウントを
使うかを尋ねる。Console のログインがそれに答えられるか、GCE 上の `native` はターミナルでのログインに任せるかは、段階 2 で決める。

### 3. ログインは Console が仕上げ、メンバーは自分で始めた試行にコードを貼り付ける

ターミナルが無いとき、`af-gcloud-exec` は `af-aws-exec` と同じくログイン要求を出す（0102 の決定 1、2、5、6。要求はプロファイル
ごとに 1 つ）。変わるのは、開始、送信、バックエンドである。

1. メンバーが toast か Settings で **ログイン** を押す。Agent はまずプロファイルを同期し直し、出されていないか隠されている
   プロファイルを断る（0102 で改訂した Settings の行の規則）。そのうえで、Agent の設定ルートで、きれいな環境（決定 2）で、自分の
   プロセスグループで、`gcloud auth login [<account>] --no-launch-browser --configuration af-<name>` を始める。試行はプロファイル
   ごとに 1 つ。プロファイルがアカウントを指定していれば必ず渡し、gcloud は別のサインインを保存する前に断る。Agent はログインを
   取り消すために何かを revoke することは決してしない。
2. gcloud が保存済みの認証情報ですぐ成功すれば、試行は URL 無しで完了として終わる。ただし、認証情報が拒否されたために出した要求
   （手順 5）は `--force` で始め、失敗したのと同じ認証情報を使い回さず、メンバーが本当に認証し直すようにする。そうでなければ Agent は URL を一度だけ解析し、
   スキームが `https`、ホストが厳密に `accounts.google.com`、`redirect_uri` がちょうど 1 つで厳密に
   `https://sdk.cloud.google.com/authcode.html`、userinfo・ポート・フラグメントが無い場合にだけ見せる。それ以外なら試行を終える。
3. 開始の経路は、押したタブに推測できない試行 id を返す。Console は、自分の押下への応答として受け取った試行に対してだけ URL と
   1 つの **検証コード** の入力欄を見せる。通知や一覧から試行を採ることはしない。
4. コードは、上限のある要求の本文でだけ、その試行の送信の経路へ送られ、CP が中継して監査する。Agent はそれを試行のロックの下で
   その gcloud の stdin に一度だけ書く。待っていない、取り消された、置き換えられた、すでにコードを受け取った試行への送信は断る。
   CP も Agent も通知も、コードや URL を記録しない。監査とログに残るのは、プロファイル、試行、呼び出しが中継を通ったかどうかである。
5. **要求が解決したかどうか**は、0102 のファイルのスナップショットではなく Google Cloud のバックエンドが決める。きれいな環境で、
   認証情報が見つからなかったために出した要求は、その構成について `print-access-token` が成功すれば解決である。それはローカルに
   認証情報があることを示すだけで、gcloud は Google に尋ねずにキャッシュ済みのトークンを返す。そのため、API がトークンを**拒否**した
   ために出した要求は、その後に完了したログインでだけ解決し、同じキャッシュ済みの認証情報が再び成功しても解決とはしない。Settings
   には、ログインが取り消されたとメンバーが分かっているとき用の **もう一度ログイン**（`--force`）を置く。何かがトークンを拒否する
   までは、Google 側での取り消しはローカルでは分からない。エラーは分類する。認証情報が無い・取り消された、`invalid_grant`、
   再認証の要求は「ログインせよ」を意味する。権限の拒否（なりすましを含む）、無効な API、ネットワークの失敗はそうではなく、役に
   立たないログインを求める代わりに、理由とともに要求を終える。要求を出した後で Settings でプロファイルが変わった要求は捨てる。

**何を守るかを、0102 と同じ言い方で。** Workspace のどのプロセスも `AGENT_TOKEN` を持ち、Agent の開始と送信の経路を呼べる。Agent は
メンバーの押下とそうした呼び出しを見分けられない。この設計が保証するのはもっと狭い。Console は、自分の押下への応答として受け
取った試行 id に対してだけ URL を見せてコードを受け付け、見せる URL は Google のものと照合してある。PKCE はコードを、それが来た URL を
出した gcloud に結び付けるので、コードはその試行にしか役立たない。だがそれは、誰がその試行を始めたかを証明しない。ガイドの規則は
そのまま持ち込む。**自分で始めたログインにだけコードを貼り付ける**。メンバーとして動く敵対的なエージェントは Agent の認証情報の
置き場を読み、gcloud のバイナリを置き換えられる。それは 0102 と同じく、ここで守れるものの外にある。

### 4. gcloud は必要なときに、版を固定して `~/.local` に入れる

`workspace-agent install-gcloud` は、固定した 1 つの版の SDK を、コアと `gke-gcloud-auth-plugin` のコンポーネントとともに、sha256 で
確かめて、停止と Recreate を越えて残る `~/.local` に入れる。`af-gcloud-exec` は初回にそれを動かす。版は `AWSCLI_VERSION` と同じく、
`versions.json` に記録され `readBuildPins` が読み戻す Dockerfile の `ARG` で、アーキテクチャごとのアーカイブ名と sha256 を持つ。
アーカイブ名は `x86_64` と `arm` を使うので、インストーラは `amd64` と `arm64` からそれに対応付ける。版の更新は AWS CLI と同じく
手で固定を変える。Toolchain タブの実効ツール版の表にそれを載せる。

イメージには焼き込まない。486 MB が、冷えたイメージの取得のたびに乗る。Fargate は起動のたびに冷えた取得をし、GKE はノードごとに
取得する。それを、一部のメンバーしか使わない道具のために負うことになる。

### 5. AWS の残りの面にも対応するものを用意し、notes はラッパーと一緒に出す

- **段階 1、ラッパーと一緒に:** `workspace/notes/gcp.md`（`af-gcp` スキル）と、`workspace/workspace-notes.md` のポリシーの項。既定の
  認証情報の連鎖はメンバーではない。メンバーのプロジェクトに関わることはすべて `af-gcloud-exec` を通す。自分で `gcloud auth login`
  を動かしたり Agent の置き場を変えたりしない。終了コード 3 はメンバーのログインが要るという意味。トークンがどのツールに届くか。
  トークンを決して出力しない。
- **段階 2、Console のログインと一緒に:** notes とガイドの貼り付けの規則、中継の監査。
- **段階 3:** Workspace のバーの AWS の隣の Google Cloud のバッジ、ガイドの連携と Settings のページを英語と日本語で。

### 対象外

- **Workforce Identity Federation。** Workforce プールの外部の主体が、Microsoft Entra ID などの IdP を通して
  `gcloud auth login --login-config` でサインインするもの。SAML で連携した Google Workspace や Cloud Identity のアカウントは普通の
  Google アカウントであり、対象に含まれる。#1487。ログイン方式の項目は、プロファイルの形を変えずにそれを入れるためにある。
- 長いコマンドのための**トークンの更新**。#1488。
- SSM のような**セッションの種類**（`gcloud compute ssh --tunnel-through-iap`）、**Google Cloud の MCP サーバ**、**サービスアカウント
  の鍵**（決定 1）。

## 却下した案

- **メンバーの `~/.config/gcloud` を共有する案。** 構成のファイルには AWS の管理ブロックのような境界が無い。Agent は自分のファイルと
  メンバーのものを見分けられず、取得がメンバーの使っている構成を切り替えうるうえ、メンバーがログインしているすべてのアカウントが、どの
  プロファイルからもプロパティ 1 つ先にある。
- **更新トークンを CP に保存し、そこでアクセストークンを発行する案。** CP をメンバーの Google の認証情報の置き場にしてしまう。
  AWS の設計が意図して避けたことである。
- **共有の置き場としての ADC**（`--update-adc`）。すべてのプロファイルで 1 つのファイルなので、「これは誰の ID か」が最後に走った
  ログインで決まってしまう。
- **アカウント違いのログインの後で認証情報を revoke する案。** gcloud はすでに保存の前に断り、置き場はアカウントごとなので、revoke
  は別のプロファイルが頼っているログインを取り消しうる。
- **gcloud をイメージに焼き込む案。** 決定 4 のとおり。

## 結果

- 2 つ目のクラウドの分の Settings・ブリッジ・ラッパー・ログイン・notes。要求と試行のライフサイクル、ブリッジのトークン、ラッパーの
  骨組みは、一度 `awsx` からプロバイダに依らないパッケージへ切り出す。認証情報のバックエンド（「ログインしている」「解決した」が
  何を意味するか、どのエラーが「ログインせよ」を意味するか）はプロバイダごとに持つ。
- Console のログインのモーダルに入力欄が増え、中継は要求の本文に、ログに残してはならない秘密を運ぶ。
- メンバーのターミナルの `gcloud` とプロファイルは別の世界になる。一方でログインしても他方ではログインしない。プロファイルを手で
  使う方法も `af-gcloud-exec` である。
- トークンより長生きするコマンドは、#1488 まで失敗する。

- **`gcloud --version` は無害ではない。** `CLOUDSDK_CONFIG` 無しで走らせると `~/.config/gcloud` を作り、そこへログファイルを書き、

## 注記 — 子の認証情報の無いパス、発行、構成（実測、2026-10-02）

Issue #1496。上の決定は何も変えない。段階 1 の Agent 側の実測を記録する。対象は未決事項 1 と、決定 2 の「どうやるかは段階 1 で
測る」である。あわせて実装上の選択を 2 つ記録する。

- **未決事項 1: 答えは「閉じて失敗する」。** 各ライブラリは、一時的な `$HOME/.config/gcloud` に合成した `authorized_user` の
  ADC ファイルを置き、`GCE_METADATA_HOST` / `GCE_METADATA_IP` / `GCE_METADATA_ROOT` で手元のメタデータのモックを指して走らせた。
  版は次のとおり。Go 1.26.8 と `golang.org/x/oauth2` 0.37.0・`cloud.google.com/go/auth` 0.24.0、Python 3.13.5 と
  `google-auth` 2.59.1、Node 22.23.3 と `google-auth-library` 11.1.0。
  先に陽性対照を 2 つ確かめた。`GOOGLE_APPLICATION_CREDENTIALS` が無ければ 4 つとも ADC ファイルを見つけ、ADC ファイルも
  無ければ 4 つともモックのトークンを取った。そのうえで `GOOGLE_APPLICATION_CREDENTIALS` を使える物の無いところへ向けた。
  4 つのコード経路はどれも、エラーを返し、モックへ要求を送らず、ADC ファイルを読まなかった。「使える物が無い」は 4 通り測った。
  - 空のプライベートなディレクトリの中の、存在しないファイル（ラッパーはこれを使う）
  - 空のファイル
  - ディレクトリ
  - 存在しないファイルに、空のディレクトリを指す `CLOUDSDK_CONFIG` を足したもの

  止めているのはこの変数で、`CLOUDSDK_CONFIG` ではない。`CLOUDSDK_CONFIG` だけを設定すると、Python と Node はホームの ADC
  ファイルを飛ばすがメタデータサーバーへ行く。Go の 2 つのライブラリは `$HOME/.config/gcloud/application_default_credentials.json`
  を読み続ける。どちらのライブラリも `CLOUDSDK_CONFIG` に触れていない。測っていないのは、Google へのトークン更新と、
  `PATH` に gcloud がある場合である。
- **発行には `gcloud auth print-access-token` ではなく `gcloud config config-helper` を使う。** 呼び出しの全体は
  `gcloud config config-helper --configuration af-<name> --min-expiry 10m --format json(credential.access_token,credential.token_expiry)`
  で、プロファイルが成り代わりを設定していれば `--impersonate-service-account` を足す。同じクリーンな環境で、Agent のルートに
  対して走らせる。587.0.0 で、合成したリフレッシュトークンと、手元のトークン・`iamcredentials` のモックを使って測った。
  - `print-access-token` はトークンだけを出して期限を出さないので、残り分数が分からない。成り代わりのトークンには、
    期限を記録する場所がそもそも無い。成り代わりの呼び出しは毎回新しいサービスアカウントのトークンを発行し、
    `access_tokens.db` に入るのは利用者のトークンだけである。
  - `print-access-token` がキャッシュ済みの利用者トークンを更新するのは、自前の約 5 分の窓の中だけである（閾値は 240〜320 秒の間）。
    残り 320・400・600 秒のトークンはそのまま返ってきたので、10 分の規則には別の手段が要る。
  - `config-helper` は 1 回の呼び出しでトークンと RFC 3339 の `token_expiry` を返し、成り代わりのトークンでも同じである。
    `--min-expiry 10m` は残り 10 分未満のキャッシュを更新する。残り 320・400・600 秒は更新され、900 秒は保たれた。
    `--min-expiry` は 1h を超える値を断る。無条件に更新するなら `--force-auth-refresh` がある。

  したがって「新しく発行させる」は `--min-expiry 10m` であり、gcloud のストアには書かない。発行後もなお残り 10 分未満のトークンや、
  `token_expiry` が無いか読めない出力は断る。JSON はメモリ上でだけ読む。書式の射影で `id_token` は落とし、エラーが出力を引用する
  ことは無い。2026-10-02 に利用者が承認した（親セッション経由）。
- **構成はファイルとして書く。** Agent は `gcloud config configurations create --no-activate` と `gcloud config set` を走らせず、
  `configurations/config_af-<name>` を直接書く。gcloud は手で書いたファイルを自分のものと同じに読む（`configurations list` と
  `config get` で実測）。`active_config` には触れない。これが `--no-activate` の目的にあたる。ファイルで書くので、5 分ごとの
  取り込みに gcloud のインストールは要らず、1 回約 1 秒の gcloud の起動もかからない。どの `core/account` がログインの持ち物かは、
  前回の同期の小さな記録（`gcloud/.agent-fleet-profiles.json`。名前ごとに id・ログイン方式・Settings のアカウント）から決める。
  実行が発行やログインをするのは、この記録とファイルのプロパティが、その実行が Settings から読んだプロファイルの版とちょうど
  同じときだけで、違えば断って再実行を求める。比べるのはプロパティで、バイト列ではない。ログインが `core/account` を書くとき、
  gcloud はファイルを自分の形に書き直すためである（実測。コメント行が消え、キーの順が変わる）。ターミナルでのログインは、
  この確認から発行の後までルートのロックを持つので、gcloud が書いている間に同期やほかの実行が構成を読んだり書き直したりする
  ことは無い。ログインの最中に Settings で変えた内容は次の同期が反映し、選択を元に戻す。
  Google が保存済みの資格情報を拒んだとき（`invalid_grant`、再認証）、ターミナルでのログインは `--force` を付けて走る。決定 3 で
  Console のログインがそうするのと同じである。付けないと `gcloud auth login <account>` は残り約 5 分を超えるキャッシュ済みの
  アクセストークンを使い回し（587.0.0 の `ShouldUseCachedCredentials`）、誰もサインインさせない。ログインが終わってもなお使える
  資格情報が無い実行は、3 ではなく 1 で終わる。
- **子からは `GCE_METADATA_*` も外す。** `CLOUDSDK_*`・`GOOGLE_*`・`GCLOUD_*` に加えて外す。メタデータサーバーを探しに行く
  ライブラリを、呼び出し元のメタデータのホストが操れないようにするためである。
