## 背景

Agent Fleet は、作業が `~/repos` の下の作業コピーで行われることを前提にしている。リポジトリを使わない
メンバーもいる。文書の下書き、スプレッドシートの集計、調べものをする人たちだ。そうした人がエージェントを
動かせる場所は今 2 つあり、どちらも合っていない。

- **「ホームでエージェントを起動」** はエージェントを `~` で動かす。出力はホームディレクトリに散らばり、
  ドットファイルやほかのセッションのファイルと混ざる。実測したあるワークスペースでは、`~` 直下に
  193 個の項目が散らばっていた（[log/116](../log/116-home-clutter-and-cache-growth.md)）。ホームでの起動では
  スキルは出ず、テンプレートもメンバー自身のものだけになる。
- **`~/.af-work/<session>`**（`paths.SessionWorkDir`）はセッションごとにあるが、エージェントの使い捨て
  置き場である。セッションを削除すると消え、アーカイブしてから 1 週間後にも消える。
- **`~/repos` の新しいフォルダ**（「新しいフォルダで始める…」）は、作業を **Recreate で消える** 場所に置く
  （[ガイド: 作り直し](../../guide/user/workspace/recreate.ja.md)）。git を使わないメンバーには、push 済みの
  控えもない。

答えの形を決めるのは、コードにある次の 5 つの事実である。

1. サーバーは `dir: ""` をホームディレクトリに解決する（`sessionx/session_create.go` の
   `resolveWorkingCopy`）。ホームのセッションを示すものはほかにない。
2. セッションの ID はディレクトリとスラッグから導かれ（`session.UUID(dir, slug)`）、Claude は作業ディレクトリから
   導いたパスの下に会話記録を保存する。**セッションのフォルダを移動・改名すると `--resume` が壊れる。**
3. 「その他のセッション」（`pj.other_sessions`）は受け皿である。フォルダ名（`sessionFolder`、`dir` の
   最後の要素）がどの作業コピーとも一致しないセッションをすべて並べる。ホームの shell、ホームのエージェント、
   リポジトリを消したセッションなどだ。フォルダ名だけでは、スペース `foo` とリポジトリ `foo` を見分けられない。
4. エージェントメモリーがプロジェクトに結びつけるのは `~/repos` の下のディレクトリだけである
   （`memoryx.agentMemProjectFor`）。その外のセッションにはメモリーのプロジェクトがない。
5. 作業コピーを削除すると、そこで開いた shell と SSM のセッションも削除される（ごみ箱に入る）。shell は
   開いた場所に結びついている。

## 決定

1. **スペースは `~/spaces/<folder>` に置く。** `~/repos`（Recreate で消える）でも、`~/.af-work`
   （セッションと一緒に消える）でも、`~` 直下でもない。Recreate では `~/spaces` は残る。Clean では、
   ホームディレクトリのほかのものと同じく消える。
2. **単位はセッションではなくスペースである。** 「はじめる」ハブは既定で新しいスペースを作り、既存のスペースを
   選び直すこともできる。何日にもまたがり、いくつものセッションにまたがる作業が 1 つのフォルダに収まる。
   セッションを削除してもスペースは残る。スペースを削除すると、今の作業コピーの削除と同じく、その中の
   セッションもごみ箱を経て削除される。
3. **スペースのフォルダは改名も移動もしない**（事実 2）。表示名はフォルダ名とは別に保存し、変えられる。
   フォルダ名は作成時に決まり、重複しない。
4. **「かんたんモード」は作らない。** 開発者もスペースを使う。リポジトリに入れない調べものや文書のための
   机として使う。メンバーごとの切り替えにすると、開発者からはスペースが、ほかの人からはリポジトリが隠れる。
   Console は、今もしているとおり（ADR 0081 決定 1、ADR 0140）、あるものと使えるものを見せる。メンバーは
   ビューを非表示にできる（決定 11）。
5. **「はじめる」ハブはアコーディオンにし、** いつも 1 つのセクションだけを開く。
   - *スペースで始める*: 指示の入力欄（「何をお願いしますか？」）、添付、場所チップ、最近使用したスペース
   - *リポジトリで始める*: 今のリポジトリ一覧
   - *その他*: 「ホームでエージェントを起動」、shell、「SSM — 別ホストへログイン」、
     「新しいリポジトリをクローン…」、「新しいフォルダで始める…」。今ハブにある行である。

   ハブは最後に開いたセクションを、左ペインの開閉状態と同じくユーザーとテナントごとに覚える。ハブへの入口は
   どれも（WS バーの「はじめる」、Alt+N、ホーム、メモから送る）そのセクションを開く。最初の 1 回は
   スペースが開く。**指示と添付はハブ全体で 1 つの下書き** で、どのセクションにも表示する。セクションを
   切り替えても文章はそのままで、開いたセクションの入力欄にフォーカスが移る。リポジトリの行は下書きを
   リポジトリの作業開始ダイアログに持っていく。*その他* では下書きを使うのはホームでの起動だけで、
   セクションにそう書いておく。
6. **「チャット（アシスタント）」の行はハブから外す。** アシスタントは自分のビューを持ち続け、会話は
   そのビュー、ホーム、初回の案内カードから始められる。
7. **起動の設定は層に分ける。**
   - 層 0: 何をするか（指示と添付）
   - 層 1、場所: 場所チップに出すのはスペースだけ（新しい・最近・すべて）。リポジトリは自分のセクションから選ぶ。
   - 層 2、「詳細」: エージェント、モデル、effort、実行方式、権限。**ブランチは入れない。** ブランチや
     worktree は場所の選択なので、リポジトリの作業開始ダイアログに残す。

   スペースでの起動は、2 つめのダイアログを挟まずにハブから直接始まる。リポジトリの作業開始ダイアログ
   （`LaunchModal`）は、リポジトリのセクション、リポジトリの行、ソース管理、作業項目、引き継ぎのために残し、
   *何を → どこで（作業コピー、ベース、ブランチ、サブフォルダ）→ 詳細* の順に並べ直す。ホーム用の形
   （「作業を始める: ホーム」）は *その他 → ホームでエージェントを起動* のために残す。

   *追記（2026-11-25、#5146）:* エージェント、モデルの経路、モデルは詳細から出て、最初の指示の真下にある
   2 行の「この設定で実行」帯に置く（ダイアログもハブのスペース用フォームも同じ）。順序は
   指示と帯 → 場所 → 詳細。経路も詳細から出る。起動ボタンにはエージェントとモデルの名前を出す。
   上の層の考え方はそのままにする。
8. **実行方式の既定。** マネージドの実行方式を持つハーネスは、スペースではマネージドで起動する。Claude には
   TUI しかないので TUI で起動し、そのペインはチャット表示で開く（`pane.content.chat`、今ある
   チャット / ターミナルの切り替え）。ターミナルにはボタン 1 つで戻れる。
9. **セッションビューのセクションは 3 つにする:** リポジトリ、スペース、その他。スペースとその他は、今の
   その他と同じく、空のあいだは出さない。リポジトリの空の案内（「リポジトリがありません」）は残す。
   スペースとリポジトリは、フォルダ名ではなくセッションのディレクトリのルートで見分ける（事実 3）。
10. **ターミナルビューに、すべての shell と SSM のセッションを並べる**（一覧なのでビュー: ADR 0140 決定 2）。
    - shell は開いた場所ごとにまとめる: ホーム、リポジトリ、スペース。データベースのタブが開く shell
      （`af-db connect`）はホームにまとめる。
    - SSM のセッションはマシンごとにまとめる: アカウント、リージョン、インスタンス ID。まとまりの名前は
      登録済みホストの別名で、一致するホストがなければインスタンス ID にする。プロファイルや run-as の
      ドキュメントの違いは、別のまとまりにせず行に表示する。
    - ビューのヘッダーから shell（ホーム、リポジトリ、スペースのどこか）や SSM のセッションを始められる。
    - セッションビューのリポジトリやスペースの行には、件数のチップだけを出す。チップを押すとターミナル
      ビューに切り替わり、その場所を開いて見せる。「ここでシェルを開く」はツリーの右クリックメニューに残す。
    - shell を開いても左ペインのビューは切り替えない（ADR 0140 決定 5）。
    - アイコンは最初からバーに出す。ハブの *その他 → shell* も残す。

    セッションビューには shell と SSM のセッションを出さなくなり、shell と SSM の「整理」の操作は
    このビューに移る。
11. **アクティビティバーに右クリックメニューを付け**（スマホは長押し、キーボードはメニューキー）、各ビューの
    アイコンの表示・非表示を切り替えられるようにする。表示中のビューと最後の 1 つは非表示にできない。
    使えないビュー（スケジューラがないときのスケジュール）は、理由を添えてグレーで出す。「既定に戻す」で
    初期状態に戻る。選択は Agent 側のメンバーの UI 設定に保存し、ブラウザが変わっても引き継ぐ。

## 段階

- **P1**: Agent がスペースを作成・一覧する（`~/spaces`、表示名を持つマーカーファイル）。ハブを共有下書き付きの
  アコーディオンにする。スペースでの起動は直接始まる。セッションビューにスペースのセクションを足す。
- **P2**: 最近使用したスペースと「既存のスペースを選ぶ」。添付をスペースにコピーする。スペースをごみ箱経由で
  削除する。`~/spaces` のホーム使用量のカテゴリ。ターミナルビューと、SSM のまとめ方に必要なワイヤの変更。
- **P3**: アクティビティバーの右クリックメニュー。未決の問い 1 と 2 の決定。ガイドのページ。

## 未決の問い

1. **スペースでの権限の既定。** (a) エージェントのいつもの既定。(b) スペースの中の編集は自動で許可し、
   それ以外は確認する。(c) 管理者が選ぶテナントの既定。推奨: (b) とし、(c) で上書きできるようにする。
   ただし、Claude の承認がすべてチャット表示に届くことが前提で、それは実際のセッションでまだ確かめていない。
2. **スペースのメモリーの範囲。** (a) 今のとおりメモリーなし。(b) メンバーのスペース全体で 1 つの共有
   プロジェクト。(c) スペースごとに 1 つのプロジェクト。推奨: (b)。スペースは短命なことが多く、(c) では
   メモリーが小さなプロジェクトにばらばらに散る。
3. **アイコンを非表示にしたビューのバッジ。** ADR 0140 決定 4 は、どのビューにもアイコンがある前提である。
   (a) バッジを出さない。(b) バーに点を出し、右クリックメニューでビューを示す。**決定: 待ちのバッジ
   （メンバーの返事で止まっているセッション）は (b)、新着は (a)。**
4. **SSM のまとめ方に必要なワイヤの変更。** 保存されたメタは SSM の接続先（`session.SSMMeta`: インスタンス ID、
   リージョン、アカウント ID、プロファイル）を持っているが、セッション一覧はそれを運んでいない。
   (a) 秘密でないこれらの項目を一覧に足す。(b) 表示名からまとめる。**決定: (a)。** 表示名は変えられるので、
   (b) はまとめる鍵にならない。

## 採らなかった案

- **スペースを `~/repos` に置く。** Recreate で消え、git を使わないメンバーには push 済みの控えがない。
- **`~/.af-work/<session>` を作業ディレクトリにする。** そこはエージェントの使い捨て置き場で、セッションと
  一緒に消える。2 つは分けておく: `~/.af-work` はエージェントの使い捨てファイル、`~/spaces` はメンバーの作業。
- **ホームでの起動だけで済ませる。** 散らかりを生んだのはそれである。
- **セッションごとに 1 つのフォルダに固定する。** セッションにまたがる作業が多くのフォルダに散り、フォルダの
  寿命がセッションの保持期間に引きずられる。
- **メンバーごとに選ぶ「かんたんモード」**（本人が選ぶ、管理者が選ぶ、リポジトリがないことから判定する）。
  開発者からスペースを隠し、git を使い始めたメンバーの前に段差を作り、中からは存在に気づけず、ガイドと
  テストが倍になる。
- **ハブのセクションをそれぞれ開閉できるようにする。** 開いているセクションの組み合わせをすべて設計する
  必要があり、下書きが閉じたセクションの中に隠れうる。アコーディオンなら覚える値は 1 つで済む。
- **場所チップにリポジトリも入れる。** ハブの中で 2 か所に出ることになる。
- **shell をセッションビューとターミナルビューの両方に出す。** 同じ shell が 2 回並ぶ。件数のチップで
  作業コピーとのつながりは見える。
- **スペースでは TUI を一切使わない。** Claude にはマネージドの実行方式がないので、スペースで Claude が
  使えなくなる。
- **データベースの shell に別のまとまりを作る。** セッションにはデータベースのタブから開いたという印がなく、
  数も少ない。それが変わるまでは行のラベルで足りる。

## 影響

- `~/spaces` はホームディレクトリの新しいデータである。ガイドの作り直しの表、設定 → マシンのホーム使用量、
  掃除のカテゴリに行が要る。
- 未決の問いが決まるまで、スペースのセッションにはメモリーも、作業コピーのスキルも、リポジトリのテンプレートもない。
- 「その他のセッション」に残るのは、ホームのエージェントと、リポジトリを消したセッションだけになる。
- 既存のセッションをスペースに移すこと、スペースをリポジトリにすること（ファイルを新しいリポジトリにコピーして
  そこで新しいセッションを始める。移動は `--resume` を壊す）は、この記録の対象外である。

## 追記：スペースの削除のしくみ（#4965 の 3 回目）

決定 2 は、スペースの削除をごみ箱経由で中のセッションごとと定めた。実装は次のとおり。

- **フォルダはアーカイブせず、移す。** ごみ箱の行は通常のアーカイブ（マニフェストだけで中身なし）で、フォルダはその
  隣に `<id>.space` として待つ。リネームなので、大きさによらずファイルの中身・権限・時刻がそのまま残る。tar にすると
  メモリに載せることになり、復元が読む 1 エントリの上限にも当たる。`~/spaces` とごみ箱が同じファイルシステムにある
  必要があり、何かを変える前に確かめる（ワークスペースのホームは 1 つ。違えば何も削除しない）。行を完全に削除すると
  フォルダも消える。
- **セッションは作業コピーの削除（ADR 0101 決定 4）に倣う。** 実行中かロック中のセッションがあれば削除を断る。停止中の
  shell / ssm を先にごみ箱へ移し（失敗すれば削除を止める）、次にフォルダを移し、そのあと停止中の AI セッションを棚へ
  移す。復元はフォルダを同じ名前で戻し（セッション ID と Claude の transcript のパスが保たれる）、棚に移ったセッションを
  戻す。その名前の場所に何かがあれば断る。
- **削除中のスペースでは、セッションを始められない**（作業コピーの削除と同じ「削除中」の印）。また、進行中の名前変更や
  添付のコピーが終わるのを待つ（`spacex` の読み書きロック）。

#5085 の未決のうち、これに関わるものの決着：

- *スペースがなくなったセッションへの貼り付け*（項目 2）。寿命は削除でつなぐ。Console から削除したスペースは中の
  セッションを一覧から外すので、貼り付けの宛先にならない。別の方法でなくなったスペース（掃除や手での削除）のセッション
  への貼り付けは、これまでどおり普通のアップロードで、保存先のパスだけを付けて 201 を返し、`spaceCopy` はなく、
  フォルダも作り直さない。テストで固定する。セッションの作成時にスペースを保存する案は要らない。
- *スペースへのコピーは `os.Root` で囲んでおり、成分ごとの `O_NOFOLLOW` ではない*（項目 3）。削除はコピーや名前変更と
  同じロックを取るので、この Agent 自身が起こす重なりは閉じる。アップロード中に同じ利用者の別プロセスが
  ワークスペースを書き換える前提の 2 つの組み合わせは、これまでどおり残す（そのプロセスは利用者の権限をすでに持つ）。
- *アーカイブしたセッションと「最近」の順*（項目 1）は変えない。削除したスペースは一覧から消えるので、失う順位がない。
