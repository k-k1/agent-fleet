## 背景

ADR 0128 で Bedrock に届くようになったのは、1 種類の資格情報だけである。メンバー自身の AWS プロファイルにモデルのルートの
印を付けたもの（決定 11、C2）で、Agent のルートゲートウェイが保持する（`workspace/agent/internal/routegw`、PR #3349、
#3389、#3400。受け入れ用のスイッチが #3417）。メンバーは SSO にサインインし、`bedrock:InvokeModel*` だけを持つプロファイル
に印を付け、起動ダイアログで選ぶ。AWS アカウントを持つメンバーにはこれが正しい道で、それ以外の人には向かない。

ユーザーが求めているのは、さらに次の 3 つである。

1. **ほかの誰かが提供するモデルへのアクセス。** (a) **テナント接続**: 管理者が一度だけ登録し、テナントが許したメンバーが
   使う。(b) **デプロイメントが提供する資格情報**: ECS-EC2、Fargate、EKS で、デプロイメントの AWS アカウントにある Control
   Plane 自身のタスクロールや IRSA の ID を使い、誰も鍵を保管しない。
2. **予算。** テナントがメンバーごとに予算（たとえば月あたり USD）を与え、呼び出しの前に強制し、メンバーに見せる。動機と
   なる使い方: メンバーのサブスクリプションのウィンドウが尽きたとき、しばらくテナントの Bedrock で続ける。
3. **メンバーごとの費用**を、トークン台帳（ADR 0029: 推定、リアルタイム）とクラウド費用（ADR 0048: コスト配分タグからの
   AWS 実費、約 1 日遅れ）の両方で見せる。

…しかも 1 つのハーネスに限らない。claude、opencode（ADR 0128 の P2c）、codex のすべてが、ADR 0128 決定 4 の許可リストを通
して同じ提供ルートに乗る。

ツリーがすでに言っていることと、設計を縛るもの:

- **ワークスペースにはわざと AWS の ID がない。** `awsx.IsolateWorkloadChain`（`workspace/agent/internal/awsx/workload.go:51`）
  は、何かを起動する前に ECS のコンテナ資格情報の変数を Agent の環境から消す。メンバーの資格情報がないビルドツールが、
  ワークスペースのタスクとして動く代わりに失敗するようにするためである。`WsTaskRole` にはポリシーが 1 つもない
  （`opencode/catalog.go:153-155`）。Control Plane が除外の `AF_WS_WORKLOAD_AWS=1` を渡すのは、運用者がそれを設定したとき
  だけである（`control-plane/workspace_lifecycle.go:563`）。したがってデプロイメントが提供する資格情報は「ワークスペースの
  ロール」にはなれない。あのロールは理由があってセッションから外されている。
- **同じ UID のプロセスは、持ち主のプロセスツリーを通して動ける。** #3389 はルートトークンを、Unix ソケットと
  `SO_PEERCRED` によってセッションの起動ペインのプロセスツリーに縛った。そのレビューは残りを受け入れた。同じユーザーの別の
  プロセスは、持ち主のペインに打鍵できるし、ptrace が許す所では注入できるし、接続済みのソケットを渡してもらうこともできる
  （ADR 0128 の 2026-11-06 の注記、「Still possible after this」）。資格情報がメンバー自身のものなら、それを悪用できるのは
  メンバーだけなので許せる。テナントやデプロイメントが払う資格情報では許せない。ワークスペース全体が Agent も含めてメン
  バーとして動くので、その中で強制する予算は、メンバーが回り込めるコードで強制されることになる。
- **Control Plane はすでにモデルの通信を中継している。** エンジンのゲートウェイ（ADR 0071）は `/engine/{key}/v1/*` を
  提供し、リクエストごとにセッショントークン、生きているメンバーシップ、テナントの関門を確かめ
  （`control-plane/engine_gateway.go:472-511`）、接続を追跡してメンバーの削除が流れているストリームを切れるようにし
  （`:497`）、各呼び出しの使用量を Agent の台帳に送る（`POST /engine/usage`、`control-plane/engine_usage.go:365`、
  `workspace/agent/engines.go:1439`）。そのトークンは、そのまま写してはいけない前例である（30 日、失効しない。ADR 0128 決定 7）。
- **今のメンバーごとの上限は数であって、お金ではない。** guide/admin/02-limits.md: super_admin はテナント全体の上限と
  エンジン利用のスイッチを決め、tenant_admin はメンバーごとのセッション上限、ワークスペースのサイズ、ロールごとのエンジン
  利用を決める。お金の上限はセッションごとの支出予算（#1054、ADR 0029 の 2026-10-04 の追補）だけで、セッション自身のトラン
  スクリプトを定価で値付けする。
- **ADR 0048 は共有費用を按分しない**（決定 4）。頭数で割った数字は実費ではなくなる。

## 決定

### 1. 言葉: 資格情報の出どころと、提供ルート

ルート（ADR 0128 決定 1）は**資格情報の出どころ**を持つ。誰が資格情報を登録し、誰が払うかを言う。

| 出どころ | 登録する人 | 払う人 |
|---|---|---|
| `member` | メンバー（設定 > AWS プロファイル/SSM で、モデルのルートの印を付ける） | メンバーの AWS アカウント |
| `tenant` | tenant_admin（テナント設定 > 接続） | テナントの AWS アカウント |
| `deployment` | 運用者（スタックのパラメータ）。super_admin がテナントごとに許可する | デプロイメントの AWS アカウント |

**提供ルート**とは、出どころが `tenant` か `deployment` のルートである。カタログ（ADR 0128 決定 3）はルート id ごとに資格
情報の層を 1 つ記録し、台帳のロールアップのキーは `Route` を持つ（決定 8）。そこで出どころは**それぞれ別のルート id** に
なる。`bedrock` はメンバーのもののまま、`bedrock-tenant` と `bedrock-deployment` を足す。これで新しいキー項目なしにすべて
のロールアップに「誰が払うか」が残り、セッションが目に見える停止なしに接続を移ることはないという決定 3 の規則も保たれる。

**提供された出どころは、#3400 がメンバーのプロファイルを縛ったように、生涯縛る。** 出どころの登録にはそれぞれ永続的な id と、
誰が払いどこへ呼び出しが行くかを決めるもの（ロールの ARN、外部 ID の版、リージョンの集合）にわたる**支払い元の
fingerprint** を持たせる。作成時に、セッションの選択を `<source id>#<fingerprint>` に縛る（`routes.BindAWSConnection` の形）。
CP ルートトークンと CP の資格情報キャッシュのキーはどちらもそれを持つ。fingerprint を変える編集は、縛られたすべてのセッ
ションを次の発行と次の呼び出しで拒否し（`route_connection_changed`）、再開、フォーク、作り直し、Agent の再起動で請求を
移すことはしない。古い fingerprint のキャッシュ済み資格情報は編集の時点で捨てる。モデルの許可リストや予算の変更は誰が
払うかを変えないので、fingerprint を変えずに、縛られたセッションの次の呼び出しから効く。許可リストには別に**ポリシーの版**
があり、資格情報のキャッシュはそれでもキーを分ける（D2 のセッションポリシーはそこから作る）。許可リストに足したモデルは、
キャッシュ済みの資格情報が期限切れになるまで拒否され続けるのではなく、次の呼び出しから届く。

### D1. 資格情報の 3 つの出どころ

- **D1a. どの出どころにも秘密を保管する**（アクセスキーか Bedrock の長期 API キーを CP の暗号化ストアに置く）。単純で、
  どのランタイムでも動く。長期キーは IAM ユーザーのものなので請求でメンバーを区別できず、CP はテナントが回さなければなら
  ない常設の秘密の保管者になる。
- **D1b. ID があるところでは秘密を保管しない** *（推奨）*:
  - `deployment`: CP 自身の ID（ECS のタスクロール `CpTaskRole`、`deploy/aws/ecs/cfn/20-platform.yaml:213`。EKS では IRSA）
    が、デプロイメントのアカウントにある**ルートロール**を引き受ける。ルートロールはスタックが D2 のセッションポリシーの
    最小権限の閉包だけで定義し、その信頼ポリシーは CP のロールに `sts:AssumeRole` と `sts:TagSession` を許す。何も保管しない。運用者はスタックのパラメータ（ロールの ARN と許すリージョン）で有効にし、出ど
    ころがあるかどうかはランタイムが宣言する。ADR 0048 決定 9 で費用の画面の有無を宣言するのと同じである。docker、native、
    CP が AWS の ID を持たない Kubernetes クラスタには、デプロイメントの出どころはない。
  - `tenant`: テナントの AWS アカウントにある**クロスアカウントのロール**で、デプロイメントの CP のロールを、**CP がテナント
    ごとに生成する外部 ID** つきで信頼する（AWS の
    [第三者アクセス](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_common-scenarios_third-party.html)の形）。
    CP が保管するのはロールの ARN、リージョン、外部 ID で、どれも秘密ではない。CP のロールにはそうしたロールへの
    `sts:AssumeRole` が要り、IAM が広がる。スタックはそれをロールのパス（たとえば `role/af-model-route/*`）に絞り、機能全体は
    運用者が有効にする。CP 側のクロスアカウントアクセスを望まないデプロイメントは、それを決して与えない。
    - **ID を生成しても、ロールがそれを要求している証明にはならない。** そうでなければ、テナント A は、条件なしに CP のロール
      を信頼しているテナント B のロールを登録し、CP に B のお金を使わせられる。そこで接続は **CP による 3 つの試しを通ってから
      有効になる**。このテナントの ID では AssumeRole が成功し、ID なしと、誤った ID（同じ形の乱数で、ほかのテナントの ID の
      代わりも兼ねる）では失敗すること。続いて D2 のセッションポリシーの下で最小のモデル呼び出しを 1 回行い、ロールがルートに
      要る権限を持つことを示す。どれかに外れた接続は無効のままで、外れた試しを名指す。ARN が変わるたびに同じ試しを
      やり直す。
    - 外部 ID は CP のものである。呼び出し側から受け取る API、Console のフォーム、インポートはない。tenant_admin にできるのは
      CP に回転を頼むことだけで、CP は新しい ID を発行し、その版を上げ（したがって fingerprint も変わる。決定 1）、ロールの
      信頼ポリシーを更新したうえで試しを通るまで接続を無効にしておく。
  - `member`: 変わらない（ADR 0128 C2）。メンバーの印付きプロファイルで、ワークスペースの Agent が保持する。
  - CP が AWS の ID を持たないデプロイメントのテナントは、代わりに Bedrock の長期 API キーを登録できるかもしれない（D1a の形
    で、テナントの出どころに限る）。これは未決の問い 1 で、推奨には含めない。
- **D1c. 提供された資格情報をワークスペースに持たせる**（`AF_WS_WORKLOAD_AWS=1` でデプロイメントのロールを、または Agent
  にテナントの鍵を）。退ける。`IsolateWorkloadChain` の理由を崩し、ほかの誰かが払う資格情報を、メンバーが握るコンテナに
  入れることになる（D2）。

どの出どころも、登録した人（`deployment` は運用者、`tenant` は tenant_admin）が決める**モデルの許可リスト**を持ち、ゲート
ウェイが各呼び出しの名指すモデル id に対して強制する。Opus と Haiku は値段が 1 桁違い、予算だけではテナントがどちらに払う
つもりだったかが分からない。

### D2. 出どころごとに、ゲートウェイをどこで動かすか

- **G1. どの出どころにも Agent のルートゲートウェイを使う**（今の `routegw` に提供された資格情報を渡す）。提供された出どころ
  には退ける。メンバーとして動くものはメンバーが読める。Agent のメモリと環境は同じ UID のもので、予算の確認はメンバーのコン
  テナの中のコードになる。#3389 の限界はメンバー自身のセッションどうしの話だが、ここではテナントやデプロイメントのアカウン
  トをさらすことになる。
- **G2. ハーネスが直接呼ぶ CP のゲートウェイ**で、CP が発行したベアラをペインに置く。払う側にとって弱いわけではない。G3 も
  Agent の発行用の資格情報が取り出されうることを受け入れているので、払う側を守るのはどちらでも CP の許可と予算である。退ける
  のは、メンバーの側で失うもののためである。ハーネスごとに出どころで変わる 2 つ目の設定の形（ソケットの代わりに遠隔の HTTPS
  ベース URL）が要り、ベアラが呼び出し元の束縛のないプロセス環境に置かれるので、1 人のメンバーのセッションどうしの最善の
  努力の隔離（#3389 が作ったもの）がなくなる。
- **G3. CP のゲートウェイを、Agent が中継する** *（推奨）*:

  ```
  harness ──Unix socket, route token (0128 P2b binding)──▶ Agent routegw
          ──AF_CP_INTERNAL_URL (else the public base), CP route token──▶ CP route gateway
          ──AssumeRole(source, membership) + SigV4──▶ bedrock-runtime.<region>.amazonaws.com
  ```

  - **3 つの出どころに、ハーネス側の取り決めは 1 つ。** ハーネスは同じソケットに同じ形のベアラで話し、違うのは Agent の上流
    だけである（`member`: その場で署名する。`tenant`/`deployment`: 中継する）。ADR 0128 の呼び出し元の束縛、即時の失効、
    10 分で更新されるトークンはそのまま保つ。
  - **CP ルートトークンとは何か。** CP が Agent のために発行し、セッションのためには決して発行しない。Agent 自身の CP 資格
    情報で求める（エンジンの `/internal/engine/token` の形、`engine_gateway.go:227`）。CP が署名し、メンバーシップ、セッション
    の名前と世代、ルート、縛られた出どころ（`<source id>#<fingerprint>`、決定 1）に縛る。寿命は短い（10 分。P2b と同じく、
    セッションの起動ペインが生きている間は Agent の掃除が更新する）。メンバーは原理的にはこれを、あるいは Agent の発行用の
    資格情報を取り出し、CP を直接呼べる。それを受け入れられるのは、**CP が境界であり、呼び出し側の言うことを何も信用しない**
    からに限る（次の項目）。そういう呼び出し側に対しては、Agent 側の確認は何も守らない。
  - **CP の署名の取り決め。** CP のゲートウェイはいくつかのモデル操作のためのゲートウェイであり、汎用の SigV4 や STS の代理人
    では決してない。テナントのロールは必要以上に広いかもしれず、それを狭めるのは CP 自身の規則である。
    - **ID は CP 自身の記録から取る。** メンバーシップは検証したトークンから、テナントとワークスペースはそのメンバーシップに
      ついての CP のデータベースから取り、予算のキー、`RoleSessionName`、セッションタグはそこから導く。呼び出し側が送るヘッダ、
      クエリパラメータ、本文の項目を ID として読むことはない。
    - **上流へのリクエストは CP が組み立てる。** ホストとリージョンは出どころの登録から、ロールの ARN と外部 ID は CP のデータ
      ベースから取る。呼び出し側が渡す URL、リージョン、ロール、外部 ID、タグは、無視するのではなく拒否する。呼び出し側の
      ヘッダで通すのは `content-type`、`accept`、名前を挙げた Bedrock のリクエストヘッダだけで（一覧は作るときに操作ごとに
      書く）、呼び出し側の `Authorization` は決して通さない。
    - **操作とモデルは Agent だけでなく CP でも確かめる。** 許すのは
      `/model/<id>/{invoke,invoke-with-response-stream,converse,converse-stream}` への `POST` と、Q7 からの
      `/openai/v1/responses` だけである。モデル id はパス（URL デコードは一度だけ）か、Responses では本文から取り、出どころの
      モデルの許可リストの項目と文字どおり一致しなければならない。許可リストの項目は基盤モデルとシステム推論プロファイルの
      id（`us.anthropic.…`、`global.openai.…`）で、ARN はすべて拒否する。ほかのアカウントのアプリケーション推論プロファイルや
      リストの外のモデルに、ARN を名指して届くことはない。
    - **セッションポリシーが、引き受けたどのセッションも**、許可リストの**最小権限の閉包**に狭める。AWS の前提条件
      （[推論](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-prereq.html)、[推論プロファイル](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles-prereq.html)、*ドキュメント*）から、
      API とモデルごとに作る:
      - 自分のリージョンで呼ぶ基盤モデル: その `foundation-model` の ARN に対する `bedrock:InvokeModel` /
        `bedrock:InvokeModelWithResponseStream`。
      - システム推論プロファイル: 同じ 2 つのアクションを、`inference-profile` の ARN **と**、そのプロファイルのすべての宛先
        リージョンの基盤モデルに（AWS: 「関連付けられた各リージョンの基盤モデルも指定しなければならない」）。後者は
        `bedrock:InferenceProfileArn` を条件にして、基盤モデルにはプロファイル経由でしか届かないようにする。前提条件が名指す
        所では、プロファイルに対する `bedrock:GetInferenceProfile` も。
      - `bedrock-runtime` の Responses（Q7）: さらに、Responses のページが推論の対象に加えて求める、アカウントの**既定の
        Project** に対する `bedrock:InvokeModel`。H が閉じる保存された状態の権限 `bedrock:GetInvoke`、`bedrock:CancelInvoke`、
        `bedrock:DeleteInvoke` は**決して**含めない。
      実効の権限はセッションポリシーとロール自身のポリシーの共通部分なので、**両方が**この閉包を許さなければならない。デプロ
      イメントのルートロールはちょうどこれで定義し、テナントのロールは少なくともこれを持たなければならない（D1 の有効化で
      モデルを 1 回呼ぶ）。CP の ID には、同じアカウントでもクロスアカウントでも、ルートロールへの `sts:AssumeRole` **と**
      `sts:TagSession` が要り、ロールの信頼ポリシーは両方を許さなければならない。正確な最小の集合はライブの関門で確かめ、
      それは**意図したこれらのポリシーで行い、デプロイする人自身の権限では決して行わない**。許可リストのポリシーの版が変わる
      とポリシーを作り直す（決定 1）。
    - **タグは帰属のためで、認可には決して使わない。** セッションタグは請求のためにある（D5）。AF の判断がそれを読み返す
      ことはない。
    - **CP は資格情報を決して返さず**、それを運ぶ上流のヘッダも返さず、記録にも残さない。
  - **CP での、呼び出しごとの確認の順序:** トークンの署名と期限。メンバーシップが生きていること。その出どころについての
    テナントの許可（D3）。メンバーの許可。縛られた出どころがまだあり、同じ fingerprint で有効であること。操作とモデルが上の
    取り決めを通ること。そのうえで予算の受け入れ（D4）。それからはじめて資格情報をキャッシュ（キーは出どころの id、
    fingerprint、許可リストのポリシーの版、メンバーシップ）から取り、リクエストに署名し、応答を読み取るたびにフラッシュして流す。エンジンのゲート
    ウェイがすでにしていることと同じである。
  - **2 種類の失効。** *信頼できる*失効は CP 自身のもので、Agent が何をしようと次の呼び出しで効く。テナントの関門が切られた、
    許可や予算が外された、出どころが消された・無効にされた・fingerprint が変わった、メンバーシップが削除された（これは、
    エンジンのゲートウェイと同じ接続の追跡、`g.mgr.memberConns.track`、`engine_gateway.go:497` で、流れているストリームも
    切る）、のいずれも。*ライフサイクルの*失効（セッションが終わった、世代が変わった）は、メンバーが握る Agent が求める
    ものである。トークンの中のセッション名と世代は Agent の主張で、エンジンの前例でも、発行者が証明するのはメンバーシップ
    であってセッションではない。したがってセッションごとの帰属と、1 人のメンバーのセッションどうしの隔離は、ADR 0128 と同じ
    く最善の努力にとどまる。**CP の境界はメンバーの許可と予算であり、それより細かくはない。**
  - **遅延** *（未計測）*: メンバーのルートより 1 ホップ多い（Agent → Bedrock の代わりに Agent → CP → Bedrock）。運用者が
    `AF_CP_INTERNAL_URL` を設定した所では（ADR 0106 決定 8）、CP はそれをワークスペースの起動のたびに渡し
    （`control-plane/workspace_lifecycle.go:647`）、このホップはデプロイメントのネットワークの中に収まる。そうでなければ公開
    のベースを通る。関門では、最初のトークンまでに増える時間を測る。
  - **ストリーミング。** 公開ロードバランサのアイドルタイムアウトは 60 秒である（`deploy/aws/ecs/cfn/30-ingress.yaml:501`）。
    そこを通るストリームが 60 秒何も送らなければ切られる。Bedrock のストリームがそれほど長く黙ることがあるか（たとえば長い
    拡張思考の間）は *未計測* である。そこで Agent は内部アドレスが渡されている所では必ずそれを使う。**リリースの条件は統計
    ではなく構造で決める**。デプロイメントが提供ルートを差し出すのは、Agent と CP の間のどのホップのアイドルタイムアウトも、
    CP が強制する上流の期限（D4）より長いときだけで、CP が許すどんな沈黙も経路より長くは続かない。試験には、期限の直前まで
    わざと黙る代役の上流を使い、ストリームが最後まで届けば合格、切られれば不合格とする。普通のライブのストリームは沈黙の上限
    の証拠にならず、その抜き取りでこの試験に替えることは決してない。ハートビートを認めるのは、ハーネスが無視すると証明できる
    ものを通信の形式が定めている所だけである（Responses の SSE のコメント行。Q7 で codex がそれを無視すると測れた場合）。AWS
    のイベントストリームには何も差し込まない。どちらも満たさないデプロイメント（参照スタックの 60 秒の公開の経路と、それより
    長い期限）は**提供ルートを差し出さない**。その組み合わせは文書に書くのではなく、拒否する。
  - **CP の容量** *（未計測）*: 流れている呼び出し 1 つにつき、CP の中で goroutine 1 つと接続 2 つを使う。流れるのはトークン
    なので帯域は小さい。CP の再起動やデプロイは流れているストリームをすべて切るので、ルートゲートウェイは停止時に新しい呼び
    出しの受け入れをやめ、受け入れ済みのものは期限まで終わらせ、切れたストリームはその予約額で精算する（D4）。メンバーごと
    の同時呼び出しの上限（D4）も CP の負荷を抑える。
  - **Fargate、ECS-EC2、EKS:** ワークスペースには AWS の ID がまったく要らないので、CP が ID を持った時点で、どのワーク
    スペースのランタイムでもルートが動く。Bedrock への出口は CP のもので、ワークスペースの出口制限の外にある（ADR 0069 の
    テナント層）。
  - **使用量。** 台帳はメンバーのワークスペースにあるので、メンバーごとの支出の正本は CP が持つ（D4）。Agent の `routegw` は、
    メンバーの呼び出しと同じく、同じ応答から中継した呼び出しの台帳の行を書き、両者は同じ呼び出し id を持つ。
- **G4. 専用のゲートウェイサービス**（別の ECS サービスや Deployment）。先送りする。デプロイの単位が 1 つ増え、CP が渡す
  資格情報も増えるのに、容量の問題は測られていない。G3 の関門で CP がストリームを運べないと分かったら見直す。
- **G5. メンバーごとに Bedrock の短期 API キーを発行し、セッションに渡す。** 退ける。Bedrock に直接届き、何時間も有効で、
  途中に予算の確認がないベアラになる。

### D3. 誰が何を使ってよいか

関門は ADR 0084 に従う。super_admin がテナントごとに、tenant_admin がメンバーごとに決め、メンバーが選ぶ。

| 誰が | `deployment` | `tenant` |
|---|---|---|
| 運用者 | デプロイメントでその出どころを有効にする（スタックのパラメータ: ロール、リージョン、モデルの許可リスト） | デプロイメントでテナント接続を有効にする（CP のクロスアカウントの権限） |
| super_admin | テナントごとに許可し、そのテナントの**月の上限額**を決める | テナントごとに「**テナント接続を登録してよい**」を許可する。上限額は決めない。払うのはテナント自身のアカウントだから |
| tenant_admin | メンバーごとの予算（テナントの既定とメンバーごとの上書き）と、エンジン利用と同じ「すべてのメンバー」/「許可したメンバーのみ」を決める | 接続を登録して有効にし（D1 の試し）、そのモデルの許可リストを決める。テナント全体の月の上限額を自分で決めてもよい（空 = なし）。あとは `deployment` と同じ予算と許可 |
| メンバー | 起動時か切替の提案（D6）で選ぶ | 同じ |

- **どの許可も新しい能力なので、既定は off にする:** ゼロ値が false の素の `bool` で、`AllowEngineIngest` の前例に倣う。
  nil が「許可」を意味する ADR 0084 決定 7 の `*bool` ではない（あちらは前からあった能力を守るもの）。アップグレードで何かが
  有効になることはない。テナントが払う場合でもテナントの出どころに super_admin の許可を置くのは、CP がテナントに代わって別の
  アカウントのロールを引き受け、その通信を運ぶからである。
- **予算がなければ使えない。** メンバーが提供ルートを使えるのは、その出どころについての super_admin の許可が on で、出どころ
  が有効で、そのメンバーの実効の予算が 0 より大きいときだけである。許可が on なのに `deployment` の上限額が空のものは、保存時
  に拒否する。空にできない上限という ADR 0128 B3 と同じ規則である。
- **ADR 0128 決定 12 が今も最初に来る。** どの作成の経路でも（Console、REST、MCP の `create_session`、新規・再利用・ローテー
  ションのスケジュール）、CP は、メンバーが使えない提供ルート — 許可が off、出どころがない・無効・fingerprint が変わった、
  予算が 0 — を名指す選択を、**ワークスペースを起こす前に**拒否する。未知のルートをすでに拒否しているのと同じである。下の
  確認は後ろの備えであって、その代わりではない。
- **ADR 0084 決定 8 の 4 か所が当てはまり**、関門は CP になる。(1) Agent の生きている種別カタログは、メンバーが使ってよいと
  CP の許可の答えが言うときだけ提供ルートを載せるので、起動ダイアログは拒否されるものを決して差し出さない。(2) CP は CP
  ルートトークンの発行を拒む。(3) CP のゲートウェイは呼び出しごとに拒む。(4) 許可や予算が変わったら、events のストリーム
  で Console に知らせる。1 が関門で（上の起こす前の拒否とともに）、2 と 3 は古い答えが握られている間の隙間を埋める。
- 許可、上限額、予算、接続の変更は監査の行を書く（ADR 0084 は limits のエンドポイントが何も書いていないことを見つけた）。
- ADR 0128 決定 12 は、テナント接続について許可とは所有ではなく利用だとすでに言い、テナントの管理者がルートを許可・拒否
  してよいかを未決にしている（その未決の問い 2）。提供ルートについてはこれで答える。許可と予算を通して、してよい。メンバー
  自身の資格情報のルートは、今と同じくテナントの管理の外に置く。

### D4. 予算

- **単位: Bedrock の定価での USD。** 台帳が `route.gateway` の行を値付けするのと同じ方法（`amazon-bedrock` の表）で値付け
  する。請求ではなく推定である。実費は 1 日遅れで届き（D5）、予算は呼び出しの前に答えなければならない。Console は、セッ
  ションの支出予算がすでにしているように「≈」を付けて書く。これで提供ルートについて ADR 0128 の未決の問い 5 に答える。
  予算はリアルタイムの推定を数え、実費はその横に見せ、決して予算に混ぜない。
- **期間: UTC の暦月。** Cost Explorer が報告する日の境目である。Console はリセットを見る人のローカル時刻で示す。
  **呼び出しは受け入れた月に属する。** 受け入れの月と価格表の版を呼び出しの予約に固定し、1 日の 0 時を過ぎて届いた精算も
  その元の月に入れ、新しい月の枠には決して入れない。
- **段:** テナントの月の上限額（`deployment` は super_admin、`tenant` は tenant_admin が任意で決めるもの）と、メンバーの月の
  予算（tenant_admin）。両方を確かめ、厳しい方が勝つ。メンバーの予算の合計は上限額を超えてよく、そのとき上限額が共有の枠と
  して働く。
- **呼び出し前の受け入れと、呼び出し後の精算** *（推奨）*。呼び出し後の計上だけでは、予算内で始まった呼び出しがすべて走る
  ので、超過は同時実行数と呼び出しの大きさに応じて増える。代わりに:
  - **予約は推定ではなく、証明された上限である。** CP がモデルと API ごとに計算し、強制する:
    - *出力:* リクエスト自身の上限 — Anthropic の invoke の本文では `max_tokens`、Converse では `inferenceConfig.maxTokens`、
      Responses では `max_output_tokens` — で、必ずあり、CP のモデル上限表にあるそのモデルの最大出力を超えないこと。上限の
      ないリクエストや最大を超えるリクエストは拒否する（どのハーネスも必ず送るかは、それぞれのハーネスの関門で確かめる）。
    - *入力:* 同じ表にあるモデルの固いコンテキストウィンドウ。リクエストの大きさは上限にならない。画像、文書、キャッシュ
      された接頭辞はバイト数に比例してトークン化されないし、勝手な呼び出し側が JSON を握っている。
    - *単価:* 課金されるどの区分も、当てはまりうるいちばん高い単価で数える — 入力はキャッシュ書き込みの単価（通常の入力より
      高い。`usage_price.go:54-66` は出どころが示さないとき 1.25 倍で値付けしている）、モデルに長いコンテキストの段があれば
      その段、出力はいちばん高い段。
    - 価格と上限の行がないモデルや、表が扱わない、値段を左右するオプション（たとえばサービスの段）を持つリクエストは、
      **拒否し、0 で値付けすることは決してない**。モデルの許可リスト（D1）に載せられるのは、両方の行があるモデルだけである。
    - その帰結は隠さずに書く。コンテキストが大きく値段の高いモデルでは予約 1 つが小さな予算の大きな割合を占めるので、月の終わり
      近くでは同時に走れる呼び出しが少なくなる。コンテキストウィンドウより厳しい入力の上限に替えてよいのは、その API で証明
      できたときだけである（たとえば、入力がすべて CP が正確に数えられる平文の本文）。抜き取りで測った比率では決してできない。
  - **全額が収まるときだけ受け入れる。** 呼び出しを受け入れるのは、メンバーの段とテナントの段の両方で
    `spent + reserved_in_flight + this_reservation ≤ budget` であり、メンバーの流れている呼び出しの数が上限（デプロイメントの
    既定値。*値は未計測*）より少ない間だけである。候補を数に入れ、予約がその値段の上限なので、**受け入れた呼び出しが支出を予算
    の先へ押し出すことはない**。残る超過は価格表や上限表の欠陥だけで、精算が予約を超えたときにそれと分かるよう記録する（そし
    て報告どおりに精算する）。予算の終わり近くでは、いくらか残っていてもメンバーは拒否される。メッセージはそう言う（「次の
    呼び出しは最大 $X かかりうる」）。
  - **受け入れは 1 つのトランザクションで、送る前に永続化する。** CP のストアの 1 つのデータベーストランザクションが、メン
    バーとテナントの期間の行と、メンバーの流れている呼び出しの数を更新し、呼び出しの予約の行（呼び出し id、メンバーシップ、
    テナント、縛られた出どころ、モデル、API、受け入れの月、価格の版、予約額、状態 `in_flight`、受け入れ時刻、CP のインスタン
    ス）を挿入する。条件は書き込みそのものに入れる（条件付きの更新か Postgres の行ロック。CP が 1 つのデプロイメントでは SQLite
    の単一の書き手）。同じ合計を読んだ 2 つのリクエストや、ロールアウト中の 2 つの CP が、両方とも通ることはない。そのトラン
    ザクションがコミットされるまで、Bedrock には何も送らない。
  - **精算はちょうど 1 回。** 1 つのトランザクションが行を `in_flight` から `settled` に移し、受け入れの月の枠の予約を最終額に
    置き換える。行がまだ `in_flight` であることを条件にするので、重複した精算（再試行、再生、2 つ目の CP）は何も変えない。
  - **最終額が値付けした使用量になるのは、終わりの合計が完全だと証明できたときだけである。** ストリームでない本文の全体、
    ストリームの最後のイベントの呼び出しメトリクス、Converse の `metadata` イベントがそれにあたる。それに満たないもの —
    `message_start` といくつかの `message_delta` の後で切れた Anthropic のストリーム、失敗したストリーム、使用量がまったく
    ないもの — は**予約額で精算する**。`routegw.usageObserver` は今、`message_start` / `message_delta` だけから `Known=true`
    を返す（`workspace/agent/internal/routegw/usage.go:236`）。台帳の推定の行にはそれでもよいが、精算には決して使わない。
  - **宙に浮いた呼び出しは控えめに精算する。** CP は上流の呼び出しごとに期限を設ける（デプロイメントの設定で、D2 の経路の
    試験が照らすのと同じもの）。CP のインスタンスがなくなったか期限を
    過ぎた `in_flight` の行は、掃除が予約額で精算する。CP が死んでも Bedrock がまだその呼び出しを走らせているかもしれないから
    である。予約を 0 に戻すことは決してない。
  - いったん受け入れた呼び出しは、予算を理由に切らない。ストリームを切っても、どのみち課金されるトークンが失われ、ハーネス
    のターンが壊れるだけで、全額が収まるときだけ受け入れるのでその必要もない。
- **尽きたとき:** CP はゲートウェイ自身の拒否で答える。**`x-should-retry: false` 付きの 503** で、P2b の part 2 で、Claude
  Code が再試行せずにゲートウェイのメッセージを一度だけ出すと測ったステータスである（ADR 0128 の 2026-11-06 の注記）。予算、
  使った額、尽きた段、リセットの日を名指す。Agent はそのルートに制限のエピソードを記録し（支出の制限。待って解けるのは期間
  の境目だけ）、セッションは失敗したターンの後で止まり、メンバーに通知する。**黙っているかどうかにかかわらずフォールバックし
  ない**（ADR 0128 決定 3）。Console はまだ使えるルートを並べた切替の提案（D6）を見せてよいが、メンバーが選ぶまで何も動かない。
- **メンバーに見せる**のは使う前と使っている間である。起動ダイアログと切替の提案は、提供ルートごとに残りの予算を示す。セッ
  ションが提供ルートに乗っている間、そのミラーは今の期間の支出を示す。メンバーの使用量のページには提供ルートごとの行がある。
  tenant_admin はメンバー詳細で、ほかの上限と並べて、各メンバーの予算に対する支出を見る。
- **ほかの上限はそのまま残り、それぞれ独立に効く。** セッションごとの支出予算（#1054）は引き続きセッションのトランスク
  リプトを値付けし、上限に達したターンの後で止める。ルートの予算は CP で呼び出しを拒む。先に当たった方が働く。メンバーごと
  のセッション上限とテナントの上限は数で、変わらない。管理者ガイドの「2 種類の上限」の節には、3 つ目の種類としてメンバー
  ごと・月ごとのお金である予算が加わる。

### D5. 費用: 台帳の推定とクラウドの実費

- **台帳（推定、リアルタイム）。** 中継した呼び出しは、メンバーの呼び出しがすでにそうしているように、ワークスペースの台帳
  に `feature=route.gateway` の行を 1 つ、`Route=bedrock-tenant` か `bedrock-deployment`、`Billing=metered` で書く。CP の支
  出の表は同じ呼び出しを同じ呼び出し id で持ち、予算と管理者の画面に使う。台帳はメンバーの写しで、強制するのは CP の方である。
- **実費: セッションタグによる IAM プリンシパルの帰属** *（推奨）*。CP はルートロールを（出どころ、メンバーシップ）ごとに一度
  引き受け、`RoleSessionName` をメンバーシップ id に、セッションタグを `af-membership`（メンバーシップ id）と `af-tenant`
  （slug）にし、資格情報を期限の 5 分前までキャッシュする（AWS のページが警告するとおり、STS の呼び出しはリクエストごとでは
  なくメンバーごとに 1 時間に 1 回）。すると各呼び出しはメンバーのタグを持つプリンシパルに課金され、費用はメンバーに**直接
  結び付く**。ADR 0048 の規則は見直さずに守る。頭数で割るものは何もなく、なぜかタグなしで走った呼び出しは「共有」に落ちる。
  - 値は ADR 0048 決定 3 がすでに選んだものである。不透明なメンバーシップ id（メールアドレスやそのハッシュは決して使わない）
    と slug（不明なら空にせず、付けない）。
  - *（未計測）* `af-membership` と `af-tenant` をリソースタグとして有効化した既存の設定が、**IAM プリンシパル**のタグとし
    ても効くか（請求のコンソールはコスト配分タグを種類「IAM principal」で絞り込むので、別の項目であることを示唆する）。また
    0048 の `ce:GetCostAndUsage` のタグでのグループ化が、プリンシパルタグの費用を同じキーで返すか。AWS は CUR 2.0 の
    `iamPrincipal/` 接頭辞の列と、Cost Explorer のプリンシパルタグでのグループ化を文書にしている。Q1 の受け入れ試験の呼び出し
    が最初のタグ付きの呼び出しになり、AWS がキーを見つけられるようになる。キーは Q2 のリリースの前に有効化する。キーは見つか
    ってからでないと有効化できず、有効化には遡及がないことを ADR 0048 が測っているからである。
  - **どこに出るか。** `deployment` の出どころの費用はデプロイメントのアカウントにあり、そこは 0048 の CP がすでに Cost
    Explorer を読んでいる。メンバー詳細に「デプロイメントの Bedrock でのモデル呼び出し」の行を、「ワークスペースに直接結び付
    く費用」の中ではなくその横に足す。`tenant` の出どころの費用はテナント自身のアカウントにあり、AF はそれを読まない。AF は
    台帳の推定だけを見せ、テナントが自分の請求を同じようにまとめられるようタグを文書にする。
  - **2 つを結ぶ。** 締まった日や月について、Console は推定と実費をそれと分かる見出しで並べて見せる。どちらも他方を補正しな
    い。予算は推定を数え続ける（混ぜないという 0048 決定 2 の理由）。
- **アプリケーション推論プロファイルの評価。**
  - *メンバーごと:* 退ける。モデルごと・メンバーごと・リージョンごとに 1 つで、クォータはリージョンごとに 1,000（引き上げ
    可）*（ドキュメント）*。メンバーシップと新しいモデルのたびに作って消す。CP には `bedrock:CreateInferenceProfile`、
    `TagResource`、`DeleteInferenceProfile` が要る。どのハーネスもモデル id としてプロファイルの ARN を送らなければならない。
    Responses はそれを拒むので、codex はまったく使えない *（ドキュメント）*。そして AWS 自身の規模の注意書きが、ユーザーごと
    の費用には代わりにプリンシパルによる帰属を勧めている。
  - *テナントごと:* 帰属のためには要らない。`af-tenant` のセッションタグがすでにテナントで切り分ける。プロファイル単位の
    CloudWatch のメトリクスを望むテナントのための選択肢として残す（未決の問い 5）。
  - *リクエストごとのメタデータ:* 呼び出しログにしか届かない *（ドキュメント）*。台帳がすでに各呼び出しを記録している。使わない。

### H. 提供ルートでのハーネス、通信、モデル

提供ルートには、メンバーのルートと同じハーネスの行を通って届く（ADR 0128 決定 4 と 5）。出どころはハーネスが話すものを
変えない。どの行も、これまでどおり決定 14 のライブの関門を通って初めて出す。

| ハーネス | ゲートウェイに話すもの | 上流の Bedrock API | 意味のあるモデル | 変換 |
|---|---|---|---|---|
| claude | `ANTHROPIC_UNIX_SOCKET` 越しの `ANTHROPIC_BEDROCK_BASE_URL` への Bedrock InvokeModel（`invoke-with-response-stream`）、ベアラは `AWS_BEARER_TOKEN_BEDROCK` から（代役を相手に測った。ADR 0128 P2b part 2） | 今と同じ `bedrock-runtime` の invoke | Anthropic のモデルだけ（CLI 自身のもの） | なし |
| opencode | 自前の `amazon-bedrock` プロバイダ。入っている v2 系（v2.2.5）向けの [v2 のプロバイダのページ](https://dev.opencode.ai/v2/docs/providers/)は、AWS の既定の資格情報チェーン、Bedrock API キー用の `AWS_BEARER_TOKEN_BEDROCK`、プライベートなエンドポイント用の `providers.<id>.settings.baseURL` を文書にしている。資格情報の出どころの間の優先順位は書いておらず、リージョンだけではプロバイダが有効にならないと書いている。より強い記述（ベアラがほかのどの方法よりも優先される、`endpoint` が `baseURL` の別名である、モデル id に推論プロファイルの ARN を使える）は [v1 のプロバイダのページ](https://opencode.ai/docs/providers/)にしかないので、v2 では前提にしない。入っている版で、どの API を呼ぶか（Converse か Invoke か）、ベアラだけで有効になるか、`baseURL` がゲートウェイを受け付けるか、Unix ソケットを使えるかは、どれも Q6 まで *未計測* | それを送るのであれば Converse / ConverseStream（ゲートウェイの許可リストにすでにある） | Converse が提供するもの全般: Claude、Converse 対応の GPT モデル、`gpt-oss`、ほか | なし |
| codex | `base_url` をゲートウェイに向けたカスタムの `model_providers.<id>`、`wire_api = "responses"`（「唯一サポートされる値」と文書化）、ベアラは `env_key` か `auth.command`（ベアラを出力するコマンドで、既定では 5 分ごとに更新）から。[設定リファレンス](https://developers.openai.com/codex/config-reference)による *（ドキュメント）*。Unix ソケットへの対応は *未計測* | `bedrock-runtime` の Responses（`/openai/v1/responses`）。ゲートウェイの許可リストにその `POST` 1 つを足す | `bedrock-runtime` で Responses に対応する OpenAI の GPT モデル（システムプロファイル `us.openai.…` / `global.openai.…` で名指す）。Bedrock に Responses API がない **Claude は不可**。そこでの **`gpt-oss` も不可**で、その Responses API は `bedrock-mantle` だけにある（[API compatibility](https://docs.aws.amazon.com/bedrock/latest/userguide/models-api-compatibility.html)、*ドキュメント*） | なし（下記） |

- **ゲートウェイでプロトコルを変換しない** *（推奨）*。codex の Responses を Converse に変換すれば codex で Claude を動かせ
  るが、範囲が広く（ツール呼び出し、推論の項目、ストリームのイベントの形、保存される状態）、codex のリリースのたびに動き
  うるし、codex のプロンプトとツールは OpenAI のモデル向けに調整されている。Bedrock で Claude を使いたいメンバーには claude
  と opencode がある。各ハーネスは自分の通信が届くモデルだけを持ち、起動ダイアログはそれだけを差し出す。
- **codex の組み込みの `amazon-bedrock` プロバイダ**は、AWS のプロファイルとリージョンで文書化されている
  （`model_providers.amazon-bedrock.aws.profile` / `.region`、*ドキュメント*）。`AWS_BEARER_TOKEN_BEDROCK` も受け付けるかも
  しれない。退けはしない。証明されていないのは、その向け先をゲートウェイに向けられるかである。`base_url` を設定する文書化
  された方法はカスタムのプロバイダなので、それを予定とし、組み込みのものがそれに替わるのは、ゲートウェイで動く向け先の上書き
  とベアラが測定で示されたときだけである。
- **保存された Responses の状態は、Q7 の前に CP で閉じる。** Bedrock では `store` が false でなければ応答を 30 日間保ち、
  `previous_response_id` は保存された文脈を普通の `POST` で読む。その範囲はアカウントの Project で、`bedrock-runtime` には
  既定の Project しかない（[Responses API](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-responses-api.html)、*ドキュメント*）。したがって共有のルートロール
  の下では、ほかのメンバーやテナントの応答 id がその人の文脈を再利用できてしまい、小さな本文が巨大な隠れた文脈を引き込んで
  D4 の上限を破れてしまう。そこで提供ルートでは、CP はすべての Responses のリクエストに **`store: false` を強制し**、
  **`previous_response_id`、`conversation`、そのほか保存された状態への参照をすべて拒否する**。リクエストの解析は知らない最上位
  の項目に対して閉じる側に倒すので、後から足された項目は見直すまで拒否される。codex が保存された状態を必要とすると分かった
  ら、提供ルートでの codex は、どの応答 id をどのメンバーと出どころが持つかを CP が持つ登録簿と、連鎖した文脈の全体を予約に
  数える仕組みを待つ。それはここでは設計しない。
- **Responses のストリームは別の形式である。** `routegw` の使用量の解析は AWS のイベントストリームを読む。Responses のスト
  リームは server-sent events である。Q7 で、その終わりの使用量を読む解析と、codex が再試行するか一度で示すかの拒否のステー
  タスを作り、関門を通す（P2b の part 2 が claude について測ったように測る）。
- **TCP で話すハーネスの呼び出し元の束縛。** opencode や codex が Unix ソケットを使えないなら、束縛は ADR 0128 の P2b の注記
  が名指すものになる。ループバックの相手を `/proc/net/tcp` でソケットの inode に、さらにそれを持つプロセスに解決する。
- **マネージド実行。** ADR 0128 決定 5 の規則はそのまま立つ。共有の opencode `serve` や codex の app-server は 1 つの資格情
  報を運び、そのプロセスはどのセッションの起動ペインのツリーにも入っていない。マネージドで提供ルートを使うには、セッション
  ごとのデーモン（あるいはデーモンを根とする束縛と、デーモンには出せないセッションごとの帰属）が要る。ターミナルが先で、
  マネージドの費用は差し出す前に測る。

### D6. 提供ルートを含む切替（ADR 0128 決定 10、P4）

- **切替先はリストになる。** ハーネスが切替先を宣言し（`agents.RouteSwitcher`。claude は今 `anthropic-api` を宣言する）、
  提案はメンバーが**今**使えるものを並べる。メンバーの Anthropic API キー、メンバー自身の印付きプロファイル（`bedrock`）、
  そして予算の残っている各提供ルートである。各項目は誰が払うかを言い、提供ルートでは残りの予算も示す。何も事前に選ばない。
- **戻る切替は新しい。** P4 は一方向である。この提案で `anthropic-subscription` から切り替えたセッションは、その切替の境目
  （`Meta.RouteSwitches`）にそれを記録する。案:
  - **R1、手動の提案**: 制限のエピソードのリセット時刻を過ぎたら「サブスクリプションに戻る」を出す。
  - **R2、選んだときだけの自動の戻り**: 切替の確認で選び、リセット後の最初のアイドルの時点で行う。
  - **R3、なし**。
  - **推奨: R1、そして R2 を、切替先が提供ルートのときは最初からチェックの入った選択肢として。** 戻ればルートを貸した払い手
    から支出が離れ、動機となる使い方（「しばらく」）が求めるのもそれである。R2 はエピソードごとに多くても 1 回だけ動く。戻っ
    た最初のターンが再びウィンドウに当たったら、セッションは提案を出して止まり、ひとりでに行き来することはない。
- **両方向に同じ遷移。** 戻りは P4a の排他的な遷移をそのまま使う（ライフサイクルの関門、段階の記録、予約の取り消し、停止、
  保存、再開、巻き戻し、クラッシュからの回復）。違うのは行き先がサブスクリプションであることだけである。台帳は各ターンを、
  そのターン自身の時刻に有効だったルート（`Meta.RouteAt`）で記録する。
- **提案が述べる注意:**
  - *キャッシュの共有は保証されない。* Bedrock と Anthropic のキャッシュは別なので、切替の後の最初のターンは冷えた接頭辞から
    始まり、文脈の一部または全部のキャッシュ作成を払うかもしれず、それは通常の入力より高くつきうる。戻るときは、元のルート
    のキャッシュがまだ温かいこともあれば、切れていることもある。台帳は実際の数字を記録する。ルートの組ごとに測るまでは、
    提案は数字ではなく「高くなる場合がある」と書く（ADR 0128 決定 10）。
  - *機能が違う。* モデル id が変わる（`--model opus` は Bedrock で `us.anthropic.claude-opus-5-5` になった。P2b part 2 で測
    定）。モデルが出どころのリージョンや許可リストにないこともある。Anthropic 自身の API の機能（サーバー側のツール、ベータの
    ヘッダ、差し出されるコンテキストウィンドウ）は Bedrock では違うかもしれない *（未計測。測るまで一覧は書かない）*。
- **codex にはまだ切替を差し出さない。** その制限の証拠はイベントのたびに送り直されるアカウント全体のスナップショットで
  （ADR 0128 の 2026-11-03 の注記、P0b）、「このセッションのルートが制限に達した」ことを証明できない。

### D7. 段階

どの行も、それが開くハーネス × ルートの行ごとに本物の Bedrock での決定 14 の関門と、表に挙げた関門を要する。

| 段階 | 内容 | 関門 |
|---|---|---|
| Q0 | カタログの id `bedrock-tenant` / `bedrock-deployment`。CP の支出・予約・許可・予算のモデル。出どころの id と fingerprint。モデルの価格と上限の表。ふるまいは変えない | 既存の `bedrock` の行とロールアップが変わらない。同じモデルの提供の行とメンバーの行がロールアップで分かれたままである |
| Q1 | **受け入れ試験のみ。`AF_WS_CLAUDE_BEDROCK_ROUTE` のようなスイッチの後ろに置き、リリースしない。** `deployment` の出どころでの CP ルートゲートウェイ（G3）とその署名の取り決め。Agent の中継。super_admin の許可と上限額。tenant_admin の予算。受け入れと精算。セッションポリシー付き・セッションタグ付きの AssumeRole。どの作成の経路でも起こす前に拒否すること。claude、ターミナル | 意図したルートロールとセッションポリシーの下で（デプロイする人の権限ではなく）、本物の Bedrock で CP を通る claude のライブのターン。許可リストに足したモデルが次の呼び出しで呼べる。最初のトークンまでに増える時間を測る。**予算:** 予算の縁で競う 2 つの CP が予算を越えて受け入れない。受け入れと精算の間で殺した CP は、掃除が精算する予約を残し、0 にはならない。UTC の 23:59:59 に受け入れた呼び出しは自分の月に精算される。重複した精算は何も変えない。切れたストリームは予約額で精算される。値段のないモデルと出力の上限のないリクエストは拒否される。**取り決め:** 偽造や期限切れのトークン、ID のヘッダ、呼び出し側のタグ・リージョン・URL・ロール、ARN のモデル id、リストの外のモデル（パスと本文）、ほかの操作 — どれも拒否され、何も署名されない。**失効:** 予算 0 → 目に見える 503 でフォールバックなし。許可を切る → 次の呼び出しが拒否される。メンバーの削除 → ストリームが切れる。この最初のタグ付きの呼び出しで、AWS がプリンシパルタグを見つけられるようになる |
| Q2 | **リリース。** 最低限の見える化（起動ダイアログと切替の提案での残りの予算、尽きたときのメッセージ、tenant_admin のメンバーの画面）。プリンシパルタグの有効化。CP の経路が保たれること | リリースの前に支払いアカウントでタグを有効化する（ADR 0048: 遡及はなく、キーは見つかってからでないと有効化できない）。Agent→CP のどのホップのアイドルタイムアウトも上流の期限より長いことを、期限の直前まで黙る代役の上流で示す（合格: 最後まで届く、不合格: 切られる）。さもなければそのデプロイメントの提供ルートは off のまま（D2）。そのデプロイメントが見込む同時ストリーム数での CP の容量。デプロイは流し終えるか、目に見えて失敗する |
| Q3 | より豊かな報告: ミラー、使用量のページ、プリンシパルタグからのクラウド費用の行、推定と実費を並べる | プリンシパルタグの費用が Cost Explorer に見える（呼び出しから 24 時間以上後）。試験用メンバーの 1 日を推定と実費で比べ、差を消すように調整せず、そのまま述べる |
| Q4 | D6: 切替先のリスト、戻り（R1、R2） | ライブのウィンドウの停止 → 提供ルートへの切替 → リセット → 自動と手動の戻り。借りたルートで予算が尽きると目に見えて止まる。戻りでの強制した失敗が巻き戻る |
| Q5 | `tenant` の出どころ: super_admin の許可。CP の外部 ID と D1 の有効化の試しを伴うクロスアカウントのロール。テナント設定 > 接続。そのモデルの許可リストと任意の上限額 | ID なしや誤った ID で AssumeRole が成功する（条件なしに CP を信頼する）ロールでは有効化が拒否される。試しのモデル呼び出しが拒否されたときも拒否される。正しい ID で失敗するときも拒否される。呼び出し側が渡した ID は受け付けない。消されたロールは目に見えて拒否される。編集された ARN や回転した ID は、縛られたセッションを移すのではなく拒否する |
| Q6 | 提供ルートでの opencode（ADR 0128 P2c の後）: その通信を測り、必要なら TCP の束縛。ターミナル、次にマネージド | 実行方式ごとの決定 14。Converse の使用量が読める。出どころごとの陰性対照 |
| Q7 | 提供ルートでの codex: Responses の通信、OpenAI 系のモデルだけ。`store: false` の強制と、保存された参照の拒否。Responses の SSE の使用量の解析 | 実行方式ごとの決定 14。Claude のモデル id が、最初のメッセージではなく起動時に拒否される。ほかのメンバーの応答 id と、連鎖した `previous_response_id` が拒否される。本物のストリームから終わりの使用量が読める。ゲートウェイの拒否のステータスを codex がどう扱うかを測る |

Q1 は、同じアダプタとソケットを使うので、ADR 0128 の claude `bedrock` の行が自分のライブの関門を通ることに依存する。

## 退けた案

- **ワークスペース自身の AWS の ID をデプロイメントの出どころにする**（`AF_WS_WORKLOAD_AWS=1` と、`WsTaskRole` への Bedrock
  のポリシー）。どのワークスペースのどのプロセスも、予算なしに、ワークスペースのタスク以上の帰属もなしに、デプロイメントの
  アカウントで Bedrock を呼べることになる。`IsolateWorkloadChain` はまさにそれを防ぐためにある。
- **Agent の中の提供された資格情報**（G1）と、**ペインの中の CP のベアラ**（G2）: D2。
- 帰属の仕組みとしての**メンバーごとのアプリケーション推論プロファイル**: D5。
- **共有ロールの費用を台帳から頭数で割る**: 推定を実費として見せることになる（ADR 0048 決定 4）。
- codex で Claude を動かすための**ゲートウェイでのプロトコル変換**: H。
- **呼び出しの途中で予算が尽きたらストリームを切る**: 課金済みのトークンが失われ、ターンが壊れる。証明された上限に対して
  全額が収まるときだけ受け入れるので、その必要はない（D4）。
- **リクエストの大きさや、抜き取りで測った比率からの予約**: JSON、画像、文書、キャッシュ書き込みを握る呼び出し側に対して、
  上限にならない（D4）。
- **メンバー自身の資格情報が失敗したら提供ルートに、ある提供ルートが尽きたら別の提供ルートに、フォールバックする**: 請求を
  黙って移すことになる（ADR 0128 決定 3）。

## 未決の問い

1. CP が AWS の ID を持たないデプロイメントのテナントが、ロールの代わりに Bedrock の長期 API キーを登録してよいか（D1）。
   請求でメンバーを区別できないことを受け入れたうえで。
2. テナントに初めて出どころを許可したときの、メンバーごとの既定の予算: 0（tenant_admin が動くまで誰も使えない）か、許可の
   ときに選ぶテナントの既定か。
3. メンバーごとの同時呼び出しの上限（D4）。Q1 の測定から決める。あわせて、どの API ならコンテキストウィンドウより厳しい
   入力の上限を証明できるか。
4. 既存のタグの有効化が IAM プリンシパルのタグにも効くか、Cost Explorer がそれを同じキーでまとめるか（D5）。有効化は Q2 の
   リリースの前に、まとめ方は Q3 で確かめる。
5. プロファイル単位のメトリクスを望むテナントのための、テナントごとのアプリケーション推論プロファイル（D5）。
6. USD 以外の通貨: AWS が何を返すかは ADR 0048 決定 6 が示している。デプロイメントが必要とするまで、予算は USD とする。

## 結果

- AWS アカウントを持たないメンバーも、テナントやデプロイメントが貸す Bedrock を、自分に見える予算の中で使える。メンバーの
  ルートは変わらない。
- CP は、エンジンですでにしているように提供ルートのモデルの通信を運び、提供ルートの予算と許可を強制する場所になる。
- デプロイメントの出どころと、ロールによるテナント接続には秘密を保管しない。CP の IAM には、ルートロールへの
  `sts:AssumeRole`（テナント接続を有効にしたときは、ほかのアカウントのロールのパスへのそれ）が加わる。
- 提供された Bedrock のメンバーごとのクラウド費用は、プリンシパルタグを通して 1 日遅れの実費になる。トークン台帳はリアル
  タイムの推定を保つ。2 つは並べて見せ、決して混ぜない。
- Bedrock での codex は OpenAI 系のモデルに限られる。Bedrock での Claude は claude と opencode のためのものになる。
- 提供ルートのハーネス × ルートの行は、ADR 0128 決定 14 のとおり、実行方式ごとにライブの関門を 1 つずつ要する。
