## 背景

タスクごとに pod を立てる設計を知っている読者は、まずこれを訊く——なぜメンバーごとに長寿命のワークスペースを
1 つ持たせるのか。タスクごとに新しいコンテナを立て、終わったら捨てる形にしないのはなぜか。開発者向け文書の答えは
1 行だけで（「利用者の隔離: 1 利用者 1 コンテナ」、[build/00](../build/00-project-context.ja.md)）、
それを説明する決定記録は無い。

**形はどこから来たか。** 製品は個人のフリート運用環境を一般化したものである
（[build/00](../build/00-project-context.ja.md)「何から作られたか」）。その環境は
`scripts/tmux-claude.sh` で、1 台の機械の detached tmux で複数の Claude CLI を起動・再開・世代管理していた。
加えてプロファイルごとに別の `CLAUDE_CONFIG_DIR` を持っていた。以後のフェーズは、代案を比べることなくこの形を
固めていった。

- **Phase 0**（[log/phase0-poc](../log/phase0-poc.md)）は、`claude /login` がヘッドレスで通るかを確かめた。
  その仮説のうち 2 つは、この決定の縮図である。H3: 資格情報がバインドマウントしたホームに永続し、
  **コンテナを作り直しても再ログインなしで** claude が動く。H6: tmux 上の claude を切り離し、
  **`--resume` で呼び戻せる**。どちらも合格した（2026-06-26）。
- **Phase 1**（[log/phase1-plan](../log/phase1-plan.md) §11.1・§11.4）は 1 利用者分のコンテナを作り、
  `./data/home/<user>` を `~` にバインドマウントした。この時点ではまだ単一のワークスペースである（§11.10）。
  中の Agent は `claude_*` の tmux セッションを**複数**、一覧・起動・停止する。
- **Phase 2** でワークスペースを利用者ごとにした（ロードマップ、`roadmap.md`）。その §12.1 が後に
  membership ごと、つまり identity × tenant ごとに 1 つとした。

これらの記録のどれも、タスクごとの環境を検討していない。両者を比べた実測も無い。

**ここで言う「長寿命」の意味。** 長く生きるのは状態であって、機械ではない。

- ホームは停止と起動を越えて残る。作り直し（recreate）が消すのは `~/repos` だけで、残りは保たれる
  （[workspace-notes](../../workspace/workspace-notes.md)「What survives」）。
- `CLAUDE_CONFIG_DIR` の裏にある CLI の状態は、何も消さない別マウントにある。
- 計算資源はアイドルになると止まる（[log/p3-9-idle-stop](../log/p3-9-idle-stop.md)、ADR 0055）。
  `ecs-ec2` では毎回同じ機械ですらない。汎用スロットのプールが、メンバーの EBS ボリュームを付け替えて使う
  （ADR 0045 決定 8）。

## 決定

membership ごとに**ワークスペースを 1 つ**与え、次の 4 つの性質を保つ。

### 決定 1: 永続するホームがメンバーの状態を持つ

ホームには、メンバーの CLI ログインと設定、`~/.local` に入れたツール、パッケージのキャッシュ、クローン、
各 CLI 自身の会話ストアが入る。クローンが残らない場面でもログインは残る。

- 作り直しは `~/repos` を消し、残りは保つ。
- ホームが利用者ごとのディスクにある配備では、資格情報を常に使えるストレージからリンクしているので、
  「ホームのディスクを失ってもログインは失わない」
  （[workspace-notes](../../workspace/workspace-notes.md)、`workspace/notes/environment.md` の永続化モデル、
  ADR 0087 の 3 ボリュームの表）。

### 決定 2: そのワークスペース 1 つで多数のセッションが同時に走る

セッションは、会話・作業ディレクトリ・設定・実行状態を束ねる 1 つの枠である
（[build/04](../build/04-agent.ja.md) §4.2）。メンバーはそれを 1 つのコンテナで同時にいくつも走らせる。
**コンテナ境界が隔てるのはメンバー同士であって、1 人のメンバーのセッション同士ではない。**
境界は「唯一の砦」であり（[build/07](../build/07-security.ja.md) §7.1）、中のシェルはどのセッションとも
同じ uid で動く（§7.2）。

### 決定 3: セッションはそのホームにあるクローンの git worktree で作業する

セッションは通常、`~/repos` 配下のクローンの自分専用の worktree で作業する
（[build/93](../build/93-worktree-deps.ja.md)）。worktree 同士は親クローンのオブジェクトストアと設定を共有する。

### 決定 4: 計算資源は長寿命ではない

CP の reaper がアイドルのセッションを halt し、アイドルのワークスペースを止める
（[build/03](../build/03-control-plane.ja.md)。既定ではそれぞれ 1 時間と 2 時間、`control-plane/main.go`）。
halt したセッションは「トランスクリプトがディスクにあるので再開できる」。次のアクセスでワークスペースは
ホームから起動し直す。作り直しの安いビルド成果物は、停止とともに消えるディスク `/scratch` に置いてよい
（ADR 0044 決定 3）。

## 理由——記録が示すもの

### 理由 1: 資格情報は CLI 自身のログインで、CLI がそれをホームに書く

- **席はメンバー自身のもの。** ADR 0001 は Claude を持ち込みのままにした（「各人が `/login` する」）。
- **CLI が資格情報を自分の設定ディレクトリに書く。** ADR 0002 の決定は `claude auth login --claudeai` で、
  claude 自身が refresh token 付きの `.credentials.json` を書く。対話 TUI がサブスクの機能を保ったまま
  認証済みでいられるのは、これによる。
- **注入する経路は試されて失敗した**（ADR 0002「訂正の連鎖」、
  [build/08](../build/08-integrations.ja.md) §8.5）。
  - 環境変数で渡す setup token を読むのは `claude -p` だけである。
  - refresh token の無い合成 `.credentials.json` は TUI が拒む。
  - API キーの変数は API 利用として課金され、サブスクの機能を止めうる。
- **ほかの kind も資格情報を自分のディレクトリか、ホームの暗号化ストアに持つ**
  （[build/04](../build/04-agent.ja.md) §4.3「資格の置き場」）。
- **資格情報の写しは、回転すると古くなる。** ADR 0087 は、借用中に回転した資格情報が旧ボリュームに残ることを
  見つけた。「使い捨ての refresh token を使うプロバイダでは利用者が再サインインを求められる」。ADR 0095 の
  プローブが本物の `XDG_CONFIG_HOME` を使ったのも同じ理由で、`auth.json` を複製すると「リフレッシュトークンが
  回って利用者のログインを壊しかねない」。

つまり資格情報は、1 つのディレクトリが持ち、どの 1 回の実行よりも長く生きなければならない状態である。
Phase 0 はまさにそれ（H3）を完了条件にした。

### 理由 2: 会話は CLI のローカルストアにあり、再開はそのストアを読む

- **正本は CLI 自身のストアである。** claude と codex は自前の JSONL、opencode は自前のデータベース
  （[build/04](../build/04-agent.ja.md) §4.3）。「会話本体を自前のストアへ複製することはない」
  （§4.3、ADR 0015）。
- **再開にはストアと作業ディレクトリが要る。** 再開するセッションはストアを読み、エージェントの kind は
  「作業ディレクトリが無くなると再開できない」（§4.2）。Phase 0 の H6 はこの性質だった。
- **halt が安いのはこのためである。** アイドル停止の計画は claude セッションの halt を「実質 hibernate」と呼ぶ。
  会話は JSONL に永続化されており、`claude --resume` で文脈ごと戻る
  （[log/p3-9-idle-stop](../log/p3-9-idle-stop.md) §19.1）。同じ計画が不変条件を書いている。止めるのは
  インフラ資源だけで、会話・ホーム・資格情報は永続し、次のアクセスで戻る。
- **下流の機能はこれを前提にしている。** ADR 0055 は保留中のやり取りを停止の向こうへ持ち越す。ADR 0097 は
  停止したセッションを保持する（アーカイブし、削除はしない）。

### 理由 3: 新しい環境は、起動と作り直しの費用をもう一度払う

以下のどれも、タスクごとの環境と比べるために測ったものではない。永続する形を速くする過程で測ったもので、
この系で新しい環境が何を払うかについて、記録にある数字はこれだけである。

| 起動 | 時間 | 出典 |
|---|---|---|
| 新規利用者、空のホーム、冷えたスロット | 144.0 秒 | ADR 0045 決定 19 |
| Fargate で温まったホームへ戻る | 約 84〜105 秒 | ADR 0045 決定 2・5・8 |
| 稼働中のスロットにメンバーのボリュームを付け替える | 22〜27 秒 | ADR 0045 決定 8 |

- **イメージキャッシュ**で pull が 31.8 秒から 0.09 秒になる（ADR 0045 決定 1）。
- **作り直し**にも費用がある。`npm ci` は、`node_modules` をローカルディスクに置くと 105 秒が 11 秒になる
  （ADR 0045 決定 2。ADR 0044 決定 3 を引いている）。ADR 0045 決定 5 は、毎朝の作り直し（`npm ci` と最初の
  ビルド）が 5 分を超えることを、EC2 の形へ進む条件の 1 つにした。
- **温まったキャッシュが N 個目の写しを安くする。** [build/93](../build/93-worktree-deps.ja.md) は、ホームの
  キャッシュが残るので「入れ直しは安く、複製は高い」ことを土台にしている。親クローンから種まきした worktree の
  サブモジュールは、リモートが落ちていても 41 MB に 0.23 秒、ディスクは 168 KB で済んだ
  （[build/04](../build/04-agent.ja.md) §4.6）。

### 理由 4: 一般化した元の環境が、すでに 1 か所で多数のセッションを走らせていた

これは歴史上の理由であって論証ではない。製品は 1 台の機械で複数の CLI を動かす tmux のフリートを一般化したもので、
Phase 1 の Agent 契約はその形を引き継いだ（[log/phase1-plan](../log/phase1-plan.md) §11.4）。
誰かがほかの何かと比べてこれを選んだとは、記録は言っていない。

### 記録が理由を示していないこと

- **メンバーのセッションが 1 つの隔離境界を共有する理由。** [build/07](../build/07-security.ja.md)
  §7.1〜7.2 はその限界（壁は 1 枚、uid は 1 つ）を書き、受け入れている。1 人のメンバーのタスク同士を
  隔離する案と比べた文書は無い。
- **別々のクローンや別々の環境ではなく worktree にした理由。** 記録は worktree が何を共有するかを測り
  （[build/93](../build/93-worktree-deps.ja.md)、[build/04](../build/04-agent.ja.md) §4.6）、共有するための
  規則を書いている（[workspace-notes](../../workspace/workspace-notes.md)）。選んだこと自体は一度も書いていない。

## 却下: タスクごとの環境

案は、タスクごとにイメージと新しいチェックアウトからコンテナ（または pod）を作り、タスクが終わったら捨てる形である。
**この案を検討した記録は無い。** 以下の理由は、記録された決定が何に依存しているかから組み立て直したもので、
当時誰かが書いた却下理由ではない。

- **どのタスクにもメンバーのログインを入れる必要がある。** 資格情報を注入する経路は対話 TUI では働かない
  （理由 1）。設定ディレクトリをタスクごとに写して捨てれば、借用中に起きた回転がすべて失われる。ADR 0087 の件が
  タスクの数だけ起きる。
- **会話が環境と一緒に捨てられる。** 再開・フォーク・アイドル停止のための halt・持ち越したやり取りは、どれも
  CLI のローカルストアと作業ディレクトリを読む（理由 2）。それを保つには、ストアと作業コピーを外へ持ち出して
  また持ち込むことになる。それは名前の違う永続ホームである。
- **どのタスクも冷えた状態から始まる。** 起動と作り直しがタスクごとに繰り返される（理由 3）。冷えた空の起動の
  144 秒に対し、稼働中スロットへの付け替えは 22〜27 秒である。
- **以後に作った機能は 1 つのホームを前提にしており**、どれも環境をまたぐ層が要ることになる。
  - セッション間メッセージ（ADR 0041。決定 12 は境界を 1 つのワークスペースと明言している）
  - セッションが起動するセッション（ADR 0073）
  - ワーキングセット（ADR 0036）
  - 親クローンからのブランチ命名（ADR 0103）
  - メンバー間の引き継ぎ（ADR 0057）。その決定 1 自体が、この理由を裏から述べている。セッションを別の
    メンバーへ移せないのは、「transcript・worktree・未コミット変更・エージェント CLI の OAuth はすべて
    A の home にあ」るからである。

タスクごとの環境なら得られたもので、この選択が手放すもの:

- 1 人のメンバーのタスク同士の隔離
- worktree の規律が要らないこと
- タスクごとのまっさらな状態
- 保持も掃除も要る後始末が残らないこと

## 帰結——この選択の費用

- **アイドル停止が効かなければ請求が膨らむ。** 持ち込みの席では、運用者の費用は「トークンではなく占有」である
  （[build/03](../build/03-control-plane.ja.md)）。
  - [build/09](../build/09-deploy.ja.md) §9.8.2: ワークスペースは 1 時間あたり約 $0.049。平日 8 時間なら
    1 人月 $8.7、24 時間なら $36 で、「その 2 行目は scale-to-zero が壊れたときの請求額でもある」。
  - ADR 0055: 画面に残った質問 1 つのせいで、誰も触っていないワークスペースが m7i.large を一晩 9.4 時間占有した。
    その決定 1 は、コンテナを起こしておいてよい理由を機械が働いていることだけにした。
  - 単一 VM では、アイドル停止が節約するのはお金ではなくメモリである（§9.8.1）。そこでの危険は、1 台のホストの
    RAM が尽きて OOM killer が稼働中のフリートを落とすことである
    （[log/p3-9-idle-stop](../log/p3-9-idle-stop.md)）。
- **メンバーのセッションは、1 つのコンテナの CPU・メモリ・ディスクを分け合う。**
  - メモリ: ADR 0073 の見積もりでは、稼働中の claude セッションは RSS 340〜435 MB、10 GiB の cgroup に
    およそ 23 本入る。ADR 0073 は親 1 つあたりの子の数をそれより十分下に抑えている。親の数を縛るものが無いからである。
  - ビルド: ワークスペースのポリシーのビルドメモリの規則は、1 つのコンテナを分け合うビルドが「実際の事故を起こした」
    から存在する（[workspace-notes](../../workspace/workspace-notes.md)）。
  - ディスク: `node_modules` は共有しなければ worktree ごとに 349 MB になる
    （[build/93](../build/93-worktree-deps.ja.md)）。
  - 共有ストレージ: `ecs-ec2` では資格情報と CLI の状態（`CLAUDE_CONFIG_DIR`）が、全ワークスペースが使う
    1 つの EFS ファイルシステムにある。2026-09-16 にそのバーストクレジットが尽きたとき、配備全体が遅くなった。
    ADR 0087 はその後、セッションごと・開いたタブごとの費用を測った。
- **1 つのコンテナの中の worktree には規律が要る。** コンテナ内のすべてのエージェントが読むポリシーは、
  これがあるから存在する（[workspace-notes](../../workspace/workspace-notes.md)「You share one container with
  your other sessions」）。
  - パターンで kill しない
  - ポートは共有されている
  - 親クローンや他のセッションの作業コピーを checkout も fast-forward もしない
  - stash のスタックは共有されている
  - 共有した `node_modules` のリンクは全員の分を空にしうる

  コードも同じものを守っている。
  - ADR 0073 決定 7 は、他の稼働中セッションのディレクトリに対する `worktree=false` を断る。
  - ADR 0103 決定 9 は、すべての worktree が読む設定への書き込みを直列化する。
  - [build/04](../build/04-agent.ja.md) §4.6 は、サブモジュールの URL の上書きをコマンドラインで渡す。
    設定ファイルは兄弟の worktree すべてと共有されているからである。
- **状態は溜まり、管理が要る。** 停止したセッションは保持してアーカイブし（ADR 0097）、削除はごみ箱を通し
  （ADR 0101）、使い捨てのファイルには専用の置き場を与えた（ホームの散らかりの作業記録、
  [log/116](../log/116-home-clutter-and-cache-growth.md)）。作り直しは `~/repos` を、中の未コミットの作業ごと消す。
- **AWS では、永続性が運用の面を広げる。** ワークスペース 1 つが「サービス 1 つと EFS アクセスポイント 1 つ」から
  6 種類のリソースになった（ADR 0045 決定 2 の理由 3。決定 10 はこれを代価として受け入れた）。

## 見直す条件

- **CLI が状態をホームに持たなくなる。** それには、サブスクの機能を失わずに注入された更新可能な資格情報を受け入れる
  対話 TUI（ADR 0002 の試みはどれもそこへ届かなかった）と、ローカルストア以外の場所から再開できる会話が要る。
  そうなれば理由 1 と 2 は弱まる。
- **新しい環境が、キャッシュ込みで、いまの付け替え（22〜27 秒）と同じくらい速く起動する。** そうなれば理由 3 は
  弱まる。
- **テナントが、1 人のメンバーのタスク同士の隔離を必要とする。** たとえば信頼できないリポジトリを並べて走らせる
  場合である。いまはコンテナが唯一の砦である（build/07 §7.1）。
- **どこかのランタイムでアイドル停止を確実にできない。** そこではこの形は build/09 §9.8.2 の 24 時間の行の
  費用になる。
