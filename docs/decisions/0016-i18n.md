# 0016. Full i18n for the Console — a hand-rolled lightweight layer for Japanese↔English, with the settings store as the single source of truth for locale

English | [日本語](0016-i18n.ja.md)

- Status: decided; every phase implemented (P0–P5, 2026-07-16, `temp/sm5hcv2`) — the first
  instalment is Japanese (the source) ↔ English. The approach is a hand-rolled lightweight i18n
  layer, with no external library. P5 introduced an AST-based lint that detects bare Japanese
  literals (wired into `ci.yml`, with a pending ratchet) and migrated the secondary screens
  wholesale, taking bare Japanese in the console to zero (1738 catalogue keys in total). The
  design proper is [28-i18n.md](../log/28-i18n.md).
- See also: [0011-console-rebuild.md](0011-console-rebuild.md) (the foundation that put the Console on React) /
  [0012-go-internal-refactor.md](0012-go-internal-refactor.md) (the pairing of `internal/agents` and errcodes) /
  docs/23 P0-3 (the code-based approach linking `ERR_TEXT` and `errcodes.go`).

## Context

Every string in the Console UI was hard-coded Japanese. There was no i18n library, no `Intl.*`
and no `navigator.language` detection, and `index.html` was fixed at `<html lang="ja">`. That
said, earlier design work had left the seams in place: right above `ERR_TEXT` in `client.ts` it
says "when i18n arrives, add a locale layer to this map", and the backend returns
language-independent codes with an English fallback (docs/23 P0-3). Settings use a hand-rolled
`useSyncExternalStore` (`lib/settings.ts`) that keeps `theme` in localStorage, syncs it to the
server, and applies it to `<html data-theme>` before the first paint — `theme` is a complete
template for `locale`. The material to translate was roughly 956 front-end strings (123 files)
plus 70–90 on the backend.

## Decision

1. **The first instalment is Japanese↔English.** Japanese is the source, English the second
   language. The catalogue and runtime are shaped so a third language can be added, but the first
   edition ships two.

2. **No external i18n library — build a lightweight layer ourselves.** Add `locale` to
   `lib/settings.ts` and hand-roll `t(key,vars)` / `useT()` / `<Trans>` / plurals via
   `Intl.PluralRules` on top of it. The grounds: (a) the existing code consistently uses a
   hand-rolled store and a hand-rolled provider, a minimal-dependency stance; (b) i18n has to be
   callable from **both React and non-React** code (`errText`, `wording`, reading aloud), which is
   the same shape as `settings.ts`'s dual consumption; (c) plurals are needed in about 25 places
   and `Intl.PluralRules` suffices, and this rides along with the tidy-up that collects duplicated
   date/number/relative-time formatters into `Intl`. react-i18next was passed over because locale
   state would be duplicated against settings and need bridging; FormatJS/Lingui because they
   require introducing a macro/plugin into the Vite build.

3. **The single source of truth for locale is `settings.locale`.** It follows `theme`
   (localStorage plus `/api/env/ui-prefs` sync, `applyLocale` applied before the first paint,
   `document.documentElement.lang` updated at runtime). Unlike `theme`, though, it is **not
   device-local**: language follows the person across all their devices. The default comes from
   `navigator.language` (`ja*` → ja, anything else → en, unsupported falls back to ja).

4. **Missing keys are caught by the type system.** `ja` is canonical, so
   `type MsgKey = keyof typeof ja`, and `en` is forced by the type to cover every key. CI's
   `typecheck` detects untranslated keys, so we do not depend on a library's tooling.

5. **Japanese-only features are not translated — they are locale-gated.** TTS kana conversion,
   Narou-style ruby and vertical writing switch on `locale==='ja'` (effectively
   `provider==='voicevox'`). The IME composition guard stays on for every locale.

6. **Scope is the front-end UI, plus the backend's user-facing errors, plus the server-rendered
   pages (login/OAuth).** Codes that are already mapped only need the `ERR_TEXT` locale layer (no
   backend change). The ~47 Japanese error messages in `workspace/agent/` that had no code get
   codes. The Go-rendered login/OAuth pages do not ride on React, so they are localised
   separately by `Accept-Language` / a locale cookie.

7. **The agent's output language (the `outputLanguage` axis) is out of scope.** The fixed
   Japanese in automatic title suggestions, the forced Japanese in chat, and the various LLM
   prompts determine model behaviour rather than display, so making them follow the UI locale is
   not part of this (to be considered separately).
   → **Partly superseded by [0033](0033-stored-text-locale.md).** This exclusion is limited to
   "strings the model reads". Text that is stored in conversation data but that **we generate
   solely for the user to read** (the `role=="notice"` cards) is display wording: it is stored as
   a key plus arguments and translated through the Console's catalogue. "Stored data is uniformly
   JA" from docs/19 is withdrawn.

## Options rejected

- **react-i18next**: the standard choice with a low bootstrap cost, but locale state would live
  separately inside i18next and be duplicated against `settings.ts`. `t()` from non-React code
  would also take a different path, breaking the single source of truth.
- **FormatJS (react-intl) / Lingui**: natively ICU and powerful, but they require introducing a
  macro/extraction plugin into the Vite build, which is a heavy setup. Overkill at this scale
  (~25 plurals, 2 languages).
- **Defaulting to English based on the browser language**: existing users are mainly Japanese
  speakers, so we detect but fall back to Japanese for anything unsupported or unknown, leaving
  existing behaviour intact.
