## 背景

ツール呼び出しに承認が要るかどうかは、今は kind 自身の権限モードが決めている。ADR 0056 はメンバーが kind ごと・セッションごとに
スキップのフラグを切れるようにし、既定はどの kind でも「スキップ」のままである（`workspace/agent/internal/agents/agents.go:25-68`）。
この選択は kind ごと・ツールごとのスイッチである。Agent Fleet にはセッションの中のツール呼び出しの**並び**を見るものが何も無いので、
次のような規則は書けない。

- 「同じセッションでエージェントが npm パッケージを落とした後の `git push` は承認が要る」
- 「このセッションのツール呼び出しは N 回まで」
- 「このセッションが作ったファイルだけ編集してよい」
- 「コマンドを動かすツールやファイルシステムに触るツールの前には必ず尋ねる」

Issue が求めているのはまさにこれで、Omnigent（Databricks、Apache 2.0、alpha）にならい、デプロイ → ユーザー → セッションと積み、
厳しい層が勝つ。そしてまず設計を、と求めている。

### 各 kind が差し出す差し込み口

**block** は、ツールが動く*前に* kind が AF の制御下にある何かに尋ね、それに否と言え、その時点で引数が見えることを言う。
**observe** は、呼び出しが始まった後か終わった後にしか AF が見られないことを言う。**none** は、構造化されたものを AF が何も見ない

## 決定

### 1. 判定点は Agent に 1 つ、強制点は kind ごと

**判定点**は Agent のプロセスの部品である。生きている各セッションの有効なポリシーと、そのツール呼び出しの台帳（決定 4）を持ち、
1 つの問いに答える。*このセッションの履歴に照らして、この正規化したツール呼び出しを動かしてよいか。異議なしか、deny か、
メンバーに尋ねるか。* CLI を覆すという意味の「allow」は決して答えない。**ポリシーは制限を足すだけ**であり、メンバーの ADR 0056 の
選択は効いたままである。

**強制点**は薄く、kind ごとにあり、ポリシーを持たない。それぞれが kind の差し込み口を判定点への呼び出しに変え、答えを kind の語彙に
戻す。

- **claude Terminal:** マッチャが空（全ツール）の PreToolUse フックが `workspace-agent policy-check` を動かす。このサブコマンドは
  フックの JSON を読み、ローカルの Agent に尋ね、`deny` か `ask` を出すか、何も出さない。「異議なし」は判定なしとして出す
  （`defer` か何も出さないか、CLI 自身のモードに任せるのはどちらかを P0 の関門で測る）。
- **codex Terminal:** 同じサブコマンドを `-c hooks.PreToolUse=…` として差し込む。codex は `deny` しか受け付けないように見えるので、
  `ask` の判定はフックの中で保持する（決定 6）。
- **ACP の kind（Managed）:** ドライバの `onServerRequest` が、`Interaction` を立てる前に判定点に尋ねる。合成の規則はメンバーの選択を
  保つ。
  - deny の判定は reject の選択肢を送る。ask の判定は承認の `Interaction` になり、ポリシーの印が付く。
  - 異議なしなら、要求には**メンバー自身の権限の選択が答えたであろうとおりに**答える。セッションの解決済みの ADR 0056 の選択が
    「スキップ」で、差し込み口を得るためだけにスキップのフラグを切っているなら（決定 7）、ドライバはメンバーに代わって allow と
    答える。スキップのフラグがあったらそうしていたからである。メンバーが確認を選んでいたか、セッションがプランモードなら、元の
    `Interaction` をそのままメンバーに渡す。
- **lcpp:** 変更系のツールしか見ない `approve()` の中だけでなく、**すべての** `tool.Run` の前に判定を置く。`approve()` は判定の後に
  自分のゲートを保つ。
- **observe しかできない kind**（agy、muse、opencode、codex Managed、kiro と cursor の Terminal、そして関門を通っていないすべての
  候補）は、すでに後から読んでいるものから台帳を埋める。それが何を意味してよいかは決定 7 が言う。

**判定点は CP ではなく Agent に置く。** フックはコンテナの中で動き、ミリ秒で答えなければならない（§ 性能の予算）。CP への往復は、
すべてのツール呼び出しの中にネットワークを置くことになる。docs/log/20 は、当時 Agent→CP が届かなかったためにフックから CP への
push を退けた。今 Agent の pull を運んでいる Workspace 専用の listener は定期的な取得のためのもので、呼び出しごとのホットパスの
ためのものではない。CP はポリシーの出どころであって、呼び出しごとの裁き手ではない。

どの強制点も、尋ねる前に呼び出しを 1 つの形に正規化する。`{session, 呼び出し id, kind, tool, category, argv の段, パス,
mcp サーバ}`。**`tool` は正規化した id** であって、CLI の生の名前ではない。`shell`、`edit.write`、`edit.patch`、`read.file`、
`web.fetch`、`mcp:<server>/<tool>` などである。**category** は閉じた集合で、`shell`、`edit`、`read`、`web`、`mcp`、`agent`、
`other` である。各 kind は自分のツール名を両方に写す（claude の `Bash` → `shell`、`Write` → `edit.write`。ACP の `kind` の値も
同じように写す）。ポリシーは category、正規化した id、argv、パスに対して書き、1 つの CLI のツール名に対しては決して書かない。
どの写しも知らないツール名は `other` であり、fail closed のポリシーは `other` を自分が名指すあらゆる category に合うものとして
扱う。解析できないコマンドと同じ規則である（決定 2）。

### 2. ポリシーのモデル: 小さな組み込みの集合、宣言的、利用者のコードは無し

ポリシーは**パラメータを持つ組み込みの型**であり、データとして保存する（エディタでは YAML、ワイヤでは JSON）。式の言語も、
スクリプトも、利用者が渡すバイナリも無い。マルチテナントの配備では判定点はメンバーごとの Agent の中で動き、あるメンバーや
テナントのコードが別の人の判定の経路で動くことはあってはならない。

最初の 4 つの型。Issue の例 1 つにつき 1 つ。

| 型 | パラメータ | 判定 |
|---|---|---|
| `tool_call_cap` | `max`（セッションごと）。任意でセレクタ（`categories`、正規化した id） | セレクタに合う数えた呼び出しが `max` に達した後は `deny`（または `ask`。未決事項 6） |
| `approval_gate` | `after`: マッチャ。`then`: マッチャ。`verdict`（`ask` / `deny`） | `after` に合う呼び出しがセッションで一度許された後は、`then` に合う呼び出しすべてが `verdict` になる。1 つの呼び出しの中で `after` の段の後か横に並ぶ `then` の段も数える（下記） |
| `path_scope` | `allow`: 作業コピーからの相対のパスの glob、または `created_by_session: true`、あるいはその両方。`categories`（既定は `edit`） | 範囲の外の編集は `deny` か `ask` になる |
| `ask_on_categories` | `categories`（例 `shell`、`edit`） | 合う呼び出しはすべて `ask` になる |

**マッチャ**は閉じた文法である。category、正規化したツールの id、`["git","push"]` や `["npm",["i","install","ci","add"]]` の
ような argv の前置部、パスの glob。組み込みの例「ダウンロードの後の push」は、`after` = {npm、pnpm、yarn、pip、uv の
add/install、curl、wget}、`then` = `git push` の `approval_gate` である。

**シェルのコマンドは Agent の中の新しい静的なパーサで解析する。** 今は存在しない（本番の `Stages` は muse の MSP の argv から
来るものだけである）。パーサは何も実行しない。文法は次のとおり。

- **理解するもの:** リテラルの語からなる単純コマンド、パイプライン（`|`）、リスト（`&&`、`||`、`;`、`&`）、サブシェルと
  グループ、リダイレクト、`env VAR=x cmd`、そして**リテラル**の引数を持つ `sh -c` / `bash -c`（引数を再帰的に解析する）。普通の
  複合コマンド（`cd x && npm ci && npm test | tee log`）は解析できる。
- **既知のラッパーは照合の前に剥がす:** `rtk`、`env`、`nice`、`time`、`timeout`、`nohup`、`xargs`（そのコマンドの引数）、
  `npx`/`pnpm dlx`（実行するパッケージ）。だから `rtk git push` への書き換えも `git push` に合う。ポリシーのフックが rtk のフックの
  書き換えの前と後のどちらのコマンドを見るかは P0 の関門で測る。照合はどちらでも同じである。
- **不明なもの:** プログラム名がリテラルの語でない段（`$cmd`、`$(…)`、バッククォート）、`eval`、リテラルでない引数の `sh -c`、
  シェルに流し込むヒアドキュメントやパイプ（`base64 -d | sh`）、ファイルの `source`/`.`。不明な段は、fail closed のポリシーの
  **あらゆる `shell` のマッチャに合うものとして数える**。難読化はすり抜けではなく承認になる。それでもサンドボックスではない
  （決定 9）。

**1 つの呼び出しの中の並びも数える。** 1 つの呼び出しの段はリストの順に評価し、並行する段（`&`、`|`）は同時に起こるものとして
扱う。`then` の段が `after` の段の後か横にあれば、呼び出し全体がゲートの判定になる。だから台帳が空でも
`npm install x && git push` は尋ねる。旗を立てる呼び出しが許されれば、続く呼び出しのために旗が立つ。

**承認疲れは「不明なら合う」の本物のコストである。** 解析できないコマンドを多く使うセッションは早くにゲートを立て、その後は
`then` の呼び出しのたびに尋ねる。選択肢はここで選ばずに記録する。不明なものが `after` の旗を立てる（書いたとおりの厳しい読み方）。
不明なものは自分については尋ねるが旗は立てない。あるいは、不明な呼び出しの承認カードでどちらの読み方にするかをメンバーが言う
（未決事項 11）。

「**セッションが作った**」には 2 つの状態がある。存在しないパスを作る edit の category の呼び出しを判定点が通すと、そのパスは
セッションにとって **pending** になる。同じ呼び出し id の完了イベントが成功とファイルの存在を確かめたときにだけ **owned** になる
（claude の PostToolUse、ステータスが completed の ACP の `tool_call_update`）。pending のパスは owned ではない。呼び出しが
断られたか失敗し、別のセッションがそのパスを作ったなら、最初のセッションの後の編集は範囲の外である。`created_by_session` が
**最初の**作成の編集を許すのは、パスが存在せず、作業コピーの中にあるときだけである。パスは照合の前に解決する。セッションの cwd
からの相対とし、正規化して `..` を解決する。存在する対象は `realpath` で解決するので、作業コピーの外のファイルを指す作業コピー
内のリンクは範囲の外である。まだ存在しない対象は、もっとも近い存在する祖先を解決する。作業コピーの外に解決されるパスは決して範囲に
入らない。判定と書き込みの間にすり替えたリンク（TOCTOU）は捕まえない。これはガードレールであってサンドボックスではない（決定 9）。edit のツールに
よる削除と再作成は、新しい pending の状態から始める。`shell` のコマンドによる改名や作成は見えないので、所有はそれについて行かない。
完了イベントで呼び出しを確かめられない kind は、`created_by_session` を block として出せず、そのポリシーについては observe に落ちる。

利用者が書くポリシー（新しいマッチャ、新しい組み合わせ）は後で来る。同じ文法のままで、やはりコードは動かさない（§ 段階）。

### 3. 積み方: デプロイ → テナント → ユーザー → セッション、厳しい値が勝つ

ポリシーは 4 つの層で設定する。**どの層も、上の層が設定したものを緩められない。**

| 層 | 誰が設定するか | どこにあるか | どう Agent に届くか |
|---|---|---|---|
| デプロイ | super_admin | CP のデータベース | ブランチ規則と同じ pull（`GET /internal/tool-policies`、5 分ごと、最後の写しをキャッシュ） |
| テナント | テナント管理者 | CP のデータベース | 同じ応答の中で、メンバーのテナントについて解決したもの |
| ユーザー | メンバーが Settings で | CP（Workspace をまたいでメンバーについて回るように） | 同じ応答 |
| セッション | セッションを起動する者（Console、`create_session`、スケジュール） | `session.Meta`。`SkipPermissions` と同じく再起動とフォークで写す | 起動時 |

テナントの層が要るかどうかは未決事項 1 である。Issue は 3 層を挙げているが、AF にはデプロイとユーザーの間にテナントがある。

**積むことはすべての制約を保つ。1 つの数に畳みはしない。** 各層の各ポリシーはそれぞれ独立に評価し、呼び出しの判定はすべての
判定のうちもっとも厳しいものである（`deny` > `ask` > 異議なし）。全呼び出しに対するデプロイの上限 100 と、`shell` に対する
ユーザーの上限 10 は、両方が成り立つ 2 つの制約であって、上限 10 ではない。2 つのポリシーを合わせるのは型とセレクタが同じときだけで、
そのとき各パラメータは厳しい方の値を取る。小さい方の `max`、`path_scope` の許可の積、`ask` より `deny`、`observe` より `block`、
`open` より `closed`。異なるゲートは決して合わせない。

**判定を誰が取り消せるか。** 承認は尋ねたポリシーにちょうど答え、カードはそれぞれを id で名指す。`once` の承認はこの呼び出しを
通す。広いスコープ（`turn`、`thread`）が外せるのは、答える人が編集できる層のポリシーだけである。だからメンバーは自分の
ユーザー層やセッション層のゲートをセッションの間外せるが、デプロイやテナントのゲートは外せない。最初の版では上限をカードから
引き上げることは無い。それを設定した層を編集するとポリシーは緩むが、緩めるものはその後に起動したセッションにしか届かない（下記）。
だから上限に達したセッションが続けられるのは、**明示的な例外**によってだけである。その層を編集できる人がそのセッション 1 つに
ついて引き上げを与え、それは監査され、セッションのスナップショットと有効な集合を更新する（緩めるものは効いた後に書いてよい。
クラッシュすれば厳しい方の状態に戻るからである）。そもそも例外を出すかは未決事項 6 である。

**ポリシーは起動時に固定し、生きている間は締めるだけ。** 有効な集合はセッションの開始時に計算する。後の pull がポリシーを足したり
締めたりしたら、動いているセッションの次の呼び出しから効く。セッションがそれを強制できないときは決定 7 に従う。緩める pull は
その後に起動したセッションに効く。だから CP の一瞬の不通や編集で、動いているセッションがターンの途中で開け放たれることは無い。
再開、再起動、作り直しはこの意味での起動ではない。セッションの有効な集合を（その後のすべての締めとともに）保ち、それを緩めるのは
上の例外だけである。

**動いているセッションに足されたポリシーは、セッションの全履歴から始まる。** 台帳は直近 N 件だけでなく、セッションのすべての
呼び出しの簡潔な記録を持つ。だから pull が足したポリシーや、セレクタが変わった（それで新しいポリシーになった）ポリシーは、その
記録を再生して初期化する。セッションが `npm install` を動かした後に足されたダウンロードの後の push のゲートは、すぐに立つ。
履歴が欠けているところ（observe しかできない差し込み口が取りこぼした呼び出し、台帳ができる前に始まったセッション）では、closed の
ゲートは旗を立てた状態で始まり、closed の上限は再生した呼び出しから数え、カードと監査の記録に *partial* の印を付ける。partial の
上限は少なく数えることがあり、ガイドはそう言う。

### 4. 状態: 判定点が持ち、原子的に更新する、セッションごとの台帳

判定点はセッションごとに**台帳**を持つ。制約ごとの回数、立っているゲートの旗、pending と owned のパス（決定 2）、
`prepared` か `awaiting` のままの記録、セッションのすべての正規化した呼び出しの簡潔な記録（カードと監査のため、そして後で
足されたポリシーを初期化するため。決定 3）。転写は出どころではない。転写は求められたときに数秒遅れで読むもので、
それを待つポリシーでは、先行する `npm install` が読まれるより先に、後続の `git push` が動いてしまう。

**1 つの判定は、セッションごとに 1 つの原子的な段である。** 1 つのセッションの判定は直列にする。各判定は評価し、予約し、
永続化し、それから初めて答える。だから 1 つのターンの並列なツール呼び出しが、同じ残数を両方とも読むことは無い。

- **冪等性。** ここでの*再試行*は、同じ判定がもう一度届くこと（HTTP の再送、同じ呼び出しについて CLI がフックを動かし直すこと）を
  言い、モデルがツールをもう一度動かすことでは決してない。それは新しい呼び出し id を生む。鍵は、セッション、CLI の世代（その
  プロセスの開始）、kind が渡す呼び出し id（claude と codex の `tool_use_id`、ACP の `toolCallId`、lcpp の呼び出し id）、正規化した
  入力のハッシュである。各記録は、判定したときのポリシーの版も持つ。同じ鍵での再試行は何も数えないが、**今のポリシーの下で
  もう一度評価する**。だから間に届いた締めはそれに効き、すでに数えた呼び出しは数えたままである。同じ呼び出し id で入力が違うもの、
  あるいは別の世代のものは拒む。安定した id の無い kind は判定をすべて数える（厳しい方の誤り）。
- **何を数えるか。** 判定点が異議を唱えなかったか、メンバーが承認したときに、呼び出しを数える。「試み」は*判定点を通った*ことを
  言い、*実行された*ことではない。その後 CLI が断ったり失敗したりした呼び出しも数え、旗も立てる。判定点が拒んだ呼び出しや、
  承認が拒まれた・タイムアウトした・取り消された呼び出しは何も数えず、旗も立てない。
- **各記録は 4 つの状態を、それぞれ高々一度ずつ通る:** `prepared`（評価済みで、異議なしの答えを返すところ）、`awaiting`
  （承認が開いている）、`committed`（数えた、旗を立てた）、`released`（何も数えない）。記録は `prepared` か `awaiting` の間、
  それが数えられるであろうすべての上限の 1 単位を持つので、メンバーが決める間に並列な呼び出しが超えることは無い。承認は
  `awaiting` を、その間にほかの呼び出しが通ったかもしれないので今の台帳に照らした新しい評価に移し、それから `committed` か
  `released` に移す。拒否、タイムアウト、取り消しは `released` に移す。1 単位はちょうど一度だけ消費される。確定で使うか、解放で
  返すかである。
- **P0 の ask は AF が保持するものだけである。** 自前の ask（claude 自身の確認）は CLI の中でキーで答えるので、Agent は答えを
  知ることがなく、記録を閉じられない。自前の ask は、自前の allow・deny・取り消しを呼び出し id に結び付けられ、呼び出しが動く
  直前に記録をもう一度評価できることを示す関門（決定 10 の項目 8）を待つ。
- **永続化。** 台帳は Agent の状態ディレクトリの下のセッションごとの追記専用のファイルである。状態の変化は、それに頼る答えを返す
  前に fsync する。再起動のとき、答えの無い `prepared` の記録は確定する（厳しい方。CLI がその呼び出しを動かしたかもしれない）。
  `awaiting` の記録は解放し、その承認 id は失効する。カードも待っていたフックも Agent とともに死んだからである。その呼び出しの
  再試行は新しい判定であり、なお要るなら新しいカードになる。保存した `ask` を二度と渡すことは無い。
- **再起動、再開、作り直し**は同じセッションのままで、その台帳を読み直す。AF のセッション（どれにも印がある。決定 8）の台帳が
  無いか解析できないなら、closed のポリシーはどれも*上限を使い切り、旗が立っている*ものとして扱う。通知を出す。人は状態を初期化
  できるが、その人が編集できる層のポリシーの状態だけである（決定 3）。メンバーはユーザー層とセッション層の回数と旗を初期化し、
  デプロイやテナントのポリシーの状態はそれぞれの管理者が初期化する。observe しかできない kind からの（遅れた）観測の項目には、
  判定したものではなく観測したものとして印を付ける。
- **ごみ箱**（[ADR 0101](0101-session-delete-via-trash.ja.md)）。台帳はセッションとともに動く。セッションのアーカイブが書かれる
  前に消すことは無く、復元はセッションの有効な集合、回数、旗をそのときのまま戻し（復元は初期化ではない）、完全削除で消す。復元は
  古いスナップショットも古い承認 id も決して蘇らせない。起動し直しが新しいスナップショットを書き、開いていた承認はセッションが
  止まったときに解放されている。

**家系: 子とフォーク。** 新しいセッションが何を受け継ぐかは、どう始まったかで違う。

| どう始まったか | ポリシー | 台帳 |
|---|---|---|
| 再開、再起動、作り直し | 同じ | 同じ台帳 |
| フォーク | 親のセッション層 | ゲートの旗と owned のパスを写す。上限をどう数えるかは未決事項 12 |
| `create_session` による子 | 親のセッション層。足すことしかできない | ゲートの旗を写す。だから親がダウンロードした後に親が子に頼んだ `git push` も尋ねる。上限をどう数えるかは未決事項 12 |
| 新しいセッション | ほかのセッションからは何も無い | 空 |

未決事項 12 に答えが出るまでは、上限はセッションごとに数え、この記録は、親が子や並列のフォークを通して自分の上限を超えられない
**とは言わない**。#1054 は支出について同じ問いを立てている。

### 5. 承認は既存のカードに出す

`ask` の判定は、Console にすでにある 2 つの承認の面のどちらかになる。3 つ目は作らない。

- **kind が自前で尋ねられるところ**（claude Terminal の `ask`）では、P1 から、それも決定 10 の項目 8 の後にだけ、CLI が自分の
  メニューを出し、既存の `PermissionCard` がキーでそれに答える。カードには尋ねたポリシーを名指す 1 行が加わる。P0 では ask は
  すべて AF が保持する（決定 4）。
- **それ以外のところ**では、判定点が **AF が保持する承認**を立てる。種別 `approval` の `Interaction` で、既存の `ApprovalRequest`
  （要約、ツール、コマンド、段）に、新しい任意の `policies` 欄（尋ねた各ポリシーの id、層、1 行の理由）を足したものである。既存の
  `ApprovalCard` として描かれ、既存の `permission-request` の通知を出すので、チャットブリッジと Console の通知はそのまま運ぶ。
  このやり取りを持つのは CLI ではなく Agent なので、`POST /sessions/{name}/respond` は Terminal セッションについてもこれを
  受け付ける。Terminal セッションのほかのやり取りについては 501 のままとする。
- **スコープ**は `once` / `turn` / `thread` を流用し、誰が何を外せるかについての決定 3 の規則で制限する。
- **答えるのは人だけである。** 承認に答える af MCP のツールは無く、親セッションは子の代わりに承認できない
  （[guide/member/02-sessions.ja.md](../../guide/member/02-sessions.ja.md) が CLI の承認についてすでにそう言っている）。
- **停止は承認を許可として持ち越さない。** ADR 0055 の決定 13 と同じく、残るのは承認が保留中だったという事実だけである。再開の
  とき、古い id への答えは断る。CLI がその呼び出しを次に試みれば新しい判定になり、なお承認が要るなら新しいカードになる。

### 6. フックの中で承認を保持する、そしてタイムアウト

codex では、またスキップのフラグの下で `ask` が確認を出さない場合の claude では、AF が保持する承認が開いている間フックの
プロセス自身が待ち、その後で `deny` か判定なしを出す。

- **AF の期限は CLI のものより短い。** 差し込むフックの構成は CLI のフックのタイムアウトを明示的に設定し、フックはそのタイムアウト
  から余裕幅（最初の版では 10 秒）を引いたところで諦め、モデルが読む理由（「承認がタイムアウトした。利用者に尋ねよ」）を付けて
  `deny` を出し、カードを引っ込める。ポリシー自身の `approval_timeout` はさらに短くてよい。claude 2.1.288 の内部のスキーマの文字列は
  フックのタイムアウトの上限を 600 秒としているが、測ってはいない。codex のものは分かっていない。
- **フックが kill されたとき、タイムアウトしたとき、0 以外で終わったときに CLI が何をするかは、仮定ではなく関門である。** そのどれかで
  呼び出しを動かす kind は、保持する ask を安全に置けない。その kind では `ask` のポリシーは自前の ask でだけ強制するか、それらに
  ついて observe に落ちる（決定 10）。
- **呼び出しは待つ。ターンの残りは待つとは限らない。** フックが待っている呼び出しは、メンバーが答えるか期限が過ぎるまで動かない。
  その間に CLI が同じターンの兄弟の呼び出しを動かすか、すでに動いているシェルがどうなるかは kind 自身のスケジューリングであり、
  測る（決定 10 の項目 9）。カードが約束するのは、この呼び出しが待つことだけである。
- **停止、中断、再起動は待ち手を解放する。** フックには deny させ、カードは引っ込め、記録は解放する（決定 4）。何が残るかは決定 5 が
  言う。

無人のセッション（スケジュール、子）ではむしろ止まって待つべきかは未決事項 4 である。

### 7. 止められない kind、そして能力の変化

ポリシーは `enforcement: block | observe` を持つ。**block**（組み込みのどの型でも既定）には、その実行方式で、そのポリシーの型に
ついての関門を強制点が通った kind が要る。

- **起動時に** Agent は有効な集合を計算する。block のポリシーが当たり、その kind がそれを止められないなら、起動を理由付きで断る
  （`policy_requires_blocking_kind`）。ADR 0056 が `permission_choice_unsupported` を断るのと同じ方法である。Agent が解決するので、
  ADR 0056 の決定 3 と同じく、すべての起動の経路（Console、`create_session`、スケジュール、再起動、フォーク、再開）に効く。
  **これは P0 で出す**。すべての kind についてである。そうしないと、デプロイの P0 のポリシーは、ほかのどれかの kind を起動する
  だけですり抜けられてしまう。
- block のポリシーを持つ **ACP の kind** は、その構成ですべての呼び出しが要求に届くことを P1 の関門が示した後に、スキップのフラグを
  切って起動する。異議なしの経路は決定 1 のとおりに答える。
- **強制できない block のポリシーを得た、動いているセッション**（observe しかできない kind や、スキップのフラグを入れたまま動いて
  いる ACP のセッションに、pull が block を足したり、observe を block に締めたりした場合）は、**止める**。
  Agent はターンを中断してセッションを止め、ポリシーを名指す通知を出す。止められる差し込み口を持つ kind では、停止が終わるまで次の
  判定を拒む。observe しかできない kind には拒む判定が無いので、すでに動いている呼び出しや中断と競う呼び出しはまだ動きうる。
  その隙は測り（決定 10 の項目 9）、ガイドに書く。再開は起動時の判定を通り、ACP の kind は
  フラグを切って起動し直し、止められない kind は断る。実行方式の切り替え（Terminal ↔ Managed）も同じ判定を通る。
- **observe** のポリシーは、区分が observe か block のどの kind でも動く。台帳は遅れて埋まる。違反は通知と監査の記録を出し、
  ターンを中断してもよい（未決事項 7）が、違反したその呼び出しを防ぐことはできない。区分が **none** の kind（shell、ssm）では、
  observe のポリシーは**測れない**。セッションにはそのバッジを付け、観測しているふりは何もしない。

「observe のみ」のバッジを付けて起動する代わりに起動を断るのが製品として正しいかは、未決事項 3 である。

### 8. 失敗時の倒れ方、ポリシーごと

各ポリシーは `on_error: closed | open` を持つ。組み込みの既定は、`tool_call_cap`、`approval_gate`、`path_scope` は **closed**、
`ask_on_categories` は **open** である。`ask_on_categories` は便宜のためのもので、それを closed に倒すと障害が拒否の壁に変わる。

**スナップショット**は、Agent が答えられないときにフックが決められるようにする。Agent がセッションの id、世代番号、ポリシーの版を
付けて書くセッションごとのファイルで、closed のポリシーが当たるかどうかを言う。

- **原子的に書き**（一時ファイル、fsync、rename）、それが表す状態が効く**前に**書く。起動はそれを待つ。締めるときはまず
  スナップショットに書き、その後で適用する。書き込みに失敗したら起動を断る。動いているセッションでは順序は次のとおり。締めるものを
  メモリで適用し、セッションを止めて CLI が終わったことを確かめ、スナップショットが永続化されるまで再開を断る。残る窓は、pull と
  確かめた停止の間の Agent のクラッシュである。Agent が落ちている間、フックは古いスナップショットに戻る。その窓は Agent の再起動
  （どの判定に答えるより前に今の写しを適用し直す）で区切られ、隠さずに書く。それを除けば、スナップショットが判定点の適用している
  ものより緩いことは無い。
- **AF のセッションには、ポリシーがまだ当たるかどうかにかかわらず、起動時から印を付ける。** 印はすでに持っている
  `AF_SESSION_NAME` であり、Agent は CLI が始まる前にスナップショット（何も当たらなければ空）を書く。だから動いているセッションに
  最初のポリシーが届いても、フックが統制外とみなすセッションに出会うことは無い。
- **フックが Agent に届かない**（落ちている、再起動中）: スナップショットが closed のポリシーが当たると言うなら、フックは理由付きで
  拒む。セッションに印があり、スナップショットが無い・読めない・途中まで・別のセッションのものなら、フックは拒む。判定なしを返すのは、
  `AF_SESSION_NAME` の無いプロセス（メンバー自身の端末の `claude`）か、closed のポリシーは当たらないとスナップショットが言う
  場合だけである。
- **CP に届かない:** CP に届かない間は、最後に pull した写しが効いたままである（ブランチ規則と同じ）。Console は写しを最後に取った
  時刻を見せる。一度も写しを取っていない配備は、組み込みの既定（空）で始まる（未決事項 8）。ある限度より古い写しは closed に
  倒すべきかは未決事項 13 である。
- **コマンドを解析できない:** 決定 2（合ったものとする）。
- **判定点が内部で panic するかタイムアウトする:** 届かないものとして扱う。

スナップショットは、台帳と同じくエージェントの uid で書ける。決定 9。

### 9. セキュリティ: エージェントの uid でのガードレールであり、サンドボックスではない

この層は事故と、プロンプトインジェクションで仕込まれた並び（「これを落として、それから push して」）を捕まえる。打ち破ろうと
するエージェントは止められない。強制するものすべてと同じ uid でエージェントが動くからである（build/07 §7.2）。具体的には次の
とおり。

- **エージェントが自分のポリシーを書き換える。** ポリシーは Workspace の中からは書けない。Agent はポリシーを変えるルートを出さず、
  出どころは CP である。それでもエージェントは台帳、スナップショット、pull したキャッシュ、claude の `settings.json`
  （`disableAllHooks` を含む）に書け、自分が始めるシェルで `AF_SESSION_NAME` を消せる。だから claude の強制のフックは、
  エージェントが書けない場所、つまりイメージの `/etc/claude-code/` の下の root 所有の新しい managed settings のファイルに置く
  （今そのディレクトリにあるのは `CLAUDE.md` だけである）。2.1.288 で managed のフックがユーザースコープの `disableAllHooks` を
  越えて残るかは P0 の関門である。台帳、スナップショット、キャッシュの整合性検査は事故に対するものでしかない。意図した
  エージェントに対しては守られず、ガイドはそう言う。
- **プロンプトインジェクション。** モデルが読む拒否の理由はポリシーを名指し、「利用者に尋ねよ」と言う。規則がどう照合されるかは
  決して説明しないので、仕込まれた指示は正確な難読化の仕方を知ることができない。カードは書かれたままのコマンドと解析した段を
  見せるので、メンバーはエージェントによる説明ではなく、実際に動くものを承認する。
- **止められない kind を通したすり抜け。** 決定 7 が起動を断る。`create_session` で起動した子を含め、すべての経路で断り、強制できない
  ポリシーを得た動いているセッションは止める。統制下のセッションの中で起動した入れ子の CLI（Bash からの `claude -p`）は
  `AF_SESSION_NAME` と managed のフックを受け継ぐので、親の台帳に照らして判定される。shell セッションは人の端末であり、統制しない。
- **子を通したすり抜け。** ゲートの旗は受け継ぐ（決定 4）。上限は未決事項 12 に答えが出るまで合算せず、ガイドは合算していると
  言ってはならない。
- **シェルを通したすり抜け。** `shell` の呼び出しは `edit` の呼び出しにできることは何でもでき、それ以上もできる。`path_scope` と
  `created_by_session` は構造化された編集しか見ない。シェルについても成り立たせたいポリシーは `shell` でも尋ねなければならない。
  エディタは封じ込めをほのめかすのではなく、その引き換えを示す。
- **判定点は裁定者ではない。** モデルを動かさず、ネットワークを呼ばない。ポリシーが呼び出しの安全性を LLM に尋ねることはできない。

### 10. kind が block と数えられる前の測定の関門

kind があるポリシーの型について候補から block に移るのは、AF が実際に使う起動フラグ（スキップのフラグ、trust、rtk のオンと
オフ）の下の本物のセッションが、次のすべてを示したときだけである。1 つでも落ちるか、測れない kind は observe のままである。

1. **被覆。** すべての呼び出しが差し込み口に届く。各 category（`read`、`edit`、`shell`、`web`、`mcp`、`agent`）、繰り返しの
   呼び出し、CLI 自身の許可リストや前の「常に許可」が許す呼び出し、CLI のサブエージェントがする呼び出し。
2. **判定。** `deny` は呼び出しを止め、モデルが理由を読む。何も出さなければ CLI 自身のモードに任せる。`ask`（あるなら）は
   スキップのフラグの下でも確認を出す。
3. **失敗。** フックがタイムアウトしたとき、kill されたとき、0 以外で終わったとき、壊れた出力を出したときに、呼び出しが動くか。
   これで、その kind に保持する ask（決定 6）を置けるかが決まる。
4. **改竄への耐性**（claude）: ユーザースコープの `disableAllHooks` の後も managed のフックが発火するか。
5. **順序。** ほかのフック（rtk）がコマンドを書き換える前と後のどちらを、ポリシーのフックが見るか。
6. **同一性。** 呼び出し id が、判定、完了イベント、再試行をまたいで安定しているか。
7. **予算。** § 性能の予算の数字。
8. **自前の ask**（kind 自身の確認が AF の保持する承認に代わる前に）: 自前の allow・deny・取り消しを呼び出し id に結び付けられ、
   呼び出しが動く直前に記録をもう一度評価できる。
9. **並行と停止。** 1 つのフックが待つ間に CLI が兄弟の呼び出しを動かすか、中断や停止が動いている呼び出しに何をするか、そして
   observe しかできない kind では、停止を決めてから CLI が終わるまでにいくつの呼び出しが通りうるか。

| kind | 関門の段階 | 注記 |
|---|---|---|
| claude Terminal | P0 | 項目 1–7 と 9。項目 8 は自前の ask の前（P1） |
| lcpp | P1 | 1、2、7 だけ。ハーネスは AF 自身のもの |
| cursor、kiro、copilot Managed | P1 | スキップのフラグを切ったときの 1 が決め手 |
| codex Terminal、copilot Terminal | P2 | codex では 2 が deny のみを示すと見込む |
| codex Managed、opencode、kiro と cursor の Terminal | P2 | まず差し込み口そのものを作る必要がある |

### 性能の予算

判定はツール呼び出しのたびに通る。測定: `workspace-agent --version` の起動は 17–33 ms（中央値 22 ms、20 回、1 つの Workspace、
2026-10-04）。これはプロセスの起動だけで、HTTP と永続化を含む判定ではない。下の予算は P0 が測らなければならないものであって、
この数字が証明するものではない。

- **判定点:** 評価について、p95 で判定 1 回 ≤ 2 ms、メモリの中で。fsync する台帳の追記（決定 4）と、`path_scope` での対象の
  `stat`/`realpath` は、コストがディスクに依るので、category ごとに別に測って報告する。
- **フックの端から端まで**（プロセスの起動、ローカルの HTTP、答え）: ツール呼び出し 1 回につき足される分が p95 で ≤ 50 ms。人を
  待つ時間は含めない。
- **呼び出しあたりのプロセス。** ポリシーの判定は呼び出し 1 回につきプロセス 1 つである。`edit` と `shell` の呼び出しでは既存の
  `permtool` の記録を吸収するので、それらの呼び出しはプロセスが増えない。`permtool` が発火しない `read`、`web`、`mcp`、`other` の
  呼び出しは 1 つ増える。claude のほかのフック（AskUserQuestion、ExitPlanMode、rtk、PostToolUse のハートビート）は別の
  プロセスのままである。P0 は category ごとに足される総コストを報告する。

P0 が守れない予算は黙って引き上げるのではなく、P0 を止める。

### 対象外

- セッションごとのネットワークの egress。egress は build/07 §7.8 が持ち、ここのポリシーはそこに欠けている柵の代わりにはならない。
- モデルやトークンの予算（#1054）。
- ツールの引数の書き換え。それは rtk がしており、ポリシーは決めるだけである。

## 退けた案

- **規則をモデルへのプロンプトにする。** Issue が置き換えたいのはこれである。プロンプトの中の規則はお願いであり、仕込まれた指示が
  それに勝つ。
- **呼び出しごとに CP で判定する。** すべてのツール呼び出しで、フックの予算の中に Agent→CP の往復が要り、CP の障害が統制下の
  セッションすべてを止めることになる（決定 8 はそれを最後の写しで済ませる）。
- **状態を転写から導く。** 転写は求められたときに数秒遅れで読むもので（決定 4）、ゲートのかかった呼び出しが先に動いてしまう。
- **P0 での汎用のポリシー言語（OPA/Rego、CEL）や利用者のスクリプト。** Rego は Agent ごとのランタイムと、メンバーが覚えなければ
  ならない言語を要する。スクリプトはあるテナントのコードを別のテナントの判定の経路で動かすことになる。CEL はサンドボックス化されて
  おり、利用者が書くポリシーの候補として残す（未決事項 10）。
- **代わりに各 CLI 自身のもっとも厳しいモードを入れる。** それは ADR 0056 のスイッチである。並びも上限も表せず、kind ごとに違い、
  いくつかの kind では中を確かめられない。
- **スキップのフラグを入れたまま ACP の要求に答える。** フラグが入っていると要求はそもそも送られない（cursor について測定済み、
  `workspace/agent/internal/agents/cursor/driver.go:20-24`）。
- **ポリシーに引っかからない ACP の要求をすべて自動承認する。** メンバーが ADR 0056 で選んだ確認を黙って消すことになる（決定 1 は
  それを保つ）。

## 結果

- 統制下のセッションのすべてのツール呼び出しの前に、新しいホットパスができる。そこのバグはそうしたセッションすべての作業を止める。
  だから予算と倒れ方をポリシーごとに持ち、測る。
- block のポリシーを持つセッションは、ACP の CLI をスキップのフラグを切って動かす。メンバーの選択が「スキップ」だったときは、
  スキップのフラグが答えたであろうものを判定点が答えるので、各 kind 自身の「尋ねる」集合を写さなければならない（P1 の関門）。
- claude の強制のフックはイメージの新しい managed settings のファイルに移るので、Workspace のすべての claude、メンバー自身が
  セッション無しで端末から動かす `claude` にも入る。`AF_SESSION_NAME` が無ければ、すぐに判定なしを返す。
- 動いているセッションが、強制できないポリシーの変更で止められることがある（決定 7）。
- `respond` は Terminal セッションの AF が保持する承認を受け付ける。Console の承認カードが Terminal セッションで初めて出る。
- `guide/ref/agents.md` に kind ごとの「ツールポリシー: block / observe / none」の行が加わり、権限の選択の行と同じく
  `scripts/docs-check.py` が kind の能力フラグと照らす。

## 利用者への未決事項

この記録が決めない、製品としての決定である。この設計が頼る測定はここには無い。それは決定 10 の関門である。

1. **層。** デプロイとユーザーの間にテナントの層が要るか（決定 3）。それとも Issue どおりのデプロイ → ユーザー → セッションか。
2. **セッションの層を誰が設定してよいか。** 起動ダイアログのメンバーだけか、`create_session` を通した親セッションやスケジュールも
   か。決定 3 は彼らに制限を足すことだけを許す。
3. **止められない kind。** 起動を断るか（書いたとおりの決定 7）、「observe のみ」のバッジと警告を付けて起動するか。
4. **答えの無い承認。** タイムアウトの後に拒むか（書いたとおりの決定 6）、スケジュールや子のような無人のセッションでは待たせたままに
   するか（どれだけの間か）。
5. **ポリシーが保持する承認への「常に許可」。** そもそも `turn` / `thread` のスコープを許すか。許すなら、決定 3 の境界、つまり
   メンバーは自分のユーザー層とセッション層のゲートは外せるが、デプロイやテナントのゲートは決して外せない、で正しいか。
6. **上限に達した。** それ以降の呼び出しをすべて拒むか（書いたとおり）、セッションを止めるか。そして決定 3 のセッションごとの例外を
   そもそも出すか、出すなら誰にか。上限を設定した層を編集できる人だけか、デプロイやテナントの上限についてメンバーにもか。
7. **observe のみの違反。** 通知だけか、ターンの中断もか。
8. **既定。** ポリシーを何も有効にせずに出すか（書いたとおり）、ダウンロードの後の push のゲートのようなデプロイの既定を 1 つ
   入れて出すか。
9. *（決定 10 へ移した。測定は決定ではなく関門である。）*
10. **利用者が書くポリシー。** 同じ閉じた文法を広げるか、後で CEL にするか。
11. **解析できないシェルのコマンド。** ゲートの旗を立てるか（書いたとおり）、自分について尋ねるだけか、カードでメンバーに選ばせるか
    （決定 2）。
12. **家系。** 上限を親、その子、そのフォークをまたいで合算するか、セッションごとに数えるか（書いたとおり）。同じ答えが #1054 の
    支出の予算にも使えるべきである。
13. **古いポリシーの写し。** CP に届かない間は最後の写しを無期限に効かせ続けるか（書いたとおり）、限度を過ぎたら closed に倒すか。
