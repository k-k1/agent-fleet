## 背景

Console にホーム画面が入り、続いて役割のプリセットが入る（#2026）。どちらも**メンバーに何を見せるか**を
決める。どちらも、既存の保存先では扱えない 2 つの状況で動く必要がある。

- **ワークスペースが停止している。** 左ペインとホームは、ワークスペースの起動前に表示される。
  `ui-prefs` はワークスペースの中にある（`workspace/agent/internal/uiprefs`）ので、起動するまで
  Console は読めない。
- **メンバーが別の端末を使う。** 初回カードは「あとで」と選んだトラックを `localStorage` に持つ
  （`af.onboarding.dismissed`、`af.onboarding.track`）。そのため、PC で閉じたようこそカードがスマホで
  また出る。

#2026 のもう半分はテナント既定値（既定のエージェント、既定の役割、起動の既定値など）である。テナントごとに
違うので、これはテナントの設定になる。置き場所が同じく必要になる。

## 決定

1. **設定は 2 種類あり、置き場所も 2 つ。** Agent が参照して動く設定は `ui-prefs` に残す。例は、起動時の
   検査で使う非表示のモデル、`skipPermissions`、起動ダイアログが挿入するテンプレートである。Console だけが
   読む設定は CP に置く。表示の状態と、ワークスペースの停止中に Console が読む必要のあるものがこれに当たる。
   同じ設定を両方に持たない。写しが 2 つあるとずれ、どちらが正しいかを示すものがない。
2. **身元単位ではなく、メンバーシップ単位。** 役割と既定値はテナントごとのもので、2 つのテナントに属する人は、
   片方では開発者、もう片方では SRE でありうる。行はすべて `membership_id` をキーにし、ルートはメモキューと
   同じ `withMembership` で解決する。この経路はワークスペースを作らない。
3. **メンバーシップごとに JSON 文書を 1 つ持ち、スキーマは閉じる。** テーブルは
   `member_ui_state(membership_id, state, version, updated_at)`。CP は未知のフィールドを拒否して
   （`DisallowUnknownFields`）デコードし、16 KiB を上限とする。列ではなく JSON 文書にするのは、
   キーが画面ごとに増え（今は初回の状態、次は役割のプリセットとヒント）、CP がそれで検索しないためである。
   開いた map にしないのは、誰も読み返せない物置になるからである。
4. **`PATCH` はトップレベルのキーを置き換え、それ以外には触れない。** 2 つのタブや 2 台の端末は、違うキーを
   書く（片方で初回カード、もう片方で今後のヒント）。文書全体の `PUT` だと、片方が気づかれずにもう片方を
   取り消してしまう。CP は楽観的な `version` のもとでマージする。行を読み、マージし、`WHERE version = ?` で
   書き、負けたら数回やり直す。これは `SELECT … FOR UPDATE` を使わずに、SQLite と Postgres で同じように動く。
5. **秘密ではなく、監査もしない。** これはメンバー自身の表示の状態である。秘密は入れない。P2 のテナントへの
   書き込みは管理操作なので、ブランチ命名ルールと同じく監査する。
6. **Console が `localStorage` を 1 回だけ移す。** CP の文書に `onboarding` キーが無く `localStorage` には
   ある最初の読み込みで、Console はそれを `PATCH ?if_absent=1` で送る。CP は、まだ持っていないキーだけを
   楽観的なループの中で確かめて埋めるので、2 つ目のタブからの遅れた送信が、その間に保存された値を取り消す
   ことはない。古いキーは、CP が受け取ったと確認できてから消す。`localStorage` は最初の描画のための読み取り
   キャッシュとしてだけ残し、(ユーザー, テナント) ごとに分ける。
   タブに自分の未確定の選択があるあいだは、送信を待つ。
   CP の応答が届いたらそちらが勝つが、次の防ぎを置く。
   - 持ち主が変わるたびに世代（epoch）を進め、応答は要求を出した世代のうちだけ使う。キーの比較だけでは、
     A→B→A と戻ったときに古い応答を受け入れてしまう。
   - PATCH は 1 本ずつ送り、作ったときのテナントを付けて送る。切り替えの時点でまだキューにある PATCH は
     送らない。送ると別のテナントの行に書き込んでしまう。
   - 未確定のキーはどの応答の上にも重ねて表示する。失敗したキーは重ねるのをやめるので、次の応答で CP の
     値が表示される。
   - 確定した PATCH より前に始まった GET は、その PATCH の応答を置き換えない。
7. **寿命はメンバーシップに従う。** 行は `deleteMembershipTx` で、他のメンバーシップ単位のテーブルと一緒に
   消える。受信箱と同じく外部キーは宣言しない。古い CP の物理削除は独自の削除リストを持っていて、知らない
   外部キーがあるとその削除が失敗するためである。
8. **テナント既定値の優先順位（P2）。** 低い方から、組み込み、テナントの既定値、管理者がメンバーごとに
   決めた値、メンバー自身の選択。実効値は CP が計算し、メンバー自身の `state` と並べて返す。規則を 1 か所に
   置くためで、Console は導き直さない。既定のエージェントには他の層がない。名指しするだけで何も
   制限しないので、メンバーが上書きするものがない。そのため応答には `defaults` としてそのまま載せる。
   `effective` は、層を持つ最初のキーである役割と一緒に加える。

## 段階

- **P1（実装済み）：** `member_ui_state`、`GET`／`PATCH /api/me/ui-state`、`onboarding` キー
  （`dismissed`、`track`）、Console のストア、`localStorage` からの 1 回限りの移行、そして最初の読み手としての
  ホーム（#2028）。
- **P2（実装済み）：** キー `agent` を 1 つ持つ `tenant_member_defaults`。テナント管理者がテナント設定 →
  メンバーの既定で設定する（監査は `tenant.member_defaults`）。メンバーは `GET /api/me/ui-state` の
  `defaults` で読み、初回カードの接続の手順がそれを名指しする。どのエージェントでも手順は完了になる。
- **#2032 へ移した：** 役割のプリセットのテナント既定値、管理者がメンバーごとに決める役割、メンバー自身の
  選択、`effective`（決定 8）。効果の見えない役割は何もしない設定になるので、それを読むプリセットと一緒に作る。
- **P3：** 起動の既定値、チームのリポジトリ、秘密ではない運用ツールの設定値（#2032・#2033 と一緒に）。
  未解決の問い：テナントの起動既定値は、そのいくつかを強制する Agent にどう届くか（決定 1）。ダイアログに
  入れるだけにするか、`ui-prefs` の初期値にするか。

## 結果

- Console の起動時の要求が 1 つ増える（`GET /api/me/ui-state`）。CP のデータベースだけで答えるので、
  ワークスペースを待たない。
- メンバーの初回の状態が、端末をまたいでついてくる。
- Console だけが使う状態を今後足すとき、置き場所がはっきりする。ここに置くべきかどうかは、決定 1 で判断する。

## 追記（2026-11-12）：P3 の未解決の問いを決めた

テナントの起動既定値が Agent にどう届くかは、利用者が次のように決めた。**起動ダイアログと「開始」
画面の初期値に入れるだけにする。** Agent の `ui-prefs` には書かず、初期値にもしない。Agent はこれまで
どおり自分の `ui-prefs` を適用する。決定 1 は変わらない。1 つの設定が 2 か所に置かれることはない。

- テナントの 3 つのグループ（起動既定値、チームのリポジトリ、秘密ではない運用ツールの設定値）は、
  `tenant_member_defaults` と同じ管理者向けエンドポイント、同じ `tenant.member_defaults` の監査を
  拡張する。起動時のエージェントは、文書にすでにある `agent` を使う。
- メンバー自身の上書きは Console だけが使う状態なので、決定 1 と 3 に従い、`member_ui_state` の
  閉じたスキーマの `launch` キーと `ops` キーに置く。
- 優先順位は決定 8 のまま（組み込み、テナントの既定値、メンバー自身の選択）。CP が項目ごとに層を重ね、
  結果を `defaults` の隣に `effective` として返す。Console はそれを読むだけで、自分で導き直さない。
- 可用性は branch-rules の先例（0103 決定 10）に従う。Console は最後の応答を (ユーザー, テナント) ごとの
  キャッシュに持つので、ワークスペースが停止中でも CP に届かなくても、ダイアログと「開始」は最後に
  知っている値を使う。
- 運用ツールの設定値は狭く検証する（資格情報・クエリ・フラグメントを含まない https の URL、12 桁の
  アカウント ID、ロール名）。秘密が入る欄はなく、秘密はメンバーごとのまま。
