# 0089. 量子化リポジトリごとに 1 枚のカードと、ダウンロード前に答える「収まるか」

[English](0089-quantisation-ladder-and-fit.md) | 日本語

- Status: **accepted**（2026-09-18）。同じ変更で実装済み。「ある」「ない」はすべて `2939551d`
  （develop、ADR 0088 マージ済み）への grep で確認し、「実測」はすべて同日に上流の API か実物の
  GGUF ヘッダを直接読んだ。
- 前提: [0088](0088-model-catalogue-names-and-examples.ja.md)（カードの名前と分類。本 ADR は
  チャット役割についてそれを 1 段細かくする）、[0072](0072-engine-model-catalog.ja.md) 決定 3
  （窓はモデルごと）、[0074](0074-engine-instance-classes.ja.md) 決定 6（モデルがカードに何を
  要求し、それがどれだけ分かっているか）。

## 背景

報告は 2 つ、根は 1 つ。

**「別の量子化を足すのに、配布元をもう一度探さないといけない」。** GGUF のリポジトリは 1 つの
モデルを十数のサイズで出したものだ。`unsloth/Qwen3.8-27B-GGUF` を実測（2026-09-18）: `.gguf` が
30 個——`UD-IQ1_S`（6.19 GB）から `BF16` まで量子化が 14 種、ほかに importance matrix 1 つと
vision projector 2 つ。目録は量子化ごとにカードを 1 枚描き、互いの関係は何も描かず、2 つ目の
サイズに至る道は `探す` タブで配布元名をもう一度打つことだけだった。

**「どのファイルを選んでも `KV キャッシュ 66560 MiB` と出る。22,000 MiB では絶対動かない」。**
計算は正しく、入力が間違っていた。

- 実物のヘッダを読んだ（2026-09-18）: `UD-IQ4_XS` と `UD-Q2_K_XL` は `block_count` **65**、
  `head_count_kv` **4**、`key_length`/`value_length` **256**/**256**、`context_length`
  **262144**。`65 × 4 × (256+256) × 262144 × 2 バイト` はちょうど **66,560 MiB**。
- リポジトリ内でほぼ一定に見えるのは、KV キャッシュがアテンションの形と窓だけで決まり、重みの
  量子化はどちらも変えないから。そして llama.cpp はキャッシュを f16 で持つ（`LlmExtraArgs` の
  既定は `-ngl,99,--jinja,--no-mmap` で `-ctk`/`-ctv` はサーバに届かない。画面が明言している
  f16 の仮定は、この配備については正しい）。ただし**厳密には一定ではない**: `UD-IQ2_XXS` と
  `UD-IQ2_S` は 64 ブロックなので 65,536 MiB。差 1.6%、画面では見分けがつかない。
- **262,144 は誰も選んでいない。** `adminEngineAdd.tsx` が窓のフィールドに `context_length` を
  既定で入れていた。CP はその値に自分で警告を付けて送っている（`engine_admin.go`）——
  *「a ceiling, not a setting — the 30B in this deployment publishes 262144 and is run at 32768」*。
  画面はその上限を設定値として使い、その値でキャッシュを見積もっていた。

窓 32,768 なら同じ数字は 8,320 MiB になり、22,000 MiB のカードは `UD-IQ1_S` から `UD-IQ3_XXS` まで
余裕を持って収まる。画面は、動くモデルについて「無理だ」と言っていた。

運用者が挙げた先行例は Hermes Agent のローカルモデル選択で、ダウンロード前に量子化ごとに
*VRAM に収まる* / *システム RAM を使う* / *このマシンには大きすぎる* を出す——そして公式
ドキュメント自身が「これは推定で、実行時に食い違うことがある」と認めている。3 状態のうち 2 つ目は
**ここには移植できない**: エンジンは GPU インスタンスで `-ngl 99` 固定なので、溢れる先のホスト RAM
が無い。3 つ目には、こちらに「大きすぎる」より良い答えがある: この配備は箱を**買う**のだから、
梯子の次の段を名指しできる。

## 決定

### 決定 1 — チャットの行は**配布者**ではなく**リポジトリ**で分類する

ADR 0088 決定 3 は GGUF を `display_name` の最初のセグメントで分類した。段が 1 つ間違っていた:
unsloth が両方出しているというだけで `Qwen3.8-27B` と `Gemma` が同じ山に入り、分けるべきものは
何も分かれなかった。グループはリポジトリ id 全体になり、見出しはそのうち何件が手元にあるかを言う。

行は量子化ごとに 1 つのまま。統合できない: `--models-max 1` は 1 度に 1 つしか持たず、利用者が
「速い」と「良い」を選ぶというのはその 2 つを選ぶことなので、それぞれに id と窓と有効/無効が要る。

リポジトリのグループの中では、カードの見出しは**量子化**（`UD-IQ2_S`）にする。リポジトリはその上の
見出しだからだ——両方のカードをリポジトリ名で呼ぶと、1 つのモデルの 2 枚のカードが同じ名前を名乗る
（テストではなく、実描画した画面で見つけた）。

### 決定 2 — サイズの梯子を 1 押しで開き、行ごとに可否を描く

グループの見出しの下で `POST …/ingest/files` がリポジトリを一覧する。量子化が全部並び、取り込み
済みには印が付き、残りには `追加` が付く。押すと通常の取り込みダイアログが記入済みで開く。

🔴 **押したときだけ。マウント時ではない。** 8 つのリポジトリを持つ目録を先読みすると、誰も頼んで
いない上流一覧 8 回とレンジ読み 8 回になる。相手は 503 で負荷を落とすサイトだ（ADR 0085 の検索
リトライ）。ADR 0088 決定 4 と同じ規則、同じ理由。

🔴 **入口はダイアログ 1 つのまま。** 梯子のボタンが埋めるのは**フォーム**だ——ダイアログ自身の
`initialRef` に Hugging Face の blob URL を渡す。これはダイアログがすでに解析している形である。
リクエストは組み立てない。計画も価格もライセンスも今まで通り同じ画面に出る。取り込みを始める
2 本目の道、しかもそれらを飛ばす道は作らない。

*（作りながら実測: この URL を `hit.ref` に載せて渡すと `revision:
"https://huggingface.co/…"` が上流に飛んだ——`hit.ref` は HF のリビジョンだからだ。だから専用の
prop にした。）*

### 決定 3 — 判定は「重み＋KV」対クラスの 3 状態で、入らないときは次の段を名指しする

`engineFit.ts` が 3 つの呼び出し元（取り込みフォーム・梯子・行）の計算をまとめて持つ。

| 状態 | 条件 | 表示 |
|---|---|---|
| `fits` | クラスの VRAM の 85% 以下 | 収まります |
| `tight` | 85〜100% | ぎりぎり（n%） |
| `over` | 100% 超 | このクラスでは入りません（収まる最小の段があればその名前も） |

85% は測定値ではなく**予備**だ。数えているのは重みと KV キャッシュで、数えられないのは llama.cpp の
計算バッファと CUDA コンテキスト——バッチサイズ依存で、どのヘッダにも書かれていない。間違えると
何を払うかは ADR 0074 が実測している: L4 が重み 17 GB を載せた後、
`cudaMalloc failed: out of memory ... failed to allocate buffer for kv cache` で死んだ。押してから
4 分、GPU 1 台ぶんの後に。だから 99.6% を「収まります」とは言わない。見積もりが**含まないもの**は
表の上に 1 度だけ書く。

次の段を名指しするのは Hermes Agent に対応物が無く、この配備にはある部分だ。自分で箱を買うので
「このマシンには大きすぎる」は事実ではなく決定になる。

🔴 KV が読めなかったときに `unknown` にするのは、**重みがまだ収まっている間だけ**。重みだけで
カードを超えたら、キャッシュがいくつでも救えない。レンジ GET に答えないリポジトリの、いちばん
大きい量子化が肩をすくめて隠れることになる。

### 決定 4 — 窓は画面に出す操作子にし、既定は「箱に収まる最大」にする

フィールドを `詳細設定` の折りたたみから出し、それが決める判定のすぐ隣に置く。既定値は、選択中の
クラスで「余裕のある線」を割らない最大の 2 冪。モデルの公開上限はその横に、上限として描く。

2 冪なのは、モデルカードがその単位で書かれていて、人が打つのもその値だから。37,491 を提示するのは
算術的には正しく、機械が独り言を言っているように読める。

棄却——32768 固定。この配備が 30B を実際に走らせている値だが、両方向に間違う: 46 GB のクラスでは
無駄に小さく、カードとほぼ同じ大きさのモデルでは依然として不可能。棄却——空欄。正直だが、
「ではいくつにすればいいのか」に何も答えない。それはこの画面が答えるべき問いだ。

梯子の上の窓は、そのリポジトリの行が実際に宣言している値から取る。編集すると表が引き直され、
**何も書かない**: 行の窓は行の持ち物で、行の上で編集する。

### 決定 5 — 一覧はモデルでないものを**分類する**。落としはしない

`engineCandidate.Role` は `model` / `projector` / `imatrix` で、ファイル名から読む。梯子は
`model` だけを描く。手動のファイル選択は全部を出したままにする——探しに来た人からファイルを隠すのは、
この一覧がそもそも直すために作られた古いほうの欠陥だからだ（ADR 0072: 1 文字足りない名前は、
存在しない名前と見分けがつかない）。

分割片（shard）はこの語彙に無い。`engineIngestWanted` が ADR 0072 以来 `-00002-of-00003` を落として
いる。

ヘッダでなく名前で判定するのは意図的だ。30 ファイルを分類するのに 30 回レンジ読みするのは、この
画面の価値に見合わない。間違えても、運用者が開き直せるグループに 1 行畳まれるだけである。

### 決定 6 — ヘッダ 1 回でリポジトリ全体を値付けし、どのファイルから読んだかを言う

一覧は `kv_mib_per_1k_tokens` と `kv_from` を返す。1,024 トークンあたりなのはキャッシュが窓に
線形だからで、1 つの数字が誰が打ったどの値にも答え、式は 1 か所に留まる。

🔴 これはリポジトリ全体の**見積もり**で、読んだファイル名を名乗る。1 つのリポジトリの版どうしでも
形が完全には同じでないからだ（上の実測、64 対 65 ブロック）。実際に取り込む行は resolve で自分の
ヘッダを読み、押下はその数字で値付けされる。

### 決定 7 — 依然として管理者の目録だけ

ADR 0088 決定 5 はそのまま: `engineCatalogModelRow` は無変更なので、モデルを選ぶ利用者にはいまも
id が見え、可否は見えない。帰結を改めて書いておくのは、本 ADR がそれを鋭くするからだ——配備は
1 つのモデルの `UD-IQ2_XXS` と `UD-IQ2_S` を同時に持てるようになり、起動メニューには 4 文字しか
違わない 2 つの id が、どちらが何かを言うもの無しに並ぶ。

## 実測したこと

| 主張 | 方法 |
|---|---|
| 27B の KV は公開上限で 66,560 MiB、32,768 で 8,320 MiB | `unsloth/Qwen3.8-27B-GGUF` の実 GGUF ヘッダ 4 ファイルをレンジ GET、2026-09-18 |
| 1 つのリポジトリの版どうしで形が違う（64 対 65 ブロック） | 同じ 4 回の読み取り |
| そのリポジトリは `.gguf` を 30 個、うち imatrix 1・projector 2 | `GET /api/models/unsloth/Qwen3.8-27B-GGUF?blobs=true`、2026-09-18 |
| この配備は `-ctk`/`-ctv` を渡していない＝キャッシュは本当に f16 | `deploy/aws/ecs/cfn/60-engines.yaml` の `LlmExtraArgs` 既定値 |
| 2bit の 27B は 22,000 MiB に窓 32,768 で収まり、4bit は収まらない | 上の 2 つを `engineFit.ts` に通した結果 |

## 追記 — 自動判定を「登録時だけ」から「行の一生」へ（2026-09-19）

利用者からの指摘: **LLM の知識が無い人に、モデル導入時にこれらの数字を入力させるのは無理**。
選んでいるインスタンスでそのモデルが動くのか、どれだけコンテキストが使えるのかが
**自動で決まり、画面に出て、設定された状態で、すぐ使える**のが望ましい。

この ADR の設計はまさにそれだったが、3 か所で成立していなかった。

### 1. 自動計算が 4 倍外していた

`kv_mib_per_1k_tokens` は `engineKVCacheMiB` そのもので、その式がハイブリッドな系統で
4 倍過大だった（ADR 0074 の 2026-09-18 追記）。稼働中の CP に acrt と同じモデルを解決させた
実測: `kv_mib_per_1k_tokens = 260`（正しくは 64）。同じ 27B・同じ L4 で
`windowThatFits` が提示する窓は **16,384 → 65,536**。**画面が 4 倍控えめに嘘をついていた。**

### 2. 収まる窓が出せない時に「上限」を入れていた

```ts
windowThatFits(...) || found.context_length   // ← 失敗時は上限
```

この ADR が止めようとした当のもの（262,144 をそのまま設定）に、エラー経路から戻っていた。
af-sandbox にその形の行が残っていて、実際に 16 GiB の KV を要求して L4 が落ちている。

**0 も答えにならない**——0 は「未宣言」として opencode まで伝わり、opencode は文脈 0 を
「自動コンパクション無効」と読む（`opencode/engine.go`）。セッションはエンジンに拒否される
まで走る。小さい窓より悪い。

→ `windowWhenUnsized`（32,768 を上限で丸めたもの）を**フォールバックと名乗った上で**入れる。

### 3. 登録済みの行には判定が無かった

編集ダイアログは素の数値入力が 3 つ。**後から直すには KV の見積もりを暗算するしかない。**

→ 追加フォームと同じ `modelFit` の判定と、`windowThatFits` の結果を 1 押しで適用する
ボタンを置いた。そのために CP が登録済み行にも `kv_mib_per_1k_tokens` を載せる。

さらに **`context_length`（アーキテクチャの上限）は保存されていなかった**。解決時に読んで
画面に出すだけで、行が出来た瞬間に失われていた。上限が無いと再フィットの探索に上界が無く、
**そのモデルが訓練されていない窓を提案してしまう**。移行 0070 / pg 0055 で
`context_ceiling` を追加し、取り込み時に書く。🔴 保存するが**適用はしない**——
何が許されるかと何が載るかは別の問いで、答えるのは前者だけが配布元の仕事。

上限を持たない既存行には**ボタンを出さない**。上界の無い提案より、提案しないほうがよい。

### 残っている穴

- **既存行の幾何は空のまま**（`vram_need_source: floor`）。バケツのオブジェクトから
  GGUF ヘッダを読み直すバックフィルが要る。これが入るまで、既存行は再フィットを提案されず、
  ADR 0074 追記の番人が毎回確認を求める。
- **インスタンスの段を変えても窓が追随しない。** 窓は登録時の `class.vram_mib` に対して
  1 回だけ計算される。段を上げた時に各行を再フィットして提示する導線はまだ無い。

### A の実装 — 幾何は「バケツからも」読む（2026-09-19）

`engine_gguf.go` の冒頭が自分で認めていた穴:「バケツから登録された行にはこの読み手へ至る道が
無いので、幾何は不明のままで VRAM 見積りは重みだけになる」。**両配備の llm 行は全部その状態**
で、だから全部 `vram_need_source: floor` を返し、重みだけはどのカードにも収まるので
262,144 を宣言した行が無言で有効化できていた。

道を 1 本足した。`engineGGUFGeometryOfObject` が `engineStorageMetadataPort.Prefix` で
オブジェクトの先頭 64 KiB（足りなければ 1 MiB）を読み、同じ `parseGGUFGeometry` に通す。
隣の `engineVaeOfObject` と同じ形、同じ「静かに失敗する」約束。

呼ぶのは 2 か所:

- **登録時**（`POST …/models`）——上流 URL が無いこの経路で、VAE の判定と並べて読む。
- **有効化のとき**（`healGeometry`）——幾何を持たない行への loading な書き込みで 1 度だけ読み、
  保存する。判定の**前**に走るので、直った行はその場で確認を求められずに通る。操作者から見ると
  何も増えない。

`context_length` も同じ走査で読むようにした（`engineKVGeometry.Ceiling`）。上限が無いと
再フィットの探索に上界が無く、訓練されていない窓を提案してしまうため。

これで「導入したらすぐ使える」が既存行にも成立する。残るのは B（段を変えた時の再フィット）。
