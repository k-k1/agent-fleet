# 0105. 停止は実行中のターンを終えてキューへ進む。2 回目の停止が残りを終える

[English](0105-stop-continues-into-the-queue.md) | 日本語

- 状態: **accepted**（2026-09-30）・未実装（#1289）。実測は [docs/log/127](../log/127-cli-stop-with-queued-input.md)。
  2 段階にする形は #1258 の議論での利用者の提案で、その後の実測で、測った場面では claude と codex がそう動くと分かった。
- Follow-ups: #1289（実装）、#1256（未測定の CLI）、#1255（再起動を越えて残るキュー）
- 置き換え: docs/log/27 §12.2-4（「停止の意思はキューに及ぶ」）。[0041](0041-cross-session-messaging.ja.md) の
  補遺 2026-09-30 の決定 1（停止を生き残るのは peer メッセージだけ）を改める。
- 関連: docs/log/125 §4、docs/log/126 §4

## 背景

チャットの **実行を停止（Esc）** は、今は実行方式によって 2 つの違う意味を持つ。

- **Terminal（CLI）**: CLI に Esc を送り、CLI が決める。実測（docs/log/127、それぞれ 1 回）:
  - claude 2.1.285 と codex 0.159.2 は、実行中のターンを止め、**積まれた入力をその場で送った**。claude は積まれた
    2 件を 1 つのリクエストに入れた。codex は画面で「press esc to interrupt and send immediately」と案内する。
    2 回目の Esc はそのリクエストを止めた。
  - opencode 1.18.33 は Esc が 2 回要る。積まれた入力を流さずに履歴へ残し、次のプロンプトと一緒に載せた。
- **Managed**: どのドライバの `Interrupt` も、ターンを止めて**利用者自身が積んだ入力を捨てる**。別のセッションからの
  メッセージ（`KeepOnInterrupt`、ADR 0041）だけが生き残り、次のターンとして始まる。

Managed の規則は peer メッセージより前に書かれたもので、いちばん多い場面を取り違えている。実行中に追い打ちを
積むのは、たいてい実行中のターンを正すため（「違う、X をして」）だ。訂正を今すぐ効かせようとターンを止めると、
その訂正が捨てられる。規則は一貫してもいない。peer メッセージは続き、利用者自身の入力は続かない。同じセッションを
Terminal と Managed で切り替えると、同じボタンで逆の結果になる。

逆向きの要請もある。Managed のセッションには、時間と競争せずに**1 つの操作で全部を止める手段**が常に要る。
止めたターンが成功した前提の追い打ち（「それからデプロイして」）が、先に止める手段のないまま続いてはいけない。
Terminal の経路ではキューが CLI の中にあり、Agent Fleet はそこでこれを約束できない（決定 6）。

同じ `Interrupt` は、停止と書かれていない操作の裏にもある。計画の却下と、別の場所での計画レビューの起動は、
Console の停止を送る。codex では、質問のキャンセル・拒否も `Interrupt` を呼ぶ。

## 決定

### 決定 1: 1 回目の停止は実行中のターンを終え、キューは続く

`Interrupt` は実行中のターンを止め、それ以外には触れない。積まれたものは、利用者自身の入力も peer メッセージも
同じく、止めたターンが落ち着いたあと次のターンとして始まる。Managed のドライバが peer メッセージに対して既に
していることであり、測った場面で claude と codex がしたことである。

- 積まれた入力は**1 件ずつ 1 ターン**で、順番に走る。claude は積まれた 2 件を 1 つのリクエストに入れたが、それは
  採らない。peer メッセージの封筒と転写の `source: peer` が、利用者の文章に混ざってしまう。
- `TurnInput` は**出どころ**を持つ。語彙はミラーの注入の印（`recordInjection`）のもので、利用者、peer とその送り手の
  セッション、spawn、operator（`report_to`）、スケジュール、チャットブリッジである。これが `KeepOnInterrupt`
  （「利用者ではない」としか言わない）を置き換える。今は出どころがドライバまで届かないので、**`TurnInput` を作る
  すべての場所がそれを付ける**:
  - `/turn` の start と steer（Console の入力欄）: 利用者
  - `/input`: peer、operator、スケジュール、spawn。今 `badgeOriginOf` が印のために決めているとおり。何も決まらない
    とき（印の無い送信）は利用者
  - `injectSessionPrompt` / `injectManagedPrompt`: チャットブリッジ（ブリッジ）と自動再開（`abort_resume.go`、
    自動再開）が共用するので、出どころを引数で受け取る
  - `create_session` の初回入力: `noteCreateOrigin` の分岐どおり、operator（`report_to`）、スケジュール（手動実行を
    含む）、spawn、利用者（通常の Console からの起動と引き継ぎ）
  - 持ち越した回答の再送（`sendManagedPrompt`）: 利用者

  決定 2 と 4 の**利用者の入力**とは、出どころが利用者かブリッジのもの、つまり人がこのセッションの利用者として
  打った入力である。それ以外は、自動再開も手動で走らせたスケジュールも含めて、利用者の入力ではない。
- **ほかにターンが走っていないときに**開始を送り出し中の入力は、キューではない。止めようとしているターンそのもので
  ある。1 回目の停止はそれを止める。muse（`stopStarting`）と codex（`stopStart`）は、ランタイムがターンを名指し
  した時点で既にそうしている。開始が失敗したなら、ターンは作られておらず、止めるものは無い。開始の失敗は今と同じく
  表示する（codex はエラー付きの失敗したターンを足す）。
- **実行中のターンの後ろで**待っている入力は、どこで待っていてもキューにある。ドライバのキュー、ポンプが保持して
  いるもの（opencode。別のクライアントのターンの後ろで、まだ送っていない）、muse のホスト側のキュー（送ってある）で
  ある。1 回目の停止では続き、2 回目の停止では止まるか捨てられる。取り除いたり戻したりできる（決定 4・5）のは、
  まだ取り消せる（決定 3）入力だけである。

### 決定 2: 2 回目の停止は停止エピソードを終え、残りを捨てる

何かを積んだまま終わる 1 回目の停止は、**停止エピソード**を開く。ドライバはエピソードを専用の項目に、`accept` と
同じロックの下で記録する。表示用のターンの状態は使わない。`accept` はその状態を上書きする（codex、opencode、ACP の
ドライバは `queued` にする）ので、`interrupting` の間に送信が来ると、2 回目の停止が 1 回目に化ける。

- エピソードは、**キューが空になり、エピソードが始めた最後のターンが落ち着くまで**続く。積まれた入力がいくつあっても同じである。
- **利用者の新しい入力が受け付けられた**（決定 1）ときにも終わる。ターンを始めても、積まれても同じである。
  ほかの出どころの入力では終わらない。断られた送信も、再送も数えない。再送かどうかは、受け付けの時点で
  `ClientMessageID` を ledger に記録せずに引くことと、既に積まれている ID との照合で決める。copilot、cursor、kiro、
  lcpp はポンプが取り出すときにしか ledger に記録しないので、`accept` だけでは再送と新しい入力を区別できない。
- **エピソード中の停止はすべて 2 回目の停止である。** 実行中のターン、または送り出し中の入力を止め、**まだ積まれて
  いるものをすべて捨てる**（peer メッセージも含む）。そしてエピソードを終える。
- エピソードの外の停止は 1 回目の停止である。

判定は状態で行い、**時間では行わない**。Console のポーリング、スマホの遅延、遅いモデルのどれもが「N 秒以内に
2 回」を当てにならなくする。続いたターンが 1 分走ってから気付いた利用者でも、それを止められなければならない。

Console の停止の操作は、**停止の要求が返ってくる前でも使える**ようにする。今の `sendInterrupt` は `sending` を立て、
最初の要求が返るまでボタンを無効にする。2 回目の停止が要るのは、まさにその間である。

### 決定 3: 1 つの操作で全部止める

停止の操作は、そのメニューに**常に** 2 つ目の操作を持つ。**停止してキューを捨てる**である。Console に積まれた
ものが見えている間は目立たせるが、見えていなくても出しておく。前回のポーリングが映していない入力が、サーバの
キューには既にあるかもしれないからである。これが背景の求める緊急ブレーキで、時間に依存しない。

- 送るのは `/turn {"op":"interrupt","discard_queue":true}` である。ドライバは、エピソードの状態にかかわらず、
  `accept` と同じロックの下で、送っていない入力をすべて捨て、実行中のターンを止める。ただの `interrupt` はこれをしない。
- **取り出しただけでは送っていない。線はロックの下で引く。** どのドライバも、項目をキューから取り出すことと送ることを
  2 段で行い、その間でロックを放す（ACP のポンプは `session/prompt` の前、muse の `beginStartLocked` は `turn/start`
  の前、opencode の解放は `/message` の前）。取り出した項目は**取り消せる**か**確定した**かのどちらかである。ポンプは、
  ランタイムを呼ぶためにロックを放す前の最後の操作として、捨てる操作に取り消されていなければ、項目を取り消せるから
  確定したへ移す。先にロックを取った捨てる操作はその項目を取り消し、それは決して始まらない。確定の後に来た捨てる操作は、
  その項目を送ったものとして扱う。印を確かめてからロックの外で送るのでは足りない。その間に捨てる操作が入り得るから
  である。今の opencode の `abortAsked` の確認もこれにあたる。
- 確定した項目は、ランタイムがそれを持った時点で**受領済み**に進む。停止を届けるのはそのときであって、その前では
  決してない。入力を追い越した取り消しは何も見つけられず、入力を走らせてしまうからである。muse と codex では、
  その時点はランタイムがターンを名指ししたとき（`turn/started`、`turn/start` の応答）である。
- 引き継ぎはロックの下で決め、停止を届けるのは必ずどちらか一方だけにする。確定した項目を見つけた停止は**停止待ち**を
  立て、届けるのをポンプに任せる。ポンプは項目を受領済みにするとき、停止待ちが立っていれば自分で停止を届ける
  （muse の `stopStarting`、codex の `stopStart`）。既に受領済みの項目を見つけた停止は、
  自分でただちに届ける。どちらの側も、1 度確かめて立ち去ることはしない。
- **ACP と opencode にはそのような時点が無い**ので、確定した項目の停止はできる限りのものにとどまる。
  - ACP: `session/prompt` はターンが終わるまで応答しない。要求を子プロセスの stdin に書き終えたことは、ランタイムが
    ターンを登録したかについて何も言わない。その直後に書いた `session/cancel` が先に処理されると、何も見つけられず、
    プロンプトを走らせてしまう。ドライバは書き終えた時点を境に同じ引き継ぎを行い、そこで `session/cancel` を送る。
    書いた直後の取り消しの順序は測っておらず（docs/log/127 はこれを何も測っていない）、ACP のランタイムごとに測る
    までは停止を約束しない。
  - opencode: serve の `/session/status` はセッションが実行中か待機中かを報告するだけで、この入力と結び付ける ID を
    持たず、`/message` はターンが終わるまで返らない。したがってポンプは、serve が持っているのがこの入力か、別の
    クライアントのターンかを区別できない。短いターンは一度も見えないこともある。実行中の報告で送った中断が別の
    クライアントのターンに当たることがあり、入力はその後に走り得る。
- **いつでも届く。** 走っているか、何かが積まれている Managed のセッションでは、この操作に常に届く。質問や承認の
  カードが出ている間も含み、カードのキャンセルには頼らない。今は質問が保留中の間、停止ボタンが描画されない。codex
  の質問は、後ろに入力が積まれたまま出ることがある。
- **このブレーキが保証すること**: 捨てる操作がロックを取った時点でまだ確定していなかった入力は、このあと 1 つも
  始まらない。確定した入力は、ランタイムがそれを持った時点で止める（上記）ので、止まる前に最初の一歩を踏み出し得る。
  その停止は muse と codex では約束され、ACP のドライバと opencode ではできる限りのものである。
  このドライバが始めていないターンの後ろに muse のホスト側で積まれた入力は、`turn/unqueue` を測るまでは保証の外である。

### 決定 4: 捨てたものは、ドライバから戻ってくる

ドライバは、2 回目の停止（または決定 3）が捨てた項目を、セッションごと・**捨てた操作の ID ごと**に、利用者が
それを戻すか片付けるまで持つ。あとで捨てたものが前のものを置き換えることはない。1 セッションで持つのは直近 5 回
分までで、それを超えたら古いものから落とす。それをセッションのメッセージの応答に、`queuedPrompts` と並べて出す。`/turn interrupt` の
応答も同じ一覧を返すが、Console はそれに頼らない。タブを閉じたり接続が切れたりして応答が失われても、次の
ポーリングで取り戻せる。

各項目は本文、添付、出どころ（決定 1）を持つ。ここに入るのは、捨てたときにまだ取り消せた（決定 3）入力だけである。

Console は通知を出す（例:「停止しました。キュー済みの 2 件を取り消しました」）。通知には、捨てられた
**利用者の入力**を入力欄に戻す操作を付ける。戻すのは 1 件ずつ続けて入り、何も送らない。ほかの出どころ（peer、
operator、スケジュール）の捨てた入力は、同じ通知に出どころごとに並べる。利用者が書いたものではないので、入力欄には
戻さない。戻すか片付けると、ドライバにその捨てた分を落とすよう伝えるので、ほかのタブも次のポーリングでその操作を
出さなくなる。それまでに 2 つのタブがそれぞれ自分の下書きに文章を入れることはあり得るが、二重に送られることは
ない。送るのは利用者自身の操作で、新しい `ClientMessageID` が付く。

限界: 持っておく項目は Agent のメモリにあるので、キューそのものと同じく Agent の再起動で失われる（#1255）。
6 回目に捨てると最も古いものが落ちる。この決定はそれ以上の保護はしない。

### 決定 5: 停止しなくてもキューを編集できる

チャットの **キュー済み** の吹き出しに、2 つの操作を付ける。入力欄に取り戻すことと、取り除くことである。
claude の「Press up to edit queued messages」に相当し、追い打ちを 1 件だけ取り消す正確な手段である。

- 積まれた項目はすべて ID を持ち、その ID が吹き出しまで届く。今の `queuedPrompts` は本文しか運ばない。ID は、
  項目に `ClientMessageID` があればそれ、無ければドライバが採番したものである。
- 新しい `/turn` の op が、ID で項目を取り除く。**取り消せる間**、つまり積まれているか、ポンプが取り出したがまだ確定して
  いない（決定 3）間に限る。同じロックを取り、同じ確定点を使うので、取り除きと捨てる操作は同じ線を引く。応答はその項目か、
  確定した後の `already_started` である。別のタブの古い吹き出しからの操作にも同じ答えが返る。
- Console は、取り除けたときだけ本文を入力欄に戻す。もう一度送るのは新しい送信で、新しい `ClientMessageID` が付く。
  取り除いた項目の ID は二度と使わない。受け付け時に ledger へ記録するドライバでは、再送が重複として捨てられるからである。
- 確定した項目とランタイムに既に送った項目（決定 1）は表示するが、操作は付けない。

### 決定 6: Terminal（CLI）セッションは CLI 自身の振る舞いのまま

Terminal の経路では、停止は CLI への Esc のまま、2 回目の押下は 2 回目の Esc である。測った場面では、claude と
codex は 1 回目の Esc で積まれた入力を送り、2 回目の Esc はそれを運ぶリクエストを止めた。CLI の中のターン境界は
見ていない。リクエストの実行中に claude の巻き戻しメニューは開かなかった。その場面では 1 回目の Esc のあとに
積まれたものが残っておらず、2 回目の Esc がさらに積まれた入力も捨てるかは見ていない。Agent Fleet はこの経路に
独自のキューもエピソードも足さず、決定 3 の捨てる操作もここでは出さない。キューは CLI の中にあり、Agent Fleet には
空にできないからである。opencode の Terminal の振る舞いは違う（積んだ入力が履歴に残る）が、CLI のものとして残す。

### 決定 7: ほかのどの操作がこの規則に従うか

- **計画の却下**と**別の場所での計画レビューの起動**は Console の停止を送る。Managed では決定 1 と 2 に従う。
  Terminal では停止は Esc であり、CLI が決める（決定 6）。
- **質問のキャンセル・拒否**が `Interrupt` に届くのは codex だけなので、そこで決定 1 と 2 に従うのは codex だけである。
  ほかのドライバは、ランタイム自身の拒否で答える（opencode の質問の reject、ACP の許可要求の `cancelled`、lcpp の
  回答チャネル）。その答えはキューに触れず、変えない。

### 決定 8: 片付けはキューを捨てる

halt、アーカイブ、再作成、実行方式の切替（`DropHandle`）、Agent の終了（`AbortManaged`）、codex のデーモンの drain は、
今までどおりキューを全部捨てる。それを走らせるランタイムが残らないからである。今の例外は opencode の drain で、
キューを消さずにセッションを中断する（docs/log/125 §3）。代わりにキューをその再起動の向こうへ持ち越すのは #1255 の仕事である。

### 範囲外

- Agent の再起動を越えて残るキュー（#1255）。
- peer メッセージを捨てたことを送り手のセッションへ知らせること。決定 4 が見せるのは受け取った側だけである。
  docs/log/125 §4 はプロトコルの負担を理由に送り手への通知を採らず、その判断は今も変わらない。
- ランタイムが既に持っている入力を取り除くこと。muse のホスト側のキュー（`turn/unqueue` は未測定）と、codex の
  送り出し中の開始がこれにあたる。決定 2 と 3 は、そうした入力がターンになった時点で止めるが、戻しはしない。
- このドライバが始めていないターン（opencode: 付けた TUI のターン）を停止が中断するかどうか。今の不揃いは
  docs/log/126 §4 にある。

## 採らなかった案

- **今の規則のまま**（利用者の入力は捨て、peer は続ける）。利用者が積んだ訂正そのものを捨て、Terminal の経路とも、
  主要な 2 つの CLI とも食い違う。
- **1 回目の停止で利用者の入力を入力欄に戻す**（実測前の推奨）。1 回目の停止を完全なブレーキに保てるが、いちばん
  多い「訂正を今すぐ効かせる」場面で操作が 1 つ増える。Managed が Terminal の経路と逆向きに食い違うことにもなる。
  決定 4 の回復手段として残る。
- **2 つのボタンを常に並べる**（「このターンを止める」と「全部止める」）。すでに多くの操作が並ぶ入力欄に場所が要り、
  何も積まれていないときにも選択を迫る。決定 3 は、2 つ目の操作を停止の操作のメニューに置き、常に届くようにし、
  積まれているときだけ目立たせる。
- **Console にキューが見えている間だけ捨てる操作を出す**。決定 3 で退けた。Console の見え方はサーバより 1 回の
  ポーリング分遅れ、ブレーキがそれに頼ってはならない。
- **N 秒以内に 2 回押す**。決定 2 で退けた。ポーリングとスマホの遅延の上では当てにならず、Terminal の経路では
  そもそも表現できない。
- **測った場面の claude のようにキューを 1 つのリクエストにまとめる**。出どころが混ざるので決定 1 で退けた。
- **表示用のターンの状態で 2 回目の停止を決める**。`accept` が上書きするので決定 2 で退けた。

## 結果

- 何か積まれているとき、ただの 1 回目の停止はもう完全なブレーキではない。完全なブレーキは決定 3 の操作と、時間の
  制約が無い決定 2 の 2 回目の停止である。どちらも、ランタイムが既に持っている入力は取り戻せず、Terminal の経路には
  どちらも無い（決定 6）。停止ボタンのヒントは、もう一度押すと続いたものが終わることを伝えるべきで
  ある。文言は実装に任せ、Console 自身の文字列から取る。
- claude と codex では、測った範囲で、チャットの振る舞いが Terminal と Managed で揃う。
- 7 つの Managed ドライバすべてで `Interrupt` の契約が変わる。`KeptOnInterrupt` はなくなり、`TurnInput` は出どころを
  持ち、各ドライバに停止エピソード、キューを捨てる中断、捨てた項目の保持、キュー項目の ID、取り除く op、取り出した
  項目の「取り消せる／確定した」の状態、副作用の無い ledger の照会が加わる。`TurnInput` を作るすべての場所が
  出どころを付け、メッセージの応答に ID と捨てた項目が加わる。Console には停止の操作のメニュー（質問や
  承認の保留中も届く）、通知、吹き出しの操作が加わり、停止の要求中に停止を無効にするのをやめる。利用者ガイドのセッションの章（英日）に 2 つの停止を書く。
- #1244 と #1258 で足した「利用者の入力は停止で捨てられる」を確かめるテストは、消さずに反転する。「利用者の入力は
  1 回目の停止のあと続き、2 回目で捨てられて（戻すために保持されて）」を確かめるものになる。
