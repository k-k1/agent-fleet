# 0105. 停止は実行中のターンを終えてキューへ進む。2 回目の停止が残りを終える

[English](0105-stop-continues-into-the-queue.md) | 日本語

- 状態: **proposed**（2026-09-30）。実測は [docs/log/127](../log/127-cli-stop-with-queued-input.md)。
  2 段階にする形は #1258 の議論での利用者の提案で、その後の実測で claude と codex が既にそう動くと分かった。
- Follow-ups: #1282（この決定）、#1256（未測定の CLI）
- 置き換え: docs/log/27 §12.2-4（「停止の意思はキューに及ぶ」）。[0041](0041-cross-session-messaging.ja.md) の
  補遺 2026-09-30 の決定 1（停止を生き残るのは peer メッセージだけ）を改める。
- 関連: docs/log/125 §4、docs/log/126 §4

## 背景

チャットの **実行を停止（Esc）** は、今は実行方式によって 2 つの違う意味を持つ。

- **Terminal（CLI）**: CLI に Esc を送り、CLI が決める。実測（docs/log/127）では、claude 2.1.285 と codex 0.159.2 は
  実行中のターンを止め、**積まれた入力をその場で次のターンとして送る**。claude は複数の入力を 1 つのターンに
  まとめる。codex は画面で「press esc to interrupt and send immediately」と案内する。2 回目の Esc はそのターンを
  止める。opencode 1.18.33 は Esc が 2 回要り、積まれた入力を流さずに履歴へ残し、次のプロンプトと一緒に載せる。
- **Managed**: どのドライバの `Interrupt` も、ターンを止めて**利用者自身が積んだ入力を捨てる**。別のセッションからの
  メッセージ（`KeepOnInterrupt`、ADR 0041）だけが生き残り、次のターンとして始まる。

Managed の規則は peer メッセージより前に書かれたもので、いちばん多い場面を取り違えている。実行中に追い打ちを
積むのは、たいてい実行中のターンを正すため（「違う、X をして」）だ。訂正を今すぐ効かせようとターンを止めると、
その訂正が捨てられる。規則は一貫してもいない。peer メッセージは続き、利用者自身の入力は続かない。同じセッションを
Terminal と Managed で切り替えると、同じボタンで逆の結果になる。

逆向きの要請もある。1 回の押下は緊急ブレーキであり続けなければならない。止めたターンが成功した前提の
追い打ち（「それからデプロイして」）が、止める手段のないまま黙って続いてはいけない。

同じ `Interrupt` は、停止と書かれていない操作の裏にもある。計画の却下、質問のキャンセル・拒否（codex）、
別の場所での計画レビューの起動である。

## 決定

### 決定 1: 1 回目の停止は実行中のターンを終え、キューは続く

`Interrupt` は実行中のターンを止め、それ以外には触れない。積まれたものは、利用者自身の入力も peer メッセージも
同じく、止めたターンが落ち着いたあと次のターンとして始まる。Managed のドライバが peer メッセージに対して既に
していることであり、claude と codex がすべての入力に対してしていることである。

- 積まれた入力は**1 件ずつ 1 ターン**で、順番に走る。claude は 1 つのターンにまとめるが、それは採らない。peer
  メッセージの封筒と転写の `source: peer` が、利用者の文章に混ざってしまう。
- キューを出たがまだターンになっていない入力（docs/log/126: muse の応答待ちの `turn/start`、opencode で別の
  クライアントのターンの後ろに待たせている入力、codex の `turn/start` の応答前）は、この規則ではキューの一部である。
  したがって 1 回目の停止ではもう取り消さず、続く。
- `KeepOnInterrupt` は何も決めなくなるので廃止する。入力が peer から来たかは引き続き `peer_from` で分かり、
  決定 3 が表示のためだけに使う。

### 決定 2: 2 回目の停止は、1 回目が続けたものを終え、残りを捨てる

次のどちらかが成り立つ間に来た停止を **2 回目の停止** とする。

- 1 回目の停止がまだ落ち着いていない（ターンの状態が `interrupting`）。
- 実行中のターンが、**停止の直接の結果として**キューが始めたものであり、その間に利用者からの新しい入力が無い。

2 回目の停止は、そのターンを止め、**まだ積まれているものをすべて捨てる**（peer メッセージも含む）。判定は
ドライバの状態で行い、**時間では行わない**。Console のポーリング、スマホの遅延、遅いモデルのどれもが「N 秒以内に
2 回」を当てにならなくする。続いたターンが 1 分走ってから気付いた利用者でも、それを止められなければならない。

キューが空のときの 2 回目の停止は、ただの 1 回目の停止である。それ以外のターンを止めるのは、また 1 回目の停止である。

### 決定 3: 捨てたものは戻ってくる

`POST /sessions/{name}/turn {"op":"interrupt"}` は、捨てたものを応答で返す。1 回目の停止では空である。各項目は
本文、添付、peer メッセージなら送り手のセッションを持つ。

Console は 2 回目の停止のあとに通知を出す（例:「停止しました。キュー済みの 2 件を取り消しました」）。通知には、
利用者自身が書いて捨てられた入力を入力欄に戻す操作を付ける。戻すのは捨てた文章の全部で、1 件ずつ続けて入る。
何も送らない。捨てた peer メッセージは、同じ通知に送り手ごとに並べる。利用者が書いたものではないので、入力欄には
戻さない。

これが、2 回目の停止を「全部止める」として安心して使える理由になる。利用者が書いたものは永久には失われず、
peer が送ったものも、受け取った側では跡形なく消えはしない。

### 決定 4: 停止しなくてもキューを編集できる

チャットの **キュー済み** の吹き出しに、2 つの操作を付ける。入力欄に取り戻すことと、取り除くことである。
claude の「Press up to edit queued messages」に相当する。停止を押す前に追い打ちを取り消すための直接の手段で、
積んだ 1 行を消すために決定 1 と 2 を考えなくて済むようにする。

このために、どのドライバのキュー項目にも ID を持たせる。`ClientMessageID` があればそれを使い、無ければドライバが
採番する。新しい `/turn` の op が ID で項目を取り除く。取り戻しは、取り除いたうえで Console がその本文を入力欄に
入れることである。

### 決定 5: Terminal（CLI）セッションは CLI 自身の振る舞いのまま

Terminal の経路では、停止は CLI への Esc のまま、2 回目の押下は 2 回目の Esc である。claude と codex はそれで
決定 1 と 2 のとおりに動く（実測。ターン実行中の 2 回目の Esc で claude の巻き戻しメニューは開かない）。Agent Fleet は
そこへ独自のキューを足さない。opencode の Terminal の振る舞いは違う（積んだ入力が履歴に残る）が、CLI のものとして残す。

### 決定 6: どの中断も同じ規則に従う

計画の却下、質問のキャンセル・拒否、別の場所での計画レビューの起動は `Interrupt` を通るので、決定 1 と 2 にも従う。
それぞれが Esc である Terminal の経路と揃う。

### 決定 7: 片付けは変えない

halt、アーカイブ、再作成、実行方式の切替（`DropHandle`）、Agent の終了（`AbortManaged`）、デーモンの drain は、
今までどおりキューを全部捨てる。それを走らせるランタイムが残らないからである。

### 範囲外

- Agent の再起動を越えて残るキュー（#1255）。
- peer メッセージを捨てたことを送り手のセッションへ知らせること。決定 3 が見せるのは受け取った側だけである。
  docs/log/125 §4 はプロトコルの負担を理由に送り手への通知を採らず、その判断は今も変わらない。
- このドライバが始めていないターン（opencode: 付けた TUI のターン）を停止が中断するかどうか。今の不揃いは
  docs/log/126 §4 にある。

## 採らなかった案

- **今の規則のまま**（利用者の入力は捨て、peer は続ける）。利用者が積んだ訂正そのものを捨て、Terminal の経路とも、
  主要な 2 つの CLI とも食い違う。
- **1 回目の停止で利用者の入力を入力欄に戻す**（実測前の推奨）。1 回目の停止をきれいなブレーキに保てるが、いちばん
  多い「訂正を今すぐ効かせる」場面で操作が 1 つ増える。Managed が Terminal の経路と逆向きに食い違うことにもなる。
  決定 3 の回復手段として残る。
- **操作を 2 つに分ける**（「このターンを止める」と「全部止める」）。明示的だが、すでに多くの操作が並ぶ入力欄に
  場所が要り、スマホでは急いでいるときに選択を迫る。正確に 1 行を消したい場面は決定 4 のほうがよく応える。
- **N 秒以内に 2 回押す**。決定 2 で退けた。ポーリングとスマホの遅延の上では当てにならず、Terminal の経路では
  そもそも表現できない。
- **claude のようにキューを 1 つのターンにまとめる**。出どころが混ざるので決定 1 で退けた。

## 結果

- 何か積まれているとき、1 回目の停止はもう完全なブレーキではない。緩和策は、決定 2（2 回目の停止に時間の制約が
  無い）と決定 4（停止の前に積んだ行を消せる）である。停止ボタンのヒントは、もう一度押すと続いたものが終わることを
  伝えるべきである。文言は実装に任せ、Console 自身の文字列から取る。
- claude と codex では、チャットの振る舞いが Terminal と Managed で揃う。
- 7 つの Managed ドライバすべてで `Interrupt` の契約が変わる（`KeptOnInterrupt` はなくなる）。`/turn interrupt` の応答に
  本文が付き、ドライバのキューに項目の ID と取り除く op が加わる。Console には通知と吹き出しの操作が加わる。
  利用者ガイドのセッションの章（英日）に 2 つの停止を書く。
- #1244 と #1258 で足した「利用者の入力は停止で捨てられる」を確かめるテストは、消さずに反転する。「利用者の入力は
  1 回目の停止のあと続き、2 回目で捨てられて（戻されて）」を確かめるものになる。
