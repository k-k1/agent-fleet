# 0105. 停止は実行中のターンを終えてキューへ進む。2 回目の停止が残りを終える

[English](0105-stop-continues-into-the-queue.md) | 日本語

- 状態: **proposed**（2026-09-30）。実測は [docs/log/127](../log/127-cli-stop-with-queued-input.md)。
  2 段階にする形は #1258 の議論での利用者の提案で、その後の実測で、測った場面では claude と codex がそう動くと分かった。
- Follow-ups: #1282（この決定）、#1256（未測定の CLI）、#1255（再起動を越えて残るキュー）
- 置き換え: docs/log/27 §12.2-4（「停止の意思はキューに及ぶ」）。[0041](0041-cross-session-messaging.ja.md) の
  補遺 2026-09-30 の決定 1（停止を生き残るのは peer メッセージだけ）を改める。
- 関連: docs/log/125 §4、docs/log/126 §4

## 背景

チャットの **実行を停止（Esc）** は、今は実行方式によって 2 つの違う意味を持つ。

- **Terminal（CLI）**: CLI に Esc を送り、CLI が決める。実測（docs/log/127、それぞれ 1 回）:
  - claude 2.1.285 と codex 0.159.2 は、実行中のターンを止め、**積まれた入力をその場で送った**。claude は積まれた
    2 件を 1 つのリクエストに入れた。codex は画面で「press esc to interrupt and send immediately」と案内する。
    2 回目の Esc はそのリクエストを止めた。
  - opencode 1.18.33 は Esc が 2 回要る。積まれた入力を流さずに履歴へ残し、次のプロンプトと一緒に載せた。
- **Managed**: どのドライバの `Interrupt` も、ターンを止めて**利用者自身が積んだ入力を捨てる**。別のセッションからの
  メッセージ（`KeepOnInterrupt`、ADR 0041）だけが生き残り、次のターンとして始まる。

Managed の規則は peer メッセージより前に書かれたもので、いちばん多い場面を取り違えている。実行中に追い打ちを
積むのは、たいてい実行中のターンを正すため（「違う、X をして」）だ。訂正を今すぐ効かせようとターンを止めると、
その訂正が捨てられる。規則は一貫してもいない。peer メッセージは続き、利用者自身の入力は続かない。同じセッションを
Terminal と Managed で切り替えると、同じボタンで逆の結果になる。

逆向きの要請もある。利用者には、時間と競争せずに**1 つの操作で全部を止める手段**が常に要る。止めたターンが
成功した前提の追い打ち（「それからデプロイして」）が、先に止める手段のないまま続いてはいけない。

同じ `Interrupt` は、停止と書かれていない操作の裏にもある。計画の却下と、別の場所での計画レビューの起動は、
Console の停止を送る。codex では、質問のキャンセル・拒否も `Interrupt` を呼ぶ。

## 決定

### 決定 1: 1 回目の停止は実行中のターンを終え、キューは続く

`Interrupt` は実行中のターンを止め、それ以外には触れない。積まれたものは、利用者自身の入力も peer メッセージも
同じく、止めたターンが落ち着いたあと次のターンとして始まる。Managed のドライバが peer メッセージに対して既に
していることであり、測った場面で claude と codex がしたことである。

- 積まれた入力は**1 件ずつ 1 ターン**で、順番に走る。claude は積まれた 2 件を 1 つのリクエストに入れたが、それは
  採らない。peer メッセージの封筒と転写の `source: peer` が、利用者の文章に混ざってしまう。
- `TurnInput` は**どこから来たか**を持つ。利用者か、peer とその送り手のセッション名かである。これが
  `KeepOnInterrupt`（「利用者ではない」としか言わない）を置き換える。今は `peer_from` が `/input` で止まり、
  ドライバまで届かないので、決定 2 と 3 のためにこの項目が要る。
- キューを出たがまだターンになっていない入力がある（docs/log/126）。opencode で別のクライアントのターンの後ろに
  待たせている入力は**まだ送っていない**。muse の応答待ちの `turn/start` と、codex の `turn/start` の応答前の入力は
  **送ってある**。どれも決定 1 と 2 ではキューにあるものと数える。1 回目の停止では続き、2 回目の停止では止まる。
  取り除いたり戻したりできる（決定 3・4）のは、送っていない入力だけである。送った入力の停止は、そのターンの停止であり、
  転写には既に中断されたターンとして出る。

### 決定 2: 2 回目の停止は停止エピソードを終え、残りを捨てる

何かを積んだまま終わる 1 回目の停止は、**停止エピソード**を開く。ドライバはエピソードを専用の項目に、`accept` と
同じロックの下で記録する。表示用のターンの状態は使わない。`accept` はその状態を上書きする（codex、opencode、ACP の
ドライバは `queued` にする）ので、`interrupting` の間に送信が来ると、2 回目の停止が 1 回目に化ける。

- エピソードは、**キューが空になり、エピソードが始めた最後のターンが落ち着くまで**続く。積まれた入力がいくつあっても同じである。
- **利用者の新しい入力が受け付けられた**ときにも終わる。ターンを始めても、積まれても同じである。ledger の重複と、
  断られた送信は数えない。peer の入力が届いても終わらない。
- **エピソード中の停止はすべて 2 回目の停止である。** 実行中のターン、または送り出し中の入力を止め、**まだ積まれて
  いるものをすべて捨てる**（peer メッセージも含む）。そしてエピソードを終える。
- エピソードの外の停止は 1 回目の停止である。

判定は状態で行い、**時間では行わない**。Console のポーリング、スマホの遅延、遅いモデルのどれもが「N 秒以内に
2 回」を当てにならなくする。続いたターンが 1 分走ってから気付いた利用者でも、それを止められなければならない。

Console の停止の操作は、**停止の要求が返ってくる前でも使える**ようにする。今の `sendInterrupt` は `sending` を立て、
最初の要求が返るまでボタンを無効にする。2 回目の停止が要るのは、まさにその間である。

### 決定 3: 1 つの操作で全部止める

何かが積まれている間、停止の操作はその横に 2 つ目の操作を出す。**停止してキューを捨てる**である。これは 1 つの
操作で行う 2 回目の停止であり、背景が求める緊急ブレーキで、時間に依存しない。捨てるものがあるときだけ出すので、
入力欄に 2 つ目のボタンを常に置くことにはならない。

### 決定 4: 捨てたものは、ドライバから戻ってくる

ドライバは、2 回目の停止（または決定 3）が捨てた項目を、次に捨てたもので置き換わるまでセッションごとに持つ。
それをセッションのメッセージの応答に、`queuedPrompts` と並べて、捨てた操作の ID 付きで出す。`/turn interrupt` の
応答も同じ一覧を返すが、Console はそれに頼らない。タブを閉じたり接続が切れたりして応答が失われても、次の
ポーリングで取り戻せる。

各項目は本文、添付、出どころ（決定 1）を持つ。ここに入るのは送っていない入力だけである。

Console は通知を出す（例:「停止しました。キュー済みの 2 件を取り消しました」）。通知には、利用者自身が書いて
捨てられた文章を入力欄に戻す操作を付ける。戻すのは 1 件ずつ続けて入り、何も送らない。捨てた peer メッセージは、
同じ通知に送り手ごとに並べる。利用者が書いたものではないので、入力欄には戻さない。この操作は、捨てた操作の ID
ごと・タブごとに 1 回出す。2 つのタブがそれぞれ自分の下書きに文章を入れることはあり得るが、二重に送られることは
ない。送るのは利用者自身の操作で、新しい `ClientMessageID` が付く。

限界: 持っておく項目は Agent のメモリにあるので、キューそのものと同じく Agent の再起動で失われる（#1255）。
この決定はそれ以上の保護はしない。

### 決定 5: 停止しなくてもキューを編集できる

チャットの **キュー済み** の吹き出しに、2 つの操作を付ける。入力欄に取り戻すことと、取り除くことである。
claude の「Press up to edit queued messages」に相当し、追い打ちを 1 件だけ取り消す正確な手段である。

- 積まれた項目はすべて ID を持ち、その ID が吹き出しまで届く。今の `queuedPrompts` は本文しか運ばない。ID は、
  項目に `ClientMessageID` があればそれ、無ければドライバが採番したものである。
- 新しい `/turn` の op が、ID で項目を取り除く。**まだ送っていない場合に限り**、ポンプに対して原子的に行う。応答は
  その項目か、ポンプが先に取った場合の `already_started` である。別のタブの古い吹き出しからの操作にも同じ答えが返る。
- Console は、取り除けたときだけ本文を入力欄に戻す。もう一度送るのは新しい送信で、新しい `ClientMessageID` が付く。
  取り除いた項目の ID は二度と使わない。受け付け時に ledger へ記録するドライバでは、再送が重複として捨てられるからである。
- ランタイムに既に送った項目（決定 1）は表示するが、操作は付けない。

### 決定 6: Terminal（CLI）セッションは CLI 自身の振る舞いのまま

Terminal の経路では、停止は CLI への Esc のまま、2 回目の押下は 2 回目の Esc である。測った場面では、claude と
codex は 1 回目の Esc でキューへ進み、2 回目でそのターンを止めた。ターン実行中に claude の巻き戻しメニューは
開かなかった。その場面では 1 回目の Esc のあとに積まれたものが残っておらず、2 回目の Esc がさらに積まれた入力も
捨てるかは見ていない。Agent Fleet はこの経路に独自のキューもエピソードも足さない。opencode の Terminal の振る舞いは
違う（積んだ入力が履歴に残る）が、CLI のものとして残す。

### 決定 7: ほかのどの操作がこの規則に従うか

- **計画の却下**と**別の場所での計画レビューの起動**は Console の停止を送るので、どの実行方式でも決定 1 と 2 に従う。
- **質問のキャンセル・拒否**が `Interrupt` に届くのは codex だけなので、そこで決定 1 と 2 に従うのは codex だけである。
  ほかのドライバは、ランタイム自身の拒否で答える（opencode の質問の reject、ACP の許可要求の `cancelled`、lcpp の
  回答チャネル）。その答えはキューに触れず、変えない。

### 決定 8: 片付けはキューを捨てる

halt、アーカイブ、再作成、実行方式の切替（`DropHandle`）、Agent の終了（`AbortManaged`）、codex のデーモンの drain は、
今までどおりキューを全部捨てる。それを走らせるランタイムが残らないからである。今の例外は opencode の drain で、
キューを消さずにセッションを中断する（docs/log/125 §3）。代わりにキューをその再起動の向こうへ持ち越すのは #1255 の仕事である。

### 範囲外

- Agent の再起動を越えて残るキュー（#1255）。
- peer メッセージを捨てたことを送り手のセッションへ知らせること。決定 4 が見せるのは受け取った側だけである。
  docs/log/125 §4 はプロトコルの負担を理由に送り手への通知を採らず、その判断は今も変わらない。
- ランタイムが既に持っている入力を取り除くこと。muse のホスト側のキュー（`turn/unqueue` は未測定）と、codex の
  送り出し中の開始がこれにあたる。決定 1 はそうした入力を止めるが、戻しはしない。
- このドライバが始めていないターン（opencode: 付けた TUI のターン）を停止が中断するかどうか。今の不揃いは
  docs/log/126 §4 にある。

## 採らなかった案

- **今の規則のまま**（利用者の入力は捨て、peer は続ける）。利用者が積んだ訂正そのものを捨て、Terminal の経路とも、
  主要な 2 つの CLI とも食い違う。
- **1 回目の停止で利用者の入力を入力欄に戻す**（実測前の推奨）。1 回目の停止を完全なブレーキに保てるが、いちばん
  多い「訂正を今すぐ効かせる」場面で操作が 1 つ増える。Managed が Terminal の経路と逆向きに食い違うことにもなる。
  決定 4 の回復手段として残る。
- **2 つの操作を常に並べる**（「このターンを止める」と「全部止める」）。すでに多くの操作が並ぶ入力欄に場所が要り、
  何も積まれていないときにも選択を迫る。決定 3 は、2 つ目を意味があるときだけ出す。
- **N 秒以内に 2 回押す**。決定 2 で退けた。ポーリングとスマホの遅延の上では当てにならず、Terminal の経路では
  そもそも表現できない。
- **測った場面の claude のようにキューを 1 つのリクエストにまとめる**。出どころが混ざるので決定 1 で退けた。
- **表示用のターンの状態で 2 回目の停止を決める**。`accept` が上書きするので決定 2 で退けた。

## 結果

- 何か積まれているとき、ただの 1 回目の停止はもう完全なブレーキではない。完全なブレーキは決定 3 の操作と、時間の
  制約が無い決定 2 の 2 回目の停止である。停止ボタンのヒントは、もう一度押すと続いたものが終わることを伝えるべきで
  ある。文言は実装に任せ、Console 自身の文字列から取る。
- claude と codex では、測った範囲で、チャットの振る舞いが Terminal と Managed で揃う。
- 7 つの Managed ドライバすべてで `Interrupt` の契約が変わる。`KeptOnInterrupt` はなくなり、`TurnInput` は出どころを
  持ち、各ドライバに停止エピソード、捨てた項目の保持、キュー項目の ID、取り除く op が加わる。`/input` は `peer_from` を
  ドライバまで渡し、メッセージの応答に ID と捨てた一覧が加わる。Console には停止の 2 つ目の操作、通知、吹き出しの
  操作が加わり、停止の要求中に停止を無効にするのをやめる。利用者ガイドのセッションの章（英日）に 2 つの停止を書く。
- #1244 と #1258 で足した「利用者の入力は停止で捨てられる」を確かめるテストは、消さずに反転する。「利用者の入力は
  1 回目の停止のあと続き、2 回目で捨てられて（戻すために保持されて）」を確かめるものになる。
