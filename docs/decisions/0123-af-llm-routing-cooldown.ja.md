## 背景

Agent Fleet は自分でも LLM を呼ぶ。アシスタント・チャット（Console、Discord/Slack のオペレーター、
スケジュール実行、セッション報告への自動ターン）、ワンショット生成（タイトル、ブランチ名、返信候補、
翻訳、編集提案、計画更新）、バックグラウンドのメモリレビューである。どれも優先順位（設定 > アシスタント、
設定 > AI 補助）からバックエンドを選ぶが、「使える」とは「CLI にログインしている」ことだけだった。
利用制限に当たったターンはエラーのまま利用者に返り、次のターンも同じバックエンドへ行って同じように
失敗し、それが何時間も続いた。

既にあった利用制限の知識（`agents/claude` の中断マーカーとリセット時刻の読み取り、`agents/muse` の
クォータ判定、`sessionx/rate_limit_resume.go`）は CLI セッションだけのものだった。

## 決定

1. **分類器もクールダウン表も 1 つ。** `routehealth.Classify` は失敗した呼び出しのエラー文を分類する。
   claude と muse はセッションが使っている判定をそのまま通すので、ルーターとセッションの自動再開で
   「制限とは何か」が食い違わない。ほかの kind は汎用のマーカーと、単語として現れた HTTP ステータスで
   判定する。`routehealth.Table`（メモリ上、`routehealth.Default`）が休止を持つ。
2. **休止させるのは可用性の失敗だけ。** 使用量の枠、支出上限、リクエストレートの 429、5xx / 過負荷。
   404、不明なモデル、不正なリクエストは設定の不具合として表に出し、休止させない。休止させると、
   決まって起きる不具合が、付いたり消えたりする可用性の信号に化けるからである。認証の失敗は既存の
   ログイン確認に任せ、説明のつかない失敗も休止させない。
3. **範囲はクォータに合わせる。** サブスクリプションの枠と支出上限はアカウント全体のものなので、
   kind ごと休止させる。モデルごとの使用量上限（「You've reached your <model> limit」）、429、5xx は
   (kind, model) の 1 組だけを休止させる。CLI 自身の既定モデルは独立したモデルのキーで、kind 全体の
   キーとは別にする。サブスクリプションや課金の文言を伴わない単なる「quota exceeded」は、リクエスト
   レートの制限として読む。ステータスの数字は、HTTP や status などの文脈があるか、文の先頭にある
   ときだけ数える。
4. **期間。** 提供元が示したリセット時刻まで（8 日より先は読み違いとして無視）。リセット時刻は
   文言そのものが示した時刻からだけ取り、その分を過ぎた直後に読んだ時刻を翌日へ繰り越さない。
   示されなければ、連続した失敗ごとに 1 分から倍にして最大 4 時間。支出上限は 4 時間。推測は
   生きている休止を短くしない。新たに示されたリセット時刻は置き換える。成功すると、そのモデルの
   休止と kind の休止を解く。ただし解くのは、その呼び出しを始める前に設定された休止だけである。
   上限の前に受け付けられたリクエストは、別のリクエストが上限に当たった後でも成功しうるからだ。
   最後の休止が終わって 4 時間以上たってからの失敗は、連続の 1 回目に戻る。
5. **回復が近いなら切り替えない。** 2 分以内に終わる休止では呼び出しを動かさない。ただし終わりが
   バックオフの推測にすぎない使用量の枠と支出上限は例外とする。これらは何時間も続く。
6. **適用先。**
   - チャット：送信時の選択（`chatRoute`）は、休止中のピンと優先順位の項目を飛ばす。休止させる判定で
     失敗したターンは、次に使えるバックエンドで 1 回だけやり直す。履歴はプロバイダー間の文脈同期が
     引き継ぐ。成功したら notice（`chat.notice.agent_failover`）で切り替えを残す。会話のエージェント
     設定は変えないので、休止が終われば次のターンから元に戻る。ストリームのターンをやり直すのは、
     まだ delta も step もクライアントに届いていないときだけ。
   - ワンショット：同じく飛ばし、次のバックエンドで 1 回だけやり直す。ピンは、未ログインの CLI のときと
     同じように譲る。
   - メモリレビュー：休止中のピンは、会話内容を別の提供元へ移さず「使用不可」を返す（0117）。試行は
     消費されず、レビューは後で再試行される。
   - 候補がすべて休止中なら、この変更の前と同じ行き先へ送る。断っても誰の役にも立たない。
7. **新しい会話には影響しない。** 会話を作るときのバックエンドは、引き続き優先順位とログイン状態だけで
   決める。1 時間で解ける制限のせいで新しい会話を代わりのバックエンドに固定すると、その代わりが
   ずっと残ってしまう。

## 結果

- 最初のバックエンドが制限に当たっても、別のバックエンドが接続されていれば、チャットのターンも
  ワンショットも失敗しなくなる。どのバックエンドが答えたかは利用者に見える。
- 範囲外：CLI セッション（途中で切り替えると文脈を失う）、lcpp（ピンしたときだけ動く）、画像生成
  （クールダウンのない順序付きフォールバックを別に持つ）、利用枠ボードの読み取り（`limitobs`）による
  呼び出し前の判定、設定画面の「現在の使用先」の行（休止をまだ反映しない）。
- codex を headless で動かしたときの利用制限の文言は、ツリーに実測がない。実物が取れるまでは汎用の
  マーカーで拾う。
- Agent を再起動すると表は消える。次の失敗 1 回分の呼び出しで覚え直す。
