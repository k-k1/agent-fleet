## 背景

0108 は、エージェントのすべての種類に 1 つのストアと 5 つのツールを与えた。エージェントはそこへ書く。直近に公開された
300 件の変更（2026-10-10〜11-06）のうち、エージェントによる作成が 122 件、更新が 82 件、忘却が 1 件だった。ストアが
育っても良くする仕組みはない。大きくなるだけで、書かれている世界のほうが足元で動いていく。

### 測定（2026-11-06、読み取り専用）

1 プロジェクトとユーザースコープで、メモリ 568 件、本文 1.72 MB。本文は Console のメンバー用ルートで読んだ。この
ルートは利用回数を数えない（`agent_memory_member.go:6`）。`memory_read` で総なめにすると、すべてのメモリに利用が 1 回
足され（`agent_memory.go:803`、`agent_memory_search.go:102`）、判定しようとしている順位そのものを歪めていた。

| LLM を使わない検査（使い捨てのスクリプトで測定） | メモリ | 備考 |
|---|---|---|
| 存在しないメモリへの `[[link]]` | 7 | リンク 1,669 本のうち 9 本 |
| 本文が 4,096 バイト超（`agent_memory.go:79`。recall は先頭しか見せない） | 100 | 8 KiB 超が 33、最大 45 KB |
| 廃止した語（廃止した AWS プロファイル、以前のトランクのブランチ） | 48 | 該当 78 行のうち 13 行は既に「廃止」と書いてあり、18 行はコマンド |
| 存在しないリポジトリのパス・`Test*` 名・ADR 番号 | 63 | 12 件の抜き取り確認では、およそ半分が本当の移動か削除 |
| ほぼ重複する本文（5-gram の包含率 ≥ 0.4） | 8 | 3 組。文字どおりの重複はまれ |
| 上のいずれか、ログ型、冷えたもの | 219（39 %） | 1.02 MB |
| 事実が変わったもの（リンク・廃止語・パス） | 111（20 %） | 該当行 ±1 行と説明文で 0.11 MB |

最後の行の 0.11 MB は抜き出した断片の大きさで、ストアの本文バイトの 6 % にあたる。これはどのモデル呼び出しの入力でも
ない。統合のプロンプトには指示、トピック、パッチを当てる本文全体も載るので、実際にどれだけ減るかは段 3 で測る
（決定 9）。規模の目安として、本文をすべて 1 回読むと約 570 k トークンになる。これは日本語と英語が混ざった本文を
1 トークン約 3 バイトとしてバイト数から**推定**した値で、トークナイザで数えたものではない。

整理役が欲しい手がかりが、そもそも無い:

- 448 件（79 %）の `updated` は取り込んだ日付で、522 件はリビジョン 1 のまま。経過日数は何も語らない。
- `uses` は読み出しのほかに返った検索ヒットも数え、本文の大きさにつれて増える（小さいほうの四分位の中央値 3、
  大きいほうは 9）。いちばん「使われた」メモリは、いちばん大きいメモリである。
- ピン留めされたメモリは 1 件もない。「めったに使わないが残しておくべき」を表す手段がない。
- `memory_index` で最上位に並ぶ `feedback` のメモリが、廃止したトランクのブランチを今も名指ししている。

### 0117 のレビューがうまくいかなかった理由

モードは `off`。測ったワークスペースでは、2026-10-19〜20 の提案 25 件（13 実行・5 セッション）が 17 日間、返事の
ないままキューに残っていた。直近に公開された 300 件の変更のうち、作者が `review` のものは 1 件。25 件すべてが
`create` で、11 件には名前のほぼ同じメモリが既にある。1 件は、本文で `develop-trunk-ci` と矛盾すると自分で書いて
いながら、それでも `create` だった。原因は構造にある:

1. ヘルパーが更新できるのは見せられたメモリだけで（`memreview/prompt.go:18`）、見せるのはキーワードの重なりで
   選んだ最大 5 件（`memreview/limits.go:20`）、そのうち本文全体が `BodyChars` = 2,000 文字に収まったものだけ
   （`input.go:229`）。それより長いメモリの更新は拒まれる（`ops.go:153`）。測ったストアでは 568 件中 146 件（26 %）
   の本文が 2,000 文字を超える（中央値は 1,343 文字、2,228 バイト）。つまりストアの 4 分の 1 については、ヘルパーが
   変更を提案したくても、新しい名前にするしかなかった。
2. `update` は本文全体を置き換える（`prompt.go:26`）ので、許される場面でも高くつき、危うい選択になる。
3. 実行は会話のターン 30 回またはユーザーのプロンプト 3 回で始まり（`loop.go:39`）、そのセッションの窓を
   `WindowChars` = 40,000 で区切って読む（`limits.go:13`）。世界の変化で古くなったことや、セッションをまたいだ
   重複は、1 つの窓の中からは見えない。
4. 提案 1 件ごとに、人の判断が 1 回要る。0117 の「結果」は誰も読まないキューを予告していた。そのとおりになった。
5. エージェントはすでにターンの中で保存している。レビューは、たいてい同じ場面を小さく提案し直しただけだった。

## 先行事例

2026-11-06 に調査した。出典と、読んだもの・二次資料・推測の区別は [docs/log/136](../log/136-cultivated-memory-survey.md)
にある。それぞれがここにもたらすもの:

- **ACE（Agentic Context Engineering、ICLR'26）** — 全体の書き直しに反対する根拠。以前の手法（Dynamic Cheatsheet）を
  AppWorld で調べた事例で、1 回の書き直しでコンテキストが 18,282 トークンから 122 トークンに縮み、正解率は 66.7 から
  57.1 に下がった。適応しない場合の 63.7 より低い。ACE 自身は、項目ごとに helpful/harmful のカウンタを持たせ、差分を
  LLM を使わない処理でまとめる。金融の結果は、振り返り役（reflector）に正解ラベルが無いと 81.9 から 77.1 に下がる。
  ずっと弱い振り返り役でも、毎回敵対的な更新を入れる場合を除いて基準モデルを上回る。それでも著者は、ある程度強い
  振り返り役に頼っていると書いている。
- **Mem0** — 自身の文書は、v2 の抽出を ADD のみと説明している。独立した研究（arXiv 2606.15903）は、同じ v2.0.2 で
  LLM の更新ルーター（`infer=True`）を入れた場合と切った場合を、敵対的なテスト群で比べた。モデルは Mem0 が調整済みの
  既定ではなく DeepSeek-V3。ルーターを入れると、置き換え系のカテゴリで 31〜92 ポイント落ちた（たとえば言い換えによる
  置き換えで 82 % → 0 %）。識別子系のカテゴリでは上がった。自由に更新・削除させたモデルは、まさにこの記録が気に
  かける場面でしくじった。
- **Zep / Graphiti** — 二重の時間軸を持つ事実（`valid_at`/`invalid_at`、`created_at`/`expired_at`）。矛盾した事実は
  削除せず、閉じる。書き込みごとに複数回の LLM 呼び出しとグラフデータベースが要る。
- **GitHub Copilot Memory** — いちばん近い類例。リポジトリについての事実はコードの引用を持ち、使う直前に現在の
  ブランチと照合する（LLM による判断）。有効期限（既定 90 日）は、**確かめられた利用でだけ延び、取り出しでは延び
  ない**。
- **「Revoked but Still Authoritative」（arXiv 2609.08258）** — 5 つのメモリシステムのどれも、取り消した事実を既定で
  は検索から外していなかった。取り消した事実が、その置き換え先より上位に出ることも多かった。
- **Codex のメモリ** — アイドル後にセッションごとに抽出し、そのあとロックを取った 1 つの統合エージェントが範囲を
  区切った差分を書く。未解決のバグ（#48679 要約の切り詰め、#57091 存在しないパスへのリンク）は、統合役の出力を保存
  前に決定的に検証する必要があることを示している。
- **fiberplane/drift**（MIT）— 文書→コードのアンカーを AST のフィンガープリントとしてロックファイルに持ち、差分が
  触れた範囲を CI で確かめる。アンカーの先行事例だが、対象は文書である。
- **Hermes Agent**（`90d6b98` で読んだ）: 常に読み込むメモリに文字数の上限（2,200 文字）があり、あふれると
  「まとめる＋足す」を 1 回のバッチで強いる。部分文字列による `patch`。10 ユーザーターンごとに分岐したレビュー役が
  走り、追加はそのまま適用され、パッチと削除は人のために保留される。スキルは利用回数のサイドカーを持ち、アイドル時の
  整理役がいる（active → 14 日で stale → 30 日で archived、削除はしない）。自身の問題: 毎回書くようにレビュー役を
  急かすプロンプト、直接の利用回数だけで刈り込んで間接的に参照されたスキルを壊したこと、無人の実行がメモリを
  消したこと、レビューのたびに会話全体を読み直すこと（最大 600 k トークン）。
- **Honcho**（Plastic Labs、AGPL-3.0、v3.5.0 2026-10-30）は**ピア中心の推論エンジン**である。README は「変わって
  いく人・エージェント・グループ・プロジェクト・アイデア」を理解するエージェントのためのメモリと説明し、文書や
  ツールの痕跡も入力にでき、コーディングエージェント（Claude Code、OpenCode、Hermes、任意の MCP クライアント）との
  連携や、複数のエージェントが共有できるワークスペースを持つ。（観察する側、観察される側）の組ごとに、裏のワーカーが
  明示・演繹・帰納の「結論」を導き、定期的な「dream」（前回から新しい結論が 50 件以上かつ 8 時間以上）が重複をまとめ、
  新しい事実に置き換えられた結論を削除する。Postgres + pgvector、マネージドかセルフホスト、既定は小さなホスト型
  モデル。読んだ文書には、人が結論を見直したり直したりする手段は書かれていない。
- **Letta の sleep-time エージェント、LangMem、Claude Code の auto memory と `/doctor prompt-audit`、Supermemory、
  Basic Memory（Markdown + MCP、AGPL-3.0）、agentskills.io** — 同じ部品の別の形。Cursor はメモリをやめてルールに
  寄せた。

この調査が扱った製品と版の範囲では、エージェントのメモリについて、コードのアンカー・廃止語リスト・リンクを
LLM なしの検査で組み合わせるもの、複数の書き手が同時に書く中でリビジョンを確かめる差分パッチを当てるもの、知識の
種類ごとに寿命を変えるもの、メモリ項目のファイル仕様を公開するものは見つからなかった。これはこの調査が届いた範囲に
ついての記述で、存在しないことの証明ではない。

## 決定

### 1. 「育つ」とは何か

ストアが育つとは、より**正確**になること（世界が変わったあと、古くなった項目がすぐ見つかって直る）、より**密**に
なること（1 つの教訓は 1 つの規則になり、件数は減ってもよい）、より**抽象的**になること（出来事が規則や検証済みの
手順になり、出来事そのものは履歴になる）、そしてより**よく置かれる**こと（必要なセッションに正しい項目が届き、
要らないものは視界から外れる）である。件数は目標ではない。それぞれをどう観測するかは決定 9 に書く。

### 2. 次のリリースで 0117 のレビューを廃止する

廃止するもの（それぞれのテストと一緒に）:

| 面 | どうなるか |
|---|---|
| ui-prefs の `memoryReview` と `memoryReviewAuto` | 読むときは無視し、次の保存で落とす。これらのための Agent のメンバー由来の確認・スイッチの同期・起床（`workspace/agent/ui_prefs.go:263`、`:312`、`:340`、`:366`）はなくなる。Console の prefs レジストリと `equivalence.golden.json` から両方のキーを除く |
| ループ、「メモリを提案させる（今すぐ）」、`POST /agents/memory-review/run` | Agent と CP のリレー（`control-plane/relays_memory.go:42` 以降）から除く |
| 提案一覧、承認・却下のルートとその監査（`control-plane/proxy.go:127`） | 下の書き出しが成功したあとに除く |
| レビューのスイッチと、`memory.review` の「AI 補助」の行（`workspace/agent/ai_assist.go`、`console/src/lib/aiAssistFeatures.ts`） | 除く |
| 保留件数の通知 | もう出さない。既にある通知は変更一覧へ案内する |
| 台帳の `memory.review` | 列挙値と Console のカタログに残す。0029 は追記のみで、過去の行がこの値を持つ |
| 「このレビューの変更を元に戻す」（`console/src/features/settings/memory/memoryChanges.tsx:253`、`/agents/memory-review/runs/revert`） | 残す。レビューのキューのモジュールから変更一覧へ移し、メンバー由来の印の後ろに置いたまま。過去の実行は引き続き取り消せる |
| guide/member/18 と 20、`guide/ref` での言及、契約テスト | 同じ変更で更新する |

**保留中のキューは捨てずに書き出す。** すべてのワークスペースで 1 回だけ、版つきで冪等な移行を行う。保留中の提案を
1 件ずつ（id、scope、project、基準リビジョン、操作、本文、理由、根拠、実行 id）と却下ハッシュの一覧を、ストアの作業
ディレクトリ下のファイルに書き、fsync してから、はじめてキューを消す。再起動すればもう一度走り、済んでいることを
見つける。移行のあと、0117 の実行の復旧が古い実行を再び送り出すことはなく、そのための通知も出さない。書き出した
提案は**観測**であって、承認ではない。決定 6 ができたら、それを入力として読み、決定 6 の規則（復活の禁止を含む）が
すべてかかる。

### 3. スキーマ: 種類・ライフサイクル・アンカー、可視性、カウンタ

**フロントマター（すべて任意）** — これらを持たないメモリは今と同じに振る舞う:

- 分類: `kind` — `preference` | `lesson` | `procedure` | `state` | `log`。どう古くなるかを表し、0108 の `type`
  （誰についてか）と並ぶ。寿命の案: preference と lesson は期限切れにならない。procedure はアンカーが動いたら
  確かめる。state は再確認しなければ N 日で期限切れになる。log は履歴で、索引の説明つきの部分には決して入らず、
  要約とポインタを残す。
- 依存: `anchors` — パス、シンボル、テスト名、ADR 番号、プロファイル名やブランチ名、コマンド、`[[links]]`。機械的に
  抜き出し、編集もできる。
- ライフサイクル: `status`（`active` | `quiet` | `archived`）と `status_by`（`agent`、`member`、`consolidator`）、
  `superseded_by`（メモリか、決定 11 からはドキュメント）と `invalid_at`（Graphiti の語彙）、そして `reasons`。`reasons` は未解決の疑いのリストで、各要素は
  `{by: lint|feedback|member, rule, note, revision}` — 発火した規則（lint の検査 id、または `stale`/`wrong`）、1 行の
  メモ、見つかったリビジョン。**suspect は status ではない**。`reasons` が空でない間、そのメモリは suspect である。
  どの書き手の出力も、この 1 つのスキーマで検証する。

エージェントに何が見えるかは、この順で決める。各段は後の段に左右されない（メンバーのルートにはすべて見える）:

1. **archived または superseded は除外する**。kind やピンに関係なく、索引の行も検索のヒットもなく、`memory_read`
   はスタブを返し、注入も書き戻しもしない。
2. **未解決の理由は必ず見せる**。suspect なメモリの行・ヒット・読み出し・注入のすべてに理由を添え、claude には
   書き戻さない。
3. **置き場所**: `log` の kind は status に関係なく `quiet` と同じに置く。`quiet` は索引の説明つきの部分には入らず、
   名前だけの末尾、検索、読み出しには入る。
4. **ピンは最後**: ピンは `active` のメモリを説明つきの部分へ持ち上げる。`quiet` や `log` は持ち上げず（だから
   「log は説明つきの部分に決して入らない」が成り立つ）、段 1 を覆すこともない。

| | 説明つきの索引 | 名前だけの末尾 | `memory_search` | 名前指定の `memory_read` | lcpp の注入 | claude への書き戻し |
|---|---|---|---|---|---|---|
| `active` | 入る（今と同じ順位） | 収まらなければ | 入る | 全文 | 入る | する |
| 未解決の理由がある `active` | 入る、理由を前置 | 収まらなければ | 入る、理由を前置 | 全文、理由を前置 | 入る、理由を前置 | しない |
| `quiet`、またはすべての `log` | 入らない | 入る | 入る | 全文（理由があれば前置） | 入らない | しない |
| `archived` または superseded | 入らない | 入らない | 入らない | スタブのみ | 入らない | しない |

すべての経路での受入条件: archived の log、suspect の log、ピン留めした log、superseded の log、ピン留めした quiet の
メモリ。

**誰が何を設定でき、各書き手が何を保つか。** 保存・パッチ・ピン・取り込みが名指ししないフィールドは、今の値を保つ。
これは `agentMemSave`（`agent_memory.go:1080` は今は created・source・hash・pin しか保たない）と、claude と muse の
取り込み（`agent_memory_claude_import.go:487`、`:781` は項目を作り直す）の契約になる。エージェントが設定できるのは
`kind` と `anchors`。ライフサイクルのフィールドを設定できるのは、lint、フィードバック、承認の関門を通った統合役、
メンバーだけ。`reasons` の各要素は、それぞれの規則で消える。lint の理由は、より新しいリビジョンを lint が確かめて
その規則がもう発火しないときだけ消える。フィードバックの理由は、本文の変更で消える（`memory_save` でも
`memory_patch` でも同じ）。メンバーの理由は、どの理由でも、メンバーの明示的な操作で消える。だから句読点だけの修正では
存在しないパスの理由は消えない。受入条件: lint の理由とフィードバックの理由が両方あるところへ本文を変更して、
(a) lint の規則の原因を直さない変更ではフィードバックの理由だけが消え、lint の理由は次の lint の後も残る。(b) 原因も
直す変更では、lint の理由はそのリビジョンでの次の lint まで残り、規則がもう発火しないのでそこで消える。取り込みは、
外からライフサイクルのフィールドを受け取らない。**取り消し（revert）は「保つ」の例外**で、以前の版を丸ごと戻す。
kind、anchors、ライフサイクルのフィールド、ピンも戻す。本文とピンについては `agent_memory_changes.go:610`–`620` が
既にそうしている。リビジョンは増え続け、作者はメンバーになる。lint の理由やピンを取り消せば、それが元に戻る。
受入条件: 書き手ごと（保存・パッチ・ピン・claude の取り込み・muse の取り込み・プロジェクトの移動）に各フィールドが
残るテスト、取り消しについては lint の理由とピンが元に戻るテスト。

**可視性は 1 つの述語で、エージェント向けのすべての読み出し経路に当てる。** `archived` と superseded のメモリは、
`memory_index`、`memory_search`、外部のメモリ MCP（同じハンドラ）、lcpp のターンごとの注入、claude への書き戻し
（`agent_memory_claude_export.go:504` はスコープ全体を読む）から返さない。名前指定の `memory_read` はスタブ（名前・
status・`superseded_by`・理由）を返し、本文は返さない。だから古い名前や `[[link]]` から本文が現役として戻ってくる
ことはない。メンバーのルート（一覧・履歴・差分・復元・バンドルの書き出し）にはすべて見える。経路ごとにテストを
置く。取り消しの研究が、どのシステムも既定ではこれをしていないと示したからである。

claude への書き戻しはフィルタだけでは足りない。書き戻しは AF のファイル名をすべて保護し、選ばなかったネイティブの
ファイルを残し（`agent_memory_claude_export.go:519`、`:639`–`668`）、それらを `MEMORY.md` に並べ直す（`:773`–`803`）。
だから、書き戻しの対象だった間に書いた写しが、また現れてしまう。1 つの述語 — 上の表の書き戻しの列、つまり
`active` で、superseded でなく（`superseded_by` がない）、未解決の理由がなく、`log` でないこと。段 1 の除外もこれに
含まれる — が、3 つを一緒に決める。AF が何を選ぶか、以前 AF が書いた写しのどれを引き上げるか、`MEMORY.md` に何を
並べるか。AF が書き、その後誰も編集していない写しは、メモリが対象から外れた時点で、表のどの理由であっても引き上げる
（削除し、プレビューに示す）。ネイティブ側で編集された写しはメンバーへの競合として示す。どちらの場合も `MEMORY.md`
には並べない。経路テスト: 書き出す → メモリを suspect、quiet、log、archived、superseded（最後は `status` を `active`
のまま `superseded_by` と `invalid_at` だけ設定したもの）にする → もう一度書き出す。

**カウンタ。** 今の `.usage/<name>` は、利用 1 回ごとに 1 バイト伸び、その大きさで数えるファイルである
（`agent_memory_usage.go:5`、`:47`）。あとから読み出しと検索ヒットを区別できない。新しいサイドカーも同じ 1 バイト追記
の方式を使うので、同時に書く者がいても数え漏れはない。名前がぶつからないよう、それぞれ専用のディレクトリに置く
（名前には `.` を使える（`agent_memory.go:93`）ので、`foo` と `foo.reads` はどちらも有効な名前である）:
`.usage-v2/reads/<name>`、`.usage-v2/hits/<name>`、`.usage-v2/confirmed/<name>`、`.usage-v2/stale/<name>`。最後に
読まれた時刻は reads のファイルの mtime で、上限を超えても mtime は更新する。受入条件には、`foo` と `foo.reads` が
並ぶ場合と 64 文字の名前で、数える・忘れる・作り直すを通すテストを含める。以前のファイルは 1 リリースのあいだ
数え続け、順位付けもそれを使い続ける。`reads` への切り替えは、1 リリース分のデータがたまってからにする。忘却と
作り直しでその名前のサイドカーはすべて消え、プロジェクトの移動では一緒に動き、復元ではゼロから始まる — 今と同じ。

### 4. 安い書き込み: パッチは今、フィードバックは段 2（ツール）

**`memory_patch(scope, name, revision, edits: [{old, new}], description?)`。** 編集は本文にだけ当たる。`description`
を渡せば説明文を置き換える。フロントマターには決して触れない。どの `old` も空でなく、今の本文でちょうど 1 回だけ
一致し、一致どうしは重ならない。すべての編集を同じ元の本文に照らして、まとめて当てる。全部成功するか、何も書かない
かのどちらかで、リビジョン 1 つ、コミット 1 つ、`memory_save` と同じ秘密情報の検査・作者の規則・履歴になる。存在しない
メモリやリビジョン 0 は拒む — パッチで作成はしない。1 行直すのに 8 KB を送り直すことはなくなる。

**新しい名前での `memory_save`** は、近い既存の名前があればそれを返し（`memory_search` の名前と説明文の順位付け）、
「X には memory_patch を使うほうがよい」と添える。拒みはしない。

**`memory_feedback(scope, name, revision, verdict: confirmed|stale|wrong, note)`**（段 2）。revision は、読み手が頼った
リビジョン。それが今のリビジョンなら、`confirmed` は確認を 1 回足して最後の確認の時刻を更新し、`stale` や `wrong` は
メモをつけてフィードバックの要素を `reasons` に足す。古いリビジョンなら、報告は観測として残すだけで、status も確認も
変えない。だからリビジョン 3 への報告が、直したリビジョン 4 に印をつけることはない。メモは本文と同じく秘密情報を検査
する。1 つのセッションから 1 つのリビジョンへの報告は 1 回だけ数える。`confirmed` はどの理由も消さない。それぞれの
理由の消え方は決定 3 にある。Copilot Memory と同じく、メモリを延命するのは確認だけで、取り出されたことでは延びない。
ガイダンスが頼むのは否定の場合だけである。

### 5. LLM を使わない失効: lint

**段 1 — 報告のみ。** アンカーはまだ無いので、lint は各本文からその場で抜き出し（パス、`Test*` やコードらしい
シンボル、ADR 番号、`[[links]]`）、存在だけを確かめる: プロジェクトの既定ブランチに無いパスやシンボル、どのメモリ
にもつながらないリンク、メンバーが管理する廃止語リストの語、4,096 バイトを超える本文。リポジトリは ref で読み
（プロジェクトの git-common-dir で `origin/<default>` に対する `git ls-tree` / `git grep`）、どの作業コピーも
チェックアウトしたり変えたりしない。git の無いプロジェクト、孤立したプロジェクト、ユーザースコープは、リンク・語・
大きさの検査だけになる。出力は、設定 → エージェントメモリの読み取り専用の報告と `af-memory lint`。何も書かない。

廃止語リストはメンバーが編集する。報告は、リポジトリから読み取れる追加の候補も出す — 状態が superseded になった
ADR、既定ブランチがもう使っていないブランチ、削除された設定キー — が、どれもメンバーが受け入れるのを待つ。候補が
自分でリストに入ることはない。ある場所で廃止された語が、別の場所ではまだ正しいことが多いからである。

**段 2 — 理由。** アンカーを保存したら、lint は該当ごとに `reasons` へ要素を足す。確かめたリビジョンを記録し、ストアの
ロックの中でそのリビジョンに対する比較交換（compare-and-swap）で適用する。その後に変わったメモリは確かめ直し、古い
本文で印をつけることはない。理由を足すのも消すのも公開される変更で、作者 `lint` のコミット 1 つになり、**リビジョンを
増やす**。だから古いリビジョンを持ったエージェントは拒まれて読み直す（0108 決定 4 の規則）。黙って印を消してしまう
ことはない。取り消しは他の変更と同じに働く。「存在するが変わった」を見るには基準（アンカーごとのコミットか
フィンガープリント。drift と同じ）が要る。それはアンカーと一緒に記録し、段 2 で足す。

決定的な名前の変更（アンカーされたパスの git 上のリネーム）は独立した操作 `lint-rename` にする。本文のそのパスだけを
置き換え、コミットを根拠として持ち、同じ比較交換を使い、取り消せる。これは自動で適用する（決定 7）。

**書き手は 1 つ。** `agentMemMu` はプロセス内のミューテックスである（`agent_memory.go:98`）。AF の中では、エンジンの
書き込みはすべて Agent のストアを通る。AF のストアに対して単独で動かすエンジンは Agent の API を呼び、AF の外では
ストアのロックファイルを取る。2 つのプロセスが同じストアに直接書くことはない。

### 6. 統合（段 3）: 受け箱 → トピック → 差分パッチ

次のリリースには入れない。段 1 がこれを妨げないよう書き残す。観測（書き出した 0117 のキュー、`stale`/`wrong` の
メモ、のちに `observe` ツール）を、そのクラスタの suspect なメモリと一緒にトピックのクラスタごとにまとめる。モデルが
各観測をクラスタに照らして、追加・パッチ・置き換え・何もしない、のどれかに断片から分類し、モデルが**差分パッチ**
（決定 4 の形）を書く。全体の書き直しはしない。同じ教訓が 2 回出たら 1 つの規則にし、狭い事例は傘になるメモリに
畳み込む。

**いつ動くか: ワークスペースが暇なときに、熟したトピックだけ。セッションの終わりではない。** セッションごとに動かす
と 0117 の誤り（1 つの窓だけを見て、他のセッションも世界の変化も見えない）を繰り返し、1 つのセッションが残す数件の
観測のためにモデルを呼ぶことになる。代わりに:

- **いつ見るか**: ワークスペースのどのセッションも 15 分ターンを動かしていないとき、3 時間に 1 回まで。動いている
  セッションとメモリや CPU を取り合いにくい。実行中にターンが始まったら、進行中のモデル呼び出しだけ終えて残りは
  先に延ばす。
- **何を動かすか**: 熟したトピックだけ — `wrong` か `stale` の報告（いちばん強い信号なので 1 件で足りる）、新しい
  観測が 3 件、または 24 時間待った観測。
- **どれだけ**: 1 回ごとのトークンの予算。入りきらないものは次の回を待つ。熟したトピックは古い観測のものから
  取るので、忙しいトピックが静かなトピックを飢えさせることはない。

これは目標で、保証ではない: 動いていて暇になるワークスペースなら、`wrong` の報告にはその日のうちに修正案が出る。
ワークスペースが止まっている、暇にならない、予算が尽きた、のどれかなら遅れ、報告は遅れたトピックとその理由を
見せる。警告そのものは実行を待たない:
lint とフィードバックの理由はすぐに見える（決定 3）。数字（15 分、3 時間、3 件、24 時間）は出発点の値で、段 3 で
測って調整する。

引き継ぐ規則:

- **復活の禁止**（0117 決定 5）: 忘れられた名前や、かつて存在した名前での作成は拒む。キューに入れるときと承認する
  ときの両方で、ストアのロックの中で確かめる。`agentMemSave` だけでは許してしまう。今 `noRevival` を設定するのは
  レビューだけである（`agent_memory_review_publish.go:126`）。
- **置き換え（supersede）は 1 つのメモリ、古いほうへの変更である。** 置き換え先を先に、それ自体の公開される変更として
  作成またはパッチする。そのあとの置き換えで、古いメモリに `superseded_by` と `invalid_at` を設定する。その前に
  ストアのロックの中で、置き換え先が同じプロジェクトかユーザースコープに、提案が見たリビジョンで存在し、循環が
  できないことを確かめる。どちらも普通の 1 対象の変更なので、変更一覧・差分・最新の変更の確認・取り消しは今のまま
  動く（`agent_memory.go:1371` は `AF-Memory` のトレーラーを 1 つだけ書き、`agent_memory_changes.go:316`、`:434`、
  `:627` は対象が 1 つだと前提している）。置き換えを取り消すと、古いメモリが置き換え先の横に戻る。2 つの active な
  メモリで、次の lint か統合が見つける重複であり、中途半端な状態にはならない。複数のメモリを 1 つのコミットで変える
  変更には、別の記録が要る。
- **キューに入れる前の決定的な検証**: 大きさ、すべての `[[link]]` とパスの存在、フロントマターのスキーマ、今の
  リビジョンにパッチが当たること — Codex の統合役のバグがまさにこれだった。
- **既定は小さなモデル層。信頼する前に測る**（2026-11-07 のオーナーの目標: Haiku や GPT Luna の級のモデル）。
  モデルには、範囲が限られていて検証できる手順だけを担わせるように仕事を切る:
  - トピックへのまとめは決定的に行う（名前、アンカー、リンク、`memory_search` の順位付け）。
  - 分類の呼び出しは、観測 1 つと、そのトピックのメモリ数件の抜粋だけを見て、追加 / パッチ / 置き換え / 何もしない
    のどれかを決まった JSON スキーマで答える。
  - パッチの呼び出しは、本文 1 つを見て `{old, new}` の編集（決定 4）を返す。本文全体は返さない。
  - どの出力も上の検証を通す。当たらないパッチは捨て、大きなプロンプトで再試行はしない。

  2 つの操作は大きな層へ回すか、ただの観測としてメンバーに渡す: 置き換えと、2 つのメモリの統合。Mem0 の更新
  ルーターが失敗したのがこの場合である（先行事例）。これは慎重な選択で、測った結果ではない: その研究は、
  ルーターが失敗した場所を示すが、大きなものなら成功することは示していない。ACE の結果は、小さな判定役が失敗する
  ことも、安全であることも示していないので、段 3 は何かをキューに入れる前に、オフラインの評価から始める。書き出した
  0117 のキューと、2026-11-06 の lint で得た直し候補の一覧（古いトランクのブランチ、廃止したプロファイル、壊れた
  リンク、無くなったテスト名）から正解集合を作る: 各事例に、メンバーが正しい操作、残すべき事実、何もしないのが
  正しいかどうかの印を付ける。キューと lint の当たりそのものは正解ではない。どちらにも誤りが混じっているからである。
  両方の層をこの正解集合に照らして操作ごとに採点し（誤った変更、失った事実、見逃した修正）、層どうしの一致は補助の
  指標にとどめる。小さな層は、その操作の基準を満たすところでだけ既定にする。

  規模の目安としてだけ、**推定**: 分類 1 回の入力は約 3 k トークン、パッチ 1 回は約 2.5 k（本文の中央値 2,228
  バイト）。測った数字は 1 日約 5 件の作成だけである。観測が何件来るか、フィードバックがどれだけか（段 2 はまだ
  無い）、どれだけ上の層へ回るかは仮定である: 1 日に分類 5 回とパッチ 2 回なら月に約 0.6 M 入力トークン、20 回と
  10 回に上の層への回付を足すと約 3 M。月の上限はオフラインの評価のあとに決める。

### 7. 誰が何を適用するか

3 つの担い手、3 つの規則:

- **対話するエージェント**は 0108 決定 8 のまま: `memory_save`、`memory_patch`、`memory_forget` はすぐ公開され、あとから
  変更一覧で見つけて元に戻せる。
- **決定的な lint** は、証明できるものを自分で適用する: 理由（段 2）と `lint-rename`。
- **自律的な統合役**は決して公開しない: どの操作もメンバーを待つ。トピックごとにまとめ、項目ごとではなくトピック
  ごとに承認する。暦は無い: トピックの提案はその実行が終わった時点で見え（実行がいつ始まるかは決定 6）、待って
  いるものがある間、メンバーへの通知は 1 日 1 回まで。待つことの損は小さい。警告は待たないからである: lint と
  フィードバックが付けた理由は、誰かが修正を承認する前からすべてのエージェントに届く（決定 3）。提案は承認の時点で
  今のリビジョンに照らして検証し直す（決定 6）。14 日決められなかった提案は期限切れになり、キューが 0117 の残した
  ような溜まりにはならない: 承認はもう効かず、その観測は提案の記録（観測の ID、対象のリビジョン、使った証拠）を

### 8. AF からの独立と、位置づけ

形式（決定 3）は版つきの仕様として書く。エンジン — lint、パッチ、フィードバックの記録、のちの統合 — は AF の
パッケージを import せず、モデルの呼び出しを差し込み（1 回きりの CLI コマンドか API）として受け取る。AF はアダプタの
1 つ（スコープ、スケジューラ、台帳、Console での承認、認証）で、MCP サーバーとして動かすのも別のアダプタである。
**エンジンはこのリポジトリの中の別の Go モジュールに置く**（オーナー、2026-11-07）: 自分の `go.mod` を持ち、AF の
パッケージを import すると落ちるテストを置き、2 つ目の利用者ができるか形式が v1 になった時点で、`git subtree split`
で履歴ごと自分のリポジトリへ切り出す。

近いものに対する位置づけ:

- **Hermes Agent はハーネスであって、メモリのエンジンではない。** 学習のループはそれ自身のランタイムの中で動く。
  ファイルは持ち出せるがループは持ち出せず、1 人の利用者の 1 つのエージェントのためのもので、履歴もリビジョンの
  確認もない。AF は Hermes を種類の 1 つとして動かせるし、このエンジンを Hermes の `MemoryProvider` インタフェース
  経由で差し出すこともできる。それは上の独立性の試験にもなる。
- **Honcho は、いちばん近い独立したエンジンだが、原理が違う。** プロジェクトやコーディングエージェントも扱うが、
  持つものは、モデルが裏で導いた結論をデータベースに置いたものである。git の履歴も取り消しもなく、書き手どうしの
  リビジョンの確認もなく、リポジトリへの決定的なアンカーもなく、承認の段もなく、dream はこの記録が残すものを削除
  する。決定 3〜7 が拠って立つのはこれらの性質なので、Honcho はここでのエンジンではない。**AF の方針として**
  （Honcho の制約としてではなく）、差し込める最初の場所は `preference` の kind である: オプトインで、その出力は他の
  メモリと同じく証拠として読み、命令としては読まず、見直さずにストアへ書くこともしない。推論のために会話をサービスへ
  送る（0117 決定 2 が秘匿化で応えた懸念）。
- **より近い競争相手は、CLI に組み込まれたメモリである**（Claude Code の auto memory、Copilot Memory、Codex の
  メモリ）。この記録がそれらに無いものとして差し出すのは、すべての種類が読む 1 つのストア、リポジトリに照らした
  確認、履歴と取り消しである。

### 11. メンバーのメモリから、プロジェクトのドキュメントへ（提案、段 4）

メモリはメンバー 1 人のものである。プロジェクトのドキュメント（`AGENTS.md`、`CLAUDE.md`、`docs/`、ガイド）は、
すべてのメンバーとすべてのエージェントが読み、コードと同じようにレビューされる。1 人のストアで確かめられた知識は
そこへ行き着くべきで、そのあとメモリは中身を繰り返さず、そこを指せばよい。Cursor はメモリをやめてルールにした
（先行事例）。これはその 2 つの間の道である。

- **候補はモデルの好みではなく、信号から出す**: メンバーではなくリポジトリについての `lesson`、`procedure`、
  `preference` で、今のリビジョンで異なる 2 つ以上のセッションから確認され、開いた理由が無く、アンカーが既定
  ブランチに在り、数日変わっていないもの。`confirmed` のカウンタではこれを示せない（決定 3: 名前ごとの数）ので、
  昇格は、決定 4 の「1 セッション・1 リビジョンにつき 1 回」に既に要る記録 — セッション、リビジョン、時刻 — を使う:
  リビジョン 3 と 4 を確認した 1 つのセッションは 1 回と数え、前の本文への確認は今の本文の確認には数えない。lint は
  逆向きの検査も足す: アンカー先のリポジトリのドキュメントが既に言っていることを述べている
  メモリを、重複として報告する。
- **出力はリポジトリへの変更の提案で、コミットではない**: 対象のファイルと節、リポジトリの言語と決まりに沿った
  文面、元になったメモリ。メンバーがプルリクエストとして出すか、セッションに出させる。関門はリポジトリ自身の
  レビューである。AF が自分で push したりプルリクエストを開いたりはしない。文面は本文の秘密の走査と、リポジトリ
  自身の pre-commit の走査を通す。1 人のメモリには、共有のリポジトリに書いてはいけないホストやアカウントが
  含まれうるからである。
- **マージのあと、メモリは忘れずに置き換える。** `superseded_by` は 2 つの対象のどちらかを指す: メモリ（決定 6 の
  検証はそのまま）か、ドキュメント — リポジトリの識別、正規化したパス、見出し、それが既定ブランチに在ることを
  確かめたマージのコミット。ユーザースコープのメモリはリポジトリを明示する。相対パスだけで解決することはない。
  置き換えはストアのロックの中で、メモリが昇格の提案が引いたリビジョンのままであることも確かめる。プルリクエストを
  待つ間に変わっていたら置き換えは拒否してメンバーに戻すので、古い文面のマージが新しい中身を隠すことはない。古い
  メモリ 1 つへの変更のままなので、履歴と取り消しは決定 6 と同じに働く。メモリはエージェントの視野から外れ
  （決定 3）、履歴には残る。
- **ドキュメントの対象は、lint が検査し続けるアンカーである**。置き換え済みのメモリも対象にする: ファイルの改名や
  削除、見出しの消失、マージの取り消しはメンバーに報告し、メンバーが対象を新しい場所へ向け直すか、置き換えを取り
  消す。本文がひとりでに戻ることはない。受け入れ条件: 昇格してマージし、ファイルを改名、見出しを削除、マージを
  取り消す。どれも報告され、どの修復も効く。
- **逆向きの道は決定 5 である**: リポジトリが廃止したものが廃止語リストに入り、それをまだ使っているメモリに lint が
  印を付ける。

役に立つ最初の形には確認（段 2）とトピックのまとめ（段 3）が要る。次のリリースには入らない。

- **2026-11-10 — `lint-rename` がディレクトリ改名に従い、lint が保存済みの `anchors` を検査する（#3650、パート 2 と 3）。**
  git はディレクトリ改名を記録しないので、1 つのコミットのファイル改名から推定する。ファイル
  `a/b/c/x -> n/m/c/x` は `a/b -> n/m` と `a/b/c -> n/m/c` を意味する。コミット内で配下のファイルが別々の

  ディレクトリ改名を通してパスを書き換えるのは、パスがそのディレクトリ自身か、そのセグメント単位の配下
  （`dir2/x` は `dir` の配下ではない）にあり、そのコミットが親にあったディレクトリのファイルをすべて移し
  （`<commit>^` の `git ls-tree` で確認する。分割された、またはファイルを残したディレクトリは理由に任せる）、
  新しいパスがデフォルトブランチにあるときだけである。ファイル自身の改名はディレクトリの改名に優先する。

  `AF-Lint-Rename` を付ける。末尾スラッシュ付きのディレクトリ表記は完全パスとして扱い、先頭の `./` は綴りの違いとして扱う。

  トークンだけを見るので、コミットが丸ごと改名した最上位ディレクトリも最上位として数える（一部だけ移した、または
  複数の行き先に分けたものは数えない）。保存済みの `anchors` は本文の種類別ルール（パス、ADR 番号、`Test*` とコードらしい

  改名検出は git のもの（`-M`、類似度 50 %）なので、移動と同じコミットで中身を書き換えたファイルが多いディレクトリは
  丸ごと移ったとは数えない。**スケジューリング（パート 1）は作っていない。** 統合器の tick はモデルを呼ぶ
  `memoryConsolidation` スイッチ、3 時間の窓、専用の状態ファイルで制御され、いずれも提案フローのものである。lint は
  モデルを呼ばずそれらを要しないので、その tick へのフックではなく、専用のスイッチと窓が要る。
