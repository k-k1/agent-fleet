## 背景

Google サインインを使うアプリは、プレビューホストの背後ではログインを完了できない。Google は OAuth
クライアントに登録したリダイレクト URI しか受け付けず、プレビューのホスト名は起動のたびに変わる
（0062 決定 3）。既存の手では埋まらない。

- **スラグの固定**（0062 決定 3）でも、Google クライアントに「開発者 × アプリ」ごとのリダイレクト URI が要る。
  しかもそのクライアントは別チームの持ち物だったり、本番と共有だったりする。
- **登録済みの `http://localhost:…` をブラウザペインで使う**手は、ペインの Chromium（ヘッドレス・CDP 駆動）での
  サインインを Google が拒否するため通らない。
- ワークスペース内で Google のホスト名を上書きする（hosts と私設 CA）手は**却下**した。認可の手順はユーザー自身の
  ブラウザで走り、`dev` は root を持たず、`gcloud` や `gh` も動くコンテナの中に `google.com` を署名できる CA を
  置くことは許容できない。

Control Plane は現状 OIDC の*クライアント*でしかなく（`internal/auth/oauth_oidc.go`）、署名鍵も、ローテーションも、
JWKS もない。本記録はそのサーバー側を、小さく、かつ開発用であることを隠さない形で加える。

## 決定

### 1. 発行者（issuer）は Console のオリジン上の 1 つ：`{PUBLIC_BASE_URL}/dev-idp`

アプリは issuer・client id・client secret を設定で差し替えるだけで、ほかは何も変えない。この IdP は Google を
名乗らない。issuer は独自のもので、すべての ID トークンと userinfo の応答に `af_dev: true` が入る。

置くのは **Console のオリジンだけ**。プレビューホストはユーザーのアプリへ中継されるので、そこでの
`/dev-idp/…` はアプリのルートであって、こちらのものではない（0062 決定 8）。アプリの*サーバー*が呼ぶもの
（discovery、token、userinfo、jwks）はセッションを持たないので `authGate` の対象外にし、`authorize` は内側に置く。

| `/dev-idp` 以下 | 認証 | 役割 |
|---|---|---|
| `/.well-known/openid-configuration` | なし | discovery |
| `/jwks` | なし | 公開鍵 |
| `/authorize` | Console のセッション（`authGate`） | サインイン中のメンバーが本人。パスワード入力なし |
| `/token` | クライアントシークレット | code → ID トークン＋アクセストークン |
| `/userinfo` | Bearer アクセストークン | 同じクレーム |

`token`・`userinfo`・`jwks` へはワークスペースの中からも、他のワークスペース→CP の呼び出しと同じ道で届く。
コンテナ内のサーバーがブラウザと同じ公開 Console URL（`AF_CP_BASE_URL`）を呼ぶので、第 2 のリスナーは要らない。

### 2. 署名は RS256

openid-client（Auth.js）も Spring Security も既定が RS256 なので、提供するアルゴリズムはこれだけ。2048 ビット、
`kid` は公開鍵のサムプリント。

### 3. 有効化：デプロイのフラグ → ワークスペースのオプトイン。どちらも既定は off

`AF_DEV_IDP=1` でデプロイが提供する（issuer のオリジンである `PUBLIC_BASE_URL` も要る。無ければ off のままで、
起動時にその旨を出す）。それまでは**全エンドポイントがメソッドを問わず、サインインの有無も問わず 404**（IdP が off の間、`authGate` は `/dev-idp/authorize` をログイン画面へ飛ばさず、その 404 まで通す）。そのうえで各ワークスペースが
ワークスペース設定 `devIdp`（`PUT /api/env/ws-settings`）でオプトインする。していないワークスペースでは
`authorize` が拒否し、`token` は `invalid_client` を返す。IdP を提供しないデプロイでは設定を保存できない
（409）。保存された「on」が、フラグを立てた日に誰の判断もなく点灯してしまうからである。

テナントごとの運用者ゲート（`allow_agent_self_update` の隣のテナント上限）は検討したが初回では見送った。
運用者のスイッチはデプロイのフラグである。必要になれば Console 画面（#2222）と一緒に入れる。

### 4. 鍵：保存時に封緘、30 日でローテーション、退役した鍵は 1 日公開

- `dev_idp_key` に、PKCS#8 の秘密鍵をキーカストディアンで **`deployment`** の鍵参照のもとに封緘して置く
  （エンジンのトークンと同じ。テナントではなくデプロイに属する）。公開鍵（PKIX）は平文なので、JWKS の提供で
  何かを開封することはない。この列は `sealedColumns` にあり、`rewrap-keys` の対象になる。
- 最初のリクエストが鍵を作る。30 日を過ぎると次の署名で新しい鍵を作り、古い鍵を退役させる。退役した鍵は
  トークンの寿命よりはるかに長い 24 時間 JWKS に残り、その後削除する。複数の Control Plane が同時に作っても
  どちらも成功し、署名は新しい方、公開は両方になる。
- 秘密鍵がある場所は 3 つだけ：封緘された列、このプロセスのメモリ、それが作る署名。ログにも応答にも監査行にも
  出さない（トークン応答・JWKS・discovery・ログ・監査行を探すテストがある）。

### 5. クライアント登録：ワークスペースに 1 つ。値は env でコンテナに渡す

- `client_id`（`afdev-…`）と 32 バイトのランダムなシークレットは、ワークスペースがオプトインしたときに
  Control Plane が生成し、`dev_idp_client` に置く。シークレットはテナントの鍵で封緘する。コンテナは**起動の
  たびにもう一度**これを要るからである。`aud` はその client id で、コードもトークンも、発行したクライアント
  （かつ、そのワークスペースがまだオプトインしていること）に対してしか通らない。
- オプトインを切ると登録を削除し、また入れると新しい client id とシークレットが出る。これがローテーションで、
  忘れられる別の「ローテート」呼び出しは作らない。
- `AF_DEV_IDP_ISSUER`、`AF_DEV_IDP_WELL_KNOWN`（discovery の URL。Auth.js の `wellKnown` が欲しがる）、
  `AF_DEV_IDP_CLIENT_ID`、`AF_DEV_IDP_CLIENT_SECRET` を、`AF_PREVIEW_URL_{port}` と同じ場所
  （`workspaceExtraEnv`）で注入する。名前に `DEV_IDP` を入れたのは意図的で、本番の設定がこれを読んでいれば
  grep で見つかる。`GOOGLE_*` にしなかったのは、本番用の変数へ黙って写されないようにするため。起動済みの
  コンテナは起動時の env を持ち続ける。エンドポイントは設定にすぐ従う。
- ws-settings の応答は issuer と client id を返し、シークレットは返さない。

### 6. Google に似せたクレーム

`sub`、`email`、`email_verified`、`name`、`picture`。付与されたスコープで絞る（`sub` は常に。`email` は
`email`・`email_verified`、`profile` は `name`・`picture`）。

- メンバーの紐づいたアイデンティティに realm が `https://accounts.google.com` のもの（`IdentityLink.Realm`）が
  あれば、`sub` とメールアドレスは**本物の Google の値**になり、アプリの既存ユーザー行と一致する。**`hd` は付けない**。
  `hd` は Google ホストのドメインに属することを表すが、アドレスのドメインからは証明できず（個人の Google
  アカウントでも任意のアドレスを使える）、リンクには Google が検証した値も残っていない。`hd` で組織所属を
  確認するアプリには、非所属者と同じく欠落して見える。検証済みの `hd` をリンクに保存すれば、後から出せる。
- なければ `sub` は `af-` ＋アイデンティティ ID のハッシュ。人ごとに安定し、Google の `sub`（数字）とは
  衝突し得ない。アドレスはアイデンティティのもの。
- `picture` は Control Plane が知らないので、作らずに省く。
- `iss` は issuer、`aud`／`azp` は client id、`nonce` は素通し、`at_hash` を付け、トークンの寿命は **10 分**。

### 7. `authorize`：本人は Console のメンバー。何よりも先にリダイレクト先を検査する

呼び出し元は、**そのワークスペース自身のテナント**の有効なメンバーとして解決され（許可されたネットワーク・
プロバイダ経由。`/preview-auth` と同じリゾルバ）、かつそのワークスペースのプレビューを開ける人でなければ
ならない。持ち主、または持ち主が `previewTenantShare` を on にしている間の同テナントの同僚
（0062 決定 14・15）。したがって同僚は、共有されたプレビュー上で自分自身としてサインインする。

`redirect_uri` が通るのは次のどちらかだけ。

- `https://{slug}-{port}.{PreviewDomain}/…`：**このワークスペースの現在のスラグ**で、プレビューのポート一覧に
  あるポート。他のメンバーのスラグ、再起動前のスラグ、一覧外のポートは通らない。
- `http://127.0.0.1:{port}/…` または `http://localhost:{port}/…`（ポート明示）。

照合は**正規の綴り**で行う。大文字のホスト、末尾のドット、明示の `:443`、userinfo、フラグメント、バックスラッシュ、
`host.evil.example` や `localhost:3000@evil` のような接尾・接頭の細工は、正規化せず拒否する。正規化のたびに、
この検査とブラウザの解釈がずれる余地が生まれるからである。クライアントやリダイレクト先を信用できない要求には
**400 のページを返し、リダイレクトはしない**（この入口が成ってはならないオープンリダイレクト）。理由によらず
メッセージは 1 つ。リダイレクト先が信用できてから初めて、プロトコルエラーを `state` 付きでそこへ返す。応答には
`iss`（RFC 9207）を付け、クライアントが別 issuer のコードを拒否できるようにする。

再認証の要求は無視せず拒否する。`none` 以外の `prompt` と、あらゆる `max_age` は、（検査済みの）`redirect_uri` へ `invalid_request` として返す。ID トークンに `auth_time` は入れない。Console のセッションが唯一の認証で、その経過時間は保持していないからである。無視すると、`max_age` の扱いを試すアプリが偶然に通ってしまう。

`token` の段階では `redirect_uri` が `authorize` で運ばれたものとバイト単位で一致しなければならず、許可の判定は
**そこでもう一度**行う。その 1 分の間に再起動でスラグが変われば、コードは死ぬ。

### 8. `token`：機密クライアント、1 回限りで短命のコード、PKCE は提示されたら強制

- クライアント認証は `client_secret_basic`（資格情報を form-urlencode してから Base64、RFC 6749 §2.3.1）か
  `client_secret_post`。両方同時、または URL に載せたシークレットは拒否する。未知のクライアントと誤った
  シークレットは同じ応答にする。
- コードの寿命は **60 秒**。ハッシュで保存し、条件付き `UPDATE` 1 回で使い切るので、同時に引き換えても勝つのは
  ちょうど 1 つ。2 回目は `invalid_grant` で、そのコードが生んだトークンも失効させる（RFC 6749 §4.1.2）。失効はコード自体への永続的な印（そのコードが生み得るトークンがすべて切れるまで保持）で、トークンの削除より先に書く。まだ処理中だった引き換えが保存するトークンは、保存時か `userinfo` で拒否されるので、どの順序で重なっても生きたトークンは残らない。
  別のクライアントが出したコードは拒否され、使い切られているので本来のクライアントにも使えなくなる。
- **PKCE：S256 のみ。要求にチャレンジがあれば必ず強制し、なければ任意。** Spring Security は機密クライアントでは
  既定でチャレンジを送らず、このクライアントは常に機密（`token` でシークレットが要る）で、`state` と `nonce` が
  ほかの守りになる。チャレンジのない要求に対するベリファイアの送付は拒否（ダウングレードの探り。RFC 9700
  §4.8）、`plain` も拒否。Spring のケースが要らないと分かれば、PKCE の必須化は 1 行の変更で済む。
- アクセストークンは JWT ではなく不透明な値（ハッシュを保存、コードと一緒に失効できる）。`userinfo` が鍵を
  要らず、リプレイ時に落とせる。

### 9. 監査

`workspace.dev_idp`（on/off と実行者）は設定を変える前に書く。`workspace.dev_idp_token` は**発行のたびに、
応答が出る前に**書く。行がなければトークンもない。内容はクライアントとサブジェクトで、トークンも鍵も入れない。
認可の拒否は URL を含めずにログへ出す。

### 10. ペルソナは本変更に含めない

テスト用の任意の ID（`admin@…`、`viewer@…`）は選ぶための同意画面が要るが、この IdP にはない（`authorize` は
サインイン中のメンバーとして黙って承認する）。続き（#2223）が間違えないよう、制約は今のうちに決めておく：
ペルソナのアドレスは予約ドメイン `example.test`（RFC 2606）、`sub` には `persona:` の接頭辞を付ける。実在メンバーの
アドレスも Google の `sub` も名乗れない。

### 11. 本当に危ないことと、その手当て

危険なのは、本番に出たアプリがこの issuer を信用したままの状態である。そうなると、Console アカウントを持つ
誰もが、Control Plane が保証する任意の ID を作れる。防ぎとして：

- issuer のパスが目立つ（`/dev-idp`）。env 名にも `DEV_IDP` が入る。
- audience は 1 つのワークスペースの client id なので、ここのトークンは他のクライアントには通らない。
- トークンは 10 分、コードは 60 秒、すべてのトークンに `af_dev: true`。依存側で検査できる。
- デプロイも、ワークスペースも、既定は off。
- ガイド（member/10）が 1 行で言う：本番の設定にこの issuer を信用させない。

## 却下したもの

- **本物の Google 向けに Console オリジンへ固定のリダイレクト中継を置く。** Spring Security などは戻ってきた
  URL を `redirect_uri` と照合するので、中継は対象のアプリ自体を壊す。Google API のアクセストークン
  （Calendar、Drive）と合わせてスコープ外。
- **ワークスペース内の hosts／CA 上書き。** 背景を参照。
- **パスワードや同意の入力。** メンバーはすでに Console にサインインしている。もう一度聞けばクリックを素通りする
  癖がつく。同意画面が戻るのはペルソナ（#2223）のときだけ。
- **implicit／hybrid フロー、`form_post`、リフレッシュトークン、`plain` の PKCE。** Auth.js や Spring で Google
  サインインを使うアプリには要らず、どれも面が増える。
- **JWT のアクセストークン。** `userinfo` に鍵が要り、コードと一緒に失効もできない。
- **PKCE の必須化。** 決定 8。
- **テナントごとの鍵。** 開発用のデプロイ単位の道具であり、テナントごとの鍵はクライアント束縛以上の分離を
  生まずにローテーションだけ増やす。

## 影響

- Control Plane：`dev_idp.go`（エンドポイント）、`dev_idp_client.go`（登録、クレーム、リダイレクト先の許可
  リスト）、`dev_idp_keys.go`（鍵束と RS256）、`store_dev_idp.go`、`ws_settings.go`（`devIdp`）。マイグレーションは
  **sqlite と Postgres の両方**：`0101_dev_idp.sql`／`0086_dev_idp.sql`。前方互換で、ダウングレードの道はない。
- デプロイ：`AF_DEV_IDP=1` と `PUBLIC_BASE_URL`。証明書も DNS も要らない。
- Control Plane を複数立てる構成では鍵テーブルを共有し、各レプリカは 1 分ごとにその見え方を更新する。
- ガイド：`guide/member/10-integrations.md`（両言語）に Auth.js と Spring Boot の設定、本番への警告。

## 追記（2026-10-16）：ペルソナを実装した（#2223）

決定 10 は初回の変更からペルソナを外していた。制約はそのままに、いま実装した。決定 1〜9 と 11 は書かれた
とおり有効。

- **定義。** ペルソナは `handle`（と任意の表示名）で、ワークスペースごとに保存する（`dev_idp_persona`、
  マイグレーション `0102` / `0087`、ワークスペース＋handle で一意、最大 20 件）。handle は
  `[a-z0-9][a-z0-9._-]{0,31}` に一致する必要があり、入力したままの綴りで保持する（大文字小文字や Unicode の
  正規化はしない）ので、どんな綴りも別のアドレスにはならない。表示名は `name` クレームにしか出ない。
  アドレスは `<handle>@example.test`、`sub` は `persona:<handle>`。そのアドレスが実在の identity やリンク済み
  サインインのものなら、定義時と**使用時にも**拒否する（テスト用テナントが `x@example.test` を本当に持つことが
  ありうる）。管理は `/api/env/ws-settings/dev-idp/personas`（GET / POST / `DELETE …/{id}`）、変更は
  `workspace.dev_idp_persona` として監査し、Console のプレビュータブで編集する。
- **同意画面。** `authorize` はこれまでどおり全てを検証した後、ワークスペースにペルソナが 1 つ以上あり、かつ
  `prompt=none` でなければ、コードの代わりにページを返す。リクエストは `dev_idp_grant` の `consent` 行
  （5 分・1 回限り）として預かり、そのランダムな id がフォームの ticket になる。フォームは `authGate` の内側の
  `/dev-idp/consent` へ POST する。リダイレクト先・`state`・nonce・PKCE challenge は預かったリクエストから取り、
  フォームからは取らない。ticket は表示したメンバーに結び付き、POST は ticket に触れる前に他サイトの `Origin` と
  `same-origin` 以外の `Sec-Fetch-Site` を拒否し、メンバー・`redirect_uri` の規則・オプトインを改めて判定する。
  他ワークスペースのペルソナ id は「存在しない」。ページは `frame-ancestors 'none'`・`no-store`・`no-referrer`
  付きで返し、`html/template` でエスケープする。他の `/dev-idp` と同じく Console オリジンにだけ存在し
  （0062 決定 8）、IdP が off の間は 404。

## 追記（2026-10-16）：同意ページの Referrer-Policy は `same-origin`（#2243）

上のペルソナの追記は同意ページを `no-referrer` で返すとしている。この値だとブラウザがページ自身のフォーム POST に
`Origin: null` を付け、厳格な `sameOrigin` が拒否するため、実環境では送信のたびに 403 になった（Go のテストは
`Origin` を手で付けるので気づけなかった）。ページは `Referrer-Policy: same-origin` で返すようにした：同一オリジンの
POST には本物の Console オリジンが付き、リダイレクト先のアプリには `Referer` が渡らない。`sameOrigin` は変えない
（`Origin: null` は今も拒否）。認可のリダイレクトは `no-referrer` のまま（フォームを持たない）。

## 追記（2026-10-17）：Agent Fleet の画面としての同意ページと「キャンセル」（#2245）

## 追記（2026-10-16）：クライアントはオプトインより前に作る。ワークスペースごとのスイッチは無くす（#2242）

決定 5 の「オプトイン時に作成し、オフ→オンで再発行」と、決定 3 のワークスペースごとのオプトインを置き換える。
オプトインに再起動が要ったのは、クライアントの値が起動時の環境変数でしかコンテナに届かず、オフ→オンのたびに新しい
secret が発行されたためである。そのうえでスイッチ自体を無くす。環境変数は起動時に固定されるがスイッチは固定されないので、
スイッチはガイドどおりに作ったアプリを壊すことしかできない（`AF_DEV_IDP_ISSUER` があれば dev の issuer を選ぶアプリは、
オフの間サインインに失敗する）。

- 配備が IdP を提供している間（有効・固定されていない・`PUBLIC_BASE_URL`・プレビュー用ドメインが揃っている）、
  すべてのワークスペースのクライアントを `authorize` / `token` / `userinfo` が扱う。クライアントは起動時に無ければ
  作る（`CreateDevIdPClient` は挿入か既存維持なので、並行起動でも 1 行に落ち着く）。`AF_DEV_IDP_*` は起動のたびに渡す。
  配備が提供していないときは何も渡さず、全ルートがオフのときと同じ 404 になる。前の追記のプレビュー用ドメインの規則は
  「提供している」に含める：プレビュー用ドメインが無いと `devIdPIssuer` は空になる。
- `PUT /api/env/ws-settings` の `devIdp` は受け付けて無視する（古いクライアントに 400 を返さない）。応答には含めない。
  保存済みの値は効かない。`devIdpAvailable` は配備が IdP を提供しているときだけ true。
- `POST /api/env/ws-settings/dev-idp/rotate` は新しい client id と secret を 1 回の upsert（`ReplaceDevIdPClient`）で発行し、
  `workspace.dev_idp_rotate` として監査する。古い組はすぐ使えなくなり、コンテナには次の起動で新しい組が届く。Console はそう案内する。
- 管理者向けの状態のフィールド `opted_in` は `clients` になった。数えるのは登録で、起動済みのワークスペースすべてに存在する。
- 変えないもの：ペルソナ、テナント共有のプレビュー、リダイレクトの許可リスト、PKCE、使い切りの code、`af_dev`。

## 追記（2026-10-17）：ブラウザ向けのエラーページは同意ページの外枠を共有する（#2262）

## 追記（2026-10-18）：ワークスペースが停止中でも loopback へのリダイレクトを使える（#2301）

`http://localhost:<port>/…` と `http://127.0.0.1:<port>/…` へのサインインは、メンバーのワークスペースが停止中でも使える
機能として扱う。メンバー**自身のマシン**上のアプリが使えるようにするためである。許可リストはもともと、オーナー（と
テナント共有の閲覧者）に対してプレビューのスラッグなしでこれらのホストを通しており、`authorize`・`consent`・`token`・
`userinfo` はストアからクライアントを読むだけで、ワークスペースが起動中かどうかは見ない。プレビューホストへの
リダイレクトは現在のスラッグが要るので、停止中は拒否されたままである。挙動は変わらない。`dev_idp_stopped_test.go` で
固定しており、停止中のワークスペースのクライアントを拒否する確認を足すとこのテストが落ちる。

- 代償：クライアントシークレットがコンテナの外に出る。シークレットは `AF_DEV_IDP_CLIENT_SECRET` にしかないので、
  メンバーのマシン上のアプリがそのコピーを持つことになる。コピーされたシークレットの失効は、シークレットのローテーション
  （`POST /api/env/ws-settings/dev-idp/rotate`）で行う。古い組はすぐ使えなくなる。
- IdP は、ブラウザーペインの loopback とメンバーのマシンの loopback を区別できない。どちらも同じリダイレクトである。
- メンバー向けの案内は #2302。
