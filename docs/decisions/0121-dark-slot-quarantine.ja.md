## 背景

`ecs-ec2` のスロットは、EC2 が `running` のまま、ステータスチェックもすべて通るのに、応答しなくなることがある。
本番、2026-10-21：スロットがメモリ逼迫で約 20 分スラッシングした（EBS の読み出しが 5 分あたり約 100 から約 19 万、
CPU 35〜95 %）。ECS エージェントは切断し、SSM エージェントの最後の ping はメンバーの Stop の 1 分前で、メンバーは、
運用者が保留中の umount を取り消してインスタンスを手で止めるまで、起動し直せなかった。同じ形の先の事件
（docs/log/64 §64.40）が `abandonLostSlot` のある理由である。

暗いスロットに対してツリーがすでにしていること、そして止まるところ：

| 場所 | していること | 欠けているもの |
|---|---|---|
| `waitSlotRegistered`（Start） | `slotLostAfter`（300 秒。100 回のポーリング）のあいだ 3 秒ごとに `registeredSlots` を見て、最後に EC2 が `running` かを 1 回確かめ、`errSlotLost` を返す | *このスロットを待っている* Start だけが見る。メンバーが不在の間は誰も見ない。300 秒はポーリング回数で、連続して暗かったことの計測ではない |
| `abandonLostSlot` | `quarantined` タグ、コンテナインスタンスの強制登録解除、タスク ENI が消えるのを待つ、Force 付き `StopInstances`、home の切り離し（フォールバックは強制切り離し）。どの手順も Start 自身の所有権チェック（`ifOwned`、#2462）の下 | その Start からしか届かない |
| `quarantineSlot` | マウント失敗に対して：`quarantined` タグ、マウントロック、SSM で上限つきの umount、切り離し、claim を落とす、通常の `StopInstances`。登録解除は**しない**。SSM が要る | マウント失敗のみ。暗い箱には使えない |
| `sweepVolume` | `if live workspace: leave it alone`（`DesiredCount`・`RunningCount`・`PendingCount` のどれかが 0 超） | 暗いスロットで名目上動いているワークスペースが、まさにこれに飛ばされる |
| `sweepVolume` の休眠側 | `slotSleepAfter` 後にスロットを止める。ただしタスク ENI を持つものは止めない（決定 3-3） | 暗いスロットはタスク ENI を持ち続けるので、「leaving it running for now」と永遠にログに出る |
| `sweepGhostInstances` | EC2 インスタンスが**消えた**コンテナインスタンスを登録解除（`ghostAfter`、1 時間） | 動いている箱は対象外 |
| `stuckStoppingReason`（#2447、`main` にある） | 切断したスロットで `STOPPING` のまま止まったタスクを、ブロックされた起動フェーズとして示す | 検出のみ |
| #2474（未マージ） | 運用者が 1 台止める：CP の SSM コマンドを取り消し、載っている Start を終わらせ、`StopInstances`。スロットは使われ続け、次の Start が起こす。ゲートは、ECS エージェントが接続**かつ** SSM が Online のスロットを拒否する | 手動。ENI の確認も登録解除もない |

欠けているのは*だれも Start していない間の目*と、見たときに何をするか、である。それが見かけより難しい理由が 4 つあり、
最初の 3 つはどれも痛い目を見て分かったことだ：

1. **クラスターに応答しない箱には何も頼めない。** SSM も暗いので、コマンドを走らせる手順（umount）はどれも固まり、
   それを待つ Start はイングレスの 60 秒の中で終われない（#2446）。
2. **止めることは無料ではない。** 動いているタスクの ENI はまだ付いている。その間に止めると箱は multi-ENI で戻り、
   NAT のないデプロイでは egress を失って、エージェントは二度と再接続しない（決定 3-3、スイーパー自身の経路で再現）。
   だからスイーパーはそういう箱を止めず、暗いスロットが何時間もそこに居座る。`abandonLostSlot` はそれを回避する
   コード（先に登録解除して、ECS に ENI を手放させる）だが、2026-08 の事件から書かれたもので、そのとき手で観察できたのは
   ENI の半分だけ。登録解除がそれ以外に何をするかは確立して**いない**（未解決の問いを参照）。
3. **スロットに手を出すものは、それを使う人たちと競合する。** #2474 は「スロットを隔離する」として始まり、その競合が
   どこにあるかを見つけるのに 4 巡のレビューを要した（決定 3 を参照）。「止める。ほかは何も変えない」に絞り、
   隔離はこちらへ移した。
4. **暗いという信号は偽りやすい。** エージェントの再起動、起動、wake、インスタンスの再起動は、どれもしばらく暗く見え、
   暗さより古い起点は何も証明しない。そのどれかに反応すれば、健全な箱を捨てることになる。

## 決定

### 1. 検出：述語は 1 つ、連続した暗さを証明する起点、そして Start が持つスロットにスイーパーは触れない

スロットが、あるスイープで**暗い**とは、次のすべてが成り立つことをいう：

- EC2 が `running`（`pending` や `stopping` は起動中・停止処理中であって暗いのではない）。
- ECS のコンテナインスタンスが `ACTIVE` で `agentConnected=false`、または未登録。
- SSM が `Online` 以外の `PingStatus`（`ConnectionLost`、`Inactive`）で載せているか、載せていない。
- 起動または開始から少なくとも `darkBootGrace` が経っている（`LaunchTime`。開始のたびに動く。既定 300 秒。測った
  起動・wake の待ち、約 35 秒と約 20 秒より上）。
- ワークスペースのサービスが**動いている**（`DesiredCount > 0`）スロットでは、ワークスペース Agent へのプローブも失敗する。
  ECS エージェントが暗くてもコンテナはメンバーに応答しているかもしれず、それを止めるのは救出ではない。`State()` は今は
  Agent をプローブせず（ボリューム・claim・ECS サービスから状態を導く）、このプローブは**新しい部品**になる。それができるまで、
  サービスが動いているスロットは L0（観察）にとどまり、自動では救出しない。

**失敗した読み取りは答えではない。** ECS・EC2・SSM の呼び出しがエラー・スロットル・タイムアウトになれば、そのスロットについて
そのパスは*不明*になる：刻印も、消去も、動作もしない。「SSM が載せていない」は、呼び出しが成功したときだけ答えになる。

**起点。** 起動世代の中で述語全体が成り立つと最初に確かめたパスが、インスタンスタグ `af-dark-since` を `<時刻>/<LaunchTime>` で
書く。フォールバックとしてだけでなく*常に*書く。ほかのコードがこのタグでスロットを除外するからだ（決定 3）。以降のパスは、述語が
まだ成り立ち、`now − 刻印 ≥ darkAfter` のとき動く。スロットが健全だと確かめたパスは刻印を消し、`LaunchTime` が今のものと違う
刻印は古いものとして書き直すので、開始のたびに時計はやり直しになる。

外部のタイムスタンプが待ちを縮められるのは、**両方**の半分を独立に証明するときだけ：`darkAfter` より古い SSM の
`LastPingDateTime` *と*、このコンテナインスタンスで `STOPPING` のまま止まったタスクの `StoppingAt`（#2447）が `darkAfter` より古い、
の両方が、今の起動世代のもので、このパスで確かめられていること。片方だけでは、もう片方について何も証明しない。何日も前から
オフラインの SSM エージェントを持ち、ECS エージェントは 1 分前まで正常だった箱が、そうでなければ 10 分暗かったと読まれてしまう。

**しきい値。** `darkAfter` の既定は **10 分**、環境変数（`AF_ECS_EC2_DARK_AFTER_SEC`、0 = オフ）。`darkBootGrace` 以上、かつ
`slotLostAfter + sweepEvery` 以上でなければならず、逆転して設定したデプロイは起動時にログを出して引き上げる。健全な箱が待つどの
時間（ホットなスロット：最初のポーリング、wake：約 20 秒、新しい箱：約 35 秒）よりも長く、すでに待っている Start を支配する
`slotLostAfter`（300 秒）よりも長い。`placementBlockedGrace`（120 秒）は CP 自身が作る待ちに対する*メッセージ*のもので、
`ghostAfter`（1 時間）は EC2 インスタンスが**消えた**コンテナインスタンスのもの。どちらも流用しない。既定値は、未解決の問いに
答えが出るまでは推測である。

**対象。** **home が付いていて、生きている claim のない**スロットだけ。`sweepVolume` が歩くのと同じ母集団である。生きている
claim は Start が収束中であることを意味し、`slotLostAfter` による判断はその Start のもの。スイーパーは `sweepVolume` と同じに
飛ばす。空きの暗いスロットは救う相手がいないので、通常の空きスロットの規則に従い、プール画面が印を付ける。

*却下した案。* CloudWatch 駆動の検出器：CP が持たないもう 1 つの真実の源が要り、同じ競合の問いに答える必要も残る。短い
しきい値：wake 中の箱に動いてしまう。CP 側の検出回数カウンター：再起動で失われる。SSM か ECS のタイムスタンプだけを起点にする
こと：上を参照。

### 2. 対処のはしご：まず救出、隔離は 2 度暗くなった箱か救出できない箱だけ

メンバーに要るのは動く箱の上の home で、運用者に証拠が要るのは*箱*に非があるときだけだ。メモリのスラッシングはたいてい
*ワークロード*の非で、同じワークロードを新しい箱へ移せばそこでもスラッシングする。だから最初の発生で隔離すると、運用者が
終了するまで課金される root ボリューム（決定 30）と、上限のうちのスロット 1 つと、長い Start を払うことになる。得るのは、
ログがすでに語っていることの証拠である。したがって：

- **L0. 観察。** 刻印を書き、プール画面は「N 分暗い」と出す。最初のリリースでは、これが挙動のすべて（決定 5）。
- **L1. 救出**（`darkAfter` 暗かったとき）：home を箱から外し、箱は使い続ける。各手順は次の手順のゲートであって、押し通す
  連なりではない：
  1. 所有権を取り（決定 4）、救出マーカーを書き、箱の上の CP 自身の保留中 SSM コマンドを取り消す（生きている間は home の
     マウントロックを握り続ける）。
  2. Start を Stop と同じように終わらせる（`abortStarts`、desiredCount 0、claim を落とす）。
  3. コンテナインスタンスを強制登録解除し、上限内に**タスク ENI が物理的に消えたことを確かめる**（`DescribeInstances`）。
     登録解除がほかに何かをするとは仮定しない。AWS はタスクのプロセスを止めないと文書化している。
  4. ENI が消えているときだけ `StopInstances`（まず通常、終わらなければ Force。#2474 と同じく、その後に起動し直された
     インスタンスには決して使わない）。そして **`stopped` を確かめる**。
  5. 箱が止まっているときだけ、home の普通の切り離し。ロールは `slot` のまま、`af-wedge-at` を刻み、マーカーを消す。

  上限内に ENI が消えない、または箱が止まらなければ、救出は**ブロック**される：それ以上は何もせず、箱はそのまま、マーカーは
  段階を保ち、プール画面と監査がそう示す。ブロックされた救出は毎パス再試行され、次の段が有効でなければ運用者が解決する
  （手動の強制停止か終了ボタン）。
- **L2. 隔離**：箱が前の `af-wedge-at` から `darkRepeatWindow`（既定 24 時間）以内に**もう一度**暗くなったとき、**または**
  救出が `rescueBlockedAfter`（既定 30 分）ブロックされたままのとき、使い続ける代わりに隔離する。隔離は箱に理由つきの
  `af-role=quarantined` を付け、残し、回収しない（決定 30）。ブロックされた救出では、`abandonLostSlot` がすでに認めている
  唯一の例外、止まらない箱からの home の**強制切り離し**も許す。これは、だれも届かないワークスペースの下でディスクを引き抜く
  ことで、トレードオフは明示する：失うのはそのワークスペースの未フラッシュの書き込みに限られ（ext4 も XFS も次のマウントで
  ジャーナルをリプレイする）、対するのはメンバーが無期限に塞がれること。有効になるのは `quarantine` モードだけで、
  未解決の問い 5 の測定のあと。

`STOPPING` のまま残るタスクは、救出で消えると**仮定しない**。消えるかどうかは未解決の問い 4。残れば、メンバーの次の Start は
#2447 のブロック済みフェーズの文を読み、既存の対処が使える（古いインスタンスを一度起動してエージェントに報告させる。やり方は
ガイドにある）。

*却下した案。* **常に隔離**（#2474 の最初の設計）：上の議論と決定 3。**常に強制停止して同じ箱を起こす**（#2474 が運用者に
してくれること）：タスク ENI のない箱には安全だが、暗い実行中ワークスペースでは ENI が付いたままなので停止は multi-ENI の罠で、
egress がなくて wake に失敗し得る。運用者の選択としては良く、自動の既定としては誤り。**インスタンスだけ止めて home は付けた
まま**：メンバーは塞がれたまま。次の Start は、STOPPING のタスクが残る箱に home があるのを見つけ、それを待つ（#2447）。
**止めずに登録解除**：動いている箱が ECS から切り離され、借り手のないまま課金される。

### 3. home を移すとき：使用中スロットに届くすべての行為者と不変条件

L1 も L2 も home が箱を離れて終わる。したがって、home の載ったスロットに何かが触れ得るすべての経路を数え上げなければならない。
動詞は `releaseSlot` と `terminateSlot` の 2 つで、以下は `runtime_ecs_ec2*.go` のすべての呼び出し元と、その背後の行為者、
L1 と共有するもの。

**使用中スロットに届く行為者**

| 行為者 | スロットへの動詞 | L1 との直列化 | 暗いスロットへの規則 |
|---|---|---|---|
| 占有者自身の Start、同じタイプのアフィニティ（`placeHome`） | claim して起こす | home の Start カウントと claim ロック | L1 の所有権が追い越す。claim を持つスロットについての Start 自身の `slotLostAfter` の判断は残る |
| 占有者自身の Start、サイズ/class 不一致（`placeHome` → `releaseAndReplace`） | 背景で `releaseSlotSince` | 各境界での `startSuperseded`。マウントロック | 同じ |
| 占有者自身の Start、予約/古い（`replaceReservedSlot`） | `moveHomeOff`（`releaseSlot`）のあと**古い**箱を `terminateSlot` | 同じカウントとマウントロック | 同じ。`terminateSlot` は隔離された箱を拒否（規則 4） |
| ほかのメンバーによる追い出し（`evictLongestIdle`） | 最もアイドルの長い占有者に `victim.releaseSlot` | 犠牲者自身のランタイム：そのマウントロックと Start カウント | `af-dark-since` が刻まれたか救出マーカーのあるスロットは**飛ばす** |
| ほかのメンバーの `makeRoom` | `victim.releaseSlot`、そのあと**呼び出し側が**箱を `terminateSlot` | 犠牲者のマウントロックとカウント。終了そのものはフェンスされない | **飛ばす**（休眠中の暗い占有者は実行中のタスクがないので `tasks[id] > 0` では除外されない） |
| ゴールデンのベイカー（`ReleaseForBake`、seed と probe の Start/Stop） | seed や probe の home への `releaseSlot` | 同じ home のロックとカウント。ベイカー専用のリースは L1 とは直列化**しない** | 特別扱いなし：seed と probe は普通のワークスペース。救出されればベイクは失敗し、ベイカー自身の期限がすでに扱う |
| ハイバネーション（リーパーからの `hibernate`） | 最初の手順として `releaseSlot` | 同じ | **飛ばして**再試行。L1 のあとは home が切り離されているのでハイバネーションは進む |
| `Destroy`、`EraseHome`（メンバーか管理者の操作） | `Stop` のあと `releaseSlot` | 同じ。`Stop` がカウントを進める | その `Stop` が L1 を追い越す。umount は、今と同じく、応答できない箱を待つ。L1 は先に CP の保留中コマンドを取り消し、umount の寿命のあいだロックが握られないようにする |
| `sweepVolume` の drift と terminate の段 | `releaseSlot`、続いて `terminateSlot` | 同じ | 暗い刻印のあるスロットは**飛ばす**（暗いスキャンはパスの最初に走る） |
| `sweepFreeSlots` | home のないスロットを停止・終了 | 不要 | 空きの暗いスロットは L1 の対象ではない。プール画面が印を付ける |
| #2474、運用者の強制停止 | 占有者の `Stop`、取り消し、`StopInstances` | 同じカウントの手順（決定 4） | 許す。運用者の判断である |

**まだ home を持たないスロットを選ぶ経路**（したがって暗い使用中スロットではあり得ない）：`placeHome` の空きスロット attach
（`af-role=slot` と `slotExcluded` で絞った一覧。attach の前に 1 回、attach と claim のあとに 1 回の読み直し）、`growPool` → claim
（新品のスロット。読み直しなし）、`adoptEarlier`（前の試行が起動したスロット。claim を書く前に死んだものや claim が切れたものも
含む。claim のあとに 1 回の読み直し）。claim TTL（`claimTTL`、300 秒）は行為者ではない：期限切れの claim は `claimLive` が無視し、
それが、追い越された Start が最長 1 TTL だけ無害に claim を残せる理由である。

**不変条件を 1 文で：** *home の付いたスロットに対するすべての行為者は、その home のマウントロックと Start カウントを通って
届き、破壊的な呼び出しの前ごとにカウントを読み直す。自動の解放者はすべて、暗い刻印のあるスロットか救出マーカーのあるスロットを
飛ばす。home のないスロットは L1 や L2 の対象にならない。*

だから、この設計は home が付いていて生きている claim のないスロットにだけ動き（決定 1）、空きスロット・新品スロットの経路に
フェンスが要らない。#2474 の最初の版はタグで隔離してから保持者を読んだ。これは**空きかもしれない**スロットには正しい形で、
4 巡（所見は、そのレビューにならって R2〜R9 とラベルする）がその形を完成させるべき場所をすべて示した：

- **R3**（占有者を止めたあとにタグを書いた）には 2 つの半分がある。ほかのメンバーがそのスロットを選ぶことは、使用中のスロット
  ではあり得ない（表）。**占有者自身のワークスペースの新しい Start** は起こり得て、決定 4 の所有権の手順がまさにそのため
  にある。
- **R3b**（タグの前に候補を一覧し、タグのあとに attach した配置）と **R7**（claim のあとに読み直しのない新品スロット）は空き
  スロット・新品スロットの経路：使用中スロットには到達できず、`darkBootGrace` より若いスロットは暗くない。
- **R8**（home の claim をボリューム ID だけで消すクリーンアップが、*新しい* Start の claim まで消した）：スイーパーによる
  claim の削除はすべて決定 4 の所有権トークンで守られ、トークンはロックの下で読み、判断時の値を使い回さない。
- **R9**（隔離された置換先のスロットを未使用のものとして片付け、**終了**して証拠を壊した）と **R2**（置換予約も持つ隔離
  スロットが、古い箱を終了する `replaceReservedSlot` を通った）：下の規則 1 と 4。

これを実装するコードに対して次の 4 つの規則が出てくる。どれも安く試せる：

1. `slotTypeMatches` は、予約やテンプレートを読む**前に**、隔離スロットを単なる不一致として扱う。隔離された箱に付いたままの
   home（切り離しに失敗した L2）は、CP がもう命令を許されていない箱（`SendCommand` は `af-role=slot` にだけ付与）を
   起こすのではなく、解放して置き直される。`releaseSlot` は、まだ `stopping` の箱が止まりきるのを待ってから切り離す。
2. 表の自動の解放者はすべて、`af-dark-since` が刻まれたスロットか救出マーカーのあるスロットを飛ばす。
3. 所有権は決定 4 に従い、チェックと破壊的な呼び出しは 1 つのリースを共有する。取れないロック、読めないカウント、失効した
   リースは、その手順を**中止**する：ロックが取れないときに手順を無保護で走らせる `ifOwned` のフォールバックは使わない。
4. `terminateSlot` は意図を受け取る。**自動の**呼び出し元（スイーパーの terminate の段、`replaceReservedSlot`、
   `retireUnusedReplacement`、`makeRoom`）は、ロールが `quarantined` の箱を拒否する。認可され監査される運用者の
   `TerminateQuarantinedSlot`（決定 30）だけが明示の意図を渡すので、証拠を消せる唯一の操作は今も動く。

*却下した案。* **すべての配置経路に claim 後の隔離チェックを足してフェンスする**（#2474 が試したこと）：正しいが、1 つの
関心を 7 つの呼び出し箇所に散らし、4 巡のレビューがそのたびに 1 つずつ漏れを見つけた。使用中スロットの規則があれば、それらの
箇所には到達できず、到達できないチェックは、規則が変わった日に間違うデッドコードになる。**置換予約のタグをフェンスに流用する**：
両側のチェックはすでにあるが、行き着く先が `terminateSlot` で、L2 が残そうとする証拠を壊す。**隔離された箱への
`terminateSlot` をどこでも拒否する**：運用者の終了ボタンが壊れる。

### 4. だれが何を持つか、所有権トークン、再起動を越えて残るもの

- **Start** は生きている claim を持つ間そのスロットを持つ。判断は自分の `slotLostAfter`、動作は `abandonLostSlot`。変更なし。
- **スイーパー**は home があって生きている claim のないスロットを持つ。ワークスペースから見れば第三者である。
- **管理者の操作**（#2474）は、同じコードを人が使うもの：同じ所有権を取り、同じゲート（決定 2 の手順 3 と 4）で止まる。
  タスク ENI が付いている間は先に登録解除する、または拒否するようにそれを移すのは #2450 の実装の一部で、同じ ENI ゲートであり、
  検証もそこに属する。今の #2474 のゲートは「ECS エージェントが接続かつ SSM が Online」だけで、そのガイドも 0045 の追記も ENI の
  リスクに触れていない。ゲートを `slotDark`（起動猶予、継続時間、Agent プローブ）に切り替えるのは、本書が提案する挙動の変更で、
  すでにあるものではない。

**所有権トークン。** 判断のパスは Start カウント `g_d`、home のボリューム ID、起動世代を記録する。L1 を始めるとき、**home の
claim ロックとリースの下で、1 手順で**：カウント `g` を読み、`g == g_d` を要求し、そうなら `g_r`（Stop が行う増分）に上げて、
`g_r` を持つ救出マーカーを書く。そうでなければ、判断以降に何かが動いた（メンバーの Stop、新しい Start、Destroy）ので、
スイーパーは退き、次のパスがもう一度判断する。以降の破壊的な呼び出しの前ごとに、ロックとリースの下で、カウントがちょうど
`g_r` であること、マーカーがあって同じ home と起動世代を指すことを要求する。ほかの値なら、ほかのだれかが home を持って
いるので、救出は止まり、マーカーを落とし、残りには触れない。Stop を呼んでからカウントを確かめるのは両方向に間違う：新しい
Start（`g_d + 1`）が先に着地していれば自分の Stop の増分がそれを打ち切り、自分の増分のあとに `g_d` を使い回せば自分の Stop を
追い越しと読む。だから `g_d` の確認と増分は 1 つのロックされた手順で、トークンはそれが作った `g_r` である。

**救出マーカー**はインスタンスタグ `af-rescue = <home のボリューム ID>/<起動世代>/<段階>/<g_r>` で、**最初の副作用の前に**書く。
段階は `begun`、`deregistered`、`stopped`。再起動を越えて残るのはこれで、検出の述語は残れない。`stopping` や `stopped` の箱や、
登録解除のあとに SSM が戻った箱は、定義上もう「暗い」ではないからだ。検出とは別の**再開スキャン**が、状態（`running`、
`stopping`、`stopped`）を問わずマーカーを持つすべてのインスタンスを列挙し、次の条件がすべて成り立つときだけ次の段階を続ける：
同じボリュームがまだこの箱に付いている。`stopped` より前の段階では起動世代が変わっていない。カウントがまだ `g_r`。ボリュームが
なくなったか別の home、箱が起動し直された、カウントが動いた、のどれかならマーカーを落とし、古い救出を新しい状況に適用
**しない**。始まった救出は、エージェントが戻っても取り消されず、人や Start に追い越されるだけ。home のリース
（`homeLeaseTTL`、90 秒）は死んだ CP では失効するので、再開するレプリカが取れる。

- **2 つのレプリカ**はどちらも検出し、どちらも同じ値を刻む。所有権はロックされた手順で取るので、2 つ目はカウントが動いて
  いるのを見て退く。どの手順も冪等（`StopInstances`、未登録インスタンスの登録解除、切り離し済みボリュームの切り離し）。
- **監査**はコールバック（アダプターにデータベースがないため）：`Config.OnSlotAutoReplace` と同じ形で、actor は `system`、
  アクションは `pool.slot_dark_detected`（1 エピソードにつき 1 回）、`pool.slot_dark_rescued`、`pool.slot_dark_blocked`、
  `pool.slot_dark_quarantined`。

### 5. 見える場所と展開

- **プール画面**：スロットの `dark_since` と、いまの段（観察中 / 救出中 / ブロック / 救出済み / 隔離）を、#2474 の
  `stopping_task` の隣に。`registered` はそのまま。
- **メンバー**：救出されたワークスペースは `stopped` に見える。救出の後ろに回った Start は、何もない `starting` ではなく
  #2447 のブロック済みフェーズの文を読む。新しいメンバー画面は作らない。
- **運用者**：上の監査アクション、段ごとに 1 行のログ、ガイドのプールの節。
- **展開**：しきい値は推測なので、`AF_ECS_EC2_DARK_SLOT_ACTION` は `off | detect | rescue | quarantine`、最初のリリースの既定は
  **`detect`**（刻印、プール画面、監査 `detected`。ほかの AWS への書き込みはなし）。`rescue` は、検出のみの期間に偽陽性が
  出ないと確かめてから、デプロイごとに有効にする。強制切り離しの例外を含む L2 は `quarantine` の裏。既定を変えるのは、
  黙ってではなくリリースノートで。
- **IAM**：新しいインスタンスタグのキー（`af-dark-since`、`af-wedge-at`、`af-rescue`）を、既存の `af-slot-idle-since` と並べて
  CP ロールのタグキー許可リスト（`20-platform`）に加える。`ssm:DescribeInstanceInformation`（#2474 がすでに足している）。
  `ecs:DeregisterContainerInstance` はすでに付与されている。`ec2:StopInstances` と `DetachVolume` の呼び出し箇所はすべて
  `deploy/local/cfn-cp-ec2-scope-test.py` に載せる。

## 未解決の問い（どれも実機の実行が要る）

1. **#2474 の経路で、タスク ENI が付いたまま止めること。** 再起動した箱は、NAT のあるデプロイとないデプロイで egress を取り戻すか。
   取り戻さなければ、手動の操作は ENI が付いている間は拒否する、または先に登録解除しなければならない。この確認と #2474 の
   操作の変更は #2450 の実装が持つ（決定 4）。別の Issue は起こさない。
2. **無害な暗い時間。** 健全な箱でも ECS エージェントや SSM エージェントはどれだけ沈黙し得るか（エージェントの自己更新、
   docker の再起動、インスタンスの再起動、短い停滞）。`darkAfter` の 10 分は、検出のみの期間が答えるまでは推測。
3. **SSM の鮮度。** `LastPingDateTime` はどのくらいの頻度で更新され、`PingStatus` はいつ `ConnectionLost` になるか。決定 1 の
   早い起動の規則はこれ以上には良くならない。
4. **登録解除がタスクに何をするか。** 2026-08 の事件で観察したのは、強制登録解除のあとに ENI が消えたこと。`STOPPING` で
   止まったタスクが解放されるのか、プロセスが孤児として動き続けるのか（AWS が登録解除について文書化しているのはこちら）は、
   ここでは確立していない。#2447 が観察したのは、箱を起動すると消えたこと。設計はどちらにも頼らない。
5. **強制切り離しや Force 停止は home を壊すか。** スラッシング中の箱で、それぞれのあとの ext4 / XFS のジャーナルリプレイを
   測る。これが `quarantine` モードのゲートになる。
6. **スラッシング中の箱で、ワークスペース Agent のプローブは安く、正直か。CP は Agent にどこから届くか。** 決定 1 は動いている
   サービスについてそれを要する。遅くタイムアウトするなら、スイープの 1 パスに予算が要る。
7. **`MemoryMin` とホスト予約（#2452、メモリ逼迫への対応）で基準の発生率は変わるか。** 暗いエピソードが稀になれば、L2 の再発の
   規則は発火せず、`darkRepeatWindow` は捨てられる。
