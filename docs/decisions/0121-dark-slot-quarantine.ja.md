## 背景

`ecs-ec2` のスロットは、EC2 が `running` のまま、ステータスチェックもすべて通るのに、応答しなくなることがある。
本番、2026-10-21：スロットがメモリ逼迫で約 20 分スラッシングした（EBS の読み出しが 5 分あたり約 100 から約 19 万、
CPU 35〜95 %）。ECS エージェントは切断し、SSM エージェントの最後の ping はメンバーの Stop の 1 分前で、メンバーは、
運用者が保留中の umount を取り消してインスタンスを手で止めるまで、起動し直せなかった。同じ形の先の事件
（docs/log/64 §64.40）が `abandonLostSlot` のある理由である。

暗いスロットに対してツリーがすでにしていること、そして止まるところ：

| 場所 | していること | 欠けているもの |
|---|---|---|
| `waitSlotRegistered`（Start） | EC2 `running` のまま ECS に登録されない状態が `slotLostAfter`（300 秒）続くと `errSlotLost` | *このスロットを待っている* Start だけが見る。メンバーが不在の間は誰も見ない |
| `abandonLostSlot` | `quarantined` タグ、コンテナインスタンスの強制登録解除、タスク ENI が消えるのを待つ、Force 付き `StopInstances`、home の切り離し。すべて Start 自身の所有権チェック（`ifOwned`、#2462）の下 | その Start からしか届かない |
| `quarantineSlot` | マウント失敗に対する同じ処理 | マウント失敗のみ |
| `sweepVolume` | `if live workspace: leave it alone`（`DesiredCount`・`RunningCount`・`PendingCount` のどれかが 0 超） | 暗いスロットで名目上動いているワークスペースが、まさにこれに飛ばされる |
| `sweepVolume` の休眠側 | `slotSleepAfter` 後にスロットを止める。ただしタスク ENI を持つものは止めない（決定 3-3） | 暗いスロットはタスク ENI を持ち続けるので、「leaving it running for now」と永遠にログに出る |
| `sweepGhostInstances` | EC2 インスタンスが**消えた**コンテナインスタンスを登録解除（`ghostAfter`、1 時間） | 動いている箱は対象外 |
| `stuckStoppingReason`（#2447、`main` にある） | 切断したスロットで `STOPPING` のまま止まったタスクを、ブロックされた起動フェーズとして示す | 検出のみ |
| #2474（未マージ） | 運用者が 1 台止める：CP の SSM コマンドを取り消し、載っている Start を終わらせ、`StopInstances`。スロットは使われ続け、次の Start が起こす | 手動 |

欠けているのは*だれも Start していない間の目*と、見たときに何をするか、である。それが見かけより難しい理由が 4 つあり、
最初の 3 つはどれも痛い目を見て分かったことだ：

1. **クラスターに応答しない箱には何も頼めない。** SSM も暗いので、コマンドを走らせる手順（umount）はどれも固まり、
   それを待つ Start はイングレスの 60 秒の中で終われない（#2446）。
2. **止めることは無料ではない。** 動いているタスクの ENI はまだ付いている。その間に止めると箱は multi-ENI で戻り、
   NAT のないデプロイでは egress を失って、エージェントは二度と再接続しない（決定 3-3、スイーパー自身の経路で再現）。
   だからスイーパーはそういう箱を止めず、暗いスロットが何時間もそこに居座る。`abandonLostSlot` はそれを回避する
   コード（先に登録解除して、ECS に ENI を手放させる）。
3. **スロットに手を出すものは、それを使う人たちと競合する。** #2474 は「スロットを隔離する」として始まり、その競合が
   どこにあるかを見つけるのに 4 巡のレビューを要した（決定 3 を参照）。「止める。ほかは何も変えない」に絞り、
   隔離はこちらへ移した。
4. **暗いという信号は偽りやすい。** エージェントの再起動、起動、wake、インスタンスの再起動は、どれもしばらく暗く見える。
   そのどれかに反応すれば、健全な箱を捨てることになる。

## 決定

### 1. 検出：述語は 1 つ、持続する起点、そして Start が持つスロットにスイーパーは触れない

スロットが**暗い**とは、ある 1 回のスイープで次のすべてが成り立つことをいう。起点から `darkAfter` が過ぎたあとにも
同じことが成り立つとき、**暗くなっていた**とする：

- EC2 が `running`（`pending` や `stopping` は起動中・停止処理中であって暗いのではない）。
- ECS のコンテナインスタンスが `ACTIVE` で `agentConnected=false`、または未登録。
- SSM が `PingStatus=Online` で一覧に載せていない（`ConnectionLost`、`Inactive`、または載っていない）。
- 起動または開始から少なくとも `darkBootGrace` が経っている（`LaunchTime`。開始のたびに動く。`waitSlotRegistered` の
  起動・wake の待ちは約 20〜35 秒と測っており、ここで繰り返さない）。
- ワークスペースのサービスが**動いている**（`DesiredCount > 0`）スロットでは、CP がワークスペース Agent にも届かない
  （`State()` がすでに使っているプローブ）。ECS エージェントが暗くてもコンテナはメンバーに応答しているかもしれず、
  それを止めるのは救出ではない。

計算する関数は 1 つ（`slotDark`）で、#2474 の健全性ゲートはその否定になる。手動の操作は、自動のものも健全と呼ぶスロットを
拒否する。定義が 2 つあれば食い違う。

**起点**とは `darkAfter` の時計が走り出す点で、データベースなしでも CP の再起動を越えて残らなければならない（ADR 0012）：

- SSM がその箱を一覧に載せているなら、SSM の `LastPingDateTime`（持続する、AWS 自身の値）。
- なければ、コンテナインスタンス上で `STOPPING` のまま止まったタスクの `StoppingAt`（#2447 の信号。切断したエージェントで
  `stuckStoppingGrace` を超えて止まったタスクは、ECS 側の条件もすぐに満たす証拠でもある）。
- それもなければ最初に見た時点で、インスタンスのタグ `af-dark-since` に刻む。あるパスが書き、あとのパスが動く。これは
  `af-slot-idle-since`（決定 22）の形で、2 つのレプリカが同じ結論に達する理由でもある。刻印を消せるのは、スロットが健全だと
  確かめたパスだけで、エージェントのばたつきで時計が毎回戻ることはない。

**しきい値。** `darkAfter` の既定は **10 分**。健全な箱が待つどの時間よりも長く（ホットなスロット：最初のポーリング、
wake：約 20 秒、新しい箱：約 35 秒。`placementBlockedGrace` の 120 秒は、CP 自身が作る待ちに対する*メッセージ*のもので、
箱についてのものではない）、すでに待っている Start を支配する `slotLostAfter`（300 秒）よりも長い。`ghostAfter`（1 時間）は
別のもの（EC2 インスタンスが**消えた**コンテナインスタンス）で、流用しない。既定値は、未解決の問いに答えが出るまでは推測で、
環境変数（`AF_ECS_EC2_DARK_AFTER_SEC`、0 = オフ）にする。

**対象。** **home が付いていて、生きている claim のない**スロットだけ。`sweepVolume` が歩くのと同じ母集団である。生きている
claim は Start が収束中であることを意味し、`slotLostAfter` による判断はその Start のもの。スイーパーは `sweepVolume` と同じに
飛ばす。空きの暗いスロットは救う相手がいないので、通常の空きスロットの規則に従い、加えてプール画面に印を付ける。

*却下した案。* CloudWatch 駆動の新しい検出器：CP が持たないもう 1 つの真実の源が要り、同じ競合の問いに答える必要も残る。
短いしきい値（`placementBlockedGrace` の 120 秒）：その定数はメッセージ向けの大きさで、それで動けば wake 中の箱を止める。
CP 側の検出回数カウンター：再起動で失われる。タグの起点は失われない。

### 2. 対処のはしご：まず救出、隔離は 2 度暗くなった箱だけ

メンバーに要るのは動く箱の上の home で、運用者に証拠が要るのは*箱*に非があるときだけだ。メモリのスラッシングはたいてい
*ワークロード*の非で、同じワークロードを新しい箱へ移せばそこでもスラッシングする。だから最初の発生で隔離すると、運用者が
終了するまで課金される root ボリューム（決定 30）と、上限のうちのスロット 1 つと、長い Start（新しい箱）を払うことになる。
得るのは、ログがすでに語っていることの証拠である。したがって：

- **L0. 観察。** 最初のパスが起点を刻み、プール画面は「N 分暗い」と出す。最初のリリースでは、これが挙動のすべて（決定 5）。
- **L1. 救出**（`darkAfter` 暗かったとき）：ワークスペースの home を箱から外し、箱は使い続ける。**順序は `abandonLostSlot` が
  すでに裏付けているもの**：Start を終わらせる（Stop として：`abortStarts`、desiredCount 0、claim を落とす）。
  コンテナインスタンスを強制登録解除する（ECS がタスクとその ENI を手放し、#2447 の **`STOPPING` で止まったタスクも消える**）。
  タスク ENI が消えるのを、上限つきで待つ。`StopInstances`（まず通常、終わらなければ Force。#2474 と同じく、その後に
  起動し直されたインスタンスには決して使わない）。home を切り離す（箱は止まっているので普通の切り離し）。ロールは `slot` の
  まま、`af-wedge-at` を刻む。メンバーの次の Start は home が置き場なしになっているのを見つけ、ほかと同じように置く
  （そのころこの箱は空きの停止中スロットで、再起動のあとなら、置かれる先がまさにこの箱ということもあり得る）。
- **L2. 隔離**：箱が前の `af-wedge-at` から `darkRepeatWindow`（既定 24 時間）以内に**もう一度**暗くなったとき、または
  L1 の救出が終わりきらなかったとき（ENI が消えない、停止が終わらない）は、使い続ける代わりに隔離する。隔離は既存の
  `abandonLostSlot` の末尾（理由つきの `af-role=quarantined`、停止のまま、回収しない。終了は決定 30 のボタンのまま）。
  1 回の再発は、問題が*箱*にあることの最も安い、正直な証拠である。

*却下した案。* **常に隔離**（#2474 の最初の設計）：上の議論と決定 3。**常に強制停止して同じ箱を起こす**（#2474 が運用者に
してくれること）：タスク ENI のない箱には安全だが、暗い実行中ワークスペースでは ENI が付いたままなので停止は multi-ENI の罠
（背景の 2）で、egress がなくて wake に失敗し得る。止まったタスクの報告もエージェント任せで、その wake が動くことが前提になる。
運用者の選択としては良く、自動の既定としては誤り。**インスタンスだけ止めて home は付けたまま**（決定 3-3 を慎重に読む案）：
メンバーは塞がれたまま。次の Start は、STOPPING のタスクが残る箱に home があるのを見つけ、それを待つ（#2447）。
**止めずに登録解除**：動いている箱が ECS から切り離され、借り手のないまま課金される。

### 3. home を移すとき：競合の在りかと不変条件

L1 も L2 も home が箱を離れて終わる。したがって、配置がスロットを選び得るすべての経路を数え上げなければならない。一覧
（すべて `runtime_ecs_ec2*.go`）と、各行への問い：*スイーパーが読んでから書くまでの間に、ほかのだれがこのスロットを選び得るか。*

| 経路 | 選ぶもの | 今のフェンス | 暗いスロットを争うか |
|---|---|---|---|
| `placeHome` 同じタイプ、home が付いている | home が付いているスロット（アフィニティ） | 入口で予約・古さを読む。home 自身の Start カウント | **はい。その home のワークスペースだけ** |
| `placeHome` 不一致 → 背景で解放（`releaseFrom`） | home が付いているスロット | `releaseSlotSince`、Start カウントでフェンス | 同じワークスペースだけ |
| `placeHome` 予約 / 古い → `replaceReservedSlot` | **新しい**スロット、そのあと古いものを終了 | claim 後（と移す前）の `slotNowReserved` | いいえ（新しいスロット）。古いものを終了する |
| `placeHome` 空きスロット → attach → claim | `freeSlots` の空きスロット | 一覧を `af-role=slot` と `slotExcluded` で絞る。attach 後と claim 後の `slotNowReserved` | いいえ。home のある暗いスロットは空きではない |
| `placeHome` 追い出し（`evictLongestIdle`） | 最もアイドルの長い**使用中**スロット。占有者自身のランタイムを通して解放 | attach 後の `slotNowReserved`。解放は占有者の Start カウントとマウントロックでフェンス | **はい。ほかのメンバーの Start が、休眠中の暗いスロットを犠牲に選び得る** |
| `placeHome` `growPool` → claim | **新品**のスロット | claim 後には何もない | いいえ（新品） |
| `adoptEarlier` | 前の試行が起動したスロット | `adoptableReplacement` の判定。claim 後の `slotNowReserved` | いいえ（同じワークスペースの claim を持つ） |
| `releaseAndReplace` / `errSlotLost` の置き直し | `abandonLostSlot` 後のスロット | 各境界での `startSuperseded` | 同じワークスペース |
| #2462 の `Stop`（`abortStarts`） | なし：Start カウントを進める | `homeLockClaim` | 同じワークスペース |
| claim TTL（`claimTTL`、300 秒） | なし：期限切れの claim は `claimLive` が無視する | | 追い越された Start が、無害に、最長 1 TTL だけ claim を残せる理由 |

**不変条件を 1 文で：** *home の付いたスロットに対するすべての行為者（自分のワークスペースの Start と Stop、ほかのメンバーによる
その追い出し、スイーパー）は、その home のロックと Start カウントを通ってスロットに届き、破壊的な呼び出しの前ごとに
カウントを読み直す（`underStart`、`ifOwned`）。home のないスロットは L1 や L2 の対象にならない。*

だから、この設計は home が付いていて生きている claim のないスロットにだけ動き（決定 1）、*ほかのメンバー*の空きスロット・
新品スロットの経路にフェンスが要らない。使用中のスロットに届くほかのメンバーの経路は追い出しだけで、それはすでに占有者の
ロックを通っている。加えて `af-dark-since` が刻まれたスロットは飛ばさなければならない。暗いスロットを解放すると、走れない
umount を走らせるからだ（#2446）。#2474 の最初の版はタグで隔離してから保持者を読んだ。これは**空きかもしれない**スロットには
正しい形で、4 巡（所見は、そのレビューにならって R2〜R9 とラベルする）がその形を完成させるべき場所をすべて示した。そのどれも、
使用中スロットの規則で到達できなくなる空きスロット・新品スロットの経路だ：

- **R3 / R3b**（占有者を止めたあとにタグを書いた。タグの前に候補を一覧し、タグのあとに attach した配置）：どちらも、運用者が
  手を出していたスロットを*別の* Start が選ぶ話。使用中スロットの選び手は、占有者自身のワークスペースと、追い出す Start で、
  どちらも占有者のロックとカウントで直列化される。占有者の Stop（`abortStarts`）がフェンスのすべて。
- **R7**（`growPool` の新品スロットは claim 後のチェックがなかった）：スイーパーは生きている claim のある新品スロットには
  動かず、`darkBootGrace` より若いスロットは暗くない。
- **R8**（home の claim をボリューム ID だけで消すクリーンアップが、*新しい* Start の claim まで消した）：スイーパーによる
  claim の削除はすべて `unclaimUnlessSuperseded` を通し、Start カウントはクリーンアップの入口ではなく、**スイーパーが判断した時点**
  で読む。
- **R9**（隔離された置換先のスロットを未使用のものとして片付け、**終了**して証拠を壊した）：ロールが `quarantined` のスロットに
  対して `retireUnusedReplacement` と `terminateSlot` に届いてはならない。`terminateSlot` 自身の中で確かめるので、呼び出し側が
  覚えている必要はない。
- **R2**（置換予約も持つ隔離スロットが `replaceReservedSlot` を通り、古い箱を終了した）：`slotTypeMatches` の順序は
  *隔離が先*、次に予約、次に古さ。

これを実装するコードに対して次の 3 つの規則が出てくる。どれも安く試せる：

1. `slotTypeMatches` は、予約やテンプレートを読む**前に**、隔離スロットを単なる不一致として扱う。隔離された箱に付いたままの
   home（切り離しに失敗した L2）は、CP がもう命令を許されていない箱（`SendCommand` は `af-role=slot` にだけ付与）を
   起こす（`wake`）のではなく、解放して置き直される。`releaseSlot` は、まだ `stopping` の箱が止まりきるのを待ってから切り離す。
2. 追い出しは `af-dark-since` が刻まれたスロットを飛ばす。
3. スイーパーの L1 と L2 は占有者の `Stop` の意味づけで始まり、`abandonLostSlot` が #2462 の下でそうするように、破壊的な呼び出し
   の**前ごとに** Start カウントを確かめ直す。判断のあとに始まった Start が勝ち、次のパスがもう一度見る。

*却下した案。* **すべての配置経路に claim 後の隔離チェックを足してフェンスする**（#2474 が試したこと）：正しいが、1 つの関心を
7 つの呼び出し箇所に散らし、4 巡のレビューがそのたびに 1 つずつ漏れを見つけた。使用中スロットの規則があれば、それらの箇所には
到達できず、到達できないチェックは、規則が変わった日に間違うデッドコードになる。**置換予約のタグをフェンスに流用する**：
両側のチェックはすでにあるが、行き着く先が `terminateSlot` で、L2 が残そうとする証拠を壊す。

### 4. だれが何を持つか：スイーパー、Start、管理者

- **Start** は生きている claim を持つ間そのスロットを持つ。判断は自分の `slotLostAfter`（300 秒）、動作は
  `abandonLostSlot`。変更なし。
- **スイーパー**は home があって生きている claim のないスロットを持つ。ワークスペースから見れば第三者なので、Stop と同じように
  動く：`homeLockClaim` の下で、判断した時点に読んだ Start カウントから。その後に Start が始まっていれば、スイーパーは退き、
  その Start の経路が引き継ぐ。
- **管理者の操作**（#2474）は、同じコードを人が使うもの：同じ述語を*ゲート*として使い（健全なスロットは、上書きしない限り
  拒否）、手動なので、スイーパーがまだ判断していないスロットにも使える。home には手を付けない停止のまま。ADR 0045 の追記と
  ガイドは、タスク ENI が付いているとき multi-ENI の罠に当たり得ると述べる。本書はそれを変えず、未解決の問い 1 が、そのとき
  拒否すべきかを問う。
- **2 つのレプリカ**はどちらも検出し、どちらも同じ起点を刻む。動作はワークスペースの `cp_lease` と共有 Start カウントの下で
  走るので、2 つ目のレプリカはカウントが動いているか、リースが握られているのを見る。どの手順も冪等（`StopInstances`、
  未登録インスタンスの登録解除、切り離し済みボリュームの切り離し）。
- **途中で再起動した CP** は AWS から再開する：起点と `af-wedge-at` はタグで、home のリースは期限が来て（`homeLeaseTTL`、90 秒）、
  終わらなかった手順は導き直せる（登録解除済みのコンテナインスタンスのまま動いている箱は再び暗いスロットで、次のパスが
  L1 を続ける）。メモリには何も持たない（ADR 0012）。
- **監査**はコールバック（アダプターにデータベースがないため）：`Config.OnSlotAutoReplace` と同じ形で、actor は `system`、
  アクションは `pool.slot_dark_detected`（1 エピソードにつき 1 回）、`pool.slot_dark_rescued`、`pool.slot_dark_quarantined`。

### 5. 見える場所と展開

- **プール画面**：スロットの `dark_since` と、いまの段（観察中 / 救出済み / 隔離）を、#2474 の `stopping_task` の隣に。
  `registered` フラグはそのまま。
- **メンバー**：救出されたワークスペースは `stopped` に見える。救出の後ろに回った Start は、何もない `starting` ではなく
  既存のブロック済みフェーズの文（#2447）を読む。新しいメンバー画面は作らない。
- **運用者**：上の監査アクション、段ごとに 1 行のログ、ガイドのプールの節。
- **展開**：しきい値は推測なので、`AF_ECS_EC2_DARK_SLOT_ACTION` は `off | detect | rescue | quarantine`、最初のリリースの既定は
  **`detect`**（起点、プール画面、監査 `detected`。刻印以外の AWS への書き込みはなし）。`rescue` は、検出のみの期間に偽陽性が
  出ないと確かめてから、デプロイごとに有効にする。L2 は `quarantine` の裏。既定を変えるのは、黙ってではなくリリースノートで。
- **IAM**：新しいインスタンスタグのキー（`af-dark-since`、`af-wedge-at`）を、既存の `af-slot-idle-since` と並べて CP ロールの
  タグキー許可リスト（`20-platform`）に加える。`ssm:DescribeInstanceInformation`（#2474 がすでに足している）。
  `ec2:StopInstances` と `DetachVolume` の呼び出し箇所はすべて `deploy/local/cfn-cp-ec2-scope-test.py` に載せる。

## 未解決の問い（どれも実機の実行が要る）

1. **#2474 がタスク ENI が付いたまま止めること。** 手動の強制停止は先に登録解除しないので、暗い実行中ワークスペースでは
   multi-ENI の罠になる。再起動した箱は、NAT のあるデプロイとないデプロイで egress を取り戻すか。取り戻さなければ、手動の
   操作はタスク ENI が付いている間は拒否する（または先に登録解除する）べきで、それは本書ではなく #2474 の変更になる。
2. **無害な暗い時間。** 健全な箱でも ECS エージェントや SSM エージェントはどれだけ沈黙し得るか（エージェントの自己更新、
   docker の再起動、インスタンスの再起動、短い停滞）。`darkAfter` の 10 分は、検出のみの期間が答えるまでは推測。
3. **SSM の鮮度。** `LastPingDateTime` はどのくらいの頻度で更新され、`PingStatus` はいつ `ConnectionLost` になるか。起点はこれ
   以上には良くならず、公開されている頻度は測定ではない。
4. **登録解除でここでも止まったタスクが消えるか。** #2447 が観察したのは*箱を起動する*ことで消えたこと。`abandonLostSlot` の
   強制登録解除で ECS がタスクを諦めると考えているが、暗い箱で `STOPPING` のタスクを使って確かめる。
5. **Force は home を壊すか。** `abandonLostSlot` はそのために切り離しを停止のあとに置いている。スラッシング中の箱を Force で
   止めたあとの ext4 / XFS のジャーナルリプレイを測る。
6. **スラッシング中の箱で、ワークスペース Agent のプローブは安く、正直か。** 決定 1 は名目上動いているサービスについてそれに頼る。
   遅くタイムアウトするなら、スイープの 1 パスに予算が要る。
7. **`MemoryMin` とホスト予約（#2452、メモリ逼迫への対応）で基準の発生率は変わるか。** 暗いエピソードが稀になれば、L2 の再発の
   規則は発火せず、`darkRepeatWindow` は捨てられる。
