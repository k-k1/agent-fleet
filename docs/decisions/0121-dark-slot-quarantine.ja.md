## 背景

`ecs-ec2` のスロットは、EC2 が `running` のまま、ステータスチェックもすべて通るのに、応答しなくなることがある。
本番、2026-10-21：スロットがメモリ逼迫で約 20 分スラッシングした（EBS の読み出しが 5 分あたり約 100 から約 19 万、
CPU 35〜95 %）。ECS エージェントは切断し、SSM エージェントの最後の ping はメンバーの Stop の 1 分前で、メンバーは、
運用者が保留中の umount を取り消してインスタンスを手で止めるまで、起動し直せなかった。同じ形の先の事件
（docs/log/64 §64.40）が `abandonLostSlot` のある理由である。

暗いスロットに対してツリーがすでにしていること、そして止まるところ：

| 場所 | していること | 欠けているもの |
|---|---|---|
| `waitSlotRegistered`（Start） | `slotLostAfter`（300 秒。100 回のポーリング）のあいだ 3 秒ごとに `registeredSlots` を見て、最後に EC2 が `running` かを 1 回確かめ、`errSlotLost` を返す | *このスロットを待っている* Start だけが見る。メンバーが不在の間は誰も見ない。300 秒はポーリング回数で、連続して暗かったことの計測ではない |
| `abandonLostSlot` | `quarantined` タグ、コンテナインスタンスの強制登録解除、タスク ENI が消えるのを待つ、Force 付き `StopInstances`、home の切り離し（フォールバックは強制切り離し）。どの手順も Start 自身の所有権チェック（`ifOwned`、#2462）の下 | その Start からしか届かない |
| `quarantineSlot` | マウント失敗に対して：`quarantined` タグ、マウントロック、SSM で上限つきの umount、切り離し、claim を落とす、通常の `StopInstances`。登録解除は**しない**。SSM が要る | マウント失敗のみ。暗い箱には使えない |
| `sweepVolume` | `if live workspace: leave it alone`（`DesiredCount`・`RunningCount`・`PendingCount` のどれかが 0 超） | 暗いスロットで名目上動いているワークスペースが、まさにこれに飛ばされる |
| `sweepVolume` の休眠側 | `slotSleepAfter` 後にスロットを止める。ただしタスク ENI を持つものは止めない（決定 3-3） | 暗いスロットはタスク ENI を持ち続けるので、「leaving it running for now」と永遠にログに出る |
| `sweepGhostInstances` | EC2 インスタンスが**消えた**コンテナインスタンスを登録解除（`ghostAfter`、1 時間） | 動いている箱は対象外 |
| `stuckStoppingReason`（#2447、`main` にある） | 切断したスロットで `STOPPING` のまま止まったタスクを、ブロックされた起動フェーズとして示す | 検出のみ |
| #2474（未マージ） | 運用者が 1 台止める：CP の SSM コマンドを取り消し、載っている Start を終わらせ、`StopInstances`。スロットは使われ続け、次の Start が起こす。ゲートは、ECS エージェントが接続**かつ** SSM が Online のスロットを拒否する | 手動。ENI の確認も登録解除もない |

欠けているのは*だれも Start していない間の目*と、見たときに何をするか、である。それが見かけより難しい理由が 4 つあり、
最初の 3 つはどれも痛い目を見て分かったことだ：

1. **クラスターに応答しない箱には何も頼めない。** SSM も暗いので、コマンドを走らせる手順（umount）はどれも固まり、
   それを待つ Start はイングレスの 60 秒の中で終われない（#2446）。
2. **止めることは無料ではない。** 動いているタスクの ENI はまだ付いている。その間に止めると箱は multi-ENI で戻り、
   NAT のないデプロイでは egress を失って、エージェントは二度と再接続しない（決定 3-3、スイーパー自身の経路で再現）。
   だからスイーパーはそういう箱を止めず、暗いスロットが何時間もそこに居座る。`abandonLostSlot` はそれを回避する
   コード（先に登録解除して、ECS に ENI を手放させる）だが、2026-08 の事件から書かれたもので、そのとき手で観察できたのは
   ENI の半分だけ。登録解除がそれ以外に何をするかは確立して**いない**（未解決の問いを参照）。
3. **スロットに手を出すものは、それを使う人たちと競合する。** #2474 は「スロットを隔離する」として始まり、その競合が
   どこにあるかを見つけるのに 4 巡のレビューを要した（決定 3 を参照）。「止める。ほかは何も変えない」に絞り、
   隔離はこちらへ移した。
4. **暗いという信号は偽りやすい。** エージェントの再起動、起動、wake、インスタンスの再起動は、どれもしばらく暗く見え、
   暗さより古い起点は何も証明しない。そのどれかに反応すれば、健全な箱を捨てることになる。

## 決定

### 1. 検出：述語は 1 つ、連続した暗さを証明する起点、そして Start が持つスロットにスイーパーは触れない

スロットが、あるスイープで**暗い**とは、次のすべてが成り立つことをいう：

- EC2 が `running`（`pending` や `stopping` は起動中・停止処理中であって暗いのではない）。
- ECS のコンテナインスタンスが `ACTIVE` で `agentConnected=false`、または未登録。
- SSM が `Online` 以外の `PingStatus`（`ConnectionLost`、`Inactive`）で載せているか、載せていない。
- 起動または開始から少なくとも `darkBootGrace` が経っている（`LaunchTime`。開始のたびに動く。既定 300 秒。測った
  起動・wake の待ち、約 35 秒と約 20 秒より上）。
- ワークスペースのサービスが**動いている**（`DesiredCount > 0`）スロットでは、ワークスペース Agent へのプローブも失敗する。
  ECS エージェントが暗くてもコンテナはメンバーに応答しているかもしれず、それを止めるのは救出ではない。`State()` は今は
  Agent をプローブせず（ボリューム・claim・ECS サービスから状態を導く）、このプローブは**新しい部品**になる。それができるまで、
  サービスが動いているスロットは L0（観察）にとどまり、自動では救出しない。

**失敗した読み取りは答えではない。** ECS・EC2・SSM の呼び出しがエラー・スロットル・タイムアウトになれば、そのスロットについて
そのパスは*不明*になる：刻印も、消去も、動作もしない。「SSM が載せていない」は、呼び出しが成功したときだけ答えになる。

**起点。** 起動世代の中で述語全体が成り立つと最初に確かめたパスが、インスタンスタグ `af-dark-since` を `<時刻>/<LaunchTime>` で
書く。フォールバックとしてだけでなく*常に*書く。ほかのコードがこのタグでスロットを除外するからだ（決定 3）。以降のパスは、述語が
まだ成り立ち、`now − 刻印 ≥ darkAfter` のとき動く。スロットが健全だと確かめたパスは刻印を消し、`LaunchTime` が今のものと違う
刻印は古いものとして書き直すので、開始のたびに時計はやり直しになる。

**外部のタイムスタンプは待ちを縮めない。** SSM の `LastPingDateTime` もタスクの `StoppingAt`（#2447）も、述語全体がどれだけ続いて
いたかの証拠では*ない*：`StoppingAt` は停止を求めた時刻でエージェントが切断した時刻ではなく、`LastPing` は ECS エージェントが
1 分前まで正常だった箱でも何日も古いことがある。時計の唯一の起点は、すべての条件を一度に観測した最初のスイープで、したがって箱での
最初のエピソードは、その観測から `darkAfter` 後に動く（箱が暗くなってから最大 `sweepEvery` 遅れる）。2 つのタイムスタンプは
説明としてプール画面に出すだけで、ほかには使わない。代償は最大 1 スイープ間隔の余分な遅れで、得るのは、SSM がすでにオフライン
だった箱の短い ECS 切断が 10 分と読まれないことである。

**しきい値。** `darkAfter` の既定は **10 分**、環境変数（`AF_ECS_EC2_DARK_AFTER_SEC`、0 = オフ）。`darkBootGrace` 以上、かつ
`slotLostAfter + sweepEvery` 以上でなければならず、逆転して設定したデプロイは起動時にログを出して引き上げる。健全な箱が待つどの
時間（ホットなスロット：最初のポーリング、wake：約 20 秒、新しい箱：約 35 秒）よりも長く、すでに待っている Start を支配する
`slotLostAfter`（300 秒）よりも長い。`placementBlockedGrace`（120 秒）は CP 自身が作る待ちに対する*メッセージ*のもので、
`ghostAfter`（1 時間）は EC2 インスタンスが**消えた**コンテナインスタンスのもの。どちらも流用しない。既定値は、未解決の問いに
答えが出るまでは推測である。

**対象。** **home が付いていて、生きている claim のない**スロットだけ。`sweepVolume` が歩くのと同じ母集団である。生きている
claim は Start が収束中であることを意味し、`slotLostAfter` による判断はその Start のもの。スイーパーは `sweepVolume` と同じに
飛ばす。空きの暗いスロットは救う相手がいないので、通常の空きスロットの規則に従い、プール画面が印を付ける。

*却下した案。* CloudWatch 駆動の検出器：CP が持たないもう 1 つの真実の源が要り、同じ競合の問いに答える必要も残る。短い
しきい値：wake 中の箱に動いてしまう。CP 側の検出回数カウンター：再起動で失われる。SSM か ECS のタイムスタンプだけを起点にする
こと：上を参照。

### 2. 対処のはしご：まず救出、隔離は 2 度暗くなった箱か救出できない箱だけ

メンバーに要るのは動く箱の上の home で、運用者に証拠が要るのは*箱*に非があるときだけだ。メモリのスラッシングはたいてい
*ワークロード*の非で、同じワークロードを新しい箱へ移せばそこでもスラッシングする。だから最初の発生で隔離すると、運用者が
終了するまで課金される root ボリューム（決定 30）と、上限のうちのスロット 1 つと、長い Start を払うことになる。得るのは、
ログがすでに語っていることの証拠である。したがって：

- **L0. 観察。** 刻印を書き、プール画面は「N 分暗い」と出す。最初のリリースでは、これが挙動のすべて（決定 5）。
- **L1. 救出**（`darkAfter` 暗かったとき）：home を箱から外し、箱は使い続ける。各手順は次の手順のゲートであって、押し通す
  連なりではない：
  1. **準備**：claim ロックだけの下で（決定 4、ロックの順序）、所有権を取り、救出マーカーを書き、Start を Stop と同じように
     終わらせ（`abortStarts`、desiredCount 0、claim を落とす）、claim ロックを持ちトークンが有効なまま、**箱の上の CP 自身の
     保留中 SSM コマンドを列挙して、そのコマンド ID の集合を確定する**。そのあと claim ロックを手放す。この手順はマウントロックを
     待たない。
  2. その集合のコマンドだけを、**home のロックを持たずに**取り消す。それらは生きている間は home のマウントロックを握り続ける
     ので、救出がそのロックを求める前に、取り消しが届けなければならない。集合はあとから列挙し直さない：メンバーの後の Start は
     トークンを取ったあとにコマンドを送るので、それらはこの救出が取り消すものではない。再開した救出が列挙し直してよいのは、
     claim ロックを取り直してカウントがまだ `g_r` だと確かめたときだけで、その列挙が返したものだけを取り消す。
  3. マウントロックを上限つきの待ちで取る。上限内に取れなければ、そのパスはここで止める（マーカーは残り、次のパスが
     再試行する）。ここからの破壊的な呼び出しはすべてマウントロックの下で走り、その内側の claim ロックの下でトークンを
     確かめ直す。
  4. `deregistering` を書いてから、コンテナインスタンスを強制登録解除し、上限内に**タスク ENI が物理的に消えたことを確かめる**（`DescribeInstances`）。
     登録解除がほかに何かをするとは仮定しない。AWS はタスクのプロセスを止めないと文書化している。
  5. ENI が消えているときだけ `stopping` を書いて `StopInstances`（まず通常、終わらなければ Force。#2474 と同じく、その後に起動し直された
     インスタンスには決して使わない）。そして **`stopped` を確かめる**。
  6. 箱が止まっているときだけ、home の普通の切り離し。その前に `detaching` のマーカー段階を書く（決定 4）。ロールは `slot` の
     まま。決定 4 のファイナライザがそのあとエピソードを記録する。

  上限内に ENI が消えない、または箱が止まらなければ、救出は**ブロック**される：それ以上は何もせず、箱はそのまま、マーカーは
  段階を保ち、プール画面と監査がそう示す。ブロックされた救出は毎パス再試行され、次の段が有効でなければ運用者が解決する
  （手動の強制停止か終了ボタン）。
- **L2. 隔離**：箱が前の `af-wedge-at` から `darkRepeatWindow`（既定 24 時間）以内に**もう一度**暗くなったとき、**または**
  救出が `rescueBlockedAfter`（既定 30 分）ブロックされたままのとき、使い続ける代わりに隔離する。隔離は箱に理由つきの
  `af-role=quarantined` を付け、残し、回収しない（決定 30）。ブロックされた救出では、`abandonLostSlot` がすでに認めている
  唯一の例外、止まらない箱からの home の**強制切り離し**も許す。これは安全な操作ではなく、方針として選ぶ最後の手段である：
  使用中のボリュームを切り離すとファイルシステムが壊れ修復が要り得ることを、AWS は文書化している。損傷の範囲は
  ここでは限定も測定もされておらず、回復はファイルシステムのチェックと、それで足りなければ home の直近のバックアップか
  ハイバネーションのスナップショット（決定 17 がコピーを持つ）になる。対するのはメンバーが無期限に塞がれること
  で、その選択は運用者のもので、デプロイごとに `quarantine` モードを有効にして一度だけ行い、未解決の問い 5 の測定と回復手順が
  できたあとに限る。

`STOPPING` のまま残るタスクは、救出で消えると**仮定しない**。消えるかどうかは未解決の問い 4。残れば、メンバーの次の Start は
#2447 のブロック済みフェーズの文を読む。#2447 の対処（古いインスタンスを一度起動してエージェントに報告させる）は、登録解除**して
いない**箱で測ったもので、登録解除したコンテナインスタンスで効くとは仮定しない。これは未解決の問い 4 の受け入れ条件である。

*却下した案。* **常に隔離**（#2474 の最初の設計）：上の議論と決定 3。**常に強制停止して同じ箱を起こす**（#2474 が運用者に
してくれること）：タスク ENI のない箱には安全だが、暗い実行中ワークスペースでは ENI が付いたままなので停止は multi-ENI の罠で、
egress がなくて wake に失敗し得る。運用者の選択としては良く、自動の既定としては誤り。**インスタンスだけ止めて home は付けた
まま**：メンバーは塞がれたまま。次の Start は、STOPPING のタスクが残る箱に home があるのを見つけ、それを待つ（#2447）。
**止めずに登録解除**：動いている箱が ECS から切り離され、借り手のないまま課金される。

### 3. home を移すとき：使用中スロットに届くすべての行為者と不変条件

L1 も L2 も home が箱を離れて終わる。したがって、home の載ったスロットに何かが触れ得るすべての経路を数え上げなければならない。
動詞は `releaseSlot` と `terminateSlot` の 2 つで、以下は `runtime_ecs_ec2*.go` のすべての呼び出し元と、その背後の行為者、
L1 と共有するもの。

**使用中スロットに届く行為者**

| 行為者 | スロットへの動詞 | L1 との直列化 | 暗いスロットへの規則 |
|---|---|---|---|
| 占有者自身の Start、同じタイプのアフィニティ（`placeHome`） | claim して起こす | home の Start カウントと claim ロック | マーカーが拒否しない唯一の行為者：カウントを動かして L1 を追い越し、L1 は次のチェックで止まる。claim を持つスロットについての自身の `slotLostAfter` の判断は残る |
| 占有者自身の Start、サイズ/class 不一致（`placeHome` → `releaseAndReplace`） | 背景で `releaseSlotSince` | 各境界での `startSuperseded`。マウントロック | 同じ |
| 占有者自身の Start、予約/古い（`replaceReservedSlot`） | `moveHomeOff`（`releaseSlot`）のあと**古い**箱を `terminateSlot` | 同じカウントとマウントロック | 同じ。`terminateSlot` は隔離された箱を拒否（規則 4） |
| ほかのメンバーによる追い出し（`evictLongestIdle`） | 最もアイドルの長い占有者に `victim.releaseSlot` | 犠牲者自身のランタイム：そのマウントロックと Start カウント | 救出マーカーがある間は `releaseSlotSince` で**拒否**される（規則 2）。選択時に飛ばすのは最適化 |
| ほかのメンバーの `makeRoom` | `victim.releaseSlot`、そのあと**呼び出し側が**箱を `terminateSlot` | 犠牲者のマウントロックとカウント。終了そのものはフェンスされない | 同じく**拒否**され、その `terminateSlot` は箱のマーカーと刻印を読み直す（規則 2）。休眠中の暗い占有者は実行中のタスクがないので `tasks[id] > 0` では除外されない |
| ゴールデンのベイカー（`ReleaseForBake`、seed と probe の Start/Stop） | seed や probe の home への `releaseSlot` | 同じ home のロックとカウント。ベイカー専用のリースは L1 とは直列化**しない** | 特別扱いなし：seed と probe は普通のワークスペース。救出されればベイクは失敗し、ベイカー自身の期限がすでに扱う |
| ハイバネーション（リーパーからの `hibernate`） | 最初の手順として `releaseSlot` | 同じ | 同じく**拒否**されて再試行。L1 のあとは home が切り離されているのでハイバネーションは進む |
| `Destroy`、`EraseHome`（メンバーか管理者の操作） | `Stop` のあと `releaseSlot` | 同じ。`Stop` がカウントを進める | その `Stop` が L1 を追い越す。umount は、今と同じく、応答できない箱を待つ。L1 は先に CP の保留中コマンドを取り消し、umount の寿命のあいだロックが握られないようにする |
| `sweepVolume` の drift と terminate の段 | `releaseSlot`、続いて `terminateSlot` | 同じ | 同じく**拒否**（暗いスキャンはパスの最初に走る） |
| `sweepFreeSlots` | home のないスロットを停止・終了 | 不要 | 空きの暗いスロットは L1 の対象ではない。プール画面が印を付ける |
| #2474、運用者の強制停止 | 占有者の `Stop`、取り消し、`StopInstances` | 同じカウントの手順（決定 4） | 許す。運用者の判断である |

**まだ home を持たないスロットを選ぶ経路**（したがって暗い使用中スロットではあり得ない）：`placeHome` の空きスロット attach
（`af-role=slot` と `slotExcluded` で絞った一覧。attach の前に 1 回、attach と claim のあとに 1 回の読み直し）、`growPool` → claim
（新品のスロット。読み直しなし）、`adoptEarlier`（前の試行が起動したスロット。claim を書く前に死んだものや claim が切れたものも
含む。claim のあとに 1 回の読み直し）。claim TTL（`claimTTL`、300 秒）は行為者ではない：期限切れの claim は `claimLive` が無視し、
それが、追い越された Start が最長 1 TTL だけ無害に claim を残せる理由である。

**不変条件を 1 文で：** *home の付いたスロットに対するすべての行為者は、その home のマウントロックと Start カウントを通って
届き、破壊的な呼び出しの前ごとにカウントを読み直す。占有者自身の Start を除く自動の解放者は、その home に救出マーカーがある間、
破壊的な入口で、同じロックの下で拒否される。home のないスロットは L1 や L2 の対象にならない。*

だから、この設計は home が付いていて生きている claim のないスロットにだけ動き（決定 1）、空きスロット・新品スロットの経路に
フェンスが要らない。#2474 の最初の版はタグで隔離してから保持者を読んだ。これは**空きかもしれない**スロットには正しい形で、
4 巡（所見は、そのレビューにならって R2〜R9 とラベルする）がその形を完成させるべき場所をすべて示した：

- **R3**（占有者を止めたあとにタグを書いた）には 2 つの半分がある。ほかのメンバーがそのスロットを選ぶことは、使用中のスロット
  ではあり得ない（表）。**占有者自身のワークスペースの新しい Start** は起こり得て、決定 4 の所有権の手順がまさにそのため
  にある。
- **R3b**（タグの前に候補を一覧し、タグのあとに attach した配置）と **R7**（claim のあとに読み直しのない新品スロット）は空き
  スロット・新品スロットの経路：使用中スロットには到達できず、`darkBootGrace` より若いスロットは暗くない。
- **R8**（home の claim をボリューム ID だけで消すクリーンアップが、*新しい* Start の claim まで消した）：スイーパーによる
  claim の削除はすべて決定 4 の所有権トークンで守られ、トークンはロックの下で読み、判断時の値を使い回さない。
- **R9**（隔離された置換先のスロットを未使用のものとして片付け、**終了**して証拠を壊した）と **R2**（置換予約も持つ隔離
  スロットが、古い箱を終了する `replaceReservedSlot` を通った）：下の規則 1 と 4。

これを実装するコードに対して次の 4 つの規則が出てくる。どれも安く試せる：

1. `slotTypeMatches` は、予約やテンプレートを読む**前に**、隔離スロットを単なる不一致として扱う。隔離された箱に付いたままの
   home（切り離しに失敗した L2）は、CP がもう命令を許されていない箱（`SendCommand` は `af-role=slot` にだけ付与）を
   起こすのではなく、解放して置き直される。`releaseSlot` は、まだ `stopping` の箱が止まりきるのを待ってから切り離す。
2. 除外は、候補の選択ではなく、**破壊的な入口で、home のマウントロックの下で**行う。救出が始まる前に
   `evictLongestIdle` や `makeRoom` が選んだ候補と、そのあとにマーカーを書く救出は、そうしないと `releaseSlotSince` で出会い、
   そこは自分の入口でカウントを読み、動かさない。だから `releaseSlotSince`（すべての `releaseSlot` 呼び出し元が共有する唯一の
   入口）は、その home に救出マーカーがあり、呼び出し元がその救出でない間は拒否し、救出は home がまだ付いていると確かめたあとに、claim ロックの下でマーカーを書き、
   そのあとでようやくマウントロックを取る。すでにマウントロックを持つ解放者が先に終わる（その保留中 SSM コマンドは手順 2 で
   取り消されるので、umount の寿命のあいだロックを握り続けられない）。救出はそのあと home がなくなっているのを見て止まる。`makeRoom` では、犠牲者の解放のあとの箱の `terminateSlot` が箱のマーカーと刻印を
   読み直す（自動の意図による拒否、規則 4）。救出はロックの下で home が付いていることを要し、そのころ犠牲者の home はもうない
   ので、これは安全である。マーカーが拒否**しない**唯一の行為者は占有者自身の Start（`releaseAndReplace` と
   `replaceReservedSlot` を含む）：カウントを動かして救出を追い越し（決定 4）、救出は次のチェックで止まる。選択時に飛ばすこと
   （`af-dark-since`）は上に載せる最適化であって、フェンスではない。
3. 所有権は決定 4 に従い、チェックと破壊的な呼び出しは 1 つのリースを共有する。取れないロック、読めないカウント、失効した
   リースは、その手順を**中止**する：ロックが取れないときに手順を無保護で走らせる `ifOwned` のフォールバックは使わない。
4. `terminateSlot` は意図を受け取る。**自動の**呼び出し元（スイーパーの terminate の段、`replaceReservedSlot`、
   `retireUnusedReplacement`、`makeRoom`）は、ロールが `quarantined` の箱を拒否する。認可され監査される運用者の
   `TerminateQuarantinedSlot`（決定 30）だけが明示の意図を渡すので、証拠を消せる唯一の操作は今も動く。

*却下した案。* **すべての配置経路に claim 後の隔離チェックを足してフェンスする**（#2474 が試したこと）：正しいが、1 つの
関心を 7 つの呼び出し箇所に散らし、4 巡のレビューがそのたびに 1 つずつ漏れを見つけた。使用中スロットの規則があれば、それらの
箇所には到達できず、到達できないチェックは、規則が変わった日に間違うデッドコードになる。**置換予約のタグをフェンスに流用する**：
両側のチェックはすでにあるが、行き着く先が `terminateSlot` で、L2 が残そうとする証拠を壊す。**隔離された箱への
`terminateSlot` をどこでも拒否する**：運用者の終了ボタンが壊れる。

### 4. だれが何を持つか、所有権トークン、再起動を越えて残るもの

- **Start** は生きている claim を持つ間そのスロットを持つ。判断は自分の `slotLostAfter`、動作は `abandonLostSlot`。変更なし。
- **スイーパー**は home があって生きている claim のないスロットを持つ。ワークスペースから見れば第三者である。
- **管理者の操作**（#2474）は、同じコードを人が使うもの：同じ所有権を取り、同じゲート（決定 2 の手順 3 と 4）で止まる。
  タスク ENI が付いている間は先に登録解除する、または拒否するようにそれを移すのは #2450 の実装の一部で、同じ ENI ゲートであり、
  検証もそこに属する。今の #2474 のゲートは「ECS エージェントが接続かつ SSM が Online」だけで、そのガイドも 0045 の追記も ENI の
  リスクに触れていない。ゲートを `slotDark`（起動猶予、継続時間、Agent プローブ）に切り替えるのは、本書が提案する挙動の変更で、
  すでにあるものではない。

**ロックの順序。** どこでも、マウントロック（`homeLockMount`）が外側、claim ロック（`homeLockClaim`）が内側で、今の `quarantineSlot`
（マウント、続いて `ifOwned`）と同じ。claim ロックを持ったままマウントロックを待つものはない：救出の準備の手順は claim ロックだけを
取り、マウントロックを求める前に手放し、手順 2 の取り消しはどちらも要らない。2 つのロックの間の隙間を越えてフェンスを運ぶのは
マーカーとトークンで、破壊的な呼び出しはそのたびに、マウントロックの内側の claim ロックの下でトークンを確かめ直す。

**所有権トークン。** 判断のパスは Start カウント `g_d`、home のボリューム ID、起動世代を記録する。L1 を始めるとき、**home の
claim ロックとリースの下で、1 手順で**：カウント `g` を読み、`g == g_d` を要求し、そうなら `g_r`（Stop が行う増分）に上げて、
`g_r` を持つ救出マーカーを書く。そうでなければ、判断以降に何かが動いた（メンバーの Stop、新しい Start、Destroy）ので、
スイーパーは退き、次のパスがもう一度判断する。以降の破壊的な呼び出しの前ごとに、ロックとリースの下で、カウントがちょうど
`g_r` であること、マーカーがあって同じ home と起動世代を指すことを要求する。ほかの値なら、ほかのだれかが home を持って
いるので、救出は止まり、マーカーを落とし、残りには触れない。Stop を呼んでからカウントを確かめるのは両方向に間違う：新しい
Start（`g_d + 1`）が先に着地していれば自分の Stop の増分がそれを打ち切り、自分の増分のあとに `g_d` を使い回せば自分の Stop を
追い越しと読む。だから `g_d` の確認と増分は 1 つのロックされた手順で、トークンはそれが作った `g_r` である。

**救出マーカー**はインスタンスタグ
`af-rescue = <home のボリューム ID>/<起動世代>/<段階>/<g_r>/<began>/<blocked_since>` で、**最初の副作用の前に**書く。段階は
`begun`、`deregistering`、`deregistered`、`stopping`、`stopped`、`detaching`、`detached`。箱への AWS の副作用はどれも、それを名指す段階
（`deregistering`、`stopping`、`detaching`）を厳密な条件の下で先に書いてから行うので、呼び出しと次の書き込みの間で落ちても、箱に
手を付けたと言うマーカーが残る。2 つの時刻は再起動を越えて残る（`rescueBlockedAfter` は、手順が上限を初めて越えた
ときに書く `blocked_since` から数える。`af-dark-since` はその時刻ではない）。再起動を越えて残るのはマーカーで、検出の述語は
残れない。`stopping` や `stopped` の箱や、登録解除のあとに SSM が戻った箱は、定義上もう「暗い」ではないからだ。

検出とは別の**再開スキャン**が、状態を問わずマーカーを持つすべてのインスタンスを列挙し、次のすべてが成り立つときだけ
救出自身の手順を続ける：同じボリュームがこの箱に付いている。
箱の `LaunchTime` がマーカーの起動世代と、`stopped` を含む**すべての段階で**等しい。Start カウントがまだ `g_r`。段階は、この救出が
何をしたかの記録であって、箱の現在の状態の証拠ではない：箱の状態に依存する手順の前、特に切り離しの**直前**には、EC2 に尋ね、
`stopped` と答えなければならない。止まったあとに運用者が EC2 コンソールから起動し直した箱（`LaunchTime` が動き、Start カウントは
動かない）を、スキャンが見つけても、動いている間に切り離すことはない。これらの条件を満たさないマーカーは、読まれずに捨て
られるのではなく、下のファイナライザへ回る。

**マーカーの所有権。** 救出が変更・削除してよいのは**自分が書いた正確なマーカー**だけ：削除は、その救出が書いた値を持つ条件付きの
`DeleteTags`（EC2 は値が一致するときだけタグを消す）で、更新は読んだ値の置き換え。カウントが動いた、起動世代が変わった、
home がなくなった、のいずれかを見つけたスキャンも、同じ方法でそのマーカーを消すので、遅れて再開した古い救出が、新しい救出の
マーカーを消すことはない（R8 と同じ形）。

**2 つの仕事、2 組の条件。** 救出の*回復*（箱や home に触れる段階を続けること）には上の厳密な一致が要る：同じボリューム、同じ
`LaunchTime`、カウントがまだ `g_r`、切り離しの前に EC2 が `stopped` と答えること。*ファイナライザ*は、エピソードがあったことを
記録するだけで、箱の状態にもボリュームにも触れず、タグだけに触れるので、カウントや起動世代の一致は要らない：

- 登録解除・停止・切り離しのそれぞれの前に、マーカーをそれを名指す段階（`deregistering`、`stopping`、`detaching`：意図）に進める。
  これは厳密な条件の下で行う。呼び出しが成功したら完了の段階（`deregistered`、`stopped`、`detached`。最後は `detached_at` も記録）に進める。
- 段階が `begun` を越えたマーカー（意図の段階も完了の段階も）は、箱に手を付けたかもしれないことを意味するので、救出がどうなったかに
  かかわらずエピソードである：ファイナライザは `af-wedge-at = marker.began` を、**すでにある `af-wedge-at` より新しいときだけ**
  書き、そのあと自分の正確なマーカーを消す。まだ `begun` のマーカーは箱に何もしていない（準備は Start と claim にしか触れない）
  ので、消すだけ。`CreateTags` は無条件に上書きするので、「新しいときだけ」にはフェンスが要る：すべてのファイナライザの
  `af-wedge-at` の読み取り・比較・書き込みは、インスタンスごとのリース（`ec2-slot-wedge/<instance id>`。home のロックと同じ
  `cp_lease` ストア）の下で走る。リースはその箱のすべての救出で、home や世代を問わず共有され、書き込みの前に時計でリースを
  確かめ直す。リースが取れなければマーカーは残り、次のパスが再試行するので、これは通常時の並行するファイナライザを直列化する。
  すでに AWS に送られ、リースの失効後まで遅れた要求は**フェンスしない**。未解決の問い 8 を参照。
- `detaching` で home がもうこの箱にないときは、カウントで決める：まだ `g_r` なら、ほかのだれも動かせなかった（ほかの解放者は
  マーカーがある間は拒否される、規則 2）ので、この救出で、完了している。カウントが動いていれば占有者自身の Start が動かした
  ので、同じようにエピソードを記録する。どちらでも再発の窓は正しく、救出自身の残りの手順は捨てられる。

したがって、どの 2 手順の間で落ちても**エピソードは失われない**。ほかのだれかが先に着いたときに捨てられるのは救出の残りで、箱が
暗くなったという記録ではない。始まった救出は、エージェントが戻っても取り消されず、人や Start に追い越されるだけ。home のリース
（`homeLeaseTTL`、90 秒）は死んだ CP では失効するので、再開するレプリカが取れる。

- **2 つのレプリカ**はどちらも検出し、どちらも同じ値を刻む。所有権はロックされた手順で取るので、2 つ目はカウントが動いて
  いるのを見て退く。どの手順も冪等（`StopInstances`、未登録インスタンスの登録解除、切り離し済みボリュームの切り離し）。
- **監査**はコールバック（アダプターにデータベースがないため）：`Config.OnSlotAutoReplace` と同じ形で、actor は `system`、
  アクションは `pool.slot_dark_detected`（1 エピソードにつき 1 回）、`pool.slot_dark_rescued`、`pool.slot_dark_blocked`、
  `pool.slot_dark_quarantined`。

## 未解決の問い（どれも実機の実行が要る）

1. **#2474 の経路で、タスク ENI が付いたまま止めること。** 再起動した箱は、NAT のあるデプロイとないデプロイで egress を取り戻すか。
   取り戻さなければ、手動の操作は ENI が付いている間は拒否する、または先に登録解除しなければならない。この確認と #2474 の
   操作の変更は #2450 の実装が持つ（決定 4）。別の Issue は起こさない。
2. **無害な暗い時間。** 健全な箱でも ECS エージェントや SSM エージェントはどれだけ沈黙し得るか（エージェントの自己更新、
   docker の再起動、インスタンスの再起動、短い停滞）。`darkAfter` の 10 分は、検出のみの期間が答えるまでは推測。
3. **SSM の鮮度。** `LastPingDateTime` はどのくらいの頻度で更新され、`PingStatus` はいつ `ConnectionLost` になるか。もう何のゲートにも
   ならない（決定 1 は待ちを縮めるのに外部のタイムスタンプを使わない）が、プール画面が示し、裏づける信号は歓迎される。
4. **登録解除がタスクに何をするか。** 2026-08 の事件で観察したのは、強制登録解除のあとに ENI が消えたこと。`STOPPING` で
   止まったタスクが解放されるのか、プロセスが孤児として動き続けるのか（AWS が登録解除について文書化しているのはこちら）は、
   ここでは確立していない。#2447 が観察したのは、箱を起動すると消えたこと（登録解除していない箱で）。受け入れ条件：登録解除したコンテナインスタンスで、箱を起動するとエージェントが再接続してタスクを報告するのか、タスクはすでに消えているのか。設計はどちらにも頼らない。
5. **強制切り離しや Force 停止は home を壊すか。** スラッシング中の箱で、それぞれのあとの ext4 / XFS のジャーナルリプレイを
   測る。これが `quarantine` モードのゲートになる。
6. **スラッシング中の箱で、ワークスペース Agent のプローブは安く、正直か。CP は Agent にどこから届くか。** 決定 1 は動いている
   サービスについてそれを要する。遅くタイムアウトするなら、スイープの 1 パスに予算が要る。
7. **`MemoryMin` とホスト予約（#2452、メモリ逼迫への対応）で基準の発生率は変わるか。** 暗いエピソードが稀になれば、L2 の再発の
   規則は発火せず、`darkRepeatWindow` は捨てられる。
8. **リースが失効したあとに着地する古い `CreateTags`。** インスタンスごとのリースはファイナライザの読み取り・比較・書き込みを
   直列化し、書き込みの送信前に時計も確かめるが、どちらも AWS がすでに受け取った要求を取り消しもフェンスもしない。シナリオ：
   ファイナライザ A がリースを持って `af-wedge-at` を読み、`t1` を送る。RPC が遅れてリースが失効する。別のレプリカがその古い
   エピソードを完了してマーカーを消す。次のエピソードのファイナライザがリースを取って `t2`（t2 > t1）を書く。そのあと A の要求が
   着地し、タグが `t1` に戻る。影響は L2 の再発の判断に出る：古い時刻を読み、`darkRepeatWindow` を過ぎたかもしれず、2 度暗くなった
   箱が最初のエピソードとして扱われる（昇格の見逃しであって、誤った停止ではない）。EC2 のタグには条件付き書き込みがないので、
   単調な更新には別のものが要り、選択は未決：権威あるストアでのアトミックな max（決定 4 のコールバックがデータベースに書いてよい
   なら CP のデータベース）、上書きできない記録（エピソードごとに 1 つのタグか 1 行の監査で、再発の判定は最大値を取る）、書き込み先が
   検証するフェンシングトークン。#2450 の実装は、`af-wedge-at` が何かのゲートになる前にこれを決めなければならず、それまで再発の
   規則は助言にとどまり、`quarantine` モードをそれを根拠に有効にしてはならない。

**2026-11-12（wedged 判定、#3963。同日のオーナー判断）。** 決定 1 は、エージェントが沈黙したスロットを扱う。2026-11-12 の本番では
逆の形が出た。8 GiB のスロットが約 1 時間スラッシングし、そのあいだ ECS エージェントは接続中、SSM は `Online` のままで、古いタスクは
30 分以上 `STOPPING` に留まり、CP から Agent（`:7700`）への呼び出しは ECS が `HEALTHY` と言うのに即座に失敗した
（`connection reset`、`EOF`）。上のどの段も動かなかった。通常のバックグラウンド `releaseSlot` で回復した（umount 8 秒、タスクは
約 75 秒後に `STOPPED`）。決定 1〜5 は変えない。ここでは dark 判定の隣に、同じ対象範囲・同じ起点の規則・同じ展開方針で、2 つ目の判定を足す。

*wedged の判定。* あるスイープで、次がすべて成り立つスロットを **wedged** とする。

- EC2 が `running`、`darkBootGrace` 以上前に起動し、home が付いていて、生きた claim が無い（決定 1 の対象範囲。claim を持つ Start が
  判定を持つ）。
- ECS エージェントが**接続中**。「エージェントはまだ応答している」が定義で、これが 2 つの判定を分ける。ECS エージェントが沈黙した
  スロットは dark のスキャン（と #2447 のブロック段階の 1 行）の対象であり、1 台の箱から両方のエピソードが出ることはない。
- **次のどちらか**：ワークスペースのサービスのタスクのうち、このスロット上のものが、120 秒に
  `wedgedStopGrace`（5 分。どちらも定数）を足した時間より長く
  `STOPPING`（または `DEACTIVATING` / `DEPROVISIONING`）のまま（120 秒は、このリポジトリが登録するどの `stopTimeout` の上限でもある。
  `AF_STOP_GRACE_SEC` は 1〜120 秒に丸められるため、登録時と CP の現在の設定が違うタスクも誤判定しない。健全な停止は、タイムアウトに
  エージェントの報告を足した時間で終わる）。**または**、ワークスペース Agent のプローブ（`LastAgentProbe`、
  #3960 / PR #3971）が `failed` で、ECS がこのスロット上のタスクを `HEALTHY` と報告している。

*信号ではないもの。* 120 秒と猶予の内にある停止中のタスク、停止時刻の無い停止中タスク（時間を測れない）、デプロイの入れ替え中
（タスクが複数、別の箱にいる、まだ `HEALTHY` でない）、`healthy` のプローブ、`unknown` のプローブ。これらはスタンプを残さない。
`unknown` のプローブと、時刻を測れない停止中タスクは、既存のスタンプにも触れない。

*読み取りの失敗は答えではない*（決定 1 と同じ）。サービス・タスク・コンテナインスタンスの読み取りが失敗すればそのスロットは不明、
クラスタの読み取りが失敗すればスキャン全体が不明になる。「wedged ではない」と言ってスタンプを消せるのは、成功した読み取りだけ。

*プローブの同一性の注意（#3971 のレビューより）。* Service Connect のエイリアスは、どのタスクが答えたかを証明できない。プローブの結果が
スロットを代弁するのは、エイリアスにまだ答えうるタスクがすべてそのスロット上にあるときだけ（desired が `STOPPED` でまだ消えていない
タスクと、停止から 2 分以内のタスクも数える。2026-11-12 の Agent プローブの注記と同じ）。タスクの入れ替え中、プローブは failed ではなく
**不明**。停止中タスクの信号はプローブも同一性の推測も要らず、タスク自身のコンテナインスタンスを読む。

*`mem-pressure` 行。* Agent の `mem-pressure` ログ行が途絶えることは、3 つ目の信号として検討したが**使わない**。CP は Agent のログを
安く読めない（スロットごと・スイープごとの CloudWatch Logs 読み取りか、存在しない Agent エンドポイントになる）。観測した事故は上の
2 つで足りる。安い取得元ができたら足せる。

*起点。* インスタンスタグ `af-wedged-since`、`<時刻>/<LaunchTime>[/detected]`。形も規則も `af-dark-since` と同じ。述語が成り立つと最初に
確かめたパスが書き、wedged でない（箱が動いていない、ECS エージェントが沈黙した場合も含む）と確かめたパスが消し、`LaunchTime` が違う
スタンプは書き直して起動のたびに時計を張り直し、報告したら `detected` を付けて「1 エピソードにつき 1 回」を再起動越しに保つ。
`wedgedAfter`（`AF_ECS_EC2_WEDGED_AFTER_SEC`、既定 600 秒、0 = オフ）は `darkAfter` と同様に、`darkBootGrace` と
`slotLostAfter + sweepEvery` の大きいほうまで引き上げる。外部の時刻で待ちを短縮しない：タスクの `StoppingAt` は信号の条件として
すでに使われ、時計は述語全体を最初に観測したスイープから始まる。

*アクション（ここで決める。実装はしない）。* そのスロットの home に対する通常の `releaseSlot` 経路：SSM の umount、タスクの停止、
デタッチ。スロットは使い続ける。決定 4 の所有権トークン（claim ロックの下で取り、破壊的な呼び出しの前ごとに確認する。L1 救出と
同じトークン）の下で動き、箱には触れない（登録解除も `StopInstances` もしない。エージェントは応答しているため）。wedged のスタンプが
`detected` に達した後に動く。umount のために SSM が `Online` である必要があり、SSM がオフラインの wedged スロットをどうするかは実装で
決める（#3991）。

*フラグ。* `AF_ECS_EC2_DARK_SLOT_ACTION` ではなく**兄弟**の `AF_ECS_EC2_WEDGED_SLOT_ACTION`（`off | detect | release`、既定 `detect`。
`release` はアクションができるまで解釈されるが `detect` として動く）。2 つの段は終わりのアクションが違い（箱の救出と、home の
通常の解放）、どちらを有効にする前にも、検知のみの期間が示すべき誤検知の率が違い、wedged のスキャンは追加の AWS 読み取り
（対象スロットごと・スイープごとにサービスの読み取り、タスク一覧、コンテナインスタンスの読み取り）を行う。dark のスキャンを失わずに
運用者がこちらだけ止められる必要がある。

*画面など。* 監査 `pool.slot_wedged_detected`（1 エピソードにつき 1 回。`workspace`、`volume`、`wedged_since`、`signal` =
`task_stopping` | `agent_probe_failed`）。プール画面の `wedged_since` と `wedged_rung`（今は `observing`）と、dark の隣の Console バッジ。
IAM：`af-wedged-since` はテンプレートの変更が要らない（スロットのタグ書き込みの文が、プールのリソースに対し `af-pool` / `af-role`
以外のキーを許している。キーは `deploy/local/cfn-cp-tag-fence-test.py` に入れた）。`af-dark-since` と違い、このスタンプは箱を
`makeRoom` から**除外しない**：wedged スロットの治療が通常の解放であり、`makeRoom` の犠牲者の解放もそれを通るため。

- 各段階はマーカーのフェーズから始まり、フェーズを信用せず世界を読み直す。段階: (4) タスク ENI が付いていれば、フェーズ
  `deregistering`、強制登録解除、ENI が消えたことの上限付きポーリング（2 秒間隔 15 回）、`deregistered`（タスク ENI の無い

**2026-11-12（L1 の Start 側、#3965）。** ダークなスロットにホームがあるメンバーの Start は、そのボックスを待たなくなった。動くのは
`AF_ECS_EC2_DARK_SLOT_ACTION=rescue` のときだけで、`detect` のときの Start は変わらない（コード: `runtime_ecs_ec2_start_dark.go`）。決定 3 の
「占有者自身の Start はカウントを動かして L1 を追い越す」は、読み取れないレスキューに出会った Start については今も正しい（後述）。この注記が足すのは、
読み取れる場合の引き継ぎである。

*引き継ぎ: Start は道を譲る。* レスキューの準備段階はカウントを `g_r` に上げ、あらゆる Start を終わらせる。先に自分を数えた Start は、自分が起こしたレスキューに
中断され、後で数えた Start はレスキューを追い越す。そこで次の場合、Start は数えない。`Start` は `beginStart` の代わりに `admitStart` を呼び、クレームロックの下で
カウント `g` を読み、次の三つの道のどれかを取る。

1. **ダークでなく、レスキューもない**（通常の場合と、読み取りが失敗したすべての場合）: これまでとまったく同じに自分を数える。
2. **レスキューがホームを持っている**: ボックスにこのホームのマーカーがあり、フェーズが `begun` から `detaching` まで、`m.Gen == g`、エポックがボックスの
   `LaunchTime` と一致する。Start は数えない。#2447 の blocked フェーズの行を出して待つ。`preparing` のマーカー、別のホームのマーカー、カウントが動いたもの、
   エポックが違うものは持ち主ではない（最初のものは、`g_r` と等しいカウントが何も証明しないため。レビュー第 1 巡を参照）ので、Start は自分を数え、決定 3 のとおり追い越す。
   マーカーの確認を加算と同じロックで行うので、直前にスイープが始めたレスキューを、その前に見に行った Start が追い越すことはない。
3. **ボックスがダーク**: ホームのボックスが実行中のスロットで、有効なクレームもマーカーもなく、このエポックの `af-dark-since` が `darkAfter` 以上古い。Start はそのロックの下で
   `g_d = g` を取り、ロックを離して、レスキュー自身の準備段階（`rescuePrepare`、同期で実行。数回の AWS 呼び出しで待ちはない）を実行する。カウントはそこで動く。
   Start は数えていないので、自分のレスキューを追い越せない。準備が引き下がった場合（決定のあとにカウントが動いた: Stop や新しい Start）は決め直し、最大
   `darkAdmitTries`（3）回まで、それでも続けば Start は自分を数える。準備が失敗した場合は、原因をつけて Start を失敗させる。レスキューを始められない Start は、
   `starting` のまま居座らず、そう報告する。

どの道でも Start はそのリクエストを `nil` で終え、バックグラウンドの処理が続ける。自分がレスキューを始めた場合は、その残り（キャンセル、続いてスイープと同じ手順 4〜6）を実行する
（プロセスが死んでも、スイープの再開スキャンが終わらせる）。どちらの場合も、そのあと**待ち**（`awaitRescue`、5 秒ごと、バックグラウンドの予算まで）、読み取った内容で動く。

- カウントが `g_r` でなくなった（Stop、`Destroy` / `EraseHome`（先に Stop する）、新しい Start）: 終わる。仕事は相手のもので、レスキューが動いていれば次の確認で止まる。
- ホームはボックスにあり、マーカーもある: 行を出し続け、更新する（`blocked_since` があるレスキューは「`<phase>` で止まっている。自動で再試行する。運用者がボックスを止める必要があるかもしれない」と読める）。
  詰まったレスキューは、黙って待たずに見せる。
- ホームが外れ、マーカーも消えた（ファイナライザとプールの後始末が済んだ）: **後続の Start**。クレームロックの下でカウントがまだ `g_r` のときだけ自分を数え、
  あとは通常の Start（`startFrom`）として、ホームを持たないホームと同じように配置する。
- ホームはボックスにあり、マーカーが消え、カウントは動いていない（レスキューが準備を取り下げた）: 行を消して終わる。

後続の Start は自動で、メンバー自身の再試行は待ちのない同じものである。レスキューのあとはマーカーがなく、ホームは外れているので、通常どおり数える。続けて 2 回 Start しても、
どちらも道を譲って待ち、先にカウントした後続が勝つ。もう一方はカウントが動いたことを見て終わる。ホームがボックスから外れると `State()` が行を消すので、上限で諦めた待ちや、
スイープが終わらせたレスキューのあとに、Console のダイアログが停止中のワークスペースの上に開いたままになることはない。

*確認: サービス稼働中の拒否（#3993）は妨げにならない。* `State()` が `stopped` と答える Start では、サービスは desired 0（またはなし）で、`rescuePrepare` が許す場合である。
稼働中のサービスは `starting` か `running` なので、この経路に来ない。

*ホームの行き先。* ホームは、ホームを持たないホームと同じく `placeHome` が配置する。空いている起動中のスロットが先、停止中のスロットが後である。レスキュー済みのボックスは
稼働のまま残る（決定 2）ので、停止中の空きスロットとして最後の選択肢になる。ほかに空きがないときだけ使われ、そのときは新しい起動になる。

*未実施。* スタンプは、スイープが残したまま（最大 1 スイープ分古い）信頼する。Start は SSM や Agent を改めて問わない。サービスは停止中で、戻ってきたボックスをレスキューしたときの
コストは、ワークスペースを失うことではなく Start が遅くなることだからである。実際の AWS では未実行。
