## 背景

メンバーの仕事はチケットとセッションとプルリクエストで、Console はそれを 3 か所に分けて見せている。ワークアイテムの
レール（ADR 0061）、セッション一覧と概観（ADR 0078）、セッション行の PR バッジである。「このチケットはレビュー待ち」
「このチケットのセッションはあなたを待っている」と言う場所はない。ボードに要る 2 つの入力は、その後 #3134 と #3129 で
入った。いまのツリーにあるものと足りないものは次のとおり。

1. **リンクはあり、ミラーされている。** セッションはロール付きのリンクをいくつも持つ（`started`、`created`、
   `working`、`reviewing`、`watching`。`workspace/agent/internal/session/links.go:21-25`）。Agent は生きている
   セッション一覧にそれを載せて返し、CP がセッションの行と同じトランザクション（`ReplaceSessions`）で
   `session_work_link`（SQLite 0118/0119、Postgres 0103/0104）に書くので、Workspace が止まっていても読める。Agent が作った
   ばかりのリンクは、CP が次に一覧をミラーするまでこの表に載らない。
2. **ミラーは活動を持たない。** `SessionRow` が持つもの（識別子、由来、リンクなど。
   `control-plane/internal/store/store_session_index.go:11-32`）のうち、活動についての情報は `State`（`running` | `stopped`）と
   `Carried`（セッションを畳んだとき答えを待っていたやりとり）だけである。working、
   question、plan、permission、blocked は生きている Agent の一覧にしかなく、Console の `stateInfo()`
   （`console/src/lib/sessionview.ts:149`）が分類する。ADR 0078 決定 5 が、二重に導いてはならないとした唯一の導出である。
3. **リンクが持つ PR の情報は state だけ。** `WorkItemLink.State` は `open`、`draft`、`merged`、`closed`。セッションの
   PR について、CI、changes-requested、conflict が通信に乗るのは、その*現在のブランチ*の PR（`branchpr.PR` の
   `ChangesRequested`/`Conflict`、`branchpr.go:59-60`）だけである。メンバーの受信箱の行になっている開いた PR には別の経路が
   ある。Agent が行の `Checks` と `Mergeable` を埋め、CP が配る（`work_item_cache.checks` と `.mergeable`、マイグレーション
   0074、`workitems_prstatus.go:34-45`）。`branchpr.PR` の `ReviewDecision` と `Mergeable` は `json:"-"` で、`Ready()`
   （`branchpr.go:118`）はそれらに対するメソッドである。Agent は自分の `pr.ready` 通知にこれを使うが、Console が読む
   どの一覧にも `ready` の真偽値はない。
4. **スイッチが入っていない限り、セッションが離れた PR の state はリンクに書き戻されない。** 経路は 3 つある。セッションの
   現在のブランチの PR は、セッション一覧と一緒に読まれてリンクに書かれる（`sessionx/session_work_links.go:181-225`）。ブランチを離れて保持している
   リンクは、PR フィードバックの tick が番号で読み、書き戻す（読み取りは `pr_feedback.go:242-260`、書き戻しは
   `pr_feedback.go:603-635`）。PR フィードバックが切れていると tick は最初に return する（`pr_feedback.go:503-511`）。切れて
   いるのが既定である。メッセージキューの PR スナップショットも保持しているリンクを番号で読む
   （`sessionx/queue_pr_snapshot.go`）が、そのキューの配信に答えるためだけで、何も書き戻さない。セッションが離れたマージ
   済みの PR は、リンク上で永久に `open` のままになる。
5. **受信箱は、止まっている間は古く、そこにないことは何の証拠にもならない。** CP は取得時刻付きでキャッシュを
   配る（ADR 0061 決定 1・15）。レールが描くのは、有効なクエリ全体で 1 つの集約時刻
   （`WorkItemsSection.tsx:294-296,326-332`）で、行ごとではない。行がキャッシュから消えるのは、それを返したクエリが次に成功し、もう返さなくなったとき。既定の
   クエリはプロバイダーで違う（Jira のクエリは done を除く。GitHub は `is:open` と `involves:@me`。Bitbucket は
   メンバー宛てのレビューから始める）ので、行がないことは項目が done の証拠ではない。プルリクエストのトラッカー状態はさらに
   粗い。GitHub は、マージされたかどうかに関わらず closed を `done` に写し（`workitems.go:460-472`）、draft は
   `in_progress` になる。
6. **台帳は 2 つある。** `work_item_session` を書くのは Console の起動だけ（ADR 0061 決定 9）。`session_work_link` は
   Agent があらゆるロールで持つリンクを、CP のミラーが書く。セッションが開いた PR や、チケットを見張る子が見えるのは後者
   だけである。

問いは、カードとレーンをどう定義すれば、それが情報源に従うか。そして、情報源が十分に語るために何を足さなければならないか。

## 決定

### 1. カードは 1 つのワークアイテム。セッションと PR はリンクを通してそれに付く。

- **同一性**は `(provider, 大文字小文字を畳んだキー)`。`session_work_link` が使う畳み方と同じ。
- **駆動ロール。** `started`、`working`、`created`。駆動ロールのリンクだけが、カードに何かを付け、レーンを動かす。
  `watching` と `reviewing` のリンクは、名指した項目のカードにチップとして出るだけで、ほかには何もしない（未決の問い 3）。
- **付き方。** セッションは、駆動リンクを持つ、PR ではない項目すべてに付く。PR リンクが同じカードに付くのは、その PR リンク
  自身が駆動ロールを持つときだけである。チケット A を駆動し、PR B を見張っているだけのセッションでは、B の CI の失敗が A を
  動かさない。駆動リンクが PR で、駆動するチケットを持たないセッションは、その PR 自身のカードに付く。受信箱の PR 行や、
  チケットなしで開いた PR は、それ自身がカードになる。
- **孤児。** 駆動リンクを持たないセッション（見張るだけ、レビューするだけのものを含む）は、それ自身がカードで、キーは
  Workspace とセッション名。決定 2 では自分自身を駆動セッションとして数える。
- **カードが存在する**のは、次のどれかが成り立つとき。終わったプルリクエストではない受信箱の行（PR の行の `done` はマージか
  close を意味する。事実 5）、駆動するセッション、開いているかマージ済みの、駆動ロールを持つ PR リンク。マージされずに閉じた
  PR や、`merged` のリンクがない終わった PR の行はそれだけではカードを作らず、そのどれにも当たらない項目への `watching`
  リンクも作らない。そのような PR の駆動セッションは自分のカード（またはそのチケットのカード）を持つので、落ちはしない。
  ボードはカードを保存しない。
- **1 つの PR は 1 つの項目。** PR の同一性は `(provider, 大文字小文字を畳んだキー)`。同じ PR が受信箱の行とリンクの両方、または
  複数のセッションのリンクにあるときは 1 つにまとめる。各事実は最も新しい観測（`observedAt`、または行の取得時刻）から取り、
  `merged` は終端で古い `open` に勝ち、片方のソースしか持たない事実（キャッシュの checks、Agent のレビュー判定）はそのソース
  から取り、既定値で埋めない。同じ PR を 2 つの開いた PR として数えない。
  導いた判定は、その元の事実より長生きしない。リンクの `ready` は、その PR の最も新しい観測であるあいだだけ使う。より新しい受信箱の
  観測（checks や mergeable）がそれを退け、その観測が緑でも退いたままで、より新しい Agent の観測が新しい判定をくれるまで戻らない。
  受信箱の行にはレビューの判定がなく、Console は `ready` を計算し直してはならないからである。有効な判定がなければ、その PR は Ready to merge の条件を
  満たさず、カードは他の事実で表の先頭から判定される。

### 2. レーンはカードの事実の純関数。最初に当たったものが勝つ。

| # | レーン | カードがここに入るとき |
|---|--------|------------------------|
| 1 | **Done** | 開いた PR がなく、かつ次のどれか。チケットをトラッカーが done と言う。マージされた PR があり、生きている駆動セッションも carried のやりとりを持つ駆動セッションもない。カードが PR で、その PR 自身の state が merged |
| 2 | **Needs you** | 駆動するセッションが注意の状態（下）にある。あるいは開いた PR に CI 失敗、changes requested、conflict がある |
| 3 | **Ready to merge** | 開いた PR が 1 つ以上あり、draft がなく、すべてが `ready` |
| 4 | **In review** | draft でない開いた PR がある |
| 5 | **In progress** | アーカイブされていない駆動セッションがある、または開いた draft PR がある |
| 6 | **To do** | 受信箱の行があり、駆動セッションも PR もない |

「開いている」とは、マージも close もされていないことで、draft も、state が一度も観測されていない PR も開いている。PR だけのカード
（決定 1）はその PR 自身の state を取り、マージされた PR は、そのセッションが何をしていても Done になる。

- **注意が PR の状態に勝ち、PR の状態が活動に勝つ**。Issue が求めた順である。理由が要る規則は次のとおり。
  - **トラッカーによる Done は、開いた PR がなくなれば Needs you に勝つ。** トラッカーが done と言い、開いた PR のない
    チケットは、セッションがまだ質問していても Done に残る。開いた PR があれば、ほかのカードと同じく行 2 から 5 で判定する。
    質問はセッション自身のチップとセッション一覧に出る。トラッカーが閉じたレーンを、カードが開き続けてはならない。
  - **マージされた PR だけでは、セッションが生きている間チケットは閉じない。** PR A がマージされ、別のセッションが PR B に
    ついて質問しているチケットは終わっていない。トラッカーはそう言っておらず、生きているセッションはまだ仕事がある。carried のやりとりを残して畳まれた
    セッションも同じ未完の仕事なので、カードを保つ。生きている駆動セッションも carried を持つものもなく、開いた PR もなくマージ
    済みの PR があれば Done である。PR だけのカードにはチケットがなく、PR が
    マージされれば Done である。
  - **不明は良しではない。** 観測のない、draft でない開いた PR は `checks` が空で、空は緑ではない（`branchpr.PR` のコメントが
    すでにそう言う）。`ready` ではないので、上の行に当たらなければ In review に入る。state が一度も観測されていない PR は
    開いているものとして数える。これは、決定 4 と 5 が取り除く既知の古さである。
- **注意とは何か**はここに並べない。セッションは、`stateInfo()` が `question` の色のクラスを与え、かつ `limited` でない
  とき注意である。生きていれば question、plan、permission、blocked、auth、spend limit、input not delivered を含み、止まって
  いれば carried のやりとりを含む。作業フォルダが消えたセッションは含まない。`stateInfo` はそれを dead と示し、答えられない。この除外が効くのは、一覧がそう言う場合（生きている一覧の
  `resumable: false`）だけである。止まっているミラーはフォルダが残っているかを知らず、そのセッションを再開可能として配る
  （`workspace_handlers.go:1143-1214`）ので、止まった Workspace ではまだ Needs you に出ることがある。ボードは共有ヘルパーを呼ぶので、`stateInfo` が変われば追従する。
  `limited`（利用枠のリセット待ち）は誰も必要とせず、In progress に数える。
- **マージされずに閉じた PR** はカードの PR の集合から外れ、カードは残りの事実で、表の先頭から判定し直される。ほかに何もない
  PR だけのカードは消える（決定 1）。
- **トラッカーの状態。** トラッカーの done は、ADR 0061 決定 9.5 が固定した、プロバイダーに依らない状態（Jira ではステータスの
  名前ではなく*カテゴリ*）から読み、チケットや issue にだけ使う。受信箱にない項目のトラッカー状態は分からず、不明は done では
  ない。受信箱の*プルリクエスト*の行は次のように読む。`open` は開いた PR、`in_progress` は draft、`done` は終わったことだけを
  意味し、マージされたかは分からない（事実 5）ので、Done の証拠にならない。PR だけのカードが Done になるのは、セッションの
  リンクが `merged` と言うときだけで、そのようなリンクのない終わった PR の行はカードを持たない。
- **受信箱の PR も事実を供給する。** セッションのない、受信箱の行だけの開いた PR は、checks と mergeable をキャッシュから取る
  （事実 3）ので、レビュー依頼の CI の失敗は Needs you に入り、どれもない開いた PR は In review に入る。そこにはレビューの判定が
  ないので、キャッシュだけから `ready` になることはない。
- **レーンは保存された値ではない。** `lane` 列も、カードごとの上書きも、履歴もない。読むたびに計算し直すことで、セッションや
  PR と食い違わないようにする。

### 3. 導出は Console で、すでに持っているデータから、1 つの関数で行う。

`laneOf(card)` は Console の純関数で、入力はセッション一覧（生きていれば Agent から、止まっていればミラーから。どちらもリンク付き）と
受信箱の行である。注意の判定は `stateInfo()` と同じ分類を小さな共有ヘルパー経由で呼ぶので、ボードと一覧が同じセッションを違う
名前で呼ぶことはない（ADR 0078 決定 5）。新しいエンドポイントも、CP 側での導出もない。

CP は、いまのところ自分ではレーンを導けない。活動を持っておらず（事実 2）、持たせると状態が変わるたびにミラーを書くことになる。
そのコストが買うのはテナント概観（#3136）で、いまメンバーが必要とするものではない。#3136 がサーバー側のレーンを要するように
なったら、関数のコードではなく規則を再利用できる。

### 4. PR の事実がリンクに届かなければならない。これが唯一の構築上の依存である。

レーン 2・3・4 は、PR リンクごとに、事実 3 と 4 が欠けていると示したものを必要とする。Agent の通信上の PR リンクに、小さな事実の
オブジェクトを足す。`checks`（`success` | `failure` | `pending` | 空）、`changesRequested`、`conflict`、`ready`、`observedAt`。
それを `session_work_link` に、既定値つきの追加列としてミラーする（#5052）。

- **`ready` は Agent 自身の `PR.Ready()` の判定**で、真偽値として送る。Console が checks、レビュー、mergeable から作り直して
  はならない。それは「マージできる」の 2 つ目の定義であり、1 つ目は Agent がすでに `pr.ready` 通知とマージのライフサイクルに
  使っている。
- **列挙値とタイムスタンプだけ。** チェック名、スレッドの本文、レビュアー名は含めない（ADR 0061 決定 2）。失敗したチェックの
  *名前*は、`branchpr.PR` が保つとおりリンクと一覧には載せない。PR フィードバック通知は、宛先のセッションにはそれを届ける。
- マイグレーションは既定値つきの列を足すだけで、何も落とさず書き換えない。0119 と同じように出せる。

### 5. 保持している PR を観測することと、それを通知することは別にする。

いまは 1 つのスイッチが両方を握っている（事実 4）。分ける（#5053）。保持している PR リンクを番号で読むのは、Workspace が動いて
いる間は常に、駆動する PR リンクを持つセッションについて行い、PR フィードバックの tick がすでに持つ上限
（`prFeedbackMaxLinks`、キャッシュの TTL）の下で動かす。通知の差し込みはオプトインのままにする。これがないと、ボードはマージ
済みの PR を In review と見せる。

tick がいましている観測には、ボードが許せない穴が 2 つある（`pr_feedback.go:168-189`）。1 つは、セッションごとに、ロールと
新しさの順で最初の `prFeedbackMaxLinks` 件のリンクしか見ないこと。最初の 5 件が開いている間、6 件目は一度も読まれない。もう 1 つは、
リンクが `merged` か `closed` になるとそれを飛ばすこと。閉じてから再オープンされた PR は、二度と読まれない。したがって観測は、上限の
中でリンクを回し、順は最後の*成功*ではなく最後に*試みた*時刻で決めなければならない。読み取りが失敗し続けるリンク（権限を失った
など）が先頭を占め続けないためである。また `closed` のリンクをゆっくり読み直す（`merged` は終端）。#5053 が両方を担う。

コストは、セッションごとにその上限で、PR ごとにキャッシュの TTL で、押さえられる。常に動かすか、ボードを開いた後だけにするかは
未決の問い 4 である。ここでは、Workspace が止まっている間は何も読まない（ADR 0055）。決定 6 を見よ。

### 6. 止まっている Workspace も同じボードを描き、いつの話かを添える。

ミラーはリンク、リンクの state、`carried` をくれる。決定 4 の事実は `observedAt` 時点の PR の状態をくれる。受信箱キャッシュは、
取得時点の To do とトラッカーの状態をくれる。

- どのカードも **「as of hh:mm」** を示す。カードをそのレーンに置いた事実のうち、最も古い時刻である。リンクの事実は
  `observedAt`、受信箱の行の事実はその行の取得時刻で、CP は行ごとに持つがレールは見せず（集約を 1 つ描く）、ボードには CP が
  行ごとに配ることが要る（#5054）。これは ADR 0061 決定 1 の「各行が最後の取得時刻を持つ」を、カード単位にした規則である。
  どの事実にも時刻がなければ何も出さず、作った時刻は決して出さない（ADR 0078 決定 11）。
- *セッション*由来の注意は、止まっている間は `carried` だけ。決定 2 の作業フォルダ消失の除外は、ミラーが見分けられないので
  効かない。Workspace が止まったとき作業中だったセッションは止まっているので、表の上の行に当たらなければ、そのカードは
  Needs you ではなく、止まったチップ付きの In progress になる。*PR* 由来の注意は残り、最後に記録した PR の
  事実が `observedAt` つきで効く。止まる前にキャッシュやリンクが CI の失敗を記録していたカードは、いまも Needs you にあり、
  いつ時点かを添える。
- **経過時間はカードの並びもレーンも決めない。** 示すだけで、使わない。

### 7. 操作は既存のものを使う。ボードは書き込みを足さない。

To do のカードからセッションを始める（ADR 0061 決定 20 の起動）。セッションをボードの横で開く（ADR 0078 決定 3）。PR を開く
（決定 24.1）。リンクとリンク解除（#3134 の Console の経路）。Ready to merge のカードでは、詳細モーダルの人が確認するマージ
ボタン（2026-10-25 の注記）。レーンとボタンは同じ判定ではない。`ready` は通知とレーンが使う Agent の近似で、
モーダルはさらに、ベースより遅れている PR では Merge を無効にし、メンバーの権限も確かめる
（`console/src/features/workitems/read.ts:323-379`）。したがって Ready to merge のカードが、Merge ボタンが理由つきで無効のモーダルや、ボタンのないモーダルを開くことがある
（権限がない、head のコミットがない、許可されたマージ方式がないときは、ボタンも理由も出ない）。どちらもモーダルがすでに決めている。

- **ドラッグはない。** レーンは導かれるので、カードは動かせない。動かしても、それを保持するものがない。
- **トラッカーへの書き戻しはない。** セッションを始めても Jira のチケットは In Progress に動かず、レーンが変わっても何も書かない。
  ADR 0061 決定 6 は有効で、どんな書き込みも明示的に、操作ごとに行い、エージェントからは届かない。遷移ボタンが要るなら、それ自身の
  ADR にする。

### 8. 置き場所: セッション概観の 2 つ目のビュー。新しいペイン種別ではない。

概観ペイン（ADR 0078）はすでに、カード、`stateInfo`、セッションメニュー、それを開く画面上の 2 つのボタンを持つ。ボードはそのヘッダーにある
*グループ化*の選択で、リポジトリ（いまの形）かレーンかを選ぶ。ワークアイテムのカードは別のカードだが、チップ、メニュー、横で開く
ふるまいを再利用する。ADR 0049 決定 4 は PaneKind を軽々しく作るなと言い、ADR 0078 はその例外を論じる必要があった。こちらには
その論拠がない。別案は未決の問い 2 である。

### 9. まず個人。テナントのビューは自分の規則を保つ。

ボードが見せるのは 1 人のメンバー自身の Workspace、セッション、受信箱である。メンバーをまたぐものはない。#3136 が ADR 0111 の
オプトインでサーバー側で絞る規則の下でテナント概観を持ち、レーンの規則（決定 3）は再利用できるが、このビューは再利用しない。

## 段階

どの段階も、単独で `main` をリリース可能に保つ。

1. **P1 — 事実（#5052、#5053）。** 追加のみの通信と列。観測の分離。見える変化は、セッション行のリンクの state が正しいままに
   なることだけ。
2. **P2 — 関数（#5054 の前半）。** `laneOf` とカードの組み立て。表のすべての行と各優先規則を覆うフィクスチャでテストする。
   UI からは届かない。
3. **P3 — ビュー（#5054 の後半）。** レーンでグループ化するビュー、「as of」の時刻、決定 7 の操作。

## 未決の問い

オーナーのもので、#5051 に集めてある。どれも上に推奨がある。

1. **#1086 を畳むか。** 状態が変わると消える手動の上書き付きのセッションのレーンは、保存されたピンと、それが置き換えたレーンを
   要る。決定 2 の逆である。推奨: #1086 をこの調査に畳んで閉じ、チケットのないセッションが要るなら、あとでセッションだけの
   上書きを足す。
2. **2 つ目のビューか、独自のペインか**（決定 8）。
3. **`watching` と `reviewing` はカードを動かすか**（決定 1）。推奨: 動かさない。別案は、`reviewing` がレビュー対象の PR の
   カードにだけ数えられること。
4. **常に観測するか、ボードを一度開いた後だけか**（決定 5）。
5. **止まったままのセッション。** 止まっていてアーカイブされていないセッションは、ADR 0097 の保持がアーカイブするまで、そのカードを
   In progress に保つ。数か月前に止めたセッションがカードを占める。
   逆の誤りも表の中にある。carried のない止まったセッションは終わったものと区別できないので、唯一の PR がマージされたチケットは、
   そのセッションが次の PR を開く前に止めただけでも Done と読まれる。正確な信号はトラッカー自身の done で、Done のカードには
   セッションの止まったチップが残るので、メンバーには見える。この ADR は閾値を足さない。データなしに選んだ数字が、メンバーに
   見えるものを決めてしまうからである。P3 の後に実際のボードを見て決める。
6. **トラッカーへの書き戻しはしない**（決定 7）。レーンが変わっても何もトラッカーに書かないことを確かめる。

## 既知の限界

- **種別の分からないリンク。** 起動から作られる `started` のリンクは URL も種別も持たず、PR のブランチが観測されるまで state が
  空なので、Agent は同じ形の PR のキーと issue のキーを見分けられない（`links.go:49-59`、`pr_feedback.go:146-176`）。ボードは
  そのリンクを、PR ではなく名指した項目として扱い、番号による観測にも入らない。いまのツリーより悪くはなく、#5062 が種別を記録
  する。
- **計測していない。** 上のコストと古さについての主張は、すべてコードから読んだものである。

## 採らなかった案

- **カンバンのように、ドラッグできる保存されたレーン。** 保存されたレーンは、要約しているセッションや PR とずれる。ADR 0078
  決定 11 はすでに、誰も保証できない値を出すより何も出さないことを選んだ。さらに、人の移動が観測された事実に負ける場面の規則が
  要り、それは #1086 の上書きの問題に戻る。
- **CP で導く。** 状態が変わるたびに活動をミラーする必要がある（決定 3）。#3136 で見直す。
- **Console で「ready」を作り直す。** checks、レビュー、mergeable から。`PR.Ready()` からずれていく 2 つ目の定義になる（決定 4）。
- **セッションごとのカードに、項目をチップで添える。** それがいまの概観（ADR 0078）である。3 つのセッションと 2 つの PR を持つ
  チケットがレビュー待ちだとは言えない。
- **PR ごとのカード。** PR がまだないチケットはカードを持たず、To do が成り立たない。
- **`work_item_session` からカードを作る。** 記録するのは Console の起動だけ（事実 6）なので、セッションが開いた PR や子の見張りが
  抜ける。ADR 0061 決定 9 の二重起動の防止として残る。
- **レーンをトラッカーに書き戻す。** 決定 7。

## 影響

- レーンは、読むたびに同じ入力から計算するので、セッションのチップや PR のバッジと常に一致する。鮮度は最後の観測までで、そう
  表示する。
- P1 が出るまで、ボードは既知の形で間違う。決定 4 と 5 がないと、セッションのブランチを離れた PR は、マージ後も In review の
  ままになる。P3 は P1 より先に出してはならない。
- レーンを足すことは、1 つの関数と 1 つの表を直すことである。
- セッション一覧のリンクごとに、列挙値とタイムスタンプに限った項目がいくつか増えて載る。
