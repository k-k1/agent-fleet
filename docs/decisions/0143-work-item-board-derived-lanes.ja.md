## 背景

メンバーの仕事はチケットとセッションとプルリクエストで、Console はそれを 3 か所に分けて見せている。ワークアイテムの
レール（ADR 0061）、セッション一覧と概観（ADR 0078）、セッション行の PR バッジである。「このチケットはレビュー待ち」
「このチケットのセッションはあなたを待っている」と言う場所はない。ボードに要る 2 つの入力は、その後 #3134 と #3129 で
入った。いまのツリーにあるものと足りないものは次のとおり。

1. **リンクはあり、ミラーされている。** セッションはロール付きのリンクをいくつも持つ（`started`、`created`、
   `working`、`reviewing`、`watching`。`workspace/agent/internal/session/links.go:21-25`）。CP はそれを
   `session_work_link`（SQLite 0118/0119、Postgres 0103/0104）にミラーするので、Workspace が止まっていても読める。
2. **ミラーは活動を持たない。** `SessionRow` が持つのは `State`（`running` | `stopped`）と `Carried`（セッションを畳んだ
   とき答えを待っていたやりとり。`control-plane/internal/store/store_session_index.go:11-19`）だけである。working、
   question、plan、permission、blocked は生きている Agent の一覧にしかなく、Console の `stateInfo()`
   （`console/src/lib/sessionview.ts:149`）が分類する。ADR 0078 決定 5 が、二重に導いてはならないとした唯一の導出である。
3. **リンクが持つ PR の情報は state だけ。** `WorkItemLink.State` は `open`、`draft`、`merged`、`closed`。CI、
   changes-requested、conflict が通信に乗るのは、セッションの*現在のブランチ*の PR（`branchpr.PR` の
   `ChangesRequested`/`Conflict`、`branchpr.go:59-60`）だけである。`Ready()`（`branchpr.go:118`）、`ReviewDecision`、
   `Mergeable` は `json:"-"` で、「マージできる」を決める判定は Agent から出ない。
4. **スイッチが入っていない限り、セッションが離れた PR は二度と読まれない。** Agent がリンクの PR の state を読むのは
   「セッションがそのブランチにいる間だけ」（`links.go:57`）。保持している PR リンクを番号で読むコードは PR フィードバックの
   tick だけで、PR フィードバックが切れていると最初に return する（`sessionx/pr_feedback.go:503-510`）。切れているのが
   既定である。マージされた PR は、リンク上で永久に `open` のままになる。
5. **受信箱は、止まっている間は古く、既定では done を含まない。** CP は「最後に取得した時刻」付きでキャッシュを描く
   （ADR 0061 決定 1・15）。既定のクエリは「自分に割り当て、かつ done でない」（決定 8）なので、トラッカーで done になった
   項目はキャッシュから消える。`Done` はキャッシュだけからは読めない。
6. **台帳は 2 つある。** `work_item_session` を書くのは Console の起動だけ（ADR 0061 決定 9）。`session_work_link` は
   Agent があらゆるロールで書く。セッションが開いた PR や、チケットを見張る子が見えるのは後者だけである。

問いは、カードとレーンをどう定義すれば、それが情報源に従うか。そして、情報源が十分に語るために何を足さなければならないか。

## 決定

### 1. カードは 1 つのワークアイテム。セッションと PR はリンクを通してそれに付く。

- **同一性**は `(provider, 大文字小文字を畳んだキー)`。`session_work_link` が使う畳み方と同じ。
- **付き方。** セッションは、*駆動ロール*（`started`、`working`、`created`）で持つ、PR ではない項目のリンクすべてに付く。
  そのセッションの PR リンクも同じカードに付く。駆動する項目リンクを持たないセッションの PR リンクは、それ自身がカードになる
  （受信箱の PR 行、チケットなしで開いた PR）。`watching` と `reviewing` のリンクはセッションをカードに付けない。名指した
  項目のカードにチップとして出るだけで、レーンは動かさない（未決の問い 3）。
- **孤児。** 駆動リンクを持たないセッションは、それ自身がカードで、キーは Workspace とセッション名。
- **カードが存在する**のは、次のどれかが成り立つとき。受信箱の行、駆動するセッション、PR リンク。そのどれにも当たらない項目への
  `watching` リンクはカードを作らない。ボードはカードを保存しない。

### 2. レーンはカードの事実の純関数。最初に当たったものが勝つ。

| # | レーン | カードがここに入るとき |
|---|--------|------------------------|
| 1 | **Done** | 開いた PR がなく、かつ（マージされた PR がある、またはトラッカーが done と言う） |
| 2 | **Needs you** | 駆動するセッションが question、plan、permission、blocked で生きている、または carried のやりとりを残して止まっている。あるいは開いた PR に CI 失敗、changes requested、conflict がある |
| 3 | **Ready to merge** | 開いた PR が 1 つ以上あり、draft がなく、すべてが `ready` |
| 4 | **In review** | draft でない開いた PR がある |
| 5 | **In progress** | アーカイブされていない駆動セッションがある、または開いた draft PR がある |
| 6 | **To do** | 受信箱の行があり、駆動セッションも PR もない |

- **注意が PR の状態に勝ち、PR の状態が活動に勝つ**。Issue が求めた順である。理由が要る規則は 2 つ。
  - **Done は Needs you に勝つ。** マージ済みのカードで、セッションがまだ質問していても、Done に残る。質問はセッション自身の
    チップとセッション一覧に出る。トラッカーが閉じたレーンを、マージ済みのカードが開き続けてはならない。
  - **不明は良しではない。** 観測のない PR は `checks` が空で、空は緑ではない（`branchpr.PR` のコメントがすでにそう言う）。
    `ready` ではないので In review に入る。
- **`limited` は注意ではない。** 利用枠のリセットを待つセッションは誰も必要としない。In progress に数える。`blocked` は
  `stateInfo` が言うとおり注意である。
- **マージされずに閉じた PR** はカードの PR の集合から外れ、カードは他の事実で In progress か To do に落ちる。
- **トラッカーの状態。** トラッカーの done は、ADR 0061 決定 9.5 が固定した、プロバイダーに依らない状態（Jira ではステータスの
  名前ではなく*カテゴリ*）から読む。受信箱にない項目のトラッカー状態は分からず、不明は done ではない。
- **レーンは保存された値ではない。** `lane` 列も、カードごとの上書きも、履歴もない。読むたびに計算し直すことで、セッションや
  PR と食い違わないようにする。

### 3. 導出は Console で、すでに持っているデータから、1 つの関数で行う。

`laneOf(card)` は Console の純関数で、入力はセッション一覧（生きていれば Agent から、止まっていればミラーから。どちらもリンク付き）と
受信箱の行である。注意の判定は `stateInfo()` と同じ分類を小さな共有ヘルパー経由で呼ぶので、ボードと一覧が同じセッションを違う
名前で呼ぶことはない（ADR 0078 決定 5）。新しいエンドポイントも、CP 側での導出もない。

CP は、いまのところ自分ではレーンを導けない。活動を持っておらず（事実 2）、持たせると状態が変わるたびにミラーを書くことになる。
そのコストが買うのはテナント概観（#3136）で、いまメンバーが必要とするものではない。#3136 がサーバー側のレーンを要するように
なったら、関数のコードではなく規則を再利用できる。

### 4. PR の事実がリンクに届かなければならない。これが唯一の構築上の依存である。

レーン 2・3・4 は、PR リンクごとに、事実 3 と 4 が欠けていると示したものを必要とする。Agent の通信上の PR リンクに、小さな事実の
オブジェクトを足す。`checks`（`success` | `failure` | `pending` | 空）、`changesRequested`、`conflict`、`ready`、`observedAt`。
それを `session_work_link` に、既定値つきの追加列としてミラーする（#5052）。

- **`ready` は Agent 自身の `PR.Ready()` の判定**で、真偽値として送る。Console が checks、レビュー、mergeable から作り直して
  はならない。それは「マージできる」の 2 つ目の定義であり、1 つ目は Agent がすでに `pr.ready` 通知とマージのライフサイクルに
  使っている。
- **列挙値とタイムスタンプだけ。** チェック名、スレッドの本文、レビュアー名は含めない（ADR 0061 決定 2）。失敗したチェックの
  *名前*は、`branchpr.PR` が保つとおり Agent の内に残る。
- マイグレーションは既定値つきの列を足すだけで、何も落とさず書き換えない。0119 と同じように出せる。

### 5. 保持している PR を観測することと、それを通知することは別にする。

いまは 1 つのスイッチが両方を握っている（事実 4）。分ける（#5053）。保持している PR リンクを番号で読むのは、Workspace が動いて
いる間は常に、駆動する PR リンクを持つセッションについて行い、PR フィードバックの tick がすでに持つ上限
（`prFeedbackMaxLinks`、キャッシュの TTL）の下で動かす。通知の差し込みはオプトインのままにする。これがないと、ボードはマージ
済みの PR を In review と見せる。

コストは、セッションごとにその上限で、PR ごとにキャッシュの TTL で、押さえられる。常に動かすか、ボードを開いた後だけにするかは
未決の問い 4 である。ここでは、Workspace が止まっている間は何も読まない（ADR 0055）。決定 6 を見よ。

### 6. 止まっている Workspace も同じボードを描き、いつの話かを添える。

ミラーはリンク、リンクの state、`carried` をくれる。決定 4 の事実は `observedAt` 時点の PR の状態をくれる。受信箱キャッシュは、
取得時点の To do とトラッカーの状態をくれる。

- どのカードも **「as of hh:mm」** を示す。カードをそのレーンに置いた事実のうち、最も古い `observedAt` である（ADR 0061 決定 1 の
  「各行が最後の取得時刻を持つ」と同じ規則）。どの事実にも時刻がなければ何も出さず、作った時刻は決して出さない
  （ADR 0078 決定 11）。
- 止まっている間の注意は `carried` だけ。Workspace が止まったとき作業中だったセッションは止まっているので、そのカードは
  Needs you ではなく、止まったチップ付きの In progress になる。
- **経過時間はカードの並びもレーンも決めない。** 示すだけで、使わない。

### 7. 操作は既存のものを使う。ボードは書き込みを足さない。

To do のカードからセッションを始める（ADR 0061 決定 20 の起動）。セッションをボードの横で開く（ADR 0078 決定 3）。PR を開く
（決定 24.1）。リンクとリンク解除（#3134 の Console の経路）。Ready to merge のカードでは、詳細モーダルの人が確認するマージ
ボタン（2026-10-25 の注記）。

- **ドラッグはない。** レーンは導かれるので、カードは動かせない。動かしても、それを保持するものがない。
- **トラッカーへの書き戻しはない。** セッションを始めても Jira のチケットは In Progress に動かず、レーンが変わっても何も書かない。
  ADR 0061 決定 6 は有効で、どんな書き込みも明示的に、操作ごとに行い、エージェントからは届かない。遷移ボタンが要るなら、それ自身の
  ADR にする。

### 8. 置き場所: セッション概観の 2 つ目のビュー。新しいペイン種別ではない。

概観ペイン（ADR 0078）はすでに、カード、`stateInfo`、セッションメニュー、2 つの入口を持つ。ボードはそのヘッダーにある
*グループ化*の選択で、リポジトリ（いまの形）かレーンかを選ぶ。ワークアイテムのカードは別のカードだが、チップ、メニュー、横で開く
ふるまいを再利用する。ADR 0049 決定 4 は PaneKind を軽々しく作るなと言い、ADR 0078 はその例外を論じる必要があった。こちらには
その論拠がない。別案は未決の問い 2 である。

### 9. まず個人。テナントのビューは自分の規則を保つ。

ボードが見せるのは 1 人のメンバー自身の Workspace、セッション、受信箱である。メンバーをまたぐものはない。#3136 が ADR 0111 の
オプトインでサーバー側で絞る規則の下でテナント概観を持ち、レーンの規則（決定 3）は再利用できるが、このビューは再利用しない。

## 段階

どの段階も、単独で `main` をリリース可能に保つ。

1. **P1 — 事実（#5052、#5053）。** 追加のみの通信と列。観測の分離。見える変化は、セッション行のリンクの state が正しいままに
   なることだけ。
2. **P2 — 関数（#5054 の前半）。** `laneOf` とカードの組み立て。表のすべての行と各優先規則を覆うフィクスチャでテストする。
   UI からは届かない。
3. **P3 — ビュー（#5054 の後半）。** レーンでグループ化するビュー、「as of」の時刻、決定 7 の操作。

## 未決の問い

オーナーのもので、#5051 に集めてある。どれも上に推奨がある。

1. **#1086 を畳むか。** 状態が変わると消える手動の上書き付きのセッションのレーンは、保存されたピンと、それが置き換えたレーンを
   要る。決定 2 の逆である。推奨: #1086 をこの調査に畳んで閉じ、チケットのないセッションが要るなら、あとでセッションだけの
   上書きを足す。
2. **2 つ目のビューか、独自のペインか**（決定 8）。
3. **`watching` と `reviewing` はカードを動かすか**（決定 1）。推奨: 動かさない。別案は、`reviewing` がレビュー対象の PR の
   カードにだけ数えられること。
4. **常に観測するか、ボードを一度開いた後だけか**（決定 5）。
5. **止まったままのセッション。** 止まっていてアーカイブされていないセッションは、ADR 0097 の保持がアーカイブするまで、そのカードを
   In progress に保つ。数か月前に止めたセッションがカードを占める。この ADR は閾値を足さない。データなしに選んだ数字が、メンバーに
   見えるものを決めてしまうからである。P3 の後に実際のボードを見て決める。

## 採らなかった案

- **カンバンのように、ドラッグできる保存されたレーン。** 保存されたレーンは、要約しているセッションや PR とずれる。ADR 0078
  決定 11 はすでに、誰も保証できない値を出すより何も出さないことを選んだ。さらに、人の移動が観測された事実に負ける場面の規則が
  要り、それは #1086 の上書きの問題に戻る。
- **CP で導く。** 状態が変わるたびに活動をミラーする必要がある（決定 3）。#3136 で見直す。
- **Console で「ready」を作り直す。** checks、レビュー、mergeable から。`PR.Ready()` からずれていく 2 つ目の定義になる（決定 4）。
- **セッションごとのカードに、項目をチップで添える。** それがいまの概観（ADR 0078）である。3 つのセッションと 2 つの PR を持つ
  チケットがレビュー待ちだとは言えない。
- **PR ごとのカード。** PR がまだないチケットはカードを持たず、To do が成り立たない。
- **`work_item_session` からカードを作る。** 記録するのは Console の起動だけ（事実 6）なので、セッションが開いた PR や子の見張りが
  抜ける。ADR 0061 決定 9 の二重起動の防止として残る。
- **レーンをトラッカーに書き戻す。** 決定 7。

## 影響

- レーンは、読むたびに同じ入力から計算するので、セッションのチップや PR のバッジと常に一致する。鮮度は最後の観測までで、そう
  表示する。
- P1 が出るまで、ボードは既知の形で間違う。決定 4 と 5 がないと、セッションのブランチを離れた PR は、マージ後も In review の
  ままになる。P3 は P1 より先に出してはならない。
- レーンを足すことは、1 つの関数と 1 つの表を直すことである。
- セッション一覧のリンクごとに、列挙値とタイムスタンプに限った項目がいくつか増えて載る。
