## Context

### 前提が変わった

ADR 0072 は「diffusion model・text encoder・VAE が何かを知っていて、ファイルがどれかを自分で
言える運用者」向けに書かれた。この配備の利用者は 2026-09-15、4 日で 4 回直した後にこう言った。

> 満足に使えていない。場当たり的な対応ではなく、設計や、モーダルも含めて根本的に見直したい。
> （画像生成の理解が乏しい）利用者が、疑問に思わず、検索しすぐに取り込み使える機能にしたい。

「検索して、取り込んで、使う。疑問が湧かないように」。これが要件で、以下の決定はすべてこれで
測る。0072 の取り込みフォームの「運用者が全部宣言する」形が、置き換えられる対象である。

### 何が順に壊れ、なぜ直すたびに次の壁が出たか

| PR | 直したこと | その裏にあった壁 |
|---|---|---|
| #684 | 分割ファミリー（anima / krea2）を 1 回で取り込む。既存行はワンプッシュで補完 | 本体がまだ「チェックポイント（単一）」＝分割ファミリーのテンプレートが読まない役割だった |
| #688 | キーは `<役割 dir>/<ベース名>` でないと ComfyUI のローダーが一覧しない。既存行は `MODE=move` で修復。Console はキーを平らに合成、CP はそれ以外を拒否 | `reuse_s3_key` が**旧キー**を運ぶので、HF からの取り直しが 400 `s3Key must be empty or identical`（`engine_admin.go:1892`） |
| #690 | ingest タスク定義をファミリー名で指す。CP はテーブル再読込のたびに ingest ブロックを採り直す | 失敗した 3 回の押下がジョブ行を書き、宛先 3 キーを押さえていた |
| #691 | タスクを得ずに `failed` したジョブは押さえ手でない | （執筆時点で open） |

さらに 2026-09-15 に af-sandbox で実測し、どの PR も扱っていないこと 2 つ。

1. **ジョブ履歴の「この鍵で登録する」は目に見える何も起こさない。** `onReuse`
   （`adminEngineAdd.tsx:632`）は手動フォームにプレフィルするだけで、そのフォームはジョブ一覧より
   **上**の閉じた `<details>`（`adminEngineAdd.tsx:626`）の中にある。開きもスクロールもしない。
2. **行を消した後に戻る道が無かった。** 運用者は両ファミリーで 登録を消す を押した。バイト列は残った
   （誤った鍵に 4.18 GB と 13.1 GB、部品は誤った鍵と正しい鍵の両方に。合計約 24 GB、すべて
   HeadObject で `present`）。バイト列を動かす唯一の修復 `engineMainFileFixFor`
   （`engine_file_move.go:52`）は**行から**計算される。行が無ければ修復も無い。手動の道は
   「失敗ジョブ 3 件を忘れる（これが Console から届いておらず、API を直接 `DELETE` すると 200
   だった）→ 旧ジョブと**同じ id** で、**わざと誤った鍵**を指す行を登録する（`engineKnownArtifacts`
   （`engine_storage.go:206`）が done ジョブの `model_id` を押さえ手に数えるので、別 id だと移設が
   "also declared by" で拒否される）→ 揃える を押す」。誰にも見つけられない。

### 根が 3 つ

上の壁はすべてこの 3 つのどれかで、症状ごとに直したから直すたびに次が出た。

1. **宛先キーを決める主体が 3 つ。** Console が合成し（`adminEngineAdd.tsx:994`、
   `engineIngestPrefix`＋ベース名）、CP が再計算して不一致を拒否し（`postIngest` の
   `engineComfyKeyFor` 検査）、検証済み再利用が第 3 の鍵＝以前のジョブが記録した鍵を持ち込んで
   `s3Key` に一致を要求する。鍵は `(役割, フラグ, ベース名)` の純関数（`engine_catalog.go:290`）。
   計算する主体は 1 つで、それは検査もする側であるべき。
2. **CP にバイト列の台帳が無い。** `GET …/storage` は「サーバが既に知っている鍵だけ返す」
   （`engine_storage.go:302`）＝行とジョブが名指す鍵への HeadObject の扇状問合せ。行とジョブを
   忘れると、オブジェクトは課金され続けるのに Console からは存在しなくなる。ジョブを忘れる前の
   確認文（`admin.engines_ingest_job_forget_last`）はまさにそう言っている。一方 CP のタスクロールは
   prefix 条件 `llm/*`, `image/*` 付きの `s3:ListBucket` を**既に持っている**
   （`60-engines.yaml:299-304`）。隣の注記「the CP has no list operation」はコードの話であって
   権限の話ではない。
3. **修復が行の属性にぶら下がる。** `files_missing`・`main_file_fix`・`vae_missing` は行ごとに
   計算され、救済ルートはすべて行 id を取る。S3 Bucket 側の見方＝「このオブジェクトはローダーが
   一覧しないディレクトリにある」は表現できず、孤児オブジェクトにボタンは無い。

これに語彙が乗る。バイト列を行に入れる道が 6 つ（new / attach / replace＝1 要求の 3 モード、
検証済み再利用＝同じ要求の中で自動、揃える＝部品＋移設、手動 S3 登録＋ジョブからのプレフィル）。
画面の操作は 8 つ、ja カタログの `admin.catalog_*` / `admin.engines_ingest_*` /
`admin.engines_model_*` は 214 本。運用者の壁は毎回「別の道に落ちた」形をしていた。

### 正しくて残るもの

- **配置。** `image/<役割 dir>/<ベース名>`、ローダーごとに 1 ディレクトリ、Agent はベース名で
  名指す（`workspace/agent/engines.go:140`）。ここでは事後検査でなく「壊れ得ない」形に組む。
- **二層の真実**（0072 決定 2）。S3 が何があるか、DB が何を提供するか。この ADR は第一層に
  専用ルートを与える。
- **`MODE=move`**（contract 3）。払い済みのバイト列はサーバ側で動かし、二度取らない。
- **`enabled` は人の行為。** S3 Bucket の中身が行を有効にはしない（0072 が却下した「ListObjects から
  カタログを導出」は却下のまま。台帳は列挙するだけで、提供はしない）。
- **ファミリーの語彙と部品表**（`engineComfyRequiredFlags`、`engineFamilyParts`）。ファミリーが何を読むかの知識は
  CP にある。変わるのは「訊く」代わりに「使う」こと。
- **テナントの許可**（`allow_engine_ingest`、0072 未解決 11）。台帳はジョブ一覧と同じ規則で絞る。

## Decision

### 決定 1 — 宛先キーは CP が決める。ワイヤはキーを運ばない

`POST …/ingest` から `s3Key` と `reuse_s3_key` を外す。CP はファイル語彙を持つプロバイダ全部に
ついて `(役割, フラグ, 上流ファイルのベース名)` から `engineComfyKeyFor` で鍵を計算する。
`sdcpp` / `openai-compat` の行は変わらない（`checkpoints/` 直下の 1 ファイル）。#688 で足した
`engineComfyKeyFor` 不一致の拒否は到達不能になり、Console の写しを固定していたテスト
（`contract_engine_keys_test.go`）ごと消す。`engineIngestPrefix` は Console から消える。

再利用は要求のモードではなくなる。台帳（決定 2）が、resolve が今計算した artifact identity と
同じ記録を持つオブジェクトを既に持っているとき、CP が行うことになる:

- 正規の鍵にある → 宣言するだけ。何も落とさない（今日の再利用）
- 別の鍵にあり present → 正規の鍵へ**移設**（今日の `MODE=move`）してから宣言
- 無い → ダウンロード

応答は 3 つのどれが起きたかを言う。`s3Key` が無いので 400 `s3Key must be empty or identical` は
起こり得ない。

### 決定 2 — S3 Bucket が台帳: `GET /api/admin/engines/{key}/objects`

1 本のルートが役割の prefix を `ListObjectsV2` で列挙し（1 ページ 1,000。sandbox の S3 Bucket は
100 未満）、各オブジェクトを DB が知る事実と結合する。**IAM 変更なし**: 権限はある
（`60-engines.yaml:299-304`）。隣の注記は「今は何のためか」に書き換える。CP はオブジェクトの
中身は相変わらず読まない。

各オブジェクトが答えるもの:

| フィールド | 出所 |
|---|---|
| `key`, `bytes`, `last_modified` | S3 |
| `role_dir`（`checkpoints` / `diffusion_models` / `text_encoders` / `vae` / `loras` / `other`） | 鍵のパス。`engineComfyRoleDir` の表を逆引き |
| `placement`: `ok` / `misplaced` | 鍵が `engineComfyKeyFor(役割, role_dir のフラグ, ベース名)` に等しいか。`image/checkpoints/split_files/…` や深さ 2 以上は `misplaced` |
| `declared_by[]` | この鍵を `files[]` に持つ行と、そこで使うフラグ |
| `source`, `artifact_identity`, `license` | この鍵の最新 `done` ジョブ、無ければ宣言する行、無ければ空 |
| `job` | 宛先がこの鍵の最新ジョブが `pending` / `running` / `failed` のとき、そのメッセージ付き |

加えて DB が名指すがオブジェクトが**無い**鍵（今日の `missing`）も同じルートで `state: missing`
として返す。「行が何も無い所を指している」も台帳の事実だから。

`GET …/storage` は 1 リリースだけこの表の射影として残し（登録済みカードのバッジが読む）、
その後消す。

**可視範囲。** super_admin は prefix 全部。`allow_engine_ingest` を許可されたテナント管理者は
自テナントのジョブが作ったか自テナントの行が宣言するオブジェクトだけ（ジョブ一覧が既に
適用している規則、`engine_ingest_perm.go:182`）。S3 Bucket は運用者のもので、許可されたテナントは
自分が置いたものを見る。

### 決定 3 — 操作は 2 つ。どちらもモデルに対して: **取り込む** と **揃える**。部品は主語にならない

運用者がバイト列を行に入れるためにできることは 2 つの要求のどちらかで、どちらもモデル
（チェックポイントの行）から始まる。部品からは始まらない。利用者が理由を 1 行で言った:
部品から宛先を選ぶのは逆で、人が意味するのはチェックポイントであり、それに合う部品は機械が
知っている。

- **取り込む**: `POST …/ingest` — 上流 → オブジェクト → 行、1 押しで（決定 4）。
- **揃える**: `POST …/models/{id}/complete` — 行が主語。CP はファミリーが読むもの・行が持つもの・台帳
  （決定 2）が持つものを見て差を埋める:
  - 欠けている役割のファイルを台帳が正規の鍵に持っている → 宣言、0 バイト
  - 別の鍵にあり present → 移設（`MODE=move`）してから宣言
  - 行自身の本体が誤った鍵にある → 移設（今日の `main_file_fix`。いまや 1 ケースにすぎない）
  - 無い → ファミリーの部品表（`engineFamilyParts`）から取り込む。表の無いファミリーは `unknown` として、
    人がまだ供給すべき役割を名指す
  - **候補。** 欠けている役割について CP はその役割ディレクトリのオブジェクトを順位付けする:
    ファミリーが宣言する部品（artifact identity で一致）が先、次に記録されたファミリーが合う任意のオブジェクト。
    候補が 1 つならその押下で使う。複数なら行の 揃える ダイアログに出す。人が部品を選ぶのは
    ここだけで、**このチェックポイントのために**選ぶ。`{choices: {"--vae": key}}` で運ぶ。
  - 行が既に持つ部品の**差し替え**は同じダイアログの埋まった枠（今日の `replace`）:
    `{choices: {flag: key}, replace: true}`。`replace` 無しの拒否は `next` を運ぶ（決定 5）。
  - 部品オブジェクトは台帳で**自分のボタンを持たない**。その行為は行がそれに対して行うものだけ、
    加えて誰も宣言しないときの削除（決定 7）。

**S3 Bucket に既にあるチェックポイントを登録する**のがオブジェクト側の唯一の操作で、それも
モデルに対する操作である: `POST …/objects/register` `{key, base_model?, id?}`。対象は
`checkpoints/` か `diffusion_models/`（またはそのどちらかを名前に含む誤配置パス）にあって
どの行も宣言しないオブジェクト。CP は決定 4 の計画と同じ方法で `id` と `base_model` を提案し、
行を無効で作り（`license_accepted_by` は空。既にあるバイト列を割り当てるのはライセンス受諾という
人の行為ではない）、誤配置なら正規の鍵へ移し、その新しい行に**揃える**を走らせる。af-sandbox が
2026-09-15 に居た状態（バイト列はある、行は無い）に落ちた配備のための道で、誤配置の本体ごとに
登録 を押せば、台帳が持つエンコーダと VAE は同じ押下で付く。S3 Bucket に無い鍵は拒否する
（HeadObject。CP にはできる）。`POST …/models`（super_admin が行の答えから行を再構築する JSON
往復）は未検証の鍵を受け続ける唯一のルートとして残し、そのフォームは Console から消える。

`attach`・`replace`・`reuse_s3_key` は `POST …/ingest` から消える。`POST …/models/{id}/parts` と
`…/vae` は**揃える**に畳む。揃える ボタンは残り、意味は「このチェックポイントのために台帳が
持つものを宣言し、誤配置を移し、残りを取り込む」になる。

### 決定 4 — 取り込みは 1 押し。その押下が何をするかは CP が決める

`POST …/ingest/resolve`（フォームが見ている間に既に呼んでいる）は、フォーム欄に化ける事実の
集まりでなく**計画**を答える:

```
{ id, base_model, main_flag,
  files: [ {flag, name, bytes, action: "download"|"reuse"|"move", source} … ],
  bytes_to_download, license, license_name, commercial_use,
  gated / login_required（配備のトークン状態つき）,
  warnings: [ … ] }
```

- `id` はファイル名から提案し（`engineIdFromFile`）、カタログに対して接尾辞で一意にする。
  人が編集できるのは 詳細 の中だけ。
- `base_model` は CP の読み（上流のメタデータと名前に対する `engineFamilyGuess`）。CP が言えない
  ときは計画がそう言い、ファミリーセレクタがカードに出る**唯一の**欄になる。候補はプロバイダが知る
  ファミリーだけで、自由記入は無い。
- `main_flag` と `files[]` は `engineFamilyMainFlag` と `engineFamilyParts` から。台帳が既に持つ
  部品は `reuse`（0 バイト）、誤った鍵にあるものは `move`（0 バイト）、残りは `download`。ファミリーの
  VAE は今日 `engine_vae.go` が適用する規則で `files[]` に加わる。
- カードは計画をファイル 1 行ずつ費用つきで示し、ライセンスと商用可否の判定を示し、ボタンは
  1 つ、取り込む。役割セレクタ・鍵欄・部品チェック・attach/replace の選択は無い。フォームの
  詳細 に id・説明・生成の既定値が入る。
- `POST …/ingest` は `{source, plan_token, license_accepted}` を取る。`plan_token` は計画の
  ハッシュ。CP は開始時に再計画し（今日の VAE 読みと同じ規則: フォームの答えは数分古いことが
  あり、これは金を使う呼び出し）、重要な何か（バイト数・ライセンス・押さえられた鍵）が変わって
  いれば新しい計画で拒否する。

部品表の無いファミリー（今日は flux1・sd35・zimage・flux2-klein）は CP が言える所まで計画する: 本体を
正規の鍵へ、部品はファミリーが読む役割つきの `unknown` として列挙し、カードは人が後で供給する役割を
言う。計画はパスを捏造しない（0072 の 2026-09-15 追記: 「記憶で書いた項目は押した数分後の 404」）。

### 決定 5 — すべての拒否は押さえ手と次の操作を名指す

この領域の `apiError` に構造化フィールドを 2 つ足す:

```
{ code, message,
  holder?: { kind: "row"|"job"|"object"|"task", id, key },
  next?:   { act: "register"|"complete"|"replace"|"forget_row"|"dismiss_job"|"wait", target } }
```

`engine_admin.go`・`engine_file_move.go`・`engine_family_parts.go` の 409 は両方を**必ず**運ぶ。
テストが 409 の箇所を列挙し、欠けていれば落ちる。Console は `next` をエラー行のボタンとして
描く。「The S3 key … is already recorded; choose a new destination …」は「03:42 の失敗ジョブが
押さえています — 消す」と、それを行うボタンになる。

### 決定 6 — ジョブはオブジェクトの進行であって、第二の一覧ではない

ジョブ履歴タブは消える。`pending` / `running` のジョブは宛先オブジェクトの `uploading` 状態
（タスクが報告すれば進捗つき）。`failed` はその鍵の `failed` 項目で、タスクのメッセージと操作
1 つ（消す）。`done` はオブジェクトの出所（`source`, `artifact_identity`）であってそれ以上では
ない。もはや「鍵の最後の記録」ではない（S3 Bucket がそう）ので、忘れる前の確認ダイアログも消える。

#691 の規則（`task_arn` の無い `failed` は押さえ手でない）はそのまま残り、押さえ手の定義になる:
**オブジェクトか、オブジェクトを書き得たタスク。**

`ListEngineIngestJobs` の固定上限 20（`engine_ingest_perm.go:183`）はタブと共に消える。台帳は
S3 Bucket のページで区切る。

### 決定 7 — 修復と掃除は台帳から始まるが、ボタンはモデル側にある

- 誤配置の**本体**（`checkpoints/` か `diffusion_models/` を名前に含むパスにあり、どの行も
  宣言しないオブジェクト）は 登録（決定 3 の `register`）を出す。行が宣言している誤配置の本体は
  その行の 揃える が直す。
- 誤配置または孤児の**部品**は割り当てボタンを出さない。それを読むチェックポイントの 揃える が
  付け、移す。それまでは何であるか・誰が（誰も）宣言しているか・消す だけを出す。
- `DELETE …/objects` `{key}` は `MODE=delete` を走らせ（CP に `s3:DeleteObject` は無い、0072
  決定 7）、いずれかの行が鍵を宣言している間は拒否（holder ＝ その行）。
  `DELETE …/models/{id}?purge=1` は残り、同じ操作を行の鍵に適用したもの。
- 行側のマーク（`files_missing`, `vae_missing`, `base_model_missing`）は「なぜこの行は有効に
  できないか」に答えるので残す。`main_file_fix` はワイヤから消える。「誤配置」は台帳の事実で、
  揃える が台帳を読むから。

### 決定 8 — 画面

1 ペイン、2 タブ、ウィザード無し:

- **探す** — 今日と同じ。カードのボタンが計画（決定 4）を開く。1 押し。
- **登録済み** — 行は今日と同じ。それぞれに 有効にする / これで起動する / 揃える / 編集 /
  登録を消す。揃える は選ぶか確認するものがある時だけ開き（役割に候補が複数、支払うダウンロード
  がある）、そうでなければそのまま動く。行の下に**S3 Bucket（台帳）**: 全オブジェクトと状態。誰も
  宣言しない本体は 登録、孤児は 消す、それ以外は何も持たない。孤児と誤配置が先頭に並ぶ。これが
  ジョブ履歴・手動 S3 フォーム・「この鍵で登録する」を置き換える。

操作ダイアログには検索で見つからないモデルのための手入力（owner/repository か URL）が残り、
同じ計画に流れる。

## 却下した案

- **A: 決定 1 だけ**（CP が鍵を決め、再利用が移設になる）。PR 1 本で 400 は直るが、死んだ
  ボタン・行が無ければ修復できない穴・語彙は残る。この ADR の最初の PR であって、止まる場所ではない。
- **C: ジョブ表をいま退役させる**（ジョブをストア上でオブジェクトの属性にする）。正しい終着だが、
  テナント可視性と reconciler のタスク所有を UI 変更と同じリリースで新表に移すことになる。決定 6
  はストア変更なしで画面をそこへ連れて行く。表は次に邪魔になった時に。
- **6 経路を残して文言を良くする。** 決定 5 の構造化拒否はどの経路にも効く。しかし壁は経路が
  あること自体から来ており、素人の利用者は自分がどの経路にいるかを学ぶべきでない。
- **もっと良い表で Console がキーを合成する。** Console は S3 Bucket の中身を知り得ない。鍵の規則は
  すべて S3 Bucket の規則。
- **台帳から `enabled` を導出する。** 却下のまま（0072）。
- **マニフェスト `<file>.json` を書いて読み返す。** 0072 決定 2 が約束したが何も書かない。DB は
  マニフェストが持つはずの全部を既に持っている。S3 Bucket の列挙に随伴ファイルは要らない。

## Open questions

1. **誰が register と complete をできるか。** 今日 `postModel` は super_admin、取り込みは許可
   テナント。`register` は運用者のバイト列から行を作るので草案は super_admin のみ、許可テナントは
   自テナントのジョブが作ったオブジェクトだけ登録可。`complete` は取り込みの許可に従う。P1 前に確定。
2. **`plan_token` か計画の再送か。** ハッシュは小さく偽造できない。再送はデバッグしやすい。
   P1 で「運用者が見るべき差分を隠す」と分かるまではハッシュ。
3. **llm 役割。** 台帳はそのまま適用（`llm/*`、1 ディレクトリ、シャードは `llm/<name>/`）、
   `placement` は常に `ok`。この ADR は llm の挙動を変えない。画面には台帳が加わる。
   🔴 **2026-09-19 に解決。そして「変えない」は半分が間違いだった。** llm プレフィックスを
   一覧するのに特別扱いは要らなかったが、**決定 3 の唯一のオブジェクト側の行為には要った**——
   「登録」が ComfyUI のローダーディレクトリ 2 つという綴りだったため、利用者が報告した
   `llm/` 配下の GGUF 3 本——この配備が金を払っていて、どの行も宣言していないバイト列——には
   「消す」しか出ていなかった。一覧はあるのに行為が無い、というこの ADR が書かれた原因そのものが、
   役割を 1 つずらして再発していた。**モデル自身の重みとは何か**を役割に訊くようにした: image は
   ローダーディレクトリ（深さは問わない）、llm は平ら（`llm/<file>.gguf` だけ。よって
   `llm/loras/…` はアダプタ、`llm/<name>/shard.gguf` はファイルの一片）。押下では同じバイト列から
   GGUF ヘッダも読む（理由は ADR 0074 の追補）。
   🔴 同じ調査で見つかった、より古い欠陥: **「揃える」は役割に関わらず ComfyUI の配置で宛先を
   組み立てていた**ため、llm の行はすべて `llm/checkpoints/…` への移動を計画されていた——
   `llama-server` が決して見ないディレクトリである。直すための押下が、動いている行を止めるところ
   だった。宛先は役割自身の配置（`engineIngestKeyFor`）になった。image では両者は同じ関数である。
4. **2026-09-15 に Console の 履歴を消す が CP に届かなかった理由。** 同じ `DELETE` が curl
   からは 200 だった。未解明。タブは P2 で消えるが、原因が `apiJSON` かペインにあるなら新しい
   ボタンも噛まれる。P2 前に headless で再現する。
