## 背景

同じテナントのメンバー同士がすでにできることは 3 つある。

- セッションを RO / RW で共有する（docs/59）。
- RW なら、所有者が承認してからエージェントに届くプロンプトを提案する。
- セッションを引き継ぎ、受け手が自分のワークスペースで作業を始める（ADR 0057。P0 は実装済みだが、
  2 アカウントでの通し確認はまだ一度もない）。

それ以外の協働は Agent Fleet の外で行われている。

- 同僚に何かを頼んで、それが引き受けられたか、誰が引き受けたか、何になったか（どのセッション、
  どの PR）を確かめる手段が無い。
- すでにセッションを共有していない限り、同僚にすぐ実行できるプロンプトを送れない。
- 同僚が利用上限で止まっていることも、それがいつ解けるかも見えない。
- 2 人のメンバーのエージェントが午後いっぱい同じファイルを編集していても、マージまで誰も気付かない。

既存の仕組みと、その足りないところをコードで確かめた。

- **メモキューは受け手本人のもの。** `POST /api/memos` は呼び出し元の membership に挿入し、
  メモブリッジのトークンもその membership に固定されている（`control-plane/memo.go`、
  `control-plane/memo_bridge.go`）。他メンバーのキューへ挿入する経路は無い。メモには送信者・
  レシピ・出所の欄も無く、本文は平文で保存される。
- **エージェントはメモキューを読む。** `list_memos` はキュー上の全メモをセッションのエージェントに渡す
  （`workspace/agent/internal/mcpx/mcp_stdio.go`）。送信（flush）は本文を連結するので出所が落ちる。
- **CP は稼働中の全ワークスペースから毎分すでに取りに行っている。** idle reaper が稼働中の各 Agent に
  `GET /sessions` を呼ぶ（`agentSessionsEnv`、`control-plane/agent_client.go`）。その封筒には live 状態の
  `limited`（`rateLimitResumeAt` 付き）と `spend_limit` が載っている。一方、通知 outbox が吸い上げられるのは
  Console が問い合わせたときと停止直前だけ（`control-plane/notification.go`、`drainAgentOutbox`）。
  reaper を切ると（`AF_IDLE_SWEEP_INTERVAL=0`）この取得も止まる。
- **利用枠はブラウザ経由でしか CP に届かない。** `console/src/app/usageResetNotify.ts` が観測を送るのは
  Console のタブが開いている間だけ。`notification_usage_state` が持つのは `resets_at` と `armed` で、
  割合も観測時刻も持たない。
- **利用枠の出し方は kind ごとに違う。**
  - claude：最後の statusline 捕捉を返し、リセットを過ぎた窓に `stale` を付ける。
  - codex：`adjustWindow` が過ぎた窓を 0% と次のリセットへ補外し、`stale` は付けない。
  - muse：窓を、その長さと一緒に返す。
  - agy：モデルグループごとの週間枠を返し、読むたびに TUI を起動する。
  - copilot：クレジットプールを返す。
  - 残りの kind：セッションの `limited` / `spend_limit` 状態しか出さない。
- **共有先の検索は名簿ではない。** `GET /api/session-share-recipients` はテナントのメンバーを絞り込み、
  最大 20 件を返す。
- **`GET /api/events` は接続ごとのスナップショット差分送信であり、配送台帳ではない。** 連番も、
  再送カーソルも、受け手ごとの既読も持たない。入口は `withResolved` で、ワークスペースを解決する
  （`control-plane/events.go`）。
- **テナント鍵での封緘は運用者からの秘匿ではない。** RW 提案の本文はテナント鍵カストディアンで包む。
  カストディアンが無ければ base64 で保存するだけ（`control-plane/session_share.go`、`sealProposal`）。
  どちらでも CP は読める。
- **マーカーは所有者のワークスペースに置かれる注釈。** 付け外しは RW だけができ、所有者の
  ワークスペースが止まっている間は届かない（docs/69）。
- **通知センターはすでに対応が要るセッションイベントを運んでいる。** answer-ready・質問・計画の承認・
  権限要求・利用枠のリセット・引き継ぎを、membership ごとに 7 日保持する。

## 決定

### 1. メンバーが送ったものが、別のメンバーのエージェントを動かすことはない

ここにあるどの機能も、あるメンバーの文面を、別のメンバーの明示操作なしにその人のエージェントや
ワークスペースへ届けない。これは ADR 0057 決定 1 をすべてに当てはめたもので、越境するのは文章・git 座標・
読み取り権だけである。ADR 0041 はこの危険を permission laundering と呼んだ。具体的には、受け取ったものに
次のことはさせない。

- 権限・計画・質問への受け手の承認を代わりに果たす。
- 別のメンバーが拒否された作業を代わりに行う。
- 受け手のセッションを統べるもの（権限設定・指示ファイル・MCP 設定・フック・資格情報）を変える。
- 受け手が取り込む前に、受け手のエージェントから見える（決定 3）。

既存の RW 提案は、所有者が承認する段を残す。しばらく RW 提案を自動承認する「ペアモード」は
**採用しない**（決定 13）。

### 2. 中心となる物はチャットのメッセージではなく、依頼

Agent Fleet にしかできないのは、頼みごとを、それが引き起こした作業と結び付けること。CP には
**受信箱の項目**という物を 1 つ置く。中身は送信者、受け手（送信時点で固定した membership の集合）、
本文、作成時刻、型付きの添付で、必要に応じて**依頼としての意味**を持つ。

- 状態は `open → claimed → done`、または `declined` / `withdrawn`。
- **担当は 1 人。** `open → claimed` を「まだ `open` のときだけ」の条件付き更新で取るので、2 人の受け手が
  両方とも着手することはない。
- 結果へのリンクを持つ：その依頼から起動したセッション、そのブランチ、PR。リンクは担当者の Console が
  起動時に書く。エージェントは申告しない。

ただのメッセージ（DM）は、依頼としての意味を持たない受信箱の項目である。レシピ（決定 4）は添付の一種。
未読と未処理は別物で、依頼は読まれたかどうかに関わらず、最終状態に達するまで送り手と受け手の
「未処理」一覧に残る。

### 3. 受信箱は独立した保存先。メモキューへは受け手が明示的に取り込む

受信箱の項目は、受け手ごとの連番と既読カーソルを持つ専用の CP テーブルに置く。メモ API に
宛先を足すことはしない。

- **取り込むまで**、項目はどのエージェントからも見えない。`list_memos` は返さず、flush にも含まれない。
- **レシピを取り込むと**、受け手自身のメモとしてメモキューに複製される。その際、サーバーが
  `origin = {送信者, 項目 ID}` を付ける。Console はバッジを出す。送るときは受け手自身のメモと
  連結せず、出所を保ったまま単独で送る。
- その先はメモキューの既存の経路（編集・セッションへ送る・新規起動）を使う。起動したセッションには
  出所のバッジが付く。

### 4. レシピはリポジトリの識別子を運ぶ。取得はしない

レシピが持つのは、プロンプト、推奨の kind / モデル / effort、そして任意でリポジトリ。

- リポジトリは正規化した識別子（接続済み git プロバイダなら `host/owner/repo`）にする。URL を残す場合は
  userinfo・query・fragment を落とす。正規化できない remote は、そのまま通さずに拒否する。
- 識別子はプロンプト本文とは分けて表示し、受け手が指し先を確かめられるようにする。
- 受け取っただけでは何も fetch も clone もしない。受け手が自分の接続で、自分の作業コピーに対応付ける。
  clone は別の明示操作のまま。
- レシピは RW 提案ではない。受け手のこれからの作業を対象にし、共有を必要としない。

### 5. セッションの添付は、人が与えていない権限を与えない

- **添付によって共有を作れるのは、そのセッションの所有者だけ。** 所有者が、セッション・受け手全員・範囲
  （後から追記される分も含めた会話全体）を確認する。権限は通常の `session` 範囲の共有規則で、
  メッセージと同じ操作の中で作る。どちらかが失敗したら、両方とも残さない。
- **所有者でない人も、自分に共有されているセッションなら添付できる。** その場合、CP は受け手それぞれの
  ACL を確かめ、権限の無い受け手には「あなたには共有されていません」と出す。権限は新しく作らない。
- メッセージを取り下げても、それ以前からある共有は解除しない。
- ルーム（P3）を作るとしても、ルームへの参加で共有が広がることはない。

### 6. 利用枠ボードは opt-in、サーバー側で縮約し、観測の古さを隠さない

**取得元。** reaper が毎分すでに取りに行っている `GET /sessions` の封筒に、Agent が利用枠の
スナップショットを足す。リクエストもトークンも増えず、ワークスペースも起こさない。reaper 自身の
時計はこれを無視する。reaper が切られている環境では、ブラウザからの送信を代わりに使う。

**観測ごとに保存するもの。** `kind`、枠の単位（窓・モデルグループ・クレジットプール）、`percent`、
`resetsAt`、`observedAt`（CP が受け取った時刻ではなく、Agent が捕捉した時刻）、`receivedAt`、取得元、
`stale`。古い観測で新しい観測を上書きしない。

**2 つの軸を分ける。**
- kind と単位ごとのアカウントの枠。
- セッションが実際に当たったもの：再開時刻つきの `limited`、`spend_limit`（待っても解けないので再開時刻は
  出さない）、`blocked`、`auth`。

あるセッションが止まっていても、別のモデルや kind が使えないとは限らない。データの無い kind は
「不明」と出し、「使える」とは言わない。

**リセット時刻を過ぎた窓は**「リセット未確認」と出す。0% とも「使える」とも出さない。codex が補外した
0% も同じ扱いで、Agent がそれを導出値だと印を付ける。

**kind ごとの対応。** claude・codex・muse は窓を持つ。copilot はクレジットプールを持つ。agy は読むたびに
TUI を起動するので、定期的には集めない。残りの kind はセッションの状態だけを出す。実装したら、この表は
`guide/ref/` に置く。

**公開範囲。**
- 既定は**非公開**。
- 見せる相手（テナント全体、または指定したメンバー）と粒度（状態だけ／帯：<50 / <80 / <95 / 上限／正確な値）は
  本人が選ぶ。
- CP は、ボード・引き継ぎの選択画面・SSE・エクスポートのどの経路でも、外へ出す前に縮約する。
- プロバイダのアカウントのメールアドレス、プラン、エラーの原文は出さない。他の人からは、非公開と未観測が
  同じに見える。
- ランキングや比較グラフは出さない。管理者向けの表示（docs/67、docs/83）は広げない。

**名簿。** ボードには専用のページ送り付きメンバー一覧を設ける。最大 20 件の共有先検索は流用しない。

### 7. 利用枠は融通しない

Agent Fleet は、資格情報を移さず、あるメンバーの仕事を別のメンバーのアカウントで走らせず、残り枠で
仕事を振り分けず、余裕でメンバーを順位付けしない。人が自分で仕事を引き受けると決め、自分の
アカウントで実行する。個人向けプランの規約はアカウントの共有や上限の回避を制限している。テナントの
メンバーがどの契約を持っているかはテナント側の問いとする（未解決の問い）。

引き継ぎの選択画面には、受け手が公開している利用枠の状態を参考として出してよい。ただし引き継ぎの ACL は
広げない（「すでに共有している相手」のまま）。受け手がその作業を実行できるかも判定しない。リポジトリの
権限・ブランチ・kind・サインインは、ADR 0057 のとおり受け手の側で起動前に確かめる。この参考表示は、
ADR 0057 の 2 アカウント通し確認が済んでから入れる。

### 8. 配送：正本は DB、SSE は合図

- 項目、受け手ごとの連番、既読カーソルは DB に置く。`GET /api/events` には「受信箱が連番 N まで
  変わった」とだけ伝えるストリームを足す。Console はそのあと、membership だけで通る REST で取りに行く。
  この REST は、ワークスペースのレコードが無くても、ワークスペースが止まっていても動く。
- membership の削除や、受け手の権限喪失は、開いている接続にも次の tick で効く。
- 受信箱には専用のバッジを付ける。項目は通知センターに入れない。通知センターは自分のセッションに関する
  イベントの場所で、会話の既読や未処理の依頼の在庫を混ぜると埋もれる。また通知センターは 7 日で消えるが、
  未処理の依頼は黙って期限切れにしてはいけない。

### 9. 秘匿と寿命

- **封緘が約束すること。** カストディアンがあれば、本文はテナント鍵カストディアンで封緘する。これが防ぐのは
  DB の漏洩で、運用者に対してではない。CP は復号できる。製品として「管理者にも秘密」は約束しない。
  カストディアンが無い環境では、本文が暗号化されずに保存されることを設定画面に明記する。
- **P1 では管理者が本文を読む API を置かない。** 管理者が本文を読めるか・エクスポートできるかは未解決の問い。
  作る場合は、読むたびに監査し、参加者から見えるようにする。
- **寿命はそれぞれ別に扱う。**

| 対象 | 終わるとき |
|---|---|
| 受信箱の項目の本文 | 保持期限、または最後の参加者の membership 削除 |
| 依頼の状態とリンク | 項目と一緒に残る |
| メモキューに取り込んだレシピ | 以後は受け手のメモで、メモの保持に従う。回収はしない |
| メッセージと一緒に作った共有 | 通常の共有。他の共有と同じく解除する |
| 既読カーソル | membership と一緒に消える |

- 期限切れの行は、復号の前に除外する。復号してから捨てるのではない。
- 監査ログには、誰が、どの種類の項目を、誰に、いつ送ったかを残す。本文は残さない。

### 10. 受け取るかどうかは受け手が決める

受け手が決められること：
- テナント全員から受け取るか、選んだメンバーからだけにするか。
- 送り手をブロックする。
- 応答不可（DND）：バッジとトーストは止めるが配送は止めない。辞退とは見なさない。

CP が強制する上限：
- 本文の大きさ。
- 送り手→受け手ごとの未処理件数。
- 送り手ごとの 1 時間あたりの送信数。
- 1 項目あたりの受け手の数。

管理者のお知らせ（P2）は独自の規則を持つ別種の項目で、ブロックできず、管理者だけが送れる。

### 11. エージェントは下書きまで、送るのは人

エージェントは、自分の利用者の作成欄に、メッセージやレシピの下書きを書いてよい。`add_memo` が利用者の
メモキューに書くのと同じ形である。宛先を選んで送信を押すのは利用者。どのエージェントにも、送信 API・
名簿・他メンバーの受信箱は渡さない。

### 12. 編集の重なり候補は別の同意を取り、安全の宣言にはしない

CP は、同じリポジトリで別メンバーのセッションが編集したパスを突き合わせて、「B さんのセッションも
`x.go` を編集しています」と出してよい。これはファイルパスをワークスペースの外へ出すので、独自の規則を置く。

- メンバー × リポジトリごとの別の opt-in にする。repo 範囲の共有があっても、それだけでは同意とみなさない。
  共有 DTO はファイル座標を意図的に落としているからである。
- 出すのはリポジトリ内の相対パスだけ。作業コピーの外のパス、絶対パス、秘密らしい名前
  （`.env*`、`*.pem` など）は落とす。
- メンバーをまたぐリポジトリの同一性は別途設計する。`workingCopyId` は所有者ごと・作業コピーごとの値で、
  テナント共通ではない。
- 元データは転写の編集履歴（docs/68）。shell やフォーマッタによる編集を取りこぼし、古い編集も残り、
  kind によって違う。そこで機能名は「最近の編集の重なり候補」とし、観測時刻と対象 kind を表示する。
  **「重なりなし」とは決して言わない。**

### 13. ペアモード・配布できるスキル・チームの知見・チャットブリッジは別の ADR

- **ペアモード**は、あるメンバーのエージェントとその課金を、別の人に継続的に委任することになる。RW 提案には
  質問や計画への回答も含まれる。安全に作るなら、サーバー側で、取り消せて、上限付きで、claim のたびに
  確かめる委任が要る。採用しない。いまは勧めない。
- **スキル**は、常設の指示・スクリプト・フックを含みうる。プロンプトのコピーと違い、導入は統治の変更である。
  先に、版を固定した人向けの**レシピ棚**を作れる（P3）。スキルの配布には、導入・更新の確認を別に設計する。
- **チームの知見メモリ。** 公開の承認は、CP に本人認証した人が行う。Agent のトークンで公開できては
  いけない。Agent の中ではセッションが自分で承認できてしまう。ADR 0108 は記憶を指示ではなく証拠として
  扱っており、メンバーをまたいでもそれを保つ。
- **チャットブリッジへのミラー。** ブリッジは各メンバー自身のワークスペースに、本人のトークンで置かれている。
  そのワークスペースが止まっている間は CP にある項目を届けられず、入力も紐付いた本人からしか受け付けない。
  ミラーには送り手の同意と受け手の opt-in が要り、ルームの返信をエージェントの入力にしてはならない。
  トークンを CP へ移すなら別の ADR が要る。メッセージは Console の中に留める。

### 14. 段階の順序

| 段階 | 内容 | ここに置く理由 |
|---|---|---|

## 却下した案

- **汎用チャットを先に作る。** 汎用チャットは Slack がすでにこなしており、ブリッジでも届く。ルームは依頼が
  使われてから（P3）。
- **ワークスペースをまたぐ peer メッセージ。** `send_to_peer_session` の宛先はセッションであって人ではなく、
  受け手のエージェントに 1 ターンを使わせ、ADR 0041 が囲い込まねばならなかった経路でもある。人と人の
  やりとりをエージェント経由にすべきではない。
- **他メンバーのメモキューへの直接挿入。** エージェントはキューを読む。同僚の文面が利用者自身の指示に見えてしまう。
- **ブラウザ経由だけの利用枠ボード。** 更新されるのは本人がタブを開いている間だけで、それは他の人が
  知る必要がいちばん小さい時間である。
- **既定で状態を見せる。** 「状態だけ」でも、働いている時間帯や課金の問題が漏れる。opt-in とは、選ぶまで
  非公開であること。
- **リセットを過ぎた窓を 0% とみなす。** 捕捉が止まっているのに、余裕があるように見えてしまう。
- **動いているセッションにレシピを直接注入する。** それは共有抜きの RW 提案である。
- **枠の融通、残り枠での振り分け、共有のサービスアカウント。** 決定 7。
- **時間制限付きの UI スイッチとしてのペアモード。** ブラウザのタイマーでは、期限・取り消し・レプリカの境界を
  守れない。決定 13。

## 未解決の問い

- 保持期限の既定値（案：受信箱の項目は 90 日、未処理の依頼は最終状態に達してから 90 日）。
- 管理者による本文の閲覧・エクスポート：無しにするか、監査付きで参加者から見える形にするか。
- ボードでの枠の単位：membership × kind か、プロバイダのアカウント／モデルグループか。別アカウントで
  再ログインしたとき、複数テナントに属するメンバーではどうなるか。
- テナントのメンバーがどの契約を持っているか。テナント管理者がそもそも利用枠ボードを望むか（テナント単位の切り替え）。
- 想定するテナントの規模（数人か数十人か）。名簿・送信上限・ルームの大きさが決まる。
- P1 の受け入れ条件：CP と Agent の版違い、まだワークスペースを持たない受け手、解除された共有、
  削除されたメンバー、2 人の同時 claim。
