## 背景

同じテナントのメンバー同士がすでにできることは 3 つある。

- セッションを RO / RW で共有する（docs/59）。
- RW なら、所有者が承認してからエージェントに届くプロンプトを提案する。
- セッションを引き継ぎ、受け手が自分のワークスペースで作業を始める（ADR 0057。P0 は実装済みで、
  実フリートでの 2 アカウント通し確認は docs に記録が無い）。

足りないもの：

- 同僚に何かを頼んで、それが引き受けられたか、誰が引き受けたか、何になったか（どのセッション、
  どの PR）を確かめる手段が無い。
- すでにセッションを共有していない限り、同僚にすぐ実行できるプロンプトを送れない。
- 共有済みセッションの行には `limited` / `spend_limit` がすでに出る。しかしメンバーのアカウントの枠や、
  共有していないセッションのことは何も見えず、本人が選んで公開する手段も無い。
- 2 人のメンバーのエージェントが午後いっぱい同じファイルを編集していても、マージまで誰も気付かない。

既存の仕組みと、その足りないところをコードで確かめた。

- **メモキューは受け手本人のもの。** `POST /api/memos` は呼び出し元の membership に挿入し、
  メモブリッジのトークンもその membership に固定されている（`control-plane/memo.go`、
  `control-plane/memo_bridge.go`）。他メンバーのキューへ挿入する経路は無い。メモには送信者・
  レシピ・出所の欄も無く、本文は平文で保存される。
- **エージェントはメモキューを読む。** `list_memos` はキュー上の全メモをセッションのエージェントに渡す
  （`workspace/agent/internal/mcpx/mcp_stdio.go`）。送信（flush）は本文を連結するので出所が落ちる。
- **CP は稼働中のワークスペースからすでに取りに行っている。** idle reaper は既定で 1 分ごと
  （`AF_IDLE_SWEEP_INTERVAL`）に直列で掃引し、稼働中の各 Agent に `GET /sessions` を呼ぶ
  （`agentSessionsEnv`、`control-plane/agent_client.go`）。どの機能（セッション・対話・ワークスペースの idle、
  hibernate、backup）も有効でないテナントは飛ばし（`tierClocks.anyOn`、`control-plane/reaper.go`）、間隔が 0 なら reaper 自体が動かない。封筒には
  live 状態の `limited`（任意で `rateLimitResumeAt` 付き）と `spend_limit` が載る。通知 outbox が吸い上げ
  られるのは Console が問い合わせたときと停止直前だけで（`control-plane/notification.go`、
  `drainAgentOutbox`）、reaper の `GET /sessions` は outbox を吸い上げない。
- **利用枠はブラウザ経由でしか CP に届かない。** `console/src/app/usageResetNotify.ts` が
  `windowKey / percent / resetsAt` を送るのは claude と codex の 5h・7d だけで、Console のタブが開いている
  間だけ。`notification_usage_state` が持つのは `resets_at` と `armed` で、割合も観測時刻も持たない。
- **利用枠の出し方は kind ごとに違い、古さについて正直とは限らない。**
  - claude：最後の statusline 捕捉を返し、リセットを過ぎた窓に `stale` を付ける。
  - codex：`adjustWindow` が過ぎた窓を 0% と次のリセットへ補外し、`stale` は付けない。アカウントの
    キャッシュは取得に失敗しても `fetched` を打ち直すので、取得失敗の直後は古い値が数秒前の値に見える
    （`codex/usage.go`、`accountUsage`）。
  - muse：窓を、その長さと一緒に返す。
  - agy：モデルグループごとの週間枠と、有料プランでは 5 時間枠を返す。更新は TUI の読み取りで、
    5 分のキャッシュがある。
  - copilot：クレジットプールを返す。
  - セッションが上限に当たったことの検知（rate-limit の監視）は claude・muse・Managed の codex が対象。
    他の kind や実行方式にその契約は無い。
- **共有先の検索は名簿ではない。** `GET /api/session-share-recipients` はテナントのメンバーを絞り込み、
  最大 20 件を返す。
- **`GET /api/events` は接続ごとのスナップショット差分送信であり、配送台帳ではない。** 連番も、
  再送カーソルも、受け手ごとの既読も持たない。入口は `withResolved` で、初めて Console を開いた
  メンバーにはワークスペースのレコードを作る（`control-plane/events.go`、`control-plane/resolver.go`）。
- **テナント鍵での封緘は運用者からの秘匿ではない。** RW 提案の本文はテナント鍵カストディアンで包む。
  カストディアンが無ければ base64 で保存するだけ（`control-plane/session_share.go`、`sealProposal`）。
  どちらでも CP は読める。
- **マーカーは所有者のワークスペースに置かれる注釈。** 付け外しは RW だけができ、所有者の
  ワークスペースが止まっている間は届かない（docs/69）。
- **通知センターは membership ごとのイベント履歴で、7 日保持。** answer-ready・質問・計画の承認・
  権限要求・利用枠のリセット・引き継ぎのイベントを持つ。会話の既読や、まだ処理中の依頼という概念は無い。
- **引き継ぎの受け手の作業コピーは推測で選ばれる。** 受諾の行は remote の basename を受け手の作業コピーと
  突き合わせ、無ければ先頭のものを選ぶ。リポジトリの同一性も HEAD も確かめない
  （`console/src/features/sharing/HandoffOfferRow.tsx`）。

## 決定

### 1. メンバーが送ったものが、別のメンバーのエージェントを動かすことはない

ここにあるどの機能も、あるメンバーの文面を、別のメンバーの明示操作なしにその人のエージェントや
ワークスペースへ届けない。これは ADR 0057 決定 1 をすべてに当てはめたもので、越境するのは文章・git 座標・
読み取り権だけである。ADR 0041 はこの危険を permission laundering と呼んだ。具体的には、受け取ったものに
次のことはさせない。

- 権限・計画・質問への受け手の承認を代わりに果たす。
- 別のメンバーが拒否された作業を代わりに行う。
- 受け手のセッションを統べるもの（権限設定・指示ファイル・MCP 設定・フック・資格情報）を変える。
- 受け手が取り込む前に、受け手のエージェントから見える（決定 3）。

既存の RW 提案は、所有者が承認する段を残す。しばらく RW 提案を自動承認する「ペアモード」は
**採用しない**（決定 13）。

### 2. 中心となる物はチャットのメッセージではなく、依頼

Agent Fleet にしかできないのは、頼みごとを、それが引き起こした作業と結び付けること。CP には
**受信箱の項目**という物を 1 つ置く。中身は送信者、受け手（送信時点で固定した membership の集合）、
本文、作成時刻、型付きの添付で、必要に応じて**依頼としての意味**を持つ。ただのメッセージ（DM）は
依頼としての意味を持たない項目である。レシピ（決定 4）は添付の一種。

**状態は 2 か所に置く。** 項目は共有の状態を持つ：`open`、`claimed`（担当 1 人）、`done`、`declined`、
`withdrawn`。受け手はそれぞれ自分の配送状態を持つ：未読、既読、辞退。

| 誰が | 操作 | 許される状態 | 結果 |
|---|---|---|---|
| 受け手 | 引き受け（claim） | `open` | `claimed`、担当＝呼び出した人。「状態がまだ `open` なら」の条件付き更新で行う |
| 受け手 | 辞退 | `open` | その受け手の配送状態が辞退になる。受け手全員が辞退したら項目は `declined` |
| 担当者 | 手放す | `claimed` | `open` に戻る |
| 担当者 | 完了 | `claimed` | `done` |
| 送り手 | 取り下げ | `open`・`claimed` | `withdrawn`。担当者に知らせる |
| システム | 担当者の membership 削除、または担当者が送り手をブロック | `claimed` | `open` に戻る |
| システム | 送り手の membership 削除 | `open`・`claimed` | `withdrawn` |

**引き受けが保証すること、しないこと。** 保証するのは、記録上の担当が 1 人であることと、製品自身の
依頼開始の操作が競合しないこと。依頼に付いたレシピを取り込んだり起動したりできるのは現在の担当者だけで、
CP がそれを確かめる。取り込みは（項目, 担当者）ごとに冪等で、二度押しや再試行でもメモは 1 つになる。
文面を手で写す人までは止められない。取り下げは、その依頼としての以後の採用を止めて担当者に知らせる
ものであり、すでに動いている作業を止めたり、複製を回収したりはしない（決定 9）。ただの DM に付いた
レシピには引き受けが無く、どの受け手も取り込める。

**結果へのリンク。**
- 依頼から起動に成功したとき、担当者の Console が、セッションと、その時点の作業コピー・ブランチを記録する。
- PR と最終的なブランチは、担当者が依頼カードから手で追加・更新する。起動時点では PR はまだ無く、
  ブランチも変わりうる。
- エージェントはリンクを申告しない。git 接続を使って PR を自動で見つけるのは別の後続工程で、同名ブランチや
  アクセス喪失を扱う必要がある。

未読と未処理は別物で、読むことは辞退ではない。依頼は読まれたかどうかに関わらず、最終状態に達するまで
次のように残る。

- `open` の間（手放された後を含む）は、送り手の一覧と、まだ辞退しておらず引き受けられる受け手全員の
  「担当待ち」一覧に残る。
- `claimed` の間は、送り手と担当者が進行中として追い、他の受け手には担当済みとして見える。

membership を削除された受け手や、送り手をブロックした受け手は、もう引き受けられない。担当待ちの一覧から
外れ、受け手全員が辞退したかどうかの判定にも数えない。

### 3. 受信箱は独立した保存先。メモキューへは受け手が明示的に取り込む

受信箱の項目は、受け手ごとの連番と既読カーソルを持つ専用の CP テーブルに置く。メモ API に
宛先を足すことはしない。

- **取り込むまで**、項目はどのエージェントからも見えない。`list_memos` は返さず、flush にも含まれない。
- **レシピを取り込むと**、受け手自身のメモとしてメモキューに複製される。その際、サーバーが
  `origin = {送信者, 項目 ID}` を付ける。メモを編集しても origin は消えない。Console はバッジを出す。
  送るときは受け手自身のメモと連結せず、出所を保ったまま単独で送る。
- その先はメモキューの既存の経路（編集・セッションへ送る・新規起動）を使う。起動したセッションには
  出所のバッジが付く。

### 4. レシピはリポジトリの識別子を運ぶ。取得はしない

レシピが持つのは、プロンプト、推奨の kind / モデル / effort、そして任意でリポジトリ。

- リポジトリは正規化した識別子（接続済み git プロバイダなら `host/owner/repo`）にする。URL を残す場合は
  userinfo・query・fragment を落とす。正規化できない remote は、そのまま通さずに拒否する。
- 識別子はプロンプト本文とは分けて表示し、受け手が指し先を確かめられるようにする。
- 受け取っただけでは何も fetch も clone もしない。受け手が自分の接続で、自分の作業コピーに対応付ける。
  clone は別の明示操作のまま。
- レシピは RW 提案ではない。受け手のこれからの作業を対象にし、共有を必要としない。

### 5. セッションの添付は、人が与えていない権限を与えず、権限の無い人には何も見せない

- **添付によって共有を作れるのは、そのセッションの所有者だけ。** 所有者が、セッション・受け手全員・範囲
  （後から追記される分も含めた会話全体）を確認する。権限は通常の `session` 範囲の共有規則で、
  メッセージと同じ操作の中で作る。どちらかが失敗したら、両方とも残さない。
- **所有者でない人も、自分に共有されているセッションなら添付できる。** 権限は新しく作らない。
- **受け手に何を見せるかは、受け手ごとに、読むたびに決める。**
  - 権限のある受け手には添付を見せる。
  - 権限の無い受け手には、サーバーが作る中身の無いプレースホルダーだけを見せる。catalog ID、タイトル、
    リポジトリの座標、ブランチ、所有者、プレビューは載せない。
  - ACL は一覧・詳細・リンクの解決・エクスポートのたびに評価し直す。送信後に共有が解除されたら、
    カードはプレースホルダーに変わる。
  - メッセージ中の送り手自身の文章はそのまま出す。CP がリソースから取ってきたメタデータは出さない。
- メッセージを取り下げても、それ以前からある共有は解除しない。
- ルーム（P3）を作るとしても、ルームへの参加で共有が広がることはない。

### 6. 利用枠ボードは opt-in、サーバー側で縮約し、観測の古さを隠さない

**取得元：Agent がすでに捕捉したスナップショット。**
- reaper がすでに取りに行っている `GET /sessions` の封筒に、Agent が利用枠のスナップショットを足す。
  封筒を作るときは、収集器がすでに捕捉した値を読むだけにする。プロバイダへの問い合わせは独立した、
  有界の周期で行い、封筒がそれを待つことはない。
- スナップショットは任意の欄で、他から隔離する。壊れていたり版が未知だったりしても、その kind の枠が
  `unknown` になるだけ。セッション・リポジトリジョブ・画像ジョブのデコードを失敗させず、idle・busy・
  在席の判定も変えない。
- **届く範囲。** reaper が届くのは、`tierClocks.anyOn()` が true のテナントの稼働中ワークスペースだけで、
  設定された間隔で直列に回る。届かないところはブラウザからの送信を使う。ボードは更新頻度を約束しない。

**観測の契約（両方の取得元で共通）。**
- `observedAt` は、プロバイダから最後に実際に観測できた時刻。取得の失敗やキャッシュの読み出しでは動かない。
  失敗時に時刻を打ち直す収集器（現在の codex のアカウントキャッシュ）は、この作業の一部として直す。
- `receivedAt` と取得元は別に持つ。
- 導出した値（過ぎた窓を 0% に補外したもの）は元の `observedAt` を保ち、`derived` の印を付ける。
  「リセット未確認」を打ち消すことはない。
- kind ごとに非公開の**ログイン世代**を持ち、本人が別のプロバイダアカウントにサインインしたら変わる。
  古い世代の観測は捨て、新しいアカウントの値として出さない。世代は他の人には見せない。
- 古い観測で新しい観測を上書きしない。reaper とブラウザから来た同一の観測は
  （membership, kind, 単位, 世代, `observedAt`）で重複を除く。
- 一定の古さを過ぎた観測は `stale`。観測時刻の分からない kind は `unknown`。
- ブラウザの送信（`POST /api/notifications/usage-observations`）は同じ欄を運ぶように改める。送った時刻を
  `observedAt` の代わりにしない。利用枠リセット通知の `armed` は別に保ち、導出値や stale な値では立てない。

**2 つの軸を分ける。**
- kind と単位（窓・モデルグループ・クレジットプール）ごとのアカウントの枠。
- セッションが実際に当たったもの：`limited`（自動再開が予定されていればその時刻。任意）、`spend_limit`
  （待っても解けないので再開時刻は出さない）、`blocked`、`auth`。

あるセッションが止まっていても、別のモデルや kind が使えないとは限らない。データの無い kind は
「不明」と出し、「使える」とは言わない。

**リセット時刻を過ぎた窓は**「リセット未確認」と出す。0% とも「使える」とも出さない。

**P1 で扱う範囲。**

| kind | 枠 | セッションの上限状態 |
|---|---|---|
| claude | 5h / 7d の窓 | あり |
| codex | 5h / 7d の窓 | Managed のみ |
| muse | 長さ付きの窓 | あり |
| copilot | クレジットプール | 不明 |
| agy | ボードでは集めない（更新が TUI の読み取りのため）。時刻付きのキャッシュ値を後で載せることはありうる | 不明 |
| その他 | 不明 | 不明 |

この表に無いものはすべて `unknown`。実装したら、完全な表は `guide/ref/` に置く。

**公開範囲。**
- 既定は**非公開**。
- 見せる相手（テナント全体、または指定したメンバー）と粒度（状態だけ／帯：<50 / <80 / <95 / ≥95「上限間近」
  ／正確な値）は本人が選ぶ。帯は単位ごとに出し、まとめない。実際に上限に当たったことは別のセッション状態で
  示し、最上位の帯では示さない。
- CP は、ボード・引き継ぎの選択画面・SSE・エクスポートのどの経路でも、外へ出す前に縮約する。
- プロバイダのアカウントのメールアドレス、プラン、エラーの原文は出さない。他の人からは、非公開と未観測が
  同じに見える。
- ランキングや比較グラフは出さない。管理者向けの表示（docs/67、docs/83）は広げない。

**名簿。** ボードには専用のページ送り付きメンバー一覧を設ける。最大 20 件の共有先検索は流用しない。

### 7. 利用枠は融通しない

Agent Fleet は、資格情報を移さず、あるメンバーの仕事を別のメンバーのアカウントで走らせず、残り枠で
仕事を振り分けず、余裕でメンバーを順位付けしない。人が自分で仕事を引き受けると決め、自分の
アカウントで実行する。個人向けプランの規約はアカウントの共有や上限の回避を制限している。テナントの
メンバーがどの契約を持っているかはテナント側の問いとする（未解決の問い）。

引き継ぎの選択画面には、受け手が公開している利用枠の状態を参考として出してよい。
- 引き継ぎの ACL は広げない（「すでに共有している相手」のまま）。
- 受け手がその作業を実行できるかも判定しない。現在の引き継ぎの受諾行は remote の basename で作業コピーを
  推測し、リポジトリの同一性も HEAD も確かめない。起動前にリポジトリの同一性・ブランチ / コミット・
  kind と実行方式・サインインを確かめることは、引き継ぎの後続作業の要件であって、この参考表示が
  与えるものではない。

### 8. 配送：正本は DB、SSE は合図、受信箱にワークスペースは要らない

- 項目、受け手ごとの連番、既読カーソルは DB に置く。Console は membership だけで通る REST
  （`withMembership`）で受信箱を読み書きする。
- 即時の合図は `GET /api/events` にストリームを足すのではなく、**membership だけで通る受信箱専用の
  ストリーム**にする。`GET /api/events` は `withResolved` を通るので、受信箱しか使わないメンバーにも
  ワークスペースのレコードを作ってしまう。新しいストリームは、`withResolved` が既存のストリームに
  与えているもの（メンバー接続の登録と、membership 削除時の切断）を引き継ぐ。ストリームが使えない
  ところでは、Console は REST をポーリングする。
- 受け入れ条件：受信箱を普通に使っても、ワークスペースのレコードを作らず、ワークスペースも起動しない。
- 受信箱には専用のバッジを付け、項目は通知センターに入れない。通知センターは 7 日分のイベント履歴であり、
  未処理の依頼は黙って期限切れになってはならず、answer-ready の並びに埋もれてもならない。会話を
  読むことも、別の種類の「既読」である。

### 9. 秘匿と寿命

- **封緘が約束すること。** カストディアンがあれば、本文はテナント鍵カストディアンで封緘する。これが防ぐのは
  DB の漏洩で、運用者に対してではない。CP は復号できる。製品として「管理者にも秘密」は約束しない。
  カストディアンが無い環境では、本文が暗号化されずに保存されることを設定画面に明記する。
- **P1 では管理者が本文を読む API を置かない。** 管理者が本文を読めるか・エクスポートできるかは未解決の問い。
  作る場合は、読むたびに監査し、参加者から見えるようにする。
- **寿命はそれぞれ別に扱う。**

| 対象 | 終わるとき |
|---|---|
| 受信箱の項目の本文 | DM は `createdAt` から数えた保持期限。依頼は最終状態から数えた保持期限（未処理の依頼は黙って失効しない）。いずれも、最後の参加者の membership 削除でも終わる |
| 依頼の状態とリンク | 項目と一緒に残る |
| メモキューに取り込んだレシピ | 以後は受け手のメモで、メモの保持に従う。回収はしない |
| メッセージと一緒に作った共有 | 通常の共有。他の共有と同じく解除する |
| 既読カーソル | membership と一緒に消える |
| 監査記録（本文なし） | 本文とは別の保持期限 |

- **削除は CP の仕事。** CP 側の冪等な削除処理が、期限切れや持ち主のいなくなった本文を消す。誰かが
  読むかどうか、ワークスペースやブラウザが動いているかどうかには依存しない。読み出し時も、期限切れの行は
  復号の前に除外する。稼働中の DB からの削除と、バックアップに残る期間は分けて明記する。
- **未処理の依頼は黙って期限切れにしない。** 一定期間を過ぎたら、上の一覧で「長期未処理」と示す。
  依頼が終わるのは `done`、`withdrawn`、受け手全員の `declined` のどれかだけで、送り手はいつでも取り下げられる。
  手放すのは担当を返すだけで、依頼は open のまま長期未処理の表示も続き、未処理件数の上限（決定 10）にも
  数え続ける。片付けのために `done` を押すことはしない。
- 監査ログには、誰が、どの種類の項目を、誰に、いつ送ったかを残す。本文は残さない。

### 10. 受け取るかどうかは受け手が決める

受け手が決められること：
- テナント全員から受け取るか、選んだメンバーからだけにするか。
- 送り手をブロックする。
- 応答不可（DND）：バッジとトーストは止めるが配送は止めない。辞退とは見なさない。

CP が強制する上限：
- 本文の大きさ。
- 送り手→受け手ごとの未処理件数。
- 送り手ごとの 1 時間あたりの送信数。
- 1 項目あたりの受け手の数。

管理者のお知らせ（P2）は独自の規則を持つ別種の項目で、ブロックできず、管理者だけが送れる。

### 11. エージェントは下書きまで、送るのは人

P1 では、エージェントは既存のツールで下書きする。`add_memo` で利用者自身のメモを書き、利用者が Console で
そのメモをメッセージやレシピにして、宛先を選び、送信を押す。そのための新しいエージェントのツールは要らない。
下書き専用のツールは、受信箱がワークスペースを要らないという性質を変えない任意の後続段階として、後で
作ってもよい。どのエージェントにも、送信 API・名簿・他メンバーの受信箱は渡さない。

### 12. 編集の重なり候補には 2 つの同意と公開相手が要り、安全の宣言にはしない

CP は、同じリポジトリで別メンバーのセッションが編集したパスを突き合わせて、「B さんのセッションも
`x.go` を編集しています」と出してよい。これはファイルパスをワークスペースの外へ出すので、独自の規則を置く。

- **メンバー × リポジトリごとの 2 つの同意：**
  1. そもそもパスを出すか。
  2. 誰に見せるか（テナント全体、または指定したメンバー）。

  repo 範囲の共有があっても、どちらの同意にもならない。共有 DTO はファイル座標を意図的に落としているからで
  ある。利用枠ボードの公開相手も、どちらの同意にもならない。
- **投影。** 候補を見せるのは、両側の公開相手にその閲覧者が含まれるときだけ。候補に出すセッション名・
  タイトル・リンクには、さらにそのセッションの共有 ACL を適用する。パスを出しても会話は開かない。
- **出すもの。** リポジトリ内の相対パスだけ。作業コピーの外のパス、絶対パス、秘密らしい名前
  （`.env*`、`*.pem` など）は落とす。
- **取り消し。** 同意の取り消しやテナントからの離脱で、CP が持っているパスと、そこから計算した候補を無効にする。
- **リポジトリの同一性**（メンバーをまたぐもの）は別途設計する。`workingCopyId` は所有者ごと・作業コピー
  ごとの値で、テナント共通ではない。
- **正直さ。** 元データは転写の編集履歴（docs/68）。shell やフォーマッタによる編集を取りこぼし、古い編集も
  残り、kind によって違う。そこで機能名は「最近の編集の重なり候補」とし、観測時刻と対象 kind を表示する。
  **「重なりなし」とは決して言わない。**

公開相手のモデルが決まらなければ、この機能は専用の ADR を待つ。

### 13. ペアモード・配布できるスキル・チームの知見・チャットブリッジは別の ADR

- **ペアモード**は、あるメンバーのエージェントとその課金を、別の人に継続的に委任することになる。RW 提案には
  質問や計画への回答も含まれる。安全に作るなら、サーバー側で、取り消せて、上限付きで、claim のたびに
  確かめる委任が要る。採用しない。いまは勧めない。
- **スキル**は、常設の指示・スクリプト・フックを含みうる。プロンプトのコピーと違い、導入は統治の変更である。
  先に、版を固定した人向けの**レシピ棚**を作れる（P3）。スキルの配布には、導入・更新の確認を別に設計する。
- **チームの知見メモリ。** 公開の承認は、CP に本人認証した人が行う。Agent のトークンで公開できては
  いけない。Agent の中ではセッションが自分で承認できてしまう。ADR 0108 は記憶を指示ではなく証拠として
  扱っており、メンバーをまたいでもそれを保つ。
- **チャットブリッジへのミラー。** ブリッジは各メンバー自身のワークスペースに、本人のトークンで置かれている。
  そのワークスペースが止まっている間は CP にある項目を届けられず、入力も紐付いた本人からしか受け付けない。
  ミラーには送り手の同意と受け手の opt-in が要り、ルームの返信をエージェントの入力にしてはならない。
  トークンを CP へ移すなら別の ADR が要る。メッセージは Console の中に留める。

### 14. 段階の順序と、機能ごとの依存

| 段階 | 内容 |
|---|---|
| **P0** | この ADR を承認する。受信箱の 2 membership での受け入れ条件を書く：認証、宛先、引き受けの競合、メンバー削除、ワークスペースを持たないメンバー。並行して ADR 0057 の 2 アカウント引き継ぎを通しで確かめる。 |
| **P1-A 前半** | 受信箱：永続的な保存先、membership だけで通る REST とストリーム、受信制御、DM、状態表どおりの依頼、起動時に記録するセッションのリンク、手動の PR リンク。`add_memo` によるエージェントの下書き。 |
| **P1-A 後半** | レシピ：origin 付きの明示的な取り込み、依頼に対する担当者限定で冪等な取り込み。共有を作るセッション添付（決定 5 のトランザクションを単独で検証できてから）。 |
| **P1-B**（A と独立） | 利用枠ボード：軽いスナップショット、観測の契約、ログイン世代、既定は非公開、サーバー側の縮約、P1 の範囲だけ。 |
| **P2** | 引き継ぎの選択画面での利用枠の参考表示。セッションのフォロー（明示の opt-in、共有済みセッションだけ。まずは最後に観測した状態と時刻）。RO レビュー。`workItem` / `pr` の添付。テナントのお知らせ（要望があれば）。 |

機能ごとの依存：

| 機能 | 必要なもの |
|---|---|
| 受信箱（P1-A） | P0 の受け入れ条件だけ。引き継ぎの通し確認は待たない。 |
| 引き継ぎの参考表示（P2） | P1-B と 2 アカウントの引き継ぎ確認。受信箱は要らない。 |
| セッションのフォロー（P2） | 常に：明示の購読で、共有 ACL ですでに見えるセッションだけが対象。投影のたびに ACL を確かめ直す。共有の解除・テナントからの離脱・購読の解除で以後の配送を止め、表示していたものも消す。利用枠の公開はセッションをフォローする許可ではない。状態だけなら P1-B のスナップショット経路。遷移の通知にするなら、ブラウザが開いていない稼働中ワークスペースからの永続的なイベント経路（ack とイベント ID 付きの outbox 吸い上げ、停止前の吸い上げ）が要り、それ自体が独立した作業になる。権限要求や質問の中身・回答ボタンは他のメンバーに届けない。 |
| RO レビュー（P2） | 注釈だけの新しい権限と、所有者のワークスペースのマーカーではなく CP に置くレビューコメント。 |

## 却下した案

- **汎用チャットを先に作る。** 汎用チャットは Slack がすでにこなしており、ブリッジでも届く。ルームは依頼が
  使われてから（P3）。
- **ワークスペースをまたぐ peer メッセージ。** `send_to_peer_session` の宛先はセッションであって人ではなく、
  受け手のエージェントに 1 ターンを使わせ、ADR 0041 が囲い込まねばならなかった経路でもある。人と人の
  やりとりをエージェント経由にすべきではない。
- **他メンバーのメモキューへの直接挿入。** エージェントはキューを読む。同僚の文面が利用者自身の指示に見えてしまう。
- **ブラウザ経由だけの利用枠ボード。** 更新されるのは本人がタブを開いている間だけで、それは他の人が
  知る必要がいちばん小さい時間である。
- **利用枠のための Agent→CP 専用 push の入口とトークン。** reaper の既存の認証付き取得が稼働中の
  ワークスペースの大半に届き、製品としては入口・資格情報・その運用を増やすよりこちらを選ぶ。代償は P1 の
  制約として受け入れる：reaper が届かない（無効、またはテナントでどの機能も有効でない）ワークスペースは、
  本人のブラウザも閉じている間は更新されず、stale か unknown と出る。その場合にも更新が必要なテナントが
  出てきたら、収集経路を考え直す。
- **既定で状態を見せる。** 「状態だけ」でも、働いている時間帯や課金の問題が漏れる。opt-in とは、選ぶまで
  非公開であること。
- **リセットを過ぎた窓を 0% とみなす。** 捕捉が止まっているのに、余裕があるように見えてしまう。
- **動いているセッションにレシピを直接注入する。** それは共有抜きの RW 提案である。
- **受信箱を `GET /api/events` に足す。** 受信箱がワークスペースのレコードを作るようになる。
- **枠の融通、残り枠での振り分け、共有のサービスアカウント。** 決定 7。
- **時間制限付きの UI スイッチとしてのペアモード。** ブラウザのタイマーでは、期限・取り消し・レプリカの境界を
  守れない。決定 13。

## 追記（2026-10-10）— 未解決の問いの決着

決定 1〜14 はそのまま有効。上の未解決の問いをここで決める。

1. **管理者による本文の閲覧・エクスポートは設けない。** 管理者が得る記録は、本文を含まない監査ログ
   （決定 9）とする。同僚に読まれうると知ったメンバーは書く量を減らし、機能の目的が損なわれる。
   閲覧は後から足せるが、存在を知られた後で取り下げることはできない。CP の運用者が技術的には復号
   できることは、決定 9 のとおり明記し続ける。コンプライアンス上どうしても本文の閲覧が要るテナントが
   現れたら、監査付きで参加者から見えるテナント設定として足す。それはこの ADR の改訂になる。
2. **保持期限：DM は作成から 90 日、依頼は最終状態から 90 日。** 依頼は 14 日で「長期未処理」と示す。
   どちらも固定で、テナントごとには変えられない。
   - 通知センターの 7 日では依頼を追い切れない。
   - 90 日あれば、どの依頼がどの PR になったかを四半期単位で振り返れる。
   - 14 日は 2 週間の反復 1 回分で、それだけ動かない依頼は実質放置されている。
   - 期間を設定可能にすると削除処理の検証範囲が広がるので、要望が出るまで待つ。
3. **公開設定はテナントの membership ごとに 1 つ。** 複数テナントに属するメンバーは、それぞれ別に設定する。
   テナントは信頼の単位で、データももともと membership ごとに持っている。あるテナントに公開したものが
   別のテナントに届いてはならない。1 つのプロバイダアカウントが複数のテナントに現れうるので、ボードは
   本人に、どのテナントに公開しているかを示す。
4. **利用枠ボードにはテナント単位の切り替えを設け、既定は有効。** メンバー個人の既定は非公開のまま
   （決定 6）。残り枠を見せること自体を方針として望まない組織のために、管理者がテナント全体で止められる。
   テナントの既定まで無効にすると二重の opt-in になり、実際には使われない。製品はメンバーがどの契約を
   持っているかを尋ねない。ガイドに決定 7 を書き、その判断はテナントに委ねる。
5. **想定規模は 2〜30 人。上限は 100 人程度でも破綻しない値にする。** 初期の上限：
   - 1 項目あたりの受け手は 20 人まで。
   - 送り手ごとの送信は 1 時間に 30 件まで。
   - 送り手→受け手ごとの未処理は 10 件まで。

   ボードと依頼が効くのは、互いの顔が分かるチームの範囲である。数十人を超えると、引き受けの競合や
   お知らせの性質が変わる。ルームを P3 に置いたままにする理由もこれである。
6. **stale は 60 分、長期未処理は 14 日。**
   - 1 つの窓の中では使用率は増える一方なので、リセット時刻より前の古い観測は、下限としてはなお正しい。
     ボードは「X% 以上（N 分前）」と出し、60 分（5 時間窓のおよそ 5 分の 1）を超えたら stale の印を付ける。
   - リセット時刻を過ぎると下限としての意味も失うので、決定 6 のとおり「リセット未確認」と出す。
