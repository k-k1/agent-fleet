## Context

メモキュー（docs/log/21）は、メンバーごとのメモを、レポジトリのフォルダと自由なカテゴリで分けて持つ。人がどの端末からでも、
Workspace が止まっていても溜められ、あとで選んだものを 1 通にまとめてセッションへ送る。セッションはメモを足すことと直すことが
でき、消すことと送ることは人に残してある（`workspace/agent/internal/mcpx/mcp_fleet_observe.go:41-53`）。ツールの説明文も
そう言っている。`add_memo` は「人間あてのメッセージ」である。

欲しいのは、人が毎回「送信」を押さなくても回るサイクルである。

- 人がキューに仕事を入れる。または、セッションに指示して入れさせる。
- キューがその仕事のためのセッションを自分で起こす。
- そうしたセッションは同時に N 本まで。1 本がタスクを終えたら、その空きに次のメッセージを起こす。
- 発火の前に、エージェントが溜まったものを整理してよい。分類する、重複をまとめる、3 つの話が入ったメモを分ける。

きっかけになった例は 3 つ。着手すべき GitHub Issue を、見つけるたびにキューへ入れる。sandbox で確認が要る Issue を日中に溜めて
夜に回す。その日のアイデアを夕方に整理して Issue にする。

### すでにあるもの

- **定時実行**（ADR 0021、`control-plane/scheduler*.go`）。1 分ごとの tick が期限の来たものを並べ、同時に 4 本まで発火する
  （`scheduler.go:196`）。発火はメンバーを解決し、reaper を止めておき、停止中の Workspace を起こし、Agent を待ち、セッションを
  作る。2026-11-10 の補遺でゲートが入った。発火の前の安い検査、2 つの tick が両方発火しないよう投入の前に書く確保、1 日の上限
  である。
- **reaper のための、セッション行の分類**（`control-plane/session_activity.go:118`）。機械が動いている、人が動く番である、ターンが
  終わっている、不明、の 4 つ。同じ行は Workspace の停止中もデータベースに残り、待っていた対話も一緒に残る（ADR 0055）。
- **メンバー由来の印**（ADR 0113）。ある書き込みがメンバー本人から Console を通って来たことを Control Plane が確かめられる。
  Workspace の中のものには偽造できない。
- **ツールを持たないと検証された 1 回きりのモデル呼び出し**（`workspace/agent/internal/chatx/chat_denyall.go:176`、ADR 0117
  決定 3）。本番の呼び出し元はまだ無い。
- `create_session` にある、**セッションごとの支出の予算**と**セッションごとの作業項目**。

### 設計を決める事実

1. **Control Plane が知っているのは、投入したメンバーであって、セッションではない。** `AF_MEMO_TOKEN` が運ぶのはメンバーシップ
   だけで（`control-plane/memo_bridge.go:29-62`）、MCP のプロセスはモデルの引数をそのまま Control Plane へ送る
   （`workspace/agent/internal/mcpx/mcp_client.go:30`）。Workspace の中のプロセスはどれも同じ uid で動き、そのトークンを読める
   （docs/build/07-security §7.2「The limit」）。同じトークンは `POST /internal/memos/flush` と
   `DELETE /internal/memos/{id}` でも通る（`control-plane/routes.go:612-614`）。「セッションは送れない」を守っているのは
   MCP の層だけである。
2. **送信は、メンバーが打った入力として読まれる。** `sendMemoPrompt` は source なしで `{op:start, prompt}` を送る
   （`control-plane/memo.go:658`）。だからそのターンには封筒も出自も付かない。人が押した送信にはそれで正しく、自動のものには
   誤りである。
3. **Workspace の停止中に生きているのは Control Plane だけである**（ADR 0021 Context）。投入はすでに停止中でもできる。発火の
   判断も同じ場所に置くしかない。
4. **プロジェクトという実体は無い。** `memo.repo` は前後を削っただけの文字列で（`control-plane/memo.go:165`）、実際には
   `~/repos` の下のフォルダ名である。だから worktree から足したメモは `repo@slug` という別のバケツに入りうる。
5. **定時実行の新規セッションは、ディレクトリをそのまま受け取り、worktree を作らない**（`control-plane/scheduler_wake.go:410`）。
   `max_sessions` のクォータを検査するのは Console からの作成と分岐だけである
   （`control-plane/workspace_handlers.go:1201,1236`）。
6. **ターンの終わりは、タスクの終わりではない。** CI やレビューを待つセッションはターンを終え、通知でまた起こされる（ADR 0133）。
7. **API の段で失敗したセッションは、終わったセッションと同じに見える。** idle で、最後のターン終了時刻も付く（実測、
   docs/log/87 §87.19.2）。
8. **セッションは重い。** 親と子 6 本で PSS は 1.76〜1.90 GiB と測れた。claude より軽い種別は無い（docs/log/87 §87.19.3）。

## Decision

メモキューをその場で育てる。メモがメッセージである。メモのカテゴリは、人が常設指示と消費者を与えたときに**キュー**になる。
発火は ADR 0021 のスケジューラに乗り、発火ごとに新しいセッションを起こす。同時に動くのは `max_active` 本までで、その数は
完了のイベントからではなく、セッションの状態から数える。セッションが投入したものは、人が 1 回押すまで発火できない。

### 1. キュー、メッセージ、配達

- **キュー。** `memo_category` の行（すでに第一級で、安定した id を持つ）に、人だけが書く設定を足したもの。設定は、常設指示
  （§5）、消費者（エージェントの種別、モデル、effort、経路、支出の予算、worktree の有無）、流量の設定（§6）、§3 と §8 の
  スイッチである。設定の無いカテゴリと未分類のバケツは、今とまったく同じに振る舞う。人あてのメモで、人が送る。`add_memo` の
  「人間あてのメッセージ」は、それらについては正しいままである。
- **メッセージ。** `memo` の行に、状態、出どころ（§3）、省略できる型付きの参照（§4）、重複排除のキーを足したもの。状態は、
  `held`（人の解放を待っている）、`pending`（発火してよい）、`claimed`（発火が確保した）、`delivered`、`unconfirmed`（届いたか
  どうかを発火が判断できなかった）、`superseded`（整理で置き換えられた、§8）。手動の送信は `sent_at` をそのまま使い、人による
  配達として扱う。
- **配達。** 1 回の発火のこと。運んだメッセージ、起こしたセッション、状態（`claimed`、`open`、`closed`。`closed` には clean、
  failed、aborted、unknown のどれかの結果が付く）を持つ。Console が見せる台帳であり、同時実行数の上限を数える元でもある。
  スケジュールの実行履歴と同じように保持する。

名前の変更で 2 つのカテゴリが 1 つになるときは、残るカテゴリの設定を残す。

### 2. 鍵は親レポジトリで、メンバーごと

キューは（メンバーシップ、レポジトリ、カテゴリ）である。レポジトリは親レポジトリのフォルダ名とする。worktree のフォルダを
名指しした投入は、その親の下に入れる（Agent では `gitx.WorktreeParent`、Console では `folderBase`）。リモートを正規化できる
ときは、`host/owner/repo` を横に保存する（`canonicalRepoIdentity` が作る形、`control-plane/inbox_recipes.go:49`）。これは
鍵ではない。あとの記録がキューをメンバー間で共有するときに、意味の移行をせずに済ませるために置く。キューはメンバー本人の
ものである（§9）。

### 3. 誰が投入してよいか、何を押さずに発火してよいか

メッセージの出どころは、Control Plane が、届いた経路から決める。引数からは決めない。

| 出どころ | 経路 | 入るときの状態 |
|---|---|---|
| `member` | Console。メンバーのセッション付き | `pending` |
| `workspace` | キューのトークン。Agent がセッションの名前と出自を添えて中継する | `held` |
| `mcp` | `/mcp`。接続の id 付き | `held` |
| `inbox` | メンバーの受信箱から取り込んだもの（origin の列、ADR 0111） | 発火の対象にならない。人が単独で送る |
| `curator` | 整理が派生させたもの（§8） | 元のメッセージの状態 |

- **解放は 1 回押すだけ。** セッションがキューに投入すると、Console はセッションとキューの組ごとにカードを 1 枚出す。どの
  セッションが、どのキューに、何を入れたかが載る。押すとそれらが `pending` になる。この操作はメンバー由来の印（ADR 0113）を
  伴うので、約束ではなく壁である。セッションに「これをキューに入れて」と言った人は Console にいて、1 回押す。誰もいない
  ところでセッションが投入したものは、待つ。
- **キューごとのスイッチで、人が始めたセッションについては押す手間を省ける。**「自分が始めたセッションからは受け入れる」を
  on にすると（設定には印が要る）、出自が `user` のセッションからの `workspace` メッセージは `pending` で入る。その帰属を
  申告するのは Agent なので、このスイッチは壁ではなくガードレールである（事実 1）。既定は off。
- **押さずに通ることが無いもの**: キュー、スケジュール、別のセッション、オペレーター、`/mcp` が起こしたセッション。`/mcp` の
  クライアント。だからキューは自分に餌をやれない。
- **セッションにできないこと**: キューを作る、設定を変える、解放する、消す、発火する。設定は Console から印付きで書く。
  オペレーターのアシスタントは、どのセッションとも同じ `workspace` の投入者である。
- **常時出すツールは増やさない。** セッションは `add_memo` で、キューになっているカテゴリへ投入する。`list_memos` がどの
  カテゴリがキューかを示す。`add_memo` は Control Plane へ直接ではなく Agent を通るようにし、Agent がセッションを刻む。
  説明文は変わるが、ツールの数は変わらない。
- **上限**は peer メッセージにあるものと同じ種類を置く（`workspace/agent/internal/sessionx/session_peer.go:37-48`）。投入者
  ごとのレート制限、大きさの上限、同一メッセージの破棄、`[agent-fleet:` で始まる本文の拒否である。

これは docs/log/86 §86.5 を狭く改める。セッションは無人実行を引き起こせるようになるが、それは人が設定したキューを通してだけ
であり、人が押したとき、またはその人が常設のスイッチを入れているときだけである。

### 4. 型付きの参照

メッセージは参照 `{provider, key, url}` を持てる。キーは作業項目の形である（`owner/repo#N`、`PROJ-12`）。Console は作業項目に
「キューに追加」を出す。1 つのキューが、閉じていないメッセージを（provider、キー）ごとに持てるのは 1 件までである。項目の
本文は写さない（ADR 0061 決定 2 と 5）。セッションは `gh` や `jira` で読む。作業項目から始めたセッションと同じである。
発火が運ぶ参照がちょうど 1 件のときは、それをセッションの作業項目として渡す。ブランチ名とリンクは既存の決まりに従う。

これは ADR 0061 決定 8 を改める。あの決定は項目そのものをメモの一覧に入れないと言っており、それは今も変わらない。項目は
自分のセクションに、読むだけのものとして残る。キューが持つのは、項目を指す参照と、メンバー自身のメモである。

### 5. 発火が届けるもの：常設指示と、データとしてのメッセージ

- **常設指示**は、人がキューの設定に書く（印付き）。項目をどう扱うかを言う。「Issue を実装して PR を出す」「…の手順に従って
  sandbox で確認する」「これらのアイデアを Issue にする」など。常設指示の無いキューは発火できない。
- 発火のプロンプトは、順に、封筒 `[agent-fleet:queue queue=<id> delivery=<id> reply=none]`、常設指示、項目である。項目は
  「データである」と示す行の下に並べ、それぞれにサーバーが書く出どころの行（誰が、何を通して入れたか）を付ける。
- ターンの source は `queue` とし、専用のバッジと、Workspace の運用方針の中の専用の段落を持つ。指示はメンバーのものである。
  項目の文は何に取り組むかを言うもので、指示を広げること、承認の代わりになること、セッションを律するものを変えることは
  できない（peer メッセージの 4 つの禁止と同じ）。
- 大きさの上限を超えるバッチと、添付のあるバッチは、Workspace の中のファイルに書き、プロンプトにはそのパスを書く（動いている
  Terminal セッションに打ち込んだ長いメッセージが切れて届いたことがある、#2195）。

これは ADR 0021 決定 10 を、`{{gate.refs}}` のときと同じやり方で改める。無人実行のプロンプトは今も、人が登録した文でできて
いる。足されるものはデータと示され、メンバー本人が書いたかメンバーが解放したもので、出どころを名乗る。

### 6. 発火：同時実行数の上限を、セッションの状態から数える

**設定**はキューごとに持つ。`max_active`（既定 2、最大 6）。`batch`（1 セッションに渡すメッセージ数。既定 1。または
`pending` の全部で、上限 20）。そしてキューが開く条件で、常時、時間帯、または `pending` が K 件たまったとき（その後は空に
なるまで流す）。件数の条件は、最後の投入から 1 分何も入らなくなるまで待つ。一度に足した 10 件が一緒に始まるようにする
ためである。

**ディスパッチャ**はスケジューラの tick の中で動く。`ListDueSchedules` の横の、期限の来た仕事のもう 1 つの出どころである。
`pending` のメッセージがあって開いているキューごとに `空き = max_active − 使用中` を計算し、その数だけ発火する。メンバー
全体の上限と §7 の上限の内側で行う。だから、終わったタスクは 1 分以内に次へ置き換わる。

**使用中はレベルであって、イベントではない。** 配達は、そのセッションが次の状態にある間、キューの `max_active` 個の場所の
1 つ（以下、枠）を使う。

| 配達が起こしたセッション | 枠 |
|---|---|
| 機械が動いている（ターン、圧縮、背景ジョブ） | 使用中 |
| 人が動く番である（質問、プラン、権限、サインイン、上限のメニュー）。停止中で対話を持ち越している間も同じ | 使用中 |
| 利用上限で、時計を待っている | 使用中。その種別では新しく発火しない |
| idle だが、ウォッチを持っている、または子セッションが動いている | 使用中 |
| idle で、待つものが無い。連続 2 回の tick で確認できた | 空き。配達を閉じる |
| 持ち越した対話なしで停止している、アーカイブされた、削除された | 空き。配達を閉じる |
| `max_task_hours`（既定 12）より長く開いている | 空き。配達を unknown で閉じ、メンバーに通知する |

上の 3 行は、reaper がすでに分類している状態を読む（上限待ちのセッションは、reaper にとっては畳んでよく、ここでは使用中
である）。4 行目には、セッション行に新しい欄が 1 つ要る（ウォッチと子を知っているのは Agent で、Control Plane は知らない）。
Workspace が止まっているとき、行はデータベースから読む。使用中になるのは持ち越した対話だけである。

人を待っているセッションが枠を使い続けるのは、意図したものである。夜に 2 本が質問で止まれば、キューも止まる。メンバーが
朝に見つけるのは 2 つの質問で、10 個ではない。

**発火**はまず確保する。条件付きの書き込み 1 回で、選んだメッセージを `pending` から `claimed` へ動かし、配達を作る。だから
2 つの tick でも、2 つの Control Plane のタスクでも、勝つのはちょうど 1 つである。そのあとスケジューラの経路が走る。
起こす、Agent を待つ、セッションを作る。作るときに渡すのは、冪等キー `q_<配達>`、キューの消費者の設定、`queue` の
source、そして、キューが別の指定をしていない限り**キューのレポジトリから切った新しい worktree** である（1 つの作業コピーに
2 つのセッションがいると、互いの作業を壊す）。

- **届いていないと証明できるとき**（起こせなかった、Agent が時間内に準備できなかった、メモリ圧迫やクォータで Agent が
  断った）: メッセージは `pending` に戻り、キューは間隔を空ける。失敗には数えない。
- **証明できないとき**（作成を送ったが応答が来なかった）: メッセージは `unconfirmed` になる。人に見せ、自動では二度と発火
  しない。重複は、1 つの Issue を 2 回実装させる。
- 閉じた配達のセッションは停止する（再開できる）。アーカイブも削除もしない。

### 7. 安全弁

- **サーキットブレーカー。** 配達が 2 回続けて failed か aborted で閉じたとき、または clean なターンが無いまま開始から
  1 分以内に閉じたとき（事実 7）、キューを一時停止してメンバーに通知する。再開は人がする。
- **利用上限。** キューのセッションが上限で止まっている間、その種別のセッションは起こさない。
- **メンバー全体の上限。** すべてのキューを合わせた使用中の枠に上限を置く（既定 4）。キューの発火にも `max_sessions` の
  クォータを適用する（事実 5）。メモリ圧迫による Agent の拒否（ADR 0120 の段階 2）に従う。
- **上限**: キューごとの 1 日の発火回数（既定 20）と、キューの設定から来るセッションごとの支出の予算。
- **通知**は、スケジュールと同じく Control Plane の通知センターから出す。一時停止した、すべての枠が人を待っている、未確認が
  ある、期限が切れた。
- **削除の保護**: 有効なキューは、有効なスケジュールと同じく、そのレポジトリの削除を止める。

### 8. 発火の前の整理

キューごとに選べ、人が設定する。発火の期限が来て、そのキューにまだ整理が見ていない `pending` のメッセージがあるとき、
整理は起こしたあと、確保の前に走る。

- **呼び出し**は `OneShotDenyAll` で、専用の利用区分を持つ。ツールも、MCP サーバーも、ファイルも、ネットワークも無い。それを
  プローブと本番の実行自身の出力で検証し、示せないときは整理を飛ばす。
- **モデルが提案し、Agent Fleet が適用する。** 入力は、そのキューの `pending` のメッセージをデータとして渡したもので、
  それぞれに id が付く。出力は、その id に対する JSON の操作である。統合、分割、同じレポジトリの別のカテゴリへの移動、
  そのまま。Agent Fleet は返答の全体を検証し（どの id も入力にあった、件数と大きさが上限内である、移動先が実在する
  カテゴリである）、形の崩れた返答は丸ごと捨てる。
- **何も失わない。** 統合と分割は `derived_from` を持つ新しいメッセージを作る。元のメッセージは `superseded` になり、保持
  期間が過ぎるまで残る。結果が確保されていない間は、1 回の操作でその整理を取り消せる。
- **出どころは残る。** 出どころが違うメッセージ、投入者が違うメッセージは統合しない。派生したメッセージの出どころは、
  `curator` と、元のメッセージの出どころである。
- **手は届かない。** 整理は、設定、消費者、どのキューがいつ発火するかを変えられない。失敗した整理と飛ばした整理では、
  メッセージをそのまま発火する。
- **上限**: メンバーごとに同時 1 回、1 回の呼び出しは 2 分、1 日の回数の上限。

Console にある今の「整理」（プレビューしてから承認）にも同じ操作を足し、手動の経路として残す。

これは ADR 0021 の 2026-10-03 の補遺を改める。次のプロンプトに届く文は、人が解放したメッセージだけから、ツールを持たない
呼び出しが作り、検証されたものである。セッションの出力ではない。

### 9. メンバー 1 人

キューはメンバー 1 人のものである。他のメンバーの文がキューに届くのは、受信箱からの取り込みだけで、それは手動かつ単独の
ままである（ADR 0111 決定 1 と 3）。プロジェクトのメンバーで共有するキューには、別の記録が要る。

### 10. 面

- **Console**: メモのセクションがキューに印を付け、メッセージごとの状態と出どころを見せる。設定のダイアログ。解放のカード。
  配達の一覧と、そのセッションへのリンク。一時停止、再開、「今すぐ発火」（人の操作で、同じ確保を通る）。
- **Control Plane**: 設定と解放は `/api` の下で、印を要求する。トークンの面は、投入と一覧だけ。
- **Agent**: `add_memo` の中継、`queue` のターンの source、セッション行の新しい欄、整理の呼び出し。
- **ガイド**: タスクのページ、上限の表、用語集の語。「キュー」は Console ではすでにセッションの待ち入力の名前である
  （ADR 0105）。メンバーに見せる語は、ここではなくそこで選ぶ。

### 11. 段階

1. **自動発火の無いキュー。** 設定、メッセージの状態、出どころ、Agent の中継、解放のカード、封筒と source、配達の台帳、
   発火ごとの worktree、「今すぐ発火」。
2. **自動発火。** ディスパッチャ、`max_active`、セッション行の欄、開く条件、クォータ、ブレーカー、上限、通知。
3. **型付きの参照**と、作業項目の「キューに追加」。
4. **「自分が始めたセッションからは受け入れる」。**
5. **発火の前の整理。**

## Rejected

- **メモキューの横に、新しいキューの置き場を作る。** メモする場所が 2 つ、セクションが 2 つ、同期の経路が 2 つになる。
  メモキューには、分け方も、端末間の同期も、トークンの面もすでにある。
- **件数か時刻だけで発火し**、1 つのバッチを 1 つのセッションへ渡す。何本のセッションが動くかを抑えられない。溜まった分は
  次の回を待つか、1 つのセッションの文脈に全部載るかになる。
- **完了のイベントで枠を返す**（`af_report`、ターン終了のコールバック）。イベントを 1 つ落とすと、枠は永久に埋まる。報告の
  台帳がエッジからレベルへ移ったのも同じ理由である（ADR 0035）。
- **ターンの終わりをタスクの終わりとする。** CI やレビューを待つセッションには早すぎる（事実 6）。
- **セッションの投入を、そのまま自動発火に乗せる。** docs/log/86 §86.5 のバックドアを、全セッションに広告するツール付きで
  作ることになる。
- **投入者を認証するために、セッションごとの資格情報を配る。** 同じ uid なので、どのプロセスも読める（事実 1）。
- **既存のセッションへ届ける。** 発火ごとの冪等性が無い。Terminal セッションの入力キューは Agent Fleet から見えない。
  長く生きる消費者の文脈は際限なく育つ（ADR 0021 決定 3）。
- **ウォッチエンジンに載せる**（ADR 0133）。種類ごとに最新の状態だけを伝え、途中を捨てる。自由文を運ばない。Workspace の
  停止中は動かない。
- **整理に `/chat/ask` か、スケジュールしたオペレーターのターンを使う。** 前者はツールを拒否リストで絞るチャットのターンで、
  ツールが無いと検証されていない。後者はメモのツールを全部と、`flush_memos` と、`create_session` を持つ。
- **トラッカーのラベルをキューにする。** 保存済みクエリに対するゲート付きスケジュールは、ラベルの付いた Issue が現れたときに
  すでにセッションを起こせる（ADR 0021 補遺 2026-11-10）。トラッカーが正本であるときは、それが今も正しい道具である。
  消費済みの状態、同時実行数の上限、Issue でないメモの置き場は持たない。
- **タイムアウトのあとで再配達する。** 報告しなかったセッションは、何もしなかったセッションではない。
- **メンバー間で共有するキューを今作る。** あるメンバーの文が別のメンバーのセッションで発火するのは、受け手がそれを有効に
  していない限り、ADR 0111 決定 1 に反する。

## Consequences

- セッションから届く無人実行の面が、初めてできる。それを抑えるのは、人が押すこと（または常設のスイッチ）、常設指示、
  同時実行数と 1 日の上限、支出の予算、ブレーカーである。
- スケジューラは、期限の来た仕事の出どころをもう 1 つ持ち、同時 4 本の発火をスケジュールと分け合う。
- フックの無い種別は idle をポーリングで知らせるので、遅れることも早すぎることもある。それらには `max_task_hours` が
  最後の支えになる。キューの消費者には、ターンのフックを持つ種別のほうが向く。
- 終わったセッションとその worktree は、人が削除するまで溜まる。
- トークンの面は、メモの `flush` と `DELETE` を受け付けるままである（事実 1）。この記録はそれを広げず、閉じもしない。
- 受理のときに、ADR 0021 と ADR 0061 へ、ここを指すメモを足す。

## Open questions

1. **既定値**: `max_active` は 2（最大 6）、メンバー全体で 4、1 日 20 回の発火、12 時間。docs/log/87 のメモリの数字からの
   見積もりであり、実際のキューの稼働を測る必要がある。
2. **押さずに通す参照。** セッションからのメッセージが参照だけなら、自由文を運ばない。それを押さずに `pending` で入れて
   よいかは、トラッカーの中身を信用できるかによる。それはレポジトリごとに違う。
3. **引き取りのツール。** 人が操っているセッションのためのもの（「キューから次の 5 件を取って」）。それと、既存のセッションが
   消費者になれる場合があるか。
4. **誰も見ていない完了済みの仕事の上限。** 閉じた配達が M 件を超えて人を待っている間は、発火を止める。
