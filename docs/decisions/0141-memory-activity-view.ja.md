## 背景

メモリーペイン（#3720）は 1 枚のペインに 3 つのタブを持つ。メモリーのマスター・ディテール、変更一覧、
統合役の提案である。どのタブも自分のリストを自分の詳細の横に描くので、ペインの幅ではリストが本文の
幅を食う。セッションの横にメモリーを 1 件開いておきたいだけでも、ビューア全体を開いておくことになる。
「新しいリストはビューにする」は ADR 0140 決定 2 がすでに決めている。

メモリーはワークスペースのファイルではない。ストアは Agent の設定ディレクトリの下にあり、どの閲覧ルートの
外でもある。メンバーの書き込みは `member-save` を通る必要がある。リビジョン照合、秘密情報スキャン、
サイズ上限、メンバーを作者とする記録、Control Plane の署名（0113）がそこにある。Markdown ファイルを
直接書くファイルエディタは、そのすべてを飛ばしてしまう。

## 決定

1. **メモリーをアクティビティバーのビューにする**（`RAIL_VIEWS` に `memory` を足す。アイコンは
   `archive`、メモキューの次）。ビューは上から順に次を持つ。
   - 絞り込み: 検索（項目は即時、本文は少し待ってから `member-search` で）、スコープ、
     全て / ピン留め / 忘却のチップ、type。
   - **提案**: 既定では統合役の未決の提案（決定済み・期限切れはワンクリック先）。実行状態と実行ボタンは
     セクションの見出しに置く。折りたためる。
   - **メモリー**: 絞り込んだ一覧をスコープごと（ユーザー、続いて各プロジェクト）にまとめる。
   - 末尾に変更一覧をメモリーペインで開くリンク。見出しに `+` とオーバーフロー（新規メモリー、
     設定 > エージェントメモリー）。
2. **バッジは未決の提案の数で、待ちのカウントとして出す。** 提案はメンバーの判断を待ち、メンバーが
   足したわけでもないのに届く。答えを待って止まったセッションと同じ扱いになる（0140 決定 4）。
   メモリー本体にはバッジを付けない。
3. **メモリー一覧は初めて表示したときにマウントする。** Files と同じ扱い（0140 決定 3）。一覧は
   Agent を読むので、隠れたビューが読んではならない。隠れている間に読むのは未決の提案の数だけにする。
   ワークスペースが止まっていれば、起動ボタン付きの停止中セクションを出す。
4. **メモリーをクリックすると専用のペインで開く**（新しい種別 `memoryEntry {scope, project, name}`。
   ファイルと同じく 1 メモリー 1 ペイン）。見た目と振る舞いはファイルビューアに揃える。見出しに名前・
   スコープ・type・ピン・使用回数・更新日時・作者を並べ、本文はレンダリングした Markdown で出す。
   編集でコードエディタに切り替わる。説明と type はエディタ上のフォームで編集し、frontmatter として
   本文に混ぜない。壊れたヘッダーが保存に届くことは無い。保存は `member-save` を通し、その拒否
   （リビジョン競合、秘密情報の検出、上限）はその場に出す。ピン留め、忘れる、履歴の削除、履歴は、
   マスター・ディテールからペインの見出しとオーバーフローメニューに移す。忘れたメモリーは読み取り専用で
   開き、「元に戻す」を出す。`+` は編集モードの空のペインを開く。
5. **提案をクリックすると、その詳細をメモリーペインに出す**
   （`{kind:"memory", memoryView:"proposals", proposalId}`）。全幅で、承認 / 却下は今と同じ。
   メモリーペインは引き続き 1 枚で、2 回目に開くと中身を差し替える（`openMemoryView`）。
6. **メモリーペインは変更と提案を残し、メモリータブは無くす。** 保存済みレイアウトの
   `memoryView:"memories"` のペインは、ビューを案内するペインに移行する。
7. **両側で 1 つのストアを使う。** 一覧・提案・書き込みのバージョンを `features/memory/store.ts` に移す。
   ペインでの判断や保存がビューを更新し、その逆も起こる。今コンポーネント間で受け渡している `reload`
   カウンタは無くなる。
8. **入口もこれに合わせる。** 統合役の通知はビューを出し、先頭の未決の提案を開く。コマンドパレットは
   `memoryEntry` ペインを開き、その行をビューで見せる。設定 > エージェントメモリーはビューを出す。

## 採らなかった案

- **仮想パス（`af-memory://…`）で FileView そのものを使い、ファイル API がそのパスを `member-save`
  に回す。** 流用できるコードは最も多い。しかし FileView（約 1,000 行）は作業コピーのパスを前提に
  できている。git の変更バー、probe、外部変更の追従、編集提案、送信ピル。そのどれにも「出ない」を
  教えることになる。代わりに後の段階で `useFileEditor` に `{load, save}` アダプタを持たせれば、
  未保存ガード、復元、競合処理を FileView 抜きで持ってこられる。
- **ストアの Markdown ファイルを直接開く。** 秘密情報スキャン、リビジョン照合、署名（0113）を
  飛ばすので出さない。
- **エディタ内の frontmatter。** 最もファイルらしいが、保存時の YAML 解析とそのエラーの説明が要る。
  オーナーはフォームを選んだ。
- **マスター・ディテールをペインに残し、ビューはランチャーとして足す。** リストがペインの幅に
  残ったままで、それが問題そのものである。

## 影響

- アクティビティバーのビューは 7 つになり、スマホのスワイプで送るビューも 1 つ増える。
- メモリーはセッションの横で普通のペインタブとして開き、保存済みレイアウトにも残る。
- `memoryMasterDetail.tsx` は、ビューが使うデータのフックと、ペインの詳細の部品に分かれる。スマホでの
  2 画面レイアウトは不要になる。ドロワーとペインがすでに 2 画面だからである。

## 注記

- 2026-11-20: `useFileEditor` が任意の `FileEditorIO`（`load`・`save`）を受け取り、既定はファイル API のままにした。「検討して退けた案」にある adapter の最初の段階にあたる。メモリのペインはまだ使っていない。#4569 の残りがそれにあたる。
- 2026-11-20: 既存メモリの `memoryEntry` ペインは、adapter（`memory/memoryEntryIO.ts`）を付けた `useFileEditor` で編集する。バッファは description・type を入れた JSON 1 行と本文、ストアの版番号は読んだ本文のハッシュで引き、member-save の `memory_conflict` は `revision_conflict` に写す。未保存ガードとファイル編集の解決パネルがメモリにも効く。新規メモリ（バッファの鍵にする名前がまだない）は下書きをペインに持ったままで、それをフックへ移すのが #4569 の残り。
