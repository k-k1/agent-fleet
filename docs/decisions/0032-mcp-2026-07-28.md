# 0032. Take MCP 2026-07-28 by serving both eras at once — discriminated on one thing, the version in `_meta`

English | [日本語](0032-mcp-2026-07-28.ja.md)

- Status: **adopted and implemented** (the probe and af's two servers). Aligning authorisation with
  OAuth 2.1 is out of scope. The design and the measurements are in
  [docs/49](../log/49-mcp-2026-07-28.md).
- See also: [0006](0006-mcp-unified.md) (the MCP af provides; PAT authentication) /
  [0031](0031-mcp-registry.md) (the MCP registry — the probe's owner)

## Context

MCP 2026-07-28 is final. It contains a **breaking change**: the `initialize` handshake and
`Mcp-Session-Id` are gone, and the version, client information and capabilities travel in `_meta` on
every request.

af stands on both sides of MCP: it provides it (the CP's `/mcp`, the Agent's `mcp-stdio`) and it
consumes it (the registry's connection test). Going through the code, **af's two servers were
already effectively stateless** (a plain switch; `initialize` merely echoes the version; no session
ID is issued). The heaviest part of this revision, removing session state, is nothing to do.

On the other hand, all three places declared `2025-06-18`, which was **already one version behind**
the current release, `2025-11-25`.

## Decision

### 1. Serve both eras at once (keep the old `initialize`)

The specification says explicitly that a server wanting to support both may keep implementing the
old `initialize` (SEP-2575, Backward Compatibility). Dropping it would stop claude and codex that
have not been updated yet from connecting to af's MCP. **When a user's CLI gets a new version is
outside af's control**, and there is no reason for us to set a deadline.

**Old-era behaviour does not change by one byte.** No new-version validation and no header rules are
applied, and an unknown method still returns `200` + `-32601` as before. That the new-version support
is a no-op for existing clients is pinned by regression tests.

### 2. The era is discriminated on the presence of `protocolVersion` in `_meta`, and nothing else

An old client never sends this key and a new client always does. The aim is **to keep the branch
point singular**: secondary material such as the presence of a header, the method name or the
User-Agent is never consulted. With several sources of judgement, nobody can explain what happens
when they disagree.

### 3. Validation runs in the order "version → required `_meta` fields → header check"

The version comes first so that a mix-up between old and new produces an **actionable** error
(`UnsupportedProtocolVersionError` plus a `supported` list). In the opposite order, a client that is
merely on an old version is told "your header is wrong", and it cannot renegotiate.

The header check (`-32020`) is both a requirement of the specification and a security requirement.
When an intermediary judges by header and the server judges by body, a disagreement between them is
itself a mix-up. The base64 sentinel in `Mcp-Name` is **decoded before comparison** (otherwise a
non-ASCII name always mismatches).

### 4. The probe leads with `server/discover`; silence falls back to the old version after 2 seconds

For stdio the specification prescribes "send `server/discover` first, and fall back to the old
version on `Method not found`". We use the same procedure over HTTP as well — it keeps to one path,
and it incidentally yields `serverInfo` and `supportedVersions`, which enriches the connection test's
display.

There is one addition not in the specification. **An old server that does not respond at all to an
unknown method is taken to be old after 2 seconds.** JSON-RPC obliges it to return `-32601`, but
implementations that stay silent exist in reality, and waiting for them eats the probe's whole
timeout so that all we can say is "it timed out". In exchange for a wasted second or so, an
inexplicable hang disappears.

The connection test's result states **which era answered**. During the transition, "it connects, but
over the old version" versus "it is connected on the new version" is operational information.

### 5. Emit `serverInfo` in both shapes, and read both shapes

Where `serverInfo` sits in `DiscoverResult` differs between SEP-2575 (top level) and the draft
document (under `_meta`). So that **it does not break whichever becomes canonical**, the server emits
both and the client reads both. An extra field is harmless, and there is no reason to bet on one.

### 6. Authorisation (aligning with OAuth 2.1 / OIDC) is out of scope here

Six SEPs repositioned MCP servers as OAuth 2.1 resource servers, but the CP is primarily PAT Bearer,
which is exactly the premise of [0006](0006-mcp-unified.md) ("PAT first, OAuth later"). Touching that
is not keeping up with a version — it is reconsidering the authentication method, and belongs in a
separate ADR.

Incidentally, SEP-2575's requirement that "with sessions abolished, every request must be
authenticated independently" is already satisfied, because the CP has always resolved the PAT per
request.

## Options rejected

| Option | Why rejected |
|---|---|
| Migrate to the new version only and delete `initialize` | Every un-updated CLI stops connecting. The specification itself permits supporting both |
| Defer new-version support until the CLIs support it | af's servers were already one version behind. Deferring only widens the gap, and here the addition is small |
| Discriminate the era by an HTTP header (the presence of `MCP-Protocol-Version`) | It does not exist on stdio. Splitting the discriminator by transport makes the behaviour inexplicable (decision 2) |
| Add `resultType` only in the new era | An old client simply ignores unknown fields. There is no benefit to adding a branch |
| Build a shared module for the CP and the Agent | The two binaries are separate modules, and a shared module was already deferred in [0012](0012-go-internal-refactor.md). We continue to accept the duplication of two implementations of the same shape |
| Move onto the Go beta SDK | The addition is small and the SDK is still beta. Compare once it is stable (left over) |

## Results

- af's MCP works from both old and new clients. Zero impact on old clients.
- The registry's connection test can inspect both old and new servers, and reports which one
  answered.
- The version declaration is now `["2026-07-28", "2025-11-25", "2025-06-18"]`, closing the
  one-version gap.

## Left over

- Aligning authorisation with OAuth 2.1 / OIDC (decision 6).
- `subscriptions/listen` / MRTR / cache directives / the MCP Server Card — all features af does not
  currently use.
- Settle on one shape once the specification's `serverInfo` inconsistency converges (decision 5).
