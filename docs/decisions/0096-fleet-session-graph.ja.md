## 背景

**この図は 3 本の ADR が名指しで空けてきた穴である。** 0027 は「全フリートの俯瞰は別図・別タスク」と
書いて送り出し、0041 決定 9 は「peer の帰属は会話ではないので `operator-graph/<conv>.jsonl` では
表現しきれない＝俯瞰図が要る」と**必要性まで確定**させ、0078 は却下欄で「一覧ペインとは別物」と
線を引いた。空いたまま 3 か月が経っている。

同じ期間に、見たいものの形が変わった。0027 を書いた時点のフリートは「1 人のオペレーターが N 本の
セッションを駆動する」放射状で、往復はシーケンス図に載った。いまは ADR 0073（セッションが
セッションを起こす）と 0041（セッション同士が直接話す）が入り、**家系が 2 段・3 段に伸びる**。
親が子を起こし、子が親に報告し、兄弟が直接メッセージを投げる——この形は「誰が誰に何を言ったか」
より先に「**いつ、何本が、同時に生きていたか**」が読めないと理解できない。

利用者の要求は GitHub の network graph の形で出された。

```
Session A     ○--*-----+-------+-----+--×
Session A-c1      +-----⤴       ↿     |
Session A-c2      +-------------+     ⇂
Session D                   ○--------+----------×
```

一方で、**いま実際に引ける線は限られている**（2026-09-20 に実測。詳細は docs/101 §1）。

| 要素 | 現状 |
|---|---|
| ○ 誕生・× 終了 | **ある**（`session.Meta` の `CreatedAt` / `StoppedAt`、異常終了は `ExitReason`） |
| + 分岐（spawn / fork / 引き継ぎ） | **ある**（`Origin` + `OriginSession`・ADR 0073。ただし `ForkFrom` は会話 id で逆引きが要る） |
| ↿ ⇂ peer の矢印 | **無い**。`session_peer.go` は永続記録を一切持たない（レート制限だけがメモリ上） |
| → 指示 / ← 報告 | `instr-ledger` に `delivered_at` / `reported_at` として**部分的にある**（後述の理由で図の根拠にはしない） |
| 稼働帯（いつ働いていたか） | **無い**。状態の履歴はどこにも残らず、`tokenSpends` は数値の列だけで時刻を持たない |
| 7 日より前 | **消える**。停止セッションの meta は `session.StoppedTTL()`（既定 7 日）で prune され、系譜も一緒に消える |

なお 0027 決定 2 が新設しようとした「指示の台帳」は、その後の ADR 0035（報告 v2・2026-07-29）が
`instr-ledger/<session>.json` として**先に実装してしまっている**。0027 のまま着工すると二重台帳になる。

## 決定

### 決定 1 — 図は 1 枚にする。0027 の縦シーケンス図は本 ADR が置き換える

**レーン＝セッション（縦）／時間（横）**の 1 枚だけを作る。0027 は superseded とし、
`console/src/types/opgraph.ts`（唯一入っている成果物・どこからも import されていない）は本 ADR の
P0 が新しい契約で置き換える。

- **なぜ転置するのか。** レーンの本数（セッション）は有界で数十、時間は無限に伸びる。**有界な軸を
  縦に置く**のが network graph が正しい理由であり、シーケンス図（縦＝時間）はスクロール方向が
  時間なので「いま何本が同時に走っているか」が 1 画面に収まらない。0073 と 0041 が家系を 2〜3 段に
  伸ばした今、その 1 画面こそが読みたいものである。
- **なぜ併存させないのか。** 2 図を残すと台帳・純関数・ペイン種別・i18n がそれぞれ 2 つになる。
  しかも 0041 決定 9 が確定させたとおり、0027 側は **conv 単位では peer を表現できないまま**残る
  ——直らない図を保守することになる。
- 0027 が持っていた「1 オペレーター会話の往復」は失わない。**会話 id による絞り込み**（その会話が
  触れたレーンだけを残す）として新図に吸収する。

### 決定 2 — 台帳は 2 本に分ける。系譜は永続・活動は回転

```
~/.config/agent-fleet/fleet-graph/lineage.jsonl          # 追記・永続（prune しない）
~/.config/agent-fleet/fleet-graph/activity-<YYYY-MM-DD>.jsonl  # 日次回転・既定 30 日
```

- **保持期間が違うものを 1 ファイルに混ぜない。** 混ぜると、活動行の回転が系譜行を道連れにする
  （逆に系譜に合わせて永続化すると、活動行が無限に伸びる）。行数の桁も違う——系譜は 1 セッション
  数行で一生ぶん、活動は 1 日数千行（見積もりは docs/101 §3）。
- **書き込みは `O_APPEND` の 1 行追記**とし、`fstore` の read-modify-write は使わない
  （メモ `fstore-no-read-modify-write`：素の read→変更→write は並行する書き手の行を落とす）。
  追記は分岐点が無いので、複数の書き手（HTTP ハンドラ・リコンサイラ・観測点）が素直に同居できる。
- **読み出しは窓で切る。** 日次ファイルなので「直近 24 時間」は 1〜2 ファイルしか開かない。
  ADR 0087（EFS のメタデータ IO が本番全体を遅くした）を踏まえ、**ファイル数を増やす方向の設計を
  取らない**（セッションごとのファイルにはしない・1 イベント 1 ファイルにはしない）。
- **時刻の表現は台帳と DTO で違い、変換は必ずサーバが行う。** 台帳の行は **RFC3339（ミリ秒）**
  ——jsonl を人が grep する前提のファイルで、リポジトリの他の台帳（`Meta` / `instr-ledger`）と
  **同じ形式**を使う。精度だけ上げるのは、変化したときだけ書く設計では**同じ 1 秒の中に 2 つの
  遷移がありうる**からで、秒精度（`instr-ledger` はそちらを意図的に選んでいる）では順序が壊れる。DTO（`FleetGraphPage`）は **unix ミリ秒の数値**——ブラウザ側で日時を解釈させない。
  型ファイルが millis 一本なのに台帳の例が RFC3339 だと、**S-BE がどちらで書くかは読んだ文書で
  決まってしまう**ので、ここで方向を固定する。
- **日次ファイルの日付は UTC** とする。窓（millis）からファイルを選ぶ側とワークスペースのローカル
  タイムゾーン（ポリシーどおり `date` はローカル）が食い違うと、境界の 1 日が無言で読み落とされる。

### 決定 3 — 稼働帯は「観測された状態遷移」だけを書く。転写は走査しない

一覧（`GET /sessions`）が**すでに全セッションぶん算出している** live state を、**変化した瞬間だけ**
1 行にする。`working → idle → question → limited …` の遷移と時刻。

- **なぜ転写ではないのか。** 転写のターン時刻から稼働帯を作る案は、kind ごとに転写の在処が違う
  （claude の jsonl / codex の rollout / opencode の SQLite …）ので、**claude だけ埋まって他が空白**に
  なる。ADR 0078 の P1.1 が同じ壁で止まっている。live state はすべての kind が既に通っている
  述語なので、**遷移を書くだけなら kind 非依存**で、コストは O(遷移数)＝1 ターンあたり数行。
- **なぜポーリングを足さないのか。** ADR 0078 が最も避けた形は「カードごとに `/messages` を叩く」
  ＝4 秒 × セッション数である。本決定は**既に走っている観測に 1 行の追記を相乗りさせるだけ**で、
  新しいタイマーも新しいプロセスも作らない。
- 🔥 **観測の間隔は「誰かが見た間隔」であり、一定ではない**（実測・docs/101 §2）。Console を開いて
  いれば 4 秒、誰も見ていなければ CP の idle-stop reaper が 1 分（`AF_IDLE_SWEEP_INTERVAL` 既定
  `1m`・`control-plane/main.go`）、**reaper を切った配備では観測がゼロになる**。Agent 側に全
  セッションを回す常設の掃引は存在しない（`chat_report_reconcile.go` の sweep は**未報告の行を持つ
  セッションだけ**を回る）。
- したがって: **観測が無かった区間は「稼働していない」ではなく「不明」として描く**（帯を塗らず
  斜線にする）。これは報告 v2 が高い授業料を払って得た規則——「**無ファイルは『不明』であって
  idle ではない**」（docs/log/51）——の 2 度目の適用である。
- Agent の再起動直後は、全セッションの現在状態を 1 回まとめて書く（`resync` 行）。再起動を挟んだ
  区間が「不明」として正しく残る。
- **状態の語彙は台帳専用の `LedgerState` として凍結する。** `SessionState`（`types/session.ts`）を
  そのまま使わない理由は 2 つ: あれは **`""` が idle** という Console の行の都合を持ち、
  `limited` / `blocked` / `auth` / `spend_limit` / `failed` / `aborted`（`agents/notify.go`）や
  `compacting`（`agents/codex`・自動圧縮中＝明確に稼働中）を含まない。TS では
  `SessionState | string` は `string` に潰れて**何も縛らない**ので、リテラル union で書き下す。
- 🔥 **語彙外は `idle` に倒さず `unknown` にする。** `""`→`idle` は正しいが、**知らない綴りを
  `idle` にするのは危険な側への転び方**である——ある kind が新しい稼働中の状態を報告し始めた瞬間、
  その区間は「何もしていなかった」として記録されてしまう（`compacting` が実在し、これを
  取りこぼしかけた）。生の綴りは `raw` に残す。
- **正規化は 1 つの規則・2 か所の実装。** 書き手（Agent・Go）と、**ライブの `Session.state` から
  現在の帯を作る読み手（S-LOGIC・TS）**の両方が通る——`Session.state` は
  `SessionState | string` で、同じ `""` と同じ未知の綴りを運んでくるからである。同じ表を 2 言語で
  持つことになるので、**同一の fixture を Go と vitest の両方の試験に置く**（食い違うと「帯の色と
  行のチップが合わない」ともっともらしく壊れる）。
- **状態 → 帯（`SegmentKind`）の写像も契約に入れる**（`SegmentKindByState`）。
  `working`・`compacting`→`active`／`idle`・`failed`・`aborted`→`idle`／`question`・`plan`・
  `permission`・`blocked`・`auth`・`limited`・`spend_limit`→`waiting`／`unknown`→`unknown`。
  **帯は色のため、正確な語は tooltip のため**
  に `GraphSegment.state` が別に残るので、`limited` に専用の帯は要らない。
- **重複行の防止は書き手が担う。** 観測を駆動するのは一覧ハンドラ（GET）で、**Console（4 秒）と
  reaper（1 分）が同時に叩きうる**。書き手はセッションごとの直前状態をプロセス内に持ち、
  **変化したときだけ**書く（セッション単位の mutex で直列化）。`StateEvent.from` はその表から
  埋め、**表に無ければ省く**——`from` が無いのは「直前は不明」であって「直前は idle」ではない。
  再起動でこの表は空になるので、そこは `resync` が境界を打つ。

### 決定 4 — 往復の矢印 3 種（指示・報告・peer）は同じ 1 行形式で書く。`instr-ledger` は読まない

```jsonc
{"ts":"…","ev":"instruct","from":"conv:<id>","to":"<session>","source":"operator","excerpt":"…"}
{"ts":"…","ev":"report","from":"<session>","to":"conv:<id>","kind":"answer-ready"}
{"ts":"…","ev":"peer","from":"<session>","to":"<session>","intent":"request"}
```

**`from` / `to` の語彙は「レーンになるもの」と「ならないもの」の 2 群に分かれる。** レーンになるのは
セッション名だけで、`conv:<id>`（チャット会話＝オペレーター）・`user`（Console のコンポーザや端末の
打鍵）・`schedule`（定時実行・ADR 0021）・`bridge:discord` / `bridge:slack` は**レーンを持たない**。
これらとの往復は**図の上端／下端へ抜ける矢印**として描く（決定 8-2）。

- **`instr-ledger` を図の根拠にしない理由は、それが履歴ではなく作業リストだからである。**
  閉じた行は新しい 20 件だけを残して捨てられ（`instrClosedKeep`）、`cancelled` / `reopened` で
  状態が書き換わる。図の根拠にすると**古い指示が黙って消え、reopen で過去の時刻が動く**。
- **peer はそもそも載らない。** ADR 0041 決定 4（arm を一切いじらない）は AF 版の回避不能な必須
  要件であり、peer 送信が `instr-ledger` に行を作ることは将来も無い。3 種のうち 1 種だけ別経路に
  すると、図の読み手が 2 つになる。
- `instr-ledger` は「**報告が済んだか**」の権威のまま据え置く。本 ADR はそこを一切変更しない
  （状態機械に触らない＝報告の消失というクラスの事故を持ち込まない）。
- 本文の抜粋は **≤140 字・単一行・表示専用**（0027 決定 2 の方針を継承）。描画時にサニタイズし、
  prompt injection の扱いは docs/30 を踏襲する。

### 決定 5 — レーンの id はセッション名（乱数スラグ）。表示名は別に持つ

台帳の行はセッション**名**だけで紐づける。名前は乱数スラグで**再利用されない**
（メモ `session-slug-immutable-managed-no-env`）ので、改名・引き継ぎ・fork を経ても行は壊れない。
図に出す文字列は `Display`（title → claude ラベル → `repo@MMDD-HHMM`）で、**スラグを単独で人に
見せない**という既存の規約（`session.Display` のコメント）をそのまま守る。

### 決定 6 — 系譜の行は自動 prune では消さない。人が明示的に消したときだけ消す

ADR 0073 は「系譜を永続させたいなら別の置き場（台帳）が要る——本 ADR では取らない」と判断し、
**docs/log/94 でその対価が利用者に見える形になった**（セッションを 1 本削除すると子の入れ子と色が
その場で失われる）。本 ADR はこの判断を覆す。理由は、俯瞰図にとって**系譜が消えることは線が
消えること**であり、7 日の prune（`session.StoppedTTL()`）で親が消えた瞬間に子の分岐線の根が無くなる
からである。

- `lineage.jsonl` は**停止 TTL の自動 prune の対象外**。
- ただし `DELETE /sessions/{name}?reclaim=1`（回収）と cleanup の削除導線では**行も消す**。
  削除は削除であるべきで、「消したのに図には残っている」は利用者の期待に反する。
- 行が持つのは `{ts, ev, name, kind, repo, origin, originSession, display}` だけで、
  **プロンプト本文も報告本文も持たない**。消えるべき中身を最初から置かない。
- 🔴 **2026-09-20 追記（ADR 0097 と同日に入った）**: 本決定の動機だった「**7 日の自動 prune が
  系譜を消す**」は、[0097](0097-session-retention.ja.md) が prune の削除そのものを廃したので
  もう起きない（TTL は `Archived = true` の書き戻しになった）。**決定は変えない**——削除で系譜を
  消す規則も、台帳が要る理由（活動と矢印は `Meta` に無い／アーカイブ済みは一覧に出ないので
  ライブ地図から引けない／導入以前の書き起こし）も残る。変わったのは 2 点: ①下の「TTL prune だけ
  残す」は**呼び手ゼロの枠**になった（＝いま `RemoveMeta` を呼ぶ経路は**すべて人の削除**）
  ②遡及の骨格は**7 日で切れなくなった**（アーカイブ済みの meta は消えないので、決定 8 の
  3 段目はそのぶん長く伸びる）。
- 🔥 **消す経路は「人の操作で meta を忘れる所すべて」**（P1 で確定）。`session.RemoveMeta` の呼び出しは
  5 箇所あり、**7 日の自動 prune（一覧ハンドラ）だけが系譜を残す**。残る 4 つ——`DELETE /sessions/{name}`
  （reclaim の有無を問わず）・**`/stop`**（コード自身が「これが Console の削除」と書いている）・
  作業コピー削除の巻き添え（削除ロックがこの経路も拒む＝製品として削除扱い）——では**行も消す**。
  ⚠️ **経路を列挙したコードにしない**。呼び出しが増えたときに気づける形（件数の固定か、消去を
  `RemoveMeta` 側へ寄せる）で押さえること。
- 🔥 **削除しても活動行は残る**（回転するまで最大 30 日）。系譜を消すと、その id を名指す
  `peer` / `report` の行だけが残り、**素朴に実装するとセッション間の peer が「図の外から来た矢印」に
  化ける**（レーンが作れないので外部アクターに落ちる）。活動行まで遡って消す案は取らない——
  追記専用のファイル 30 本を書き換えることになり、ADR 0087 の逆を行く。代わりに
  **「系譜の無いレーン id は *削除済みレーン* として、線を引かない 1 行で描く」**（`erased`）。
  **帯（稼働の矩形）は描かない**——状態の行は回転まで残るが、それで帯を描くと**利用者が消した図を
  組み直す**ことになる。矢印だけ残すのは、消すと**相手のレーンのメッセージが「図の外から来た」に
  化ける**からであって、削除済みレーンの都合ではない。
  ラベルに出せるのは**スラグだけ**なので、**「削除済み」の語を添えるのは S-VIEW（i18n）**とする
  ——スラグを単独で人に見せない、という既存の規約（`session.Display`）はここでも守る。
  消えるのは**中身**（表示名・リポジトリ・系譜）であって、id の痕跡は活動の保持期間だけ残る——
  この非対称は意図であり、利用者に見える形（「削除済み」のラベル）で示す。

### 決定 7 — 範囲は 1 ワークスペース。読み出しは Agent の 1 本、CP は許可リストに 1 行

`GET /api/fleet-graph?since=…&until=…` を Agent に足し、CP の**明示許可リスト**に登録する
（メモ `cp-rest-proxy-allowlist`：CP は素通しではなく許可リスト方式）。テナント横断の俯瞰は
管理者の別表（`GET /api/admin/sessions`）の仕事であって、この図の仕事ではない。

🔥 **系譜は窓で切らない。** 応答の `lineage` は「窓の中のイベント」ではなく、次の 3 つの和である:
①窓の中の全イベント、②**窓に重なるレーンの系譜イベントは全部**（`birth`・`convid`・`death`・
`revive`・`archived`）、③そのレーンの祖先の `birth`（家系順・決定 9 のため）。
②を `birth` だけにすると、**1 日目に生まれ・2 日目に死に・3 日目に再開したレーン**が、4 日目の
24 時間窓では `death` も `revive` も無しに届き、`runs` が 1 本に潰れて**停止していた丸 1 日が
図から消える**。系譜は 1 セッション数行の永続台帳（docs/101 §101.3）なので、切って節約するものが無い。素直に窓で切ると、**3 日前に
生まれて今も動いているレーンに `kind` も `origin` も表示名も無い**——ライブの `Session` には
`origin` が無い（`originSession` だけ）ので、Console 側では埋められない。窓に重ならない祖先は
**並びと表示名のための文脈**であってレーンにはしない。

### 決定 8 — 時間軸は線形。既定の窓は直近 24 時間、右端が「いま」。遡及は有界でよい

- ズーム／パンで窓を動かす。ライブのレーンは右端で脈打つ（0027 決定 1 が手書き SVG を選んだ理由＝
  ライブ状態・稼働アニメ・クリック起動は静的な図では賄えない、をそのまま継承する）。
- **遡れる範囲は有界でよい**（利用者の合意・2026-09-20）。左へパンすると 3 段で減衰する:
  **活動（矢印・稼働帯）は保持 30 日 → その先は系譜と生没だけの骨格 → 導入以前は
  `Meta` から書き起こした 7 日ぶんだけ**。どこで何が減ったのかは図の背景に明示する
  （「ここから先は骨格だけ」の境界線を引く）。無言で薄くならない。
- **却下: 空白の畳み込み**（全レーンが idle の区間を潰す）。稼働帯を描く図で空白を潰すと、
  「**そこで止まっていた**」という一番読みたい事実が消える。
- **却下: コミット順の等間隔軸**（GitHub network graph 本来の形）。イベントの間隔——ある指示から
  報告まで 40 分かかった、という事実——が消える。横軸を時間にするのが利用者の要求そのものである。

### 決定 8-2 — セッションでない発信元にはレーンを作らない。図の上下へ抜ける矢印にする

会話（`conv:<id>`）・人（`user`）・定時実行（`schedule`）・ブリッジ（`bridge:*`）との往復は、
**上端から降る矢印（指示）と上端へ抜ける矢印（報告）**で描く。どの会話かは矢印の色と tooltip で示し、
クリックでその会話を開く。

```
        ↓指示(会話)   ↑報告    ↓定時

Session A   ○--*-------+--------+------+--×
Session A-c1     +------⤴
Session A-c2     +--------------+
Session D              ○----------+--------×
```

- **なぜレーンにしないのか。** この図のレーンは「**生まれて死ぬもの**」の帯であり、x 軸は
  その生存期間を意味する。会話・人・スケジューラは生没を持たない（常にそこにある）ので、
  レーンにすると**同じ横線が 2 つの意味を持つ**ことになる。軸の意味は 1 つに保つ。
- 却下: 会話も上部に固定レーンとして置く案（ADR 0027 のシーケンス図に最も近い形）。往復が
  レーン間の線で閉じる利点はあるが、上記のとおり軸の意味が割れる。
- 🔥 **描かれないレーンが相手のときの規則は、矢印の種類で分ける**（P1 で確定）。**往復**
  （instruct / report / peer）は、相手が「既知だが今回の窓・絞り込みで除外された**内部の**レーン」
  なら**矢印を落とす**——残すと `fromRow:null` ＝外部発信元と区別がつかず、決定 6 が 1 段落かけて
  防いだ誤帰属そのものになる。**家系**（spawn / fork / handoff）は逆に、親に行が無くても
  **矢印を残して `fromRow:null`** とし、決定 9 の「**欠けた親は左端の印**」として描く。
  `variant` が家系かどうかで機械的に区別できるので混ざらない。「いつ誰から生まれたか」はこの図の
  主目的なので、窓を狭めたら枝が黙って消える、は受け入れない。
- 却下: 矢印を描かずレーン上の小さな印だけにする案。密度は下がるが、**報告が返ったかどうか**が
  ひと目で分からなくなる（0041 決定 10 が「人間が一番見たい場面で見えない」ことを受入条件から
  外さなかったのと同じ理由）。

### 決定 9 — レーンの並びは家系。クリックの規則は 0078 からそのまま借りる

親の直下に子、兄弟は古い順、根は新しい順（ADR 0078 決定 6 と同じ規則）。**親が窓の外でレーンを
持たなくても、子は親の id と `rootId` を持つ**（`GraphLane.parent` / `rootId` / `depth`）——
ここを「描かれる親が居るときだけ」にすると、親が窓の左端から外れた瞬間に子が根に昇格し、
**兄弟が窓の取り方次第で離れる**。並びの鍵は `rootId` であって、描かれているかどうかではない。

**親の系譜が削除されている場合**（決定 6）は鎖がそこで止まる。その**辿れない親の id 自身を
`rootId` とし**、族の並び順の鍵は「**その族で分かっている最古の `birth`**」を使う——根の `birth`
そのものが存在しないことがあるのに「根は新しい順」は常に存在する鍵を要求するからである。
段は `depth`（辿れた祖先の数）で字下げし、**depth 1 の行が無いまま depth 2 が並ぶ**ことを許す
（親が居ないからといって子を根に繰り上げない。欠けた親は左端の印で示す）。
クリックは
**隣に余地があれば隣のペイン・スマホは同じペイン・修飾キーと中クリックは別ペイン**
（0078 決定 3 の改訂版）。同じ操作感を 2 通り作らない。

### 決定 10 — 新しいペイン種別 `fleetgraph` を 1 つ足す。入口は 3 つで、一覧ペインと相互に行き来する

ADR 0049 決定 4（PaneKind を安易に増やすな）の例外条件を、0078 が満たしたのと同じ形で満たす:
**眺め続ける面**でありモーダルに置けない、レイアウトと URL に載る、ポップアウトできる。

🔥 **入口を決めるところまでが決定 10 である**（2026-09-20 追記）。初版はペイン種別を足すとしか
書かず、実装は**リーダーキー `g f` とコマンドパレットだけ**で出荷された——**ボタンがどこにも無い**。
比較対象の 0078 決定 8 は「操作バーのボタン＋レール上部のレイアウト図＋`g s`」の 3 つを持つ。
同じ 3 つを置く。

| 入口 | 置き場所 |
|---|---|
| 操作バーのボタン | `WsBar.tsx`（「セッション一覧」「画像生成」の隣） |
| レール上部のレイアウト図 | `LayoutMap`（ペインが 2 つ以上のときだけ出る） |
| リーダーキー / コマンドパレット | `g f` |

🔥 **レイアウト図だけに置くのは不可**。あれは**ペインが 1 つのとき消える**ので、一番普通の場面で
入口が無くなる（メモ `sessions-overview-pane` の罠）。だから操作バーのボタンが要る。

**一覧ペイン（`sessions`）と俯瞰図は相互に切り替える。** 同じ「フリートを見る」面の 2 つの見え方
なので、**既定は同じペインでの差し替え**（`setPaneTarget`）とし、Ctrl/⌘・中クリックのときだけ
別ペインに開く（0078 決定 3 の修飾キーの規則をそのまま借りる）。両ペインのヘッダが互いの
ボタンを持つ——片方向だけだと、俯瞰図から一覧へ戻る道がまた無くなる。

### 決定 11 — 描画は手書き SVG、レイアウトは純関数

`console/src/lib/fleetgraph.ts`（純関数・`.ts`）＋ `features/fleetgraph/FleetGraphView.tsx`。
SCM のコミットグラフ（`lib/gitgraph.ts` / `features/scm/CommitGraph.tsx`）の「純関数レイアウト＋
インライン SVG」を構造テンプレートとして流用する（0027 決定 1 と同じ判断）。
色は kind 色を使い、全 twin を grep で突合する（メモ `kind-color-css-checklist`）。

🔥 **ただし稼働帯（バー）の色は kind 色ではなく「状態の色」にする**（利用者決定・2026-09-21 の改訂）。
`stateInfo()` が使う色をそのまま採る——**進行中＝`--accent`／待ち＝`--warn`／待機＝`--muted2`**。
初版は稼働帯だけ kind 色で塗っていたが、**同じ行に並ぶ状態チップ（決定 15）と色が食い違う**:
質問待ちの codex レーンが「緑の帯＋橙のチップ」になり、同じ瞬間について図とチップが違うことを言う。
**どのエージェントかはレーンの線（`--lane-color`）と、ラベル列の kind アイコンが引き続き持つ。**
- 帰結（意図）: 帯が線を覆うので、**働いている区間では kind 色がほぼ見えない**。
  「いま誰が動いているか」を色で読むのはラベル列のアイコンの役目になる。
- 突合は目でなく数値で: 帯の `fill` と `.session-state.working` の `color` を**ブラウザに解決させて
  比較する**（`console/scripts/fleetgraph/check.mjs`）。`var()` の名前どうしを比べる試験は、
  2 つの変数が別の色を指していても緑になる。

### 決定 12 — 線種が「まだ居るか」を言う。停止中は点線、アーカイブ済みは薄い点線、もう居ないものは × で終端

レーンの横線は 4 通りに描き分ける（利用者の指示・2026-09-20）。

| 状態 | 線 | 意味 |
|---|---|---|
| 稼働中 | 実線 ＋ 稼働帯 | いま走っている（右端で脈打つ） |
| 停止中（再開可） | × のあと**点線**を右端まで | 一覧にまだ居る。**再開できる** |
| アーカイブ済み | × で**終端**（線も帯も伸ばさない） | 畳んである。復元できることは**ラベル列のチップが語で言う** |
| prune 済み・削除済み | × で**終端**（線を伸ばさない） | もう居ない。系譜台帳の行だけが残っている |

🔥 **アーカイブ済みは 2026-09-21 に「薄い点線」から「終端」へ改訂した**（利用者指示）。理由は 2 つ。
①**畳んだものが図の端まで描かれ続ける**——人が意図的に片付けたレーンが、生きているレーンと同じだけ
図の幅を占めていた（薄い点線に加えて、`SegmentKind: "archived"` のグレーの帯も右端まで伸びていた）。
②**線種にこの区別を負わせる必要がなくなった**——決定 15 でラベル列に状態チップが入り、「アーカイブ」
という語がそのまま出る。線種の細い差（点線 vs 薄い点線）より語のほうが確実に読める。
**停止中（再開できる）の点線は残す**: そちらは「一覧に居て再開できる」という、いま行動できる情報である。
`SegmentKind` から `"archived"` は**削除した**——生み出す側が消えた語彙を型に残すと、ビューに
**絶対に実行されない分岐**が残る。

**規則は 1 つ: 点線＝まだ居る（再開できる）／終端＝もう居ない、または畳んである。** × はどの場合も「終わった時刻」
ではなく「**終わったと初めて観測された時刻**」である（`Meta.StoppedAt` は遅延で入る。決定 3 の
観測の話と同じ性質）ので、図はそれを ×の tooltip に明記する。

🔥 **1 本のレーンの生涯は「複数の走行（run）」である。** 停止したセッションを再開すると
`Meta.StoppedAt` は**クリアされる**（`sessionx/session_handlers.go` の一覧・`session_tmux.go`・
`session_driver.go`）。つまり ○──×──（点線）──○──× が 1 レーンに並ぶ。台帳には
`ev:"revive"` を足し、`GraphLane` は `runs: LaneRun[]` を持つ。死と再生を 1 組しか持てない
モデルにすると、2 回目の × がどの区間の終わりか決まらず、**死んで再開した区間が「停止中の点線」に
化ける**。
- 限界（意図）: `Meta` からの遡及書き起こしでは、**過去の停止・再開の周期は復元できない**
  （`Meta` に残っているのは最後の `StoppedAt` だけ）。導入以前のレーンは run を 1 本として描く。
- 🔥 **生きたまま畳むときは `death` を書いてから `archived` を書く**（P1 で確定）。
  `HandleArchiveSession` は**生きているセッションの pane を kill して畳む**が、終了を遅延で気づく
  唯一の場所＝一覧ハンドラは `if m.Archived { continue }` で**アーカイブ済みを飛ばす**ので、
  死は永久に書かれない。台帳が `[birth, archived]` だけになると、読み手では run が開いたまま
  ＝**線が右端まで実線で伸び、× も出ず、稼働中と区別できない**。読み手側にも「archived で run が
  開いていたら `archived` の時刻で閉じる」防御を置くが、それは**遡及データ用**であって、
  正しいのは書き手が死を書くことである。
- **最後の run が開いたまま「もう居ない」場合**（death を書く前に Agent 自身が落ちた・削除された）
  は、その run を**最後に何かを観測した時刻で切り**（`LaneRun.cut`）、× を中抜きで描いて
  **その先は「不明」**にする。`gone` を「最後の × で終端」とだけ定義すると、× が存在しないこの
  場合に終端が決まらない。

- 停止中のセッションは**既定で描く**。ADR 0078 の一覧は「既定は稼働中のみ」だが、あれは*いま*の
  断面であり、この図は*経過*である——過去から停止中を隠すと、図は空になる。
- アーカイブ済みも既定で描き、トグルで隠せる（ペインごとの設定＝`PaneContent` に持つ。
  メモ `sessions-overview-pane` の罠: React state に持つとタブ切替で消える）。

### 決定 13 — `ForkFrom` の逆引きは、系譜台帳の birth 行に「そのセッション自身の会話 id」を焼いて解く

`Meta.ForkFrom` は**会話 id**（claude=sid / opencode=`ses_…` / codex=uuid）であってセッション名では
ないので、そのままではレーンに結べない（docs/101 §101.1）。系譜台帳の `birth` 行に、そのセッション
自身の会話 id を一緒に焼く。突き合わせは「**その時刻に有効だった会話 id**」で行う。

- 🔥 **焼く id は、その kind の `Forker.ForkSource` と同じ解決を通したものでなければならない。**
  `ForkFrom` の実値を作るのはこの関数であり、**どの kind も観測側のストアから解く**:
  claude は `LiveSID()`（ドリフト後の実際の書き込み先）、codex は hook が記録した slot 別 id
  （`sids.Read`）、opencode は会話ストアの現行セッション。AF が起動時に渡した id を焼くと、
  **codex と opencode の fork エッジは永久に一致しない**。birth の時点でまだ解決できない kind は
  **空のままにして、`convid` 行で後追いする**。
- ⚠️ ただし claude には別の罠がある。fork 直後の claude は、自分の jsonl が実体化するまで
  **元セッションの転写を読む**（`internal/sessionx/session_transcript.go`）。転写の在処から
  id を推測すると子の行に親の id が入り、**エッジが自分自身を指す**。解決は必ず `ForkSource` と
  同じ経路を通し、転写の観測から導かない。
- 会話 id は途中で変わりうる。claude が自分を再起動すると argv から `--session-id` が落ち、
  **新しいランダム id で書き始める**（実測 2.1.239・`internal/agents/claude/sid.go` の `claude-sid`
  台帳がまさにこれを追っている）。ドリフトを観測したら `convid` 行を 1 行足す。
- prune 済みの親でも系譜台帳には行が残る（決定 6）ので、**7 日より前の fork でも線が引ける**。
  これは決定 6 を入れたことで初めて成立する。

### 決定 14 — 家系は親の行の「＋／−」で畳める。畳む対象は親子の縁があるレーン全部

**対象は origin で分けない**（利用者決定・2026-09-20）。`session`（spawn）・`handoff`（fork）・
`user`＋`originSession`（引き継ぎ提案から人が起こしたもの、ADR 0073）——**`originSession` を持つ
レーンはすべて**親の下に畳まれる。図の並びはもともと `originSession` の連鎖だけで決まっており
（決定 9）、畳むときだけ origin で対象を分けると、**同じ段にいる兄弟の一部だけが消える**。

- **絞り込むのは純関数側**（`buildFleetGraph` の `collapsed`）。`showArchived` と同じ形で、
  行を落として `row` を振り直す。🔥 ビュー側で二重に絞ると、純関数側のバグをクライアントの
  フィルタが覆い隠す。
- **畳んだ状態は `PaneContent` に持つ**（`fleetgraph.collapsed` / `sessions.collapsed`）。
  React state だとタブ切替で消える（メモ `sessions-overview-pane` の罠）。
- **畳んだら親の行に「＋3」を出す**（`GraphLane.hiddenDescendants`）。隠れたことが分かる印が
  どこにも無いと、図は「子が居なかった」と読める。数えるのは**全段の子孫**で、外側の親は
  内側の親が隠している分も含める——飲み込んでいるのは外側だからである。
- **＋は「押すと何かが起きる」ときだけ出す**（`GraphLane.hasChildren`）。窓の外にしか子が居ない
  親に＋を出すと、押しても何も起きない飾りになる。
- **畳みは描かれている親にしか効かない。** 親がこの窓に行を持たないなら（左端の外・削除済み）
  その子は隠さない——戻す押しどころが画面に無いからである。
- **セッション一覧ペイン（0078）も同じ操作にする**（利用者決定）。`overview.ts` の `foldFamilies`
  が同じ規則の純関数で、カードのヘッダに同じ＋／−が出る。見出しの「稼働 n / 全 m」は
  **畳む前の数**のまま——畳むたびに減ると、セッションが終わったように読める。

### 決定 15 — レーンのラベル列の状態は `stateInfo()` を借りる。4 つ目の消費者になる

図は稼働帯の色で状態を示すが、ラベル列には kind アイコンと名前しか無かった。ここに
**いまの状態のチップ**を出す（利用者要求・2026-09-20）。

🔥 **状態の導出は複製しない。** `console/src/lib/sessionview.ts` の `stateInfo()` が正で、
左ペインの行・ペインのヘッダ・一覧カードが同じものを読んでいる（ADR 0078 決定 5）。図は
**4 つ目の消費者**として同じ関数・同じ `.session-state` のマークアップを借りる。独自に導出すると、
この図だけが「入力待ち」と言い、ほかの 3 面が「利用上限待ち」と言う状態になる。

- **`GraphLaneKnown.state`（`LedgerState`）では足りない。** あれは台帳の語彙で、生きている
  レーンにしか付かず、`stateInfo()` が拾う**回数制限の再開予定・認証切れ・引き継ぎ待ち・
  異常終了の理由**を持たない。台帳の語は稼働帯の色と tooltip のまま使う。
- **一覧に載っていないレーン**（アーカイブ済み＝一覧ハンドラが飛ばす・削除済み）は聞く相手が
  居ないので、**線種が既に言っている presence の語**を出す。観測していない状態を推測しない。

### 決定 16 — 時間軸は図の上端に貼り付ける。左右の移動は「動かした距離だけ動く」

初版は目盛りを**キャンバスの最下部**に描き、ホイールは**縦も含めて全部**時間軸のパンに
変えていた（利用者指摘・2026-09-20）。どちらも図が大きいときに壊れる。

- **目盛りは上端の固定帯**（`position: sticky; top: 0`）。下端に描くと、**レーンが一画面に
  収まらないときだけ**——つまり目盛りが要る場面でだけ——スクロールしないと読めない。
- **縦ホイールはレーン一覧のスクロールに返す。** 実際にあふれるのは縦であって、それを時間軸の
  パンに使うと**折り返しから下の行に到達する手段が無くなる**。
- **横の移動は px を時間に写す**（`deltaX` とドラッグの移動量 × `span / width`）。1 イベント
  あたり窓の 12% という固定量だと、トラックパッドの 1 フリック（数十イベント）で窓が何日も飛ぶ。
- **ドラッグでパンできる**（掴む＝`grab`/`grabbing`）。`DRAG_SLOP_PX` を超えて動いたら、
  最後に出るクリックは**捕捉段階で飲む**——でないとドラッグの終わりに掴んだレーンが開く。
- **再取得は動きが止まってから**（`FETCH_SETTLE_MS`）。1 フリックで毎フレーム `/api/fleet-graph`
  を叩いていた。初回だけは遅らせない。

**2026-09-21 の追補——掴んで動かす面にする（利用者指示）。**

- **ドラッグは上下左右の両方に効く。** 横は時間、縦はレーン一覧のスクロール。縦は DOM の
  `scrollTop` を手で動かす——キャンバスは `touch-action: none` を持つので（下記）、ブラウザは
  もうこの面の縦スクロールを代行してくれない。
- **2 本指のピンチで時間軸を拡大縮小する。** 対象は**時間軸だけ**（利用者決定）——行の高さを
  一緒に変えると、ラベル列・チップ・折り畳みボタンまで連動させることになる。
- 🔥 **`touch-action` は `pan-y` ではなく `none`。** ブラウザが自分のために取っておくジェスチャは、
  **ポインタイベントとしても配られない**。ピンチと縦ドラッグの両方を自分で扱う以上、面ごと引き取る
  しかない。**ラベル列は `auto` のまま**なので、名前の上を普通にフリックすれば従来どおり縦に
  流れる（＝全部を奪ってはいない）。
- 🔥 **スマホの「左スワイプでセッションを切り替える」と衝突する。** キャンバスに
  `data-no-swipe` を付けて明示的に降りる（`app/swipeGuard.ts`）。横スクローラと誤認させる形で
  逃げると、中身の都合で判定が揺れる。
- **窓の算術は `features/fleetgraph/viewport.ts` に出した**（`clampWindow` / `panByPx` / `zoomAt` /
  `pinchSpanFactor`）。**符号がここに集まる**からである——ホイールは*視点*を動かし、ドラッグは
  *内容*を動かし、ピンチの指の比は*逆数*が倍率になる。3 つとも向きが違い、**間違えても図は
  「動かない」としか見えない**（クランプが窓を「いま」に押し付ける）。方向ごとに落ちる試験を置いた。
- **ズームは指／ポインタの位置を軸に据える**（`zoomAt` の `fraction`）。右端固定のままだと、
  つまんだ瞬間が指から逃げていく。ただし**アンカーよりクランプが優先**で、右端が「いま」を
  越えるときはアンカーを諦める。

### 決定 17 — 図の中のレーンはクリックで開かない。セッションを開くのは「名前」

キャンバスのレーン（線・稼働帯・行の当たり判定）は**クリック／タップで何も開かない**
（利用者指示・2026-09-21）。**開くのは左のラベル列の名前**で、そこは従来どおり
「隣に余地があれば隣・修飾キーと中クリックは別ペイン」（決定 9）である。

- **理由は決定 16 と一体である。** キャンバスは**掴んで動かす面**になった。掴む面と開く面が
  同じだと、**パンのつもりの指がセッションを開く**——しかも開いた先はペインなので、図の見ていた
  場所を失う。ドラッグ後のクリックを捕捉段階で飲む仕掛けは既にあるが、あれは「動いたとき」しか
  効かない。**動かないタップは正当なタップに見える**ので、面の役割そのものを分ける。
- **矢印のクリックは残す**（会話やレーンを開く）。細い線を狙って押すのは意図的な操作で、
  パンと取り違えようがない。
- **行のホバー強調は残す。** あれは「どの行を見ているか」を言うためのもので、押せることの
  予告ではない。密な図で 1 本のレーンを横に追うときに効く。

## 却下した案

- **`instr-ledger` をそのまま図の台帳として読む**: 決定 4 のとおり、作業リストであって履歴ではない
  （閉じた行 20 件の上限・reopen で時刻が動く・peer は構造的に載らない）。
- **0027 のシーケンス図を残して 2 図にする**: 決定 1。直らない図を保守することになる。
- **転写のターン時刻から稼働帯を作る**: 決定 3。claude だけ埋まって他 kind が空白になる
  （ADR 0078 P1.1 と同じ壁）。過去に遡れるように見えるのが、かえって危ない。
- **系譜を `Meta` だけに置き続ける**（ADR 0073 の当初判断）: 決定 6。prune で線が消えることを
  受け入れる立場は、俯瞰図を作らないあいだだけ成立していた。
- **一覧ペイン（0078）に兼ねさせる**: 0078 自身が却下欄で「別物」と線を引いている。カードの
  グリッドは「いま」の断面で、この図は「経過」である。
- **mermaid の `gantt` / `sequenceDiagram`**: レーン＝横帯という形は近いが、交差する矢印・ライブ
  状態・クリックでセッションを開く・`--kind-*` テーマ追従のいずれも載らない（0027 決定 1 の
  調査結果をそのまま引き継ぐ）。
- **全セッションを掃引する常設のタイマーを Agent に足す**: 観測の穴（決定 3）は埋まるが、誰も
  見ていない時間にも tmux とファイルを触り続けることになる。穴は**塗らずに「不明」と描く**方が、
  費用も正直さも上である。

## 帰結

- **追加は書き込み 8 箇所と読み出し 1 本。** 1 行追記を併置する先は: ①create
  （`session_handlers.go`）②stop/exit ③**resume** ④**archive / restore**
  （`HandleArchiveSession` / `HandleRestoreSession`）⑤状態観測（一覧のハンドラ）⑥peer 送信
  （`session_peer.go`）⑦指示投入（`session_io.go`）⑧報告配送（`chat_report_reconcile.go` の
  シンク）。読みは `GET /api/fleet-graph`。既存の報告・通知・arm の経路は**無改造**。
  - 🔥 ③④を数え落とすと、**`revive` と `archived` の書き手が居ないまま実装が「完了」する**。
    型に `runs[]` と `presence:"archived"` があっても、書かれなければ `runs` は常に 1 本で、
    決定 12 の「死んで再開した区間」はまた点線に化ける。
  - 🔥 ③の条件は「**スロットが再び alive になった**」であって、「`StoppedAt` をクリアする経路」
    ではない。`grep 'StoppedAt = ""'` は **4 箇所**当たり、4 つ目の `HandleRestoreSession` は
    **停止したまま一覧に戻すだけ**（`wireSession(m, false)`）——そこに `revive` を書くと
    **走ってもいない run が生える**。復元が書くのは ④の `archived:false` だけである。
- **追加のポーリングはゼロ**（決定 3）。台帳は 1 日あたり数百 KB 級（docs/101 §3 の見積もり）。
- **限界（意図）**: 左へ遡ると 3 段で減衰する（決定 8）——活動 30 日 → 系譜と生没だけの骨格 →
  導入以前は `Meta` から書き起こした 7 日ぶん。系譜と生没は初回起動時に 1 回書き起こすので、
  **導入直後から過去 7 日ぶんの骨格は出る**。
- **限界（意図）**: 観測の分解能は配備の設定に依存する（4 秒／1 分／ゼロ）。図はそれを隠さず
  斜線で示す。
- **限界（意図）**: 子の**起動タスクの本文は図に出ない**。spawn は `birth` の `origin`/`originSession`
  から矢印が引けるので、同じ往復を `instruct` としても書くと**矢印が二重に出る**。本文を見せたい
  なら「同時刻・同じ対の spawn と instruct を 1 本に畳み、抜粋をその矢印のラベルにする」規則が要る
  ——P3 で扱う。
- **停止中・アーカイブ済みも描く**（決定 12）ので、一覧（0078・既定は稼働中のみ）より**レーンの
  本数は多い**。家系順（決定 9）と点線の濃淡がその密度を支える前提であり、実装後に実測して
  レーン数の上限（折り畳み・仮想化の要否）を判断する。
- 0027 は superseded、`types/opgraph.ts` は P0 で置き換え。docs/44 には 🔴 の追記を入れる。
