## Context

エージェントの利用上限に達したセッションは、窓が解除されるまで止まる。週次の上限なら数日になる。
別の場所で続ける方法は二つあるが、どちらも足りない。

- **別のエージェントへ引き継ぐ**は、オペレーターのアシスタントに元セッションを読ませて要約を書かせる。
  これは LLM 呼び出しなので要約側も上限に当たり得るし、情報が落ちるし、何が残るかはオペレーターの
  判断次第になる。
- **分岐**（ADR 0039）は会話を丸ごと運ぶが、同じ種別にしか行けない。その種別こそが今使い切ったもので、
  しかも分岐できる種別に限られる。

P1（#2183）で、会話を読めるすべての種別に、正規化済みの `transcript.Turn` から Markdown への
レンダラーが 1 本でき、秘密情報はレイアウト前にマスクされるようになった。この記録は、そのファイルを
**別の**種別のセッションの出発点にする方法を決める。

### 種別ごとに今の転写から取れるもの

develop（2026-10-15）の `Agent.Transcript`／`claude.CollectAllTurns` を読んだ結果。ツール出力の上限は
レンダラーではなくパーサーが掛けていて、パーサーが切ったものは移動では取り戻せない。「rune」と
「byte」はコードの数え方のまま：`transcript.CapOutput` は rune で数え、独自の `outClip`／`toolOutputMax`
を持つパーサーは byte で切る。切った出力の末尾には省略の印が付く。

| 種別 | 読み元 | ツール出力 | 利用上限の検知（`limited`） |
|---|---|---|---|
| claude | `CollectAllTurns` 経由のセッション jsonl。コンテキスト圧縮の要約も含む | 最大 4000 rune | あり |
| codex | rollout | 最大 4000 rune | managed のみ |
| opencode | managed と共有サーバーにつなぐターミナル：v2 の HTTP API。それ以外：SQLite ストア | 最大 4000 rune | なし |
| cursor | ターミナル：転写ファイル。**managed：ドライバーのメモリ。停止すると空** | ターミナル：なし。managed：最大 4000 byte | なし |
| kiro | managed：動作中はメモリ、その後は v2 JSONL | 最大 4000 byte | なし |
| agy | 会話 jsonl（＋保留中の質問は DB プローブ） | 最大 4000 byte | なし |
| copilot | `events.jsonl` | 最大 4000 byte | なし |
| lcpp | 自前のストア | 最大 4000 rune | なし |
| muse | 自前のストア＋コメンタリーのログ | 最大 4000 rune | あり |
| shell／ssm | なし | — | — |

ここから言えること：移動は `CanTranscript` のすべての種別で提供するが、`limited` から移動を
**きっかけとして出せる**のは claude・managed の codex・muse だけ。managed の cursor セッションは、
ハンドルが生きているうちに移さなければならない。会話がほかのどこにも無いからだ。読み取りに失敗すると
（たとえば opencode v2 のサーバーが応答しない）ターンが返らないので、移動は空のファイルを書かずに
断らなければならない（決定 6）。

## Decisions

1. **引き継ぎは、移動先が読むファイルで行い、最初のプロンプトでそのファイルを名指しする。** Agent が
   元セッションを描画して書き出し、ファイルの場所・中身・何より先に冒頭を読むことを伝える短い
   プロンプトで移動先を起動する。会話は途中で一度も LLM を通らない。
2. **不採用：移動先 CLI の保存形式を合成する。** どのストアも非公開で版ごとに変わる契約で
   （opencode v2 のストアはスキーマを丸ごと置き換えた）、claude の thinking ブロックは署名付きなので、
   合成した履歴は拒否されるか、thinking 抜きで黙って再生される。ストアを書いて安全なのは同じ種別の中
   だけで、そこではすでに分岐が種別ごとのやり方でやっている（ADR 0039。たとえば codex と opencode は
   CLI の分岐 API、claude の地点分岐は切り詰めた jsonl、lcpp は Fleet 自身のストア）。
3. **不採用：最初のターンで履歴を全部送る。** コンテキストの小さいモデル（lcpp）ではあふれるし、
   最初のターンの費用が履歴の長さに比例する。ファイルなら、移動先は冒頭を読み、必要なときだけ
   残りを読みに行ける。
4. **不採用：LLM による要約。** それは既存の引き継ぎそのもの。要約が欲しいときのために残し、
   移動はその隣に置く決定的な代替とする。
5. **同じ種別は移動先に出さない。** 移動はある種別の枠から逃れるためのもので、同じ種別のセッションは
   同じアカウントの枠を使う。分岐できる種別（`CanFork`）なら、ダイアログは分岐を案内する。分岐の
   ほうが多くを運ぶ（ネイティブの履歴、thinking、ツールの状態）。分岐できない種別（今は cursor・kiro・
   agy）では、別の種別が必要だとだけ伝える。
6. **ファイルの構成：状態が先、履歴が後。** 最初の 1 画面しか読まない移動先でも、何をすべきかが
   分かっていなければならない。順に：
   1. ヘッダー：元セッション、種別、モデル、作業フォルダ、ブランチ、移動した時刻。そして
      「このファイルが記録のすべてで、元セッションのファイルは開かないこと」という一文。
   2. **止まった地点**：最後のユーザー発言（全文。決定 7 の規則により Agent 内部のプロンプトは
      これに当たらない）、最後のアシスタントの本文、未回答の質問があればそれ、キューに入ったまま
      転写に届かなかった指示（`TranscriptData.Queued`／`QueuedItems`）、元セッションの保留 spool で
      待っているピアメッセージ（送り手・intent・本文）、最後のターンが上限で切られたかどうか。
   3. 移動した時点の**作業コピーの状態**：`git status --porcelain`、差分の統計、上流より先にある
      ブランチのコミット。
   4. セッションの**変更ファイル**（ADR 0049 の一覧、Agent 側での集計）。
   5. **開いている糸**：元セッションが起こした子セッションとその状態、元セッションの保留中の
      handoff 提案を名前で（決定 12）。
   6. **会話**。決定 7 で絞り込み、決定 8 で描画する。

   読み取りでターンが一つも得られない元セッションは、理由を添えて断る。空のファイルは決して書かない。
7. **移動先が続けるのに要るものを残し、要らないと示せるものだけ落とす。** 各パートへの問いは「それが
   無いと移動先の行動が変わるか」。規則はパートの種類・ツール・位置による機械的なもので、LLM も
   重要度の推測も使わない。落としてよいとデータから示せないパートは残す。
   - **全文で残す：** ユーザー発言、質問とその選択肢と回答、計画、ピア・オペレーターからの
     メッセージ、コンテキスト圧縮の要約、アシスタントの本文、`userfile` パート（パスとキャプション。
     「この画像を直して」にはパスが要る）。
   - **1 行（名前とラベル）で残す：** 下の読み取り専用リストに無いすべてのツール呼び出しと、すべての
     `error` パート。シェルのコマンドや MCP の呼び出しが何かを変えたかはデータから分からない
     （`Part` には副作用を表す欄が無く、`File` は認識できた編集にしか付かない）。済んだ副作用を落とすと、
     移動先がそれを繰り返しかねない。編集は動詞とファイルを残す。差分は作業コピーと 6.3・6.4 にある。
   - **指示と結果で残す：** 委任。サブエージェント自身のツール呼び出しは除く。
   - **落とす：** thinking とサイドチェーン（P1 と同じ）、使用量・費用の行（`CostOnly`）、モデルの
     バッジ、最後の 3 ターンより前のツール出力、種別ごとの明示的な読み取り専用ツールのリスト（ファイルの
     読み取り・検索・一覧・Web の取得）に載ったツール呼び出し（リストは各パーサーのツール名の隣で
     管理する）、そして Agent 自身が注入したプロンプトのうち**既知の Agent プロンプトと本文が一致する
     もの**（利用上限からの再開 `isRateLimitResumePrompt` とその仲間）。出自だけでは足りない：
     `Turn.Source` は Agent の再開でも利用者自身の定時実行でも `schedule` になり、オペレーター・ピア・
     チャットブリッジ・spawn のメッセージにも印が付き、印の台帳は最近の本文しか持たない。出自の
     分からないターンは残す。
   - **知らないパートの種類**は、レンダラーが書くとおりに残す。
   - **例外は止まった地点：** 最後の 3 ターンは、すべてのツール呼び出しを出力付きで残す。上限で
     切られたターンはたいてい調査の途中で、その出力が無ければ移動先は同じことをやり直す。
   - **大きさ：** 最終的な Markdown で 256 KiB（UTF-8 のバイト数。描画したファイルで測る）は努力目標。
     超えたら、古いアシスタントの本文から順に最初の段落だけに切り詰め、切った箇所には目に見える印を
     残す。ユーザー発言、最後の 3 ターン、6.1〜6.5 の各節は切らないので、それでも目標を超えることが
     ある。そのときはそのまま書き、ダイアログに大きさを出す。断ると利用者は先へ進めなくなるし、
     移動先はどのみちファイルを少しずつ読む。
   - 256 KiB と 3 は出発点の値で、実測ではない。1 か所の定数にして、最初の実際の移動のあとで見直す。
   - 秘密情報は P1 と同じく必ずマスクする（`bridge.ScrubSecrets`）。
8. **ディスク上の新しい形式は作らない。メモリ上の形を 1 つ作り、一度に全部描画する。** 正規化済みの
   `transcript.Turn` がすでに種別に依存しない表現で、移動先が読むファイルは Markdown にする。LLM が
   いちばんよく読めるのが Markdown だからだ。JSON の引き継ぎ形式を作ると、レンダラーと歩調を合わせ
   続けるべき 2 本目の契約になる。その間で、Agent は `Handover` 値を組み立てる：決定 6 の各部で、決定 7
   は値そのものに適用する（落とすパートは取り除き、呼び出しだけ残すところは `Output`／`Edits` を空に
   する）。それを全体 `ToolOutput: true` で描画する。`ToolOutput: false` が隠すのはツール出力だけでは
   なく、コンテキスト圧縮の要約、委任の指示と結果、質問のプレビューも落とすからだ。テストは値（何を
   残したか）と最終的な Markdown（圧縮の要約・委任・プレビューが残ること、バイト数）の両方を確かめる。
   機械可読な形がいつか必要になれば、同じ値のもう一つの描画にする。
9. **ファイルは移動先の使い捨てディレクトリに置く**：`~/.af-work/<移動先>/handover-<元>.md`
   （`paths.SessionWorkDir`）。作業コピーの外なので決してコミットされない。`$AF_WORK_DIR` が設定されない
   managed の移動先でも同じで、パスは環境変数から読まずに計算する。
   - **このファイルを読める種別だけを移動先に出す。** lcpp の組み込みのファイルツールは作業フォルダの
     外のパスをすべて断る（`harness/cwd.go` の `resolvePath`）ので、P2a では lcpp を移動先にしない。
     cursor と kiro は P2a で測る（プランモードと既定の権限モード）。利用者の予期しない確認なしには
     読めない種別も、同じように外す。冒頭だけをプロンプトに貼るのは代替にならない：移動先は履歴に
     たどり着けず、利用者もそれを知らない。
   - **このファイルは使い捨てではなく移動先の会話の一部だ。** 移動先は冒頭を先に読み、残りは後から
     読みに行くし、最初のプロンプトがこのパスを名指ししている。そこで、移動先をごみ箱に移すときは
     ファイルをセッションと一緒にアーカイブし、復元すればファイルも戻す（`archiveSessionForDelete` に、
     claude の jsonl と同じやり方で、戻し先付きのペイロードとして足す）。これが無いと
     `removeSessionSideFiles` が `~/.af-work/<移動先>` を消し、復元した移動先はもう存在しないファイルを
     指すことになる。削除せずに停止・アーカイブするだけならファイルはそのまま残るので、手当てが要るのは
     ごみ箱の経路だけだ。
   - **移動が続くときは、前の記録を先へ写す。** 元セッション自身が移動先だった場合（A → B のあと、今度は
     B → C）、B の会話にあるのは `handover-A.md` への参照と、B がたまたま読んだその断片だけだ。そこで
     移動は B 自身の引き継ぎファイルを C のディレクトリの `handover-B.md` の隣に写し、新しいファイルの
     ヘッダーにそれらを前の履歴として挙げる。こうすると C は自分が頼るファイルをすべて自分で持ち、あとで
     A や B を削除しても C に要るものは何も消えない。上のごみ箱の規則はこれらすべてに及ぶ。
10. **移動先は同じ作業コピーで動く**（分岐と同じ）。元セッションを先に凍結する（決定 11）ので、
    二つの書き手が同時に共有することはない。`shared-working-copy` の警告は付けない。
11. **元セッションの凍結。** 移動のあと、作業コピーに手を出せるセッションはちょうど一つでなければ
    ならない。次の巡回だけでなく、元セッションを起こし得るすべての経路に対してだ。移動には元セッションの
    meta に記録する二つの状態がある。実行中の `moving: <移動先>` と、移動先ができたあとの
    `movedTo: <移動先>` で、どちらも元セッションの入力を閉じる。
    1. **meta ロックではなく、セッションごとの門。** meta ロック（`sessionLockMu`）は全セッションで
       一つのミューテックスなので、送信や CP 呼び出しをまたいで保持できない。代わりにセッションごとに
       ライフサイクルの門を持つ。元セッションでターンやプロセスを始め得るすべての経路は、確認から入力が
       確定するところまで門を共有で保持する：`/input` と `/turn`（停止中のセッションを再開してから送る
       managed の経路を含む）、起動と再開、ピアへの配送（`/input` を通る `deliverPendingPeer`）、
       report-back、定時実行の配送、そしてキューの項目をランタイムに渡す前のドライバー自身のキュー処理
       （cursor の `pump` はどの HTTP ハンドラーの外でも動く）。移動は門を排他で取るので、すでに受け付けた
       入力が確定し終わるのを待ち、そのあとは何も始まらない。
       - **入力操作ひとつにリースはひとつ。** これらの経路は互いを呼ぶ（`deliverPendingPeer` →
         `HandleSessionInput`、managed の `/input` → `Resume` → `Send`）。Go の `RWMutex` は読みロックの
         再帰を禁じている：待っている書き手の後ろに並んだ内側の `RLock` は、外側の保持者ごと
         デッドロックする。そこで公開の入口が共有のリースを一度だけ取って内側へ渡し、内側の手順はリースを
         前提とする内部関数にして、門を自分では取らない。
       - **キュー処理は呼び出し側のリースではなく自分のリースを持つ。** 入力にとっての「確定」は、
         ドライバーのキューに受け付けられることを指す。呼び出し側はそこでリースを返し、リースを持ったまま
         キュー処理を待たない。キュー処理は、ランタイムに渡す項目ごとに自分のリースを取る。こうすると、
         移動の前に受け付けた項目は、すでに渡されたか、まだキューにあってスナップショットが読むかの
         どちらかになる。
    2. **排他の門の下で、状態を確かめてから入力を閉じる。** 元セッションは idle・`limited`・`spendLimit`
       のいずれか。作業中なら断る（利用者が止めるか、ターンが終わるのを待つ）。保留中の質問・計画・
       権限確認がある場合も断る。移動するとそれを黙って放り出すことになるからだ。それから
       `moving: <移動先>` を書く。ここからは、門を通るすべての経路が移動先を名指しした `session_moved`
       で断る。ピアメッセージは断り、送り手が新しい名前を知る。元セッション自身の利用上限の予約の配送を
       断ったときは、決定 11.4 のためにそれを移動に記録する。
    3. **スナップショット、描画、書き出し、作成——止めるのはそのあと。** 入力が閉じていれば元セッションは
       何も始められないので、移動の作業中は動かしたままにする。そのハンドルには managed の cursor の転写と
       ドライバーのキューがまだある。転写・`Pending`・`Queued`／`QueuedItems`・保留中のピアメッセージの
       spool（`agents.PendingPeers`。ドライバーのキューとは別物）・作業コピー（決定 6）を読み、描画し、
       ファイルを書き（書き込みは完了して同期されてから次へ進む）、移動先を作る。元セッションを止めるのは
       確定（11.5）のあとだけ。cursor と kiro は停止時にキューを捨てる（`q.DropAll`）が、そのときには
       中身はすべてファイルにある。停止は stop-after-turn の予約を消費する。
    4. **失敗と巻き戻し。** 移動先ができる前に何かが失敗したら（ターンが無い、書き込みの失敗、Agent が
       作成を断った）、移動を巻き戻す：元セッションは止めておらずキューも捨てていないので、何も失われない。
       ファイルを消し、`moving` を消す。利用上限のエピソードは元のまま残すが、一点だけ直す：移動中に
       元セッションの予約が発火して門がそれを断った場合（11.2）、その一回きりの予約は使い切られていて、
       エピソードがその ID を持つ限り既存の監視は予約し直さない（`ScheduleID` があると
       `scheduleRateLimitResume` はすぐ戻る）。そこで巻き戻しは、使い切った ID を消し、元の時刻に、それが
       過ぎていればスケジューラーが許す最も早い時刻に、再開を明示的に予約し直す。作成で移動先が動き出した
       かもしれない場合（タイムアウト、セッションを書いたあとのエラー）は `moving` もファイルも残す：
       元セッションは閉じたままで、どちらが動けるかを推測せず、その行に「再試行」（同じファイルを使う）と
       「移動を取り消す」を出す。
    5. **確定。** 移動先ができたら `moving` を `movedTo` にし、spool にあったピアメッセージを元セッションの
       spool から取り除き（それらはファイルにある。決定 6.2。送り手には知らせない）、元セッションを止める。
       それから利用上限の監視を片付ける：
       - `rateLimitTick` は `ListMetas` のスナップショットで動くので、移動の前に meta を読んだ巡回が、
         そのあとで予約しうる。そこで巡回は `putRateLimitSchedule` の直前に門の下で meta を読み直し、
         `moving` か `movedTo` があれば諦める。
       - 予約の取り消しは、失敗したことが分かる形でなければならない：`deleteRateLimitSchedule` はエラーを
         返し、取り消しが確認できていない予約 ID は、エピソードとは別の永続的な片付け待ちの記録に残す。
         表示上のエピソードは閉じるが、ID を捨てるのは CP が削除を確認したか、予約がもう無いと答えた
         ときだけ。巡回のたびに片付け待ちを再試行するので、CP に届かなかったときの取り消しも、Agent の
         再起動をまたいで、元セッションを起こさずに CP の復帰後に完了する。それまでに発火した予約は門が
         断る。
    6. **移動済みの元セッションを開き直せるのは利用者だけ。** `movedTo` を消す明示的な「それでもここで
       再開する」による。
    7. **そのあと利用者に見えるもの。** 元セッションは停止しているがアーカイブはされず、その行は会話が
       どこへ行ったかを示す。managed の cursor の元セッションは停止するとミラーが空になる。そのときは
       引き継ぎファイルが唯一の記録になるので、ダイアログが移動の前にそう伝える。それ以外の点では、
       移動済みのセッションは普通の停止セッションで、停止セッションの TTL でほかと同じように
       アーカイブされる。
12. **持ち主は移さない。** 子セッションと保留中の handoff 提案は元セッションの名前のまま。これらを
    移すのは別の、より難しい変更になる（spawn の台帳、子の上限、ピアの ACL はすべて名前で引いている）。
    ファイルにはそれらを一覧し（決定 6.5）移動先が存在を知れるようにする。まだ動いている子がいれば、
    移動のダイアログで警告する。子から元セッションへの report-back は決定 11.2 で断られるので、利用者が
    Console で読む。
13. **編集の途中で切れたターンは、移動の前に見せるだけで直さない。** ダイアログに作業コピーの
    未コミットの状態（決定 6.3 と同じデータ）を出す。決めるのは利用者で、Agent はコミットも
    stash も reset もしない。
14. **指示ファイルとスキルは写さない。** Fleet のポリシーと利用者の指示はすでにすべての種別に届いて
    いる（ADR 0042）。プロジェクトの指示ファイルは種別で違う（`CLAUDE.md` と `AGENTS.md`）ので、
    元の種別は読むが移動先の種別は読まないファイルをヘッダーに挙げ、移動先が自分で読めるようにする。
    スキルは CLI 間で翻訳しない。
15. **移動先は元 CLI の内部状態を決して読まない。** プロンプトでそう伝え、ファイルには CLI の
    ストアへのパスを載せず（ヘッダーは `TranscriptData.Path` を含めない）、移動先の入力は描画した
    ファイルだけにする。

## Phases

- **P2a — 移動。** Agent に `POST /api/sessions/{name}/move {kind, model?, driver?}`：門を取って状態を
  確かめてから入力を閉じ（決定 11.1〜11.2）、元セッションを動かしたまま、スナップショットを取り、組み立てて
  描画し（決定 6〜8）、書き出し（9）、`initial_prompt` 付きで移動先を作り（1、11.3）、確定して元セッションを
  止めるか、巻き戻す（11.4〜11.5）。CP のルート許可リストにも足す。Console：セッションメニューの既存の
  引き継ぎの隣に項目を置き、ダイアログにエージェントの選択（ファイルを読める別の種別のみ。使用量の取れる
  種別は `get_agent_usage` を添える）、未コミットの状態、キューに入った指示、spool のピアメッセージ、動いて
  いる子セッションを出す。テスト：絞り込みと大きさの規則を値と最終的な Markdown の両方で、移動が門を待って
  いる間にリースを持った入力が内側へ呼び進んでも入力と移動の両方が完了すること、門の確認と確定の間で止めた
  入力と、確定しかけたキュー処理が、スナップショットの前に終わるか断られること、移動と競合した巡回が
  生き残る予約を作らないこと、CP に届かない間に失敗した取り消しが、Agent の再起動のあとに元セッションを
  起こさずに完了すること、すべての入力経路が移動中・移動済みの元セッションを断ること、空の転写・書き込みの
  失敗・断られた作成がそれぞれきれいに巻き戻り、元セッションのキュー（未送信の普通のユーザー入力を含む）が
  残っていること、移動中に発火して巻き戻った予約が予約し直されること、spool にピアメッセージのある
  元セッションがそれをファイルに一度だけ運ぶこと、停止した managed の cursor が理由付きで断られること、
  ごみ箱に移して復元した移動先に引き継ぎファイルが残っていること、A → B → C のあとで A と B を削除しても
  C のファイルが読めること。
- **P2b — きっかけ。** セッションが `limited`（または `spendLimit`）を示したとき、ミラーの上限バナーに、
  枠の残っている候補付きで移動を出す。今この状態になるのは claude・managed の codex・muse だけ。
- **P2 に含めない：** 持ち主の移動（決定 12）、決定 7 の上限値を実際の移動で測ること。

## Consequences

- 上限に達したセッションを、移動先自身の最初のターンより前にモデル呼び出しを一切挟まず、
  1 回の操作で別の種別に続けさせられる。
- 移動先は元より少ないものから始まる：thinking も、ネイティブのツール状態も、最後のターンより前の
  ツール出力も、読み取り専用の呼び出しの記録も無い。ネイティブのストアに触れないことの代償で、分岐が
  ある種別では同じ種別の中は分岐が答えであり続ける理由でもある。元が読んだファイルが必要なら移動先が
  読み直す。作業コピーは同じだ。
- 移動済みの元セッションは、その利用者以外の何ものにも起こされない。ほかのどの停止セッションより
  厳しいが、それが作業コピーごとに書き手を一人に保つ。

## 追記（2026-10-16）— 実装した元セッション側のゲート（P2a ステップ 2、#2182）

決定 11 が元セッションに求めるものは Agent に入った。それを動かす `/move` はまだ無い。

- **ゲート**は `internal/lifegate`。セッションごとに一つで、入力操作ごとの共有の `Lease` と、移動の
  ための排他の `Lock` を持つ。待っている書き手を優先するので、入力が途切れなく来ても移動は待たされ
  続けない。その代わり入れ子の取得はデッドロックになる。公開の入口が一度だけリースを取り、内側の手順は
  `*lifegate.Lease` を引数で受けて確かめる（`Check`）。リクエストのコンテキストに載ったリースは
  `Enter` が借りる（`deliverPendingPeer` → `/input`）。閉じた状態はメタに加えてメモリにも持つ。
  無関係な書き換えの最中に読んだメタはパースできないからだ。存在するのに読み直しても読めないメタは、
  受け入れずに拒否する（`ErrMetaUnreadable`）。再起動後は移動の唯一の記録だからだ。cursor のポンプは
  `session/prompt` が子プロセスの stdin に書かれた時点でリースを返す。
- **ゲートを通る経路:** `/input`（peer を含むすべての形）、`/turn`（すべての op。Managed ではどれも
  ランタイムを再開する）、`/start`、`/recreate`、`/driver`、`/respond`、`/answer-question`、
  `/plan-respond`、`/carried-answer`、チャットブリッジの受信テキストとボタン回答、中断・認証の自動再開
  （`injectSessionPrompt` 経由）、起動タスクの投入（`typeInitialPrompt`）、`deliverPendingPeer`
  （メッセージを spool から出す前にリースを取る）、利用上限の巡回、cursor のキューポンプ。拒否は
  `409 session_moved` で、`error.target` に移動先が入る。
- **開始できる状態:** idle・`limited`・`spendLimit` に加えて `stopped` も受ける。週の上限で止まった
  元セッションは、移動される頃にはたいてい idle reaper に停止されている。停止中のセッションも何も
  始められない。保留中の対話は従来どおり拒否する。会話がハンドルの中にしか無かった停止中の
  **Managed の cursor** も拒否する。
- **巡回**は `putRateLimitSchedule` の前後だけでなく、そのセッションの一歩全体でリースを持つ。予約を
  記録したエピソードファイルが、移動が入力を閉じる前に書かれ、確定時に必ず取り消す id が見つかる。
- **取り消し**は `cancelRateLimitSchedule` を通る。id は CP を呼ぶ前に `session-rate-limit-cleanup`
  に書き、CP が確認したとき（404 も確認とみなす）だけ消す。巡回のたびに再試行し、期限は無い。確定は
  エピソードを閉じる前に id を記録し、記録が書けなければ何も変えずに失敗する。
- **拒否された予約とロールバック**は一つのロックで順序付ける。ロールバックは修復・`moving` の消去・
  再開をその中で行う。ロールバックの後で記録に来た拒否（その間に止まっていた要求）は、元が開いて
  いるのを見て自分で予約し直す。巡回の一歩も（リースの後で）同じセッション単位のエピソードロックを
  取る。共有のリース同士は排他にならず、修復はリースを持たないからだ。
- 確認済みの取り消しも、そのセッションのエピソードが id を指している間は完了の印付きで記録に残す。
  id を記録した後で止まった確定は移動中の元を残し、巡回が取り消した後でもロールバックがその id を
  死んだものと分かる必要がある。
- **どの遷移も返る前にディスクにある**: `moving`・`movedTo` とその消去は `session.WriteMetaChecked`
  （一時ファイルをメタへ rename し、すべてのエラーを返す）を通る。メモリ上の写しの変更とエピソードを
  閉じるのは、その書き込みが成功した後だけだ。書き込みに失敗した移動は元の段階に留まる。
- **移動の基本操作**は `beginSessionMove`・`rollback`・`commit`（sessionx の `session_move_gate.go`）と、
  決定 11.6 のための `reopenMovedSession`。確定はメタを変え、エピソードを閉じ、その予約を取り消す。
  元セッションの停止と spool の peer メッセージの取り出しは、順序を持つ移動の側に残した。
- 自前のリースを取るのは cursor のポンプだけだ。ほかの Managed ドライバのポンプは後続の作業。
- 拒否された予約は、その瞬間にメタが読めなくても記録する（まずメタのロックの下で読む）。巡回は開いた
  セッションに記録済みの拒否を見つけると予約し直すので、ロールバックが取りこぼした記録が死んだ id の
  まま残ることはない。
- **決定 11.2 の修正**（2026-10-16）: 上の開始状態を利用者が承認した。移動は `stopped` からも始め
  られる。ただし停止中の Managed の cursor は除く。

## 追記（2026-10-17）— すべての Managed ポンプが自前のリースを取る（#2236）

- Managed ドライバのキューポンプはすべて、項目がキューを出る前に項目ごとのリースを自分で取り、
  ランタイムが入力を持った時点で返す。
  - cursor・kiro・copilot: `session/prompt` が子プロセスの stdin に書かれた時点。
  - codex: `turn/start` に応答が返った時点。
  - opencode: 入力を運ぶ要求（`/message`、2.x では `/prompt`）が serve に書き込まれた時点。リースは
    `waitIdle` をまたぐので、移動はポンプが送る直前の項目をスナップショットせず、別クライアントの
    ターンを最大 60 秒の待ちの分だけ待つ。
  - lcpp: ユーザーのターンがこの種別のトランスクリプトであるストアに追記された時点。
  - muse: `turn/start` に応答が返った時点。`queued` の応答はホストが実行中のターンの後ろに入力を
    持っていることを意味し、実行中のターンがある元セッションは移動できない（11.2）。呼び出し元が
    リースを持っており、そこでもう一つ取ると入れ子になるため、`accept` は呼び出し元の goroutine で
    ポンプを回さなくなった。
- この時点でのリースの解放は状態の判定には早い。キューが項目を手放した後も、ランタイム自身の記録
  （copilot の `events.jsonl`、opencode のストア、muse の `turn/started`）は前のターンの idle を示して
  いることがある。そこで `beginSessionMove` は排他ゲートの下で Managed のハンドルにも、取り出して
  まだ決着していない項目を持っているか（`ManagedInFlight`。キューに残る項目は数えない）を尋ね、
  持っていれば元を `working` として拒否する。
- ゲートに拒否されたポンプは項目をキューに残したまま止まり、`lifegate.Reopen` で再び動く。メタが
  読めないときは 1 秒後に見直す。
- `POST /sessions/{name}/settings` はリースを取り、移動中・移動済みの元を `session_moved` で拒否する。
  会話がすでに移動先へ移ったセッションに変更が残るためだ。`GET` は開いたセッションでは `Resume` の間
  リースを持ち、移動中・移動済みのセッションではランタイムを起こさずメタのモデル・effort・モードで
  答える。

## 追記（2026-10-17）— 移動エンドポイントの実装（P2a ステップ 3a、#2182）

- **ルート**（Agent と、CP の許可リストに同じパス）: `POST /sessions/{name}/move
  {kind, model?, driver?}`、`GET …/move/preview`、`POST …/move/retry`、`POST …/move/cancel`、
  決定 11.6 の「それでもここで再開」にあたる `POST …/move/reopen`。移動と再試行はセッションを作るので、
  CP では fork と同じ割り当て上限の確認を通す。プレビュー以外は `session.move[.retry|.cancel|.reopen]`
  として監査に記録する。
- **移動先の名前は begin の前に確保する**。`moving` にその名前を書き、作成の前にファイルを
  `~/.af-work/<target>` に書くためだ。作成は `POST /sessions` と同じ経路をプロセス内で通る。確保した
  名前は、クライアントからは設定できない非公開のフィールドで渡す。
- **移動先:** claude・codex・opencode・copilot・agy・muse。lcpp は除く（決定 9）。cursor と kiro は、
  決定 9 の実測が済むまで `moveUnmeasuredAllowed` の後ろで無効のままにする（#2252）。元と同じ種別への
  要求は `move_same_kind` で拒否し、代わりに fork を示すかどうかを `canFork` で返す。
- **作成の結果が分からないとき:** ロールバックするのは、作成が応答を返し、かつ移動先の名前で何も
  残っていない（メタもペインも無い）場合だけ。結果が分からないときや、移動先のメタを書いた後の失敗では
  `moving` とファイルを残す。移動の内容（要求・ファイル・spool の peer の id）は状態ディレクトリ
  （`session-move`）に記録するので、Agent が再起動しても再試行と取り消しができる。再試行は、移動先が
  あれば確定し、無ければ同じファイルから同じ名前でもう一度作成する。取り消しは、移動先がある間は
  拒否する。
- **決め手は移動先のメタ。** 移動は移動先のメタがディスクにあるときだけ確定する。移動の作成はメタを
  検査付きで書き、それから最初のプロンプトを送る。メタの無い 2xx では移動は保留のまま残る。メタ無しで
  その名前のペインやランタイムが動いている（孤児）ときは、再試行で作り直さず、取り消しが止める。確保した
  名前は、移動が終わるまでメモリと保留中の記録の両方で、すべての採番から守る。
- **存在するのに読めないメタ**を不在とはみなさない。再試行と取り消しはそれを拒否し、メタのファイルが
  まったく無い移動先だけを孤児として止める。移動先の名前は記録だけでなく元の `moving` でも守るので、
  begin と最初の記録の書き込みの間に Agent が止まっても、その名前を再び採番しない。
- **最初のプロンプトも移動の一部。** 作成の前に移動先ごとに記録し（`session-move-delivery`）、移動先の
  `InitialPromptState` が delivered になるまで残す。それまでは移動の応答と元のプレビューがそれを示し、
  利用者の操作で `POST /sessions/{target}/move/deliver` がもう一度送る。届いたかもしれない unknown を
  勝手に再送することはしない。Terminal の移動先への再送は、作成時と同じ配送（入力欄の準備待ち、Enter の
  押し直し、ターン開始の確認）を裏で走らせ、確認の取れない打鍵は unknown のまま残す。元の移動が移動先を
  まだ作っていない間は、記録を残したまま再送を拒否する。
- **確定の後も**記録は `committed` として残り、spool の peer メッセージの取り出しと元の停止が済んでから
  消える。その間に Agent が止まったら、起動時（`RecoverMoves`）・再試行・再開の前に残りを済ませる。
  再開は移動と同じ操作ロックの下で行う。
- **プレビューも**ファイルと同じくマスクし、git の読み取りは時間とバイト数に上限を設け、切った旨を書く。
- **決定 14 のヘッダー:** 種別ごとのプロジェクト指示ファイルは固定の表（`projectInstructionFiles`）に
  した。その種別が読むと分かっているファイルだけを載せるので、移動先が実際には読んでいないファイルを
  読んだことにはならない。ヘッダーには、元の種別のファイルのうち作業フォルダに実在し、移動先の種別が
  読まないものを挙げる。
- **ここで作っていないもの:** ゴミ箱に入れた移動先と一緒に引き継ぎファイルを保管し、復元で戻す処理
  （P2a ステップ 3b）。Console のダイアログと、セッション行の `moving` / `movedTo`（#2254）もまだ無い。

## 追記（2026-10-17）— Console のダイアログとセッション行（P2a ステップ 4、#2182、#2254）

- **行のワイヤー**は Agent の `session.Session` と CP の `sessionWire` に `moving` と `movedTo` を
  載せる。DB ミラーの列は設けない。再試行・取り消し・再開・再送はどれも稼働中の Agent を要するので、
  ワークスペース停止中にミラーから出す一覧には出さない。
- **メニュー**は引き継ぎの直後に「別のエージェントへ移す…」を出す。対象は引き継ぎと同じ（会話があり、
  フォルダがあり、ワークスペースが稼働中）。移動中・移動済みの元セッションには通常の再開を出さない
  （Agent が `session_moved` で拒否するため）。同じダイアログが、未完了なら再試行と取り消し
  （決定 11.4）を、移動済みなら移動先・最初の指示の再送・「それでもここで再開する」（決定 11.6）を
  受け持つ。行の 2 行目には、会話の移動先か、移動が未完了であることを出す。
- **移動先の選択肢**は、プレビューが可とした種別から接続確認で未接続と分かったものを除いたもの。
  それ以外の種別は理由つきで並べる。使用量は Console がすでに読んでいる種別（WS バーの claude・
  codex・muse）に限り、ダイアログを開いたときに一度だけ読む。モデルと実行方式の初期値は、新規
  セッションのダイアログがその作業コピーで選ぶものと同じにする。

## 追記（2026-10-17）— 上限バナー（P2b、#2182）

- **ミラーには拡張できる上限バナーがなく**、あるのは状態チップだけだった。そこで P2b は、ほかのミラーの帯の
  下に帯を 1 つ（`MoveLimitBanner`）足す。稼働中のワークスペースで `limited` / `spend_limit` のときだけ出し、
  移動中・移動済みの元セッションには出さない。プレビューが拒否なしで、接続済みかつ元と同じ種別でなく、
  まだ上限に達していない移動先を 1 つ以上残すときに限る。ボタンは既存のダイアログを、上限から開いたという
  印つきで開く。
- **枠の並べ替えは表示だけ。** バナーから開いたとき、移動先は枠に余裕のある種別を先頭（使用率の低い順）、
  次に使用量の取得元や値がない種別、最後にいずれかの枠が 100% の種別の順に並ぶ。ユーザーが選ぶまでは
  先頭が初期選択。使用量は WS バーと同じ 3 つの取得元で、取得元のない種別はどちらとも判定せず、選べるが
  印は付けない。

## 追記（2026-10-20）— kiro を移動先に加え、cursor は引き続き対象外（#2252）

- **計測したもの。** kiro、マネージド、既定の権限モード（kiro-cli 2.32.0、claude-haiku-4.5）：
  最初のターンで、作業フォルダ外の `~/.af-work/<自分の名前>/` 配下のファイルを指名すると、
  承認プロンプトなしでファイルを読み、ランダムなトークンを正しく返した。cursor を素の CLI
  （`cursor-agent -p --plan --trust --model auto`、2026.10.18）で動かした場合も、cwd 外の
  `~/.af-work/` 配下のファイルを承認なしで読み、トークンを返した。
- **計測できていないもの。** kiro のターミナル（TUI）。cursor のマネージド：ドライバー実行は
  最初のターンで "Upgrade your plan to continue" と返った（アカウントのプラン）ため、ドライバーの
  trust 処理とフラグは未計測。cursor のターミナル。
- **推論（計測ではない）：kiro のターミナル。** 移動先の一覧は種別単位なので、kiro への移動は
  ターミナルのドライバーも起動し得る。マネージドは既定モードで計測したが、権限フラグ
  （`--trust-all-tools` を付けたか）は独立に記録しておらず、「権限確認を省略」設定がオフの状態で
  の結果とは結びつけられない。その設定がオフなら kiro の両ドライバーは `--trust-all-tools` を
  外し、その場合に外部ファイルを確認なしで読めるかは未計測。ターミナルのチャットがマネージドと
  同様に振る舞うと見込むのは、両者が kiro のツール権限を共有しているからで、推論であり実行
  ではない。もし確認が出た場合は、移動先自身の画面でユーザーが答える形になり、最初の指示は
  そこで待つ。
- **決定。** kiro を移動先にする。cursor は、マネージドドライバー経由で計測できるまで対象外のままで、
  `not_measured` として報告する。フォローアップ：#2252。

## 追記（2026-10-25）：マネージドのセッションにも `AF_WORK_DIR` が付く
