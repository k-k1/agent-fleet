# 0079. 別の配備のエンジンを借りる——エンジン表に `remote` の行を足し、待つのも箱を買うのも向こうの Control Plane に任せる

[English](0079-remote-engine-from-another-deployment.md) | 日本語

- 状態: **提案**（2026-09-12）。実装はしていない。
- **この文書のために新しく測ったものは無い。** 根拠はすべて出所を書き分けてある——
  (a) ADR 0071・0072・0074・0075・0077 の実測、(b) 2026-09-12 にこのリポジトリのコードから
  読んだ事実（「確認した出典」に file:line で列挙した）、(c) Caddy・ALB・AWS の公開仕様として
  知っているだけで**我々のどの配備でも確かめていない**もの。(c) に依存する決定は
  「未解決の点」に書いた。
- 利用者の要求は 1 つである——**手元のホストで動く Agent Fleet（native / docker）の
  ワークスペースから、AWS で動く Agent Fleet の llm / image エンジンを使いたい。**

## 背景

### 何が 1 つの配備に縛られているか（2026-09-12 に読んだ）

セッションからエンジンまでの経路は 3 段で、**自分がどの配備にいるかを知っているのは
真ん中の 1 段だけ**である。

1. **Workspace は runtime を知らない。** どちらの provider も `AF_CP_BASE_URL` に CP が
   返した `base_url` を足した先にしか行かず（`workspace/agent/engines.go:185`）、資格情報は
   engine session token だけである。AWS SDK もバケットもサービス名も無い。向こうが ECS か
   LAN の箱か別のフリートかは、**この層からは区別できないし、区別する必要も無い**。
2. **ゲートウェイが仮定しているのは「上流 URL が 1 本ある」ことだけ。** `dial` は
   `def.URL` に provider 依存の接頭辞とパスを足して組み立て（`control-plane/engine_gateway.go:766`）、
   エンジン自身の鍵を付けて中継する。ECS に触れる唯一の場所は `ensureStarted`
   （`engine_gateway.go:845`）で、ADR 0076 がそこに「ここは誰もこのエンジンを所有していない」
   という答えを既に教えてある。
3. **行が何であるかを決めているのは登録側。** `newEngineRegistry`（`control-plane/engines.go:635`）
   は表を読み、各行に ECS アダプタ・制御ループ・active set・pending の監視・GPU の梯子を
   付ける。`lifecycle` が `external` の行だけがそのどれも受け取らない
   （`engines.go:753-772`、ADR 0076 決定 1）。

つまりこの ADR が答える問いは「バイトが届くか」ではない。**エンジンが、それを起こして
くれる別の Agent Fleet のものであるとき、その行は何を意味するか**である。

### 向こう側は、すでにトークン認証つきの公開された玄関である

エンジンを持っている配備の側に、新しく開ける口は無い。

- `/engine/*` と `/internal/engine/*` は session 免除で、**すべての形態で**登録される
  （`engine_gateway.go:174-177`、`control-plane/routes.go:33` から無条件に呼ばれる）。
- ecs-ec2 の ingress ALB にパス規則は無く、WAF は運用者が頼まない限り作られない
  （`deploy/aws/ecs/cfn/30-ingress.yaml`）。compose 形態の Caddy は素の
  `reverse_proxy 127.0.0.1:8099` である（`deploy/compose/Caddyfile`）。どちらも全面を通す。
- 資格情報はもともと 2 段である。メンバーシップごとの**発行（issuing）**トークンが、
  セッションごと・エンジンごとの**セッション**トークンを買う
  （`control-plane/engine_token.go:47,85`）。メンバーシップは毎要求で live に解決されるので、
  外されたメンバーはトークンの有効期間内でも拒まれる（`engine_gateway.go:340`）。

無いのは**借りる側**である——「このエンジンは別の配備のもので、その配備が起こしてくれる」
と言う行が、手元のエンジン表に無い。

### 「他人のエンジン」には 3 つの型がある

同じ問題ではない。混ぜると、1 つの設計が残り 2 つに対して間違う。

| 型 | 向こう側 | 手元の CP がすべきこと |
|---|---|---|
| **1. 箱を買うフリート**（ecs-ec2） | 要求に応じて GPU を起こし、また止める CP | 転送し、**向こうに要求を待たせる** |
| **2. 常時稼働のエンジンを指しているフリート**（compose / native / ec2-single ＋ ADR 0076 の `external` 行） | 転送するだけの CP | 転送する。待つものは無い |
| **3. 経路にフリートが無い** | 到達できる URL 上のエンジン本体 | 今の ADR 0076——`external` 行 |

この ADR は型 1 と型 2 を扱う。両者は同じ行・同じコードで、型 2 は単に待つ経路を通らない
だけである。**型 3 は却下ではない——エンジンが常時稼働なら、それが正解である。** ADR 0076 の
`external` 行がすでにそれをしており、あの決定は URL が LAN 上にあることを要求していないし、
決定 7 は前段に reverse proxy を置いて CP に bearer を渡す手順をすでに書いている。

### 今日、コードを 1 行も変えずに何が起きるか

書き留めておく価値がある。以後の実測がこれと比較されるからであり、**あと一歩で使えて
しまう**からである。

`AF_COMFY_URL=https://<向こうのフリート>/engine/image/v1` と
`AF_COMFY_API_KEY=<afe_… のセッショントークン>` を置くと、上流は正しく組み上がる——comfy の
接頭辞は `/` なので（`engine_gateway.go:811`）、要求は向こうの経路に
`/engine/image/v1/prompt` として着く。そのうえで 3 つの理由で失敗し、その 1 つ 1 つが下の
決定になっている。

- **向こうのエンジンが暖まっているときしか動かない。** `engineHealthy` はプローブに 5 秒しか
  与えない（`engine_gateway.go:920`）。寝ているエンジンに対して向こうのゲートウェイは
  ホールドしたのち 503 を返すので、手元の行は——`external` であるから——即座に失敗する
  （`engine_gateway.go:845`）。🔥 **無駄どころではない**: 失敗したその 5 秒のプローブは
  向こうで需要として記録され、**誰も待っていない GPU の箱を買う**。
- **llm 役はそもそも配線できない。** `AF_ENGINES_JSON` の inline 行は受理されるが
  （`engines.go:498`）、bearer を載せる手段が無い。`apiKey` が埋まるのは合成された comfy の行
  （`engines.go:768`）か SSM 経由だけで、external のレーンは SSM を意図的に読まない。
- **`X-AF-Model` が落ちる。** `dial` は Content-Type と Accept しか転送しないので、向こうは
  使用量の計上と pending の判定が両方読んでいるモデルの宣言を失う。

## 決定

### 1. 借りたエンジンは表の 1 行であり、`lifecycle: "remote"` で**宣言する**

`engineDef.Lifecycle` に 3 つめの値を足す。空はこの配備の ECS サービス、`external` は
ADR 0076 の「URL があるだけで、誰も起動しない」行、**`remote` は「別の Agent Fleet の
ゲートウェイであり、そのフリートが起こす」行**である。URL の形から推し量るのではなく
宣言する（ADR 0053）——たまたま `/engine/` を含む URL が、行の意味を黙って変えてはならない。

`remote` 行が受け取らないものは `external` とまったく同じである——ECS アダプタ、制御ループ、
active set、pending の監視、GPU の梯子、稼働ヒートマップのサンプラ。`external` と違うのは
決定 5・6・7 の 3 か所だけで、その違いはすべて**向こう側にエンジンを起こせる者がいる**ことに
由来する。

いまコードが分岐に使っている述語は `engineDef.external()`（`engines.go:119`）である。これを
2 つに割る——「ここが管理していない」（external と remote。管理行の形、ECS アダプタの不在、
`ondemand` の拒否）と、「誰も起こさない」（external だけ。即時失敗）。1 つの述語を両方に
使い回すことが、remote 行に ADR 0076 決定 4 を継がせて**すべてのコールドスタートを
落とす**やり方である。

### 2. 運用者は「どこ」と「何で」を宣言する。「どれ」は向こうのカタログが宣言する

`AF_COMFY_URL` と同型の環境変数 2 つ、加えて任意の絞り込み 1 つ。

| 変数 | 意味 |
|---|---|
| `AF_REMOTE_ENGINE_URL` | 向こうのフリートのベース URL。パスは付けない: `https://af.example.com` |
| `AF_REMOTE_ENGINE_TOKEN` | `afei_…` の発行トークン（決定 3） |
| `AF_REMOTE_ENGINE_KEYS` | 任意。`image` ならその役だけを借りる。空なら向こうが出しているすべての役 |

**どのエンジンが在り、それぞれの `api` と `provider` が何であるかは、向こうの配備自身の
カタログから読む**（`GET /internal/engine/catalog`、`engine_gateway.go:224`）。手元で宣言は
しない。これは導出ではない——カタログは向こうの管理者の宣言であり、それを宣言してよいのは
彼らだけである。推測は積極的に危険でもある: image 役はある配備では `comfy`、別の配備では
`sdcpp` であり、Workspace はその 2 つでまったく違う要求を組み立てる。推測を外すと、
OpenAI 互換のエンドポイントに ComfyUI のグラフを投げることになる。

その帰結として、**行は起動時ではなく、最初のカタログ取得が成功したときに現れる**。その経路は
既にある: ADR 0077 P1 が、起動後に現れた行をレジストリが adopt するようにした——表が
しばらく空であることは、配備の実在する状態だからである。したがって起動時に向こうが
到達不能な CP にはエンジンが無い。それが事実である。

### 3. 資格情報は「そのためだけのメンバーシップ」の発行トークンで、失効はそのメンバーシップの削除

向こうの配備は `afei_<membership>` を署名マスタから決定的に導出し（`engine_token.go:47`）、
そのメンバーシップのすべてのワークスペースに注入する（`control-plane/workspace_lifecycle.go:401`）。
そのトークンが開けるのは `/internal/engine/token` と `/internal/engine/catalog` だけである。
git も MCP もメモも API も開かない。

- 🔴 **人のトークンを使ってはいけない。** 決定的に導出されるので、1 本を無効にする唯一の道は
  署名マスタの回転であり、それは git・memo・schedule のトークンと共有されている
  （`control-plane/git_http.go:88`）。借り手 1 人を失効させるとフリート全体がログアウトする。
- **他に使わないメンバーシップを 1 つ作る。** 招待し、そのワークスペースから
  `AF_ENGINE_ISSUE_TOKEN` を一度だけ読み、ワークスペースを止める。借り手の失効は
  **そのメンバーシップを消すこと**になる: `liveMembership` は毎要求でそれを解決し、
  消えた瞬間に 401 を返す（`engine_gateway.go:340`）。新しい資格情報の保管も、新しい有効期限も、
  新しい書式も要らない。
- ついでに決定 9 も無償で解決する: 走っているワークスペースを持たないメンバーシップは、
  向こうの使用量 POST が届けられない相手であり、それがまさに望みである。

P1 で、向こうの super-admin にこのトークンを発行して見せるボタンを足す——環境変数を読むために
ワークスペースを起動しなくて済むように。30 行程度だが、意図的に **P0 には入れない**: P0 は
**エンジンを持っている配備に新しいコードを配備せずに**証明できなければならない。

### 4. パスは素通しし、`X-AF-Model` も一緒に送る

remote 行の上流は `<AF_REMOTE_ENGINE_URL>/engine/<key>/v1/` ＋ 手元の `/engine/<key>/v1/` の
後ろのパス、およびクエリである。provider 依存の接頭辞（`engineUpstreamPrefix`、
`engine_gateway.go:811`）は付けない——**その書き換えは向こうのゲートウェイの持ち物**であり、
2 度掛けると `/v1/v1/chat/completions` になる。

`dial` は `X-AF-Model` も転送しなければならない。向こうがどのカタログ行への要求かを知る手段で
あり、使用量の計上が読み、モデルがインスタンスへ同期中のあいだ `engine_waking` を返す
pending の判定も読む（ADR 0072 P2 欠落 7）。落としても要求は失敗しない——向こうの配備の
計上と、いちばん役に立つ再試行可能な拒否を、静かに劣化させるだけである。バグとしては
最悪の形である。

### 5. remote 行に health は掛けない。ここでは起こさない

`ensureReady` は remote 行に対して即座に返る。プローブも起動も待ちも無い。

🔥 **health プローブはここでは無駄なだけでなく、高くつく。** `engineHealthy` は自身を 5 秒で
区切るが（`engine_gateway.go:920`）、冷えた GPU は実測 527 秒かかる（ADR 0071）——だから
プローブは失敗しかしない。しかもそのプローブは向こうのゲートウェイへの普通の要求であり、
需要を記録して箱を買う（`engine_gateway.go:384` 以降）。**必ず失敗する 5 秒の検査が
$1.26/時のインスタンスを起動する**——この設計で起こりうる最悪の帰結であり、`external` の
レーンを素朴に流用するとそれが出来上がる。

そもそも掛ける先も無い: 向こうのフリートは、エンジン本体に届かない health のパスを
公開していない。

### 6. 🔥 手元のホールドは向こうより長く、その期限切れは `engine_waking` である

コールドスタートが成立するかどうかを決める罠はここである。

- 向こうの非ストリーミング経路は 45 秒ホールドし、`Retry-After` 付きの
  `503 engine_waking` を返す（`engine_gateway.go:100`。ingress ALB の 60 秒アイドルの下に
  抑えてある）。
- 手元の非ストリーミング経路も既定は同じ 45 秒。先に切れたほうが答えを決め、手元のほうが
  先に時計を回し始めている。
- 🔴 手元の期限切れは、いまは `engine_waking` に**ならない**: `ensureReady` が経路上に無いので
  期限は `engineClient.Do` の中で発火し、`plain` はそれを `engine_unavailable` に変える
  （`engine_gateway.go:716-740`）。そして image の provider は `engine_waking` を 16 分
  再試行するが、**`engine_unavailable` はまったく再試行しない**
  （`workspace/agent/internal/imagegen/sdcpp.go:505`）。コールドスタートは恒久的な失敗に
  なり、しかも「起動に失敗した」と報告される。

したがって remote 行では、有効なホールドは `AF_ENGINE_PLAIN_HOLD` の**既定を上げた 75 秒**とし、
remote 行への中継中に期限へ達した場合は `Retry-After` 付きの `engine_waking` に写像する——
それが事実だからである。ストリーミング経路には何も要らない: 向こうは即座に 200 と 10 秒ごとの
ハートビートを返し、`dial` はその最初のバイトで戻り、あとはそのまま流れる。

手元の配備が自前の proxy の後ろにいる場合だけは、この処理から問い合わせようがない——だから
knob にしてあり、だから未解決 2 がある。

### 7. カタログは向こうの配備から読み取り専用で鏡写しにする

`engineCatalog` は `store.EngineModelStore` の上の薄いキャッシュである
（`control-plane/engine_catalog.go:58`）。remote 行にはこのインタフェースの実装を渡し、
`ListEngineModels` は鏡写しにした向こうのカタログを読み、書き込みは拒む。

手元で手入力する案——LAN の ComfyUI に対する ADR 0076 の答え——は**ここでは却下する**。

- Workspace は ComfyUI のグラフを**自分の**配備のカタログ行（`files`・`params`・`base_model`）
  から組み立てる。向こうのエンジンには、向こうの active set が置いたファイルしか無い。
  両者の乖離は生成時の `Value not in list` であり、ADR 0072 の P2 の記録がその失敗の
  読みにくさを残している。
- `negative_always`、モデルごとの窓、宣言されたサイズ、`warm`——どれもすでに向こうの
  カタログに在り、どれも推測すれば間違える。

更新は Agent と同じ 10 分の周期で。取得に失敗したら前の答えを保つ——手元のカタログが
そうしているのと同じ理由である（一時的な失敗が「モデルが無い」＝「このエンジンを起動するな」に
化けてはならない）。

**向こうのフリートが off にした役は、そのカタログから消える**（`engine_gateway.go:224` が
`engineModeOff` を飛ばす）。すると鏡にはその行のモデルが無くなり、`serve` はそれを
`engine_unavailable` と「このエンジンには有効なモデルが無い」で既に拒む。つまり行はプロセスの
生存中に**足されはするが、消えはしない**——生きている行を消すことをレジストリは支えていないし、
支える必要も無い。

### 8. 手元のセッション名を向こうに伝える

手元のゲートウェイは手元のセッショントークンを検証済みなので、セッションを知っている
（`engineSessionClaims.Session`）。発行トークンを向こうのセッショントークンに交換するとき、
その名前を伝える。向こうの配備の使用量行には借り手のセッション名が載る——向こうの運用者が
借り手ごとの支出を見分けられる唯一の手段である。

トークンは (エンジンの鍵, セッション) ごとにキャッシュし、期限より前に更新する。Agent が
既にやっているのと同じ形で、TTL は 30 日なので（`engine_token.go:85`）安い。

### 9. 使用量は両側が数え、向こうの POST はどこにも着かない

手元の CP は今までどおり数える——`recordUsage` が中継したバイトから使用量を読み
（`control-plane/engine_usage.go:198`）、要求したワークスペースへ行を POST する。ここは
何も変わらない。

向こうの CP も、借りているメンバーシップに対して数える。その POST 先はそのメンバーシップの
ワークスペースを解決して決まるが（`engine_usage.go:218-232`）、決定 3 の「そのためだけの
メンバーシップ」にはワークスペースが無いので POST は空振りし、**無関係なワークスペースの
台帳を汚さない**。同じ生成を 2 つの台帳が記録するのは正しい: 一方の配備が消費し、他方が
支払っている。

### 10. 管理行は `managed:false`・`lifecycle:"remote"`・on/off の 2 値

ADR 0076 決定 5 が external 行に書いた契約と同じである（`control-plane/engine_admin.go:205-217`）:
行は `url` と `warm` を持ち、`state`・`desired`・`box`・`stop_eta`・`idle_secs`・`window_*` を
**省略する**。0 で埋めるのではなく省略する——どれもこの配備が主張してよいものではないから。
`warm` はそのまま働く: 手元のゲートウェイが最後に答えを見たモデルだからである。

`ondemand` は remote 行に対して 400 で拒む。external で既にそうしているのと同じ
（`engine_admin.go:463`）——ここでの `off` は経路を閉じることであって、他人の箱を止めることでは
ない。Console は P0 では無改修でよい（すでに `managed` で分岐している）。P1 で「別のフリート」の
表示を足す——向こうに自分のパネルを持ったフリートがいるとき、「外部管理」は正しいが役に立たない
からである。

### 11. external 行にも、SSM 無しで bearer を宣言する欄が要る

小さく、独立していて、それでもこの ADR に属する——型 2 はこれが無いと届かない。`apiKey` が
埋まるのは `AF_COMFY_URL` から合成された comfy の行だけである（`engines.go:768`）。inline の
`AF_ENGINES_JSON` の行——外部の **llm** エンジンを宣言する唯一の道——は bearer を運べず、
検査する者があれば 401 で拒まれる。

`AF_ENGINE_API_KEY_<KEY>` を足し、レジストリ構築時に external 行について読む。これで native・
docker・ec2-single が外部の llm エンジンを持てるようになる——いまは外部の image エンジンは
持てるのに、外部のチャットエンジンはまったく持てない。P2 に置くのは、P0 が何も依存しないから
である（remote 行は自分で資格情報を作る。決定 3）。

## 却下した案

| 却下 | 理由 |
|---|---|
| **Workspace が向こうの CP を直接叩く**（2 本目のベース URL と発行トークンをコンテナに渡す） | 行数は圧倒的に少なく、3 つの点で間違っている: 向こうの CP の使用量 POST は**自分の**ストアを解決するので、無関係なワークスペースに行を届けてしまう（`engine_usage.go:218-232`）。借りるための資格情報がすべてのワークスペースコンテナの環境に載る。そしてワークスペースコンテナの egress 先が増える——ADR 0071 決定 4(a) がまさにそれを避けるために在る |
| **長命の静的トークンを持たせた `external` 行** | 向こうのエンジンが暖かいあいだしか動かず、health プローブは失敗のたびに GPU の箱を買う（決定 5）。成立させるには、向こうのゲートウェイにデータ経路で失効しない資格情報を受け入れさせることになる——手前を楽にするために向こうを弱くする話である |
| **エンジンの箱へのトンネル / VPN**（SSM ポート転送、VPC への Tailscale） | 箱は寿命が短く、Cloud Map で引かれ、SG は CP だけを通す。さらに悪いことに、**箱を買って起こせるのは向こうの CP だけ**——トンネルの先はたいてい何も居ない。そして llama-server と ComfyUI には自分の認証が無い: 到達性がそのまま権限である |
| **向こうの ALB にエンジンを公開する** | 同じ認証の問題を、より広い聴衆に対して抱えることになる。そのうえゲートウェイが存在する理由である起動・ホールド・カタログ検査・計上を捨てる |
| **先に ec2-single のエンジン段をやる**（1 台 VM の配備から ECS のエンジン役を駆動し、それを借りる） | 却下ではなく**順序の入れ替え**。向こう側の費用最適化であって能力ではない——借り手が向き合うのは依然として型 1 で、この ADR は結局必要になる。CloudFormation・IAM・VPC 配置・ec2-single の runbook に触れ、証明には実機の立ち上げが要り、経済性は NAT gateway を避けられるかで決まる。この ADR の後に回せば、完了条件が「同じワークスペースから同じ画像が、より安く出る」になる |

## 上書きする既存の決定と、維持する決定

- **ADR 0071 決定 4（Workspace がエンジンに届く唯一の道はゲートウェイ）: 維持。** 借りていることが
  Workspace から見えないのはこれのおかげであり、この文書はどこでも Agent の改修を提案して
  いない。
- **ADR 0071 決定 5（最初の要求を保持し、10 秒ごとにハートビート）: 維持し、継承する。**
  待つのは向こうで、手元はそのハートビートを中継する。
- **ADR 0076 決定 1（lifecycle は宣言する。external 行には機構を付けない）: 3 つめの値で拡張。**
  付けないものの一覧は変わらない。
- **ADR 0076 決定 4（external のエンジンは即座に失敗する。誰も起こせないから）: remote 行には
  適用しない。その理由はこの決定自身の理由である**——起こせる者がいる。
- **ADR 0053（導出せず宣言する）: 維持。** 決定 1（lifecycle は欄である）でも、決定 2（どの
  エンジンが在るかは向こうの管理者の宣言から読み、プローブから推し量らない）でも。
- **ADR 0072 決定 1（カタログが宣言の全部）: 維持。** 借りた行にとっての宣言は、向こうの配備の
  カタログである（決定 7）。

## 未解決の点（測ってから決める）

1. **手元のホールドは 75 秒でよいか。** 向こうの 45 秒を超え、かつ手元の接続を切るものより
   短くなければならない。45 秒は 60 秒の ALB に対して選ばれた値である（`30-ingress.yaml`）。
   native の CP には proxy が無く、compose には Caddy がある——その `reverse_proxy` は自前の
   タイムアウトを持たないと理解しているが、**(c)、ここでは未確認**。
2. **手元の前段は SSE をバッファせずに通すか。** ハートビートは何もバッファしない場合にだけ
   効く。CP は nginx 向けに `X-Accel-Buffering: no` を既に送っている（`engine_gateway.go:610`
   以降）。Caddy は既定でストリームすると理解している——**(c)**。
3. **借りたコールドスタートは実時間でいくらかかるか。** ホールドが 2 つ、再試行ループが 2 つ、
   その間にインターネットの往復がある。ADR 0071 は冷えた状態で 527 秒、image 役で 165 秒を
   測った。借りた場合の数字は不明で、P1 の最初の実測である。
4. **WAF を有効にした配備で、comfy のポーリングはレート制限に当たるか。** `/history` は生成ごとに
   ポーリングされ、借りるフリート全体が 1 つの NAT アドレスから来る。`WafRateLimitPer5Min` の
   既定は 0 なので（`30-ingress.yaml:166`）、有効にした配備だけの問題である。
5. **「行は最初のカタログ取得の成功で現れる」は運用上受け入れられるか。** 起動時に向こうが
   落ちていると、手元の起動メニューからそのモデルが消え、運用者に届く合図はログ 1 行だけである。
   代案——`api` と `provider` を手元で宣言する——は決定 2 が却下したものである。

## フェーズ

**P0 — 借りるレーン。向こうの配備に触れずに証明できる範囲。**

1. `lifecycle: "remote"` と、`external()` の「ここが管理していない」／「誰も起こさない」への分割。
2. `AF_REMOTE_ENGINE_URL` / `AF_REMOTE_ENGINE_TOKEN` / `AF_REMOTE_ENGINE_KEYS`、および
   AWS 無しでレジストリを建てられるようにする門（`engineTableNeedsAWS` のレーン、
   `engines.go:622`）。
3. トークンの客体: 交換、(鍵, セッション) ごとのキャッシュ、早めの更新。
4. カタログの鏡と、それが adopt する行。
5. remote 行の `dial`: 素通しのパス、`X-AF-Model`、接頭辞なし。
6. `ensureReady` の即時復帰、決定 6 のホールドの順序と `engine_waking` への写像。
7. 決定 10 の管理行。
8. 試験。`engine_external_test.go` の型で、`httptest` の偽ゲートウェイに対して——冷
   （`engine_waking` が中継され、`Retry-After` が保たれる）、暖、ハートビート付きの
   ストリーム応答、トークンの更新、鏡写しのカタログ、起動時に向こうが落ちている場合。

**完了の定義**: 偽ゲートウェイに対して、冷えた借用エンジンが再試行可能な拒否を返し、暖かい
ものが答えを返すこと。実在の向こうの配備に対して、手元のワークスペースの `generate_image` が
画像を 1 枚返し、向こうの使用量行に手元のセッション名が載ること。

**P1 — 実機と、運用者の入口。** 実在の ecs-ec2 配備に対して画像 1 枚を、時間を測って
（未解決 3）。向こうの super-admin に、借用の資格情報を発行するボタン（決定 3）。Console の
「別のフリート」表示（決定 10）。運用者の章——`guide/operate/07-image-engine.*` に節を足し、
`.env` と native の runbook に欄を足す。

**P2 — `AF_ENGINE_API_KEY_<KEY>`**（決定 11）。llm エンジンについて型 2 を到達可能にするもの。

**明示的に範囲外。** TTS: VOICEVOX は CP→エンジンの直 URL で、前段にトークン認証の
ゲートウェイが無い（ADR 0013・0070）ので、音声を借りるのは別の設計である。逆向きの借用
（AWS のフリートが自宅のエンジンを使う）は同じ行を逆に向けるだけだが、向こうが家庭用の網の
後ろにいることになり、到達可能であることをここでは何も仮定していない。
