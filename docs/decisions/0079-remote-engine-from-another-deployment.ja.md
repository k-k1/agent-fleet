# 0079. 別の配備のエンジンを借りる——エンジン表に `remote` の行を足し、待つのも箱を買うのも向こうの Control Plane に任せる

[English](0079-remote-engine-from-another-deployment.md) | 日本語

- 状態: **受理**（2026-09-12）。P0 は「誰もまだ設定していない宣言」の後ろに実装済みである——
  `AF_REMOTE_ENGINE_URL` を設定しない配備は、以前とまったく同じ経路を通る。P0 の完了条件の
  実機側、したがって未解決 1・3・4・6 は未実測である（まだどの配備も何も借りていない）。
- **この文書のために新しく測ったものは無い。** 根拠はすべて出所を書き分けてある——
  (a) ADR 0071・0072・0074・0075・0077 の実測、(b) 2026-09-12 にこのリポジトリのコードから
  読んだ事実（「確認した出典」に file:line で列挙した）、(c) Caddy・ALB・AWS の公開仕様として
  知っているだけで**我々のどの配備でも確かめていない**もの。(c) に依存する決定は
  「未解決の点」に書いた。
- 利用者の要求は 1 つである——**手元のホストで動く Agent Fleet（native / docker）の
  ワークスペースから、AWS で動く Agent Fleet の llm / image エンジンを使いたい。**

## 背景

### 何が 1 つの配備に縛られているか（2026-09-12 に読んだ）

セッションからエンジンまでの経路は 3 段で、**自分がどの配備にいるかを知っているのは
真ん中の 1 段だけ**である。

1. **Workspace は runtime を知らない。** どちらの provider も `AF_CP_BASE_URL` に CP が
   返した `base_url` を足した先にしか行かず（`workspace/agent/engines.go:185`）、資格情報は
   engine session token だけである。AWS SDK もバケットもサービス名も無い。向こうが ECS か
   LAN の箱か別のフリートかは、**この層からは区別できないし、区別する必要も無い**。
2. **ゲートウェイが仮定しているのは「上流 URL が 1 本ある」ことだけ。** `dial` は
   `def.URL` に provider 依存の接頭辞とパスを足して組み立て（`control-plane/engine_gateway.go:766`）、
   エンジン自身の鍵を付けて中継する。ECS に触れる唯一の場所は `ensureStarted`
   （`engine_gateway.go:845`）で、ADR 0076 がそこに「ここは誰もこのエンジンを所有していない」
   という答えを既に教えてある。
3. **行が何であるかを決めているのは登録側。** `newEngineRegistry`（`control-plane/engines.go:635`）
   は表を読み、各行に ECS アダプタ・制御ループ・active set・pending の監視・GPU の梯子を
   付ける。`lifecycle` が `external` の行だけがそのどれも受け取らない
   （`engines.go:753-772`、ADR 0076 決定 1）。

つまりこの ADR が答える問いは「バイトが届くか」ではない。**エンジンが、それを起こして
くれる別の Agent Fleet のものであるとき、その行は何を意味するか**である。

### 向こう側は、すでにトークン認証つきの公開された玄関である

エンジンを持っている配備の側に、新しく開ける口は無い。

- `/engine/*` と `/internal/engine/*` は session 免除で、**すべての形態で**登録される
  （`engine_gateway.go:174-177`、`control-plane/routes.go:33` から無条件に呼ばれる）。
- ecs-ec2 の ingress ALB にパス規則は無く、WAF は運用者が頼まない限り作られない
  （`deploy/aws/ecs/cfn/30-ingress.yaml`）。compose 形態の Caddy は素の
  `reverse_proxy 127.0.0.1:8099` である（`deploy/compose/Caddyfile`）。どちらも全面を通す。
- 資格情報はもともと 2 段である。メンバーシップごとの**発行（issuing）**トークンが、
  セッションごと・エンジンごとの**セッション**トークンを買う
  （`control-plane/engine_token.go:47,85`）。メンバーシップは毎要求で live に解決されるので、
  外されたメンバーはトークンの有効期間内でも拒まれる（`engine_gateway.go:340`）。

無いのは**借りる側**である——「このエンジンは別の配備のもので、その配備が起こしてくれる」
と言う行が、手元のエンジン表に無い。

### 「他人のエンジン」には 3 つの型がある

同じ問題ではない。混ぜると、1 つの設計が残り 2 つに対して間違う。

| 型 | 向こう側 | 手元の CP がすべきこと |
|---|---|---|
| **1. 箱を買うフリート**（ecs-ec2） | 要求に応じて GPU を起こし、また止める CP | 転送し、**向こうに要求を待たせる** |
| **2. 常時稼働のエンジンを指しているフリート**（compose / native / ec2-single ＋ ADR 0076 の `external` 行） | 転送するだけの CP | 転送する。待つものは無い |
| **3. 経路にフリートが無い** | 到達できる URL 上のエンジン本体 | 今の ADR 0076——`external` 行 |

この ADR は型 1 と型 2 を扱う。両者は同じ行・同じコードで、型 2 は単に待つ経路を通らない
だけである。**型 3 は却下ではない——エンジンが常時稼働なら、それが正解である。** ADR 0076 の
`external` 行がすでにそれをしており、あの決定は URL が LAN 上にあることを要求していないし、
決定 7 は前段に reverse proxy を置いて CP に bearer を渡す手順をすでに書いている。

### 今日、コードを 1 行も変えずに何が起きるか

書き留めておく価値がある。以後の実測がこれと比較されるからであり、**あと一歩で使えて
しまう**からである。

`AF_COMFY_URL=https://<向こうのフリート>/engine/image/v1` と
`AF_COMFY_API_KEY=<afe_… のセッショントークン>` を置くと、上流は正しく組み上がる——comfy の
接頭辞は `/` なので（`engine_gateway.go:811`）、要求は向こうの経路に
`/engine/image/v1/prompt` として着く。そのうえで 3 つの理由で失敗し、その 1 つ 1 つが下の
決定になっている。

- **向こうのエンジンが暖まっているときしか動かない。** `engineHealthy` はプローブに 5 秒しか
  与えない（`engine_gateway.go:920`）。寝ているエンジンに対して向こうのゲートウェイは
  ホールドしたのち 503 を返すので、手元の行は——`external` であるから——即座に失敗する
  （`engine_gateway.go:845`）。🔥 **無駄どころではない**: 失敗したその 5 秒のプローブは
  向こうで需要として記録され、**誰も待っていない GPU の箱を買う**。
- **llm 役はそもそも配線できない。** `AF_ENGINES_JSON` の inline 行は受理されるが
  （`engines.go:498`）、bearer を載せる手段が無い。`apiKey` が埋まるのは合成された comfy の行
  （`engines.go:768`）か SSM 経由だけで、external のレーンは SSM を意図的に読まない。
- **`X-AF-Model` が落ちる。** `dial` は Content-Type と Accept しか転送しないので、向こうは
  使用量の計上と pending の判定が両方読んでいるモデルの宣言を失う。

## 決定

### 1. 借りたエンジンは表の 1 行であり、`lifecycle: "remote"` で**宣言する**

`engineDef.Lifecycle` に 3 つめの値を足す。空はこの配備の ECS サービス、`external` は
ADR 0076 の「URL があるだけで、誰も起動しない」行、**`remote` は「別の Agent Fleet の
ゲートウェイであり、そのフリートが起こす」行**である。URL の形から推し量るのではなく
宣言する（ADR 0053）——たまたま `/engine/` を含む URL が、行の意味を黙って変えてはならない。

`remote` 行が受け取らないものは `external` とまったく同じである——ECS アダプタ、制御ループ、
active set、pending の監視、GPU の梯子、稼働ヒートマップのサンプラ。`external` と違うのは
決定 5・6・7 の 3 か所だけで、その違いはすべて**向こう側にエンジンを起こせる者がいる**ことに
由来する。

いまコードが分岐に使っている述語は 1 つではなく **2 つ**であり、レビューはその両方を数えた——
`engineDef.external()` が試験以外で 9 か所、`e.ecs == nil` / `e.ctrl != nil` がさらに 4 か所。
前者を 2 つに割る——「ここが管理していない」（external と remote。表の `service` の不要、
行に与えない機構、管理行の形、`ondemand` の拒否）と、「誰も起こさない」（external だけ。
即時失敗）。1 つの述語を両方に使い回すことが、remote 行に ADR 0076 決定 4 を継がせて
**すべてのコールドスタートを落とす**やり方である。

`e.ecs` 型の 4 か所は手を入れずに済む: `mode`（`engines.go:877`）と管理行の `managed`
（`engine_admin.go:200`）は「ここにサービスが在るか」を訊いていて、remote 行に対してそれは
正しい問いであり、正しく答える。例外は `ensureStarted`（`engine_gateway.go:851`）で、同じ
問いから ADR 0076 決定 4 の拒否を作る——これは「誰も起こさない」の側が別の綴りを着ているだけ
であり、決定 5 が置き換えるのはここである。

そして 2 つではなく 3 つに割れる 1 か所があり、レビューが壊れているのを見つけたのはそこである:
`warm`（`engines.go:928-944`）。到達するには「ここが管理していない」側に入る必要があるのに、
中身は能動的な health プローブ——決定 5 が禁じたものである。remote 行の warm がどこから来るかは
決定 10 に書いた。

### 2. 運用者は「どこ」と「何で」を宣言する。「どれ」は向こうのカタログが宣言する

`AF_COMFY_URL` と同型の環境変数 2 つ、加えて任意の絞り込み 1 つ。

| 変数 | 意味 |
|---|---|
| `AF_REMOTE_ENGINE_URL` | 向こうのフリートのベース URL。パスは付けない: `https://af.example.com` |
| `AF_REMOTE_ENGINE_TOKEN` | `afei_…` の発行トークン（決定 3） |
| `AF_REMOTE_ENGINE_KEYS` | 任意。`image` ならその役だけを借りる。空なら向こうが出しているすべての役 |

**どのエンジンが在り、それぞれの `api` と `provider` が何であるかは、向こうの配備自身の
カタログから読む**（`GET /internal/engine/catalog`、`engine_gateway.go:224`）。手元で宣言は
しない。これは導出ではない——カタログは向こうの管理者の宣言であり、それを宣言してよいのは
彼らだけである。推測は積極的に危険でもある: image 役はある配備では `comfy`、別の配備では
`sdcpp` であり、Workspace はその 2 つでまったく違う要求を組み立てる。推測を外すと、
OpenAI 互換のエンドポイントに ComfyUI のグラフを投げることになる。

その帰結として、**行は起動時ではなく、最初のカタログ取得が成功したときに現れる**。その機構は
ADR 0077 P1 が作った——`engineRegistry.adopt`（`engines.go:374`）は起動時と同じ `build` の
クロージャで行を組み立てる——が、🔴 **配線されているのは AWS のレーンだけで、借りるだけの CP は
そこに一切届かない。** 門は 4 つあり、P0 はそのすべてを開ける必要がある（レビューで 4 つとも
見つかった。どれも難しくはないが、1 つ漏らすとエンジンも経路も無い配備になる）:

- `newEngineRegistry` は `AF_ENGINES_SSM_PARAM`・`AF_ENGINES_JSON`・`AF_COMFY_URL` のどれも
  無い配備に対して nil を返す（`engines.go:639`）。`AF_REMOTE_ENGINE_URL` をこの門に足す。
- 起動時の表に行が無く AWS も無いとき、もう一度 nil を返す（`engines.go:696`）——それは
  まさに「借りる native / docker の CP」である。行は後から来るのだから。
- `reg.build` は `if haveAWS` のときだけ代入され（`engines.go:826-828`）、それが無い `adopt` は
  false を返す（`engines.go:375`）。AWS 無しのレーンにも builder を付ける。
- `adopt` を呼ぶポーリングは**流用できない**: `newEngineTableReloader` は SSM 無しでは
  そもそも作られず（`engine_table_reload.go:61-65`）、読むのは SSM のパラメータである。
  remote のレーンは自分のポーリング——決定 7 のカタログの鏡、同じ 10 分周期——を持ち、
  `adopt` だけを借りる。

さらに `registerEngineRoutes` は、レジストリが nil のとき `exemptPrefix` と 3 つのハンドラの
手前で return する（`engine_gateway.go:168-177`）ので、4 つのどれかで落ちた CP は
`/engine/…` の経路すら持たない。起動時に向こうが到達不能な CP にエンジンが無いのは事実だが、
借りるのにレジストリという物が無いのはバグである。

**手元の行がすでに持っている鍵は借りない**。そして 1 行そう言う。レジストリは `key` を鍵にした
map であり（`adopt` はすでに在る鍵を拒む。`engines.go:383-388`）、`AF_COMFY_URL` には
「管理行が勝つ」という明示の合流規則が既にある（`engineTableWithEnvRow`、`engines.go:601-617`）。
remote 行も同じ向きに倣い、どちらの goroutine が先に着いたかに答えを任せない。

### 3. 資格情報は「そのためだけのメンバーシップ」の発行トークンで、失効はそのメンバーシップの削除

向こうの配備は `afei_<membership>` を署名マスタから決定的に導出し（`engine_token.go:47`）、
そのメンバーシップのすべてのワークスペースに注入する（`control-plane/workspace_lifecycle.go:401`）。
そのトークンが開けるのは `/internal/engine/token` と `/internal/engine/catalog` だけである。
git も MCP もメモも API も開かない。

- 🔴 **人のトークンを使ってはいけない。** 決定的に導出されるので、1 本を無効にする唯一の道は
  署名マスタの回転であり、それは git・memo・schedule のトークンと共有されている
  （`control-plane/git_http.go:88`）。借り手 1 人を失効させるとフリート全体がログアウトする。
- **他に使わないメンバーシップを 1 つ作る。** 招待し、そのワークスペースから
  `AF_ENGINE_ISSUE_TOKEN` を一度だけ読み、ワークスペースを止める。借り手の失効は
  **そのメンバーシップを消すこと**になる: `liveMembership` は毎要求でそれを解決し、
  消えた瞬間に 401 を返す（`engine_gateway.go:340-352`——`GetMembershipByID` で、`!ok` が 401）。
  新しい資格情報の保管も、新しい有効期限も、新しい書式も要らない。
- ついでに決定 9 も無償で解決する: 走っているワークスペースを持たないメンバーシップは、
  向こうの使用量 POST が届けられない相手であり、それがまさに望みである。

🔴 **「一度だけ読む」はこの一文より難しく、レビューは「サインインできる人」無しには
成立させられなかった。** 事実は 3 つ、すべてコードから読んだ:

- 後ろに人のいないメンバーシップは**作れる**: `AddMembership` は
  `UpsertIdentity(ctx, email, key, "")` で identity を先に作るので
  （`internal/tenantsrv/tenants.go:587`）、`user_key` だけを書いた招待はアドレスの無いものを
  1 つ作る。`checkInviteDomain` が効くのはテナントが `allowed_domains` を設定したときだけで、
  そのときはアドレスを要求する。
- しかしトークンは**そのメンバーシップ自身のワークスペースのコンテナの中にしか存在しない**
  （`workspace_lifecycle.go:401`。しかもそれ自体が `if m.publicBaseURL != ""` の中——つまり
  `PUBLIC_BASE_URL` が前提で、AWS の配備はそれを満たす）。そして**他のメンバーのワークスペースを
  起動する経路も、その中にセッションを開く経路も無い**: 管理側にあるのは停止・ホーム消去・破棄
  （`tenant_wiring.go:80-100`）と読み取り専用のセッション一覧（`admin_sessions.go:39`）である。
  つまりその値に届くのは、そのメンバーシップ**として**サインインする道だけであり、`user_key`
  だけの招待が作る identity は IdP が決して認証しない。
- 手元で計算する道は原理的には在って実務では使えない: 導出はこのリポジトリに公開されている
  （`engineSignKey(SHA-256(AF_MASTER_KEY))`、`main.go:128-129`、`engine_token.go:39-49`）ので、
  `AF_MASTER_KEY` を持つ運用者は 10 行と配備 0 でトークンを作れる——が、メンバーシップの **id**
  が必要で、それが現れるのは super_admin の応答 1 つ（クラウド費用の画面、`cloudcost.go:734`）
  だけ、しかも費用が計上されたメンバーシップに限る。招待したばかりの相手には使えない。

したがって P0 の資格情報は**向こうの IdP が実際にログインさせる専用アカウント**である——実在の
アドレスを 1 つ、他に使わず、環境変数 1 本を読むために一度サインインする。運用者向けの章が
述べなければならない費用であり、未解決 6 が問うのはこれである。

**P1 でその経路を作り、これで閉じた**（`POST /api/admin/engines/issue-token`、super_admin のみ、
`control-plane/engine_issue_token.go`）: 向こうの運用者がメンバーシップを指定すると発行トークンが
返るので、借りるのにアカウントもサインインも要らない。`GET` は無い——資格情報が URL や
ブラウザ履歴・プロキシログに載ってはいけない——応答はそのトークンが何を開けるかと失効の方法を
述べ、ゲートウェイが拒むメンバーシップはここでも拒む（409）。401 を返すだけの文字列を渡すより
良いからである。意図的に **P0 には入れなかった**: P0 は**エンジンを持っている配備に新しい
コードを配備せずに**証明できなければならず、その偽ゲートウェイの半分（フェーズ P0 の 8）は
どんな資格情報も要らない。

### 4. パスは素通しし、`X-AF-Model` も一緒に送る

remote 行の上流は `<AF_REMOTE_ENGINE_URL>` ＋ 向こうが自分で名乗ったパス ＋ 手元の
`/engine/<key>/v1/` の後ろのパス、およびクエリである。provider 依存の接頭辞
（`engineUpstreamPrefix`、`engine_gateway.go:811`）は付けない——**その書き換えは向こうの
ゲートウェイの持ち物**であり、2 度掛けると `/v1/v1/chat/completions` になる。

向こうの `/internal/engine/token` の答えは `base_url`（`/engine/<key>/v1`、
`engine_gateway.go:215`）を載せてくるので、その中間の区間は**組み立てるのではなく読む**。
ここで組み立てることは、この文書が向こうの経路の配置を主張することであり、Workspace が
意図的にやっていないこと——`AF_CP_BASE_URL` ＋ 返ってきた `base_url` を叩く
（`workspace/agent/engines.go:185`）——と同じである。同じ規則を 1 段上でも使う。

🔴 **remote 行の資格情報は要求ごとなので、他の 2 つと同じ場所には置けない。** `dial` が
提示するのは `eng.apiKey`（`engine_gateway.go:789-791`）で、行を組み立てたときに決まる 1 本の
文字列である。決定 8 のトークンは (エンジンの鍵, **セッション**) ごとであり、そもそも `dial` は
claims を受け取っていない（`dial(ctx, eng, r, body)`、`engine_gateway.go:754`）。P0 で
セッションを通し、bearer を要求ごとに解決する。`apiKey` は他の 2 つの lifecycle に対して
そのままである。

`dial` は `X-AF-Model` も転送しなければならない。向こうがどのカタログ行への要求かを知る手段で
あり、使用量の計上が読み、モデルがインスタンスへ同期中のあいだ `engine_waking` を返す
pending の判定も読む（ADR 0072 P2 欠落 7）。落としても要求は失敗しない——向こうの配備の
計上と、いちばん役に立つ再試行可能な拒否を、静かに劣化させるだけである。バグとしては
最悪の形である。

### 5. remote 行に health は掛けない。ここでは起こさない

`ensureReady` は remote 行に対して即座に返る。プローブも起動も待ちも無い。

素朴な理由だけで足りる: 掛ける先が無い。`engineHealthy` が訊くのは `engineHealthURL(d)`——
行の URL ＋ `/health`（`engine_gateway.go:911-913`）——であり、向こうのフリートはそこに
エンジンについて何かを言うものを公開していない。しかも自身を 5 秒で区切るので
（`engine_gateway.go:920`）、実測 527 秒の冷間起動（ADR 0071）に対しては、プローブが
エンジンに**届く**唯一の形においてすら失敗しかしない。

🔥 **そしてその 1 つの形では、無駄なだけでなく高くつく。** 行の URL がすでにエンジンのパスを
含んでいるとき——上の「コードを 1 行も変えない」基準線、
`AF_COMFY_URL=https://<向こうのフリート>/engine/image/v1` がそれである——プローブは向こうの
ゲートウェイに `/engine/image/v1/system_stats` として着地し、需要を記録して箱を買う
（`engine_gateway.go:384` 以降）。**必ず失敗する 5 秒の検査が $1.26/時のインスタンスを
起動する**——ここで起こりうる最悪の帰結であり、`external` のレーンを素朴に流用すると
それが出来上がる。決定 4 の URL は素のベースなので、そこへのプローブは向こうの CP の根までしか
届かない——が、運用者が最初に手を伸ばすのは手で書いたその行である。

⚠️ 決定 10 の `warm` も health プローブである。生成の経路ではなく管理パネルの経路で走る。
それがこの決定の残り半分であり、レビューが本文の誤りを見つけたのはそこである。

### 6. 🔥 手元のホールドは向こうより長く、その期限切れは `engine_waking` である

コールドスタートが成立するかどうかを決める罠はここである。

- 向こうの非ストリーミング経路は 45 秒ホールドし、`Retry-After` 付きの
  `503 engine_waking` を返す（`engine_gateway.go:100`。ingress ALB の 60 秒アイドルの下に
  抑えてある——`idle_timeout.timeout_seconds: "60"`、`30-ingress.yaml:452`）。
- 🟢 その拒否は中継を**生き延びる**: `plain` は上流のヘッダ・ステータス・本文をそのまま
  複写する（`engine_gateway.go:738-746`）ので、向こうの `engine_waking` と `Retry-After` は
  provider まで無傷で届く。この決定全体が乗っている機構であり、コードは要らない。
- 手元の非ストリーミング経路も既定は同じ 45 秒。先に切れたほうが答えを決め、手元のほうが
  先に時計を回し始めている。
- 🔴 手元の期限切れは、いまは `engine_waking` に**ならない**: `ensureReady` が経路上に無いので
  期限は `engineClient.Do` の中で発火し、`plain` はそれを `engine_unavailable` に変える
  （`engine_gateway.go:732-736`）。そして image の provider は `engine_waking` を 16 分
  再試行するが、**`engine_unavailable` はまったく再試行しない**
  （`workspace/agent/internal/imagegen/sdcpp.go:505`。`sdcppRetryable` は*共有*の述語で、
  comfy も `engineHTTPAttempt` 経由でそこに来る——`comfy.go:670-681`——ので、これは sd.cpp
  だけでなく image の provider 両方に効く）。コールドスタートは恒久的な失敗になり、
  しかも「起動に失敗した」と報告される。

したがって remote 行では、変更は 2 つで、効いているのは 2 つめである:

- ホールドは**行ごとに**上げる。全体では上げない。`enginePlainHold()` は引数を取らず
  （`engine_gateway.go:100-107`）、75 秒を新しい*既定*にすると ecs-ec2 のあらゆる配備で管理行の
  ホールドが **ALB の 60 秒を超え**、45 秒がまさに避けるために選ばれた 504 を呼び戻す
  （`30-ingress.yaml:452`）。P0 は行を見るようにし、45 秒はそのまま残す。他に待ちを縛るものは
  無い: `engineClient` は `Timeout` を設定せず `ResponseHeaderTimeout: 0` である
  （`engine_gateway.go:135-144`）ので、ホールドが唯一の境界であり knob で足りる。
- remote 行への中継中に期限へ達した場合は `Retry-After` 付きの `engine_waking` に写像する——
  それが事実だからである。🔴 **借りたコールドスタートを成立させるのは 75 秒ではなくこれである。**
  向こうの 45 秒は*向こうの配備の* `AF_ENGINE_PLAIN_HOLD`——こちらからは読めず、仮定する権利も
  無い knob である。向こうの運用者が 120 秒に上げれば、こちらが何秒にしていようと手元の期限が
  また先に来る。数字が決めるのは「向こうの文面が届くか、こちらの文面になるか」の頻度だけで、
  要求が再試行可能かどうかを決めるのは写像である。

ストリーミング経路には何も要らない——ただし一見の理由とは少し違う: 向こうは 200 を即座に
flush するが、最初の*本文*のバイトは 10 秒後の最初のハートビートであり
（`engine_gateway.go:620-628`）、`dial` はそのバイトで待つ（`:797-800`）。隙間を埋めるのは、
手元の経路が同じ周期で自分のハートビートを書いていることであり、そこでの境界は plain の
ホールドではなく `engineWakeTimeout()`（900 秒）である。両側が 900 秒待って手元が 1 往復ぶん
早く切れる——失うのは向こうの言い回しだけである。

手元の配備が自前の proxy の後ろにいる場合だけは、この処理から問い合わせようがない——だから
knob にしてあり、だから未解決 2 がある。

### 7. カタログは向こうの配備から読み取り専用で鏡写しにする

`engineCatalog` は `store.EngineModelStore` の上の薄いキャッシュである
（`control-plane/engine_catalog.go:58`）。**remote 行のカタログには別の「ソース」を与える。
別のストアではない。** 欄 1 つと `list` の分岐 1 つ（`engine_catalog.go:74-88`）で済み、
その読み手が使われているのはそこだけである。

🔴 起草時は「このインタフェースの実装を渡し、書き込みは拒む」と書いてあり、レビューは
そういう実装が**何も拒まない**ことを見つけた: 書き込みは 1 つも `engineCatalog` を通らない。
10 個すべてが `a.mgr.store` か `g.models` を直に叩き、鍵はパスの中の `key` である——
トグルが `engine_admin.go:865,868,876,882,885,888`、登録が `:1132`、削除が `:1177`、
取り込みが `engine_ingest.go:820,869`。インタフェースは 10 メソッド（読み 1・書き 9）なので、
その実装は「効かない」だけでなく「大きい」方の変更でもあった。拒否は書き込みが在る場所に置く:

- **管理の書き込み経路が remote の役を拒む。** 理由を添えた 400 で、`ondemand` を拒むのと
  同じ形である（決定 10）。借りたカタログは向こうの管理者の文書であり、このパネルはそれを
  編集する場所ではない。
- **鏡は空のリストであり、ソースの不在ではない。** `hasModels` はストアがまったく無いとき
  **true** を返す（`engine_catalog.go:122-124`）——false の側が GPU を止めるので意図的に
  そうしてある。ソースが単に無い remote 行は、したがって `serve` の「モデル無し」の門を通り、
  そのあとモデル名を書いたチャット要求すべてに 404 `model_unknown` を返す
  （`engine_gateway.go:435-440`）。最初の取得より前ですら、nil として見せてはならない。

手元で手入力する案——LAN の ComfyUI に対する ADR 0076 の答え——は**ここでは却下する**。

- Workspace は ComfyUI のグラフを**自分の**配備のカタログ行（`files`・`params`・`base_model`）
  から組み立てる。向こうのエンジンには、向こうの active set が置いたファイルしか無い。
  両者の乖離は生成時の `Value not in list` であり、ADR 0072 の P2 の記録がその失敗の
  読みにくさを残している。
- `negative_always`、モデルごとの窓、宣言されたサイズ、`warm`——どれもすでに向こうの
  カタログに在り、どれも推測すれば間違える。

🟢 向こうのカタログは実際にすべてを載せている——`files`（flag ＋ `s3_key`）・`params`・
`base_model`・`sizes`・`negative`・`selected`・`default`・`warm`・窓
（`engine_catalog.go:556-604`）。そして*鏡写しにした* `s3_key` が「他人のバケットの配置の
漏れ」ではなく「正しい」ものになる理由は 1 つで、使われるのは常にその**ベース名**だけだから
である: Agent はローダのノードに入れるファイル名として最後のパス区間を取る——「箱はバケットの
鍵をそのままディスクに写す」から（`workspace/agent/engines.go:519-521` と `:544-556`）。
バケットは無関係で、旅をするのはファイル名である。

⚠️ ただし線の上の行は `store.EngineModel` ではなく、2 つの欄は読むのではなく鏡が復元する:

- **`kind` は線の上にまったく無い。** LoRA は `model_rows` の隣の別配列に乗る
  （`engine_gateway.go:270-286`）ので、鏡は *どちらの配列から来た行か* で `Kind:"lora"` を
  立てる。間違えると借りた LoRA はすべてモデルになる: 起動メニューに入り、LoRA だけの
  カタログで `hasModels` が true になる——何も動かさないために箱を起こすことになる。
- **`enabled` も線の上に無い。** 有効な行しか publish されないからである。鏡はこれを true に
  する。「向こうが off にした役」が空のリストに潰れるのも同じ理由である。
- `bytes` は落ちるので、パネルの「次の冷間起動に +N 秒」は借りた行では 0 になる。無害である——
  その見積もりはこの配備が払わない箱についての話だから。

更新は Agent と同じ 10 分の周期で。取得に失敗したら前の答えを保つ——手元のカタログが
そうしているのと同じ理由である（一時的な失敗が「モデルが無い」＝「このエンジンを起動するな」に
化けてはならない）。決定 2 の行を adopt するのも、このポーリングである。

**向こうのフリートが off にした役は、そのカタログから消える**（`engine_gateway.go:224` が
`engineModeOff` を飛ばす）。すると鏡にはその行のモデルが無くなり、`serve` はそれを
`engine_unavailable` と「このエンジンには有効なモデルが無い」で既に拒む。つまり行はプロセスの
生存中に**足されはするが、消えはしない**——生きている行を消すことをレジストリは支えていないし、
支える必要も無い。

### 8. 手元のセッション名を向こうに伝える

手元のゲートウェイは手元のセッショントークンを検証済みなので、セッションを知っている
（`engineSessionClaims.Session`）。発行トークンを向こうのセッショントークンに交換するとき、
その名前を伝える。向こうは言われたとおりに受け取り、検証はしない——意図的である
（`engine_gateway.go:182-186`）。向こうの `recordUsage` は、その名前を載せた使用量行を組み立てる。

🔴 **2026-09-13 訂正: その行はこのあと捨てられる。つまりこの決定は向こうの運用者に何ももたらさない。**
起草は、この名前を「向こうの運用者が借り手ごとの支出を見分けられる唯一の手段」（llm 役に限る）と
書いた。そうではない。名前を載せる行が向こう側に存在しないからである。台帳は Control Plane の表
ではなく **Workspace の中のファイル**であり（`engine_usage.go:6-10`——CP 自身の使用量の表
`0008_usage.sql`・`0053_usage_hourly.sql`・`0055_engine_hourly.sql` はどれも占有秒であって
feature 列を持たない）、行を記録する唯一の方法は**稼働中の**ワークスペースへ POST することだが、
決定 3 の専用 membership はそれを持たない。決定 9 は 2 段落あとで同じことを**利点として**書いて
おり、両者は突き合わされないままだった。コードに合っているのは決定 9 のほうである。

名前がいまも果たしていることは、実在するが小さい: 向こうまで届くこと、向こうのトークンがそれを
対象に発行されること、そして向こうに永続する記録を作るなら鍵にせざるを得ないものであること
（未解決 7）。

トークンは (エンジンの鍵, セッション) ごとにキャッシュし、期限より前に更新する。Agent が
既にやっているのと同じ形で、TTL は 30 日なので（`engine_token.go:85`）安い。

### 9. 会話は両側が数える。絵はどちらも数えない

手元の CP は今までどおり数える——`recordUsage` が中継したバイトから使用量を読み
（`control-plane/engine_usage.go:198`）、要求したワークスペースへ行を POST する。ここは
何も変わらない。

向こうの CP も、借りているメンバーシップに対して数える。その POST 先はそのメンバーシップの
ワークスペースを解決して決まるが（`engine_usage.go:218-232`）、決定 3 の「そのためだけの
メンバーシップ」にはワークスペースが無いので POST は空振りし、**無関係なワークスペースの
台帳を汚さない**。同じ会話を 2 つの台帳が記録するのは正しい: 一方の配備が消費し、他方が
支払っている。

🔴 **image 役はどちらの側にも「エンジンの」使用量の行を書かない。起草時の本文はそう
書いていなかった。**
`engineUsageRowFor` は `api` が `chat` でない行を拒む（`engine_usage.go:170-172`）ので、
`recordUsage` はメモリ上の warm モデルの記録で止まって返る。これは既存で意図的でもあるが
（image の答えはトークン数を持たない）、この ADR が引き受けなければならない帰結がある:

- 借り手自身の記録は残る: Agent が自分の台帳に `tool.imagegen` として、トークンではなく枚数と
  ピクセルで書く（`workspace/agent/engines.go:403`、ADR 0069）。借りた生成が**こちら側で**
  見えなくなるわけではない。
- 🔴 一方で向こうの運用者には、**借りられた生成についての永続する記録が何も残らない**:
  需要の印と、1 プロセスのメモリ上の warm モデルの記録だけである。借りた image の支出の帰属は、
  したがって決定 8 が既に解いた問題ではなく未解決（7）である。
- ⚠️ そして image 役には、そもそも伝えるセッション名が無い。Agent はそこでは手元の CP に
  **ワークスペース単位**のエンジントークンを求める（セッションは空。意図的である——その資格情報は
  Agent のプロセスから出ず、使用量の行は Agent 側で書かれるから。
  `workspace/agent/engines.go:399-405`）ので、向こうのトークンを買うときの claims にセッションが
  乗っていない。決定 8 は二重の意味で llm 役についての記述である。
- P0 の完了条件を変えなければならない。「向こうの使用量行に手元のセッション名が載る」は、
  借りた **llm** 役で証明でき、`generate_image` では証明できない。

### 10. 管理行は `managed:false`・`lifecycle:"remote"`・on/off の 2 値

ADR 0076 決定 5 が external 行に書いた契約と同じである（`control-plane/engine_admin.go:205-221`）:
行は `url` と `warm` を持ち、`state`・`desired`・`box`・`stop_eta`・`idle_secs`・`window_*` を
**省略する**。0 で埋めるのではなく省略する——どれもこの配備が主張してよいものではないから。
`managed:false` には何も要らない: すでに `e.ecs != nil` である（`engine_admin.go:200`）。

起草時にここで 2 つ間違えており、レビューは両方を見つけた:

- 🔴 **`lifecycle` は行自身の欄ではなく、ハードコードされた定数である。** ハンドラは
  `row["lifecycle"] = engineLifecycleExternal` と literal で書く（`engine_admin.go:210`）ので、
  remote 行は自分を `external` と名乗り、P1 の「別のフリート」の表示は分岐する先を持たない。
  P0 で `e.def.Lifecycle` を出す。（Console 側は準備済みだと確認した: 行の型に
  `lifecycle?: string` は既に在り（`console/src/features/settings/admin/engineTypes.ts:311`）、
  まだどの部品も読んでいない——だから P0 に Console の改修は本当に要らない。）
- 🔴 **`warm` は「そのまま働く」ことが 2 重に無い。** 書かれたままだと remote 行に false を
  返す——`warm` は `e.ctrl != nil` を過ぎて `if !e.def.external() { return false }` に落ちる
  （`engines.go:928-934`）——のでパネルは借りたエンジンを常に冷えていると報告する。かわりに
  external の枝に入れるのはもっと悪い: その枝は 10 秒キャッシュの後ろの能動的な
  `engineHealthy` 呼び出しであり（`engines.go:893-896,935-944`）、パネルを開くたびに走る——
  まさに決定 5 が拒んだプローブである。そして「手元のゲートウェイが最後に答えを見た」ものは
  コードに存在しない。いちばん近いのは `noteServed` で、それは warm なモデルの *id* である。
  **remote 行の `warm` は鏡から読む**: 向こうのカタログは、向こうの CP が最後に答えを見た
  モデルに既に印を付けている（`"warm": true`、`engine_catalog.go:591-594`）。それが向こうの
  配備自身の観測であり、ここで得られる唯一正直なものである。

`ondemand` は remote 行に対して 400 で拒む。external で既にそうしているのと同じ
（`engine_admin.go:463`）——ここでの `off` は経路を閉じることであって、他人の箱を止めることでは
ない。Console は P0 では無改修でよい（すでに `managed` で分岐している）。P1 で「別のフリート」の
表示を足す——向こうに自分のパネルを持ったフリートがいるとき、「外部管理」は正しいが役に立たない
からである。

⚠️ 運用者が必要とする行がもう 1 つある: remote 行の失敗は**行の名前を出さずに**ログされる。
`streamed` は `eng.ecs.logKey()` を通して印字するが（`engine_gateway.go:658`、`:692`）、それは
nil 安全な代わりに、アダプタが無いとき素の `"engine"` を返す（`engine_ecs.go:464-469`）——
未解決 5 が「運用者の唯一の signal はログ 1 行」としているのに、借りた 2 つの役が見分けられない。
P0 はその 2 行を `eng.def.Key` で出す。

### 11. external 行にも、SSM 無しで bearer を宣言する欄が要る

小さく、独立していて、それでもこの ADR に属する——型 2 はこれが無いと届かない。`apiKey` が
埋まるのは `AF_COMFY_URL` から合成された comfy の行だけである（`engines.go:768`）。inline の
`AF_ENGINES_JSON` の行——外部の **llm** エンジンを宣言する唯一の道——は bearer を運べず、
検査する者があれば 401 で拒まれる。

`AF_ENGINE_API_KEY_<KEY>` を足し、レジストリ構築時に external 行について読む。これで native・
docker・ec2-single が外部の llm エンジンを持てるようになる——いまは外部の image エンジンは
持てるのに、外部のチャットエンジンはまったく持てない。P2 に置くのは、P0 が何も依存しないから
である（remote 行は自分で資格情報を作る。決定 3）。

## 却下した案

| 却下 | 理由 |
|---|---|
| **Workspace が向こうの CP を直接叩く**（2 本目のベース URL と発行トークンをコンテナに渡す） | 行数は圧倒的に少なく、3 つの点で間違っている: 向こうの CP の使用量 POST は**自分の**ストアを解決するので、無関係なワークスペースに行を届けてしまう（`engine_usage.go:218-232`）。借りるための資格情報がすべてのワークスペースコンテナの環境に載る。そしてワークスペースコンテナの egress 先が増える——ADR 0071 決定 4(a) がまさにそれを避けるために在る |
| **長命の静的トークンを持たせた `external` 行** | 向こうのエンジンが暖かいあいだしか動かず、health プローブは失敗のたびに GPU の箱を買う（決定 5）。成立させるには、向こうのゲートウェイにデータ経路で失効しない資格情報を受け入れさせることになる——手前を楽にするために向こうを弱くする話である |
| **エンジンの箱へのトンネル / VPN**（SSM ポート転送、VPC への Tailscale） | 箱は寿命が短く、Cloud Map で引かれ、SG は CP だけを通す。さらに悪いことに、**箱を買って起こせるのは向こうの CP だけ**——トンネルの先はたいてい何も居ない。そして llama-server と ComfyUI には自分の認証が無い: 到達性がそのまま権限である |
| **向こうの ALB にエンジンを公開する** | 同じ認証の問題を、より広い聴衆に対して抱えることになる。そのうえゲートウェイが存在する理由である起動・ホールド・カタログ検査・計上を捨てる |
| **先に ec2-single のエンジン段をやる**（1 台 VM の配備から ECS のエンジン役を駆動し、それを借りる） | 却下ではなく**順序の入れ替え**。向こう側の費用最適化であって能力ではない——借り手が向き合うのは依然として型 1 で、この ADR は結局必要になる。CloudFormation・IAM・VPC 配置・ec2-single の runbook に触れ、証明には実機の立ち上げが要り、経済性は NAT gateway を避けられるかで決まる。この ADR の後に回せば、完了条件が「同じワークスペースから同じ画像が、より安く出る」になる |

5. **「行は最初のカタログ取得の成功で現れる」は運用上受け入れられるか。** 起動時に向こうが
   落ちていると、手元の起動メニューからそのモデルが消え、運用者に届く合図はログ 1 行だけである。

   答えた（P1）。** 問い自体は本物だった——他のメンバーのワークスペースを起動する管理経路も

7. **借りた利用は、向こう側でどう帰属させるか。** ~~借りた IMAGE の生成は~~ ——
   **問いは起草が置いたより広く、起草の「いちばん安い答え」は成立しない（2026-09-13）。**

   **広い**: 借りた**会話**もまた、向こうに永続する記録を残さない。向こうの CP の post-back は
   借り手 membership のワークスペースを解決し、無ければ無言で return する
   （`engine_usage.go:226-232`）。決定 3 の専用 membership はそれを持たないし、発行ルートは
   むしろ「ワークスペースを持つ membership を貸すな」と向こうの運用者に警告する
   （`engine_issue_token.go:54-56, 68-70`）。つまり向こうの運用者に残るのは「買われた GPU」と
   「誰のためだったかの記録の不在」で、それは**両方の役について**である。決定 9 は既にそう
   書いており、そうでないと書いていた決定 8 は上で訂正した。

   **いちばん安い答えは成立しない。** `engineUsageRowFor` に image でもトークン 0 の行を出させても、
   その行には行き先が無い: 台帳は Workspace の中のファイルで（`engine_usage.go:6-10`）、向こうの
   membership にワークスペースは無く、chat の行を捨てるのと同じ分岐がその行も捨てる。そもそも形
   としても誤りである理由が 2 つある——image の要求が向こうで使うトークンは**セッションが空**で
   （Agent が手元の CP に **ワークスペース**スコープのエンジントークンを求めるため。
   `workspace/agent/engines.go:399-418`）、帰属させる借り手がそもそも載らない。そして
   `engine.image` は ADR 0029 §2 の凍結された列挙に無い feature 値であり、借り手が既に持っている
   `tool.imagegen` の行の上に重ねて書くことになる。`TestOnlyChatEnginesAreCountedByTheGateway`
   （`engine_gateway_test.go:766-790`）は、まさにそれを拒むために在り、コメントに同じ 2 つの理由が
   書いてある。

   **残る道は、受け口を作ること。** 向こうの Control Plane 側である。membership と永続ストアの
   両方を持っているのはその側だけだからだ。形は 2 つあり、その分かれ方は決定 9 が引いた線と
   同じである——会話には行があり、絵には無い:

   - **会話には、行の落ちる先を。** 行は捨てられるその瞬間に、既に完成した形で存在している:
     `engineUsageRowFor` が借り手のセッション名を載せて組み立て、`postUsage` が宛先が無いことを
     理由に投げ捨てている。membership に稼働中のワークスペースが無いときにそれを受け取る表を
     向こうの CP に置くだけなら、新しい計数も、列挙への新しい値も要らない。🔴 **しかもこれは
     借用とまったく関係のない穴を塞ぐ**: 同じ分岐は、普通の利用者のエンジン行も「答えたあと・
     記帳の前にワークスペースが止まった」だけで黙って落としており、`engine_usage.go:226-232` の
     コメント自身がそれを認めている。天秤にかけるべき対価は、ADR 0029 の台帳が**意図的に**
     Workspace の中のファイルであること——エンジンの行が住める 2 つめの場所を作ることになる。
   - **絵には、行ではなく秒と要求数を。** 記録すべきトークンが無く、帰属させるセッションも無い
     （上述）ので、正直な単位は `engine_hourly`（`migrations/0055_engine_hourly.sql`）が既に
     持っているもの——エンジンの鍵ごと・時間ごとの GPU 秒——に、欠けている membership 軸を
     足したものになる。ゲートウェイは demand を記録するその場所で `mv.MembershipID` を手にして
     いる。

   どちらにせよ、これは借りるかどうかに関わらず**向こうの配備自身の記帳**の話であり、ADR 0048
   決定 2 と ADR 0071 決定 9 はどちらもそこに値段を付けることを禁じている。ここでは意図的に
   決めない。借り手はこれが無くても何も止まらない。無いことの代価は、向こうの運用者が「あの箱は
   誰のためだったか」に答えられないことで、今日それに答えているのは監査ログの
   `engine.issue_token` 1 回きり（`engine_issue_token.go:141`）であり、以後は無い。

## フェーズ

**P0 — 借りるレーン。向こうの配備に触れずに証明できる範囲。**

1. `lifecycle: "remote"` と、`external()` の「ここが管理していない」／「誰も起こさない」への
   分割——9 か所すべて。どちらにも当たらない `warm`（決定 10）を含む。
2. `AF_REMOTE_ENGINE_URL` / `AF_REMOTE_ENGINE_TOKEN` / `AF_REMOTE_ENGINE_KEYS`、および決定 2 が
   挙げた 4 つの門: 起動の門（`engines.go:639`）、表が空のときの return（`:696`）、
   AWS のレーン外での `reg.build`（`:826-828`）、remote のレーン自身のポーリング。AWS を
   そこから追い出しているのは `engineTableNeedsAWS` のレーン（`engines.go:622`）である。
3. トークンの客体: 交換、(鍵, セッション) ごとのキャッシュ、早めの更新——そして `dial` への
   引き回し。`dial` は今 claims も要求ごとの bearer も持っていない（決定 4）。
4. カタログの鏡: `engineCatalog` のソース、`kind` と `enabled` の復元、remote の役を拒む
   管理の書き込み経路、そしてポーリングが adopt する行。
5. remote 行の `dial`: 向こうが名乗った `base_url`、素通しのパス、`X-AF-Model`、接頭辞なし。
6. `ensureReady` の即時復帰、決定 6 の**行ごとの**ホールドと `engine_waking` への写像。
7. 決定 10 の管理行: 行から出す `lifecycle`、鏡から読む `warm`、鍵を名乗る 2 本のログ。
8. 試験。`engine_external_test.go` の型で、`httptest` の偽ゲートウェイに対して——冷
   （`engine_waking` が中継され、`Retry-After` が保たれる）、手元のホールドの期限切れ
   （`engine_unavailable` ではなく `engine_waking`）、暖、ハートビート付きのストリーム応答、
   トークンの更新、LoRA を含む鏡写しのカタログ、拒まれる管理の書き込み、起動時に向こうが
   落ちていて——その後到達可能になり adopt される場合。ここに資格情報も向こうの配備も要らない。

**完了の定義**: 偽ゲートウェイに対して、冷えた借用エンジンが再試行可能な拒否を返し、暖かい
ものが答えを返し、何も無い状態で起動した CP が借用行を adopt すること。実在の向こうの配備に
対して、手元のワークスペースの `generate_image` が画像を 1 枚返し、借りた llm 役への
チャット補完 1 回が、手元のセッション名を載せた使用量行を向こうに残すこと（image 役は何も
残さない——決定 9）。

**P1 — 実機と、運用者の入口。** 実在の ecs-ec2 配備に対して画像 1 枚を、時間を測って
（未解決 3）。向こうの super-admin に、借用の資格情報を発行するボタン（決定 3）。Console の
「別のフリート」表示（決定 10）。運用者の章——`guide/operate/07-image-engine.*` に節を足し、
`.env` と native の runbook に欄を足す。

**P2 — `AF_ENGINE_API_KEY_<KEY>`**（決定 11）。llm エンジンについて型 2 を到達可能にするもの。

**明示的に範囲外。** TTS: VOICEVOX は CP→エンジンの直 URL で、前段にトークン認証の
ゲートウェイが無い（ADR 0013・0070）ので、音声を借りるのは別の設計である。逆向きの借用
（AWS のフリートが自宅のエンジンを使う）は同じ行を逆に向けるだけだが、向こうが家庭用の網の
後ろにいることになり、到達可能であることをここでは何も仮定していない。

  返す。決定 7 自身の失敗が、決定 7 が挙げていない経路で来る。いまはその行を build で拒み理由を
  ログし、二重の鍵として `catalogSource()` は nil handle でも空リストを返す。(b) **向こうは
  「off」を「消す」ことで言う。** mode が `off` の役、あるいは有効モデルが 0 になった役は、向こうの
  カタログのハンドラが空で報告するのではなく*飛ばす*ので、在った行だけで鏡を更新すると、
  提供を止めた役を提供し続ける。poll は借用中なのに答えに出てこない役について空行を合成し、
  その行の 10 秒キャッシュも捨てる（でないと変化がもう 1 窓ぶん遅れる）。
- **決定 4 は signature が増えた。** `dial` はセッションの claims を取る（`dial(ctx, eng, r,
  body, claims)`）。bearer が (エンジンの鍵, セッション) ごとなのに、どのセッションが訊いている
  かを知る手段が無かったからである。向こうの `base_url` は決定どおりトークンの答えから読み、
  不明なときは `/engine/<key>/v1` を推測せずエラーにする。
- **決定 6 は「2 つめの既定」であって新しい既定ではない。** `enginePlainHold()` を
  `enginePlainHoldFor(eng)` に置き換えた。管理行の既定は 45 秒のままで、それを ALB の 60 秒の
  下に固定していた試験に「借用行はそれより長い」「2 つを同じにできない」も加えた。
  `engine_waking` への写像は中継が失敗しうる 3 か所すべてを包み、切断された要求では発火しない
  ——「context が終わったのだから waking だろう」と緩めると、もう居ない相手に
  `engine_waking` を返すことになる。
- **決定 7 の拒否はもう一度場所を変えて、5 本の経路に着いた。** `putModel`・`postModel`・
  `deleteModel`・`putNegative`・`postIngest` が借用の役に 400 `engine_not_ours` を返し、文面は
  向こうの配備を名指しする（運用者の次の行動はそちらだから）。`negative_always` は、ここに
  書けないのと同じ理由で鏡から読む。新しいエラーコードは Console のカタログに項目が必要で、
  無いと `TestCPEmittedErrCodesHaveConsoleCatalogEntry` が落ちる——実際に落ちた。
- **変わらなかったこと（書いておく価値がある）:** Agent の変更 0・Workspace の変更 0・
  CloudFormation の変更 0・新しい IAM 0。Console は i18n の 1 行だけで、決定 10 の予想どおり。

**まだやっていない・P0 の外:** 実機とその時間（未解決 3）、向こうの super-admin のボタン

## P2 の実装（2026-09-13）

決定 11 だけ。Control Plane の中だけで完結する: `AF_ENGINE_API_KEY_<KEY>` を、**external** の行に
ついてレジストリ構築時に読み、`dial` と `engineHealthy` が既に上流へ提示している同じ `apiKey`
欄に入れる。設定しなければ何も変わらない。決定の文面を超えて、書いたことで決まった点:

- **名前は畳む。表のキーは自由文字列だが、環境変数名はそうではないから。**
  `engineAPIKeyEnvName` はキーを大文字にし、`[A-Z0-9]` 以外の文字をすべて `_` にする——
  `image-2` は `AF_ENGINE_API_KEY_IMAGE_2`。2 つのキーが同じ名前に畳まれ得るが、それは誰も書かない
  表であり、代案は「bearer をそもそも宣言できないキー」を作ることになる。
- **変数は配備ごとでなく行ごと。** 1 本の共有 bearer にすると、llm エンジンの前に立つ
  reverse proxy の資格情報を、同じ網の ComfyUI に提示することになる。2 つは別の箱・別の
  reverse proxy であり、ADR 0076 の脅威モデルは「到達可能性がアクセス制御」である。
- **`AF_COMFY_URL` が合成する行では `AF_COMFY_API_KEY` が勝ち**、汎用の変数はその予備であって
  死に変数ではない: 同じ行を inline で宣言した運用者には、設定すべき `AF_COMFY_API_KEY` が
  そもそも無い。両方が宣言されているときは 1 行のログが両方の名前を出す——いま編集したはずの
  bearer が黙って使われないのは、読むもののない 401 だから。
- **述語は `external()`。この ADR 全体で、狭いほうが正しい唯一の場所。** 管理行の鍵は SSM の
  SecureString であり、借用行は (エンジンのキー, セッション) ごとに自分で買っていて `dial` は
  借用行の `apiKey` を読まない（決定 4）。静的な値をそこに置くのは、既に答えのある問いへの
  2 つめの・古いほうの答えになる。これを固定する試験は、借用行を**同じキー・同じ変数を設定した
  external の行**と対にしている——管理行と対にすると「何も読まない」実装でも緑になる。
- **試験は 4 本**、`engine_external_test.go` に: 名前の畳み方、上の lifecycle の対、両方向の
  優先順位、そして能力そのもの——AWS がどこにも無い inline の表と、**要求だけでなくヘルス経路でも**
  bearer を検査するエンジンに届くチャット補完。これ以前は、同じ表は `apiKey` が空の行を作り、
  ヘルス検査だけで `engine_unavailable` に終わっていた。
