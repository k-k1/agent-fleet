## 背景

egress の forward proxy（`control-plane egress-proxy`、docs/log/20）は記録もブロックもできるが、届いた
通信についてだけだ。届くかどうかは Workspace の環境にある `http_proxy` / `https_proxy` 次第で、それを無視する
プロセスは見えないまま外に出る。本書の要件は次のとおり。**Workspace から外への接続はすべて記録されること。
記録されない素通しは、導入組織にとって許容できない。** 現状：

- どのテンプレートもプロキシを起動しない（`deploy/compose`、`deploy/aws`、`deploy/kubernetes`、`deploy/gcp`）。
- 通信をプロキシに通す強制がない。docker のユーザー別ネットワークは internal ではなく、ECS の Workspace 用
  セキュリティグループには egress ルールがなく、Kubernetes の `egress-internet` ポリシーは RFC 1918 以外の
  全アドレスを通す。
- 変数がすべてのターゲットに届くわけではない。`main.go` は `mgr.extraEnv` に入れ、docker・native・Kubernetes
  はそれを読む（`runtime.go`、`runtime_native.go`、`runtime_kubernetes.go`）。ところが `ecsFactory.New`
  （`runtime_ecs.go`）は起動ごとの env しか使わないので、ECS と ecs-ec2 の Workspace にはプロキシ変数が
  まったく入らない。
- 観測が失われうる。`egressBatcher.flush` は POST の前にバッチを空にし、通信エラーや 2xx 以外の応答では
  そのまま捨てる（`egress_proxy.go`）。
- 観測が持つのはホストと件数だけで、どの Workspace の接続かは分からない。

ターゲットを見て分かった制約：

- AWS のスタックは VPC と、固定した Elastic IP を持つ NAT ゲートウェイを自前で作る。導入組織は安定した
  出口アドレスを許可リストに入れられる（`00-network.yaml`）。ECS のタスクは `awsvpc` で、タスクごとに
  ENI とプライベート IP を持つ。
- GKE のスタックは、予約したアドレスを持つ Cloud NAT を自前で作る（`network.tf`）。
- compose では CP がホストネットワークにいて、各 Workspace へ公開した `127.0.0.1` のポート経由で届く。
  docker の `--internal` ネットワークは公開ポートを壊す。マスカレードを切ったブリッジは fence にならない。
  止まるのは NAT であってルーティングではなく、ホスト、メタデータのアドレス、docker の組み込み DNS に
  届いたままになる。
- Cloud NAT と AWS の NAT ゲートウェイは転送して数えるだけで、ホスト名で判定も記録もしない。

## 決定

### 1. fence はネットワークに置く。log-only でも常にオン

Workspace の通信は 1 つの egress ゲートウェイを通って出る。ほかに外へ出る経路はない。プロキシ変数を
すべて無視するプロセスでも、ゲートウェイを通るか、通れずに止まる。そのための Workspace 側の設定は要らず、
`http_proxy` 系の変数は役目を外れる。

ただし変数は残す。ゲートウェイは明示プロキシとしても同じ変数を受ける（決定 2）。プロキシに対応した
クライアントは `CONNECT` でホスト名を自分から名乗るので、Encrypted Client Hello が SNI の読み取りに
残す穴をふさげる。#1056（認証情報の注入）が置かれるのも、明示プロキシ側になる。

### 2. ゲートウェイは自前のプロキシではなく既製のソフトウェア

第一候補は intercept モードの **Squid**。443 を `https_port … intercept ssl-bump` に redirect し、
step 1 の `ssl_bump peek` で TLS Client Hello の SNI を読む。許可された名前は `splice`（復号せず
トンネル）、拒否された名前は `terminate`。80 番は、`Host` ヘッダを見る intercept の `http_port` を通す。
TLS は復号しないので、証明書をピン留めするツールや `SSL_CERT_FILE` に影響しない。

同じ Squid が明示的な forward proxy（`http_port`。`AF_EGRESS_PROXY_ADDR` が指すアドレス）としても
待ち受けるので、プロキシに対応した通信も無視する通信も、1 つの許可リスト、1 つの判定、1 つのログを
共有する。1 つの Squid が 2 種類のリスナーを意図どおり同時に動かせるかは**試していない**。

同じホストの `nftables` が、Squid の見えない部分を受け持つ。それ以外の TCP と UDP は既定でログに取って
落とす。QUIC（UDP 443）は落として TCP にフォールバックさせ、その試行はログに残す。

### 3. log-only と enforce の意味

- **log-only：** Squid は全部の名前を splice し、本来下したはずの判定をつけてログに取る。記録できない
  もの（非 HTTP や、名前のないアドレスへの直接接続）は fence が止める。止めたこともログに残す。
- **enforce：** 許可リスト外の名前は terminate する。

いまのドキュメントは log-only を「ブロックしない」と書いている。これは直す（「結果」を参照）。

### 4. ポリシーと記録は CP が持ち、ゲートウェイ上の小さなエージェントがつなぐ

許可リスト、提案と承認の流れ、Admin の Egress タブは今のまま。ゲートウェイ上の小さなエージェントが
(a) 有効なポリシーを Squid の許可ファイルにして reload し、(b) ログを**ファイルのオフセットから**既存の
ingest エンドポイントに送る。POST が失敗しても捨てずに再送できる。イベントには送信元アドレスを足し、
CP が帰属できるようにする（「未決事項」を参照）。全ターゲットがゲートウェイを使うようになったら、
`control-plane egress-proxy` は廃止する。

### 5. ターゲットごと

| ターゲット | ゲートウェイ | fence |
|---|---|---|
| ecs、ecs-ec2 | 台数 1 の Auto Scaling グループの EC2。NAT ゲートウェイの代わりにプライベートルートテーブルの既定ルートになる。固定した Elastic IP を引き継ぐ | Workspace のセキュリティグループは、ゲートウェイ・CP・AWS のエンドポイントだけを通す |
| GKE | **未決**（下記） | **未決** |
| compose（docker） | **未決**（下記） | **未決** |

## 却下

- **プロキシ変数だけが経路になる現状**：迂回できるので、記録されない通信が残る。
- **docker の internal ネットワークで CP がコンテナ IP から届く案**、**マスカレードを切る案**、
  **ホストの iptables だけの案**：1 つ目は CP の接続方式を大きく変える上に、結局ゲートウェイが要る。
  2 つ目は fence にならない。3 つ目はホストの root が要り、INPUT・DNS・IPv6 を覆えない。ネットワークが
  経路として通すゲートウェイが、この 3 つの代わりになる。
- **クラウドの NAT ゲートウェイだけ**（AWS、GCP）：数えて転送するだけで、ホスト名では判定も記録もできない。
- **AWS Network Firewall**：SNI で判定してログも出せるマネージドの代替。土台にしない理由は、AWS 専用で、
  エンドポイント時間と GB 単位で課金され、GKE と compose には何も与えないから。AWS のゲートウェイの
  差し替え候補としては残る。
- **VyOS のようなルーター機器**：全ターゲットで 1 つの設計にできるが、名前による規則は DNS で引いた
  アドレスに落ちる。ルーターを同梱して運用する負担は、Squid 1 台より大きい。
- **自前の透過プロキシ**（Client Hello を自分で読む）：Squid がすでにやっている仕事。
- **`control-plane egress-proxy` と Squid を恒久的に並べて動かす**：1 つの許可リストに対して、食い違い
  うる判定経路が 2 本になる。自前のプロキシは、ターゲットがゲートウェイに移るまでだけ残す（ゲートウェイが
  未決の docker と GKE は、それまで使い続ける）。
- **エージェントごとの OS サンドボックス**（#1067）：Workspace コンテナの中では使えない。

## 結果

- **ゲートウェイは全接続の経路上に載る。** 1 台は単一障害点になる。Auto Scaling グループが置き換え、
  ルートと Elastic IP が置き換え後に追従しなければならない。スループットはインスタンスタイプで頭打ちになる。
  マネージドの NAT ゲートウェイにはなかった運用が増える。
- **識別情報を持たない Workspace の通信は、アドレスでしか帰属できない。** 「未決事項」を参照。
- **名前はクライアントの申告どおり。** SNI はクライアントの主張で、悪意あるプロセスは許可された名前を
  名乗って別のアドレスに接続できる（ドメインフロンティング）。記録には申告された名前と宛先アドレスが
  残る。Squid のホスト検証で狭められるかもしれないが、ここでは評価していない。
- **SNI がなければ名前もない。** Encrypted Client Hello と素のアドレスへの接続は、使える名前を持たない。
  アドレスで記録し、enforce では許可しない。
- **非 HTTP は通らなくなる。** SSH 経由の git と、Workspace が選んだリゾルバへの直接 DNS。どちらも
  フォローアップ。
- **実装時に直すドキュメント：** `guide/operate/04-secure.md`（「Operating egress control」。log-only は
  もう「何もブロックしない」ではなく、「まだ作っていない」の注記も直す）、`docs/build/07-security.md` §7.8、
  `docs/build/09-deploy.md`（変数を受け取るのは docker と native だけと書いているが、Kubernetes も受け取る）、
  `docs/build/03-control-plane.md`、およびそれぞれの日本語版。
- **ゲートウェイを出す前に、SSM ログインを実際のアカウントで確かめる。** 固定した session-manager
  プラグインは `HTTPS_PROXY` を尊重する（読んだだけで、動かしてはいない）。ゲートウェイなら変数は
  まったく要らないが、SSO の開始 URL のホスト（通常は `awsapps.com` 配下）は `defaultEgressAllowlist` に
  ない。

## 未決事項

1. **GKE。** Pod の通信はノードから出る。Workspace のノードプールを転送用 VM 経由にするには、ネットワーク
   タグで絞ったルートが要り、CP 自身の Pod が巻き込まれてはならない。GKE 自前の FQDN 対応ネットワーク
   ポリシーや Cloud NGFW が代替になる。評価していない。
2. **compose。** CP がエージェントに届く方式を変えずに、ユーザー別ネットワークが経由するゲートウェイの
   コンテナか VM。試せるホストが要る。
3. **帰属。** Squid は送信元アドレスをログに取る。CP が Workspace を特定するには、起動時に各 Workspace の
   アドレスを記録しなければならない。ecs-ec2 ではタスクの ENI アドレスが取れるが、ほかは設計していない。
4. **非 HTTP：** 名前で指定したホストへの SSH git を通すかどうか。直接 DNS をどう記録するか
   （AWS では Route 53 Resolver のクエリログ）。
5. **pause と resume。** `deploy/aws/ecs/pause.sh` は時間課金を避けるために NAT ゲートウェイを削除する
   （#2386）。ゲートウェイのインスタンスにも同じ扱いが要り、resume は Workspace が起動する前にルートと
   Elastic IP を戻さなければならない。
6. **既存のデプロイ：** 既定ルートを NAT ゲートウェイからゲートウェイへ移すのは、稼働中の VPC への変更で、
   ロールバックの手順が要る。
7. **導入組織が許可リストに入れる出口アドレス。** 今は NAT ゲートウェイに付いた、保持された 1 つの
   Elastic IP（`NatEip`、`DeletionPolicy: Retain`）。`NatEipAllocationId` は新規 stand-up 専用で、稼働中の
   スタックに渡すと CloudFormation が NAT ゲートウェイを置換する（デプロイ済みのスタックに
   `--no-execute-changeset` で測った）。ゲートウェイのインスタンスは同じアドレスを引き継ぐ必要があるが、
   NAT ゲートウェイが持っている間はインスタンスに付けられない。だから切り替えには、計画しない限り
   egress の空白が生じる（切り替え用の 2 つ目のアドレスか、短いメンテナンス時間帯）。
8. **ゲートウェイ 1 台は 1 つの Availability Zone。** NAT ゲートウェイはすでに単一 AZ で、台数 1 の
   Auto Scaling グループのインスタンスもそれを引き継ぐ。ゾーンごとにゲートウェイを置くと、導入組織が
   許可リストに入れるアドレスが 2 つになる。アドレスを配る前に決めておく必要がある。

### 帰属：イベントは生のアドレスを持ち、CP は時間範囲つきのアドレス表を持つ

**ゲートウェイに見えるもの。** ECS と ecs-ec2 では各タスクが自分の ENI を持ち（`awsvpc`）、同じ VPC の
ゲートウェイにはそのアドレスがそのまま見える。GKE では既定ではそうならない。Google の IP masquerade
agent のページによれば、非 masquerade リスト（RFC 1918、100.64.0.0/10、予約済みのテスト用・文書用
ブロック）の外への通信では「GKE changes source Pod IP addresses to source node IP addresses」。
つまり 1 台のノード上の Workspace は、すべてノードのアドレスとしてゲートウェイに届く。

**この経路だけ SNAT を止めることはできない。** masquerade は宛先だけで決まり、`ip-masq-agent` の
ConfigMap（`nonMasqueradeCIDRs`）はクラスタ全体に効く（ノードプール単位の指定はページに無く、DaemonSet
にもノードセレクタが無い）。ただ、その必要もない。`nonMasqueradeCIDRs: [0.0.0.0/0]` にすればすべての
宛先でポッドの送信元アドレスが保たれる。そしてこのスタックの Cloud NAT はポッドの範囲も含めた全範囲を
すでに変換している（`network.tf` の `source_subnetwork_ip_ranges_to_nat =
"ALL_SUBNETWORKS_ALL_IP_RANGES"`）。だから system プールのポッドは同じ予約アドレスから出たままで、
ゲートウェイには Workspace のポッドのアドレスが見える。`--disable-default-snat` でも同じことになるが、
効くのは `ip-masq-agent` の DaemonSet が無いクラスタだけで、しかもノードの入れ替え後。使う手段は
ConfigMap にする。

**fence を SNAT に依存させない。** Workspace の通信をゲートウェイへ向けるルートは、ポッドの送信元範囲
ではなく、Workspace ノードプールのネットワークタグで絞る。ConfigMap がいつか失われても、通信がノードに
帰属するようになるだけで、記録は残る。ポッドの範囲で照合するルートだと、ノードのアドレスになったパケット
が既定ルートで外へ出てしまい、記録されない。

**記録の形。** Squid のイベントに送信元アドレスと時刻を足す。CP は届いたものをそのまま保存し、自分が
持つ表で帰属させる。

| 列 | 意味 |
|---|---|
| Workspace（membership） | そのアドレスが誰のものだったか |
| アドレス | ゲートウェイから見た IPv4 |
| from / until | そのアドレスがその Workspace のものだった期間。持っている間は `until` が空 |
| ref | 問い合わせた対象：タスク ARN、ポッド UID、コンテナ ID |

帰属はアドレスと時刻での結合で決め、アドレスだけでは引かない。アドレスは再利用されるから（止まった
タスクの ENI アドレスも、消えたポッドの IP も、すぐに別のものへ払い出されうる）。結合の結果はイベントと
一緒に保存するが、生のアドレスは捨てない。どの行にも合わないイベントは**帰属不明**、2 行に合うものは
**曖昧**として両方の候補つきで表示し、どちらも捨てないし推測もしない。スタック自身が持つアドレス
（ノード、スロットのインスタンス、CP）は「帰属不明」ではなく「基盤」という別の区分にする。

**各ランタイムが表を埋める場所**（`control-plane/internal/runtime/`）：

- **ECS と ecs-ec2。** 今はどちらもタスクを describe していない。`State()` が読むのはサービスだけ
  （`describeService`）で、`Start` はサービスが desired count 1 になった時点、タスクが走る前に返る。
  したがって `Start` で記録するだけでは足りない。ECS のサービススケジューラは失敗したタスクを自分で
  入れ替え、新しい ENI と新しいアドレスになるが、CP はそのタスクのために `Start` を呼ばない。表は
  サービスのタスクに対する `DescribeTasks` から埋める：ENI アタッチメントの `privateIPv4Address` を、
  `createdAt` から `stoppedAt` まで。タスクの ENI は `createdAt` の後に作られ、`STOPPED` までに消える
  （文書にあるタスクのライフサイクル。測ってはいない）ので、1 つのアドレスについて 2 つのタスクの期間は
  重ならない。調整ループとして回し、表に無いアドレスのイベントが届いたときはその場でも問い合わせる。
  止まったタスクを describe できるのは一定時間だけなので、ループはその時間より十分短い間隔で回す。
  ecs-ec2 のスロットのインスタンス自身のアドレスは基盤。プラットフォームの通信もタスクの ENI から出る
  （ECR からのイメージ取得、ログ、SSM のシークレット。このスタックには S3 ゲートウェイエンドポイントしか
  無い、`00-network.yaml`）。そのためゲートウェイはそれらのホストを許可する必要があり、それらは
  Workspace の記録にも現れる。
- **Kubernetes と GKE。** `workspacePods` はすでに StatefulSet のポッドをラベルで一覧している。表に
  要るのは `metadata.uid`・`status.podIP`・`status.startTime` で、`kPodStatus` はまだこれらを読んで
  いない。`from` はポッドの開始時刻、`until` は CP がポッドの消滅を確認した時刻。StatefulSet のポッドは
  再起動しても名前は同じだが、UID とアドレスは変わるので、行は UID で引く。ポーリングでは削除に気づく
  のが遅れるので、Workspace のポッドを watch する方を選ぶ。それでも重なりが紛れ込めば、別の Workspace に
  誤って帰属させるのではなく「曖昧」として出る。
- **docker。** ユーザー別ネットワーク（`ensureNetwork`。`Start` で作り `Stop` で消す）は 1 人の
  ユーザーのもの。行には、そのネットワークのサブネットとその上のコンテナのアドレスを、`Start`
  （`docker run` の後、`docker network inspect` / `docker inspect` で）から `Stop` まで記録する。
  コンテナのアドレスが変わっても、サブネットで帰属できる。docker のゲートウェイはまだ未決事項 2 なので、
  これが意味を持つのは、そのネットワーク上のアドレスが見えるゲートウェイができてから。
- **native**：本書にはゲートウェイが無い。表の対象外。

ゲートウェイ上のエージェントは単純なままにする。アドレスと時刻を送るだけで、結合は CP が行う。
Workspace を知っているのは CP だけだから。

### GKE のゲートウェイ：同じ Squid を転送 VM で動かし、Workspace プールのタグでルートを向ける

要件（すべての接続を、名前があれば名前つきで、log-only でも記録する）に照らして 4 案を比べた。

| 案 | 判定の基準 | 記録するもの | 要件に対して |
|---|---|---|---|
| **FQDN ネットワークポリシー** + **NetworkPolicy ログ** | ポッドが受け取った DNS の応答。生 IP には一致しない | 5 タプル（許可・拒否）。ホスト名は無い | 満たさない。log-only ではすべてを許可するしかなく、IP の記録しか残らない。allow-union なので、既存の `egress-internet`（非プライベートの全アドレス）がすでにこれを上書きする |
| **Cloud NGFW** の FQDN オブジェクト + ファイアウォールルールのログ | 定期的に解決したアドレス。ワイルドカード不可、1 名前あたり最大 32 アドレス、結果はリージョンで変わる（Google 自身が `googleapis.com` を該当例に挙げている） | 5 タプル | 同じ理由で満たさない。名前がアドレスに落ちる。NGFW Enterprise（URL フィルタリング、IPS）はゾーンごとのファイアウォールエンドポイントが要り、評価していない |
| **Secure Web Proxy の next hop モード** | TLS インスペクション無しで、`sessionMatcher` の SNI `host()` | Cloud Logging のトランザクションログ（送信元 IP つき） | HTTP(S) と TCP については満たす。それ以外の通信は「dropped without notification」で、落としたことが記録されない。VPC・リージョンごとに 1 つ。どの egress アドレスを使うかは見つからなかった |
| **転送 VM 上の Squid**（決定 2） | SNI の peek と splice、80 番は `Host` | Squid のログ。それ以外は nftables | 満たす。ソフトウェア・エージェント・ログ形式が AWS と同じ |

**決定 5 の GKE 行として選ぶもの：転送 VM 上の Squid**（AWS と同じゲートウェイ）。

- Workspace ノードプールにネットワークタグを付ける。そのタグに向けた `0.0.0.0/0` の静的ルートを、
  既定ルートの 1000 より小さい優先度で作り、ネクストホップをゲートウェイ VM にする。VM には IP 転送が
  要り、VM 自身にはタグを付けない。
- サブネットルートとピアリングのルートはカスタム静的ルートより優先されるので、プライベートの
  コントロールプレーンエンドポイントとノードのサブネットには影響しない。メタデータサーバはルーティング
  されない。CP が動く system プールはタグが無く、既定ルートのまま。
- ゲートウェイ VM もタグが無いので既定ルートで出て、Cloud NAT の予約アドレスになる。導入組織が許可
  リストに入れる egress アドレスは変わらない。
- Workspace ノード自身の通信（Private Google Access 経由のイメージ取得、ログ・モニタリングの
  エージェント）もこのルートを通る。Google API の範囲に向けたより具体的なルートは足さない。足すと
  Workspace も任意の Google API に記録なしで届くから。その通信は基盤として記録し、ノードが必要とする
  Google のホストをゲートウェイで許可する。どのホストかは #2658 で測る。
- 明示プロキシのリスナーにはゲートウェイ VM のプライベートアドレスで届く。`egress-internet`
  NetworkPolicy はその `/32` とポートを通す必要がある。ノードではない `/32` なので、ADR 0106 の
  remote-node セレクタの問題には当たらない。
- 帰属の節の `ip-masq-agent`（`nonMasqueradeCIDRs: [0.0.0.0/0]`）を加える。

**next hop モードの Secure Web Proxy は、この VM の差し替え候補として残す**（AWS ゲートウェイに
対する AWS Network Firewall と同じ扱い）。復号せずに SNI で判定し、クライアントのアドレスを記録し、
マネージドである。それでも土台にしない理由は 3 つ：落とした通信が記録されない、許可リストを Google API
経由で SWP のポリシールールに変換する必要がある、AWS と compose には何ももたらさない。
**NetworkPolicy のログは 2 本目の線として役に立つ。** 拒否だけをログに取れば、NetworkPolicy が止めた
試み（RFC 1918、メタデータの範囲）を安く記録できる。ただし egress の記録そのものではない。

GKE でまだ決まっていないのは HA の形（台数 1 のマネージドインスタンスグループで、ルートがインスタンスに
追従する形か、内部パススルーロードバランサをネクストホップにする形か）とスループットの見積もりで、
どちらも #2658 で扱う。

### AWS：S3 ゲートウェイエンドポイントは、ゲートウェイでは塞がらない素通し

`S3Endpoint`（`00-network.yaml`）は S3 のプレフィックスリストをプライベートのルートテーブルから
外へ逃がし、エンドポイントポリシーを持たない（つまりフルアクセス）。このため Workspace は、今は NAT
ゲートウェイを、決定 5 の後はその代わりの egress ゲートウェイを通らずに、リージョン内の任意の S3 バケット
へ届く。このエンドポイントがあるのは、ECR のレイヤーのバイトを NAT ゲートウェイに通さないため。対処
（スタックが必要とするバケットに絞ったエンドポイントポリシー、または Workspace のサブネットにはルートを
置かない）は #2657。ポリシーを付けても、エンドポイント経由のアクセスは Workspace ごとには帰属しない。

### AWS：S3 ゲートウェイエンドポイントは当面置かない（2026-10-25、メンテナと決定）

`S3Endpoint` を `00-network.yaml` から外した（#2657）。ポリシー（ECR のレイヤーバケット、AL2023 の

### 未決事項 4：SSH の git と DNS（2026-10-24、メンテナと決定）

  Route 53 Resolver のクエリログと Cloud DNS のログは本記録の対象外。

## 追記（2026-10-24）— 決定 4：ゲートウェイのエージェントを作った

決定 4 のエージェントは `control-plane egress-agent` として存在する（#2683、コードは
`control-plane/internal/egressagent`）。Squid 本体・nftables・デプロイテンプレートは含まない。
**本物の Squid では動かしていない**。パーサとローテーションの扱いは、行とファイルのフィクスチャで
テストした。

- **形。** CP バイナリのサブコマンド（`egress-proxy` や `efs-home-op` と同じ）なので、ゲートウェイには
  同じバイナリを置く。パッケージは CP の `main` から何も import しないので、ゲートウェイでサイズが
  問題になれば単独のバイナリにできる。
- **policy。** `GET /internal/egress/policy` をポーリングし、2 つのファイルを一時ファイルと rename で
  書く。許可ファイル（dstdomain のエントリ。ほかのエントリに覆われるものを Squid は警告し、既定の
  リストにはその組があるので、最小の集合に絞って並べる）と、log-only か enforce の `ssl_bump` と
  `http_access` の行を入れたモードの include。Squid の再読込はファイルのバイトが変わったときと、起動時に 1 回（前の実行がファイルを書いたまま
  再読込に成功していないことがある）。この再読込はディスク上のファイルで行い、CP を待たない。
  CP に届かない・200 以外・許可リストが空、のときはファイルをそのままにする。
- **ログ。** Squid の `logformat`（`af1`、パッケージに記載）はエージェントが決める。接続が始まった時刻
  （`%tS`。行を書いた時刻ではない。トンネルは閉じたときに記録され、そのときには Workspace がもう
  アドレスを手放していることがある）、送信元とサーバのアドレス、Squid のステータスと bump モード、
  SNI とリクエストのドメイン（悪意ある SNI がフィールドを足せないよう URL エンコード）。1 行が 1 イベントで、
  id はファイルの世代と行のバイトオフセット。世代は、エージェントがファイルを初めて見たときに拡張属性
  `user.af-egress.gen` へ書くランダムな id。rename と再起動をまたいで残り、新しく作られたファイルには無い。
  ファイル自体から取れるものはどれも一意ではない。新しいファイルは削除されたファイルの inode を再利用しうるし、
  作成時刻はカーネル時計の数ミリ秒の分解能しかない（記録されないこともある）し、2 つのファイルが同じ行で
  始まることもある。衝突すると、エージェントは誤った offset から再開し、CP は本物のイベントを重複として捨てる。
  そのためエージェントには Squid のログファイルへの書き込み権限と user xattr の使えるファイルシステムが要り、
  無ければ起動を拒否する。世代はイベントに載せる前に fsync する。ホスト障害で行だけがディスクに残り、
  世代が失われて別の値を振り直す、ということが起きないように。
  オフセットは 2xx の後にだけ確定する。
  後半が壊れた行も、時刻と送信元だけで名前なしとして送る。ローテーションは Squid 自身のもの
  （`logfile_rotate` が 1 以上）に限り、`copytruncate` には対応しない。
- **判定。** `allowed` は名前に対する policy の判定で、Squid が拒否・terminate した接続は false。
  log-only では、その接続が受けたはずの判定になる。送る時点の policy で計算するので、policy が変わる
  直前に書かれた行は新しい判定を持ちうる。
- **照合器は 1 つ。** 許可リストの照合器は `control-plane/internal/egressallow` に移し、CP と
  エージェントが共有する。

## 追記（2026-10-25）— 生イベントの保持期間（#2675）

上の決定は変わらない。`egress_event` と `workspace_address` は一度も削除されず、前者は 100
events/s で 1 日あたり約 860 万行になる。maintainer が決めたこと:

- **生イベントは 30 日保持する。** `AF_EGRESS_EVENT_RETENTION_DAYS` で設定する（`0` で無期限）。
  `egress_daily` には触れない。
- **purger が上限付きバッチで削除する**（1 文あたり 5000 行、古い順、バッチ間に短い待ち）。SQLite と
  Postgres の両方で。アドレスレコーダーと同じく、CP lease `egress-event-purge` のもと CP 1 台だけが動く。
- **`workspace_address` は、帰属させるイベントより長く残す。** 閉じた期間は終了時刻が purge の
  基準時刻より古いときだけ削除し、イベントを先に消す。開いた期間は削除しない。
- **再送の上限。** `id` による重複排除は行が残っている間しか効かず、gateway agent は確定済みの
  オフセットから再送するので、長い停止の後には保持期間より古い行を再送しうる。そこで ingest は、
  `id` を持ち `at` が「現在 − 保持期間」より古い、または**purge の下限**より古いイベントを、保存も `egress_daily` への加算もしない。下限は
  DB に持つ単調増加の基準時刻（`cp_counter` の `egress-event-floor`）で、purge は削除の前にこれを
  引き上げて確定し、`RecordEgressEvent` は挿入と同じトランザクションで読む（Postgres では `FOR SHARE`。
  処理中の ingest を待ってから引き上がる）。そのため、消したイベントはどの CP でも、時計や保持期間の
  設定によらず拒否され、後から保持期間を延ばしても `0` にしても下限は下がらない。
  拒否した件数はログに出し、応答は 2xx のままにして、gateway が永久に再送しないようにする。`id` を持たない
  イベント（自前 proxy のもの）は元々重複排除されておらず、影響を受けない。
  **帰結:** 起きてから保持期間より後に届いたイベントは、生テーブルからも集計からも失われる。
  purge 済みの id の表を持たないことの代価である。
- **この変更ではアーカイブしない。** purge の前にオブジェクトストレージへ退避する件は #2699。

## 追記（2026-10-25）— アドレス記録は ECS をクラスタ単位で一度だけ読む

記録役は ECS に対してワークスペースごとに自分のサービスを問い合わせていた（`ListTasks` の
RUNNING と STOPPED、続けて `DescribeTasks`）。稼働中 1 ワークスペースにつき 1 巡あたり約 3
リクエストで、アカウント共有の ECS 読み取りスロットルを消費していた。`runtime.AddressSnapshotter`
を実装するファクトリは、1 巡全体をクラスタごとの 1 回の読み取りで賄う。希望状態ごとの
`ListTasks`（ページング）、100 件ずつの `DescribeTasks`、タスクの `service:<name>` グループ
による振り分け。実装しないファクトリと他のランタイムは従来どおりワークスペース単位で読む。

区間のルールは変わらない。クラスタの一覧に出てこない open の ref は従来どおり ARN で
describe し、MISSING は未解決のまま。ページまたはバッチが 1 つでも失敗したら、その巡では
そのクラスタの全ワークスペースの読み取りを失敗とし、一部だけの一覧で区間を閉じない。
Follow-ups: #2674（実アカウントでの確認）。

## 追記（2026-10-25）— Workspace 用サブネットと、プライベートのルートテーブルへ戻した S3 エンドポイント（#2716）

上の決定も、同日の「ポリシーで絞ったエンドポイントに Workspace の S3 を決めさせない」という決定も変わらない。変わるのは Workspace の置き場所である。

- **Workspace のタスク ENI は専用のサブネットに置く。** AZ ごとに 1 つ、外への経路が NAT ゲートウェイだけの Workspace 用ルートテーブルに載せる。決定 5 のゲートウェイが NAT に代わって既定経路になるのは*この*ルートテーブルだけで、GKE の設計が Workspace のノードプールに経路を絞るのと同じ形になる。CP、スロットのインスタンス、エンジンはゲートウェイを通らない。CP には `AF_ECS_WORKSPACE_SUBNETS`（30-ingress の `WorkspaceSubnets`、00-network の出力から）として渡す。
- **S3 ゲートウェイエンドポイントはプライベートのルートテーブルにだけ戻す。** ポリシーはコミット `6829e6e` でレビュー済みのもの（ECR のレイヤー、AL2023 のリポジトリ、モデル用バケット）に、スロットとエンジンのインスタンスが `AWS-UpdateSSMAgent` で使う SSM Agent 更新用のバケット（`amazon-ssm-<region>`、`aws-ssm-<region>`）と、ecs-init がキャッシュの無いときに読む ECS エージェント配布用のバケット（`amazon-ecs-agent`、`amazon-ecs-agent-<region>`）を加えたもの。`S3EndpointEnabled` で切り替え、稼働中のスタックではすべての Workspace を Workspace 用サブネットへ起動し直すまで `false` のままにする。`false` に戻すのがロールバックでもある。利用者が動かすものはこのルートテーブルに載らないので、拒否されても壊れる Workspace はない。ecs-ec2 ではイメージの取得を ECS エージェントがスロットのインスタンスの ENI で行うので、コールドプルはエンドポイントを通る。
- **Fargate の Workspace も移す。** 取得はタスク ENI を通るので得はないが、プライベートのルートテーブルに残すと自分の S3 がエンドポイントのポリシーに当たる。Workspace が全部 1 つのルートテーブルに載ることがゲートウェイの前提でもある。
- **Workspace 用サブネットの無い AZ は拒否する。** プライベートのサブネットで代用せず、新しいホームも置かない。

未決事項 5 は実質変わらない。`pause.sh` は `NatEnabled` で両方の既定経路を落とす。配備済みのアカウントでは未検証（エンドポイント経由のコールドプル、NAT 経由の Workspace の S3、サブネットをまたいだ CP からエージェントへの到達）。Follow-ups: #2716。

## 追記（2026-10-25）— purge 前の生イベントの任意アーカイブ (#2699)

上の決定は変わらない。保持期間より長く接続ごとの記録を残す必要がある配備は、
`AF_EGRESS_ARCHIVE_URL`（`s3://bucket/prefix` または `file:///dir`。空が既定で無効）を設定できる。
決めたこと:

- **UTC の日ごとに 1 つの gzip JSON Lines オブジェクト**。`egress/yyyy=/mm=/dd=` で分割し、その日の
  イベントと、その日に区間が触れる `workspace_address` の行を入れる。補遺（後述）と合わせて読み、帰属できる。
  先頭に `header` 行、末尾に `manifest` 行（件数、id と時刻の範囲、スキーマ版）を置くので、途中まで
  のオブジェクトや誤ったオブジェクトは検出できる。形式と運用は `docs/build/03-control-plane.ja.md` §3.8。
- **アーカイブしていないものは消さない。** アーカイブするのはカットオフより前の丸 1 日（UTC）だけなので、
  アーカイブ有効時のカットオフは「現在 − 保持期間」以前で最も新しい UTC 0 時になる。下限はアーカイブを
  読む前にそこまで引き上げるので、アーカイブ済みの日に遅れて届いたイベントは、未保存のまま消える
  のではなく拒否される。古い日から順に保存し、最初に失敗した（または確認できない）日の先頭で削除可能
  範囲が止まり、次の実行が再試行する。保存先は 3 メソッドのインターフェース（`Exists`・`Get`・原子的な
  `Put`）で、S3 とローカルディレクトリの実装がある。オブジェクトがある日は検証（header・件数・gzip チェックサム）したうえで書き直さないので、書き込み後
  のクラッシュからの再実行は安全で、途中で打ち切られた削除が、完全な 1 日を残りで置き換えることもない。
- **address の行は版ごとにアーカイブする。** 下限は `workspace_address` への書き込みを止めないので、削除する閉じた行は直前に補遺オブジェクトとして保存し、その行のその版だけを削除する。読み戻しは、日のオブジェクトと補遺の address 行を (ref, address, from) で 1 行にまとめ（`until` は 0 を無限大として 0 以外の最小値。store が終了時刻を短くする方向にしか動かさないのと同じ）、そのうえで帰属させる。
- **読み戻しはオフライン**（ダウンロードして source と時刻で帰属）。アーカイブしたイベントを ingest
  し直さない。上の ingest の下限は変わらないので、アーカイブと `egress_daily` が二重に数えることはない。

## 追記（2026-10-25）— AWS の第 1 段階：`EgressRoute` とゲートウェイ（#2717）

ecs と ecs-ec2 の決定 5 は、置き換えではなく選択として作った。`00-network` の `EgressRoute`（既定の `nat-gateway` か `gateway`）が決めるのは **Workspace** 用ルートテーブル（#2716）の既定経路だけである。CP、スロットのインスタンス、エンジンは NAT ゲートウェイのままなので、NAT ゲートウェイはどちらのモードでも残る。実アカウントでは動かしていない。

- **経路は固定のインターフェースで入れ替えに追従する。** スタックが `GatewayEni`（送信元／送信先チェック無効）とその Elastic IP を持ち、Workspace 用ルートテーブルはそれを指す。台数 1 の Auto Scaling グループの各インスタンスは起動時にそれを 2 枚目のインターフェースとして付け、すべての通信をそこから出す。経路、明示プロキシのアドレス、出口のアドレスは動かず、インスタンスのロールには経路やアドレスの権限が要らず、そのインターフェースへの `AttachNetworkInterface` だけで済む。代償は AZ が 1 つ（インターフェースの AZ）になることと、入れ替えの起動中は経路がブラックホールになること。却下したのは、起動時に経路を書き換えアドレスを付け替えるインスタンス（権限が増え、経路をスタックとインスタンスの両方が持つ）と、インターフェースを 1 枚目に持つ単独の EC2 インスタンス（固定インターフェースのまま CloudFormation が入れ替えられない）。
- **Squid** は 1 台で明示プロキシと 2 つの intercept（80、443）を受け、`egressagent/doc.go` の行を使う。明示プロキシのポートも `ssl-bump` にした。`ModeEnforce` は CONNECT を `ssl_bump` の SNI で判定するので、`ssl-bump` の無いポートの CONNECT は `http_access` を素通りする。転送は一切しない（`ip_forward=0`）。セキュリティグループは Workspace 用サブネットからの 80/443/3128 だけを通すので、この段階ではそれ以外のプロトコルは記録されずに落ちる。モードにかかわらず、Squid はループバック、リンクローカル（ゲートウェイ自身のメタデータサービス。そうしないと Workspace が明示プロキシ経由でゲートウェイのロールを読める）、VPC、80/443 以外のポートを拒否し、nftables は Squid 自身の 169.254.0.0/16 への接続を落とす。エージェントが最初のポリシーを取るまで Squid はすべてを拒否する。入れ替えたインスタンスや CP に届かない状態は、log-only ではなく閉じた側に倒れる。
- **エージェント** は CP のイメージから取り出した CP のバイナリで、Squid のユーザーで動く。設定（イメージ、公開 URL）は 30-ingress が書く SSM パラメータから読み、10 分ごとに見直すので、リリースはインスタンスを入れ替えずに届く。
- **`AF_EGRESS_TOKEN`** は `00-network` で Secrets Manager が生成し、渡るのは ARN だけ（30-ingress の `Secrets`）。CP とエージェントには届き、**Workspace には届かない**。egress イベントを書ける資格情報だからである。Workspace に届くのは `AF_EGRESS_PROXY_ADDR` によるプロキシ変数で、`169.254.170.2`、`169.254.169.254`、CP の内部ホストは `NO_PROXY` に入る（#2604 の受け入れ。実行はこれから）。
- 未決事項 5 と 7 はゲートウェイについて残る。`pause.sh` は `EgressRoute=gateway` を拒み、`standup.sh` は警告する（#2729）。Workspace は NAT ゲートウェイではなくゲートウェイ自身の Elastic IP から出る。1 つのアドレスを両者の間で移すのは #2728。

Follow-ups: #2728, #2729, #2687（実 Squid。手順は README にある）。

## 追記（2026-10-25）— GCS のアーカイブ保存先 (#2720)

`AF_EGRESS_ARCHIVE_URL` は `gs://bucket/prefix` も取る。アーカイブの保存先インターフェース（#2699）の 3 つ目の実装で、公式の `cloud.google.com/go/storage` クライアントを使う。新しく増えるクライアントライブラリはこれだけ（`google.golang.org/api` も直接 import として付いてくる）。配置と、検証して書き直さない規則は変わらない。

- **認証は Application Default Credentials のみ**（GKE では Workload Identity）。キーファイルの設定はない。ロールはバケットへの `roles/storage.objectCreator` と `roles/storage.objectViewer`。一覧・削除・上書きはしない。
- **キーは置き換えない。** アップロードに `ifGenerationMatch=0` を付けるので、既にあるキーへの 2 回目の Put は 412 で失敗し、そこにあるオブジェクトはそのまま残る。412 は、保存済みの長さと CRC32C が送ったものと等しくても常にエラーにする。応答を失った後の再試行はそう見え、CRC32C の衝突もそう見えるうえ、nil を返すとアーカイバの検証と DB との突き合わせが飛ばされるため。次の実行が `Exists` でそのキーを見つけ、S3 と同じく検証する。
- **確認とは、保存されたオブジェクトが一致していること。** アップロードは本文の CRC32C を付けて送り（異なるバイト列はサービスが拒否する）、Put は確定したオブジェクトの長さと CRC32C を比べてから nil を返す。コピーが失敗したときは、閉じずに取り消す。閉じると、そこまで送った分が確定してしまうため。
- **実際の GCS では動かしていない。** テストは `STORAGE_EMULATOR_HOST` の向こうに置いた JSON API の偽物を使う。CP のバイナリはクライアントとその gRPC・OpenTelemetry の依存分だけ大きくなった（サイズは PR に記載）。リリースビルドは `disable_grpc_modules` タグで使わない gRPC トランスポートを外す。

## 追記（2026-10-25）— AWS の未決事項 5：ゲートウェイの一時停止と再開（#2729）

`pause.sh` は `EgressRoute=gateway` を拒まなくなり、`standup.sh` もそれについて警告しなくなった。実アカウントでは動かしていない。

- **切り替えるのはグループの台数だけ。** `00-network` の `GatewayEnabled`（既定 `true`）が Auto Scaling グループの最小台数と希望台数を 1 か 0 にする。最大台数は 1 のままにする。ローリング更新は `MinInstancesInService`（0）が最大台数より小さいことを求め、止めたグループにも新しい起動テンプレートは届きうるからである。`GatewayEni`、`GatewayEip`、Workspace の経路、トークンは `GatewayOn` だけに従うので、一時停止が出口のアドレスを手放したり経路の行き先を変えたりすることはない。終了したインスタンスがインターフェースを離し、次のインスタンスがそれを付ける。`autoscaling update-auto-scaling-group` の呼び出しではなくスタックのパラメータにしたのは、次のスタックのデプロイで台数が戻らないようにするためと、キャプチャに残すためである（`standup.sh` はキャプチャの `false` を `NatEnabled` と同じく `true` に上書きする）。これに従うのが `GatewayAsg` だけであることは `deploy/local/cfn-egress-gateway-test.py` が固定する。
- **止めたゲートウェイは Workspace の経路をブラックホールにする。** 経路は `GatewayEni` に残り、NAT ゲートウェイには戻らない（戻ると記録されない egress になる）。問題にならないのは、先にすべての Workspace を止めるからに過ぎない。
- **順序。** 止めるとき：Workspace を止めたあと、クラスタに Workspace のタスクが 1 つも残っていないこと（サービスの希望数に関係なく）を待ち、Squid を止め（開いたトンネルは閉じたときにしか記録されない）、そのログのすべてのバイトが、CP が受け取ったあとでエージェントが確定したオフセットより手前にあるまで待つ。そのあとでゲートウェイ、次に CP。スケールインはインスタンスのディスクを消すので、確かめられないものがあれば一時停止は失敗し、両方とも動いたまま残る。戻すとき：ゲートウェイは NAT ゲートウェイと同じデプロイで起動し（自分のパブリックアドレスで起動する）、`pause.sh` は CP の前に、インスタンスがインターフェースを付け Squid とエージェントが動くまで待ち、CP の後に、エージェントが最初のポリシーを適用するまで待つ。2 回目はポリシーを配る CP より前には置けない。その間に起動した Workspace は閉じた初期ポリシーで拒否され、外へは出ない。
- **準備完了と送り切りは SSM Run Command で読む。** 準備完了とは、エージェントの今回の実行で Squid がポリシーを適用したことを指す。モードファイルにエージェントの `# mode: ` の見出しがあり（閉じた初期ファイルには無い）、ユニットの今回の起動が `policy applied`、または CP が止まっている間に始まった実行なら `reloaded Squid with the policy on disk` を記録していること。エージェントはどちらも Squid の再読込が成功したあとにしか書かない。さらに、その最後の行がポリシーファイルの最終書込みより古くないこと（新しいインスタンスは CP のポリシーが書かれる前に初期ファイルを再読込する）。送り切りの確認は Squid が止まっているときだけ有効とし、インターフェースを読めないときは「インスタンスなし」とせず失敗にする。ファイルが書かれただけでは適用ではない。インスタンスの外からの確認では、初期ポリシーと本物のポリシーを区別できない。

これで AWS の未決事項 5 は閉じる。未決事項 7（#2728）は残る。

## 追記（2026-10-25）— AWS のテンプレートがアーカイブをつなぐ（#2732）

#2699 のアーカイブには AWS 側の配線が無く、同一リージョンの `s3://` バケットを手で指定しても 2 か所で失敗していた。S3 エンドポイントのポリシーが拒否し（NAT 経由にはならず AccessDenied）、CP のタスクロールにもそのバケットへの権限が無い。作業と合わせて次のように決めた。まだ実アカウントでは動かしていない。

- **スタックが持つバケットだけにする。** 10-data が `EgressArchive=create` で作る（Retain、SSE-S3、バージョニングなし、`egress/` に有効期限）。既定はバケットなしで、アーカイブは無効のまま。運用者自身のバケットは対象外とした。エンドポイントのポリシーは 00-network にあり、10-data のバケットを名指しできないので、モデル用バケットと同じく `s3:ResourceAccount` を付けて `af-*-egress-archive-<アカウント ID>` を許可している。外部のバケット名はそこで拒否される。
- **CP の権限は `egress/*` への `PutObject` と `GetObject`、バケットへの `ListBucket`。** 20-platform のマネージドポリシーにした（CP ロールのインライン合計には上限がある、#1576）。`ListBucket` に `s3:prefix` 条件は付けない。存在しないキーへの HeadObject を 403 でなく 404 にする判定はプレフィックス無しで行われ、sink は 403 をエラーとして扱うため。このバケットにはアーカイブしか入らない。エンドポイントの文も同じ操作にしてある。
- **URL は接頭辞なしの `s3://<バケット>`。** CP のキーがすでに `egress/` で始まるため。`standup.sh` と `update.sh` は 10-data の出力からバケット名を取り、20-platform と 30-ingress に渡す。

詳細は `deploy/aws/ecs/cfn/PARAMETERS.md` の "The egress archive"。`deploy/local/cfn-s3-endpoint-test.py` と `deploy/local/cfn-egress-archive-test.py` が固定している。

Follow-ups: #2734

## 追記（2026-10-26）— AWS の未決事項 7：2 つの送信元アドレス（#2728）

メンテナと決めた（2026-10-25、#2728 に記録）。`EgressRoute=gateway` の配備は **2 つの恒久的なアドレス** から外へ出る。CP、スロットのホスト、エンジンは NAT ゲートウェイのアドレス（`NatEip`）のまま、Workspace はゲートウェイのアドレスを使う。組織は両方を登録する。実アカウントでは動かしていない。

- **`GatewayEipAllocationId` / `GatewayEipAddress`**（`00-network`）は `NatEipAllocationId` に対応するもの。
  - スタックの外で確保したアドレスを渡せば、`gateway` へ切り替える前に許可リストへ登録でき、空白は生じない。
  - 渡さなければスタックがアドレスを確保して保持する。渡したときはスタックがそれを作ることも、置き換えることも、手放すこともない（`GatewayEip` は `CreateGatewayEip` のときだけ存在する）。
  - 公開アドレスもパラメータにした。ALB はこのアドレスでゲートウェイを通すが、CloudFormation は自分で作っていない割り当てのアドレスを読めないからである。2 つを揃えて渡すことは Rules で強制する。
- **作り直しても残る。**
  - 同じ名前の出力が、誰が確保したかにかかわらずアドレスを運ぶ。そのため `capture-env.sh` は、`NatEipAllocationId` と同じく、空でキャプチャされた 2 つのパラメータを埋める。
  - `EgressRoute=gateway` のとき、`standup.sh` は次のときには構築を始めない：割り当てが無くなっている、アドレスがキャプチャと違う、別のインターフェースが持っている。
  - 以前のゲートウェイが残したアドレスは `af-<stack>-egress-gateway-eip` のタグで見つけ、同じ方法で渡し直す（README の "Two egress addresses"）。
- **ゲートウェイを作るときに設定する。** すでにゲートウェイが動いているスタックで設定すると、Workspace が使っている最中に `GatewayEipAssoc` が置き換わる（未計測）。
- **却下：** `NatEip` をゲートウェイへ移す案（C）。NAT ゲートウェイのアドレスはその場では変えられないので、どのみち CP とホストは新しいアドレスになり、その前に通信できない時間ができる。
- **作らず、代替として記すもの：** ゲートウェイが NAT ゲートウェイ経由で外へ出る案（B）。2 つ目のアドレスを登録できない組織向けで、アドレスは 1 つになるが、Workspace の全通信に NAT のデータ処理料金が戻る。

これで AWS の未決事項 7 は閉じる。

## 追記（2026-10-26）— 配る policy には CP 自身のホストが常に入る（#2742）

サンドボックス（ecs-ec2、`EgressRoute=gateway`、log-only）で、デプロイ自身の console ホストが Workspace からの全接続で would-block と判定された。ECS の Workspace は公開 URL（`AF_CP_BASE_URL`）しか持たず、`NO_PROXY` に CP のホストが入るのは `AF_CP_INTERNAL_URL` からだけで、それを設定するのは Kubernetes だけである。さらに gateway は Workspace のルートテーブルで 443 を横取りするので、`NO_PROXY` だけでは Squid を避けられない。enforce にすると Workspace は CP を失っていた。

- **CP が配る policy は `PUBLIC_BASE_URL` と `AF_CP_INTERNAL_URL` のホストを常に許可する**（`cpEgressHosts`）。製品既定と並ぶ完全一致のホストで、allowlist の表の外にある。管理者の編集では外せず、Admin の一覧と `list_allowlist` には組み込みとして出る。完全一致だけなので、親ドメインまで enforce が開くことはない。gateway のエージェントも自前の forward proxy もこのエンドポイントが配るものを強制するので、どのランタイムでも成り立つ。docker と native の Workspace も公開 URL へは proxy を通る。
- **組み込みのエントリが覆うもの、覆わないもの。** allowlist はホスト単位なので、CP のホストはどのポートもどのパスも許可される。自前の proxy はそのホストの任意のポートへの CONNECT を受け付け、同じ名前の裏にある別のサービス（共有の ALB や CDN）も通る。したがって CP には専用のホスト名を持たせる。このエントリは名前を許可するだけで、gateway のほかの拒否は何も解除しない。gateway が扱うのは 80 と 443 だけで、ループバック・リンクローカル・VPC 内の宛先は引き続き拒否する。そのため、別のポートの CP や、公開名が VPC 内に解決される CP には、この変更だけでは gateway 経由で届かない。http(s) でない URL、ホストが完全一致の 1 つの名前でないもの（先頭の `.` や `*`）、IPv6 リテラルは許可せず、起動時にログに出す。前の 2 つは兄弟まで開いてしまい、3 つ目はエージェントの allow ファイルに書けない（#2754）。
- **ここでしていないこと：ECS 向けの VPC 内の CP URL**（#2742 の案 b）。CP への通信を gateway から外せるが、CP の内部リスナー、セキュリティグループの規則、テンプレートのバイトが要り、しかも上の対処は不要にならない。公開 URL は人が開くリンクと内部 git ホストとして使われ続ける。
- 実アカウントでは動かしていない。サンドボックスでの enforce の確認は未実施。

Follow-ups: #2746, #2754

## 追記（2026-10-26）— 横取りした TLS はリレーを通して Squid に渡す（#2759）

サンドボックス（ecs-ec2、`EgressRoute=gateway`、log-only と enforce）で、横取り経路の S3・ECR・STS への HTTPS が curl rc=35 で失敗した。同じリクエストを明示プロキシ経由で送ると成功し、`checkip.amazonaws.com` はおよそ 8 回に 1 回失敗した。Squid の `cache.log` には「Host header forgery detected ... (local IP does not match any domain IP)」が出ていた。

- **原因**（Squid のソース。v5・v6・v7 で同じ。2026-10-26 に確認）。横取りする `https_port` では、peek の後の splice が SNI 宛ての偽の CONNECT を作り（`ConnStateData::splice`、`fakeAConnectRequest`）、宛先を Squid 自身によるその名前の名前解決と照合する（`hostHeaderVerify`、`hostHeaderIpVerify`）。CONNECT で一致しなければ `host_verify_strict` の値にかかわらず必ず 409 になり（「For now suspicious intercepted CONNECT requests are always responded to with an HTTP 409」）、`client_dst_passthru` は照合に通った後にしか効かない。Squid は回答を最低でも `negative_dns_ttl`（1 分）保持し、これらのサービスは問い合わせごとに違うアドレスの部分集合を返すので、Workspace が接続したアドレスはたいてい Squid の集合に入っていない。`host_verify_strict off` と `client_dst_passthru on` はもともと既定値である。
- **却下：共有のキャッシュリゾルバ。** ECS の `awsvpc` タスクは VPC のリゾルバを使う。変えるには VPC の DHCP オプションを変えることになり、CP やホストにも及ぶ。しかもクライアント側のキャッシュは Squid のものとずれ続ける。
- **却下：ステップ 2 で peek、ステップ 3 で splice。** 偽の CONNECT は避けられるが、Squid は判定の前に接続してクライアントの hello を送るので、拒否する名前でもその宛先に届く。拒否する名前をステップ 2 で先に terminate すればそれは防げるが、今度はゲートウェイの OpenSSL がすべてのサーバー hello を解析することになり、知らない鍵交換グループで失敗しうる。それはオフラインでは確かめられない。
- **決定。** nftables は引き続き Workspace の 443 を `:3130` へリダイレクトする。そこで `af-cp egress-relay`（`egressagent.Relay`、ユーザー `squid`）が conntrack から元の宛先を読み、ループバック限定の `http_port 127.0.0.1:3131 require-proxy-header ssl-bump` に PROXY ヘッダ（送信元は Workspace）と `CONNECT <元のアドレス>:443` を送る。Squid はこれを明示プロキシと同じに扱う。ガードの拒否はアドレスに効き、`ssl_bump` が SNI で判定し、splice は Workspace が接続したアドレスへ向かう。Squid から見て横取りではないので、ホストの照合は走らない。Squid が PROXY ヘッダを信じるのは localhost からだけ（`proxy_protocol_access`）。`af1` の行には Workspace のアドレスと SNI が残り、`%>rd` は元のアドレスになる。CP は SNI を優先して帰属させる。80 番は変えていない。平文 HTTP で照合に失敗してもログに出るだけで、リクエストは元の宛先へ送られる。
- **横取りした 443 に限り、決定 2 を置き換える。** 決定 2 は、ゲートウェイは既製のソフトウェアで自前のプロキシではない、としていた。この経路では、横取りしたすべての TLS 接続を自前のコードが運ぶ。接続の受け付け、PROXY ヘッダと CONNECT への変換、バイトのコピー、接続の寿命（Squid 側が終わった後の猶予と、同時接続数の上限）がそれにあたる。許可の判定、SNI、ガードの拒否、ログは Squid に残る。リレーは何も判定しないので、不具合があれば接続が失敗したり切れたりはしても、Squid が拒否する名前を通すことはない。80 番と明示プロキシは Squid だけのまま。保守するのは自分たちで、リレーが止まれば横取り経路の HTTPS も止まる。
- **強制は弱まらない。** 拒否する SNI は、どのアドレスに送っても terminate される（同じ `af_allowed_sni` の規則）。許可された SNI なら 443 番の任意の公開アドレスに届くが、これは明示プロキシ（アドレス宛ての CONNECT）ですでにそうだった。範囲は 443 番（nftables とセキュリティグループ）、アドレスへのガードの拒否（ループバック、リンクローカル、VPC）、`ip_forward=0` で限られる。名前とアドレスを結びつけるには復号が要る。
- **代償。** リレーは CP イメージに入っていてエージェントと一緒に起動するので、最初のインストールまで新しいゲートウェイは横取りした 443 を拒否する（どのみち最初の policy までは全部拒否している）。新しいイメージでリレーが再起動し、そのとき開いている横取り経路の TLS 接続は切れる。
- 実際の Squid では動かしていない。サンドボックスでの確認（log-only と enforce で、横取り経路の S3・ECR・STS と `checkip` 100 回、許可アドレスへの拒否 SNI とその逆）は #2759 に書いた。
