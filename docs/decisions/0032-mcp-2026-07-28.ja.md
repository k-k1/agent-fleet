# 0032. MCP 2026-07-28 は「両 era 同時 serve」で受ける — 判別は `_meta` の版 1 点

[English](0032-mcp-2026-07-28.md) | 日本語

- 状態: **採用・実装済み**（probe と af のサーバー 2 本）。認可の OAuth 2.1 整合は範囲外。
  設計と実測は [docs/49](../log/49-mcp-2026-07-28.md)。
- 関連: [0006](0006-mcp-unified.ja.md)（af が提供する MCP・PAT 認証）/
  [0031](0031-mcp-registry.ja.md)（MCP レジストリ — probe の持ち主）

## 背景

MCP 2026-07-28 が確定した。`initialize` ハンドシェイクと `Mcp-Session-Id` を廃し、版・
クライアント情報・能力を毎リクエストの `_meta` で運ぶ**破壊的変更**を含む。

af は MCP を提供する側（CP `/mcp`、Agent `mcp-stdio`）と利用する側（レジストリの接続テスト）の
両方に立っている。コードを当たったところ、**af の 2 つのサーバーは元から実質ステートレス**
だった（純粋な switch、`initialize` は版を echo するだけ、セッション ID を発行しない）。
今回の改訂で最も重い「セッション state の撤去」は、やることが無い。

一方で af は 3 箇所とも `2025-06-18` を宣言しており、現行リリース版 `2025-11-25` に対して
**既に 1 版遅れていた**。

## 決定

### 1. 両 era を同時に serve する（旧 `initialize` を残す）

仕様は「両対応したいサーバーは旧 `initialize` を実装し続けてよい」と明示している
（SEP-2575 Backward Compatibility）。落とせば、まだ更新されていない claude / codex が
af の MCP に繋がらなくなる。**利用者の CLI がいつ新版になるかは af の管理外**であり、
こちらから期限を切る理由がない。

**旧 era の挙動は 1 バイトも変えない**。新版の検証もヘッダ規則も適用せず、未知メソッドは
従来どおり `200` + `-32601` を返す。新版対応は既存クライアントに対して no-op であること
——これを回帰テストで固定した。

### 2. era の判別は `_meta` の `protocolVersion` の有無、ただ 1 点

旧クライアントはこのキーを絶対に送らず、新クライアントは必ず送る。**分岐点を 1 つに保つ**のが
狙いで、ヘッダの有無・メソッド名・User-Agent といった副次的な材料は一切見ない。
複数の判定材料を持つと、それらが食い違ったときの挙動が誰にも説明できなくなる。

### 3. 検証は「版 → `_meta` 必須項目 → ヘッダ照合」の順

版を最初に見るのは、旧新の取り違えに対して**行動可能な**エラー
（`UnsupportedProtocolVersionError` + `supported` 一覧）を返すため。順序を逆にすると、
版が古いだけのクライアントに「ヘッダが違う」と答えることになり、相手は再交渉できない。

ヘッダ照合（`-32020`）は仕様上の要求であると同時にセキュリティ要件でもある。中間装置が
ヘッダで、サーバーが本文で判断する構成では、両者の食い違いがそのまま取り違えになる。
`Mcp-Name` の base64 sentinel は**比較前に復号する**（しないと非 ASCII 名が必ず不一致になる）。

### 4. probe は `server/discover` 先行。沈黙は 2 秒で旧版に倒す

仕様は stdio について「`server/discover` を先に投げ、`Method not found` なら旧版へ落ちる」と
定めている。HTTP でも同じ手順を使うことにした——経路が 1 本で済み、ついでに `serverInfo` と
`supportedVersions` が取れて接続テストの表示が厚くなる。

仕様に無い追加が 1 つある。**未知メソッドに無反応な旧サーバーは 2 秒で旧版とみなす**。
JSON-RPC 上は `-32601` を返す義務があるが、黙殺する実装は現実に存在し、それを待つと probe 全体の
タイムアウトを食い潰して「タイムアウトしました」としか言えなくなる。1 秒台の無駄と引き換えに、
原因不明の停止を消す。

接続テストの結果には**どちらの版で応答したか**を載せる。移行期は「繋がるが旧版経由」と
「新版で繋がっている」の区別が運用情報になる。

### 5. `serverInfo` は両方の形で出し、両方の形で読む

`DiscoverResult` の `serverInfo` の置き場が SEP-2575（top-level）と draft ドキュメント
（`_meta` 配下）で食い違っている。**どちらが正になっても壊れない**ように、サーバーは両方に出し、
クライアントは両方を読む。余分なフィールドは無害で、片方に賭ける理由がない。

### 6. 認可（OAuth 2.1 / OIDC 整合）は今回の対象外

6 つの SEP が MCP サーバーを OAuth 2.1 リソースサーバーとして位置づけ直したが、CP は PAT Bearer 主で、
それは [0006](0006-mcp-unified.ja.md) の前提そのもの（「PAT 主・OAuth は後」）。ここに手を入れるのは
版追随ではなく認証方式の再判断であり、別 ADR で扱う。

なお SEP-2575 の「セッション廃止により全リクエストが独立に認証されねばならない」という要求は、
CP が元からリクエスト毎に PAT を解決しているため既に満たしている。

## 却下した案

| 案 | 却下理由 |
|----|---------|
| 新版だけに移行し `initialize` を削除する | 未更新の CLI が全部繋がらなくなる。仕様自身が両対応を許している |
| 新版対応を CLI が対応するまで見送る | af のサーバーは既に 1 版遅れていた。追随を先送りすると差が開く一方で、しかも今回は追加分が小さい |
| era を HTTP ヘッダ（`MCP-Protocol-Version` の有無）で判別する | stdio に無い。判別材料を transport ごとに分けると挙動が説明できなくなる（決定 2） |
| `resultType` を新 era のときだけ付ける | 旧クライアントは未知フィールドを無視するだけ。分岐を増やす利益がない |
| CP と Agent で共通モジュールを作る | 2 バイナリは別モジュールで、共有モジュールは [0012](0012-go-internal-refactor.ja.md) で見送り済み。同型の実装を 2 つ持つ重複を引き続き受け入れる |
| Go beta SDK に載せ替える | 追加分が小さく、SDK はまだ beta。安定後に比較する（積み残し） |

## 結果

- af の MCP は新旧どちらのクライアントからも使える。旧クライアントへの影響はゼロ。
- レジストリの接続テストは新旧どちらのサーバーも検査でき、どちらで応答したかを報告する。
- 版宣言が `["2026-07-28", "2025-11-25", "2025-06-18"]` になり、1 版遅れが解消した。

## 積み残し

- 認可の OAuth 2.1 / OIDC 整合（決定 6）。
- `subscriptions/listen` / MRTR / キャッシュ指示 / MCP Server Card — いずれも af が現状使わない機能。
- 仕様側の `serverInfo` 不一致が収束したら片方に寄せる（決定 5）。
