## 背景

Qwen-Image 2.1 は 2026-09-20 に公開された。名前は ADR 0094 が足した Qwen-Image-Edit 2 族の隣に
置きたくなるが、中身は「その版」の正反対である。

| | qwen-image-edit-2509 / 2511 | qwen-image-2.1 |
|---|---|---|
| 拡散モデル | 20B MMDiT | 7B single-stream DiT |
| テキストエンコーダ | Qwen2.5-VL-7B | Qwen3-VL-8B |
| オートエンコーダ | Qwen-Image VAE — 16ch・downscale 8 | 自前 — **64ch・downscale 16**・RGBA |
| op | 編集のみ | **生成と編集** |
| エンコードノード | `TextEncodeQwenImageEditPlus` | `TextEncodeQwenImage21` |
| ライセンス | Apache 2.0 | **Qwen Research License — 非商用** |

ADR 0094 決定 6 の規則は「族は**トポロジ**ごとで、版ごとではない」。上の表の 3 つの事実は
それぞれ単独でも新しい族にする理由になる——エンコードノードが違う、オートエンコーダが違う、
既存のどの族も持っていない op の組み合わせを持つ。

静かに壊れるのはオートエンコーダである。`VAELoader` はどちらも受け、`--vae` はどちらの役も
名乗り、CP の部品表は S3 鍵で配る——だからこの族を他 4 族が共有する Qwen-Image VAE に向けても
どこも拒否せず、ノイズに復号される。部品表の鍵を共有せず**新しい鍵**にしたのはそのためで、
あの 4 族がわざわざ共有するように書かれているのの逆を行っている。

## 実測したこと

すべて 2026-09-21、断りが無ければ匿名で。

**上流のリポジトリ。** `Qwen/Qwen-Image-2.1` は **ungated**（`gated: false`）、
`license: other`、`license_name: qwen-research`、タグに `rgba`。`Comfy-Org/Qwen-Image-2.1` が
ComfyUI 向けのミラーで、これも ungated。この配備のローダが読む単一ファイルの分割を配布している。

```
diffusion_models/qwen_image_2.1_bf16.safetensors            13.25 GiB
diffusion_models/qwen_image_2.1_int8_convrot.safetensors     6.76 GiB
text_encoders/qwen3vl_8b_bf16.safetensors                   16.33 GiB
text_encoders/qwen3vl_8b_int8_convrot.safetensors            8.71 GiB
text_encoders/qwen3vl_8b_w4a8.safetensors                    5.88 GiB
vae/qwen_image_2.1_vae_bf16.safetensors                      0.63 GiB
```

⚠️ 同じリポジトリの `text_encoders/qwen3.5_9b_qwen_image_2.1_pe_{t2i,i2i}.int8_convrot.safetensors`
は**テキストエンコーダではない**——プロンプト強化モデルで、公式テンプレート自身のモデル一覧に
載っていない。

**ピン中のエンジン。** `comfy_extras/nodes_qwen.py` を 3 つのタグで読んだ。
`TextEncodeQwenImage21` は v0.35.2（現在のピン）にも v0.36.0 にも無く、**v0.37.0** にある。
ピンに対して測ると、このバンプは既にあるものにとっても安全である: この Agent の 10 本の
テンプレートが出すノード 30 種はどちらのタグにも存在し、それらに触れる定義の変更は無害な
3 つだけ——`CLIPLoader` の type 一覧に `yue2` が増えた、`EmptyLatentImage` の width/height の
**既定値**が 512 → 1024 に動いた（ここのテンプレートは常に両方を明示する）、
`ModelSamplingAuraFlow` に既定 `flow` の任意入力 `sampling` が増えた。`nodes_qwen.py` は追加のみ。

**モデルの形、v0.37.0 のエンジン自身のソースから。** `comfy/latent_formats.py` の
`QwenImage21` は `latent_channels = 64`・`spacial_downscale_ratio = 16`。
`comfy/supported_models.py` は `shift: 0.69`・`memory_usage_factor: 6.0`。`comfy/sd.py:1955` は
この族のエンコーダに `clip_type == CLIPType.QWEN_IMAGE` **かつ** state dict が
`TEModel.QWEN3VL_8B` と判定されたときだけ到達する——つまり CLIPLoader の `type` はここでは
読まれ（krea2 の側であって anima の側ではない）、同じ type の中でこの族を兄弟から分けるのは
**ファイル**のほうである。

**公開されたグラフ。** Comfy Org は `image_qwen_image_2_1_t2i.json` と
`image_qwen_image_2_1_image_edit.json` を同梱している。並べて読むと同じノードの同じ配線である。
どちらの KSampler も **25 steps・cfg 1・euler・simple・denoise 1**。どちらの注記も
「negative_prompt: unused while cfg is 1. Raise it only if you use a negative prompt」と
「公式パイプラインは euler で 40-50 steps 程度。このテンプレートは 25 から始める」と言う。
編集テンプレートが配線するのは **image_1 … image_10** で、注記は「参照画像は最大 10 枚」。
ノード自身は image_1 … image_16 を受ける。

**Civitai。** model-version 3344134（`Qwen Image 2.1 GGUF`）は `baseModel: "Qwen 2"`、AIR urn
`urn:air:qwen2:…`、4.10 / 7.09 / 7.51 GB の GGUF 3 本。絞り込みは、`types=Checkpoint` で
1 ページ目ではなく**全件**:

```
baseModels=Qwen 2  ->  チェックポイント 5 件、全部 Qwen-Image 2.1
baseModels=Qwen    ->  チェックポイント 20 件超、5 アーキテクチャにまたがる:
                       Qwen-Image / Qwen-Image-2512 / Qwen-Image-Edit・2509・2511 /
                       テキストエンコーダである `Qwen-3-0.6B base/anima`
```

Hugging Face では `filter=base_model:Qwen/Qwen-Image-2.1` が派生物を返す（Comfy-Org のミラーと
GGUF 変換がいくつか）。

## 決定

### 決定 1 — 新しい族 `qwen-image-2.1`、ドット付きで綴る

既存テンプレートに対する行の `params` ではなく新しいテンプレートにする。理由は上の表の 3 つ
すべて。綴りは製品のドットを持つ。CP はその文字列そのもので行を検証し、
`engine_catalog_test.go` は Agent のソースからそれを読むので、2 つの写しは 1 つの綴りである。
（その試験の族定数の正規表現にドットを教える必要があった——無いと `qwen-image-2.1` が
`qwen-image-2` として拾われ、存在しないドリフトを報告する。）

### 決定 2 — 1 本のテンプレートが両方の op を担い、違いは latent だけ

公開された 2 本のテンプレートの違いはちょうど 1 本の配線である。生成は呼び手の寸法の
`EmptyLatentImage` から始まり、編集は `TextEncodeQwenImage21` 自身の第 3 出力——リサイズされた
先頭の参照画像に合わせた全ゼロの latent——から始まる。これが「出力は image_1 に従う」の表現形。
テンプレートは両者の間に `ComfySwitchNode` を置くが、この builder は参照画像の有無で選ぶ。
同じ選択で、ノードが 1 つ少ない。

どちらの配線も入れ替えがきかず、どちらの壊れ方も声を出さない。生成にエンコードの latent を
使うと、何を頼まれても 1024² で答える。編集に `EmptyLatentImage` を使うと、条件付けが想定して
いない画布の上に編集を置く——テンプレート自身の注記が「リサイズ後の image_1 の寸法に近づけること。
さもないと編集がずれる」と言っている。

inpaint は未主張のまま。ADR 0072 決定 3 の根拠——マスクは配線できるが、上流の誰も配布しておらず、
ここの誰も走らせていない。

### 決定 3 — この族が「指示編集」と「編集専用」を分ける

これまでは**1 つの事実**が 5 つの問いに同時に答えていた。指示編集の族がたまたま編集専用でもあり、
かつ 1 つの builder で組めてもいたからである。ADR 0094 未解決 4 がそれを
`comfyFamilyRow.InstructionEdit`（非 nil なら決定 2・3・4・5・12 がすべて当てはまる）に畳んだ
直後に、この族が**そのうち 3 つの軸で同時に反例**になった。だからポインタ 1 本が背負っていた
ものを行のフィールドに分ける。

- `InstructionEdit` は畳んだときの狭い意味を保つ——非 nil の族はちょうど
  `comfyGraphQwenImageEdit` が組める族。この族は **nil**（自前の builder を持つ）。
- `FixedDenoiseEdit` は決定 2 の事実だけ——`op=edit` は画像で sampler を条件付け、denoise は
  1 固定＝`strength` の行き場が無い——で、この族は**真**。`comfyFamilyInstructionEdit` は
  こちらを読む。配線ポインタはこれを含意するが逆は成り立たない。その片道を試験で固定し、
  「ポインタ無しで真の族が少なくとも 1 つある」ことも対照として見る（無ければ 2 つの欄が
  黙って 1 つの問いに戻っている）。
- `Ops` と `RefInputs` は行の宣言で、空・0 は寛容な既定。

🔴 `comfyFamilyHasNoSizes` は 2 度目の宣言を増やさず **`Ops` から導出**した。導出こそが決定 4 の
本来の言い方である——寸法が届く先は `EmptyLatentImage` だけで、それを組むのは生成経路だけ。
だから生成できない族には寸法の置き場が無い。

🔴 寸法の帰結は明記しておく価値がある: **この族は寸法を持つ**。隣の 2 族に揃えて空にすると、
唯一寸法を読む op である生成側から寸法の操作が消える。編集側で寸法が無視されるのは同じだが、
それを言うのは全族が既に共有している img2img の警告であって、半分の場合に嘘になる
「寸法なし」の族単位の宣言ではない。

### 決定 4 — 参照画像は 10 枚。これは**引用**であって実測ではない

ノードは image_1 … image_16 を取り、公式の編集テンプレートは 10 本配線している。この族が宣言
するのは 10。

🔴 隣の 3 のように黙って置かず、名指しで断る。ADR 0094 決定 5 はあの数字を「配線がループだから
もっと通るはず」で上げることを**意図的にしなかった**——実測 F を待った。ここには走行が 1 つも
無いので、正直な根拠は公開された配線であり、それは recipe についてこのリポジトリが受け入れて
いるのと同じ根拠である（sd15・anima・krea2 はいずれも未走行の recipe を引用付きで持つ）。
10 枚目が無視されると分かった走行があればこの数字は誤りで、直す場所は行の `RefInputs`。

### 決定 5 — `resolution` は 1024。公開グラフを素通りさせない唯一の数字

`TextEncodeQwenImage21` は参照画像を `resolution × resolution` の画素予算へ、アスペクト比を
保ったまま 32 の倍数に丸めてリサイズする——そして latent 出力を通じて、それが編集の画布になる。
公開された数字は 2 つあって食い違う: ノード自身の既定は 1024、注記は 1024 を「official default」
と呼び、編集テンプレートの昇格ウィジェットは **0**（「各参照を自分の寸法のまま保つ」）である。

0 はテンプレートの作者にとっては妥当で、題材を選べるからである。この経路では妥当でない:
ここは利用者が上げた任意の写真を受けるので、0 は 8000 画素の写真を 8000 画素で encode する——
VAE の encode も視覚トークン数もこの経路の誰も上限を掛けておらず、しかもカードは同時に
15 GiB 級の重みを抱えている。だから「公開グラフの数字を採る」はこのテンプレートの他のすべてで
守り、ここだけ声を出して破る。

### 決定 6 — ライセンスは既存のテナント別承諾に乗せ、`qwen-research` は分類する

Qwen Research License §2a は "FOR NON-COMMERCIAL PURPOSES ONLY" で権利を付与する。新しい仕組みは
作らない: 取り込みは既にテナント別に `license_accepted_by` / `_at` / `_tenant` / `_license` を
記録しており（ADR 0072）、Flux.2 Klein 9B が既にその経路でカタログに入っている。

1 行だけ要ったのは分類器のほうである。`engineCommercialUse` は**語**を読む（"non-commercial"・
"-nc"）が、"qwen-research" はそのどれも含まないので、正しく埋まった行が `unknown` を返していた。
`unknown` は「誰も読んでいない条項」への本物の答えであって（ADR 0072 決定 10）、
「読んだが名前が違う条項」への答えではない。needle は実測した綴りだけで、それより広くしない——
「research」一般の needle は、読んでいない他社のライセンスまで分類してしまう。

### 決定 7 — 部品は Comfy-Org のミラーから、int8 で、**新しい** S3 鍵に

`--clip_l` は `text_encoders/qwen3vl_8b_int8_convrot.safetensors`、`--vae` は
`vae/qwen_image_2.1_vae_bf16.safetensors`、どちらも `Comfy-Org/Qwen-Image-2.1` から。
publisher 自身のリポジトリでなくミラーなのは `Comfy-Org/Qwen-Image_ComfyUI` を既に使っているのと
同じ理由——どちらも ungated で、ComfyUI のローダが読むのは単一ファイルの分割のほうだから。

bf16 でなく int8 なのは、公式テンプレート 2 本の CLIPLoader ウィジェットがそれを名指すからで、
かつ 8.71 GiB と 16.33 GiB は重みの隣に載るか載らないかの差だから——ここでは引用できる選択と
成立する選択が同じ選択になっている。

🔴 VAE の鍵は Qwen-Image VAE を指す 4 族と**共有しない**。共有は誤ったパスより悪い: 再利用の
検査が「もう置いてある」と誤ったバイト列を見つけ、何もダウンロードしない。

### 決定 8 — Civitai の GGUF 経路は範囲外

この作業のきっかけになったモデルページは GGUF 変換を 3 本配布している。この配備はそれを
読み込めない: **ComfyUI-GGUF はエンジン画像に焼かれていない**し、それは意図的である
（`deploy/aws/ecs/comfyui/Dockerfile`）——ピン留めしてゴールデンで守るエンジンは実行時に
カスタムノードを入れない。だからこの族の GGUF 量子化ラダーは、存在しないローダへ向かう梯子に
なる。取り込みの経路は safetensors のミラーであり、image 役に GGUF 対応を足すのはそれ自身の
供給鎖の議論を持つ別の決定である。

### 決定 9 — 族の推測は `Qwen 2` を全体一致で取り、`Qwen` には依然として規則を置かない

`Qwen 2` は**全体一致**（`engineFamilyRule.equal`、anima と同じ機構）。部分一致にすると正規化後の
`qwen2` が `Qwen 2.5` と `Qwen2-VL` を飲み、そのたびにこのテンプレートが読めない行の
`base_model_missing` を黙らせる。

実測がそのまま論拠であり、それは ADR 0094 が仮定のまま残した問いにも決着をつける。
`baseModels=Qwen` は「Qwen-Image-Edit の文字列」ではない——テキストエンコーダを含む 5 つの
アーキテクチャが入った雑多な引き出しである。だから `Qwen` は意図的な不在を保ち、
チェックポイントの全件がちょうど 1 アーキテクチャである `Qwen 2` が規則と
`engineFamilyUpstreams` の項を得る。

⚠️ 残るリスクは、**将来の** Qwen-Image が同じ `Qwen 2` で公開されること。そのとき推測は
読み込めないトポロジに 2.1 のテンプレートを勧める。これは `Flux.2 Klein 9B-base` と同じ形の罠で
（ADR 0072 の follow-up）、needle では先回りできず、答えになるのはこの表を信じることではなく
測り直すことである。

## 却下した案

### qwen-image-edit-2511 の行にする／配線フラグ付きの共有テンプレートにする

2 つはファイルもエンコードノードもオートエンコーダも共有しない。`params` にはそのどれも表現
できず（ADR 0072 の `params` の語彙は sampler の 4 欄）、違いごとに分岐を持つ共有 builder は
1 つの関数に入った 2 本のテンプレートである。

### 編集テンプレートに倣って `QwenImage21Cache` を出す

あちらでのウィジェットは `auto` / `default` で、モデルは
`transformer_options.get("qwen_image21_cache", {})` を読む——ノードが無いとき device は `auto`、
dtype は `default` に落ちる（`comfy/ldm/qwen_image21/model.py` の `select_prefix_cache`）。
つまりその値でのノードは証明可能に no-op で、しかも `is_experimental` である。出せば
v0.37.0 以降にしか存在しないノードを増やして何も変わらない。

### 両テンプレートに倣って `SaveImageAdvanced` を使う

`SaveImage` はこのモデルが出すアルファを保つ——生の配列をそのまま PIL に渡すので、4ch の絵は
アルファ付き PNG として書かれる（`nodes.py` の `save_images`）。加えて `SaveImage` がやり、
この経路が依存しているのが、`readImageProps` が読む `prompt` PNG チャンクを書くことである
（ADR 0094 P2）。テンプレートとの見た目の一致のために保存ノードを替えるのは、動いている props
経路を何も得ずに手放すことになる。

### `op=edit` の寸法を拒否する

ADR 0094 決定 4 の `comfySizeRefusal` と対称に見えるが、ここでは誤り: この族は寸法を広告するので
ペインは寸法の選択欄を描き、値で拒否するとペインが送る編集を全部拒否することになる。正しい継ぎ目
は既存の img2img 警告で、それは既に鳴る。

⚠️ その警告は**入力画像自身**の寸法を名乗っていたが、この族は `resolution` の予算にリサイズする
——つまり報告される数字は近似だった。0094 の族でも近似だった（FluxKontextImageScale がリサイズ
する）ので、これは新しい不正確さではなく既存のものであり、「未解決」に置いた。その後すべての族に
ついて直した（「未解決の項目のその後」節）。

## フェーズ

- **P0 — ComfyUI のバンプ（別の変更）。** `COMFYUI_REF` を v0.35.2 → v0.37.0 にし、
  `.github/workflows/comfyui-image.yml` で焼き直す。静的な側の確認は済んでいて「実測したこと」に
  ある。それが覆えないのは既存 10 族を載せた GPU での実際のコールドスタートで、それはその変更
  自身の受け入れ条件である。

- **P2 — 実機受け入れ。** パネルから行を取り込み、op ごとに 1 枚ずつ撮る。完了の定義: 寸法を

## P2 の実機（2026-09-23）

開発配備で走らせた: Control Plane と Agent は `0.22.2-dev-ea8ecbe9`（この ADR のコードを含む）、
エンジンは `af-comfyui:v0.37.0`、箱は梯子が既に買っていた g6e.xlarge（L40S 48GB）。すべて本番の
経路を通した——パネルの取り込み API、カタログの行、そして `comfyGraphQwenImage21` でグラフを組む
Agent 自身の `POST /imagegen/generate`。

**取り込み——設計どおり 1 押し。** int8 の拡散モデルに対する `…/ingest/resolve` は 3 部品すべてを
計画して返し（ダウンロード 17.28 GB）、`commercial_use: "no"`・`license_name: qwen-research`——
決定 6 の分類器が実際の行で効いている。押下から 3 本のダウンロードまで約 15 分。行の
`vram_need_mib` はファイル合計の床 16,482 で、有効化はエンジンの選択中クラスが T4 の段（14,500）の
ため `confirm_vram` を求めた——ADR 0094 P1 が当たったのと同じ門。

**Agent がこの行について広告するもの**は決定 3 のとおり: `ops: [generate, edit]`、
`max_inputs: 10`、`knobs: [steps, cfg, sampler, scheduler]`——recipe の cfg が 1 なので `negative`
が消え、denoise 固定なので `strength` が無い——と、メガピクセルの寸法一覧。

**文章からの生成: 通った。**

| 要求 | 結果 | エンジン |
|---|---|---|
| `1216x832`・写真 | HTTP 200・端から端まで 59.6 秒・`1216x832` の PNG | `latent_shapes=[(1, 64, 52, 76)]`・58.1 秒 |
| `1024x1024`・テンプレートの RGBA の書き方 | HTTP 200・27.3 秒 | `(1, 64, 64, 64)`・26.0 秒 |

エンジン自身のログがモデルの形を裏付ける: 64ch・downscale 16 で、4ch の `EmptyLatentImage` から
`fix_empty_latent_channels` の空間側の補正で到達している。呼び手が名指した寸法は出力まで届いた＝
決定 2 の生成側。

RGBA の要求は透過で返った: α=0 が 17.6%、残りは柔らかい縁に沿う。⚠️ 普通の写真も RGBA で返り、
α は **252〜255**（画素の 47% が 255 未満）。画面では見えないが、背景に合成すると最大 1.2% 透ける。
未解決 4 への最初の実測の答えで、`SaveImage` ではなくモデルの復号の性質である。

**編集: 毎回失敗した。この ADR 自身の試験が固定していた鍵で。** 最初の参照 2 枚の編集は 1.2 秒で
HTTP 502 を返し、エンジンのログが理由を言った:

```
TextEncodeQwenImage21.execute() got an unexpected keyword argument 'image_1'
```

参照画像は `images` という名の V3 **Autogrow** グループで、各要素の API 形式の id はグループと要素を
ドットで繋いだもの——`images.image_1`（`comfy_api/latest/_io.py` の `finalize_prefix`）。`image_1`
はエディタが描くラベルに過ぎない。公開テンプレートの JSON は両方を持っており、builder は誤った方を
採っていた。`/prompt` は未知の任意の鍵を受け付けるので、グラフは検証を通ってノードの中で落ちた。
生成は参照のループに入らないので、壊れていたのは編集側だけ。

🔴 ゴールデンはずっと緑で、試験の 1 本（`…WiresEveryReferenceOntoTheOneEncode`）は裸の鍵を
アサートしていた——バグを捕まえずに固定していた。未解決 1 が書いたとおりのことが起きた:
ゴールデンはグラフの形を固定し、誤っていたのは形のほうだった。

**直しと、同じ箱での陽性対照。** builder は `images.image_N` を書くようになり、試験はそれを
アサートし、他の `image*` の鍵を拒む。同じ要求（`image_1` に狐、`image_2` に透過のマフラー）に
ついて**直した** builder が出すグラフを、ゲートウェイ経由でエンジンに直接投げた（配備済みの Agent
はまだ古い builder を持つため）: 約 35 秒で `execution_success`、マフラーは狐の首に巻かれ、
森・岩・光・枠は変わらなかった。

出力は `1216x832` の 1 枚目に対して **1248x832**: ノードは 1024² の予算へ 32 の倍数で再標本化する
（`round(sqrt(1024²·1.4615)/32)·32 = 1248`）。これが未解決 2 の不正確さの実測値——img2img の警告
は 1216x832 と名乗る。

**意図して取らなかったもの。** `vram_mib` は取らない: L40S には余裕があり、読めるのはファイル一式が
載ったままの値＝ADR 0094 決定 8 が「その欄の値ではない」とするもの。

**直しを配備したあとの Agent 経由（2026-09-23・`0.22.2-dev-ef644598`）。** 同じ参照 2 枚の編集を
ゲートウェイではなく Agent 自身の `POST /imagegen/generate` へ: HTTP 200・35.7 秒・`1248x832`——
しかも上のゲートウェイでの陽性対照と**画素単位で一致**（各チャンネルの差の最大 0）。配備された
Agent は直した builder が出すグラフをそのまま組んでいる＝P2 の編集側はこれで閉じる。

## P3 の実機 — T4 に載るか（2026-09-23）

取る価値がある `vram_mib` は、配備が買う箱を変えうる値だけだった。ファイル合計の床（16,482 MiB）が
既に 22,000 の段を選ぶので、L4 や L40S で読んでも買う箱は同じ。買う箱を動かすのは **T4 の段**
（g4dn・宣言 14,500・$0.34/h・エンジンの既定クラス）に収まる値だけである。そこで ADR 0094 P1 の
逆順で走らせた: 仮説（`vram_mib: 14000`）を宣言して段を候補に入れ、クラスを `g4dn-spot` に固定し、
箱を入れ替え、エンジン自身の `/system_stats` を 1 秒ごとに読む。

| | 生成・1024² | 編集・参照 2 枚 |
|---|---|---|
| 結果 | HTTP 200・破綻の無い絵 | エンジンは完走・指示どおりの絵 |
| サンプリング | **8.75 秒/ステップ**・プロンプト 249 秒 | **34.8 秒/ステップ**・約 15 分 |
| VRAM 使用のピーク（14,912 中） | 11,863 MiB・空き 3,048 | 13,757 MiB・空き 1,154 |
| ホスト RAM のピーク（15,791 中） | 13,720 MiB | 13,738 MiB |

**載る**。しかもカードはきつかった——テキストエンコーダはエンコード後に退避され、編集では重みが
出入りし続けた——ので、ADR 0094 決定 8 に照らしてこれらは**その欄の値である**。T4 は bfloat16 を
持たず、エンジン自身がそう言った: `model weight dtype torch.bfloat16, manual cast: torch.float32`。
fp32 の計算でも絵の質は保たれる（編集は L40S の結果とチャンネル差最大 94 で、見た目は同じ）が、
時間は保たれない。

**判断: 何も宣言しない。** 同じ編集を g22 の段で走らせると 35 秒・$1.35/h ≒ $0.013、T4 では
約 $0.085——時給は 4 分の 1 だが時間は 25 倍——で、しかも 15 分は Agent 自身の実行予算 15 分に
張り付く。13,757 を宣言すると、この行がエンジンの要求を決める日には、遅くて**しかも高い**カードを
梯子が買う。行は床のままとし、この実測は `vram_mib` ではなく理由としてここに残す。（今日は krea2 の
17,774 がエンジンの要求を決めているので実害は出ないが、その行を切った日に効いていた。）

⚠️ **T4 での編集は Agent 経由では返ってこなかった。** 74 秒で Agent が HTTP 502 を返した:
CP の `DescribeServices` 呼び出しが取り消されて `/history` が 503 を返し、`/history` の 503 は
リトライされない（ADR 0072 の P2 follow-up が既に名指している穴）。エンジンは走り続けて完走し、
絵はゲートウェイから取った。これは遅いカードでのポーリング経路の失敗であってこの族の失敗ではなく、
ここでは直さずにその穴に預ける。

エンジンは元に戻した: 仮説を撤回（`vram_mib: 0`）、クラスの固定を外し、箱を入れ替え——梯子は
再び `g22-spot` で g6e.xlarge を買った。

## 未解決の項目のその後（2026-09-23）

P2 が残した 4 項目を、開発配備（`0.22.2-dev-ef644598`・エンジンは g6e.xlarge / L40S・GPU の梯子
には触れていない）とコードで片付けた。要求は Agent 自身の `POST /imagegen/generate` を通し、
配備済みの Agent がまだ組めないグラフ 1 本だけは P2 と同じくゲートウェイに直接投げた。

### 未解決 2 — img2img の寸法警告は、絵が**実際に作られた**寸法を名乗る

警告は最初の参照画像自身の寸法を名乗っていた。リサイズする族では二重に誤りで、ここでは 1216x832
の参照が 1248x832 で返り（エンコードの 1024² 予算・32 の倍数）、しかもちょうど 1216x832 を頼んだ
呼び出し側には**何も言わなかった**——頼んだ寸法が入力の寸法と等しかったからである。

族ごとに画布を計算する案が、この項目の問いだったが、採らなかった。2 つのノード
（FluxKontextImageScale の推奨解像度の選び方・TextEncodeQwenImage21 の予算と丸め）の算術を Go で
再導出することになり、それは次のピンのバンプが黙って変える 2 つ目の写しである。この経路は既に
すべての出力のヘッダを読んでいる（`viewOne`）ので、警告は取得の後に最初の絵の**実測の**寸法から
組み立てるようにした（`comfyImg2ImgSizeWarning`）: 頼んだ寸法と作られた寸法が違えば必ず出し、
入力の寸法（呼び出し側が実際に変えられるもの）と出力の寸法を名乗り、出力が読めなければ入力の
寸法だけに戻る。0094 の族にも効く——族ごとのコードは無い。

### 未解決 3 — native 2K: 1 本走らせてから出す

| 要求（Agent 経由） | 結果 | 端から端まで | VRAM 使用のピーク（45,457 中） |
|---|---|---|---|
| `1024x1024`・狐・seed 1234（ここでモデルを載せる） | HTTP 200・破綻の無い絵 | 44.2 秒 | 16,706 MiB |
| `2048x2048`・同じ | HTTP 200・被写体は 1 つ・タイル化なし・毛並みも細かい | 116.3 秒 | 19,592 MiB |

2048² は既に経路の上限の内側にあった——`imagegenMaxPixels` は 4<<20 でちょうど 2048²、判定は
`>`——ので、利用者を止めていたのは一覧だけである。この族の行は自前の `Sizes` を宣言するように
なった: メガピクセルの 5 つ、続いて同じ 5 つの形の辺を倍にしたもの（`2048x2048`・`2304x1792`・
`1792x2304`・`2432x1664`・`1664x2432`）。走らせたのは正方形だけで、残り 4 つはそれより画素が少なく、
どの辺も 16 倍 latent のための 32 の倍数である。先頭は 1024² のままなので、寸法を名乗らない要求の
費用は変わらない。Console の予備のカード（`families.ts`）も同じ 10 個を持つ。

代償はメモリではなく時間である: このカードで 1024² の端から端までの約 2.6 倍で、2048² のピーク
（19.6 GB）はファイル合計の床が既に買う 22,000 の段の内側にある。T4 では走らせていない。P3 の
そこでの時間から、あのカードでの 2K は良くて 1 枚 15 分になる。

### 未解決 4 — RGBA: 頼まれない限り落とし、受け手は確かめた

**エンジンより後ろで、透過で壊れるものは無い。** props の読み手は PNG のチャンクを復号せずに歩き
色型を見ない。サムネイル（`fs_thumb.go`）は不透明な絵にだけ JPEG を選び、それ以外はアルファ付きの
PNG のままにし、黒に合成することは無い。Console のカードは透過部分にパネルの色を、ライトボックスは
市松を見せる。JPEG に平らにする canvas は無い。どの `LoadImage` も IMAGE 出力しか配線しないので、
参照として送り返された RGBA の絵が誤ってマスクになることも無い。

**代償はほぼ不透明な写真だった。** 255 未満の画素が 1 つあれば `Opaque()` は偽になるので、この族の
普通の絵のサムネイルはすべて PNG（JPEG の 5〜8 倍）になり、ライトボックスは縮小版でなく 1〜2 MB の
原本を配り、背景に重ねると最大 1.2 % 透けていた。

**判断（利用者による）: 透過を頼まれなければ不透明にする。** 行の新しい欄 `Alpha` が、復号が
アルファチャンネルを持つ唯一の族を宣言する。その族では、要求が `background=transparent` と言わない
限り、テンプレートが復号と保存の間に `SplitImageWithAlpha`（`image[..., :3]`・3 チャンネルには何も
しない）を挟み、その呼び出し側に `comfyWarnings` が「opaque produced」と言うのもやめた。Agent で
再エンコードせずグラフの中で落とすのは、SaveImage が書く `prompt` チャンクを保つためである。
エンジンで確かめた: 落とすグラフは `RGB` の PNG をチャンク付きで保存し、同じ要求の RGBA 出力の
RGB チャンネルと画素まで一致した。

⚠️ アルファ 0 の下にあるのは白ではない: P2 の透過背景の絵はそこに平らな紫（約 163,58,206）を
持っている。プロンプトでは透過を頼み `background` では頼まない呼び出し側は、今後その紫を背景と
して受け取る。`generate_image` には `background` 引数があるが、**Console の生成フォームには無い**
ので、ペインからはこの族は不透明だけになった（未解決 6）。

**途中で見つけたもの: props がこの族のプロンプトを失っていた。** `TextEncodeQwenImage21` は 1 つの
ノードから両方の条件付けを出し、プロンプトは `prompt`、ネガティブは `negative_prompt` にある。props の
読み手はクラスで欄を選んでいたので、この族の絵は生成でも編集でも**プロンプト無し**で返っていた
（開発配備自身の出力で読んだ）。欄はサンプラーの辺が指す出力スロットで選ぶようにし、参照画像は
見つけた最初の `LoadImage` ではなく `img1..imgN` を順に読むようにした。

### 未解決 5 — プロンプト強化モデル: 配線できるが、しない

Comfy-Org のミラーの README は `qwen3.5_9b_…_pe_{t2i,i2i}` を「TextGenerate ノードで使う」と言い、
v0.37.0 ではコアのノードだけでその通りになる: Qwen3.5 の state dict は CLIPLoader の type に
関わらず形で検出され（`comfy/sd.py` の `QWEN35_*` 分岐）、9B の設定は `lm_head` を持ち、
`TextGenerate` → `RegexReplace`（`<think>` ブロックを落とす）→ `JsonExtractString`
（`rewritten_prompt`）→ エンコードの `prompt` は /prompt が受け付けるグラフである。上流のモデル
カード（`Qwen/Qwen-Image-2.1-PE-T2I` / `-I2I`）は `system_prompt.txt`（10 KB と 18 KB）を同梱し、
思考ブロックの後に JSON オブジェクトで答える。

配線しない。理由は 4 つで、どれも走行ではなくファイルから測った:

- **メモリ。** 強化モデルは int8 で 1 本 9.47 GB、この行が既に持つ 16.5 GB の横に並ぶ。ComfyUI は
  両者の間で退避できるが、ファイル合計の床は 16,482 から約 25,500 MiB に上がり、この族が今日走る
  22,000 の段を超える。
- **時間。** 上流の例は思考を有効にして `max_new_tokens=24000`。絵ごとに思考する 9B モデルを前に
  置けば、画像のために買ったカードで数分のテキスト生成になる。
- **枠を決めてしまう。** T2I の答えは `wh_ratio` を持つ——強化モデルがアスペクト比を選ぶ——ので、
  呼び出し側が名乗った寸法と矛盾する。I2I の答えの `ratio_follow` は編集での同じ問いである。
- **黙って失敗する。** `JsonExtractString` は解析に失敗すると空文字を返すので、きれいな JSON 以外を
  答えた強化モデルは、エラーも警告も無く**空のプロンプト**から絵をサンプリングさせる。

しかもこの経路の前には既にもっと良い強化役がいる: `generate_image` を呼ぶのは、それ自体が言語
モデルであるエージェントである。取り上げるなら、GPU に 2 つ目のモデルを置くより、上流のシステム
プロンプトをその呼び出し側に渡す（この族の知識の層）ほうが安い形である。

## 影響

- 語彙は 11 族になり、その 4 つの写し（Agent の定数・CP の `engineComfyFamilies`・Console の
  `wire.ts`・Console の `families.ts`）すべてに新しい語が入った。このうち 3 つは
  `engine_catalog_test.go` が互いに固定しているが、**`families.ts` は対象外**で、4 つ目の写しは
  この ADR だけが保つ（ADR 0072 からの継続注記）。
- `comfyFamilyRow` の欄が 3 つ増えた。表に足してゼロ値のままにした族はエラーにならず寛容な既定
  （op 3 つ・参照 1 枚・`strength` を出す）を得る。これは `TrialSteps` が既に持っていた形で、
  守り方も同じ——族を列挙する試験ではなく、**語彙全体を舐める**試験で守る。
- その後の対応で `comfyFamilyRow` に 4 つ目の欄 `Alpha` が増え、この族だけが宣言する（試験が
  固定している）。後から足す族の復号もアルファを書くなら、宣言した**うえで**テンプレートで落とさ
  ないと、すべての呼び出し側に余計なアルファが戻る。
- エンジン画像のピンが、カタログの語彙に入った族にとって効くものになった。P0 が着地するまで、
  運用者は `qwen-image-2.1` の行を登録して有効化でき、どの画面もその行を「揃っている」と言う。
  落ちるのは `/prompt` で、ノード種別のエラーとして声を出して落ちる。
- `engineCommercialUse` はライセンス名に `qwen-research` を持つ行すべてに `no` と答える。既存の
  Qwen-Image-Edit の行にも届くが、あちらは Apache 2.0 なので影響は無い。今後 research ライセンス
  で公開される Qwen のモデルは、もう 1 回の変更無しで分類される。
