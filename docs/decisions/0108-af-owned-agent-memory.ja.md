## 背景

エージェントが作業中に学んだことは、学んだ CLI のメモリにしか残らない。[0022](0022-agent-memory-management.ja.md)
が当時の CLI を調べた時点（その Context）で、ローカルにメモリを持つのは 2 つだった：claude の
auto-memory（既定でオン）と codex の memories（既定でオフ）。opencode・agy・kiro には無く、copilot は
Copilot Memory をサーバー側に持ち、cursor の旧 Memories は削除されていた。AF のメモリルートは今もこの
2 つである（`memoryx/memory_roots.go`）。lcpp と muse はその調査の後に来た：lcpp 自前のシステムプロンプトには
メモリ層が無く（`harness/systemprompt.go`）、muse がネイティブのメモリを持つかは確かめていない。途中で
種別を替える、別の種別へ引き継ぐ、別の種別の子を起動する、のいずれでも、最初のエージェントが記録した
ものは失われる。

すぐ思いつく解 — claude のメモリを他の種別に渡す — は、1 ベンダーの非公開の形式と置き場をフリートの
正本にしてしまう。形式は Claude Code のどの版でも変わりうるし、中身は claude 向けに書かれている
（「claude の TUI は X をする」）し、書けるのは claude だけである。

設計を形づくる事実が 2 つある。どちらも 2026-10-03 に 1 つの Workspace で、このリポジトリのプロジェクト
について実測した：claude のメモリ索引（`MEMORY.md`）は **25,399 バイト**、ディレクトリは **469 ファイル・
2.7 MB**。これを全セッションの指示に押し込むのはターンごとの費用として誰も受け入れない。必要時に
取りに行く形でなければならない。

仕組みの部品は AF に既にある。[0042](0042-user-instructions.ja.md) は AF が持つ 1 本の文章を各種別の
**ユーザー全体の**指示層に配る — 種別ごとに 1 ファイルで、プロジェクトやセッションごとではない
（`agent_instructions.go`）— そして cursor にはそれが書けるローカルのユーザー層が無い（決定 2）。
[0022](0022-agent-memory-management.ja.md) はメモリのディレクトリを bare git リポジトリで版管理し、巻き戻し・
bundle での移送・輸出時の秘密検査（`memoryx/memory_secrets.go`）を持つ。af MCP はすべてのエージェント種別に
届く：7 つの CLI 種別へは `mcpreg` で、muse へは専用の配線で、lcpp へはプロセス内で。shell と ssm は
エージェントではない。欠けているのは、AF が持ちエージェントが書いてよい置き場と、1 つのセッションが
書いたものを全種別が読むときにも安全な書き込み経路である。

## 決定

1. **AF はユーザー指示とは別にメモリの置き場を持つ。** ユーザー指示は人が書き、正本である。
   [0042](0042-user-instructions.ja.md) 決定 8 はエージェントがそれを書くことを禁じており、それは変えない。
   AF メモリはエージェントが書き、参考情報である。別のファイルに置き、別のブロックとして配り、ポリシー
   文がどちらがどちらかをエージェントに伝える。統合すると 0042 決定 8 が無効になる。
2. **範囲はユーザー × Workspace × プロジェクトで、プロジェクト ID は AF が自分で定める。** Git の作業コピー
   なら、プロジェクトはその作業コピーが属するメインのクローン（`gitx` が解決する `git-common-dir` の親）
   であり、worktree は親とメモリを共有する。claude の*会話*ディレクトリの命名は流用しない：cwd ごとで、
   単射でなく、worktree ごとに別の slug になる（`agents/claude/project_dir.go`）。Git でない作業コピー
   （SVN・ローカルフォルダ。どちらも正式対象、`guide/ref/repos.md`）は、AF が登録したルートを鍵とする
   独立したプロジェクトである。作業コピーの無いセッションはユーザー全体の範囲だけを見る。別のパスへの
   再クローンは、メンバーが 2 つを統合するまで別プロジェクトである（未決事項 5）。v1 ではメモリは
   Workspace をまたがない（決定 10）。
3. **形式は 1 メモリ 1 Markdown ファイル＋frontmatter**（`name`・`description`・`type` に加え、AF の
   `revision`・`author_kind`・`author_session`・`created`・`updated`、一部の種別にだけ当てはまるメモリには
   任意の `kinds` リスト、取り込んだものには `source` / `source_hash`）。AF が確かめられない書き手は
   不明と記録し、推測しない。claude のメモリが既に使う形なので取り込みはコピー＋項目追加で済み、人が
   ツール無しで読める。
4. **全種別が af MCP ツールで読み書きする** — `memory_index`・`memory_search`・`memory_read`・
   `memory_save`（作成・更新）・`memory_forget`。更新と忘却は元にした `revision` を持ち、古ければ断って
   エージェントに読み直し・再提案させる。Markdown は機械的にはマージしないからである
   （[0022](0022-agent-memory-management.ja.md) の 3-way merge について）。変更の公開、0022 の履歴への
   コミット、索引の更新はプロジェクトごとに 1 つの手順で行い、公開された変更 1 つが書き手つきの
   1 コミットになる。
5. **配るのは固定の案内で、メモリではない。** 0042 の配布器が書くのはユーザー全体のファイルなので、
   そこにプロジェクト別の一覧を置くと、最後に書いたプロジェクトで上書きされるか、全プロジェクトが全
   セッションに混ざる。そこで配るブロックは、ツールがあることと呼ぶ時機 — 作業の始めに `memory_index`、
   何かを導き直す前に `memory_search` — だけを、専用のバイト上限の下で述べる（0042 決定 7 と同じ理由）。
   プロジェクトの項目は、呼び出したセッションの範囲で `memory_index` が返す。システムプロンプトを
   セッションごとに組む lcpp は直接注入してよい。cursor には同じ案内をツールの説明で渡す。
6. **claude 自身の auto-memory：今は 1 回だけの種まき、いずれメモリは 1 つ。**
   - 段 1：メンバーがプロジェクトごとに claude の既存メモリを 1 回だけ、Console の明示的な操作で
     取り込む。秘密検査（決定 9）を通し、メンバーが一括または 1 件ずつ承認する提案として入り
     （決定 8）、`source` / `source_hash` を記録し、書き手は不明とする。継続同期はしない：契機のたびの
     claude → AF は、AF で忘れたメモリを復活させ、AF での編集を claude の古い文章で上書きし、却下した
     提案を再提出させる。
   - 段 2（実測してから決める）：claude の auto-memory を切り（`autoMemoryEnabled` /
     `CLAUDE_CODE_DISABLE_AUTO_MEMORY`）、他の種別と同じく MCP ツールを使わせる。claude のネイティブの
     書き手を置き場に向ける（`autoMemoryDirectory`）のは、claude がそこに書いたものが提案として扱われる
     — 書いただけで公開されない — 場合**に限り**認める。どちらの名前も 2.1.288 のバイナリから得たもので、
     どちらも実測していない。
7. **メモリは証拠であって命令ではない。** 読み出しツールの説明にそう書き、メモリに出てくるファイル・
   関数・フラグは頼る前に実在を確かめるよう書く。メモリはユーザー指示やフリートポリシーに優先しない。
8. **すべての書き込み経路は提案を作り、公開するのはメンバーだけ。** 保存・更新・忘却・取り込み・復元の
   どれもが、本文を変えられない提案を作る。保留中の提案は、書いた本人を含むすべてのセッションの
   `memory_index`・`memory_search`・`memory_read` から見えない。承認 — とプロジェクトの直接書き込みへの
   切り替え — は Console の REST にだけあり、MCP ツールにはしない。理由は 0042 決定 8 と同じ。承認時に
   revision を確かめ直し、元が動いた提案は古いものとして書き手に戻す。これが無ければ、1 つのセッションが
   読んだ 1 つの悪意あるページが全種別に配られる。承認の経路は #1559 の自動レビューが必要とするものと
   同じで、1 度だけ作る。
9. **秘密は保存される前に止める。** 保存と取り込みはすべて、何かを永続化する前に（提案も含め）0022 の
   規則（`memory_secrets.go`）で検査する。検出は既定で止め、メンバーが Console で明示的に了承したときだけ
   通す。値そのものは返さず記録もしない — 今の輸出時と同じく、規則名・パス・行・マスクした手掛かりだけ。
   既に在るメモリは、読み出しや索引で初めて公開する前に検査する。`memory_forget` はメモリを公開対象から
   外すが履歴からは消さないので、秘密を履歴から消し去るのはメンバーだけが行う別の操作とする
   （未決事項 3）。
10. **v1 は Workspace の中に置く。** 置き場は claude 専用マウントの `af-memory.git` の隣
    （`memoryx/memory_repo.go`）で、stop/start・recreate・「clean home」を越えて残るが、Workspace の削除は
    越えない。メンバーの複数の Workspace で CP を通してメモリを共有するのは別の道筋で、0022 が満たせな
    かった条件がそのまま要る：所有者だけの ACL（0022：内部 git プロバイダはテナントの全メンバーに読ませる）、
    正本となる 1 つの履歴、Workspace が止まっている間の振る舞い、メンバーが抜けたときの削除。

## 却下した案

- **claude のメモリを正本として他の種別と共有する。** 1 ベンダーの非公開の形式と置き場がフリートのものに
  なり、書けるのは claude だけで、中身が claude 固有である。
- **置き場全体を全種別の指示に配る。** 索引だけで 25 KB、全セッション・全ターン。
- **プロジェクト別の索引を 0042 の配布器で配る。** そのファイルは種別ごとにユーザー全体なので、同時に
  開いた 2 つのプロジェクトが互いの項目を読む（決定 5）。
- **claude → AF の継続同期。** 削除の印と優先順位が無いと、忘れたメモリや却下したメモリが復活する。
  1 回だけの種まきならこの問題が起きない（決定 6）。
- **claude のネイティブの書き手に置き場へ公開させる。** 決定 8 を迂回する。
- **外部のメモリサービス（例：Honcho）。** 会話が Workspace の外に出て、サービス側が自前の LLM で推論し、
  自前運用には Workspace に無い Docker が要る。メンバー自身が Settings → MCP で選ぶ選択肢のまま残す。
- **代わりにエージェントにユーザー指示を書かせる。** 0042 決定 8 が無効になる。
- **種別ごとの置き場を互いに同期する。** N 個の形式・N 人の書き手と、編集のたびの衝突。置き場 1 つ・
  書き込み経路 1 つの方が単純。
- **v1 の置き場を CP の Postgres にする。** 0022 が持っていなかった所有者だけの ACL と、Workspace 停止中の
  答えが要る（決定 10）。

## 結果

- Workspace の中では、種別を替える・引き継ぐ・別種別の子を起動する、のいずれでも知識が残る。
- ローカルに自前のメモリを持たない種別がメモリを得る。muse については、ネイティブのメモリと重複するかが
  まだ確かめられていない（未決事項 6）。
- すべてのメモリに書き手と履歴があり、悪い教訓を見つけて巻き戻せる。
- 新しい故障の型：汚染されたメモリが全種別に届く。決定 8 と 9 がその対策で、書き込みツールと同時に出す
  （後回しにしない）。
- プロジェクトを直接書き込みに切り替えるまで、メンバーに承認の手間がかかる。#1559 のレビューはそれを
  減らすためのものである。
- 決定 6 の段 2 が決まるまで claude には 2 つのメモリが並存し、その間 claude は両方の索引の費用を払う。

## 未決事項（測ってから決める）

1. 出荷版の Claude Code で `autoMemoryDirectory` と `CLAUDE_CODE_DISABLE_AUTO_MEMORY` が実際に何をするか：
   ディレクトリ設定で索引とファイルが移るか、claude がそこから索引を読み込み続けるか、そこへの書き込みを
   提案として留められるか。
2. `memory_index` の応答の大きさと項目の並べ方（新しさ・`kinds`）、並存期間の費用を実プロジェクトで測る。
3. 秘密を履歴から消し去る方法：1 つのメモリについて 0022 の履歴を書き換えることと、それが輸出済みの
   bundle に及ぼすこと。
4. codex の `external_agent_memory_import`（[0022](0022-agent-memory-management.ja.md) 決定 6）が、MCP
   ツールと並ぶ codex ネイティブの経路を持つ価値を生むか — ネイティブの書き手は公開しないという決定 8 の
   規則の下で。
5. 時間を通じたプロジェクトの同一性：改名・再クローンしたリポジトリと、メンバーが 2 つのプロジェクト ID を
   統合する方法。
6. muse がネイティブのメモリを持つか、持つならこのメモリとどう並存するか。
7. Workspace をまたぐ道筋（決定 10）。
