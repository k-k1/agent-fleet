## 背景

「前はこれをどう解いたか」に、今の Agent Fleet は答えられない。あるのはファイル名検索と、ミラーでの
今のセッション自身のプロンプトの逆順検索だけで、セッションをまたいで「何を話したか」を探す手段は無い。
しかも会話の置き場と形式は CLI ごとに違う（claude の jsonl、codex の rollout、opencode の SQLite、
cursor・kiro・copilot・agy のファイル、AF 自前の muse と lcpp の置き場 — `docs/build/04-agent.ja.md` §4.7）。

設計を形づくる事実が 3 つある。

- **正規化はもうある。** 転写を持つ種別はすべて、ミラーのために `transcript.Turn` へ読み替えられて
  いる。`sessionx.UsageTurns` は使用量の台帳のために、claude を含むどの種別でも会話の全体を返す。
- **転写は Workspace の外へ出ない**（`docs/build/06-data.ja.md` §6.2）。CP が持つのはセッションの
  メタデータだけである。
- **SQLite FTS5 はもうリンクされている。** Agent は `modernc.org/sqlite`（SQLite 3.53.2）に依存しており、
  その FTS5 には unicode61 と trigram のトークナイザーがある。実測すると、trigram の表は
  「前回の認証エラーを直した」から「認証」を 1 行も返さない。trigram は 3 文字未満の問い合わせに
  一致できないからで、日本語では 2 文字の語がふつうである。

問題の大きさ（上の Workspace での実測）：セッションのメタ 739 件、うち転写を持つもの 738 件、
索引対象のターン 17,696 件、会話本文 15.3 MB。

## 決定

1. **索引は Workspace 内に、キャッシュとして置く。** SQLite のファイル 1 つで、場所は
   `~/.local/state/agent-fleet/session-search/index.db`（`0600`。ファイルブラウザーが隠す Agent の
   状態ディレクトリの下）。その場に残る転写から作るものなので、消しても常に安全である。スキーマが
   変われば捨て、次のパスが作り直す。転写と同じく停止と recreate では残る。Agent の状態ディレクトリが
   失われるところ（clean home、ボリュームの喪失）では失われ、作り直される。
2. **読み手は全種別で 1 つ。** パスは `sessionx.UsageTurns(meta)` を読む。使用量の台帳が畳むのと同じ
   会話なので、パーサーと歩調を合わせる種別ごとの索引器は要らない。転写の無いセッション（shell・ssm）
   は飛ばす。空の読み取りは、索引済みの行を決して消さない。停止した Managed の cursor セッションは、
   会話があったのに空として読めるからである。行を消すのはごみ箱だけである（決定 7）。
3. **索引に入れるのは会話だけ。** 残すのは本文、計画、尋ねた質問とその答えである。外すのは次のもの：
   - ツールの呼び出しと出力。転写の大半を占め、中身はほとんどがファイルの内容とコマンドの出力で、
     秘密がいちばん紛れ込みやすい。
   - 思考、サブエージェントのサイドチェーン、委任のプロンプト。エージェントが自分自身や助手に話して
     いるもので、人に向けたものではない。
   - claude の圧縮要約。索引済みのターンの言い直しである。

   1 ターンは 32 KiB で打ち切る。貼り付けたログが索引を占めないようにするためである。
4. **日本語は Go で bigram に切ってから unicode61 に渡す。** 漢字・かな・ハングルの連なり（語の中に
   現れる「ー」「々」を含む）は重なり合う bigram に、1 文字だけの連なりは unigram にする。全角・半角は
   先に幅をそろえる。問い合わせも同じ関数を通す。空白で区切った語の 1 つずつを、そのトークン列の
   引用付きフレーズにし、すべての語が現れることを求める。CJK 1 文字だけの語は前方一致で問い合わせ、
   その文字で始まるすべての bigram に一致させる。利用者の入力が引用なしで FTS5 の構文に届くことは無い。
5. **差分で取り込み、専用のタイマーは持たない。** `usage_fold.go` にならい、パスは検索が来たときだけ、
   1 分に 1 回まで、裏で走る。検索はその時点の索引から答え、`indexing: true` と `indexed`/`total` の
   件数を添える。パスはセッションを 1 つずつ処理する。メモリに載る転写は一度に 1 つで、検索が待つのは
   長くても 1 セッション分の書き込みである。
   - 前回索引したときと同じ `StoppedAt` で止まっているセッションは読み直さない。再開は `StoppedAt` を
     消し、次の停止が新しい値を押すので、この判定は正確である。
   - 伸びた転写は、索引済みの最後の行（まだストリーミング中だったかもしれない）とそれ以降だけを
     書き直す。それ以外（短くなった転写、claude の sid が隣の jsonl へ移った場合など）はそのセッションの
     行をまるごと置き換える。

   739 セッションの Workspace での実測：

   | 測定項目 | 結果 |
   |---|---|
   | 初回のパス | 83 秒 |
   | 初回のパス中の Go ヒープの最大 | 210 MB |
   | 2 回目のパス | 8 秒（読み直すのは停止印の無いセッションだけ） |
   | 索引ファイル | 31.7 MB |
   | 検索 1 回 | 40〜110 ms |
6. **全種別に af MCP で配る。セッションからの利用はスイッチで制御し、既定でオンにする。**
   - ツールは `search_sessions` で、1 つのツールに 2 つの使い方がある。`query` を渡すとヒット
     （セッション・`idx`・抜粋）を返す。`session` と `idx` を渡すと、ヒットの前後の索引済みターンを
     返す。行き先は Agent の `GET /session-search` と `GET /session-search/turns` である。
   - スイッチは ui-pref の `sessionSearch` で、起動引数 `--session-search` がそれを運ぶ。切り替えると、
     他のスイッチと同じく各 CLI の MCP 設定を書き直す。
   - Agent は、セッションの帰属（`from`）が付いた呼び出しのたびにスイッチを確かめ直す。`from` は
     ピアの覗き見と同じく、af サーバーが自分の結び付きから埋める。そうした呼び出しは問い合わせの本文を
     含めずにログへ残す。セッションが何を探したか自体が機微でありうるからである。
   - Console 自身の検索はこのスイッチの対象外である。

   ピアメッセージ（0041）が既定オフで、他セッションの生の出力は親だけが読める（0073 決定 4）のに、
   これを既定オンにする理由：
   - あれらの規則が守っているのは、他セッションへの書き込みと操縦である。毒された指示を広げるのは
     そちらで、このツールは読むだけである。
   - 読む先はこの利用者自身の転写で、セッションのシェルは同じ uid としてそれをもう開ける。

   届く範囲はこの Workspace のすべてのセッションで、動作中・停止済み・アーカイブ済みの別を問わず、
   呼び出し元自身も含む。他の Workspace には決して届かない。
7. **行はセッションのメタと同じだけ生きる。**
   - セッションをごみ箱へ移すと、メタを消した直後に行も消す。以後はごみ箱の gz の束が唯一の写しで、
     復元するとメタが戻り、次のパスが索引し直す。
   - どの回答も現在のメタと突き合わせるので、前回のパスの後に削除されたセッションが見つかることは
     無い。パスもメタの無い行を刈り取る。
   - アーカイブしたセッションは検索に残る。アーカイブは元に戻せる（0097）し、昔の作業を見つけるのが
     この検索の目的だからである。
8. **順位付け。** FTS5 の bm25 で並べ、2 つの調整を加える：
   - 予約実行のターン（`origin=schedule`）は重みを半分にする。同じプロンプトを繰り返すので、人が
     問題に取り組んだ会話を押し出してしまう。
   - 新しさの係数は 180 日ごとに重みを半分にする。同点を分けるためのもので、絞り込みではない。

   1 セッションから返すヒットは最大 3 件（変更可）である。長い会話 1 本が、その話題に触れた他の
   セッションを隠さないようにするためである。

## 却下した案

- **CP の Postgres（`tsvector`）。** 会話本文を Workspace の外へ出し、`06-data.ja.md` §6.2 に反する。
  SQLite の方言（単一 CP の構成）でも作る必要があり、Postgres には拡張なしの日本語パーサーが無い。
  Workspace が止まっている間は使えなくもなる。
- **trigram トークナイザー。** 2 文字の問い合わせをすべて取りこぼすことを実測した。
- **ツール出力を索引に入れる。** 索引も秘密を索引してしまう確率も膨らむのに、ヒットの多くは
  リポジトリがすでに持っているファイルの内容である。
- **ヒットを LLM で要約する。** 検索のたびにモデル呼び出しの費用がかかる。呼び出し元はもともと
  ターンを読める LLM である。#1558 のきっかけになった hermes も要約をやめた。
- **各 CLI の置き場に対する種別ごとの検索。** N 個の形式に歩調を合わせる N 個の実装になり、答えを
  横断して並べる共通の順位も無い。
- **常駐のタイマーやファイル監視。** ホストは共有でメモリが限られており、走査は誰も探していない転写を
  読み直すことになる。
- **ピアメッセージのスイッチに相乗りする。** 「セッション同士が書き込み合ってよい」という意味の
  スイッチに読み取り専用の機能が混ざり、ほとんどのフリートで検索がオフのままになる。
- **既定でオフ。** ほとんどのセッションに見えないツールは使われない。書き込みの経路が求める明示的な
  オプトインを、この読み取りが必要としない理由は決定 6 に書いた。

## 結果

- どのセッションも、別の種別も含めて前のセッションが何を結論したかを、利用者の中継なしに尋ねられる。
- Workspace は会話本文の 2 つ目の写しを持つ。大きさは本文とほぼ同程度である（ここでは本文 15.3 MB に
  対して 31.7 MB）。置き場は転写と同じストレージ、同じ uid で、寿命はメタに従う（決定 7）。
- 更新や clean home の後の最初の検索は、初回のパスが走っている間、作りかけの索引から答える。回答は
  そのことを示す（`indexing`、`indexed` < `total`）。
- エージェントにとって検索結果は過去の文脈であって指示ではない。ヒットが挙げるファイル・コマンド・
  フラグは頼る前に確かめるよう、ツールの説明に書いてある。

## 追記（2026-10-08）— ミラーの窓より古いヒット（#1663）

ジャンプはスクロールマークに乗っており、マークはマウント済みのターンしか復元できない。ミラーは
末尾 400 位置しかマウントしない。そこで窓より古いヒットは、先に古い履歴を遡って読み込む
（`reachTurn.ts`）。ターンの idx はページング用カーソル（`firstLine`）と常に同じ単位とは限らない:
claude はどちらも jsonl の行番号だが、ストア型のエージェントは配列位置でページングしつつ、
ターンは元イベントの idx を持つ。そのため「到達」は実際に保持している最古の idx で判定し、
カーソルは頁の取得にだけ使う（頁の大きさは idx の差で決める。claude では正確、他では多めの見積もり）。
Agent の API は変えない。上限付き: 1 回のジャンプで idx 8,000 位置・4 リクエストまで、それを超える
距離はリクエストせずに断り、末尾に黙って着地する代わりに通知を出す。読み手と新しいジャンプ・
セッション切替には譲る（入力、またはビューポート下の内容が動いたこと＝スクロールバーのドラッグも含む）。
