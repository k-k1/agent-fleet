## 背景

Console で画像を見る手段は 2 つしかない。**ファイルペインで 1 枚開く**
（`viewer/ImageView.tsx`。ホイールとピンチで拡大・ドラッグで移動）か、**ミラーの転写に出た
共有ファイルカードを拡大する**（`mirror/transcript/blocks.tsx` の `FileCard` →
`mirror/parts/ImageLightbox.tsx`）。どちらも「1 枚」が単位で、**フォルダに何が入っているかを
一覧する面が無い**。

これがいちばん効くのは画像生成（ADR 0069）である。`generate_image` の出力は
`~/.cache/agent-fleet/generated/<sid>/image-<unixnano>-<n>.png` に溜まる
（`internal/imagegen/store.go`・保持 30 日・1 枚 2〜3MB）。

- フォルダ名は**セッション UUID** なので、ファイルツリーからは事実上たどれない。
- 転写のカードは折りたたみの中に隠れることがある（`.cache` の下は閲覧可なので開けはするが、
  「生成画像が出ない」と読まれた既知の弱点）。
- 生成は 1 回で複数枚・何度も回すのが普通で、**見比べる場所**がどこにも無い。

一方で土台はほぼ揃っている。

- **サムネイルの口が既にある**: `GET api/fs/download?path=…&thumb=<最長辺>`（`fs_thumb.go`）。
  実測で 1024x1536 / 3.2MB の PNG が 341x512 / 約 60KB になり、`Cache-Control: private, max-age=60`
  ＋ `Last-Modified` なので 2 回目以降は 304。ディスクキャッシュ付き・同時デコードは 2 本に制限
  （共有ホストはメモリが細い）。**引数は助言的**で、デコーダの無い形式や小さすぎる画像は
  原本が返る——呼ぶ側に能力判定が要らない。
- **拡大の部品がある**: `ImageView` は zoom ハンドルを外へ出しており、`ImageLightbox` が
  ボタン列を自前で描いている。
- **カードの作法がある**: 「本体＝拡大／角のボタン＝ペインで開く」。見るだけでペインを
  消費しないための分け方で、既に利用者が学んでいる。
- **ペイン種別を足す定型がある**（ADR 0078 で 8 か所を踏んだ）。

足りないのは**フォルダ単位の面**と、**そこへ行く導線**だけである。

## 決定

### 決定 1 — 新しいペイン種別 `gallery` として作る（ファイルペインの面にしない）

```ts
| { kind: "gallery"; galleryPath: string; sort?: "new" | "name"; galleryFocus?: string; gallerySession?: string }
```

- **0049 決定 4 / 0046 との関係。** 両者の結論は「**載せられる既存のペインがあるなら**面を 1 つ
  増やす方が安い」である。ここには載せる先が無い。`kind:"file"` の `filePath` は**ファイル 1 本**の
  契約で、その上に編集バッファ・差分・外部変更追従・朗読・PDF/Office 分岐がぶら下がっている
  （`fileMode.ts`）。ディレクトリを入れるとその全部が嘘になる。SCM ペインの主語はリポジトリで、
  やはりフォルダではない。**`galleryPath` は PaneContent で初めてディレクトリを指すフィールド**であり、
  それが新種別の理由そのものである。
- ペインにすれば分割・タブ・ポップアウト・レイアウト永続化・スマホの 1 ペイン表示が
  **すべて既存の仕組みで付く**。ミラーと並べて「生成しながら見る」も自然に出る。
  （面内検索は**付かない**。Console に find-in-pane の仕組みは無く、`Ctrl+F` はブラウザ素の検索で、
  カードに出ているファイル名しか当たらない。）
- 種別追加の定型 8 か所（union・保存形式の検証・同一判定・描画 switch・タイトル・ミニマップ略号・
  ポップアウト可否・i18n）を全部踏む。**`migrate.ts` の検証を忘れると再読み込みで空ターミナルに
  化ける**。`galleryPath` は保存値＝信用できない入力なので、文字列・先頭 `/` 無し・`..` 無し・
  制御文字無し・長さ上限で弾く（`browser` 種別の `path` 検証と同じ厳しさ）。
- `sort` は React state でなく**ペインの内容に持つ**。タブ切替でこのビューは unmount されるので、
  state に置くと切替のたびに戻って壊れて見える（0078 決定 1 と同じ）。既定は `"new"`。
- `gallerySession` に入れるのは**セッションのスラグ（`name`）であって表示名ではない**。決定 8 の
  導線から開いたときだけ入り、描画側がその名前から今のセッションを引き直して
  「生成した画像 — <セッション表示名>」を出す（フォルダ名が UUID なので、タイトルにパスの末尾を
  出しても読めない）。無ければタイトルはフォルダ名。**表示名を焼き込んではいけない**——
  改名すると古い題が残るうえ、`migrate.ts` の検証はセッション名の字種
  （`ValidName` と同じ `^[A-Za-z0-9_-]{1,40}$`）なので、**日本語の題は再読み込みで丸ごと消える**
  （実装中に実際に踏んだ）。
- 同一判定（`sameTarget`）は `galleryPath` で行う。`sort`・`galleryFocus`・`gallerySession` は
  同じ面の状態なので見ない——同じフォルダを 2 度開いても 2 枚にならない。
- **コマンド表（0017）には登録しない**（P0）。0078 は `open.sessions`（`g s`）を
  `features/keys/commands.ts` に足せたが、あれは引数の無い面だった。ギャラリーはフォルダが要り、
  グローバルなキーには渡す当てが無い。開くのは常に文脈（右クリック・ヘッダ・セッション）である。
  「直前に開いたギャラリー」のような既定の的が欲しくなったら P1 で足す。

### 決定 2 — 一覧は既存の `api/fs/tree` で取る。足すのは `fsEntry` の `mtime` 1 つだけ

- 新しい一覧エンドポイントは作らない。フォルダ 1 階層の `{name, type, size}` は既にこの口が返す。
- **`mtime` を足す**（`workspace/agent/fs.go` の `fsEntry`）。「新しい順」と「3 分前」はこれ無しには
  書けない。生成画像はファイル名に `unixnano` が入るので名前順＝時刻順だが、それは**生成画像だけの
  偶然**で、スクリーンショットの入ったフォルダには効かない。
  - 形は **unix 秒の整数 `mtime`**（`omitempty`）。`Size` を埋めている `e.Info()` が
    `ModTime()` も返すので、**ディレクトリにも同じ 1 回で入る**（今は `Size` が file のときだけ
    埋まっている——ここを踏襲して file だけにしないこと。フォルダを新しい順に並べたくなるのは次の一手）。
  - **古い Agent は `mtime` を返さない。** Agent は Console とは別に配られる（native / pin）ので、
    これは実際に起きる。**無いときは名前順に落として相対時刻を出さない**——`fs_thumb.go` の
    「引数は助言的」と同じ作法で、能力判定も版比較もしない。
- ツリー側への影響は無い: 一覧を読む側は `Entry` を**各自で局所宣言している**
  （`features/project/ProjectFiles.tsx` ほか。共有の型は無い）ので、フィールドが増えても誰も壊れない。
  `ProjectFiles` の `sameEntries` は name/type だけを比べるので、mtime が動いても再描画は増えない。
- **サブフォルダの再帰は P0 に入れない**（決定 9・P1）。`api/fs/search` で代用してはいけない——
  `.gitignore` を尊重するので生成物やビルド出力が**黙って消え**、`q` が必須で「全部」を頼めない。
- 巨大フォルダ対策は客側の打ち切り（決定 4）。`api/fs/tree` に上限が無いのは既存の性質であり、
  本 ADR では変えない（変えるならツリーごと変える話になる）。

### 決定 3 — 画像かどうかは `imageFormat()` 1 か所で決める

Console の `lib/filemeta.ts` の `IMAGE_EXT` が唯一の判定（Agent 側の `imageContentType` が
対になっており、コメントで互いを指している）。ギャラリーが独自の拡張子表を持つと、
**ファイルペインでは画像なのにギャラリーには出ない**という食い違いが必ず出る。
サムネイル可能かどうかは見ない——`thumb` は助言的で、webp/avif/bmp/svg は原本が返って
ブラウザが描く。

### 決定 4 — サムネイルは `thumb=512`。ミラーと同じ数字にそろえ、遅延読み込みと打ち切りを付ける

- **512 はミラーの共有ファイルカードと同じ値**。サムネイルのディスクキャッシュは鍵に最長辺を
  含むので、ギャラリーだけ 256 を頼むと同じ画像を**2 回デコードする**（費用の本体はデコードで、
  約 100ms ＋ 幅×高さ×4 バイト）。小さく見せたい分は CSS で縮める。
- `loading="lazy"`＋`decoding="async"`。初期は**新しい順に 300 枚で打ち切り**、残りは「さらに表示」。
  上限が無いと、たまたま画像の多いフォルダを開いた 1 回で 300 枚 × デコード 2 並列が待ち行列になる。
  待たせる要素はデコードだけではない: `max-age=60` を過ぎた再マウントは**カードの数だけ条件付き
  リクエスト**になり、ブラウザの同一ホスト 6 本の制限に並ぶ（304 でも往復は往復である。未解決 1）。
- 原本を取るのは拡大したときだけ（ライトボックス）。カードは常に縮小版を見る。
  - 🔴 **P1 で足りないと分かった（2026-09-14）**: その「拡大したとき」が待たされる。原本はここでは
    1 枚およそ 1MB で、届くまで枠が真っ白だった。**カードの縮小版をそのまま代役として出し**、
    原本が裏で読めたら同じ `<img>` の `src` を差し替える（拡大・移動の状態はそのまま）。
    ぼかしを 1 段かけて「まだ来ていない」と分かる形にし、届くと鮮明になる。
    あわせて**隣の 1 枚を 400ms 後に先読み**し（`saveData` のときはしない）、原本の URL にも
    `v=<mtime>` を載せて `immutable` を効かせる——戻ってきた 1 枚は無通信で出る。
  - 🔴 **同日の 2 つ目の P1（2026-09-14）**: 「体感が遅い」という報告が 3 件あったが、どれも
    ブラウザ側は測っていなかった——測ってあったのは `fs_thumb.go` 自身のデコード費用だけ
    （冷たい 95ms／キャッシュ命中 44µs・4 並列）。実物のフォルダ（202 枚）を headless Chromium で
    実測した（`console/scripts/gallery-perf/check.mjs`: 実バンドルを、`api/fs/download` が同じ
    並列数・遅延の形を再現するスタブに向けて走らせる——実の Agent が無くてもブラウザ側は
    現実的な待ち行列を見る）。
    - `entries === null` は**一覧が埋まっているときと同じ分岐**に落ちていたので、アプリが起動中の
      間は「上へ」だけが描かれていた——実測で約 1.2 秒、その間なにも起きている様子が見えない。
      専用の分岐（`EmptyState icon="loading"`）で直した。バックグラウンドの再読み込みではここに
      来ない——`load()` はフォルダの**最初の読み**以外では前の一覧を画面に残す——ので、これは
      必ず「そのフォルダを初めて見るとき」限定になる。
    - `loading="lazy"` だけに任せると、**スクロールを一切していなくても** 202 枚中 54 枚が
      要求されていた（Chromium 自身の「どこまで先読みする価値があるか」という判定はかなり
      気前がよく、カードが画面外へ流れても要求は絞り直されない）。マウント直後に一番下まで
      スクロールすると、いま見えている行は**見ている人がもういない 50 件の要求の後ろ**に並び、
      到着は約 1 秒遅れた。
    - カードごとの `IntersectionObserver`（`useArmed`。`rootMargin: "480px 0px"`、
      ビューポートではなく `.gal-body` を根に取る——ペインは窓より狭いことがある）で、
      `loading="lazy"` に任せきりにせず `<img src>` 自体を出し分けて直した。枠に近づいていない
      カードはブラウザの同一ホスト 6 本の待ち行列に**そもそも入らない**。一度近づいたら固定
      （読み込み済みの絵を画面外へ流してまた戻しても再要求しない）。再測定: 静止時 34 件
      （54 から減）、マウント直後のスクロールでも合計 33 件で 107 件には膨らまず、
      スクロールの瞬間に競合していた要求は 0 件（50 件から減）。`fetchPriority="high"` は
      armed になったカードにだけ付けている——もともと短くなった行列の上に載せる、安い上乗せ。

### 決定 5 — カードの操作は転写のカードと同じ分け方。ライトボックスは共有して ←/→ を足す

- **本体＝拡大（ライトボックス）／角のボタン＝ファイルペインで開く**。既に `FileCard` が
  この分け方で、理由も同じ（見るだけでペインを消費させない）。
- `mirror/parts/ImageLightbox.tsx` を**共有の場所（`features/viewer/ImageLightbox.tsx`）へ引き上げ**、
  `←`/`→` の送りと「3 / 12」の現在位置を足す。`ImageView` の zoom ハンドルはそのまま使う。
  **ミラー側の見た目と挙動は変えない**（送りは並びを渡されたときだけ出る）。
- Escape は `useEscLayer`、背景クリックで閉じる・画像のクリックは拡大に残す既存の判定
  （ドラッグ判定込み）をそのまま引き継ぐ。**スマホの Back で閉じるのは引き継がない**——
  `useBackClose` を呼んでいるのは `MirrorView` 側で、部品の中には無い。引き上げた先でも
  「閉じる」を呼ぶのは持ち主の責任なので、ギャラリー側でも同じように繋ぐ。繋ぎ忘れると
  スマホの Back がライトボックスを飛び越してペインごと戻る。
- **スマホのスワイプで送らない**（P0）。水平ドラッグはセッション回転に取られており
  （`data-no-swipe` との綱引き）、ここを触ると既存の操作が壊れる。ボタンと矢印キーで送る。
  - 🔴 **P1 で入れた（2026-09-14・利用者の要望）。** 前提が 1 つ間違っていた——ライトボックスの
    overlay は**自分で `data-no-swipe` を付けている**ので、開いている間セッション回転は既に
    降りており、綱引きは overlay の中では起きない。実際に取り合う相手は**拡大中のパン**
    （`ImageView`）だけなので、条件は 2 つ: **タッチのときだけ**（マウスの横ドラッグは誰も
    「送り」のつもりで引かない）、**等倍のときだけ**（拡大中の横ドラッグはパンのもの）。
    しきい値は 48px、かつ横移動が縦の 1.5 倍以上——縦スクロールが横に流れた分で送らないため。

### 決定 6 — 自動更新は「イベントが引き金・間隔は保険」の既存方針に従う

`features/files/refreshPolicy.ts` の数字をそのまま使う。

- マウント時に 1 回・`useFilesStore` の `tick`（ワークスペースの起停・アップロード）・
  **タブに戻ったとき**（`REVALIDATE_GAP_MS` = 10 秒の床）・**稼働中のセッションがある間だけ
  20 秒間隔**（`WORKING_TICK_MS`。誰も走っていなければタイマーごと畳む）・ヘッダの更新ボタン。
- **常駐ポーラーにはしない**（Console↔CP の通信削減方針）。生成は 1 回に数分かかり、
  ターン終了の合図（`sessionRefresh.ts`）では遅すぎるので、この面では 20 秒の網が主役になる。
  一覧は JSON なので CP の ETag が効き、変化が無ければ 304 で終わる。
- 新しく増えた画像はツリーと同じ「新着ハイライト」で出す（生成が着地する瞬間が見える）。

### 決定 7 — 導線は既にある並び（メニュー、またはライトボックスのバー）に 1 項目ずつ。新しい面は足さない

1. **左ペインのフォルダの右クリック** →「ギャラリーで開く」。
2. **左ペインの画像ファイルの右クリック** → 同じ項目。`menuDir` は既に親フォルダを指しているので、
   親のギャラリーをその画像に合わせて開く（`galleryFocus`）。画像以外のファイルには出さない。
3. **ミラーの共有ファイル（`FileCard`）から開いたライトボックスのボタン列** →「フォルダを開く」。
   その画像の**親フォルダ**を開くだけなので、セッションの解決は要らない。
   ミラーに「共有ファイル欄」という面は無く、あるのは転写の中のカード（`transcript/blocks.tsx` の
   `FileCard`／`UserFileBlock`）で、**画像のカードは既に本体＝拡大・角＝ペインの 2 つで埋まっている**。
   3 つ目のボタンを角に足すと決定 5 の分け方が読めなくなるので、**既にあるボタン列**
   （決定 5 で共有にするライトボックスのバー）に 1 つ足す。ギャラリー側からも同じ列に出る。
4. **画像ビュアーのヘッダ** →「同じフォルダのギャラリー」。ヘッダは
   `viewer/parts/FileHeadControls.tsx`（`FileView` が組み立てる情報バー）。
   `viewer/parts/FileViewerShell.tsx` は読む面そのもので、ヘッダを持たない。
   フォルダを主語にする操作の前例は `FileView` の `revealInFiles`（`onOpenDir`）である。
5. **セッションの右クリックメニュー** →「生成した画像 (N)」。`sessions/SessionMenu.tsx` は
   行・タブ・セッション一覧のカードの 3 か所で共有されているので、**1 項目で 3 導線**になる
   （0078 決定 7 と同じ理由——項目を複製しない）。

開き方は既存の慣習に従う: 素のクリックは今のペイン、`Ctrl/⌘`・中クリックは別ペイン。
スマホは隣が無いので同じペインに開く（0078 決定 3 の改訂に同じ）。

### 決定 8 — セッションの項目は**生成物があるときだけ**出す。そのために一覧の wire に 2 フィールド足す

`session.Session`（Agent）→ `sessionWire`（CP）→ `types/session.ts`（Console）に:

- `generatedImages`（枚数・`omitempty`）
- `generatedImagesPath`（browse-root 相対のフォルダ・`omitempty`）

- **なぜ wire か。** フォルダ名は `uuidV5(dir + "|" + セッション名)`（`internal/session/uuid.go`。
  実際に呼ぶのは `imagegen/http.go` の `session.UUID(meta.Dir, body.Session)`）。入力の
  `dir` と `name` は wire にあるので **Console が計算できないわけではない**——SHA-1 は
  `crypto.subtle` にある。やらないのは、それが**Agent の内部事情を写す重複**だからで、
  片方を直すともう片方が黙ってずれる（メニューを組む同期の場所で `await` が要る、という
  実装上の不都合も付く）。クリック時に問い合わせる案だと「あるか無いか」がメニューを開いた**後**に
  決まり、項目が遅れて生える（マウスはもう動いている）。パスを wire に載せれば
  **新しいエンドポイントも CP の許可リストも要らず**、クリックは即座にペインを開く。
- **費用。** 一覧を組むたびにセッション 1 本あたり `ReadDir` 1 回（一覧はすでにセッションごとに
  meta を読み、必要なら書いてもいる）。**「小さなディレクトリ」は保証ではない**——保持は 30 日で、
  毎日回すセッションのフォルダは数百件になる。数えるには名前を全部読むしかないので、
  **フォルダの mtime を鍵にした memo 化は P0 で入れる**（数行で、後から測り直さずに済む）。
  wire のバイトは 0 件で落ちるので、生成していない配備では増えない。
- **古い Agent は 2 つとも返さない**（`mtime` と同じ理由）。そのときメニュー項目は出ない。
  能力判定も版比較もせず、**無ければ出さない**で正しく落ちる。
- **中継の落とし穴。** `control-plane/workspace_handlers.go` の `sessionWire` は Agent の応答を
  decode して re-emit する中継で、**そこに無いフィールドは黙って落ちる**。Console の単体・DOM 試験は
  `Session` を直に組むので中継を通らず、TS 側が optional なので typecheck も黙る。症状は
  「項目が永久に出ない」。**触るのは 4 か所**: `sessionWire` 本体／`contract_session_test.go` の
  `sessionWireBinding` と `tsKeys`（両方）／`session_wire_test.go` の Agent 形 payload と往復後の
  期待値／`testdata/wire.golden` の再生成（`# count:` が動く）。捕まえるのは CI の `control-plane`
  ジョブだけなので、**書き終えてから初めて赤くなる**。
- **ワークスペース停止中は DB ミラー経由なので両方とも落ち、項目も消える。** エージェントが
  居なければギャラリー自体が読めないので、これは正しい挙動である。
- **数えるのは af の `generate_image` の出力だけ。** codex 自前の `generated_images` は `.codex` の
  下＝意図的に閲覧禁止（`fsDeny`・ADR 0069 がわざわざ移した理由）なので、ここには出ない。
  貼り付け画像（`pasted`）も対象外——別の軸であり、必要なら別の導線を足す。

### 決定 9 — 1 階層だけを見る。再帰は P1 で、別の口として足す

P0 は `galleryPath` 直下のみ。再帰は「歩き回る」ことなので、`.gitignore` を無視して数を制限できる
専用の口（`GET /fs/images?path=&depth=&limit=`）が要る。それは**再帰が要ると分かってから**作る。
1 階層で足りる用途（生成画像・`docs/img`・スクリーンショット置き場）が先に来る用途のほとんどである。

**P1 の改訂（2026-09-14・利用者の要望）: 歩くのは利用者に任せる。**
フォルダを**カードとして並べ**、押すと**そのペインがそこへ移動する**（パンくずで戻る・
`galleryFocus` と `gallerySession` は捨て、`sort` は持ち越す）。**一覧の口は 1 階層のまま**で、
再帰する口はやはり作っていない——`fs/tree` を 1 回、行き先でもう 1 回引くだけである。
これで「サブフォルダを見たい」は満たされ、専用の口が要るのは「全部まとめて 1 枚に並べたい」
（未解決 2 の X/Y グリッドなど）が来たときだけになった。

- **フォルダのカードに枚数は出さない**——出せるのは**セッションのフォルダだけ**である。
  一覧の wire が `generatedImagesPath` と `generatedImages` を運んでいるので、パスが一致した
  カードには**セッションの表示名と枚数**を出す。他のフォルダに同じものを出すには
  `fs/tree` をカードの数だけ引くことになり、それは決定 2 が避けたものそのもの。
- `galleryPath` に**空文字（ブラウズルート）**が入るようになった。「上へ」がファイルツリーと
  同じ場所まで戻れないと `.cache` で行き止まりになるためで、保存値の検証も空文字を通す
  （鍵ごと無いのは今までどおり拒む——`str()` の真偽値判定では両者を区別できない）。
- 🔴 **P1・利用者の要望（2026-09-14）: パンくずを専用の行に分け、常時出る「上へ」ボタンを足し、
  ブラウザの Back ボタンでフォルダの行き来を戻れるようにする。**
  - パンくずはタイトル・枚数・並び替えトグルと同じ 1 行を取り合っており、数段潜ると伸びる
    余地が無くなっていた。ヘッダの下に専用の全幅の行（`.gal-path`）を新設し、そこへ移した——
    `TerminalView` が `ContextBar` に使っているのと同じ形で、`<ViewHead>` のすぐ下に置く
    ただの兄弟要素であり、ヘッダ自身の機能ではない。
  - **「上へ」はその行に常時出るボタンにもなった（ルートでは無効）**。グリッドのカードだけだと、
    長いフォルダで先頭までスクロールしないと押せない。呼ぶのはパンくずやグリッドの「上へ」札と
    まったく同じ `navigate()` なので、この 3 つと下記のブラウザの Back ボタンは常に同じ答えを出す。
  - **Back ボタンとの統合はほぼタダで済んだ。** `layout/store.ts` は本 ADR より前から、**push した**
    レイアウトのコミットごとにブラウザの履歴を 1 件積み、`popstate` で復元する仕組み
    （`wireLayoutHistory`）を既に持っていた——`setPaneTarget` は単に、そこから**外れている**
    呼び出し元の 1 つだった（`push: false`。タブ選択やディバイダのドラッグと同じ立場で、
    内容のちょっとした調整は戻り先ではない、という判断）。直したのは、この 1 呼び出し元だけの
    立場替え: `setPaneTarget` に省略可能な第 3 引数 `push`（既定 `false`、他の呼び出し元は無影響）
    を足し、パンくず・フォルダのカード・ヘッダの「上へ」が既にすべて通っている
    `GalleryView.navigate()` から `true` を渡す。ギャラリー側で新しい履歴／popstate の配線は
    1 行も書いていない。
  - headless Chromium で実物のフォルダに対して確認済み: サブフォルダへ入る → ヘッダの「上へ」を
    押す → Back を 2 回 → サブフォルダへ入った直後の場所に戻り、続けてそのサブフォルダへ入る
    前の場所に戻る。`sort` はどの一歩でも保たれる（履歴の側に保存せずその場で読むので、
    Back が戻す対象にそもそも入らない）。

## 却下した案

- **モーダルのギャラリー**（掃除／アーカイブと同型）: 安いが、ミラーと並べる・タブにする・
  別タブへ切り離す・レイアウトに残す——ペインだから只で付くものを全部捨てる（決定 1）。
- **`kind:"file"` にディレクトリを渡す**: `filePath` の契約と FileView の機構が全部嘘になる（決定 1）。
- **ギャラリー用の一覧エンドポイントを P0 で作る**: `fs/tree` ＋ `mtime` 1 つで足りる。
  端から作ると、画像判定・並び・上限が Agent と Console の 2 か所に増える（決定 2・3）。
- **`api/fs/search` で再帰一覧を作る**: `.gitignore` を尊重するので生成物が黙って消え、`q` が必須で
  「全部」を頼めない。**空の結果と走っていない検索は見分けが付かない**（決定 2）。
- **カードに W×H を出す**（P0）: `fs/tree` は寸法を持たない。サムネイルの `naturalWidth` は
  整数倍に縮んだ後の値で、原本の寸法ではない（小さい画像は原本が返るので**当たることもある**——
  当たったり外れたりする数字は、いつも外れるより悪い）。原本を読む拡大とファイルペインには
  今も出ている。寸法をカードに出すなら `DecodeConfig` でヘッダだけ読む口が必要で、それは P1。
- **サムネイルを 256 で頼む**: 帯域は減るが、同じ画像をミラーと 2 回デコードする（決定 4）。
- **クリック時に問い合わせてメニュー項目を出し分ける**: 項目が遅れて生える（決定 8）。
- **セッション UUID を Console 側で導出する**: `uuidV5` の入力（`dir + "|" + name`）が Agent の
  内部事情で、写した瞬間から黙ってずれ始める（決定 8）。
- **`generatedImagesPath` の代わりに枚数だけを載せ、パスはエンドポイントで引く**: 項目の出し分けは
  できるが、エンドポイント 1 本・CP の許可リスト 1 行・往復 1 回が増えて、得るものが無い（決定 8）。
- **左ペインにサムネイルを並べる**: 撤回済みの左ペイン IA と衝突する。レールは行、面は右
  （0078 と同じ）。
- **仮想スクロール**: 300 枚打ち切り＋`loading="lazy"` で足りる。先に測る（未解決 1）。
- **スマホのスワイプで送る**: 水平ドラッグはセッション回転が持っている（決定 5）。
- **動画・PDF も混ぜる**: 「画像のギャラリー」から始める。PDF は既に専用の面があり
  （ADR 0063）、動画は再生と帯域の話が別に要る（未解決 2）。
