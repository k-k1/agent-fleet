# 0065. Postgres に拒否されたら DB パスワードを引き直す。プロセスが保証できない健全性を報告しない

[English](0065-db-credential-rotation.md) | 日本語

- 状態: **採用・実装済み**（2026-09-01）。同日の本番障害を受けたもの。
- 関連: [0045-ec2-persistent-workspace.md](0045-ec2-persistent-workspace.ja.md)（決定 21 ——
  タスクロールの権限はデプロイヤの権限ではない。その差は本番まで見えない） /
  [0058-workspace-resource-observation.md](0058-workspace-resource-observation.ja.md)

## 背景

2026-09-01 14:10 JST、acrt のデプロイが **`GET /api/*` のすべてに 500** を返し始め、15 分続いた。
配備は何もしていない。直近のリリースは 11:39 で、それまで問題なく動いていた。

RDS がマネージドなマスターパスワードを自動ローテーションした。シークレット
（Secrets Manager の `rds!db-…`）は `RotationRules.AutomaticallyAfterDays = 7` を持ち、
Control Plane はそのパスワードを ECS タスク定義の `secrets` で受け取っている。

```yaml
Secrets:
  - Name: AF_DB_PASSWORD
    ValueFrom: "arn:aws:secretsmanager:…:secret:rds!db-…:password::"
```

**ECS がこれを解決するのはタスク起動時の 1 回だけ**である。値はただの環境変数になり、その
プロセスはその後何週間も走り続ける。だから 14:10 以降にプールが開いた接続はすべて、DB が
受け付けなくなったパスワードを提示していた。

```
failed SASL auth: FATAL: password authentication failed for user "afadmin" (SQLSTATE 28P01)
```

書き残す価値があるのは障害の後半である。**あらゆる計器が「健全」と言っていた。** `/healthz` は
リテラル文字列を書くだけで何にも触れないので `ok` を返す。したがって ALB のターゲットは healthy、
したがって ECS は steady state、CloudFormation にもドリフト無し。製品は完全に使えないのに、
監視面は全会一致で正常だと言った。痕跡は CP のログの 1 行だけで、それを読んでいる者はいなかった。
読めと促すものが何も無かったからである。

復旧は `aws ecs update-service … --force-new-deployment`。4 分・blue/green なので断は無し。
そしてこれが効くのは、**新しい**タスクなら ECS がシークレットを解決し直すから、それだけである。

## 決定

### 1. 環境変数はブートストラップの手掛かりであって、パスワードではない

`AF_DB_PASSWORD` はそのまま残す —— AWS への往復無しでプロセスが起動できるのはこれのおかげだし、
オンプレではこれが全部だからである。ただし格下げする。**真値は、接続を開くその瞬間に
Secrets Manager が言う値である。**

引き直しは呼び出し側ではなく**コネクタ**でやる。`pgx` の `stdlib.OptionBeforeConnect` は
接続ごとの設定コピーに対して走るので、新しい物理接続は必ず現在のパスワードを拾う。その上で
コネクタを包み、`28P01` / `28000` を見たらシークレットを読み直して**同じ `Connect` の中で**
リトライする。`database/sql` は失敗した `Connect` をリトライせず、接続を求めた者へそのまま
エラーを渡す —— それこそが、1 回のローテーションが「全エンドポイント 500」になった機構である。
この線より下で回復させれば、呼び出し側はこの仕組みの存在を知らなくてよい。

確立済みの接続は触らない。Postgres は生きているセッションを再認証しないので、ローテーションは
プールが次に増えるまで何のコストも生まない。

**ローテーションには真ん中に穴があり、そこも塞ぐ。** ローテーション関数は `setSecret`
（DB のパスワードが新値になる）を `finishSecret`（`AWSCURRENT` が新版を指す）より先に呼ぶので、
数秒のあいだ、皆が読むラベルはもう通らない方を指している。だから第 2 段として `AWSPENDING` を
試す。`AWSPREVIOUS` は**意図的に見ない** —— あれは逆向き、DB がすでに受け付けなくなった値である。

不採用:

- **ローテーションイベント（EventBridge）で CP を force-new-deployment する。** 欠陥を消さずに
  回避策を自動化するだけで、ルールとロールとターゲットを維持する義務が増え、プロセスが API
  1 回で直せることのためにタスク置換を買うことになる。しかも「古い資格情報」の**この原因**しか
  カバーしない。
- **`SetConnMaxLifetime` を短くして接続を回転させ、引き直させる。** 引き直す先が同じ環境変数で
  ある。プロセスの中に AWS へ問い合わせるものが一つも無いのだから、何も変わらない。
- **`28P01` で CP を fatal にして ECS に再起動させる。** クラッシュループをエラー処理と呼ぶ話で、
  回復可能な数秒を障害に変えてしまう。

### 2. シークレット ARN が設定されていなければ全部動かない

`AF_DB_PASSWORD_SECRET_ARN` が未設定なら、上のどれも走らない。クライアントも作らず、API も呼ばず、
パスワードは DSN で来た値のまま。compose・オンプレ・SQLite・テストは**以前と 1 バイトも変わらない**。

ARN が**設定されているのに**呼び出しが失敗したとき —— もっともありそうなのは `AccessDenied`、
変数を注入する実行ロールと `CpTaskRole` は別の身元だからである —— CP は**注入された値のまま
動き続け**、ログに残す（`DB_SECRET_REFRESH_FAILED`）。安全網を失うこと自体が障害になってはならない。
ただし、見えなければならない。

### 3. `/healthz` とは別に `/readyz`。ALB は `/healthz` に据え置く

liveness は readiness ではない。両者を混ぜたことが、この障害を隠した当のものである。`/readyz` は
ストアに ping する。`/healthz` はプロセスが走っている限り `ok` を返し続ける。

**ALB のヘルスチェックは意図的に `/readyz` へ移さない。** 移したくはなる —— 落ちたターゲットは
置き換えられ、置き換わればシークレットは解決し直され、つまり今回の障害は自己修復していた。
しかし CP は `desiredCount 1` なので、RDS の一瞬の不可用がそのまま**本物の断＋再起動**になる。
それを永久に買う代わりに得られる自己修復は、決定 1 が再起動無しで既に果たしている。
`/healthz` は凍結された契約でもある（`deploy/local/restart-cp.sh` が body を `ok` と
verbatim 比較している）。

`/readyz` はセッション無しで届く（監視はログインできない）。body には未認証の呼び出し元に
見せてよくないものを一切書かない —— DSN も、ユーザー名も、SQLSTATE も。詳細に基づいて動ける者は
ログを読める。

### 4. ログの 1 行をメトリクスにし、メトリクスが人に届くようにする

`/readyz` は誰かが叩いていて初めて意味を持つが、当該デプロイでは誰も叩いていなかった。そこで
CP は接続を開けないとき `DB_UNAVAILABLE` を出し、`30-ingress.yaml` の CloudWatch メトリクス
フィルタがそれを数え、`CpAlarmEmail` パラメータ（既定は空・スロットプールのアラームに倣った）が
それをメールに変える。

**フィルタは無条件**で、アラームだけが条件付きである。何にもマッチしないフィルタは何も publish
せず、何のコストも生まない。そしてこの種の障害の教訓は、**見ようと思ったときには履歴が既に
存在していてほしい**、というものである。

## 影響

- `CpTaskRole` に `secretsmanager:GetSecretValue`（`secret:rds!*`）が増える（`20-platform.yaml`）。
  無いと機構は今までの挙動へ無言で退行する —— だからログに出す。
- `control-plane` が `aws-sdk-go-v2/service/secretsmanager` に依存する。コア SDK のリビジョンを
  動かさない版に固定した。
- `Store` に `Ping` が増える。
- デプロイ側は `CpAlarmEmail` を設定することが期待される。既存スタックは未設定でも動き続け、
  メトリクスは得るが通知は得ない。
- ローテーション経路には実 Postgres を相手にするテストがある。そして**サーバが `trust` 認証の
  ときは声を上げて skip する** —— `trust` では誤ったパスワードでも普通に繋がるので、テストは
  対象のコードを 1 行も通さずに緑になってしまうからである。
