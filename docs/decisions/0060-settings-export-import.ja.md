# 0060. 設定の書き出し / 取り込みは「秘密を含まないセクションの集合」1 本にし、取り込みは足すだけにする

## 背景

「SSM の設定を書き出し / 取り込みしたい」から始まった。SSM の登録は手入力が重く、環境を
移るたびに入れ直している。しかし移りたいのは SSM ではなく **その人の環境**で、SSM はその
一部でしかない。個別のボタンを足すと、同じ形の要望のたびに増え、ファイルの形式もばらける。

## 決定

### 1. 1 個の JSON（`kind: "agent-fleet-settings"` / `version` / `sections`）にまとめる

セクションの集合にする。今回運ぶのは **個人設定（ui-prefs）/ AWS SSM / エージェントへの指示**。
環境変数・MCP 定義・内部リポジトリ登録は後からセクションを足すだけで載る。

**版は前方互換にしない。** 知らない `version` は読まずに断る。部分的に読めるふりをすると、
何が入って何が入らなかったのかを利用者が確かめる手段が無くなる。

### 2. 秘密は常に除外する

接続（Git / エージェント / AWS / チャットのトークン・API キー）は入れない。移った先では
もう一度サインインしてもらう。

**理由:** このファイルは「設定ファイル」として気軽に扱われる（メールで送る、チャットに貼る、
リポジトリにコミットする）。1 つでも秘密が混ざると、その扱いの軽さがそのまま漏洩の経路に
なる。**除外を既定にするのではなく、除外しかしない** —— チェックボックス 1 つで含められる
なら、事故は「そのチェックを外し忘れた」ではなく「入れたことを忘れた」で起きる。

副次的に、バンドルは**人に渡せる**ものになる（チームの SSM 登録一式を配る、が成立する）。

### 3. ホストはプロファイルを id ではなく「表示名」で参照する

CP の id は環境ごとに違うので、id で運ぶと取り込み先で必ず張り替えが要る。表示名は
`~/.aws` のプロファイル名の素でもある自然キーなので、**形式の側で id 問題を消す**。

### 4. 取り込みは足すだけ・既存は書き換えない

プロファイルは表示名、ホストは alias ＋ インスタンス id で既存と突き合わせ、一致したら
スキップして理由を出す。同名で中身が違う場合にどちらが正しいかは Console に判断できず、
上書きが正解であることは滅多にない。設定の移送で既存環境を削るのは割に合わない。

### 5. 個人設定は「重ねる」。累積データを空で潰さない

ui-prefs は state をまるごと PUT・最後の書き手が勝つ。2026-08-18 に、この性質と hydrate の
無言失敗が重なって**全端末の学習済み返信候補が消える事故**が起きている。取り込みは他所から
来た blob を一発で書き込む操作なので、素直に実装すると同じ穴をもう一度開ける。

- 既知のキーで既定値と形が合う値だけを残す（`sanitizeImportedPrefs`）。
- 現在値へ重ねる。累積キーは**空で上書きしない**、オブジェクトは**足し算**（`mergeImportedPrefs`）。

### 6. サーバ側の変更はゼロ（フロント完結）

必要な REST（`api/env/ui-prefs`・`api/ssm/*`・`api/user-notes`）は全て既にある。新しい REST を
足すと CP のプロキシ許可リストと Agent の両方に入れる必要があり、片方だけ入れて 404 にする
事故を繰り返している。

**代償:** 原子性が無い（プロファイルを作った後にホストで失敗し得る）。取り込みが「足すだけ・
既存はスキップ」なので**同じファイルをもう一度取り込めば残りだけが入る** —— 冪等性で足りる
と判断した。

## 捨てた選択肢

- **SSM タブにだけ書き出し / 取り込みを付ける（最小）。** 早いが、次の要望で形式を作り直す。
  器を先に作る方が安い。
- **秘密を明示チェックで含められるようにする。** 「自分の環境の完全な引っ越し」には便利だが、
  ファイルの性質が「渡せる物」から「渡してはいけない物」へ変わり、**見た目では区別できない**。
  秘密入りと秘密なしのファイルが同じ名前で混在する状態を作らない。
- **CP に一括取り込み API を足して原子的にする。** 許可リストの二重登録という既知の事故経路を
  増やしてまで買う価値が、冪等な再取り込みに対して無い。
- **取り込みで既存を上書きする / 差分を選ばせる。** 前者は破壊的、後者は 3 層 × 数十項目の
  差分 UI になる。移送の道具としては過剰。
- **ui-prefs をそのまま PUT する（最も素直な実装）。** 事故の再演（決定 5）。

## 追記（2026-10-30）— 手元の `~/.aws/config` を読む（#3010）

AF へ移る妨げとして「作り込んだ AWS プロファイルを 1 つずつ手で入れ直すこと」が挙がった。このバンドルは AF が
書き出したものしか読まないので、手元の PC から移る人には効かない。そこで **ネイティブ形式を「入口」として足し、
出口は既存の取り込み計画（`planSsmImport`）と同じにする**。

1. **AWS CLI と同じ読み方をする。** configparser の strict モード（セクション・キーの重複はファイルごとエラー、
   字下げ行は前の値の続き、`[DEFAULT]` は全セクションに効く）と botocore の対応づけに合わせる。読み方が違うと、
   手元で動いている設定が Settings で別のものになる。
2. **別人として動くものは作らない。** 完全な SSO プロファイルと、そこから 1 段のロール引き受けだけを作る。鍵や
   `credential_process` が並んでいる行は「鍵を捨てて SSO として作る」ことをせず、取り込めないとする。
3. **値は Agent の許可リストで確かめる。** CP の最低条件より厳しい。Agent は弾いた値をそのまま同期ログに
   引用するので、継続行に入った鍵がそこから漏れうる。理由に出すのはキー名と行番号だけにする。
4. **既存の行への接続は、同じサインインだと示せるときだけ。** 引き受け元がファイルにあり座標が一致するとき、
   または利用者がプレビューで選んだとき（「確かめていない」と表示する）。名前だけでは繋がない。
5. **書き込む前に今の一覧を読み直し、読めなければ何も送らない。** `api()` は失敗をエラー本文で返し、CP には
   ラベルの一意制約がないため、読めないまま進むと全部が二重にできる。バンドルの取り込みも同じ実行部
   （`ssmImportExec.ts`）に揃えた。

決定 6（サーバー側の変更なし）は保つ。ファイルはブラウザの中だけで読み、送るのは既存の
`POST api/ssm/profiles` へ、行ごとの項目だけ。同時に 2 か所から取り込んだときの重複までは防がない（防ぐなら CP の一意制約が要る）。
手順と残りの段階（`~/.ssh/config`・gcloud・書き出し）は [docs/79 §9](../log/79-settings-export-import.md#9-手元の-awsconfig-を読む3010)。

## 追記（2026-10-30）— gcloud の構成を読む（#3017 第 2 部）

`~/.aws/config` と同じ理由で、gcloud の構成ファイル（`~/.config/gcloud/configurations/config_<名前>`）も
ソースに加える。**シンクは既存の CP の CRUD（`api/gcp/profiles`）のまま。** 新しい REST は足さない。

1. **CP が受け付ける形だけ作る。** ログイン方式は Google、project は CP と同じ正規表現、権限借用は
   サービスアカウント 1 つ。`core/account` がサービスアカウントの構成は、鍵なしではログインできないので取り込まない。
2. **ログインや向き先を変える設定は、省いて取り込まず理由をつけて断る。** `auth/` の認証上書き、委任チェーン、
   プロキシ、エンドポイント上書き、universe domain。省いて作ると、手元とは別の相手に向いたプロファイルになる。
3. **資格情報には触れない。** 資格情報 DB・ADC・鍵ファイルは読まず、構成に書かれたパスやトークンファイルは
   表示も送信もしない。理由に出すのは既知のキー名と行番号だけ。
4. 書き込む前に今の一覧を読み直し、読めなければ何も送らない（決定 5 と同じ実行部の規則）。

決定 6 は保つ。手順は [docs/79 §9.4](../log/79-settings-export-import.md#94-gcloud-の構成を読む3017-第-2-部2026-10-30)。

## 追記（2026-10-30）— Settings の AWS プロファイルを `~/.aws/config` として書き出す（#3017 第 3 部）

逆方向は、保存された値を連結するのではなく、許可した項目だけから作る。CP は SSO 行の項目を Agent より緩く見るので、
保存値が INI の読み手にとって新しい鍵やセクションに見えるものを含みうる。描画器はすべての値を Agent の許可リストで
確かめ、どの行を書き出すかも Agent の規則に合わせ（予約名 `default`、名前の衝突は両方除外、SSO 行にはアカウントと
ロール、ロール行には書き出される引き受け元）、除外した行は項目名だけの理由つきで示し、自分が書く形でない行を含む
テキストは出さない。結果は「Agent Fleet が表現できるもの」で、取り込みの逆ではないので、`~/.aws/config` と取り違え
ない名前の断片として、手で取り込む形で渡す。サーバー側の変更はない。sso-session の名前は 1 つの関数で決めるので、
複数のプロファイルが共有するサインイン（後の決定）は書き出しの 1 か所の変更で済む。
