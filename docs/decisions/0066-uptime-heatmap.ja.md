# 0066. 占有を 1 時間ごとに記録してヒートマップにする——金額は塗らない

[English](0066-uptime-heatmap.md) | 日本語

- 状態: **採用・P0（時バケットのサンプリング）/ P1（API）/ P2（Console 3 面）実装済み**
  （2026-09-01）。設計と実測は [docs/83](../log/83-uptime-heatmap.md)。
- 関連: [0048-member-cloud-cost.ja.md](0048-member-cloud-cost.ja.md)（金額の面。あちらの決定 2 が
  「時間に値段を付けない」の根拠）/ [0029-usage-accounting.ja.md](0029-usage-accounting.ja.md)
  （トークンの面と、「使用量」が既に 3 つを指している話）/
  [0055-idle-stop-and-carried-interactions.ja.md](0055-idle-stop-and-carried-interactions.ja.md)（`sessionActivity`＝「動いている」の唯一の定義）

## 背景

占有についてこのシステムが持っている数字は 1 日 1 つしか無い（`usage_daily.running_secs` と、
AWS の請求があるなら `cloud_cost_daily`）。それでは「金曜が高かった」までは分かっても
**なぜか**は分からない——止め忘れたワークスペースと、人が働いていたワークスペースは、日単位では
同じ顔をしている。動いているワークスペースの中でセッションが何本開いていたかに至っては、
時系列の記録が**どこにも無い**（CP の `session` 表は読むたび `ReplaceSessions` が消す現在値）。

メンバーを見ている管理者の手元にはボタンが 2 つ（強制停止・ディスク上限）あるのに、どちらを
押すべきかの根拠が無い。

## 決定

**決定 1. 新しい表に時バケットを持ち、既存のサンプラが埋める。** `usage_hourly` のキーは
`(membership_id, hour)`（UTC）。書き手は、既に全テナントのワークスペースを列挙している
5 分ごとの showback サンプラ。常駐タイマーは増やさない——同じ walk をするタイマーをもう 1 本
立てるのは、この host でメモリを使い切る典型である。

**決定 2. 占有だけ——ヒートマップは金額を運ばない。** 実費は日単位でしか取れないので、時間別の
金額は「秒 × 誰かが一度打ち込んだ単価」にしかならず、[0048](0048-member-cloud-cost.ja.md)
決定 2 がそれを否定している。よってこの機能は**クラウド費用ではなく「稼働時間」**に属する。
両方が出る面（メンバー詳細）では、費用カードの**下に別のカードとして**置く——1 日の請求を
説明はするが、値段を付け直さない。

**決定 3. マスは 3 値。サンプラが動いたことをハートビート行が記録する。**
`membership_id = ''` がその時間のハートビート（`cloud_cost_daily` の共有バケットと同じ規約）。
ハートビートがあってメンバーの行が無い＝観測できて停止（灰色）、ハートビートが無い＝未観測
（空白）。これが無いと、CP が落ちていた日が「このメンバーは何もしていない」と自信たっぷりに
描かれる。⚠️ ハートビートは**スイープが完走したときだけ**打つ——途中で失敗した回に打つと、
辿り着かなかったワークスペースに灰色が塗られる。

**決定 4. `measured_secs` が「0 本」と「聞けなかった」を分ける。** Agent に届かない稼働中の
ワークスペースは、まさに「分からない」場合であって、0 と記録すると忙しかった時間に冷たいマスが
描かれる。セッションの計数は Agent が実際に答えた秒数の上でだけ積み、マスは「稼働中・本数不明」
と言う。

**決定 5. 「動いている」は `sessionActivity` が言うとおり——ピンも含む。** 述語は呼ぶだけで
写さない（写せば、状態が増えた日に片方が古くなる）。ピンが busy に入るのは意図的で、
**週末ずっと温まったままのピンこそ、この画面が見せるためにある浪費**である。

**決定 6. API はメンバー別の系列を返し、合計はクライアントが積む。** 合算とホバーの内訳が同じ
応答から出るので、「合計と内訳が食い違う」が表現できない。3 つの入口は同じ形を返す——理由は
[0048](0048-member-cloud-cost.ja.md) と同じで、形が 2 つあると片方を直した日からずれる。

**決定 7. 保存は UTC、ローカル時刻へずらすのはブラウザ。** UTC のまま 24 段を描くと、東京の
読み手に「あなたは朝の 4 時に働いている」と告げる表になる。端の列を埋めるためクライアントは
前後 1 日ぶん広く要求する。30 分オフセットのタイムゾーンでは開始時刻の属する時間に丸め、
その旨を画面に出す。

**決定 8. ランプは 1 色の逐次（ordinal）で、モードごとに検証する。** カテゴリの `--viz-1..8` では
ない——これが符号化するのは大きさである。明色・暗色とも、モーダルの面色に対して dataviz の
検証器を `--ordinal` で通した。段が 5 つしか無いので、指標によって最下段の使い方を変える:
本数の指標では「起きているが 0 本」が最下段（**停止の灰色とは別物**）、稼働率の指標では 0 の
マスは描かれないので 5 段すべてが大きさを表す。

**決定 9. 時バケットには保持期間を置き、日バケットには置かない。** 行数は 24 倍で、去年の春の
何時かを聞く人はいない: 92 日。聞かれる方の `usage_daily` は全部残す。

## 帰結

- **過去は埋められない。** この決定からサンプラが配備に届くまでの日数は永久に欠測になる。
  P0 を UI より先に出したのはそのためで、[0048](0048-member-cloud-cost.ja.md) のコスト配分タグが
  教えたのと同じ非対称である。
- 書き込みは日バケットの 24 倍だが、上限はサンプラの間隔と**動いている**ワークスペースの数
  （止まっているワークスペースは 1 行も書かない）。
- セッション本数の取得で、1 サンプルにつき稼働中ワークスペース 1 台あたり 1 リクエストが増える。
  刺さった Agent が自分の tick を追い越さないよう 10 秒で打ち切る。
- メンバーの設定に占有まわりのタブが 3 枚並ぶ（トークン / クラウド費用 / 稼働時間）。名前は
  意図的に別のままにした——「使用量」を 4 つ目として再利用していない。
