# 0125. 設定の AWS プロファイルは IAM Identity Center のサインインを 1 つ共有できる

[English](0125-shared-sso-sign-in.md) | 日本語

- Issue: #3014
- 関連: [0102](0102-aws-login-through-the-console.ja.md)（Console からのログイン。リクエスト・試行・状態・
  期限警告・ログアウトはすべて sso-session をキーにしている）/ [0060](0060-settings-export-import.ja.md)（設定
  バンドル。`ssmProfileDTO` を運ぶ）/ #3010（`~/.aws/config` からの取り込み。Phase 1 は PR #3018）/ #3017
  （`~/.aws/config` への書き出し）

## 背景

設定の SSO プロファイルは、それぞれ専用の sso-session `[sso-session af-<profile>]` で描画される
（`ssm.RenderSSMConfig`）。この名前がキャッシュのキーになる。botocore は IAM Identity Center のトークンを
`~/.aws/sso/cache/<sso-session 名の sha1>.json` に（`SSOTokenLoader._generate_cache_key`）、ロールの資格情報を
`~/.aws/cli/cache/<{accountId, roleName, sessionName} の sha1>.json` に保存する。ADR 0102 で作ったものも
すべて同じ名前をキーにしている。ログインリクエストとその取り消し印（sso-session ごとに 1 つ）、試行枠と
ログアウトのゲート（`cloudlogin`）、キャッシュ済みログインのロック、行のログイン状態（`profileLoginState`）、
期限警告（`readSSOExpiry`・`warnExpiringSSO`）、ログアウト（`HandleProfileLogout`）である。文字列
`"af-" + name` は `workspace/agent/internal/awsx` の十数か所と `ssm/config.go` の 1 か所で組み立てている。

ノート PC で 20 個のプロファイルを 1 つの `[sso-session]` にまとめているメンバーは、手元では 1 回、
ここでは 20 回サインインする。#3010 の取り込みでこれが一度に目に見えるようになった。その解決器は各プロファイルの
手元のサインインを既に記録している（`NativeProfile.signIn`: `session:<sso_session>`、レガシーなら
`url:<start URL>`）。

Issue からの制約:

- 同じポータルへの別々のログインは意図的なことがある（別ユーザー、別の権限セット）。「start URL と SSO
  リージョンが同じものを全部まとめる」形のまとめ方はできない。
- メンバー自身の `[sso-session af-<name>]` がこちらの定義に勝つ規則（`SessionShadowed`）は維持する。

設計を縛る botocore の挙動:

- `sso_session = X` のプロファイルは start URL と SSO リージョンを `[sso-session X]` からだけ読む。
  プロファイル側にも書くなら同じ値でなければならず、違えば CLI が拒否する。
- トークンのローダーは、キャッシュ内の `startUrl` を設定と照合しない。キーの下にあるものをそのまま使う。
- 更新でリフレッシュトークンが新しくなることがある（`_attempt_create_token` は応答の `refreshToken` を残す）。
  そのため、同じリフレッシュトークンの写しを持つ 2 つのキャッシュファイルは、互いを無効にしうる。

## 決定

### 1. サインインはそれ自体で保存される。プロファイルは多くても 1 つに属する

CP にテーブル `ssm_sign_in` を追加する。列は `id`・`membership_id`・`name`・`start_url`・`sso_region`・
`created_at` で、`(membership_id, name)` に一意インデックスを張る。`ssm_profile` には
`sign_in_id TEXT NOT NULL DEFAULT ''` を足す。

- **空の `sign_in_id` は今と同じ意味。** プロファイルは自前の `start_url` と `sso_region` で、専用の
  サインイン `af-<profile name>` を持つ。既存の行は変わらないので、まとめていないプロファイルの描画結果も
  トークンキャッシュも何も変わらない。
- **空でない `sign_in_id`** は、そのプロファイルを共有サインインに入れる。入れるのは `kind = sso` の
  プロファイルだけ。assume-role プロファイルは今と同じく、ソースのサインインに従う。
- **start URL と SSO リージョンの正はサインインの行。** メンバーのプロファイル行は写しを持ち、サインインや
  所属を変える書き込みと同じトランザクションでストアが写しを書く。写しがあるので、この ADR より前から
  ある読み手（SSM セッションの書き換え、バンドルの書き出し、ロールバック後の古い CP バイナリ）は正しく動き
  続ける。古いバイナリは、まとめたプロファイルをそれぞれ専用のログインで描画する。これはこの ADR より前の
  動きで、別アカウントになることはない。
- **サインインの名前はメンバーが付ける。** 名前は設定画面に表示され、`af-<name>` として描画される。使える
  文字は `^[A-Za-z0-9._@-]{1,61}$` で、`af-<name>` が Agent の 64 文字の許可リストに収まる。整形はしない。
  許可リストの外の名前は拒否するので、2 つの名前が 1 つに潰れることはない。
- **サインインは、プロファイルが属している間だけ存在する。** 最初にその名前を指定したプロファイルが作り、
  最後のメンバーが抜けるか削除されるのと同じトランザクションで消える。空のサインインを作る経路も消す経路も
  ない。

### 2. sso-session 名はサインインごとに 1 つで、メンバー内で一意

SSO プロファイルの描画される sso-session は、サインインがあれば `af-<サインイン名>`、なければ
`af-<profile name>`。2 つの名前空間が重なるので、CP はストアのトランザクションで次の不変条件を 1 つ守る:
**サインイン名は、同じメンバーの、まとめていない SSO プロファイルのプロファイル名と一致しない。** これを
破る書き込み（新しいサインイン、サインインの改名、プロファイルの新規作成やラベル変更、サインインからの
脱退）は、相手側を名指しして `409 sign_in_name_taken` で拒否する。

サインインは **自分のメンバーの** 名前なら名乗ってよい。そのメンバーは、加わる前も後も `af-<name>` で
描画される。既存のログインがまとめても残るのはこの仕組みによる（決定 7）。

Agent はこの不変条件を信用しない。書き出す 2 つの項目が同じ sso-session 名で start URL か SSO リージョンが
違う場合（古いキャッシュ、古い CP）、どちらも書き出さず、新しい `SyncResult.SessionConflict` で報告する。
扱いは `Conflicts` と同じ。

### 3. API: プロファイルが自分のサインインを名指しし、サインイン自体の編集は専用の経路で行う

- `ssmProfileDTO` に `signIn`（サインイン名。空なら省く）を足す。`POST` と `PUT /api/ssm/profiles` はこれを
  読む:
  - 空: 今と同じ専用サインイン。
  - メンバーが持つ名前: そこに加わる。DTO の `startUrl` と `ssoRegion` は空か、サインインと同じ値でなければ
    ならず、違えば `409 sign_in_mismatch`。
  - 新しい名前: DTO の `startUrl` と `ssoRegion` からサインインを作る。この 2 つは今と同じく必須。

  名前で「加わるか作る」ので、バンドルの取り込み（ADR 0060）も #3010 の実行器も、`POST` を 1 件ずつ送る
  だけでまとめたプロファイルを作れる。呼び出し順の決まりは増えない。
- `GET /api/ssm/sign-ins` は `{id, name, startUrl, ssoRegion, profiles: [profile id]}` を返す。
  `PUT /api/ssm/sign-ins/{id}` はサインインの改名かポータルの変更を行い、同じトランザクションでメンバーの写しを
  書き直す。改名するとログインは新しいキャッシュキーに移るので、メンバーはもう一度サインインする。ポータルを
  変えると、古いキーの下に古いポータルのトークンが残る。どちらも Console が保存前に伝える（決定 9）。
- ブリッジの `awsProfileWire`（`GET /internal/aws-profiles`）に `signIn`（空なら省く）を足す。SSM セッションの
  書き換え（`rewriteSSMCreate`）は本文に `sso_session` を足す。Agent の `SSMMeta` には `SSOSession` を足し、
  同じ許可リストで検査する。無ければ Agent は `af-<profile>` を描画するので、古い CP でも動き続ける。
- `TestContractFamilies` には `ssmProfileDTO` の新しいフィールドと、新しいファミリー `ssmSignInDTO` を加える。
  Console の型もそれに合わせる。

### 4. 描画

`renderProfile` と `RenderSSMConfig` は、sso-session 名を自分で組み立てずにプロファイルから受け取る。
管理ブロックは各 `[sso-session af-<g>]` を、書き出す最初のメンバーの前に **1 回だけ** 書き、各メンバーの
`[profile …]` はそれを指す。書き出すメンバーが 1 つもないサインインは、セクションを書かない。

- **シャドウ。** メンバー自身の `[sso-session af-<g>]` は `g` の **全メンバー** を止める（今と同じく
  `SessionShadowed`。理由にはサインイン名を出す）。メンバー自身の `[profile x]` が止めるのは `x` だけ。
  ほかのメンバーは共有セクションとともに描画される。
- `[DEFAULT]`（`defaultClash`）は、書き出す `sso_session = af-<g>` と比べる。衝突で止まるのはそのプロファイル
  だけ。
- 連鎖のソースの sso-session 検査（`exec_nonsso.go`）、`consoleEligible`、`settingsFor`、`notDefined` は、
  `"af-" + name` ではなくプロファイル自身の sso-session 名と比べる（ヘルパー 1 つ、`ssoSessionOf(Profile)`）。

### 5. ログイン・状態・ログアウト・期限・ロックはサインイン単位

これらはすべて既に sso-session をキーにしているので、キーは変わらない。変わるのは、その後ろに立つ
プロファイルの数である。

- **リクエスト。** どのメンバーの `af-aws-exec` も、`af-<g>` の 1 つのリクエストを出すか、それに加わる。
  リクエストは出したプロファイルを持ち続ける。待ち手の記録には、それぞれが頼んだプロファイルを足す。
  `GET /aws-login` は `signIn` と待っているプロファイルを足し、`signIn` があればトーストは「`<g>` に
  サインイン（N 個のプロファイル）」と出す。アカウントとロールは今と同じく設定から取り、リクエストからは
  取らない。
- **試行。** 今と同じく sso-session ごとに 1 枠。どのメンバーの行で押しても、トーストで押しても、互いを
  置き換える。デバイス URL の許可リストはサインインの start URL と SSO リージョンから作り、全メンバーで
  共通。
- **状態。** `GET /aws-login/profiles` は各プロファイルに `signIn` とその sso-session の状態を付け、
  `signIns: [{name, state, expiresAt?, expiring?, profiles}]` を足す。キャッシュの `startUrl` か `region` が
  設定と違うときは `none` とみなす。ポータルを変えたとき（決定 3）に、動くログインに見えず「サインイン
  していない」と出るようにするためで、まとめていないプロファイルにも同じ規則を当てる。
- **期限。** `warnExpiringSSO` は sso-session と終了時刻の組ごとに 1 回警告する。対象は書き出し済みの
  メンバーが 1 つ以上ある sso-session（キー `aws-sso-expiring:<sso-session>:<end>`）。ペイロードは `profile`
  （書き出し済みの最初のメンバー。古い Console でもモーダルを開けるように）を残し、`signIn` を足す。
- **ログアウト。** トークンを共有しているので、メンバー 1 つのログアウトはサインインのログアウトになる。
  既存の経路 `POST /aws-login/profiles/{name}/logout` は残し、そのメンバーの sso-session に対して動く。
  キャッシュ済みのロール資格情報は、名指しされたものだけでなく **全メンバー** の分を消す（メンバーごとの
  `roleCachePaths`）。メンバーのロール資格情報が残ると、「ログアウト」後もそのプロファイルが動いてしまう。
  応答には、サインアウトした名前の `profiles` を足す。Console はその一覧で確認してから経路を呼ぶ。
- **ロックとゲート。** 変わらない。`logins.LockKey` と `logins.Gate` は sso-session を取る。
- **SSM の強制再ログイン**（`ssmForgetLogin`）は共有トークンを消すので、全メンバーがサインアウトする。
  まとめたプロファイルの SSM ホストで Console の「再ログイン」を押すと、そのことを伝える。

ログインのための CP の経路は変わらない。Agent の経路は引き続きプロファイル名をキーにし、CP は今と同じく
中継する。

### 6. Console の表示

- **設定 > AWS プロファイル/SSM。** サインインに属するプロファイルは、サインイン名とポータルを示す 1 つの
  見出しの下に並ぶ。ログイン状態、**ログイン**、**ログアウト** は見出しに 1 回だけ置く。まとめていない
  プロファイルは今の行のまま。メンバーの行はアカウント・ロール・リージョンを残し、ログインのボタンは
  持たない。
- **プロファイルのフォーム。** 「サインイン」欄を設けると、start URL と SSO リージョンの入力はそれに置き
  換わる。選択肢は「専用のサインイン」（既定。今の入力欄）、メンバーのサインインのどれか、名前を付ける
  「新しい共有サインイン」。サインインの改名とポータルの変更は見出しで行い、決定 3 の警告を出す。
- **既存プロファイルのまとめ。** 同じ start URL と SSO リージョンの、まとめていないプロファイルを選んで
  「1 つのサインインを共有」する操作。名前には、その中で今サインインしているプロファイルを提案する
  （決定 7）。
- **取り込み（#3010）。** `session:<name>` のプロファイルには `signIn = <name>` を付ける。プレビューには手元の
  `sso-session` ごとに 1 つのサインインが並び、Console でのログイン回数は手元のサインインの数になる。
  許可リストの外の名前や、`sign_in_name_taken` で拒否される名前は、その理由と編集できる名前とともに示す。
  同じ名前で別ポータルの既存サインインがあれば、それらの行を拒否し（`sign_in_mismatch`）、プレビューで
  名指しする。レガシーの `url:` プロファイルは未決事項 B。
- **書き出し（#3017）。** まとめたプロファイルは `sso_session = <name>` と 1 つの `[sso-session <name>]` で、
  まとめていないものは `[sso-session <profile name>]` で書く。そのファイルを取り込み直すと同じまとまりになる。

### 7. 移行と既存のログイン

- **データ移行はしない。** マイグレーション `0116_ssm_sign_in.sql`（SQLite）と `0101_ssm_sign_in.sql`
  （Postgres）でテーブル、列（既定 `''`）、インデックスを足す。前方互換である。古いバイナリはどちらも無視し、
  写した座標のおかげで出力も正しい。番号は変更を出すときに `main` と照合し直す。
- **メンバーがまとめるまで、何も変わらない。** 既存のログインはすべて動き続ける。
- **サインインした状態のメンバーの名前をサインインが名乗れば、ログインはまとめても残る。** そのメンバーの
  sso-session 名が変わらないので、そのトークンがグループのものになる。Console はその名前を提案する。
  別の名前なら、グループはサインアウト状態で始まり、ログインが 1 回要る。
- **残ったプロファイル単位のトークン。** 別の名前のサインインに加わったメンバーは、`af-<member>` の
  トークンをディスクに残す。もう誰も使わない。移しも写しもしない（却下を参照）。サインインからログアウト
  すると、そのメンバーの残った `af-<member>` トークンも失効させて消す。メンバー自身のファイルが
  `af-<member>` という名前を使っている場合は飛ばす（未決事項 C）。

### 8. 同じポータルへの別々のログインは引き続きできる

自動でまとめることはしない。start URL と SSO リージョンが同じでサインインのない 2 つのプロファイル、または
別々のサインインに属する 2 つのプロファイルは、2 つの sso-session として描画され、別々にログインする。
start URL でまとめるのは、取り込み時のレガシーなプロファイルに対する Console の提案だけで（未決事項 B）、
メンバーはプレビューで変えられる。

### 9. ドキュメント

`guide/member/16-cloud-accounts.md`（と `.ja.md`）で、サインイン、全メンバーに及ぶログアウト、改名や
ポータル変更で何が起きるかを説明する。`workspace/notes/aws.md`（`af-aws` スキル）には、ログインリクエストが
単一のプロファイルではなくサインインを名指しすることがある、と書く。

## 却下した案

- **start URL と SSO リージョンで自動的にまとめる。** 意図的な別々のログインを壊す（Issue の制約）。
- **各プロファイルに自由記述の `sso_session` 列を持たせ、サインインの行は作らない。** ポータルが N 行に
  分かれ、それらを等しく保たなければならない。変えるには N 回書く必要があり、CP はプロファイルの経路から
  それを不可分に変えられない。
- **ポータルはサインインにだけ持たせ、メンバー側は空にする。** サインインより前からある読み手（SSM の
  書き換え、バンドル、ロールバック後の古いバイナリ）に、ポータルの無いプロファイルが見えてしまう。
- **加わるときにメンバーのトークンを新しいキーへ写す、または移す。** 写しは、もう一方の更新で失われうる
  リフレッシュトークンを持ち、どちらかが失敗するまで両方とも有効に見える。移すのは、キャッシュファイルの
  形と、ローダーが `startUrl` を照合しないことに頼る。メンバーの名前を引き継げば、CLI 自身のキーで同じ
  結果が得られる。
- **サインイン用の別の接頭辞**（`af-signin-<name>`、`af:<name>`）。接頭辞もプロファイル名と衝突しうるし、
  衝突しえない接頭辞には CLI で測っていない文字が要る。まとめたときにログインを残すこともできなくなる。
- **サインイン内でのプロファイル単位のログアウト。** トークンは 1 つ。ほかを残して 1 つだけサインアウト
  させることはできない。
- **空のサインインを単独のオブジェクトにする**（作成・削除の経路）。それ単体では意味のない 3 つ目の
  オブジェクトが増え、取り込みに 2 種類の呼び出しが要る。

## 結果

- 手元の 1 つのサインインに N 個のプロファイルを持つメンバーは、Console で 1 回ログインすればよい。
- ログアウト、SSM の強制再ログイン、サインインの改名は全メンバーに及び、Console はそれを先に伝える。
- Agent は sso-session 名を、十数か所の文字列連結ではなく 1 つのヘルパーで作る。
- SSO キャッシュの状態は、期限に加えてキャッシュファイルの `startUrl` と `region` も読む。

## 未決事項

- **A. 出し方。** 推奨: 3 つの PR を順に出す。CP（マイグレーション、ストアの不変条件、DTO、経路、ブリッジ、
  契約）、次に Agent（描画、シャドウ、`ssoSessionOf`、リクエスト、状態、期限、ログアウト）、最後に Console
  （まとめた一覧、フォーム、まとめる操作、取り込みの既定）。新しいフィールドはどれも空なら省くので、
  どの PR も単独で安全。
- **B. 取り込み時のレガシーなプロファイル**（プロファイルに `sso_start_url` があり、`sso_session` がない。
  手元では start URL ごとに 1 つのログインを共有している）。推奨: プレビューで start URL と SSO リージョン
  ごとに 1 つのサインインを提案し、名前はポータルのホストのラベル（`d-1234567890`。編集でき、外せる）に
  する。代案はまとめずに取り込むこと。
- **C. 加わった後に残るプロファイル単位のトークン。** 推奨: サインインのログアウトのときだけ片付ける
  （決定 7）。代案は加わったときに失効させて消すことで、設定の同期からネットワーク呼び出しをすることに
  なる。
