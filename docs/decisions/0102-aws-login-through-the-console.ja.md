# 0102. `af-aws-exec` は SSO ログインを Console に依頼し、デバイスコードは利用者の押下でだけ始まる

[English](0102-aws-login-through-the-console.md) | 日本語

- 状態: **proposed**（2026-09-27）。実装は別の変更で行う。
- Issue: #1026
- Follow-ups: #1028, #1029
- 関連: #1010（`af-aws-exec` の受け入れ。この穴が見つかった場）／#1025（SSM の再開ボタンがログインモーダルを
  飛ばしていた件。デバイスコードの表示部品を共有する）

## 背景

`af-aws-exec` は Settings > SSM のプロファイル 1 つの認証情報でコマンドを実行する。IAM Identity Center の
キャッシュ済みログインが無いか期限切れのとき、ログインするのは端末の前に人がいる場合だけである
（`awsx.PlanExec`、`Login: "auto"`）。エージェントのシェルには端末が無いので、コマンドは exit 3 で終わり、
`aws sso login --profile <name> --use-device-code --no-browser` を表示する。エージェントは利用者に、端末を開いて
これを実行するよう頼むしかない。#1010 の受け入れ実行では、利用者が Console を離れなければならない手順はここだけ
だった。

Console に要るものの大半はすでにある。

- **トークンのキャッシュは 1 つ。** SSM セッションと `af-aws-exec` は同じ `[sso-session af-<name>]`
  （Settings から `awsx.renderProfile` が描く。`ssoOnlyConfig` は意図してこの名前を保つ）と同じ
  `~/.aws/sso/cache` を使う。どこでログインしても両方に効く。
- **デバイスコードの表示。** `SsmLoginModal` が SSM セッションのログインの確認 URL とコードを表示する。
  Agent はそれをセッションの tmux ペインから読む（`parseSSMLogin`）。
- **Console への経路。** 通知の送信箱（`internal/notice`）。`workspace-agent notify-arch-residue` と同じく、
  CLI の子プロセスから直接書ける。

Issue の素案を変える事実が 1 つある。**エージェントのシェルは `AGENT_TOKEN` を持っている。** af の MCP サーバが
Agent に届くように渡されていて（`mcpreg/attach.go`）、Control Plane が使うのと同じトークンである。したがって
エージェントのセッション内のどのプロセスも、Agent のどのルートでも呼べる。「デバイス認可を始められるのは Console
だけ」は、ルートを呼べる者を絞ることでは守れない。

守るべき規則は `workspace/notes/aws.md` が教えているものである。**自分で始めたコードだけを承認する。**
デバイスコードはフィッシングの道具になる。コードを持つ者は、利用者に承認させたログインを自分のものにできる。

## 決定

### 決定 1 — 端末が無いとき、`af-aws-exec` は失敗するだけでなくログイン依頼を出す

ログインが要り、`--no-login` が無く、端末の前に誰もいないとき、`af-aws-exec` は**ログイン依頼**を登録し、
そのあと待つ（決定 5）。

- 依頼は Agent の状態ディレクトリ（`paths.AgentStateDir()/aws-login/`）のファイルで、CLI のプロセス自身が
  ロックを取って書く。依頼を出すのに Agent のルートは要らない。依頼は Agent の再起動を越えて残り、Agent が
  動いていなくても出せる。
- **sso-session ごとに依頼は 1 件。** 同じ sso-session に対する 2 本目の `af-aws-exec` は、既存の依頼に待ち手と
  して加わる。今は Settings のプロファイルごとに固有の sso-session（`af-<name>`）があるので、実際にはプロファイル
  ごとに 1 件になる。
- 依頼には、プロファイル名、最初と最後に依頼された時刻、待ち手（`AF_SESSION_NAME` があれば依頼元セッションの
  名前と、コマンドの先頭の語）を記録する。**利用者に見せるアカウントとロールは依頼から取らない。** Agent が依頼を
  表示するときに Settings のプロファイルから引く。呼び出し側が誤解を招くアカウントを画面に出すことはできない。
- この方法でログインできるのは **Settings のプロファイル**だけである。利用者が自分の `~/.aws` に定義した
  プロファイル（`--account` を付けて実行する）については、表示するアカウントとロールの確かな出どころが Agent に
  無い。その場合は今までどおり exit 3 と端末用のコマンドを返す。
- 依頼は、最後に `af-aws-exec` が依頼してから 15 分で失効する。

### 決定 2 — Console は画面下部に消えないトーストを出し、「ログイン」ボタンを置く

依頼を出すと、新しい種類 `aws-login-required` の通知も送信箱に書く（依頼ごとに 1 件で、待ち手ごとではない。
依頼をキーにした `notice.PutOnce`）。宛先は、分かれば依頼元のセッション、分からなければワークスペースである。

通知が届くと、Console は**画面下部に消えないトースト**を出す。「新しいバージョンがあります」のトースト
（`UpdateToast`、`duration: 0`）と同じ形である。トーストには、プロファイル、アカウントとロール、依頼元を書く。
ボタンは 1 つ、**ログイン**で、ログインモーダルを開く（決定 3）。

- 通知センターだけでは足りない。依頼は人を待っていて、エージェントのコマンドがそれを待っている間に、センターの
  1 行は見落とされやすい。
- Console はモーダルを自分では開かない。端末ペインで入力している最中にモーダルが出ると、打鍵を奪う。
- 依頼が片付くとトーストは消える。片付くのは、ログイン済み（どのタブからでも、端末からでも）、キャンセル、
  失効のいずれかである。表示は通知をその場で受け取れたかどうかにも依らない。Console は起動時に保留中の依頼を
  1 回問い合わせるので、再読み込みしても失われない。

### 決定 3 — デバイスコードは押下で始まり、押したタブにだけ表示される

モーダルの「ログイン」は `POST /api/aws-login/{id}/start` を呼ぶ。そのときに初めて、Agent のデーモンがその
sso-session について `aws sso login --use-device-code --no-browser` を実行する。実行はどのペインの外でもなく、
Settings から描いた sso-session だけを持つ設定ファイル（`ssoOnlyConfig` と同じ形）で行う。Agent はコマンドの
出力から、`parseSSMLogin` と同じパターンで確認 URL とコードを読む。

`start` は**試行 ID** を返す。モーダルは `GET /api/aws-login/{id}/attempts/{attempt}` をポーリングし、その試行の
URL とコードだけを表示する。`start` のたびに新しい試行が始まり、それまで走っていた試行は終わる。これにより、

- コードが画面に出るのは、その試行を作った押下のあったタブのモーダルだけである。
- エージェントが自分で `start` を呼んでも（`AGENT_TOKEN` を持っている）、その試行はどのモーダルにも表示されない。
  そのコードでエージェントにできること——チャットに書く——は、今でも自分のシェルで `aws sso login` を実行すれば
  できる。その場合はガイドの規則が扱っていて、この設計はそれを弱めない。
- エージェントの `start` が利用者の試行を終わらせた場合、モーダルは試行が置き換えられたと伝え、もう一度始めるよう
  促す。別の試行のコードに切り替わることは決してない。

「キャンセル」は `POST /api/aws-login/{id}/cancel` を呼ぶ。走っている試行を終わらせ、依頼を取り下げる。待っている
`af-aws-exec` はすぐに exit 3 で終わり、利用者が Console でログインを断ったと伝える。

デバイスコードの表示（コード、利用者が手で開く「サインイン」ボタン、注意書き）は `SsmLoginModal` から 1 つの
部品に切り出し、両方のモーダルで使う。`SsmLoginModal` の props と `ssmResume` の store は変えない。

### 決定 4 — Control Plane は 4 本のルートを中継し、開始とキャンセルを監査する

CP は、メンバーのエージェントプロキシに `GET /api/aws-login`、`POST /api/aws-login/{id}/start`、
`GET /api/aws-login/{id}/attempts/{attempt}`、`POST /api/aws-login/{id}/cancel` を加える。対象はメンバー自身の
Workspace だけである。`start` と `cancel` を、プロファイル名付きで `aws.login.start` / `aws.login.cancel` として
監査する。コードと URL はログにも監査にも残さない。

### 決定 5 — `af-aws-exec` は約 90 秒待ち、依頼を保留にしたまま exit 3 で終わる

依頼を出したあと、`af-aws-exec` は Console でログインを依頼したと表示し、最大 90 秒待つ。90 秒はエージェントの
ツール呼び出しのタイムアウトに収まる。

- 待つ間は依頼ファイルを読む（安い）。Agent が試行の成功を記録したとき、あるいはいずれにせよ 15 秒ごとに
  （端末でのログインは依頼に触れない）、CLI に認証情報をもう一度求める（`exportCreds`）。
- 認証情報が返れば、最初からログインしていたのと同じようにコマンドを実行する。
- 時間切れなら exit 3 で終わる。メッセージは、Console でログインを依頼したこと、承認したらコマンドをもう一度実行
  することを伝える。依頼は保留のまま残るので、トーストも残る。

### 決定 6 — フラグと端末の場合は変えない

- 本物の端末での `--login` は、端末内のデバイスコードのログインのまま。
- `--no-login` は依頼を出さず、待たない。
- exit 3 の意味は保つ。「SSO ログインが要り、ここでは完了していない」。

`workspace/notes/aws.md`（`af-aws` スキル）と `guide/member/10-integrations.md` に、新しい exit 3 の文言を書く。
エージェントには、利用者に端末を開くよう頼むのではなく、ログインが Console で待っていると伝えるよう書く。

## 却下した案

- **CLI が Agent のルートを呼んで依頼を出す。** 送信箱と同じく、状態ディレクトリを使えば Agent 無しで出せる。
  ルートにすると失敗の仕方が増えるだけで、守りは増えない。呼び出し側はどちらにせよ `AGENT_TOKEN` を持っている。
- **`start` をエージェントから隠す。** どのルートも `AGENT_TOKEN` で呼べる。Console のトークンとエージェントが持つ
  トークンを分けるのは、CP↔Agent の認証の大きな変更になる。コードを押下に結びつける（決定 3）ことで、それをせずに
  肝心の性質が得られる。
- **Console がモーダルを自分で開く**（Issue の最初の素案）。入力を遮る（決定 2）。
- **通知センターだけ。** コマンドが待っているものとしては見落としやすい（決定 2）。
- **SSM セッションと同じく、デバイスコードを呼び出し元のシェルで走らせて画面から読む。** エージェントのシェルには
  Console が表示するペインが無く、誰も何も押す前にコードが始まってしまう。

## 結果

- 利用者は `af-aws-exec` の流れの間ずっと Console の中にいられる。エージェントが見るのは、完了したコマンドか、
  ログインが Console で待っていると伝える exit 3 のどちらかになる。
- 消えないトーストの新しい種類ができる。今のトーストの仕組みにはコードからトーストを取り下げる手段が無いので、
  実装でそれを加える。
- ここで扱わず、それぞれ別の Issue にするもの: Settings > SSM のプロファイル行から同じモーダルを開く「ログイン」、
  SSO セッションが切れる前の警告。実際の IAM Identity Center での受け入れ実行も、利用者が行うまで残る。
