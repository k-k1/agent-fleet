# 0102. `af-aws-exec` は SSO ログインを Console に依頼し、デバイスコードは利用者の押下でだけ始まる

[English](0102-aws-login-through-the-console.md) | 日本語

- 状態: **proposed**（2026-09-27）。実装は別の変更で行う。
- Issue: #1026
- Follow-ups: #1028, #1029
- 関連: #1010（`af-aws-exec` の受け入れ。この穴が見つかった場）／#1025（SSM の再開ボタンがログインモーダルを
  飛ばしていた件。デバイスコードの表示部品を共有する）

## 背景

`af-aws-exec` は Settings > SSM のプロファイル 1 つの認証情報でコマンドを実行する。IAM Identity Center の
キャッシュ済みログインが無いか期限切れのとき、ログインするのは端末の前に人がいる場合だけである
（`awsx.PlanExec`、`Login: "auto"`）。エージェントのシェルには端末が無いので、コマンドは exit 3 で終わり、
`aws sso login --profile <name> --use-device-code --no-browser` を表示する。エージェントは利用者に、端末を開いて
これを実行するよう頼むしかない。#1010 の受け入れ実行では、利用者が Console を離れなければならない手順はここだけ
だった。

Console に要るものの大半はすでにある。

- **トークンのキャッシュは 1 つ。** SSM セッションと `af-aws-exec` は同じ `[sso-session af-<name>]`
  （Settings から `awsx.renderProfile` が描く。`ssoOnlyConfig` は意図してこの名前を保つ）と同じ
  `~/.aws/sso/cache` を使う。どこでログインしても両方に効く。
- **デバイスコードの表示。** `SsmLoginModal` が SSM セッションのログインの確認 URL とコードを表示する。
  Agent はそれをセッションの tmux ペインから読む（`parseSSMLogin`）。
- **Console への経路。** 通知の送信箱（`internal/notice`）。`workspace-agent notify-arch-residue` と同じく、
  CLI の子プロセスから直接書ける。Control Plane は取り出した通知を種類も中身も問わず保存するので、新しい種類に
  CP の変更は要らない。

Issue の素案を変える事実が 1 つある。**エージェントのシェルは `AGENT_TOKEN` を持っている。** af の MCP サーバが
Agent に届くように渡されていて（`mcpreg/attach.go`）、Control Plane が使うのと同じトークンである。したがって
エージェントのセッション内のどのプロセスも、Agent のどのルートでも呼べる。「デバイス認可を始められるのは Console
だけ」は、ルートを呼べる者を絞ることでは守れない。

守るべき規則は `workspace/notes/aws.md` が教えているものである。**自分で始めたコードだけを承認する。**
デバイスコードはフィッシングの道具になる。コードを持つ者は、利用者に承認させたログインを自分のものにできる。

### この設計が守るもの、守らないもの

エージェントは Agent と同じユーザーで動く。そのユーザーが書けるものはエージェントも書ける。送信箱、依頼ファイル、
`~/.aws/sso/cache`、そして `aws` のバイナリそのもの（`install-awscli` は `~/.local/bin` に置く）である。したがって
利用者自身のワークスペースにいる敵対的なエージェントは、この設計が守れる範囲の**外**にいる。そのエージェントは、
誰かがログインしたあとでキャッシュからトークンを読めるし、`aws` を差し替えて、利用者自身の押下で自分の選んだ
コードを表示させることもできる。

この設計が守るのは次のことである。

- 利用者の押下以外で始まったコード——開始ルートを呼んだエージェント、チャットに書かれたコード、ワークスペースの
  外から来たコード——は、Console のモーダルにもトーストにも決して出ない。
- Console が表示するアカウント、ロール、確認 URL は Settings から取り、Settings と照合したものであって、呼び出し側が
  書いた文字ではない。

それ以外については、引き続きガイドの規則が利用者を守る。

## 決定

### 決定 1 — 端末が無いとき、`af-aws-exec` は失敗するだけでなくログイン依頼を出す

ログインが要り、`--no-login` が無く、端末の前に誰もいないとき、`af-aws-exec` は**ログイン依頼**を登録し、
そのあと待つ（決定 5）。

- 依頼を出すのは、ログインの前に `PlanExec` がすでに行っている検査をすべて通ってからである。プロファイルが
  書き出されていること、利用者自身の定義に隠されていないこと、欠けがないこと、`[DEFAULT]` で差し止められていない
  こと。そうでないと、利用者自身の節も使っている `af-<name>` のキーにデーモンがログインしかねない。
- 依頼は Agent の状態ディレクトリ（`paths.AgentStateDir()/aws-login/`）のファイルで、CLI のプロセス自身が
  ロックを取って書く。依頼を出すのに Agent のルートは要らない。依頼は Agent の再起動を越えて残り、Agent が
  動いていなくても出せる。
- **sso-session ごとに依頼は 1 件。** 同じ sso-session に対する 2 本目の `af-aws-exec` は、既存の依頼に待ち手と
  して加わる。今は Settings のプロファイルごとに固有の sso-session（`af-<name>`）があるので、実際にはプロファイル
  ごとに 1 件になる。依頼にはそれぞれ乱数の ID があり、依頼を作るたびに新しくなる。
- 依頼には、プロファイル名、最初と最後に依頼された時刻、待ち手（`AF_SESSION_NAME` があれば依頼元セッションの
  名前と、コマンドの先頭の語）を記録する。どちらもエージェントが書いた文字である。保存する前に短い長さと限られた
  文字種に切り詰め、「誰が依頼しているか」としてだけ表示し、アカウントについての記述としては決して表示しない。
- **利用者に見せるアカウントとロールは依頼から取らない**（決定 2）。
- この方法でログインできるのは **Settings のプロファイル**だけである。利用者が自分の `~/.aws` に定義した
  プロファイル（`--account` を付けて実行する）については、表示するアカウントとロールの確かな出どころが Agent に
  無い。その場合は今までどおり exit 3 と端末用のコマンドを返す。
- 依頼には、**依頼を出した時点の sso-session のトークンキャッシュの状態**を記録する。無いか、あればキャッシュ
  ファイルの `expiresAt` とトークンのハッシュである。キャッシュには、期限切れでないのに AWS が拒否するトークンが
  あり得る（セッションが取り消された、またはポータルのセッションが先に終わった。`loginNeeded` はまさにその
  botocore のメッセージに一致する）。そのため決定 2 と 5 は、期限切れでないキャッシュだけでなく、**依頼の時点から
  変わった**キャッシュを探す。既存の依頼に加わる実行は、自分の失敗した確認が見た状態が記録と異なれば、同じロックの
  下で記録をその状態に置き換える。こうして記録は常に、使えないと分かっているキャッシュを表す。
- 「確認が見た状態」とは、認証情報を求める**前に**読んだスナップショットであって、あとで読んだものではない。確認が
  失敗したあとでキャッシュファイルがそのスナップショットと異なっていれば、その間にログインが済んだかもしれない。
  その場合、実行は何も記録せず、認証情報をもう一度だけ求める。あとで読んだ状態を記録すると、正しいログインを
  使えないものとして記録してしまい、依頼はいつまでも片付かない。
- **依頼を失効させるのは Agent だけである。** 最後に `af-aws-exec` が依頼してから 15 分で依頼を捨てるが、Agent が
  その依頼のために走らせている試行が生きている間は捨てない（決定 3）。CLI は依頼ファイルを決して消さない。Agent
  の試行が見えないからである。

### 決定 2 — Console は画面下部に消えないトーストを出し、「ログイン」ボタンを置く

依頼を出すと、新しい種類 `aws-login-required` の通知も送信箱に書く。通知は依頼ごとに 1 件で、待ち手ごとでは
ない。依頼の乱数 ID をキーにした `notice.PutOnce` なので、あとで同じプロファイルに新しい依頼ができれば、それにも
通知が出る。宛先は、分かれば依頼元のセッション、分からなければワークスペースである。

**通知はきっかけにすぎない。** 利用者のユーザーで動くものなら誰でも送信箱に好きな中身を書けるので、Console は
通知から依頼 ID 以外を読まない。通知が届くと、`GET /api/aws-login` で Agent に問い合わせる。Agent は保留中の
依頼をそれぞれ Settings のプロファイルと突き合わせ、プロファイル、Settings のアカウントとロール、決定 1 の
待ち手、依頼がまだ保留中かどうかを返す。Agent が知らない ID には何も表示しない。

依頼がまだ保留中なら、Console は**画面下部に消えないトースト**を出す。「新しいバージョンがあります」のトースト
（`UpdateToast`、`duration: 0`）と同じ形である。トーストには、プロファイル、アカウントとロール、依頼元を書く。
ボタンは 1 つ、**ログイン**で、ログインモーダルを開く（決定 3）。

- 通知センターだけでは足りない。依頼は人を待っていて、エージェントのコマンドがそれを待っている間に、センターの
  1 行は見落とされやすい。
- Console はモーダルを自分では開かない。端末ペインで入力している最中にモーダルが出ると、打鍵を奪う。
- **依頼が片付いたかどうかは Agent が決める。** 依頼が片付くのは、その sso-session のトークンキャッシュ
  （`~/.aws/sso/cache/<sso-session 名の sha1>.json`）が依頼の時点（決定 1）から変わっていて、かつ期限切れでない
  トークンを持つときである。ログインがこの Console、別のタブ、端末のどこで行われたかは問わない。依頼の時点から
  あって変わっていないキャッシュは、`expiresAt` がどれほど先でも何も片付けない。そのファイルを読むのはファイル
  読み 1 回で、`aws` の実行ではない。Agent は片付いた依頼を捨てる。キャンセルされた依頼と失効した依頼も捨てる
  （決定 1 と 3）。
- トーストが出ている間、そのタブは数秒ごとに `GET /api/aws-login` を問い合わせ、依頼が保留でなくなればトーストを
  消す。Console は起動時にも 1 回問い合わせるので、再読み込みしても保留中の依頼は失われない。トーストが出て
  いないときは何もポーリングしない。
- トーストの閉じるボタンは、そのタブでだけトーストを隠す。次に再読み込みしたとき、または新しい依頼の通知が
  届いたときに再び出る。依頼そのものは保留のまま残る。

### 決定 3 — デバイスコードは押下で始まり、押したタブにだけ表示される

モーダルの「ログイン」は `POST /api/aws-login/{id}/start` を呼ぶ。そのときに初めて、Agent のデーモンがその
sso-session について `aws sso login --use-device-code --no-browser` を実行する。実行はどのペインにも属さず、
Settings から描いた sso-session だけを持つ設定ファイル（`ssoOnlyConfig` と同じ形）で行う。Agent はコマンドの
出力から、`parseSSMLogin` と同じパターンで確認 URL とコードを読む。

- **URL は表示する前に検査する。** ホストは、プロファイルの Settings から組み立てた固定の一覧のどれかと、
  部分一致や末尾一致ではなくホスト名全体として完全に一致しなければならない。一覧は、`sso_region` のデバイス認可
  ホスト（そのリージョンのパーティションのもの。`amazonaws.com`、中国なら `amazonaws.com.cn`）と、開始 URL の
  ホストである。それ以外なら試行を失敗として終え、モーダルがその理由（「想定外のサインイン URL」）を伝える。
  `parseSSMLogin` のパターンはどの https ホストでも受け入れ、`device\.sso\.` は `device.sso.evil.example` の中にも
  一致するので、検査はパターンとは別の段階で行う。
- 試行が成功するのは、コマンドが exit 0 で終わり、そのあと決定 2 のトークンキャッシュに期限切れでないトークンが
  あるときである。パターンは端末の出力でしか確かめられていない。実装を受け入れる前に 2 つを実測する。CLI が
  ブロックする前に URL とコードをパイプへ書き出すこと、そして新しいポータルのドメインの開始 URL の場合も含めて、
  CLI がどのホストを表示するかである。受け入れるホストの一覧はその実測に従う。

`start` は**試行 ID** を返す。モーダルは `GET /api/aws-login/{id}/attempts/{attempt}` をポーリングし、その試行の
URL とコードだけを表示する。`start` のたびに新しい試行が始まり、それまで走っていた試行は終わる。これにより、

- コードが画面に出るのは、その試行を作った押下のあったタブのモーダルだけである。
- エージェントが自分で `start` を呼んでも、その試行はどのモーダルにも表示されない。そのコードでエージェントに
  できること——チャットに書く——は、今でも自分のシェルで `aws sso login` を実行すればできる。その場合はガイドの
  規則が扱っていて、この設計はそれを弱めない。
- 別の `start` が利用者の試行を終わらせた場合、モーダルは試行が置き換えられたと伝え、もう一度始めるよう促す。
  別の試行のコードに切り替わることは決してない。
- `start` を呼び続けるエージェントは利用者の試行を置き換え続けられるので、利用者はいつまでも終えられない。これは
  受け入れる。目に見える（モーダルが置き換えられたと伝える）し、誰もログインさせないし、そこまで敵対的な
  エージェントは同じユーザーとしてもっと悪いことがすでにできる。
- `GET /api/aws-login` は試行 ID、URL、コードを決して返さない。それらを返すのは試行のルートだけで、問い合わせ
  られた試行 ID の分だけである。

試行は Agent のメモリにある。試行の途中で Agent が再起動すると、`aws sso login` の子プロセスも一緒に終わり、
`GET …/attempts/{attempt}` は試行が無くなったと答え、モーダルはもう一度始めるよう促す。依頼そのものはディスクに
あって保留のまま残る。

「キャンセル」は `POST /api/aws-login/{id}/cancel` を呼ぶ。Agent は走っている試行を終わらせ、同じディレクトリに
その sso-session の**キャンセル印**（キャンセルした依頼の ID、プロファイル、キャンセルした時刻、依頼に記録された
キャッシュの状態）を書き、そのあとで初めて依頼を取り下げる。待っている `af-aws-exec` は印を読んですぐに exit 3 で
終わり、ログイン依頼が**キャンセルされた**と伝える（利用者が断った、とは言わない。エージェントもこのルートを
呼べる）。待ち手が反応するのは自分の依頼を名指す印だけなので、以前の依頼の印が残っていても待ちは終わらない。

キャンセルから 10 分間は、そのプロファイルの新しい `af-aws-exec` は印を見つけて依頼を出さず、トーストも出さない。
これが無いと、次の実行でトーストがすぐに戻ってきてしまう。すぐに exit 3 で終わり、Console でログインがキャンセル
されたことを伝え、端末用のコマンド（`aws sso login --profile <name> --use-device-code --no-browser`）を表示する。
#1028 までは、その間に Console からログインする手段が他に無いからである。記録されたキャッシュの状態が今の
キャッシュと合わなくなった印は無効とみなす。別の場所でのログインで意味が無くなったからである。印を書くのも消す
のも Agent だけである。

デバイスコードの表示（コード、利用者が手で開く「サインイン」ボタン、注意書き）は `SsmLoginModal` から 1 つの
部品に切り出し、両方のモーダルで使う。`SsmLoginModal` の props と `ssmResume` の store は変えない。

### 決定 4 — Control Plane は 4 本のルートを中継し、開始とキャンセルを監査する

CP は、メンバーのエージェントプロキシに `GET /api/aws-login`、`POST /api/aws-login/{id}/start`、
`GET /api/aws-login/{id}/attempts/{attempt}`、`POST /api/aws-login/{id}/cancel` を加える。対象はメンバー自身の
Workspace だけである。`start` と `cancel` を、プロファイル名付きで `aws.login.start` / `aws.login.cancel` として
監査する。

この監査が扱うのは CP を通ったものだけである。エージェントは `AGENT_TOKEN` で同じルートを Agent に直接呼べる。
そのため Agent も、開始とキャンセルをすべて自分のログに、プロファイル名と CP 経由だったかどうかを付けて書く。
コードと URL は、どちらの側でもログにも監査にも残さない。

### 決定 5 — `af-aws-exec` は約 90 秒待ち、依頼を保留にしたまま exit 3 で終わる

依頼を出したらすぐに、`af-aws-exec` は Console でログインを依頼したと表示する。待つ前に真っ先に表示するので、
呼び出し側のタイムアウトで殺された実行でも、それは伝わっている。そのあと最大 90 秒待つ。

- 待つ間は 2 秒ごとに、依頼ファイル、キャンセル印、sso-session のトークンキャッシュを読む（安い）。CLI に
  認証情報をもう一度求める（`exportCreds`。`aws` を丸ごと 1 回起動する）のは、キャッシュが依頼の時点に記録した
  状態から変わっていて、かつ期限切れでないトークンを持つときだけである。2 秒ごとではなく、変化 1 回につき 1 回で
  ある。
- 認証情報が返れば、最初からログインしていたのと同じようにコマンドを実行する。
- それでもログインの問題で失敗するなら、Agent はすでに依頼を片付いたものとして捨てているかもしれない（キャッシュが
  変わった。同じ sso-session の別の利用者が更新するだけで起きる）。その場合、実行は**新しい**依頼を出し——新しい
  乱数 ID、見たキャッシュの状態（決定 1 のスナップショット）、新しい通知——残りの時間を待ち続ける。無くなった
  依頼を待つことは決してない。出し直しも、新しい実行と同じキャンセル抑止の確認を通る。その sso-session に有効な
  キャンセル印があれば、何も出さずにキャンセルとして exit 3 で終わる。
- 自分の依頼のキャンセル印が現れたら、すぐに exit 3 で終わる（決定 3）。印の無いまま依頼ファイルが消えたら
  片付いたという意味で、認証情報を求める。失敗したら上の規則に従う。
- 時間切れなら exit 3 で終わる。メッセージは、Console でログインを依頼したこと、承認したらコマンドをもう一度実行
  することを伝える。依頼は保留のまま残るので、トーストも残る。

90 秒は、エージェントのコマンドのタイムアウトがそれより長いことを前提にしている。実装を受け入れる前に、エージェント
の種類ごとに 2 つを実測し、実装の作業記録に残す。シェルコマンドの既定のタイムアウトと、そのタイムアウトで殺された
コマンドの途中までの出力がエージェントに渡るかどうかである。上の即時の表示がログインの待ち場所をエージェントに
伝えられるのは、その出力が残る場合だけである。`AF_SESSION_NAME` があれば、`af-aws-exec` はそのセッションの
メタを読み（種類が書いてある）、その種類の待ち時間を取る。90 秒か、その種類のタイムアウトがそれより短く出力を捨てる
なら、そのタイムアウトより短い時間である。種類が分からないとき（Managed セッションには `AF_SESSION_NAME` が無い
ことがある）は、全種類のうち最も短い待ち時間を取る。メタが種類を示していても、作業記録に実測が無い種類
（スクリプトを走らせる shell や ssm のセッション、あとから加わった種類）は、分からないものとして扱う。

### 決定 6 — フラグと端末の場合は変えない

- 本物の端末での `--login` は、端末内のデバイスコードのログインのまま。
- `--no-login` は依頼を出さず、待たない。
- exit 3 の意味は保つ。「SSO ログインが要り、ここでは完了していない」。

`workspace/notes/aws.md`（`af-aws` スキル）とメンバーガイドの連携の章（`guide/member/10-integrations.md` と
`10-integrations.ja.md`）に、新しい exit 3 の文言を書く。エージェントには、利用者に端末を開くよう頼むのではなく、
ログインが Console で待っていると伝えるよう書く。

## 却下した案

- **CLI が Agent のルートを呼んで依頼を出す。** 送信箱と同じく、状態ディレクトリを使えば Agent 無しで出せる。
  ルートにすると失敗の仕方が増えるだけで、守りは増えない。呼び出し側はどちらにせよ `AGENT_TOKEN` を持っている。
- **`start` をエージェントから隠す。** どのルートも `AGENT_TOKEN` で呼べる。Console のトークンとエージェントが持つ
  トークンを分けるのは、CP↔Agent の認証の大きな変更になる。コードを押下に結びつける（決定 3）ことで、それをせずに
  肝心の性質が得られる。
- **Console がモーダルを自分で開く**（Issue の最初の素案）。入力を遮る（決定 2）。
- **通知センターだけ。** コマンドが待っているものとしては見落としやすい（決定 2）。
- **SSM セッションと同じく、デバイスコードを呼び出し元のシェルで走らせて画面から読む。** エージェントのシェルには
  Console が表示するペインが無く、誰も何も押す前にコードが始まってしまう。
- **トーストの文を通知の中身から組み立てる。** 送信箱はどのエージェントでも書けるので、表示されるアカウントは
  何にでもなり得る（決定 2）。

## 結果

- 利用者は `af-aws-exec` の流れの間ずっと Console の中にいられる。エージェントが見るのは、完了したコマンドか、
  ログインが Console で待っていると伝える exit 3 のどちらかになる。
- 消えないトーストの新しい種類ができる。今のトーストの仕組みにはコードからトーストを取り下げる手段が無いので、
  実装でそれを加える。
- ログインのトーストを出しているタブは、依頼が片付くまで数秒ごとに安い Agent のルートを 1 本ポーリングする。
- コマンドのタイムアウトが短い種類や、種類の分からない呼び出し元では、利用者が承認するのに待ち時間が足りない
  ことがある。その場合エージェントがふつう目にするのは、承認後に完了するコマンドではなく、exit 3 と再実行である。
- ここで扱わず、それぞれ別の Issue にするもの: Settings > SSM のプロファイル行から同じモーダルを開く「ログイン」、
  SSO セッションが切れる前の警告。実際の IAM Identity Center での受け入れ実行も、利用者が行うまで残る。
