## 背景

利用ガイド（`guide/`）は網羅的で正確だが、読みにくい。英語で 175,603 語あり、日本語も同じだけある。6,000 語を超える
章がいくつもある（`member/16-cloud-accounts.md` は H2 が 2 つで 10,861 語）。タイトルは機能を 3〜5 個並べたもの
（「ファイル — ツリー・ビューア・Markdown/スライド」）で、1 つの段落に手順・例外・設計の理由・復旧が混ざっている。
エージェントは grep でうまく引けるが、1 つの作業を探す人は要点を見つけられない。

利用者は、ガイドをいまどきのドキュメントサイトの形で HTML として公開したいと考えている。上にトピックがあり、トピック
ごとにサイドバーがあり、1 ページ 1 機能の短いページで、検索があり、両言語がそろっている形である。変換だけでなく、
中身の再構成も求めている。

## 決定

### 1. 置き場所と作り方

- **`https://agent-fleet.org/docs/`** で配信する。サブドメインではなくパスにする（利用者の選択）。トップページの隣に置く。
- `k-k1/agent-fleet-site` で **Astro Starlight** を使い、**リリースタグ**から作る。`main` からは作らない。`main` には
  まだ出荷していない機能が書かれているからである。入力は `deploy/release/stage-docs.sh` の出力を使う。これは runbook と
  リリースノートをコピーし、そのリンクも書き換えて、すでにツリーを閉じている。
- いまの Cloudflare Pages は `site/` をそのまま配信している。`/docs/` を足すには、Actions からビルド結果を合わせて
  デプロイする形に変える。`_headers` には `/docs/` 用の CSP を足す。
- 検索は Starlight に付いている Pagefind を使う。*（パイロット）* 日本語の検索で、狙ったページが上位に出た。
  「子セッション」では `11-many-sessions` が先頭、「使用量の上限」では共同作業の章と `admin/02-limits` が上位だった。
- リンク検証（`starlight-links-validator`）を入れ、リンクやアンカーが壊れていればビルドを失敗させる。

### 2. 原本は `guide/` 1 つのまま

サイトは `guide/` のもう 1 つの描画先であって、別の原稿ではない。Console の利用ガイド、エージェントの知識、
`docs-check.py` は同じファイルを読み続ける。サイトに要るものは、変換スクリプトがすべて作る。

- タイトルは H1 から作り、サイドバーの表示名からは `NN.` を外す。
- `X.ja.md` は `/ja/X/` に、`README.md` はそのディレクトリの索引にする。言語切り替えの行は消す。
- 相対の `.md` リンクはサイトの経路にする。ステージしたツリーの外を指すリンクは、同じタグの GitHub を指す。
- GitHub のアラート（`> [!TIP]`）は Starlight の吹き出しにする。
- スクショは 2 倍で撮り、`width` に画素幅の半分を入れる。引き伸ばされないようにするためである。

**見出しの ID は、`guide/` では Console の規則に従う**（`console/src/lib/filemeta.ts` の `slug()`）。runbook は
github-slugger に従う。`docs-check.py` はすでにこの規則でガイドのアンカーを確かめている。*（パイロット）* Starlight の
既定の slugger では 77 個のアンカーが壊れた。Console の規則にすると、壊れたものはなかった。

### 3. トピックと 2 つの層

上に並べるトピックは **ユーザーガイド / チーム管理 / セルフホスト / リファレンス / リリースノート** で、ADR 0064 の棚に
合わせる。トピックごとにサイドバーを持つ（`starlight-sidebar-topics`）。

層は 2 つにする。

- **作業のページ**（ユーザーガイド、チーム管理、セルフホスト）: 読者のやりたいこと 1 つにつき 1 ページ。
- **リファレンス**: 網羅的に書く。コマンドは 1 つにつき 1 ページ、MCP ツールは一覧を 1 つ、それに今ある能力表。
  作業のページが省いた例外はここに置くので、正確な記述は失われない。

### 4. 作業のページの型

この型は、AWS のページで利用者が合意したもの（*パイロット*）。最初の下書きは一度差し戻されている。

- **タイトル**: 読者のやりたいことを動詞句で書く。「AWS SSO を使う」（"Use AWS SSO"）。名詞や列挙にしない。
- **冒頭**: 読み終えると何ができるようになるかを 1〜2 文で書く。
- **全体像**（"How it works"）: *あなたがやること* / *エージェントがやること* の 2 列の表。Agent Fleet のツールは
  エージェントが使うので、読者はまずこの分担を知る必要がある。
- 続けて **設定する**（画面つき）、**使う**（ログインのトーストのように画面に出るものも含める）、**もっと安全に使う**、
  **困ったとき**（症状ごと）、**関連**。
- **書かないもの**: 前置き（「会社の…」）と、秘密情報の扱い。秘密情報の扱いは、横断の 1 ページ「資格情報の扱い」にまとめる。
  仕様の例外はリファレンスへ移す。設計の理由は公開しない。
- **画面の文言はロケールのカタログから引用する**（`console/src/lib/i18n/locales/{en,ja}/`）。訳し直さない。

### 5. スクショ

- `console/scripts/shots/` で撮る。本物の Console のバンドルに架空のデータを入れて撮る仕組みである。リリースのたびに
  撮り直せるし、テナント、アドレス、本物のアカウント ID は写らない。
- ライトテーマで撮る。**写すのは、部品と、それを開く操作部だけにする**。ポップアップならそのバッジ、トースト、ダイアログ。
  周りのバーやペインまで写すと雑音になる。これは利用者からの明示的な指摘である。
- 撮影の仕組みには、要素の `clip`（複数のセレクタの範囲を合わせ、余白を足す）と、ドキュメント用の場面を足す。*（パイロット）*

### 6. リファレンスのページ

- **コマンド**（`af-aws-exec`、`af-gcloud-exec`、`af-db`、`af-memory`、`af-scratch`、`af-arch-repair`）: 1 つにつき
  1 ページ。一次情報であるコマンドの `--help` をもとに書く。
- **MCP ツール**: セッションの `af` サーバー、Console のアシスタント（読み取り / 書き込み）、Control Plane の `/mcp` と
  `/mcp/memory` を合わせて、ツール名は 81 個ある。一覧は、テストで固定しているツール一覧
  （`workspace/agent/internal/mcpx/testdata/mcp_tools/list.json`、`control-plane/internal/mcpsrv/testdata/mcp_tools/list.json`）
  から**生成する**。説明文は小さな日英の説明ファイルから入れ、一覧にあるツールに説明が無ければチェックで落とす。手で書いた
  一覧は、次にツールが増えたときに古くなる。

### 7. ページの作り方

1. ページの流れを利用者と合意する。読者が何をして何を見るかを 10 行ほどで書く。
2. 事実を集める。ロケールのカタログ、画面のコンポーネント、今のガイド、コードから。
3. スクショを撮る。
4. 日本語のページを書く。利用者は日本語でレビューする。
5. 別のモデルが、ページをソースに照らして事実確認する。*（パイロット）* 17 の記述を確かめ、誤りは 0 件、誤解を招くもの
   が 5 件あり、すべて直した。
6. 利用者が読む。
7. 英語のカタログを使って英語版を書き、日英を突き合わせ、両方を 1 つの変更に入れる。正は英語のままとする
   （`docs/CONVENTIONS.md` §5）。

## 結果として起きること

- **`guide/` のパスが変わる。** 古いリンクが動くように、転送表（`guide/_redirects.tsv`）を置く。`docs-check.py` が表を
  確かめ、`stage-docs.sh` が出荷するリリースノートの古いリンクを書き換え、サイトは転送を出す。`guide/` を指している
  `workspace/workspace-notes.md`、topic notes、Go のエラー文、Console のリンクは、ファイルと一緒に動かす。
- §4 と §5 の書き方ルールは、この記録が採用されたら `docs/CONVENTIONS.md` に入れる。
- Console の Markdown ビューア（`marked`）は GitHub のアラートを描画しない。ガイドで使う前に描画できるようにする必要がある。
- 長い作業になる。2 言語で約 110 ページあるので、棚ごとに分け、1 つの Issue で追う。

## パイロットで分かったこと

- **Cursor にはフリートの運用ルールが届かない**（`workspace/agent/agent_instructions.go`: "cursor cannot be reached at
  all"）。そのため Cursor は `af-aws-exec` を知らず、頼むときに伝える必要がある。ほかの 8 種類は知っている。AWS のページ
  にもそう書いた。
- 撮影用のスタブは `/api/ssm/profiles`、`/api/ssm/hosts`、`/api/ssm/sign-ins` にオブジェクトで答えていたが、Console は
  配列を期待している。そのため、撮影の仕組みでは 設定 › AWS プロファイル/SSM が必ずエラー表示になっていた。

## 採らなかった案

- **VitePress**: 組み込みの検索が日本語を分かち書きしない。
- **Docusaurus**: 重い。i18n が別のツリーを前提にしていて、`X.md` / `X.ja.md` の形に合わない。
- **ホスティングサービス（Mintlify など）**: ガイドがリポジトリの外に置かれ、リリースに固定しにくい。
- **`guide/` とは別に、サイト専用の原稿を書く**: 原稿が 2 つになるとずれていくし、Console のガイドは読みにくいまま残る。
- **再構成せずに変換だけする**: パイロットの 1 巡目は表示こそ問題なかったが、利用者は要点を見つけられなかった。

## 追記（2026-11-07）— 対応表とともに承認した。runbook も分ける

**上の決定は変わらない。** 今の文書から新しいページへの対応表を利用者と合意し、この記録で決めていなかった点も決めた。

- **対応表**は `k-k1/agent-fleet-site` の `docs/research/page-map.ja.md` にある。`guide/` と、出荷する runbook 6 本の
  H1〜H3 の見出し（748 個）を、227 のページのどれかに割り当てている。規則は TSV で、`docs/scripts/page_map.py` は、
  規則のない見出しや、どの見出しにも当たらない規則があると失敗する。「結果として起きること」のリダイレクト表は、
  この対応表から作る。
- **ページが小さくても、1 ページに 1 つの機能にする。** そのため 1 言語あたり 227 ページになり、上の見積もり
  （約 110 ページ）より多い。元の文章が 200 語に満たないページが 12 あるが、まとめない。
- **大きすぎる章はさらに分ける。** たとえば `operate/07-engines` の推論エンジンの節は、エンジンを動かす、モデルを取り込む、
  状態と履歴を見る、の 3 ページにする。`guide/ref/agents.md` は 1 ページのままにする。リファレンスは長くてもよい。
- **`member/lite` は各タスクのページに散らす。** 残すのは、ターミナルを使わない読者のための入口のページだけである。
- **`guide/member/` は `guide/user/` にする。** パイロットですでに使っている名前である。`admin/`・`operate/`・`ref/` は
  名前を変えない。
- **runbook も同じ型で分ける。** runbook はガイドの一部として出荷され（`stage-docs.sh` がコピーする）、ECS の runbook
  だけで 1 ページ 28,773 語あった。ECS は 20 ページ、Kubernetes は 9 ページにする。compose と native の runbook のうち、
  一般的な作業と重なる節は、`operate/` のその作業のページにまとめる。WSL と EC2 1 台は 1 ページのままにする。
  リポジトリでは、分けた runbook はディレクトリにして `README.md` を目次にし、`stage-docs.sh` はディレクトリごとコピーする。
- **コントリビューター向けの内容は公開しない。** ECS の動作確認の手順と、その E2E 完了ゲート、Kubernetes の
  live harness は、テンプレートそのものを確かめるためのもので、デプロイするだけの人は使わない。runbook を分けるときに
  `docs/` へ移す。これは ADR 0064 の分けかたを runbook に当てはめたものである。Agent Fleet を使う人（デプロイする人も
  含む）と、Agent Fleet を変える人を分ける。
- **§4・§5・§7 の書き方とスクショのルールは、`docs/CONVENTIONS.md` の §12 に移した。**
