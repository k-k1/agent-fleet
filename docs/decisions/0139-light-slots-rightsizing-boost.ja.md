## 背景

要望は「ライトなメンバーはもっと安いものに載せたい。実際の使用量からメンバーのインスタンスタイプを
賢く変えたい」。検討の俎上には 2 案——ライトなメンバー数人を 1 台の共有インスタンスに詰める案と、
メンバー毎に自動で右サイズ化する案——があり、議論の中から 3 つ目、メンバー自身が押す**ブースト**が出た。

### いまのコードが言っていること

- **メンバーの次の起動が何に載るかは、ランタイムではなく CP で解決される。** 全ての起動・リサイズの
  経路が通る `withResolvedSize`（`workspace_lifecycle.go`）が、メモリ要件（`resolveWorkspaceSize`:
  メンバーの `mem_limit` を、テナントとデプロイの上限で丸める）とクラス（`resolveSlotClass`: メンバー →
  テナント既定 → デプロイ既定。いずれもデプロイが宣言し、かつテナントの `AllowedSlotClasses` に含まれる
  もの。許可された宣言済みクラスが 1 つも無いときは、それでもデプロイ既定を返し、クラスが無いことで
  Start を失敗させない）を決める。ランタイムの `rungFor(classID, memBytes)`（`runtime_ecs_ec2_pool.go`）は、その後で
  そのクラスの中から宣言メモリが要件以上である最小の段を選ぶだけである。**要件 0 はそのクラスの最小の段**
  （ADR 0045 決定 21）。
- **Console はどちらにも尋ねない。** メンバー一覧とメンバー詳細は、保存された `mem_limit` とクラスから、
  `SizingProfile` が宣言する梯子の上で `slotFor` / `ladderFor`
  （`console/src/features/settings/parts/adminShared.ts`）を使って箱を計算し直す。
- **クラスと要件はメンバー毎**（`limits.go` の `SlotClass`、テナントは `AllowedSlotClasses` を持つ）で、
  **変更は次のコンテナ起動で反映**される（[70](../log/70-slot-instance-classes.md) §70.4.3）。したがって
  別の段への移動はすでに「次の Start が新しい種別のスロットを取り、home の EBS をそこに付ける」ことで
  ある。いまそれにかかる時間は決定 8 の 22〜27 秒**ではない**。ADR 0045 決定 10-5 と 12 が、Service
  Connect ありで 43〜110 秒に訂正している。
- **ワークスペースの上限は段から一律のホスト予約を引いたもの**: `workspaceMemCapMiB` は宣言 MiB −
  `ec2HostReserveFloorMiB`（2048）を返す。予約がこの大きさなのは、デーモン（実測 約 1.2〜1.4 GiB）と、
  段の宣言メモリと箱の実際の MemTotal との差（「8192 MiB」の m7i.large の MemTotal は 7784 MiB、実測）の
  両方を吸収しなければならないからである。予約は箱が小さくなっても縮まない。
- **出荷時の梯子は `large` から始まる**（`30-ingress.yaml` の `Ec2SlotTypes`: `standard` = m7i、
  `saver` = m6i、いずれも x86_64、8/16/32 GiB）。
- **Agent はすでにワークスペースを測っている**: `resources.Read()`（CPU は `cpu.stat` の `usage_usec`、
  メモリ）と `mempressure.Current()`（PSI `some`/`full` の avg10/avg60、ワーキングセット、refault 率）を
  Stats エンドポイントで返し、CP はそれを Console に素通しする（`agent_client.go`）。**CP はそれらの
  数値の履歴を持たない。** CP の利用サンプラ（`usage.go`、既定 5 分毎、`AF_USAGE_SAMPLE_INTERVAL`）が
  記録するのは稼働秒数だけである。Agent 自身の `mempressure.Series` は閾値決め用に、1 分 1 行で約 4 日分を
  ワークスペース上に持つ（ADR 0120 決定 8）。
- **CPU の数値は固定窓の測定ではない。** `cpuMeter`（`resources.go`）は、誰かの直前の Stats 呼び出し
  からの差分を返す。だから窓は、誰かが Console を開いている間は約 4 秒、それ以外は直前の呼び出しから
  の間隔になる。PSI はカーネルの最新の avg10/avg60 である。Stats クライアントは 5 秒で諦める
  （`agentStatsClient`）ので、忙しい箱ほど応答が得られにくい。
- **root ボリュームはスロット毎**で、`SlotRootVolumeGiB` の既定は 100（スロットが存在する間 約 $9.6/月、
  [70](../log/70-slot-instance-classes.md) §70.3）。アイドルのスロットがタイマーで terminate されるのは
  `Ec2SlotTerminateAfterSec` を設定したときだけである（ADR 0045 決定 23、既定 0 = しない）。それとは
  独立に、`makeRoom`（`runtime_ecs_ec2_slots.go`）は、プールの上限のせいで Start が失敗しそうなとき、
  別サイズの空きまたは休眠中の箱を terminate する。

## 決定 1 — いまは相乗りしない。ADR 0045 決定 8 はまだ成り立ち、最初の節約は小さい専有スロットで取る

**相乗りによる節約は実在し、箱が小さくなるほど大きくなる。** オンデマンド価格は同一ファミリ内で vCPU と
メモリに比例する（m6g・m7g・m8g・m6i・m7i で [70](../log/70-slot-instance-classes.md) §70.3 が実測）
ので、箱のメモリそのものは分けても分けなくても値段は同じである。詰めて浮くのは**箱毎に**払うもの、
つまり root ボリューム（ADR 0045 決定 8 が挙げている）とホスト予約である。予約は宣言メモリから一律
2 GiB なので、8 GiB の段の 4 分の 1、**4 GiB の段の半分**になる。例えば（見積もりであり、測定ではない）、
4 GiB のワークスペース上限 7 つは専有なら 8 GiB の箱 7 台（56 GiB）を要するが、32 GiB の箱 1 台なら
オーバーコミット無しに収まる（上限の合計 28 GiB ＋予約 2 GiB 1 つ）。オーバーコミット——上限の合計が
箱を超える——ならさらに浮くが、それだけは単独で除外する。ADR 0120 の発端の事故は、**メンバー 1 人だけ**で
8 GiB のスロットを 20 分の refault thrash に追い込んだものだった。

それでもいまは却下する。木から読んだ、相乗りの代償:

- **ENI の密度。** ワークスペースは `awsvpc`（`runtime_ecs_ec2_taskdef.go`）でタスク 1 つに ENI 1 本。
  ENI トランキング無しでは 1 台に載るタスクは数個しかない。
- **「1 スロット = 1 home」の規則すべて** — `freeSlots`、`releaseSlot`、`af-slot-idle-since`、アイドル停止
  （共有の箱は全員がアイドルになるまで止まらない）、隔離（1 回の隔離で N 人が落ちる）、eviction。
- **コストの帰属。** ADR 0048 はスロットを `af-membership` でメンバーに帰属させる。共有の箱は共有コスト
  になり、ADR 0048 決定 4 はそれを配分しない。
- **隔離。** root ボリューム・カーネル・書き込み層がメンバー間で共有になる（ADR 0045 決定 8 の
  「残る代償」が N 倍になる）。テナントをまたぐなら受け入れられない。

プールに別の Docker ホストを混ぜる形はさらに悪い。CP が走らせる `AF_RUNTIME` はちょうど 1 つで、
`docker` アダプタは Docker デーモンが CP と同じ場所にあることを前提にしている。

決定 2 は、それらの代償を一切払わずに、安い最初の一歩を取る。ワークスペースが 2 GiB に収まるメンバーは
8 GiB の箱から 4 GiB の箱に移る。取り残すのはまさに箱毎の予約と root であり、それが相乗りでさらに
浮かせられる分である。

**再検討するのは**、決定 3 の履歴が「持続的なワーキングセットが最小の軽量の箱に余裕をもって収まる
メンバーが多く、残る節約が箱毎の予約と root だ」と示したときである。その場合でも形は `ecs-ec2` の中の
同一テナント共有スロットであって、2 つ目のランタイムではない。

## 決定 2 — 軽量クラスは別建て・運用者宣言・オプトインのクラスとする。出荷時の梯子は変えない

運用者は既存の `id|label|arch|type:memMiB[:vcpu]` 構文で `AF_ECS_EC2_SLOT_TYPES` に軽量クラスを宣言する。
**パーサにも起動経路にも新しいものは要らない。**

🔴 **軽量の段を既存のクラスに入れない。** 要件 0 が最小の段に解決されるので、`standard` の下に
`medium` を足すと、サイズを一度も選んでいない全メンバーが、ワークスペース 2 GiB の 4 GiB の箱に黙って
移る。軽量の箱はメンバーか管理者が選ぶもの（または決定 4 が提案するもの）であって、梯子の編集が
メンバーに対して行うものではない。

候補（ガイドで推奨する前にどれも測る）:

| クラス（案） | arch | 段 | 理由 |
|---|---|---|---|
| `light-arm` | arm64 | m8g.medium（1 vCPU / 4 GiB）、m8g.large | `medium` は Graviton の m ファミリにしか無い。m8g は §70.3.2 でドルあたり最速 |
| `burst-arm` | arm64 | t4g.medium（2 / 4 GiB）、t4g.large（2 / 8 GiB） | バースト型。ワークスペースは大半アイドル（§70.3.3）で、ベースラインはアイドルの箱に要る分 |
| `burst-x86` | x86_64 | t3.medium、t3.large | home を x86_64 のまま保てる唯一の軽量案（アーキ移動無し、§70.5） |
| `mem-arm`（任意） | arm64 | r8g.medium（1 / 8 GiB） | 軽量ワークスペースが先に尽きるのは CPU ではなくメモリ |

- 🔴 **4 GiB の段はワークスペースの上限を 2048 MiB にする**（4096 − 2048。予約がすでに MemTotal との差を
  吸収しているので、それ以上は引かない）。デーモンが得るのは箱の実際の MemTotal − 2048 MiB で、4 GiB の
  箱でのその値も測っていない。エージェントのセッション 1 つと Agent が 2 GiB に収まるかは**測っていない**。
  この測定が、4 GiB の段をそもそも出すのか、軽量を 8 GiB から始めるのかを決める。小さい箱で予約を下げる
  ことはこの決定に含めない。予約を 2 GiB に上げたのは、それ未満で箱が thrash したからである。
- **バースト型クラスは `unlimited` クレジットモードで走らせる。** いまはスロットの起動テンプレート
  （`40-ec2-pool.yaml`）も CP も `CreditSpecification` を設定していないので、t クラスは EC2 の既定を
  受け取る。t4g と t3 の既定は文書上 `unlimited` である（このデプロイでは未確認、未解決の問い 2）。
  `standard` モードは、メンバーがビルドを待っているまさにそのときにベースラインへ絞る。`unlimited` は
  代わりに超過クレジットを課金し、それはメンバーのコスト行（ADR 0048）と履歴（決定 3）に持続的な
  CPU として現れる。それが決定 4 にとって、バースト型クラスから外す合図になる。
- **arm64 のクラスは、[70](../log/70-slot-instance-classes.md) が m8g のために要したものをすべて引き継ぐ**
  （multi-arch イメージ、arm64 AMI、アーキ毎の golden、§70.5 の home の一度きりの入れ直し）。x86 の
  バースト型クラスはどれも要らない。
- **断片化**（[70](../log/70-slot-instance-classes.md) §70.7）: クラス毎に予備スロットを持つので、軽量
  クラスは既存のクラスがすでに保持している root に、さらに root を足しうる。軽量メンバー 1 人の月の節約は
  保持される root 1 本と同じ桁である（見積もり: `medium` を実測の m8g.large $0.11594/h の半分とすると
  約 $0.058/h、160 h で m8g.large に対し約 $9.3 の節約。root は約 $9.6/月）。したがって軽量クラスが
  元を取るかは、それが余分に残すスロットの数と使うメンバーの数で決まる。ガイドはクラスの横で
  `Ec2SlotTerminateAfterSec` を推奨する。それがアイドルの予備スロットの積み上がりを止めるタイマーだから
  である。
- **出荷時の既定は無し**（ADR 0074 決定 1 の規則）: 例の梯子は、価格と 2 GiB の問いをデプロイ上で
  測るまでは提案にすぎない。

## 決定 3 — CP はメンバー毎の利用履歴を持つ

右サイズ化もガイドの助言も「このメンバーは実際にどれだけ使うか」を要し、いまは後からそれに答えられる
者がいない。

- **何を**: メンバー × 日 × **メンバーが実際に載った箱**（インスタンス種別、クラス、もしあればそこに
  載せたオーバーライド——決定 4）毎に 1 行。ブーストを含む日は 2 行になる。各行は、稼働分数、
  **信号毎の測定分数**、CPU の p50/p95、ワーキングセットの p95/最大、PSI `full` avg60 の最大と
  ADR 0120 の警告閾値を超えた分数、refault 率の p95、クラスのバーストベースラインを超えた分数を持つ。
- **箱は設定からではなく起動から取る。** Start が成功したとき、ランタイムは実際にタスクを置いた
  インスタンス種別を記録し、行はそれで引く。`withResolvedSize` から読み戻すと、変更から次の Start までの
  間——設定はすでに新しい箱を指し、メンバーはまだ古い箱にいる——に誤る。
- **固定窓で、Agent で集計する。** Stats エンドポイントの CPU には固定の窓が無く、PSI は時点の値で
  ある（背景）ので、どちらも CP から採取して分数にすることはできない。Agent はすでに 1 分 1 行を
  書いている（`mempressure.Series`）。そこに同じ 1 分の `usage_usec` の差分から CPU を足し、CP が返す
  カーソル以降の分の要約を出す。CP は利用サンプラの周期でそれを取り、日次の行に畳み込む。生の分単位の
  データは CP に保存しない。
- **稼働時間は CP から、測定は Agent から。** CP は全ての起動——開始、停止、箱とそれを選んだ
  オーバーライド——を記録し、稼働分数とブースト分数はその記録から読む。Agent の標本からは決して読まない。
  Agent の 1 分の行はどれも、Start で渡された起動の ID を持つので、その分は測られた箱に帰属する。
- **停止の境界。** サンプラの 2 回の周期の間に起動して停止したワークスペースは、稼働中に一度も
  取りに行かれない。そこで CP はタスクを止める直前に、時間を限った最善努力の取得を 1 回行い、まだ
  カーソルの後ろに残っているものは次の Start で取る。series は停止を生き延びる home 上にあり、起動の ID が
  それらの分を新しい箱ではなく古い箱に留める。それまでに series の約 4 日の窓から落ちた分は失われ、
  稼働したが未測定のままになる。
- **CPU を正規化するのは、段が vCPU を宣言しているときだけ**（任意の欄、`AF_ECS_EC2_SLOT_TYPES` の
  `type:memMiB[:vcpu]`）。無ければ列は NULL。バーストベースラインはいまの CP が知らないもので、バースト
  列が欲しいバースト型の段は梯子でベースラインを宣言する（新しい任意の欄）。無ければ列は NULL。
- **無いことはゼロではない**（`agent_client.go` の `memPressure` の規則）: Agent が測らなかった分は
  稼働分数ではあっても測定分数ではなく、Agent が読めない信号は NULL のままにする。忙しい箱ほど応答が
  得られにくいので、決定 4 はカバー率を脚注ではなく条件として使う。
- **保持** 90 日。決定 4 が要る窓に余裕を持たせた長さ。
- **見える人**: メンバーは自分のもの、テナント管理者は自テナントのもの（メンバー詳細の、ADR 0048
  決定 12 のコスト行の隣）。中身は持たず、資源の数値だけを持つ。

## 決定 4 — 右サイズ化はまず提案し、テナントが有効にしたところでだけ適用し、動作中のワークスペースは決して止めない

推奨器は決定 3 の履歴を読み、メンバー毎に**目標の段**（クラスとメモリ要件）を出す。

- **上げは速く、下げは遅く。** 上げ: PSI `full` が ADR 0120 の警告閾値を 7 日中 2 日、持続的に超える、
  またはワーキングセットの p95 が上限の 85% を超える。下げ: ワーキングセットの p95 が 1 段下の上限の
  50% 未満、**かつ** CPU の p95 が 40% 未満、を 14 稼働日。どの閾値もフェーズ 0 のデータが出るまで
  暫定である（ADR 0120 決定 8 と同様）。
- **下げにはカバー率が要る。** ある日が下げの根拠に数えられるのは、規則が読む全ての信号について、
  測定分数が稼働分数の一定割合（暫定: 80%）以上ある日だけで、メンバーのいまの箱の行だけを数える。
  欠けた分がメンバーを軽く見せることは決してない。上げは測れた分だけで判断してよい。
- **1 つのアーキの中で。** 自動の移動は x86_64 ↔ arm64 を決してまたがない。その移動は home の一部を
  入れ直す（§70.5）、メンバーか管理者の選択である。アーキをまたぐものは推奨器は提案だけする。
- **バースト型クラスでベースライン超えの CPU が持続したら、そこから外す提案をする**。移り先は、宣言済み・
  許可済み・同じアーキの非バースト型クラスで、段がいまのメモリ以上のもの。それが無いとき——出荷時の
  クラスは 8 GiB から始まる、またはテナントがバースト型クラスしか許していない——推奨器は提案と警告だけ
  をし、メンバーをテナントが許す範囲の外へ動かすことは決してない。
- **管理者の保存した選択は上書きしない。** 結果は、それを出した理由と履歴の窓をつけて、その横に保存する
  `auto` オーバーライドである。消せば保存された選択に戻る。
- **解決器は 1 つ、CP に置く。** オーバーライドは `withResolvedSize` で、ランタイムの `rungFor` が段を
  選ぶ前に適用し、Start の度にそこで再検査する。検査するのは、いまデプロイが宣言しているクラス、いまの
  テナントの `AllowedSlotClasses`、テナントとデプロイのメモリ上限（`resolveWorkspaceSize` の丸め）、
  保存された選択のアーキである。検査に落ちたオーバーライドは適用せず、`resolveSlotClass` が守れない
  クラスを報告するのと同じように報告する。デプロイ既定に落とすことは決してしない。それは別のアーキに
  ありうるからである。この厳格さはオーバーライドの経路の契約であり、保存された選択の既存の解決
  （最後の手段としてデプロイ既定に落ちること、背景）はこの記録では変えない。`rungFor` は純粋な段の
  選択器のままにする。
- **Console には教え、計算し直させない。** サイズの API はメンバー毎に 3 つを返す: 保存された選択、
  次の Start が使う箱（それを決めるオーバーライドといつまでか）、動作中のワークスペースが載っている箱。
  `slotFor` / `ladderFor` は梯子を描き続けるが、メンバーが「何を得るか」はもう決めない。
- **新しい境界**: どのオーバーライドも出られない、テナントの最小・最大の段。
- **適用は次の Start だけ。** 変更が動作中のワークスペースを止めたり再起動したりすることは無い。
  メンバーには前もって知らせる（「次の起動から m8g.large になります。理由は…」）。
- **フェーズ**: 0 — 履歴のみ（決定 3）。1 — テナント管理者とメンバーに提案を見せ、クリックで適用。
  2 — 自動。テナント毎、既定は無効、メンバー毎のオプトアウトつき。

## 決定 5 — ブースト: メンバーが時間を限って 1 段上を求める

- **何を**: メンバーのワークスペース画面の「ブースト」は、**次の Start がそうでなければ使う箱から 1 段上**
  （`auto` オーバーライドがあればその箱、無ければ保存された選択）を、その箱のクラスの中で N 時間取る。
  解決は決定 4 の解決器が行う。
- **`auto` とは別に保存し、順序を決める。** `boost` と `auto` はそれぞれ寿命を持つ別のオーバーライドで、
  **boost > auto > 保存された選択 > テナント既定**の順に解決する。推奨器はブーストの最中に `auto` を
  書き換えてよい。それはメンバーが戻る先を変えるだけで、ブーストは変えない。ブーストが切れたら、次の
  Start はその時点の `auto`（または保存された選択）が言う箱に載る。
- **いつ効くか**: 次の Start。ワークスペースが動作中なら、画面はブーストの目標と**ワークスペースが
  いま載っている箱**を比べる。目標の方が大きいときだけ「いますぐ大きい箱で再起動する」を示し、再起動が
  その中で動いているセッションを終わらせることを書く。目標が同じか小さいとき（例えば `auto` が下がった
  後も、期限切れのブーストの箱にまだ載っているとき）は、ブーストが次の起動から効くと書き、再起動は
  示さない。自分から再起動することは無い。
- **終わり**: 期限で `boost` オーバーライドを外す。動作中のワークスペースをメンバーの下で縮めることは
  決してないので、期限後も止まるまでは大きい箱のままでいられる。ブーストが有効な間のブーストは延長で
  あって、さらに上には登らない。期限後のブーストは、古いブーストの箱にまだ載っていても新しいブーストで
  あり、上と同じく次の起動の箱から計算する。
- **月の上限が数えるもの。** テナント管理者がブーストを有効にし、最高の段と、**ブーストでの稼働時間**の
  月の予算を決める。数えるのは、ブーストが載せた箱でメンバーが実際に稼働した時間で、CP の起動の記録
  （決定 3）から読み、**期限後の時間も含む**。付与されたが一度も起動しなかった
  時間は数えない。予算を使い切ったらボタンを無効にする。すでにブーストの箱で動いているワークスペースは
  それでも止めず、超過分をテナント管理者とコスト行に示す。
- **ADR 0120 との接点**: 圧力応答器が警告する、または新規セッションを拒むとき、その通知は「セッションを
  閉じる」だけでなくブーストを示す。

## 帰結

- 軽量クラスを宣言せず、テナントのスイッチを無効のままにしたデプロイでは何も変わらない。
- 履歴は、利用サンプラの周期毎に動作中ワークスペース 1 つにつき Agent への呼び出し 1 つと、メンバー ×
  日 × 箱毎に 1 行を足す。
- `withResolvedSize` は保存された選択の前にオーバーライドを持つ。Agent は分単位の要約エンドポイントを
  持つ。CP は全ての起動（箱、オーバーライド、開始と停止）を記録し、Agent の分を周期毎に加えて停止時と
  次の Start でも取る。Console のサイズ表示とスロットタブは、
  オーバーライドがどこから来たか（`auto` か `boost`）といつまでかを示す。さもないとメンバーは自分の箱が
  なぜ変わったか分からない。

## 却下した案

- **共有スロットでの相乗り、またはプールに混ぜた Docker ホスト** — 決定 1。
- **既存クラスへの `medium` の追加** — サイズを保存していない全メンバーを黙って動かす（決定 2）。
- **停止中スロットのその場でのリサイズ（`ModifyInstanceAttribute`）** — スロットはプールであり、目標の
  種別のスロットを取るのはすでに Start がしていること。その場の変更は、どのクラスも宣言していない
  種別のスロットをプールに残す。
- **動作中ワークスペースの自動リサイズ** — メンバーの同意無しにセッションを終わらせる。
- **CP が Pricing API から価格を読んで段を順位付けする** — 梯子の順序は運用者の宣言である（ADR 0045
  決定 21）。推奨器はドルではなく段で動く。
