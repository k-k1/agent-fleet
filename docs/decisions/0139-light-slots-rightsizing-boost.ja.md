## 背景

要望は「ライトなメンバーはもっと安いものに載せたい。実際の使用量からメンバーのインスタンスタイプを
賢く変えたい」。検討の俎上には 2 案——ライトなメンバー数人を 1 台の共有インスタンスに詰める案と、
メンバー毎に自動で右サイズ化する案——があり、議論の中から 3 つ目、メンバー自身が押す**ブースト**が出た。

### いまのコードが言っていること

- **メンバーの箱は `rungFor(classID, memBytes)`**（`runtime_ecs_ec2_pool.go`）で決まる。メンバーのクラスの
  中で、宣言メモリがメンバーのメモリ要件以上である最小の段。**要件 0 はそのクラスの最小の段**
  （ADR 0045 決定 21）。
- **クラスと要件はメンバー毎**（`limits.go` の `SlotClass`、テナントは `AllowedSlotClasses` を持つ）で、
  **変更は次のコンテナ起動で反映**される（[70](../log/70-slot-instance-classes.md) §70.4.3）。したがって
  別の段への移動はすでに「次の Start が別のスロットを取り、home の EBS をそこに付ける」だけである。
  ホットなスロットで 22〜27 秒、停止中からで約 50 秒（ADR 0045 決定 8、実測）。
- **ワークスペースの上限は段から一律のホスト予約を引いたもの**: `ec2HostReserveFloorMiB = 2048`。
  デーモンが約 1.2〜1.4 GiB と実測され、段の宣言は MemTotal を約 5% 上回るため（`workspaceMemCapMiB`）。
  予約は箱が小さくなっても縮まない。
- **出荷時の梯子は `large` から始まる**（`30-ingress.yaml` の `Ec2SlotTypes`: `standard` = m7i、
  `saver` = m6i、いずれも x86_64、8/16/32 GiB）。
- **Agent はすでにワークスペースを測っている**: `resources.Read()`（CPU は `cpu.stat` の `usage_usec`、
  メモリ）と `mempressure.Current()`（PSI `some`/`full` の avg10/avg60、ワーキングセット、refault 率）を
  Stats エンドポイントで返し、CP はそれを Console に素通しする（`agent_client.go`）。**CP は履歴を持たない。**
  Agent 自身の `mempressure.Series` は閾値決め用に約 4 日分をワークスペース上に持つ（ADR 0120 決定 8）。
- **root ボリュームはスロット毎**で、`SlotRootVolumeGiB` の既定は 100（スロットが存在する間 約 $9.6/月、
  [70](../log/70-slot-instance-classes.md) §70.3）。回収されるのは `Ec2SlotTerminateAfterSec` を設定した
  ときだけである（ADR 0045 決定 23、既定 0 = しない）。

## 決定 1 — 相乗りはしない。ADR 0045 決定 8 はまだ成り立ち、節約は小さい専有スロットで取る

ライトなメンバーを 1 台に詰めて得が出るのは**オーバーコミット**——上限の合計が箱を超える——のときだけ
である。オンデマンド価格は同一ファミリ内で vCPU とメモリに比例する（m6g・m7g・m8g・m6i・m7i で
[70](../log/70-slot-instance-classes.md) §70.3 が実測）ので、32 GiB の箱に 4 GiB の上限を 8 つ置くのは、
4 GiB の箱 8 台とちょうど同じ値段になる。そしてメモリはワークスペースがオーバーコミットできない唯一の
資源である。ADR 0120 の発端の事故は、**メンバー 1 人だけ**で 8 GiB のスロットを 20 分の refault thrash に
追い込んだものだった。

木から読んだ、相乗りの代償:

- **ENI の密度。** ワークスペースは `awsvpc`（`runtime_ecs_ec2_taskdef.go`）でタスク 1 つに ENI 1 本。
  ENI トランキング無しでは 1 台に載るタスクは数個しかない。
- **「1 スロット = 1 home」の規則すべて** — `freeSlots`、`releaseSlot`、`af-slot-idle-since`、アイドル停止
  （共有の箱は全員がアイドルになるまで止まらない）、隔離（1 回の隔離で N 人が落ちる）、eviction。
- **コストの帰属。** ADR 0048 はスロットを `af-membership` でメンバーに帰属させる。共有の箱は共有コスト
  になり、ADR 0048 決定 4 はそれを配分しない。
- **隔離。** root ボリューム・カーネル・書き込み層がメンバー間で共有になる（ADR 0045 決定 8 の
  「残る代償」が N 倍になる）。テナントをまたぐなら受け入れられない。

プールに別の Docker ホストを混ぜる形はさらに悪い。CP が走らせる `AF_RUNTIME` はちょうど 1 つで、
`docker` アダプタは Docker デーモンが CP と同じ場所にあることを前提にしている。

**再検討するのは**、決定 3 の履歴が「持続的なワーキングセットが、存在する最小の専有の箱を大きく
下回るメンバーが多い」と示したときだけである。その場合でも形は `ecs-ec2` の中の同一テナント共有
スロットであって、2 つ目のランタイムではない。

## 決定 2 — 軽量クラスは別建て・運用者宣言・オプトインのクラスとする。出荷時の梯子は変えない

運用者は既存の `id|label|arch|type:memMiB[:vcpu]` 構文で `AF_ECS_EC2_SLOT_TYPES` に軽量クラスを宣言する。
**パーサにも起動経路にも新しいものは要らない。**

🔴 **軽量の段を既存のクラスに入れない。** 要件 0 が最小の段に解決されるので、`standard` の下に
`medium` を足すと、サイズを一度も選んでいない全メンバーが、ワークスペース約 1.8 GiB の 4 GiB の箱に
黙って移る。軽量の箱はメンバーか管理者が選ぶもの（または決定 4 が提案するもの）であって、梯子の
編集がメンバーに対して行うものではない。

候補（ガイドで推奨する前にどれも測る）:

| クラス（案） | arch | 段 | 理由 |
|---|---|---|---|
| `light-arm` | arm64 | m8g.medium（1 vCPU / 4 GiB）、m8g.large | `medium` は Graviton の m ファミリにしか無い。m8g は §70.3.2 でドルあたり最速 |
| `burst-arm` | arm64 | t4g.medium（2 / 4 GiB）、t4g.large（2 / 8 GiB） | バースト型。ワークスペースは大半アイドル（§70.3.3）で、ベースラインはアイドルの箱に要る分 |
| `burst-x86` | x86_64 | t3.medium、t3.large | home を x86_64 のまま保てる唯一の軽量案（アーキ移動無し、§70.5） |
| `mem-arm`（任意） | arm64 | r8g.medium（1 / 8 GiB） | 軽量ワークスペースが先に尽きるのは CPU ではなくメモリ |

- 🔴 **4 GiB の段はワークスペースに約 1.8 GiB しか残さない**（4096 − 予約 2048、さらに MemTotal の
  約 5% の過大宣言）。エージェントのセッション 1 つと Agent がそこに収まるかは**測っていない**。この
  測定が、4 GiB の段をそもそも出すのか、軽量を 8 GiB から始めるのかを決める。小さい箱で予約を下げる
  ことはこの決定に含めない。予約を 2 GiB に上げたのは、それ未満で箱が thrash したからである。
- **バースト型クラスは `unlimited` クレジットモードで走らせる。** いまはスロットの起動テンプレート
  （`40-ec2-pool.yaml`）も CP も `CreditSpecification` を設定していないので、t クラスは EC2 の既定を
  受け取る。t4g と t3 の既定は文書上 `unlimited` である（このデプロイでは未確認、未解決の問い 2）。
  `standard` モードは、メンバーがビルドを待っているまさにそのときにベースラインへ絞る。`unlimited` は
  代わりに超過クレジットを課金し、それはメンバーのコスト行（ADR 0048）と履歴（決定 3）に持続的な
  CPU として現れる。それが決定 4 にとって、バースト型クラスから外す合図になる。
- **arm64 のクラスは、[70](../log/70-slot-instance-classes.md) が m8g のために要したものをすべて引き継ぐ**
  （multi-arch イメージ、arm64 AMI、アーキ毎の golden、§70.5 の home の一度きりの入れ直し）。x86 の
  バースト型クラスはどれも要らない。
- **断片化**（[70](../log/70-slot-instance-classes.md) §70.7）: クラス毎に予備スロットを持つ。軽量メンバー
  の計算費は root ボリューム 1 本と同じ桁である（見積もり: `medium` を実測の m8g.large $0.11594/h の
  半分とすると約 $0.058/h、160 h で約 $9.3。root は約 $9.6/月）。したがって**軽量クラスが元を取るのは
  `Ec2SlotTerminateAfterSec` を設定したデプロイだけ**である。ガイドはクラスの横にそう書く。
- **出荷時の既定は無し**（ADR 0074 決定 1 の規則）: 例の梯子は、価格と 1.8 GiB の問いをデプロイ上で
  測るまでは提案にすぎない。

## 決定 3 — CP はメンバー毎の利用履歴を持つ

右サイズ化もガイドの助言も「このメンバーは実際にどれだけ使うか」を要し、いまは後からそれに答えられる
者がいない。

- **何を**: メンバー × 日に 1 行。稼働分数、CPU の p50/p95（段の vCPU に対する比）、ワーキングセットの
  p95/最大、PSI `full` avg60 の最大と ADR 0120 の警告閾値を超えた分数、refault 率の p95、その分数が
  走った段とクラス、バースト型クラスでベースラインを超えた分数。
- **どう**: CP が既存の巡回で、動作中ワークスペースの Stats エンドポイントを採取し（巡回毎に動作中の
  ワークスペース 1 つにつき 1 呼び出し。数値はすべて Agent がすでに計算している）、標本を日次の行に
  畳み込む。生の標本は保存しない。
- **無いことはゼロではない**（`agent_client.go` の `memPressure` の規則）: 応答の無い巡回は分数を足さず、
  測れない Agent は列を NULL のままにする。
- **保持** 90 日。決定 4 が要る窓に余裕を持たせた長さ。
- **見える人**: メンバーは自分のもの、テナント管理者は自テナントのもの（メンバー詳細の、ADR 0048
  決定 12 のコスト行の隣）。中身は持たず、資源の数値だけを持つ。

## 決定 4 — 右サイズ化はまず提案し、テナントが有効にしたところでだけ適用し、動作中のワークスペースは決して止めない

推奨器は決定 3 の履歴を読み、メンバー毎に**目標の段**（クラスとメモリ要件）を出す。

- **上げは速く、下げは遅く。** 上げ: PSI `full` が ADR 0120 の警告閾値を 7 日中 2 日、持続的に超える、
  またはワーキングセットの p95 が上限の 85% を超える。下げ: ワーキングセットの p95 が 1 段下の上限の
  50% 未満、**かつ** CPU の p95 が 40% 未満、を 14 稼働日。どの閾値もフェーズ 0 のデータが出るまで
  暫定である（ADR 0120 決定 8 と同様）。
- **1 つのアーキの中で。** 自動の移動は x86_64 ↔ arm64 を決してまたがない。その移動は home の一部を
  入れ直す（§70.5）、メンバーか管理者の選択である。アーキをまたぐものは推奨器は提案だけする。
- **バースト型で CPU が持続するメンバーは、バースト型クラスから外す**。移り先は同じアーキ・同じ
  メモリの非バースト型クラス。
- **管理者の保存した選択は上書きしない。** 結果はその横に保存する*オーバーライド*（`auto`、理由と、
  それを出した履歴の窓つき）であり、箱はオーバーライド → 保存された選択 → テナント既定の順に
  **1 か所**で解決する。全配置と全画面がすでに通っている関数（`rungFor`）である。オーバーライドを
  消せば保存された選択に戻る。オーバーライドが決して出られない境界は、テナントの
  `AllowedSlotClasses` と、新設するテナントの最小・最大の段である。
- **適用は次の Start だけ。** 変更が動作中のワークスペースを止めたり再起動したりすることは無い。
  メンバーには前もって知らせる（「次の起動から m8g.large になります。理由は…」）。
- **フェーズ**: 0 — 履歴のみ（決定 3）。1 — テナント管理者とメンバーに提案を見せ、クリックで適用。
  2 — 自動。テナント毎、既定は無効、メンバー毎のオプトアウトつき。

## 決定 5 — ブースト: メンバーが時間を限って 1 段上を求める

- **何を**: メンバーのワークスペース画面の「ブースト」は、メンバー自身のクラスの 1 段上（またはテナント
  管理者が許した段）を N 時間取る。決定 4 と同じ種類の時間制限つきオーバーライドで、同じ場所で解決
  するので、メンバーがどの箱を得るかについて両者が食い違うことはない。
- **いつ効くか**: 次の Start。ワークスペースが動作中なら、画面は「いますぐ大きい箱で再起動する」を
  示し、再起動がその中で動いているセッションを終わらせることを書く。自分から再起動することは無い。
- **終わり**: 期限でオーバーライドを外し、次の Start で戻る。動作中のワークスペースをメンバーの下で
  縮めることは決してない。ブースト中のブーストは延長であって、さらに上には登らない。
- **境界**: テナント管理者が有効にし、最高の段と、メンバー毎・月毎のブースト時間を決める。ブースト
  時間は履歴（決定 3）に現れ、金額はコスト行がすでに示している。
- **ADR 0120 との接点**: 圧力応答器が警告する、または新規セッションを拒むとき、その通知は「セッションを
  閉じる」だけでなくブーストを示す。

## 帰結

- 軽量クラスを宣言せず、テナントのスイッチを無効のままにしたデプロイでは何も変わらない。
- 履歴は、動作中ワークスペース毎の巡回呼び出し 1 つと、メンバー × 日に 1 行を足す。
- `rungFor` は保存された選択の前にオーバーライドを持つ。Console のサイズ表示とスロットタブは、
  オーバーライドがどこから来たか（`auto` か `boost`）といつまでかを示さなければならない。さもないと
  メンバーは自分の箱がなぜ変わったか分からない。

## 却下した案

- **共有スロットでの相乗り、またはプールに混ぜた Docker ホスト** — 決定 1。
- **既存クラスへの `medium` の追加** — サイズを保存していない全メンバーを黙って動かす（決定 2）。
- **停止中スロットのその場でのリサイズ（`ModifyInstanceAttribute`）** — スロットはプールであり、目標の
  種別のスロットを取るのはすでに Start がしていること。その場の変更は、どのクラスも宣言していない
  種別のスロットをプールに残す。
- **動作中ワークスペースの自動リサイズ** — メンバーの同意無しにセッションを終わらせる。
- **CP が Pricing API から価格を読んで段を順位付けする** — 梯子の順序は運用者の宣言である（ADR 0045
  決定 21）。推奨器はドルではなく段で動く。
