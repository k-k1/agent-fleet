## 背景

ADR 0013 は機能を作り、その 1 行だけを作らずに残した。AWS ではエンジンを ECS サービスとし、
管理者トグルが desired count を 0↔1 に振り、Cloud Map の固定名を `AF_VOICEVOX_URL` に差す——
という一行である。**CP 側は存在し、テストもある**。`tts_ecs.go` はサービスを
`running | starting | stopped | none` に写して desired を振り、`chooseTTSProvider` は
エンジンに届かない間の日本語を Polly へ落とし、管理モーダルがそれを操作する。

**インフラ側は一度も書かれていない。** `deploy/aws/ecs/cfn/` のどのテンプレートも VOICEVOX の
Service・TaskDef・Cloud Map を作らず、CP タスクに `AF_VOICEVOX_URL` も `AF_TTS_ECS_SERVICE` も
渡していない。したがって CP は既定の `http://127.0.0.1:50021` を指したまま、そこには誰も
応答せず、`auto` は日本語も含めて全部 Polly へ流れる。**ECS 配備でエンジンが動いたことは一度も
ない。**

要求はその穴を塞ぐことだけではなく、形を変えることである。エンジンを常時動かさない。
求められたときに建て（その間は Polly が読む——ルーティングは既にそうなっている）、
誰も聴かなくなったら落とす。

### 実測（2026-09-06）

- **イメージ** `docker.io/voicevox/voicevox_engine`: 安定版 CPU タグ
  `cpu-ubuntu24.04-0.25.2`（2026-04-30 公開）が **1.99 GB**、`0.26.0-dev` が 2.02 GB。
  どちらも **amd64 と arm64 の両方**を含む単一の OCI index。安定版の `nvidia-*` は 3.18 GB
  （`0.26.0-dev` では 3.66 GB）で amd64 単一——CPU 合成が対象なので要らない。
- **Fargate・ap-northeast-1**（Pricing API）: x86 は vCPU-時 **$0.05056**・GB-時 **$0.00553**、
  ARM は **$0.04045**・**$0.00442** ＝ちょうど **20.0% 安い**。
- **Polly・ap-northeast-1**（Pricing API）: neural **$16**/100 万文字、standard **$4**。
  CP タスクロールに `polly:SynthesizeSpeech` が無いと分かったときに記録された数字と一致。
- 導出: **2 vCPU / 4 GiB は x86 で $0.1232/時** ＝ **常時起動なら月 $90**。この配備の
  日額はおよそ $5.50（運用者が実配備で読んだ値。README の 2026-08-15 の見積もりは月 ≈$107＋EFS）
  なので、**常時起動は配備全体を 5 割以上増やす**。ARM なら $0.0986/時。
- **損益分岐は、エンジンが起きている 1 時間あたり 7,703 文字**（neural 比。standard 比なら
  30,810 文字）。エージェントの回答 1 本は 2,000 文字規模なので、**1 時間に 4 本読ませれば
  もうエンジンのほうが安い**。逆に、通知の短文が 1 日に何度か鳴るだけでは全く届かない。
- **コールドスタートは 90〜150 秒と見積もる（未実測）**: `desiredCount` 1 からタスクが生えるまで
  4〜11 秒 ＋ Fargate の provision（ENI attach）10〜16 秒 ＋ pull 約 60 秒
  （1.99 GB を、この配備で実測された Fargate の pull 速度 31 MiB/s で割った値）＋ 展開 ＋
  エンジン起動（**誰も計っていない**）。**Fargate はイメージをキャッシュしないので、起動の
  たびに全量 pull する。**
- 問題にならないので先に書いておく: `00-network.yaml` の**無料の S3 ゲートウェイ
  エンドポイント**が ECR の層 blob を NAT の外へ逃がしているため、毎回の 2 GB pull に
  NAT のデータ処理料はかからない。
- `30-ingress.yaml` は **40,222 バイト**で、CloudFormation の上限は 51,200 バイト。
  **YAML のコメントも本文に数えられる。**
- **ecs-ec2 配備で読み取り専用に実測:** 停止中の Workspace サービス（`desiredCount` 0・
  Service Connect 有効。7 本）は、すべて名前空間に **HTTP 型**の Cloud Map サービスとして
  列挙され、`DiscoverInstances` は**インスタンス 0**を返し、Route 53 の private zone には NS と
  SOA しか無い。SOA レコードの TTL は **15 秒**＝この名前空間で NXDOMAIN が負のキャッシュに
  残る時間。
- **CloudFormation 自身の `DesiredCount` の契約**（リソーススキーマ
  `describe-type AWS::ECS::Service` の説明文）: *"For new services, if a desired count is not
  specified, a default value of 1 is used. … For existing services, if a desired count is not
  specified, it is omitted from the operation."*
- **クラスタに capacity provider は無い**（EC2 プールはインスタンスを直接登録する）ので、
  `LaunchType` を書かないサービスは API の既定＝EC2 になる。同じ配備で Workspace サービスは
  すべて `launchType EC2` と読め、CP が `FARGATE` なのは `30-ingress` がそう書いているから
  にすぎない。
- エンジン `0.25.2` の README には `--disable_mutable_api`（または
  `VV_DISABLE_MUTABLE_API=1`）、`--cpu_num_threads`、`--load_all_models` がある。

### いまのコードが言っていること

- `tts.go` の合成クライアント `ttsHTTP` は素の `http.Client` で、**`dialAgent` を使っていない**。
  Service Connect の別名が引けないときに CP→Agent を救う Cloud Map フォールバックは、
  この経路には効かない。決定 8 のもとでは効く必要も無い——Cloud Map の DNS 名は別名でなく
  VPC リゾルバが引く。
- `GET /api/tts/status` は**毎回** `DescribeServices` を呼ぶ（キャッシュ無し）。
- `synthCacheKey`（`ttsAudio.ts`）はクライアント側の音声キャッシュを**設定値のプロバイダ**
  ＝ `auto` でキーにしており、コメント自身が「auto の行き先が変わった直後は古い声が鳴りうるが
  許容」と認めている。
- `GET /api/tts/speakers` は生きたエンジンを proxy し、停止中は 502 を返す＝キャラクター選択は
  読み取り専用に落ちる。
- 読み仮名辞書はクライアント側で適用される（ユーザー辞書とテナント共通辞書のマージ）。
  **エンジンは、壊しても失う状態を持たない。** これがこの設計を成立させている。
- `CpTaskRole` には既に `ecs:DescribeServices` / `UpdateService` / `DescribeTasks` /
  `ListTasks` / `servicediscovery:DiscoverInstances` / `polly:SynthesizeSpeech` がある。
  **この設計で新しい IAM 権限は 1 つも要らない。**

## 決定

1. **Fargate に置く。EC2 スロットプールには決して置かない。** `ecs-ec2` 配備でも同じ——
   そこでも CP 自身は Fargate タスクである。プールの不変条件はすべて `af-pool` /
   `af-role=slot` タグ起点の走査と「ECS タスク 0 の箱は空き」という前提（ADR 0045 の決定 22・
   23・29）に乗っており、Workspace でないタスクが 1 つ混ざるとその前提が崩れる。さらに
   `Ec2MaxSlots` の枠を 1 つ食う＝**文章を読み上げるために、誰かが Workspace を起動できなく
   なる**。加えて EC2 は停止しても root ボリュームが課金され続けるので、目的である
   scale-to-zero そのものが失われる。したがってサービスは **`LaunchType: FARGATE` を明示する**。
   書かなければクラスタの既定がプールに置き、この決定は 1 行の欠落で破れる。

2. **独立した任意採用のスタック `50-tts.yaml` を、`30-ingress` より先に配る。** VPC・
   プライベートサブネット・CP のセキュリティグループを `00-network` から、クラスタ・実行
   ロール・名前空間を `20-platform` から import する。`30-ingress` には依存しない。
   `30-ingress` 側は既定が空のパラメータ 2 つ（`TtsEcsService` / `VoicevoxUrl`）を受け、
   非空のときだけ環境変数に出す——既存の条件付きシークレットと同じ形。循環参照は起きず、
   音声が要らない配備は何も建てない。`30-ingress` に足す案は、51,200 バイトの壁まで残り
   11 KB しかない枠を、多くの配備が有効にしない機能で削ることになる。（`50-` は `40-ec2-pool`
   の後に並ぶが、あれも standup は `30-ingress` より先に配る。順序はファイル名でなく README に
   書く。）

3. **需要とは「意図」であって「結果」ではない。** アイドル時計を押し直すのは、
   *エンジンが起きていれば* `chooseTTSProvider` が voicevox へ振ったはずの合成要求
   （`provider` が `auto` か `voicevox`、言語が `en` でない、ルーティングが OFF でない）で
   あって、実際にどこへ行ったかではない。結果で数えると成立しない: 起動中の要求はすべて
   Polly が返すので、**一番大事な 2 分間の需要がゼロに見え**、コントローラは自分が建てた
   サービスを止め、次の要求がまた建てる。**「voicevox が処理した要求」を数える実装は、
   構造的にフラップする。** 意図は利用者の**設定値**で判定する。したがって決定 13 の発話中の
   固定は専用の要求フィールドで運び、決して `provider: polly` にしない——固定された回答の残りが
   数えられなくなると、自動の引き金が飢え、誰かが聴いている最中にアイドル時計が切れる。
   意図でない要求は、設定値が `polly` のものだけである。（`lang=auto` は英語の本文も数えるが、
   それは既存のルーティングがどのみちエンジンへ送るものである。）

4. **損益分岐を超えたら自動で建て、人が求めたらいつでも建てる。** 引き金は 2 つあり、
   答えている問いが違う。
   - **自動**: 直近 5 分間の「voicevox 意図」の文字数が `AF_TTS_ECS_START_CHARS`
     （既定 **2,000**＝回答 1 本ぶん。時間換算 24,000 文字/時＝実測した損益分岐のおよそ 3 倍で、
     アイドル窓のぶんの余裕を残す）を超えたとき。待っても無音にはならない——Polly が読んで
     いるからである。この規則は、**セッション通知を有効にして Console を開きっぱなしにして
     いるだけでは自動起動しない**ことも意味する。数十文字の告知のために 8 時間ぶんの Fargate を
     買ってしまう唯一の経路が、これで塞がる。
   - **明示**: `POST /api/tts/wake`。「ずんだもんを呼ぶ」操作の裏で、ログイン済みの利用者なら
     誰でも押せる。通知をあの声で聴きたい人が、量で資格を稼がされる筋合いはない。
     費用が発生するので監査に残す。冪等（`running` / `starting` 中の wake は需要時計を押す
     だけ）で、利用者ごとにレート制限する。
   - どちらの引き金にもできないのは、引き金を引いた回答自身にエンジンを間に合わせること
     である。2,000 文字の回答は読み上げに 4〜6 分、エンジンの到着は 90〜150 秒なので、最初の
     回答は少なくとも前半が Polly になり、その窓をエンジンが稼ぐかどうかは次の回答が続くかで
     決まる。P0 で両方の所要を測る（未解決の点 3）。

5. **アイドル窓で止める。`AF_TTS_ECS_IDLE_SEC`、既定 1800 秒、`0` = 止めない。** `0` が OFF
   なのはこの repo の流儀（スロットの sleep で一度これを間違えている）。15 分でなく 30 分に
   するのは、**縛っているのが費用ではないから**である——無駄になった窓 1 回の費用は **$0.062**
   にすぎない一方、建て直しには 90〜150 秒かかり、その間はみんなが知っている声が Polly に
   置き換わる。**建て直しで高いのは請求書ではなく中断のほうだ。** 窓は `starting` にも
   適用する。さもないと、配置できずに desired 1 で張り付いたサービスが、誰も待っていなく
   なった頃に突然エンジンを起こす。窓の下限は決定 9 の起動期限に clamp する——コールドスタート
   より短い窓は `starting` の最中にサービスを止め、次の 1 文がまた建てる。意図の規則では
   防げないフラップである。

6. **需要の時刻は永続化する**（書き込みは 1 分に 1 回へ絞る）。置き場は `tts_engine` と
   `tts_dict` が既に居る `SettingsStore`。メモリだけだと、CP 再起動が「需要ゼロ」と読んで
   **聴いている人の足元でエンジンを止める**。保存値が無い CP は**刻むだけで、その回は判定
   しない**——空きスロット掃除が使っているのと同じ「初回は押すだけ」の規則で、これが
   デプロイ中に CP が 2 レプリカ重なっても安全な理由でもある。`lastStart` はそもそも保存
   しない。`DescribeServices` の `deployments[].createdAt` から読むので、起動の途中で置き換わった
   CP も前任と同じ時計で期限を判定する。

7. **`tts_engine` を 3 値化する（`off` / `on` / `ondemand`）。desired count は管理者の意図で
   あることをやめる。** いまの `ttsAdminAPI.status()` は managed のとき
   `enabled = desired >= 1` と答える。オンデマンドでは desired が自分で動くので、管理者は
   触っていないトグルが動くのを見ることになる。画面は**モード**（意図・保存値）と**状態**
   （`running`/`starting`/`stopped`・実況）を別のものとして出す。これは VOICEVOX の無い配備で
   見つかった「嘘 3 件」と同じ種類の欠陥＝**設定値を実態であるかのように出す画面**である。

8. **エンジンには Cloud Map の DNS 名で到達する。Service Connect は使わない。** `50-tts` は
   既存の `DNS_PRIVATE` 名前空間に `ServiceRegistries` で A レコード（TTL 10 秒程度）を登録し、
   `voicevox.<名前空間>` は他の名前と同じく VPC リゾルバが引く。`/etc/hosts` のスナップショット
   も、要求経路の Envoy サイドカーも無く、`ttsHTTP` と `AF_VOICEVOX_URL` はそのまま——ADR 0013
   と `tts_ecs.go` のヘッダが最初から想定していた形である。desired 0 の間は名前にレコードが
   無く、NXDOMAIN → `Ready` は false → Polly が読む。実測した SOA TTL 15 秒が、起動が負の
   キャッシュに隠れる時間の上限になる。却下した 2 案（却下した案を参照）: Service Connect の
   別名＋`ttsHTTP` を共有 Agent トランスポートに載せる案と、`ListTasks` / `DescribeTasks` で
   タスクの ENI を引く案。後者の動機だった別名のスナップショットは、そもそもここでは起きない
   ——音声の有効化は CP の task definition に環境変数を足すので、CP タスクはエンジンのスタックが
   できた後に必ず置き換わる。この決定が依存する 2 つの遅延は P0 で測る: `RUNNING` から
   A レコードが現れるまで、停止からレコードが消えるまで。

9. **コントローラの判断は純関数にする。** `chooseTTSProvider` と同じ流儀で
   `decideEngineAction(now, state, desired, lastDemand, lastStart, cfg) → none | start | stop`
   とし、テーブルテストを付ける。AWS 呼び出しはその外側に置く——既存の偽 `ttsEngineAPI` が
   そのまま使える。起動の失敗は `DescribeServices` の `events[]` から診断する（追加権限は
   不要で、本当の理由——配置制約を満たす箱が無い、pull に失敗した——が文章で書いてある唯一の
   場所である）。期限内に `running` にならなかった起動は、**その文言つきで失敗を名乗り**、
   永久に再試行せず desired を 0 に戻す——**そしてクールダウンの間は建て直しを拒む**（15 分。
   連続失敗ごとに倍）。これが無いと次の 1 文が即座にサービスを建て直し、繰り返す失敗は試行
   ごとに 2 GB の pull を払う。

10. **`DescribeServices` に短い TTL キャッシュを被せる**——これは何より先に。status
    ハンドラは要求ごとにこれを呼んでおり、管理モーダルだけがポーリングしている今は無害だが、
    「準備中」を描くために全クライアントがポーリングし始めた瞬間に無害でなくなる。隣にある
    4 秒の readiness キャッシュと同じ形でよい。

11. **既定は x86_64。arm64 は合成時間を実測してから。** イメージは両対応で ARM Fargate は
    20.0% 安いが、ここでの ONNX 推論が Graviton でどうなるかは何も分かっていない。
    レイテンシが効く機能で「20% 安く 30% 遅い」は悪い取引である。アーキはスタック
    パラメータとして**宣言する（導出しない）**——ADR 0053 が CP で確立した形。どちらのアーキ
    でも `--cpu_num_threads` はタスクの vCPU 数に合わせる。放っておくとエンジンが勝手に決める。

12. **キャラクター一覧は、エンジンが止まっていても生き残らせる。** `/api/tts/speakers` は
    生きたエンジンを proxy するので、停止が通常状態になるオンデマンドでは、キャラクター選択が
    ほとんど常に使えない。一覧は永続キャッシュし、エンジンが起きているときに更新する。

13. **クライアントは 1 回の発話の間プロバイダを固定し、`auto` で焼いた音声はルーティングが
    変わったら捨てる。** キャッシュのコメントは既に「auto の行き先が変わった直後は古い声が
    鳴りうる」と認めているが、オンデマンドではそれが例外ではなく**起動のたびに必ず起きる**。
    そして回答の途中で声が変わるのは、どちらか一方の声で通すより悪い。応答は既に
    `X-TTS-Provider` を返し、クライアントはバッファごとにそれを覚えているので、どちらの修正も
    小さい。設定値が `voicevox` の要求は、管理下のエンジンが停止中なら 502 でなく Polly が
    `X-TTS-Provider: polly` つきで答える。いまの `synthToBuffer` はその 502 を「その文を飛ばす」
    に変えるので、オンデマンドではエンジンが来るまで全文が無音になる。

14. **エンジンに到達できるのは CP だけにする。** 専用のセキュリティグループ、50021 の ingress は
    CP のセキュリティグループからのみ、ロードバランサ無し、プライベートサブネット。VOICEVOX の
    HTTP API は無認証で変更系のエンドポイントを持つ。`0.25.2` は `--disable_mutable_api`
    （または `VV_DISABLE_MUTABLE_API=1`）でそれを無効化でき、task definition がそれを渡す。
    イメージは版で固定し、タスク起動時に Docker Hub から引くのではなく `crane` で ECR へ
    複製する——この配備の外向きは NAT の 1 アドレスから出るため、匿名 pull の枠を配備全体で
    共有することになるからである。

15. **サービスにはコンポーネントの費用配分タグを付ける。** これは共有費用であり、ADR 0048 の
    とおり**共有費用は表示するが、メンバーへ按分しない**。

16. **`Ready` は「温まっている」の意味であり、`running` は `Ready` ではない。** `/version` は
    音声モデルを読み込む前に 200 を返すので、起動直後の最初の合成は遅い。コントローラは
    `/version` が答えた後に既定話者で短いウォームアップ合成を 1 回行い、それから初めて ready
    として扱う（P0 では `--load_all_models` も測る。起動が伸びる代わりにウォームアップを
    置き換えられるかもしれない）。ECS の `RUNNING` はコンテナが始まったと言っているだけで、
    P2 の「準備中・いまは Polly が代読」表示は `Ready` 基準にし、サービス状態では決して
    判断しない。task definition には `/version` のコンテナヘルスチェックを付け、固まった
    エンジンを `running` のまま到達不能に放置せず ECS に置き換えさせる。

## 実測で解けた点（2026-09-06）

1. **`desiredCount: 0` のサービスは名前空間に現れる——インスタンスの無い「名前」として。**
   ecs-ec2 配備で実測（「実測」の節を参照）: 停止中の Workspace サービスは HTTP 型の Cloud Map
   サービスとしてインスタンス 0 で列挙され、ゾーンには desired に関係なく A レコードが無い。
   Service Connect は DNS を書かないからである。したがって決定 8 はこの点に一切依存しない。
   Cloud Map の DNS サービスは停止中は A レコードが無いだけで、タスクが動けばそれが生える。
2. **CloudFormation が `DesiredCount` を戻すのは、プロパティを宣言していて、かつ Service
   リソース自体が更新されるときだけ。** リソーススキーマより: 省略すると作成時に 1 で立ち、
   以後の更新では操作から省かれる。`50-tts` は省略し、standup が作成直後に 0 へ落とす
   （どのみちコントローラがアイドル窓 1 回・$0.062 で落とす）。`0` を宣言すると、サービスの
   task definition やタグの変更のたびに——誰かが聴いている最中に——戻る一方、Service リソースに
   触れない更新では戻らない。省略はその非対称を避ける。実スタックでは試していない（実配備は
   使用中）。スキーマの文言が契約である。

## 未解決の点——P0 を書く前に潰すこと

1. **VOICEVOX とずんだもんの利用規約を、「運用者＝聴く人」でない配備について確認する。**
   クレジット表記は実装済み。未確認なのは、第三者に声を提供する形——マルチテナント配備が
   まさにそれをする——のほうである。エンジンは各キャラクターの規約原文を自分で配る
   （`GET /speaker_info` の `policy`）ので、P0 では動いているエンジンから原文を取れる。
2. **サイズと起動時間**: 1 vCPU/2 GiB と 2 vCPU/4 GiB、`--load_all_models` の有無それぞれでの
   エンジンの起動所要、両者での 1 文あたり合成レイテンシ、そして arm64 での同じ数値。P0 は
   この数字を出すためにも存在する。上記の既定値はそれまで見積もりである。
3. **「5 分で 2,000 文字」は正しい引き金か。** 損益分岐から導いた値であって、観測された行動から
   出した値ではなく、決定 4 が書くとおり引き金を引いた回答自身にはエンジンが間に合わない。
   P0 で「起動から最初の voicevox 応答まで」と「回答 1 本の読み上げ時間」を測り、実利用が
   1 週間ぶん溜まったら閾値を見直す。

## 却下した案

- **常時起動のまま。** 月 $165 規模の配備に月 $90＝5 割増を、1 日の大半は黙っている機能のために
  払う。
- **EC2 スロットプールに載せる**（決定 1）。
- **最初の日本語 1 文で建てる。** 最も単純でレイテンシも最良だが、30 文字の告知のために 30 分の
  窓を買う。セッション通知を有効にして Console を開きっぱなしにすれば、数文のために一日中
  エンジンが生きる。本当にそれを望む人は、決定 4 の明示操作で救われる。
- **明示ボタンのみ。** 予測可能で費用にも正直だが、Polly で既に百文を読ませた人は需要を
  証明済みであり、そこで改めて頼ませるのは儀式である。
- **業務時間のスケジュール起動。** 予測可能だが、黙っている時間に払い、時間外の人には常に
  間違っており、誰が聴いているかを知らない。上限として後から重ねることはできるが、規則の
  本体にはならない。
- **既定を Fargate Spot にする。** 約 70% 安く、中断しても Polly に落ちるだけだが、アイドル停止
  を入れた時点で残る請求は既に小さく、容量不足は「いつまでも来ないエンジン」として表に出る。
  後段のつまみとして残す。
- **いま SOCI を入れる。** Workspace イメージでこれを却下したゲートは「pull が 40 秒以上かつ
  全体の 40% 以上」で、**別の、より小さいイメージに対して**測ったものである。ここでは pull が
  コールドスタートの大半を占めそうなので答えが変わりうる。**それは測り直す理由であって、
  そうだと決めてよい理由ではない。** しかもエンジンは起動時にモデルを読むので、遅延ロードは
  費用を移動させるだけかもしれない。
- **Lambda / App Runner。** Fargate に対する scale-to-zero の利点が無く、当てはまりも悪い
  （2 GB のモデルサーバは関数ではないし、App Runner はインスタンスを温存する）。
- **ECS でタスクの ENI を引く（`ListTasks` → `DescribeTasks`）**——初稿の決定 8。動くし DNS に
  依存しないが、コードが最も多く（リゾルバ、そのキャッシュ、タスク置換時の無効化、miss ごとに
  API 2 回）、動機だった Service Connect 別名のスナップショットは、音声の有効化がエンジンの
  スタックの後に CP タスクを置き換えるので、そもそも起きない。
- **Service Connect の別名＋`ttsHTTP` を共有 Agent トランスポートに載せる。** Go では 1 行だが、
  合成の経路に Envoy サイドカーが入る。その per-request timeout の既定 15 秒は `ttsHTTP` の
  30 秒より短いので、エンジン側の Service Connect 設定で引き上げねばならず、サイドカーは
  コールドスタートを毎回伸ばす。
- **テナントごとのエンジン。** エンジンはテナント固有の状態を持たない（辞書の項を参照）ので、
  買えるのは負荷の分離だけで、費用は N 倍になる。同時実行が苦情になったら再考する。

## フェーズ

- **P0 — まず存在させる。** `50-tts.yaml`、`30-ingress` のパラメータ、固定版イメージの ECR への
  複製、standup / update / teardown / capture-env に新スタックを教える。完了の定義は、
  **既存の**管理者トグルで実配備のエンジンが起動・停止し、日本語の合成が耳で聴いてずんだもんに
  なること。ここで以降が依存する数字（コールドスタート、起動所要、合成レイテンシ、arm64 の
  同じ値。加えて `--load_all_models` の有無、決定 8 の Cloud Map の遅延 2 つ、起動から最初の
  voicevox 応答まで、回答 1 本の読み上げ時間）が出る。
- **P1 — 自動にする。** 需要トラッキング（決定 3・6）、コントローラ（決定 5・9。アイドル窓の
  clamp と失敗後のクールダウンを含む）、キャッシュ（決定 10）、3 値モードと管理画面（決定 7）、
  ウォームアップとヘルスチェック（決定 16）。アドレッシング（決定 8）は P0 に含まれる——
  スタックの話であって CP の話ではない。自動の起動と
  停止はすべて監査に残す——**誰にも説明できない請求は、誰にも信用されない。**
- **P2 — 気持ちよくする。** 「ずんだもんを呼ぶ」操作と、利用者向けの「準備中・いまは Polly が
  代読」表示、プロバイダの固定・キャッシュ破棄・停止中の `voicevox` 明示要求への Polly 応答（決定 13）、
  永続キャラクター一覧（決定 12）。
- **P3 — 根拠つきで安くする。** arm64、Fargate Spot、そして P0 の数字が「pull が支配的」と
  言ったときにだけ SOCI。
