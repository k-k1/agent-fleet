## 背景

ADR 0013 は機能を作り、その 1 行だけを作らずに残した。AWS ではエンジンを ECS サービスとし、
管理者トグルが desired count を 0↔1 に振り、Cloud Map の固定名を `AF_VOICEVOX_URL` に差す——
という一行である。**CP 側は存在し、テストもある**。`tts_ecs.go` はサービスを
`running | starting | stopped | none` に写して desired を振り、`chooseTTSProvider` は
エンジンに届かない間の日本語を Polly へ落とし、管理モーダルがそれを操作する。

**インフラ側は一度も書かれていない。** `deploy/aws/ecs/cfn/` のどのテンプレートも VOICEVOX の
Service・TaskDef・Cloud Map を作らず、CP タスクに `AF_VOICEVOX_URL` も `AF_TTS_ECS_SERVICE` も
渡していない。したがって CP は既定の `http://127.0.0.1:50021` を指したまま、そこには誰も
応答せず、`auto` は日本語も含めて全部 Polly へ流れる。**ECS 配備でエンジンが動いたことは一度も
ない。**

要求はその穴を塞ぐことだけではなく、形を変えることである。エンジンを常時動かさない。
求められたときに建て（その間は Polly が読む——ルーティングは既にそうなっている）、
誰も聴かなくなったら落とす。

### 実測（2026-09-06）

- **イメージ** `docker.io/voicevox/voicevox_engine`: 安定版 CPU タグ
  `cpu-ubuntu24.04-0.25.2`（2026-04-30 公開）が **1.99 GB**、`0.26.0-dev` が 2.02 GB。
  どちらも **amd64 と arm64 の両方**を含む単一の OCI index。安定版の `nvidia-*` は 3.18 GB
  （`0.26.0-dev` では 3.66 GB）で amd64 単一——CPU 合成が対象なので要らない。
- **Fargate・ap-northeast-1**（Pricing API）: x86 は vCPU-時 **$0.05056**・GB-時 **$0.00553**、
  ARM は **$0.04045**・**$0.00442** ＝ちょうど **20.0% 安い**。
- **Polly・ap-northeast-1**（Pricing API）: neural **$16**/100 万文字、standard **$4**。
  CP タスクロールに `polly:SynthesizeSpeech` が無いと分かったときに記録された数字と一致。
- 導出: **2 vCPU / 4 GiB は x86 で $0.1232/時** ＝ **常時起動なら月 $90**。この配備の
  日額はおよそ $5.50（運用者が実配備で読んだ値。README の 2026-08-15 の見積もりは月 ≈$107＋EFS）
  なので、**常時起動は配備全体を 5 割以上増やす**。ARM なら $0.0986/時。
- **損益分岐は、エンジンが起きている 1 時間あたり 7,703 文字**（neural 比。standard 比なら
  30,810 文字）。エージェントの回答 1 本は 2,000 文字規模なので、**1 時間に 4 本読ませれば
  もうエンジンのほうが安い**。逆に、通知の短文が 1 日に何度か鳴るだけでは全く届かない。
- **コールドスタートは 90〜150 秒と見積もる（未実測）**: `desiredCount` 1 からタスクが生えるまで
  4〜11 秒 ＋ Fargate の provision（ENI attach）10〜16 秒 ＋ pull 約 60 秒
  （1.99 GB を、この配備で実測された Fargate の pull 速度 31 MiB/s で割った値）＋ 展開 ＋
  エンジン起動（**誰も計っていない**）。**Fargate はイメージをキャッシュしないので、起動の
  たびに全量 pull する。**
- 問題にならないので先に書いておく: `00-network.yaml` の**無料の S3 ゲートウェイ
  エンドポイント**が ECR の層 blob を NAT の外へ逃がしているため、毎回の 2 GB pull に
  NAT のデータ処理料はかからない。
- `30-ingress.yaml` は **40,222 バイト**で、CloudFormation の上限は 51,200 バイト。
  **YAML のコメントも本文に数えられる。**
- **ecs-ec2 配備で読み取り専用に実測:** 停止中の Workspace サービス（`desiredCount` 0・
  Service Connect 有効。7 本）は、すべて名前空間に **HTTP 型**の Cloud Map サービスとして
  列挙され、`DiscoverInstances` は**インスタンス 0**を返し、Route 53 の private zone には NS と
  SOA しか無い。SOA レコードの TTL は **15 秒**＝この名前空間で NXDOMAIN が負のキャッシュに
  残る時間。
- **CloudFormation 自身の `DesiredCount` の契約**（リソーススキーマ
  `describe-type AWS::ECS::Service` の説明文）: *"For new services, if a desired count is not
  specified, a default value of 1 is used. … For existing services, if a desired count is not
  specified, it is omitted from the operation."*
- **クラスタに capacity provider は無い**（EC2 プールはインスタンスを直接登録する）ので、
  `LaunchType` を書かないサービスは API の既定＝EC2 になる。同じ配備で Workspace サービスは
  すべて `launchType EC2` と読め、CP が `FARGATE` なのは `30-ingress` がそう書いているから
  にすぎない。
- エンジン `0.25.2` の README には `--disable_mutable_api`（または
  `VV_DISABLE_MUTABLE_API=1`）、`--cpu_num_threads`、`--load_all_models` がある。

### P0 の実測（2026-09-06・ap-northeast-1 の実配備）

以下はこの作業のために建てた配備で、P0 のスタックのまま、VPC の中からエンジンを叩いて測った
数値である。上の見積もりと食い違う場合はこちらが正しい。

- **コールドスタートは 70〜77 秒**（見積もりの 90〜150 秒より速い）。タスク作成 +8 秒 /
  ENI +15 秒 / pull 開始 +28 秒 / **pull 完了 +62 秒（1.86 GiB を 32.9 秒 ≒ 58 MiB/s。
  見積もりが仮定した 31 MiB/s のほぼ 2 倍）** / `RUNNING` +81 秒。
- **決定 8 が依存する 2 つの遅延**: 停止から A レコードが消えるまで **10 秒以内**、
  `RUNNING` から A レコードが現れるまで **67〜73 秒**。
- **エンジンの起動: `--load_all_models` 無しで 1 秒未満、有りで 19 秒。** モデルは遅延ロード
  で、その代償は **最初の `audio_query` の 650 ms だけ**である。決定 16 がウォームアップを
  選び、19 秒を毎回払わない理由がこれである。
- **合成**（同一の 42 字文・音声 7.232 秒。比は合成時間 ÷ 音声長で、1.0 未満なら再生に追いつく）:
  x86 2 vCPU/4 GiB **4.42 秒 / 0.61**、同＋`--load_all_models` 3.79 秒 / 0.52、
  x86 **1 vCPU/2 GiB 5.74 秒 / 0.79（単価は半分）**、**arm64 2 vCPU/4 GiB 6.73 秒 / 0.92**。
- **実経路で回答 1 本**: 2,037 字＝63 文で、**合成 251.7 秒・音声 6 分 00 秒・比 0.70**。
  決定 4 の警告を裏側から裏づける——引き金を引いた回答自身には、エンジンは間に合わない。
- **`DesiredCount` の契約をライブで確認**（「実測で解けた点」2）: TaskDef を変える stack update
  を成功させても desired は 0 のままだった。避けられないのは**作成時**だけで、そこは
  CloudFormation がサービスの安定を待つため、必ず 1 回コールドスタートを払う。
- **設計が生き延びねばならない「エンジンの死に方」2 つ**（いずれも実測）:
  1. **4 GiB は 1 リクエストの巨大な合成に耐えない。** 約 2,000 字を**単発**で投げると
     OOM kill（exit 137）。400 字（38 秒）までは生存を確認した。実クライアントは文単位に
     送るので通常経路は無事だが、起きたとき **`/version` のコンテナヘルスチェックは最後まで
     HEALTHY のまま**＝決定 16 のヘルスチェックでは捕まらない。ECS がタスクを置き換える
     約 2.5 分は Polly が代読する。コントローラは**これを自分の start/stop と区別できる**
     必要があり、そのための `stoppedReason` / `events[]` である。
  2. **`ttsHTTP` のタイムアウトは 30 秒で、268 字の 1 文が 25.2 秒。** つまり概ね 300 字を
     超える 1 文は、OOM に至る前にタイムアウトする。
- 利用規約（未解決の点 1）: ずんだもんは「VOICEVOX:ずんだもん」とクレジットすれば商用・
  非商用で利用可（`zunko.jp`）。エンジンは起動時に全キャラクターの規約を stderr に吐くので
  CloudWatch に残り、別のキャラクターで `/speaker_info` の `policy` と同文言であることを
  照合した。

### P3 の実測（2026-09-07・同じ配備）

P3 に残っていた問いは 3 つ——安いタスクは割に合うか、Spot は使えるか、SOCI は元を取るか——
と、P0 から引き継いだ未解決の点が 1 つ（1 要求の「大きすぎる」はどこか）。4 つとも
`deploy/aws/ecs/harness/bench-tts-engine.sh` で測った。サイズごとに RunTask でエンジンを
1 本だけ建て（**サービスの外**に建てる。最初はサービスを使って測ろうとして、オンデマンドの
コントローラに測定中のエンジンを止められた）、VPC 内から合成時間を測る。

**2 サイズを、同じ文章で、同じ実行の中で。** 比は合成秒数 ÷ 音声秒数で、1.0 未満なら再生に
追いつく。

| | 2 vCPU / 4 GiB | 1 vCPU / 2 GiB |
|---|---|---|
| 回答 1 本＝36 文・1,368 字・音声 251.5 秒 | 166.2 秒 / **0.66**、170.9 秒 / 0.68、170.8 秒 / 0.68 | 172.5 秒 / 0.69、175.2 秒 / 0.70、**254.5 秒 / 1.01** |
| 35 字の 1 文 | 4.53、4.55、4.56 秒 | 4.68、4.72、**6.35** 秒 |
| 228 字の 1 文 | 26.2、26.7、26.7 秒 | 28.1、28.2、**42.0** 秒 |
| OOM kill する単発要求 | 370 字は無事・**518 字で死ぬ**（684 字も） | 259 字は無事・**370 字で死ぬ** |
| 328 字 × 同時 4 本 | 生存 | *2 本*で死んだ |
| 74 字 × 同時 8 本（実クライアントの形） | 生存 | 生存 |
| 単価（ap-northeast-1） | $0.1232/時 | $0.0616/時 |

- **1 vCPU/2 GiB は不採用。ただし P0 が予想した理由ではない。** P0 は 1 文で 30% 遅いと
  測ったが、きちんと測れば回答 1 本では普段 5% 程度しか遅くない。落ちたのは残り 2 行である。
  1. **OOM の壁が、CP が許す範囲の内側にある。** 単発 370 字で死に、328 字の同時 2 本でも
     死んだ——4 GiB は同時 4 本でも生きていた。1 要求の上限は 300 字（決定 17）なので、
     **合法な要求 2 本で、聴いている全員のためのエンジンが落ちうる**（Polly が 2 分半＋
     2 GB の pull をもう一度）。
  2. **速いのではなく「たいてい速い」。** 2 回は 4 GiB と 5% 以内で並んだが、3 回目は 50%
     遅く、回答 1 本の実時間比が **1.01**——ここで再生が追いつかなくなり、文と文の間に沈黙が
     開く。2 vCPU の 3 回は 0.66・0.68・0.68 だった。n=3 は分布ではないが、1 vCPU の Fargate
     タスクにはバースト余地が無く、運が悪いときの症状が「機能が働かない」である。
  そして節約できるのは、**聴いている間しか動かないエンジン**の $0.06/時である。
- **同時実行は並列化ではなく待ち行列である。** 2 vCPU で 328 字を同時 4 本投げると
  40 秒・80 秒・119 秒・159 秒で返り、1 vCPU で 74 字を同時 8 本だと 13.5 秒〜107 秒だった。
  エンジンは直列化するので、2 人目の聴き手はレイテンシを半分にせず、尾を倍にする。
  1 配備 1 エンジンで数人ぶんは足りるという根拠であり、部屋いっぱいを賄えると期待する
  根拠ではない。
- **コールドスタートをもう 2 回**: pull 34.7 秒（起動全体 51.0 秒）と 35.9 秒（同 56.4 秒）。
  RunTask なので、サービス経由で P0 が測った「81 秒のうち 34 秒」との差はサービス側の
  スケジューリングぶんである。pull は 62〜68% を占め——**それでも SOCI 採否ゲートの
  「40 秒以上」に届かない**。SOCI を入れない理由がこれである（「却下した案」）。
- **Fargate Spot は LaunchType 無しで配置される**（`defaultCapacityProviderStrategy` が
  空のクラスタで実測。決定 1）。
- **実エンジンの `/speakers` を VPC 内から取得**（決定 12 が焼くことになる形）: HTTP 200・
  13,117 バイト・**43 キャラクター**・固定版 `0.25.2` では全スタイルが `"type": "talk"`・
  `id` は JSON の数値。`voicevoxSpeakers` が解釈する形そのもので、永続一覧は空ではなく
  43 件になる。確かめる価値があるのはここで、外すと「いつまでも空のキャラクター選択」
  としてしか表に出ない。

### いまのコードが言っていること

- `tts.go` の合成クライアント `ttsHTTP` は素の `http.Client` で、**`dialAgent` を使っていない**。
  Service Connect の別名が引けないときに CP→Agent を救う Cloud Map フォールバックは、
  この経路には効かない。決定 8 のもとでは効く必要も無い——Cloud Map の DNS 名は別名でなく
  VPC リゾルバが引く。
- `GET /api/tts/status` は**毎回** `DescribeServices` を呼ぶ（キャッシュ無し）。
- `synthCacheKey`（`ttsAudio.ts`）はクライアント側の音声キャッシュを**設定値のプロバイダ**
  ＝ `auto` でキーにしており、コメント自身が「auto の行き先が変わった直後は古い声が鳴りうるが
  許容」と認めている。
- `GET /api/tts/speakers` は生きたエンジンを proxy し、停止中は 502 を返す＝キャラクター選択は
  読み取り専用に落ちる。
- 読み仮名辞書はクライアント側で適用される（ユーザー辞書とテナント共通辞書のマージ）。
  **エンジンは、壊しても失う状態を持たない。** これがこの設計を成立させている。
- `CpTaskRole` には既に `ecs:DescribeServices` / `UpdateService` / `DescribeTasks` /
  `ListTasks` / `servicediscovery:DiscoverInstances` / `polly:SynthesizeSpeech` がある。
  **この設計で新しい IAM 権限は 1 つも要らない。**

## 決定

1. **Fargate に置く。EC2 スロットプールには決して置かない。** `ecs-ec2` 配備でも同じ——
   そこでも CP 自身は Fargate タスクである。プールの不変条件はすべて `af-pool` /
   `af-role=slot` タグ起点の走査と「ECS タスク 0 の箱は空き」という前提（ADR 0045 の決定 22・
   23・29）に乗っており、Workspace でないタスクが 1 つ混ざるとその前提が崩れる。さらに
   `Ec2MaxSlots` の枠を 1 つ食う＝**文章を読み上げるために、誰かが Workspace を起動できなく
   なる**。加えて EC2 は停止しても root ボリュームが課金され続けるので、目的である
   scale-to-zero そのものが失われる。したがってサービスは**置き場所を必ず明示する**——通常は
   **`LaunchType: FARGATE`**、P3 の Spot つまみを ON にしたときは（両者は排他なので）
   **`CapacityProviderStrategy` に `FARGATE_SPOT` を明示する**。この決定を破るのは
   「どちらも書かないこと」である——API 既定は EC2 で、プールに落ちる。**2026-09-07 実測**:
   `defaultCapacityProviderStrategy` が空のクラスタで、LaunchType なしに
   `capacityProvider=FARGATE_SPOT` を指定したタスクは Spot に配置された＝明示の戦略は
   LaunchType と同じだけ拘束力がある。こちらの言い方のほうが長持ちもする: このクラスタの
   `capacityProviders` はもう空ではなく（別の作業が 1 本関連付けた）、「クラスタに capacity
   provider が無いから」はもう理由ではない。理由は「置き場所が書いてあるから」である。

2. **独立した任意採用のスタック `50-tts.yaml` を、`30-ingress` より先に配る。** VPC・
   プライベートサブネット・CP のセキュリティグループを `00-network` から、クラスタ・実行
   ロール・名前空間を `20-platform` から import する。`30-ingress` には依存しない。
   `30-ingress` 側は既定が空のパラメータ 2 つ（`TtsEcsService` / `VoicevoxUrl`）を受け、
   非空のときだけ環境変数に出す——既存の条件付きシークレットと同じ形。循環参照は起きず、
   音声が要らない配備は何も建てない。`30-ingress` に足す案は、51,200 バイトの壁まで残り
   11 KB しかない枠を、多くの配備が有効にしない機能で削ることになる。（`50-` は `40-ec2-pool`
   の後に並ぶが、あれも standup は `30-ingress` より先に配る。順序はファイル名でなく README に
   書く。）

3. **需要とは「意図」であって「結果」ではない。** アイドル時計を押し直すのは、
   *エンジンが起きていれば* `chooseTTSProvider` が voicevox へ振ったはずの合成要求
   （`provider` が `auto` か `voicevox`、言語が `en` でない、ルーティングが OFF でない）で
   あって、実際にどこへ行ったかではない。結果で数えると成立しない: 起動中の要求はすべて
   Polly が返すので、**一番大事な 2 分間の需要がゼロに見え**、コントローラは自分が建てた
   サービスを止め、次の要求がまた建てる。**「voicevox が処理した要求」を数える実装は、
   構造的にフラップする。** 意図は利用者の**設定値**で判定する。したがって決定 13 の発話中の
   固定は専用の要求フィールドで運び、決して `provider: polly` にしない——固定された回答の残りが
   数えられなくなると、自動の引き金が飢え、誰かが聴いている最中にアイドル時計が切れる。
   意図でない要求は、設定値が `polly` のものだけである。（`lang=auto` は英語の本文も数えるが、
   それは既存のルーティングがどのみちエンジンへ送るものである。設定値が明示 `voicevox` の
   要求は言語によらず数える——それは実際にエンジンへ届く要求だからである。）

4. **損益分岐を超えたら自動で建て、人が求めたらいつでも建てる。** 引き金は 2 つあり、
   答えている問いが違う。
   - **自動**: 直近 5 分間の「voicevox 意図」の文字数が `AF_TTS_ECS_START_CHARS`
     （既定 **2,000**＝回答 1 本ぶん。時間換算 24,000 文字/時＝実測した損益分岐のおよそ 3 倍で、
     アイドル窓のぶんの余裕を残す）を超えたとき。待っても無音にはならない——Polly が読んで
     いるからである。この規則は、**セッション通知を有効にして Console を開きっぱなしにして
     いるだけでは自動起動しない**ことも意味する。数十文字の告知のために 8 時間ぶんの Fargate を
     買ってしまう唯一の経路が、これで塞がる。
   - **明示**: `POST /api/tts/wake`。「ずんだもんを呼ぶ」操作の裏で、ログイン済みの利用者なら
     誰でも押せる。通知をあの声で聴きたい人が、量で資格を稼がされる筋合いはない。
     費用が発生するので監査に残す。冪等（`running` / `starting` 中の wake は需要時計を押す
     だけ）で、利用者ごとにレート制限する。

     **実装（P2）**: 需要時計は**状態によらず、起動より先に**押す——押した事実が「いま聴いて
     いる人がいる」という申告であり、エンジンが到着する前にアイドル窓が閉じるのを防ぐのは
     それだからである。失敗の連続回数は管理者トグルと同じく人の操作でクリアする（クール
     ダウンは自動再試行を止めるためのもので、ボタンを押した人を断るためのものではない）。
     取り繕わずに断る場合が 2 つある: ここから起動できるエンジンが無ければ `501`、モードが
     `off` なら `409`——利用者が管理者の判断を金で越えることはできないし、ルーティングが
     OFF のまま建てたタスクは誰にも聴かれずに課金される。上限は 5 分あたり 3 回／利用者。
     コールドスタートは 70〜77 秒で、ボタンの前には待つ以外にすることのない人が座っている。
   - どちらの引き金にもできないのは、引き金を引いた回答自身にエンジンを間に合わせること
     である。実測では 2,037 文字の回答が音声 6 分 00 秒、エンジンの到着が 70〜77 秒なので、
     最初の回答はよくても最初の 1/5 が Polly になり、その窓をエンジンが稼ぐかどうかは次の
     回答が続くかで決まる。

5. **アイドル窓で止める。`AF_TTS_ECS_IDLE_SEC`、既定 1800 秒、`0` = 止めない。** `0` が OFF
   なのはこの repo の流儀（スロットの sleep で一度これを間違えている）。15 分でなく 30 分に
   するのは、**縛っているのが費用ではないから**である——無駄になった窓 1 回の費用は **$0.062**
   にすぎない一方、建て直しには 70〜77 秒かかり、その間はみんなが知っている声が Polly に
   置き換わる。**建て直しで高いのは請求書ではなく中断のほうだ。** 窓は `starting` にも
   適用する。さもないと、配置できずに desired 1 で張り付いたサービスが、誰も待っていなく
   なった頃に突然エンジンを起こす。窓の下限は決定 9 の起動期限に clamp する——コールドスタート
   より短い窓は `starting` の最中にサービスを止め、次の 1 文がまた建てる。意図の規則では
   防げないフラップである。

   **明示 OFF にも約 1 分の猶予を置く（`AF_TTS_ECS_OFF_GRACE_SEC`・既定 60）。** 理由は費用
   ではなく、**画面上 ON/OFF をこまめに押せてしまうこと**である（試しに切って、やっぱり戻す）。
   ON のたびに 2 GB の pull と 70〜80 秒を払うのは割に合わない。遅らせるのは**停止ではなく
   desired count の書き込み**——窓の内に ON へ戻れば count は一度も動いておらず、中断も費用も
   ゼロである。画面は OFF を押した瞬間から `stopping` と出す（決定 7）。モードは既に off で
   あり、それ以外を出すのは意図の逆を報告することだからである。**30 分ではなく 1 分**にする
   非対称がこの決定の要点で、`tts_engine=off` の間は `chooseTTSProvider` の `engineOff` が
   `auto` を Polly へ回すので、**猶予中に生きているエンジンは誰の役にも立たない**——ただ
   「買い直すより持ち続けるほうが安い」だけである。（唯一救われないのは設定値を
   `voicevox` に固定している利用者で、その要求は `engineOff` を見る前に無条件で返される。
   エンジンが落ちた瞬間 502 になり、`synthToBuffer` はそれを黙って読み飛ばす。猶予では
   直らない。直すのは決定 13 であり、P2 の範囲である。）

6. **需要の時刻は永続化する**（書き込みは 1 分に 1 回へ絞る）。置き場は `tts_engine` と
   `tts_dict` が既に居る `SettingsStore`。メモリだけだと、CP 再起動が「需要ゼロ」と読んで
   **聴いている人の足元でエンジンを止める**。保存値が無い CP は**刻むだけで、その回は判定
   しない**——空きスロット掃除が使っているのと同じ「初回は押すだけ」の規則で、これが
   デプロイ中に CP が 2 レプリカ重なっても安全な理由でもある。`lastStart` はそもそも保存
   しない。`DescribeServices` の PRIMARY デプロイの **`updatedAt`** から読むので、起動の途中で
   置き換わった CP も前任と同じ時計で期限を判定する。**`createdAt` ではない**——実サービスで
   実測したところ、あれは*デプロイ*が作られた時刻（スタック作成時＝数時間〜数日前）で、
   desired が 0 → 1 になっても動かない。それを起点に期限を測ると、**できあがっているサービス上の
   起動はすべて開始した瞬間に「失敗」と判定され、エンジンは永久に上がらない。**

7. **`tts_engine` を 3 値化する（`off` / `on` / `ondemand`）。desired count は管理者の意図で
   あることをやめる。** それまでの `ttsAdminAPI.status()` は managed のとき
   `enabled = desired >= 1` と答えていた。オンデマンドでは desired が自分で動くので、管理者は
   触っていないトグルが動くのを見ることになる。画面は**モード**（意図・保存値）と**状態**
   （実況）を別のものとして出す。これは VOICEVOX の無い配備で
   見つかった「嘘 3 件」と同じ種類の欠陥＝**設定値を実態であるかのように出す画面**である。

   状態は `running` / `starting` / `stopped` に **`stopping`** を足した 4 つ。`stopping` は
   ECS の状態をモード越しに見たもの＝desired はまだ 1 だがモードは off、つまり決定 5 の
   取り消し窓の最中である。未設定は、エンジンが管理下ならオンデマンド、そうでなければ on。
   `50-tts` を配ったこと自体が採用の意思表示であり、**値を選ばなかった配備が月 $90 を払い
   続ける側であってはならない**からである。

8. **エンジンには Cloud Map の DNS 名で到達する。Service Connect は使わない。** `50-tts` は
   既存の `DNS_PRIVATE` 名前空間に `ServiceRegistries` で A レコード（TTL 10 秒程度）を登録し、
   `voicevox.<名前空間>` は他の名前と同じく VPC リゾルバが引く。`/etc/hosts` のスナップショット
   も、要求経路の Envoy サイドカーも無く、`ttsHTTP` と `AF_VOICEVOX_URL` はそのまま——ADR 0013
   と `tts_ecs.go` のヘッダが最初から想定していた形である。desired 0 の間は名前にレコードが
   無く、NXDOMAIN → `Ready` は false → Polly が読む。実測した SOA TTL 15 秒が、起動が負の
   キャッシュに隠れる時間の上限になる。却下した 2 案（却下した案を参照）: Service Connect の
   別名＋`ttsHTTP` を共有 Agent トランスポートに載せる案と、`ListTasks` / `DescribeTasks` で
   タスクの ENI を引く案。後者の動機だった別名のスナップショットは、そもそもここでは起きない
   ——音声の有効化は CP の task definition に環境変数を足すので、CP タスクはエンジンのスタックが
   できた後に必ず置き換わる。この決定が依存する 2 つの遅延は P0 で測る: `RUNNING` から
   A レコードが現れるまで、停止からレコードが消えるまで。

9. **コントローラの判断は純関数にする。** `chooseTTSProvider` と同じ流儀で
   `decideEngineAction(now, state, desired, lastDemand, lastStart, cfg) → none | start | stop`
   とし、テーブルテストを付ける。AWS 呼び出しはその外側に置く——既存の偽 `ttsEngineAPI` が
   そのまま使える。起動の失敗は `DescribeServices` の `events[]` から診断する（追加権限は
   不要で、本当の理由——配置制約を満たす箱が無い、pull に失敗した——が文章で書いてある唯一の
   場所である）。期限内に `running` にならなかった起動は、**その文言つきで失敗を名乗り**、
   永久に再試行せず desired を 0 に戻す——**そしてクールダウンの間は建て直しを拒む**（15 分。
   連続失敗ごとに倍）。これが無いと次の 1 文が即座にサービスを建て直し、繰り返す失敗は試行
   ごとに 2 GB の pull を払う。

   **勝手に死んだエンジンは「起動の失敗」ではなく、そう記録もしない。** コントローラが
   `running` を離れるのは desired 0 を書いたときだけで、それは `stopped` に見える。desired が
   1 のまま `running` → `starting` に戻ったなら、タスクを奪ったのは別の何か——「P0 の実測」の
   OOM kill、ヘルスチェックによる置換、中断——である。この遷移は別の行為として監査に残し
   （`tts.engine.replaced`）、desired は動かさない。ECS が既に置き換えており、warm ゲートは
   閉じているので、戻るまでは Polly が読む。

10. **`DescribeServices` に短い TTL キャッシュを被せる**——これは何より先に。status
    ハンドラは要求ごとにこれを呼んでおり、管理モーダルだけがポーリングしている今は無害だが、
    「準備中」を描くために全クライアントがポーリングし始めた瞬間に無害でなくなる。隣にある
    4 秒の readiness キャッシュと同じ形でよい。

11. **x86_64。arm64 は実測の結果、採らない。** イメージは両対応で ARM Fargate は 20.0% 安い
    ので、Graviton の ONNX 推論が元を取れるかが問いだった。**取れない——arm64 は 20% 安く
    52% 遅い**（同じ文で 6.73 秒 対 4.42 秒）。これはこの決定が拒むと書いた取引そのもので、
    42 字文でも実時間比 0.92、短文では 1.15 で再生に追いつかない。アーキは
    スタックパラメータとして**宣言する（導出しない）**——ADR 0053 が CP で確立した形。
    `--cpu_num_threads` はタスクの vCPU 数に合わせる。放っておくとエンジンが勝手に決める。

    **安いほうの x86 サイズもその後に実測し、これも不採用にした**（「P3 の実測」）:
    1 vCPU/2 GiB は普段は 5% 程度しか遅くない。落ちたのは別の 2 行である——**OOM の壁が
    CP の 1 要求上限（決定 17 の 300 字）の内側に入り**、3 回に 1 回は 50% 遅く（回答 1 本の
    実時間比 **1.01**＝再生が追いつかない）なった。**サイズは 2 vCPU/4 GiB のままとする。**
    どちらもスタックのパラメータのままにする: この結論はこのエンジン・このイメージについての
    ものであり、どちらかが変わったら引き継がずに測り直すべきものである。

12. **キャラクター一覧は、エンジンが止まっていても生き残らせる。** `/api/tts/speakers` は
    生きたエンジンを proxy するので、停止が通常状態になるオンデマンドでは、キャラクター選択が
    ほとんど常に使えない。一覧は永続キャッシュし、エンジンが起きているときに更新する。

    実装（P2）は `SettingsStore` の 1 エントリ（`tts_speakers`。`tts_engine` / `tts_dict` の
    隣）で、応答はそれが生きた一覧かどうか（`live`）も返す。更新は生きた読み取りのたびと、
    **コントローラが新しいエンジンを温めた瞬間**——効くのは後者である。前者だけだと、
    エンジンが生きている 30 分の間に誰も設定画面を開かなかった配備は一覧を一度も掴めず、
    以後ずっとキャラクター選択が空のままになる。ハンドラはエンジンへ行く前に到達性の
    キャッシュを見るので、停止中は HTTP を 1 回も投げない。

13. **クライアントは 1 回の発話の間プロバイダを固定し、`auto` で焼いた音声はルーティングが
    変わったら捨てる。** キャッシュのコメントは既に「auto の行き先が変わった直後は古い声が
    鳴りうる」と認めているが、オンデマンドではそれが例外ではなく**起動のたびに必ず起きる**。
    そして回答の途中で声が変わるのは、どちらか一方の声で通すより悪い。応答は既に
    `X-TTS-Provider` を返し、クライアントはバッファごとにそれを覚えているので、どちらの修正も
    小さい。設定値が `voicevox` の要求は、管理下のエンジンが停止中なら 502 でなく Polly が
    `X-TTS-Provider: polly` つきで答える。いまの `synthToBuffer` はその 502 を「その文を飛ばす」
    に変えるので、オンデマンドではエンジンが来るまで全文が無音になる。

    **実装（P2）は 3 つで、それぞれ形が効いている:**
    - 固定は**専用の要求フィールド**（`pin`）で運び、`provider` は利用者の設定値を運び続ける。
      `provider: "polly"` で代用すれば行数は減るが、6 分の回答の残りが需要として数えられなく
      なる——決定 3 のフラップが「聴いている人の足元でアイドル窓が閉じる」形で現れる。
    - 音声キャッシュのキーは `pin || provider` にし、さらに**未固定の `auto` 要求が別の
      プロバイダから返ってきた瞬間に `auto` キーのエントリを捨てる**。キーだけでは足りない:
      *次の*読み上げの 1 文目は未固定で、そこで古いエントリを引くからである。
    - **固定が決まるまで先読みは 1 本に絞る**。通常の 2 本同時では 2 文目も未固定で飛び、
      それこそが別の声で返りうる文である。代償は読み上げ開始時の先読み 1 文ぶんで、そこは
      読点で切った短い頭出しである。

14. **エンジンに到達できるのは CP だけにする。** 専用のセキュリティグループ、50021 の ingress は
    CP のセキュリティグループからのみ、ロードバランサ無し、プライベートサブネット。VOICEVOX の
    HTTP API は無認証で変更系のエンドポイントを持つ。`0.25.2` は `--disable_mutable_api`
    （または `VV_DISABLE_MUTABLE_API=1`）でそれを無効化でき、task definition がそれを渡す。
    イメージは版で固定し、タスク起動時に Docker Hub から引くのではなく `crane` で ECR へ
    複製する——この配備の外向きは NAT の 1 アドレスから出るため、匿名 pull の枠を配備全体で
    共有することになるからである。

15. **サービスにはコンポーネントの費用配分タグを付ける。** これは共有費用であり、ADR 0048 の
    とおり**共有費用は表示するが、メンバーへ按分しない**。

16. **`Ready` は「温まっている」の意味であり、`running` は `Ready` ではない。** `/version` は
    音声モデルを読み込む前に 200 を返すので、起動直後の最初の合成は遅い。コントローラは
    `/version` が答えた後に既定話者で短いウォームアップ合成を 1 回行い、それから初めて ready
    として扱う。実測すると、これは安いほうの取引である——遅延ロードの代償は**一度きりの
    650 ms**、`--load_all_models` の代償は**起動のたびに 19 秒**。よってウォームアップを採り、
    フラグは使わない。ECS の `RUNNING` はコンテナが始まったと言っているだけで、
    P2 の「準備中・いまは Polly が代読」表示は `Ready` 基準にし、サービス状態では決して
    判断しない。task definition には `/version` のコンテナヘルスチェックを付け、固まった
    エンジンを `running` のまま到達不能に放置せず ECS に置き換えさせる。**ただしこのチェックは
    P0 が見つけた OOM kill の網にはならない**——死ぬ瞬間まで HEALTHY のままだった。実際に
    効くのは、`/version` が答えなくなった時点で warm ゲートが落ちること、そして ECS が
    タスクを置き換えることのほうである。

    **利用者側の半分（P2）** は読み上げ設定タブに置いた。オンデマンドが「停止」を通常状態に
    したから必要になったものである——それ以前は、日本語が急に Polly で読まれ始めた利用者には
    見るものも押すものも無かった。区別するのは *準備中*（数秒待てばよい）・*停止中*（呼べば
    よい＝決定 4 のボタン）・*管理者が無効*（利用者にできることは無い）の 3 つで、最初の 1 つは
    `Ready` で判定し、サービス状態では決して判定しない。

17. **1 回の合成要求は 300 文字を上限とする**（`AF_TTS_MAX_CHARS`、`0` で無効）。超えたら
    `413 tts_text_too_long`。これで未解決の点 3 を閉じる。割り当て制限ではなく安全柵である:
    **2026-09-07 実測、4 GiB のエンジンは 684 文字の単発要求で OOM kill される**（exit 137。
    P0 の「約 2,000 字」より早い。ヘルスチェックが死ぬ瞬間まで HEALTHY なのは P0 のとおり）。
    その後 ECS がタスクを置き換える 2 分半、全員が Polly を聴くことになる——不注意な 1 人の
    要求が、聴いている全員の費用になる。

    この数字は、分けたい 2 つのものの間にある。上側: どのみち成功しなかったもの——`ttsHTTP`
    のタイムアウトは 30 秒で、228 字の 1 文が実測 26 秒なので、300 字はもう縁を越えている。
    下側: 実クライアントは遥かに下——文末で切り、60 字を超える文はさらに割ってから CP を
    呼ぶので、この上限に届くのはスクリプトだけである。サーバ側で分割する案より上限を採る:
    WAV の連結は本物の作業量で、それを必要とするのはまさにこの上限がエンジンを守っている
    相手だけだからである。

## 実測で解けた点（2026-09-06）

1. **`desiredCount: 0` のサービスは名前空間に現れる——インスタンスの無い「名前」として。**
   ecs-ec2 配備で実測（「実測」の節を参照）: 停止中の Workspace サービスは HTTP 型の Cloud Map
   サービスとしてインスタンス 0 で列挙され、ゾーンには desired に関係なく A レコードが無い。
   Service Connect は DNS を書かないからである。したがって決定 8 はこの点に一切依存しない。
   Cloud Map の DNS サービスは停止中は A レコードが無いだけで、タスクが動けばそれが生える。
2. **CloudFormation が `DesiredCount` を戻すのは、プロパティを宣言していて、かつ Service
   リソース自体が更新されるときだけ。** リソーススキーマより: 省略すると作成時に 1 で立ち、
   以後の更新では操作から省かれる。`50-tts` は省略し、standup が作成直後に 0 へ落とす
   （どのみちコントローラがアイドル窓 1 回・$0.062 で落とす）。`0` を宣言すると、サービスの
   task definition やタグの変更のたびに——誰かが聴いている最中に——戻る一方、Service リソースに
   触れない更新では戻らない。省略はその非対称を避ける。**P0 で実スタックに対して確認した**
   ——TaskDef を変える更新を通しても desired は 0 のままだった。省略でも避けられないのは
   **作成時**で、そこは CloudFormation がサービスの安定を待つため、スタックを建てれば必ず
   1 回コールドスタートを払う。
3. **サイズ・起動時間・合成レイテンシ** ——「P0 の実測」を参照。エンジンは 1 秒未満で起動して
   最初のクエリで 650 ms を払い、2 vCPU/4 GiB は実時間比 0.61、1 vCPU/2 GiB は単価半分で 0.79、
   arm64 は 0.92（決定 11）。

## 未解決の点

1. **VOICEVOX とずんだもんの利用規約を、「運用者＝聴く人」でない配備について。** P0 で材料は
   揃えた: ずんだもんは「VOICEVOX:ずんだもん」のクレジットで商用・非商用とも利用可、エンジンは
   起動時に全キャラクターの規約を吐く（CloudWatch に残る）、その文言は `/speaker_info` の
   `policy` と同じ。**それがマルチテナント配備で第三者に声を提供するのに足りるかの判断は、
   この文書ではなく運用者の仕事である。**
2. **「5 分で 2,000 文字」は正しい引き金か。** 損益分岐から導いた値であって、観測された行動から
   出した値ではない。決定 4 の警告は両側から実測できた（到着 70〜77 秒・回答 1 本の読み上げ
   6 分）。実利用が 1 週間ぶん溜まったら閾値を見直す。
3. ~~**4 GiB の OOM kill と 30 秒のクライアント側タイムアウト。**~~ **決定 17 で閉じた**
   （2026-09-07）。上限を測り直したところ、4 GiB を殺すのに必要なのは単発 **684 文字**で、
   P0 が見積もった約 2,000 字よりずっと手前だった。CP は 1 要求 300 文字で上限を切る。
   `ttsHTTP` の 30 秒は意図して据え置く——いまやそれは「上限のわずかに上」であって、
   「無制限の要求の下」ではない。

## 却下した案

- **常時起動のまま。** 月 $165 規模の配備に月 $90＝5 割増を、1 日の大半は黙っている機能のために
  払う。
- **EC2 スロットプールに載せる**（決定 1）。
- **最初の日本語 1 文で建てる。** 最も単純でレイテンシも最良だが、30 文字の告知のために 30 分の
  窓を買う。セッション通知を有効にして Console を開きっぱなしにすれば、数文のために一日中
  エンジンが生きる。本当にそれを望む人は、決定 4 の明示操作で救われる。
- **明示ボタンのみ。** 予測可能で費用にも正直だが、Polly で既に百文を読ませた人は需要を
  証明済みであり、そこで改めて頼ませるのは儀式である。
- **業務時間のスケジュール起動。** 予測可能だが、黙っている時間に払い、時間外の人には常に
  間違っており、誰が聴いているかを知らない。上限として後から重ねることはできるが、規則の
  本体にはならない。
- **既定を Fargate Spot にする。** 約 70% 安く、中断しても Polly に落ちるだけだが、アイドル停止
  を入れた時点で残る請求は既に小さく、容量不足は「いつまでも来ないエンジン」として表に出る。
  後段のつまみとして残す。**P3 はそのつまみをそのまま出荷した**（`UseSpot`・既定 OFF）。
  決めるべきだったのは「決定 1 を壊さずに Spot を表現できるか」だけで——Spot は capacity
  provider strategy であり `LaunchType` と排他である——実測はできると言った（決定 1）。
  未決なのは ON にするかどうかで、それは実際に聴く人のいる配備での判断である: 中断は通知の
  チャイムなら安く、6 分の回答の途中なら高い。
- **SOCI の遅延ロード。** Workspace イメージでこれを却下したゲートは「pull が 40 秒以上かつ
  全体の 40% 以上」で、**別の、より小さいイメージに対して**測ったものだった。ここでは pull が
  コールドスタートの大半を占めそうだったので、答えが変わりうると書いた。**P3 で測り直した
  （2026-09-07・このイメージの起動 2 回）: pull は 34.7 秒と 35.9 秒、起動全体は 51.0 秒と
  56.4 秒——62〜68% を占めるが、ゲートの「40 秒以上」には届かない。** つまり反対側から同じ
  ゲートに落ちる: pull は支配的だが、リリース経路に索引付けの工程と 2 つ目の成果物を増やす
  ほどの量ではない。イメージが太ったら再考する。
- **Lambda / App Runner。** Fargate に対する scale-to-zero の利点が無く、当てはまりも悪い
  （2 GB のモデルサーバは関数ではないし、App Runner はインスタンスを温存する）。
- **ECS でタスクの ENI を引く（`ListTasks` → `DescribeTasks`）**——初稿の決定 8。動くし DNS に
  依存しないが、コードが最も多く（リゾルバ、そのキャッシュ、タスク置換時の無効化、miss ごとに
  API 2 回）、動機だった Service Connect 別名のスナップショットは、音声の有効化がエンジンの
  スタックの後に CP タスクを置き換えるので、そもそも起きない。
- **Service Connect の別名＋`ttsHTTP` を共有 Agent トランスポートに載せる。** Go では 1 行だが、
  合成の経路に Envoy サイドカーが入る。その per-request timeout の既定 15 秒は `ttsHTTP` の
  30 秒より短いので、エンジン側の Service Connect 設定で引き上げねばならず、サイドカーは
  コールドスタートを毎回伸ばす。
- **テナントごとのエンジン。** エンジンはテナント固有の状態を持たない（辞書の項を参照）ので、
  買えるのは負荷の分離だけで、費用は N 倍になる。同時実行が苦情になったら再考する。

## フェーズ

- **P0 — まず存在させる。完了（2026-09-06）。** `50-tts.yaml`、`30-ingress` のパラメータ、
  固定版イメージの ECR への複製、standup / update / teardown / capture-env に新スタックを
  教える。実配備でエンジンが動き、以降が依存する数字は「P0 の実測」にある。1 点だけ確認
  できなかったのは **CP を通した `X-TTS-Provider: voicevox`** で、そこでは Console の Google
  ログインをヘッドレスブラウザから通せなかった。エンジン自身が VPC 内から正しい WAV を返す
  ことは実測済みである。
- **P1 — 自動にする。完了（2026-09-06）。** 需要トラッキング（決定 3・6）、コントローラ
  （決定 5・9。アイドル窓の clamp、失敗後のクールダウン、明示 OFF の取り消し窓）、
  `DescribeServices` のキャッシュ（決定 10）、モードと状態を分けて出す 3 値モード（決定 7）、
  `Ready` の前段に立つウォームアップ（決定 16）。アドレッシング（決定 8）は P0 に含まれる——
  スタックの話であって CP の話ではない。自動の起動と停止はすべて監査に残す
  （`tts.engine.auto`・アクター `tts-controller`）——**誰にも説明できない請求は、誰にも
  信用されない。** つまみ（既定値は上のとおり）:
  `AF_TTS_ECS_CONTROL_INTERVAL_SEC`（30・`0` でコントローラ停止）、`AF_TTS_ECS_WINDOW_SEC`
  （300）、`AF_TTS_ECS_START_CHARS`（2000）、`AF_TTS_ECS_IDLE_SEC`（1800・`0` で止めない）、
  `AF_TTS_ECS_START_DEADLINE_SEC`（300）、`AF_TTS_ECS_FAIL_COOLDOWN_SEC`（900・連続失敗ごとに
  倍、上限 16 倍）、`AF_TTS_ECS_OFF_GRACE_SEC`（60）。
- **P2 — 気持ちよくする。完了（2026-09-07）。** 停止中の `voicevox` 明示要求への Polly 応答、
  発話中のプロバイダ固定とそれに伴うキャッシュ破棄（決定 13）、永続キャラクター一覧
  （決定 12）、「ずんだもんを呼ぶ」操作（`POST /api/tts/wake`・決定 4）と、その隣の
  「準備中・いまは Polly が代読」表示（決定 16）。決定 17 の 1 要求上限も一緒に入れた——
  同じクライアントの同じ要求がぶつかる先だからである。
- **P3 — 根拠つきで安くする。完了（2026-09-07）。ただし根拠はおおむね「やめておけ」と
  言った。** **arm64 は入れない**（P0: 20% 安く 52% 遅い）。**1 vCPU/2 GiB も入れない**——
  「P3 の実測」のとおり、安くなる場所が悪い: OOM の壁が CP の 1 要求上限の内側へ入り、
  3 回に 1 回は再生に追いつかなかった。**Fargate Spot は `UseSpot`（既定 OFF）として出荷**し、
  「明示の capacity provider strategy は `LaunchType` と同じだけ拘束力がある」という実測を
  添えた（決定 1）。ON にするかは実際に聴く人のいる配備での判断であって、実測の話ではない。
  **SOCI は不採用**: pull はコールドスタートの 62〜68% を占めるが約 35 秒しかなく、Workspace
  イメージを却下したのと同じ 40 秒のゲートに届かない。
