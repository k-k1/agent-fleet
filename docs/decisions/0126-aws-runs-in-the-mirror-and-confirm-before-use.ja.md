## 背景

設定のプロファイルにサインインした後は、`af-aws-exec --profile <p> -- <command>` を実行しても、トランス
クリプトに残るツール呼び出しのコマンド行以外に痕跡が残らない。その行は見落としやすく、スクリプトの中で
呼べば完全に隠れる。今はプロファイルごとのログインが承認の役も果たしている。各プロファイルの初回使用には
メンバーがデバイスコードを承認する必要があり、エージェントはそれを一人ではできない。ADR 0125 は複数の
プロファイルに 1 つのトークンを共有させるので、1 回の承認がサインイン内の全プロファイルに及ぶ。本番の
管理者プロファイルも含めてである。

あるもの・ないもの（コードを読んで確かめた）:

- **セッションのミラーに表示専用の行を差し込む仕組みはない。** ミラーは CLI のトランスクリプトと、Agent が
  `GET /sessions/{name}/messages` で返すパネルを表示する。パネルは保留中のピアメッセージ
  （`AgentStateDir/pending-peer/<session>/` の置き場、`PendingPeersNotice`）、破棄、引き継ぎ提案である。
  セッション宛ての通知は通知センターにしか届かず、CP はそのセッションが存在するかを確かめない。
- **帰属は `AF_SESSION_NAME` を信用している。** プロセスをセッションに結び付ける経路はどれも環境変数から
  読む（`listenports.sessionOf`、`aws_exec.go`、`gcloud_exec.go`）。エージェントは自分の環境を設定できるので、
  別のセッション名を名乗ることも、名乗らないこともできる。
- **Agent の経路はすべて `AGENT_TOKEN` で呼べる。** エージェントのシェルはそのトークンを持っている。CP は
  中継したものに `X-AF-Relay: cp` を付けるが、エージェントも同じヘッダーを送れる。エージェントが書けない
  記録は CP の監査だけ。
- **エージェントはメンバーのユーザーとして動く。** `~/.aws/config`、SSO トークンのキャッシュ、ロール資格情報の
  キャッシュを読めるし、`af-aws-exec` を通さずに `aws` を実行できる。

## 決定

### 1. 実行ごとに、そのセッションの実行記録に 1 行書く

`af-aws-exec` はコマンドの開始前に **実行行** を書き、コマンドの終了時に完成させる:

- **項目:** 時刻、プロファイル、アカウント、ロール、リージョン、サインイン（ADR 0125）、連鎖ならソースの
  プロファイル。アカウントとロールは、コマンドが実際に動く身元である。連鎖ならターゲットのロールで、ソースは
  「`<source>` 経由」として出す。プログラムのベース名も、`[A-Za-z0-9._-]{1,32}` に切り詰めて記録する。
  コマンドの終了時に終了ステータスと所要時間を足す。身元はコマンド行からではなく、`PlanExec` がその実行に
  ついて解決したものから取る。
- **サービスと操作は、既知の名前だけ。** 正規表現ではサービスとオプションの値を見分けられない。
  `aws --profile <小文字>` も、打ち間違えた `aws ssm <小文字の秘密>` も `^[a-z0-9-]+$` に合う。そこで記録するのは、
  プログラムが `aws` で、最初の引数が `-` で始まらず、それがサービスのコマンド名の一覧にあり、2 番目の引数が
  そのサービスの操作のコマンド名の一覧にあるときだけ。2 つの一覧は固定した aws-cli から生成し、古くなれば
  テストが落ちる。それ以外は（サービスの前のグローバルオプションも含めて）`aws` だけを記録する。
- コマンド行の残り、引数、環境変数、コマンドの出力は **決して** 記録しない。引数には秘密が入りうる。引数と
  環境変数に番兵を仕込んだコマンドを実行し、その番兵が実行記録のファイル、`/messages` の応答、通知、Agent の
  ログ、CP へのリクエストのどれにも届かないことをテストで確かめる。番兵には、サービスや操作の位置に置いた
  小文字とハイフンの値（`aws ssm <番兵>`）と、AWS のグローバルオプションの値（`aws --profile <番兵> s3 ls`、
  `--region`、`--endpoint-url`）を含める。
- 資格情報の前に拒否された実行（exit 1・2・3、または下の 4）も、理由コードを付けて、コマンドの終了ステータス
  なしで 1 行書く。
- **置き場:** `AgentStateDir/cloud-runs/<session>/`。1 回の実行につき 1 ファイルで、ログインリクエストと同じく
  CLI のプロセス自身が書く（ADR 0102 決定 1）。ディレクトリ名は特定のクラウドに依らないので、後で
  `af-gcloud-exec` も書ける（この ADR の範囲外）。1 セッションにつき最大 200 行を保ち、古いものから消す。
  ディレクトリはセッションとともに消える。
- **どのセッションか:** `AF_SESSION_NAME` が指し、Agent が知っているセッション。名前がない、または Agent の
  知らない名前の実行は `cloud-runs/_workspace/` に入れ、7 日間保つ。

### 2. ミラーには行を、設定には全セッションの行を出す

- `GET /sessions/{name}/messages` に、そのセッションの行 `cloudRuns` を足す。ミラーは各行を、ターンの間に時刻順
  で 1 行として描く: 「AWS · `prod-admin` · 123456789012 / AdministratorAccess · ap-northeast-1 ·
  `aws s3 ls` · exit 0 · 3 秒」。どの種類のセッションでも同じ場所に出し、トランスクリプトに時刻のない種類では
  最後のターンの後に出す。
- 設定 > AWS プロファイル/SSM に「最近の実行」の一覧（`GET /aws-runs`。全セッションと `_workspace` の直近 100 件）
  を置く。セッション名を消された、または偽られた実行も、どこかには見える。
- 実行ごとの通知もチャットブリッジへのメッセージも出さない。実行は人を必要とする出来事ではなく、毎回通知すると
  人を必要とする通知が埋もれる。

**帰属が意味すること。** セッションは、実行が **申告した** もの。正直なエージェントや、それが走らせる
スクリプトは、自分のミラーに出る。`AF_SESSION_NAME` を変えたエージェントは、行を別のセッションのミラーや
`_workspace` に移せるが、「最近の実行」から消すことはできない。`af-aws-exec` を使わないエージェントは行を
まったく残さない。行は見える化であって、監査ではない。実行のプロセスツリーをセッションと照合すれば（決めたこと H）
帰属の偽りは止まるが、迂回は止まらない。

### 3. SSM セッション

SSM セッションのミラーはその端末である。`aws ssm start-session` の前に、ペインは 1 行を表示する:
「`[Agent Fleet] AWS プロファイル <p> · アカウント · ロール · リージョン · ターゲット <instance>`」。同じ実行行を
SSM セッション自身の実行記録にも書く。開始は CP が既に監査している（`ssm.start_session`）。

**関門は SSM を覆わない。** SSM セッションの開始と、開始モーダルのインスタンス一覧（`POST /ssm/instances`）は
Console でのメンバーの押下であり、メンバー自身の使用とみなす。どちらも `PlanExec` を通らない。資格情報は
ペインや探索の呼び出しの中の CLI が解決し、CLI はロール資格情報を `~/.aws/cli/cache` にキャッシュする。関門の
あるプロファイルのものもである。だから決定 6 の主張（「ロール資格情報をディスクに残さない」「`~/.aws/config`
に書かない」）が成り立つのは `af-aws-exec` だけ。メンバーが関門のあるプロファイルで SSM セッションを開いたり
インスタンスを一覧したりした後は、エージェントは自分で書いた設定を通じて、そのキャッシュ済みのロール資格情報を
期限まで使える。ガイドにそう書く。`AGENT_TOKEN` で Agent 自身の経路から SSM セッションを作るエージェントは、
決定 6 の 1 の迂回にあたる。

### 4. 「使用前に確認」はプロファイルごとの設定項目

- `ssm_profile` に `confirm_use INTEGER NOT NULL DEFAULT 0` を足す。`ssmProfileDTO` とブリッジの
  `awsProfileWire` には `confirmBeforeUse`（偽なら省く）を足す。どの種類のプロファイルでも設定できる。
- **実行に要る承認。** 連鎖は **ターゲット** のロール（`role_arn` とそのロールのアカウント）として動く。ソースは
  認証元にすぎず、ソースのロール資格情報は `sts:AssumeRole` にだけ使う。したがって:
  - プロファイル `p` の実行は、`p` に関門があれば `p` の承認が要る。
  - 連鎖は、ソースに関門があればソースの承認も要る。ソースのロールを使うからである。
  - ソースの承認は関門のあるターゲットの承認にはならず、その逆もない。
  - 両方に関門があれば両方が要る。1 枚のカードに 2 行で尋ね、ターゲットの身元を先に、次に「`<source>` 経由
    （アカウント / ロール）」を出す。

  検査は SSO の取り出しの前だけでなく、連鎖の分岐（`exec_nonsso.go`）の前でも行うので、どの資格情報の経路も
  それを飛ばさない。
- これはプロファイルの項目で、サインイン（ADR 0125）の項目ではない。`prod-admin` を確認しても、同じサインインの
  ほかのものは確認されないし、サインインにログインしても何も確認されない。
- メンバー自身の `~/.aws` のプロファイルにはこの項目がない。情報源は設定の一覧だけ。

### 5. `af-aws-exec` が資格情報より前に強制する

検査は `PlanExec` の中で、ADR 0102 決定 1 のプロファイル検査の後、資格情報の取り出しやログインの **前** に行う。
確認が先、ログインが後。確認は安く、先に聞けば拒否された実行がデバイスコードを始めることはない。

- **承認の範囲:** 1 回の承認は、そのセッションとそのプロファイルについて 8 時間か、セッションの終了までの
  短いほうに及ぶ（決めたこと F）。記録は `AgentStateDir/aws-confirm/` の Agent 状態ファイル。名前だけでは
  キーにならない。承認の後にプロファイルのアカウントやロールを編集できるし、名前は新しいプロファイルや
  新しいセッションが再利用できる。そこで承認は次を記録し、実行のたびに照合する:
  - **プロファイルの不変の id**（ブリッジの `id`。名前は表示用）。
  - **セッションの世代**: 名前と、メタにある作成時刻。同じ名前の新しいセッションは承認を引き継がない。
  - **実効の身元**: アカウント、ロール、リージョンと、SSO プロファイルならサインインの id かポータル、連鎖なら
    ロール ARN とソースのプロファイル id。

  どれかが違えば承認はなく、実行はもう一度尋ねる。関門のあるプロファイルを消したり変えたりする設定の同期は
  その承認を捨て、セッションの終了はそのセッションの承認を捨てる。
- **帰属できるセッションがない。** 承認には結び付けるセッションが要る。`AF_SESSION_NAME` がない、または Agent に
  生きたセッションのない名前の、関門付きの実行は、何も出さずにすぐ exit 4 で終わる:「確認には Agent Fleet の
  セッションが要ります。セッションから実行してください」。空のセッションで共有する承認は作らない。
- **尋ね方:** 有効な承認のない実行は、ログインリクエストと同じ仕組みで **確認リクエスト** を出す。セッションと
  プロファイルごとに 1 つで、待ち手、ランダムな id、id だけを運ぶ種類 `aws-use-confirm` の通知を持つ。
  Console はリクエストを Agent から読み（`GET /aws-confirm`）、次を出す:
  - セッションのミラーの最新ターンの下にカード:「`<session>` が `prod-admin`（123456789012 /
    AdministratorAccess）を使おうとしています」。ボタンは **このセッションで許可** と **拒否**。
  - メンバーがそのミラーを見ていないときは、同じものを消えないトーストで。

  ADR 0102 と同じく、プロファイル・アカウント・ロールはリクエストからではなく設定から取る。リクエストは、
  出したときの身元（上の 3 つ）を記録し、カードはその写しを出し、承認はその写しにだけ与える。待っている間に
  設定が変われば、リクエストは捨てられ、待っている実行は新しい身元で出し直す。カードと取り出す対象がずれる
  ことはない。
- **答え方:** Agent の `POST /aws-confirm/{id}/approve|deny`。メンバー自身のワークスペースについて CP が中継し、
  プロファイルとセッションを付けて `aws.use.approve` / `aws.use.deny` として監査する。
- **待ち:** 実行はログインと同じように待つ（ADR 0102 決定 5）。種類ごとの待ち時間で、メンバーの端末なら 10 分。
  許可されれば続ける。拒否されればその場で **exit 4** と「`prod-admin` の使用は Console で拒否されました」で
  終わる。その後 1 分間、同じセッションとプロファイルは新しいリクエストを出さないので、すぐ再試行する
  エージェントがカードを戻すことはない。時間切れなら exit 4 と「Console で確認を待っています」で終わる。
  リクエストは保留のまま残る（15 分）ので、メンバーは後から許可でき、エージェントの次の実行は通る。
- **exit 4** は `cloudexec` の新しいコードで、「メンバーの確認が要り、得られなかった」を意味する。exit 3 の意味は
  変わらない。`workspace/notes/aws.md` で、確認が Console で待っていると伝え、繰り返し再試行しないよう
  エージェントに書く。
- **誰も見ていないとき:** 実行は待ち時間の後に exit 4 で失敗し、何も走らない。それがこの関門の目的である。
  関門のあるプロファイルが要る予約実行も同じく失敗し、メンバーは保留中のカードを見る。

### 6. 関門が止めないもの、迂回を減らすもの

関門が止めるのは、`af-aws-exec` を通した **うっかりや気付かれない使用** である。わざと抜けようとする
エージェントに対する境界ではない。そのエージェントは次のことができる:

1. `AGENT_TOKEN` で `POST /aws-confirm/{id}/approve` を自分で呼ぶ（ヘッダーも付けて）。そのとき CP の監査には
   承認が残らない。Agent はそれをログに残し、承認に中継ヘッダーがなければ、実行のミラー行に「Console を通さずに
   承認」と出す。ヘッダーを偽ればそれも隠せる。
2. `af-aws-exec` を通さず `aws --profile prod-admin` を直接実行する。あるいは `sso_session = af-<sign-in>` と
   管理者ロールで自分の設定を書き、キャッシュ済みの SSO トークンを使う。

2 を減らすもので、この決定に含めるもの:

- **関門のあるプロファイルは `~/.aws/config` の管理ブロックに書かない**（決めたこと E）。素の
  `aws --profile prod-admin` は黙って動かずに失敗する。名前でプロファイルを要するツールは `af-aws-exec` の下で
  動かす。`af-aws-exec` はもともと任意のコマンドを包める。

  今は「ブロックに書いた」が「使える」も意味している。`PlanExec` は `~/.aws` に定義のないプロファイルを拒否し
  （`notDefined`）、行のログインとログアウトは `ExportedIn` を要し、連鎖は自身とソースが書き出されていることを
  要する。単にブロックから外すと関門のあるプロファイルはすべて壊れ、検査なしに隔離した設定へ描画すると、
  メンバー自身の定義を守る仕組みを落とす。そこで同期は、今と **同じ** 規則で 2 つの集合を作る。規則とは、
  メンバー自身のプロファイルや `[sso-session]` によるシャドウ、`[DEFAULT]` との衝突、不正、不完全、名前や
  セッションの衝突、壊れた連鎖である。
  - **使える:** すべての規則を通った。
  - **書いた:** 使えて、関門がない。ソースに関門のある連鎖も書かない。その `source_profile` がファイルにない
    プロファイルを指してしまうからである。

  同期は両方の集合を、ブロックと同じロックの下で保存する（設定のキャッシュの隣の `aws-usable.json`）。今
  「書き出し済みか」を尋ねているところはすべて、代わりに「使えるか」を尋ねる。`PlanExec`（その後、プロファイル、
  その sso-session、連鎖ならソースを実行の隔離した設定に描画する）、行のログイン・ログアウト・状態、期限警告、
  `af-aws-exec --list`（関門のあるプロファイルを「af-aws-exec 経由でのみ使用可」と出す）、連鎖の検査である。
  使えないプロファイルは、関門の有無によらず今の理由で拒否する。
- **`af-aws-exec` は関門のあるプロファイルのロール資格情報をディスクに残さない。** 子プロセスには環境変数で
  渡し、取り出しの後に CLI の資格情報キャッシュの項目を消す。SSM は例外（決定 3）。

メンバーにしかできないこと: **エージェントが一人で抜けられない関門は、エージェントが持っていないトークン
だけ。** 専用のサインインに置き、使い終わったらサインアウトするプロファイルは、毎回デバイスコードの承認を
要する。関門のあるプロファイルを、ほかのプロファイルがサインインしたままにしているサインインに入れると、
それがなくなる（ADR 0125）。関門のあるプロファイルが共有サインインに加わるとき、または共有サインインにいる
間に関門を付けるとき、Console はそのことを伝える（決めたこと G）。

### 7. ADR 0125 との順序

共有サインインは、この ADR の実行行より先には出さず、関門はそれと同時かそれより先に出す:

1. 実行行とミラー表示: Agent、Console、そして CP の読み取りの中継 `GET /api/aws-runs` とその中継の試験
   （`relays_sessions.go` は経路を 1 つずつ登録するので、中継がなければ「最近の実行」は届かない）。
   `/messages` は既に中継されている。
2. 使用前の確認（CP の項目とマイグレーション、Agent、Console）
3. 〜 5. ADR 0125 の 3 つの PR（CP、Agent、Console）

マイグレーション: 関門の列が次の番号（現在の `main` で SQLite `0116`、Postgres `0101`）を取り、ADR 0125 の
サインインのテーブルはその次を取る。どちらも各変更を出すときに `main` と照合し直す。

**契約は PR ごとに。**
- PR 1: `/messages` の `cloudRuns` と `/aws-runs` の行を Agent の `contract_wire_test.go` のファミリーに加え、
  同じ PR で Console の型を結び付ける。
- PR 2: `ssmProfileDTO` の `confirmBeforeUse`（CP の `TestContractFamilies`）。ブリッジには、`confirmBeforeUse` と、
  決定 5 の承認のキーになるプロファイルの不変の `id` を足し、その通信の CP 側と Agent 側の両方を加える。
  `/aws-confirm` のリクエストと応答は Agent のファミリーに入れる。Console の型は同じ PR で結び付ける。
- PR 3 〜 5: ADR 0125 決定 3 のとおり。各 PR は Console の型を同じ PR で結び付けるので、契約の試験が後の PR を
  待つことはない。

### 8. 古い書き手と古い読み手

- **無いことと偽は違う。** `confirmBeforeUse` の無い `PUT /api/ssm/profiles/{id}` は関門をそのままにし、
  `false` は外す。PR 2 より前の Console が関門のあるプロファイルを編集しても、関門は残る。
- **古い Agent と新しい CP。** PR 2 より前の Agent は `confirmBeforeUse` を無視し、プロファイルを関門なしで
  `~/.aws/config` に書いてしまう。そこで Agent はブリッジを引くときに `X-AF-AWS-Profiles: 2` を送る。それの
  ない引き取りに答える CP は、関門のあるプロファイルと、ソースに関門のある連鎖を一覧から外す。その Agent では
  関門が外れるのではなく、使えなくなる。
- **PR 2 をまたぐ CP のロールバック。** 古い CP はこの列を知らない。保存された値には触れないが、配るブリッジには
  `confirmBeforeUse` も `id` もない。だから関門ありの id をその行に対応付けられない。古い Console で改名・削除・
  作り直しされたプロファイルは関門を失ってしまう。そこで規則は、答え全体について決める。新しい CP は
  `X-AF-AWS-Profiles: 2` を付けて答える。**一度そうした答えを受け取った Agent は、版のない答えを決して適用
  しない。** 最後の版付きの一覧（ブロック、使える集合、関門）を保つ。今、CP に届かないときとまったく同じ扱い
  である。古い Control Plane からの設定は適用していない、とログに残し、`af-aws-exec --list` もそう伝える。
  ロールバック中の編集がワークスペースに届くのは上げ直した後になる。どの関門もそのまま残り、関門のない
  ものは現れない。版付きの答えを一度も見ていない Agent には守る関門がないので、今と同じく答えを適用する。
  試験: 版付きの答えの後、関門のあるプロファイルを改名・削除・作り直しした版のない答えがディスクを何も変えず、
  関門付きの実行がなお尋ねることを確かめる。
- **古い Console。** カードを出さない。関門付きの実行は待ち時間の後に exit 4 で終わる。これは安全で、保留中の
  リクエストは新しい Console を読み込めば見える。

## 却下した案

- **実行ごとの通知。** 人を必要とする通知が埋もれる（決定 2）。
- **コマンド行全体、またはその先頭 N 文字を行に入れる。** 引数には秘密が入りうるし、伏せ字にするのは当て推量に
  なる。
- **今すぐプロセスツリーで帰属を決める。** マネージドの種類は、ツールのコマンドを環境にセッション名のない共有
  デーモンの下で動かす（`listenports` に記録がある）。ツリーをたどると本物の実行を取りこぼす。決定 6 の迂回にも
  効かない。決めたこと H として残す。
- **CP が署名した承認を Agent が検証する。** 関門を抜けたいエージェントは、`aws` を直接実行できるので承認を
  偽る必要がない（決定 6）。署名は、開いている扉の隣の扉を守るだけになる。
- **プロファイルではなくサインインに関門を付ける。** 危険はポータルごとではなくロールごと（管理者プロファイル）
  にある。
- **ログインを確認とみなす。** 共有サインインへのログインは全メンバーについて 1 回で済む。この ADR が切り離す
  のはまさにその結び付きである。

## 結果

- セッションを申告した `af-aws-exec` の実行はすべて、そのセッションのミラーに、どの身元で動いたかとともに出る。
- 関門のあるプロファイルは、セッションごとに 1 回（決定 F の範囲内で）メンバーの押下を要し、誰も答えない実行は
  exit 4 で失敗する。
- 関門のあるプロファイルは、ワークスペースで素の `aws --profile` の名前としては使えない（E を採るなら）。
- ガイド（`guide/member/16-cloud-accounts.md` と `.ja.md`）に、決定 6 の限界をメンバーの言葉で書く。関門は
  間違いを捕まえるもので、わざと回り込もうとするエージェントを止めるものではない。

## 決めたこと（2026-10-30、ユーザーが決定）

- **E. 推奨案を採った。** **関門のあるプロファイルを `~/.aws/config` から外す。** 推奨: 外す。素の `aws --profile` で黙って関門を
  迂回できないようにする。代わりに、そのプロファイルは `af-aws-exec` を通してしか使えなくなる。
- **F. 推奨案を採った。** **承認の範囲。** 推奨: セッションとプロファイルごとに、8 時間かセッションの終了まで。代案は 1 時間の
  枠、または実行ごと（`aws` を何度も呼ぶスクリプトではうるさい）。
- **G. 推奨案を採った。** **共有サインインの中の関門付きプロファイル。** 推奨: 許し、フォームとまとめる操作で決定 6 の警告を出す。
  代案は禁止。デバイスコードが本物の関門として残るが、#3014 の主な使い方（同じポータルの管理者プロファイル）を

- **H. 推奨案を採った。** **プロセスツリーによる帰属** を後続にする。推奨: 今はしない（決定 2 と却下した案）。帰属を偽った行が実際に
  出てきたときだけ Issue にする。

## 注記 — ワークスペースの置き場は `.workspace`（2026-10-30）

決定 1 の実装（#3050、PR 1）。`_workspace` はセッション名として有効（`^[A-Za-z0-9_-]{1,40}$`）なので、その名前の
セッションがあると、帰属のない実行の置き場を共有してしまう。そこで置き場は `cloud-runs/.workspace/` とした。
ドットはセッションの名前空間の外にある。決定 1 と 2 の `_workspace` は `.workspace` と読み替える。ほかは変わらない。

決定が触れていなかった細部を 2 つ:
- ワークスペースの置き場も最大 500 行に保つ。7 日の間に大量の実行があっても上限がある。
- セッションの置き場は、ゴミ箱に移したときではなく、ゴミ箱から完全に消したときに消す。復元したセッションは
  行を保つ。

## 注記 — 行は終了ステータスを持たない（2026-10-31）

決定 1 の実装（#3050、PR 1、#3063 のレビュー）。決定 1 は、行を「コマンドの終了時に」終了ステータスと所要時間で
完成させるとしている。終了を見るには、af-aws-exec がコマンド自身になるのではなく、子として動かす必要がある。
レビューで測ったところ、それは呼び出し側のシグナルの効き方を変える:

- プロセスグループに送ったシグナル（エージェントのシェルツール、`timeout`）が、端末のないときにコマンドへ 2 回
  届く。直接の 1 回と、ラッパーが転送する 1 回である。
- SIGTERM を無視するコマンドが、ラッパーへの SIGKILL の後も資格情報を持ったまま生き残る。コマンドを別の
  プロセスグループに移せば 1 つ目は直るが、グループへの SIGKILL がコマンドの子に届かなくなる。

exec の振る舞いをそのまま保つ監督方式はなく、af-aws-exec はデプロイを動かす。そこで引き続きコマンド自身になり、
**行は開始と身元、または実行を拒否した理由を記録する。終了ステータスと所要時間は持たない**。呼び出し側が既に
受け取るラッパーの終了ステータスは変わらない。実際のラッパーを動かし、コマンドがラッパーの PID を持つこと、
グループへの SIGINT 1 回が 1 回だけ届くこと、その PID への SIGKILL でコマンドが終わることを試験で確かめる。

## 注記 — 待っている対象が変わったら、待っている実行は終わる（2026-10-31）

決定 5 の実装（#3050、PR 2、#3072 のレビュー）。決定 5 は、設定の変更で保留中のリクエストが捨てられ、「待っている
実行は新しい身元で出し直す」としている。実行にはそれを安全に行えない。実行の計画（どのプロファイルを、どのソース
経由で、どの設定から）は開始時に読んだ設定から立てたもので、古い計画のまま新しい身元について尋ねれば、カードと
取り出す対象がずれうる。そこで **待っている間にセッションが終わった実行、またはプロファイルの設定が変わった実行は、
どちらかを示して exit 4 で終わる**。エージェントはコマンドを実行し直し、新しく計画して尋ねる。答えのないまま期限を
迎えたリクエストは、待ち続けている実行が引き続き出し直す。

関連する細部を 3 つ:
- リクエストと承認は、そのセッションの世代が生きている間だけ有効。Agent は終わったセッションのリクエストを一覧に
  出さず、その回答を受け付けず、その承認を捨てる。
- 拒否は、名指しした各プロファイルを 1 分間止める。次の実行がどの組み合わせで尋ねても同じ。
- 待った後、資格情報を取り出す直前に、af-aws-exec はメンバー自身のファイルがプロファイル、その sso-session、
  そのソースを取っていないかをもう一度確かめる。

## 注記 — SSM ペインの 1 行と行は「設定どおり」と言う（2026-10-31）

決定 3 の実装（#3064）。ペインは資格情報を自分のシェルの中で解決する。Agent が知っているのは、設定がそのセッションに
挙げているもの（プロファイル、アカウント、ロール、リージョン、サインイン、対象）であって、STS が確かめたものではなく、
`aws ssm start-session` がどう終わったかも見えない。そこで:

- **1 行**は、`exec aws ssm start-session` の直前（ログインの手順より後）に出す:
  `[Agent Fleet] AWS profile <p> (identity from Settings, not confirmed) · account · role · region · via <source> ·
  sign-in <name> · target <t>`。空の部分は省く。チェーンではアカウントとロールが対象ロールのもので、ソースは「via」。
  サインイン（ADR 0125）に入っているプロファイルでは、その名前を出す。
- **行**は同じ実行行で、`identityFromSettings: true` と `signIn`・`target`（どちらも新設の省略可）を持つ。プログラムは
  `aws`、サービスは `ssm`、操作は `start-session`。開始した行と同じく終了ステータスも終了時刻も持たない。ペインの
  プログラムを組み立てるとき、つまりセッションの起動・再起動のたびに書く。行があること自体は start-session が実行された証拠にはならない。ログインが終わらなければ終わりなしのまま残る。Console は行に印（「identity from Settings,
  not confirmed」に当たる表示）を描くので、`PlanExec` が解決した身元を持つ `af-aws-exec` の実行と取り違えない。
  古い Console は新しいフィールドを無視し、普通の実行として表示する。
- **中身**は、許可リストを通った身元と対象だけ。対象は表示できる文字に直し（制御文字は `?`、最大 128 文字）、シェルには
  引用した `printf '%s\n'` の引数 1 つとしてだけ渡すので、空白・引用符・`$` はそのまま出る。
- **ゲートは変えない。** 決定 3 のとおり SSM はゲートの外のままで、ここでは確認を求めない。
