# 0126. `af-aws-exec` の実行をセッションのミラーに出し、プロファイルごとに使用前の確認を求められるようにする

- Issue: #3050
- 関連: [0125](0125-shared-sso-sign-in.ja.md)（サインインの共有。この ADR はそれより先に入る）/
  [0102](0102-aws-login-through-the-console.ja.md)（Console からのログイン。リクエスト、待ち、exit 3、

## 背景

設定のプロファイルにサインインした後は、`af-aws-exec --profile <p> -- <command>` を実行しても、トランス
クリプトに残るツール呼び出しのコマンド行以外に痕跡が残らない。その行は見落としやすく、スクリプトの中で
呼べば完全に隠れる。今はプロファイルごとのログインが承認の役も果たしている。各プロファイルの初回使用には
メンバーがデバイスコードを承認する必要があり、エージェントはそれを一人ではできない。ADR 0125 は複数の
プロファイルに 1 つのトークンを共有させるので、1 回の承認がサインイン内の全プロファイルに及ぶ。本番の
管理者プロファイルも含めてである。

あるもの・ないもの（コードを読んで確かめた）:

- **セッションのミラーに表示専用の行を差し込む仕組みはない。** ミラーは CLI のトランスクリプトと、Agent が
  `GET /sessions/{name}/messages` で返すパネルを表示する。パネルは保留中のピアメッセージ
  （`AgentStateDir/pending-peer/<session>/` の置き場、`PendingPeersNotice`）、破棄、引き継ぎ提案である。
  セッション宛ての通知は通知センターにしか届かず、CP はそのセッションが存在するかを確かめない。
- **帰属は `AF_SESSION_NAME` を信用している。** プロセスをセッションに結び付ける経路はどれも環境変数から
  読む（`listenports.sessionOf`、`aws_exec.go`、`gcloud_exec.go`）。エージェントは自分の環境を設定できるので、
  別のセッション名を名乗ることも、名乗らないこともできる。
- **Agent の経路はすべて `AGENT_TOKEN` で呼べる。** エージェントのシェルはそのトークンを持っている。CP は
  中継したものに `X-AF-Relay: cp` を付けるが、エージェントも同じヘッダーを送れる。エージェントが書けない
  記録は CP の監査だけ。
- **エージェントはメンバーのユーザーとして動く。** `~/.aws/config`、SSO トークンのキャッシュ、ロール資格情報の
  キャッシュを読めるし、`af-aws-exec` を通さずに `aws` を実行できる。

## 決定

### 1. 実行ごとに、そのセッションの実行記録に 1 行書く

`af-aws-exec` はコマンドの開始前に **実行行** を書き、コマンドの終了時に完成させる:

- **項目:** 時刻、プロファイル、アカウント、ロール、リージョン、サインイン（ADR 0125）、連鎖ならソースの
  プロファイル。プログラムのベース名も、`[A-Za-z0-9._-]{1,32}` に切り詰めて記録する。`aws <service>
  <operation>` なら、両方が `^[a-z0-9-]{1,64}$` に合うときだけサービスと操作を記録する。コマンドの終了時に
  終了ステータスと所要時間を足す。アカウント・ロール・リージョンはコマンド行からではなく、`PlanExec` がその
  実行について解決したものから取る。
- コマンド行の残り、引数、環境変数、コマンドの出力は **決して** 記録しない。引数には秘密が入りうる。引数と
  環境変数に番兵を仕込んだコマンドを実行し、その番兵が実行記録のファイル、`/messages` の応答、通知、Agent の
  ログ、CP へのリクエストのどれにも届かないことをテストで確かめる。
- 資格情報の前に拒否された実行（exit 1・2・3、または下の 4）も、理由コードを付けて、コマンドの終了ステータス
  なしで 1 行書く。
- **置き場:** `AgentStateDir/cloud-runs/<session>/`。1 回の実行につき 1 ファイルで、ログインリクエストと同じく
  CLI のプロセス自身が書く（ADR 0102 決定 1）。ディレクトリ名は特定のクラウドに依らないので、後で
  `af-gcloud-exec` も書ける（この ADR の範囲外）。1 セッションにつき最大 200 行を保ち、古いものから消す。
  ディレクトリはセッションとともに消える。
- **どのセッションか:** `AF_SESSION_NAME` が指し、Agent が知っているセッション。名前がない、または Agent の
  知らない名前の実行は `cloud-runs/_workspace/` に入れ、7 日間保つ。

### 2. ミラーには行を、設定には全セッションの行を出す

- `GET /sessions/{name}/messages` に、そのセッションの行 `cloudRuns` を足す。ミラーは各行を、ターンの間に時刻順
  で 1 行として描く: 「AWS · `prod-admin` · 123456789012 / AdministratorAccess · ap-northeast-1 ·
  `aws s3 ls` · exit 0 · 3 秒」。どの種類のセッションでも同じ場所に出し、トランスクリプトに時刻のない種類では
  最後のターンの後に出す。
- 設定 > AWS プロファイル/SSM に「最近の実行」の一覧（`GET /aws-runs`。全セッションと `_workspace` の直近 100 件）
  を置く。セッション名を消された、または偽られた実行も、どこかには見える。
- 実行ごとの通知もチャットブリッジへのメッセージも出さない。実行は人を必要とする出来事ではなく、毎回通知すると
  人を必要とする通知が埋もれる。

**帰属が意味すること。** セッションは、実行が **申告した** もの。正直なエージェントや、それが走らせる
スクリプトは、自分のミラーに出る。`AF_SESSION_NAME` を変えたエージェントは、行を別のセッションのミラーや
`_workspace` に移せるが、「最近の実行」から消すことはできない。`af-aws-exec` を使わないエージェントは行を
まったく残さない。行は見える化であって、監査ではない。実行のプロセスツリーをセッションと照合すれば（未決事項 H）
帰属の偽りは止まるが、迂回は止まらない。

### 3. SSM セッション

SSM セッションのミラーはその端末である。`aws ssm start-session` の前に、ペインは 1 行を表示する:
「`[Agent Fleet] AWS プロファイル <p> · アカウント · ロール · リージョン · ターゲット <instance>`」。同じ実行行を
SSM セッション自身の実行記録にも書く。開始は CP が既に監査している（`ssm.start_session`）。

### 4. 「使用前に確認」はプロファイルごとの設定項目

- `ssm_profile` に `confirm_use INTEGER NOT NULL DEFAULT 0` を足す。`ssmProfileDTO` とブリッジの
  `awsProfileWire` には `confirmBeforeUse`（偽なら省く）を足す。どの種類のプロファイルでも設定できる。
- 実行に **確認が要る** のは、プロファイルにこの項目が立っているとき、連鎖ならソースに立っているとき。連鎖は
  ソースのロールで動く。
- これはプロファイルの項目で、サインイン（ADR 0125）の項目ではない。`prod-admin` を確認しても、同じサインインの
  ほかのものは確認されないし、サインインにログインしても何も確認されない。
- メンバー自身の `~/.aws` のプロファイルにはこの項目がない。情報源は設定の一覧だけ。

### 5. `af-aws-exec` が資格情報より前に強制する

検査は `PlanExec` の中で、ADR 0102 決定 1 のプロファイル検査の後、資格情報の取り出しやログインの **前** に行う。
確認が先、ログインが後。確認は安く、先に聞けば拒否された実行がデバイスコードを始めることはない。

- **承認の範囲:** 1 回の承認は、そのセッションとそのプロファイルについて 8 時間か、セッションの終了までの
  短いほうに及ぶ（未決事項 F）。記録は `AgentStateDir/aws-confirm/` の Agent 状態ファイルで、セッションと
  プロファイルをキーにする。
- **尋ね方:** 有効な承認のない実行は、ログインリクエストと同じ仕組みで **確認リクエスト** を出す。セッションと
  プロファイルごとに 1 つで、待ち手、ランダムな id、id だけを運ぶ種類 `aws-use-confirm` の通知を持つ。
  Console はリクエストを Agent から読み（`GET /aws-confirm`）、次を出す:
  - セッションのミラーの最新ターンの下にカード:「`<session>` が `prod-admin`（123456789012 /
    AdministratorAccess）を使おうとしています」。ボタンは **このセッションで許可** と **拒否**。
  - メンバーがそのミラーを見ていないときは、同じものを消えないトーストで。

  ADR 0102 と同じく、プロファイル・アカウント・ロールはリクエストからではなく設定から取る。
- **答え方:** Agent の `POST /aws-confirm/{id}/approve|deny`。メンバー自身のワークスペースについて CP が中継し、
  プロファイルとセッションを付けて `aws.use.approve` / `aws.use.deny` として監査する。
- **待ち:** 実行はログインと同じように待つ（ADR 0102 決定 5）。種類ごとの待ち時間で、メンバーの端末なら 10 分。
  許可されれば続ける。拒否されればその場で **exit 4** と「`prod-admin` の使用は Console で拒否されました」で
  終わる。その後 1 分間、同じセッションとプロファイルは新しいリクエストを出さないので、すぐ再試行する
  エージェントがカードを戻すことはない。時間切れなら exit 4 と「Console で確認を待っています」で終わる。
  リクエストは保留のまま残る（15 分）ので、メンバーは後から許可でき、エージェントの次の実行は通る。
- **exit 4** は `cloudexec` の新しいコードで、「メンバーの確認が要り、得られなかった」を意味する。exit 3 の意味は
  変わらない。`workspace/notes/aws.md` で、確認が Console で待っていると伝え、繰り返し再試行しないよう
  エージェントに書く。
- **誰も見ていないとき:** 実行は待ち時間の後に exit 4 で失敗し、何も走らない。それがこの関門の目的である。
  関門のあるプロファイルが要る予約実行も同じく失敗し、メンバーは保留中のカードを見る。

### 6. 関門が止めないもの、迂回を減らすもの

関門が止めるのは、`af-aws-exec` を通した **うっかりや気付かれない使用** である。わざと抜けようとする
エージェントに対する境界ではない。そのエージェントは次のことができる:

1. `AGENT_TOKEN` で `POST /aws-confirm/{id}/approve` を自分で呼ぶ（ヘッダーも付けて）。そのとき CP の監査には
   承認が残らない。Agent はそれをログに残し、承認に中継ヘッダーがなければ、実行のミラー行に「Console を通さずに
   承認」と出す。ヘッダーを偽ればそれも隠せる。
2. `af-aws-exec` を通さず `aws --profile prod-admin` を直接実行する。あるいは `sso_session = af-<sign-in>` と
   管理者ロールで自分の設定を書き、キャッシュ済みの SSO トークンを使う。

2 を減らすもので、この決定に含めるもの:

- **関門のあるプロファイルは `~/.aws/config` の管理ブロックに書かない**（未決事項 E）。素の
  `aws --profile prod-admin` は黙って動かずに失敗し、`af-aws-exec` はその実行の隔離した設定にだけ描画する。
  名前でプロファイルを要するツールは `af-aws-exec` の下で動かす。`af-aws-exec` はもともと任意のコマンドを包める。
- **`af-aws-exec` は関門のあるプロファイルのロール資格情報をディスクに残さない。** 子プロセスには環境変数で
  渡し、取り出しの後に CLI の資格情報キャッシュの項目を消す。

メンバーにしかできないこと: **エージェントが一人で抜けられない関門は、エージェントが持っていないトークン
だけ。** 専用のサインインに置き、使い終わったらサインアウトするプロファイルは、毎回デバイスコードの承認を
要する。関門のあるプロファイルを、ほかのプロファイルがサインインしたままにしているサインインに入れると、
それがなくなる（ADR 0125）。関門のあるプロファイルが共有サインインに加わるとき、または共有サインインにいる
間に関門を付けるとき、Console はそのことを伝える（未決事項 G）。

### 7. ADR 0125 との順序

共有サインインは、この ADR の実行行より先には出さず、関門はそれと同時かそれより先に出す:

1. 実行行とミラー表示（Agent と Console。CP の変更なし）
2. 使用前の確認（CP の項目とマイグレーション、Agent、Console）
3. 〜 5. ADR 0125 の 3 つの PR（CP、Agent、Console）

マイグレーション: 関門の列が次の番号（現在の `main` で SQLite `0116`、Postgres `0101`）を取り、ADR 0125 の
サインインのテーブルはその次を取る。どちらも各変更を出すときに `main` と照合し直す。

## 却下した案

- **実行ごとの通知。** 人を必要とする通知が埋もれる（決定 2）。
- **コマンド行全体、またはその先頭 N 文字を行に入れる。** 引数には秘密が入りうるし、伏せ字にするのは当て推量に
  なる。
- **今すぐプロセスツリーで帰属を決める。** マネージドの種類は、ツールのコマンドを環境にセッション名のない共有
  デーモンの下で動かす（`listenports` に記録がある）。ツリーをたどると本物の実行を取りこぼす。決定 6 の迂回にも
  効かない。未決事項 H として残す。
- **CP が署名した承認を Agent が検証する。** 関門を抜けたいエージェントは、`aws` を直接実行できるので承認を
  偽る必要がない（決定 6）。署名は、開いている扉の隣の扉を守るだけになる。
- **プロファイルではなくサインインに関門を付ける。** 危険はポータルごとではなくロールごと（管理者プロファイル）
  にある。
- **ログインを確認とみなす。** 共有サインインへのログインは全メンバーについて 1 回で済む。この ADR が切り離す
  のはまさにその結び付きである。

## 結果

- セッションを申告した `af-aws-exec` の実行はすべて、そのセッションのミラーに、どの身元で動いたかとともに出る。
- 関門のあるプロファイルは、セッションごとに 1 回（決定 F の範囲内で）メンバーの押下を要し、誰も答えない実行は
  exit 4 で失敗する。
- 関門のあるプロファイルは、ワークスペースで素の `aws --profile` の名前としては使えない（E を採るなら）。
- ガイド（`guide/member/16-cloud-accounts.md` と `.ja.md`）に、決定 6 の限界をメンバーの言葉で書く。関門は
  間違いを捕まえるもので、わざと回り込もうとするエージェントを止めるものではない。

## 未決事項

- **E. 関門のあるプロファイルを `~/.aws/config` から外す。** 推奨: 外す。素の `aws --profile` で黙って関門を
  迂回できないようにする。代わりに、そのプロファイルは `af-aws-exec` を通してしか使えなくなる。
- **F. 承認の範囲。** 推奨: セッションとプロファイルごとに、8 時間かセッションの終了まで。代案は 1 時間の
  枠、または実行ごと（`aws` を何度も呼ぶスクリプトではうるさい）。
- **G. 共有サインインの中の関門付きプロファイル。** 推奨: 許し、フォームとまとめる操作で決定 6 の警告を出す。
  代案は禁止。デバイスコードが本物の関門として残るが、#3014 の主な使い方（同じポータルの管理者プロファイル）を
  塞いでしまう。
- **H. プロセスツリーによる帰属** を後続にする。推奨: 今はしない（決定 2 と却下した案）。帰属を偽った行が実際に
  出てきたときだけ Issue にする。
