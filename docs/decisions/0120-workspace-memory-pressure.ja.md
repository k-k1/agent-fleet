## 背景

割り当てられたメモリを超える数のエージェントセッションを動かした Workspace は、きれいには失敗しない。
`ecs-ec2`（8 GiB スロット、2026-10-21）では、あるメンバーのセッション群がコンテナを上限まで押し上げた。
ファイルページはまだ回収できたため、Linux は何も OOM キルしなかった。ボックスは約 20 分間リクレイムの
スラッシングに入った。EBS の読み取り操作は 5 分あたり約 100 から約 19 万へ、CPU は 35〜95% に張り付き、
Agent は応答をやめ（Control Plane からのプロキシ呼び出しがすべてタイムアウト）、最後にはスロットの ECS
エージェントと SSM エージェントが沈黙した。同じ日に 2 人目のメンバーが同じ型に当たった。Agent のログが 40 分
無音だったのに、ECS はタスクを HEALTHY と報告し続けた。

すでにツリーにあるものと、それがしないこと：

- **上限と予約**（`workspaceMemCapMiB`、`runtime_ecs_ec2.go`、#2451）は 8 GiB スロットのうち 2 GiB を
  コンテナから取り置く。**`system.slice` の `MemoryMin`**（`40-ec2-pool.yaml`、#2452）はボックスの
  デーモンのページをリクレイムから守る。両方でスラッシングは Workspace 自身の cgroup に閉じ込められる。
  だが止まりはしない。その cgroup の中では、Agent を含むすべてが同じページを取り合う。
- **アイドル停止**（`control-plane/reaper.go`）は*アイドルな* claude セッションを停止し、のちにアイドルな
  Workspace を止める。メモリは入力にない。忙しいボックスはアイドルではない。
- **`resources.Read`**（`workspace/agent/internal/resources`）はすでに `memory.current`、`memory.max`、
  `memory.events` の `oom_kill` を 4 秒の Stats ティックで報告している（読めない軸は 0 にせず省く）。
  圧迫は報告しない。また `memory.current` は単独では誤った指標である。ページキャッシュを数えるので、
  大きなリポジトリを読んだ健全なボックスも上限の近くに見える。
- **Agent はすでにセッションを再開可能な形で止められる**：`HandleHaltSession` は tmux セッションを落とす
  （Managed ならランタイムのハンドルを手放す）が、行は残し、停止済みの印を付ける。

足りないのは、「キャッシュが満杯」と「ボックスがスラッシングしている」を分ける信号、それにコンテナの内側から
働きかける仕組み、そしてメンバーに伝える手段である。本書はそれらを決める。決めるのは設計だけである。

## 決定

### 1. 信号はコンテナ cgroup の PSI を Agent 自身が読む。使用量の数字は裏付けにとどめる

コンテナ自身の cgroup ディレクトリ（Agent がすでに尊重している `AF_CGROUP_DIR`）から、5 秒ごとに 1 サンプル
読む：

| ファイル | 取るもの | 用途 |
|---|---|---|
| `memory.pressure` | `some` と `full` の `avg10`、`avg60`、マイクロ秒の `total` カウンタ | **トリガー** |
| `memory.stat` | `anon`、`file`、`shmem`、`inactive_file`、`workingset_refault_file` | ワーキングセットと、第二のスラッシング信号としてのリフォールト率 |
| `memory.current`、`memory.max` | ワーキングセット = `current − inactive_file` を `max` に対して | 裏付けと、メンバー向けの「M のうち N」 |
| `memory.events` | `high`、`max`、`oom`、`oom_kill` の差分 | 証拠（`max` イベントは、割り当てが上限に当たってリクレイムを強いられた印） |

PSI をトリガーにするのは、害そのもの（タスクがメモリ待ちで止まった時間の割合）を測る唯一の数字だからで、
無害なことも多い原因を測るのではない。`some` は「少なくとも 1 タスクが止まった」、`full` は「止まっていない
タスクがすべて止まった」で、後者が障害の特徴である。Agent はカウンタを自分でサンプリングし、PSI トリガー
（`memory.pressure` への書き込み）では待たない。書き込みにはファイルの所有者である必要があるが、コンテナ内で
そのファイルは root のもので、Agent は uid 1000 だからである。

各ランタイムの状況。コードと文書化された既定からの読みであり、**印のあるものを除き各ランタイムでは測って
いない**：

| ランタイム | cgroup v2 と、コンテナ自身のものだと確認できた `memory.pressure` があるか（下記参照） | Agent の動作 |
|---|---|---|
| `ecs-ec2` | あるはず（AL2023 は既定で cgroup v2。コンテナは自分の cgroup 名前空間を持つ）。**実スロットで測る**（決定 8） | 確認できた場合に全段階 |
| `ecs`（Fargate） | **不明。** プラットフォームのカーネルと PSI の公開有無はこちらに文書がない | 計測する。確認できたときだけ段階を動かす |
| `docker` | PSI が有効な cgroup v2 ホストなら。フリートホスト上の開発用 Workspace で、2026-10-22 に uid 1000 のまま `memory.pressure`、`memory.events`、`memory.max` が読めた | 全段階 |
| `kubernetes` | ノード次第（cgroup v2 で `psi` が無効化されていないこと）。メモリ上限はコンテナの resources に設定される（`runtime_kubernetes.go`）ので、それを担うのはコンテナ自身の cgroup | 確認できた場合に全段階 |
| `native` | Agent は誰かの手元のマシンで動く。`/sys/fs/cgroup` が読めても自分専用の cgroup とは限らず、他の OS には cgroup がない | **警告のみ**（段階 1）。拒否も停止もしない |

PSI が読めない、または確認できない場合、および cgroup が v1 の場合（Agent はすでに v1 の使用量ファイルへフォールバックするが、
圧迫の値はない）：

- **確認できたとは、読めたではなく解決できたこと。** 読めるファイルが、このコンテナについて述べている保証は
  ない。docker デーモンの cgroup 名前空間の設定や、（`native` では）マシンが Agent 専用の cgroup を与えて
  いるかによる。Agent は起動時に自分の cgroup を `/proc/self/cgroup` から解決し、`mountinfo`（cgroup2 の
  マウントのルートと読んでいるパス）と照合する。読んでいるディレクトリがその cgroup（プライベート cgroup
  名前空間ならその名前空間のルート）であり、かつ `memory.max` がランタイムに設定させた上限と一致する場合に
  限って受け入れる。確認できないものは下記の「PSI なし」として扱い、計測と警告だけを行う。
- Agent は `mem_pressure` を **0 ではなく不在**として報告する。ほかの Stats 軸と同じ規則。
- 動かしてよいのは**段階 1（警告）だけ**で、ワーキングセット比とメジャーフォールト率から出し、そう明示する
  （「この環境では圧迫を測れない。使用量からの推定である」）。
- **PSI なしに段階 2・3 は動かさない。** 使用量の比率だけで仕事を断ったりセッションを止めたりすれば、単に
  キャッシュしているだけのボックスを罰することになる。その誤検知が、メンバーにこの機能を切らせる原因になる。
  迷ったら何もしない。
- `/proc/pressure/memory`（ボックス全体のファイル）はコンテナには**使わない**。名前空間化されていないので、
  共有 docker ホストでは他のメンバーの圧迫である。読むのはボックスがメンバー自身のものである `native`
  だけで、そこでも警告段階にしか使わない。

採らなかった案：

- **Agent の外にある PSI 応答役。** 置き場所は 3 つあり、性質が違う：
  1. *コンテナ内の Agent（本書）。* どのランタイムでも持ち運べ、セッションを知っていて、予告も保留も再開も
     できる。弱点は障害が示したとおり、スラッシングする cgroup を共有していること。
  2. *`ecs-ec2` のホスト上の `systemd-oomd` など root のデーモン。* その弱点を逃れる、最も有力な代替案。
     今は採らない。コンテナ cgroup 全体に作用し（止められる単位は全セッション一度にで、犠牲の選択も予告
     つきの猶予も再開の意味論もない）、1 つのランタイムにしかなく、圧迫の上限値にはどのみちフェーズ 0 の
     数字が要るから。Agent の*保護役*としての役割は未決事項 3 に残す。
  3. *セッションごとに委譲したサブ cgroup、それぞれに `memory.high` と kill。* 帰属が正確になり、
     `memory.high` がセッション単位で意味を持つ。起動時の root セットアップがすべてのランタイムで必要で、
     「内部プロセス禁止」規則（子を持つ cgroup は自身にプロセスを置けない。Agent と tmux の置き方が変わる）が
     あり、shared-daemon のセッションのスレッドをデーモンから分けられない。しきい値がまだ分からない設計に
     は大きすぎる変更。
  `earlyoom` はホストの `/proc/meminfo` を読むが、コンテナ内ではそれはボックスのもので cgroup のものではない。
- **カーネルの OOM キラー（`memory.oom.group`）。** これこそ避けたい失敗である。障害では発動せず、発動
  しても `oom_score` で選び、メンバーが再開できるかは考えない。
- **Control Plane が `mem_used` から判断する。** CP が見るのは Stats のティックだけで、圧迫は見えず、障害では
  タイムアウトしていたのがまさに CP のプロキシ呼び出しだった。CP には事実を渡す（決定 5）が、判断できない
  数字からセッションを止める権限は渡さない。
- **スワップや zram で崖を和らげる。** root が要り、先送りにしかならない。

### 2. 段階的な対応：警告、拒否、停止。それぞれに持続窓と確認と、抜けるときのヒステリシスを置く

しきい値は `some avg10` と `full avg10`（止まっていた時間の割合、%）に置き、`avg60` を緩衝に使う。値は
すべて**暫定**（決定 8 が測定値に置き換える）で、内部定数でありメンバー設定ではない。

| 段階 | 入る条件（持続） | 抜ける条件（持続） | 効果 |
|---|---|---|---|
| 0 正常 | — | — | — |
| 1 警告 | `some avg10` ≥ 10 が 60 秒、またはワーキングセットが `max` の 85% 以上で 120 秒 | `some avg10` < 5 かつワーキングセット < 80% が 120 秒 | 数字付きの Console 通知 |
| 2 拒否 | `some avg10` ≥ 25 が 30 秒、または `full avg10` ≥ 5 が 30 秒 | `some avg10` < 12 かつ `full avg10` < 2 が 120 秒 | 新規セッションと再開を明確なエラーで断る |
| 3 停止 | `full avg10` ≥ 15 が 60 秒 **かつ** `full` の `avg60` ≥ 8 **かつ** ワーキングセット ≥ 90% **かつ** 匿名メモリと共有メモリの合計がワーキングセットの 60% 以上 | 段階 2 の抜ける条件 | 予告つきの猶予（後述）の後、選んだセッションを停止 |

短いビルドのスパイクをスラッシングと取り違えない方法：

- **「W 秒持続」はタイムスタンプで定義する。** 直近 W 秒のすべてのサンプルで条件が成り立ち、かつ連続する
  サンプルの間隔が 10 秒以下（間隔の 2 倍）であること。サンプルの欠落や遅延は、段階を上げる窓を**リセット**し、
  保留中の停止を**延期**する。圧迫とも緩和とも数えない。偽の時計でテストできる。
- **コンパイラの 20 秒のバーストは `avg10` を動かすが `avg60` はほとんど動かさない。** 段階 3 は両方を要る。
- **段階 3 はワーキングセットの大半が匿名ページか共有メモリページであることを要る**（`anon + shmem` が
  60% 以上）。これは唯一の破壊的な動作に対する保守的な適用範囲であり、ファイル主体の圧迫は無害だという主張
  ではない。収まらなくなったアクティブなファイルのワーキングセットも、匿名の割合が低いまま本当にスラッシング
  しうる（`full` の持続、`workingset_refault_file` の上昇）。その場合、セッションを止めても効かないかもしれ
  ない。その形は段階 2 にとどまり、「ファイル主体・未対応」として記録し、フェーズ 0 が測るべきものとする
  （決定 8）。`shmem` はスワップがないと落とせないので、匿名メモリと一緒に数える。
- **予告つきの猶予、そのあとで新たに判断する。** 段階 3 に入ると、Agent は通知（「メモリが空かなければ 30 秒後に
  セッション X を停止する」）を出して 30 秒待つ。停止を実行するのは、猶予の**後**に取った 10 秒以内のサンプルが
  **段階 3 の入る条件をすべて**（60 秒窓ではなく瞬時値で）満たし、選んだ犠牲が同じセッションで、その見込み
  回収量（決定 3）が 0 より大きいときだけ。そうでなければ何も止めず、段階は 2 のままになる。段階 2 の
  抜けるときのヒステリシス（120 秒）が決めるのは*拒否*をいつ解くかだけで、halt を取り消す条件ではない。古い
  サンプルが halt を許可することはない。サンプラーが遅れているなら、拒否は維持したまま停止を待つ。
- **停止は一度に 1 つ、クールダウン付き。** 停止後は数字が落ち着くまで 120 秒待ってから次を選べる。測れる
  ほど空かなかった停止はそう記録し、同じセッションには再試行しない。
- **拒否は安く元に戻せるが、停止はそうではない。** だから段階 2 は段階 3 よりずっと早く入り、長い窓で抜ける。
  段階が行ったり来たりするのはバグである。Agent は窓より頻繁には段階を変えず、遷移は数字付きで 1 回だけ
  記録する。

拒否（段階 2）は、Agent 自身のセッション作成・再開・再作成のハンドラが行う。エラーコード `memory_pressure` に
現在の数字と大きな消費者を添えて返し、Console が翻訳済みの文にする。**起こす操作も開始に数える**：停止済みの
セッションを再開させるスケジュール実行、ピアのメッセージ、MCP 呼び出しも同じように断り、保留のままにする
（Agent はすでに次の開始まで prompt を保留する）。そうしないと、Agent がいま止めたセッションが、次のタイマーで
同じ圧迫の中に復活してしまう。

### 3. 対象になるもの、犠牲の選び方、決して触らないもの

止める単位は**セッション**で、止め方は既存の halt（`HandleHaltSession`）である。行は残り、セッションは「停止」と
表示され、アイドル停止されたものと同じ経路で再開できる。再開できない停止は提供しない。halt はセッションの
メタに `stopped_reason: memory_pressure` を記録し、Console が理由を言えるようにする。

**セッションを安く測る。** 強制の経路では、段階 0 のあいだはプロセス単位の計測をしない。段階 1 以降（および
フェーズ 0 自身の低頻度サンプラー、決定 8）で、Agent はサンプルごとに `/proc` を 1 回走査し（`procx` のスナップショットがすでに 750 ms に 1 回までで行っている）、各プロセスの
`/proc/<pid>/status` から `RssAnon` と `RssShmem` を読む。RSS は使わない。共有ページとファイルページを二重に
数えるが、それこそカーネルが捨てられるものだからである。選ぶ瞬間には、上位の数件を
`/proc/<pid>/smaps_rollup` の `Pss_Anon` + `Pss_Shmem` で測り直す。これは共有ページを利用者の間で公平に割り、費用は
サンプルごとではなくプロセスごとにミリ秒である。

**プロセスをセッションに帰属させる。** まず、セッションの tmux ペインの下のプロセスツリーで（`procx` はすでに
親と session id を持つ）。デーモン化した開発サーバーや親が付け替わったビルドはそのツリーを出るので、次に、
セッションのプロセスが環境変数に持つ `AF_SESSION_NAME` で（同じ uid で読める。毎サンプルではなく pid と開始
時刻ごとにキャッシュする）。帰属できないものはコマンド名つきで「その他」として報告し、セッションには負わせ
ない。

| プロセス | 対象か |
|---|---|
| エージェントセッション（`claude`、`codex`、`opencode` …）と、そこから起動したすべて（ビルド、テスト、開発サーバー、ヘッドレス Chromium） | **対象。** セッションの占有量として数えるが、見込み回収量に入れるのは halt が**確実に**解放する部分だけ（「halt が解放するもの」参照） |
| `shell` セッション | **シェルの占有量が最大のエージェントセッションの 2 倍を超える場合のみ。** halt はシェルの実行中ジョブを落とし、それは永続しない（reaper のアイドル段が shell を飛ばすのと同じ理由）。同点の決め手ではなく、明らかな原因のときに選ぶ |
| プロセスモデル別のセッション（`agents/driver.go` の `ProcessModel`） | `tui`：上記のとおり tmux ペインのツリー。`per-session-child`（copilot、cursor、kiro、muse）：子プロセスを**本体ごと**数え、`DropHandle` がそれを止める。`shared-daemon`（codex、opencode）：セッションに帰属できるプロセスだけで順位を付け、デーモンの基底分は除く。`DropHandle`（codex はスレッドの購読解除も行う）がデーモンのメモリを返すかは**測っていない**。`in-process`（lcpp）：メモリは Agent の内側にあり帰属できないので、**メモリを理由に選ぶことはない**（安全側）。モデルごとの回収確認をフェーズ 0/3 で行う |
| 孤立したヘッドレス Chromium（セッションはもうない） | **どのセッションよりも先に**、段階 3 の前処理として。メンバーに何の負担もない |
| `af-db` サーバー | **自動では決して止めない。** 止めれば中断するデータを持つ。通知で消費者として挙げ、提案する操作はメンバー自身の `af-db stop` |
| workspace Agent、tmux サーバー、Agent が Console のために動かすもの（プレビューやポートのプロキシ、ターミナルブリッジ） | **決して触らない。** どれを止めても全セッションが一度に終わる |

**halt が解放するもの。** `HandleHaltSession` が確実に取り除くのは tmux セッションのツリーだけである。`setsid`
したりデーモン化したり disown した子は `kill-session` を生き延び、`AF_SESSION_NAME` でセッションに帰属
させたが親が付け替わったプロセスも同じである（`procx.ToolProcessIn` があるのは、ツールを独自のセッションで
起動する CLI があるため）。だから見込み回収量は確実な部分の占有量であり、メモリ圧迫の halt は残りについて
**追加の契約**を持つ：halt の後、Agent はセッションに帰属させたプロセスにシグナルを送る。送るのは身元を
再確認できたものだけ（同じ uid、同じ pid **と開始時刻**、セッションの印がまだある、下記の保護対象でない）で、
`SIGTERM`、短い待ちの後に `SIGKILL`、そして再計測して消えたことを確認する。身元を再確認できないプロセス
には触れず、「まだ動いている。確信を持って帰属できなかった」と報告する。回収量を「解放した」と記録するのは
再計測の結果からだけ。`procx.Info` には開始時刻がまだないので、身元確認のためにそれを足す必要がある。

**不明は 0 ではない。** プロセスごとの読み取り（`status`、`smaps_rollup`、`environ`）はどれも失敗しうる。
`smaps_rollup` と `environ` は ptrace の読み取りチェックで守られており、別 uid のプロセスや、ダンプ不可・
サンドボックス化されたプロセスは、同 uid なら通常読めるにしても、読めないことがある。そのため各計測は
既知・部分・不明を持つ。部分的な合計を完全な占有量として比べることはせず、不明なプロセスを含むセッションを
含まないものより下位に置くこともしない。上位の候補に不明なものがあれば、読めるものの中から選ばずに停止を
延期し、そう記録する。読めない、または帰属できないことは、孤立の証拠に**決して**ならない。Chromium を孤立と
扱うのは、環境変数から空でない有効な `AF_SESSION_NAME` を実際に読め、その名前が停止済みまたは削除済みのセッションで、かつ Agent がメンバーの閲覧用に保持している Chromium などの保護対象でないときだけ。印がない、空、未知、または環境変数を読めない（メンバーが手で起動したブラウザ）ものは「その他」として触れない。起動時に Agent は陽性対照（同 uid の
プロセスは読める）と陰性対照（拒否された読み取りが拒否と認識される）を実行し、どちらかが期待どおりでなければ
強制はオフにする。フェーズ 0 も同じ確認を記録する。

エージェントセッションの中での選択：`Pss_Anon` + `Pss_Shmem` の占有量が最大のもの。ただし**ターンの最中のセッションは、占有量が
その 25% 以内のアイドルなセッションがあればそちらに譲る**（ターン中の halt はターンを中断する。トランスクリプトは
永続するが、進行中のターンは永続しない）。通知にはセッション名、占有量、何が食っていたかを書く。

既存のものとの関係：

- **アイドル停止**は動き続け、補完関係にある。アイドルなものをタイマーで止め、圧迫の段階は最大のものを測定で
  止める。どちらも同じ halt を使うので、どちらで止まっても同じように再開できる。互いには知らせない。圧迫の段階は
  アイドル停止が待ったはずの時間を縮めるもので、そのタイムアウトを置き換えない。
- **reaper の Workspace 停止**は影響を受けない。段階 3 の Workspace は定義上アクティビティがある。
- **セッションの再開**が唯一の回復経路で、段階 2 以上のあいだは決定 2 のエラーで断る。メモリのために止まった
  セッションには「メモリを空けるために停止」の理由と通常の再開操作が表示される。

### 4. `memory.high` は最初の段階では設定しない。応答役は Agent であり、応答役のいない絞りはより悪い

`memory.high` は、`memory.max` に達する前に、cgroup の割り当てを直接リクレイムの中で絞る。何も殺さない。
スワップがなく、使用量の大半が匿名メモリで `memory.high` を超えたままの cgroup は、失敗する代わりに永久に
遅くなる。Agent を含む中のすべてが遅くなり、何かがプロセスを止めるまで続く。その「何か」が決定 2 の段階で
あり、それ自体が絞られる。だから段階が実証される前の `memory.high` は、障害をより長い時間にしたものである。

一様には使えもしない。Docker と ECS が出すのは `memory`（→ `memory.max`）と `memoryReservation`（ソフトな
上限）で、`memory.high` ではない。Kubernetes はノードの `MemoryQoS` 機能経由でしか出さない。Agent は書けない
（コンテナの cgroup ファイルは uid 1000 の所有ではない）。置ける場所があるのは `ecs-ec2` だけで、すでに root で
動くスロット自身のブートスクリプトが、コンテナのスコープを見つけて管理プレーンに `MemoryMin` を設定している
（`af-protect-mgmt`、`40-ec2-pool.yaml`）。

決定：**フェーズ 0〜2 では `memory.high` を使わない。** フェーズ 3 で `ecs-ec2` のみについて見直す。測定で確認
または反証できる仮説は 1 つ：*上限の約 92% に置いた `memory.high` は、`max` より早く PSI を上げ
`memory.events` の `high` を増やし、段階に上限までの助走を与える。* 採用した場合の既存の数字との組み合わせ：

- #2451：コンテナの上限は `slot − 2048 MiB` のまま。`memory.high` は上限の**内側**にあり、2048 MiB のホスト
  予約には触れない。その大きさは名目のラングではなく実際の `MemTotal` に対して決めてある。
- #2452：`MemoryMin` はデーモンをリクレイムから守るが、Workspace の cgroup にいる Agent は守らない。これが
  どんな `memory.high` でも塞げない隙間である（未決事項 3）。
- サイジングの目安（決定 5）は、`memory.high` ができたらそれを基準に出し、上限は基準にしない。

### 5. 表面：Console へは事実、メンバーへは通知、管理者へは粗いスイッチ

**メンバー。**

- **Stats に軸を 1 つ足す**：`mem_pressure`（`some`/`full` の `avg10` と現在の段階）。読めなければ省く。
  Console のリソース表示はこれで、いまはキャッシュ込みの `memory.current` を示す使用量バーの隣に「メモリが
  逼迫している」状態を出す。
- **通知**は Agent の永続アウトボックス（`internal/notice`）を通じ、Workspace レベルのイベントとして出す。CP が
  確認応答するまで Agent の再起動を越えて残る。段階の遷移ごとに 1 件、重複排除する。文面には実行中のセッション
  数、段階、大きな消費者の名前（セッション名とコマンド名。パスは書かない）を入れる。
- **拒否のエラー**（決定 2）と**停止の通知**（決定 3）が、残る 2 つのメンバー向けの文。3 つとも両言語の Console
  文字列である。
- **マシン／サイジングの画面。** サイズごとの目安「8 GiB でおよそ N セッション同時」を、目安として示す。
  `(上限 − 基底) / セッション占有量の p75` で導く。入力の両方はフェーズ 0 から来るので、フェーズ 0 の結果が
  出るまでは**数字を出さず**、推測値を印字するより何も言わない。数字ができたら、フリート全体の数字より
  このマシンで Agent が観測したセッションごとの占有量を優先する。

**運用者と監査。**

- 段階の遷移と停止ごとに Agent のログを 1 行、トリガーになった数字つきで出す（`some`・`full` の
  `avg10`/`avg60`、ワーキングセット、`max`、選んだセッションとその占有量 `Pss_Anon` + `Pss_Shmem`）。
- CP は段階の遷移と自動停止を、専用のアクションで監査ログに記録する（メンバー操作の halt のアクションは再利用
  しない）。「このセッションを止めたのは誰か」の答えが「メモリの段階」になる。

**設定。** テナント設定を 1 つ、テナントのほかの上限と同じ場所で編集する。値は `off`、`measure`、`warn`、
`enforce` の 4 つ。`measure` は収集とログのみでメンバーに見える効果はなく、`warn` は段階 1 を足し、`enforce` は
段階 2〜3 を足す。デプロイの既定は同じ 4 値の環境変数で決め、テナント値はそれを狭める方向にだけ働く（デプロイが
オンにしていても、テナントはオフにできる）。**しきい値は最初の版ではテナント設定にしない。** テナントが誤設定
しうる 4 つの数字は、障害を再現する 4 つの方法であり、決定 8 がいずれにせよそれらを変える。定数の運用者専用の
上書きは環境変数でできる。

### 6. ボックスが遅いときに Agent は動けるが、固まったときには動けない

サンプラーは小さなファイルを数個読むだけで目立つ割り当てをしない単一の goroutine なので、遅いボックスの中でも
動き続ける。固まったボックスの中では動けない。障害では Agent がまったく応答せず、同じ cgroup の中で動くものは
リクレイムされている間は何もできない。安価な対策を 2 つ範囲に含め、残りは未決事項とする：

- Agent はセッションのプロセスを**より高い `oom_score_adj`** で起動する（上げるのに特権は要らない）。カーネルの
  OOM キラーが発動した場合に、Agent より先にセッションを選ばせるため。
- 拒否は、サンプラーが遅れていても**維持する**（安く元に戻せる）。停止は古いサンプルからは決して許可しない
  （決定 2）。

どちらも Agent をリクレイムから守りはしない。そのためにはコンテナの圧迫が届かない場所で Agent を動かす必要が
あり（未決事項 3）、だから本書は「ボックスがスラッシングする前に」と言い、防ぐとは主張しない。

### 7. 対応そのものについて検討した代替案

- **警告のみで決して動かない。** 安全だが障害は解けない。20 分のスラッシングの間、Console を見ていた人は
  いなかった。`warn` モードとして残す。
- **セッションではなく最大のプロセスを殺す。** 安く正確だが、何も再開できない。生きているセッションの下で
  claude の子を殺すと、「実行中」のまま壊れたセッションが残る。説明でき再開できる単位はセッションである。
- **停止（`SIGSTOP`）で凍結する。** 匿名メモリを解放しないので助けにならない。
- **拒否のみで停止しない。** 段階 2 だけでは、すでに上限を超えたボックスは超えたままである。障害で問題だった
  セッションはすべてすでに動いていた。

### 8. ロールアウト：先に測り、テナントごとに強制し、数字は測ったものから選ぶ

| フェーズ | 既定 | 出すもの |
|---|---|---|
| 0 計測 | 読めるランタイムすべてで**オン**。メンバーに見える効果なし | サンプラー、ログ行、Stats の軸（`measure` モード） |
| 1 警告 | フェーズ 0 の数字を読んだ後の `ecs-ec2` でオン。他はオプトイン | 段階 1 の通知、サイジングの目安 |
| 2 拒否 | テナントごとのオプトイン | 段階 2 |
| 3 停止 | 実スロットを意図的にここまで追い込むまで**オフ**。その後はテナントごとのオプトイン | 段階 3、犠牲の選択、停止の通知、`memory.high` の見直し |

フェーズ 0 がランタイムとサイズごとに記録するもの。最新値だけでなく時系列で残す：

1. **収集の方法。** `measure` モードで Agent は、段階とは**独立した**セッション別サンプラーを 60 秒ごとに
   動かす：全プロセスの `status`、そして**予算内のセッション群**のプロセスだけ `smaps_rollup`（1 サンプルにつき最大 5 セッション・50 プロセス。ページ
   テーブルを走査し mmap ロックを一瞬保持するので、件数を制限し、`full avg10` が段階 2 の水準にあるあいだは
   省く）。セッションは種別ごとにラウンドロビンで選ぶので、小さなセッションも大きなものと同じく確実に測られる。選んだセッションは、帰属したプロセス**すべて**を 1 つの観測として測り、途中で予算が尽きたらその観測は部分ではなく欠測として記録する。カバレッジ（種別ごとの、測れたセッション数 / 生きているセッション数）と欠測も時系列と一緒に記録する。セッションの*基底*はアイドル時（ターンなし、CLI 以外の子なし）の占有量の中央値、ボックスの基底は
   Agent と帰属できないプロセス。時系列は Agent の状態ディレクトリの上限つきファイル（この頻度で約 7 日、
   数 MB）に保持し、それ以降は間引く。Stats の軸が運ぶのは最新値だけ。
2. `some`/`full` の `avg10`/`avg60`/`total` とワーキングセット。健全で忙しいボックス（大きなビルド、N 個の
   セッション、chromium）に対してしきい値を置くため。
3. PSI に対するリフォールト率（使える第二の信号か確かめるため）と、実負荷での匿名・ファイル・shmem の内訳
   （障害時のものは記録されていない）。
4. セッションの生涯にわたるセッション種別ごとの占有量（`Pss_Anon` + `Pss_Shmem`。別々に保存し使うときに合計する。サイジングの目安、ログ行、犠牲の順位付けがすべて使う唯一の数字）。サイジングの目安の p75 と、shell の「最大の
   エージェントの 2 倍」という規則の根拠を得るため。ある種別について完全な観測が十分に集まるまで、サイジングの数字は出さない。何件を十分とし p75 をどう推定するかはフェーズ 0 が決め、本書では決めない。
5. PSI に対する Agent 自身のレイテンシ（ループバックのリクエスト）。Agent 自身が応答しなくなる圧迫の水準を見つ
   けるため。段階が間に合って動けるかを決める数字である。

フェーズ 3 は、1 つのスロットを意図的に段階 3 の先まで押し込み、止めたセッションの再開を含む一連の流れを
観察するまでは始めない。負荷は合成の匿名メモリ割り当て器だけではない（それではファイル主体の盲点を確認
できない）。受け入れで動かすもの：

- 匿名メモリ割り当て器、リフォールトが増える file + anon の混合負荷、長い Go・npm・Gradle のビルド（何も止めない、
  または止める理由を示す）、短いスパイクと回復、猶予中のサンプル欠落。
- 子が `setsid` で離脱するセッションと、子の親が付け替わるセッション：halt の後に両方のメモリが**解放**される
  こと（決定 3 の回収の契約）。再計測で確かめる。
- `shared-daemon`、`per-session-child`、`in-process` のセッションをそれぞれ、halt が何を返すか確認する。
- 実行中の Agent のレイテンシと欠落したサンプルを記録し、halt が間に合った証拠とする。最悪の負荷で Agent が
  飢えることは既知の限界（未決事項 3）でブロッカーではないが、証拠は記録に残す。

段階が捕まえないケース（ファイル主体のスラッシング、in-process のセッション、読めないプロセス、固まった
Agent）は、隠さずフェーズ 3 の記録に挙げる。

## 未決事項

これらは決定ではなく、まだ担当者もいない。

1. **しきい値は成り立つか。** `some` 10/25 と `full` 5/15 は、この種の段階が普通どう置かれるかから借りた値で、
   ここで測ったものではない。数字は実スロット（少なくとも 8 と 16 GiB）で、障害時の負荷を再現したフェーズ 0
   から得なければならない。
2. **Fargate と実際の `ecs-ec2` スロットで、コンテナ内から `memory.pressure` は読めるか。**（#2517） `docker` は開発用
   Workspace で読めた。残る 2 つはプラットフォームの文書からの期待である。
3. **Agent をどうリクレイムから守るか。**（#2518） `MemoryMin`（#2452）はデーモンを守るが、スラッシングする cgroup に
   いる Agent は守らない。選択肢：スロットのブートスクリプトが Agent 用に `memory.low` を設定したサブ cgroup
   （`ecs-ec2` のみ）、上限のかかったコンテナ cgroup の外で Agent を動かす、ECS が HEALTHY と言っているのに
   Agent が N 分以上沈黙した Workspace を止める CP 側の死活確認（2 人目のメンバーの場合）。
4. **`shared-daemon` のセッション**（codex、opencode）は 1 つのデーモンを共有する。`DropHandle` が実際に
   どれだけ返すか。デーモンを再起動する以外にもっと空ける動作はあるか（再起動は許されるか）。また、メモリが
   Agent 自身のものである `in-process` のセッションをどう扱うのが正しいか。
5. **`AF_SESSION_NAME` の環境変数の印は、セッションが起動するすべてのプロセスにあるか。** Managed セッション
   のツール用プロセスを含めて。プロセスツリーを越えた帰属が機能するかを決める。
6. **メンバーが 1 つのセッションを自動停止から守れる（ピン留め）べきか。** ボックスが段階 3 でピン留めされた
   セッションしか残っていないとき、答えは変わるか。
7. **メンバーは次に何をするか。** 操作を提示しない停止通知（「この Workspace をより大きなサイズに移す」）は
   半分の文である。そのリンクを通知に入れるかは、サイズ変更の流れと、メンバーがそもそもサイズ変更できるかに
   よる。
8. **`kubernetes` と `native`** には `ecs-ec2` より狭いモードが相応しいかもしれない。`native` ではボックスが
   メンバーのノート PC で、マシンがほかのことで忙しいという理由でセッションを止められるのは歓迎されない
   かもしれない。
9. **セッション自身の `ulimit -v` や `MALLOC_ARENA_MAX`** は、段階が必要になる前にばらつきを減らせる。測る価値は
   あるが、代替にはならない。

## 結果

- **良い点：** 障害に目に見える早い状態と、静かな行き詰まりの代わりの明確なエラーができ、フェーズ 3 を
  オンにすれば、再開可能なセッションを残す限定的な対応ができる。ランタイムアダプタも上限もホスト予約も
  変えない。
- **良い点：** フェーズ 0 だけで、サイジング画面とすべてのしきい値に要るデータが、ユーザーに見える変化なしに
  得られる。ただし無料ではない：60 秒ごとの `/proc` の走査と、件数を制限した `smaps_rollup` の読み取りがあり、
  プロセスの多いボックスでのその費用自体を、フェーズ 0 が最初に測る。
- **悪い点（受け入れる）：** 未決事項 3 に答えが出るまで、段階は応答役が飢えうるボックスでのベストエフォートな
  応答役である。PSI が数分にわたって見せるゆっくりした負荷上昇という一般的な場合は改善するが、Agent がすでに
  固まっている場合は助けられない。
- **悪い点（受け入れる）：** 停止はターンを中断しうる。通知がどのセッションか、なぜか、どう再開するかを言う。
- **悪い点（受け入れる）：** `native`、`kubernetes`、Fargate は、PSI が読めるか分かるまで、決定 1 の縮退
  モードで動くかもしれない。
- **ここでは決めない：** しきい値の最終値、フェーズ 0 の後の各フェーズの既定、Agent 自身の保護、`memory.high`
  の変更。

## 追記（2026-10-27）

フェーズ 0 を実装した（#2516）：Agent が 5 秒ごとに自分の cgroup を採取し、cgroup の境界を検証し、容量を
制限した分単位の時系列を保持し、Stats の `mem_pressure` 軸を報告する。上記の決定は変わらない。警告・拒否・
セッション停止は一切行わない。

フォローアップ：#2816。

## 追記（2026-10-28）

docker では Control Plane のローカル cgroup 読み取りが Agent に問い合わせずに stats ポーリングへ答えていたため、
`mem_pressure` が Console に届かなかった。ローカル経路は、ワークスペースごとのキャッシュ（バックグラウンドで更新、
短いタイムアウト、失敗後のバックオフ、30 秒応答がなければ破棄）を通じて、この軸だけを Agent から合流させる。
他のゲージはローカル読み取りのままで、Agent のエラー時は軸が欠落する。意味づけは Agent が持ち続ける。

フォローアップ：#2837。

## 追記（2026-10-31）

決定 1 の `memory.max` の一致確認を記録するようにした。上限を要求するアダプタ（docker の `--memory`、ecs-ec2 の
コンテナ上限、kubernetes の pod 上限）は、その値を `AF_WS_MEMORY_LIMIT_BYTES` として
Agent に渡す（native、Fargate、上限なしの ecs-ec2 のランクは何も設定しない）。Agent はこれを解決した cgroup の
`memory.max` と比べ（カーネルのページ丸めは許容）、結果 `agree` / `disagree` / `unknown` をログと
`mem_pressure` 軸の `memory_max_agreement` に出す。情報提供のみで、不一致でも起動は失敗せず軸も止まらない。
「渡されていない」と、境界確認を通らなかった cgroup も `unknown`。Fargate には渡さない：コンテナ定義に
独自のメモリがなく上限はタスクの cgroup にあるため、コンテナの `memory.max` は `max` と読めて誤った
`disagree` になる。実ランタイムでは未確認。フォローアップ：#2816、#3110。
