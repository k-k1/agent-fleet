## 背景

2026-09-02 の実測:

| 対象 | 規模 | 層化 |
|---|---|---|
| `control-plane/` | 非テスト 115 ファイル / 48,505 行、テスト 117 / 35,516 行（820 本） | **`internal/` が 1 つも無い**——単一 `package main` に型 399・関数 794・221 メソッドの `sqlStore` |
| `workspace/agent/` | root 149 ファイル / 51,177 行 ＋ `internal/`（19 パッケージ・約 39,000 行）、884 本 | [0012](0012-go-internal-refactor.ja.md) で層化済み。ただし root になお 51k 行 |
| `console/src/` | TS/TSX 122,094 行（632 ファイル）＋ CSS 19,666 行、テスト 200 ファイル | feature-sliced だが `settings/` だけで 15,858 行、単一コンポーネントが 3,498 行 |

[0012](0012-go-internal-refactor.ja.md) は agent にこれをやり、control-plane の手前で止まっている。
残りを 1 セッションずつ片付けると壁時計で数ヶ月になる。だから問いは**何を切り出すか**ではなく
（それは 0012 で決着済み）、**複数セッションが同時に切り出しても、浮いた時間をコンフリクト解消で
使い切らないためにどうするか**である。

障害は具体的だ。単一 `package main` からのパッケージ抽出を素直にやると全呼び出し箇所を書き換える
＝**ツリー全域に及ぶ編集**になる。2 セッションが同時にやればほぼ全ファイルで衝突し、後からマージ
した側は自分の作業をやり直す。

## 決定

**決定 1. 移送はエイリアス越しに行い、呼び出し側を一切触らない。** 実体は `internal/x` へ移し、
元のパッケージには移した名前 1 つにつき 1 行だけ残す:

```go
// control-plane/alias_store.go —— 移送したセッションだけが所有する
type Store = store.Store
var openSQLite = store.OpenSQLite
```

呼んでいる 100 ファイルは無変更。これでパッケージ抽出が**そのセッションが所有するファイルの中に
閉じた編集**になる——並列化が成立する条件そのものである。代償は 2 つ受け入れる: 型を移せばその型の
メソッドは全部一緒に動く（Go はエイリアスにメソッドを定義できない）／元パッケージへ手を伸ばし返す
家系は、今回のウェーブの候補から外す。

**決定 2. エイリアス層はウェーブ境界で、1 セッションが単独で回収する。** エイリアスを剥がす作業
こそが決定 1 の避けた全域編集なので、そのモジュールを誰も持っていない時に走らせる。機械的
（`gopls rename`）で挙動を変えず、独立した PR にする。ウェーブ中に立っているエイリアスは欠陥では
なく、並列で走ったことの対価である。

**決定 3. 1 ファイルの所有者は 1 つ。** 各ワークパッケージは着手前に自分のファイルを glob で宣言
する。所有外のファイルに触れた PR は**読まずに差し戻す**——判定が機械的なのでレビュワーの負荷は
ゼロで、裁量の余地も無い。誰も所有しないファイル（`main.go`・`routes.go`・`client.ts`・デザイン
トークン）は**共有**扱いで、追記のみ・1 行ずつ。

**決定 4. 衝突源はファンアウトの「最中」ではなく「前」に解体する。** 全フロントセッションが追記
したがる 4,700 行の `locales/ja.ts` は、マージのたび確実に衝突する。全 Go セッションが登録しに
来る `routes.go` も同じ。Phase 0 が、他に何も走っていない状態で単独に分割する。Phase 0 は
オーバーヘッドではなく、**ウェーブを安くするもの**である。

**決定 5. 切断面はコンパイラに出させる。紙の上で設計しない。** 手順は「ファイルを移す → package
節を書き換える → `go build ./...` → `undefined:` の一覧を読む」。その一覧が**その家系の外向き依存
そのもの**であり、裁量が入らない。あとは各名前を「一緒に移す」「引数か consumer-defined interface
で受け取る」「残してエイリアス」に仕分ける。切断面を事前に当て推量すると、丸 1 日かけてから
「この切り方は無理だった」と分かる。

**但し書き（ウェーブ B・PR #313/#315 の実測を受けて追記）。「引数で受け取る」は、実装の仕方に
よっては強制力がゼロになる。** 移送は、それまで**コンパイラが強制していた依存**を、しばしば
**無言で外せる実行時の結線**に変える。実例: 移送前は `builtinAssistants()` が 2 つの関数を直接
呼んでいたが、移送後は `alias_*.go` の `init` が代入するフックになり、**その代入 2 行を消しても
テストが全部緑**になった（結線し忘れが検出されない）。

これを「引数で渡す」に直すとき、**公開フィールドの struct で束ねると穴は塞がらない**。Go の
複合リテラルは名前付きフィールドを省略できるので、`Deps{KnowledgeDir: f}` は**もう一方を書き
落としてもコンパイルが通る**——フックと同じ「無言で外れる」形が、名前を変えただけになる。

したがって規則はこう書く:

- **依存が数個なら、フィールドを非公開にし、引数 N 個のコンストラクタを唯一の入口にする。**
  そうして初めてコンパイラが引数の個数を数える。
- **依存が多くてコンストラクタが現実的でないなら、公開フィールドの struct ＋ 起動時の網羅検査でよい。**
  **ただしその検査自体を、「フィールドを 1 つずつゼロにしたら必ず落ちる」形でテストに固定すること。**
  手書きの検査一覧は、**フィールドが 1 つ増えた瞬間に漂流する**（実測: 25 依存の面で、検査 1 行を
  削って配線も外すと全緑になった）。reflect で全フィールドを回せば漂流が原理的に起きない。
  **関数型は未配線なら nil 参照で落ちるが、値型は零値のまま走る**ので、危ないのは値型である。
- ＝ **「コンパイラに数えさせる」か「テストに数えさせる」かの二択で、どちらでもない形
  （手書きの検査だけ）を採ってはならない。** 規模で選ぶ：25 引数のコンストラクタは書けないうえ、
  同型の引数が並ぶぶん**順序間違いという新しい事故**を作る。
- **ゼロ値の struct は外から書けてしまう**（`pkg.Deps{}` はコンパイルが通る）。そこは実行時に
  **panic で落とす**。無害な既定値を置いてはならない——既定値は「結線し忘れ」を緑にする。
- **「渡していること」はコンパイラ、「渡された値を実際に使っていること」はテスト**と役割を分ける。
  後者はコンパイラに見えない。
- **副作用を持つ依存は関数型のまま渡す。** 値（文字列など）に畳むと**呼ばれる回数が変わる**。

**決定 6. ワイヤ互換は非交渉であり、機械的に証明する。** Phase 0 で `buildMux` が登録する
`(method, path)` 全件のゴールデンと、主要レスポンス形状のゴールデンを置く。ルートを落とす移送や
JSON タグを変える移送は、利用者に届く前にテストが赤くなる。前提自体は
[0012](0012-go-internal-refactor.ja.md) と同じで、新しいのは**移送 40,000 行を読めないレビュワー
でもここに依拠できる**ことだ。

**決定 7. レビュワーは独立したセッションで、製品コードを書かない。** 役割は、ワイヤ互換とゲートが
実際に走ったことの検証・所有権違反の検出・マージキューの保持（`develop` に入るのは同時に 1 本）・
台帳の更新。書いた本人がレビューすれば自己レビューになり、レビュワーが実装すれば、解消するはず
だったボトルネックにレビュワー自身がなる。**`develop` へのマージは維持者（利用者）の手に残す**——
レビュワーは「合格」とキューの順番までを言う。

**決定 8. 中継は専任の司令塔セッションが行う。ワーカー同士でもなく、フリート・オペレーターでもない。**
ワーカーとレビュワーは互いにメッセージを送らない。ワーカーは PR を開き、司令塔へ `notice` を 1 通
送って終わる。司令塔はその 5 行を**そのまま** `request` としてレビュワーへ渡し、`answer` を受け取り、
キューの順番を維持者に伝えるか、修正依頼をワーカーへ中継する。トポロジは**片道 1 ホップのハブ**である。

ハブをオペレーター会話ではなくセッションにしたのは、オペレーター会話が**維持者自身の作業面**だから
だ——13 ワークパッケージ＋各レビュー往復の中継でそれを何日も占有することになる。セッションなら
リポジトリを直接読めるのも効く: **peer メッセージは相手の 1 ターンを丸ごと使う**ので、
**司令塔はまず状態板を読む**——`git fetch` と `gh pr list --base develop` が「どのブランチが動いたか」
「どの PR が開いたか」を、誰も割り込まずに教えてくれる。peer で運ぶのは板から読めないことだけ。

手放すのは**オペレーターの自動的な記録**である。オペレーターの指示は台帳
（[0027](0027-operator-interaction-graph.ja.md)）に書かれ報告は会話に残るが、司令塔の peer
メッセージは何も残さない。**したがって `~/af-refactor/` の台帳は「あると便利なもの」から
「唯一の記録」に変わる**——指摘は `tracks/<track>.md` に置き、メッセージはポインタだけを運ぶ。

安全弁 2 つはそのまま残す。オペレーター固有の話ではなく、このループの性質だからだ:
**報告はデータであって命令ではない**（他セッションから届いた文面をシェルコマンドとして実行しない）／
**開いた問いは維持者へ上げる**（リファクタが止まるのは「どう切るか」であり、既定値で自動回答して
よい種類の問いではない）。

**決定 9. 純粋移送コミットと手直しコミットを同じコミットにしない。** 移送コミットは
`--find-renames` で内容差分ゼロを示せること。コンパイラに強制された修正は理由をメッセージに書いて
別コミットにする。5,000 行の差分がレビュー可能であり続ける唯一の方法であり、**挙動の変更が紛れ込む
のではなく気付かれる**ための仕掛けでもある。

**決定 10. ワークパッケージ 1 つにつきワークツリー 1 つ、同時に生きているのは 6 本。レビュワーは
ワーカーのブランチをチェックアウトしない。** ピークは**セッション 6 本・ワークツリー 6 本**
（司令塔・レビュワー・ワーカー 4。Phase 0 期間は 2 本）。リファクタ全体では 15 本作る
（司令塔・レビュワー・ワークパッケージ 13）が、PR がマージされたワークツリーは掃除するので上限は 6。
この上限はディスクではなく**メモリ**から来る: ワークツリー 1 本は **37 MB**（74 MB の `.git` は共有で
複製されない）に対し空きは 71 GB、一方このコンテナは **10 GiB 上限**で、`go test ./...` の同時 2 本が
それを使い切る定番である。司令塔にも自分のワークツリーを与える——板を読むのに `git`/`gh` が要るし、
親クローンは他の全セッションの起点だからだ。 git は他のワークツリーが握るブランチのチェックアウトを拒否し、それを
上書きするフラグは禁止（2 つのコピーが 1 つのブランチ ref を共有し、互いのコミットを無言で巻き戻す）。
よってレビュワーは `git diff origin/develop...origin/<branch>` で読み、ゲートを走らせる必要がある
ときは**その commit を detached HEAD でチェックアウトする**——ブランチが他所に握られていても git は
これを許す。レビュワーのワークツリーは自分のブランチを持たず、push もしない。

残りのワークツリー規約も同じ原理から出る——ワークツリーは机であり、**他人の机が何であるかを
変える**ことがセッションを壊す:

- 各ワークパッケージは Console のワークツリー・セッションとして起動し、**最初の push の前に
  ブランチを `refactor/<track>` へ改名する**。マージキューと PR 一覧が読めるようになる。後から
  改名すると 2 本目のリモートブランチを push して 1 本目を消す羽目になる。
- ワークツリーは PR がマージされるまで残し、そのあと **Console から**掃除する（エージェントが
  消さない）。
- 統合は常に内向き: 自分のワークツリーで `git fetch origin && git merge origin/develop`。
  **他人のために親クローンを fast-forward しない**——無関係な編集なら `pull --ff-only` は成功して
  しまい、作業中のセッションの足元でファイルが入れ替わる。
- `console/node_modules` はワークツリーごとに約 350 MB、ボリュームは 85% 使用済み。フロントの
  ワークツリーはロックファイルが一致する限り親のツリーへ symlink し、`npm ci` の前にリンクを外す
  （末尾スラッシュ無しで）。

**決定 11. マージ前のゲートはレビュワーのローカル実行である。CI はこれらの PR を見ないからだ。**
`ci.yml` のトリガは `main`/`develop` への push と、**`main` への** pull request だけ。つまり
`develop` 宛の PR はマージされるまで無検査で、赤くなるのは**マージした後**である。リファクタの
PR 13 本でそれを踏むのは割に合わないので、`.github/workflows/` に触れる唯一のセッションである
Phase 0 が `pull_request` のトリガに `develop` を足す。公開リポジトリでランナーは無料であり、
今まで誰も気付かなかったのは `develop` 自身の push トリガが（マージ後に）赤くしてくれていたからだ。

## 却下

- **移送と同時に呼び出し側を書き換える（`gopls rename`）。** 正しいが、Go の全セッションを 1
  モジュールに直列化する。**既定としては**却下——安全な瞬間にウェーブごと 1 回やるのが決定 2。
- **長命のリファクタ・ブランチ 1 本。** レビュー不能で、`develop` から乖離する（CI が `main` しか
  見ていなかった 1 ヶ月で develop は 1,500 コミット進んだ）。
- **2 バイナリの共有モジュール化。** [0012](0012-go-internal-refactor.ja.md) で却下済み。並列
  ウェーブが再発見しないようここに再掲する。
- **ワーカー同士を直接つなぐ。** 1 通あたりは安いが、ワーカー 4 本ではメッシュになる——状態を知って
  いる場所がどこにも無く、着信はビルド中のターンに割り込む。ハブ 1 つ・片道 1 ホップにする。
- **フリート・オペレーターをハブにする。** 記録（指示台帳と読める会話）も道具も上で、ここでも最初は
  これを採った。却下の理由は、それが**維持者自身の会話**であり 2 週間分の中継で占有されること、
  そしてセッションならリポジトリと `gh` を直接読めて**メッセージ自体がほとんど要らなくなる**こと。
- **全トラックが更新する台帳ファイルをリポジトリに置く。** 調整のための成果物がツリーで最も熱い
  衝突源になる。ライブ台帳は git の外にトラック 1 ファイルずつ置き、恒久的な結論だけをここと
  `docs/` に落とす。
- **レビュワーにマージさせる。** 速いが、人間の拒否権が安く・誤りが高くつく唯一の外向き操作を
  自動化することになる。
- **worker 6 本同時。** host は共有かつメモリ制約下で、`go test ./...` の同時 2 本が既にメモリを
  使い切る定番であり、レビュワー 1 人は PR 6 系統を捌けない。worker 4 ＋レビュワー 1 をウェーブで。

## 帰結

- 移送から回収までの間、エイリアスが存在する。負債は `grep alias_` で見える。ゼロになるまでその
  ウェーブは終わりではない。
- `migrations/`・`migrations-pg/`・`assets/` は、それを embed するパッケージと**一緒に**動く——
  `//go:embed` は自分のディレクトリより上を見られない。見落とすと store 抽出が壊れる、唯一の
  機械的な罠である。
- `ci.yml` の変更を push するには `workflow` スコープ付きのトークンが要る。device flow は今は要求
  するが、修正前に保存されたトークンは持っていない。Phase 0 の push が拒否されたら、回避策を
  探さず Console の Connections から GitHub を再接続する。
- ワークスペースで peer メッセージが有効になっていること。無効ならハブに経路が無く、調整は維持者の
  手作業に落ちる。
- 前回の層化は全テスト green でマージされ、**実機（ライブフリート）では一度も確認されていない**。
  今回はイメージ再ビルドと、セッション作成・チャット・git・LFS・接続フローの一巡までを完了条件に
  含める。

## 実績（2026-09-04・完了時点で追記）

Phase 0 のマージ `9b0336e7` から `develop = 40c9142a` まで。**PR 57 本**（うち本トラック外の混入 0）。
数字は完了点で測り直したもので、数え方は開発者向けの作業ジャーナル（2026-09 の並列リファクタ）にある。

- **`package main`（モジュール直下の非テスト `.go`）**: control-plane 115 枚 48,505 行 → **96 枚 28,321 行**、
  workspace/agent 149 枚 51,177 行 → **64 枚 15,373 行**。**合計 −55,988 行（−56%）。**
  背景表の起点の値がそのまま出発点として再現する。
- **`internal/` パッケージ +16**（control-plane 0 → 7、workspace/agent 19 → 28。うち 2 つは契約検査のハーネス）。
  モジュール全体は逆に **+16.7k 行**増えた——**縮んだのは `main` だけで、増えたぶんは検査である。**
- **エイリアスは 4 ウェーブとも 0 まで回収した**（A / B 157 / C 190 / D 144 → 0）。`alias_*.go` はリポジトリに 0 枚。
- **実機一巡を 2 回**実施し、**2 回とも全ゲートが緑のまま通り抜けていた実害を 1 件ずつ**掘り当てた
  （本番の配備経路を塞いでいた CFN テンプレのサイズ超過／恒久要因を一時要因として返す診断可能性の欠陥）。
  **決定の完了条件に実機一巡を入れたのは正しかった。**
- **契約の型化**（ADR 0012 の残タスク④）で**契約検査 15 家系**・**`map[string]any` 直返し 27 サイトの struct 化**が入り、
  **実バグを 2 件**掘り当てた（1 件は同ウェーブ内で修正）。

決定がどう働いたか（**変えた決定と、守られなかった決定も含む**）:

- **決定 1（エイリアス移送）は成立した**——4 本並走で移送起因のマージ衝突はゼロ。
  🔴 **ただし代償はエイリアスだけではなかった**: 外向き依存を配線に変えると、値の確定が
  「パッケージ初期化時」から「`Configure` 時」へずれる。**受け手がトップレベル `var` の初期化式だと、
  そこだけ零値で固まる**——MCP の `inputSchema` が `enum: null` を広告して**本番のセッションが全面停止した**
  （型検査も `go vet` も鳴らない）。**移送前は同じ形がリテラルで、正しく動いていた。**
- **決定 5 は途中で本文を書き足した**（#317）——「引数で受け取る」は実装によっては強制力がゼロになる。
  現在の本文の但し書きがそれで、**この追記は同日に合格した PR を一時的に非適合にした。**
- **決定 6 のゴールデンは効いたが、撮っていない面が広かった**——`wire.golden` は型名もフィールド名も撮らないので、
  **同型フィールドの取り違えは全網で緑になる。**契約の型化はその穴を埋めるために立った段である。
- 🔴 **決定 7 は運用で変更した**（2026-09-02・維持者の指示で、合格した PR は司令塔がマージ）。
  空転は消えたが、**マージキューを書けるのはレビュワーだけ**なので**板が構造的に 1 手遅れ**、
  「合格・マージ待ちのまま取り残された行」が 3 回出た。**手順（マージ直後の 1 手を必ず通知にする）に
  変えるまで、注意では直らなかった。**
- **決定 3 の機械判定には穴があった**——`git diff --name-only` は既定の改名検出で「移動先 1 本」に畳むため、
  **所有外のファイルを自領域へ持ち出しても検査が緑**になる（`--no-renames` で修正）。
  glob に `*` を登録すると**所有外は常に 0 と出る**＝合格に情報が無い。**塞いだあと過去に遡って白を測り直した。**
- **決定 10 の上限 6 本を 1 度だけ超えた**（実機一巡を含めて 7 本）。重いゲートを回さない役だからという理由で、
  上限の意味（メモリ）には反しないが、**数字そのものは守っていない。**
