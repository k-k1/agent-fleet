## 背景

### 2026-09-16 に起きたこと

本番配備が全体的に遅くなった。真因は API でもデータベースでもなく、その下のマウントだった。
Workspace の設定・資格情報を載せている EFS が `ThroughputMode: bursting` で、**バーストクレジットを
使い切っていた**。bursting のベースラインは Standard ストレージ 1 GiB あたり 50 KiB/s であり、
この EFS は設定と資格情報しか持たない（約 2.6 GiB）ので計算上のベースラインは約 0.13 MiB/s——
ただし **AWS は全ファイルシステムに 1 MiB/s の metered throughput を最低保証する**ので、実際の
床は 1 MiB/s である（EFS UG「バーストスループット」の Note）。CloudWatch で確認した:
`BurstCreditBalance` が 09-16 09:30 JST に 896 MB、10:30 JST に **0**。同時に
`PermittedThroughput` は **104.858 MB/s（＝100 MiB/s のバースト）→ 1.049 MB/s（＝きっかり
1 MiB/s）** へ落ち、11:45 JST までそこに張り付いた。クレジットが尽きた瞬間、全 Workspace が
その 1 MiB/s を 9 個で分け合うことになった——2.4 KB のファイルの `openat` に 5.3 秒かかった。

なぜ「全部」遅くなるのかは、EFS に何が載っているかで決まる。本番の Workspace は EC2 起動タイプで、
ボリュームは 3 つ:

| ボリューム | 置き場所 | 中身 |
|---|---|---|
| `home` → `/home/dev` | **インスタンスの EBS**（ホストパス） | `~/repos` を含む home の実体 |
| `claude` → `/var/lib/af/claude` | **EFS**（アクセスポイント） | `CLAUDE_CONFIG_DIR`。`projects/`・転写・設定 |
| `keep` → `/var/lib/af/keep` | **EFS**（アクセスポイント） | `~/.config`・`~/.ssh`・`~/.claude`・`~/.codex`・`~/.gitconfig`・`~/.git-credentials`・`~/.claude.json` を `~` から symlink |

`control-plane/internal/runtime/runtime_ecs_ec2.go:3650` が `CLAUDE_CONFIG_DIR` を、`:3652` が
`AF_WS_KEEP` を注入し、`workspace/entrypoint.sh:20-52` が `~` の 7 項目を `keep` 側へ symlink する。
つまり `git` を 1 回起こすたび（`~/.gitconfig`）、`claude` を 1 回起こすたび（`CLAUDE_CONFIG_DIR`）
EFS のメタデータ I/O が出る。**リポジトリの作業コピーは EBS にあるのに、遅くなるのは全部**という
一見矛盾した症状はここから来ている。

応急処置として live の EFS を CLI で `elastic` に変えた（**09-16 11:56 JST**——`PermittedThroughput`
が 1.049 MB/s から 5,368.709 MB/s へ跳ねた時刻。反映は約 1 分、`/api/repos` が 20 秒 → 272 ms）。
並行して、転写探索の `filepath.Glob("projects/*/<sid>.jsonl")` が毎ポーリングで全プロジェクト
ディレクトリを読んでいた件を PR #711 / 0.20.2 で直し、0.21.0 として配備して全利用者が再起動した。

### 再起動が揃った後に残ったもの

**PR #711 で嵐は消えていない。** 改善幅は「どの指標で、いつと比べるか」で 13〜46% の幅に散る——
**「半分になった」とは言えない。** 同じ時計の窓（09:00〜13:20 JST）で並べたのが次で、これが
いちばん公平な比較である:

| 日 | agent | 1 箱 ops/s p50 | 1 箱 ops/s p99 | 1 箱 MB/s p50 | 全体の最大（1 分値） |
|---|---|---|---|---|---|
| 09-11 | 旧 | 175 | 476 | 0.717 | 10.100 MB/s（11:49・**箱 5 個**） |
| 09-14 | 旧 | 223 | 620 | 0.913 | 18.118 MB/s（11:46・**箱 7 個**） |
| **09-17** | **新 0.21.0** | **153** | **345** | **0.627** | 5.860 MB/s（10:48・**箱 4 個**） |

⚠️ 最右列の箱数は**そのピークの分の箱数**である（`ClientConnections` の 1 分合計 ÷ 2）。
初稿はここに「窓の中の最大箱数」（6 / 8 / 6）を書いていた——**下の外挿はこの分母を使うので、
取り違えるとピークの推定がそのままずれる**。

p50 の減少は旧 09-14 比で 31%、旧 09-11 比で 13%。p99 では 44% / 28%。別の見方として
**1 箱 1 時間あたりの I/O 量**では 5.20 GB（旧・09-16 の elastic 窓 48.2 箱時間）→ **2.78 GB**
（新・09-17 の 13.3 箱時間）で 46% 減。⚠️ **箱時間あたりの量は「箱がどれだけ忙しかったか」を
含む**ので、率の比較（13〜44%）と量の比較（46%）は別の質問への答えである。どちらも
「半分」を保証しない。

箱の数は `ClientConnections`（Sum / period × 60）から数えた。**1 箱 = 2 接続**で、CP は EFS を
使わないので寄与しない。

🔥 **箱が 1 個だけの時間帯（09-17 09:06〜10:05 JST）の 0.44〜0.45 MB/s が「きっかり平ら」だった。**
リクエスト数は推定に頼らず直接数えられる——**`MetadataIOBytes` の `SampleCount`** がメタデータ
操作の回数そのものである。この 1 時間の実測は **387,550 回 ＝ 107.7 ops/s**。
（参考: AWS は「すべての NFS リクエストを 4 KB、または実際の要求/応答サイズの大きい方として
計上する」と書いており、`MetadataIOBytes ÷ 4 KiB` は 107.7 ops/s と 0.006% で一致した。ただし
elastic の**課金**側の最低単位は別物なので——後述——回数を言うときは `SampleCount` を使うこと。）

利用者はこれを「1 ユーザーで 0.5 MB/s は多い」と見ている。正しい。設定ファイルを読むだけの
ファイルシステムが毎秒 108 回の往復をする理由は無い。

⚠️ **「0.2 MB/s まで落ちる」は目標にしてはいけない。** 12 日分の履歴では 0.2 MB/s になるのは
箱が 0〜1 個の時間帯だけで、稼働時間帯は 09-07 以降ずっと 1 箱 0.7〜1.9 MB/s の帯にいる。

## 実測 1: 何が 110 リクエスト/秒を出しているか

`ptrace_scope=1` なので走行中の Agent には attach できない。代わりに**エージェントの実コードを
そのままテストバイナリに固めて子プロセスとして起こし**、`strace -c -e trace=file` で数えた。
プロジェクト数・セッション数は本番の箱と同じ規模にした。

### 発生源 A: `ListMetas()` ——セッション台帳が EFS に載っている

`workspace/agent/internal/session/meta.go:17`:

```go
// MetaDir lives in the home volume (persists across Stop→Start) under the
// denylisted .config/agent-fleet, so stopped sessions survive a Workspace restart.
func MetaDir() string { … filepath.Join(paths.HomeDir(), ".config", "agent-fleet", "sessions") }
```

🔥 **このコメントは ecs-ec2 では誤りである。** `~/.config` は `AF_WS_KEEP_DIRS` の既定
（`.config .ssh .claude .codex`）に入っているので、entrypoint が **`keep`（EFS）へ symlink して
いる**。つまりセッション台帳は EFS にある。

`ListMetas()` は `ReadDir` 1 回のあと**メタ 1 件につき `os.ReadFile` を 1 回**する。実測
（メタ 207 件・100 回呼び出し・`strace -c`）:

```
openat 21,014   read 41,406   close 21,013   getdents64 204   = 83,637 syscalls
→ 1 回の ListMetas() あたり 836 回のファイル系システムコール（openat 210 / read 414 / close 210）
```

呼び出し側は 32 箇所あり、その中に **`GET /sessions` のハンドラ**がいる。そして
`control-plane/events.go:145` のコメントが頻度を決めている——

> this tick function runs once per open tab every 4 seconds

**Console のタブ 1 枚につき 4 秒に 1 回**、CP が Agent の `/sessions` を呼び、その 1 回が
EFS 上のファイルを 207 個開いて読む。タブ 2 枚なら 2 倍になる。

`~/.config/agent-fleet` の実測は **113 MB / 約 5,400 ファイル**だった。ADR 0045 が `keep` に
想定していたのは「認証・接続・identity の 7 つ・合計 100 MiB 未満」である。実際に載っているのは:

| パス | ファイル数 | 性質 |
|---|---|---|
| `session-status/` | 1,220 | セッション状態の書き込み先（`status.Persist`） |
| `pending-perm/` | 1,429 | 許可待ちの一時状態 |
| `chat-wd/` `chat-codex/` `chat-claude/` | 971 | チャットの作業ディレクトリ（93 MB） |
| `sessions/` | 207 | セッション台帳 |
| `session-injections/` `session-exit/` `codex-sid/` … | 約 1,500 | 各種の可変状態 |
| **`secrets.enc` / `secrets.json`（＋ `.lock`）** | 2 | 🔥 **資格情報ストア本体**（`internal/secrets/secrets.go:383` の `Path()` が `paths.AgentConfigDir()` 配下に置く。Git・Claude OAuth・接続の資格情報） |

⚠️ **最後の行が決定的である。** この ADR の初稿は「資格情報は 1 つも無い」と書いていたが誤りで、
**`~/.config/agent-fleet` は資格情報ストアそのものを含む**。ADR 0045 が `keep` を作った理由に
まっすぐ当たるので、決定 4 は「まるごと降ろす」ではいけない（決定 4 を参照）。
残りは資格情報ではない——**keep の粒度がディレクトリ単位（`.config`）だったために、
エージェントの可変状態が資格情報と同居したまま EFS に載った**、というのが事の全体である。

### 発生源 B: `subagentBases()` ——「見つからなかった」は覚えない設計の裏側

PR #711 は `jsonl_memo.go` を入れて転写探索を memo 化した。その不変条件は意図的にきつい:

> A MISS IS NEVER REMEMBERED. 転写があるのに「無い」と答えると `--session-id` が渡って claude が
> `Session ID is already in use` で落ちる。

正しい。ただし **同じ memo を使うもう一方——`subagentBases()`——は、ほとんどのセッションで
恒久的に miss する**。背景エージェントを使っていないセッションには `projects/*/<sid>/subagents`
が存在しないからで、miss は覚えないので**毎回 full sweep が走る**。

呼び出し経路は待機中の claude セッションの状態判定そのものである
（`internal/agents/claude/claude.go:213` → `BackgroundWork` → `bg.go:185` `SubagentBusy`）。
`BackgroundBusy`（/proc・安い）が false のときに必ず来る。

`strace -c` で数えた 1 回あたりのコスト（`filepath.Glob` は `projects/` を 1 回 + 一致した各
ディレクトリを 1 回ずつ `ReadDir` する）:

| プロジェクト数 | 1 回の `SubagentLogs()` あたりのファイル系システムコール |
|---|---|
| 38 | **158**（getdents64 78.8 / openat 39.9 / newfstatat 39.8） |
| 318 | **1,296** |

きれいに `(1 + プロジェクト数) × 4 + 2` である。開発配備の箱でプロジェクトディレクトリを数えると
**318 個**あった。本番の箱は 38 個で測ってある。**「全ディレクトリがきっかり同数」は 1 個ずつ
探しに行っている証拠**という見分け方は、ここでもそのまま効く。

同じ形は転写側にも残っている: memo が hit していれば 1 回の `Lstat`（実測 5 syscall/回）で済むが、
**`memoTTL = 60s` ごとに full sweep へ戻る**し、最初の turn が jsonl を書くまでは miss なので
sweep し続ける。

### 発生源 C: EFS への書き込み（小さい）

elastic では書き込みが **$0.07/GB**（読み取りは $0.04/GB）なので、状態ファイルの書き込みは
読み取りより高い。ただし量は小さい: 09-17 09:00〜14:04 JST の実測で書き込みは全体の
**1.7%**（書き 0.80 GB に対し読み 46.22 GB）。⚠️ 初稿の「0.8%」は分母を読みだけにした
計算違いである。

⚠️ この ADR の初稿は `status.Persist(sid, "working")` を「ポーリング経路から毎回書かれる」と
書いていたが誤り。`claude.go:208` のこの呼び出しは**自己修復の分岐だけ**——「ファイルは idle
なのに画面は動いている」ときにだけ通り、コメントどおり **1 ターンにつき 1 回に自己限定される**
（次のポーリングはファイルから "working" を読む）。**発生源 C は A・B と同じ桁ではない。**

### 合わせるとどうなるか（ここは仮説であって、まだ裏が取れていない）

箱 1 個・Console タブ 1 枚・メタ 207 件・プロジェクト 38 個・待機中の claude セッション 3 本:

```
ListMetas()        208 ファイル読み       × 1/4s
SubagentBusy() ×3  117 ディレクトリ読み   × 1/4s
                 → 毎秒 80 前後のファイル/ディレクトリ操作（VFS 層）
```

実測の床は 107.7 metadata ops/s なので**桁は合う**。⚠️ **ただしこれは A と B が床の主因である
ことの証明にはなっていない。** VFS 層の操作数と NFS の往復数は別物で、両者を結ぶ比
（1 操作あたり何往復か）は未測定である。本番の箱で採った `/proc/self/mountstats` の 20 秒差分
（09-17 12:20 JST・レビューセッションが SSM 経由で採取）は:

| マウント | RPC/s | 内訳 |
|---|---|---|
| `claude`（`CLAUDE_CONFIG_DIR`） | 27.5 | GETATTR 492・OPEN_NOATTR 29・CLOSE 29（20 秒間） |
| `keep` | 16.9 | OPEN_NOATTR 148・CLOSE 148・GETATTR 18・LOCK/LOCKU/FREE_STATEID 各 8 |

再送はゼロ。`keep` 側の OPEN/CLOSE 主体は `ListMetas()` のようなファイル読みの形と整合し、
LOCK/LOCKU/FREE_STATEID は `secrets.go` の flock と整合する。

⚠️ **RPC の種類から呼び出し元を断定してはいけない。** 初稿は「`claude` 側に READDIR がほぼ
出ていない＝B（全掃引）が主因ではない」と書いたが、これは言い過ぎである——ディレクトリの
内容がキャッシュから返っても、**全掃引に伴う属性の再検証が GETATTR を出し得る**。この
実測から言えるのは「READDIR の RPC は 0、GETATTR が主体、同時刻の VFS 操作数が無いので
**寄与は不明**」までである。**A と B の寄与順位は未確定**であり、決定 5 の前にこの 2 つを
同時に測ること。

## 実測 2: お金

ap-northeast-1 の単価（Pricing API・2026-09-17 取得）:

| 項目 | 単価 |
|---|---|
| Elastic の読み取り | **$0.04 / GB** |
| Elastic の書き込み | **$0.07 / GB** |
| Provisioned Throughput | **$7.20 / MiBps-月** |
| Standard ストレージ | $0.36 / GB-月 |
| bursting / provisioned の I/O | **無料**（帯域に含まれる） |

🔥 **bursting では I/O が無料だった。** Cost Explorer では 09-15 まで 1 日 $0.02（ストレージだけ）
だったものが、elastic へ切り替えた 09-16 に `APN1-ETDataAccess-Bytes` が **235.206 GB / $9.4655** として
現れた。障害を止めた代わりに、それまで「遅さ」として出ていたものが「請求」として出るように
なった、というだけのことである。

### ⚠️ `MeteredIOBytes` は課金量ではない

この ADR の初稿は「課金メーターは `MeteredIOBytes`」と書いていたが不正確だった。AWS の
`metered-sizes.html` が分けているのは次の 2 つである:

- **`MeteredIOBytes` は帯域の meter** で、**読み取りを 1/3 に割り引いた後**の値である
  （「read requests を他の I/O の 1/3 の率で計上する…この調整後の合算が `MeteredIOBytes` に
  反映される」）。スループット上限に当たるかどうかはこれで決まる。
- **elastic の課金**は割引ではなく**読み書きの単価差**で効く。メタデータの読みは read 操作、
  メタデータの書きは write 操作として課金され、**メタデータ操作は最初の 4 KiB の後 1 KiB 刻み、
  データ操作は最初の 32 KiB の後 1 KiB 刻み**で計上される。

したがって費用は `MetadataReadIOBytes + DataReadIOBytes` に $0.04、
`MetadataWriteIOBytes + DataWriteIOBytes` に $0.07 を当てて出す。

### 🔥 突き合わせると 0.12% ——課金は GiB（2³⁰）である

09-16 の elastic 窓（**11:56〜翌 09:00 JST**、Period=60 で 698 分ぶんを合算）:

| | |
|---|---|
| CloudWatch 読み合計 | 250,793,018,040 バイト |
| CloudWatch 書き合計 | 2,057,315,052 バイト |
| 読み+書き ÷ 2³⁰ | **235.485 GiB** |
| 上の式での費用 ÷ 2³⁰ | **$9.4769** |
| **Cost Explorer の実費** | **235.2056 / $9.4655**（`Estimated=true`） |

**数量で +0.119%、費用で +0.120%。** 同じ 分子（読み+書き）・同じ窓・分単位で揃えると、
CloudWatch と CE は **0.12% で一致する**。1 GB = 10⁹ とみなすと 252.85 で +7.5% ずれるので、
**AWS は GiB（2³⁰）で課金している**と読むのが整合的である。

⚠️ **初稿と 2 稿目はどちらもここを外していた。** 初稿は「`MeteredIOBytes` と一致した」と書き、
2 稿目は **CloudWatch の「読みだけ」を CE の「読み+書き合計」と比べて** 5.7% / 1.5% と

### スループットモード変更の 24 時間制限（正確な形）

AWS の記述は「モード変更は 24 時間に 1 回」ではない。EFS ユーザーガイド
"Restrictions on switching throughput and changing provisioned amount" は、**provisioned へ
切り替えた後、または provisioned の量を変更した後**、24 時間のあいだ次の 2 つが禁止される、と
書いている:

- provisioned から elastic / bursting へ戻すこと
- **provisioned の量を下げること**

🔥 **上げることは制限されていない。** したがって provisioned を選んだ場合の危険は非対称である
——足りなければ即座に上げられるが、多すぎた分は 24 時間下げられず、elastic へも戻れない。
「値をケチると当日やり直せない」という懸念は、正確には「**戻れない**」であって「上げられない」
ではない。

### 上限に当たったと分かる指標

provisioned を採るなら、この 2 つを一緒に見ること:

- **`PermittedThroughput`**（Average）が provisioned した値そのものに張り付く。elastic の
  いまは 5,400 MB/s を返している（実測）ので、値そのものが切り替わりの確認にもなる。
- **`MeteredIOBytes`** が `PermittedThroughput` と同じ高さで**平らになる**。09-16 の
  bursting 枯渇時がまさにこれで、`PermittedThroughput` は 10:00〜11:45 JST のあいだ
  **1.049 MB/s（＝1 MiB/s の最低保証）にきっかり張り付いていた**。**平らな線は需要ではなく
  上限である**。需要は解放してみるまで分からない（解放直後に 1.35 → 19.5 MiB/s へ跳ねた）。
- `BurstCreditBalance` は elastic では発行されない。provisioned では再び現れる。

## 決定

### 決定 1: 暫定は「elastic のまま据え置く」。provisioned は買わない

⚠️ **費用だけを見れば provisioned 16 MiB/s（$116/月）は elastic（約 $142/月）より安く、
20 MiB/s（$145/月）ならほぼ同額で 1.30〜1.67 倍の余裕が買える。** 初稿は逆を書いていた。
それでも据え置きを推す理由は 3 つある。

1. **買うべき高さが実測で分かっていない。** 上限は推定ピーク（12〜15 MiB/s・シナリオ推定）に
   対して置くことになるが、その推定は中央値の改善率をピークに当てたもので、1 分値では
   数秒のバーストも見えない。**推定したピークに対して天井を買う**のは、09-16 に起きたことの
   構造そのものである。しかも安いほうの 16 MiB/s は、その推定ピークに対して余裕が
   **1.04〜1.33 倍**しかない（上側の需要推定に対して 4%）——**安さは余裕を削って買っている**。
2. **壊れ方が質的に違う。** elastic の超過は請求で出る。provisioned の超過は**停止**で出る——
   しかも上限に当たった EFS は「少し遅い」ではない。09-16 の実測がそれで、1 MiB/s へ落ちた
   瞬間に 2.4 KB の `openat` が 5.3 秒になった。
3. **恒久対策は elastic だけを安くする。** 決定 4・5 が狙う 4〜8 倍減がそのまま請求に効いて
   $17〜38/月になるのに対し、provisioned は固定費なので 1 ドルも下がらない。**帯域の買い方を
   変えても 108 リクエスト/秒は 1 つも減らない。**

つまりこれは「安いほうを採る」ではなく「**実測が揃うまで天井を買わない**」という決定である。
決定 4・5 を入れて測り直した時点で、この判断は改めて見直す価値がある——そのときは需要が
下がっているので、provisioned はさらに小さく買えるか、不要になっている。

利用者が固定費の予測可能性を優先して provisioned を選ぶ場合の推奨値は **24 MiB/s**（$172.80/月）
とする。根拠は「推定ピーク 12.00〜15.33 MiB/s の 1.57〜2.00 倍」である。⚠️ 初稿はここに「旧 agent の
需要を箱 9 個へ振り直した 22 MiB/s も上回るので、0.21.0 の改善が失われても詰まらない」と
書いていたが、**その保証は撤回する**——ピーク自体が外挿なので、その倍もまた外挿にすぎない
（分母を直した今の外挿では、改善が完全に失われたときの需要は 22.2 MiB/s で 24 をほぼ使い切る）。
足りなければ即日上げられ、下げるのは翌日以降になる。CFN テンプレートの既定値もこの 24 に
合わせてある（決定 2）。

### 決定 2: `10-data.yaml` のスループットモードをパラメータにする（実装済み）

`deploy/aws/ecs/cfn/10-data.yaml:72` は `ThroughputMode: bursting` を直書きしていた。live は
CLI で elastic に変えただけで、`af-ecs-data` スタックは 2026-08-25 から更新されていない。
**次にこのスタックを更新すると、更新内容によっては bursting へ戻り、障害が再発し得る。**
⚠️ 「必ず戻る」ではない——通常の変更セットは新旧**テンプレート**を比べるので、live だけを
CLI で変えた drift はそこに現れない（実状態まで見るのは drift-aware 変更セットのほう）。
だからこそ質が悪い: **いつ戻るかが更新内容次第で、戻っても枯渇するまで何も起きない。**
⚠️ 初稿はここに
「しかも戻すには 24 時間かかる」と書いていたが、上の非対称制限が縛るのは
**provisioned へ切り替えた後／量を変えた後**だけなので、elastic → bursting → elastic は
その制限には当たらない。危ないのは待ち時間ではなく、**モードが黙って変わること自体**である
（クレジットが尽きるまで何も起きないので、気付くのは枯渇したときになる）。

`EfsThroughputMode`（`elastic` / `bursting` / `provisioned`、既定 `elastic`）と
`EfsProvisionedThroughputMibps`（既定 24）をパラメータ化し、資源のすぐ上に何が起きたかを
書いた。既定を `elastic` にしたのは live と一致させるためである
（`aws cloudformation deploy` は既存スタックに無い**新しい**パラメータには
テンプレートの既定値を使う。ここが `bursting` のままなら、パラメータ化そのものが地雷になる）。

### 決定 3: `MeteredIOBytes` に監視を置く

elastic には上限が無い＝暴走は遅さではなく請求として出る。1 か月気付かない、という壊れ方を
塞ぐために、`MeteredIOBytes` の 30 分平均が **8 MB/s** を超えたら鳴るアラームを置く（箱 9 個で
1 箱 0.9 MB/s 相当＝現状の約 1.6 倍）。これは「性能の警報」ではなく「**回帰の警報**」である
——PR #711 の逆をやるコードが入ったときに、請求書ではなくアラームで気付くためのもの。

### 決定 4（恒久・P0）: エージェントの可変状態を EFS から降ろす

`~/.config/agent-fleet` が `keep`（EFS）に載っているのは、`AF_WS_KEEP_DIRS` の粒度が `.config`
というディレクトリ単位だったからにすぎない。`meta.go` のコメントが「home ボリュームにある」と
信じているのは、**そうあるべきだ**という設計意図の記録である。

🔴 **ただし、まるごと降ろしてはいけない。** 同じディレクトリに `secrets.enc` / `secrets.json`
（`internal/secrets/secrets.go:383`）があり、これは Git・Claude OAuth・接続の資格情報ストア
そのものである。`AgentConfigDir()` を素朴に付け替えると**資格情報も一緒に EBS へ降りる**——
ADR 0045 決定 3-6 が正面から禁じていることである。したがって**どちらの案を採るにせよ、
資格情報ストアを明示的に分離して `keep` に残すことが前提条件**になる。

降ろし方は 2 通りあり、この ADR は前提条件つきで **(b) を推す**。

- **(a) keep の対象を狭める**: `.config` の代わりに `.config/opencode` `.config/cursor`
  `.config/acli` …と資格情報を持つものだけを列挙する。CLI が増えるたびに列挙を足す必要があり、
  足し忘れると**ログインが毎回消える**という静かな壊れ方をする。⚠️ 初稿は「entrypoint の 1 行で
  済む」と書いていたが誤り。既存の箱には `~/.config` → `keep` の symlink が既に張られており、
  **その解除と中身の振り分け（資格情報は keep に残し、それ以外を home へ戻す）を伴う**。
- **(b) エージェントの状態を `.config` の外へ出す**: `~/.local/state/agent-fleet`（＝ home /
  EBS）を state ディレクトリとし、`.config/agent-fleet` からの片道移行を entrypoint か Agent の
  起動時に 1 回行う。列挙の維持が要らず、「資格情報は keep、可変状態は home」という線が
  ディレクトリ名として残る。`AF_SESSIONS_DIR` という env による差し替え口は既にある。
  **移行対象から `secrets.*` を明示的に除外し、`secrets.Path()` は `keep` 側を指し続けること。**

⚠️ **移行先にも今と同等の保護が要る。** `~/.config/agent-fleet` は Console のファイルブラウザの
denylist（`fs.go:123`）で守られている。移行先が denylist に入っていなければ、可変状態
（セッション台帳・チャットの作業ディレクトリ・許可待ちの一時状態）が**ブラウザから見えるように
なる**。移行と同じコミットで denylist を足すこと。

⚠️ **トレードオフ**: ecs-ec2 の home は**単一 AZ の EBS 1 本**である（ADR 0045 が `keep` を作った
理由そのもの）。降ろしたものは、その EBS を失えば一緒に失われる——セッション台帳を失うと
セッション一覧が空になる（転写そのものは `CLAUDE_CONFIG_DIR` 側なので残る）。資格情報を失うより
軽い、というのがここでの判断である。**資格情報（`secrets.*`・`~/.ssh`・`.git-credentials`・
`.claude.json`）は EFS に残す**——平文をローカルに残さないという ADR 0045 の線は動かさない。

#### 実装（(b) を採用）

`paths.AgentStateDir()` = `~/.local/state/agent-fleet` を新設し、`AgentConfigDir()` は
`~/.config/agent-fleet` のまま残した。どちらに置くかは、この順で判定する:

1. **資格情報、または資格情報を運び得るもの**は `AgentConfigDir`。`secrets.*` のほか
   `mcp-tenant.json` がこれに当たる——🔥 `user_secret` でないテナント配布の定義は
   **ヘッダと env の「値」ごと届く**（`secrets.go:325` の `UserSecret` のコメントがその理由を
   書いている）ので、素朴に「id しか入っていない」と見なすと資格情報を EBS へ降ろすことになる。
   `chat-mcp/`（会話ごとの `--mcp-config`）も同じ理由で残した（3 ファイル・16 KB で、
   降ろしても I/O の得は無い）。
2. **利用者が与えた設定・利用者が書いたもの**は `AgentConfigDir`（`rtk.json`・`ui-prefs.json`・
   `toolchains.json`・`user-notes*`・`assistants/`・`knowledge/`・`locks.json`・`mcp-optout.json`・
   `chats/`）。`mcp-managed.json` もここに残す——af が他 CLI の設定ファイルへ書いた行を
   消してよい唯一の根拠であり、その設定ファイル自身（`~/.claude.json`・`~/.codex`・
   `~/.config/opencode`）も keep にある。片方だけ失うと**消せない孤児**が残る。
3. **残りは `AgentStateDir`。** セッション名や sid で引くものは全部こちら——台帳が降りた以上、
   台帳より長生きする状態に意味は無い。

移行は Agent 起動時の 1 回（`internal/statemig`、`main.go` のサブコマンド分岐の直後・
他のどの読み出しよりも前）。**中断時にどちらを正とするか**は次の 3 つで決めた:

- **移行先が正。** 既に移行先にあるものは決して上書きしない。書くのは新しいビルドだけなので、
  移行中にフック子プロセスが書いたファイルも含めて、移行先の方が必ず新しい。
- **ディレクトリ単位ではなくファイル単位。** ディレクトリ単位だと、途中で落ちた半分の
  ディレクトリと完了したディレクトリが見分けられず、次回起動が残りを永久に飛ばす。
- **コピーできた元ファイルは消し、完了した entry は移行先の `.migrated-from-config.json` に
  記録する。** 両方とも「移行した後で利用者が消したもの」が復活するのを止めるためにある——
  これが無いと、セッションを削除した次の起動で `.config` 側の残骸からメタが蘇る。

したがって `.config/agent-fleet` 側の残骸は想定内で、次回起動で収束する。

🔴 **symlink は symlink のままコピーする。** チャットの作業ディレクトリは**実物の資格情報を
リンクで借りている**——`chat-claude/.credentials.json` → claude の設定マウント、
`chat-codex/auth.json` → `~/.codex/auth.json`、`chat-wd/agy-*/home/.gemini/.../antigravity-oauth-token`
の 3 本（実測）。辿ってコピーすると**平文の複製が 3 つ home に落ちる**——ADR 0045 決定 3-6 が
禁じているまさにそれで、さらに `reconcileChatCreds` の書き戻し先が誰も読まないファイルになる。

移行先は同じコミットで denylist（`fs.go`）に足した。`statemig.Entries` は allowlist で、
**`paths.AgentStateDir` 経由の店子が `Entries` に無ければ落ちるテスト**（`statemig_drift_test.go`）
を付けてある。逆（denylist 方式）にしなかったのは、足し忘れの向きが違うからである——
allowlist の足し忘れは「1 つの店子が EFS に残る」だが、denylist の足し忘れは
「資格情報や利用者の設定が EBS へ降りる」。`deploy/`（`deploy/aws/ecs/env.sh` が書く）が
その典型で、移すと配備スクリプトが壊れる。

実測（`internal/session/meta_probe_test.go`・strace・メタ 207 件 × 100 回）:
`ListMetas()` 1 回あたり **836 のファイル系システムコールは変わらない**——変わったのは
**その全部が home に落ちること**で、`.config/agent-fleet` に落ちるものは **0** になった
（openat 21,018 / read 41,404 / close 21,017 / getdents64 213、すべて
`.local/state/agent-fleet/sessions/` 配下）。

⚠️ **`chats/`（アシスタントの会話そのもの）は動かしていない。** `ListConvs()` は
`ListMetas()` と同じ形（`ReadDir` ＋ 1 件ずつ `ReadFile`）で、しかも読むのは会話全文である。
ただし**ポーリング頻度を測っていない**し、これは利用者が書いた中身なので、
「EBS を失えば一緒に失われる」を会話に対しても認めるかは別の判断が要る。次の候補。

#### レビューで直した 4 件（移行の壊れ方）

- 🔴 **コピーしていないものを消していた。** `copyEntry` が「移行先に既に在る」と「通常ファイル
  でも symlink でもない（socket / fifo / device）」の両方に同じ戻り値を使っていたため、後者でも
  送り元が消えていた（レビュアーが fifo を置いて実測）。**live なソケットはそのプロセスの
  待ち受けそのもの**なので、今は「触らない・消さない」を第 3 の結果として分け、
  何か 1 つでも残した entry は**完了として記録しない**（`RemoveAll` が区別できないため）。
- 🔴 **symlink であるはずの資格情報が実ファイルのことがある。** `reconcileChatCreds` が在るのは
  「CLI がトークン更新で**リンクを実ファイルに置き換える**」からで、その状態で移行すると
  平文のトークンが home に落ちる（実測）。`auth.json` / `.credentials.json` /
  agy の OAuth トークンは、**実ファイルだったら動かさない**（次のチャットターンの reconcile が
  リンクを張り直す）。
- 🔴 **`af-db` サブコマンドは移行を追い越せる。** `main.go` の分岐は `statemig.Run()` より前に
  return し、`af-db` は**利用者が端末から直接叩く**。レジストリが見つからなければ空として
  読み、空を書き戻すので、移行先に薄い `{"instances":{}}` ができ、「移行先が正」がそれを
  採って**走っている postmaster が孤児になる**（実測）。`af-db` の分岐は自分で
  `statemig.Run()` を呼ぶようにした。フックの経路（tmux が生き残って Agent だけ入れ替わった
  場合）は**あえて直していない**——claude のターンの前に 100 MB のコピーを挟むことになるし、
  症状は 1 イベントの取りこぼしで次のフックが自己修復する。
- **`af-db` の `<engine>-<major>.pass` は平文のパスワードである。** 判定基準①に真正面から
  当たるが、**例外として state 側に置く**——この Workspace の外では何も認証しない。ここで
  生成され、同じボリューム上の datadir を持つ loopback のサーバにしか届かず、
  **そのボリュームを失えば開ける対象ごと失われる**。keep 側に置くと、開ける物より長生きする
  コピーができる。`passPath` にその一文を書いた（無いと次の読み手が①を適用して戻す）。

⚠️ **移行はブートを塞ぐ。** 5,400 ファイル / 113 MB を運び終えるまで Agent は何も serve しない。
レビューの「配備中に全 Workspace が同時にこれをやってバーストクレジットを枯らす」は、
**現在の構成では起きない**——決定 1 で `elastic` に据え置いており、elastic にバーストクレジットは
無い。残るのは初回ブートが延びることだが、**準備完了の失敗が Start を失敗させることは無い**
（`runtime_ecs.go`: 「A readiness failure must still NEVER fail Start」＝構造的に、読む者がいない）
ので、タスクが置き換わり続けるループにはならない。診断できるよう、運ぶものがあるときだけ
開始ログを 1 行出す。

⚠️ claude のフック定義は壊れない（確認済み）。`hooks.go` がコマンド行に埋めるのは
**Agent のバイナリのパスだけ**（`<exe> session-status <state>`）で、状態の置き場は
Agent が実行時に解決する。移行前に書かれたフックはそのまま新しい場所へ書く。

### 決定 5（恒久・P1）: `projects/*` の全掃引を残り 2 箇所で止める

- **`subagentBases()` の miss を、状態表示の経路に限って覚える。** 転写側の「miss を覚えない」
  不変条件は `SessionJSONLExists` → `--resume` / `--session-id` の分岐を守るためのものである。

  🔴 **subagents 側にも危険がある。** 初稿は「偽の『背景エージェント無し』はバッジが数秒
  遅れて点くだけ」と書いていたが誤り。`SubagentSnapshot` / `SubagentReceivedSince`
  （`bg.go:377,395`）も同じ `subagentBases()` を通り、
  `internal/sessionx/session_delivery.go:121` が**誤配送の判定**に使っている——入力を打った
  12 秒後に「そのプロンプトが背景エージェントの転写に入っていないか」を見て、入っていれば
  **再送を止める**（再送すれば同じ割り込みを 2 度エージェントへ撃ち込むことになる）。
  共有の `subagentBases()` に 30 秒の否定キャッシュを入れると、**打った直後に生まれた
  `subagents/` ディレクトリが見えなくなり、この安全確認をすり抜け得る**。

  🔴 **「表示 vs 配送」の二分でも足りない**（2 度目のレビューで判明）。`SubagentBusy` 自身が
  `internal/chatx/chat_report_reconcile.go:388` の `collectReportSignals` からも呼ばれ、
  `busyEvidence()`（:186）が `subagent-busy` を証拠に積んで**完了判定を抑止する**。そして
  `chat_stop_after_turn.go:81` が同じ `collectReportSignals` → `evalReportEvidence` を使い、
  quiet が続けば `stopArmedSession` へ進む。つまり否定キャッシュが busy を隠すと、
  **早期に「完了」を報告する**か、**まだ走っている背景エージェントごとセッションを止める**
  ことになり得る。主転写の `BackgroundAgentsRunning` に捕まらない新規 Workflow のように、
  子転写の鮮度だけが唯一の証拠になる場合がまさにそれである。

  したがって線は「**表示専用 vs 安全判断のすべて**」で引く。安全判断は 3 つ——
  ①配送確認（`session_delivery.go:121`）、②完了報告（`chat_report_reconcile.go`）、
  ③停止の発火（`chat_stop_after_turn.go`）——で、いずれも**実探索しなければならない**。
  実装は 2 つのどちらか: ⒜**表示専用の入口を新設**して否定キャッシュはそこだけに持たせ、
  `SubagentBusy` の既存の意味は変えない、⒝全安全経路に**明示的な迂回**を持たせる。
  ⒜のほうが安全側が既定になるので推す。⒜で差し替える**表示側の呼び出しは 2 箇所**——
  `claude.go:213`（セッション一覧）と `internal/sessionx/session_transcript.go:289`
  （チャットのヘッダ）。⚠️ 「既存の意味は変えない」は**既存の positive な `pathMemo` まで
  やめる意味ではない**（hit は `Lstat` で再検証している）。変えないのは
  「**否定キャッシュで『無い』を決めない**」という一点である。

  受け入れテスト: **miss の直後、TTL の内側で子転写を作り**、表示側にキャッシュが効いていても
  ①誤配送が見逃されない ②完了が早期に報告されない ③armed な停止が発火しない、の 3 つを
  確認する。⚠️ 転写側の memo に同じ変更を当ててはいけない——`jsonl_memo.go` の型コメントが、
  なぜ 2 箇所で二重に防いでいるかを含めて書いてある。
- **プロジェクトディレクトリを cwd から導出する。** claude は cwd をディレクトリ名に符号化する
  （`/home/dev/repos/agent-fleet` → `-home-dev-repos-agent-fleet`）。セッションの `Meta.Dir` は
  Agent が持っているので、`projects/<導出>/<sid>.jsonl` を **1 回 Lstat** して、外れたときだけ
  従来の掃引へ落ちればよい。符号化は非可逆（`.` や `@` も `-` になる）なので、**導出は
  当て推量であって真実ではない**——落ち先を必ず残すこと。
- 転写側の `memoTTL = 60s` は、hit の再探索を 60 秒ごとに full sweep へ戻す。導出が入れば
  再探索自体が安くなるので、この定数は導出の後で見直す。

#### 実装（⒜ を試みて棄却し、否定キャッシュ無しで同じ削減を得た）

🔥 **最初の実装は ⒜（表示専用の入口＋否定キャッシュ 15 秒）だったが、レビューで棄却した。**
線を「表示専用 vs 安全判断のすべて」で引くところまでは正しかったが、**表示だと思っていた
2 箇所のうち 1 箇所が表示ではなかった**——`claude.go` の `WireLive` が入れる
`LiveInfo.BackgroundBusy` は、セッションのワイヤーの `backgroundBusy` として CP まで流れ、
**CP の reaper が判断に使っている**:

```
claude.go WireLive → agents.LiveInfo.BackgroundBusy → sessionx/session.go の sessionWire
  → CP control-plane/session_activity.go の sessionActivity()
     → holdsWorkspace()  … tier2。箱そのものを止めるかどうか
     → tier1Reapable()   … tier1。セッションを halt するかどうか
```

`session_activity.go` のその行のコメント自身が「**reaper がこれを見ていなくて、走っている
背景作業を止めた**」を過去の事故として記録している。つまり否定キャッシュを入れた実装は、
ADR が Agent の中で塞いだ穴を**一層上で開け直していた**——15 秒古い「背景作業なし」で
箱ごと止まり得る。しかも tier2 にはデバウンスが無く、1 回の掃引で足りる。

**採った実装は「見ないで済ませる」のをやめ、「見る場所を 1 つに絞る」に変えたもの。**
claude は子転写のディレクトリを**セッション自身の転写の隣**（cwd から導いた同じ
プロジェクトディレクトリ）に置く。転写の位置は `jsonlPaths` が既に特定して memo 化して
いるので、`subagentBases` はその隣を **`Lstat` 1 回**見るだけでよい——**「無い」という答えも
含めて、毎回ディスクを見て出す**。否定キャッシュは削除した。

- `subagentBases` の起点（アンカー）の規則は**2 巡目のレビューでさらに 1 回直っている**。
  🔥 **「X の存在で Y の不在を断定する」形なので、アンカーが完全でないと偽陰性が出る。**
  実測で 2 つ見つかった:
  - **転写 1 本では足りない。** `Meta.CWD()` は `Subdir` が**ディスクに在るときだけ**
    `Dir/Subdir` を返し、無ければ `Dir` に落ちる（ブランチ切替でフォルダが消える等）。つまり
    同一 sid が 2 つのプロジェクトディレクトリに状態を残し得るのに、`jsonlPaths` は今日の
    cwd が指すほうしか返さない——もう一方の隣で走っている背景エージェントが見えなくなる。
    🔴 **否定キャッシュより悪い**（あれは 15 秒で自己修復したが、これは治らない）。
    `session.CWDCandidatesForUUID` が取り得る cwd を**全部**返し、その全部を見る。
  - **cwd だけをアンカーにしてもいけない。** cwd は「どこで起動したか」であって
    「claude が何をどこに書いたか」ではない。**転写が 1 本も見つからないときは断定せず、
    従来の掃引に落ちる**（この規則を外すと、既存の安全テスト
    `TestSessionReportDeferredWhileSubagentBusy`——背景エージェント実行中は完了報告を
    遅らせる——が赤になる。実際に赤にして確かめた）。
  - 残る前提は「claude はセッションの Meta から導いた cwd で走る」で、ここからは検査できない。
    AF は起動時にそう設定する（`BuildLaunch` が `m.CWD()` を渡す）ので列挙は尽くせるが、
    **前提であることをコメントに書いた**。
- `SubagentBusyDisplay` / `BackgroundWorkDisplay` / `absenceMemo` は**存在しない**。入口は
  `BackgroundWork` 1 つで、3 つの安全判断も表示も同じ新鮮な答えを読む。
- **プロジェクトディレクトリの cwd からの導出**（`project_dir.go`）は転写側にそのまま残る。
  符号化は「英数字以外を全部 `-`」で実機の木で確認済み。**非可逆かつ単射でもない**ので導出は
  当て推量で、`<sid>.jsonl` を 1 回 `Lstat` して確認が取れたときだけ採る——sid は一意なので、
  そこに在れば**それがその session の転写である**ことは確定する。外したら従来の掃引へ落ちる。
  sid から cwd は引けない（sid は UUIDv5(dir|name)）ので `session.CWDForUUID` を新設し、
  **メタの読み書きのついでに** cwd を覚える（追加の I/O 無し）。`Meta.Subdir` があるときは
  claude が実際に走る `CWD()` を返す。
- **`memoTTL = 60s` は据え置き**（見直した結果）。導出後の再探索は実測 2 システムコール。

実測（`internal/agents/claude/bg_probe_test.go`・strace・プロジェクト 39 個・10 回と 110 回の
**傾き**で 1 回あたりを出す＝バイナリ起動と fixture を分母から外す）:

| 経路 | 変更前 | 否定キャッシュ版（棄却） | 採用版 |
|---|---|---|---|
| subagent 探索（背景エージェント無し） | 201 | 表示 0 / 安全 201 | **3**（全経路） |
| 転写の再探索・cwd が既知 | 201 | 2 | **2** |
| 転写の再探索・cwd が不明 | 201 | 201 | 201 |

⚠️ **採用版は棄却版より速く、かつ古びない。** 「安全側は 201 のままが正しい」という当初の
合否基準は、**安全側と表示側を分ける実装を採る場合にのみ**必要だった。分けない実装では
基準そのものが要らなくなり、代わりに要るのは「**否定を覚えていないこと**」の証明である
——`TestAnAgentStartingIsVisibleImmediately`（miss の直後に子転写を作り、次の呼び出しで
即座に見えること）がそれで、陽性対照として `pathMemo` の「miss を覚えない」不変条件を
壊すと赤になることを確認した。

`jsonl_memo.go` の型コメントの「miss は決して覚えない」は、これで**転写側と subagents 側の
両方に効く 1 つの不変条件**になった（否定キャッシュという例外が無くなったため）。

### 決定 6（恒久・P2）: マウントの当て方は「できない」ことを先に確定させた

ECS の `EFSVolumeConfiguration` が持つのは `FileSystemId` / `RootDirectory` /
`TransitEncryption` / `TransitEncryptionPort` / `AuthorizationConfig` だけで、
🔥 **NFS のマウントオプションを渡す口が無い**（aws-sdk-go-v2 の型で確認）。したがって
`actimeo` / `lookupcache` / `nconnect` / `noatime` は、**タスク定義からは指定できない**。

指定したければ道は 1 つしか無い——**EC2 のインスタンス側で自分でマウントし、ホストパスの
ボリュームとして渡す**。ecs-ec2 では `home` が既にその形（`/af-home/<membershipID>/dev` の
ホストバインド）なので、前例はある。

⚠️ 初稿はここに「アクセスポイントの隔離と uid 写像を自前で再現することになる」と書いていたが
**誤り**。efs-utils の mount helper はアクセスポイントをそのまま受け取る:
`mount -t efs -o tls,accesspoint=<fsap-id> <fs-id> <mountpoint>`（EFS UG
"Mounting with EFS access points"）。**隔離も uid 写像も維持したまま、マウントオプションだけを
足せる。** 後回しにする理由は隔離ではなく、次の 3 つである:

- 効き目が**未測定**である。決定 4・5 が「往復の回数そのもの」を削るのに対し、これは
  「1 往復あたりの重さ」と「キャッシュの効き」を変える話で、順番としては後になる。
- transit encryption は stunnel 経由なので、`nconnect` は併用できない（`actimeo` /
  `lookupcache` / `noatime` は当てられる）。
- マウントの所有が CFN のタスク定義から EC2 の user-data へ移る。壊れたときに**箱が起動
  しない**形で出るので、`40-ec2-pool.yaml` 側の試験が要る。

**結論: P2 は決定 4・5 を入れて測り直した後に判断する。** 往復の回数を減らしたあとで
「1 往復あたり」を削る価値が残っているかは、そのとき初めて分かる。

### 決定 7: 採らなかった案

- **provisioned を買う**（決定 1 のとおり。**費用では provisioned が安い**が、天井の高さが
  実測で分かっていないので買わない）。
- **bursting へ戻す**: クレジットが尽きた後の床は 1 MiB/s（AWS の最低保証）で、稼働時間帯の
  需要はその 5〜18 倍ある。ベースラインを需要に届かせるには Standard ストレージを 1 TiB 弱まで
  水増しする必要があり、$368/月。provisioned より高い。
- **EFS をやめて S3 にする**: `~/.gitconfig` や `~/.ssh` は POSIX のファイルとして開かれる。
  S3 を挟むには FUSE か起動時の取り込み／終了時の書き戻しが要り、後者は**箱が SIGKILL された
  ときに資格情報の更新を失う**。`keep` の存在理由（ADR 0045）と正面からぶつかる。
- **EBS だけにする**: 単一 AZ の EBS を失うとログイン情報まで失う。これが `keep` を作った理由
  そのものである。
- **ポーリング間隔を延ばす**: 4 秒を 8 秒にすれば I/O は半分になるが、UI の遅さと引き換えに
  なる。**1 回のポーリングが 800 回のファイル操作をすること自体が異常**なので、頻度ではなく
  1 回の重さを直す。頻度の調整は、重さを直した後に残った分だけを対象にする。

## 実機での検証手順

決定 4・5 を入れた後、次の順で確かめる。⚠️ ベンチが全部緑でも配備の配線は測れていないので、
**必ず CloudWatch の数字で裏を取ること**。

0. **まず A と B の寄与順位を決める**（決定 5 を入れる前に）。本番の箱で
   `/proc/self/mountstats` の差分（`claude` と `keep` それぞれの READDIR / GETATTR /
   OPEN / READ の RPC 数）と、同じ時間帯の VFS 層の操作数を**同時に**採る。
   ⚠️ **RPC の種類だけでは呼び出し元を決められない**（本文の注記）——09-17 12:20 JST の
   20 秒差分で `claude` 側の READDIR RPC が 0 だったことは、B の寄与が小さいことの証明では
   ない（キャッシュから返ってもよく、属性再検証は GETATTR として出る）。**寄与は現時点で
   不明**であり、順位が分からないまま直すと、効かなかったときに何が残っているのか分からない。
1. **単体（`strace`）。** この ADR と同じ形のプローブ——実コードをテストバイナリに固めて
   子として起こし、`strace -c` で数える。⚠️ **表示側と安全側を分けて測ること**（決定 5）:
   ①**表示側**（キャッシュが温まった状態の miss）は 158 → 1 桁に落ちるはず、
   ②**安全側**（配送確認・完了報告・停止発火）は**実探索のままなので 158 のままでよい**——
   ここを 1 桁に要求すると、安全確認を消す実装が「合格」してしまう。
   `ListMetas()` の 836 は **EFS 上では 0** に（home へ移ったので）なることを確認する。
   ⚠️ **`-e trace=file` では足りない**——`read` / `close` はファイル名を取らないので
   その集合に入らず、`ListMetas()` の 836 のうち 624 を取りこぼす。実際に使ったのは
   `-e trace=getdents64,openat,newfstatat,read,close` である。
2. **箱 1 個の床。** 利用者 1 人だけが起動している時間帯を作り、`MetadataIOBytes` の
   **`SampleCount`** を 1 時間見る（推定に頼らず操作回数そのもの）。**107.7 ops/s が出発点。**
   ⚠️ 「1 桁台前半まで落ちるはず」は**未実測の期待値であって合否基準にはできない**——
   A と B の寄与順位がまだ分かっていない（手順 0）以上、どこまで落ちるかは予測できない。
   見るべきは「前後で有意に下がったか」と「下がらなかったときに次にどこを疑うか」で、

3. **稼働時間帯。** 箱の数を `ClientConnections` から数え（1 箱 = 2 接続）、**同じ時計の窓**で

   数字と比べないこと——初稿の「半分」はそれで生まれた。

   **同じ分子（読み+書き）・同じ窓・分単位・GiB 換算**で揃えること——揃えれば 09-16 の窓では
   0.12% まで一致した（揃えないと 6〜8% ずれる）。これは今回の残差であって、将来の一致の

5. **回帰の門番。** 決定 3 のアラームが鳴らないことを 1 週間確認する。

## 未解決の問い

- **`claude` 自身がどれだけ出しているか。** 転写の追記・設定ファイルの stat 反復は
  `CLAUDE_CONFIG_DIR`（EFS）で起きるが、エージェント側と切り分けて測っていない。決定 4・5 の
  後に残った床の正体はここである可能性が高い。切り分けには、claude を子プロセスとして
  `strace` 下で起こす形が使える。
- **Fargate ランタイムはもっと悪い。** `runtime_ecs.go:684` は **`home` ごと EFS に載せている**
  ——`~/repos` の作業コピー全部が EFS になる。本番は ecs-ec2 なので今回の測定には出てこないが、
  同じ測り方をすれば桁が 1 つ違うはずである。この ADR はそこを決めない。
- 🔴 **発生源 A と B のどちらが床の主因か、まだ決まっていない**（これが最大の穴）。
  `/proc/self/mountstats` は本番の箱で一度採れた（上の表）が、**RPC の種類から呼び出し元は
  決められない**ので、あの 20 秒から言えるのは「READDIR RPC は 0、GETATTR が主体、
  **寄与は不明**」までである。**VFS 層の操作数と RPC 数を同時に、床が見えている時間帯に
  採る**まで、この順位は確定しない。決定 5 より決定 4 を先に置いてあるのはそのためである。
- **決定 5 のアンカーは「ディレクトリ」については尽きているが、「セッション id」については
  尽きていない。** `jsonlPaths` は `LiveSID(sid)`（ドリフト追従）で転写を引くのに、
  `subagentBases` は**スロット sid** で `<dir>/<sid>/subagents` を組む。claude が自己再起動で
  自前 id に移ると、転写は見つかるのに隣は空＝断定的な偽陰性になり得る。⚠️ **変更前の掃引も
  同じ木で空を返した**ので回帰ではなく、以前からある穴である。塞ぐには `LiveSID(sid)` を使えば
  よく、非ドリフト時は `LiveSID(sid)==sid` なので通常経路は無変化だが、**ドリフト後に claude が
  子転写をどちらの id の下に置くかを実機で見ていない**ので、測る前に変えてはいけない。
  （2 巡目のレビューで判明。`bg.go` のコメントにも同じことを書いてある。）
- **移行で置いていったトークンの帰結。** 借用中に回転したトークンは旧ボリュームに残り、
  次のチャットターンは移行先にリンクを張り直すだけなので畳み込まれない。使い捨ての

  「一度きりのブートのために chatx へレガシーパスの知識を恒久的に持ち込む」ため採らなかった。
- **NFS の属性キャッシュがどれだけ吸収しているか。** 上の syscall 数は VFS 層の数であって
