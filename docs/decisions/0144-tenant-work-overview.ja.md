## 背景

2〜30 人のテナント（ADR 0111 補遺 5）には、2 人が同じチケットに着手したことも、チームが今日何を動かしているかも、
チケットを誰に引き継ぐかも見る手段がない。1 人のメンバー自身の仕事に要る入力は、いまは揃っている。#3134 が、
すべてのセッションにワークアイテムとプルリクエストへの型付きのリンクを持たせた。この調査が問うのは、CP が*他の*
メンバーに何を、どう見せてよいか、である。いまのツリーにあるものと足りないもの（すべて `051711e1d` で読んだ）は
次のとおり。

1. **リンクはテナント全体で、そのための表にミラーされている。** `session_work_link` は（ワークスペース、セッション、
   プロバイダ、小文字化したキー）ごとに 1 行で、ロール・タイトル・URL、プルリクエストなら最後に見た状態を持つ
   （`control-plane/internal/store/migrations/0118_session_work_link.sql`、`0119_…_state.sql`）。索引は
   `(provider, item_fold)` で、「Control Plane が、全 Agent に尋ねずに、どのセッションがそのアイテムに就いているかを
   言える」ために足された。`ReplaceSessions` はワークスペースのセッションとリンクを 1 つのトランザクションで入れ替え
   （`internal/store/store_session_index.go:59-91`）、`DeleteWorkspace` がそれらを消す。
2. **ミラーの書き手は 3 つで、reaper はその 1 つではない。** ADR 0111 決定 6 は reaper の `GET /sessions` の取得を
   利用枠ボードの取得元とした。reaper は一覧を読むが、そこから残すのは利用枠の観測だけで（`reaper.go:752-759`、
   `limit_board.go:228`）、しかも `tierClocks.anyOn()` が成り立つテナントの稼働中ワークスペースだけである
   （`reaper.go:664`、`:722`）。ミラーを書くのは、ショーバックの使用量サンプラー（`usage.go:216`）、Console の
   一覧ハンドラとその読み取りを共有するイベントストリーム（`workspace_handlers.go:1189`、`events.go:227`）、
   管理者のセッション一覧（`admin_stats.go:181`）である。サンプラーは、テナントのアイドル系機能がどうあれ、稼働中の
   すべてのワークスペースを巡回する。既定で 5 分ごとにオンで（`main.go:532`。`AF_USAGE_SAMPLE_INTERVAL=0` で止まる）、
   Agent が応答したときしか書かないので、遅い Agent や黙った Agent の行は 5 分より古くなる。`mirrorSessions` は
   書き手を読み取りの開始時刻で順序付ける（`session_mirror.go:47`）。`last_seen` は行を INSERT するときの
   `NowTS()` で打たれる（`store_session_index.go:77`）ので、読み取りの開始ではなく、読み取りのあと、DB の待ちのあとの
   時刻である。
3. **ミラーは活動を持たない。** `sessionRows` は `Alive`（`running` | `stopped` として）と `Carried` を残し、
   `sessionWire.State` を捨てる（`workspace_handlers.go:1148-1164`、state は `:880`）。working・回答待ち・idle は、
   生きている Agent の一覧にしかない。縮約の型は利用枠ボードにすでにある。`limitSessionsOf` は状態を残して名前を
   捨てる（`limit_board.go:193`）。
4. **キーは、GitHub と Bitbucket Cloud ではテナント全体で一意だが、Jira では違う。** Issue は、ワークアイテムのキーは
   すでにテナント全体の識別子だと言う。`owner/repo#45` は 1 つのプロバイダの中ではそうである（リンクはプロバイダと
   キーで識別され、Agent は `github` と `bitbucket` のキーをわざと分けている。`links.go:206-213`）。Jira のキー
   `PROJ-12` にはサイトが無く（`jiraKeyRe`、`links.go:95`）、ADR 0061 は、各メンバーが接続する Jira サイトを 1 つ
   自分で選ぶとしている。別々のサイトの 2 人が、別々のチケットに `PROJ-12` を持ちうる。リンクの URL はサイトを決め
   られない。起動アイテムのリンクには URL が無く（`LinksOf`、`links.go:125-131`）、手で入れた URL は https・ホスト・
   userinfo なししか検査されず（`sessionx/session_work_links.go:105-111`）、そのプロバイダとキーを指しているかは
   確かめられない。メンバーが使う Jira サイトは、CP ではなくその Agent の接続にある
   （`workspace/agent/connections_jira.go`）。
5. **キーは無害ではない。** `acme/payroll#45` や `SEC-9` は、非公開のリポジトリや Jira プロジェクトがあること、
   誰かがそれを動かしていることを閲覧者に伝える。ADR 0061 決定 2 は本文を CP に置かない。タイトルは、権限のない閲覧者が
   受け取ってはならないものそのものであり、キーは同じ種類のより小さな開示である。閲覧者がそのアイテムを見てよいかを
   トラッカーに尋ねることは、CP にはできない。トークンは Agent の中にある。したがってキーを見せられる根拠は、閲覧者の
   権限ではなく、公開する人の同意と選んだ公開範囲である（決定 5）。ADR 0111 決定 12 のパスと同じ立場である。
6. **タイトルには、閲覧者ごとの経路がすでにある。** 各メンバーの受信トレイのキャッシュ（`work_item_cache`）は、その
   メンバー自身の認証情報で満たされるので、そこにあるタイトルは、そのメンバーがそのアイテムを読めたことの証拠になる。
   ADR 0061 決定 26・27 は、キャッシュに無い参照を、そのメンバー自身の認証情報でその場で読み、何も保存しない。
7. **セッション名には共有 ACL がある。** `ListSessionSharesByRecipient` に対する `effectivePermission`
   （`session_share.go:401`、`:535`）が、他のメンバーのセッションを見てよいかを決める。ADR 0111 決定 5 と 12 は、
   導出したビューの中のセッションの名前・タイトル・リンクがこれを通ることを求める。
8. **利用枠ボードは、公開範囲と縮約の手本である。** 公開は既定で非公開で、公開範囲（テナント全体、または指定した
   メンバー）と粒度を持ち、1 つの関数がメンバーのデータを閲覧者向けに縮約する（`limitVisibleTo`、`boardEntry`。
   `limit_board.go:360`、`:378`）。非公開のメンバーと未観測のメンバーは同じに見える。テナントの管理者はボードを
   切れ、SSE もエクスポートもそれを運ばない（ADR 0111 補遺 4 と 2026-10-12 の注記）。

問いは、これらのどれを再利用するか、メンバーは何を公開してよいか、何を足すか、である。

## 決定

### 1. 行は、公開しているメンバーの、1 つのセッションの、1 つの駆動リンクである。

概観は「誰がどのチケットを動かしているか」に答える。セッションがアイテムに数えられるのは、*駆動ロール*のリンクを
持つときである。`started`、`created`、`working`（`links.go:21-25`。ADR 0143 決定 1 と同じ定義）。`watching` と
`reviewing` のリンクは P1 では公開しない。チケットを見張っている子は、それを動かしているのではなく、ADR 0111
決定 6 も、状態は自分以外のことを何も言わない、と言っている。駆動リンクのないセッションに行はない。概観は行を
アイテム・メンバー・リポジトリでまとめる（決定 9）。まとまり、レーン、主張は保存しない。

### 2. アイテムは、プロバイダ・サイト・小文字化したキーで識別し、サイト不明の行は混ぜない。

- **サイト**は、GitHub と Bitbucket ではプロバイダのクラウドのホストで、プロバイダが決める。Jira では、*公開する人自身の
  Jira 接続*のサイトで、Agent がリンクを作るときにリンクへ記録する。Agent はいまそのような欄を書かない（事実 4）ので、
  書くようになるまで（パート 4）、Jira のサイトはすべて*不明*である。**リンクの URL はサイトの取得元ではない。** 任意で、
  起動アイテムには無く、キーに対して検証もされていない。
- 2 つの行が同じアイテムになるのは、プロバイダ・小文字化したキー・*分かっている*サイトがすべて等しいときだけである。
  サイトが不明な行は、それだけで 1 つのまとまりになり、ほかのどの行とも（別の不明な行とも）混ぜず、捨てもしない。
  Console はその行に「サイト不明」と出す。誤って混ぜると「2 人が同じチケットに就いている」と読め、2 人は別の
  チケットの話をしに行く。ヒントが無いより悪い。
- したがってパート 1〜3 では、概観は Jira の行をメンバーごと・プロジェクトごとに見せるだけで、Jira のメンバーをまたぐ
  まとまりもヒントも出さない。GitHub と Bitbucket にはどちらもある。パート 4 で、Agent のリンクに追加の欄 `site` を
  1 つ足す。値は Agent 自身の Jira 接続から取り、URL からは決して取らない。
- 同意（決定 5）はサイトを使わない。同意が覆うのは公開する人自身のチケットで、どのサイトにあるかは問わない。

### 3. 取得元はセッションのミラーである。新しい取得も、新しいプッシュ経路もない。

- Agent から CP へのプッシュを退けた ADR 0111 の判断は保たれる。パート 1〜3 は Agent に何も足さない。Jira のメンバー
  をまたぐまとまりだけが、追加のリンクの欄を 1 つ要る（決定 2、パート 4）。
- ミラーに**追加の列を 2 つ**足し、いまと同じ書き手を通して書く（事実 2）:
  - `activity`。`sessionRows` が `sessionWire.State` から書く。`working`・`waiting`・`idle`・`unknown` のどれか
    （決定 4）。
  - `observed_at`。その書き込みの元になった読み取りの開始時刻で、`mirrorSessions` がすでに持つ `readStart` を
    `ReplaceSessions` に渡す。`last_seen` は INSERT 時に打たれて観測より遅くなりうるので、ほかの読み手のためにそのまま
    残す。移行前に書かれた行は `observed_at` が空で、次の入れ替え（1 回の更新後）まで射影しない。

  移行は既定値付きの列を足すだけで何も落とさず書き換えないので、`0119` と同じ形で出荷できる。入れ替えはすべての
  書き手ですでに走っており、これが足すのは行ごとのバインド値 2 つで、書き込みは増えない。
- **reaper は取得元ではない**（事実 2）。取得元は、サンプラー、Console の一覧の読み取り、管理者の一覧である。5 分は
  サンプラーの既定の試行間隔であって約束ではない。読み取りに失敗すれば行はそのまま残る。サンプラーが止まっていても、
  あとの 2 つがワークスペースを更新し、どの行も自分の古さを言う（決定 8）。
- **止まったワークスペースは、行からではなく射影のときに判定する。** ワークスペースの記録された状態
  （`store.Workspace.State`）が running でなければ、そのワークスペースのすべての行は、最後の読み取りで見た活動に
  かかわらず `stopped` と射影し、`observed_at` は最後の読み取りのままで、停止では動かさない。停止の直前のミラーで
  `working` だったセッションは、したがって `stopped` と読める。削除されたワークスペースに行はない。パート 1 で、
  記録された状態が停止時に最新になっていることを確かめ、この場合をテストする。

### 4. メンバーが公開するものを、項目ごとに。これ以外は出さない。

| 項目 | 取得元 | 備考 |
|---|---|---|
| メンバー | メンバーシップ | テナントの名簿にすでに出ている |
| プロバイダ・キー・サイト | リンク（決定 2） | キーは、メンバーが許可した名前空間のものだけ公開する（決定 5）。Jira のサイトはパート 4 まで不明 |
| ロール | リンク | 3 つの駆動ロールのどれか |
| `activity` | ミラーの列 | `working`（working、compacting）、`waiting`（question、plan、permission、blocked、auth）、`idle`（idle、limited、spend_limit）、`unknown`。セッションが生きていない、またはそのワークスペースが running でなければ `stopped`（決定 3）。*state* の粒度だけ |
| `observedAt` | 行の `observed_at` | *state* の粒度だけ（決定 5） |
| `current` | 導出: `observed_at` が 60 分以内 | *tickets* の粒度で、時刻の形をした唯一の欄 |
| PR の番号と状態 | PR リンクのキーと `state` | P3。#5052 が状態に観測時刻を与えたあと |

粒度にかかわらず、公開しないもの:

- **セッションの名前・タイトル・ラベル・ディレクトリ・ブランチ・kind・モデル・起点。** 名前が出るのは共有 ACL を
  通ったときだけである（決定 7）。
- **アイテムのタイトルと URL。** CP の `title` と `url` の列は持ち主自身の Console のためにあり、射影には含めない
  （決定 6）。
- **セッションが何を待っているか。** `waiting` に質問の本文・ツール・許可の種類は付かない。`limited` と
  `spend_limit` は `idle` と読ませる。利用枠ボードが「状態を既定で見せる」案を退けたとおり、閲覧者に課金の
  問題を知らせてはならない。
- **`carried` のやりとり、会話、変更ファイル、チェック名、レビュアー名。**

### 5. 公開は opt-in で、テナントのメンバーシップごとに、公開範囲・粒度・名前空間ごとの同意を持つ。

これは ADR 0111 決定 6 の規則を新しい中身に当てたものである。利用枠ボードの公開範囲は、決定 12 が編集の重なりに
ついて言うのと同じく、これを含意しない。

- **選ぶまで非公開。** 公開の行が無ければ、そのメンバーは誰の概観にも行を持たない。
- **公開範囲:** テナント全体、または指定したメンバー。設定はテナントのメンバーシップごとに 1 つ（補遺 3）。あるテナントに
  公開したものは、別のテナントには届かない。
- **粒度:** `tickets`（誰がどのアイテムに就いているか。`current` だけ）か `state`（`activity` と `observedAt` を
  足す）。opt-in 時の既定は `tickets`。行の時刻は勤務時間の手がかりなので、前提でなく粒度にする。Issue #3136 は
  すべての行に `observedAt` を求めており、`tickets` はそこからわざと外れる。ただし時刻と無縁ではない。ワークスペースが
  応答するかぎり行は `current` のままで、`current` が外れるのを見ていた閲覧者は、ポーリング間隔の範囲で、
  ワークスペースが応答しなくなった時刻を知る。プレビューにそう書く（「閲覧者はあなたのワークスペースが止まる時刻を
  見られます」）。未決の問い 7。
- **名前空間ごとの同意。** 名前空間は、GitHub と Bitbucket では `owner/repo`（プロバイダごと）、Jira では
  プロジェクトキーである。キーが公開されるのは、その名前空間がメンバーの一覧に入っているときだけである。メンバーが opt-in
  するとき、Console はいまセッションがリンクしている名前空間を並べ、閲覧者に何が見えるかの平易なプレビュー
  （決定 6 と同じ関数を、選んだ閲覧者で走らせたもの）を添え、メンバーが公開するものにチェックを入れる。あとから現れた
  名前空間は、メンバーが決めるまで公開されない。設定画面に「新しいプロジェクトが N 件待っています」と出す。これは
  決定 12 の「メンバーとリポジトリごとの 2 つの同意」であり、既定で非公開リポジトリの名前が流れない理由である。
- **キーは、閲覧者のトラッカーの権限ではなく、この同意に基づいて開示する。** 閲覧者の権限は確かめようがない
  （事実 5）ので、許可した名前空間のキー `acme/payroll#45` は、公開範囲の全員が、開けるかどうかにかかわらず見る。
  プレビューは「<公開範囲>の全員が、これらのキーを、開けるかどうかにかかわらず見ます」と言う。この立場をオーナーに
  確かめるのが未決の問い 6。
- **セッションを個別に隠せる。** 名前空間の設定にかかわらず、そのセッションの行を他のメンバーのビューから消す旗を
  1 つ（持ち主本人には見える）。話題にしてはならないチケット（セキュリティインシデントや人事の件）のためである。
  最初のパートに要るかは、未決の問い 2。
- **テナントのスイッチ。** 管理者はテナントの概観を切れる。既定はオンで、利用枠ボードと同じ（補遺 4）。**管理者に
  広い表示は与えない。** 管理者も他と同じ閲覧者であり、管理画面（docs/67、docs/83）に「誰が何を動かしているか」の
  列は増えない。Issue の最初の問いへの答えで、ADR 0111 が出した答えのままである。
- **優先順位。** メンバー M の行を閲覧者 V が読むとき、最初に当てはまるものが勝つ:
  1. テナントのスイッチが切れている: V 自身の行も含め、全員に空のビュー。
  2. V が M 本人: M のすべての行。すべての名前空間、隠したセッションも含め、`state` の粒度で。
  3. M に公開が無い、または V が M の公開範囲に入っていない: 空のビュー。
  4. それ以外: 名前空間が許可され、セッションが隠されておらず、地平（決定 8）の内にある行だけを見せる。
- **同意の取り消しは次の読み取りで効き、行だけでなく、そこから導いたものすべてに及ぶ。** セッションを隠す、名前空間を
  外す、閲覧者を外す、公開をやめる、のどれも、行・まとまり・ヒント（決定 9）を閲覧者の次の応答から消す。それらは
  射影した行から計算するからである。公開をやめると、公開・名前空間・閲覧者・隠した旗がまとめて消える。再び公開する
  ときは何も無いところから始め、プレビューをあらためて見せる。これらはすべてサーバーが強制し、パート 2 の設定画面は
  同じ記録を編集するだけである。

### 6. メンバーの行を閲覧者向けに縮約する関数は 1 つで、残りは Console に届かない。

- `overviewEntry(publication, found, viewerMembershipID, rows, now)` が、他のメンバーの行を縮約する唯一の場所で、
  `boardEntry` と同じ書き方にする。閲覧者が公開範囲に入っていなければ、ほかを何も読まずに空のビューを返す。
  **非公開のメンバー、一度も公開していないメンバー、許可した名前空間に何も無いメンバーは、すべてこの空のビューと
  同じに見える。** 閲覧者はそれらを見分けられない。（テナントのスイッチが切れているときは、全員に同じビューになる。
  決定 5。）
- **メンバーは自分の行を、決定 5 の優先順位で見る。** 公開は要らず、スイッチは依然として勝つ。公開する人のプレビューは、
  この関数を別のメンバーを閲覧者にして走らせたものである。
- **射影から、タイトル・URL・セッション名は CP の外に出ない。** Console は、公開されたアイテムを、決定 2 の識別子で、
  すでに持つものと突き合わせる。
  1. 自分の受信トレイのキャッシュ。閲覧者自身が読めたアイテムとそのタイトル・URL がある。
  2. ADR 0061 決定 26・27 の押して読む操作。閲覧者自身の認証情報で参照をその場で読み、何も保存せず、閲覧者の
     ワークスペースが動いているときだけ使える。
  3. どちらも無ければ、キーだけ。
  権限の確認は、閲覧者自身のトークンによるトラッカーのものであり、CP のものでも公開する人のものでもない。
  **Jira の行を突き合わせるのは、サイトが分かっていて、閲覧者自身の接続のサイトと等しいときだけである。** そうしないと、
  キーだけの `PROJ-12` が、閲覧者のサイトの別のチケットのタイトルを拾う。パート 1〜3 では Jira のサイトはすべて不明
  なので、Jira の行はキーだけを出し、押して読む操作も出さない。代償は、多くの行がキーだけになることである。それは
  受け入れる。「CP はあなたがこれを見てよいか知らない」という事実を、そのまま見せる形でもある。
- **履歴はない。** 射影はミラーをいまある姿で読む。誰がどのアイテムに就いていたかのログも、「先週」のビューもない
  （決定 10）。
- **有界。上限は射影のあとにかける。** 1 回の要求が返すのは最大 500 行である。上限が数えるのは閲覧者が見てよい行だけ
  （決定 5 の公開範囲・名前空間・非表示・地平の規則のあと）で、固定の順（`observed_at` の降順、次にメンバー・
  セッション・キー）に並べ、見える行を切ったときだけ `truncated: true` にする。まとまりとヒントは、返す行から計算する。
  したがって、隠した行や期限切れの行が、見える行を押し出したり `truncated` を変えたりすることはない。ミラーは
  1 セッションのリンクを 51 件に抑え（`SessionLinksFromJSON`）、テナントは 2〜30 人なので、この上限は歯止めであり、
  チームが届く限界ではない。

### 7. セッションの名前とリンクは共有 ACL に従い、概観は何も与えない。

行がセッションへの不透明な参照を持つのは、閲覧者がその（ワークスペース、セッション）のカタログ項目に対して
`effectivePermission` ですでにアクセスを持つときだけである。そのとき Console は、既存の共有セッションの経路で名前と
「開く」操作を出す。アクセスがなければ、行は「<メンバー>のセッション」と言うだけで、そのセッションを特定するものは
何も運ばない。概観は共有を作らず、広げず、含意しない（ADR 0111 決定 5）。ACL は読むたびに評価するので、共有を解いた
セッションは次の読み取りで匿名の形に戻る。

### 8. 古さを隠さない: 3 つの時刻と、1 つの地平。

- **`observedAt` はミラーの `observed_at`**（決定 3）: CP がこのワークスペースの一覧の読み取りを始めた時刻で、
  セッションが最後に何かをした時刻ではない。止まったワークスペースは最後に読んだ時刻を保ち、その行は `stopped` と
  読める。
- **60 分で古い**（利用枠ボードのしきい値、補遺 6）。古い行は一覧に残って印が付き、`state` の粒度では「N 分前に確認」、
  `tickets` の粒度では「最新ではありません」と出る。**古い行はヒントに数えない**（決定 9）。1 つのチケットに 2 人が
  リンクしていて、片方が 1 時間前の観測なら、それは「1 つのチケットに 2 人」ではない。
- **観測の古さに 7 日の地平。** `observed_at` がそれより古い行は、そもそも射影しない。そうしないと、1 か月前に止まった
  ワークスペースのメンバーが、チケットに居続ける。これは、誰かが作業をやめたという判断ではない。稼働中のワークスペースは
  更新され続けるので、その中の忘れられたセッションは `idle` として一覧に残り、概観は放棄を推測しない。チケットを
  置いたメンバーは、セッションを隠すかリンクを外して、そう伝える。7 は、データなしで選んだ最初の数字である。
  ADR 0143 の未決の問い 5 も、しきい値について同じことを言う。未決の問い 3。
- **古さは、行の並びを決めず、行をグループ間で動かさない。**（決定 6 の上限の順だけが例外で、どの行を切るかを決める
  だけである。）

### 9. ビューは 3 つ、ヒントは 1 つ、「いない」とは言わない。

- **チケット別**（「PROJ-123 には誰がいるか」）、**メンバー別**、**リポジトリ別**（決定 5 の名前空間）。
- **「1 つのチケットに 2 人」** は、同じアイテム（決定 2、サイトが分かっているもの）の最新（古くない）の駆動行が、
  *異なるメンバー*のもので 2 つ以上、返す行にあるときに出す。閲覧者が見てよい行だけから導き、ほかからは導かないので、
  閲覧者の公開範囲が覆わないセッションを明かすことはない。1 人のメンバーの 2 つのセッション（親とその子。
  ADR 0073）も、サイトが不明な 2 つの Jira の行も、ヒントではない。
- **概観は「ほかに誰もこれをやっていない」とは決して言わない。** 公開していないメンバー、隠したセッション、古い行、
  見張り、リンクを一度も記録しなかったセッションは、すべて概観から欠ける。空のまとまりは「ここに*表示されている*人は
  いない」と読ませる。名前はヒントであって、ロックでも衝突でもない（決定 12 の「重なりが無いとは言わない」）。
- **順位付けも、1 人あたりのチケット数も、チケットごとの所要時間もない。** メンバーの順位付けは、ADR 0111 決定 6
  が利用枠で退けたもので、同じ理由でここでも退ける。
- 起動時の注意喚起（ADR 0061 決定 9 の二重起動の防止、「B さんがこのチケットに就いています」）は、あとで同じ射影を
  使える。この調査の対象ではない。

### 10. 保持: ミラーより長くは持たず、ミラーにはすでに終わりがある。

Issue の 2 つ目の問いへの答えである。

| もの | 終わるとき |
|---|---|
| 行 | Agent がそのセッションやリンクを一覧に出さなくなったとき（次の入れ替えで消える）、または地平を過ぎたとき |
| 止まったワークスペースの行 | 最後に動いた時点のまま `stopped` と射影され、地平（決定 8）を過ぎるとすべての射影から外れる |
| 削除またはアーカイブしたセッション | 次の Agent の一覧にそれが無いとき |
| 削除したワークスペース | `DeleteWorkspace` がリンクごと消す |
| 公開、名前空間の一覧、閲覧者、隠した旗 | メンバーシップが外れたとき、またはメンバーが公開をやめたとき。4 つはまとめて消え、ミラーは（本人自身のデータなので）残る |
| 外した閲覧者 | 公開範囲の行が消え、次の読み取りは空のビューになる |

過去の行の表はないので、「先月 PROJ-123 を誰がやったか」にここでは答えがない。履歴は勤務時間のログになり、
それ自身の同意と ADR が要る。

### 11. 新しい ADR であり、ADR 0111 のフェーズではなく、Console 側の導出でもない。

- ADR 0111 の P2 が挙げる `workItem` / `pr` の*添付*は、受信トレイのメッセージがアイテムを引くもので、別のものである。
  これは、多くの人が読む常設の公開であり、0111 が別の ADR に回した決定 12 の公開範囲のモデルを要る。この ADR が、
  チケットについてのその ADR である。0111 は何も改めない。承認されたら、0111 の Follow-ups の行にこれへの
  ポインタを足す。
- ADR 0143 は、メンバー自身のデータから Console でレーンを導く。他のメンバーのデータは、外に出る前にサーバーで
  縮約しなければならない（決定 6 と 0111 決定 12）。両者が共有するのは語彙（駆動ロール、PR の状態）であって
  コードではない。テナントのカードが集計に 0143 のレーンを要するときは、レーンの規則を表として受け取り、import は
  しない。
- 配信は、ビューを開いている間の REST の読み取りである。P1 では SSE もエクスポートの経路もこれを運ばない。そういう
  経路を作るなら `overviewEntry` を通す。

## フェーズ

各パートは、それだけで `main` を出荷できる状態に保ち、新しい振る舞いは届かないか非公開にする。

1. **パート 1、バックエンド。** `activity` と `observed_at` の列とその書き手。公開・名前空間・閲覧者・隠したセッションの
   表と、決定 5 のサーバー側の強制。`overviewEntry`。テナントのスイッチの背後の REST の読み取りと公開のルート。
   Console にはまだ何も出ず、誰も公開していないので、読み取りは呼び出した本人の行を返し、他の誰の行も返さない。下の
   「受け入れ」のテスト。
2. **パート 2、メンバー側。** 設定: opt-in、公開範囲、粒度、プレビュー付きの名前空間の一覧、セッションごとの非表示。
   パート 1 がすでに強制している記録を編集する。
3. **パート 3、閲覧側。** 3 つのビュー、ヒント、決定 6 のタイトルの突き合わせ。PR のチップは、#5052（事実とその観測
   時刻）と #5053（持っている PR の観測）を待つ。マージ済みの PR が open と読めないようにするためである。
4. **パート 4、Jira のサイト。** Agent のリンクに追加の欄 `site` を足し（自分の Jira 接続から取る）、
   `session_work_link` にミラーする。そのとき初めて、Jira の行がメンバーをまたいでまとまり、タイトルを突き合わせる。

### 受け入れ（パート 1）

- 非公開のメンバー、一度も公開していないメンバー、公開範囲の外の閲覧者、切れたテナントのスイッチ、空の名前空間の
  一覧は、バイト単位で同じ応答を返す。
- 種を入れたセッションのタイトル・URL・セッション名・ラベル・ディレクトリ・ブランチ・kind・`carried` のそれぞれに
  置いた目印の文字列は、どの粒度でもどの射影にも現れない（利用枠ボードのテストと同じ、ゴールデン）。
- 許可した名前空間の外のキーは現れない。新しい名前空間は、許可するまで現れないままである。
- 決定 5 の優先順位を、1 ケースずつ: テナントのスイッチが切れている（持ち主本人を含め全員に空）。公開の無い持ち主
  （自分の行、すべての名前空間、隠したセッションも）。同じメンバーの別の閲覧者（空）。公開範囲の閲覧者（許可した
  名前空間、隠したセッションは無し）。
- 見える行を 1 つ用意し、次のそれぞれが、その行・そのまとまり・ヒントを閲覧者の*次の*応答から消す: セッションを隠す、
  その名前空間を外す、閲覧者を外す、公開をやめる。公開をやめて再び公開したあとは、あらためて同意するまで何も見えない。
- 外した閲覧者、抜けたメンバー、削除したワークスペースは、次の読み取りから現れなくなる。
- サイトが不明なあいだ、同じキーの Jira の行は決して混ざらない。よくある起動アイテムの行と、同じキーの 2 つ目の不明な行
  も同様で、そのために行を捨てることもない。2 人のメンバーの同じキーの GitHub の行は 1 つのまとまりになる。
- Console のタイトルの突き合わせは、サイトが不明な Jira の行にも、閲覧者の接続とサイトが違う行にも、タイトルを
  付けない。
- `observed_at` は挿入時刻ではなく読み取りの開始時刻である。DB で遅れた書き込みが、行を新しく見せることはない。
  `observed_at` が空の行は射影しない。
- 60 分を過ぎた行には印が付いてヒントに数えず、7 日を過ぎた行は消える。最後のミラーが `working` のままワークスペースが
  止まったときは、古い `observedAt` のまま `stopped` と射影する。
- 上限は射影のあとにかける。見える行がちょうど 500 あるテナントに、隠した行・未許可の行・期限切れの行を足しても、
  返す行も `truncated` もヒントも変わらない。
- `tickets` の応答に `activity` も `observedAt` も無い。`state` の応答に、待っている理由・利用枠の値・セッション名・
  タイトルが無い。
- 閲覧者に共有のないセッションは、セッションへの参照を持たない。共有すると次の読み取りで付き、共有を解くと外れる。
- ヒントは 2 人のメンバーで出て、1 人のメンバーの 2 セッションでは出ず、閲覧者の射影の外の行からは決して出ない。
- 公開範囲に入っていない管理者は、空のビューを受け取る。

## 未決の問い

オーナーが決めるもので、#5057 に集めてある。それぞれ上に推奨がある。

1. **名前空間の同意: 名前空間ごとか、すべて公開して除外するか**（決定 5）。推奨: 名前空間ごと。もう一方は設定が
   簡単だが、メンバーが気づくまで新しい非公開リポジトリの名前が漏れる。
2. **セッションごとの非表示は、パート 1 か、あとか。** 推奨: パート 2 で、設定画面と一緒に。無いと、1 つのチケットを
   隠したいメンバーが、その名前空間ごと外すことになる。
3. **数字**（決定 8）: 古いと見なすまで 60 分、地平まで 7 日。推奨: そのまま出荷し、パート 3 のあとに実際のテナントで
   見る。
4. **ビューを置く場所。** 推奨: 個人の概観ペインの中ではなく、利用枠ボードの置き場の隣の*チーム*ビュー。ADR 0143 の
   ボードが 1 人のメンバーのものに保たれる。
5. **`watching` と `reviewing` はテナントのビューに出すか。** 推奨: この ADR では出さない。
6. **公開する人の同意だけで、トラッカーの権限がないかもしれない閲覧者にキーを見せてよいか**（決定 5）。CP はその権限を
   確かめられない。推奨: よい。ただしプレビューにそう書く。公開範囲はメンバー自身の選択で、名前空間は 1 つずつ許可
   するからである。
7. **`tickets` の粒度の時刻の手がかり**（決定 5）: 閲覧者は、ワークスペースが応答しなくなる時刻を見られる。推奨:
   受け入れ、プレビューにそう書く。代わりに `tickets` から `current` を外すと、1 か月前かもしれない行に印が何も無くなる。

## 退けた案

- **CP からタイトルを公開する。** ミラーが持っており、`SELECT` 1 つで済む。権限のなかった人に、非公開リポジトリや
  Jira プロジェクトのタイトルを送ってしまう。決定 6 は閲覧者の側で突き合わせる。
- **閲覧者がそのアイテムを見てよいかを、CP からトラッカーに尋ねる。** CP はどのメンバーのトラッカーのトークンも
  持たない（ADR 0061 決定 3: Agent が持つ）。足せば、この機能が正当化しない認証情報の経路になる。
- **reaper の取得を取得元にする**（ADR 0111 決定 6 の書き方）。一覧から残すのは利用枠の観測だけで、アイドル系の機能が
  オンでないテナントがすべて抜ける。ミラーは、すでにテナント全体を覆っている。
- **新しい Agent→CP のプッシュ。** ADR 0111 で退けた。要らないことも同じである。ここで提案する Agent の欄は、リンクの
  Jira のサイト 1 つだけ（決定 2）で、CP がすでに読んでいる一覧に乗る。
- **Jira のサイトをリンクの URL から取る。** 起動アイテムには無く、キーに対して検証もされていないので、貼り付けた URL
  が、行を別のサイトのまとまりや同意済みの名前空間に入れてしまいうる。
- **状態を既定で見せる、またはすべての名前空間を既定で公開する。** 前者は ADR 0111 自身が退けた案。後者は、
  セッションが初めてリンクしたとたんに、非公開リポジトリの名前をテナントに書き出す。
- **作業コピーや変更パスでまとめる。** メンバー間のリポジトリの同一性が要るが、`workingCopyId`（持ち主ごと）は
  それを与えない（ADR 0111 決定 12）。アイテムのキーはそれを要らない。
- **`work_item_session` から行を作る。** Console の起動だけを記録し、PR も、子のリンクも、別の場所で始まった
  セッションも持たない（ADR 0143 事実 6）。
- **履歴を残して**「先月これを誰がやったか」に答える。勤務時間のログになる。決定 10。
- **テナント管理者の見える範囲を広げる。** ADR 0111 の答えは「広げない」で、ここでもその理由は変わらない。
- **「衝突」や「取られている」という主張を導く。** データがそれを支えられない（決定 9）。

## 結果

- 他のメンバーの仕事は、メンバーが選んだ範囲、つまり名前空間ごと・公開範囲ごと・粒度ごとにだけ見え、閲覧者は
  「公開しない」という選択と「公開するものが無い」ことを見分けられない。
- 概観の新しさは、使用量サンプラーが最後に成功した読み取り（既定で 5 分ごと）、Console の一覧の読み取り、管理者の
  一覧と同じで、そのことを表示する。一度も公開していないメンバーについては、そのメンバーがあなたのチケットに就いて
  いても空である。
- 閲覧者自身のクエリの外にあるチケットでは、タイトルはたいてい出ない。閲覧者が読めないかもしれないタイトルを決して
  送らない、ことの代償である。
- パート 4 までは、Jira のどの行もサイトが分からないので、2 人が 1 つの Jira チケットに就いていても、それは伝わらない。
  静かに外れるヒントのほうに倒す。
- キーは、そのリポジトリを開けないメンバーも含め、公開範囲の全員に届く（未決の問い 6）。
- ミラーに増えるのは既定値付きの列 2 つで、書き込みは増えない。パート 2 より前には、Agent にも Console にも
  ほかの変更はなく、パート 4 で Agent のリンクの欄が 1 つ増える。
