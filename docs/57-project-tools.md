## 0. なぜ土台を先に立てるか

AF には既に「エージェント横断の設定を AF が面倒を見る」仕組みが 2 軸ある:

| 軸 | 対象 | 書き手 | 例 |
|----|------|--------|----|
| 配布軸 | 各 CLI の **user/global** 設定 | af が**自動で**書く（所有台帳あり） | MCP レジストリの materialize（docs/48）、rtk ブロック（`~/.codex/AGENTS.md` 等） |
| 管理軸 | **作業コピーの中**のプロジェクトスコープ設定 | af は**利用者の明示操作でだけ**代理で書く（所有しない） | docs/56（プロジェクト MCP） |

管理軸は今 1 号機しか無いが、**同じ形の要求が続く**ことがはっきりしている
（プロジェクト指示 / メモリ、リポジトリごとのエージェント設定、…）。1 号機の中に入口・REST・
書き込み規約・整形保存エディタを埋め込むと、2 号機が**入口を新設**し**規約を微妙に変えて**
再実装することになる。**高い部分（整形保存の編集・git 判定・plan/apply）は共通で、
安い部分（各 CLI の綴り方）だけがツール固有**なので、切り方を先に決めておく。

## 1. 「プロジェクト単位ツール」の定義

次を全て満たすものを言う:

1. 対象が **1 つの作業コピー**（`~/repos/<name>`）の中のファイルである。
2. そのファイルは**エージェントが読む**（人間だけが読むファイルは対象外＝ただのエディタで足りる）。
3. **同じ意味の内容が kind ごとに別ファイル・別方言で重複している**（重複していないなら道具は要らない）。
4. ファイルは**コミットされうる**（＝差分・秘密・同僚への影響が設計制約になる）。

3 が本質で、これが「AF が横断で見せる価値」の源泉。1 と 4 が制約の源泉。

## 2. プロジェクトファイル憲章（全ツール共通の規約）

**docs/56 で MCP 向けに決めた規約のうち、対象に依存しないものをここへ引き上げる。**
新しいツールはこの 8 条を満たすことを設計レビューの通過条件にする。

1. **自動契機を作らない。** セッション起動・agent 起動・ポーリング・他機能の副作用から
   プロジェクトファイルを書かない。書くのは**利用者の明示操作 1 回**に対して 1 回だけ。
   docs/48 §8.2 は「af が*自動で*書くのは user/global だけ」と読む。
2. **所有マーカーを置かない・所有台帳を持たない。** 自動で触らないなら不要で、
   コミットされ同僚も読むファイルに AF 固有の痕跡を足す理由が無い。
   **監査証跡は git の差分**が担い、書き込み後は SCM ペインへ誘導する。
   （user スコープの rtk ブロックがマーカー方式なのは、あちらが**自動で**書く配布軸だから。）
3. **読めないファイルは触らない。** 素の JSON / TOML / 期待する形式として解釈できなければ
   エラーで返す。上書きして利用者の内容を整形し直さない。
4. **整形を壊さない編集をする。** 全体を再シリアライズしない。対象エントリのバイト範囲だけを
   差し替え、キー順・字下げ・コメント・末尾改行を保つ。**PR に載る差分をレビュー可能に保つ**のが
   目的で、これを守れない道具は使われない。
5. **0600 に頼らない。** git はモードを `100644` / `100755` しか記録しないので、
   user スコープの安全弁は**原理的に効かない**。秘密の扱いは権限ではなく
   **警告と既定値**（既定では値を書かない）で守る。
6. **秘密の警告は tracked 状態の差で決める。** 「未追跡 / ignored → tracked」だけが
   新たに git 管理下へ入る経路で、そこだけを赤にする。VCS が git でなければ（SVN 等）
   「判定不可」として断定しない。
7. **他の作業コピーに触らない。** 対象は選ばれた 1 つだけ。同じリポジトリの他 worktree は
   列挙も編集もしない（他セッションの机）。worktree のときは
   「コミットするまで他の作業コピーには反映されない」と注記する。
8. **エージェント側のゲートを代行しない。** 承認・trust・enable は利用者の信頼判断で、
   AF が代筆すると AF を経由するだけで判断が省略されたことになる。コマンドを提示して終わる。
   結果表示は「**書いた**」と「**効いている**」を別の行にする。

9. **git の状態を変える操作はコミットしない。** 無視設定への追加（`.git/info/exclude` /
   `.gitignore`）や追跡の解除（`git rm --cached`）まではツールが行ってよいが、**commit は行わない**
   — 利用者が SCM ペインで確認して打つ。ステージした変更はそのまま SCM ペインに現れるので、
   憲章 2（監査は git）と同じ線の上にある。加えて **`--assume-unchanged` /
   `--skip-worktree` は使わない**（「無視できているように見える」だけで、pull やブランチ切り替えで
   分かりにくく壊れる。問題を隠す逃げ道は提示しない）。
   ⚠️ **`.git/info/exclude` は worktree 単位ではない**（common dir にあり親クローンと全 worktree に
   効く・docs/56 §2.4 実測）。憲章 7 と衝突しうる唯一の操作なので、影響範囲を必ず表示する。

加えて、**契約は実測してから書く**（AF 全体の作法）。「同じ形のはず」で kind を増やさない。
測れない kind（ログイン必須・本ホストで起動不可）は**行としては出し、未検証バッジを付ける**
— 黙って一覧から消すと「対応漏れ」に見え、同じ質問が繰り返される。

## 3. 共通の入口 — レポ行 →「プロジェクト」モーダル

1 号機は「プロジェクト MCP」という単独のモーダルとして設計したが、**2 号機以降は
同じモーダルの中のセクションとして生やす**。

```
レポ行（RepoRow.tsx）右クリック → 「プロジェクト設定…」
┌ プロジェクト設定 — novel-lab (main)   [worktree 注記]
│ ┌ 左レール ────┬ 本体 ───────────────────────────
│ │ MCP        ●│  （docs/56 のマトリクスと操作）
│ │ 指示 / メモリ│
│ │ …          │
└─┴─────────────┴────────────────────────────────
```

- 設定モーダル（`SettingsDialog.tsx`）の**左レール作法をそのまま借りる**（docs/48 §11 /
  設定モーダル IA と同型）。ただし**別のモーダル**にする: あちらは workspace 全体＝user スコープの
  場所で、混ぜると「いまどちらのスコープを触っているか」が画面から消える。
- レールの各項目は「その作業コピーに関係するか」で出し分けず、**常に出して状態を書く**
  （「このリポジトリには設定がありません」）。無いものが消えると、無いのか未対応なのか分からない。
- **ワークスペース稼働ゲート必須**（停止中は「設定ゼロ」に見える）。
- i18n（ja/en 両方・裸和文 lint）、キーボード操作体系（docs/29）、既存モーダル作法
  （`useDismiss` / `useMenuRoving` / focus trap）に従う。
- 各ツールは設定モーダル側に**注記 1 行**を置いて導線を繋ぐ（利用者は user スコープの
  タブを先に探しに来るため、行き止まりにしない）。

## 4. 共通の REST 規約

プロジェクトファイルはコンテナ内のファイルなので **Agent 側だけ**で閉じる（CP は DB を持たない）。
ツール `<t>` は次の 3 本だけを持つ:

| メソッド | パス | 役割 |
|---------|------|------|
| GET | `/repos/{name}/<t>` | スナップショット（値はマスク） |
| POST | `/repos/{name}/<t>/plan` | 操作列 → 差分＋警告＋`planHash`（**書かない**） |
| POST | `/repos/{name}/<t>/apply` | 操作列＋`planHash` → 実行（不一致なら **409**） |

- **plan / apply の 2 段と `planHash` は必須**。作業コピーは他セッションや利用者のエディタと
  共有されており、read-modify-write の間に人が編集しうる。
- **Console は秘密の実値を受け取らない。** スナップショットは値をマスクして返し、apply は
  `withSecrets` のような**フラグだけ**を受けて、実値は Agent がファイルから読んで書く
  （docs/48 §5.1 を壊さずに「利用者が許可したらコピーする」を実装できる唯一の形）。
- ⚠️ **新 REST は `workspace/agent/routes.go` と `control-plane/routes.go` の両方に登録**する
  （CP は明示許可リスト方式。片方漏れると Console から 404）。
- 拒否理由は **1 理由 = 1 コード**で、Console は `err.<code>` カタログで解決する。

## 5. 共通の Go 土台

```
workspace/agent/internal/projcfg/    ← 共通（新設）
    repo.go       作業コピーの解決・VCS 判定・tracked / ignored 判定（git / svn / 無し）
    plan.go       操作列 → 差分・planHash・楽観ロック
    editjson.go   整形を壊さない JSON 編集（Decoder.InputOffset() でエントリの範囲を取る）
    edittoml.go   同・TOML 行編集（internal/agents/codex/settings.go の作法を一般化）
    editmd.go     同・Markdown セクション編集（2 号機以降で要る見込み）
    secret.go     秘密らしさの検出と tracked 差の警告判定
workspace/agent/internal/mcpproj/    ← 1 号機（docs/56）
workspace/agent/internal/<t>proj/    ← 2 号機以降
```

ツール側が持つのは **kind ごとのファイル名・パーサ・シリアライザ・方言**だけ。
綴り方は既存の配布軸（`mcpreg` など）と**共有する** — 二重定義すれば必ずドリフトする。

型は共有しない。配布軸の型（`mcpreg.ServerDef` など）は「AF が配るもの」の意味論
（`Origin` / `Targets` / 台帳・予約名の**拒否**）を持ち、プロジェクト側は逆に予約名を
**見つけて警告する**のが仕事。同じ型にすると配布集合へ紛れ込み、**user スコープへ配ってしまう**。

## 6. 候補ツールの棚卸し

| # | ツール | 対象ファイル（kind 別） | 状態 |
|---|--------|------------------------|------|
| 1 | **プロジェクト MCP** | `.mcp.json`（claude+copilot） / `opencode.json` / `.codex/config.toml` / `.cursor/mcp.json` / `.kiro/settings/mcp.json` | 設計確定（[56](56-project-mcp.md)） |
| 2 | **プロジェクト指示 / メモリ** | `CLAUDE.md` / `AGENTS.md`（codex・opencode・agy は対話モードのみ＝`agy/rtk.go` 実測） / `.cursor/rules/*.md`（docs/39） / `.kiro/steering/*.md`（docs/39） / `.github/copilot-instructions.md`（**未検証**） | 未設計・要実測 |
| 3 | プロジェクト単位のエージェント設定 | 権限・許可ツール・フック等（kind 別に散在） | 未調査 |

**2 は 1 と同型の問題**（同じ内容が N ファイルに重複し、片方を直すと片方が腐る）だが、
**性質が 2 つ違う**ので設計をそのまま流用できない:

- **形式が Markdown**。JSON/TOML と違い構造化された「エントリ」が無いので、
  同期の単位を何にするか（ファイル全体 / 見出しセクション / マーカーブロック）が最初の判断になる。
  「1 ファイルを正として他を `@CLAUDE.md` 参照にする」など、**コピーしない解**もありうる
  （どの CLI がファイル参照を解決するかは要実測）。
- **秘密が入りにくい代わりに、量が多く差分が大きい**。憲章 4（整形保存）の要求が
  JSON より強く出る。

⚠️ **docs/39 の「メモリ」とは別物**。あちらの版管理対象は **home 側**の
`/var/lib/af/claude/projects/<slug>/memory/`（プロジェクト単位だが置き場はリポジトリ外）と
`~/.codex/memories/` で、**配布軸でも管理軸でもない第 3 の場所**。
「プロジェクト単位のメモリ」を語るときは、**リポジトリの中の指示ファイル**なのか
**home 側のプロジェクト別メモリ**なのかを毎回区別する（混同すると、コミットされる／されないという
最も重い制約を取り違える）。

⚠️ **[60](60-user-instructions.md)（ユーザー指示）とも別物**。あちらは各 CLI の **user/global** 指示位置へ
AF が**自動で**書く**配布軸**なので、本ドキュメントの憲章 8 条（自動契機を作らない・所有マーカーを
置かない）は適用されない。同じ「指示ファイル」という言葉で 3 つ（プロジェクト指示 / ユーザー指示 /
エージェントメモリ）を指しうるので、[60](60-user-instructions.md) §60.16 の対照表で毎回確かめる。

## 7. 共有しないもの（意図的に）

- **同期モデル**。1 号機は純粋なワンショット（正本を記録しない）だが、これはツールごとに
  再判断してよい。ただし継続同期を選ぶなら**憲章 1 の例外**であり、
  「作業ツリーが利用者の操作なしに汚れる」ことの正当化が要る。
- **中間形の型**（§5）。
- **接続テストのような「実行を伴う」機能**。プロジェクトファイル由来のコマンドは
  リポジトリに書かれた任意のコマンドで、AF が起動してよいかは毎回別の判断になる。
